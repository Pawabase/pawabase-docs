Open **Activity** and choose a page in the **Requests** group. Use the time buttons (15 minutes up to 14 days) to widen or narrow the window.

## Routes

**Routes** lists every route your API serves with how many calls it got, how many failed, and how long it took. Sort by errors or by slowness to find what needs attention. Open a route to see:

| Section | What it shows |
| --- | --- |
| **Traffic and failures** | Calls over time and how many succeeded |
| **Slowest requests** | The slowest calls, each one a click away from its trace |
| **What went wrong** | The errors it returned, grouped |
| **Where the time goes** | Time spent in the database, in flows, in other work |

## Requests

**Requests** is the full list. Search by **path** or by an **exact request id**, and filter by status (`404`, or a class like `5xx`).

Every request has a **request id**. It appears on the response (`x-request-id`) and on the events, flow runs and webhook deliveries that call caused, so you can follow one action through everything it set off.

## A request trace

Open any request to see it end to end:

- Who called (which key or user) and from where.
- The access-rule decision, including why a call was refused. See [Debugging rules](/policies/debugging).
- **DB queries** it ran, how many and how long each took.
- **Events and jobs** it started.
- **Flow runs** it triggered.
- **Logs** your flows wrote during it.
- A timing **waterfall** of the steps.

## Find why a call failed

1. In your app, catch the error and read its `requestId`.
2. Open **Activity → Requests** and paste it into the search.
3. Open the trace and read the decision and the steps.

## Errors

**Errors** groups failures by **what went wrong**, so one problem shows up once with a count instead of a thousand times. Open a group to see the requests behind it.

## Locations

**Locations** is a world map of where your requests came from over the window. Each country is shaded by how many requests it sent, from pale for a few to full orange for the busiest. Point at a country to see its requests, its share of the total, its server and client errors and its average time. Very small countries show as a dot when requests came from them. Below the map, every country is ranked in a table.

Click a country, on the map or in the table, to open **Requests** filtered to it. On a phone, tap once to see the numbers and tap again to open the requests.

The headline tiles count the requests that were **placed** in a country and the ones that were **not**: calls from a private network (your own machine, a server on the same network) and addresses the server could not place.

### Where the country comes from

A country is worked out when the request arrives, from the caller's real address. Behind a load balancer that is the address in `X-Forwarded-For`, believed only when the connection comes from a trusted proxy. The server needs one of two sources:

| Setting | What it does |
| --- | --- |
| `PAWABASE_COUNTRY_HEADER` | A header the CDN or load balancer in front writes with the country: `cf-ipcountry` behind Cloudflare, `cloudfront-viewer-country` behind CloudFront, `x-vercel-ip-country` behind Vercel. Read only from a trusted proxy, so a caller cannot set its own country. |
| `PAWABASE_GEOIP_DATABASE` | The path to a country database in `.mmdb` format: MaxMind GeoLite2 Country, DB-IP Country Lite or IPinfo Lite. Used when no header says. Needs the `maxminddb` Python package. |

With neither set, Locations says so and the map stays empty. Requests recorded before a source was set have no country.

## Bandwidth

**Bandwidth** shows the bytes your API received and sent over the window, and the **endpoints, callers and requests that moved the most**, including the largest responses. Headers are not counted, only what the request and response carried. Use it to find a route that sends far more than it should.

## What a request records

| Field | Meaning |
| --- | --- |
| `request_id` | The id, also in the `x-request-id` response header |
| `method`, `path`, `route` | What was called, and the route pattern it matched (`/rest/v1/orders/{id}`) |
| `status` | The status answered |
| `duration_ms` | How long it took |
| `started_at` | When it started |
| `role`, `user` | The key's role (publishable, secret) and the signed-in person, if any |
| `ip`, `user_agent` | Where it came from: the caller's real address (through trusted proxies) and its client |
| `country` | The caller's country as a two-letter code (`NG`, `US`), when the server can tell |
| `error` | The error, for a failed request |
| `bytes_in`, `bytes_out` | What the request and response carried |

## From code

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";
import { manage } from "@pawabase/client/manage";

const m = manage(createClient({ url, project, apiKey: process.env.PAWABASE_SECRET_KEY!, environment }));

const failing = await m.observability.requests({ status: "5xx", search: "/rest/v1/orders", limit: 50 });
const trace = await m.observability.request(requestId);        // logs, database calls, spans, the traceback
const slowest = await m.observability.routes({ minutes: 60, sort: "p95" });
const route = await m.observability.route("GET", "/rest/v1/orders", { minutes: 1440 });
const traffic = await m.observability.bandwidth({ minutes: 60 });
```

```python Python
import os
from pawabase import Pawabase

pb = Pawabase(url, os.environ["PAWABASE_SECRET_KEY"], project=project, environment=env)
o = pb.manage.observability

failing = o.requests(status="5xx", search="/rest/v1/orders", limit=50)
trace = o.request(request_id)
slowest = o.routes(minutes=60, sort="p95")
route = o.route("GET", "/rest/v1/orders", minutes=1440)
traffic = o.bandwidth(minutes=60)
```
</CodeGroup>

| Endpoint | Query |
| --- | --- |
| `GET …/requests` | `request_id`, `method`, `status` (a code like `404` or a class like `5xx`), `search` (part of the path), `country` (a two-letter code), `minutes` (up to 30 days) |
| `GET …/requests/{request_id}` | One request with its trace |
| `GET …/observability/routes` | Per-route traffic, failures and latency |
| `GET …/observability/errors` | Failures grouped by what went wrong |
| `GET …/observability/bandwidth` | Bytes in and out, and the biggest endpoints, callers and requests (`minutes`) |
| `GET …/observability/countries` | Requests per country, with errors and average time, and how many were not placed (`minutes`) |

## Good practice

- Open **Errors** after every release.
- Put the request id in your own error reports and support messages.
- Keep personal data and secrets out of what your flows log.
