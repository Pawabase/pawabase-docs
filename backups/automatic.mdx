Set the schedule once and Pawabase keeps saving backups of the environment. Open **Project → Backups** and click **Schedule**.

## The schedule

| Setting | Meaning | Default |
| --- | --- | --- |
| **Back up automatically** | Turn the schedule on or off | off |
| **How often** | **Hourly**, **Daily** or **Weekly** | Daily |
| **At (UTC hour)** | For daily and weekly backups, the hour it runs, 0 to 23, in **UTC**. Pick a quiet hour for your users. | 3 |
| **On** | For weekly backups, the day: Monday to Sunday | Monday |
| **What to include** | **Definitions**, **Settings**, **Users & access**, **Data** (see [what a backup holds](/backups/overview#what-a-backup-holds)). Empty means everything. | everything |
| **Keep the last** | Keep at most this many scheduled backups; older ones are removed. 0 means no limit by count. Up to 365. | 7 |
| **Keep for (days)** | Remove scheduled backups older than this. 0 means no limit by age. Up to 3,650. | 30 |

Backups are taken by the platform's scheduler, which checks every couple of minutes whether one is due, so a daily backup at 03:00 UTC starts shortly after 03:00. If one was missed while nothing was running, the next check takes it.

### How old backups are removed

A scheduled backup never costs you one you already have. If your plan's backup limit is reached, the oldest unpinned backup is replaced **only after the new one is saved and checked**. If the new one fails, the older ones stay.

After each scheduled backup, Pawabase goes through the **scheduled** backups from newest to oldest and removes any that is **beyond the count** in *Keep the last* **or older than** *Keep for (days)*, whichever applies first. **Pinned** backups and backups you took by hand are never removed by the schedule.

| Keep the last | Keep for | Result with daily backups |
| --- | --- | --- |
| 7 | 30 | The last 7 days |
| 30 | 30 | The last 30 days |
| 0 | 14 | Everything from the last 14 days |
| 24 | 0 | With hourly backups, the last 24 hours |

## Back up now

**Back up now** takes one immediately. Give it:

| Field | Meaning |
| --- | --- |
| **Name** | Something you'll recognise, such as *Before the pricing change* (up to 160 characters) |
| **Note** | Why you took it (up to 1,000 characters) |
| **What to include** | The parts to save; everything by default |

It appears under **Saved backups** next to the scheduled ones.

## Pin a backup

**Pin** a backup to keep it until you unpin or delete it. Pin one before a release, a risky migration, a large import or a restore. You can rename a backup or change its note at any time.

## Backups are checked as they are taken

Every backup is read back right after it is written, the way a restore would read it: it can be opened, its checksums match, and it holds the parts it should. The answer is kept: the **State** column shows **Checked** or **Damaged**, and a backup that could not be read back is **Failed**.

You can check one again later with **Check it again** in its panel (or `POST …/snapshots/{id}/verify`). Do it for a backup you are about to rely on, such as the one you kept before a migration.

## Is it safe to rely on?

The banner at the top of **Backups** reads the situation for you: **On schedule**, **A backup is overdue**, **The last automatic backup failed** or **A backup needs attention**. A schedule counts as overdue when the newest good backup is more than two intervals old (an hour of grace on top). Over the API, `GET …/snapshots` returns the same reading as `health`:

| Field | Meaning |
| --- | --- |
| `status` | `ok`, `off`, `none`, `overdue`, `failing` or `damaged` |
| `message` | The sentence Studio shows |
| `last_good_at`, `age_seconds` | When the newest good backup was taken |
| `next_at` | When the schedule runs next (`null` when it is off) |
| `recent_failures`, `unverified` | Failed backups among the last five, and good ones never checked |

## Hear about every backup

When a backup finishes, the environment emits an event. Use it in a [flow](/logic/overview) or a webhook, for example to email you when one fails.

| Event | When | Payload |
| --- | --- | --- |
| `backup.completed` | A backup was saved and read back whole | `snapshot_id`, `name`, `trigger`, `parts`, `size_bytes` |
| `backup.failed` | It could not be made, or could not be read back | The same, with `error` |

`trigger` is `manual`, `scheduled` or `before-restore`.

## Download a saved backup

**Download** gives you the backup as one file, to keep somewhere else or to restore into another environment or project. A backup can contain password hashes and personal data: store the file as carefully as the database itself.

## From code

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";
import { manage } from "@pawabase/client/manage";

const m = manage(createClient({ url, project, apiKey: process.env.PAWABASE_SECRET_KEY!, environment }));

// the schedule: daily at 03:00 UTC, keep the last 14 and nothing older than 30 days
await m.backups.setSchedule({ enabled: true, frequency: "daily", hour: 3, keepLast: 14, keepDays: 30 });

// back up now, and list what's saved
const snap = await m.backups.snapshot("before-launch", { note: "release 2.0" });
const saved = await m.backups.snapshots();

await m.backups.updateSnapshot(snap.id, { pinned: true });    // pruning keeps pinned backups
await m.backups.verifySnapshot(snap.id);                      // read it back and check it
const file = await m.backups.downloadSnapshot(snap.id);       // the backup's contents
await m.backups.removeSnapshot(oldId);
```

```python Python
import os
from pawabase import Pawabase

pb = Pawabase(url, os.environ["PAWABASE_SECRET_KEY"], project=project, environment=env)
b = pb.manage.backups

b.set_schedule(enabled=True, frequency="daily", hour=3, keep_last=14, keep_days=30)

snap = b.snapshot("before-launch", note="release 2.0")
saved = b.snapshots()

b.update_snapshot(snap["id"], pinned=True)
b.verify_snapshot(snap["id"])
backup_file = b.download_snapshot(snap["id"])
b.remove_snapshot(old_id)
```
</CodeGroup>

`frequency` is `hourly`, `daily` (at `hour`, UTC) or `weekly` (on `weekday`, 0 is Monday). Backups beyond `keepLast` / `keep_last` or older than `keepDays` / `keep_days` are removed, except pinned ones. `include` limits a backup to some parts: `definitions`, `settings`, `users`, `data`. Restoring is on [Restore](/backups/restore).

| Endpoint | Does |
| --- | --- |
| `GET …/snapshots` | Saved backups, the schedule, and `health` |
| `POST …/snapshots` | Back up now: `name`, `note`, `include` |
| `GET`, `PATCH`, `DELETE …/snapshots/{id}` | Read, rename or re-note or pin (`pinned`), delete |
| `POST …/snapshots/{id}/verify` | Read it back and check it. The answer is kept on the backup (`verified_at`, `verified_ok`, `verify_error`) |
| `GET …/snapshots/{id}/download` | Download it as a file |
| `POST …/snapshots/{id}/restore` | Restore it (see [Restore](/backups/restore)) |
| `PUT …/backup-schedule` | Set the schedule |

## A sensible plan

- **Daily** automatic backups of everything, keeping the last 14 to 30.
- **Hourly** backups for environments with frequent important changes, keeping the last 24 to 48.
- **A pinned backup** before every release or risky change.
- **A download** of an important backup kept outside Pawabase.
- **A test restore** into a non-production environment every quarter. A backup you've never restored is a hope, not a backup.

If you only need to protect definitions, untick **Data** to keep backups small and quick.
