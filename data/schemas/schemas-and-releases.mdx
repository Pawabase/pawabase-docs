A release serves an API version from a snapshot of every definition, and schemas are part of the snapshot. That gives schemas two touchpoints with the release flow, and both were exercised.

**A revision compiles the snapshot, and a broken schema makes the revision invalid.** From **History**, the **Revisions** tab creates a revision of the current definitions. Creating one compiles them, and a dangling reference is recorded on the revision as a problem and marks it `invalid`:

```text
revision 1   status valid     problems []
(delete the Address schema that the people resource references)
revision 2   status invalid   problems ["resource people: field 'home' refers to unknown schema 'Address'"]
```

An invalid revision cannot become a release. Preparing a release from revision 2 was refused with `422`. So a missing schema is caught at the revision step, before it can reach a version that serves clients, which is the safety net the live environment does not have.

**The compatibility check does not read schemas.** A release is compared with the previous one, and breaking changes need an explicit `allow_breaking` acknowledgement, shown in Studio as the checkbox "I acknowledge breaking compatibility findings." The comparison covers resources, their fields and routes. Removing the `nick` field from `people` was reported as breaking and refused with `409` until acknowledged. A revision whose only change was to tighten a constraint inside the `Address` schema was reported as compatible, with no changes listed:

```text
release from a revision that removes a resource field   ->  409  breaking changes require allow_breaking
release from a revision that only tightens a schema     ->  compatible, changes: []
```

The second line is the gap. A tightened schema can make existing rows unreadable on the API version that serves the release, and the release process will not say so. Run the finder queries from the earlier sections against the data before you prepare the release, not after you activate it.

| Stage | Catches | Does not catch |
| --- | --- | --- |
| Saving a schema | Bad names, bad field names and types, duplicate names, an invalid `pattern` | A missing reference, a cycle |
| Creating a revision | A reference to a missing schema, a resource that cannot compile | Rows that no longer fit |
| Preparing a release | A revision with problems, removed fields, retyped fields, new required fields, removed routes | A tightened schema, a removed schema key, changed defaults |
| Serving a request | Nothing new. It compiles lazily and reports problems on **Overview** | A cycle, which fails every request |

Serving a release from an older revision is also the way to keep the previous shape alive. An API version bound to a release uses the schemas that were in that snapshot, so clients on `v1` keep the old `Address` while `v2` uses the new one, over the same tables. The data is shared, so rows written under `v2` have to read under `v1`'s schema as well, or the older version starts returning `500`. See [Releases and API versions](/studio/environments-and-promotion).

### Where releases show up in Studio

The controls live in the **History** sheet. Its tabs are **Branches**, **Releases**, **Revisions**, **API versions** and **Deployments**, and a schema change touches the middle three.

| Tab | What you do | What it shows about a schema change |
| --- | --- | --- |
| **Revisions** | Type a message, placeholder "Snapshot main", and choose **Create revision** | The table lists each revision with its number, branch, **Status** and message. A revision with a missing schema shows an invalid status and does not appear in the **Revision** menu used to prepare a release |
| **Releases** | Choose a **Revision**, an **API version** and a **Release name** (placeholder `v2.0.0`), tick "I acknowledge breaking compatibility findings." if needed, and choose **Prepare release** | The **Prepared releases** table shows each release's **Path** (`/rest/v1`, `/rest/v2`), **Status** and a **Compatibility** badge, green for compatible and red for breaking. A schema change alone does not turn it red |
| **API versions** | Add a version such as `v2` | The version a release is bound to, and so the schemas its clients see |
| **Deployments** | Read the log of activations | Each row has a **Rollback** button, which returns an API version to its previous release and so to the previous schemas |

**Activate** on a prepared release makes the version serve it. Because a rollback restores the snapshot, the old schemas come back with it, and any rows written in the meantime that do not fit them fail to read. The rollback restores definitions and does not rewrite data.

Two small facts about the form are worth stating, because they surprise people the first time. The **Schema** menu on a field has no "none" choice (`allowEmpty` is off), so to clear a reference you remove the field or change its type. And the menu in a route's **Response schema** does have a blank option, since a response schema is optional.


## Reading a `ref` field's JSON by hand

The form writes a small amount of JSON, and being able to read it helps when you review a definition in a pull request or edit it on the **JSON** tab. Each placement of a reference has the same pieces:

```json
{"name": "home", "type": "ref", "schema": "Address", "required": true}
```

```json
{"name": "others", "type": "array", "items": {"type": "ref", "schema": "Address"}}
```

```json
{"name": "billing", "type": "ref", "schema": "Address", "description": "Where invoices are sent"}
```

| Key | Meaning in a reference |
| --- | --- |
| `type` | `"ref"` |
| `schema` | The name of the schema, case-sensitive |
| `required` | The reference itself must be present. It says nothing about the keys inside |
| `nullable` | Whether an explicit `null` is accepted. A required reference rejects `null` unless this is `true` |
| `description`, `example` | Documentation, like any field |
| `default` | Not offered in the form. Set in JSON, it supplies the whole nested value when the key is omitted, and it is not checked against the schema |
| Everything else (`min_length`, `enum`, and so on) | Stored and ignored. Constraints belong to the schema's own fields |

A reference with a default and a required, nullable reference, both run:

```json
{"name": "home", "type": "ref", "schema": "Address", "default": {"city": "Lagos"}}
{"name": "work", "type": "ref", "schema": "Address", "required": true, "nullable": true}
```

```text
POST /rest/v1/p  {"work": {"city": "x"}}   ->  201  {"home": {"city": "Lagos"}, "work": {"city": "x"}}   (home took the default)
POST /rest/v1/p  {"work": null}            ->  201  {"home": {"city": "Lagos"}, "work": null}            (null accepted because of nullable)
POST /rest/v1/p  {}                        ->  422  missing at ["work"]                                    (required, so it must be present)
```

A default on a reference is the one way to give a nested value a starting shape through a schema, since the schema's own field defaults are not applied. It is a whole value, so it replaces the filled-out shape the schema would otherwise produce.

The `schema` value is the only link, and it is just a name. That is why renaming is dangerous and why a typo in it is reported on **Overview** as an unknown schema and never as a validation error on any request.


## Every schema-related message, in one table

| Where it appears | Message or status | Cause |
| --- | --- | --- |
| Saving a schema | `422` pattern error on `name` | The name does not match `^[A-Za-z][A-Za-z0-9_]{0,62}$` |
| Saving a schema | `409` `schema already exists` | The name is in use |
| Saving a schema | `422` `fields[i]: duplicate field 'x'` | Two fields share a name |
| Saving a schema | `422` `fields[i]: unknown type 'x'` | The type is not one of the fourteen |
| Saving a schema | `422` `fields[i]: a ref field names a schema` | A `ref` with no `schema` |
| Saving a schema | `422` `fields[i]: invalid pattern: …` | A `pattern` that is not a valid regular expression |
| Reading a schema | `404` `no schema 'x'` | No such schema |
| **Overview**, **Definitions with problems** | `schema S: field 'f' refers to unknown schema 'T'` | A `ref` inside a schema names a schema that does not exist |
| **Overview**, **Definitions with problems** | `resource r: field 'f' refers to unknown schema 'T'` | A `ref` in a resource names a schema that does not exist or was deleted |
| A revision | status `invalid` with the same problem texts | A snapshot that does not compile |
| Preparing a release | `422` revision is invalid | The revision has problems |
| Any request, and **Overview** | `500` with no body detail | A cycle of schemas |
| A route using `input_fields` | `422` bare array, with the nested `loc` | A body that breaks a constraint inside a referenced schema |
| A resource read | `500` `Response validation failed` | A stored value that no longer fits a schema |
| A flow's `validate.schema` | `500` `block_failed`, `field 'f' refers to unknown schema 'S'` | A `ref` inside the block's field list |


## Debugging a schema problem in Studio

| You see | Open | To learn |
| --- | --- | --- |
| A resource that answers `404` on every route | **Overview**, **Definitions with problems** | Which schema it needs and cannot find |
| `500` on one resource's reads only | **Observability**, filtered by **5xx server error**, then the **Request trace** | Which request failed and when it started, which tells you which change it follows |
| `500` on everything | **Schemas** | Whether a cycle was just saved. Delete a schema in the cycle |
| A `422` with a nested `loc` | **API Explorer**, send the same body | The exact entries, with `ctx` |
| A client type that disagrees with the server | **API Explorer**, the request schema | The components, with the nullability the server really has |
| A stored value that will not read | **Database**, query the column | The raw JSON, and which key or value breaks the new definition |


## An incident, start to finish: a cycle in production

The cycle is rare and its effects are dramatic enough that it is worth walking through as it would be experienced, using the requests that were observed.

A developer adds a `parent` field to a `Category` schema so categories can nest, and points it at `Category` itself. Studio's field editor does not offer the schema being edited in its **Schema** menu, so they edit the **JSON** tab instead, which accepts anything:

```json
{"name": "Category", "fields": [
  {"name": "name", "type": "string"},
  {"name": "parent", "type": "ref", "schema": "Category"}
]}
```

**Save changes** succeeds. The save validates the name, the field names and the types, and does not look for cycles. The environment's version is bumped, and nothing is compiled yet.

The next request after the change triggers the rebuild, and every request fails:

```text
GET /rest/v1/products   ->  500  Internal Server Error
GET /rest/v1/orders     ->  500  Internal Server Error
GET Overview            ->  500
```

Resources that have never heard of `Category` fail too, because the compiled application for the environment is one object and it could not be built. Clients see `500` everywhere, and **Observability**, which reads recorded requests, shows a wall of `5xx`. **Overview**, where **Definitions with problems** would normally explain a broken definition, cannot load, because the page's data is computed from the compiled application.

The page that does load is **Schemas**, because the list is read from stored definitions and not from the compiled app. Opening `Category` and choosing **Delete** removes it, and the next request recompiles:

```text
DELETE …/schemas/Category   ->  204
GET /rest/v1/products       ->  200
```

If a second schema had been involved, as in a cycle between `A` and `B`, deleting one is enough. The surviving schema is then reported as an ordinary dangling reference:

```text
Definitions with problems:
  schema B: field 'a' refers to unknown schema 'A'
```

and it is fixed by editing it or deleting it. The data is untouched by any of this, since schemas never touch tables. The cost of the incident was the minutes between the save and the delete, and the way to shorten them is to know that **Schemas** is the page to open first.

Three habits prevent it. Make reference changes in a development environment before they reach one that serves traffic. Run the cycle check from the CI section on every change that touches `ref` fields. And after saving any schema change in an environment that matters, load **Overview** immediately: a blank page there is a signal in itself.


## How this compares to other systems

If you are coming from a system that has its own idea of a reusable type, these comparisons may help with expectations. They are about the concept, not a mapping of features.

| System | Its equivalent | How Pawabase differs |
| --- | --- | --- |
| JSON Schema `$defs` and `$ref` | A named, referenced shape | JSON Schema keeps `required` through a reference. Pawabase does not, and has no `oneOf`, `allOf` or conditional keywords |
| Pydantic models | A class with typed fields, nested by reference | Pawabase builds Pydantic models underneath, and a reference is compiled in a generic mode that drops `required` and defaults |
| Postgres composite types | A named row type usable as a column | A composite is typed by the database. A schema is validated by the API and stored as JSON |
| Firestore maps | An untyped nested object | A schema validates the nested keys and rejects unknown ones |
| OpenAPI `components/schemas` | A reusable response or request type | Pawabase generates the components from schemas, and every property is nullable in them |
| GraphQL types and inputs | A reusable object type | Pawabase serves REST, and a schema describes JSON bodies |


## What to remember

- A schema is a named field list that other definitions refer to by name. It is compiled once, in a generic mode, and shared.
- Through a reference, constraints and allowed keys are enforced. `required`, defaults, `read_only` and `write_only` are not.
- A nested value is stored filled out to the schema's full shape and replaced as a whole on update.
- A schema that refers to itself, directly or through others, makes every request to the environment fail until a schema in the cycle is deleted.
- Deleting or renaming a schema in use is not blocked, and breaks every resource that uses it.
- Removing a key from a schema fails reads of every row that has the structure, including rows that stored the key as `null`.
- Route `input_schema` does not enforce `required`, `response_schema` does not filter, and a flow's `validate.schema` block cannot resolve a reference.
- Promotion copies schemas by name and never deletes one.


## Questions that come up

<AccordionGroup>
  <Accordion title="Why is required ignored inside my schema?">
    A schema is compiled once in a generic mode that treats every key as optional, because it is shared by create bodies, update bodies and responses. Constraints and the set of allowed keys are enforced. `required`, `default`, `read_only` and `write_only` are not. Use an inline `object` or a route with `input_fields` when you need them enforced.
  </Accordion>
  <Accordion title="Can a schema refer to itself for a tree?">
    No. A schema that refers to itself, directly or through other schemas, makes every request to the environment fail with a `500` until a schema in the cycle is deleted. Model trees as a resource with a `parent_id`, see [Relations](/data/relations/overview).
  </Accordion>
  <Accordion title="Can I use one schema for both a resource and a route?">
    Yes. A `ref` field names it in both, and a route can also take it as `input_schema` or `response_schema`. The same rules apply in each place: constraints enforced, `required` not.
  </Accordion>
  <Accordion title="Why does my response_schema not remove fields?">
    It documents the response and does not filter it. The route and its flow decide what is sent. Use a flow that builds the body, or a transformer on the route.
  </Accordion>
  <Accordion title="What happens if I delete a schema that is in use?">
    The delete succeeds. Every resource that referenced it stops being served (`404`) and is listed under **Definitions with problems** on **Overview**. Recreating a schema with the same name restores them, since references are by name.
  </Accordion>
  <Accordion title="Can I rename a schema?">
    Studio does not allow it. The API accepts a `PUT` with a different name and renames the schema in place, and nothing updates the fields that named it. To rename safely, create the new schema, point every use at it, then delete the old one.
  </Accordion>
  <Accordion title="Do schemas appear in a flow's validate.schema block?">
    No. The block takes a field list inline and cannot resolve a `ref`. Write the nested fields inline as an `object`.
  </Accordion>
  <Accordion title="Are schemas copied when I promote an environment?">
    Yes, by name, as an upsert. A schema deleted in the source is not deleted in the target, and promoting does not create tables.
  </Accordion>
  <Accordion title="Why does a row fail to read after I removed a key from a schema?">
    A referenced schema rejects keys it does not declare, on reads as well as writes. A row that still holds the removed key fails the response model. Add the key back, or rewrite the stored JSON, then remove it.
  </Accordion>
  <Accordion title="Can two schemas have the same name as a resource?">
    Names are separate namespaces in Studio, but they share the API document's component list. Use `PascalCase` for schemas so they do not collide with the resource names, which are lowercase.
  </Accordion>
  <Accordion title="Is there a limit on how deep schemas can nest?">
    None was reached. A three-level chain validated and located errors correctly. Deep structures get hard to read in error paths and in stored JSON, so keep them shallow.
  </Accordion>
</AccordionGroup>


## Terms used on this page

| Term | Meaning here |
| --- | --- |
| Reusable schema | A named, stored field list under **Schemas** |
| Reference, `ref` | A field of type **Schema reference** that names a schema |
| Compiled model | The model Pawabase builds from a field list for validation and the API document |
| Generic mode | The way a reusable schema is compiled: types, constraints and allowed keys, with every key optional |
| Inline object | An `object` field with its own `fields`, compiled with the operation that contains it |
| Dangling reference | A `ref` to a schema that does not exist, reported under **Definitions with problems** |
| Cycle | A schema that refers to itself directly or through others, which takes the environment down |
| Component | A named entry in the generated API reference, one per schema |
