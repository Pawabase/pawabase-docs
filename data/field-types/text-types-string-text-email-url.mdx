The four text types validate the same way: the incoming JSON value must be a string, and nothing else is converted. Sending the number `5`, the boolean `true` or a list to a text field fails with a `string_type` error, which is stricter than the number types, where strings are converted.

```json
{"name": "title", "type": "string", "required": true, "min_length": 2, "max_length": 60}
```

```text
POST /rest/v1/t  {"s": 5}        ->  422  [{"type":"string_type","loc":["s"],"msg":"Input should be a valid string", ...}]
POST /rest/v1/t  {"s": ["a"]}    ->  422  string_type
POST /rest/v1/t  {"s": "abcde"}  ->  422  string_too_long  "String should have at most 4 characters"
POST /rest/v1/t  {"s": "a"}      ->  422  string_too_short "String should have at least 2 characters"
```

Length is measured in characters, not bytes. A four-character limit accepts four emoji and rejects five. Whitespace is never trimmed: the empty string `""` and the two-space string `"  "` are both valid values and are stored as sent. If you want to reject blank input, say so with a `pattern` or `min_length`, not with `required`, because `required` only checks that the key is present and not null.

### `string`

The default type, meant for short single-line values: names, slugs, codes, statuses.

| Aspect | Behavior |
| --- | --- |
| Constraints | `min_length`, `max_length`, `pattern`, `enum` |
| Column on PostgreSQL and MySQL | `VARCHAR(n)`, where `n` is `max_length` if set when the table is created, otherwise `255` |
| Column on SQLite | `TEXT`, which has no length limit; `max_length` is enforced by validation only |
| `max_length` changed later | The existing column is not widened or narrowed. See [Migrations](/data/migrations/overview) |
| `pattern` | A Python regular expression, applied with Pydantic's pattern check; it must match the whole use you intend, so anchor it with `^` and `$` |

The column width is fixed when the table is created, from whatever `max_length` said at that moment. Raising `max_length` to 500 afterwards makes validation accept 500 characters while a PostgreSQL `VARCHAR(100)` column still rejects anything over 100, and that rejection surfaces as an unhandled database error (a `500`), not a `422`. If a string might grow, set `max_length` generously the first time or use `text`.

### `text`

Long free-form content: descriptions, notes, bodies, Markdown.

| Aspect | Behavior |
| --- | --- |
| Constraints | `min_length`, `max_length`, `pattern` through the JSON tab, `enum` is not offered in Studio for this type |
| Column | `TEXT` on every dialect |
| Size | A 100,000-character value was accepted and stored. The practical ceiling is the request body limit, see [Limits](/reference/limits) |
| Studio's Record editor | A multi-line text area, four rows tall |

`text` and `string` differ in the column and in how Studio renders them. They do not differ in validation, so a `text` field with `max_length` set behaves exactly like a `string` with the same limit, except that nothing sizes a column from it.

### `email`

A `string` with a built-in pattern.

```text
^[^@\s]+@[^@\s]+\.[^@\s]+$
```

| Input | Result |
| --- | --- |
| `maya@acme.co` | Accepted |
| `jose@exämple.com` | Accepted, because the pattern only forbids whitespace and extra `@` signs in the three parts |
| `a b@x.co` | `422` `string_pattern_mismatch` |
| `a@b` | `422`, there is no dot after the `@` |
| `""` (empty string) | `422`, the pattern needs at least one character in each part |

The pattern checks shape, not deliverability. It does not verify that a domain exists, and it does not normalize case, so `Maya@Acme.co` and `maya@acme.co` are different values and a `unique` index will treat them as two. If you set your own `pattern` on an email field, it replaces the built-in one rather than adding to it. The column is `VARCHAR(320)` on PostgreSQL and MySQL, the longest address the standard allows, and `TEXT` on SQLite. `max_length` still applies as a validation limit on top of the pattern.

<Info>
Authentication in Pawabase keeps its own user records in Akountz. An `email` field on a resource is plain application data. It has no connection to a sign-in identity unless you build one, see [Managing users](/auth/managing-users/overview).
</Info>

### `url`

A `string` that must start with `http://` or `https://`.

```text
^https?://[^\s]+$
```

| Input | Result |
| --- | --- |
| `https://x.co/a?b=1` | Accepted |
| `http://localhost:3000` | Accepted |
| `x.co` | `422`, no scheme |
| `ftp://x.co` | `422`, only `http` and `https` |
| `mailto:a@b.co` | `422` |

The pattern is deliberately loose: it accepts `https://` followed by any run of non-whitespace characters, so `https://not a url` fails only because of the space, and `https://!!!` passes. Use `url` to keep obviously wrong values out, not to prove a URL is reachable. The column is `TEXT` on every dialect.


## Number types: `integer` and `number`

Number fields accept JSON numbers and, unlike text, also accept strings that look like numbers. That is Pydantic's default conversion, and it is useful for clients that send form data, but it means a field typed `integer` will happily take `"5"`.

### `integer`

```json
{"name": "stock", "type": "integer", "minimum": 0, "default": 0}
```

| Input | Result |
| --- | --- |
| `5` | `5` |
| `"5"` | `5` |
| `" 7 "` | `7`, surrounding spaces are tolerated |
| `"5.0"` | `5` |
| `5.0` | `5` |
| `true` | `1` (a boolean is accepted as 0 or 1) |
| `5.5` | `422` `int_from_float`, "got a number with a fractional part" |
| `"abc"`, `""`, `"1e3"` | `422` `int_parsing` |
| `[1]` | `422` `int_type` |
| `2^70` (a number above 64 bits) | `500` |
| `9007199254740993` | Accepted and returned exactly |

The last two rows show where the layers part ways. Validation accepts any Python integer, but the column is a 64-bit integer (`INTEGER` on SQLite, `BIGINT` on the others), so a value that does not fit passes validation and fails at the database. Keep a `maximum` on any integer a client can influence. The value `9007199254740993` is larger than JavaScript can represent exactly (`2^53`); Pawabase stores and returns it intact, but a browser parsing the JSON will round it. For identifiers that can exceed `2^53`, use a `string` or a `uuid`.

| Aspect | Behavior |
| --- | --- |
| Constraints | `minimum`, `maximum`, `enum` |
| Column | `INTEGER` on SQLite, `BIGINT` on PostgreSQL and MySQL |
| `enum` | The values must be numbers, and the input must be a number: with `"enum": [1, 2, 3]`, the string `"2"` is rejected with "Input should be 1, 2 or 3" |
| OpenAPI | `type: integer` with `minimum` and `maximum` when set |

### `number`

A 64-bit floating-point value.

```json
{"name": "price", "type": "number", "required": true, "minimum": 0}
```

| Input | Result |
| --- | --- |
| `9.5` | `9.5` |
| `"2.5"` | `2.5` |
| `"1e3"` | `1000.0` |
| `true` | `1.0` |
| `0.30000000000000004` | Stored and returned as `0.30000000000000004` |
| `""` | `422` `float_parsing` |
| `"inf"` | `500`, accepted by validation and refused by the database |

`number` is a binary float, not a decimal. It cannot represent most decimal fractions exactly, which is why `0.1 + 0.2` comes back as `0.30000000000000004`. Do not store money as `number`. Store the amount in the smallest unit as an `integer` (cents, pence, kobo) and keep the currency in a separate `string` field, or convert at the edge. Sums of floats also drift, so totals computed from many `number` rows can differ in the last digits between runs.

| Aspect | Behavior |
| --- | --- |
| Constraints | `minimum`, `maximum`, `enum` |
| Column | `REAL`, `DOUBLE PRECISION`, `DOUBLE` |
| Whole numbers | `2` is returned as `2.0`, because the response model converts to a float |
| Out-of-range | `1e308` is accepted; values that overflow a double become infinity and fail at the database |


## `boolean`

```json
{"name": "published", "type": "boolean", "default": false}
```

Pydantic's boolean conversion is generous. These inputs were accepted:

| Input | Stored as |
| --- | --- |
| `true`, `false` | The same |
| `"true"`, `"TRUE"`, `"t"`, `"yes"`, `"on"`, `"1"`, `1` | `true` |
| `"false"`, `"no"`, `"0"`, `0` | `false` |
| `2` | Rejected, `bool_parsing` |
| `""` | Rejected, `bool_parsing` |
| `null` | Accepted when the field is not required, stored as `NULL` |

A boolean column holds three states, not two: `true`, `false` and `NULL`. A field without a `default` that the client omits is stored as `NULL`, and a record read back shows `"published": null`. If "never set" must mean "no", give the field a `default`. Defaults apply when the key is omitted, not when the client sends an explicit `null`.

| Aspect | Behavior |
| --- | --- |
| Column | `INTEGER` (0 or 1) on SQLite, `BOOLEAN` on PostgreSQL and MySQL |
| Studio's Record editor | A `true` / `false` menu |
| Studio's **Default** control | A **None / Yes / No** segmented control |

<Warning>
Filtering on a boolean with a plain value does not behave the way it reads. `?filter[published]=false`, `?filter[published]=eq.false` and `?filter[published]=0` all returned the rows where the field is **true** in testing, because any non-empty string converts to true on the way to the query. Use the `is` operator instead: `?filter[published]=is.false` and `?filter[published]=is.true` return the right rows, and `is.null` finds the rows that were never set. See [Filtering](/data/filtering/overview).
</Warning>


## Time types: `datetime` and `date`

Both types accept ISO 8601 strings. The differences are in what else they accept and in what each database stores.

### `datetime`

```json
{"name": "published_at", "type": "datetime"}
```

| Input | Result on create |
| --- | --- |
| `"2026-10-01T10:00:00Z"` | Stored as `2026-10-01T10:00:00+00:00` |
| `"2026-10-01T10:00:00+02:00"` | Offset kept, `2026-10-01T10:00:00+02:00` |
| `"2026-10-01 10:00"` (no zone) | Treated as UTC, `2026-10-01T10:00:00+00:00` |
| `"2026-10-01"` | Midnight UTC, `2026-10-01T00:00:00+00:00` |
| `1790000000` (a number) | Unix seconds, `2026-09-21T14:13:20+00:00` |
| `"01/10/2026"` | `422` |

A value without a zone is read as UTC, not as the server's local time or the caller's. Send an offset or `Z` whenever the zone matters.

What the database does with the value depends on the dialect, and this is where the types of layer four show through.

| Dialect | Column | What is stored | Consequence |
| --- | --- | --- | --- |
| SQLite | `TEXT` | The ISO string exactly as normalized, offset included | Comparisons are text comparisons. Two values with different offsets do not sort chronologically |
| PostgreSQL | `TIMESTAMPTZ` | An absolute instant | Comparisons and sorting are chronological |
| MySQL | `DATETIME(6)` | The instant converted to UTC with the zone dropped | Chronological, always UTC, microsecond precision |

If your application will run on PostgreSQL or MySQL in production and SQLite in development, normalize to UTC (`Z`) on the client. Then text comparison on SQLite and chronological comparison on the other two agree.

On a read, a **declared** `datetime` field is serialized by the response model, and the automatic `created_at` and `updated_at` columns are returned as the stored string. In practice that shows up as `…T10:00:00Z` for a declared field in a list and `…+00:00` for the timestamps. Both are valid ISO 8601, and a client that parses timestamps handles either.

### `date`

A calendar day with no time and no zone.

```json
{"name": "released", "type": "date"}
```

| Input | Result |
| --- | --- |
| `"2026-10-01"` | `2026-10-01` |
| `"2026-10-01T00:00:00"` | `2026-10-01`, a midnight timestamp is accepted |
| `"2026-10-01T10:30:00"` | `422` `date_from_datetime_inexact`, "Datetimes provided to dates should have zero time" |
| `20261001` (a number) | `422` same error, a number is read as a timestamp |
| `"01/10/2026"` | `422` |

A `date` never shifts with a time zone, which is the reason to choose it over a `datetime` for birthdays, due dates and billing days. The column is `TEXT` on SQLite and `DATE` on PostgreSQL and MySQL. A `YYYY-MM-DD` string sorts and compares correctly as text, so filters like `gte.2026-03-01` work on every dialect. Passing a full timestamp in a **filter** on a date field is a different story: `?filter[released]=eq.2026-01-01T00:00:00` returned a `500` in testing, because the filter value is parsed as a date. Filter dates with dates.


## `uuid`

```json
{"name": "external_id", "type": "uuid"}
```

| Input | Result |
| --- | --- |
| `123e4567-e89b-12d3-a456-426614174000` | Stored and returned as sent |
| `123E4567-E89B-12D3-A456-426614174000` (uppercase) | Returned lowercase |
| `123e4567e89b12d3a456426614174000` (no hyphens) | Returned with hyphens |
| `xyz` | `422` `uuid_parsing` |

A `uuid` field is validated as a real UUID and normalized to lowercase with hyphens before it is stored. The column is `TEXT` on SQLite, a native `UUID` on PostgreSQL and `CHAR(36)` on MySQL.

Filtering behaves differently from validation. On SQLite, a filter value is compared as text after the field's encoder runs, and the encoder for a UUID on that dialect does not lowercase the filter value. In testing, `?filter[external_id]=123E4567-…` (uppercase) and the hyphen-less form returned nothing, while the lowercase hyphenated form matched. On PostgreSQL the native type normalizes both sides. Send lowercase hyphenated UUIDs in filters and the question never arises.

A resource's own primary key can be a UUID with the **ID type** control set to **UUID**. That is a property of the resource, not a field, and Pawabase generates a version 4 UUID on create. A `uuid` field is for any other identifier, such as a foreign key to another resource whose key is a UUID. See [Relations](/data/relations/overview) and [Defining resources](/data/defining-resources/overview).
