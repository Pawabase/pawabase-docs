Everything the Events & runs page does is a platform API call, so scripts can do it too. All of these are under `/platform/v1/projects/{ref}/envs/{env}` and need an operator.

| Call | Purpose | Notes |
| --- | --- | --- |
| `GET /events?name=<exact>&limit=<n>` | List events, newest first | `name` is an **exact** match, not a pattern. Returns `{"data": [...]}` |
| `GET /events/<event_id>` | One event | Takes the event's `event_id` (the long hex id). The numeric `id` answers `404`, `no such event` |
| `POST /events` | Emit an event | Body `{"name": "...", "payload": ...}`. Returns `{"event_id": "..."}` |
| `GET /events-graph` | The event map | Producers and consumers per event name |
| `GET /flow-runs?status=&limit=` | Flow runs | |
| `GET /flow-runs/<id>` | One run, with its input, output and step trace | |
| `GET /webhook-deliveries` | Deliveries | |
| `POST /webhook-deliveries/<id>/redeliver` | Queue a delivery again | |
| `GET`, `POST`, `PUT`, `DELETE /subscriptions` | Event subscriptions | |
| `GET`, `POST`, `PUT`, `DELETE /webhooks` | Webhook endpoints | The creating response carries the generated signing secret once |
| `POST /jobs/<id>/retry` | Retry a failed job | |

A stored event, from the list, has these fields:

```json
{
  "id": 2,
  "event_id": "6373a07067cb4ca4b9c8cecf971a8186",
  "project": "acme",
  "env": "development",
  "name": "todos.created",
  "source": "api",
  "actor": "u-1",
  "payload": { "resource": "todos", "change": "created", "record": { "id": 2, "title": "b" } },
  "request_id": "d58bf986-52d9-4bed-acfb-4698dea7b70a",
  "occurred_at": "2026-10-01T22:19:50.907549+00:00",
  "consumers": [],
  "created_at": "2026-10-01T22:19:50.910240+00:00",
  "updated_at": "2026-10-01T22:19:50.910263+00:00"
}
```

Two ids are present: `id` is the row's number in the log, and `event_id` is the event's own id, which is the one the webhook body carries as `id` and the one the detail route takes.

Creating a webhook endpoint:

```http
POST /platform/v1/projects/acme/envs/production/webhooks
```

```json
{
  "name": "crm",
  "url": "https://crm.example.com/hooks/pawabase",
  "events": ["orders.*", "customers.created"],
  "headers": { "x-source": "pawabase" },
  "max_attempts": 5
}
```

```json
{
  "id": 2,
  "name": "crm",
  "url": "https://crm.example.com/hooks/pawabase",
  "events": ["orders.*", "customers.created"],
  "headers": {},
  "enabled": true,
  "max_attempts": 5,
  "secret": "whsec_zTu2ami8KglRg7u8SZNRretOTMQ0XSs4"
}
```

The `secret` is the signing secret. Store it where the receiver can read it, because it is not returned again.


## Troubleshooting

| What you see | Cause | Fix |
| --- | --- | --- |
| No event appeared after a write | The write did not go through Pawabase (SQL, the console, a migration), or the resource's **Emit events** is off, or the write failed validation | Check how the write was made, and the switch |
| An event appeared with no consumers | Nothing matches: a subscription's pattern or condition, a flow trigger's resource and operations, or an endpoint's events | Compare the event name with each consumer's pattern. Use **Emit test event** |
| A subscription never fires | Its condition is `{"exists": "$event.data"}`, the default **Only when…** fills in. The envelope has no `data` | Change it to a path under `$event.payload` |
| A flow did not start on an `updated` event | The **Resource change** trigger's `operations` list does not include `updated` | Add it, or omit `operations` |
| A flow starts, and cannot find the record's fields | The template reads `input.payload...` instead of `input.event.payload...` | The event is under `input.event` |
| The webhook receives the secret field | Events carry the raw record | Stop sending the raw event. Send a shaped custom event |
| A webhook delivery is `failed` with `resolves to a private address` | The URL points at a private or loopback host and the installation is not local | Use a public HTTPS address |
| A webhook delivery keeps `retrying` | The receiver is down, slow, or answering non-`2xx` | Fix the receiver, then **Redeliver** |
| A delivery makes more attempts than the endpoint's **Attempts** | That setting is not used. The job makes five | Plan for five |
| The receiver rejects the signature | It hashed a parsed body, or the wrong secret, or the clock is more than five minutes off | Hash the raw bytes, and check the secret and the clock |
| The receiver gets events out of order | Consumers run as independent jobs | Compare `record.updated_at` before overwriting |
| The same event arrives twice | A retry after a timeout, or an endpoint registered twice | De-duplicate on the body's `id` |
| A flow ran, and the record it read is old | The flow ran after later writes | Read the record by id inside the flow, or compare `updated_at` |
| A counter is wrong | The flow increments, and ran twice | Recompute from the table |
| Flow runs stream endlessly | An event loop: a flow updates the resource it listens to | Narrow the trigger, add a condition, or switch the written resource's events off |
| A realtime consumer shows `failed` | The realtime service could not be reached | Check the realtime service. The write was not affected |
| A resource event is missing for a bulk load | Events were switched off, or the load used SQL | Expected |
| The Events tab filter finds nothing | It matches the name **exactly**, and a suggested name `resource.todos.created` is not a name | Filter by `todos.created` |
| An event's Details window will not open | The row's numeric id was sent where the `event_id` is needed | Read it by `event_id` through the API |


## Questions that come up

<AccordionGroup>
  <Accordion title="Is every write guaranteed to publish an event?">
    Not guaranteed. A write through Pawabase publishes after it succeeds, but the publish is not inside the database transaction, so a crash between the two loses the event. A write that does not go through Pawabase, or a resource with events off, publishes nothing.
  </Accordion>
  <Accordion title="What is the name of a resource event?">
    `<resource>.created`, `<resource>.updated` or `<resource>.deleted`. There is no `resource.` prefix, whatever a placeholder in Studio suggests.
  </Accordion>
  <Accordion title="Where is the record in an event?">
    Under `payload.record`. The envelope also has `name`, `project`, `env`, `source`, `actor`, `id`, `occurred_at` and `request_id`.
  </Accordion>
  <Accordion title="Does an update event say what changed?">
    No. It carries the whole row after the update. Compare it with what you last saw.
  </Accordion>
  <Accordion title="What does a delete event contain?">
    The row as it was before the delete, including its last update.
  </Accordion>
  <Accordion title="Does the event respect my transformer or `write_only`?">
    No. The record is the raw row. Hidden fields are in it, for flows, subscriptions, webhooks and realtime.
  </Accordion>
  <Accordion title="Do events fire for console or SQL writes?">
    No. They are audited and clear caches, and publish nothing.
  </Accordion>
  <Accordion title="Do events fire for Records-tab writes?">
    Yes, with the actor `studio`.
  </Accordion>
  <Accordion title="Do events fire for writes made by flows?">
    Yes, with the caller as the actor when a person started the flow, and no actor when an event started it. A flow's writes can start other flows.
  </Accordion>
  <Accordion title="Are events ordered?">
    They are published in order, and consumed as independent jobs, so arrival order is not guaranteed. Use `updated_at` or a version number.
  </Accordion>
  <Accordion title="Are events delivered exactly once?">
    No. The bus is at-least-once and each consumer retries, so a consumer can run more than once. Make it idempotent.
  </Accordion>
  <Accordion title="How do I stop an infinite loop?">
    Switch events off on the resource the flow writes, narrow the trigger's operations, or add a condition. Pawabase does not detect loops.
  </Accordion>
  <Accordion title="Why did my webhook get five attempts when I set two?">
    The **Attempts** field is stored and not used. The delivery job makes five attempts with backoff.
  </Accordion>
  <Accordion title="Can a webhook go to localhost?">
    In a local or test installation, yes. In any other, the delivery is refused as a private address.
  </Accordion>
  <Accordion title="How do I resend a webhook?">
    Press **Redeliver** on its row in **Webhook deliveries**.
  </Accordion>
  <Accordion title="Can I subscribe from my own code?">
    Through a webhook, which is the supported way to hear about events outside Pawabase. Inside Pawabase, use flows, subscriptions and functions.
  </Accordion>
  <Accordion title="Can I send events from outside Pawabase into it?">
    Yes, with an inbound hook, which can emit an event or run a flow. See [Inbound webhooks](/webhooks/inbound).
  </Accordion>
  <Accordion title="Do events cross environments?">
    No. An event belongs to the environment where the write happened.
  </Accordion>
  <Accordion title="Do I pay for events I do not use?">
    Each event is recorded and routed. A resource nobody listens to is cheaper with **Emit events** off.
  </Accordion>
</AccordionGroup>


## How this page differs from earlier versions

If you have seen older documentation for resource events, these are the corrections.

| Earlier claim | What actually happens |
| --- | --- |
| The event is emitted inside the database transaction and is guaranteed if the write commits | It is published **after** the write, outside the transaction, and can be lost in a crash |
| The payload is the bare record | The payload is `{"resource", "change", "record"}` |
| The envelope has `event`, `published_at`, `correlation_id` | It has `name`, `occurred_at`, `request_id`, `source`, `actor`, `id`, `project`, `env`, `release_id` and `api_version` |
| The flow input has `$input.event`, `$input.payload` | The flow input is `{"event": {...}}`: `input.event.payload.record` |
| Events are ordered within a resource | Consumers are independent jobs. No ordering is guaranteed |
| The record is "shaped as it exists in the database" and hidden fields are not an issue | That is the problem: hidden fields are in every event |
| The resource has an **Events** tab with a toggle | The **Emit events** switch is on the main sheet, in **Behaviour** |
| Webhooks are under **Automate → Webhooks** | They are under **Webhooks** in the environment's navigation |
| Subscribe from code with an `EventBus` client | There is no client for external code. Use a webhook |
| A webhook receives the full event envelope | It receives `{id, event, project, env, data, sent_at}`, where `data` is the payload |
| Every emitted event is in the audit log | Events are in the **event log** (the Events tab). The audit log records management actions |
| A failed delivery is retried manually from the audit log | **Redeliver** on **Webhook deliveries**, and **Retry** on **Jobs & queues** |
| Retries follow each subscription's policy | A webhook endpoint's **Attempts** is stored and unused. Jobs retry with their own backoff |


## Before you rely on an event

1. **Does every writer go through Pawabase?** If not, the event is not the whole story.
2. **Is the consumer safe to run twice?**
3. **Does it cope with events arriving out of order?** Does it compare `updated_at`?
4. **What does the event contain that it should not?** Hidden fields, secrets, personal data.
5. **Is the webhook's address public,** and does the receiver verify the signature on the raw bytes?
6. **Can the flow loop?** Does it write a resource it listens to?
7. **Is the subscription's condition real?** Has it been tested with **Emit test event**, and does it avoid `$event.data`?
8. **Are the switches right?** Events on only where something listens, broadcast on only where clients need it.
9. **Who can see the event log?** It holds raw records.
10. **What happens if the event is lost?** Is there a periodic reconciliation?


## What to remember

- **A write through Pawabase publishes `<resource>.<change>`** after it succeeds, if **Emit events** is on.
- **The payload is `{resource, change, record}`**, and the record is **raw**: hidden fields included.
- **SQL, the console and migrations publish nothing.** The Records tab does.
- **Consumers are flows, subscriptions, webhooks and realtime**, each a queued job.
- **Delivery is at least once, unordered and not inside the transaction.** Write idempotent consumers.
- **A flow reads the event at `input.event`.**
- **A subscription's default condition never matches.** Use `$event.payload...`.
- **A webhook is signed, retried five times, and refused for private addresses** outside development. Its **Attempts** field is not used.
- **A flow can write, and writes publish events.** Break loops deliberately.
- **To share a record safely, share a shaped event,** not the raw one.


## Terms

| Term | Meaning |
| --- | --- |
| **Event** | A named fact with a payload, published on the platform bus |
| **Resource event** | An event for a change to a resource, named `<resource>.<change>` |
| **Envelope** | The event with its name, project, environment, source, actor, id, time and request id |
| **Payload** | For a resource event, `{resource, change, record}` |
| **Raw record** | The row as the database holds it, before any transformer or `select` |
| **Event processor** | The part of the API that records an event and routes it to consumers |
| **Event log** | The record of processed events, shown on the Events tab |
| **Consumer** | A flow, subscription target, webhook endpoint or realtime channel that receives an event |
| **Subscription** | A stored link from an event pattern, with an optional condition, to a flow, a function or a realtime channel |
| **Webhook endpoint** | A stored URL that receives matching events as signed HTTP requests |
| **Delivery** | One attempt series to send one event to one endpoint |
| **Idempotent** | Safe to run again with the same result |
