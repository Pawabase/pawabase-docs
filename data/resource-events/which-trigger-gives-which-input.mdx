A flow can start in several ways, and the shape of its `input` differs. The ones that matter for events:

| Trigger | `input` is | A value is read as |
| --- | --- | --- |
| **Resource change** (`trigger.resource`) | `{"event": {...}}` | `{{ input.event.payload.record.title }}` |
| **Event** (`trigger.event`) | `{"event": {...}}` | `{{ input.event.payload.record.title }}`, or `{{ input.event.payload.kind }}` for a custom event |
| A subscription with a flow target | `{"event": {...}}` | The same |
| **HTTP trigger** (a route) | `{"params", "query", "body"}` | `{{ input.body.reason }}` |

So the three event paths give a flow the same input, and the only difference is how the flow was started. A flow that serves both an event and a route needs to read from different places, and is usually better as two flows that share a third.


## Event patterns, at a glance

| You want | Pattern in a trigger or subscription | Pattern in a webhook |
| --- | --- | --- |
| Creations of one resource | `orders.created` | `orders.created` |
| Every change to one resource | `orders.*` | `orders.*` |
| Every deletion | `*.deleted` | `*.deleted` |
| Several resources | Several triggers or subscriptions | `["orders.*", "customers.*"]` |
| Everything | `*` | `*` |
| A custom family | `shop.*` | `shop.*` |

A **Resource change** trigger does not take a pattern: it takes a resource and a list of operations.


## Reference

### Resource event names and payloads

| Event | `payload.record` | Published when |
| --- | --- | --- |
| `<resource>.created` | The new row | An insert succeeds |
| `<resource>.updated` | The whole row after the update | An update succeeds |
| `<resource>.deleted` | The row as it was before deletion | A delete succeeds |

### Consumer statuses, on an event

| Status | Meaning |
| --- | --- |
| `queued` | A flow, function or webhook job was queued |
| `done` | A realtime publication was made |
| `failed` | Handing the work over failed. The consumer carries an `error` |

### Delivery statuses, on a webhook delivery

| Status | Meaning |
| --- | --- |
| `pending` | Queued, not attempted |
| `retrying` | An attempt failed, another will follow |
| `delivered` | Answered with a `2xx` |
| `failed` | Given up, or refused before sending |

### Where things are set

| Setting | Where |
| --- | --- |
| Whether a resource publishes events | The resource, **Behaviour**, **Emit events** |
| Whether a resource broadcasts to realtime | The resource, **Behaviour**, **Broadcast changes** |
| A flow that starts on an event | The flow's trigger: **Resource change** or **Event** |
| A rule that routes an event to a flow, a function or realtime | **Event subscriptions** |
| An outside receiver | **Webhooks** |
| What may subscribe to a resource's channel | **Settings**, **Realtime**, channel rules |
| Seeing events, runs, deliveries and mail | **Events & runs** |
| Retrying a failed job | **Jobs & queues** |

### Limits and defaults

| Item | Value |
| --- | --- |
| **Emit events** default | On |
| **Broadcast changes** default | Off |
| Webhook delivery tries | 5 (the **Attempts** field is stored and unused) |
| Webhook backoff | Exponential from two seconds, capped at a minute |
| Webhook request timeout | Fifteen seconds per attempt |
| Signature tolerance | Five minutes |
| Stored response body | The first 2,000 characters |
| Webhook **Events** default | `*` |


## What changes when you promote

Event wiring is made of definitions, and **Promote** carries them.

| Definition | Promoted | Check after |
| --- | --- | --- |
| A resource's `events` and `realtime` switches | With the resource | That the target's resource has the switches you intend |
| Flows and their triggers | With the flows | That the target has the resources the flows name |
| Event subscriptions | Yes | That the target flow, function or channel exists there |
| Webhook endpoints | Yes | The **URL** (development URLs must not reach production), the events, and the **signing secret** |
| A webhook's **extra headers** | With the endpoint | That no development token is in them |

Two mistakes to avoid. **A promoted webhook pointing at a development receiver** sends production data to the wrong place, so change the URL in the target after promoting. And **a promoted subscription whose flow was not promoted** is a consumer that fails every time, which shows as a `failed` consumer on every event.

Because promote never deletes, a subscription or endpoint you removed in the source stays in the target until you remove it there.


## Definitions you can copy

### A subscription to a flow

```json
{
  "name": "review_big_orders",
  "description": "Send big paid orders to a human",
  "event": "orders.created",
  "target_type": "flow",
  "target": "review_order",
  "condition": { "all": [
    { "gte": ["$event.payload.record.total", 1000] },
    { "eq": ["$event.payload.record.status", "paid"] }
  ] },
  "enabled": true
}
```

### A subscription to a function

```json
{
  "name": "sync_search",
  "event": "products.*",
  "target_type": "function",
  "target": "index-product",
  "condition": null,
  "enabled": true
}
```

The function is queued with `{"event": {...}}` as its input, so it reads `ctx.input["event"]["payload"]["record"]`.

### A subscription to a realtime channel

```json
{
  "name": "tenant_feed",
  "event": "orders.*",
  "target_type": "realtime",
  "target": "org:{{ event.payload.record.org_id }}",
  "enabled": true
}
```

The channel is built from the event, so each tenant's changes go to its own channel. The target is rendered with `event` in scope, which is how `alerts:{{ event.payload.kind }}` became `alerts:x` in a run.

### A webhook endpoint

```json
{
  "name": "crm",
  "description": "Customer records to the CRM",
  "url": "https://crm.example.com/hooks/pawabase",
  "events": ["shop.order_created", "customers.created", "customers.updated"],
  "headers": { "x-source": "pawabase" },
  "enabled": true,
  "max_attempts": 5
}
```

### A flow that starts on a resource change

```json
{
  "name": "welcome_new_customer",
  "definition": {
    "nodes": [
      { "id": "t", "data": { "block": "trigger.resource", "config": { "resource": "customers", "operations": ["created"] } } },
      { "id": "m", "data": { "block": "mail.send", "config": {
          "to": ["{{ input.event.payload.record.email }}"],
          "subject": "Welcome, {{ input.event.payload.record.name }}",
          "text": "Thanks for joining."
      } } }
    ],
    "edges": [{ "id": "e1", "source": "t", "target": "m" }]
  }
}
```

Mail is one of the things that does nothing visible in a development install that has no mail configured (the Overview shows it as suppressed), so confirm the mail path where mail is real before relying on it.


## What events are not

A few jobs look like events and are better done another way.

| It is not | Because | Use |
| --- | --- | --- |
| **A guaranteed work queue** | It is at least once but not transactional, and unordered | A queued job (`queue.flow`, `dispatch_flow`) that you start deliberately |
| **A replication stream** | An update carries no "before", and a crash can drop an event | Database replication, or reconciliation |
| **An audit trail** | Only changes made through Pawabase, only with the raw state, and the log has no stated retention | An audit resource written by a flow, plus the platform's audit log for management actions |
| **A transaction** | The consumer runs after the write, and can fail alone | `db.transaction` for steps that must succeed together |
| **A way to read data** | The payload is a snapshot at the moment of the change | Read the resource |
| **A secure channel** | Raw records, to every consumer | A shaped event, to a named audience |
| **A scheduler** | It fires on a change, not on time | **Schedules** |

Used for what they are, a prompt that something changed, with enough data to react, they are the simplest and most reliable way to connect the parts of a Pawabase system.


## Common design mistakes

| Mistake | What goes wrong | Instead |
| --- | --- | --- |
| Pointing a webhook at a resource with secrets | The secrets leave in every delivery | A shaped custom event |
| Using `*` for a webhook | It receives unrelated events and personal data | A short list of patterns |
| A flow that updates its own trigger resource | An endless loop | Narrow the operations, add a condition, or switch events off on the written resource |
| An incrementing counter | A retry counts twice | Recompute |
| Trusting arrival order | A late `updated` overwrites a newer state | Compare `updated_at` |
| Treating a missing event as impossible | A crash can lose one | Reconcile on a schedule |
| Writing through SQL and expecting consumers | SQL publishes nothing | Write through the API, or emit an event |
| Leaving **Emit events** on for a bulk load | A flood of consumers | Switch it off, or load with SQL |
| A subscription with **Only when…** left at its default | It never fires | Change `$event.data` to a path under `$event.payload` |
| A webhook URL on a private address | Refused outside development | A public HTTPS address |
| Verifying a signature on parsed JSON | The bytes differ, and it fails | Verify the raw body |
| Assuming **Attempts** limits retries | The job makes five | Plan for five |

Each row is a small decision made once, in a form or a flow. They are the difference between events that quietly connect a system and events that surprise it.
