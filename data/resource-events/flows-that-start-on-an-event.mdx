A flow can start on an event in two ways.

### The Resource change trigger

The **Resource change** trigger (`trigger.resource`) names a **resource** and, optionally, the **operations** that start the flow:

```json
{ "block": "trigger.resource", "config": { "resource": "todos", "operations": ["created", "deleted"] } }
```

| Setting | Meaning |
| --- | --- |
| `resource` | The resource's name. Required |
| `operations` | A list of `created`, `updated`, `deleted`. Omit it for all three |

This was run with `["created", "deleted"]`: a create and a delete started the flow, and an update did not (its event had no consumers). The trigger matches the **resource name and the change**, not a pattern.

### The Event trigger

The **Event** trigger (`trigger.event`) takes an **event name or pattern**, with the hint *Event name or pattern, e.g. order.**:

```json
{ "block": "trigger.event", "config": { "event": "todos.*" } }
```

Use it for patterns across resources (`*.deleted`), and for events that are not resource changes (`user.created`, or your own `custom.*`).

### What the flow receives

Both triggers start the flow with the event wrapped in one key:

```json
{
  "event": {
    "name": "todos.created",
    "project": "acme",
    "env": "development",
    "payload": { "resource": "todos", "change": "created", "record": { "id": 2, "title": "from records tab" } },
    "source": "api",
    "actor": "studio",
    "id": "5977bd30d884497ea0df5f629a28e7c9",
    "occurred_at": "2026-10-01T22:13:36.259369+00:00",
    "request_id": null,
    "release_id": null,
    "api_version": null
  }
}
```

so the flow's blocks read it with templates:

| In the flow | Value |
| --- | --- |
| `{{ input.event.name }}` | `todos.created` |
| `{{ input.event.payload.change }}` | `created` |
| `{{ input.event.payload.record.title }}` | The record's title |
| `{{ input.event.actor }}` | Who made the change |
| `{{ input.event.id }}` | The event's id, for de-duplication |

The run is queued, so it starts a moment after the write, and **not as the writer**: the flow runs with a system identity (`authenticated: false, kind: "system"`). A flow that needs to know who made the change reads `input.event.actor`.

<Warning>
**Loops.** A flow that updates the same resource it listens to publishes another `updated` event, which starts the flow again, and so on. Pawabase does not detect this. Break the cycle with a condition (act only when a field has a particular value), with `operations` that exclude the change you make, or by writing through a path that does not publish (a different resource that has events off).
</Warning>


## Event subscriptions

A **subscription** connects an event name to a **target**, without putting a trigger in the flow. Open **Event subscriptions**, described as *Run a flow or function, or broadcast to a realtime channel, when an event is emitted.* The form has these parts:

| Section | Field | Meaning |
| --- | --- | --- |
| (name) | **Name** | Placeholder `on_signup` |
| **When** | **Event** | A name or pattern, placeholder `user.created`, with suggestions. The section reads *Wildcards match a family: todos.* or user.** |
| | **Only when…** | A switch. Hint: *Filter on the event with rules over $event.* Turns on a condition builder |
| **Then** | The target | A **flow**, a **function** or **realtime**, and which one |
| | **Enabled** | |

The starting example (**Use example**) is a subscription called `on_signup` for `user.created`, to the flow `welcome`.

| Target | What happens |
| --- | --- |
| **Flow** | The flow is queued, with the event as its input (`{"event": {...}}`), exactly as for a trigger |
| **Function** | The function is queued with the same input |
| **Realtime** | The event's **payload** is published on a channel. The target is the channel, and it may be a template. With no target the channel is `events:<name>` |

A realtime target can be built from the event: a target of `alerts:{{ event.payload.kind }}` published to `alerts:x` for an event whose payload had `"kind": "x"`. If the realtime service cannot be reached, the consumer's status is `failed`, as it was when this was run in a test installation with no realtime service.

### The condition, and a trap in the default

**Only when…** adds a condition over the event, written with `$event`. The condition is evaluated against the **envelope** shown above, so the paths are `$event.name`, `$event.payload`, `$event.payload.record.status`, `$event.actor` and so on.

<Warning>
Turning on **Only when…** fills in the condition `{"exists": "$event.data"}`. The envelope has **no `data` key** (the data is under `payload`), so that condition is never true and the subscription **never fires**. This was run: a subscription for `todos.*` with `{"exists": "$event.data"}` produced no consumer for a create or an update, while one for `todos.created` with `{"exists": "$event.payload.record"}` fired on the create. After turning the switch on, **change the condition** before you save, and test the subscription with **Emit test event**.
</Warning>

Conditions use the same language as policies. Useful ones:

| Want | Condition |
| --- | --- |
| Only orders over a threshold | `{"gte": ["$event.payload.record.total", 1000]}` |
| Only a status | `{"eq": ["$event.payload.record.status", "paid"]}` |
| Only changes made by a person, not a flow | `{"exists": "$event.actor"}` |
| Only changes not made from the Records tab | `{"ne": ["$event.actor", "studio"]}` |

### Subscription or trigger?

| | Flow trigger | Subscription |
| --- | --- | --- |
| Lives in | The flow | A definition of its own |
| Can target a function or realtime | No | Yes |
| Can filter with a condition | Only inside the flow | Yes, before anything is queued |
| One flow, many events | Several triggers in the flow | Several subscriptions |
| Promoted | With the flow | As its own definition |

Use a trigger when a flow exists for one event. Use a subscription when the wiring should be separate from the flow, or the target is a function or a channel.
