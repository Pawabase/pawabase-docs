A **webhook endpoint** delivers events to an external URL as signed HTTP `POST` requests, with retries. Open **Webhooks** (*Deliver events to external URLs, signed, with retries.*). The form:

| Section | Field | Meaning |
| --- | --- | --- |
| (name) | **Name** | Placeholder `crm` |
| **Delivery** | **Endpoint URL** | Placeholder `https://example.com/hooks/pawabase`. Must be `http` or `https` |
| | **Events** | The events to send. Hint *\* sends everything.* Suggestions are `*`, `user.*` and `<resource>.*` for each resource |
| | **Extra headers** (optional) | Header and value pairs sent on every delivery. **Add header** |
| **Reliability & signing** | **Attempts** | Hint *Retries back off exponentially.* A number from 1 to 10, default 5 |
| | **Signing secret** (optional) | New endpoint: *Leave empty to generate one; it is shown once.* Existing: *Leave empty to keep the current secret.* At least 16 characters if you supply one. A generated secret looks like `whsec_...` and is returned **once**, in the response that creates the endpoint. Reading the endpoint afterwards does not include it |
| | **Enabled** | |

The starting example is a `crm` endpoint for `todos.*` and `user.created`.

### What is sent

One delivery per event per endpoint, as a `POST` with a JSON body:

```json
{
  "id": "5977bd30d884497ea0df5f629a28e7c9",
  "event": "todos.created",
  "project": "acme",
  "env": "production",
  "data": { "resource": "todos", "change": "created", "record": { "id": 1, "title": "one" } },
  "sent_at": 1790000000
}
```

| Key | Meaning |
| --- | --- |
| `id` | The **event's** id, the same on every attempt and every endpoint. Use it to de-duplicate |
| `event` | The event name |
| `project`, `env` | Where it happened |
| `data` | The event's **payload**: `resource`, `change` and the **raw** `record` |
| `sent_at` | When the delivery was made, as epoch seconds |

Note that `data` is the payload, so the record is at `data.record`, and that it carries the hidden fields. The body is compact JSON, so verify signatures against the exact bytes you receive.

The request headers are your extra headers plus:

| Header | Value |
| --- | --- |
| `Content-Type` | `application/json` |
| `Pawabase-Signature` | `t=<unix time>,v1=<hex HMAC-SHA256 of "<time>." followed by the body>` |
| `Pawabase-Event` | The event name |
| `Pawabase-Delivery` | The delivery's id, which changes per endpoint |

### Verifying the signature

The signature proves the request came from Pawabase and is fresh. The signed text is the timestamp, a dot, and the raw body:

```python
import hashlib
import hmac
import time


def verify(secret: str, body: bytes, header: str, tolerance: int = 300) -> bool:
    parts = dict(item.split("=", 1) for item in header.split(",") if "=" in item)
    try:
        timestamp = int(parts.get("t", ""))
    except ValueError:
        return False
    if abs(time.time() - timestamp) > tolerance:
        return False                                   # too old, or too far in the future
    expected = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, parts.get("v1", ""))
```

```js
import { createHmac, timingSafeEqual } from "node:crypto"

export function verify(secret, rawBody, header, tolerance = 300) {
  const parts = Object.fromEntries(header.split(",").map((part) => part.split("=", 2)))
  const timestamp = Number(parts.t)
  if (!Number.isFinite(timestamp) || Math.abs(Date.now() / 1000 - timestamp) > tolerance) return false
  const expected = createHmac("sha256", secret).update(`${timestamp}.`).update(rawBody).digest("hex")
  const given = Buffer.from(parts.v1 ?? "", "hex")
  const wanted = Buffer.from(expected, "hex")
  return given.length === wanted.length && timingSafeEqual(given, wanted)
}
```

Three rules for a receiver:

1. **Verify before you parse.** Read the raw bytes, check the signature, and only then decode the JSON.
2. **Reject old timestamps.** Five minutes is the tolerance Pawabase itself uses.
3. **Answer fast with a `2xx`.** Do the work afterwards. A slow or failing receiver is retried, and the retries arrive again.

### Delivery and retries

Each delivery is a job, with a record in **Webhook deliveries**:

| Status | Meaning |
| --- | --- |
| `pending` | Created, not yet attempted |
| `retrying` | An attempt failed and another will follow. The record shows the error: `HTTP 500`, or a connection error such as `ConnectError: All connection attempts failed` |
| `delivered` | A `2xx` answer. The HTTP status, the first 2,000 characters of the response body and the delivery time are recorded |
| `failed` | Given up, or refused before sending |

The record also shows **Attempts**, the response status and the duration of the last attempt. Each row has a **Redeliver** button that queues the delivery again (the toast reads *Redelivery queued*), which is how you resend after you have fixed the receiver.

A non-`2xx` answer, a timeout or a connection failure all count as a failed attempt, and the delivery is retried with an exponential backoff that starts at two seconds and is capped at a minute. Any `2xx` is success.

<Warning>
The **Attempts** setting has **no effect today**. The form stores a number from 1 to 10, but the delivery job always makes **five** attempts with its own backoff. This was run with an endpoint set to 2: the delivery to an unreachable address kept retrying and had made four attempts, still `retrying`, when it was read. Treat 5 as the real number, and do not rely on 1 to mean "once".
</Warning>

### Addresses that are refused

Webhooks and flows are configured by developers, and could be pointed at the platform's own network. Outside a local or test installation, a delivery is **refused before it is sent** when the URL:

| URL | Result |
| --- | --- |
| Is not `http` or `https` | `failed`, `only http and https URLs are allowed` |
| Has a host that cannot be resolved | `failed`, `cannot resolve <host>` |
| Resolves to a private, loopback, link-local, reserved or multicast address | `failed`, `<host> resolves to a private address` |

A refused delivery is not retried. So `http://localhost:3000/hook` and `http://10.0.0.5/hook` work in development and are **refused in production**. Use a public HTTPS address, or a tunnel, for a receiver that sits on a private network.

### Which events to send

An endpoint's **Events** are patterns on the event name, the same as a subscription's. A few combinations:

| Events | Sends |
| --- | --- |
| `orders.*` | Every change to orders |
| `orders.created`, `orders.updated` | Creations and updates, not deletions |
| `*.deleted` | Every deletion, of everything |
| `*` | **Everything**, including platform events like `user.created` and `session.revoked` |

`*` is the default for a new endpoint. Narrow it, since every event the endpoint matches costs a delivery, and an endpoint that receives user and session events may receive more personal data than it needs.

### A safe webhook for a sensitive resource

Because a delivery's `data` is the raw record, do not point an endpoint at a resource with hidden fields. Send a **shaped** event instead:

1. Leave the endpoint's **Events** to a **custom** name, such as `public.vault.created`.
2. A flow with a **Resource change** trigger on `vault` builds a safe payload with a **Transform** block (`transform.map`, with a transformer that picks the fields to share).
3. The flow emits the custom event with that payload (the **Emit event** block, or the runtime's `emit`).
4. The endpoint, subscribed to `public.vault.created`, delivers only what the flow chose.

The raw event still reaches the event log and any other consumer, so it is not hidden, only kept off the wire to the third party.


## Realtime

A resource's **Broadcast changes** switch (*Push row changes to realtime subscribers.*) publishes each change to the channel **`resource:<name>`**, as the event `created`, `updated` or `deleted`, with the same payload as the event:

```json
{ "resource": "orders", "change": "created", "record": { "id": 12, "status": "new" } }
```

Realtime is **best effort**: if the realtime service cannot be reached, the failure is logged and the write is unaffected. A client that must not miss a change should treat realtime as a hint to re-read, not as the data.

The record is **raw**, as for every other consumer. Whoever may subscribe to `resource:<name>` receives hidden fields, so the channel's subscribe rule matters as much as the resource's own policy. Channel rules are set under **Settings → Realtime**, with a default policy of *authenticated*. A resource whose rows are private to their owners should either keep **Broadcast changes** off, or have a channel rule that admits only the right callers. See [Realtime](/realtime/overview).

A subscription can also publish an event to a channel of your choosing, with the target type **realtime**. That is the way to publish a **shaped** payload, or to a channel per tenant (`org:{{ event.payload.record.org_id }}`).


## What delivery guarantees you actually have

An event has to travel from the write to each consumer, and each hop has its own guarantee. Reading them together shows where an event can be late, repeated or missed.

| Hop | Guarantee | Notes |
| --- | --- | --- |
| **Write to event** | The event is published **after** the write succeeds, in the same request | It is **not** part of the database transaction. A crash between the write and the publish loses the event, and the row stays |
| **Event to the processor** | In development, in-process. With `PAWABASE_REDIS_URL` set, a durable Redis backlog with **at-least-once** delivery | Events published while the processor is down wait for it |
| **Processor to the log** | Each event id is recorded **once** | A repeat delivery of the same id is skipped |
| **Log to consumers** | Each consumer is **queued** as its own job | A slow or failing consumer does not hold up the others |
| **Consumer to completion** | A flow or function job retries per its own settings. A webhook delivery retries up to five times with backoff | A consumer that keeps failing ends up `failed` and is visible in **Events & runs** |

Three practical readings:

**Events can be late.** Consumers run from a queue, so a flow starts a moment after the write, not inside it. A client that writes a record and immediately reads something a consumer updates may read it too early. This was seen directly: after three comments were created, the post's counter, maintained by a flow, reached 3 only after the queue had run.

**Events can repeat, in the sense that a consumer may run again.** A flow job or a webhook delivery that fails after doing part of its work is retried, so the work may run twice. Consumers should be safe to run again (see [idempotent consumers](#idempotent-consumers)).

**Events can, in rare failures, be lost.** The publish is not in the write's transaction. If the process dies after the row is written and before the event is published, no event exists for that change. There is no outbox that replays missing events. If a consumer must never miss a change, treat events as a **prompt to reconcile**, and let it also read the source of truth on a schedule.

### Ordering

Events are published in the order the writes happened, but they reach consumers as **independent jobs**, which can run in any order and in parallel. So:

| Question | Answer |
| --- | --- |
| Are two events for the **same record** processed in order? | **Not guaranteed.** An `updated` flow can finish before the `created` flow of the same record |
| Across resources? | No |
| Can I rely on arrival order in a webhook receiver? | No. Use the record's `updated_at`, or a version field, to decide which state is newer |

An earlier version of this page promised ordering per record. The platform does not provide it. A receiver that applies events in the order it receives them can end up with an older state, so compare `record.updated_at` (or your own version number) before overwriting.

### What the event log keeps

Every processed event is recorded, with its payload, source, actor, request id and the **consumers** it was routed to and their status. The **Events** tab reads that log, newest first, and the API serves it at `GET .../events` and `GET .../events/<id>`.

The log itself is not a replay queue: there is no button that re-sends an **event** to every consumer. Replay works at the level of each consumer instead:

| To redo | How |
| --- | --- |
| A **webhook delivery** | The **Redeliver** button at the end of its row in **Webhook deliveries**. The toast reads *Redelivery queued* |
| A **flow run** or **function** that failed | **Jobs & queues**: open the job, and a failed or retrying one has a **Retry** button (*Retry queued*). The page is described as *Background work on Sillo's queue: flow runs, function calls, webhook deliveries, mail. Failed jobs retry with backoff, then land here.* |
| Everything an event would have done | **Emit test event** with the same name and payload, which routes it to every current consumer again |

The log is also data, with no documented retention period, so for a busy environment watch its size, and treat its payloads as sensitive: they contain the raw records, hidden fields included.


## Idempotent consumers

A consumer that can run twice must produce the same result. Four techniques, from easiest:

| Technique | How |
| --- | --- |
| **Recompute, do not increment** | A counter is set to `COUNT(*)`, not `count + 1`. Running twice gives the same answer. This is the recipe below |
| **Upsert by key** | Write a row keyed by the event id or the record id, so a second write replaces the first |
| **Check, then act** | Look for the result of a previous run before doing the work |
| **De-duplicate on the event id** | Store the ids you have handled, and skip a repeat. The webhook body's `id` is the event's id on every attempt |

For a webhook receiver, the last one is the standard:

```python
def handle(delivery):
    if already_processed(delivery["id"]):
        return 200                       # acknowledge a repeat, do nothing
    apply(delivery["data"])
    mark_processed(delivery["id"])
    return 200
```

Record the id in the same transaction as the effect, so a crash between them does not leave one without the other.
