<Steps>
  <Step title="Create a resource and a flow that listens">
    A `todos` resource with `title` and `done`, authenticated policies on every operation. A flow `on_todo` with a **Resource change** trigger on `todos` for `created` and `deleted`, and a **Transform** block that returns the event.
  </Step>
  <Step title="Add two subscriptions">
    One for `todos.*` with the condition `{"exists": "$event.data"}` (what **Only when…** fills in), and one for `todos.created` with `{"exists": "$event.payload.record"}`. Both target `on_todo`.
  </Step>
  <Step title="Create a todo through the API">
    `POST /rest/v1/todos` as `u-1`. The Events tab gained `todos.created` with the payload `{"resource": "todos", "change": "created", "record": {...}}`, the actor `u-1` and a request id. Its consumers were **two** flow runs: one from the **Resource change** trigger and one from the subscription whose condition read `$event.payload.record`. The `$event.data` subscription did not fire.
  </Step>
  <Step title="Update and delete it">
    The `updated` event had **no consumers**: the trigger listened for `created` and `deleted` only, and the `$event.data` subscription never matches. The `deleted` event had one consumer, and its record was the row **as it was before deletion**, with `"done": true`.
  </Step>
  <Step title="Send an invalid create">
    `POST` with no `title` answered `422`, and **no event** was recorded.
  </Step>
  <Step title="Create through the Records tab and through SQL">
    The Records-tab create published `todos.created` with the actor `studio` and no request id. An `INSERT` in the SQL window with **allow writes** published **nothing**.
  </Step>
  <Step title="Read the flow's input">
    Each run's input was `{"event": {"name": "todos.created", "project": "acme", "env": "development", "payload": {...}, "source": "api", "actor": "studio", ...}}`.
  </Step>
  <Step title="Hide a field and check the event">
    A `vault` resource with a `write_only` `secret` and a transformer that omits it returned no `secret` from the API. Its `vault.created` event's record contained `"secret": "hunter2"`.
  </Step>
  <Step title="Turn events off">
    A resource with **Emit events** off accepted a create, and the log had no new entry.
  </Step>
  <Step title="Emit a test event and add a webhook">
    **Emit test event** with `custom.test` and `{"kind": "x"}` was routed to a realtime subscription (`alerts:x`, which failed in this installation for lack of a realtime service) and to a webhook endpoint pointing at an unreachable address. The delivery showed `retrying`, with the error `ConnectError: All connection attempts failed`, and kept retrying beyond the `2` attempts the endpoint was set to.
  </Step>

## Choosing a consumer

| You want to | Use | Because |
| --- | --- | --- |
| Do something in Pawabase every time a record changes | A flow with a **Resource change** trigger | One flow, one resource, the simplest wiring |
| React to a family of events across resources | A flow with an **Event** trigger and a pattern | One flow for `*.deleted` |
| React only when the event matches a condition | A **subscription** with a condition | Filtered before anything is queued |
| Run Python | A subscription to a **function** | Functions are not triggers |
| Push to browsers and apps | **Broadcast changes**, or a subscription to **realtime** | Live clients |
| Tell another system | A **webhook** | Signed, retried, with a delivery log |
| Build a safe payload for a third party | A flow that emits a **custom event**, and a webhook on that | The raw event carries hidden fields |
| Keep two tables consistent | A flow that recomputes | Idempotent by construction |
| Keep a history | A flow that writes an audit resource, with its events off | Records what changed and when |
| Notify people | A flow with **Send mail** | Subject and body from the record |


## Volume and cost

Every write through Pawabase to a resource with events on does this extra work:

| Step | Cost |
| --- | --- |
| Publish the event | One bus message |
| Record it | One database row in the event log, holding the whole payload |
| Route it | One check per subscription, per flow trigger and per webhook endpoint |
| Each matching consumer | One queued job, and for a webhook one delivery row and one HTTP request |

A resource written 100 times a second with five consumers is 600 extra operations a second. That is fine for most workloads, and it is the reason to keep **Emit events** off for write-heavy resources nobody listens to, to narrow patterns (`orders.created`, not `*`), and to keep payloads small by keeping rows small.

The event log grows with every event. Watch it on a busy environment, and remember that each row holds a raw record.


## Custom events

Resource events are one kind of event. Your own flows, functions and the Events page can publish others, and the same consumers hear them.

| Publisher | How |
| --- | --- |
| A flow | The **Emit event** block (`event.emit`), with an `event` name and a `payload` |
| A function | `await ctx.runtime.emit("order.shipped", {...})` |
| Studio | **Emit test event** |
| The API | `POST .../events` with `{"name": ..., "payload": ...}` |
| An inbound hook | Verified third-party calls can be emitted as events |

### Naming

Resource events use `<resource>.<change>`. For custom events, follow the same shape, `<noun>.<verb>`, so that patterns keep working:

| Name | Reads as |
| --- | --- |
| `order.shipped` | An order was shipped |
| `invoice.paid` | An invoice was paid |
| `import.finished` | An import finished |
| `public.vault.created` | The shaped, public version of a vault creation |

Use the past tense, so the name states a fact that has happened. Avoid names that collide with a resource's own events: a custom event called `orders.created` is indistinguishable from the real one, and a consumer cannot tell them apart. Prefix custom domains instead, such as `shop.order_shipped`.

### A good payload

A payload is read by many consumers, some you have not written yet. Keep it:

| Property | Why |
| --- | --- |
| **Small** | It is stored in the log and sent to every endpoint. Send ids and the facts a consumer needs, and let it fetch the rest |
| **Self-contained for the common case** | A consumer should not have to fetch just to learn what happened. Include the new status, the amount, the id |
| **Free of secrets and personal data it does not need** | The log and every webhook keep it |
| **Stable** | Add keys freely. Do not rename or remove them. Consumers depend on them |
| **Versioned when it must change** | Add a `version` key, or a new event name |

Compare a resource event, which carries a whole raw row because it cannot know what you need, with a custom event, where you decide. For anything sent outside your system, prefer the custom event.


## A walkthrough: order created to customer notified

A shop wants three things to happen when an order is created: the stock is reduced, the customer is emailed, and the CRM is told. This is one way to build it from the pieces above.

<Steps>
  <Step title="Decide what the order resource announces">
    `orders` keeps **Emit events** on, so every creation publishes `orders.created`. It does **not** carry card or address data, so its raw events are safe to send within the system. The CRM, an outside party, will get a shaped event instead.
  </Step>
  <Step title="Reduce stock from a flow">
    A flow with a **Resource change** trigger on `orders` (operation `created`) reads the order's lines and writes the new stock. It recomputes the stock from its source of truth rather than subtracting, so a retry is harmless.
  </Step>
  <Step title="Email the customer from a subscription">
    A subscription for `orders.created` with the condition `{"exists": "$event.payload.record.email"}` runs a `notify_customer` flow, so the flow does not start for orders without an address. The flow sends mail with a template, filling it from `input.event.payload.record`.
  </Step>
  <Step title="Tell the CRM with a shaped event">
    A third flow, on `orders.created`, builds `{ "order": id, "total": total, "customer": customer_id }` with **Transform**, and emits `shop.order_created` with that payload. A **webhook** endpoint for the CRM is subscribed to `shop.order_created` only.
  </Step>
  <Step title="Watch it in Events & runs">
    Create an order. The **Events** tab shows `orders.created` with three consumers, then `shop.order_created` with one webhook. **Flow runs** shows the three flows, and **Webhook deliveries** shows the CRM delivery with its HTTP status.
  </Step>
  <Step title="Plan for failure">
    If the mail provider is down, the `notify_customer` run fails and appears in **Jobs & queues**, where **Retry** runs it again. If the CRM is down, the delivery retries with backoff and can be **Redeliver**ed. Neither failure touches the order, because the order was written before any consumer ran.
  </Step>
</Steps>

The properties of the design are the properties of the platform: the order write is fast, because consumers run later; each consumer fails and retries alone; the CRM never sees a raw order; and any of the three can be changed without touching the others.


## Testing a consumer

A consumer is a flow, a subscription or an endpoint, so a test emits an event and checks what happened. Use a development environment.

```python
import time
import requests

BASE = "https://api.example.com/platform/v1/projects/acme/envs/development"
HEADERS = {"Authorization": f"Bearer {OPERATOR_TOKEN}"}


def emit(name, payload):
    response = requests.post(f"{BASE}/events", headers=HEADERS, json={"name": name, "payload": payload})
    response.raise_for_status()
    return response.json()["event_id"]


def event(event_id):
    return requests.get(f"{BASE}/events/{event_id}", headers=HEADERS).json()


def wait_for(predicate, timeout=15):
    deadline = time.time() + timeout
    while time.time() < deadline:
        value = predicate()
        if value:
            return value
        time.sleep(0.5)
    raise AssertionError("timed out")


def test_big_orders_reach_the_review_flow():
    payload = {"resource": "orders", "change": "created", "record": {"id": 99, "total": 2500, "status": "paid"}}
    event_id = emit("orders.created", payload)

    consumers = wait_for(lambda: event(event_id)["consumers"])
    assert any(c["target"] == "review_order" and c["status"] == "queued" for c in consumers)

    runs = wait_for(lambda: [r for r in requests.get(f"{BASE}/flow-runs?limit=20", headers=HEADERS).json()["data"]
                             if r["flow"] == "review_order" and r["status"] == "succeeded"])
    assert runs
```

What the test shows: an event with the **same name and payload shape** as a real one is routed exactly as one would be, so it exercises conditions, triggers and endpoints. It does **not** exercise the write itself (validation, policy, the actor), so keep one end-to-end test that creates a real record.

Check three things for each consumer:

1. **It fires when it should**: the event's `consumers` lists it.
2. **It stays quiet when it should**: a payload that fails the condition leaves `consumers` empty.
3. **It does the right thing twice**: emit the same payload again and confirm the result is unchanged.


## A security review for events

| Question | What to check |
| --- | --- |
| **What is in the raw record?** | Hidden, `write_only` and undeclared columns are in it. Read one event's `payload.record` |
| **Who reads the event log?** | Anyone with operator access to the environment's Events tab. It holds raw records |
| **Where do webhooks go?** | Every endpoint receives raw records for the events it matches. Confirm each endpoint's owner and its **Events** list |
| **Is `*` used?** | A `*` endpoint receives user and session events as well. Narrow it |
| **Who may subscribe to the realtime channel?** | Its channel rule. The record in it is raw |
| **Can a consumer do more than it should?** | Flows run as the system and bypass resource policies. Review what each can write |
| **Is the receiver verifying signatures?** | On the raw body, with a five-minute tolerance |
| **Are secrets in payloads?** | Never put a secret in a custom event's payload |
| **Can a loop cost money?** | A loop that sends mail or calls a paid API repeats without bound. Add conditions and rate limits to anything that costs |
| **Is the signing secret safe?** | It is returned once. Store it as a secret, and rotate it by creating a new endpoint and removing the old |

### Rotating a webhook secret

The signing secret of an endpoint cannot be read back, so rotate by replacement:

1. Create a second endpoint with the same URL and events, and let Pawabase generate a secret. Store it.
2. Make the receiver accept **either** secret for a short time.
3. Remove the first endpoint.
4. Make the receiver accept only the new secret.

Alternatively, edit the endpoint and supply a new secret yourself (at least 16 characters), then update the receiver at the same moment.


## Reconciliation: when an event must not be missed

Events are best used as a prompt. For anything where a missed event is costly (money, stock, entitlements), pair them with a periodic check against the source of truth:

| Layer | Job |
| --- | --- |
| **Event** | Reacts within seconds |
| **Schedule** | Every hour or night, a flow recomputes the derived value from the table and writes it if it differs |
| **Alert** | The reconciliation counts the corrections it makes, and a rising count means events are being lost |

The counter recipe is already a reconciliation, since it recomputes. For a webhook receiver, the equivalent is a nightly list of the source's records since a checkpoint, compared with what the receiver has. See [Schedules](/jobs/schedules).

Events make a system responsive, and reconciliation makes it correct. Use both where it matters, and either alone where it does not.


## Tracing one change from write to consumer

Every step carries the **request id** of the write that started it, so you can follow a change end to end.

<Steps>
  <Step title="Start from the request">
    In **Observability**, find the write by its path (`/orders`). Open its **Request trace**. The HTTP request's notes list the events it published, such as `orders.created`, and the **Events** section of the trace shows them.
  </Step>
  <Step title="Open the event">
    On **Events & runs → Events**, find the event by name. Its **Actor** is the caller, and its `request_id` matches the trace you came from. Its **consumers** list says what it was routed to and whether each hand-off worked.
  </Step>
  <Step title="Follow a flow consumer">
    On **Flow runs**, find the run by flow name. Its **Trigger** is `event`, and its input is the event envelope. Open it for the step-by-step trace, with each block's input and output, and any error.
  </Step>
  <Step title="Follow a webhook consumer">
    On **Webhook deliveries**, find the delivery by endpoint and event. Its status, attempts, last HTTP status and error say where it stands. **Redeliver** sends it again.
  </Step>
  <Step title="Follow the chain">
    If the flow wrote a resource, that write published its own event, with a `request_id` of its own (or none, for a system flow). Look for the next event after the flow run, with the actor empty.
  </Step>
</Steps>

Three habits make this routine: **name flows for what they do** (so Flow runs reads like a sentence), **keep payloads small** (so the Events tab is readable), and **look at the consumers list first** (so you know within seconds whether the problem is "nothing was routed" or "the consumer failed").
