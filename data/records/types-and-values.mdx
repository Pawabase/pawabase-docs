## How types flow through a query

With a generated `Database` type, each resource has three types, and the client uses each in a specific place.

| Type | Used for | Example |
| --- | --- | --- |
| `Row` | What reads return | `get()`, list pages, `first()`, `create()` results |
| `Insert` | What `create` and `createMany` accept | Required fields are required; fields with defaults are optional |
| `Update` | What `update` accepts | Every field optional; nullable fields accept `null` |

Filter methods take column names from `Row`, and the value's type from that column.
A typo in a column name, or a string passed for a number column, is a compile error.

```typescript
orders.eq("status", "open");        // ok
orders.eq("staus", "open");         // error: "staus" is not a column
orders.gte("total_minor", "100");   // error: string is not number
```

`select` narrows the row type: selected columns keep their types and the rest become optional.
The returned type therefore tells you the truth about what was fetched.

```typescript
const page = await orders.select("id", "status").perPage(10);
page.data[0].status;       // "open" | "paid" | "cancelled"
page.data[0].total_minor;  // number | undefined in the type; null at runtime
```

`expand` does not change the row type, because the base resource type does not describe relations.
Type expanded fields yourself where you use them:

```typescript
import type { Row } from "./database";

type OrderWithCustomer = Row<"orders"> & { customer: Row<"customers"> | null };

const page = await orders.expand("customer").perPage(20);
const rows = page.data as OrderWithCustomer[];
```

`filter(column, op, value)` and `where` with arbitrary keys accept strings, for dynamic queries built from user input.
They are checked at runtime by the server instead of at compile time by TypeScript.


## Values by field type

The server accepts several input forms for some field types and always answers in one.
Knowing the answer form tells you what to expect in code.

| Field type | Send from TypeScript | Read back as |
| --- | --- | --- |
| `string`, `text`, `email`, `url` | `string` | `string` |
| `integer` | `number` (or a numeric string) | `number` |
| `number` | `number` (or a numeric string) | `number` |
| `boolean` | `boolean` | `boolean` |
| `datetime` | An ISO 8601 string or a `Date` serialized by you | An ISO 8601 string |
| `date` | `"YYYY-MM-DD"` | `"YYYY-MM-DD"` |
| `uuid` | A UUID string | A lowercase, hyphenated UUID string |
| `json` | Any JSON value | The same value |
| `array` | An array | An array |
| `object`, `ref` | An object | An object |

A `Date` object in a create or update body is serialized by `JSON.stringify`, which produces an ISO string in UTC.
That is what a `datetime` field expects.
For a `date` field, send the calendar day yourself, because a `Date` serialized at midnight local time can land on the previous day in UTC.

<CodeGroup>
```typescript TypeScript
const today = new Date().toISOString().slice(0, 10);
await pawabase.from("tasks").create({ title: "Pay rent", due_on: today });
```

```python Python
from datetime import date

pb.from_("tasks").create({"title": "Pay rent", "due_on": date.today()})   # sent as "YYYY-MM-DD"
```

```bash cURL
curl -X POST "$PAWABASE_URL/rest/v1/tasks" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"title": "Pay rent", "due_on": "2026-10-25"}'
```
</CodeGroup>

Integers in JavaScript are exact up to 2^53.
Integer primary keys and counters stay far below that in practice, but values copied from other systems, such as payment provider ids, may not.
Store such values in `string` fields.


## Ids

A resource's primary key is an integer, a UUID or a ULID, chosen when the resource is created.

| Id type | Looks like | Ordering | Good for |
| --- | --- | --- | --- |
| `integer` | `42` | Creation order | Internal tables created in one place |
| `uuid` | `3f2b8c1e-…` | Random | Ids that must not reveal volume or order |
| `ulid` | `01JB9C2W0Q…` | Creation order, as text | Ids created anywhere that still sort by time |

The client accepts ids as `string` or `number` and encodes them into the path.
Use `number` for integer keys and `string` for the others in application-defined resource types.

ULIDs sort by creation time as plain strings, which makes `order("id")` a cheap, stable "oldest first" and an ideal keyset for walking a table.
Integer ids sort the same way.
UUIDs do not sort meaningfully; use `created_at` with `id` as a tie-breaker instead.
