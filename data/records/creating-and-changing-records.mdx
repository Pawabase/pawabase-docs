## Creating a record

`create(row)` sends `POST /rest/v1/<resource>` and returns the created row.
The server answers `201` with the record as it was stored, including the fields it assigned.

<CodeGroup>
```typescript TypeScript
const order = await orders.create({ customer_id: "c_42", total_minor: 4200 });
console.log(order.id, order.status, order.created_at);
```

```python Python
order = orders.create({"customer_id": "c_42", "total_minor": 4200})
print(order["id"], order["status"], order["created_at"])
```

```bash cURL
curl -X POST "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"customer_id": "c_42", "total_minor": 4200}'
# HTTP/1.1 201 with the stored record
```
</CodeGroup>

What the returned row contains that your input did not:

| Field | Comes from |
| --- | --- |
| The primary key | Generated by the server: an integer, a UUID or a ULID, depending on the resource |
| `created_at`, `updated_at` | Set by the server when the resource has timestamps |
| Fields with defaults | The default declared on the field, when you did not send a value |
| The owner field | Set to the signed-in user's id when the resource declares one |

The owner field deserves attention.
When a resource names an owner field, the server sets it to the caller's user id on every create and ignores what you sent.
An anonymous caller with a publishable key cannot create a record in such a resource; the server answers `401`.
A secret-key caller can, and must then set the owner explicitly if one is wanted.

The server validates the body against the resource's fields before the policy runs:

| You send | Server answer |
| --- | --- |
| A missing required field without a default | `422`, one issue per field |
| A value of the wrong type | `422` |
| A value outside a field's constraints (length, range, pattern, enum) | `422` |
| A field the resource does not declare | `422` |
| A read-only field | `422`; read-only fields cannot be written |
| A valid body the `create` policy refuses | `403` (or `401` when signed out) |
| A value that breaks a unique field | `409` with code `unique_violation` and `details.columns` |
| A value that breaks another database constraint | `422` with code `constraint_violation` |

The client turns these into `ValidationError`, `PermissionError`, `AuthenticationError` and `ConflictError`, so form code reads naturally:

<CodeGroup>
```typescript TypeScript
import { ConflictError, ValidationError } from "@pawabase/client";

try {
  await pawabase.from("customers").create({ email, name });
} catch (error) {
  if (error instanceof ValidationError) return { fieldErrors: error.byField() };
  if (error instanceof ConflictError) return { fieldErrors: { email: ["An account with this email exists."] } };
  throw error;
}
```

```python Python
from pawabase import ConflictError, ValidationError

try:
    pb.from_("customers").create({"email": email, "name": name})
except ValidationError as error:
    return {"field_errors": error.detail}
except ConflictError as error:
    return {"field_errors": {column: ["An account with this email exists."] for column in (error.details or {}).get("columns", [])}}
```

```bash cURL
curl -i -X POST "$PAWABASE_URL/rest/v1/customers" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"email": "ada@example.com", "name": "Ada"}'
# 409 {"error": "unique_violation", "message": "A record with the same email already exists.", "details": {"columns": ["email"]}}
```
</CodeGroup>

Validation runs before the policy.
An anonymous request with an invalid body gets `422`, not `401`.
Do not read a `422` as "this caller would have been allowed".


## Updating a record

`update(id, patch)` sends `PATCH` with only the fields you pass.
Fields you leave out keep their values.

<CodeGroup>
```typescript TypeScript
const paid = await orders.update(orderId, { status: "paid" });
```

```python Python
paid = orders.update(order_id, {"status": "paid"})
```

```bash cURL
curl -X PATCH "$PAWABASE_URL/rest/v1/orders/$ORDER_ID" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"status": "paid"}'
```
</CodeGroup>

The server reads the existing record first, then checks the `update` policy against it.
That order produces a specific set of answers:

| Situation | Server answer |
| --- | --- |
| No record has this id | `404` |
| The policy refuses an anonymous caller | `404` |
| The policy refuses a signed-in caller | `403` |
| The patch sets a non-nullable field to `null` | `422` |
| The patch contains an undeclared or read-only field | `422` |
| The patch breaks a unique field | `409` |

Notice the asymmetry between anonymous and signed-in refusals.
A signed-out caller learns nothing about whether the record exists; a signed-in caller is told they may not change it.

The owner field cannot be changed through `update`.
The server drops it from the patch silently, so a record cannot be handed to another user through the data API.
If your application needs ownership transfer, do it in a flow or route that checks the rules you want.

### Setting a field to null

`null` and "not sent" mean different things in a patch.
Leaving a field out keeps its value; sending `null` clears it, if the field allows `null`.

<CodeGroup>
```typescript TypeScript
await orders.update(orderId, { note: null });  // clears the note
await orders.update(orderId, {});              // changes nothing; returns the record
```

```python Python
orders.update(order_id, {"note": None})   # clears the note
orders.update(order_id, {})               # changes nothing; returns the record
```

```bash cURL
curl -X PATCH "$PAWABASE_URL/rest/v1/orders/$ORDER_ID" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"note": null}'
```
</CodeGroup>

A field accepts `null` when it is declared nullable, or when it is not required.
A required field is not nullable unless the definition says so, and a patch that sends `null` for it is refused with `422`.


## Replacing a record

`replace(id, row)` sends `PUT`.
On Pawabase, `PUT` is handled exactly like `PATCH`: fields you leave out keep their values.
The method exists for code that prefers `PUT` semantics on the wire, not to clear unspecified fields.

<CodeGroup>
```typescript TypeScript
await orders.replace(orderId, { customer_id: "c_42", total_minor: 5000, status: "open", note: null });
```

```python Python
orders.replace(order_id, {"customer_id": "c_42", "total_minor": 5000, "status": "open", "note": None})
```

```bash cURL
curl -X PUT "$PAWABASE_URL/rest/v1/orders/$ORDER_ID" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" \
  -d '{"customer_id": "c_42", "total_minor": 5000, "status": "open", "note": null}'
```
</CodeGroup>

To clear a field, send it as `null`.
To return a record to defaults, send the default values explicitly.

`PUT` is also not listed in the OpenAPI document; the API Explorer shows `PATCH` for updates.
Prefer `update` in new code.


## Deleting a record

`delete(id)` sends `DELETE` and resolves with nothing.

<CodeGroup>
```typescript TypeScript
await orders.delete(orderId);
```

```python Python
orders.delete(order_id)
```

```bash cURL
curl -X DELETE "$PAWABASE_URL/rest/v1/orders/$ORDER_ID" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN"   # 204
```
</CodeGroup>

| Situation | Server answer |
| --- | --- |
| Deleted | `204` |
| No record has this id | `404` |
| The policy refuses an anonymous caller | `404` |
| The policy refuses a signed-in caller | `403` |

A `DELETE` is safe to repeat, so the client retries it after a network failure or a gateway error.
If the first attempt deleted the record before the connection failed, the retry gets `404`.
Treat `NotFoundError` from `delete` as success when your goal is "the record is gone":

<CodeGroup>
```typescript TypeScript
import { NotFoundError } from "@pawabase/client";

async function ensureDeleted(id: string) {
  try {
    await orders.delete(id);
  } catch (error) {
    if (!(error instanceof NotFoundError)) throw error;
  }
}
```

```python Python
from pawabase import NotFoundError

def ensure_deleted(record_id: str) -> None:
    try:
        orders.delete(record_id)
    except NotFoundError:
        pass
```
</CodeGroup>

Deleting a record does not delete records that refer to it.
Pawabase does not enforce referential integrity between resources, so a deleted customer leaves its orders behind, and expanding `customer` on those orders gives `null`.
Clean up related records in a flow triggered by the delete event, or in your own code.


## Creating many records

`createMany(rows, options)` creates records a few at a time and reports what happened to each.

<CodeGroup>
```typescript TypeScript
const result = await pawabase.from("contacts").createMany(rows, { concurrency: 5 });

console.log(`${result.created.length} created`);
for (const failure of result.failed) {
  console.error(`row ${failure.index} failed`, failure.error);
}
```

```python Python
result = pb.from_("contacts").create_many(rows)                 # one at a time on the blocking client
# result = await apb.from_("contacts").create_many(rows, concurrency=5)   # async client

print(f"{len(result.created)} created")
for index, error in result.failed:
    print(f"row {index} failed", error)
```
</CodeGroup>

| Option | Default | Meaning |
| --- | --- | --- |
| `concurrency` | `5` | Requests in flight at once |
| `stopOnError` | `false` | Start no new requests after the first failure |
| `signal` | none | Cancel the remaining requests |

`createMany` is not atomic.
Each row is its own request, so some can succeed while others fail.
The result lists the created rows in input order and the failures by input index.

If you need all-or-nothing, write the batch through a flow or a custom route that runs it as one server-side operation.
If you need a large import, the management module's `resources.importRecords` takes parsed rows in one request; see [Environment management](/clients/typescript/management/overview).

Keep concurrency modest.
Each request counts against the environment's rate limit, and five parallel requests already finish a thousand rows quickly.


## Concurrent edits

The data API does not lock records or compare versions.
When two requests update the same field, the later one wins.

For most fields this is fine, especially when forms send only changed fields.
For values that must not be lost, such as a stock count or a balance, do not compute the new value in the client and write it back.
Two clients reading 10 and writing 9 leave 9, not 8.

Move such changes into a flow or custom route that performs the read and the write together on the server, and call it from the client:

```typescript
await pawabase.routes.post(`products/${productId}/reserve`, { quantity: 1 });
```

If you need "edit only if unchanged since I loaded it", compare `updated_at` in that route before writing, and return `409` when it moved.


## Writes that reach other parts of the platform

A record written through the client is not only stored.
Depending on the resource's settings, the same write reaches other parts of the platform:

| Resource setting | What happens after your write |
| --- | --- |
| Events on | An event named `<resource>.created`, `<resource>.updated` or `<resource>.deleted` is emitted, with `{ resource, change, record }`. Flows, subscriptions and webhooks listening for it run. |
| Realtime on | The change is sent on `resource:<resource>` to each subscriber who may read the record. |
| A response cache | Cached answers for the resource are cleared. |

This is why many applications need very little server code.
The client writes a record; a flow subscribed to `orders.created` sends the confirmation email; a webhook tells the warehouse; realtime updates the dashboard.
See [Resource events](/data/resource-events/overview) and [Event subscriptions](/events/subscriptions).

Two kinds of writes do not publish events or realtime changes: SQL statements run in the **Data → SQL** console, and changes made directly in the database outside Pawabase.
If a screen depends on realtime, make changes through the API, a flow or the records view.
