The builder writes SQL from clicks, so that a statement can be correct before anyone types a word. Every click regenerates the text area, and the text area stays editable. It is a good way to start a statement and a poor way to finish one.

### The controls

| Row | Control | What it does |
| --- | --- | --- |
| **Action** | Select, Insert, Update, Delete | Chooses the statement type. Choosing anything but **Select** ticks **allow writes** for you. Choosing **Select** unticks it |
| **From** / **Table** | One chip per table | Picks the table. Switching tables clears columns, joins and conditions, and keeps the action |
| **Columns** (Select) | **All**, **Count rows**, then one chip per column | **All** is `*`. **Count rows** is `COUNT(*)`. Click columns to select exactly those |
| **Join** (Select) | A chip per suggested join, with a type picker **LEFT** or **INNER** | Joins along a foreign key, in either direction. Tables Pawabase created have none, so the row reads *No foreign keys to join along.* |
| **Values** / **Set** (Insert, Update) | One input per column, showing its type | The value for each column you fill in. An empty input is left out. A column's default or `NULL` shows as the placeholder |
| **Where** (Select, Update, Delete) | **Add condition**, then column, operator and value | Conditions, joined with **AND** or **OR** |
| **Order** (Select) | A column picker and **Ascending** or **Descending** | `ORDER BY` |
| **Limit** (Select) | A number, default 100 | `LIMIT` |

The operators are `=`, `!=`, `>`, `>=`, `<`, `<=`, `LIKE`, `NOT LIKE`, `IN`, `IS NULL` and `IS NOT NULL`. For `IN`, type the values with commas, `a, b, c`. For `LIKE`, the placeholder suggests `%text%`.

### What it generates

These were produced by running the builder's own statement composer. The table is `tickets`, on PostgreSQL.

Select everything (the starting point):

```sql
SELECT *
FROM "tickets"
LIMIT 100
```

Two columns, two conditions, ordered, limited:

```sql
SELECT "id", "subject"
FROM "tickets"
WHERE "status" = 'open'
  AND "priority" >= 2
ORDER BY "id" DESC
LIMIT 50
```

On MySQL the same click-through quotes with backticks:

```sql
SELECT `id`, `subject`
FROM `tickets`
WHERE `status` = 'open'
  AND `priority` >= 2
ORDER BY `id` DESC
LIMIT 50
```

Count rows, with an `IN`:

```sql
SELECT COUNT(*)
FROM "tickets"
WHERE "status" IN ('open', 'pending')
```

`OR` between conditions:

```sql
SELECT *
FROM "tickets"
WHERE "subject" LIKE '%login%'
  OR "status" IS NULL
LIMIT 100
```

An insert, with an apostrophe in a value escaped by doubling it:

```sql
INSERT INTO "tickets" ("subject", "status", "priority")
VALUES ('It''s broken', 'open', 2)
```

An insert with no values filled in:

```sql
INSERT INTO "tickets" DEFAULT VALUES
```

An update, scoped by a condition:

```sql
UPDATE "tickets"
SET "status" = 'solved'
WHERE "id" = 12
```

A delete, with and without a condition:

```sql
DELETE FROM "tickets"
WHERE "status" = 'spam'
```

```sql
DELETE FROM "tickets"
```

The second is what the builder produces when no condition has a value. It deletes every row, and the builder warns you under the **Where** row: *No condition: this affects every row.* Read that warning every time.

### How values are turned into SQL

The builder decides how to write a value from the column's type and what you typed.

| You type | Column type | Written as |
| --- | --- | --- |
| `12` | A numeric column (integer, real, float, double, numeric, decimal, serial) | `12` |
| `12` | A text column | `'12'` |
| `true` or `false` | A boolean column | `TRUE` or `FALSE` |
| `true` | Anything else | `'true'` |
| `null` (any case) | Any column | `NULL` |
| `It's` | Any | `'It''s'`. Apostrophes are doubled |
| (empty) | Insert or update | The column is left out |
| (empty) | A where condition | The condition is left out entirely |

That last row is a trap worth knowing: a condition with an empty value **disappears**. If you add a condition, forget to type its value, and run a delete, the statement has no `WHERE`.

### Two quirks to avoid

**Typing `null` with `=` writes `= NULL`.** SQL never matches that, so the query returns nothing:

```sql
SELECT *
FROM "tickets"
WHERE "subject" = NULL
LIMIT 100
```

To find nulls, pick the **IS NULL** operator, and leave the value empty.

**A boolean written as `true` against a text column is a string.** Choose the operator and value for the column's real type, and check the generated SQL before you run it.

### When to leave the builder

The builder covers one table, simple conditions and foreign-key joins. Leave it, and edit the text, for:

- Aggregates other than a count (`SUM`, `AVG`, `GROUP BY`, `HAVING`).
- Subqueries and common table expressions.
- Joins across tables with no foreign key. Pawabase creates none, so on a Pawabase-made database the join row never offers a join. Write them by hand.
- Dialect-specific catalogs and functions.
- Anything with `RETURNING` (a write answers with a row count, not the returned rows), or several statements (only one runs per click of **Run**).

Remember that your edits last only until the next click in the builder, so finish the statement last.


## Reads and writes: how the console decides

Every statement is parsed before it runs (with [sqlglot](https://github.com/tobymao/sqlglot), in the environment's SQL dialect), and the parse decides **which path** it takes, not only whether it is allowed.

| Class | Path | Result shape | Audited | Clears caches |
| --- | --- | --- | --- | --- |
| **Read** | Fetch rows, in a transaction the database holds read-only | `{"rows": [...], "truncated": false}` | No | No |
| **Write** | Execute and count | `{"rows": [], "affected": N}` | Yes, as `database.write` | Yes, every resource |

A statement is accepted only when the text parses into **exactly one** statement of one of these kinds:

| Kind | Examples | Class |
| --- | --- | --- |
| A query | `SELECT`, `WITH … SELECT`, `UNION`, `VALUES` | **Read**, unless anything inside it writes (a data-modifying `WITH`, `SELECT … INTO`, `FOR UPDATE`) |
| A describing statement | `EXPLAIN …`, `SHOW …`, `DESCRIBE t`, SQLite `PRAGMA` | **Read** |
| A data change | `INSERT`, `UPDATE`, `DELETE` | **Write** |
| A schema change | `CREATE`, `ALTER`, `DROP` | **Write** |

Anything else (two statements, `BEGIN`/`COMMIT`, `SET`, `SET ROLE`, `COPY`, `GRANT`, `VACUUM`, `ATTACH`, text that does not parse) is refused with `400` and the code `unsupported_sql`. A write without **allow writes** is refused with `400` and the message `this statement writes; set allow_write to run it`.

<Note>
**allow writes** does not turn a read into a write or the other way around. It is only permission. A clean `SELECT` with **allow writes** ticked still takes the read path and returns rows.
</Note>

### The database enforces the read path

The parser decides where a statement goes; the **database** decides what a read can do. A read runs like this:

| Database | How a read is held to reading |
| --- | --- |
| PostgreSQL | Inside a transaction started with `SET TRANSACTION READ ONLY` |
| MySQL | Inside `START TRANSACTION READ ONLY`, then rolled back |
| SQLite | With an authorizer on the connection that allows reading the main database, ordinary functions and inspecting pragmas, and refuses everything else |

So a write the parser cannot see is still stopped. A `SELECT` that calls a function which deletes rows, or `EXPLAIN ANALYZE DELETE …` (which executes the `DELETE`), fails on PostgreSQL with `cannot execute DELETE in a read-only transaction`, and nothing changes. On SQLite, `PRAGMA user_version = 5` or `PRAGMA writable_schema = 1` is refused even with **allow writes** ticked, and the inspecting pragmas (`table_info`, `index_list`, `foreign_key_list`, `integrity_check`, …) and the read forms of settings (`PRAGMA user_version`) work.

### Every case

| Statement | **allow writes** | What happens |
| --- | --- | --- |
| `SELECT 1 AS ok` | off | Read path, `{"rows":[{"ok":1}],"truncated":false}` |
| `-- note` newline `SELECT email FROM accounts WHERE email = 'a;b@x.io'` | off | Read path. Comments and a `;` inside a string are understood |
| `SELECT code FROM things WHERE code = ?` with `params: ["a"]` | off | Read path. Parameters work through the API |
| `EXPLAIN QUERY PLAN SELECT * FROM things WHERE code = 'a'` | off | Read path. The plan comes back as rows |
| `PRAGMA table_info(things)` | off | Read path. One row per column |
| `WITH gone AS (DELETE FROM things RETURNING id) SELECT * FROM gone` | off | **Refused**, `400`. The `DELETE` inside is seen |
| `SELECT 1; DELETE FROM things` | on | **Refused**, `400` `unsupported_sql`. Neither runs |
| `UPDATE things SET qty = 5 WHERE code = 'a'` | off | **Refused**, `400` |
| `UPDATE things SET qty = 5 WHERE code = 'a'` | on | Write path, `{"rows":[],"affected":1}` |
| `CREATE TABLE scratch_t (a INTEGER)` | on | Write path |
| `SET ROLE postgres` | on | **Refused**, `400` `unsupported_sql` |

### Which environment a statement can reach

On the platform's default PostgreSQL, environments share one database, one schema each. A `search_path` only says where unqualified names resolve, so the console does not run your SQL as the platform's own database user. It runs it as a **login role of the environment's own** (named `pb_sql_…`), which:

- may read, write and create in **its environment's schema**, and owns that schema's tables, so `ALTER TABLE` and `DROP TABLE` work on tables Pawabase made;
- is granted **nothing else**: `SELECT * FROM pb_other_schema.orders` and the platform's own tables in `public` answer `permission denied`;
- logs in as itself, so neither `SET ROLE` nor `set_config('role', …)` can switch back to the platform's user.

Pawabase creates the role the first time SQL runs for an environment and keeps it in step afterwards; its password is derived from `PAWABASE_MASTER_KEY`, so nothing new is stored. Creating it needs the platform's database user to hold `CREATEROLE` (the bundled Docker Compose user is a superuser, so it does). When the role cannot be made, the console answers `503` with the code `sql_isolation_unavailable` instead of running the SQL unconfined.

The same confined connection serves a function's raw SQL (`ctx.runtime.db()`, `ctx.runtime.transaction()`, `db_query`), so function code cannot reach another environment either.

| Setting | Values | Meaning |
| --- | --- | --- |
| `PAWABASE_SQL_ISOLATION` | `role` (default), `off` | `off` runs console and function SQL as the platform's user. Use it only on a single-tenant install where everyone with SQL access may read every environment |

An environment with its own database (`<ENV>_DATA_URL` or a project database binding) or a SQLite file is already separate, and runs on its own connection as before. The catalogue stays readable as on any PostgreSQL: another schema's **name** can be listed, its contents cannot.

### What access control still has to do

- **Treat a Studio login with Database access as a database login for that environment.** Within the environment, the console still bypasses field validation and policies; that is its job.
- **For a person who should only read, the console's read path is now enforced by the database**, but **allow writes** is a checkbox, not a permission. Give such a person a role without Database access, or a database role of their own.


## What a write does around the statement

A write runs, and then Pawabase does two things.

| After a successful write | Detail |
| --- | --- |
| **Audit** | An event `database.write` is recorded with the project, the environment and the SQL text **cut to its first 2,000 characters** |
| **Cache** | The cache tag of **every resource** in the environment is invalidated, because the console can change any table and Pawabase cannot tell which resource a statement touched |

And what it does **not** do:

| Not done | Consequence |
| --- | --- |
| No `resource.created`, `updated` or `deleted` event | Subscriptions, webhooks and flows triggered by those events never run |
| No realtime message | Connected clients are not told |
| No validation | Values outside enums, ranges and lengths are written |
| No policy check | Every row is reachable, whoever owns it |
| No `updated_at` change | A write does not touch it unless you set it |
| No rollback | A statement that succeeds is final |

A failed statement is not audited and does not clear caches, because nothing changed.

<Tip>
If something downstream must hear about a change, make the change through the API (or a flow) instead of the console. If you did it in the console, follow it with a write through the API for any record the downstream cares about.
</Tip>
