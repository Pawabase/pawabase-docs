A `set` value is a **template**: a string with `{{ ... }}` lookups. It is a lookup, not a language, and a small set of filters formats the result.

### What a template can read

| Name | What it is |
| --- | --- |
| `record` | The **original** row, before `omit` and `pick`, as the database returned it (after `select`, see below) |
| `auth` | The caller. `auth.authenticated`, `auth.kind`, `auth.user_id`, `auth.email`, `auth.roles`, `auth.permissions`, `auth.org`, `auth.org_role`, `auth.aal`, `auth.session_id`, `auth.claims` |
| `credential` | The API key or credential used |
| `request` | The request. `request.method`, `request.path`, `request.ip`, `request.params`, `request.query` |
| `project` | The project ref |
| `env` | The environment name |
| `input` | Always empty for a resource transformer |
| `now` | The current time, as an ISO datetime |

There is **no `auth.id`**. The caller's identifier is `auth.user_id`. A template that asks for `auth.id` finds nothing, and with `| default:"anon"` it answers `anon` for **everyone**, which was observed: a signed-in user with a valid token got `"by": "anon"` until the template was changed to `auth.user_id`.

The same definition, with `auth.user_id`, answered per caller:

```json
{ "uid": "anon",  "email": null,             "role": null,    "roles": 0, "authed": false }
{ "uid": "u-9",   "email": "maya@acme.co",   "role": "admin",  "roles": 2, "authed": true  }
```

from these templates:

```json
{
  "set": {
    "uid": "{{ auth.user_id | default:\"anon\" }}",
    "email": "{{ auth.email }}",
    "role": "{{ auth.roles | first }}",
    "roles": "{{ auth.roles | length }}",
    "authed": "{{ auth.authenticated }}",
    "method": "{{ request.method }}",
    "proj": "{{ project }}"
  }
}
```

### Paths

`record.title`, `auth.roles.0`, `request.query.page`. A dot walks into an object, and a number indexes a list. A path that is not found is empty.

### Whole values and embedded values

A template that is **the whole string** returns the value itself, with its type:

| Template | Result |
| --- | --- |
| `"{{ record.price_cents }}"` | `4900` (a number) |
| `"{{ record.is_live \| bool }}"` | `true` (a boolean) |
| `"{{ auth.roles }}"` | `["admin", "editor"]` (a list) |
| `"{{ record.nope }}"` | `null` |

A template **inside** a longer string is substituted as text:

| Template | Result |
| --- | --- |
| `"https://example.com/posts/{{ record.id }}"` | `"https://example.com/posts/1"` |
| `"a {{ record.nope }} b"` | `"a  b"` (a missing value is an empty string) |
| `"{{ record.title }} ({{ record.id }})"` | `"Hello (1)"` |

An object or list inside a longer string is written as JSON text.

### A trap: two templates side by side

A string that **starts** with `{{` and **ends** with `}}` is read as **one** template, even when it contains two. The text between the first `{{` and the last `}}` is then looked up as a single path, which does not exist, and the result is `null`:

```json
{ "set": { "display_name": "{{ record.first_name }} {{ record.last_name }}" } }
```

```json
{ "id": 42, "first_name": "Maya", "last_name": "Obi", "display_name": null }
```

This was run, and `"{{ record.price_minor }} {{ record.currency }}"` gave `null` the same way. There is no error. Put **literal text at the start or the end** and it works:

| Template | Result |
| --- | --- |
| `"{{ record.first_name }} {{ record.last_name }}"` | **`null`** |
| `"Name: {{ record.first_name }} {{ record.last_name }}"` | `"Name: Maya Obi"` |
| `"{{ record.first_name }} {{ record.last_name }}!"` | `"Maya Obi!"` |
| `"{{ record.title }} ({{ record.id }})"` | `"Hello (1)"` (it ends with a bracket) |

If you need exactly two values joined with nothing around them, use a Python transformer, or store the joined value in a column.

### Filters

A filter follows a pipe: `{{ record.title | upper }}`. Filters can be chained, and some take an argument after a colon.

| Filter | Does | Example |
| --- | --- | --- |
| `default:value` | Uses the value when the lookup is empty or `null` | `{{ record.nick \| default:"guest" }}` |
| `upper` | Upper case | `HELLO` |
| `lower` | Lower case | `hello` |
| `str` | Text, with `null` as an empty string | |
| `int` | Integer, `null` for empty | `{{ record.qty \| int }}` |
| `float` | Number, `null` for empty | |
| `bool` | Boolean | |
| `json` | JSON text of the value | |
| `length` | The length of a list or string, `0` for empty | `{{ auth.roles \| length }}` |
| `first` / `last` | The first or last item of a list | |
| `keys` | The keys of an object, as a list | |

The filter set is closed. Any other name is a mistake that only shows when a record is read: see [errors](#errors-at-read-time).

`now` is the current time when the response is built. Use it for values like "generated at":

```json
{ "set": { "served_at": "{{ now }}" } }
```

### Templates see the `select`ed record

When a caller sends `?select=title`, the record the transformer receives has only the selected columns, so a template that reads another column finds nothing. This was observed with a transformer whose `live` was `{{ record.is_live | bool }}` and `n` was `{{ record.price_cents | int }}`:

| Request | `live` | `n` |
| --- | --- | --- |
| `GET /rest/v1/posts/1` | `true` | `4900` |
| `GET /rest/v1/posts?select=title` | **`false`** | **`null`** |

The same template gave different answers because the column it reads was not selected. Either keep `set` templates to columns the caller always gets, or do not let callers `select` a resource whose transformer reads other columns.


## Where a transformer runs

| Response | Transformed? |
| --- | --- |
| `GET /rest/v1/<resource>` (each item of `data`) | Yes |
| `GET /rest/v1/<resource>/<id>` | Yes |
| `POST /rest/v1/<resource>` (the 201 body) | Yes |
| `PATCH /rest/v1/<resource>/<id>` (the 200 body) | Yes |
| `DELETE` | No body, so nothing to shape |
| The list **envelope** (`page`, `per_page`, `total`) | **No.** It stays as it is, whatever `case` says |
| An **expanded** related row | Yes, by the **related resource's own** transformer |
| A **custom route's** response | Yes, when the route has a transformer |
| A flow's `transform.map` block | Yes, for whatever the flow passes it |
| **Events, webhooks, realtime** | **No.** They carry the raw record |
| The **Database console** and the **Records tab** | **No.** They show raw rows |

Creating and updating go through the transformer too, so a client that posts `{"title": "Hi"}` gets back the shaped record, camelCase and all. A client that reads the 201 body to learn the id sees `id`, unless `id` was renamed.

### The list envelope

Only the records in `data` are transformed. This was observed with `case: "camel"`:

```json
{
  "data": [
    { "id": 1, "title": "Hello", "priceCents": 4900, "createdAt": "..." }
  ],
  "page": 1,
  "per_page": 1,
  "total": 2
}
```

`per_page` stays `per_page`. A client that expects an all-camel response must handle the envelope separately.

### Expanded rows keep their own shape

`?expand=` attaches related rows, and each related row is shaped by the **related resource's** transformer, after that resource's read policy has decided whether the caller may see it. With a `posts` resource that has a camel-case transformer, and an `authors` resource whose transformer omits `email` and uses camel case:

```http
GET /rest/v1/posts/1?expand=author
```

```json
{
  "id": 1,
  "title": "T",
  "authorId": 1,
  "createdAt": "...",
  "author": {
    "id": 1,
    "fullName": "Maya Obi",
    "createdAt": "..."
  }
}
```

The author's `email` is gone, because the author's own transformer omits it, and the author's keys are camel case because of **its** transformer. The parent's `case` converts the **name** of the `author` key, and does not reach inside it. If the related resource has no transformer, its rows come back as stored, whatever the parent does, so a camel-case parent can contain a snake-case child.

### Filtering, sorting and selecting use the original names

A transformer changes what a consumer **sees**. It does not change what a consumer **asks for**. Filters, `sort` and `select` always use the stored field names:

| Request | Result |
| --- | --- |
| `?filter[author_id]=eq.a1` (the original name) | Works, and returns the shaped record |
| `?filter[author_ref]=eq.a1` (the renamed name) | `400`, `cannot filter on unknown field 'author_ref'` |
| `?sort=-price_cents` | Works. A client that sees `priceCents` must still sort by `price_cents` |

Consumers of a renamed API therefore need to know both names. If that is a problem, do not rename. Document the stored name next to the response name.

### The OpenAPI document

A resource without a transformer publishes its response as a typed schema. A resource **with** one publishes the `200` response **without** a schema, because the shape is computed at runtime. This was observed in the environment's OpenAPI document: the `GET /rest/v1/posts/{id}` `200` response had no schema for a resource with a transformer, and generated clients get an untyped body. If you need typed clients, leave the transformer off and shape the record in a custom route whose response schema describes the result. A route that has a transformer drops its response schema, in the same way, so give a route one or the other.


## Errors at read time

A definition that saved can still fail when a record is read.

| Situation | What a read does |
| --- | --- |
| The resource names a transformer that **does not exist** | `500` with `{"error": "transformer_error", "message": "unknown transformer 'nope'"}` |
| A stored transformer is **deleted** while a resource still refers to it | The same `500`. Deleting is allowed, and the resource keeps pointing at the name |
| A `set` template uses an **unknown filter**, such as `{{ record.title \| nope }}` | A plain `500`, `Internal Server Error`, with no message |
| A `set` template names a **missing path** | No error. A whole-value template gives `null`, an embedded one an empty string |

Neither of the first two is caught when you save the resource. The save succeeds, and **every read of the resource** fails until you fix it. The recovery is immediate: restore the transformer under the same name, or change the resource's `transformer`. Because every request looks the name up, there is no restart and no cache to clear.

<Warning>
Delete a stored transformer only after nothing refers to it. There is no list of what uses a transformer, so search your resources and routes for the name first. A resource whose transformer disappeared fails **every list and get**, and a public endpoint doing that is an outage.
</Warning>


## Python transformers

A transformer that needs more than five steps can be written in Python and registered by name. The code lives with your project's other code:

```text
code/
  acme/
    transformers.py     # @transformer("public-order") ...
```

```python
from pawabase_core.transformers import transformer


@transformer("public-order")
async def public_order(record, context):
    return {
        "id": record["id"],
        "status": record["status"],
        "total": record["total_cents"] / 100,
        "placed_by_you": record["customer_id"] == context["auth"]["user_id"],
    }
```

A resource then uses it by name, exactly like a stored transformer:

```json
{ "name": "orders", "transformer": "public-order" }
```

A Python transformer receives each record and the template context (`auth`, `project`, `env` and so on), may be `async`, and returns the dict to send. When a name matches both a Python transformer and a stored one, **the Python one is used**. The code directory is part of your deployment, not of the environment, so a Python transformer is not promoted and is not edited in Studio. See Code.

Use Python when a record needs real logic: arithmetic, a lookup, a condition. Keep the five steps for everything else, because a declarative transformer can be read, edited and reviewed by anyone in Studio.
