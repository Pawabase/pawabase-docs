`handler_type: "function"` names a Python function that your project registers. Functions live in your project's code directory, which the API loads:

```text
code/
  acme/
    functions/
      billing.py       # @function("charge-order") ...
```

A function takes **one argument**, a context, and returns anything that can be written as JSON:

```python
from pawabase_core.functions import function


@function(
    "refund-order",
    description="Refund an order",
    policy="authenticated",
    input_fields=[
        {"name": "id", "type": "string", "required": True},
        {"name": "reason", "type": "string", "required": True, "max_length": 200},
    ],
    timeout=30,
)
async def refund_order(ctx):
    order_id = ctx.input["id"]
    reason = ctx.input["reason"]
    order = await ctx.runtime.resource_get("orders", order_id)
    ...
    return {"refunded": True, "order": order_id}
```

<Warning>
An earlier version of this page showed `async def refund_order(ctx, input)`. A function takes **only `ctx`**, and the payload is `ctx.input`. A two-argument function is called with one and fails.
</Warning>

### What the context holds

| Attribute | Meaning |
| --- | --- |
| `ctx.input` | The payload (see the next section) |
| `ctx.auth` | The caller's policy context: `authenticated`, `user_id`, `email`, `roles` and so on |
| `ctx.project`, `ctx.env` | Where the function is running |
| `ctx.trigger` | `http` for a route |
| `ctx.request` | For a route, `{"params", "query", "body", "headers", "client_ip"}`. For a direct call to the function, `None` |
| `ctx.runtime` | The platform's capabilities (resources, and the rest that flow blocks use) |
| `ctx.log(message, **data)` | Adds a log line to the invocation |

### What `ctx.input` is for a route

For a route, `input` is built from the payload, not passed as is:

| The request | `ctx.input` |
| --- | --- |
| `POST /plain/5?q=1` with body `{"a": 1}` | `{"id": "5", "a": 1}`. The path parameters and the body's keys, merged, and **the body wins** on a clash |
| `POST /plain/5` with body `[1, 2]` | `[1, 2]`. A body that is not an object **replaces** the input |
| `POST /plain/5` with no body | `{"id": "5"}`. The path parameters |
| `GET /plain/5?q=1` | `{"id": "5"}`. The query is **not** in `input` |

The query string is available only through `ctx.request["query"]`:

```json
{ "params": { "id": "5" }, "query": { "q": "1" }, "body": null }
```

### Validation of the input

A function can declare `input_fields`, and the merged input is validated against them in create mode, so required fields are enforced. This was run with `n` required and `id` declared:

| Request | Answer |
| --- | --- |
| `POST /fn/7` with `{"n": 3}` | `200`, the function runs with `{"n": 3, "id": "7"}` |
| `POST /fn/7` with `{}` | `422`, `{"error": "invalid", "message": "invalid function input", "details": [{"type": "missing", "loc": ["n"], ...}]}` |
| `POST /fn/7` with `{"n": "x"}` | `422`, the same shape, with an `int_parsing` detail |

Note that this `422` has a different shape from a bad **body**, which is a bare list. Two validations can apply to one request: the route's `input_fields` or `input_schema` first (the body), and the function's own `input_fields` (the merged input). See [what a bad request looks like](/data/custom-routes/who-may-call-a-route#errors-and-what-they-look-like).

### What a function's failures look like

| In the function | The route answers |
| --- | --- |
| It returns a value | `200` with the value as the body, **not** wrapped |
| It raises an exception | A plain `500`, `Internal Server Error`. The message is not returned |
| It runs longer than its `timeout` | `504`, `{"error": "timeout", "message": "function 'slow' exceeded 0.2s"}` |
| It is not registered | `404`, `{"error": "not_found", "message": "no function 'not_registered'"}`, on the first call. The route saved without complaint |

A function cannot choose its status or headers. If a route needs a `202` or a custom header, use a flow with `response.return`. If the logic must be Python, call the function from a flow, and let the flow answer.

### The function's own policy does not apply through a route

A function has a `policy` of its own (default `authenticated`). It is applied when the function is called **directly** at `/functions/v1/<name>`. When a **route** calls it, the route's policy decides, and the function's is not checked. This was run with a function whose policy is `deny`:

| Call | Answer |
| --- | --- |
| `POST /functions/v1/admin-only` as a signed-in user | `403`, `policy 'deny' refused` |
| `POST /rest/v1/adm`, a route with policy `public` that calls the same function | `200`, `"secret"` |

So **a route is a way around a function's policy**, deliberately or not. When a function is meant to be restricted, put the restriction on every route that calls it, and treat the route's policy as the real one.


## When to choose which

| | Flow | Function |
| --- | --- | --- |
| Edited in | Studio | Your code repository |
| Promoted with | **Promote** | Your deployment |
| Sets status and headers | Yes, with `response.return` | No |
| Errors with a code | Yes, with `error.raise` | A plain `500`, or a typed `FlowError` raised by your code |
| Needs a deploy to change | No | Yes |
| Can use any Python library | No | Yes |
| Best for | Orchestrating resources, mail, queues, webhooks | Real computation, a specific library, careful control of a transaction |

Start with a flow. Reach for a function when a flow cannot express the logic, and let a thin flow call it when you also need a status code or a header.


## The other doors: direct flows and functions

Routes are not the only way to run a flow or a function over HTTP. Two more endpoints exist, with different rules:

| Door | Path | Policy | Response |
| --- | --- | --- | --- |
| A function | `POST /functions/v1/<name>` | **The function's** `policy`, and the key's `functions:invoke` scope | `{"data": <result>}` |
| A flow | `POST /flows/v1/<name>` | The flow's `trigger.http` node's policy, default `authenticated` | The flow's `response.return`, or `{"data": <result>}` |

A flow is directly invocable only if it has a `trigger.http` node with **no path**. A flow with a path is served by a route instead. An unknown or path-bound flow answers `404`, `no directly invocable flow '<name>'`. A function that does not exist answers `404`, `no function '<name>'`.

The result of a direct function call is wrapped in `data`:

```json
{ "data": { "input": { "n": 1, "id": null }, "user": null, "trigger": "http", "request": null } }
```

and its `ctx.request` is `None`, because there was no route. Note `"id": null`: a declared field that the caller did not send arrives as `null`.

Both doors are part of the surface you expose. A flow or function that was written to be called by a route is **also** callable here, under its own policy, if it qualifies. Check the policy on each.


## The request body

How the body is read depends on the **method** and on whether the route declares an **input model**.

| Route | The body the handler sees |
| --- | --- |
| `GET`, `DELETE` | **Always `null`.** A body the client sends is ignored |
| `POST`, `PUT`, `PATCH` with `input_fields` or `input_schema` | The **validated** body, as an object |
| `POST`, `PUT`, `PATCH` **without** an input model | The parsed JSON, **unvalidated**. An object, a list or a string all pass through. Invalid JSON becomes `null` and the request still succeeds |

The last row was run. Without an input model, a body of `{"a": 1}`, `[1, 2]` and `"text"` reached the flow as sent, and the bytes `not json` reached it as `null`, with a `200`. A route with no model therefore accepts **anything** for its body. If the handler needs a shape, declare one.

### Declaring a shape: three choices

Studio's **Request body** control offers three:

| Choice | Stored as | Validates |
| --- | --- | --- |
| **Anything** | Nothing | Nothing |
| **Define fields** | `input_fields` | The body, with the rules of a resource `create` |
| **Use a schema** | `input_schema` | The body, against a stored schema, with one important difference below |

### `input_fields`: the strict one

The fields are compiled the way a resource's `create` body is, in create mode, and an unknown key is **refused**. All of this was run on a route with one required string `reason` with `max_length` 10:

| Body | Answer |
| --- | --- |
| `{"reason": "because"}` | Accepted |
| `{"reason": "way too long reason"}` | `422`, `String should have at most 10 characters` |
| `{}` | `422`, `Field required` for `reason` |
| `{"reason": "ok", "bonus": 1}` | `422`, `Extra inputs are not permitted` for `bonus` |
| No body at all | `422`, `Request body is not valid JSON` |

The `422` body is a bare list, one entry per problem:

```json
[
  {
    "type": "string_too_long",
    "loc": ["reason"],
    "msg": "String should have at most 10 characters",
    "input": "way too long reason",
    "ctx": { "max_length": 10 },
    "url": "https://errors.pydantic.dev/2.13/v/string_too_long"
  }
]
```

and a missing body is:

```json
[{ "loc": ["body"], "msg": "Request body is not valid JSON", "type": "json_invalid" }]
```

The field rules available are those of [Field types](/data/field-types/overview) and [Validation](/data/validation/overview): `required`, `max_length`, `minimum`, `enum`, `pattern`, nested objects and the rest.

### `input_schema`: documented strictly, enforced loosely

A stored schema can validate the body instead. It is the right choice when several routes, flows and resources share a shape. It does **not** behave like `input_fields` for `required`:

A route with `input_schema: "QuoteIn"`, where `QuoteIn` declares `items` as an integer that is required with a minimum of 1:

| Body | Answer |
| --- | --- |
| `{"items": 3}` | `200` |
| `{"items": 0}` | `422`, `Input should be greater than or equal to 1` |
| `{}` | **`200`**, the handler ran with `items` missing |

The minimum was enforced and the **required** flag was not. The generated documentation agrees with the behavior: `items` is shown as an integer **or null**, so the schema compiles with every field optional. Unknown keys are refused (`additionalProperties: false` in the document).

So with a schema, **check required values in the flow** (a `validate.schema` block, or a condition), or use `input_fields` where required fields matter. See [Schemas](/data/schemas/overview) for the full list of what a referenced schema does and does not enforce.

### Both kinds of `422` are bare lists

A bad body is a bare list, as for a resource create. A bad **function input** is an object with an `error` and `details`, because it comes from a different check. A bad **flow validation** (`validate.schema` inside a flow) is yet another shape. A client that talks to several routes should handle all three. See [what a bad request looks like](/data/custom-routes/who-may-call-a-route#errors-and-what-they-look-like).

### The body is validated before the policy

On a route with an input model, validation runs **before** the policy. A caller who is not signed in and sends an invalid body gets the `422`, with the field names; sent a valid body they get the `401`:

| Caller | Body | Answer |
| --- | --- | --- |
| Signed out | invalid | `422` with the details |
| Signed out | valid | `401`, `Authentication required` |
| Signed in | invalid | `422` |

This means the **field names and rules** of a protected route are visible to anyone who can reach it. They are not secret on a well-documented API, but if the shape itself is sensitive, do not rely on the policy to hide it.
