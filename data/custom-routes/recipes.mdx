The first three recipes below (the summary, the parameterised lookup and the validated write) were built and called, and the answers shown are what came back. The rest are patterns assembled from blocks that were run separately, so test them in your environment. The flows are shown as the nodes and edges Studio stores, which you can paste into a flow's **JSON** tab.

### A summary endpoint with SQL

A resource's API cannot group or total. A route backed by a flow with a **SQL query** can.

The flow, `summary`:

```json
{
  "nodes": [
    { "id": "start", "data": { "block": "trigger.http", "config": { "method": "GET", "path": "/summary" } } },
    { "id": "q", "data": { "block": "db.query", "config": {
        "sql": "SELECT status, COUNT(*) AS n, SUM(total) AS revenue FROM orders GROUP BY status ORDER BY status",
        "params": []
    } } },
    { "id": "r", "data": { "block": "response.return", "config": { "status": 200, "body": { "by_status": "{{ steps.q.output }}" } } } }
  ],
  "edges": [
    { "id": "e1", "source": "start", "target": "q" },
    { "id": "e2", "source": "q", "target": "r" }
  ]
}
```

The route:

```json
{ "method": "GET", "path": "/orders/summary", "handler": "summary", "policy": "public" }
```

Called with `GET /rest/v1/orders/summary`, it answered:

```json
{
  "by_status": [
    { "status": "new", "n": 1, "revenue": 5.0 },
    { "status": "paid", "n": 2, "revenue": 30.0 }
  ]
}
```

Three points. The query block returns a **list of row objects**, which the template passes through unchanged. The path `/orders/summary` sits next to the `orders` resource and was accepted, because a fixed segment is not the resource's own path, and a request to it reached the route. And the query reads the **raw table**, so it ignores the resource's policy: give the route the policy the data deserves. See [the SQL block's limits](#sql-in-a-flow-is-a-read-with-the-consoles-guard).

### A parameterised lookup

Never build SQL by joining text. Pass values as parameters:

```json
{ "id": "q", "data": { "block": "db.query", "config": {
    "sql": "SELECT COUNT(*) AS n, SUM(total) AS revenue FROM orders WHERE customer = ?",
    "params": ["{{ input.params.customer }}"]
} } }
```

With the route `GET /customers/{customer}/total`, a call for `a` returned `[{"n": 2, "revenue": 15.0}]`. A call whose path value was `a' OR '1'='1` returned `[{"n": 0, "revenue": null}]`: the value was treated as data, and matched no customer. The placeholder style is the database's (`?` on SQLite, `$1` on PostgreSQL, `%s` on MySQL), so write the query for the dialect the environment uses.

### A validated write

A route with no input model accepts any body, so validate inside the flow when the shape matters:

```json
{
  "nodes": [
    { "id": "start", "data": { "block": "trigger.http", "config": { "method": "POST", "path": "/place" } } },
    { "id": "v", "data": { "block": "validate.schema", "config": {
        "value": "{{ input.body }}",
        "fields": [
          { "name": "customer", "type": "string", "required": true },
          { "name": "total", "type": "number", "required": true, "minimum": 1 }
        ]
    } } },
    { "id": "c", "data": { "block": "resource.create", "config": {
        "resource": "orders",
        "data": { "customer": "{{ steps.v.output.customer }}", "status": "new", "total": "{{ steps.v.output.total }}" }
    } } },
    { "id": "r", "data": { "block": "response.return", "config": { "status": 201, "body": { "order": "{{ steps.c.output }}" } } } }
  ],
  "edges": [
    { "id": "e1", "source": "start", "target": "v" },
    { "id": "e2", "source": "v", "target": "c" },
    { "id": "e3", "source": "c", "target": "r" }
  ]
}
```

With a route of `POST /place` and the policy `authenticated`:

| Body | Answer |
| --- | --- |
| `{"customer": "c", "total": 7}` | `201`, `{"order": {"id": 4, "customer": "c", "status": "new", "total": 7.0, ...}}` |
| `{"customer": "c", "total": 0}` | `422`, the validation object below |
| `{}` | `422`, one detail per missing field |

```json
{
  "error": "invalid",
  "message": "validation failed",
  "details": [
    { "type": "greater_than_equal", "loc": ["total"], "msg": "Input should be greater than or equal to 1", "input": 0, "ctx": { "ge": 1.0 } }
  ]
}
```

This `422` is an **object**, unlike the bare list that `input_fields` produces. It is the shape of a flow's own validation. If you prefer one shape, put the fields in the route's `input_fields` and keep the flow for the work.

The `validate.schema` block cannot resolve a `ref` to a stored schema, so nested referenced objects are not checked there. See [Schemas](/data/schemas/overview).

### A webhook receiver

A third party calls your system with a callback. A custom route can receive it:

```json
{ "method": "POST", "path": "/hooks/payments", "handler": "payment-callback", "policy": "public", "rate_limit": { "limit": 60, "window": 60 } }
```

Because the route is public, the flow must **verify the caller itself**: a shared secret in a header, or a signature. A route's flow receives the payload `params`, `query` and `body`, but not the request **headers**, so a header-based check cannot be done in a route's flow. For callbacks that must be authenticated by a signature, use an **inbound hook** instead, which verifies signatures before running anything. See [Inbound webhooks](/webhooks/inbound).

Use a route for a callback only when it carries its own secret in the body or the query, and compare it in the flow against a stored [secret](/studio/secrets).

### An endpoint your servers call

A route that only your backend should call has the `service` policy and is called with a **secret key**:

```json
{ "method": "POST", "path": "/internal/recalculate", "handler": "recalculate", "policy": "service" }
```

A signed-in user's token is refused with `403`, and a publishable key cannot satisfy `service`. The secret key must stay on the server.

### A queued job that answers at once

A slow job should not hold the request open. A flow can start the work and answer `202` immediately with `response.return`:

```json
{ "id": "r", "data": { "block": "response.return", "config": {
    "status": 202,
    "headers": { "x-custom": "yes" },
    "body": { "queued": true }
} } }
```

The route answered `202` with that body and header in a run. Place the block after the step that **starts** the work, and give the client somewhere to poll (a `jobs` resource it can read, or a status route) so it can learn the outcome.

### A search with many optional filters

A resource filter has a fixed set of operators. A route can combine several optional filters in SQL and answer a list the resource could not:

```json
{ "id": "q", "data": { "block": "db.query", "config": {
    "sql": "SELECT id, title FROM articles WHERE (? IS NULL OR status = ?) AND (? IS NULL OR title LIKE ?) ORDER BY id DESC LIMIT 50",
    "params": [
      "{{ input.query.status }}", "{{ input.query.status }}",
      "{{ input.query.q | default:\"\" }}", "%{{ input.query.q }}%"
    ]
} } }
```

Keep a `LIMIT`, parameterise every value, and remember that an uncached search with free text is the kind of route to put behind a rate limit.


## SQL in a flow is a read, with the console's guard

The SQL block runs through the **same read-only check** as the Database console. It accepts a statement the check calls a read, and refuses one it calls a write. Two things follow:

- It is for **reads**. A flow that must change data uses the resource blocks (`resource.create`, `resource.update`, `resource.delete`), or `db.transaction` for several writes that must succeed together.
- The check looks for forbidden words only when they have **spaces on both sides**, so it is a safeguard against mistakes and not a guarantee against a hostile statement. Flow authors are trusted with the database; treat the permission to edit flows accordingly. See [Database console](/data/database-console/the-query-builder#reads-and-writes-how-the-console-decides).

A route's SQL also **skips the resource's policy and transformer**. Whatever the query selects is what the route can return, so select only the columns the caller may see.


## Versions: the same path in different environments

A route is part of the definitions, so it moves with the rest:

| Action | What happens to routes |
| --- | --- |
| **Promote** with `routes` (or with no `include`) | Each route is copied to the target by **method and path**. A route that exists there is overwritten, a new one is created |
| **Promote** | Never deletes. A route removed in the source stays in the target |
| A **release** | Includes the routes of the revision. A pinned `/rest/v2` serves the routes of its release |
| A flow or function the route names | Promoted separately. The route's definition only holds the **name** |

This was run: promoting `development` to `staging` with `include: ["routes"]` answered `{"from": "development", "to": "staging", "copied": {"routes": 2}}`, and staging then listed both routes, each pointing at its flow's name.

The consequence is the usual one for names: promote the **flows** with the routes, or the target has routes whose handler does not exist, and every call answers `500`, `missing_flow`. Promote everything (omit `include`) unless you are certain. For functions, deploy the code to the target environment's service before the route is called, or it answers `404`, `no function '<name>'`.


## Choosing between a route and its neighbours

Several features can answer an HTTP request, and they are not interchangeable.

| You want | Use | Why |
| --- | --- | --- |
| Create, read, update or delete one kind of record | A **resource** | Validation, policy, pagination, filtering, events and caching are already there |
| A different view of one resource's data | A resource with a **transformer**, or a second route | A transformer shapes; a route can query |
| An action that touches several records or services | A **route** with a flow | One endpoint, one policy, and the flow does the steps |
| A calculation, totals, a report | A **route** with a SQL or function handler | The resource API cannot aggregate |
| A callback from a third party that signs its requests | An **inbound hook** | It verifies the signature before running anything |
| A callback that carries its own token | A **route** with a public policy and a check in the flow | Headers are not available, so the token must be in the body or query |
| Work on a timetable | A **schedule** | No request is involved |
| A reaction to a record changing | An **event subscription** or a flow with a resource trigger | No client is waiting |
| An endpoint that must be callable only by your servers | A **route** with the `service` policy | A secret key, never in a browser |
| A public file or page | Storage or your own web server | A route returns JSON |

Two questions settle most choices. **Is a client waiting?** If not, it is not a route. **Is it one table with the usual operations?** If so, it is a resource.
