## Jobs

A **job** is one unit of background work: a flow started by an event, a webhook delivery, an email. It runs outside the request, so the caller gets a fast answer and the slow work has its own status, attempts and record.

### Start background work

In the flow editor (**Logic → Flows**), add a **Queue flow** or **Queue function** block. Both return as soon as the job is stored.

| Field | Meaning |
| --- | --- |
| **Flow** / **Function** | What to run |
| **Input** | Becomes the input of the dispatched work. Pass identifiers, not whole records |
| **Queue** | A queue name; default `default`. Use a separate name for heavy work (`bulk`) so it can't hold up quick work |
| **Delay** | Seconds before it may start (relative: "not before") |

The block's output is the job's id. Events also run subscribed flows as jobs.

### Job states

| Status | Meaning |
| --- | --- |
| `queued` | Waiting, or waiting out a delay |
| `active` | Running |
| `retrying` | An attempt failed; another is scheduled |
| `succeeded` | Finished |
| `failed` | Gave up |

A job gets **one attempt** by default. Retrying arbitrary business logic could charge a card twice, so Pawabase doesn't guess. In the flow editor add a **Retry** block around the part that can fail for a passing reason (attempts and a first wait), and make anything with side effects safe to repeat: check a marker first (a `receipt_sent_at` column is best).

### Read jobs in Studio

**Project → Activity → Jobs.** You see queue depth and counts per queue, and a table of jobs with status, queue and time. Open a job for its input, attempts and the error from the last one. Steady, low depth is healthy; growing depth means work arrives faster than it finishes; growing with many `retrying` means a dependency is down.

### Failures and replay

**Activity → Jobs → Failed.** For one job: read the error, then **Retry**. After an outage: filter (queue, kind, **since** minutes), use **Replay** with **Dry run** first to see the count, then run it. **Dismiss** removes a failure that needs no action. A retry reuses the original input and can't know how far the first attempt got: read the error before retrying, because a bug fails the same way again.

After an outage: read two or three errors, wait for recovery, dry-run the replay over the outage window, run it, then check again.

### Show progress to a person

Keep the state in a **record** (`status: "preparing"` → `"ready"`) that the job updates, and let the app read it or listen to it ([Live records](/realtime/record-changes)). Don't poll jobs from the browser.

## Schedules

A **schedule** runs something by the clock.

### Create one in Studio

**Logic → Schedules → New schedule.**

| Field | Meaning |
| --- | --- |
| **Name** | `nightly-rollup` |
| **Cron expression** | Five fields: minute, hour, day of month, month, day of week (0 is Sunday) |
| **Interval** | Or run every N seconds instead (at least 10). Choose cron or interval |
| **Time zone** | An IANA name such as `Europe/London`. Cron is read in this zone. Empty is UTC |
| **Run** | A **flow**, a **function**, or **emit an event** |
| **Payload** | Extra data for the target |
| **If the previous run is still going** | *Allow* another run, or *Skip* this one. Use skip for sweeps and syncs |
| **Catch up** | Run occurrences missed during downtime. Off by default |
| **Enabled** | Pause without deleting |

Use **Run now** on a schedule to test it. When it fires, the target receives `{ "scheduled_at": "…" }` with your payload: use `scheduled_at`, not "now", so a late run still works on the right window.

### Cron examples

| Expression | Fires |
| --- | --- |
| `*/5 * * * *` | Every 5 minutes |
| `0 * * * *` | Hourly |
| `0 3 * * *` | Daily at 03:00 |
| `0 9 * * 1-5` | Weekdays at 09:00 |
| `0 0 1 * *` | The first of each month |

**Prefer sweeps to delayed jobs.** Instead of one delayed job per invoice, run a short schedule that finds whatever is due (`due_at` passed and `reminded` false), handles it, and marks it. A missed run only delays things until the next one.
