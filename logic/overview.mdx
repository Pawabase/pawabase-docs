The [database](/database/overview) covers reading and writing records. Sometimes a button in your app needs to do more than that: charge a card, generate a report, send an email, create three related records at once, or call a partner's API with a secret you cannot put in a browser. That work belongs on the server, and **server logic** is how your app asks for it.

You write the logic once, in one of three forms, and your app calls it by name:

| Form | What it is | Call it with | Best for |
| --- | --- | --- | --- |
| **Function** | Code you wrote and deployed, in your project | `pawabase.functions.invoke("name", input)` | Anything you want to write as a program: payments, PDFs, calls to other services |
| **Flow** | A visual automation of steps and branches, built in the dashboard | `pawabase.flows.run("name", input)` | Multi-step processes you want to read and change without redeploying |
| **Route** | A custom URL under your API that runs a flow or a function | `pawabase.routes.post("orders/42/pay", body)` | Giving a feature a clean, REST-style address |

All three run **as the person who called them**. If a user is signed in, their identity is attached to the call, and the access rule on the function, flow or route decides whether they may run it. You never pass a user id in the request and trust it.

## Get started

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";

const pawabase = createClient({ url: "https://api.example.com", apiKey: "pb_pk_…" });
await pawabase.auth.signInWithPassword({ email, password });

// 1. A function: runs your code and returns what it returned
const receipt = await pawabase.functions.invoke<{ id: string; total: number }>("orders.create", {
  sku: "A1",
  quantity: 2,
});

// 2. A flow: runs the automation and returns its response
const welcome = await pawabase.flows.run("send-welcome", { name: "Ada" });

// 3. A route: a custom URL with a method and a path
const paid = await pawabase.routes.post("orders/42/pay", { method: "card" });
```

```python Python
from pawabase import Pawabase

pb = Pawabase("https://api.example.com", "pb_pk_…")
pb.auth.sign_in_with_password(email=email, password=password)

receipt = pb.functions.invoke("orders.create", sku="A1", quantity=2)

welcome = pb.flows.invoke("send-welcome", name="Ada")

paid = pb.routes.post("orders/42/pay", method="card")
```
</CodeGroup>

Each call returns what the logic returned, already parsed. If it fails, you get one of the standard [errors](/reference/errors).

## How a call travels

1. Your app calls the method. The client adds your API key and the signed-in user's token.
2. Pawabase checks the **access rule** on that function, flow or route against the caller.
3. If allowed, your logic runs on the server. It can use secrets, other services and the database, with whatever authority you gave it.
4. The result comes back to your app.

Because step 2 happens on the server, hiding a button is never your only protection. The rule is.

## Which form should I use?

- Choose a **function** when the work is naturally code: loops, libraries, calling an SDK, heavy computation.
- Choose a **flow** when it is a sequence of steps that other people on your team should be able to see and change, or when it uses built-in building blocks such as sending mail, publishing to a channel or emitting an event.
- Choose a **route** when you want the address to look like part of your API (`POST /orders/42/pay`) and when the same logic should be reachable from outside your app too, by anything that can make an HTTP request.

You can mix them: a route can run a flow, and a flow can call a function.
