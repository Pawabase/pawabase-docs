An **event** is a named announcement: `order.paid`, `user.signed_up`, `posts.created`. Something emits it, and anything subscribed reacts. The emitter never waits and never knows who is listening, so you can add a reaction later without touching the code that causes it.

## Get started

Emit an event from your server, then subscribe a flow to it.

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";
import { manage } from "@pawabase/client/manage";

const pawabase = createClient({
  url: "https://api.example.com",
  apiKey: process.env.PAWABASE_SECRET_KEY!,
  environment: "production",
});
const m = manage(pawabase);

// React to it: run the "send-receipt" flow whenever an order is paid
await m.subscriptions.create({
  name: "receipt-on-paid",
  event: "order.paid",
  target_type: "flow",
  target: "send-receipt",
});

// Announce it
await m.events.emit("order.paid", { order_id: "o_42", total: 1999 });
```

```python Python
import os
from pawabase import Pawabase

pb = Pawabase("https://api.example.com", os.environ["PAWABASE_SECRET_KEY"], environment="production")

pb.manage.subscriptions.create({
    "name": "receipt-on-paid",
    "event": "order.paid",
    "target_type": "flow",
    "target": "send-receipt",
})

pb.manage.events.emit("order.paid", {"order_id": "o_42", "total": 1999})
```
</CodeGroup>

## What an event is

Every event has the same shape, whatever emitted it. A flow triggered by an event receives it as `input.event`:

```json
{
  "name": "order.paid",
  "payload": { "order_id": "o_42", "total": 1999 },
  "id": "evt_3b8f1c2a",
  "source": "flows",
  "actor": "usr_abc",
  "occurred_at": "2026-09-30T14:02:11.342Z",
  "request_id": "req_7e9a1c"
}
```

| Field | Meaning |
| --- | --- |
| `name` | The event name, in the form `domain.action` |
| `payload` | The data you emitted, or the record for platform events |
| `id` | Unique per event. Use it to detect duplicates |
| `source` | What emitted it: `resources`, `flows`, `auth` and so on |
| `actor` | The user whose action caused it, or `null` for background work |
| `occurred_at` | When it happened, in UTC. The field is `occurred_at`, not `timestamp` |
| `request_id` | The request that caused it, to follow a chain end to end |

## What emits events

| Source | Events |
| --- | --- |
| Your data | `<resource>.created`, `.updated`, `.deleted` after every write |
| Authentication | `user.signed_up`, `user.signed_in`, `user.signed_out` and others |
| Your code | Any name you choose, from `events.emit` or a flow's `event.emit` block |

See the [catalog](/events/catalog) for the full list and payloads.

## What can react

| Reaction | What happens |
| --- | --- |
| A flow | Runs in the background with the event as `input` |
| A function | Runs in the background |
| A live channel | The event is published to a [realtime](/realtime/overview) channel |
| An outbound webhook | The event is POSTed to your URL with a signature. See [webhooks](/webhooks/outbound) |

One event can have many reactions, and each runs on its own. A slow or failing reaction never delays the others or the emitter.

## Delivery rules to design around

- **At least once.** A reaction may occasionally run twice for one event. Make reactions safe to repeat, and use the event `id` to skip a duplicate.
- **Per environment.** Events in `production` never reach subscribers in `development`.
- **Not storage.** Events carry identifiers and a little data. Put the facts in a record and the id in the event.
