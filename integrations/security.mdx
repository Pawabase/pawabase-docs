A connected product can create and delete projects and change everything inside them. This page explains how Pawabase limits that power, what each protection is for, and the part your product must play.

## What Pawabase does

### Credentials are stored as hashes

Pawabase stores only the SHA-256 hash of every long-lived credential:

| Credential | Format | Stored as |
| --- | --- | --- |
| Client secret | `pbs_` + 43 characters | Hash, plus its last 6 characters to tell secrets apart |
| Authorization code | `pbo_` + 43 characters | Hash |
| Refresh token | `pbr_` + 43 characters | Hash, plus its last 6 characters |
| Personal access token | `pbp_` + 43 characters | Hash, plus its last 6 characters |
| Claim link token | `pbk_` + 43 characters | Hash |

Each carries 256 bits of randomness. Someone who reads Pawabase's database can't use any of them. This is also why secrets and tokens are shown only once.

The fixed prefixes let secret scanners (GitHub's, GitLab's, `gitleaks`, `trufflehog`) recognise a leaked Pawabase credential in code or logs.

### Access tokens are short and scoped to one audience

OAuth and platform access tokens are signed JWTs that last **one hour**, with audience `pawabase-api`. They're accepted only by `/v1`. The dashboard's own API refuses them, so a leaked integration token can't be used to sign in to the dashboard, change billing, invite people or manage integrations.

Every request with an OAuth access token also looks up its connection: a disconnected connection fails at once, not when the hour is up.

### Refresh tokens rotate, and reuse ends the connection

Each refresh returns a new refresh token and spends the old one. If a spent one is ever presented again, Pawabase can't tell the real product from a thief who copied it, so it ends the **whole connection**. Whoever really holds it has to connect again; the thief's copy is dead.

The same applies to authorization codes: a code used twice ends the connection it created.

### PKCE

With PKCE, an intercepted code is useless without the verifier, which never leaves your server. Pawabase accepts only `S256` (the `plain` method is refused), and a code issued with a challenge can't be redeemed without the matching verifier, even with the client secret.

### Exact callback URLs

Pawabase only redirects to a callback URL registered for the app, compared exactly (only loopback ports may vary). A bad `client_id` or `redirect_uri` is answered with an error page, never a redirect, so Pawabase can't be used as an open redirector or to send codes to an attacker's site. Plain `http` is refused except on `127.0.0.1`, `localhost` and `[::1]`.

### Consent needs the right role

Approving write access needs an admin or owner of the organization; read access inside projects needs a member. A viewer can't hand a product power they don't have.

### Role is checked on every request

What a token can do is recalculated each time from the person's **current** role. Removing someone from the organization stops every product they connected, immediately.

### Rate limits on the token endpoint

`/oauth/token` and `/oauth/revoke` accept at most 300 requests a minute per client from one address and 1,200 a minute per address, counted across every Cloud worker. Floods and secret guessing are answered `429 slow_down`.

### Spent credentials are deleted

Authorization codes are deleted a day after they're made. Refresh tokens, personal tokens and claim links that were revoked, used or expired are deleted a month later. Live credentials are never touched.

### Confined to one project

Calls inside a project go through Cloud, which signs a request valid for five minutes and for one project. The project's server checks every path against an allow-list and refuses anything that reaches another project, another environment's promotion or previews, the runtime's audit log, or the environment's `infra` (where its database and storage are configured). Unknown paths are refused.

### Deletion protection

A project with deletion protection on can't be deleted or moved by any integration. Only a person can switch it off, in the dashboard.

### Everything is recorded

Connections, disconnections, apps, secrets, tokens, created keys and project changes are recorded in the organization's activity log, and changes inside projects are recorded under "\{person\} via \{app\}".

## What your product must do

<Warning>
Pawabase can't protect people from a product that leaks its own tokens. Most integration incidents are on the integrator's side.
</Warning>

### Keep secrets on the server

- The client secret, refresh tokens and access tokens live on your server only. Never send them to the browser, embed them in a mobile or desktop app, or put them in URLs.
- A desktop app or CLI that can't keep a secret should be a **public client**: leave the secret out and rely on PKCE. Don't ship the secret inside the app.
- Store tokens encrypted at rest in your database, with the key outside the database.
- Keep tokens out of logs: redact `Authorization` headers, token responses and query strings in your logging and error reporting.

### Always use state and PKCE

- Make a fresh random `state` per sign-in, keep it in the person's session, and compare it on the callback. Without it, an attacker can make a person's browser finish a sign-in the attacker started, connecting the **attacker's** organization to the **person's** account in your product (login CSRF). The person then builds in a backend the attacker owns.
- Make a fresh PKCE verifier per sign-in. Never reuse one.

### Bind the connection to the right user

When the callback succeeds, attach the tokens to the user who is **signed in to your product in that session**, and to the organization slug from the token response. Don't trust anything else in the query (there's nothing else in it), and don't look the user up by the email from `/v1/token`: a Pawabase email is not proof of identity in your product.

### Serialise refreshes

Two concurrent refreshes of the same connection end it (see [Reuse detection](/integrations/oauth-flow#reuse-detection)). Use one lock per connection, and re-read the stored tokens inside it.

### Ask for the least

Request only the scopes you use. Use separate apps for separate products, and separate apps (or at least separate secrets) for production and staging.

### Confirm destructive actions

Deleting a project deletes all its data, irreversibly. If your product can delete projects, pausing them, or deleting definitions, confirm with the person in your interface first, by name. If your product drives Pawabase with an AI model, don't let the model delete projects without a person's explicit confirmation.

### Treat Pawabase data as untrusted input

Project names, descriptions, table names, record values and flow output are written by people. Escape them before putting them in HTML, and never pass them to a shell or `eval`.

### Clean up on disconnect

When a person disconnects in your product:

1. call `/oauth/revoke` with the refresh token,
2. revoke any API keys you created in their projects,
3. delete the stored tokens.

### Handle 401 as "connect again"

A `401` from `/v1` means the connection is gone. Stop retrying, mark the connection as disconnected, and show "Connect again".

## If something leaks

| Leaked | Do this |
| --- | --- |
| Client secret | [Rotate it](/integrations/register-an-app#rotate-the-secret) at once. Existing connections continue; only the secret changes. For a platform app, review its organization's projects for changes you didn't make |
| Your database of refresh tokens | Rotate the client secret (so stolen refresh tokens can't be used without it), then ask affected people to reconnect. Refresh tokens used by the thief will end the connection on your next refresh |
| One person's tokens | Revoke the refresh token with `/oauth/revoke`; the person connects again |
| A personal access token | Revoke it in **Settings → Integrations** |
| A claim link | If it wasn't used yet, delete the project with your platform token and make a new one (and a new link) for the person. Any copy of the old link then answers `410` |
| An API key created through the API | Revoke or rotate it through the [Studio API](/integrations/project-api#api-keys) or in Studio |

If you find a security problem in Pawabase itself, report it privately to the Pawabase team rather than in public.

## Reference: lifetimes

| Item | Lifetime |
| --- | --- |
| Authorization code | 10 minutes, one use |
| OAuth access token | 1 hour |
| Refresh token | 30 days from issue, one use (each use gives a new 30 days) |
| Platform (`client_credentials`) access token | 1 hour, no refresh token |
| Signed request from Cloud to a project | 5 minutes |
| Personal access token | 1–365 days, or until revoked |
| Claim link | 7 days, one use |
| Client secret | Until rotated |
