Pawabase is a standard OAuth 2.0 authorization server. Your product uses the **authorization code** grant with **PKCE** (RFC 7636, `S256` only). Any OAuth client library that supports PKCE works. This page shows each step with the [SDK](/integrations/sdk) (`PawabaseOAuth`) and, next to it, the raw request it makes, so you know exactly what is sent.

The flow has four calls:

| # | Who | Call | Result |
| --- | --- | --- | --- |
| 1 | The browser | `GET /oauth/authorize?…` | Sign-in (if needed), consent screen, redirect to your callback with `code` |
| 2 | Your server | `POST /oauth/token` with `grant_type=authorization_code` | `access_token`, `refresh_token`, `organization` |
| 3 | Your server | `POST /oauth/token` with `grant_type=refresh_token` | A new pair, when the access token runs out |
| 4 | Your server | `POST /oauth/revoke` | The connection ends |

Steps 2–4 run **on your server**, never in the browser: they carry your client secret.

<Note>
Examples use `https://dashboard.pawabase.com`. A self-hosted Pawabase Cloud uses its own address; read it from `/.well-known/oauth-authorization-server` instead of hard-coding it.
</Note>

## Before you start

You need, from [Register an app](/integrations/register-an-app):

- the **client id** (`pbc_…`),
- the **client secret** (`pbs_…`), kept on your server,
- a registered **callback URL**, for example `https://app.example.com/oauth/pawabase/callback`.

## 1. Send the person to /oauth/authorize

Make two random values for this sign-in and keep them in the person's session on your server:

- **`state`**: at least 16 random bytes. You'll check it when they come back, so an attacker can't make their browser finish a sign-in it didn't start (CSRF).
- **`code_verifier`**: 43–128 characters from `A–Z a–z 0–9 - . _ ~`. Its SHA-256, base64url-encoded without padding, is the **`code_challenge`**.

Then redirect the browser to `/oauth/authorize`:

<CodeGroup>
```typescript TypeScript
import { PawabaseOAuth } from "@pawabase/client/cloud";

export const oauth = new PawabaseOAuth({
  clientId: process.env.PAWABASE_CLIENT_ID!,
  clientSecret: process.env.PAWABASE_CLIENT_SECRET!,
  redirectUri: "https://app.example.com/oauth/pawabase/callback",
});

export async function startSignIn(session: { pawabase?: { state: string; codeVerifier: string } }): Promise<string> {
  // Makes the state and the PKCE verifier (and its S256 challenge) for you.
  const pending = await oauth.authorize({ scopes: ["organizations:read", "projects:read", "projects:write", "project:read", "project:write"] });
  session.pawabase = { state: pending.state, codeVerifier: pending.codeVerifier };
  return pending.url; // redirect the browser here (302)
}
```

```python Python
import os

oauth = OAuth(
```

### Parameters

| Parameter | Required | Value |
| --- | --- | --- |
| `client_id` | Yes | Your app's client id |
| `redirect_uri` | Yes, unless the app has exactly one callback URL | One of the app's registered callback URLs, exactly (loopback URLs may use any port) |
| `response_type` | No (defaults to `code`) | `code`. Anything else is refused with `unsupported_response_type` |
| `scope` | No (defaults to every scope the app may ask for) | Space-separated [scopes](/integrations/scopes-and-roles). Order doesn't matter. Each must be one the app may ask for |
| `state` | Strongly recommended | Any string up to 500 characters. Returned unchanged |
| `code_challenge` | Recommended (required for public clients) | Base64url SHA-256 of your verifier: 43–128 characters of `A–Z a–z 0–9 - _` |
| `code_challenge_method` | With `code_challenge` | `S256`. `plain` is refused |

<Warning>
Without `code_challenge`, the code can only be traded with the client secret. With it, the code also needs the verifier. Always send it: if a code is intercepted on its way back to you (a malicious browser extension, a log, a proxy), the verifier is what stops it being used.
</Warning>

### What the person sees

1. **Signed out:** Pawabase's sign-in page. After signing in (including two-step verification if their account has it) they continue to step 2 automatically.
2. **The consent screen:** your app's name, logo and website, who registered it, one line per scope, and an **Organization** picker. The picker lists only organizations where the person's role is high enough for the scopes you asked for: viewer for read-only scopes, member for `project:read`, admin for any write scope. An organization already connected to your app is pre-selected and marked **connected**.
3. **No eligible organization:** the screen says which role is needed, and **Connect** is disabled. The person can only cancel.

### Coming back

Pawabase redirects the browser to your `redirect_uri` with query parameters:

| Outcome | Query |
| --- | --- |
| Approved | `?code=pbo_…&state=…` |
| Cancelled | `?error=access_denied&error_description=The+person+declined.&state=…` |
| A problem with the request (after the client and callback were checked) | `?error=invalid_scope` (or `unsupported_response_type`, `invalid_request`) `&error_description=…&state=…` |

Your callback's existing query string is kept: registering `https://app.example.com/cb?tenant=a` sends people to `https://app.example.com/cb?tenant=a&code=…&state=…`.

### When Pawabase does not redirect

If the `client_id` is unknown or the `redirect_uri` is not registered, Pawabase can't vouch for the address, so it never redirects. It answers the browser directly:

```json
HTTP/1.1 400 Bad Request
{"error": "invalid_client", "error_description": "No app has that client_id."}
```

```json
HTTP/1.1 400 Bad Request
{"error": "invalid_redirect_uri", "error_description": "That redirect_uri is not registered for this app."}
```

You'll see these during development, never in a correctly configured app.

## 2. Trade the code for tokens

In your callback handler:

1. If the query has `error`, show the person a message and stop.
2. Check that `state` equals the one in their session. If not, stop: this sign-in was not started by you.
3. `POST /oauth/token` with the code, the verifier and your client secret.

<CodeGroup>
```typescript TypeScript
import { OAuthError } from "@pawabase/client/cloud";

export async function finishSignIn(returnedUrl: string, session: { pawabase?: { state: string; codeVerifier: string } }) {
  const saved = session.pawabase;
  if (!saved) throw new Error("This sign-in was not started here.");
  delete session.pawabase; // a sign-in is used once
  try {
    // Reads ?code, ?state and ?error from the address, checks the state, and trades the code with PKCE and your secret.
    return await oauth.callback(returnedUrl, saved);
  } catch (error) {
    if (error instanceof OAuthError && error.code === "access_denied") return null; // the person pressed Cancel
    throw error;
  }
}
```

```python Python
from pawabase.cloud import OAuthError


def finish_sign_in(returned_url: str, session: dict):
    saved = session.pop("pawabase", None)  # a sign-in is used once
    if not saved:
        raise RuntimeError("This sign-in was not started here.")
    try:
        # Reads ?code, ?state and ?error from the address, checks the state, and trades the code with PKCE and your secret.
        return oauth.callback(returned_url, state=saved["state"], code_verifier=saved["code_verifier"])
    except OAuthError as error:
        if error.code == "access_denied":
            return None  # the person pressed Cancel
        raise
```

```bash cURL
curl https://dashboard.pawabase.com/oauth/token \
  -u "$PAWABASE_CLIENT_ID:$PAWABASE_CLIENT_SECRET" \
  -d grant_type=authorization_code \
  -d code=pbo_… \
  -d redirect_uri=https://app.example.com/oauth/pawabase/callback \
  -d code_verifier=$VERIFIER
```
</CodeGroup>

`callback` returns an `OAuthTokens` object: `accessToken`, `refreshToken`, `expiresAt`, `scope` and `organization` (in Python, snake_case). Save it with your user record; see [the SDK](/integrations/sdk#the-tokens-object).

### Request

`POST /oauth/token`, body as `application/x-www-form-urlencoded` (JSON is accepted too).

| Field | Required | Value |
| --- | --- | --- |
| `grant_type` | Yes | `authorization_code` |
| `code` | Yes | The `code` from the callback |
| `redirect_uri` | Recommended | The same `redirect_uri` used in step 1. If sent, it must match |
| `code_verifier` | If you sent a `code_challenge` | The verifier from the session |
| `client_id` | Yes (in Basic auth or the body) | Your client id |
| `client_secret` | Unless you used PKCE (in Basic auth or the body) | Your client secret |

**Client authentication.** Send the id and secret as HTTP Basic (`client_secret_basic`: `Authorization: Basic base64(client_id:client_secret)`), or as `client_id` and `client_secret` fields in the body (`client_secret_post`). Basic is preferred: bodies are logged more often than headers.

**Public clients.** A desktop app or CLI that can't keep a secret may leave `client_secret` out entirely and rely on PKCE (`token_endpoint_auth_method: none`). The code must then have been issued with a `code_challenge`, and the verifier must match. A code issued without a challenge needs the secret.

### Response

```json
HTTP/1.1 200 OK
Cache-Control: no-store
{
  "access_token": "eyJhbGciOiJIUzI1NiIs…",
  "token_type": "bearer",
  "expires_in": 3600,
  "refresh_token": "pbr_4vQ9…",
  "scope": "organizations:read projects:read projects:write project:read project:write",
  "organization": "acme"
}
```

| Field | Meaning |
| --- | --- |
| `access_token` | Send it as `Authorization: Bearer …` to the [Management API](/integrations/management-api). Valid for `expires_in` seconds |
| `token_type` | Always `bearer` |
| `expires_in` | 3600 (one hour) |
| `refresh_token` | Trade it for a new pair when the access token runs out. Valid for 30 days, used once |
| `scope` | The scopes granted. The same as asked for: the person approves all or nothing |
| `organization` | The slug of the organization the person picked. Pawabase's addition to the standard response, so you know which organization this connection is for without another call |

**Store tokens on your server**, next to your own user record and the organization slug. Treat both tokens like passwords. Never put them in the browser, in URLs or in logs.

### Rules for codes

- A code is valid for **10 minutes**.
- A code can be used **once**. Using it a second time fails **and ends the whole connection**, including the tokens the first use produced: a second use means someone else has the code. Don't retry the exchange on a network error; start the sign-in again instead.
- A code is bound to your client id and the `redirect_uri` it was issued for.

### Errors

Errors follow RFC 6749: `{"error": "...", "error_description": "..."}`, with `Cache-Control: no-store`.

| Status | `error` | Cause |
| --- | --- | --- |
| 401 | `invalid_client` | Unknown client id, or a wrong secret. The response carries `WWW-Authenticate: Basic realm="pawabase"` |
| 401 | `invalid_client` | No secret and the code had no PKCE challenge ("Send the client secret, or use PKCE.") |
| 400 | `invalid_grant` | The code is unknown, belongs to another app, was used already, has expired, the `redirect_uri` differs, the verifier doesn't match, or the person disconnected meanwhile |
| 400 | `unsupported_grant_type` | `grant_type` is not one of the three |
| 429 | `slow_down` | Too many requests: see [Limits](#limits) |

## 3. Refresh

An access token lasts an hour. When it runs out (or a minute before), trade the refresh token for a new pair. **Every refresh returns a new refresh token**; the old one stops working. Save the new one, replacing the old, before you use the new access token.

<CodeGroup>
```typescript TypeScript
import { OAuthError, PawabaseCloud, type OAuthTokens } from "@pawabase/client/cloud";

// A token source refreshes a minute before expiry and hands you each new pair to save.
export function connection(stored: { id: string; tokens: OAuthTokens }) {
  return new PawabaseCloud({
    token: oauth.tokenSource(stored.tokens, { onRefresh: (next) => db.connections.save(stored.id, next) }),
  });
}

// invalid_grant: the connection is gone (disconnected, expired, or a copy was used). Ask the person to connect again.
export const isGone = (error: unknown) => error instanceof OAuthError && error.needsReconnect;
```

```python Python
from pawabase.cloud import Cloud, OAuthError, OAuthTokens


def connection(stored) -> Cloud:
    # A token source refreshes a minute before expiry and hands you each new pair to save.
    source = oauth.token_source(OAuthTokens.from_dict(stored.tokens), on_refresh=lambda t: db.connections.save(stored.id, t.to_dict()))
    return Cloud(token=source)


def is_gone(error: Exception) -> bool:
    # invalid_grant: the connection is gone (disconnected, expired, or a copy was used). Ask the person to connect again.
    return isinstance(error, OAuthError) and error.needs_reconnect
```

```bash cURL
curl https://dashboard.pawabase.com/oauth/token \
  -u "$PAWABASE_CLIENT_ID:$PAWABASE_CLIENT_SECRET" \
```

| --- | --- | --- |

| `refresh_token` | Yes | The latest refresh token |

The response has the same shape as in step 2, with the scopes the connection holds now.

### Reuse detection

If a refresh token that was already exchanged is sent again, Pawabase assumes it was copied and **ends the whole connection**: every refresh and access token issued under it stops working, and the next refresh fails with `invalid_grant`. The person has to connect again.

This protects people if your database is leaked, but it also means **refreshing must be serialised** for each connection. If two of your workers refresh the same connection at once, one of them sends a refresh token the other just used, and the connection ends. Use a lock (a row lock, a Redis lock, a single-flight promise) around the refresh, and re-read the stored tokens inside the lock before refreshing.

<CodeGroup>
```typescript TypeScript
// The token source above already does this inside one Node process: concurrent callers share one refresh, and the new pair is
// saved (onRefresh) before it is used. Across processes, take a lock around the stored row.
export async function withConnection<T>(connectionId: string, work: (pawabase: PawabaseCloud) => Promise<T>): Promise<T> {
  return db.transaction(async (tx) => {
    const row = await tx.connections.lockForUpdate(connectionId); // SELECT … FOR UPDATE
    const source = oauth.tokenSource(row.tokens, { onRefresh: (next) => tx.connections.save(connectionId, next) });
    return work(new PawabaseCloud({ token: source }));
  });
}
```

```python Python
# One refresh at a time per connection, across processes, with a PostgreSQL row lock around the stored tokens.
def with_connection(db, connection_id: str, work):
    with db.transaction():
        row = db.fetchone("select tokens from pawabase_connections where id = %s for update", [connection_id])
        source = oauth.token_source(
            OAuthTokens.from_dict(row["tokens"]),
            on_refresh=lambda t: db.execute("update pawabase_connections set tokens = %s where id = %s", [t.to_dict(), connection_id]),
        )
        with Cloud(token=source) as pawabase:
            return work(pawabase)
```
</CodeGroup>

### When refreshing fails

| `error` | Meaning | What to do |
| --- | --- | --- |
| `invalid_grant` "The refresh token has expired." | Not refreshed for 30 days | Ask the person to connect again |
| `invalid_grant` "The refresh token was revoked." | Already used, or the connection was ended | Ask the person to connect again |
| `invalid_grant` "The connection was removed." | An admin disconnected your app, or you revoked it | Ask the person to connect again |
| `invalid_client` | Wrong secret (rotated?) | Fix your configuration; the connection is still fine |

A connection that is used at least once every 30 days never expires.

## 4. Revoke

When a person disconnects Pawabase in your product, end the connection on Pawabase's side too, so it disappears from their **Connected apps** list:

<CodeGroup>
```typescript TypeScript
import type { OAuthTokens } from "@pawabase/client/cloud";

export async function disconnect(tokens: OAuthTokens) {
  await oauth.revoke(tokens.refreshToken!); // ends the whole connection, so it leaves the organization's Connected apps list
}
```

```python Python
def disconnect(tokens: OAuthTokens) -> None:
    oauth.revoke(tokens.refresh_token)  # ends the whole connection, so it leaves the organization's Connected apps list
```

```bash cURL
curl https://dashboard.pawabase.com/oauth/revoke \
  -u "$PAWABASE_CLIENT_ID:$PAWABASE_CLIENT_SECRET" \
  -d token=pbr_…
```
</CodeGroup>

| Token sent | Effect |
| --- | --- |
| A refresh token | The whole connection ends: the grant is revoked and every token under it stops working |
| An access token | That access token and the refresh token issued with it stop working at once. The connection itself stays in the organization's **Connected apps** list; to use it again, send the person through the flow |
| Anything else | Nothing |

The answer is always `200 {}` for a known client, even for unknown tokens (RFC 7009), so revoking can't be used to test whether a token exists. A wrong client id or secret is `401 invalid_client`.

## Limits

`/oauth/token` and `/oauth/revoke` together accept up to **300 requests a minute per client id from one address**, and **1,200 a minute from one address** whatever the client id. Above that they answer `429` with `{"error": "slow_down"}` and a `Retry-After` header in seconds. A server refreshing many people's tokens stays far below this; if yours doesn't, refresh shortly before expiry rather than on every request.

## The access token

The access token is a signed JWT (HS256). You don't need to read it, and you can't verify it (the key is Pawabase's), but its claims are visible:

```json
{
  "iss": "pawabase-cloud",
  "aud": "pawabase-api",
  "sub": "01M7PX72DDFTCPN6APAWK0NBFS",
  "org": "acme",
  "scope": "organizations:read projects:read projects:write project:read project:write",
  "kind": "grant",
  "client_id": "pbc_YnlsTGxjACaabxvklZNh",
  "tid": "01M7QC775E0MAF2ZZKGHDA1YCN",
  "iat": 1795000000,
  "exp": 1795003600
}
```

Treat it as opaque in your code. To know who and what it represents, call [`GET /v1/token`](/integrations/management-api#who-am-i). Its audience is `pawabase-api`, so it is refused by the dashboard's own endpoints: a leaked integration token can't be used to sign in to the dashboard.

## Server metadata

`GET /.well-known/oauth-authorization-server` returns the RFC 8414 document. OAuth libraries that support discovery can be pointed at the issuer and find everything else:

```json
{
  "issuer": "https://dashboard.pawabase.com",
  "authorization_endpoint": "https://dashboard.pawabase.com/oauth/authorize",
  "token_endpoint": "https://dashboard.pawabase.com/oauth/token",
  "revocation_endpoint": "https://dashboard.pawabase.com/oauth/revoke",
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code", "refresh_token", "client_credentials"],
  "code_challenge_methods_supported": ["S256"],
  "token_endpoint_auth_methods_supported": ["client_secret_basic", "client_secret_post", "none"],
  "scopes_supported": ["organizations:read", "projects:read", "projects:write", "project:read", "project:write"]
}
```

## Using an OAuth library

Any standard library works. Configuration for common ones:

| Setting | Value |
| --- | --- |
| Authorization URL | `https://dashboard.pawabase.com/oauth/authorize` |
| Token URL | `https://dashboard.pawabase.com/oauth/token` |
| Revocation URL | `https://dashboard.pawabase.com/oauth/revoke` |
| PKCE | On, `S256` |
| Client authentication | `client_secret_basic` (or `client_secret_post`) |
| Scope separator | Space |
| ID token / OpenID Connect | Not offered. Call `GET /v1/token` for the person's id, email and name |

<Note>
Pawabase does not issue OpenID Connect ID tokens or offer a `userinfo` endpoint. If your library insists on OpenID Connect, configure it as plain OAuth 2.0 and fetch the profile from `/v1/token` after the exchange.
</Note>

## Connecting more than one organization

A connection is for one organization. A person in several organizations who wants all of them connected goes through the flow once per organization, picking a different one each time. Each run returns its own tokens and its own `organization`. Store connections keyed by `(your user, organization)`.

Going through the flow again for an organization that is already connected doesn't make a second connection: it updates the existing one with the new scopes and the new person, and issues new tokens. Tokens issued before keep working until they expire or are rotated.

## Asking for more scopes later

Start with what you need. When a feature needs more, send the person through `/oauth/authorize` again with the larger `scope`. The consent screen lists everything asked for, the organization is pre-selected (it is marked **connected**), and approving replaces the connection's scopes with the new list. Old access tokens keep their old scopes until they expire; use the new ones.
