Bachs ([bachs.io](https://bachs.io)) takes the payment. Pawabase's **Bachs integration** is everything between your app and Bachs that you would otherwise write yourself: starting a checkout, remembering the payment, receiving Bachs's webhook, checking it is genuine, and marking the payment paid only when Bachs agrees.

You install it once, from **Integrations** in Studio's sidebar: open **Bachs** in the list.

## How it is built

The logic is **Pawabase's own code**. It is not a flow, a route or a webhook in your project, so there is nothing in **Flows**, **Routes** or **Webhooks** to open, change or delete by accident, and a route of your own cannot take the place of its endpoints. The data is **yours**: two ordinary tables you can read, query and build on. And where your project needs its own rules, there are interfaces for them:

| You want to | Use |
| --- | --- |
| Limit currencies, amounts or where buyers are sent back | [Settings](#settings) |
| Price a payment on your server, or refuse one | A [before-start flow](#price-or-refuse-a-payment-on-your-server) |
| Do something when a payment is paid | An [event](#react-to-a-payment) and a flow of yours |
| Look at the payments | The `bachs_payments` table, or the **Payments** tab |

## Install it

<Steps>
  <Step title="Make a key in Bachs">
    In the Bachs Developer Portal, create a **secret key**. Give it the **View payments** and **Create & charge** scopes, and **Webhooks** (to have the webhook made for you). Use a sandbox key, `sk_sandbox_…`, while you build.
  </Step>
  <Step title="Paste it in Studio">
    Open **Integrations**, choose **Bachs**, paste the key, and choose **Install Bachs**. Pawabase checks the key with Bachs first, and installs nothing if Bachs refuses it.
  </Step>
  <Step title="Webhook">
    If your server is reachable over https, Pawabase creates the webhook endpoint at Bachs for you and keeps its signing secret. If not, it shows the address to give Bachs, and you paste back the signing secret.
  </Step>
  <Step title="Try a payment">
    **Start** on the Overview tab runs the same path your app will use, and gives you a real sandbox checkout link.
  </Step>
</Steps>

Installing never overwrites anything. If a table called `bachs_payments` or `bachs_events` already exists, it stops and says so.

The Bachs key and the webhook's signing secret are sealed and kept by Pawabase. They are not in your project's secrets, they are never shown again (only the start and end of the key), and they are only used from the server.

## The Bachs workspace

Once installed, the Bachs page in Studio has seven tabs.

| Tab | What it is for |
| --- | --- |
| **Overview** | What needs attention (payments to review, a webhook that is not connected), the numbers (payments, paid and the volume, waiting, to review), the latest payments, and a way to try one |
| **Payments** | Every payment, searchable by reference, email or description and filterable by status. Open one to see it in full, and to **Check with Bachs**, which settles it now exactly as the webhook would |
| **Events** | Each Bachs delivery that was handled and what was done about it (paid, flagged, ignored…). Open one to see its payload |
| **Webhook** | The address Bachs delivers to, how many genuine deliveries have arrived and when the last one did, which events it acts on, and how to create the endpoint again or paste a new signing secret |
| **Settings** | The rules you can set, and your before-start flow |
| **Connection** | Which key is in use, replacing it (Bachs checks the new key first), and disconnecting |
| **Build** | Code to call it from your app, the events to build flows on, and what is built in versus yours |

## What it adds to your project

| Kind | Name | What it is |
| --- | --- | --- |
| Table | `bachs_payments` | One row per payment. Only Pawabase's Bachs integration changes a payment's status; a signed-in person can read only their own rows |
| Table | `bachs_events` | Every Bachs delivery that was handled, so a repeat is recognised |

And what Pawabase serves for it, which is not a definition in your project:

| What | Where |
| --- | --- |
| Start a payment | `POST /rest/v1/bachs/payments` |
| Read a payment | `GET /rest/v1/bachs/payments/{reference}` |
| Bachs's webhook | `/hooks/v1/{env}/bachs` |

## Start a payment

Call the route as a signed-in person. The key never reaches the browser.

<CodeGroup>
```typescript TypeScript
const payment = await pawabase.routes.post("bachs/payments", {
  amount: "5000.00",
  currency: "NGN",
  email: "ada@example.com",
  success_url: "https://yourapp.com/thanks",
  idempotency_key: `order-${order.id}`,
});

window.location.href = payment.checkout_url;
```

```bash cURL
curl -X POST "$URL/rest/v1/bachs/payments" \
  -H "apikey: $PAWABASE_KEY" -H "x-project-id: $PAWABASE_PROJECT" \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H "content-type: application/json" \
  -H "Idempotency-Key: order-77" \
  -d '{"amount":"5000.00","currency":"NGN","success_url":"https://yourapp.com/thanks"}'
```
</CodeGroup>

| Field | | |
| --- | --- | --- |
| `amount` | required | A decimal string, such as `"5000.00"` |
| `currency` | required | Three letters, such as `NGN` or `USD` |
| `success_url` | required | Where Bachs sends the buyer after paying. Bachs adds `?checkout_id=…` |
| `email` | optional | Prefills the checkout. Without it the checkout asks |
| `name`, `description` | optional | Kept on the payment |
| `cancel_url` | optional | Where Bachs sends a buyer who leaves |
| `metadata` | optional | Any JSON, kept on the payment (your order number, say) |
| `idempotency_key` | recommended | Makes a retry safe: see [Retries are safe](#retries-are-safe). Or send it as an `Idempotency-Key` header |

The answer is `201` with `payment_id`, `reference`, `status` (`pending`), `checkout_url` and `expires_at`. Send the buyer to `checkout_url`.

Each payment gets its own `reference`, which is also sent to Bachs as the idempotency key, so a retry cannot start the same payment twice.

### Retries are safe

Networks drop responses and people double-click. Send an idempotency key with every payment you start, one per thing being bought (an order id works), and asking twice never makes two payments:

| You send | You get |
| --- | --- |
| The key for the first time | A new payment, `201` |
| The same key again, for the same payment | The payment the first request made, `200`, with an `Idempotent-Replayed: true` header and `"replayed": true` |
| The same key at the same moment as another request | One payment; the second request waits a moment and answers with it |
| The same key for a different payment (another amount, say) | `409` `idempotency_conflict`, and nothing is created |
| The same key after the first attempt failed because Bachs was unreachable | The same payment, finished: Bachs is asked with the same reference, so it is the same checkout |

A key is 1 to 128 letters, digits and `_ . : -`. It belongs to the person who sent it: two people using the same key do not collide. Whatever the key, Pawabase always tells Bachs which payment a checkout is for, so Bachs itself never creates two checkouts for one payment either.

## Know that it was paid

When the buyer comes back, ask:

```typescript
const { payment } = await pawabase.routes.get(`bachs/payments/${reference}`);
if (payment.status === "paid") unlockOrder();
```

If the payment is still `pending`, Pawabase asks Bachs before answering, so the result is right even when the webhook has not arrived. Only the person who started a payment can read it.

### How a payment is trusted

A payment becomes `paid` only after all of these:

1. **The delivery is genuine.** Bachs signs every delivery (HMAC-SHA256 of the timestamp and the raw body). Pawabase checks the signature and refuses anything unsigned, wrongly signed, or more than five minutes old, before anything else happens. During a secret rotation it accepts either secret.
2. **It is new.** Each Bachs event id is handled once. A repeat is acknowledged and does nothing.
3. **Bachs confirms it.** The delivery is only a nudge. Pawabase asks Bachs for the checkout, with your key, and requires that it is **completed** and **succeeded**.
4. **It is the right payment.** The checkout's reference and currency must be the ones recorded when the payment started, and its amount must equal the amount recorded (`5000` and `5000.00` are equal). If Bachs completed a checkout that does not match, the payment is marked `flagged` for you to review, and is never marked paid.
5. **It only moves forward, once.** Only a pending payment is settled, and the database moves it out of pending in a single step, so two deliveries, or a delivery and a read, arriving together cannot both mark it paid or announce it twice. A `paid` payment is never changed by a later delivery.

Nothing a browser, a redirect or a client can send changes a payment's status. The table has no create, update or delete route.

## Settings

Set these on the **Settings** tab. Every payment is checked against them before Bachs is asked, whether it came from your app or from the Studio test.

| Setting | Meaning | Default |
| --- | --- | --- |
| Accepted currencies | Such as NGN and USD. A payment in another currency is refused | any currency Bachs supports |
| Smallest and largest amount | A payment outside the range is refused | none |
| Allowed redirect hosts | `success_url` and `cancel_url` must be on one of these hosts | any |
| Checkout stays open for | Minutes, 1 to 1440 | 60 |
| Require the buyer's email | Refuse a payment started without one | off |
| Unpaid payments one person may have open | A person with this many unpaid payments cannot start another until one is paid or expires. `0` is no limit | 20 |

A refused payment answers `422` and says which rule it broke. Nothing is recorded, and Bachs is not asked.

## Price or refuse a payment on your server

Choose one of your own flows as the **before-start flow**. Pawabase asks it about every payment before the payment begins. Start it with a **Manual** trigger and end it with a **Respond** block (or **Fail** to refuse).

It receives `amount`, `currency`, `email`, `name`, `description`, `metadata`, `success_url`, `cancel_url`, `user_id` (who is paying) and `studio` (`true` for the Studio test payment). It may return:

| Return | Effect |
| --- | --- |
| `{"amount": "250.00", "currency": "NGN"}` | The payment is for that, whatever the buyer's browser said. Price from your own database here |
| `{"metadata": {"order_id": "…"}}` | Added to the payment's metadata |
| `{"allow": false, "message": "Sold out"}` | Refused with `403` and that message |
| A **Fail** block (`status`, `message`) | Refused with that status and message |

What it returns is held to the settings above. If the flow you chose is later deleted, payments stop with an error instead of starting without your rule.

## Security

What Pawabase does for you, always:

| Protection | How |
| --- | --- |
| Your Bachs key never leaves the server | It is sealed at rest, is not in your secrets, is never shown again (only its start and end), and is only ever sent to Bachs: the address is worked out from the key (`sk_sandbox_` or `sk_live_`), never read from anything stored |
| Forged deliveries are refused | Signature and age are checked first; anything unsigned, wrongly signed or older than five minutes is refused with `401` and does not even count as received |
| Nobody can fake "paid" | Only the built-in settling marks a payment paid, only after Bachs confirms it. The table has no create, update or delete route, so a client cannot write a status; the internal columns (idempotency key, tokens) are never returned |
| A person sees only their own payments | Reads are limited to the person who started the payment, and a reference cannot be guessed |
| Live means https | With a live key, `success_url` and `cancel_url` must be https |
| Replays do nothing | Each Bachs event id is handled once; settling is a single database step; see [Retries are safe](#retries-are-safe) |
| Abuse is slowed | Starting a payment is rate limited, and one person can only have a set number of unpaid payments open |

What is up to you, and shown on the **Overview** tab as a checklist:

- **Price on your server.** If you do nothing, the amount a buyer's browser sends is the amount charged. Choose a [before-start flow](#price-or-refuse-a-payment-on-your-server) that works the price out from your own data.
- **Limit return addresses** to your own hosts, so a payment cannot send buyers elsewhere afterwards.
- **Limit currencies and amounts** to what you really accept.

## Payment statuses

| Status | Meaning |
| --- | --- |
| `pending` | Started; waiting for the buyer. A failed card attempt leaves it pending, because the checkout stays open for another try |
| `paid` | Bachs confirmed it, and the amount, currency and reference matched |
| `flagged` | Bachs completed the checkout but the amount, currency or reference does not match. Look at it before doing anything |
| `expired` | The checkout expired unpaid |
| `cancelled` | Cancelled before it was completed |
| `failed` | Bachs refused to create the checkout |

## React to a payment

Pawabase emits an event for each outcome. Build a flow that starts on it (a `trigger.event` block) to fulfil the order, send a receipt, or grant access.

| Event | When |
| --- | --- |
| `bachs.payment.created` | A payment was started and has a checkout |
| `bachs.payment.paid` | A payment was confirmed |
| `bachs.payment.flagged` | A completed checkout did not match |
| `bachs.payment.expired` | A checkout expired |
| `bachs.payment.cancelled` | A checkout was cancelled |

Each carries `reference`, `payment_id`, `user_id`, `email`, `amount`, `currency`, `status` and your `metadata`.

## Going live

Install with a sandbox key while you build. When you are ready, open **Connection**, paste the live key and choose **Replace key**: Bachs checks it first, and Pawabase switches to Bachs's live address with it. Bachs's sandbox and live environments share nothing, so then open **Webhook** and create the endpoint again for live.

## Disconnecting

**Connection → Disconnect** stops the payment endpoints and refuses Bachs's webhook. Your two tables and every payment in them are kept, and you can install again later.

## If something does not work

| You see | Because |
| --- | --- |
| "Bachs does not accept this key" | The key is wrong, or it is a live key against the sandbox, or the reverse |
| "This key can't read or create payments" | The key lacks the payments scopes |
| "Bachs can't be installed here because these are already in use" | A table called `bachs_payments` or `bachs_events` exists. Rename or remove it |
| The webhook says "manual" | Your server is not reachable over https from the internet, or the key can't manage webhooks. Add the endpoint in Bachs and paste its signing secret |
| A payment stays `pending` after paying | Look at the **Events** tab for the delivery, and the **Webhook** tab for the count of genuine deliveries. Reading the payment through the route, or **Check with Bachs**, also settles it |
| `502 bachs_unavailable` | Pawabase could not reach Bachs to confirm. Nothing was marked paid; try again |

## Not covered yet

This integration takes one-off payments. Subscriptions, refunds and payouts are separate Bachs features that it does not use yet.
