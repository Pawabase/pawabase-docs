description: "Reshape records on the way out: omit and keep fields, add computed values, rename keys and change key case, defined once and reused."

A **transformer** turns a stored record into what a consumer should see. Use it to hide internal columns, add a computed link, or match the key style your front end expects, **without changing the table** and without writing code. The same transformer applies to every record the API returns for a resource, including records inside `expand` and in realtime messages.

## In Studio

**Data → Tools → Transformers → New transformer.** *Applied in this order to every record a consumer receives.* The editor has five numbered steps:

| Step | Field | Meaning |
| --- | --- | --- |
| **1 · Omit fields** | list of field names | Removed from the output, such as `password_hash` |
| **2 · Keep only** | list of field names | When set, every other field is dropped |
| **3 · Set values** | name → value | Add or overwrite fields. Values may use `{{ record.field }}` templates |
| **4 · Rename** | old name → new name | Change a key |
| **5 · Key case** | `camel` or `snake` | Convert every key |

Name it (`public_post`), save, then attach it to a table: **Settings → Transformer**, choose it from the list. A **Preview** shows a sample record before and after.

## In code

<CodeGroup>
```typescript TypeScript
await m.transformers.create({
  name: "public_post",
  description: "What the public site shows",
  definition: {
    omit: ["internal_notes"],
    pick: ["id", "title", "author_id", "created_at"],
    set: { url: "https://example.com/posts/{{ record.id }}" },
    rename: { author_id: "authorId" },
    case: "camel",
  },
});

await m.resources.replace("posts", { ...(await m.resources.getOne("posts")), transformer: "public_post" });
```

```python Python
pb.manage.transformers.create({
    "name": "public_post",
    "definition": {
        "pick": ["id", "title", "author_id", "created_at"],
        "set": {"url": "https://example.com/posts/{{ record.id }}"},
        "rename": {"author_id": "authorId"},
        "case": "camel",
    },
})
```
</CodeGroup>

The steps always run in this fixed order: `omit`, `pick`, `set`, `rename`, `case`. Only these five are accepted; an unknown step or a wrongly typed argument is refused when you save (`omit` and `pick` take lists, `set` and `rename` take objects, `case` is `camel` or `snake`).

A transformer can also be written inline on the resource (an object instead of a name).

## Example

Stored record:

```json
{ "id": "01J…", "title": "Hello", "author_id": "u_1", "internal_notes": "…", "created_at": "2026-10-01T10:00:00Z" }
```

With the transformer above, your app receives:

```json
{ "id": "01J…", "title": "Hello", "authorId": "u_1", "createdAt": "2026-10-01T10:00:00Z", "url": "https://example.com/posts/01J…" }
```

Note the order: `pick` ran before `set`, so `url` was added after the others were filtered; `rename` then `case` changed the keys.

## What a transformer does not do

- It doesn't change what is **stored** or what **writes** accept. Use columns ([read only](/database/columns-and-types#flags) and write only) for that.
- It isn't security. Hide secrets at the source: mark the column **write only**, or protect it with access rules. A transformer is a presentation layer.
- Anything more complex (joins, calculations from other tables) is better done in a [route](/logic/routes) or a flow.

## Where it applies

| Place | Transformed? |
| --- | --- |
| List and get responses | Yes |
| The record returned by create and update | Yes |
| `expand` (the related resource's own transformer) | Yes |
| Realtime messages for the table | Yes |
| Studio's table editor | No: you see the stored record |

## Tips

- Name transformers by audience (`public_post`, `admin_post`), not by table.
- Prefer `pick` (allow-list) over `omit` (deny-list) for anything public. A new column then doesn't leak by default.
- With `case: "camel"`, remember your **filters and writes** still use the stored (snake case) names.
