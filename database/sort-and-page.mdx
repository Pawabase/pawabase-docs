A list comes back one **page** at a time, in the order you ask for. This page covers both, and how to go through a large result without loading it all at once.

## Sort

<CodeGroup>
```typescript TypeScript
pawabase.from("posts").order("created_at", "desc");                              // newest first
pawabase.from("posts").order("pinned", "desc").order("created_at", "desc");      // pinned first, then newest
pawabase.from("people").order("last_name").order("first_name");                  // ascending is the default
```

```python Python
pb.from_("posts").order("created_at", "desc")
pb.from_("posts").order("pinned", "desc").order("created_at", "desc")
pb.from_("posts").order("-created_at")            # a leading "-" also means descending
```
</CodeGroup>

- Each `order` after the first breaks ties in the earlier ones.
- Without any `order`, records come in id order. Always sort lists you show, so the order means something.
- Sorting on an unknown column answers `400` "cannot sort on unknown field". Sorting on a **write only** column is refused too.
- Text sorts in the database's collation: `"Zoe"` before `"adam"` is possible, because upper case can sort first. For a case-insensitive order, sort a lower-case copy of the column.
- `null` values sort **last** in ascending order and **first** in descending order (PostgreSQL's rule).

A search with no `order` comes back best match first. Add an `order` and it wins over relevance.

## Page size and number

<CodeGroup>
```typescript TypeScript
const page2 = await pawabase.from("posts").order("created_at", "desc").perPage(25).page(2);
page2.page;       // 2
page2.per_page;   // 25
page2.total;      // matching records, or null
page2.data;       // records 26 to 50

pawabase.from("posts").limit(10);   // limit is the same as perPage
```

```python Python
page2 = pb.from_("posts").order("created_at", "desc").per_page(25).page(2).execute()
page2.page, page2.per_page, page2.total
page2.has_next                     # whether a page 3 exists

pb.from_("posts").limit(10)        # limit is per_page
```
</CodeGroup>

| Setting | Allowed | Default |
| --- | --- | --- |
| `page` | 1 and up | 1 |
| `perPage` / `per_page` / `limit` | 1 to 200 | 20 |

A value outside the range answers `422`. A page past the end returns an empty `data` list, not an error.

`total` is the number of matches **for this caller**, or `null` when a per-row access rule means the server can't count them. See [What total means](/database/read#what-total-means).

Python's `has_next` is `page × per_page < total` when the total is known, and "this page was full" when it isn't.

## Turn paging off

For a short dropdown or a small lookup table, get every match in one response:

<CodeGroup>
```typescript TypeScript
const result = await pawabase.from("categories").order("name").paginate(false);
result.data;       // every match
result.page;       // null
result.per_page;   // null
result.total;      // how many came back
```

```python Python
result = pb.from_("categories").order("name").paginate(False).execute()
result.data, result.total   # page and per_page are None
```
</CodeGroup>

One response holds at most **5000** records. If more match, the server answers `400` "more than 5000 records match; narrow with filters or use pagination", rather than quietly cutting the list short. For anything that grows, [walk through the pages](#walk-through-everything) instead.

`page` and `perPage` are ignored with paging off.

## Load more

Keep the page number, add the next page's records to what you show, and stop when a page comes back **empty**. Don't rely on `total` (it can be `null`) or on a short page (with a per-row rule, a short page can have more after it).

```tsx
function usePosts() {
  const [rows, setRows] = useState<Post[]>([]);
  const [page, setPage] = useState(0);
  const [done, setDone] = useState(false);

  async function loadMore() {
    const next = await pawabase.from("posts").order("created_at", "desc").order("id").perPage(20).page(page + 1);
    setRows((current) => [...current, ...(next.data as Post[])]);
    setPage(page + 1);
    if (next.data.length === 0 || (next.total !== null && (page + 1) * 20 >= next.total)) setDone(true);
  }

  return { rows, loadMore, done };
}
```

When `total` is known, the second condition stops one request earlier.

### Infinite scroll

Call `loadMore` when a marker below the list scrolls into view:

```tsx
function Sentinel({ onVisible }: { onVisible: () => void }) {
  const ref = useRef<HTMLDivElement>(null);
  useEffect(() => {
    const observer = new IntersectionObserver(([entry]) => entry?.isIntersecting && onVisible(), { rootMargin: "400px" });
    if (ref.current) observer.observe(ref.current);
    return () => observer.disconnect();
  }, [onVisible]);
  return <div ref={ref} />;
}
```

Guard against loading the same page twice while one request is in flight.

## Page controls

Show "Page 3 of 12" only when `total` is a number; otherwise show Previous and Next.

```tsx
const pages = page.total === null ? null : Math.max(1, Math.ceil(page.total / page.per_page!));

<nav>
  <button disabled={page.page === 1} onClick={() => go(page.page! - 1)}>Previous</button>
  {pages !== null && <span>Page {page.page} of {pages}</span>}
  <button disabled={pages !== null ? page.page! >= pages : page.data.length === 0} onClick={() => go(page.page! + 1)}>Next</button>
</nav>
```

Keep the page number in the URL (`?page=3`) so people can share and reload a page.

## Walk through everything

For exports, reports and background jobs, go page by page instead of loading one huge result.

<CodeGroup>
```typescript TypeScript
// page by page
for await (const page of pawabase.from("orders").eq("status", "paid").pages({ pageSize: 200 })) {
  await writeToCsv(page.data);
}

// record by record
for await (const order of pawabase.from("orders").eq("status", "paid")) {
  await process(order);
}

// into memory, with a safety stop
const recent = await pawabase.from("orders").order("created_at", "desc").all({ pageSize: 200, maxRecords: 5000 });
```

```python Python
for page in pb.from_("orders").eq("status", "paid").query().pages(page_size=200):
    write_to_csv(page.data)

for order in pb.from_("orders").eq("status", "paid").iterate(page_size=200):
    process(order)

recent = pb.from_("orders").order("created_at", "desc").all(page_size=200, max_records=5000)

# async client
async for order in apb.from_("orders").eq("status", "paid").iterate():
    await process(order)
```
</CodeGroup>

| Option (TypeScript / Python) | Default | Meaning |
| --- | --- | --- |
| `pageSize` / `page_size` | the query's page size, else 100 | Records per request, at most 200 |
| `maxRecords` / `max_records` | none | Stop after this many records |
| `stopAfterEmptyPages` (TypeScript) | 1 | With an unknown total, stop after this many empty pages in a row |
| `signal`, `timeoutMs` (TypeScript) | | Apply to every request of the walk |

`pages` yields one page at a time, so memory stays flat however large the result is. Starting from `.page(5)` walks from page 5 on.

**When the walk stops:** with a known `total`, after the last page. With an unknown `total`, TypeScript keeps going until a page comes back empty; Python stops at the first page that isn't full, which can end early on a table whose rule removes many rows. For those tables in Python, loop yourself until a page is empty:

```python
page_number = 1
while True:
    page = pb.from_("orders").per_page(200).page(page_number).execute()
    if not page.data:
        break
    process(page.data)
    page_number += 1
```

## Stable pages

Pages are counted by position. If records are added or removed while someone pages, records shift: one can appear twice, or be skipped.

- Sort by something that doesn't change, and end with a unique column: `.order("created_at", "desc").order("id")`.
- For feeds, filter instead of counting pages: "newer than the newest I have" with `gt("created_at", newest)`.
- Let [realtime record changes](/realtime/record-changes) add new records at the top instead of re-reading page 1.
- For an export of a table that's changing, fix the end first: `lt("created_at", startedAt)`.

## Keyset paging

Deep page numbers get slower, because the database still steps over every skipped row. "The next 50 older than this one" stays fast at any depth:

<CodeGroup>
```typescript TypeScript
async function olderThan(cursor?: string) {
  let query = pawabase.from("events").order("created_at", "desc").limit(50);
  if (cursor) query = query.lt("created_at", cursor);
  const { data } = await query;
  return { data, next: data.at(-1)?.created_at ?? null };
}
```

```python Python
def older_than(cursor: str | None = None):
    query = pb.from_("events").order("created_at", "desc").limit(50)
    if cursor:
        query = query.lt("created_at", cursor)
    data = query.execute().data
    return data, (data[-1]["created_at"] if data else None)
```
</CodeGroup>

Pass the last record's `created_at` as the next cursor, and [index](/database/indexes) the column. If several records can share a `created_at`, records at the boundary can be skipped; a timestamp with microseconds makes that rare, and a unique sequence column makes it impossible.

## Advanced

### Sort by a computed value

The API sorts by stored columns. To sort by something computed ("most comments", "distance from me"), store the value in a column and keep it up to date with a [flow](/logic/flows) on the related table's events, or use a [route](/logic/routes) with a database query.

### Many pages at once

When `total` is known and you need every page quickly (an export), read several pages in parallel instead of one after another:

```typescript
const first = await pawabase.from("orders").perPage(200);
const pages = Math.ceil((first.total ?? 0) / 200);
const rest = await Promise.all(
  Array.from({ length: pages - 1 }, (_, i) => pawabase.from("orders").perPage(200).page(i + 2)),
);
const all = [first, ...rest].flatMap((p) => p.data);
```

Keep the number of requests at once modest (5 to 10); the environment has a [rate limit](/database/caching-and-rate-limits).

### Limits

| Limit | Value |
| --- | --- |
| Records per page | 1 to 200 |
| Records with paging off | 5000 |
| Sort columns | stored columns, not write-only ones |

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `422` on the page size | Over 200 | Use 200 and walk the pages |
| `400` "more than 5000 records match" | Paging off on a large result | Filter more, or page |
| `400` "cannot sort on unknown field" | A typo, or a column that doesn't exist | Check the name |
| A record shows twice, or one is missing | Records changed while paging | See [Stable pages](#stable-pages) |
| Pages are short but more follow | A per-row read rule | Load until a page is empty |
| "Page N of M" is wrong or missing | `total` is `null` | Use Previous and Next |
| Deep pages are slow | Large offsets | Use [keyset paging](#keyset-paging) |
