Real data links together: a post has an author and comments, an order has line items. A **relation** tells Pawabase how two tables connect, so your app can ask for both in one request instead of two.

Relations don't create foreign keys or change the table. They describe a link that already exists through an ordinary column (`post.author_id`) so `expand` can follow it.

## Two kinds

| Kind | The link is stored | Reads as | Result |
| --- | --- | --- | --- |
| `belongs_to` | On **this** table: `posts.author_id` holds an author's id | "A post belongs to an author" | One object (or `null`) |
| `has_many` | On the **other** table: `comments.post_id` holds this post's id | "A post has many comments" | An array |

## In Studio

Open the table, choose **Settings**, and find **Relations** (*Include related rows with `?expand=name`*). **Add relation** asks for:

| Field | Meaning |
| --- | --- |
| **Name** | What you call it in `expand("name")`: `author`, `comments` |
| **Resource** | The other table's resource |
| **Field** | For `belongs_to`: the column on **this** table that holds the other's id (`author_id`). For `has_many`: the column on the **other** table that holds this record's id (`post_id`) |
| **Type** | `belongs_to` or `has_many` |

**Remove relation** deletes it. Existing queries that expand it start failing with a 400, so change the app first.

## In code

<CodeGroup>
```typescript TypeScript
await m.resources.create({
  name: "posts",
  fields: [
    { name: "title", type: "string", required: true },
    { name: "author_id", type: "string", required: true, indexed: true },
  ],
  relations: [
    { name: "author", resource: "profiles", field: "author_id", type: "belongs_to" },
    { name: "comments", resource: "comments", field: "post_id", type: "has_many" },
  ],
  operations: { list: { enabled: true, policy: "public" }, get: { enabled: true, policy: "public" } },
});
```

```python Python
pb.manage.resources.create({
    "name": "posts",
    "fields": [
        {"name": "title", "type": "string", "required": True},
        {"name": "author_id", "type": "string", "required": True, "indexed": True},
    ],
    "relations": [
        {"name": "author", "resource": "profiles", "field": "author_id", "type": "belongs_to"},
        {"name": "comments", "resource": "comments", "field": "post_id", "type": "has_many"},
    ],
    "operations": {"list": {"enabled": True, "policy": "public"}, "get": {"enabled": True, "policy": "public"}},
})
```
</CodeGroup>

`type` defaults to `belongs_to`. A relation needs `name`, `resource` and `field`; anything else is refused when you save.

Index the column that holds the link (`author_id`, `post_id`). Loading related rows looks them up by it.

## In your app: expand

<CodeGroup>
```typescript TypeScript
const { data: posts } = await pawabase.from("posts").expand("author", "comments").order("created_at", "desc");

posts[0].author.name;           // an object
posts[0].comments.length;       // an array

const post = await pawabase.from("posts").get(id, { expand: ["author"] });
```

```python Python
posts = pb.from_("posts").expand("author", "comments").order("created_at", "desc").execute().data
posts[0]["author"]["name"]
posts[0]["comments"]

post = pb.from_("posts").get(post_id, expand=["author"])
```
</CodeGroup>

Asking for a relation the table doesn't define is a `400` ("posts has no relation 'x'").

## Access rules still apply

Each related record is read under **its own table's** rules and shaped by **its own** transformer. If you may read a post but not its author's profile, the author comes back empty (`null`, or fewer items in a list). Check for that:

```typescript
const authorName = post.author?.name ?? "Unknown";
```

This makes relations safe: expanding can never reveal what a direct read would hide.

## Filtering by a related record

Filter on the column that holds the link, not on the expanded object:

```typescript
const { data } = await pawabase.from("posts").eq("author_id", authorId).expand("author");
const mine = await pawabase.from("comments").eq("post_id", post.id).order("created_at");
```

## Many-to-many

A tag system (posts have many tags, tags have many posts) uses a **join table** with two `belongs_to` links:

```typescript
// post_tags: { post_id, tag_id }
await m.resources.create({
  name: "post_tags",
  fields: [
    { name: "post_id", type: "string", required: true, indexed: true },
    { name: "tag_id", type: "string", required: true, indexed: true },
  ],
  relations: [
    { name: "post", resource: "posts", field: "post_id", type: "belongs_to" },
    { name: "tag", resource: "tags", field: "tag_id", type: "belongs_to" },
  ],
  indexes: [{ name: "once", columns: ["post_id", "tag_id"], unique: true }],
});

const { data: links } = await pawabase.from("post_tags").eq("post_id", post.id).expand("tag");
const tags = links.map((l) => l.tag);
```

The unique index stops the same tag being added twice.

## Performance and limits

- Related rows are fetched in **one extra query per relation**, not one per record, so expanding a list of 50 posts costs two queries, not 51.
- A `has_many` with thousands of children makes responses big. Load those separately with a filter and [paging](/database/sort-and-page) instead of expanding.
- Don't expand relations you won't show.
