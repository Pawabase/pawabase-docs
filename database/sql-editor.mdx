The **SQL** tool runs real queries against the environment's database. Use it to answer questions ("orders per day"), find duplicates before adding a unique index, backfill a column, or understand why a query is slow.

## In Studio

**Data → Tools → SQL.** It has:

- **A schema browser:** use **Find a table** to jump to a table and see its columns.
- **An editor** that completes table and column names as you type.
- **A builder** for people who would rather click: choose a **Table**, **Column**s, a **Join type**, **Operator** and values, **Combine with** AND/OR, and **Order by**. The builder writes the SQL for you.
- **Results** below, with **No rows.** when empty. Long values are truncated; open a row to see everything.
- **Saved queries**, shared with your team: give a query a **Name** ("Orders per day") and a **Description** ("What it answers"), and load it later. Delete with the trash action.
- **Show how the database would run this query** (explain): the plan, to see whether an index is used.

By default the editor runs **read** statements. Statements that change data or structure are treated as writes, are audited, and clear the environment's caches.

### Create tables

The **Create tables** button at the top creates or extends the tables for every resource at once. It adds only: nothing is dropped or retyped.

## Useful queries

```sql
-- Duplicates before a unique index
SELECT email, count(*) FROM customers GROUP BY email HAVING count(*) > 1;

-- Rows that would break a new NOT NULL
SELECT count(*) FROM orders WHERE customer_id IS NULL;

-- Biggest customers
SELECT customer_id, sum(total) AS spent FROM orders GROUP BY 1 ORDER BY spent DESC LIMIT 10;

-- Backfill a new column
UPDATE orders SET currency = 'USD' WHERE currency IS NULL;
```

## Safety habits

1. **Select before you update.** Run the `SELECT` with the same `WHERE`, check the count, then change `SELECT` to `UPDATE`.
2. **Take a backup** before a large change. See [Backups](/backups/overview).
3. Writes **bypass access rules and events** at the SQL level. If you need events to fire, use the table editor, an import, or enable **Capture changes made outside the API** on the resource ([Events and realtime](/database/events-and-realtime)).
4. Run risky statements in `development` first.

## Reading a plan

Run explain on a slow query:

- **Index scan / index only scan:** good: the index is used.
- **Sequential scan** on a big table: no usable index. Add one that matches the `WHERE` and `ORDER BY` ([Indexes](/database/indexes)).
- A sort on millions of rows: add an index that already has the order.
