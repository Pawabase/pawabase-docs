## Tables and resources

Your data is stored in ordinary database tables. To make a table available to your app, you give it a **resource**. A resource is a small definition that sits on top of the table and says:

- what the **columns** are and what each may contain,
- which of five **operations** are available, and who may do each,
- how records **relate** to each other,
- extra behaviour: ids, timestamps, owner, events, realtime, caching, rate limits.

In Studio, the **Data** sidebar lists every table. One tagged **resource** is served as an API. A table without a resource exists but is reachable only from Studio and with a secret key.

## The five operations

Each resource has these operations. Each can be switched on or off and has its own access rule.

| Operation | Studio calls it | Client call | HTTP |
| --- | --- | --- | --- |
| `list` | See the list | `from("t")` / `.first()` / `.count()` | `GET /rest/v1/t` |
| `get` | Open one record | `.get(id)` | `GET /rest/v1/t/{id}` |
| `create` | Add records | `.create({...})` | `POST /rest/v1/t` |
| `update` | Edit records | `.update(id, {...})`, `.replace(id, {...})` | `PATCH` / `PUT /rest/v1/t/{id}` |
| `delete` | Delete records | `.delete(id)` | `DELETE /rest/v1/t/{id}` |

If an operation is off, the API answers as if it doesn't exist. If every operation is off, the table isn't served at all.

## One request, step by step

1. Your app calls `pawabase.from("tasks").eq("done", false)`. The client adds your API key and the signed-in person's token.
2. **The firewall** can block or rate-limit the request first. See [Firewall](/firewall/overview).
3. **Authentication** reads the token: who is calling, their roles, organization, assurance level.
4. **The access rule** for `list` on `tasks` is evaluated. For a list, simple rules (such as "the owner column equals the caller") become part of the database query, so only allowed rows are even read.
5. **The query runs** with your filters, sort and page.
6. **The response is shaped:** write-only columns are removed, and an optional [transformer](/database/transformers) reshapes each record.
7. **Side effects** (for writes): events are emitted, subscribers run, [realtime](/realtime/record-changes) is told.

Because step 4 is on the server, hiding a button never protects data. The rule does.

## What every record has

| Field | Meaning |
| --- | --- |
| `id` | The primary key. A ULID by default. See [Ids and timestamps](/database/ids-and-timestamps) |
| Your columns | As you defined them |
| `created_at`, `updated_at` | Added and maintained for you (switch off with `timestamps: false`) |

## Environments

Each environment (`development`, `production`, previews) has its **own database**. A definition lives in one environment. You build in `development`, then [promote](/environments/overview) definitions to `production`. Data never moves unless you export and import it.

## Definitions are data

Resources, access rules, relations and transformers are stored as JSON, which is why Studio can edit them and the management client can create them. Both write the same thing, so a change made in Studio is visible in code and the reverse.

<CodeGroup>
```typescript TypeScript
const resource = await m.resources.getOne("tasks");   // the definition Studio is editing
```

```python Python
resource = pb.manage.resources.get_one("tasks")
```
</CodeGroup>

## Mapping to your own words

| In Studio | In code (the definition) | In the database |
| --- | --- | --- |
| Table | `table` (defaults to the resource name) | A table |
| Column | An entry in `fields` | A column |
| Resource | The whole definition (`name`, `fields`, `operations`…) | Nothing; it's configuration |
| Access tab | `operations.<op>.policy` | Nothing; it's configuration |
| Pending migration | What `migrate` will run | `CREATE TABLE` / `ADD COLUMN` |
