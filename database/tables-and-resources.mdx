A **table** holds rows. A **resource** exposes a table through your API. This page covers creating both, keeping them in step, and removing them.

## Create a table in Studio

1. **Data → Data**, then **Create table** (top of the sidebar).
2. Enter a **name**: lowercase letters, digits and underscores, starting with a letter (for example `tasks`, `order_items`). Names are up to 63 characters. A few are reserved and refused: `docs`, `openapi.json`, `x`, `rpc`, `health`, `internal`, `platform`.
3. Add columns on the **Columns** tab ([Columns and types](/database/columns-and-types)).
4. Save. Studio proposes a **pending migration** that creates the table. Review the SQL and apply it ([Migrations and history](/database/migrations-and-history)).

The table appears in the sidebar with a `resource` tag. Use the **Find a table** box to search when you have many.

<Note>
**Create tables** at the top of the **SQL** page creates or extends the tables for **every** resource at once, the same step as a single resource's migrate. Columns are only ever added: nothing is dropped or retyped.
</Note>

## Create a resource in code

<CodeGroup>
```typescript TypeScript
import { manage } from "@pawabase/client/manage";
const m = manage(serverClient);      // a secret-key client

await m.resources.create({
  name: "orders",
  description: "Customer orders",
  fields: [
    { name: "customer_id", type: "string", required: true, indexed: true },
    { name: "status", type: "string", enum: ["pending", "paid", "shipped"], default: "pending" },
    { name: "total", type: "integer", minimum: 0 },
  ],
  owner_field: "customer_id",
  operations: {
    list:   { enabled: true, policy: "owner" },
    get:    { enabled: true, policy: "owner" },
    create: { enabled: true, policy: "authenticated" },
  },
});

const plan = await m.resources.migrate("orders");   // creates the table; returns the statements it ran
```

```python Python
pb.manage.resources.create({
    "name": "orders",
    "description": "Customer orders",
    "fields": [
        {"name": "customer_id", "type": "string", "required": True, "indexed": True},
        {"name": "status", "type": "string", "enum": ["pending", "paid", "shipped"], "default": "pending"},
        {"name": "total", "type": "integer", "minimum": 0},
    ],
    "owner_field": "customer_id",
    "operations": {
        "list": {"enabled": True, "policy": "owner"},
        "get": {"enabled": True, "policy": "owner"},
        "create": {"enabled": True, "policy": "authenticated"},
    },
})
pb.manage.resources.migrate("orders")
```
</CodeGroup>

Operations not listed are **off**. A definition is checked before it is stored: an unknown policy name, a bad cron or a malformed column is refused with a `422` that says why.

## The definition, field by field

| Key | Meaning | Default |
| --- | --- | --- |
| `name` | The resource's name. Lowercase, digits, underscores. The API path is `/rest/v1/<name>` | required |
| `description` | A note for your team and the API docs | `""` |
| `table` | The database table. Set it to serve an existing table under another name | same as `name` |
| `primary_key` | The key column | `id` |
| `id_type` | `ulid`, `uuid` or `integer` | `ulid` |
| `fields` | The columns. See [Columns and types](/database/columns-and-types) | `[]` |
| `operations` | `list`, `get`, `create`, `update`, `delete`, each `{ enabled, policy }` | all off |
| `relations` | See [Relations](/database/relations) | `[]` |
| `indexes` | See [Indexes](/database/indexes) | `[]` |
| `transformer` | Reshape responses. See [Transformers](/database/transformers) | none |
| `cache_ttl` | Seconds to cache list and get responses, up to 86400 | `0` |
| `rate_limit` | `{ limit, window }`. See [Caching and rate limits](/database/caching-and-rate-limits) | none |
| `events` | Emit `<name>.created/updated/deleted` | `true` |
| `realtime` | Push changes to subscribers | `false` |
| `capture` | Also announce changes made outside the API | `false` |
| `timestamps` | Maintain `created_at` and `updated_at` | `true` |
| `owner_field` | The column filled with the caller's id on create | none |
| `tags` | Group endpoints in the API docs | `[]` |

Each is explained on its own page; the Studio location is in the table in [Table settings](/database/table-settings).

## Change and read a definition

<CodeGroup>
```typescript TypeScript
const all = await m.resources.list();
const one = await m.resources.getOne("orders");
await m.resources.replace("orders", { ...one, description: "All customer orders" });   // send the whole definition
await m.resources.remove("orders");                                                   // removes the definition, not the table
```

```python Python
all_resources = pb.manage.resources.list()
one = pb.manage.resources.get_one("orders")
pb.manage.resources.replace("orders", {**one, "description": "All customer orders"})
pb.manage.resources.remove("orders")
```
</CodeGroup>

`replace` sends the complete definition. The simplest safe pattern is read, change a field, send it back.

## Keep tables and definitions in step

A table can drift from its definition: someone adds a column with SQL, or you add a column to the definition but don't migrate. Pawabase shows this and gives you the choices:

| Status in Studio | Meaning | What to do |
| --- | --- | --- |
| **In sync** | Table and definition agree | Nothing |
| **Not applied** | The definition has changes the table lacks | Apply the migration |
| **Needs review** | The change could rewrite or drop things | Read the plan; apply deliberately |
| **Changed outside** | The table has something the definition doesn't | **Acknowledge** it (adopt it into the definition) or fix the table |
| **No table yet** | A resource exists with no table | Migrate it |
| **Table dropped** | The table is gone | Re-create or remove the resource |

<CodeGroup>
```typescript TypeScript
const plan = await m.resources.schemaPlan("orders");           // what applying would change
await m.resources.schemaApply("orders");                        // apply it
await m.resources.schemaAcknowledge("orders");                  // take the table as it is as the new starting point
const overview = await m.schema.overview();                     // every resource against its definition
const stray = await m.schema.unmappedTables();                  // tables with no resource
```

```python Python
plan = pb.manage.resources.schema_plan("orders")
pb.manage.resources.schema_apply("orders")
pb.manage.resources.schema_acknowledge("orders")
overview = pb.manage.schema.overview()
stray = pb.manage.schema.unmapped_tables()
```
</CodeGroup>

### Import an existing table

If you already have a table (from a migration, or created with SQL), turn it into a resource instead of retyping it: in Studio use **Import a table** on the **Data** page; it reads the table's columns and proposes a definition. In code, list `unmappedTables()`, then create a resource whose `table` names it and `schemaAcknowledge` so the definition adopts what is there.

Internal tables used by Pawabase (names starting `pb_`, `akz_`, `perm_`, `_pbm_`) are hidden and cannot be imported.

## Deleting

- **Remove the resource:** the API stops serving the table. The table and its rows stay.
- **Drop the table:** do it deliberately, with the [SQL editor](/database/sql-editor), after taking a [backup](/backups/overview). Studio never drops a table for you.
