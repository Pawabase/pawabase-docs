## What the rules do

Each table has a rule for each action: **list, get, create, update, delete**. A rule can be as simple as "any signed-in user" or as specific as "only the owner of the record". They run on the server for every request, so they protect your data no matter what a client sends.

Rules are set in the dashboard under **Database**, in the table's settings. Typical choices:

| Rule | Who passes |
| --- | --- |
| Public | Anyone, signed in or not |
| Authenticated | Any signed-in user |
| Owner | The user whose id is in the table's owner column |
| A role | Users with a given role, such as `admin` |

## The same query, different people

Rules mean the *same code* returns different results to different users:

```typescript
const { data } = await pawabase.from("notes");   // Ada gets her notes, Bob gets his
```

If a list is empty and you expected rows, the first thing to check is who is signed in and what the rule allows.

## What each failure means

<CodeGroup>
```typescript TypeScript
import {
  AuthenticationError, PermissionError, NotFoundError,
  ValidationError, ConflictError, RateLimitError, NetworkError,
} from "@pawabase/client";

try {
  await pawabase.from("tasks").update(id, { done: true });
} catch (e) {
  if (e instanceof AuthenticationError) redirectToSignIn();         // 401: not signed in, or expired
  else if (e instanceof PermissionError) show("You can't do that."); // 403: a rule refused it
  else if (e instanceof NotFoundError) show("It's gone.");           // 404: missing, or hidden by a rule
  else if (e instanceof ValidationError) showFieldErrors(e.byField()); // 400/422: bad input
  else if (e instanceof ConflictError) show("That value is taken.");   // 409
  else if (e instanceof RateLimitError) show("Slow down a moment.");   // 429 (already retried)
  else if (e instanceof NetworkError) show("You're offline.");
  else throw e;
}
```

```python Python
from pawabase import (
    AuthenticationError, ForbiddenError, NotFoundError,
    ValidationError, ConflictError, RateLimitedError, NetworkError,
)

try:
    pb.from_("tasks").update(task_id, done=True)
except AuthenticationError: ...      # 401
except ForbiddenError: ...           # 403
except NotFoundError: ...            # 404
except ValidationError: ...          # 400 / 422
except ConflictError: ...            # 409
except RateLimitedError: ...         # 429
except NetworkError: ...
```
</CodeGroup>

| Error | Status | Usual cause |
| --- | --- | --- |
| `AuthenticationError` | 401 | Not signed in, token expired, or a wrong API key |
| `PermissionError` / `ForbiddenError` | 403 | A rule refused this action |
| `NotFoundError` | 404 | No such record, **or you are not allowed to see it** |
| `ValidationError` | 400, 422 | A missing or invalid field |
| `ConflictError` | 409 | A unique value is already used |
| `RateLimitError` / `RateLimitedError` | 429 | Too many requests |
| `ServerError` | 5xx | A problem on the server |

A 403 error (TypeScript) has `e.policy` with the name of the rule that refused, when the server says. Every API error has a `status`, a stable `code` and a `requestId` to quote when asking for help.

## Retries

The client retries by itself on rate limits, `502`, `503`, `504` and network failures, with a short delay. You only see the error if it keeps failing. Turn this off or tune it with the `retry` option when you create the client.

## Debugging checklist

1. Is the user signed in? `await pawabase.auth.getSession()`.
2. Does the table's rule allow this action for this user?
3. Try the same call with a secret key on a server (see [keys and security](/reference/keys-and-security)). If it works there, a rule is the cause.
4. Quote `error.requestId` to find the request in the dashboard's request log.
