Every write returns the saved record, so you can show the server's version, with its `id`, timestamps and defaults, without reading it again. Each write is checked against the table's `create`, `update` or `delete` [access rule](/database/access) and against the columns' types and constraints.

<CodeGroup>
```typescript TypeScript
const tasks = pawabase.from("tasks");

const task = await tasks.create({ title: "Write the docs", priority: 2 });
await tasks.update(task.id, { done: true });
await tasks.delete(task.id);
```

```python Python
tasks = pb.from_("tasks")

task = tasks.create(title="Write the docs", priority=2)
tasks.update(task["id"], done=True)
tasks.delete(task["id"])
```
</CodeGroup>

| Call | TypeScript | Python | Rule checked | Returns |
| --- | --- | --- | --- | --- |
| Create | `create(row)` | `create(**fields)` | `create` | the record |
| Create many | `createMany(rows, options)` | `create_many(rows, ...)` | `create`, per row | created and failed, see [Bulk writes](/database/bulk-writes) |
| Change some fields | `update(id, patch)` | `update(id, **fields)` | `update` | the record |
| Send the whole record | `replace(id, row)` | `replace(id, **fields)` | `update` | the record |
| Delete | `delete(id)` | `delete(id)` | `delete` | nothing |

## Create

<CodeGroup>
```typescript TypeScript
const task = await pawabase.from("tasks").create({
  title: "Write the docs",
  priority: 2,
  due_at: new Date("2026-12-01T09:00:00Z"),
  labels: ["docs"],                    // a JSON or array column
});
task.id;          // assigned by the server
task.created_at;  // timestamps are filled in
task.status;      // defaults are filled in
task.owner_id;    // the caller, when the table has an owner field
```

```python Python
from datetime import datetime, timezone

task = pb.from_("tasks").create(
    title="Write the docs",
    priority=2,
    due_at=datetime(2026, 12, 1, 9, tzinfo=timezone.utc),
    labels=["docs"],
)
task["id"], task["created_at"], task["status"], task["owner_id"]
```
</CodeGroup>

- Leave out `id`, `created_at` and `updated_at`; the server sets them. See [IDs and timestamps](/database/ids-and-timestamps).
- Columns you leave out get their **default**, or `null` if they are optional. A required column without a default must be sent.
- In Python, `datetime`, `date` and `Decimal` values are turned into text for you, including inside nested dicts and lists. In TypeScript, a `Date` becomes ISO text through JSON.
- Sending a column that doesn't exist, or a read-only one, answers `422`: the server never ignores a field silently.

### The owner field

If the table has an **owner field** (the table's **Settings → Owner field**), the server fills it with the caller's user id on every create, **whatever you send**. That is what makes "people can only edit their own records" safe: nobody can create a record in someone else's name.

A create on a table with an owner field from someone who isn't signed in answers `401`.

## Update some fields

<CodeGroup>
```typescript TypeScript
const updated = await pawabase.from("tasks").update(task.id, { done: true, priority: 1 });
await pawabase.from("tasks").update(task.id, { assignee_id: null });   // clear an optional field
```

```python Python
updated = pb.from_("tasks").update(task["id"], done=True, priority=1)
pb.from_("tasks").update(task["id"], assignee_id=None)
```
</CodeGroup>

`update` sends only the fields you pass and returns the whole record afterwards.

- Fields you don't send stay as they are.
- `null` clears an **optional** field.
- `null` for a **required** field is refused with `422` "this field may not be null". A default doesn't make a field optional.
- Unknown and read-only fields are refused with `422`.
- The owner field can't be changed through `update`; it is dropped from the patch.

### Fields a rule depends on

If the table's update rule reads a field to decide who may change the record, people can't change that field themselves. For example, with the rule *record.owner_id is the caller* or *record.team_id is one of my teams*, an update that changes `owner_id` or `team_id` is refused with `403` "owner_id decides who may change this record and cannot be changed".

This stops someone handing a record to another person, or moving it into a team they aren't in. Change those fields from your server with a secret key, or in a [flow](/logic/flows) that checks the move is allowed.

## Replace

`replace` sends the record with `PUT`. The server treats it **like `update`**: it changes the fields you send and leaves the others as they are. It doesn't clear fields you leave out.

<CodeGroup>
```typescript TypeScript
await pawabase.from("settings").replace(settings.id, { theme: "dark", language: "en" });
```

```python Python
pb.from_("settings").replace(settings["id"], theme="dark", language="en")
```
</CodeGroup>

To clear a field, send it as `null` (when it is optional). Prefer `update`; `replace` exists for code that thinks in whole records. Unlike `update`, a `replace` is retried by the TypeScript client after a network failure, because sending the same record twice is harmless.

## Delete

<CodeGroup>
```typescript TypeScript
await pawabase.from("tasks").delete(task.id);    // resolves to undefined
```

```python Python
pb.from_("tasks").delete(task["id"])             # returns None
```
</CodeGroup>

- Deleting a record that's gone answers `404`.
- If the delete rule refuses, a signed-in caller gets `403` and a signed-out caller gets `404`, so a refusal doesn't reveal that the record exists.
- A delete is permanent. For "undo" or a recycle bin, use a [soft delete](/database/patterns#soft-delete): set `deleted_at` instead, and filter it out of reads.
- Related records aren't deleted with it. A [relation](/database/relations) only describes how to expand records; clean up related records in a [flow](/logic/flows) on `tasks.deleted`.

## Errors

| Error (TypeScript / Python) | Status | Code | When |
| --- | --- | --- | --- |
| `ValidationError` | 422 | `validation_failed` | A required field is missing, a value has the wrong type or breaks a column rule (length, range, pattern), `null` for a required field, an unknown or read-only field |
| `ValidationError` | 422 | `constraint_violation` | A database constraint refused it, such as a check constraint |
| `ConflictError` | 409 | `unique_violation` | A unique column already has this value. `details.columns` names the columns; the value isn't repeated back |
| `AuthenticationError` | 401 | | Signed out, and the rule or the owner field needs a user |
| `PermissionError` / `ForbiddenError` | 403 | | The rule refused, or a protected field was changed |
| `NotFoundError` | 404 | | Update or delete of a missing record, or a refused one for a signed-out caller |
| `RateLimitError` / `RateLimitedError` | 429 | | Too many writes; see [rate limits](/database/caching-and-rate-limits) |

### Show validation errors on a form

<CodeGroup>
```typescript TypeScript
import { ConflictError, ValidationError } from "@pawabase/client";

async function save(values: SignupForm) {
  try {
    return await pawabase.from("accounts").create(values);
  } catch (error) {
    if (error instanceof ValidationError) {
      setErrors(error.byField());              // { email: ["must be a valid email"], … }
      focus(error.issues[0]?.field);
    } else if (error instanceof ConflictError) {
      const [column] = (error.details as { columns: string[] }).columns;
      setErrors({ [column ?? "form"]: ["That's already taken."] });
    } else {
      throw error;
    }
  }
}
```

```python Python
from pawabase.errors import ConflictError, ValidationError

try:
    pb.from_("accounts").create(**values)
except ValidationError as error:
    show_form_error(error.message, error.detail)
except ConflictError as error:
    taken = error.details["columns"]             # ["handle"]
```
</CodeGroup>

`fieldError("email")` returns the first message for one field, for showing under an input. Define the rules once on the columns ([Columns and types](/database/columns-and-types)) and every app gets the same checks.

## Optimistic updates

Change the screen first, confirm with the server, and put it back if the write fails:

```tsx
async function toggle(task: Task) {
  setTasks((all) => all.map((t) => (t.id === task.id ? { ...t, done: !t.done } : t)));
  try {
    const saved = await pawabase.from("tasks").update(task.id, { done: !task.done });
    setTasks((all) => all.map((t) => (t.id === saved.id ? saved : t)));   // the server's version
  } catch {
    setTasks((all) => all.map((t) => (t.id === task.id ? task : t)));
    toast("Couldn't save that change.");
  }
}
```

Replace the optimistic row with the returned one, so timestamps and values a flow changed are correct.

## Duplicate-safe creates

A double click, or a retry after a dropped connection, can create two records. The SDK never retries a create by itself for that reason. To make a create safe to repeat:

1. Add a **unique** column for an idempotency key, generated once per attempt on the client.
2. Treat `ConflictError` on that column as "already created".
3. Disable the button while the request is in flight.

<CodeGroup>
```typescript TypeScript
const key = crypto.randomUUID();   // keep it for retries of the same attempt

async function placeOrder(order: NewOrder) {
  try {
    return await pawabase.from("orders").create({ ...order, idempotency_key: key });
  } catch (error) {
    if (error instanceof ConflictError) return await pawabase.from("orders").eq("idempotency_key", key).single();
    throw error;
  }
}
```

```python Python
import uuid

key = str(uuid.uuid4())
try:
    order = pb.from_("orders").create(**order_fields, idempotency_key=key)
except ConflictError:
    order = pb.from_("orders").eq("idempotency_key", key).single()
```
</CodeGroup>

## Create or update (upsert)

There's no single upsert call. Create, and update on a conflict:

```typescript
async function saveSetting(userId: string, key: string, value: string) {
  try {
    return await pawabase.from("settings").create({ user_id: userId, key, value });
  } catch (error) {
    if (!(error instanceof ConflictError)) throw error;
    const existing = await pawabase.from("settings").where({ user_id: userId, key }).single();
    return pawabase.from("settings").update(existing.id, { value });
  }
}
```

This needs a unique index on the columns that identify the record (`user_id` and `key` here). For many rows, [import](/database/import-and-export) upserts in one go.

## Concurrent edits

When two people edit the same record, the last write wins. To catch conflicts instead:

- **Compare before writing.** Read `updated_at`, and in a [route](/logic/routes) refuse the write if it changed since. Answer `409` and let the person reload.
- **Make edits independent.** Store separate fields (or separate records, such as one comment per person) so two edits don't touch the same value.
- **Count with increments, not reads.** "Read the stock, subtract one, write it back" loses updates under load. Do it in a flow with a database query (`UPDATE … SET stock = stock - 1 WHERE stock > 0`) or a [transaction](/database/bulk-writes#all-or-nothing-a-transaction).

## What a write sets off

A successful write can do more than change the row:

- **Events:** `tasks.created`, `tasks.updated`, `tasks.deleted` go to [event flows and webhooks](/automation/events), when the table emits events.
- **Realtime:** subscribers to [record changes](/realtime/record-changes) get the change, including you. Merge by `id` so your own write isn't added twice.
- **Cache:** the table's cached list answers are cleared, so the next read is fresh.
- **Request history:** every write appears under **Activity → Requests**. Data changes aren't in the audit log, which records changes to how the project is set up.

Flows that run on these events run after the write has succeeded, so a failing flow never undoes the write.

## Writing from a server

A client with a **secret** key writes without rules, and the owner field isn't filled from a user. Set it yourself:

<CodeGroup>
```typescript TypeScript
const admin = createClient({ url, apiKey: process.env.PAWABASE_SECRET_KEY!, environment });
await admin.from("tasks").create({ title: "Imported", owner_id: userId });
```

```python Python
admin = Pawabase(url, os.environ["PAWABASE_SECRET_KEY"], environment=env)
admin.from_("tasks").create(title="Imported", owner_id=user_id)
```
</CodeGroup>

To write **as** a person from a server, so their rules apply, use `asUser(token)` (TypeScript) or `as_user(token)` (Python). See [Read records: on a server](/database/read#reading-on-a-server).

## Advanced

### Cancel a write

```typescript
const controller = new AbortController();
await pawabase.from("tasks").create(row, { signal: controller.signal });
```

Cancelling stops waiting for the answer. The server may already have saved the record, so treat a cancelled create like a dropped connection and check before trying again.

### Retries

| Call | Retried after a network failure or a `502`/`503`/`504` |
| --- | --- |
| `create`, `update` | No, because repeating could create or change twice |
| `replace`, `delete` | Yes in TypeScript |
| Any call after `429` | Yes, because the server didn't process it |

### JSON columns

A JSON column takes any JSON value. `update` replaces the whole value; it doesn't merge. To change one key, read the record, change the object, and write it back, or keep the keys as separate columns.

### Large text and files

Keep big content (images, PDFs) in [storage](/storage/overview) and store the file's key or URL in a column. A column holding a 100 KB data URL makes every list slow and can break a column's length limit.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `422` "this field may not be null" | `null` for a required field | Send a value, or make the column optional |
| `422` on a field you didn't mean to send | An unknown or read-only field in the object | Send only the table's writable columns |
| `409` `unique_violation` | The value is taken | Ask for another value, or treat it as already created |
| `403` "… decides who may change this record" | The field is used by the update rule | Change it from a server or a flow |
| `401` on create | Signed out, and the table has an owner field | Sign in, or use a guest session |
| `404` on update | Missing, or refused for a signed-out caller | Check the id and the rule |
| A value is too long | A column's length limit | Raise the limit, or store the content in storage |
| Records appear twice on screen | Your own write came back through realtime | Merge by `id` |
