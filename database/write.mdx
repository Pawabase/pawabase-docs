Writes return the saved record, so you can show the server's version (with its `id`, timestamps and defaults) without another read.

## Create

<CodeGroup>
```typescript TypeScript
const task = await pawabase.from("tasks").create({
  title: "Write the docs",
  done: false,
  owner_id: user.id,
});
task.id;           // assigned by the server
task.created_at;
```

```python Python
task = pb.from_("tasks").create(title="Write the docs", done=False, owner_id=user["id"])
task["id"], task["created_at"]
```
</CodeGroup>

Leave out `id`, `created_at` and `updated_at`; the server fills them in. If your rules use an owner field, set it to the signed-in user's id.

## Update some fields

<CodeGroup>
```typescript TypeScript
const updated = await pawabase.from("tasks").update(task.id, { done: true });
await pawabase.from("tasks").update(task.id, { assignee_id: null });   // null clears a field
```

```python Python
updated = pb.from_("tasks").update(task["id"], done=True)
pb.from_("tasks").update(task["id"], assignee_id=None)
```
</CodeGroup>

`update` changes only the fields you send. To change many records at once, query them and update each.

## Replace

`replace` writes the whole record: fields you leave out go back to their defaults.

<CodeGroup>
```typescript TypeScript
await pawabase.from("settings").replace(settings.id, { theme: "dark", language: "en" });
```

```python Python
pb.from_("settings").replace(settings["id"], theme="dark", language="en")
```
</CodeGroup>

Prefer `update` unless you really mean "this is the complete new record".

## Delete

<CodeGroup>
```typescript TypeScript
await pawabase.from("tasks").delete(task.id);
```

```python Python
pb.from_("tasks").delete(task["id"])
```
</CodeGroup>

Deleting a record that is already gone, or one you may not delete, throws `NotFoundError`.

## Create many

<CodeGroup>
```typescript TypeScript
const { created, failed } = await pawabase.from("tasks").createMany(
  [{ title: "One" }, { title: "Two" }, { title: "Three" }],
  { concurrency: 5, stopOnError: false },
);

for (const f of failed) console.log("row", f.index, "failed:", f.error);
```

```python Python
result = pb.from_("tasks").create_many([{"title": "One"}, {"title": "Two"}], stop_on_error=False)
result.created, result.failed
```
</CodeGroup>

It sends several creates in parallel and tells you which succeeded and which failed (with the row's position), so one bad row does not lose the rest. It is not a single transaction.

## Validation errors

The server checks required fields and types before your rules run, and tells you which field is wrong:

<CodeGroup>
```typescript TypeScript
import { ValidationError } from "@pawabase/client";

try {
  await pawabase.from("tasks").create({ title: "" });
} catch (e) {
  if (e instanceof ValidationError) {
    e.fieldError("title");   // "must not be empty"
    e.byField();             // { title: ["must not be empty"] }
  }
}
```

```python Python
from pawabase import ValidationError

try:
    pb.from_("tasks").create(title="")
except ValidationError as e:
    print(e)
```
</CodeGroup>

Show `fieldError("email")` under each form input. A taken unique value, such as a duplicate username, is a `ConflictError`.

## Optimistic updates

For snappy UIs, update the screen first, then confirm with the server, and roll back on failure:

```typescript
async function toggle(task: Task) {
  setTasks((all) => all.map((t) => (t.id === task.id ? { ...t, done: !t.done } : t)));
  try {
    await pawabase.from("tasks").update(task.id, { done: !task.done });
  } catch {
    setTasks((all) => all.map((t) => (t.id === task.id ? task : t)));   // roll back
  }
}
```
