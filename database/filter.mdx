Add filter methods to a query before you run it. Filters are applied by the database, so you only download what matches. Several filters combine with **and**.

<CodeGroup>
```typescript TypeScript
const { data } = await pawabase
  .from("tasks")
  .eq("project_id", projectId)
  .is("done", false)
  .gte("priority", 3)
  .order("due_at");
```

```python Python
page = (
    pb.from_("tasks")
    .eq("project_id", project_id)
    .is_("done", False)
    .gte("priority", 3)
    .order("due_at")
    .execute()
)
```
</CodeGroup>

## Every filter

| TypeScript | Python | Matches | Works on |
| --- | --- | --- | --- |
| `eq(col, v)` | `eq(col, v)` | equal | all |
| `neq(col, v)` | `neq(col, v)` | not equal | all |
| `gt(col, v)` | `gt(col, v)` | greater than | numbers, dates, text |
| `gte(col, v)` | `gte(col, v)` | greater than or equal | numbers, dates, text |
| `lt(col, v)` | `lt(col, v)` | less than | numbers, dates, text |
| `lte(col, v)` | `lte(col, v)` | less than or equal | numbers, dates, text |
| `like(col, pattern)` | `like(col, pattern)` | pattern, case-sensitive | text |
| `ilike(col, pattern)` | `ilike(col, pattern)` | pattern, any case | text |
| `in(col, values)` | `in_(col, values)` | any of the values | all |
| `notIn(col, values)` | `not_in(col, values)` | none of the values | all |
| `is(col, v)` | `is_(col, v)` | is `null`, `true` or `false` | all |
| `isNot(col, v)` | `is_not(col, v)` | is not `null` / `true` / `false` | all |
| `filter(col, op, v)` | `filter(col, op, v)` | any operator by name | all |
| `where({...})` | `where(...)` | several at once | all |

Python adds a trailing underscore to `in_` and `is_` because `in` and `is` are keywords.

The operator names for `filter` and `where` are `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `like`, `ilike`, `in`, `nin`, `is` and `isnot`.

<CodeGroup>
```typescript TypeScript
pawabase.from("tasks")
  .eq("status", "open")
  .neq("owner_id", user.id)
  .gt("priority", 2)
  .lt("due_at", new Date())
  .ilike("title", "%docs%")
  .in("label", ["bug", "urgent"])
  .is("deleted_at", null);
```

```python Python
(pb.from_("tasks")
   .eq("status", "open")
   .neq("owner_id", user_id)
   .gt("priority", 2)
   .lt("due_at", datetime.now(timezone.utc))
   .ilike("title", "%docs%")
   .in_("label", ["bug", "urgent"])
   .is_("deleted_at", None))
```
</CodeGroup>

## One filter per column

The server applies **one filter per column**. If a column appears twice, it keeps only the last, which would silently return the wrong rows. Both SDKs refuse such a query before sending it:

<CodeGroup>
```typescript TypeScript
pawabase.from("orders").gte("total", 1000).lte("total", 5000);
// InvalidQueryError: There is already a filter on "total" …
```

```python Python
pb.from_("orders").gte("total", 1000).lte("total", 5000)
# QueryError: There is already a filter on "total" …
```
</CodeGroup>

So a range with **two bounds on one column** can't be one list request. Ways around it, best first:

1. **A column that holds the bucket.** Store `month` (`"2026-11"`), `price_band` (`"10-50"`) or `day`, kept up to date by a default or a [flow](/logic/flows), and filter it with `eq` or `in`.
2. **One bound on the server, one in your code,** when the result is small:

   ```typescript
   const { data } = await pawabase.from("orders").gte("created_at", start).order("created_at").limit(200);
   const inRange = data.filter((o) => new Date(o.created_at) < end);
   ```
3. **Two columns.** For "events overlapping this week", filter `starts_at` `lt` the week's end and `ends_at` `gte` its start: two columns, one filter each.
4. **A [route](/logic/routes)** with a database query that takes both bounds, called with `pawabase.routes`.

## Values

Pass values of the column's type. The SDK turns them into what the server expects:

| You pass | Sent as |
| --- | --- |
| A string | as it is |
| A number, a `bigint` (TS), a `Decimal` (Python) | its digits |
| A `Date` (TS), `datetime` or `date` (Python) | ISO 8601 text, such as `2026-11-13T09:30:00.000Z` |
| `true` / `false` to `eq` or `neq` | rewritten to `is` / `isNot` |
| `null` / `None` to `eq` or `neq` | rewritten to `is null` / `is not null` |
| `null` / `None` to `gt`, `lt`, `in`… | refused before sending |

The boolean rewrite matters: a raw `eq.false` matches the wrong rows on the server, so the SDK always sends booleans through `is`. Writing `eq("done", false)` and `is("done", false)` is the same query.

### Dates and times

Pass a date object or an ISO 8601 string. Timestamps are stored in UTC.

<CodeGroup>
```typescript TypeScript
const weekAgo = new Date(Date.now() - 7 * 86_400_000);
const { data } = await pawabase.from("orders").gte("created_at", weekAgo);
```

```python Python
from datetime import datetime, timedelta, timezone

week_ago = datetime.now(timezone.utc) - timedelta(days=7)
page = pb.from_("orders").gte("created_at", week_ago).execute()
```
</CodeGroup>

In Python, pass a timezone-aware `datetime`. A naive one is sent without an offset, so whether it means UTC or your local time is left to chance.

For a **date** column (no time), pass `"2026-11-13"` or a Python `date`.

## Null, true and false

<CodeGroup>
```typescript TypeScript
pawabase.from("tasks").is("completed_at", null);      // not completed
pawabase.from("tasks").isNot("completed_at", null);   // completed
pawabase.from("flags").is("enabled", true);
```

```python Python
pb.from_("tasks").is_("completed_at", None)
pb.from_("tasks").is_not("completed_at", None)
pb.from_("flags").is_("enabled", True)
```
</CodeGroup>

`is` and `isNot` take only `null`, `true` or `false`; anything else is refused before sending.

Remember SQL's rule about nulls: `neq("status", "archived")` does **not** match rows whose `status` is null. If a column can be null and you want those rows too, give it a default so it is never null.

## Lists of values

<CodeGroup>
```typescript TypeScript
await pawabase.from("orders").in("status", ["paid", "shipped"]);
await pawabase.from("orders").notIn("id", alreadySeen);
```

```python Python
pb.from_("orders").in_("status", ["paid", "shipped"]).execute()
pb.from_("orders").not_in("id", already_seen).execute()
```
</CodeGroup>

- `in(col, [])` matches nothing, and the SDK answers it **without a request**, with an empty page. That is what you want when a list of ids happens to be empty.
- `notIn(col, [])` adds no filter at all.
- A value containing a **comma** is refused, because the server splits lists on commas. Filter such values one at a time, or by another column.
- The list is sent in the URL. Keep it to a few hundred values; split longer lists into several queries.

## Text patterns

| Character | Matches |
| --- | --- |
| `%` or `*` | any run of characters, including none |
| `_` | exactly one character |

<CodeGroup>
```typescript TypeScript
pawabase.from("people").ilike("name", "ada%");           // starts with "ada", any case
pawabase.from("files").like("path", "*/invoices/*");     // contains "/invoices/"
pawabase.from("codes").like("sku", "AB-___");            // AB- and exactly three characters
```

```python Python
pb.from_("people").ilike("name", "ada%")
pb.from_("files").like("path", "*/invoices/*")
```
</CodeGroup>

`like` is case-sensitive, `ilike` ignores case. A pattern must be a string.

When the pattern comes from someone's typing, their `%`, `_` and `*` become wildcards. Escape `%` and `_` with a backslash, and remove `*`, which can't be escaped:

```typescript
const literal = (text: string) => text.replace(/\*/g, "").replace(/[\\%_]/g, "\\$&");
pawabase.from("posts").ilike("title", `%${literal(term)}%`);
```

A pattern with a leading `%` can't use a normal index and scans the table. For searching text, prefer [full-text search](#search) below.

## Several conditions at once

`where` takes an object. A plain value means **equal**; an object with one operator means that operator.

<CodeGroup>
```typescript TypeScript
const { data } = await pawabase.from("tasks").where({
  done: false,
  priority: { gte: 3 },
  status: { in: ["open", "blocked"] },
  deleted_at: { is: null },
});
```

```python Python
page = pb.from_("tasks").where(
    done=False,
    priority={"gte": 3},
    status={"in": ["open", "blocked"]},
    deleted_at={"is": None},
).execute()

# a dict works too, for names that aren't Python identifiers
pb.from_("tasks").where({"done": False}).execute()
```
</CodeGroup>

A column with two operators (`{ gte: 1, lte: 5 }`) is refused, for the [one-filter-per-column](#one-filter-per-column) reason. `where` combines with chained filters; a column used in both is refused the same way.

`where` suits filters built from a form or a URL:

```typescript
function fromSearchParams(params: URLSearchParams) {
  return pawabase.from("products").where({
    ...(params.get("category") ? { category: params.get("category")! } : {}),
    ...(params.get("max") ? { price: { lte: Number(params.get("max")) } } : {}),
    ...(params.get("inStock") === "1" ? { stock: { gt: 0 } } : {}),
  });
}
```

## "Or"

Chained filters are all **and**. For **or**:

- **Several values of one column:** `in("status", ["open", "blocked"])`.
- **Different columns:** run two queries and merge them in your app (remove duplicates by id):

  ```typescript
  const [mine, assigned] = await Promise.all([
    pawabase.from("tasks").eq("owner_id", me),
    pawabase.from("tasks").eq("assignee_id", me),
  ]);
  const tasks = [...new Map([...mine.data, ...assigned.data].map((t) => [t.id, t])).values()];
  ```
- **Text across several columns:** [search](#search).
- **Anything more complex:** a [route](/logic/routes) with a database query.

## Search

Full-text search finds records whose text columns contain the words someone typed, across several columns at once, best match first.

### Turn it on

Open the table in Studio, choose **Access**, and tick text columns under **Full-text search**. Only text columns can be searched, at most 10, and the table must allow listing.

### Search from your app

<CodeGroup>
```typescript TypeScript
const { data } = await pawabase.from("products").search("red mug").eq("in_stock", true).perPage(20);
```

```python Python
page = pb.from_("products").search("red mug").eq("in_stock", True).per_page(20).execute()
```
</CodeGroup>

How it matches:

- The chosen columns are searched as one piece of text with PostgreSQL full-text search. Every word must appear somewhere in them.
- `"red mug"` in double quotes matches the phrase, `or` matches either word, `-plastic` excludes a word.
- Words are matched as written, without stemming: `running` doesn't match `run`. Search for the shorter form, or add both.
- Results come back best match first, unless you add your own `order`.
- At most 200 characters and 10 words; more answers `400`.
- An empty or blank string turns search off, so you can pass whatever is in the box.
- Search combines with filters, sorting and paging like any other part of the query.
- Access rules apply as for any list: people only find records they could read.
- A table without search columns answers `400` "does not support search; set operations.list.search.fields".

### A search box

Wait for typing to pause, and cancel the previous query so an old answer never replaces a newer one:

```tsx
function useSearch(term: string) {
  const [results, setResults] = useState<Product[]>([]);
  useEffect(() => {
    const controller = new AbortController();
    const timer = setTimeout(() => {
      pawabase.from("products").search(term).perPage(10).withOptions({ signal: controller.signal })
        .then((page) => setResults(page.data as Product[]))
        .catch(() => undefined);
    }, 250);
    return () => { clearTimeout(timer); controller.abort(); };
  }, [term]);
  return results;
}
```

For search by meaning instead of by words ("cheap places to stay" finding "budget hostel"), see [Vector search](/ai/vector-search).

## Filters and access rules

Filters narrow what you **ask** for. [Access rules](/database/access) decide what you're **allowed** to see. They work together:

- A filter can never reveal a row a rule hides. Asking for `owner_id = someone else` returns nothing.
- A rule can't be bypassed with a clever filter.
- Columns marked **write only** can't be used in filters or sorting at all. The server refuses, so a filter can't be used to guess a hidden value one character at a time.
- When a rule depends on each record, the server reads a page and then removes rows the caller may not see. Adding a filter on the same column (for example `eq("team_id", teamId)` when the rule is about teams) narrows in the database first, which is faster and keeps `total` meaningful.

## Make filters fast

Filters run in the database. On a large table, a filter or sort on a column **without an index** reads every row.

- Add an [index](/database/indexes) on columns you filter often, especially foreign keys like `project_id`.
- For filters that always go together (`project_id` and `status`), one index on both columns, in that order, serves both.
- A pattern starting with `%` can't use a normal index. Use search instead.
- **Activity → Requests** shows slow requests; open one to see the query's time.

## Advanced

### Filter on a related table

Filters apply to the table you query. To filter by something on a related table (posts whose author is verified), either store the value on the record (a `author_verified` column kept up to date by a flow), or read the related ids first:

```typescript
const { data: authors } = await pawabase.from("users_public").is("verified", true).select("id").limit(200);
const { data: posts } = await pawabase.from("posts").in("author_id", authors.map((a) => a.id));
```

### Saved views

Keep a user's filters as an object and pass it to `where` later:

```typescript
const view = { status: { in: ["open", "blocked"] }, priority: { gte: 3 } } as const;
localStorage.setItem("tasks.view", JSON.stringify(view));
const saved = JSON.parse(localStorage.getItem("tasks.view") ?? "{}");
const { data } = await pawabase.from("tasks").where(saved);
```

### Values from untrusted input

Filters are always sent as parameters, never pasted into SQL, so a value can't change the query. What a value **can** do is ask for more than you meant: a `%` in a pattern, a huge `in` list. Validate the shape of user input (lengths, allowed values) before building filters from it.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `InvalidQueryError` / `QueryError` "already a filter on" | Two filters on one column | See [One filter per column](#one-filter-per-column) |
| `InvalidQueryError` "contains a comma" | A comma in an `in` value | Filter those values another way |
| `400` "cannot filter on unknown field" | A typo, or a column that doesn't exist in this environment | Check the column name; generated types catch this |
| `400` "does not support search" | No search columns | Tick columns under **Access → Full-text search** |
| `400` "search queries are at most 200 characters" | A long search | Trim the input |
| Rows with `null` are missing from `neq` | SQL treats null as unknown | Give the column a default |
| A date filter is off by hours | A naive `datetime` in Python, or a local time string | Use UTC or timezone-aware values |
| A filter is slow | No index on the column | Add an [index](/database/indexes) |
| A filter returns nothing that should match | The read rule hides those rows | Try the caller in **Access rules → Test** |
