Add filter methods before you run the query. Several filters combine with **and**. Filters are sent to the server and applied by the database, so you only download what matches.

## The filters

<CodeGroup>
```typescript TypeScript
pawabase.from("tasks")
  .eq("done", false)               // equal
  .neq("owner_id", user.id)        // not equal
  .gt("priority", 2)               // greater than
  .gte("priority", 3)
  .lt("due_at", new Date())        // less than (dates are accepted)
  .lte("estimate", 8)
  .like("title", "Write%")         // case-sensitive pattern
  .ilike("title", "%docs%")        // case-insensitive pattern
  .in("status", ["open", "blocked"])
  .notIn("status", ["archived"])
  .is("deleted_at", null)          // is null (or true / false)
  .isNot("assignee_id", null);     // is not null
```

```python Python
(pb.from_("tasks")
   .eq("done", False)
   .neq("owner_id", user_id)
   .gt("priority", 2)
   .gte("priority", 3)
   .lt("due_at", now)
   .lte("estimate", 8)
   .like("title", "Write%")
   .ilike("title", "%docs%")
   .in_("status", ["open", "blocked"])
   .not_in("status", ["archived"])
   .is_("deleted_at", None)
   .is_not("assignee_id", None))
```
</CodeGroup>

| Method | Meaning | Works on |
| --- | --- | --- |
| `eq`, `neq` | equal, not equal | all |
| `gt`, `gte`, `lt`, `lte` | comparisons | numbers, dates, text |
| `like`, `ilike` | pattern match; `%` is any run of characters | text |
| `in`, `notIn` (`in_`, `not_in`) | one of a list | all |
| `is`, `isNot` (`is_`, `is_not`) | null / true / false checks | all |

In Python, `in_` and `is_` have a trailing underscore because `in` and `is` are keywords.

`eq("x", null)` is rejected: nothing equals null. Use `is("x", null)` and `isNot("x", null)`.

## Conditions as an object

<CodeGroup>
```typescript TypeScript
const { data } = await pawabase.from("tasks").where({
  done: false,
  priority: { gte: 3 },
  status: { in: ["open", "blocked"] },
  deleted_at: { is: null },
});
```

```python Python
data = pb.from_("tasks").where(done=False, priority={"gte": 3}, status={"in": ["open", "blocked"]}).execute().data
```
</CodeGroup>

A plain value means equal. An object picks an operator: `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `like`, `ilike`, `in`, `nin`, `is`, `isnot`.

## Dates

Pass a `Date` (TypeScript) or `datetime` (Python), or an ISO 8601 string. Times are UTC.

```typescript
const lastWeek = new Date(Date.now() - 7 * 86400_000);
const { data } = await pawabase.from("orders").gte("created_at", lastWeek);
```

## Empty lists

`in("id", [])` returns nothing at once, without a request. That is what you want when a list of ids is empty.

## Search boxes

```typescript
function search(term: string) {
  return pawabase.from("posts").ilike("title", `%${term.replace(/[%_]/g, "\\$&")}%`).order("created_at", "desc").perPage(10);
}
```

Debounce the input so you don't send a query on every key press, and cancel the previous query with an `AbortSignal`. Escape `%` and `_` in the term, since they are pattern characters.

For real full-text search across many columns, a [route](/logic/routes) backed by a database full-text query is better than `ilike`.

## Combining "or"

Chained filters are all "and". For "or", use `in` for several values of one column, or two queries merged in your app, or a [route](/logic/routes) for complex logic:

```typescript
const { data } = await pawabase.from("tasks").in("status", ["open", "blocked"]);
```

## Filters and access rules

Filters narrow what you ask for. Access rules decide what you are allowed to see. A filter can **never** reveal a row a rule hides: asking for `owner_id = someone else` just returns nothing. Likewise a rule can't be bypassed by a clever filter.

## Make filters fast

Filter on [indexed](/database/indexes) columns. A filter on an unindexed column in a table of millions of rows scans it. If a list is slow, check the filter columns first.
