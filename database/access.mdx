Every table has five operations and **each has its own rule**. A rule decides, for each request, whether the caller may do that thing to that record. This page is how to set them for a table. The language of rules, with every operator and many recipes, is in [Access rules](/policies/overview).

## The five operations

| Operation | Studio label | Used by |
| --- | --- | --- |
| `list` | **See the list** | `from("t")`, `first()`, `count()`, `exists()` |
| `get` | **Open one record** | `get(id)` |
| `create` | **Add records** | `create()`, `createMany()` |
| `update` | **Edit records** | `update()`, `replace()` |
| `delete` | **Delete records** | `delete()` |

An operation is **off** until you switch it on. Off means the API acts as if it doesn't exist (and if all five are off, the table isn't served).

## In Studio

Open a table and choose the **Access** tab.

### Quick access sets

**Quick access set** fills in all five actions at once. You can still change each one afterwards.

| Set | What it does |
| --- | --- |
| **Private: secret keys and Studio only** | All five actions use the `service` rule |
| **Signed-in users can read and change** | All five use `authenticated` |
| **Anyone reads, signed-in users change** | `list` and `get` are `public`; the rest `authenticated` |
| **Each user sees and changes their own records** | All five use `owner`, except `create`, which is `authenticated` |

**Use one policy for everything** applies a single rule to all five. If your choices don't match a set, the picker shows **Custom**.

### Per-action rules

For each action there is a toggle and a rule picker. The picker offers:

| Choice | Meaning |
| --- | --- |
| **Default (signed-in users)** | No rule of its own: any signed-in user. Studio warns you to pick one to be explicit |
| **Anyone (public)** | Signed in or not |
| **Signed-in users** | `authenticated` |
| **Record owner (owner_id)** | The user whose id is in the owner column |
| **Signed in with 2FA** | `mfa`: the session completed a second step |
| **Secret keys & Studio** | `service` |
| **Nobody** | `deny` |
| **Users with role…** / **permission…** / **Owner via field…** / **Keys with scope…** | Parameterised shorthands, such as `role:admin`, `permission:posts.write`, `owner:author_id`, `scope:resource:write` |
| **This environment** | A named rule you saved on the [Policies](/policies/named-rules) page |
| **Custom condition** | The **condition builder**: rules and groups instead of JSON (see [Condition builder](/policies/condition-builder)) |
| **List** | Several rules; **all** must pass |

### Warnings

Studio flags choices that open a table too far:

- **Red:** "Anyone on the internet, signed in or not, can add records" (a write set to `public`).
- **Red:** the named rule doesn't exist in this environment, so saving would refuse it.
- **Amber:** a write has no rule of its own, so any signed-in user can. Pick one to be explicit.
- **Blue:** every action is off, so the table isn't served through the API: only Studio and secret keys reach it.

## How rules protect lists

For a **list**, the rule is worked out *before* any rows are read. A rule like "the owner column equals the caller" becomes part of the database query, so only the person's rows are read, pages are the right size, and counts are right. A rule that can't be turned into a filter is checked row by row afterwards, which is why `total` can be `null` and pages can come back short. Prefer simple equality rules on big tables. See [How rules are evaluated](/policies/how-rules-are-evaluated).

## What your app sees

| Result | Meaning |
| --- | --- |
| Empty list | The rule filtered every row out (or there are none) |
| `NotFoundError` on `get` | The record doesn't exist **or** your rule hides it |
| `AuthenticationError` | The rule needs a signed-in user and there was none |
| `PermissionError` / `ForbiddenError` | You're signed in, but a rule refused this action |

## Defaults to start from

| Table | Suggested rules |
| --- | --- |
| Per-user data (notes, settings) | The **owner** set |
| Public catalogue (products, posts) | **public** read, `service` or `role:admin` writes |
| Team data | A [rule on the organization](/policies/recipes-teams) |
| Billing, audit logs | **Private** (`service`), expose through a [route](/logic/routes) |
