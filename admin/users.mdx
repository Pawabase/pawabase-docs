All calls on this page use the [admin client](/admin/overview) and run on a trusted server.

## Search and read

<CodeGroup>
```typescript TypeScript
const page = await a.users.search({ search: "ada", status: "unverified", limit: 50, offset: 0 });
const user = await a.users.getUser("usr_123");
```

```python Python
page = pb.admin.users.search(search="ada", status="unverified", limit=50, offset=0)
user = pb.admin.users.get_user("usr_123")
```
</CodeGroup>

| Option | Meaning |
| --- | --- |
| `search` | Matches email, username and name |
| `status` | One of `disabled`, `unverified`, `locked`, `mfa`, `no_mfa` |
| `limit`, `offset` | Paging. The default limit is 50 |

Use `status: "locked"` for a "people who can't sign in" screen, and `status: "no_mfa"` to find administrators who should turn on two-factor.

## Create

<CodeGroup>
```typescript TypeScript
const created = await a.users.create({
  email: "grace@example.com",
  password: "a long passphrase",
  name: "Grace",
  emailVerified: true,
  roles: ["editor"],
  userMetadata: { theme: "dark" },
  appMetadata: { plan: "pro" },
});
```

```python Python
created = pb.admin.users.create(
    email="grace@example.com",
    password="a long passphrase",
    name="Grace",
    email_verified=True,
    roles=["editor"],
    user_metadata={"theme": "dark"},
    app_metadata={"plan": "pro"},
)
```
</CodeGroup>

| Field | Meaning |
| --- | --- |
| `email` | Required |
| `password` | Optional. Omit it to create an account the person signs into by email code or social sign-in. The project's password rules still apply |
| `username`, `name` | Optional profile fields |
| `emailVerified` | Defaults to `true`, because you are vouching for the address. Set `false` to require confirmation |
| `roles` | Role names to assign |
| `userMetadata` | Data the user can see and edit |
| `appMetadata` | Data only your server can see and edit. Safe for access decisions |

Creating through the admin client skips sign-up restrictions such as allow-lists, so you can invite people to a closed app.

## Update

<CodeGroup>
```typescript TypeScript
await a.users.update(userId, {
  name: "Grace Hopper",
  roles: ["admin"],              // replaces the user's roles
  appMetadata: { plan: "team" },
  emailVerified: true,
});

await a.users.update(userId, { disabled: true });    // block sign-in and end sessions
await a.users.update(userId, { disabled: false });
await a.users.update(userId, { unlock: true });      // clear a lockout after failed sign-ins
await a.users.update(userId, { password: "a new long passphrase" });
```

```python Python
pb.admin.users.update(user_id, name="Grace Hopper", roles=["admin"], app_metadata={"plan": "team"})
pb.admin.users.update(user_id, disabled=True)
pb.admin.users.update(user_id, unlock=True)
pb.admin.users.update(user_id, password="a new long passphrase")
```
</CodeGroup>

Only the fields you pass change. `roles` **replaces** the whole list, so send every role the person should have.

Disabling a user blocks future sign-ins and ends their current sessions. It is reversible, so prefer it to deleting.

## Delete

```typescript
await a.users.deleteUser(userId);
```

Deletion removes the account. If other tables reference the user's id, decide in advance what happens to those records.

## History

```typescript
const events = await a.users.history(userId);   // recent sign-ins and security events
```

Use it to answer "did Ada really sign in from there?".

## Second factors

If someone loses their authenticator and recovery codes:

```typescript
await a.users.resetMfa(userId);      // removes their second factors; they can sign in with a password and enrol again
```

Verify the person's identity by another route before you do this.

## Permissions beyond roles

A role is a bundle of permissions. To give one person a single extra permission without a role:

<CodeGroup>
```typescript TypeScript
await a.users.grant(userId, ["billing:read"]);
await a.users.revoke(userId, ["billing:read"]);
```

```python Python
pb.admin.users.grant(user_id, ["billing:read"])
pb.admin.users.revoke(user_id, ["billing:read"])
```
</CodeGroup>

Permissions look like `resource:action`, with `*` as a wildcard (`posts:write`, `billing:*`).

## Sessions, devices and keys of one user

<CodeGroup>
```typescript TypeScript
await a.users.revokeSessions(userId);                   // sign out everywhere
await a.users.revokeSession(userId, sessionId);          // one session
const devices = await a.users.devices(userId);
await a.users.forgetDevice(userId, deviceId);            // they'll be asked for 2FA on that device again
const keys = await a.users.apiKeys(userId);              // the user's own API keys (never the secrets)
```

```python Python
pb.admin.users.revoke_sessions(user_id)
pb.admin.users.revoke_session(user_id, session_id)
devices = pb.admin.users.devices(user_id)
pb.admin.users.forget_device(user_id, device_id)
keys = pb.admin.users.api_keys(user_id)
```
</CodeGroup>

## A support tool in 20 lines

```typescript
async function support(email: string) {
  const { data } = await a.users.search({ search: email, limit: 1 });
  const user = data[0];
  if (!user) return "No such user";

  return {
    user,
    recent: await a.users.history(user.id),
    unlock: () => a.users.update(user.id, { unlock: true }),
    signOutEverywhere: () => a.users.revokeSessions(user.id),
    resetMfa: () => a.users.resetMfa(user.id),
  };
}
```

Wrap each action in your own access check and log who used it.
