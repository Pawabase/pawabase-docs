You can build every rule in Studio without writing JSON. This page is the tour.

## 1. The Policies page: your named rules

**Access → Policies** lists the rules you've saved. Each is a **name**, a **description** and a **condition**. Anything that accepts a rule can refer to a saved one by name, so you write it once.

**New policy** opens a sheet:

| Field | Meaning |
| --- | --- |
| **Name** | Lowercase letters, digits and dashes or underscores, such as `own_rows` or `team_member` |
| **Description** | What the rule is for. Shown when picking |
| **Who passes** | The condition, edited with the [condition builder](/policies/condition-builder). *Checks on record fields are pushed down to SQL, so filtered lists stay paginated correctly. Secret keys always pass.* |

Switch the sheet between **Configure** (the builder) and the raw **JSON** to see exactly what is stored.

See [Named rules](/policies/named-rules).

## 2. The Access tab of a table

**Data → open a table → Access.** The place most people set rules. It has quick sets, and for each of the five actions a switch and a rule picker. Studio warns about choices that open the table too far. See [Database access](/database/access).

## 3. The rule picker

Wherever a rule is chosen (table actions, bucket rules, channel rules, routes) you get the same picker:

| Choice | Result |
| --- | --- |
| **Default (signed-in users)** | No rule of its own |
| **Anyone (public)**, **Signed-in users**, **Record owner (owner_id)**, **Signed in with 2FA**, **Secret keys & Studio**, **Nobody** | The built-ins |
| **Users with role…** | `role:<name>` |
| **Users with permission…** | `permission:<name>` |
| **Owner via field…** | `owner:<column>` |
| **Keys with scope…** | `scope:<scope>` |
| **This environment** | One of your named rules |
| **Custom condition** | The condition builder inline |
| **List** | Several rules, all required |

A **Save as policy** action turns an inline custom condition into a named rule.

## 4. The condition builder

The visual editor for conditions. See [Condition builder](/policies/condition-builder).

## 5. The request inspector

**Project → Activity**, then a request. Each request records what happened, including which rule decided and why. This is how you debug a refusal. See [Debugging](/policies/debugging).

## 6. The API Explorer

**Data → API Explorer** lets you send a request **as a real user** (sign in with an email and password in **Application-user authentication**) to test what they can do. See [API Explorer](/database/api-explorer).

## A good workflow

1. Pick the closest **quick set** or built-in on the table.
2. If you need more, build a **custom condition** in the builder, then **Save as policy** with a clear name.
3. Test with the Explorer as two different users.
4. Check **Activity** to confirm which rule decided.
5. Reuse the named rule on the other tables.

## The same in code

Everything in Studio is data you can create from code:

<CodeGroup>
```typescript TypeScript
await m.policies.create({
  name: "own_rows",
  description: "Rows the caller owns",
  condition: { all: [{ authenticated: true }, { eq: ["$record.owner_id", "$auth.user_id"] }] },
});
const named = await m.policies.list();
```

```python Python
pb.manage.policies.create({
    "name": "own_rows",
    "description": "Rows the caller owns",
    "condition": {"all": [{"authenticated": True}, {"eq": ["$record.owner_id", "$auth.user_id"]}]},
})
```
