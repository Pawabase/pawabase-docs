An **access rule** (Studio calls it a **policy**) answers one question about one request: *may this caller do this, here, now?* Every table action, bucket, channel, route and subscription is protected by one. Because rules run on the server for every request, your app can talk to Pawabase directly from a browser.

This section teaches rules from both sides at once: how to **build** them in Studio (a point-and-click condition builder, named rules, quick sets), and how to **test** and **debug** them.

## Rules in one minute

<Frame caption="A rule in Studio: signed in, and owns the record.">
  <img src="/images/studio/policy-builder.jpg" alt="Policy builder showing two rules joined by AND" />
</Frame>

- **All of** these rules pass:
  - **Is signed in**: yes
  - **Compare values:** `$record.owner_id` **equals** `$auth.user_id`

Read it as: *the caller is signed in **and** the record's owner is the caller.* That is the whole idea: conditions over facts about the caller (`$auth`), the record (`$record`), the submitted data (`$input`) and the request.

Most of the time you just choose "Record owner" from a menu.

## Built-in rules

You can use these by name anywhere a rule is accepted:

| Name | Who passes |
| --- | --- |
| `public` | Everyone, signed in or not |
| `authenticated` | Any signed-in user |
| `owner` | The user whose id is in the record's `owner_id` |
| `mfa` | Signed in **and** completed a second step |
| `service` | Secret keys and Studio only |
| `deny` | Nobody (except service callers) |
