Anywhere a rule is accepted (a table action's `policy`, a bucket's `read_policy`, a channel's `subscribe`, a route's `policy`) you may write it in several forms. They are all equivalent in power; use whichever reads best.

## The forms

| Form | Example | Meaning |
| --- | --- | --- |
| Built-in name | `"public"` | One of `public`, `authenticated`, `owner`, `mfa`, `service`, `deny` |
| Saved rule | `"team_member"` | A rule you saved under **Access → Policies** |
| Parameterised shorthand | `"role:admin"` | See below |
| Condition | `{ "eq": ["$record.status", "published"] }` | An inline condition |
| List | `["authenticated", "role:editor"]` | **All** of the entries must pass |
| Boolean | `true` / `false` | Always / never |
| Empty | `null` | The default: any signed-in user |

## Parameterised shorthands

| Written as | Means |
| --- | --- |
| `role:admin` | The caller has the role `admin` |
| `permission:posts.write` | The caller has the permission (or `*`) |
| `owner:author_id` | The record's `author_id` equals the caller's id |
| `scope:resource:write` | The API key has that scope |

The text after the first colon is passed through exactly, so `scope:resource:write` means the scope `resource:write`.

## Lists mean "all"

```json
["authenticated", "role:editor", "mfa"]
```

passes only for a signed-in editor who completed a second step. For "any", use a condition with `any`, whose entries are shorthand objects:

```json
{ "any": [{ "role": "admin" }, { "owner": "owner_id" }] }
```

## Mixing names and conditions

A list can mix forms:

```json
["authenticated", { "eq": ["$record.org", "$auth.org"] }]
```

## Unknown names

An unknown rule name is refused when you save (*"'x' is not a policy in this environment"*). Studio warns before you save. Names are resolved in the **current environment**, so a rule you created in `development` must exist in `production` too (promote it).

## Choosing a form

- Use **built-ins** for the 80% case.
- Use **saved rules** for anything used more than once, or that a teammate should be able to read and change in one place.
- Use **inline conditions** for one-offs.
- Use **lists** to add requirements ("and also 2FA").
