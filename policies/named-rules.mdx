A **named rule** is a condition saved under a name. Refer to it from any table, bucket, channel or route. Change it once and everything that uses it changes.

## Why

- **One definition.** "Team member" is defined in one place, not copied onto twelve tables.
- **Readable.** A table that says `team_member` explains itself.
- **Safer to change.** You can see and test the rule on its own.
- **Shareable.** Teammates and reviewers read a small named object.

## In Studio

**Access → Policies → New policy:** a **Name** (such as `own_rows`), a **Description**, and **Who passes** (the [condition builder](/policies/condition-builder)). Save.

To save an existing inline condition: in any rule picker choose **Custom condition**, build it, and use **Save as policy**.

Use it anywhere: in a rule picker, **This environment** lists your named rules.

Edit a rule on the **Policies** page: open it, change the condition, and save.

## In code

<CodeGroup>
```typescript TypeScript
await m.policies.create({
  name: "team_member",
  description: "Callers in the record's organization",
  condition: { all: [{ truthy: "$auth.org" }, { eq: ["$record.org", "$auth.org"] }] },
});

const list = await m.policies.list();
const one = await m.policies.getOne("team_member");
await m.policies.replace("team_member", { name: "team_member", description: "…", condition: { /* new */ } });
await m.policies.remove("team_member");
```

```python Python
pb.manage.policies.create({
    "name": "team_member",
    "description": "Callers in the record's organization",
    "condition": {"all": [{"truthy": "$auth.org"}, {"eq": ["$record.org", "$auth.org"]}]},
})
pb.manage.policies.replace("team_member", {"name": "team_member", "condition": {}})
pb.manage.policies.remove("team_member")
```
</CodeGroup>

The condition is validated when you save. A malformed condition is refused and nothing is stored.

## Naming

- Name by **meaning**, not mechanism: `team_member`, `own_rows`, `staff_with_2fa`, not `rule1`.
- Don't shadow the built-ins: `public`, `authenticated`, `owner`, `mfa`, `service`, `deny`.
- Keep the description short and state the intent ("Callers in the record's organization").

## Changing a rule that's in use

Every place that names it picks up the new definition. That is powerful and risky:

1. Copy it first: create `team_member_v2` and point one low-risk table at it.
2. [Test](/policies/testing) as different users.
3. Move other uses over, then retire the old one.

For a small change you are sure about, edit in place, but test straight afterwards.

## Removing a rule

A rule that's still referenced will make the tables that use it refuse requests (an unknown name is an error). Replace references first, then remove it.

## Across environments

Named rules belong to an environment. When you [promote](/environments/overview) `development` to `production`, include policies so the names resolve. A table promoted without its rule would reference a name that doesn't exist.

## Combine named rules

Named rules can appear in lists and, by name, anywhere a rule is accepted:

```json
["team_member", "role:editor"]
```

A named rule's *condition* can't refer to another named rule by name; compose them in the place of use, with a list.
