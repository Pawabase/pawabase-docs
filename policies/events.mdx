A [subscription](/automation/events#subscribe) runs a flow, function or channel when an event fires. A **condition** on it decides whether *this* event qualifies. It isn't a permission check: events come from the system, not from a caller. It is a filter.

## In Studio

On a subscription (**Logic → Event subscriptions**), the field **Only when…** takes a rule. *Filter on the event with rules over `$event`.* Build it in the [condition builder](/policies/condition-builder).

## What it can read

| Path | Meaning |
| --- | --- |
| `$event.name` | The event's name |
| `$event.data` | The event's payload (for a record event: `resource`, `change`, `record`) |
| `$env`, `$now` | As elsewhere |

## Examples

Only big orders:

```json
{ "gt": ["$event.data.record.total", 100000] }
```

Only when the status changed to paid:

```json
{ "eq": ["$event.data.record.status", "paid"] }
```

Only sign-ins by password:

```json
{ "eq": ["$event.data.method", "password"] }
```

## In code

```typescript
await m.subscriptions.create({
  name: "notify-sales",
  event: "orders.created",
  target_type: "flow",
  target: "notify-sales",
  condition: { gt: ["$event.data.record.total", 100000] },
});
```

## Cost

The condition is evaluated before the target is queued, so an event that doesn't match costs almost nothing. Prefer a condition over starting a flow that immediately exits.

## Events and security

Events carry data. A subscription that publishes to a [channel](/policies/realtime) or sends an [outbound webhook](/automation/webhooks) sends that payload to whoever listens. Don't forward more than the receiver should see: filter fields in the flow, and use `pick` in a [transformer](/database/transformers) for the audience.
