Small conditions combine into bigger ones with three operators.

| Operator | Takes | True when | In the builder |
| --- | --- | --- | --- |
| `all` | a list of conditions | **Every** condition passes (AND) | **All of** |
| `any` | a list of conditions | **At least one** passes (OR) | **Any of** |
| `not` | one condition | The condition does **not** pass | **None of** |

## Examples

Signed in **and** the owner:

```json
{ "all": [{ "authenticated": true }, { "eq": ["$record.owner_id", "$auth.user_id"] }] }
```

The owner **or** an admin:

```json
{ "any": [{ "owner": "owner_id" }, { "role": "admin" }] }
```

Anyone except blocked users:

```json
{ "not": { "contains": ["$record.blocked_ids", "$auth.user_id"] } }
```

An owner or an admin, but only while not locked:

```json
{ "all": [
  { "any": [{ "owner": "owner_id" }, { "role": "admin" }] },
  { "ne": ["$record.locked", true] }
] }
```

## Empty groups

| | Result |
| --- | --- |
| `all` of nothing | passes |
| `any` of nothing | fails |

The builder says so: *No rules: everyone passes* / *No rules: nobody passes*. Be careful removing the last rule from a group.

## Lists versus `all`

A **list** in a place that accepts a rule reference means "all of these":

```json
["authenticated", "role:editor", "mfa"]
```

is the same as

```json
{ "all": ["authenticated", "role:editor", "mfa"] }
```

...with one difference: a list may contain **names** (`"mfa"`, saved rules), but `all`/`any` contain **conditions**. Inside `all` and `any`, write shorthand objects: `{ "role": "editor" }`, not the string `"role:editor"`.

| Where | Entries may be |
| --- | --- |
| A list at the top (`policy: [...]`) | Names, `"role:x"` shorthands, conditions |
| Inside `all` / `any` / `not` | Conditions (objects) and shorthand objects |

## Short-circuiting and cost

Order doesn't change the outcome, but it can change the work: put cheap, decisive checks first (`authenticated`, a role) and expensive row checks last. For lists on large tables, keep the row check a plain equality, so it becomes a database filter ([How rules are evaluated](/policies/how-rules-are-evaluated)).

## Keeping it readable

- Name big rules ([Named rules](/policies/named-rules)) instead of nesting four deep.
- One idea per group: "who" in one `any`, "what state" in another, joined by `all`.
- Prefer a rule per action over one rule with `$request.method` branches.
- Comment in the rule's **description**; JSON has no comments.

## De Morgan, when you need "unless"

"Everyone except staff on weekends" is awkward as `not`. Often it is clearer to write the positive case:

```json
{ "any": [
  { "not": { "role": "staff" } },
  { "not": { "eq": ["$request.method", "GET"] } }
] }
```

Test any rule with `not` carefully: a missing value inside `not` flips in ways that surprise ([Values and paths](/policies/values-and-paths#not-and-missing-values)).
