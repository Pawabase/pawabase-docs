The condition builder is how you write custom rules in Studio. You add **rules** and **groups**; it writes (and reads back) the JSON for you. Anything it doesn't recognise is kept as a raw JSON rule, never dropped, so you can mix visual and hand-written parts.

## The pieces

### Groups

A group holds rules and decides how they combine:

| Studio | Means | JSON |
| --- | --- | --- |
| **All of** | Every rule must pass | `{ "all": [ … ] }` |
| **Any of** | At least one must pass | `{ "any": [ … ] }` |
| **None of** | None may pass | `{ "not": { "any": [ … ] } }` |

Groups nest, so "signed in AND (the owner OR an admin)" is an **All of** containing an **Any of**. An empty **All of** says *No rules: everyone passes*; an empty **Any of** says *No rules: nobody passes*.

### Rule types

Add a rule and choose its **Rule type**:

| Type | Use it for | Example |
| --- | --- | --- |
| **Anyone (always allow)** / **Nobody (always deny)** | A constant | `true` / `false` |
| **Authentication required** (a shorthand) | Is the caller signed in | `{ "authenticated": true }` |
| **Compare values…** | Two values with an operator | `$record.owner_id` **equals** `$auth.user_id` |
| **Check a value…** | One value: exists, is set, is empty | `$auth.org` **is set** |
| **Shorthand** | The common conditions | **Has role** `admin`, **Owns the record (field)** `author_id` |
| **Custom (JSON)** | Anything else | raw JSON |

### Shorthands in the builder

| Choice | Takes | Writes |
| --- | --- | --- |
| **Is signed in** | none | `{ "authenticated": true }` |
| **Has role** | `admin, editor` | `{ "role": ["admin", "editor"] }` |
| **Has permission** | `posts.write` | `{ "permission": "posts.write" }` |
| **Owns the record (field)** | `owner_id` | `{ "owner": "owner_id" }` |
| **Uses a secret key** | none | `{ "service": true }` |
| **Signed in with 2FA** | none | `{ "aal": "aal2" }` |
| **Key has scope** | `resource:write` | `{ "scope": "resource:write" }` |
| **Caller kind is** | `user` | `{ "kind": "user" }` |

### Comparison operators

Pick the **Comparison operator** for **Compare values…**:

| Studio | Operator | Studio | Operator |
| --- | --- | --- | --- |
| equals | `eq` | is one of | `in` |
| does not equal | `ne` | is not one of | `not_in` |
| greater than (>) | `gt` | contains | `contains` |
| at least (≥) | `gte` | starts with | `starts_with` |
| less than (\<) | `lt` | ends with | `ends_with` |
| at most (≤) | `lte` | matches regex | `matches` |

### Check operators

For **Check a value…**: **exists** (`exists`), **is set / true** (`truthy`), **is empty** (`empty`).

### The values you type

Each side of a comparison is either a **path** (starts with `$`) or a literal. The builder suggests common paths as you type:

`$auth.user_id`, `$auth.email`, `$auth.roles`, `$auth.permissions`, `$auth.org`, `$auth.aal`, `$record.id`, `$record.owner_id`, `$record.user_id`, `$input.`, `$request.ip`, `$request.method`, `$credential.is_service`, `$credential.scopes`, `$event.name`, `$event.data`, `$env`, `$now`.

Any path works, not just the suggestions: `$record.team_id`, `$input.status`. See [Facts a rule can read](/policies/context).

## Build one: "owner or admin, but only if not locked"

1. Start with **All of**.
2. Add a **Group** → **Any of**.
   - Add **Compare values…**: left `$record.owner_id`, **equals**, right `$auth.user_id`.
   - Add **Shorthand** → **Has role**: `admin`.
3. In the outer **All of**, add **Compare values…**: left `$record.locked`, **does not equal**, right `true`.

The JSON it writes:

```json
{ "all": [
  { "any": [
    { "eq": ["$record.owner_id", "$auth.user_id"] },
    { "role": "admin" }
  ] },
  { "ne": ["$record.locked", true] }
] }
```

## Tips

- Prefer the **shorthands** to hand-written comparisons: they're shorter and Pawabase can turn them into database filters.
- Keep groups shallow. If a rule needs more than three levels, split it into named rules ([Named rules](/policies/named-rules)).
- Use **Custom (JSON)** to paste a rule from these docs, then switch back to the builder to see it as boxes.
- The builder never executes anything; saving only checks that the JSON is a valid rule.

## Validation

When you save, Pawabase checks the rule is well formed: a condition is `true`, `false`, or an object with **exactly one key**; `all` and `any` take lists; binary operators take `[left, right]`; a `matches` pattern must be a valid regular expression. A mistake is refused with a message that names where it is.
