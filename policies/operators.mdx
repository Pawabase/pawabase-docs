An operator is one key in a condition object. Comparison operators take two values in a list: `{ "eq": [left, right] }`. A value is a [path](/policies/context) (`$auth.user_id`) or a literal (`"draft"`, `3`, `true`, `["a", "b"]`).

A condition has **exactly one key**. To say two things, wrap them in [`all` or `any`](/policies/combining).

## Comparison

| Operator | Reads as | True when |
| --- | --- | --- |
| `eq` | left equals right | The values are equal. Numbers and number-like ids are compared as text, so `42` equals `"42"` |
| `ne` | left does not equal right | They differ |
| `gt` / `gte` | greater than / at least | Both sides are present and `left > right` / `left >= right` |
| `lt` / `lte` | less than / at most | Both present and `left < right` / `left <= right` |
| `in` | left is one of the list | `right` is a list that contains `left` |
| `not_in` | left is not in the list | `right` is missing, or doesn't contain `left` |

Examples:

```json
{ "eq": ["$record.status", "draft"] }
{ "gte": ["$input.quantity", 1] }
{ "lte": ["$record.publish_at", "$now"] }
{ "in": ["$input.status", ["draft", "submitted"]] }
{ "not_in": ["$auth.user_id", "$record.blocked_ids"] }
```

### Ids are normalised

A database id may be an integer on one side and a string on the other (a token carries strings). `eq` and `in` treat them the same, so `{ "eq": ["$record.owner_id", "$auth.user_id"] }` works for either id type.

### Missing values

If a side is missing (`null`), `gt`, `gte`, `lt` and `lte` are **false**. `eq` with a missing side is true only if both are missing. `in` with a missing list is false; `not_in` with a missing list is **true**. Plan for this: a record with a null `publish_at` never satisfies `lte ["$record.publish_at", "$now"]`.

## Text and lists

| Operator | True when |
| --- | --- |
| `contains` | The left **list** contains the right value; or the left **text** contains the right text |
| `starts_with` | The left text starts with the right text |
| `ends_with` | The left text ends with the right text |
| `matches` | The left text matches the right **regular expression** (searched anywhere in the text; anchor with `^…$`) |

```json
{ "contains": ["$auth.roles", "admin"] }
{ "starts_with": ["$object.key", "public/"] }
{ "ends_with": ["$auth.email", "@acme.com"] }
{ "matches": ["$input.slug", "^[a-z0-9-]+$"] }
```

`matches` patterns are checked when you save; an invalid regular expression is refused.

<Warning>
`ends_with ["$auth.email", "@acme.com"]` is a convenient company check, but only meaningful if emails are verified. Combine with `{ "truthy": "$auth.email" }` and require verified email in [Restrictions](/auth/sign-up-restrictions), or use [company sign-in](/auth/company-sign-in).
</Warning>

## Tests on one value

These take **one** value, not a list:

| Operator | True when |
| --- | --- |
| `exists` | The value is present (not missing and not `null`) |
| `truthy` | The value is set and not false, zero or empty |
| `empty` | The value is missing, `null` or empty |

```json
{ "exists": "$auth.user_id" }
{ "truthy": "$auth.org" }
{ "empty": "$record.deleted_at" }
```

## Combining (see the next page)

`all`, `any`, `not`. See [Combining rules](/policies/combining).

## Unknown operators

An unknown operator name is refused when you save. The common wrong names:

| Wrong | Right |
| --- | --- |
| `and` | `all` |
| `or` | `any` |
| `neq`, `!=` | `ne` |
| `nin` | `not_in` |
| `==` | `eq` |

## Choosing between them

- "Is the same as": `eq`. "Is one of a fixed set": `in`.
- "Has this role": the `role` [shorthand](/policies/shorthands), or `contains ["$auth.roles", "admin"]`.
- "Is set": `truthy` (also rejects empty text); `exists` only checks for presence.
