## Paths versus literals

An operand starting with `$` is a **path**: it is looked up in the situation. Anything else is a **literal**: used as written.

| Operand | Is |
| --- | --- |
| `"$auth.user_id"` | A path |
| `"draft"` | The text `draft` |
| `3`, `true`, `null` | A number, a boolean, null |
| `["a", "b"]` | A list literal |
| `"$$5"` | The literal text `$5` (write `$$` for a literal dollar) |

## Reaching inside

Dots go into objects and lists. Lists are numbered from 0:

```text
$record.address.city
$auth.claims.plan
$object.segments.0
```

If any step doesn't exist, the whole value is missing.

## Missing is null

A missing value behaves like `null`:

- `exists` and `truthy` are false; `empty` is true.
- `eq` with a missing side is true only if the other is also missing/null.
- `gt`, `gte`, `lt`, `lte` are false.
- `in` is false if the list is missing; `not_in` is true.
- `contains` and string tests are false.

## Not and missing values

`not` flips whatever its inside says, including for missing data:

```json
{ "not": { "eq": ["$record.status", "archived"] } }
```

For a record with **no** `status`, the inside is false, so the `not` is **true**: the record passes. If that isn't what you want, say it positively: `{ "in": ["$record.status", ["open", "draft"]] }`.

Prefer `ne` over `not eq`: they are equal, but `ne` is clearer.

## Types

Rules compare what the data holds:

| Data | Notes |
| --- | --- |
| Ids | Integers and strings are treated alike in `eq` and `in` |
| Numbers | Compare numerically with `gt`… |
| Booleans | `true` / `false`, not `"true"` |
| Dates | Compare ISO 8601 strings correctly with `gt`/`lt` when both are in the same format; `$now` is a real time. For date columns, compare against `$now` |
| Text | Case-sensitive |

Case-insensitive compare isn't built in. Store a normalised (lowercase) column and compare against that, or use `matches` with `(?i)`.

## Lists

`contains` works on lists (`$auth.roles`) and text. `in` takes the value on the left and the list on the right.

```json
{ "in": ["$auth.user_id", "$record.member_ids"] }        // is the caller in the record's list
{ "contains": ["$record.member_ids", "$auth.user_id"] }  // the same, the other way round
```

Both are fine. Use whichever reads better.

## Ownership across types

If a table's `owner_id` is an integer and tokens carry a string, `eq` still works, because ids are normalised before they are compared.

## The empty string

An empty string is "empty" (`empty` true, `truthy` false) but it **exists**. A form that submits `""` for an optional field gives `exists` true. Use `truthy` for "has a real value".

## Patterns that bite

| Rule | Surprise | Better |
| --- | --- | --- |
| `{ "gt": ["$record.expires", "$now"] }` | Rows with no `expires` never pass | Add `any` with `{ "empty": "$record.expires" }` |
| `{ "not": { "eq": [x, y] } }` | Missing `x` passes | `ne`, or add `exists` |
| `{ "eq": ["$auth.org", "$record.org"] }` | Both null: passes! | Add `{ "truthy": "$auth.org" }` |
| `{ "in": ["$auth.user_id", "$record.members"] }` | A null list: false (safe) | fine |

The third is the classic: when the caller has **no organization** and a record has **no org**, "both null" is equal, so everyone matches. Always require the caller's side to be set.
