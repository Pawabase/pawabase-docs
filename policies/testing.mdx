Rules protect your data, so test them like code. The idea is simple: **sign in as different people and try things that should and should not work.**

## A test harness

```typescript
import { createClient } from "@pawabase/client";
import { PermissionError, NotFoundError } from "@pawabase/client";

async function signedIn(email: string, password: string) {
  const client = createClient({ url, apiKey: publishableKey, auth: { persistSession: false } });
  await client.auth.signInWithPassword({ email, password });
  return client;
}

const ada = await signedIn("ada@example.com", "…");
const bob = await signedIn("bob@example.com", "…");
const visitor = createClient({ url, apiKey: publishableKey, auth: { persistSession: false } });
```

Create these users once in your development environment, with the [admin client](/admin/users), and keep their credentials in your test configuration.

## What to assert

| Test | Expected |
| --- | --- |
| Ada creates a note | Succeeds and `owner_id` is hers |
| Ada lists notes | Gets only hers |
| Bob reads Ada's note by id | `NotFoundError` |
| Bob updates or deletes Ada's note | `NotFoundError` or `PermissionError` |
| Visitor lists notes | `AuthenticationError`, or an empty list, depending on the rule |
| Ada sets `owner_id` to Bob on create | Refused |

```typescript
it("hides other people's notes", async () => {
  const note = await ada.from("notes").create({ text: "secret" });

  const { data } = await bob.from("notes");
  expect(data.find((n) => n.id === note.id)).toBeUndefined();

  await expect(bob.from("notes").get(note.id)).rejects.toBeInstanceOf(NotFoundError);
  await expect(bob.from("notes").update(note.id, { text: "hacked" })).rejects.toBeInstanceOf(NotFoundError);
});
```

## Reading a refusal

| You see | Meaning |
| --- | --- |
| `AuthenticationError` (401) | The rule needs a signed-in user and there was none |
| `PermissionError` / `ForbiddenError` (403) | A signed-in caller was refused by a rule. In TypeScript, `error.policy` names it |
| `NotFoundError` (404) | The record does not exist, **or a read rule hides it**. The two are the same on purpose |
| An empty list | The list rule filtered everything out |
| `total: null` | The rule is checked per row, so the server cannot count |

## Find the rule that said no

1. Repeat the call with a **secret key** on a server. If it succeeds, a rule was the cause.
2. Read `error.policy` (TypeScript) for the rule's name.
3. Open the request in the dashboard's request log with `error.requestId`. It shows which rule decided and why.
4. Look at what the rule compares. Print the caller's session (`await pawabase.auth.getSession()`) and the record, and check each value by hand, especially `owner_id` against `user.id`, and `org` against the active organization.

## Common mistakes

- **Wrong operator name.** `and`, `or`, `neq` are rejected. Use `all`, `any`, `ne`.
- **Trusting `user_metadata`.** People can edit it. Use `roles` or `app_metadata`.
- **Forgetting the owner on create.** If the record's owner column is empty, `owner` never matches, and the creator cannot see what they made.
- **A rule that works for reads but not lists.** Lists are planned before reading; a rule that is awkward to reduce to a filter makes lists slow or uncounted.
- **Testing only the happy path.** Always test the refusal.

## Preview a role's effect

To see what permissions a role gives, list the roles with the admin client:

```typescript
import { admin } from "@pawabase/client/admin";
const roles = await admin(serverClient).roles.list();
```
