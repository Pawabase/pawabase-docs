Rules protect your data, so test them like code. The method is simple: **act as different people and try things that should and shouldn't work.**

## Test in Studio first

The **API Explorer** (**Data → API Explorer**) sends real requests. Under **Application-user authentication** sign in as a test user (email, password, MFA code) and the request goes out with that person's token. Try the same request as:

1. A signed-in user who **should** pass.
2. A signed-in user who **shouldn't** (someone else's record).
3. Nobody (clear the authentication).

Then open **Activity** to confirm which rule decided each. See [API Explorer](/database/api-explorer) and [Debugging](/policies/debugging).

## A test harness (code)

Create test users once in `development` in Studio (**Users & auth → People → Users → New user**; see [Users](/auth/users)), keep their credentials in your test configuration, and sign in per test:

```typescript
import { createClient, PermissionError, NotFoundError, AuthenticationError } from "@pawabase/client";

async function signedIn(email: string, password: string) {
  const client = createClient({ url, apiKey: publishableKey, auth: { persistSession: false } });
  await client.auth.signInWithPassword({ email, password });
  return client;
}

const visitor = createClient({ url, apiKey: publishableKey, auth: { persistSession: false } });
const ada = await signedIn("ada@example.com", "…");
const bob = await signedIn("bob@example.com", "…");
const admin = await signedIn("admin@example.com", "…");
```

```python
def signed_in(email, password):
    pb = Pawabase(URL, PUBLISHABLE_KEY)        # a fresh client per user
    pb.auth.sign_in_with_password(email=email, password=password)
    return pb
```

## A table of cases per rule

For every table, write the rows of this table and a test for each:

| Case | Expected |
| --- | --- |
| Owner creates | Succeeds; the owner is set |
| Owner lists | Only their records |
| Owner gets, updates, deletes their own | Succeeds |
| Another user gets / updates / deletes it | `NotFoundError` |
| Another user lists | Doesn't include it |
| Visitor lists | `AuthenticationError`, or empty, per the rule |
| Admin (if allowed) | Succeeds |
| Owner sets `owner_id` to someone else | Refused / ignored |
| Boundary values (quantity 0, 11) | Refused |

```typescript
it("hides other people's notes", async () => {
  const note = await ada.from("notes").create({ text: "secret" });

  expect((await bob.from("notes")).data.find((n) => n.id === note.id)).toBeUndefined();
  await expect(bob.from("notes").get(note.id)).rejects.toBeInstanceOf(NotFoundError);
  await expect(bob.from("notes").update(note.id, { text: "hacked" })).rejects.toBeInstanceOf(NotFoundError);
  await expect(bob.from("notes").delete(note.id)).rejects.toBeInstanceOf(NotFoundError);
});

it("needs sign-in", async () => {
  await expect(visitor.from("notes").create({ text: "x" })).rejects.toBeInstanceOf(AuthenticationError);
});
```

## Test the edges

These are where real bugs hide:

- **The caller has no organization** and a record has none ([null equals null](/policies/values-and-paths#patterns-that-bite)).
- **A record with a null date** against `lte [..., "$now"]`.
- **A role that was just changed:** sign out and in, or wait for refresh.
- **Two organizations:** a user in both, acting in one.
- **A record created by a server** with no owner.
- **Related records:** `expand` a relation whose table has stricter rules.
- **Realtime:** subscribe as Bob; Ada's change must not arrive.
- **Files:** upload under someone else's prefix.

## Reading refusals

| You see | Meaning |
| --- | --- |
| `AuthenticationError` (401) | The rule needs a signed-in user |
| `PermissionError` / `ForbiddenError` (403) | A signed-in caller refused. `error.policy` names the rule (TypeScript) |
| `NotFoundError` (404) | Missing, **or hidden by a read rule** |
| An empty list | The `list` rule filtered everything |
| `total: null` | A per-row rule; the server can't count |

## Compare with a secret key

If a call fails and you think it shouldn't, repeat it with a secret key on a server. Success means a rule was the cause; failure means something else (validation, a missing table).

## Run rule tests in CI

Keep the harness in your repository and run it against a `development` or preview environment on each change to rules, just like unit tests. A changed named rule can alter a dozen tables at once; the tests tell you.

## After you change a rule

1. Run the cases.
2. Check **Activity** for unexpected 403s in the hour after you ship.
3. For a named rule used widely, move tables over one at a time ([Named rules](/policies/named-rules#changing-a-rule-thats-in-use)).
