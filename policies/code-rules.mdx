The rule language covers most needs, but it only reads the facts it is given. It can't ask "is this person a member of the *project* this task belongs to?" because that needs another table. For those cases your team writes a **code rule**: a small function registered on the server and referred to **by name**, exactly like a saved rule.

## When you need one

| Need | Why JSON can't |
| --- | --- |
| Membership in a list stored in another table | Rules read one record, not joins |
| "At most 3 open items" | Needs a count of other rows |
| An external check (a feature flag service, a billing status) | No network calls in rules |
| Complex business logic you want tested as code | |

First consider alternatives: copy the needed value onto the record, use a unique partial [index](/database/indexes#partial-indexes), or do the check in a [route](/logic/routes).

## What it looks like

On the server side of your project, a code rule is a function that receives the same facts (`auth`, `record`, `input`, `request`, `credential`, `env`) and returns true or false:

```python
from pawabase_server.policies import policy

@policy("project_member", description="Callers who belong to the record's project")
async def project_member(context):
    project_id = context["record"]["project_id"]
    return await is_member(context["auth"]["user_id"], project_id)
```

It may be `async`, and may use your own data access. Keep it fast: it runs on the request path, and for list requests, possibly per row.

## Use it

Once registered, it appears alongside your saved rules. Refer to it by name anywhere:

<CodeGroup>
```typescript TypeScript
operations: {
  list: { enabled: true, policy: "project_member" },
  update: { enabled: true, policy: ["project_member", "role:editor"] },
}
```

```python Python
"operations": {"list": {"enabled": True, "policy": "project_member"}}
```
</CodeGroup>

In Studio it shows in the rule picker. A code rule can't be edited in the dashboard.

## Rules for code rules

- **Pure:** decide; never write data.
- **Fast:** one indexed query at most.
- **Safe on missing data:** treat a missing `record`/`auth` as "no".
- **Tested:** unit-test with fake contexts, and include them in your [rule tests](/policies/testing).
- **Named by meaning:** `project_member`, not `check2`.
- **Remember lists:** a code rule can't become a database filter, so lists are checked per row and totals are `null`.

## A safer alternative for many cases

Often the best "code rule" is **data**: add a `project_member_ids` list to the record (maintained by a flow when membership changes) and write `{ "contains": ["$record.project_member_ids", "$auth.user_id"] }`. It stays visible in Studio and still works in JSON.
