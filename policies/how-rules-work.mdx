## A rule is data

A rule is a small JSON value, not code. That is why Studio can show it as a visual builder and why it can be copied, reviewed and tested. It is one of:

| Form | Example |
| --- | --- |
| A **name** | `"authenticated"`, `"owner"`, `"team_member"` |
| A **shorthand** with a value | `"role:admin"`, `"permission:posts.write"`, `"owner:author_id"`, `"scope:resource:write"` |
| A **condition** | `{ "eq": ["$record.owner_id", "$auth.user_id"] }` |
| A **list** of any of those | `["authenticated", "role:editor"]` (all must pass) |
| `true` / `false` | Always / never |

## The situation

Each request is described to the rule as a set of facts:

| Part | Contains |
| --- | --- |
| `$auth` | Who is calling: id, email, roles, permissions, organization, assurance level |
| `$record` | The row being read, changed or deleted |
| `$input` | The data being submitted (create and update) |
| `$request` | The request: method, path, address, parameters |
| `$credential` | The API key used: whether it is a secret key, its scopes |
| `$env` | The environment name |
| `$object` | The file being touched (storage rules) |
| `$event` | The event (subscription conditions) |
| `$now` | The current time |

See [Facts a rule can read](/policies/context) for every field.

## The decision

1. The request arrives with a key and (for a signed-in person) a token.
2. Pawabase builds the situation from the token, the key, the request and, when relevant, the record.
3. The rule for that action is evaluated against it.
4. **True:** the request goes on. **False:** it is refused before anything is read or written.

For **list** requests the rule is worked out first, so it can become part of the database query. See [How rules are evaluated](/policies/how-rules-are-evaluated).

## Who always passes

**Secret keys always pass**, as does Studio (which acts with the operator's authority). That is why testing with a secret key tells you whether a rule is the cause of a refusal. It is also why a secret key must never reach a browser.

## What a refusal looks like

| Result | Meaning |
| --- | --- |
| `AuthenticationError` (401) | The rule needs a signed-in user and the request had none |
| `PermissionError` / `ForbiddenError` (403) | Signed in, but the rule said no. In TypeScript `error.policy` names it |
| `NotFoundError` (404) | On reads and changes of one record: the record doesn't exist **or** the rule hides it |
| Empty list | The rule filtered every row out |

A refusal is decided before the record is looked up, so it never reveals whether a key or id exists.

## Rules are per action, not per table

A table has five operations, each with its own rule: you might let anyone read, signed-in users create, owners update, and nobody delete. Think of a table's access as a small grid, not one switch.

## Rules are evaluated every time

There is no session-long "permission". Every request is evaluated fresh against the current record and the caller's current token. A change to a person's roles reaches them when their token refreshes ([Roles](/auth/roles#when-changes-take-effect)).

## Defaults

| Where | If you set nothing |
| --- | --- |
| A table action | Off: the action doesn't exist |
| An enabled table action with no rule | Any signed-in user. Studio warns so you choose explicitly |
| A bucket | `authenticated` |
| A channel | `authenticated` |

**Be explicit.** Choose a rule for every action you enable.

## What rules can't do

- They decide whole **requests and rows**, not individual columns. For column-level privacy, mark columns [write only](/database/columns-and-types#flags), split a table, or use a [transformer](/database/transformers).
- They don't call other systems or run arbitrary code. When a rule needs code, your team registers a [code rule](/policies/code-rules) and you refer to it by name.
- They can't change data.
