## A rule is a set of checks

A rule is a short list of checks about a request. You build it in Studio by picking checks from menus; there is nothing to write. A rule can be as simple as **Signed-in users** or as specific as "the person owns the record, **or** is an admin, **and** the record isn't locked".

## Where you choose a rule

Anywhere a rule is needed, Studio shows the same **rule picker**:

| Choice | Meaning |
| --- | --- |
| **Anyone (public)** | Everyone, signed in or not |
| **Signed-in users** | Anyone with an account who is signed in |
| **Record owner (owner_id)** | The person whose id is stored on the record |
| **Signed in with 2FA** | Signed in and completed a second step |
| **Secret keys & Studio** | Your servers and your team only |
| **Nobody** | No one, except secret keys and Studio |
| **Users with role…**, **Users with permission…**, **Owner via field…**, **Keys with scope…** | Common checks with one value to fill in |
| **This environment** | A rule you saved on the **Policies** page |
| **Custom condition** | Build your own with the condition builder |
| **List** | Several rules; **all** must pass |

## What a rule can check

Each request is described to the rule as facts. In the builder you pick them as **paths**:

| Fact | Means |
| --- | --- |
| `$auth…` | Who is calling: id, email, roles, permissions, organization, second-factor level |
| `$record…` | The row being read, changed or deleted |
| `$input…` | The data being submitted |
| `$request…` | The request: method, path, address |
| `$credential…` | The API key: whether it's a secret key, its scopes |
| `$object…` | The file being touched (storage rules) |
| `$event…` | The event (subscription conditions) |
| `$now` | The current time |

See [Facts a rule can check](/policies/context) for every field.

## How a decision is made

1. The request arrives with a key and, for a signed-in person, their token.
2. Pawabase gathers the facts.
3. The rule for that action is checked against them.
4. **Pass:** the request goes on. **Fail:** it's refused before anything is read or written.

For **lists**, the rule is worked out first so it can become part of the database query. See [How rules are evaluated](/policies/how-rules-are-evaluated).

## Who always passes

**Secret keys always pass**, and so does Studio (it acts with your team's authority). That is why testing with a secret key tells you whether a rule is the cause of a refusal, and why a secret key must never reach a browser.

## What a refusal looks like

| Result | Meaning |
| --- | --- |
| `AuthenticationError` (401) | The rule needs a signed-in person and the request had none |
| `PermissionError` / `ForbiddenError` (403) | Signed in, but the rule said no. In TypeScript `error.policy` names it |
| `NotFoundError` (404) | On one record: it doesn't exist **or** the rule hides it |
| An empty list | The rule filtered every row out |

A refusal is decided before the record is looked up, so it never reveals whether an id exists.

## Rules are per action

A table has five actions, each with its own rule: you might let anyone read, signed-in people create, owners update, and nobody delete. Think of a table's access as a small grid, not one switch.

## Rules are checked every time

There is no session-long "permission". Every request is checked fresh against the current record and the caller's current token. A change to a person's roles reaches them when their token refreshes ([Roles](/auth/roles#when-changes-take-effect)).

## Defaults

| Where | If you set nothing |
| --- | --- |
| A table action | Off: the action doesn't exist |
| An enabled table action with no rule | Any signed-in person. Studio warns you to choose explicitly |
| A bucket | Signed-in users |
| A channel | Signed-in users |

**Be explicit.** Choose a rule for every action you turn on.

## What rules can't do

- They decide whole **requests and rows**, not columns. For column privacy, mark a column **Write only**, split a table, or use a [transformer](/database/transformers).
- They can't look at other tables or call other systems. When a rule needs that, your team adds a [code rule](/policies/code-rules) and you pick it by name.
- They can't change data.
