A **blueprint** is a whole app in one file you can share: a `.zip` of YAML files with `blueprint.yml` at its root. Install it on any Pawabase and it builds the app in **new** environments: settings, sign-in, secrets, roles, tables, policies, flows, routes, storage, mail, events, AI, realtime, operations and sample data. Export an environment and you get the same zip back.

A blueprint never changes an environment that already exists. That makes it safe to hand to someone else, to keep in a repository as a starter, or to use for a fresh copy of an app.

<Note>
This replaces the single-JSON blueprint (`GET /envs/{env}/blueprint` and `POST /blueprints/apply`). Those routes still work, but they're deprecated and answer with a `Deprecation` header. Use the zip format for anything new.
</Note>

## What's in a bundle

```text
store.blueprint.zip
├── blueprint.yml          # required: the format, the name, variables, and the files it includes
├── settings.yml           # environment settings and infrastructure
├── auth.yml               # sign-in: methods, providers, emails, branding, bot protection…
├── secrets.yml            # secrets your flows read (values come from variables)
├── access.yml             # roles, policies, organization roles and permissions
├── tables.yml             # schemas and tables
├── api.yml                # custom routes
├── storage.yml            # buckets
├── events.yml             # subscriptions, webhooks, inbound hooks, schedules
├── ai.yml                 # AI providers, models, connections, knowledge bases, agents
├── realtime.yml           # realtime channels
├── operations.yml         # status page and alarms
├── flows/
│   ├── place_order.yml    # one file per flow
│   └── send_receipt.yml
├── mail/
│   ├── receipt.yml        # one file per mail template…
│   └── receipt.html       # …and its HTML, read in with !file
└── data/
    └── products.csv       # sample rows, read in with !csv
```

Only `blueprint.yml` is required, and it can hold everything. The other files exist so a large app can be split by concern. You choose how to split it: the names above are what an export writes, not rules.

## blueprint.yml

```yaml blueprint.yml
blueprint: 2                    # the format; this server reads format 2
name: Store
description: A small shop with orders, receipts and a support desk
version: 1.4.0                  # your app's own version, shown when it's installed
environments: [development, production]   # what install builds if you don't say

variables:
  STRIPE_SECRET_KEY: {description: Stripe secret key, secret: true}
  GOOGLE_CLIENT_SECRET: {description: Google sign-in client secret, secret: true}
  SUPPORT_EMAIL: {description: Where support mail goes, secret: false, default: help@example.com}

include:
  - settings.yml
  - auth.yml
  - access.yml
  - tables/*.yml                # globs are read in name order
  - flows/*.yml
  - mail/*.yml
```

`include:` merges the named files into the file that names them. Mappings merge key by key, and lists are joined, so two files can each add tables. Any file can include others, but a file can't include itself (directly or through others).

## Writing sections

Each section takes exactly what the matching Platform API request takes. Whatever the API accepts, a blueprint can say, and it's checked by the same rules.

A list section can be written as a list or as a mapping keyed by name. These two are the same:

<CodeGroup>
```yaml As a mapping
tables:
  products:
    fields:
      - {name: title, type: string, required: true}
      - {name: price, type: number}
    operations:
      list: {enabled: true, policy: public}
      create: {enabled: true, policy: editors}
```

```yaml As a list
tables:
  - name: products
    fields:
      - {name: title, type: string, required: true}
      - {name: price, type: number}
    operations:
      list: {enabled: true, policy: public}
      create: {enabled: true, policy: editors}
```
</CodeGroup>

### Every section

| Section | What it sets | Same as |
|---|---|---|
| `settings` | Environment settings (CORS, time zone, currency, realtime defaults, your own keys) | `PATCH /envs/{env}` `settings` |
| `infra` | Infrastructure (mail server, storage) | `PATCH /envs/{env}` `infra` |
| `auth` | Sign-in: methods, providers, emails, branding, signup form, legal, directory, bot protection, password rules, sessions | `PATCH /envs/{env}` `auth` |
| `secrets` | Secrets flows read, `NAME: value` | `PUT /envs/{env}/secrets/{name}` |
| `roles` | Roles and their permissions | `PUT /envs/{env}/auth/roles` |
| `org_permissions` | Permissions organization roles can grant, `key: description` | `PUT /envs/{env}/auth/org-permissions/{key}` |
| `org_roles` | Roles every organization has, keyed by `key` | `PUT /envs/{env}/auth/org-roles/{key}` |
| `schemas`, `policies`, `tables` | Shared field sets, access rules, tables | the definition routes |
| `flows`, `routes` | Workflows, and custom routes bound to them | the definition routes |
| `buckets`, `mail_templates` | File storage, email templates | the definition routes |
| `subscriptions`, `webhooks`, `inbound_hooks`, `schedules` | Events in and out, and timed runs | the definition routes |
| `connections`, `knowledge_bases`, `agents` | App connectors, knowledge bases, AI agents | the definition routes |
| `ai` | `providers` (keyed by name) and `models` (keyed by alias) | `POST /envs/{env}/ai/providers`, `…/ai/models` |
| `mail` | `kit`: the mail designer's brand, palettes and blocks | `PUT /envs/{env}/mail/kit` |
| `realtime_channels` | Channel rules, keyed by `pattern` | `POST /envs/{env}/realtime-channels` |
| `status_page` | The public status page | `PUT /envs/{env}/status-page` |
| `alarms` | Alarms on metrics | `POST /envs/{env}/alarms` |
| `machines` | Service and agent identities | `POST /envs/{env}/auth/machines` |
| `keys` | API keys made with the environment | `POST /envs/{env}/keys` |
| `data` | Sample rows, by table name | inserted after everything else |

`resources`, `mail-templates`, `inbound-hooks` and `knowledge-bases` are accepted as other names for `tables`, `mail_templates`, `inbound_hooks` and `knowledge_bases`.

### Sign-in

The `auth` section is the whole sign-in setup: which methods are on, social providers, the emails people receive, branding and bot protection.

```yaml auth.yml
auth:
  signup_enabled: true
  require_email_verification: true
  email_code_enabled: true
  magic_link_enabled: false
  passkeys_enabled: true
  anonymous_enabled: false
  mfa_enabled: true
  password_policy: strong
  password_min_length: 12
  access_ttl: 900
  refresh_ttl: 2592000
  allowed_email_domains: []
  default_roles: [customer]
  providers:
    google:
      enabled: true
      client_id: 1234-abc.apps.googleusercontent.com
      client_secret: ${GOOGLE_CLIENT_SECRET}
    github:
      enabled: true
      client_id: Iv1.0123456789
      client_secret: ${GITHUB_CLIENT_SECRET}
  emails:
    support: ${SUPPORT_EMAIL}
  directory:
    mfa: {totp: true, email: true, require: admins}
    api_keys: {enabled: true, max_per_user: 5}
```

<Note>
Enterprise sign-in (OIDC and SAML) belongs to an organization, not to the environment. A blueprint can't create organizations, so it can't create their connections either: add those in Studio under **Enterprise sign-in** once the organizations exist.
</Note>

### AI

```yaml ai.yml
ai:
  providers:
    openai: {kind: openai, key: "${OPENAI_API_KEY}"}
  models:
    chat: {provider: openai, upstream: gpt-4o-mini, policy: authenticated, fallback: fast}
    fast: {provider: openai, upstream: gpt-4o-mini, policy: authenticated}
    embed: {provider: openai, upstream: text-embedding-3-small, kind: embedding, dimensions: 1536}
```

Providers and models are created before flows and agents, so those can name a model.

## Files and values from other files

Three tags bring other files in. Paths are relative to the file that names them, and they can never point outside the bundle.

| Tag | Gives | Example |
|---|---|---|
| `!file path` | The file's text, as a string | `html: !file welcome.html` |
| `!include path` | A YAML or JSON file's content, in place | `fields: !include fields/address.yml` |
| `!csv path` | A CSV file's rows, one mapping per line | `products: !csv data/products.csv` |

```yaml mail/welcome.yml
mail_templates:
  - name: welcome
    subject: Welcome to {{ app.name }}
    html: !file welcome.html
    text: !file welcome.txt
```

In CSV files, an empty cell is null, `true` and `false` are booleans, and numbers are numbers.

## Variables and credentials

Credentials don't belong in a file you share. Write them as **variables** and supply the values when you install:

```yaml
secrets:
  STRIPE_SECRET_KEY: ${STRIPE_SECRET_KEY}
```

- `${NAME}` is filled in at install time, anywhere in any text.
- `${NAME:-fallback}` uses the fallback when no value is given.
- `$${` is a literal `${`.
- Flow templates (`{{ input.id }}`) and policy paths (`$auth.user_id`) are left alone, because they aren't `${…}`.
- A value that is a single variable keeps its type, so `max_sessions: ${MAX_SESSIONS}` given `5` is the number `5`.

Declare variables under `variables:` with a description, whether they're secret, and an optional default. Undeclared variables still work, but declaring them tells whoever installs the blueprint what to supply.

You can also write a credential straight into the file. The blueprint installs, and the check lists every place it found one, so it's a choice you make knowingly.

<Warning>
In YAML's short `{ … }` form, quote a variable: `{kind: openai, key: "${OPENAI_API_KEY}"}`. Without the quotes YAML reads the braces as part of the mapping. In the normal block form no quotes are needed.
</Warning>

## Check, install, export

All three are Platform API routes that need a secret (management) key.

### Check

`POST /platform/v1/blueprints/plan` reads a bundle and creates nothing. It returns what an install would build, the variables it needs, where credentials are written inline, and the first problem it finds, with the file, section, item and field.

```bash
curl -X POST "$PAWABASE_URL/platform/v1/blueprints/plan" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -F file=@store.blueprint.zip
```

```json Response
{
  "name": "Store",
  "files": ["blueprint.yml", "auth.yml", "tables/products.yml", "flows/place_order.yml"],
  "variables": [
    {"name": "STRIPE_SECRET_KEY", "description": "Stripe secret key", "secret": true, "required": true, "provided": false}
  ],
  "missing": ["STRIPE_SECRET_KEY"],
  "inline_credentials": [],
  "counts": {"tables": 5, "flows": 6, "policies": 5, "secrets": 1},
  "environments": ["development", "production"],
  "problem": null,
  "ok": true
}
```

### Install

`POST /platform/v1/blueprints/install` builds **new** environments. Send the zip as a multipart `file`, with `variables` (a JSON object) and optionally `environments` (a JSON list, or names separated by commas). Variables travel in the body, never in the address.

```bash
curl -X POST "$PAWABASE_URL/platform/v1/blueprints/install" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -F file=@store.blueprint.zip \
  -F 'variables={"STRIPE_SECRET_KEY": "sk_live_…", "GOOGLE_CLIENT_SECRET": "…"}' \
  -F 'environments=["store-dev","store-prod"]'
```

The same request can be JSON instead: `{"bundle": "<the zip, base64>", "variables": {…}, "environments": […]}`.

What happens, in order, for each new environment:

1. Settings, infrastructure and sign-in.
2. Secrets, roles, organization permissions and roles.
3. Schemas and policies, then AI providers and models.
4. The rest of the definitions, then every table is created.
5. The mail kit, realtime channels, the status page, alarms, machines and API keys.
6. Sample data, into the first environment only.

Every step goes through the same checks the API uses. If one fails, nothing is kept: the half-built environments are removed with everything made for them, and the answer says where it failed:

```json 422
{"message": "the blueprint could not be installed", "where": "tables[products]", "problem": "operations.create.policy: unknown policy 'editor'"}
```

The answer to a successful install lists the environments, the keys each was given, the API keys and machine keys the blueprint made (shown once), and warnings. Webhooks are installed **switched off**, because a shared blueprint's webhooks point at its author's servers: review their URLs, then turn them on.

Plan limits apply as they do in Studio. On a plan without the AI gateway or organization access, a blueprint that sets them is refused at that section.

### Export

`GET /platform/v1/envs/{env}/blueprint.zip` writes an environment as a bundle: `blueprint.yml` and a file per concern, one file per flow and mail template, and long email HTML in `.html` files.

```bash
curl -o store.blueprint.zip "$PAWABASE_URL/platform/v1/envs/production/blueprint.zip?data=true&max_rows=100" \
  -H "apikey: $PAWABASE_SECRET_KEY"
```

An export never contains a credential. Sign-in provider secrets, AI provider keys and secret values become `${VARIABLES}`, declared in `blueprint.yml`, so the file is safe to commit. Infrastructure settings, users, sessions and API keys stay out. With `data=true`, up to `max_rows` rows per table come along as sample data.

Export follows the plan's export lock, like other exports.

## From code: pawabase-iac

If you define your backend in Python with [pawabase-iac](/tools/iac/overview), `pawabase build` compiles it into a blueprint:

```bash
pawabase build -o store.blueprint.zip --name Store --environment shop
pawabase install store.blueprint.zip --environments shop
```

`env("NAME")` values become `${NAME}` variables, and `pawabase install` reads their values from your shell or `.env`. Parts the Python kinds don't model yet (AI, organization roles, channels, alarms, the status page, the mail kit, machines, keys, sample data) are added with `BlueprintPart`:

```python
from pawabase_iac import BlueprintPart, env

BlueprintPart("ai", {"providers": {"openai": {"kind": "openai", "key": env("OPENAI_API_KEY")}}})
BlueprintPart("data", {"products": [{"title": "Lamp", "price": 25}]})
```

Hand-written YAML in a `blueprint/` folder is copied into the zip and included as well.

## Limits and safety

| | |
|---|---|
| Zip size | 25 MB, and 80 MB once unpacked |
| Files | 1,000, each at most 8 MB, UTF-8 text |
| File types | `.yml` `.yaml` `.json` `.html` `.htm` `.txt` `.md` `.csv` `.css` `.sql` `.mjml` `.svg` `.xml` `.pem` |
| Includes | 12 levels deep; a file can't include itself |

A bundle can't escape itself: absolute paths, `..`, links and anything outside the allowed types are refused before anything is read. A zip made from a folder (`store/blueprint.yml`) is read as if the folder were the root. Files editors leave behind (`.DS_Store`, `__MACOSX/`) are skipped.

## Moving from the JSON blueprint

| JSON (deprecated) | Zip |
|---|---|
| `GET /envs/{env}/blueprint` | `GET /envs/{env}/blueprint.zip` |
| `POST /blueprints/apply` with `{"blueprint": {...}}` | `POST /blueprints/install` with the zip |
| Definitions, roles, some sign-in settings, sample data | Every part of the app, sign-in providers and emails included |
| No way to give credentials | `${VARIABLES}`, supplied at install |
| One document | A file per concern, `include:`, `!file`, `!csv` |

To move an app, export it as a zip from the environment it lives in, then install that zip wherever you need it.
