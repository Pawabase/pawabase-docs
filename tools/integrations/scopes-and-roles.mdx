What an integration may do is decided twice, on every request:

1. **Scopes**: what the token was granted. Fixed when the person approves (or when a personal token is made).
2. **Role**: what the person behind the token may do in the organization **right now**: viewer, member, admin or owner.

A request goes through only if **both** allow it. A token with `project:write` held by a viewer can't change anything; an owner whose token only has `projects:read` can't create a project with it.

## The five scopes

| Scope | Allows | Includes |
| --- | --- | --- |
| `organizations:read` | See the organization: its name, plan, status and how many projects it has | |
| `projects:read` | List projects, see one project with where its API answers and its environments, list marketplace apps | |
| `projects:write` | Create, rename, pause, restore and delete projects; deploy marketplace apps; make claim links (platform apps) | `projects:read` |
| `project:read` | Read everything inside a project through the Studio API: tables and records, access rules, flows, routes, sign-in settings and users, mail, files, secrets' names, keys, logs | |
| `project:write` | Change everything inside a project, as Studio can | `project:read` |

Note the difference between the plural and the singular:

- **`projects:*`** (plural) is about the organization's **list of projects**: which exist, making and removing them.
- **`project:*`** (singular) is about what is **inside** each project: its data and definitions.

An AI app builder that creates a project and then builds tables and flows in it needs `projects:write project:write`. A monitoring tool that reads logs from existing projects needs `projects:read project:read`. A dashboard that shows a project count needs `organizations:read`.

### Includes

A write scope includes its read scope: a token with `projects:write` passes every check for `projects:read`, and `project:write` passes every check for `project:read`. You don't need to ask for both; asking for both is harmless.

## Role needed to approve

On the consent screen, a person may only connect an organization where their role is at least the highest one the requested scopes need:

| Scope | Least role to approve |
| --- | --- |
| `organizations:read` | viewer |
| `projects:read` | viewer |
| `project:read` | member |
| `projects:write` | admin |
| `project:write` | admin |

So a request for `organizations:read projects:read` can be approved by anyone in the organization; a request that includes any write scope needs an admin or owner. The organization picker greys out organizations where the person's role is too low, and the screen says which role is needed.

This is a deliberate choice: connecting a product that can change or delete projects is a decision for the people who run the organization.

## Role needed on each request

Each endpoint also requires a least role, checked against the person's role at the moment of the request:

| Endpoint | Scope | Least role |
| --- | --- | --- |
| `GET /v1/token` | none | none |
| `GET /v1/organizations` | `organizations:read` | viewer |
| `GET /v1/organizations/{slug}` | `organizations:read` | viewer |
| `GET /v1/projects` | `projects:read` | viewer |
| `GET /v1/projects/{ref}` | `projects:read` | viewer |
| `GET /v1/marketplace` | `projects:read` | viewer |
| `GET /v1/marketplace/{app}` | `projects:read` | viewer |
| `POST /v1/projects` | `projects:write` | member |
| `PATCH /v1/projects/{ref}` | `projects:write` | admin |
| `DELETE /v1/projects/{ref}` | `projects:write` | admin |
| `POST /v1/projects/{ref}/pause` | `projects:write` | admin |
| `POST /v1/projects/{ref}/restore` | `projects:write` | admin |
| `POST /v1/projects/{ref}/apps` | `projects:write` | admin |
| `POST /v1/projects/{ref}/claim` | `projects:write` | admin, and a platform app's own token |
| `GET /v1/projects/{ref}/api-keys` | `project:read` | member |
| `POST /v1/projects/{ref}/api-keys` | `project:write` | admin |
| `GET /v1/projects/{ref}/studio/{path}` | `project:read` | member |
| `POST`, `PUT`, `PATCH`, `DELETE /v1/projects/{ref}/studio/{path}` | `project:write` | admin |

These match what the same person may do in the dashboard: members create projects and read inside them, admins manage projects and change what's inside them, viewers only look.

## Whose role

| Token | Role used |
| --- | --- |
| OAuth access token | The role of the person who approved the connection, read from the organization on every request |
| Personal access token | The role of the person who made it, read on every request |
| Platform app's `client_credentials` token | Always **admin** of the organization that registered the app. Never owner |
| A dashboard session (the dashboard's own sign-in token) | The signed-in person's role, with every scope |

"Read on every request" means changes take effect immediately:

- **Demoted** from admin to member: the product can still create projects (member) but can no longer change what's inside them (admin), even though its token says `project:write`.
- **Removed** from the organization: every request fails with `403 forbidden` "The person this token acts for is no longer a member of the organization."
- **Account disabled**: every request fails with `401 unauthorized`.
- **Promoted** to admin after approving a read-only connection: the token still has only read scopes. Scopes never grow on their own; the product must ask again.

## The person who approved

A connection belongs to the organization, but it acts as the person who last approved it. If Ada approves and later leaves the organization, the product stops working for that organization. Someone else with the right role goes through the consent flow again; that replaces Ada with them on the same connection.

The dashboard's **Connected apps** list shows who connected each product, so admins know whose access a connection depends on.

## Insufficient scope

A request without the scope it needs is answered:

```json
HTTP/1.1 403 Forbidden
{
  "error": "insufficient_scope",
  "message": "This token does not have the projects:write scope.",
  "details": {"needed": "projects:write"}
}
```

`details.needed` names the missing scope, so your product can ask for it: send the person through `/oauth/authorize` again with the larger list.

## Insufficient role

A request whose scope is fine but whose person's role is too low is answered `403` with `"error": "forbidden"` and a message saying which role is needed. Asking for more scopes won't help; the person needs a higher role, or someone with one has to connect instead.

## Choosing scopes

| Your product… | Ask for |
| --- | --- |
| shows which organization is connected and its plan | `organizations:read` |
| lists projects and opens their API addresses | `projects:read` |
| creates a project for the person and builds inside it (an AI builder, an IDE) | `projects:write project:write` |
| deploys marketplace apps | `projects:write` |
| reads logs, metrics or data from existing projects (monitoring, BI) | `projects:read project:read` |
| manages definitions in existing projects from Git (CI, infrastructure as code) | `projects:read project:write` |
| creates API keys for its own use against the project | `project:write` |

Ask for the fewest. Every scope is a line on the consent screen, and more lines mean more people hesitate. You can always ask for more later; see [Asking for more scopes later](/tools/integrations/oauth-flow#asking-for-more-scopes-later).

## What no scope allows

Some things can't be done through an integration at all, whatever its scopes and role:

- **Billing**: changing the plan, payment methods, invoices.
- **The team**: inviting people, changing roles, removing members.
- **The organization itself**: renaming or deleting it.
- **Integrations**: registering apps, making personal tokens, disconnecting apps.
- **Moving a project to another organization** (except a platform app's [claim links](/tools/integrations/platform-apps), which need the receiving person to act in the dashboard).
- Inside a project, the Studio API refuses everything that reaches **outside** the project: other projects' environments, promoting to another environment, previews, the runtime-wide audit log, and repointing an environment's database or storage (`infra`). See [Inside a project](/tools/integrations/project-api#what-is-refused).

Those stay in the dashboard, done by a person.
