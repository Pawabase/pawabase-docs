Going live is a change of trust boundary, not a larger version of local testing. The Brightfield definitions can move from development to production, but student data, application users, API keys, secrets, provider credentials, and operational history remain specific to each environment.

The release model is therefore:

```text
development definitions
        │
        ├── review and promote selected definitions
        ▼
production definitions

development data, users, keys, and secrets ── do not move with promotion
production data, users, keys, and secrets  ── provision and verify separately
```

<Info>
New Pawabase projects include `development` and `production`. A staging environment is optional.
If Brightfield needs a separate acceptance boundary, create staging and apply the same promotion
and verification model there before production.
</Info>

## Promotion moves definitions, not operational identity

Use the project environment control **Promote…** and review the selected source and target. Promotion is appropriate for versioned backend definitions, such as resources, schemas, transformers, policies, routes, flows, mail templates, event subscriptions, schedules, webhooks, inbound hooks, and storage bucket definitions.

| Moves as a definition | Remains target-specific |
| --- | --- |
| Resource fields and validation | Resource records |
| Schemas and transformers | Application users and sessions |
| Policies | Roles and user assignments |
| Routes and flows | API key values |
| Templates and subscriptions | Secrets |
| Schedules and webhooks | Provider credentials |
| Bucket definitions | Uploaded objects |
| Function definitions, when selected | Run, request, and delivery history |

Review enabled states and destinations after promotion. A webhook URL is part of a webhook definition, while the secret it references remains target-specific. Copying the definition without preparing the secret produces a configuration that looks present but cannot authenticate deliveries.

## The target needs its own resource tables

A promoted resource definition describes the table Pawabase expects; it does not guarantee that the target database has been migrated. Open each affected resource under **Build → Resources** and use **Create / migrate table** after reviewing the field changes.

| Definition change | Production concern |
| --- | --- |
| New optional field | Table needs the new column; older clients may omit it |
| New required field | Existing records may require a default or backfill |
| Changed validation | Existing data may no longer satisfy new writes |
| Renamed field | Clients and flows may still send the former name |
| New relation | Both resource definitions must exist before the relation is useful |
| Disabled operation | Deployed clients may receive a refusal where they previously succeeded |

Pawabase's additive migration path does not make destructive data changes on your behalf. Treat renames, type changes, and removals as data-migration projects rather than ordinary field edits. See [Data migrations](/data/migrations).

## Infrastructure belongs to the deployment boundary

In the current product, application database, object-storage, and mail infrastructure are configured by the installation operator rather than through an environment form in Studio.

For the production deployment, coordinate:

| Capability | Production expectation | Product-facing verification |
| --- | --- | --- |
| Application database | Durable storage, restricted credentials, backups | Create and read a synthetic record through the public API |
| Object storage | Durable bucket or S3-compatible service, restricted credentials | Upload and download a harmless test object through the storage API |
| Mail | Production SMTP identity and approved sender | Send a test message and inspect **Services → Mail** |
| Public gateway URL | HTTPS address reachable by browsers and providers | Call `/v1/status` and a keyed public endpoint |
| Studio URL | HTTPS and restricted operator access | Sign in as an intended operator |
| Queue and scheduled work | Healthy background processing | Run a flow and inspect **Operate → Jobs & queues** |
| Backups | Scheduled, protected, and restorable | Restore into an isolated installation and validate records |

Sensitive values belong in the deployment's protected configuration or in **Operate → Secrets** when a Pawabase definition supports a `secret://NAME` reference. Do not paste production credentials into a reusable definition or commit them with the portal.

## Production authentication is a policy decision

Brightfield should decide whether families self-register or whether the school provisions their accounts. A school that requires verified enrollment will normally disable open sign-up and create users through **Services → Users & auth**. Authentication settings, email verification, redirect URLs, and provider configuration must all be reviewed in the production environment.

| Setting area | Brightfield decision | Risk if omitted |
| --- | --- | --- |
| Sign-up | Disabled when accounts are school-provisioned | Unknown people create portal accounts |
| Email verification | Required when email ownership matters | Mistyped or unowned addresses become active |
| Password policy | Strong enough for school records | Weak reusable passwords increase account risk |
| Site URL | Production portal origin | Recovery and sign-in links point to development |
| Redirect URLs | Exact approved portal destinations | Authentication redirects fail or accept an unwanted destination |
| Default roles | Empty unless every new user should receive the same safe role | New accounts receive unintended permissions |
| Session and token lifetime | Suitable for shared and personal devices | Access remains valid longer than the school's risk model permits |

Create the application roles explicitly in production under **Users & auth → Roles**, then assign them to production users. Role definitions and user assignments are identity data; do not assume definition promotion created them.

<Warning>
Do not test production authentication with real student records until the role and policy matrix has
passed with synthetic users. A working sign-in proves identity, not authorization.
</Warning>

## The portal needs production credentials

Create a production publishable key under **Operate → API keys** and store it in the portal's deployment configuration. The portal must use the production gateway URL and that production key together.

```bash
VITE_PAWABASE_URL=https://api.school.example
VITE_PAWABASE_PUBLISHABLE_KEY=pk_production_value
VITE_SCHOOL_NAME=Brightfield Academy
VITE_CURRENCY=NGN
VITE_LOCALE=en-NG
```

Add the exact deployed portal origin under **Operate → Settings → CORS**. The origin includes scheme, host, and port. A publishable key in an allowed browser origin still does not authorize records; user sessions and resource policies provide that decision.

| Portal configuration error | Observable result |
| --- | --- |
| Development key with production URL | Key is not valid for the intended environment |
| Production key with development URL | Requests select the wrong boundary or fail |
| Missing CORS origin | Browser blocks the request before application code receives a useful response |
| Missing bearer token | Protected operations return an authentication failure |
| Secret key in the bundle | Client holds policy-bypassing server authority; rotate it immediately |

## External integrations need stable public addresses

Enable outbound webhooks only after their production destinations and signing secrets are ready. Open **Automate → Webhooks** to review the target URL, event selection, enabled state, and delivery behavior.

For payment-provider callbacks, open **Automate → Inbound hooks**, select the production hook, and use its displayed public URL and verification secret in the provider's production account. Test and live provider environments must not share callback secrets.

| Integration | Production review |
| --- | --- |
| Accounting webhook | HTTPS target, signing secret, retry behavior, receiver idempotency |
| SMS gateway | Approved sender, production credential, rate and cost controls |
| Payment inbound hook | Production URL, signature verification, replay handling |
| OAuth provider | Production callback URL and provider credential |
| Mail | Verified sender identity, template links, unsubscribe or support behavior as applicable |

A successful provider dashboard test is not sufficient. Confirm that the corresponding webhook delivery or inbound event appears in Pawabase and that the resulting flow run has the expected trace.

## Scheduled flows should start intentionally

The tutorial includes overdue invoice checks, overdue library-loan sweeps, and fee reminders. A schedule can begin producing work as soon as its promoted definition is enabled in the target.

Open **Automate → Schedules** and review each schedule against the production timezone and data-readiness decision.

| Scheduled behavior | Safe activation condition |
| --- | --- |
| `mark_overdue_invoices` | Production invoices and due dates are loaded and verified |
| `library_overdue_sweep` | Loans and borrower identities are ready |
| `fee_reminders` | Mail is configured, recipients are verified, and balances are reviewed |

Keep schedules disabled during initial data import if running them would send messages or change statuses. Enable them only after a dry run or manual flow run shows the correct target set.

## Security review follows the data path

The most useful production review traces one sensitive action from the portal to its durable and observable result.

| Boundary | Brightfield check |
| --- | --- |
| Browser | Only gateway URL and publishable key are present in the bundle |
| Authentication | The intended production user can sign in and refresh |
| Authorization | A guardian can read only linked students and published cards |
| Validation | Invalid grades, dates, and payment amounts are refused |
| Business operation | Admission and payment routes either complete correctly or report a usable error |
| Asynchronous work | Notification and billing flows produce traceable runs |
| External delivery | Webhook and mail signatures or credentials are accepted |
| Audit | Operator configuration changes have a visible audit record |
| Recovery | Production backups can be restored into an isolated installation |

Use a dedicated synthetic family for this review. Real family data is not needed to prove that the boundary works.

**Operate → Events & runs** is the run-level view for configured automation, while **Operate → Observability** is the request-level view. A slow or refused public request belongs in Observability; a failed notification or flow branch belongs in Events & runs; queued retries and dead-lettered work belong in Jobs & queues.

## Production acceptance matrix

| Scenario | Credential | Expected result | Evidence |
| --- | --- | --- | --- |
| Guardian reads linked student | Publishable key and guardian token | Record returned | Public response and Observability trace |
| Guardian reads unrelated student | Same credential | Record not disclosed | Refused or hidden result |
| Principal publishes reviewed card | Publishable key and principal token | Card becomes published once | Route response, resource record, flow event |
| Teacher attempts publication | Teacher token without permission | Refused | Policy result |
| Bursar records valid payment | Bursar token | Payment stored and invoice updated | Records and flow trace |
| Duplicate provider callback | Signed inbound request replay | No duplicate financial effect | Hook receipt and idempotent flow outcome |
| Fee schedule manual test | Operator test context with synthetic input | Expected recipient set only | Flow trace |
| Browser from unapproved origin | Publishable key | CORS refusal | Browser and gateway evidence |
| Revoked key | Revoked production key | Authentication failure | Key record and request trace |

A launch decision should be based on this matrix and the school's own critical scenarios, not on the Studio dashboard merely loading.

## Rollback and incident readiness

Promotion does not replace a recovery plan. Before launch, record the currently active definitions, back up the target environment and installation data, and identify how the team will disable schedules, webhooks, or affected keys during an incident.

| Incident | Immediate containment | Follow-up |
| --- | --- | --- |
| Portal key leaked | Revoke and replace the publishable key | Review scope, usage, and deployment exposure |
| Secret key leaked | Revoke immediately and assess policy-bypassing access | Rotate related credentials and review request history |
| Wrong webhook destination | Disable the webhook | Correct target and replay only verified deliveries |
| Reminder sent to wrong cohort | Disable the schedule or flow | Correct selection logic and review affected users |
| Policy exposes unrelated records | Disable the operation or apply a restrictive policy | Review logs and all similar policies |
| Bad definition promotion | Stop affected traffic and use the planned rollback path | Correct in development and repeat validation |
| Data corruption | Stop writes to the affected path | Restore or repair using the tested recovery procedure |

<Info>
Production readiness is complete only when public requests, policy refusals, flow runs, queued work,
mail delivery, webhook verification, backups, and restore behavior have been tested through the
same boundaries the school will actually use.
</Info>

## Continue operating after launch

The first production check is not the last. Review failed requests, job retries, mail delivery, webhook failures, privileged role membership, expiring credentials, backup results, and audit changes on a schedule appropriate to the school's risk.

Use [Security](/operate/security), [Backup and restore](/operate/backup-and-restore), and the [production checklist](/self-hosting/production-checklist) to turn the tutorial's acceptance matrix into an operating routine.
