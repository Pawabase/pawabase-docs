Brightfield Academy is a worked product tutorial, not a template that assumes every school operates the same way. It uses one project to connect the Pawabase capabilities that become difficult to reason about when they are taught separately: relational data, family access, staff permissions, transactional workflows, scheduled work, email, and a browser client.

The central mental model is that each concern has one authoritative home. Resource definitions describe durable school records. Policies decide who may act on those records. Flows coordinate work that crosses records or external systems. The portal calls the public API and renders the result; it does not become a second authorization layer.

<Info>
Build the tutorial in the project's `development` environment. New projects also include
`production`; leave it unchanged until the definitions and test data behave correctly in
development. Add a separate staging environment only if your release process needs one.
</Info>

## The finished system

| School concern | Pawabase capability | Studio location | Why it belongs there |
| --- | --- | --- | --- |
| Students, classes, grades, invoices | Resources and schemas | **Build → Resources**, **Build → Schemas** | They are durable, validated records |
| Links between students, guardians, and classes | Relations | Resource editor | Clients can request related records without inventing joins |
| Staff, guardian, and student access | Roles and policies | **Services → Users & auth → Roles**, **Build → Policies** | Identity and authorization remain separate |
| Admissions and payments | Custom routes backed by flows | **Build → Routes**, **Automate → Flows** | Each operation coordinates several checks and writes |
| Absence and payment notifications | Events, flows, and mail | **Automate → Flows**, **Services → Mail** | Notification failure does not redefine the stored record |
| Overdue sweeps | Scheduled flows | **Automate → Schedules**, **Automate → Flows** | Time-based work is visible and observable |
| Payment-provider callbacks | Inbound hooks | **Automate → Inbound hooks** | External events enter through a verified integration boundary |
| Family and staff portal | Public authentication and REST APIs | **Services → Users & auth**, **Build → API Explorer** | The client uses the same public boundary as any application |
| Operational review | Requests, runs, jobs, and audit records | **Operate → Observability**, **Operate → Events & runs**, **Operate → Jobs & queues** | Failures remain inspectable after a request ends |

## People and trust boundaries

The same person can have two distinct relationships with the system. A school employee who manages the Pawabase project is an operator in the platform organization. A teacher who signs in to the school portal is an application user in the selected project environment. Do not grant Studio access merely because someone needs a teacher account.

| Person | Application role | Typical portal access | Studio access |
| --- | --- | --- | --- |
| System administrator | `admin` | School-wide application actions | Only when responsible for the Pawabase project |
| Principal | `principal` | Reports, staff-readable records, publication | Usually none |
| Teacher | `teacher` | Registers, assessments, grades, incidents | None |
| Bursar | `bursar` | Invoices and payments | None |
| Librarian | `librarian` | Books and loans | None |
| Guardian | `guardian` | Linked children and family finance records | None |
| Student | `student` | Their results and loans | None |

Application roles are defined per environment under **Services → Users & auth → Roles**. A role is a convenient way to grant permissions to a cohort; the policies attached to operations remain the final authorization decision.

## Data domains

The backend is easier to understand as five connected domains rather than one list of tables.

| Domain | Representative resources | Boundary to preserve |
| --- | --- | --- |
| Academic structure | `academic_years`, `terms`, `classes`, `subjects`, `class_subjects`, `timetable_slots` | A teaching assignment belongs to a class, subject, teacher, and term |
| People | `teachers`, `guardians`, `students`, `student_guardians` | A guardian profile and an authenticated user are related but not interchangeable |
| Academic records | `attendance_records`, `assessments`, `grades`, `report_cards` | Draft calculations are not the same as published results |
| Finance | `fee_items`, `invoices`, `payments` | Payments are immutable facts; corrections are compensating records |
| Community | `announcements`, `calendar_events`, `library_books`, `library_loans`, `discipline_incidents` | Visibility differs by audience, role, and record ownership |

```text
academic structure
  classes ── class_subjects ── subjects
      │              │
      │              └── assessments ── grades
      ├── students ── report_cards
      ├── attendance_records
      └── invoices ── payments

people
  students ── student_guardians ── guardians
```

The diagram describes application concepts, not database ownership rules. Relations configured in Studio describe how public API expansions connect records. Validation and policies still apply to each requested operation.

## Decisions made deliberately

| Decision | Reason | Failure avoided |
| --- | --- | --- |
| Use a join resource for student guardians | The relationship carries `is_primary` and `can_pickup` | Losing relationship-specific data in an array |
| Also keep guardian user IDs on selected family-facing records | Policies need a direct record value for family access | Expensive or unavailable cross-resource authorization checks |
| Disable update and delete for payments | A received payment is an auditable fact | Quietly rewriting financial history |
| Keep report cards unpublished until review | Computation and release are different decisions | Families seeing partial or recalculated results |
| Put multi-record operations behind flows | The operation needs checks, branches, and several writes | A client completing only half a business action |
| Keep authorization in policies | Every client must receive the same decision | A hidden button being mistaken for security |
| Use target-specific keys and secrets | Environments are isolated trust boundaries | Test credentials or data reaching production |

## How Studio is used

The environment switcher must remain visible while you build. Every resource, role, key, user, secret, and run belongs to the selected environment. If a resource appears empty or a role seems to vanish, verify the environment before changing the definition.

The tutorial uses these Studio areas repeatedly:

| Area | Work performed there |
| --- | --- |
| **Build → Overview** | Check the selected backend and definition state |
| **Build → Resources** | Define fields, relations, operations, policies, and tables |
| **Build → Schemas** | Define reusable request and embedded object shapes |
| **Build → Policies** | Create reusable access rules |
| **Build → Routes** | Expose flow-backed business operations |
| **Build → API Explorer** | Exercise the public API with real credentials |
| **Automate → Flows** | Design and test backend processes |
| **Automate → Schedules** | Inspect time-based triggers |
| **Services → Users & auth** | Manage application users, roles, and authentication settings |
| **Services → Mail** | Manage templates and inspect delivery behavior |
| **Operate → API keys** | Create and revoke publishable or secret keys |
| **Operate → Secrets** | Store target-specific confidential values |
| **Operate → Observability** | Inspect public request outcomes and latency |
| **Operate → Events & runs** | Inspect flow and event execution |

## What the portal may assume

The portal receives a public gateway URL and a publishable key for exactly one environment. A signed-in user also supplies a bearer token. The key identifies the project environment; the token identifies the user; policies decide which records and operations are available.

The portal may use roles to organize navigation, but it must handle `401`, `403`, and `404` responses as authoritative. A staff-only menu is a usability feature. It is not an access-control mechanism.

<Warning>
Never place a secret key in the school portal. Secret keys are server-side credentials and bypass
resource policies. Browser and mobile clients use publishable keys, with user access enforced by
sessions and policies.
</Warning>

## Verification strategy

A realistic tutorial needs negative cases as well as successful ones. Test each important operation with a staff user, a family user who should have access, a family user who should not, and no user session.

| Boundary | Positive case | Negative case |
| --- | --- | --- |
| Student visibility | Guardian reads a linked child | Guardian cannot read another family |
| Report publication | Principal publishes a reviewed card | Teacher without permission is refused |
| Payment entry | Bursar records an amount within the balance | Overpayment is refused |
| Announcement visibility | Intended audience reads a published notice | Unpublished or wrong-audience notice is hidden |
| Library access | Student reads their loans | Student cannot read another borrower's loans |
| Environment isolation | Development key reads development data | Development token and production key do not combine |

The later chapters explain where each result comes from. If a test fails, fix the authoritative layer rather than adding a client-side exception.

<Tip>
Keep a small set of synthetic users for each role in development. Known identities make policy,
flow, and portal regression checks repeatable without copying real student data.
</Tip>
