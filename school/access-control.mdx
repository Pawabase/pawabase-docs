School access is not one hierarchy. Staff capabilities depend on job function, family access depends on a relationship to a student, and publication state controls when results become visible. Treating all three as a single role ladder either exposes too much or produces roles that are impossible to maintain.

Pawabase separates the problem into identity, permissions, and policies:

```text
signed-in application user
        │
        ├── roles and permissions describe broad capabilities
        │
        └── policy combines those claims with the operation and record
                         │
                         └── allow, deny, or filter the result
```

Roles make permissions manageable for cohorts. Policies remain the enforcement boundary.

## Application users are not Studio operators

Create school users in the selected environment under **Services → Users & auth**. Create application roles in its **Roles** tab. These accounts sign in to the school portal; they do not gain access to Studio or the platform organization.

| Identity | Used for | Managed in |
| --- | --- | --- |
| Platform operator | Configuring the Pawabase project | Organization **Team** |
| Application user | Signing in to the Brightfield portal | **Services → Users & auth** |
| Application role | Grouping portal permissions | **Users & auth → Roles** |
| Resource policy | Allowing an operation or record | **Build → Policies** and the resource operation |

A principal who needs to publish report cards usually needs the `principal` application role, not a Studio membership. Grant Studio access only to people responsible for changing or operating the backend itself.

## Roles deliver permissions

Brightfield uses roles to attach stable permissions to job functions. Roles are flat: one role does not inherit another. If a principal should also hold every teacher permission, include those permissions in the principal role or assign both roles.

| Role | Representative permissions | Intended use |
| --- | --- | --- |
| `admin` | `*` | A tightly controlled application administrator |
| `principal` | `students.read`, `grades.read`, `reports.publish`, `finance.read`, `discipline.manage` | School-wide academic oversight |
| `teacher` | `students.read`, `attendance.write`, `grades.write`, `assessments.write`, `discipline.report` | Classroom work |
| `bursar` | `students.read`, `finance.read`, `finance.write` | Billing and payment entry |
| `librarian` | `students.read`, `library.read`, `library.write` | Catalogue and loan management |
| `guardian` | `family.read` | Linked student and family records |
| `student` | `self.read` | The signed-in student's records |

Prefer narrowly named permissions over testing role names in every policy. A permission expresses the capability the operation requires. Roles then answer the administrative question of which cohorts receive that capability.

<Warning>
Avoid placing `*` in any default role. A wildcard permission gives every new account every
capability represented by a permission check. Reserve it for a small number of controlled
application administrators.
</Warning>

## Token timing affects role changes

Roles and permissions are carried in access tokens when those tokens are issued or refreshed. A role change therefore affects newly issued or refreshed tokens; an already issued access token can continue to carry its previous claims until it expires.

This matters during incident response and testing. When validating a role change, refresh or replace the test session rather than repeatedly using the old access token. For urgent removal, review the user's active sessions under **Services → Users & auth** as well as their role assignment.

## Reusable policies express the real boundary

Open **Build → Policies** to define rules once, then attach them to resource operations. The Brightfield policies combine three kinds of evidence:

| Evidence | Example | Appropriate use |
| --- | --- | --- |
| Authentication context | `$auth.user_id`, `$auth.roles` | Who is calling |
| Permission | `reports.publish` | What capability the caller holds |
| Record value | `$record.guardian_user_ids` | Whether this particular record belongs to the caller's family |

A staff-read policy can use roles directly:

```json
{
  "role": ["admin", "principal", "teacher", "bursar", "librarian"]
}
```

A policy for school administrators is narrower:

```json
{
  "role": ["admin", "principal"]
}
```

Family access combines staff visibility with a relationship stored on the record:

```json
{
  "any": [
    {
      "role": ["admin", "principal", "teacher", "bursar", "librarian"]
    },
    {
      "contains": ["$record.guardian_user_ids", "$auth.user_id"]
    }
  ]
}
```

Report-card access adds a publication boundary for families:

```json
{
  "any": [
    {
      "role": ["admin", "principal", "teacher"]
    },
    {
      "all": [
        {
          "eq": ["$record.published", true]
        },
        {
          "contains": ["$record.guardian_user_ids", "$auth.user_id"]
        }
      ]
    }
  ]
}
```

Publication itself should depend on a capability rather than a broad job title:

```json
{
  "all": [
    {
      "authenticated": true
    },
    {
      "permission": "reports.publish"
    }
  ]
}
```

These examples are tutorial definitions. Build them with the policy editor and inspect the stored expression before attaching them to operations. The dedicated [policy condition reference](/policies/conditions) defines the supported expression shapes.

## Attach policy decisions to operations

A resource does not have one universal access rule. Reading, creating, updating, and deleting can represent different business risks, so review each enabled operation in **Build → Resources → _resource_ → Operations**.

| Resource | List and get | Create | Update | Delete | Reason |
| --- | --- | --- | --- | --- | --- |
| `students` | `family_access` | `school_admin` | `school_admin` | `school_admin` | Families may read links, but office staff manage student records |
| `report_cards` | `report_access` | `teaching_staff` | `teaching_staff` | `school_admin` | Drafts remain staff-only; publication is separate |
| `invoices` | `family_access` | `finance_staff` | `finance_staff` | `school_admin` | Families see only their own debt |
| `payments` | `finance_staff` | `finance_staff` | Disabled | Disabled | Corrections create new records instead of rewriting history |
| `announcements` | `announcement_audience` | `teaching_staff` | `author_or_admin` | `author_or_admin` | Audience and author both matter |
| `library_loans` | `borrower_or_library` | `library_staff` | `library_staff` | `school_admin` | Borrowers read; library staff manage |

Disabling an operation is stronger and clearer than enabling it with a policy that nobody should satisfy. Use disabled operations for actions such as changing or deleting a payment when the public API should not support them at all.

## Family access needs a policy-friendly field

The normalized relationship between students and guardians lives in `student_guardians`, because the relationship has its own attributes. The `students.guardian_user_ids` field is a deliberate authorization projection: it stores the application user IDs that may see that student.

This duplication creates an obligation. Any flow that changes the guardian relationship must update the policy-facing array in the same business operation. If those two representations drift, the join resource may say one thing while the policy enforces another.

| Change | Required authorization update |
| --- | --- |
| Link a guardian | Add the guardian's user ID to affected family-facing records |
| Remove a guardian | Remove the user ID from those records |
| Replace a guardian's login | Update the stored application user ID |
| Create an invoice or report card | Copy the current guardian user IDs into the new record |

For a larger system, a stable `family_id` claim and record field can be easier to index and maintain than arrays of user IDs. Choose the representation that matches the product's real tenancy model; do not add a family concept only to make one tutorial expression shorter.

## Owner fields have a specific meaning

An owner field is appropriate when the authenticated caller creates a record on their own behalf and Pawabase should stamp their user ID. It is not appropriate for `guardians.user_id`, because office staff create guardian profiles and link them to another person's account.

<Warning>
If an office operator supplies another user's ID in a field that is configured as an owner field,
Pawabase can replace it with the caller's ID. Use an ordinary validated user-ID field for records
that staff create on someone else's behalf.
</Warning>

## Filtering is part of authorization behavior

For list operations, record-aware policies can filter the returned collection rather than exposing forbidden rows and expecting the client to hide them. A guardian listing `students` should receive only linked students. Requesting a specific unlinked student should not reveal whether that record exists.

Some expressions can be applied efficiently as query constraints; others require residual evaluation and may not return an exact total. This is an API behavior clients must tolerate, not a reason to weaken the policy. Read [Policy pushdown](/policies/pushdown) before relying on exact totals for a record-filtered family view.

## Verify the matrix through the public API

Use **Build → API Explorer** with representative application sessions. Verify allowed and refused behavior, because a successful staff request alone cannot prove family isolation.

| Caller and action | Expected result |
| --- | --- |
| Guardian lists students | Only linked students are returned |
| Guardian requests another family's student | The record is not disclosed |
| Guardian lists report cards | Only linked, published cards are returned |
| Teacher creates attendance | Allowed when the teacher policy permits it |
| Teacher publishes a report card without `reports.publish` | Refused |
| Bursar records a valid payment | Allowed |
| Teacher records a payment | Refused |
| Student lists library loans | Only that student's loans are returned |
| Anonymous caller reads family data | Refused |
| Secret-key server integration performs a resource action | Treat as privileged and verify its narrower key scope separately |

A secret key bypasses resource policies, so it is not a valid credential for proving that a family or staff policy works. Use a publishable key plus the application user's bearer token.

## Diagnose unexpected results

| Symptom | Likely cause | Check |
| --- | --- | --- |
| A new role seems ineffective | Existing access token carries old claims | Refresh the session and inspect the new token behavior |
| A guardian sees no children | User ID was not copied to the policy-facing field | Compare the guardian account ID with the record |
| A guardian sees too much | Broad staff or public branch in the read policy | Inspect every branch of the attached policy |
| A user holds a role but an action fails | The role lacks the permission tested by the policy | Open **Users & auth → Roles** |
| A list has no exact total | Policy requires record-by-record residual checks | Review [policy pushdown](/policies/pushdown) |
| Studio test succeeds but portal fails | Studio test used privileged run context or a different environment | Re-run with the portal's key and user session |
| A removed permission still works briefly | Old access token remains valid | Review token lifetime and active sessions |

<Tip>
Keep the role table, policy definitions, and an executable access matrix under the same change
review. Authorization failures often come from changing one of those three without updating the
others.
</Tip>
