The school's multi-record behavior lives in **flows**: visual graphs of blocks edited under **Automate → Flows** and exposed, when needed, through endpoints under **Build → Routes**. A resource operation remains appropriate for one validated record; a flow is appropriate when a business action needs several reads, writes, branches, or side effects.

| Use a resource operation | Use a flow-backed route |
| --- | --- |
| Read one student | Admit a student and link a guardian |
| Update one announcement | Record a payment and update an invoice |
| List books | Submit a whole attendance register |
| Create one library loan | Return a loan, assess status, and notify if needed |

## Admissions: one call, four writes, one event

`POST /rest/v1/admissions` (policy `school_admin`) is a [custom route](/data/custom-routes) handled by the `admit_student` flow:

```text
flowchart TB
  http([HTTP request]) --> today[time.now · date]
  today --> number["db.query: next admission number"]
  number --> find["resource.list guardians where email = body.guardian.email"]
  find --> known{control.if total}
  known -- true --> reuse[control.set guardian = existing]
  known -- false --> create[resource.create guardians] --> use[control.set guardian = new]
  reuse & use --> student[resource.create students]
  student --> link[resource.create student_guardians]
  link --> emit[event.emit student.admitted]
  emit --> reply([response.return 201])
```

The admission number is computed in portable SQL, with no code:

```sql
SELECT 'BFA-' || SUBSTR(?, 1, 4) || '-' ||
       SUBSTR('0000' || CAST(COUNT(*) + 1 AS TEXT), LENGTH(CAST(COUNT(*) + 1 AS TEXT)) + 1, 4) AS admission_no
FROM students WHERE admission_no LIKE 'BFA-' || SUBSTR(?, 1, 4) || '-%'
```

`student.admitted` then triggers two independent flows: `welcome_family` (email) and `issue_term_invoice`. The admission response doesn't wait for either.

## Billing from the fee schedule

`issue_term_invoice` has **two triggers**, so the same logic runs on admission (event) and on demand (`POST /finance/invoices/issue`). Each trigger normalises its input into `vars.student_id`, then:

| Billing concern | Flow behavior | Why it matters |
| --- | --- | --- |
| Student and term | Load both from the normalized trigger input | Every later query uses the same billing scope |
| Idempotency | Stop when an invoice already exists for the student and term | Retrying does not create duplicate debt |
| Fee selection | Query mandatory fees for the year and applicable grade level | The invoice reflects the student's class |
| Total and number | Sum line items and generate the invoice number in SQL | The stored total agrees with the stored breakdown |
| Family access | Create the invoice with its balance and copied guardian user IDs | Family policies can authorize the intended readers |

## Class registers with absence alerts

`POST /attendance/register` takes a whole class for a day (the `BulkAttendance` schema) and a `control.foreach` writes each mark. Separately, `absence_alert` is triggered by `trigger.resource` on `attendance_records` **created**:

```json
{ "block": "control.if", "config": { "condition": { "eq": ["$input.event.payload.record.status", "absent"] } } }
```

On `true` it queries the student's guardians and sends the `absence_alert` template to each. The register response does not need to wait for the independent notification work.

## Payments that can't go wrong

`POST /finance/payments` (`finance_staff`, `PaymentInput` schema) runs `record_payment`:

| Guard | Block | Response |
| --- | --- | --- |
| Invoice exists | `resource.get` → `missing` | `404 invoice_not_found` |
| Invoice not void or paid | `control.if` `in [void, paid]` | `409 invoice_closed` |
| Amount ≤ balance | `control.if` `gt [amount, balance]` | `422 overpayment` |

Then `math.calculate` computes the new paid total and balance, the payment is created, the status becomes `paid` or `partially_paid`, the invoice is updated and `invoice.payment_received` is emitted. The `payment_receipt` flow emails every guardian and publishes to the `finance` channel for the bursary's live dashboard.

## Serious incidents escalate themselves

`incident_escalation` watches `discipline_incidents` created. For `high` or `critical` severity it publishes to `staff-alerts`, emails the guardians, marks `guardian_notified = true` and logs a warning. Teachers file reports; the platform does the follow-through.

## Time-based work

| Flow | Trigger | Does |
| --- | --- | --- |
| `mark_overdue_invoices` | `trigger.schedule` `0 1 * * *` | Invoices past due with a balance → `overdue` |
| `library_overdue_sweep` | `0 7 * * *` | Overdue loans flagged, borrowers emailed |
| `fee_reminders` | `0 8 1 * *` + manual | Email every family with a balance |

The `trigger.schedule` node identifies the flow entry point and its timing. Use **Automate → Schedules** to inspect and enable or disable the registered schedule. Cron expressions run in UTC, so convert school-local calendar rules deliberately. [Schedules →](/jobs/schedules)

## Payment gateways

An [inbound hook](/webhooks/inbound) `payment-gateway` (HMAC-verified) triggers `payment_gateway`, which finds the invoice by number and **queues** `record_payment` with the charge, so gateway payments pass through exactly the same guards as the bursary's.

<Tip>
Open **Flows → a flow → Run** in Studio to execute it with test input and see each block's output. Every production run is recorded with its trace under **Events & runs**.
</Tip>

## Failure behavior is part of the design

| Failure point | Desired behavior | Evidence to inspect |
| --- | --- | --- |
| Admission number allocation | No partly linked student | Flow trace and affected resources |
| Duplicate invoice request | Return the existing outcome or stop without a second invoice | Invoice query and route response |
| Overpayment | Refuse before creating the payment | `422` response and flow trace |
| Email provider unavailable | Preserve the school record and expose delivery failure | **Events & runs** and **Services → Mail** |
| Payment callback repeated | Produce no duplicate financial effect | Inbound-hook receipt and flow trace |
| Schedule selects no records | Complete without sending messages | Schedule run output |

Run flow tests with realistic **Run as** authentication context. An empty privileged test context can make a policy-dependent block succeed even though the same portal user would be refused.
