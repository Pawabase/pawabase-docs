This quickstart builds the task app from the [JavaScript quickstart](/quickstarts/javascript) the React way, and covers what's specific to React: where the client lives, how components learn who is signed in, how to keep a list live without leaking subscriptions, and how to type your tables.

**Before you start**, do steps **1 and 2** of the [JavaScript quickstart](/quickstarts/javascript): create the `tasks` table with its owner field, **Broadcast changes** and the **Each user sees and changes their own records** access set-up, and copy the service URL, project id and a publishable key.

## 1. Create the app and the client

```bash
npm create vite@latest tasks -- --template react-ts
cd tasks
npm install
npm install @pawabase/client
```

Put the connection details in `.env.local` (Vite exposes variables that start with `VITE_` to the browser; a publishable key is meant to be public):

```bash .env.local
VITE_PAWABASE_URL=https://YOUR-SERVICE-URL
VITE_PAWABASE_PROJECT=YOUR-PROJECT-ID
VITE_PAWABASE_KEY=pb_pk_…
```

```typescript src/pawabase.ts
import { createClient } from "@pawabase/client";

export const pawabase = createClient({
  url: import.meta.env.VITE_PAWABASE_URL,
  project: import.meta.env.VITE_PAWABASE_PROJECT,
  apiKey: import.meta.env.VITE_PAWABASE_KEY,
});
```

Create the client **at module level, once**, not inside a component. A client owns the session, its refresh timer and the realtime connection; creating one per render would sign people out and open a socket per render. Every component imports this one.

## 2. Know who is signed in

```tsx src/useSession.ts
import { useEffect, useState } from "react";
import type { Session } from "@pawabase/client";
import { pawabase } from "./pawabase";

/** The current session (null when signed out), and whether the stored session has been checked yet. */
export function useSession() {
  const [session, setSession] = useState<Session | null>(null);
  const [ready, setReady] = useState(false);

  useEffect(() => {
    const { unsubscribe } = pawabase.auth.onAuthStateChange((_event, next) => {
      setSession(next);
      setReady(true);
    });
    return unsubscribe;
  }, []);

  return { session, user: session?.user ?? null, ready };
}
```

`onAuthStateChange` is called once with `INITIAL_SESSION` as soon as the client has read the stored session, then on every sign-in, sign-out and refresh, including ones made in other tabs. Wait for `ready` before deciding a person is signed out, or a signed-in person sees the sign-in form flash on every reload.

The effect returns `unsubscribe`, so React's development double-mounting (StrictMode) and unmounting leave no listeners behind.

## 3. Sign in, including two-step verification

```tsx src/SignIn.tsx
import { useState } from "react";
import { RateLimitError, ValidationError } from "@pawabase/client";
import { pawabase } from "./pawabase";

export function SignIn() {
  const [error, setError] = useState("");
  const [finish, setFinish] = useState<null | ((code: string) => Promise<unknown>)>(null);

  async function submit(event: React.FormEvent<HTMLFormElement>) {
    event.preventDefault();
    const form = new FormData(event.currentTarget);
    setError("");
    try {
      const result = await pawabase.auth.signInWithPassword({ email: String(form.get("email")), password: String(form.get("password")) });
      if (result.status === "mfa_required") setFinish(() => result.verify); // ask for the code next
    } catch (err) {
      if (err instanceof RateLimitError) setError("Too many attempts. Wait a minute and try again.");
      else if (err instanceof ValidationError || (err as { status?: number }).status === 400) setError("Wrong email or password.");
      else setError("Couldn't sign in. Try again.");
    }
  }

  async function verify(event: React.FormEvent<HTMLFormElement>) {
    event.preventDefault();
    const code = String(new FormData(event.currentTarget).get("code"));
    try {
      await finish!(code);
    } catch {
      setError("That code isn't right.");
    }
  }

  if (finish) {
    return (
      <form onSubmit={verify}>
        <input name="code" inputMode="numeric" autoComplete="one-time-code" placeholder="6-digit code" required />
        <button>Verify</button>
        {error && <p role="alert">{error}</p>}
      </form>
    );
  }
  return (
    <form onSubmit={submit}>
      <input name="email" type="email" autoComplete="email" required />
      <input name="password" type="password" autoComplete="current-password" required />
      <button>Sign in</button>
      {error && <p role="alert">{error}</p>}
    </form>
  );
}
```

`signInWithPassword` resolves to one of two results:

| `status` | Meaning | What to do |
| --- | --- | --- |
| `signed_in` | Done; the session is stored | Nothing: `useSession` updates by itself |
| `mfa_required` | The person has two-step verification | Ask for a code and call `result.verify(code)` |

A wrong email or password answers `400` ("invalid email or password"); too many failed attempts lock sign-in for a while and answer `429` (`RateLimitError`). A wrong two-step code is `400` and counts toward the lock-out. See [Email and password](/auth/email-and-password) and [Two-step verification](/auth/two-step-verification).

You never store the session yourself: the client keeps it (in `localStorage` by default), refreshes it before it expires, and tells `useSession`.

## 4. A live list hook

A **live query** sends a list's current result, then sends it again whenever a matching record changes. Because the table's access rule is applied to live results too, each person's list only ever contains their own tasks.

```tsx src/useLive.ts
import { useEffect, useState } from "react";
import { pawabase } from "./pawabase";

/** Rows of `table`, kept current. `query` is { sort, limit, filter … }; pass a stable value (useMemo) to avoid restarting it. */
export function useLive<T>(table: string, query: Record<string, unknown>) {
  const [rows, setRows] = useState<T[] | null>(null);

  useEffect(() => {
    const live = pawabase.realtime.live<T>(table, query, ({ data }) => setRows(data));
    return () => live.stop();
  }, [table, query]);

  return rows; // null until the first result
}
```

```tsx src/Tasks.tsx
import { useMemo } from "react";
import { pawabase } from "./pawabase";
import { useLive } from "./useLive";

type Task = { id: string; title: string; done: boolean; created_at: string };

export function Tasks() {
  const query = useMemo(() => ({ sort: "-created_at", limit: 100 }), []);
  const tasks = useLive<Task>("tasks", query);

  async function add(event: React.FormEvent<HTMLFormElement>) {
    event.preventDefault();
    const form = event.currentTarget;
    await pawabase.from("tasks").create({ title: String(new FormData(form).get("title")) });
    form.reset();
  }

  if (tasks === null) return <p>Loading…</p>;
  return (
    <>
      <form onSubmit={add}><input name="title" placeholder="New task" required /> <button>Add</button></form>
      <ul>
        {tasks.map((task) => (
          <li key={task.id}>
            <input type="checkbox" checked={task.done} onChange={(e) => pawabase.from("tasks").update(task.id, { done: e.target.checked })} />
            {task.title}
            <button onClick={() => pawabase.from("tasks").delete(task.id)}>Delete</button>
          </li>
        ))}
      </ul>
    </>
  );
}
```

There's no `setTasks` after creating, updating or deleting: the write changes the table, the live query sees the change and sends the new list. This keeps every open tab, and every device of the same person, in step without extra code.

Things to know about live queries:

- The table needs **Broadcast changes** on (its **Settings** tab).
- A connection can hold up to **25** live queries; `limit` can be 1–200.
- Changes are gathered briefly (about 0.1 s) before a new result is sent, so a burst of writes is one update, not fifty.
- `live.stop()` in the effect's cleanup stops the query when the component unmounts. Forgetting it leaks queries until the connection's limit is reached.

See [Record changes and live queries](/realtime/record-changes).

## 5. Put it together

```tsx src/App.tsx
import { pawabase } from "./pawabase";
import { useSession } from "./useSession";
import { SignIn } from "./SignIn";
import { Tasks } from "./Tasks";

export default function App() {
  const { user, ready } = useSession();

  if (!ready) return null;              // the stored session hasn't been read yet
  if (!user) return <SignIn />;
  return (
    <main>
      <p>Signed in as {user.email} <button onClick={() => pawabase.auth.signOut()}>Sign out</button></p>
      <Tasks key={user.id} />
    </main>
  );
}
```

`key={user.id}` remounts the list when a different person signs in on the same browser, so their live query starts fresh. `signOut()` ends the session on the server and removes it locally; `useSession` turns `user` into `null` and the sign-in form comes back.

This is the pattern for **protected views** in any router: wait for `ready`, then render the protected tree only when there is a user. The protection that matters is still on the server: a person who forces the protected view open sees nothing, because the API refuses them.

## 6. Type your tables

`pawabase-types` (installed with the client) generates TypeScript types from your environment, so `from("tasks")` knows its columns:

```bash
npx pawabase-types --url "$VITE_PAWABASE_URL" --env YOUR-ENVIRONMENT-FULL-NAME --api-key pb_sk_… --out src/pawabase.types.ts
```

`--env` takes the environment's **full name** (shown in **Overview → Connect** as *Environment*). Run it with a secret key on your machine or in CI, never in the browser.

```typescript src/pawabase.ts
import { createClient } from "@pawabase/client";
import type { Database } from "./pawabase.types";

export const pawabase = createClient<Database>({ /* … as before … */ });
// pawabase.from("tasks").create({ titel: "x" })  ← a type error: no such column
```

Add `--check` in CI to fail the build when the types are out of date. See [TypeScript types](/database/typescript-types).

## Server-side rendering

In Next.js, Remix and other frameworks that render on the server, don't share one module-level client between requests on the server: it would mix people's sessions. On the server, create a short-lived client per request with the person's access token:

```typescript
import { createClient } from "@pawabase/client";

export function serverClient(accessToken: string | null) {
  return createClient({
    url: process.env.PAWABASE_URL!,
    project: process.env.PAWABASE_PROJECT!,
    apiKey: process.env.PAWABASE_PUBLISHABLE_KEY!,
    accessToken: accessToken ?? undefined, // the person's token, from your cookie
  });
}
```

With `accessToken` the client keeps no session and doesn't refresh: it's for one request. The browser keeps using the module-level client. See [Node.js](/quickstarts/node) for acting as a person on a server.

## Common problems

| Symptom | Cause |
| --- | --- |
| The sign-in form flashes on every reload | Rendering before `ready` |
| A list shows another person's tasks after switching accounts | The list wasn't remounted (`key={user.id}`) or a cached result was reused |
| Live updates stop after navigating around | `live.stop()` missing from an effect cleanup, so the connection hit its live-query limit |
| `origin_not_allowed` (403) in production | Your site's address isn't in the environment's allowed web origins |
| Requests go to the wrong environment | `environment` isn't set and the project's default is another one |
