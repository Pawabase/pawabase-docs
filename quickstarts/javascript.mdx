In about fifteen minutes you'll have a working web app where people sign up, add tasks, tick them off and see changes live, and where **each person sees only their own tasks**, enforced by Pawabase, not by your code.

Along the way you'll touch the four ideas every Pawabase app uses: a **table**, an **access rule**, a **publishable key** and a **signed-in user**. If any of them is new, [How Pawabase works](/concepts/how-pawabase-fits-together) explains them in a few minutes.

**You need:** a Pawabase account and project ([dashboard.pawabase.com](https://dashboard.pawabase.com)), Node.js 18 or later, and a terminal.

## 1. Create the table

A table in Pawabase is both a database table and an API. You'll create one called `tasks` and decide who may use it.

1. Open your project's **Studio** and make sure the environment picker shows `development`.
2. Go to **Develop → Data** and click **Create table**.
3. Name it `tasks` and add three columns:

   | Column | Type | Notes |
   | --- | --- | --- |
   | `title` | Text (short) | Turn on **Required** |
   | `done` | Yes / no | Default `false` |
   | `owner_id` | Text (short) | Will hold the id of the person who created the task |

   Pawabase adds `id`, `created_at` and `updated_at` for you.
4. Save. The table now exists in the database and is served at `/rest/v1/tasks`, but nobody can use it yet: a new table exposes nothing until you say who may.
5. Open the table's **Settings** tab and set **Owner field** to `owner_id`. From now on, whenever a signed-in person creates a task, Pawabase writes their user id into `owner_id` itself; your app can't set or fake it.
6. Turn on **Broadcast changes** on the same tab, so changes can be pushed to the browser live (step 7).
7. Open the **Access** tab. Under **Quick set**, choose **Each user sees and changes their own records** and save.

That last choice sets one rule per operation:

| Operation | Rule | Meaning |
| --- | --- | --- |
| See the list, open one record, edit, delete | `owner` | Only records whose `owner_id` is the caller's user id |
| Add records | `authenticated` | Anyone signed in |

These rules run on the server for every request. Someone who opens the browser console and calls the API directly gets exactly the same answer your app does.

## 2. Get the connection details and a key

Open **Overview → Connect** in Studio. Note:

- the **Service URL** (`https://…`),
- the **Project ID** (`01JC4…`),

then click **Make a publishable key** and copy it (`pb_pk_…`).

A **publishable key** identifies your app. It is safe to put in a web page because it grants nothing by itself: what a visitor can do is decided by the access rules you just set. Never put a **secret key** (`pb_sk_…`) in a web page; it passes every rule. The client refuses to start with a secret key in a browser.

## 3. Create the app

```bash
npm create vite@latest tasks -- --template vanilla
cd tasks
npm install
npm install @pawabase/client
```

Create `src/pawabase.js` with one shared client:

```javascript src/pawabase.js
import { createClient } from "@pawabase/client";

export const pawabase = createClient({
  url: "https://YOUR-SERVICE-URL",   // Overview → Connect → Service URL
  project: "YOUR-PROJECT-ID",        // Overview → Connect → Project ID
  apiKey: "pb_pk_…",                 // the publishable key you made
});
```

Create the client **once** and import it everywhere. It holds the signed-in session, refreshes it before it expires, keeps it in `localStorage` so people stay signed in across reloads, and retries requests that fail for temporary reasons (rate limits, `502`–`504`, network errors).

Without an `environment` option, requests go to the project's default environment (`development` for a new project). To target another, add `environment: "production"`; see [Projects and environments](/concepts/projects-and-environments).

## 4. Sign up and sign in

Replace `index.html`'s body and `src/main.js`:

```html index.html
<body>
  <main>
    <section id="signed-out">
      <h1>Tasks</h1>
      <form id="auth">
        <input name="email" type="email" placeholder="Email" required />
        <input name="password" type="password" placeholder="Password (8+ characters)" required minlength="8" />
        <button name="action" value="sign-in">Sign in</button>
        <button name="action" value="sign-up">Create account</button>
      </form>
      <p id="auth-error" role="alert"></p>
    </section>
    <section id="signed-in" hidden>
      <p>Signed in as <b id="who"></b> <button id="sign-out">Sign out</button></p>
      <form id="add"><input name="title" placeholder="New task" required /> <button>Add</button></form>
      <ul id="list"></ul>
      <p id="task-error" role="alert"></p>
    </section>
  </main>
  <script type="module" src="/src/main.js"></script>
</body>
```

```javascript src/main.js
import { pawabase } from "./pawabase.js";

const $ = (id) => document.getElementById(id);

$("auth").addEventListener("submit", async (event) => {
  event.preventDefault();
  const form = new FormData(event.target);
  const credentials = { email: form.get("email"), password: form.get("password") };
  $("auth-error").textContent = "";
  try {
    if (event.submitter.value === "sign-up") {
      const { verificationRequired } = await pawabase.auth.signUp(credentials);
      if (verificationRequired) $("auth-error").textContent = "Check your email to confirm your address, then sign in.";
    } else {
      await pawabase.auth.signInWithPassword(credentials);
    }
  } catch (error) {
    $("auth-error").textContent = error.message;
  }
});

$("sign-out").addEventListener("click", () => pawabase.auth.signOut());

// One place decides what to show: whenever someone signs in or out (or a stored session is restored on load).
pawabase.auth.onAuthStateChange((_event, session) => {
  $("signed-out").hidden = !!session;
  $("signed-in").hidden = !session;
  if (session) {
    $("who").textContent = session.user.email;
    showTasks();
  }
});
```

What happens here:

- **`signUp`** creates an account in this environment. New environments sign people in straight away. If you turn on **Require a verified email** in **Security → Users & auth**, `signUp` returns `verificationRequired: true` instead and no session; the person clicks the link in their email, then signs in.
- **`signInWithPassword`** returns a session (an access token valid for a short time, and a refresh token). From now on every request the client makes carries the access token, so your access rules know who's asking.
- **`onAuthStateChange`** is called once straight away with the current session (`INITIAL_SESSION`, restored from storage after a reload), then on every sign-in, sign-out and refresh, including ones in other tabs, so the screen is always right.

Wrong credentials throw an error whose `message` you can show ("invalid email or password"). A person with two-step verification gets a challenge instead of a session; see [Two-step verification](/auth/two-step-verification).

## 5. Read and add tasks

Add to `src/main.js`:

```javascript src/main.js
async function showTasks() {
  const { data } = await pawabase.from("tasks").order("created_at", "desc");
  $("list").replaceChildren(...data.map(renderTask));
}

function renderTask(task) {
  const item = document.createElement("li");
  const box = Object.assign(document.createElement("input"), { type: "checkbox", checked: task.done });
  box.addEventListener("change", () => setDone(task, box.checked));
  const remove = Object.assign(document.createElement("button"), { textContent: "Delete" });
  remove.addEventListener("click", () => removeTask(task));
  item.append(box, ` ${task.title} `, remove);
  return item;
}

$("add").addEventListener("submit", async (event) => {
  event.preventDefault();
  const title = new FormData(event.target).get("title");
  await pawabase.from("tasks").create({ title });
  event.target.reset();
  showTasks();
});
```

- **`from("tasks")`** starts a query on the table. `order("created_at", "desc")` sorts newest first; awaiting it runs the request and returns a page: `{ data, page, per_page, total }`. You can chain filters such as `.eq("done", false)` or `.ilike("title", "%docs%")`, and paging with `.perPage(50).page(2)`. See [Read data](/database/read).
- **`create({ title })`** sends only the title. `done` takes its default, `id` and the timestamps are generated, and `owner_id` is filled with the signed-in person's id because you made it the owner field. The created record comes back with all of them.
- **No `where owner_id = …` anywhere.** The `owner` rule adds that condition on the server, inside the database query, so `total` and paging count only this person's tasks.

## 6. Change and delete

```javascript src/main.js
async function setDone(task, done) {
  await pawabase.from("tasks").update(task.id, { done });
}

async function removeTask(task) {
  await pawabase.from("tasks").delete(task.id);
  showTasks();
}
```

`update` sends only the fields you pass (a partial change) and returns the updated record. Both are checked against the `owner` rule: a request to change someone else's task is refused, even if the id is guessed.

Run the app:

```bash
npm run dev
```

Open the address Vite prints, create an account, and add a few tasks.

## 7. See the rule working

Open a private window, create a **second** account, and look at the list: it's empty. Both people use the same table, the same key and the same code; Pawabase returns each person only their own rows.

Try reading the first person's task from the second person's console:

```javascript
await pawabase.from("tasks").get("THE-FIRST-PERSONS-TASK-ID");
// → NotFoundError: the record doesn't exist for this caller
```

A record you may not see answers `404`, the same as one that doesn't exist, so ids can't be probed.

## 8. Live updates

You turned on **Broadcast changes** in step 1. A **live query** keeps a list current: Pawabase runs the query, sends the result, and sends it again whenever a matching record changes, still filtered by the access rule.

Replace `showTasks` with a live version:

```javascript src/main.js
let live;

function showTasks() {
  live?.stop();
  live = pawabase.realtime.live("tasks", { sort: "-created_at", limit: 100 }, ({ data }) => {
    $("list").replaceChildren(...data.map(renderTask));
  });
}
```

and remove the `showTasks()` calls after `create` and `delete`. Open the app in two windows signed in as the same person: ticking a task in one updates the other. The second person's window doesn't change, because the rule filters live results too. See [Live queries](/realtime/record-changes).

## 9. Handle errors properly

Every failed call throws an error from `@pawabase/client`. Check its class to decide what to tell the person:

```javascript src/main.js
import { AuthenticationError, PermissionError, ValidationError, RateLimitError, NetworkError } from "@pawabase/client";

async function safely(action) {
  $("task-error").textContent = "";
  try {
    return await action();
  } catch (error) {
    if (error instanceof ValidationError) $("task-error").textContent = "Check the task: " + error.message;
    else if (error instanceof AuthenticationError) $("task-error").textContent = "Your session ended. Sign in again.";
    else if (error instanceof PermissionError) $("task-error").textContent = "You can't do that.";
    else if (error instanceof RateLimitError) $("task-error").textContent = "Too many requests. Wait a moment.";
    else if (error instanceof NetworkError) $("task-error").textContent = "You're offline.";
    else throw error;
  }
}

// e.g. await safely(() => pawabase.from("tasks").create({ title }));
```

| Error | When | Status |
| --- | --- | --- |
| `ValidationError` | A field is wrong or missing: an empty `title`, an unknown field | `422` |
| `AuthenticationError` | Not signed in, or the session can't be refreshed | `401` |
| `PermissionError` | An access rule refused a signed-in person | `403` |
| `NotFoundError` | The record doesn't exist, or the rule hides it | `404` |
| `ConflictError` | A unique value already exists | `409` |
| `RateLimitError` | Too many requests for this key (retried for you first) | `429` |
| `NetworkError`, `TimeoutError` | No answer from the server (retried for you first) | — |

API errors carry `status`, the server's stable `code` (such as `rate_limit_exceeded`) and `requestId`, which you can search for in Studio's **Activity**. See [Errors](/reference/errors).

## What you built, and what Pawabase did

| Your code | Pawabase |
| --- | --- |
| A form that calls `signUp` and `signInWithPassword` | Stored the account, hashed the password, issued and refreshed tokens |
| `from("tasks").create(...)` | Validated the record, filled `owner_id`, `id` and timestamps, stored it, emitted `tasks.created` |
| `from("tasks").order(...)` | Applied the `owner` rule inside the SQL query, paged and counted |
| `realtime.live(...)` | Kept the query result current, filtered per person |

## Before you ship

- Make a separate **production** environment, promote the table to it ([Promote](/environments/promote)), and make a production publishable key that reaches only production.
- List your site's address under **allowed web origins** for publishable keys ([Environment settings](/environments/settings)).
- Decide whether new accounts must confirm their email.
- Read the [production checklist](/guides/production-checklist).
