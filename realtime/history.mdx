A channel can keep its recent messages. That lets a screen open with context (the last 50 chat messages) and lets a client that lost its connection catch up on what it missed.

## How much is kept

Every channel keeps a backlog unless its rule says otherwise:

| Rule field | Default | Meaning |
| --- | --- | --- |
| **History depth** | 50 | How many recent messages a client may read back, 0 to 1000. 0 keeps nothing |
| **Kind** | *Public* | *Durable* also writes every message to the database |
| **Retention (seconds)** | 7 days | For durable channels: how long messages are kept. 0 uses the platform's default |

Set them in **Realtime → Channels** on the rule that covers the channel. Under **Realtime → Settings**, each rule's **Messages kept for latecomers** is the same field as **History depth**.

| | Kept in | Survives a server restart | Limit |
| --- | --- | --- | --- |
| A normal channel | The server's memory | No | **History depth** messages per channel, within an overall memory budget |
| A **Durable** channel | The database, as well | Yes | **History depth** per read, kept for **Retention** |

Use durable channels for messages someone would be upset to lose in a restart, such as an order feed for staff. For most chat-like uses, memory is enough, because the real data lives in records (see [History is not storage](#history-is-not-storage)).

## Load recent messages

<CodeGroup>
```typescript TypeScript
const room = pawabase.realtime.channel("chat:lobby");
const recent = await room.history(50);                              // over the open connection, oldest first

const same = await pawabase.realtime.history("chat:lobby", 50);    // over HTTP, without a channel object
```

```python Python
recent = pb.realtime.history("chat:lobby", limit=50)     # over HTTP: works on the blocking client too

room = apb.realtime.channel("chat:lobby")
recent = await room.history(50)                          # over the connection
```
</CodeGroup>

- Messages come **oldest first**.
- You get at most the channel's **History depth**, however many you ask for.
- Reading history needs the same permission as subscribing: if the subscribe rule refuses someone, they can't read the backlog either.
- Each message has a `seq` that increases along the channel, for ordering and for remembering where you stopped.

The HTTP form suits a server rendering the first screen: send the last messages with the page, and connect in the browser afterwards.

## Merge history with live messages

A chat screen should **subscribe first**, so nothing sent while you load is missed, then load history, and skip any message it already has:

<CodeGroup>
```typescript TypeScript
const room = pawabase.realtime.channel<ChatMessage>("chat:lobby");
const seen = new Set<string>();
const messages: Array<{ id: string; payload: ChatMessage; sent_at: string }> = [];

function add(m: { id: string; payload: ChatMessage; sent_at: string }) {
  if (seen.has(m.id)) return;
  seen.add(m.id);
  messages.push(m);
  messages.sort((a, b) => a.sent_at.localeCompare(b.sent_at));
  render(messages);
}

room.onEvent("message", add);
await room.subscribe();
(await room.history(50)).forEach(add);
```

```python Python
seen: set[str] = set()
messages: list[dict] = []

def add(message):
    if message["id"] in seen:
        return
    seen.add(message["id"])
    messages.append(message)
    messages.sort(key=lambda m: m["sent_at"])

room = apb.realtime.channel("chat:lobby")
room.on("message", add)
await room.subscribe()
for message in await room.history(50):
    add(message)
```
</CodeGroup>

## Catch up after a disconnect

Connections drop, and the client reconnects by itself. Messages sent while it was away are lost unless you ask the channel to replay them:

<CodeGroup>
```typescript TypeScript
const room = pawabase.realtime.channel("chat:lobby", { replay: 100 });
```

```python Python
room = apb.realtime.channel("chat:lobby", replay=100)
```
</CodeGroup>

After each reconnect, the channel reads up to that many recent messages and delivers the ones it hadn't delivered, **once each**: it remembers the ids of the last 1000 messages it delivered. Without `replay`, only messages sent while connected arrive.

Replay is bounded by the channel's **History depth**. If someone was away for longer than that covers, reload the screen's data from your records. A simple signal: if the oldest replayed message is newer than the last one you had, something was missed in between.

```typescript
let lastSeq = 0;
room.on("message", (m) => {
  if (m.seq !== undefined && lastSeq && m.seq > lastSeq + 1) reloadFromRecords();
  if (m.seq !== undefined) lastSeq = Math.max(lastSeq, m.seq);
});
```

`seq` is present on messages read from history, which is what replay delivers.

## History is not storage

For anything people expect to find tomorrow (chat logs, orders, notifications), **save a record** and use the channel to announce it:

1. Write the message to a `messages` table.
2. Turn on **Broadcast changes** for the table, and listen to `resource:messages` or a [live query](/realtime/record-changes#live-queries).
3. Load the screen from the table.

A missed realtime message then costs nothing: the app reads the record. Access rules, search, export and backups all work on records, not on channel history.

Use channel history for what's fine to lose: typing indicators, "Ada is looking at this", progress updates, cursor positions.

## Durable channels

With **Kind** set to *Durable*, every message is also written to the database. History survives restarts, and messages are kept for the rule's **Retention**; a sweep removes older ones.

| Retention | Effect |
| --- | --- |
| A number of seconds | Messages older than that are purged |
| 0 | The platform's default, 7 days |

Durable channels cost a database write per message, so use them for low-volume channels that matter, not for high-frequency signals.

## See it in Studio

In **Realtime → Playground**, join a channel: the messages kept for latecomers appear when you join. **Realtime → Channels** shows each rule's history depth and kind; **Overview** shows how many messages were published and delivered.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `history()` returns nothing | **History depth** is 0, or nothing was sent since the server restarted | Raise the depth; use *Durable* if it must survive restarts |
| Fewer messages than asked for | Capped at **History depth** | Raise it, up to 1000 |
| `forbidden` reading history | The subscribe rule refuses the caller | Same rule as subscribing |
| History is empty after a deploy | Normal channels keep history in memory | Use *Durable*, or store records |
| Duplicates after a reconnect | Merging by something other than `id` | Merge by `id` |
