A channel is a name. Anyone subscribed to it receives what is sent to it. Names are free text; use a prefix and an id so rules can match groups of them: `chat:lobby`, `order:42`, `doc:abc123`.

## Subscribe and listen

<CodeGroup>
```typescript TypeScript
const room = pawabase.realtime.channel("chat:lobby");

const stop = room.onEvent("message", (m) => {
  console.log(m.from, m.payload, m.sent_at);
});

await room.subscribe();
// later
stop();                      // stop this listener
await room.unsubscribe();    // leave the channel
```

```python Python
room = pb.realtime.channel("chat:lobby")

room.on("message", lambda m: print(m["from"], m["payload"], m["sent_at"]))

await room.subscribe()
# later
await room.unsubscribe()
```
</CodeGroup>

Asking for the same channel name twice returns the same channel, so listeners from different parts of your app share one subscription. The first `subscribe()` opens the connection for you.

`subscribe()` fails if the channel's rules do not let you in. See [errors](#errors).

## What a message looks like

| Field | Meaning |
| --- | --- |
| `id` | A unique id. The SDK uses it to drop duplicates |
| `channel` | The channel name |
| `event` | The label it was sent with |
| `payload` | Whatever was sent: any JSON |
| `from` | The sender's user id, or `"server"` for a server publish |
| `sent_at` | Time it was accepted |
| `seq` | Order number, present on messages read from history |

## Send

<CodeGroup>
```typescript TypeScript
await room.send("message", { text: "hello" });
await room.send("typing", { on: true });
```

```python Python
await room.send("message", {"text": "hello"})
await room.send("typing", {"on": True})
```
</CodeGroup>

The call resolves with the message id once the server accepts it. You also receive your own messages, so render from the channel's messages rather than adding yours twice. If the channel's publish rule refuses you, `send` throws.

You can publish without subscribing through `pawabase.realtime.publish(channel, event, payload)` (`pb.realtime.publish(...)`), which also works on the synchronous Python client.

## Listen to everything, or to one event

<CodeGroup>
```typescript TypeScript
room.on("message", (m) => log(m.event, m.payload));   // every message
room.onEvent("typing", (m) => showTyping(m.from));     // only "typing"
room.on("subscribed", () => setStatus("live"));
room.on("closed", ({ reason }) => setStatus(reason));
room.on("error", (e) => report(e));
```

```python Python
room.on(None, lambda m: log(m["event"], m["payload"]))   # every message
room.on("typing", lambda m: show_typing(m["from"]))      # only "typing"
```
</CodeGroup>

TypeScript channel events are `message`, `presence`, `subscribed`, `closed` and `error`. `on` and `onEvent` return a function that removes the listener.

## Read messages as a loop

Both SDKs can iterate a channel's messages instead of using callbacks.

<CodeGroup>
```typescript TypeScript
for await (const message of room) {
  render(message);
}
```

```python Python
async for message in room:
    render(message)
```
</CodeGroup>

The loop ends when you unsubscribe.

## Type your payloads (TypeScript)

```typescript
type ChatMessage = { text: string };
type Member = { name: string };

const room = pawabase.realtime.channel<ChatMessage, Member>("chat:lobby");
room.onEvent("message", (m) => m.payload.text);   // string
```

## React

Subscribe when a component appears and leave when it goes away:

```typescript
useEffect(() => {
  const room = pawabase.realtime.channel(`order:${orderId}`);
  const stop = room.onEvent("status", (m) => setStatus(m.payload.status));
  room.subscribe();
  return () => { stop(); room.unsubscribe(); };
}, [orderId]);
```

## Errors

<CodeGroup>
```typescript TypeScript
import { RealtimeError } from "@pawabase/client";

try {
  await room.subscribe();
} catch (e) {
  if (e instanceof RealtimeError) console.log(e.code, e.message);
}
```

```python Python
from pawabase.errors import RealtimeError

try:
    await room.subscribe()
except RealtimeError as e:
    print(e)
```
</CodeGroup>

Typical causes: the channel's rule refuses you, you are not signed in and the rule needs a user, or the key is wrong.
