A **channel** is a name, such as `chat:lobby` or `order:42`. Everyone subscribed to it receives what is sent to it, within a few milliseconds. A [channel rule](/realtime/channel-rules) decides who may join and who may send. Without a rule for a channel, the environment's default applies: signed-in people may join and send.

<CodeGroup>
```typescript TypeScript
const room = pawabase.realtime.channel("chat:lobby");

room.onEvent("message", (m) => addToChat(m.from, m.payload));
await room.subscribe();

await room.send("message", { text: "hello" });
```

```python Python
from pawabase import AsyncPawabase

async with AsyncPawabase(url, key, environment=env) as pb:
    room = pb.realtime.channel("chat:lobby")
    room.on("message", lambda m: add_to_chat(m["from"], m["payload"]))
    await room.subscribe()

    await room.send("message", {"text": "hello"})
```
</CodeGroup>

Live channels in Python need the async client and `pip install "pawabase[realtime]"`. Sending without subscribing works on any client; see [Send without subscribing](#send-without-subscribing).

## Methods

| TypeScript | Python | Meaning |
| --- | --- | --- |
| `realtime.channel(name, { presence, replay })` | `realtime.channel(name, presence=, replay=)` | The channel object. Asking twice for one name returns the same object |
| `subscribe()` | `await subscribe()` | Start receiving. Opens the connection if needed |
| `unsubscribe()` | `await unsubscribe()` | Stop receiving; loops over the channel end |
| `on("message", h)` | `on(None, h)` | Every message |
| `onEvent(event, h)` | `on(event, h)` | Messages sent with one event name |
| `on("presence", h)` | `on_presence(h)` | People arriving and leaving. See [Presence](/realtime/presence) |
| `on("subscribed" \| "closed" \| "error", h)` | | The channel's own state (TypeScript) |
| `send(event, payload)` | `await send(event, payload)` | Publish over the connection |
| `track(meta)` | `await track(meta)` | Change your presence data |
| `history(limit)` | `await history(limit)` | Recent messages, oldest first. See [History](/realtime/history) |
| `presenceState()` | `presence_state()` | Who is here now |
| `subscribed` | `subscribed` | Whether it's joined right now |
| `for await (const m of channel)` | `async for m in channel` | Messages as a loop |

## Subscribe and listen

<CodeGroup>
```typescript TypeScript
const room = pawabase.realtime.channel("chat:lobby");

const offAll = room.on("message", (m) => log(m.event, m.payload));      // every message
const offTyping = room.onEvent("typing", (m) => showTyping(m.from));    // only "typing"

await room.subscribe();

// later
offTyping();                // remove one listener
await room.unsubscribe();   // leave the channel
```

```python Python
room = pb.realtime.channel("chat:lobby")
room.on(None, lambda m: log(m["event"], m["payload"]))      # every message
room.on("typing", lambda m: show_typing(m["from"]))         # only "typing"
await room.subscribe()

# later
await room.unsubscribe()
```
</CodeGroup>

- Asking for the same channel name again returns the **same** object, so different parts of your app share one subscription and its listeners.
- `subscribe()` is safe to call twice; the second call waits for the first.
- In Python, `on` is chainable: `room.on("a", f).on("b", g)`. A handler may be a coroutine function.
- A listener that throws doesn't stop the others or break delivery.

<Warning>
In Python, `on(event, handler)` matches the message's **event name**. `on("message", h)` hears only messages sent as `send("message", …)`. Use `on(None, h)` for everything, for example on `resource:` channels whose events are `created`, `updated` and `deleted`.
</Warning>

### When subscribing is refused

`subscribe()` rejects (raises) with a `RealtimeError` whose `code` says why:

| `code` | Meaning |
| --- | --- |
| `forbidden` | The channel's subscribe rule refuses this caller, or the name isn't allowed |
| `capacity` | The connection already holds 100 channels, or the channel's subscriber limit is reached |
| `ack_timeout` | No answer from the server within 10 seconds |

<CodeGroup>
```typescript TypeScript
import { RealtimeError } from "@pawabase/client";

try {
  await pawabase.realtime.channel(`org:${slug}`).subscribe();
} catch (error) {
  if (error instanceof RealtimeError && error.code === "forbidden") showJoinOrgPrompt();
  else throw error;
}
```

```python Python
from pawabase.errors import RealtimeError

try:
    await pb.realtime.channel(f"org:{slug}").subscribe()
except RealtimeError as error:
    if error.code == "forbidden":
        show_join_org_prompt()
    else:
        raise
```
</CodeGroup>

In TypeScript the channel also emits `error` with the same error.

## What a message holds

| Field | Meaning |
| --- | --- |
| `id` | Unique. Used to drop duplicates |
| `channel` | The channel's name |
| `event` | The event name it was sent with, `message` if none |
| `payload` | Whatever was sent: any JSON value |
| `from` | The sender's user id, `null` for an anonymous sender, or `"server"` for messages from your backend (a secret key, a flow) |
| `sent_at` | When the server accepted it, ISO 8601 |
| `seq` | Its order number, on messages read from history |

The `from` field is set by the server, so a client can't pretend to be someone else.

## Send

<CodeGroup>
```typescript TypeScript
const { id } = await room.send("message", { text: "hello" });
await room.send("typing", { on: true });
```

```python Python
answer = await room.send("message", {"text": "hello"})
answer["id"]
```
</CodeGroup>

`send` resolves with the message's id once the server has accepted it. It rejects with `RealtimeError`:

| `code` | Meaning |
| --- | --- |
| `forbidden` | The publish rule refuses you, or **Apps may publish** is off for the environment |
| `rate_limited` | More than about 20 messages a second from this connection (bursts up to 40), or the rule's own publish rate |
| `payload_too_large`, `message_too_large` | The payload is over 32 KB, or the whole message over 64 KB (or the rule's smaller size limit) |

You receive your **own** messages too. Render from what the channel delivers, rather than adding a message when you send it and again when it arrives, or match them by `id`.

Event names start with a letter or digit and use letters, digits, `:`, `_`, `.` and `-`, up to 100 characters.

### Send without subscribing

`publish` sends one message over a normal HTTP request. It works on servers, in edge functions and on the blocking Python client:

<CodeGroup>
```typescript TypeScript
await pawabase.realtime.publish("order:42", "status", { status: "shipped" });
```

```python Python
pb.realtime.publish("order:42", "status", {"status": "shipped"})
```
</CodeGroup>

The channel's publish rule applies. Flows can publish too, with the **Publish to channel** block (`realtime.publish`). See [Publishing](/realtime/publishing).

## Read as a loop

<CodeGroup>
```typescript TypeScript
const room = pawabase.realtime.channel("jobs:42");
await room.subscribe();
for await (const message of room) {
  render(message);
  if (message.event === "done") break;   // leaving the loop unsubscribes
}
```

```python Python
async for message in pb.realtime.channel("jobs:42"):
    render(message)
    if message["event"] == "done":
        break
```
</CodeGroup>

- The loop ends when you unsubscribe.
- In TypeScript, breaking out of the loop unsubscribes.
- Messages that arrive while your loop body is busy wait in a queue (up to the latest 1000), so a slow loop doesn't lose recent messages.
- In Python, iterating subscribes for you if needed.

## Catch up after a reconnect

When the connection drops and comes back, the channel rejoins by itself. Messages sent **while** you were away are lost unless you ask for them:

<CodeGroup>
```typescript TypeScript
const room = pawabase.realtime.channel("chat:lobby", { replay: 50 });
```

```python Python
room = pb.realtime.channel("chat:lobby", replay=50)
```
</CodeGroup>

With `replay`, after every reconnect the channel reads that many recent messages from history and delivers the ones it hasn't delivered yet, de-duplicated by id. The channel's rule must keep history (its **History depth** above 0).

For the **first** load, read history yourself before you subscribe; see [History](/realtime/history).

## Typed payloads (TypeScript)

```typescript
type ChatEvent = { text: string; replyTo?: string };
type Presence = { name: string; avatar: string };

const room = pawabase.realtime.channel<ChatEvent, Presence>("chat:lobby");
room.onEvent("message", (m) => m.payload.text);          // string
room.presenceState()[0]?.meta.name;                      // string
```

The first type is the payload, the second the presence data. The server doesn't check payload shapes, so validate messages from other people before trusting them.

## Naming channels

| Do | Don't |
| --- | --- |
| A prefix per kind of thing, then an id: `order:42`, `doc:abc`, `chat:room-1` | Put spaces or text people typed into names |
| Put the owner in the name when a rule needs it: `org:acme`, `user:7f3…` | Put secrets in names |
| Keep one prefix per rule | Use a different prefix per screen |

Names start with a letter or digit and use letters, digits and `: _ . @ = + -`, up to 200 characters. Anything else is refused with `forbidden`.

A rule pattern such as `user:{{ auth.user_id }}` makes a channel only its owner can open; see [Channel rules](/realtime/channel-rules).

## In React

```tsx
function useChannel<T>(name: string, event: string, onMessage: (payload: T) => void) {
  const handler = useRef(onMessage);
  handler.current = onMessage;

  useEffect(() => {
    const channel = pawabase.realtime.channel<T>(name, { replay: 20 });
    const off = channel.onEvent(event, (m) => handler.current(m.payload));
    channel.subscribe().catch((e) => console.warn("could not join", name, e));
    return () => { off(); channel.unsubscribe(); };
  }, [name, event]);
}

function OrderStatus({ orderId }: { orderId: string }) {
  const [status, setStatus] = useState("…");
  useChannel<{ status: string }>(`order:${orderId}`, "status", (p) => setStatus(p.status));
  return <Badge>{status}</Badge>;
}
```

Because the same channel object is shared, two components listening to `order:42` each add a listener, and unsubscribing in one would stop the other. If several components share a channel, keep the subscription in one parent or a context, and let children add listeners only.

## On a server

A Node process or a Python worker can hold a channel too, for example to react to messages or push progress:

<CodeGroup>
```typescript Node
import WebSocket from "ws";
import { createClient } from "@pawabase/client";

const pawabase = createClient({ url, apiKey: process.env.PAWABASE_SECRET_KEY!, environment, realtime: { webSocket: WebSocket as any } });
const jobs = pawabase.realtime.channel("jobs:incoming");
jobs.onEvent("start", async (m) => {
  const { jobId } = m.payload as { jobId: string };
  await run(jobId, (pct) => pawabase.realtime.publish(`jobs:${jobId}`, "progress", { pct }));
});
await jobs.subscribe();
```

```python Python
async with AsyncPawabase(url, os.environ["PAWABASE_SECRET_KEY"], environment=env) as pb:
    async for message in pb.realtime.channel("jobs:incoming"):
        if message["event"] == "start":
            asyncio.create_task(run(message["payload"]["jobId"]))
```
</CodeGroup>

A secret key passes every channel rule, so keep it on the server.

## Limits

| Limit | Value |
| --- | --- |
| Channels per connection | 100 |
| Payload size | 32 KB (whole message 64 KB), or the rule's smaller limit |
| Messages per second per connection | about 20, bursts up to 40 |
| Channel name | 200 characters |
| Event name | 100 characters |

See [Connection](/realtime/connection#limits) for the rest.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `forbidden` on subscribe | The subscribe rule refuses, or the name has a character that isn't allowed | Check the rule in **Realtime → Channels**, and the name |
| `forbidden` on send | The publish rule refuses, or **Apps may publish** is off | Check the rule and **Realtime → Settings** |
| Python handler never runs | `on("message", …)` while messages use other event names | `on(None, …)`, or the right event name |
| Messages arrive twice | You added your own message and received it | Render from the channel, or match by `id` |
| Missed messages after a drop | No `replay` | Set `replay`, and keep history on the rule |
| One component's cleanup stops another's messages | They share one channel object | Subscribe once higher up |
| `rate_limited` | Sending in a tight loop (typing indicators, cursors) | Throttle to a few per second |
