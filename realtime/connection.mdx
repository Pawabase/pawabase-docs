The first `subscribe()` (or live query) opens one WebSocket for the whole client. The client keeps it healthy: it sends heartbeats, reconnects after a drop, rejoins your channels and reopens your live queries. Most apps only need to show its status.

## Status

<CodeGroup>
```typescript TypeScript
pawabase.realtime.status;    // "idle" | "connecting" | "open" | "reconnecting" | "closed"

const stop = pawabase.realtime.onStatusChange((status) => {
  offlineBanner.hidden = status === "open";
});
// later: stop();

pawabase.realtime.connectionId;   // the server's id for this connection, once open
```

```python Python
room = pb.realtime.channel("chat:lobby")
await room.subscribe()

room.subscribed                   # True while joined
pb.realtime.connection_id         # the server's id for this connection
```
</CodeGroup>

| Status | Meaning |
| --- | --- |
| `idle` | Nothing has asked for a connection yet |
| `connecting` | Opening for the first time |
| `open` | Connected; channels are joined |
| `reconnecting` | It dropped, and the client is trying again |
| `closed` | Closed by you, or by the server for good (a wrong key, a refused token) |

Show a small "reconnecting…" hint when the status isn't `open`. Channels rejoin by themselves, so you don't need to subscribe again.

Each channel also tells you when it stops and starts receiving:

```typescript
room.on("subscribed", () => setLive(true));
room.on("closed", ({ reason }) => setLive(false));   // unsubscribed, or the connection dropped
```

## Open and close

<CodeGroup>
```typescript TypeScript
await pawabase.realtime.connect();       // optional: subscribe() does it for you
await pawabase.realtime.whenOpen(5000);  // wait until it's really open, connecting if needed
pawabase.realtime.disconnect();          // close, and stop reconnecting
```

```python Python
await pb.realtime.connect()              # optional: subscribe() does it for you
await pb.realtime.close()                # close, and end every channel's iteration
```
</CodeGroup>

`disconnect()` keeps your channels and their listeners: the next `connect()` (or `subscribe()`) rejoins them. Disconnect when you discard a client, on sign-out, and in tests, so timers stop. `pawabase.dispose()` disconnects for you; in Python, `async with AsyncPawabase(...)` closes it.

## What keeps it healthy

- **Heartbeats.** The client sends a ping every `heartbeatSeconds` (25). If nothing at all arrives for two intervals, the connection is treated as dead and replaced, which catches links that broke without closing (a laptop waking from sleep, a phone changing networks).
- **Reconnecting.** After a drop, the client waits a short random delay, growing from 0.5 s to at most 15 s between attempts, and tries again.
- **Rejoining.** On reconnect, every channel you subscribed to is joined again with its presence, and every live query is reopened. A channel with `replay` fetches messages it missed. See [Channels](/realtime/channels#catch-up-after-a-reconnect).
- **Deduplication.** Each channel remembers the ids of the last 1000 messages, so a message delivered twice (live and from replay) reaches your handlers once.

## Options (TypeScript)

```typescript
const pawabase = createClient({
  url, project, apiKey, environment,
  realtime: {
    heartbeatSeconds: 25,
    ackTimeoutMs: 10_000,
    connectTimeoutMs: 10_000,
    reconnect: { baseDelayMs: 500, maxDelayMs: 15_000, maxAttempts: 20 },
    onProtocolError: (detail) => console.warn("realtime:", detail),
  },
});
```

| Option | Default | Meaning |
| --- | --- | --- |
| `heartbeatSeconds` | 25 | Seconds between pings. Silent for two intervals: replaced |
| `ackTimeoutMs` | 10000 | How long `subscribe`, `send` and `track` wait for the server's answer before throwing `ack_timeout` |
| `connectTimeoutMs` | 10000 | How long to wait for the connection to open |
| `reconnect` | on, no attempt limit | `{ baseDelayMs, maxDelayMs, maxAttempts }`, or `false` to stay closed after a drop |
| `webSocket` | the global `WebSocket` | A WebSocket class. Browsers and Node 22+ have one; on Node 20 pass the `ws` package |
| `onProtocolError` | none | Called with frames the client didn't understand, and with errors the server reports outside a request |

`environment` from the client options is sent when connecting, and must match the key's environment.

### Node and other runtimes

```typescript
import WebSocket from "ws";

const pawabase = createClient({ url, project, apiKey, environment, realtime: { webSocket: WebSocket as any } });
```

Without any WebSocket class, the first `subscribe()` throws `ConfigError` "No WebSocket implementation found".

### Python

Live channels and live queries need the **async** client and the `websockets` package:

```bash
pip install "pawabase[realtime]"
```

```python
from pawabase import AsyncPawabase

async with AsyncPawabase(url, key, project=project, environment=env) as pb:
    room = pb.realtime.channel("chat:lobby")
    await room.subscribe()
```

On the blocking client, or without `websockets`, opening a connection raises `ConfigError`. Publishing, history, presence and one-way streams work over plain HTTP on **both** clients. Python reconnects with the same growing delay (0.5 s to 15 s) and never gives up unless the close code says retrying can't help.

## Signing in and out

The connection follows the person signed in on the client:

- It opens with the current access token, so channel rules see who they are.
- When the session **refreshes**, the client sends the new token on the open connection, with no reconnect.
- When the person **signs out**, the client tells the server, and the connection carries on as anonymous. Channels whose rule needs a signed-in person stop receiving.
- If the server refuses the token (close code `4003`), the TypeScript client refreshes the session once and reconnects; if that fails, the status becomes `closed`.

After someone signs in, subscribe to the channels that need them. Channels that anyone may join keep working throughout.

## Without a socket

### Publish over HTTP

`publish` sends one message over a normal request. It works anywhere, including servers, edge functions and the blocking Python client:

<CodeGroup>
```typescript TypeScript
const { id } = await pawabase.realtime.publish("order:42", "status", { status: "shipped" });
```

```python Python
pb.realtime.publish("order:42", "status", {"status": "shipped"})
```
</CodeGroup>

The channel's **publish** rule applies as for any sender. A client with a secret key always may publish, and its messages show `from: "server"`.

### Listen over Server-Sent Events

If you only listen (a dashboard, a server process, a network that blocks WebSockets), use a one-way stream over plain HTTP. There's no socket to manage, and it passes through strict proxies.

<CodeGroup>
```typescript TypeScript
const controller = new AbortController();
for await (const frame of pawabase.realtime.stream(["chat:lobby", "order:42"], { signal: controller.signal })) {
  if (frame.type === "message") show(frame.channel, frame.event, frame.payload);
}
// stop with controller.abort(), or break out of the loop
```

```python Python
# blocking client
for frame in pb.realtime.sse(["chat:lobby", "order:42"]):
    if frame["type"] == "message":
        show(frame["payload"])

# async client
async for frame in apb.realtime.sse("order:42"):
    ...
```
</CodeGroup>

- Frames are `welcome`, `message` and `presence_diff`.
- At most 20 channels per stream.
- The signed-in person, if any, is who is listening, so channel rules apply as on a socket.
- Streams don't reconnect by themselves: wrap the loop in your own retry with a delay.
- To send, use `publish`.

### Read presence and history over HTTP

<CodeGroup>
```typescript TypeScript
const members = await pawabase.realtime.presence("doc:abc");
const recent = await pawabase.realtime.history("chat:lobby", 50);   // oldest first
```

```python Python
members = pb.realtime.presence("doc:abc")
recent = pb.realtime.history("chat:lobby", limit=50)
```
</CodeGroup>

Useful on a server rendering a page: show who's online and the last messages before the browser connects.

## Limits

| Limit | Value |
| --- | --- |
| Channels per connection | 100 |
| Live queries per connection | 25 |
| Connections per signed-in person | 20 (anonymous connections count only toward the environment) |
| Message size | 64 KB per frame; a payload up to 32 KB |
| Presence data | 2 KB per member |
| History per request | up to 1000 messages |
| Messages per second per connection | 20, with bursts up to 40 |
| Channels per one-way stream | 20 |

Your plan can also limit realtime connections and messages per month; see [Plans and limits](/cloud/plans-and-limits). A connection that keeps breaking limits is closed.

## Close codes

When the server closes the connection, the code says why:

| Code | Meaning | What the client does |
| --- | --- | --- |
| `4001` | No API key, or a wrong one | Stays closed. Fix the key |
| `4003` | The access token was refused | TypeScript refreshes once and reconnects; then stays closed |
| `4008` | Too many broken limits on this connection | Reconnects; fix what's sending too much |
| `4429` | The server or the plan is at capacity | Reconnects with backoff |
| `1012` | The server is restarting | Reconnects |

Errors on single requests come back as `RealtimeError` with a `code`:

| `code` | Meaning |
| --- | --- |
| `forbidden` | A channel rule refused the subscribe, publish or presence |
| `rate_limited` | Too many messages per second |
| `message_too_large`, `payload_too_large` | Over the size limits |
| `bad_request`, `invalid_message`, `unknown_type` | A frame the server couldn't use |
| `capacity` | No room for another channel, query or connection |
| `ack_timeout` | No answer within `ackTimeoutMs` |
| `not_connected` | Called while the connection wasn't open, and it didn't open in time |
| `connect_timeout` | The connection didn't open within `connectTimeoutMs` |

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `ConfigError` "No WebSocket implementation found" | Node 20 without `ws` | Pass `realtime: { webSocket: WebSocket }` from `ws` |
| Python `ConfigError` on `subscribe` | The blocking client, or no `websockets` | Use `AsyncPawabase` and `pip install "pawabase[realtime]"` |
| Status stays `closed` | Code `4001` (key) or `4003` (token) | Check the key and the environment; sign in again |
| Constant reconnecting behind a proxy | The proxy closes idle WebSockets | Lower `heartbeatSeconds`, or use the one-way stream |
| `ack_timeout` | A slow or broken network | Retry; check status first with `whenOpen()` |
| `capacity` on subscribe | 100 channels on one connection | Unsubscribe from channels you no longer show |
| Messages stop after sign-out | The channel rule needs a signed-in person | Expected; subscribe again after sign-in |
