## Overview

A resource with **realtime** turned on publishes every create, update and delete to the channel `resource:<name>`. A client that subscribes to that channel is told about each change **to a row it is allowed to read**, and about nothing else.

<CardGroup cols={2}>
  <Card title="Per-row authorization" icon="shield">Each change is checked against the resource's read policy for each subscriber before it is sent.</Card>
  <Card title="Same shape as the API" icon="brackets-curly">Records are shaped as `/rest/v1` returns them: write-only and undeclared fields are never sent.</Card>
</CardGroup>

## Turning it on

Set `realtime` on the resource definition (Studio: the resource's **Realtime** switch):

```json
{
  "name": "notes",
  "realtime": true,
  "owner_field": "owner_id",
  "fields": [{ "name": "text", "type": "string", "required": true }],
  "operations": {
    "list": { "enabled": true, "policy": "owner" },
    "get":  { "enabled": true, "policy": "owner" },
    "create": { "enabled": true, "policy": "authenticated" }
  }
}
```

Every change made through the API, a flow or a function publishes. A change made in the [Database console](/data/database-console) does not.

## Subscribing

```json
{ "type": "subscribe", "channel": "resource:notes", "ref": "1" }
```

Anyone may subscribe to `resource:<name>` while the resource can be read at all (its `get` or `list` operation is enabled). Subscribing does not, by itself, let anyone see anything: what arrives is decided per row, below. When neither `get` nor `list` is enabled, only service connections may subscribe.

Clients cannot publish on `resource:*` channels. Only the platform does.

## Who receives which change

For every change and every subscriber, Pawabase checks the resource's read policy (the `get` operation's, or `list`'s when `get` is off) with that subscriber's identity:

1. **Against the row in the change.** `owner` passes only for the row's owner; a `$record` condition is evaluated on that row.
2. **Against the row as it is now** (for creates and updates). A row that has since been handed to someone else, or deleted, is not sent to someone who could read it a moment ago.

Only a subscriber for whom both pass receives the message. With the `notes` definition above, Ada receives the changes to her notes and Bob to his; neither is told the other's notes exist.

The record in the message is shaped like an API response: fields marked **write-only** (a PIN, a secret) and columns the resource does not declare are removed, at every level of nesting. The row is read from the database once per change, not once per subscriber.

## The message

```json
{
  "type": "message",
  "id": "5f0c…",
  "channel": "resource:notes",
  "event": "created",
  "payload": {
    "resource": "notes",
    "change": "created",
    "record": { "id": "01J…", "text": "Buy milk", "owner_id": "1", "created_at": "…", "updated_at": "…" }
  },
  "from": "server",
  "sent_at": "2026-10-15T12:00:00+00:00",
  "seq": 42
}
```

| `event` / `change` | When |
| --- | --- |
| `created` | A record was created |
| `updated` | A record was updated; `record` is the new state |
| `deleted` | A record was deleted; `record` is the state before deletion |

## Catching up after a reconnect

Subscribe with `since` (the last `seq` you saw) to receive the changes you missed, up to the channel's history limit:

```json
{ "type": "subscribe", "channel": "resource:notes", "since": 42 }
```

History is filtered exactly like live delivery, with the subscriber's identity at the time of the request: a change to a row you can no longer read is not replayed. A request for history without an identity returns nothing for a resource channel.

## Integration with flows and events

Realtime messages are for connected clients. To run work when a record changes, use the resource's **events** (`notes.created`, …) with a flow, function or webhook; see [Resource events](/data/resource-events). Event payloads use the same public record shape.
