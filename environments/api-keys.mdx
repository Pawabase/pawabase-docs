Your apps and servers prove who they are with an **API key**. A key belongs to the **project**: it reaches every environment of it, or only the ones you choose.

| Key | Looks like | Use it in |
| --- | --- | --- |
| **Publishable** | `pb_pk_…` | Browsers and mobile apps. Safe to ship. It can only do what your [access rules](/policies/overview) allow the public or a signed-in user to do. |
| **Secret** | `pb_sk_…` | Your servers only. It can manage the environments it reaches, so never put it in a browser, app or repository. |

A client sends the key with the project's ID and, optionally, the environment by its name in the project:

```ts
const pawabase = createClient({
  url: "https://api.example.com",
  project: "01JC4…",          // Studio → Overview → Connect
  environment: "production",  // optional: left out, the project's default environment
  apiKey: "pb_pk_…",
});
```

The **default environment** answers requests that name none. Change it under **Settings → Environment → Default environment**; each project has its own.

## Create a key

1. **Settings → API keys → New API key.**
2. Choose a **Name** (what it's for, such as *Web app* or *Nightly job*) and the **Key type**.
3. Under **Environments**, choose **All environments** (today's and any you add later) or **Only some**, and tick them. A production server's key is usually limited to `production`.
4. Under **Permissions**, choose what it may do. **Start from** a preset, then adjust. Areas that manage an environment need a secret key.
5. Optionally set **Limits**:

| Limit | Effect |
| --- | --- |
| **Expires** | The key stops working on that date. |
| **Allowed IP ranges** | Every other address is refused. Comma-separated IPs or CIDR ranges such as `203.0.113.0/24`. |
| **Allowed routes** | Anything outside these is refused at the gateway, whichever route it uses. Examples: `GET /rest/v1/*`, `POST /flows/v1/*`. |

6. **Create.** The key is shown **once**. Copy it now and store it as a secret in your host.

## Rotate a key without downtime

Rotate when someone who knew a key leaves, or on a schedule.

1. Open the key and choose **Rotate key**.
2. Choose **Keep the old key working** for how long, so your apps have time to switch.
3. Copy the replacement (it reaches the same environments, with the same permissions and limits).
4. Deploy it, and the old key expires when you said.

## Revoke a key

**Revoke key** stops anything using it **at once**. This cannot be undone. Make a new one if you need it.

## See what a key does

Each key shows when it was last used and how many times. Every request carries the key's name in [Activity](/activity/overview), so you can find which key did what.

## Good practice

- One key per app or job, so you can revoke one without breaking the rest.
- Give each the least it needs: only the environments it works in, and only the permissions it uses. A job that reads one table shouldn't hold a key that can manage the project.
- Keys made before keys belonged to projects keep working: each reaches only the environment it was made for. Make a new key when you want one that reaches more.
- Use **Allowed IP ranges** for servers with fixed addresses.
- Keep secret keys in your host's secret store, never in code.
- Use [machine identities](/auth/machines) for services that call your API as themselves.
