An **environment** is a complete, separate copy of your backend: its own database, users, files, rules, keys and secrets. You build in `development`, check in `staging`, and serve real people from `production`. Nothing you do in one affects another.

## Where

The environment picker is in the top bar; **Project → Environments** lists them all. Each environment has its own sidebar of everything in these docs.

## Create one

1. **Project → Environments → New environment.**
2. **Name:** lowercase letters, digits and dashes.
3. Optionally **copy from** another environment to start with its definitions (tables, rules, flows). *Definitions are copied; never secrets, keys or data.*
4. Create.

## What is separate

| Per environment | Shared across the project |
| --- | --- |
| Database and every row | The project itself and its team |
| Users, roles, organizations | Your plan and billing |
| Tables, rules, flows, routes, subscriptions, webhooks | |
| Buckets and files | |
| Secrets and API keys | |
| Auth settings, mail settings, domains | |

Your app chooses the environment with its keys and the `environment` option:

```typescript
const pawabase = createClient({ url, apiKey: process.env.PAWABASE_KEY!, environment: "production" });
```

## API versions

**Project → API versions** lists the versions of your live API (`v1` is always live at `/rest/v1`). **Release a version** serves another environment's definitions as `v2`, `v3` and so on next to `v1`, over the same data. **Promote to…** copies this environment's definitions to another.

Versions share the environment's tables, so a version can add tables, columns and indexes but can't rename, retype or remove anything a live version uses.

## Promote: copy definitions forward

**Promote** copies definitions from one environment to another so `production` matches what you tested. It never copies data, secrets or keys.

1. In the environment you built, choose **Promote** in the environment menu.
2. Choose the **target** environment.
3. Choose which kinds to include (tables, access rules, flows, routes…).
4. Review the differences, then confirm.

Promoting copies the **definition**. A new column still needs its [migration](/database/migrations-and-history) applied in the target (Studio shows it as pending); named [rules](/policies/named-rules#across-environments) must be included, or the tables that use them won't resolve.

### A release routine

1. Change and test in `development`.
2. Take a [backup](/backups/overview) of `production`.
3. Promote to `staging`; apply migrations; run your rule tests ([Testing](/policies/testing)).
4. Promote to `production`; apply migrations.
5. Watch [Activity](/activity/overview) for errors.

## Previews

A **preview** is a temporary environment for a branch or pull request. It copies definitions, has its own data, and **expires by itself** (72 hours by default). Create one from **Project → Environments → New preview**, name it after the branch (lowercase letters, digits, dashes), point your preview deployment at it, run your tests, and let it expire.

## Good practice

- Keep `production` locked down: few people open Studio there; changes arrive through promote.
- Use different keys per environment; never reuse a production secret in development.
- Don't copy production data into development without anonymising it.
- Name environments for their purpose, not for a person.
