An **environment** is a complete, separate copy of your backend: its own database, users, files, rules, keys and secrets. You build in `development`, check in `staging`, and serve real people from `production`. Nothing you do in one affects another.

## In Studio

The environment picker is in the top bar. **Project → Environments** lists them, with **New environment**. Each environment has its own sidebar of everything in this documentation.

**New environment:** a **name** (lowercase letters, digits, dashes) and, optionally, **copy from** another environment to start with its definitions (tables, rules, flows). *Definitions are copied, never secrets, keys, or data.*

## In code

<CodeGroup>
```typescript TypeScript
const envs = await m.environments.list();

await m.environments.create("staging", { copyFrom: "development" });

const one = await m.environments.getOne("staging");

await m.environments.update("staging", { auth: { signup_enabled: false }, settings: {} });  // merged in
await m.environments.deleteEnvironment("staging");
```

```python Python
envs = pb.manage.environments.list()
pb.manage.environments.create("staging", copy_from="development")
pb.manage.environments.update("staging", auth={"signup_enabled": False})
```
</CodeGroup>

`update` merges what you send into the environment's infrastructure (`infra`), sign-in settings (`auth`) and general `settings`. Sign-in settings are covered in [Configuring Auth](/auth/configuring-auth).

## What is separate

| Per environment | Shared across the project |
| --- | --- |
| Database and every row | The project itself and its team |
| Users, roles, organizations | Your plan and billing |
| Tables, rules, flows, routes, subscriptions, webhooks | |
| Buckets and files | |
| Secrets, API keys | |
| Auth settings, mail settings, domains | |

Your app picks the environment with the `environment` option and the matching keys:

```typescript
const pawabase = createClient({ url, apiKey: process.env.PAWABASE_KEY!, environment: "production" });
```

## Promote: copy definitions forward

**Promote** copies definitions from one environment to another so `production` matches what you tested. It never copies data, secrets or keys.

**Studio:** **Promote** in the environment menu: choose the target, then which kinds to include (tables, policies, flows…), review the differences, and confirm.

<CodeGroup>
```typescript TypeScript
await m.environments.promote("production", { include: ["resources", "policies", "flows", "routes"] });
```

```python Python
pb.manage.environments.promote("production", include=["resources", "policies", "flows", "routes"])
```
</CodeGroup>

Promoting copies the **definition**. A new column still needs its [migration](/database/migrations-and-history) applied in the target; named rules must be included or the rules that use them won't resolve ([Named rules](/policies/named-rules#across-environments)).

### A release routine

1. Change and test in `development`.
2. Take a [backup](/backups/overview) of `production`.
3. Promote definitions to `staging`; apply migrations; run your rule tests ([Testing](/policies/testing)).
4. Promote to `production`; apply migrations.
5. Watch [Activity](/activity/overview) for errors.

## Previews: short-lived copies

A **preview** is a temporary environment for a branch or pull request. It copies definitions, has its own data, and **expires by itself**.

```typescript
const preview = await m.environments.createPreview("pr-142", { expiresInHours: 72, auth: { signup_enabled: true } });
await m.environments.deletePreview(preview.name);
```

The `ref` is lowercase letters, digits and dashes. Point your preview deployment at it, run your tests, and let it expire.

## Blueprints: a project as a file

A **blueprint** exports an environment's definitions and roles as a document you can apply to a new project:

```typescript
const blueprint = await m.environments.blueprint();
await otherProject.environments.applyBlueprint(blueprint, ["development", "production"]);
```

Use it to template a product you create per customer, or to move between projects. Secrets and keys are never included.

## Good practice

- Keep `production` locked down: few people can open Studio there; changes arrive through promote.
- Use different keys per environment, and never reuse a production secret in development.
- Don't copy production data into development without anonymising it.
- Name environments for their purpose, not for a person.
