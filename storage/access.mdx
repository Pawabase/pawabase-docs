A bucket has a rule for each action. You set them in Studio when you [create the bucket](/storage/buckets), or later in its [settings](/storage/bucket-settings). This page explains how they behave and how to design keys so one short rule protects a whole bucket. The rule language itself is in [Access rules](/policies/overview).

## The five rules

| Action | Studio setting | If unset |
| --- | --- | --- |
| Read a file | **Who may read** | Signed-in people. With **Public bucket** on: everyone, whatever this says |
| Upload to a key that doesn't exist | **Who may upload new objects** | Signed-in people |
| List the bucket | **Who may list objects** | The same as reading |
| Upload to a key that exists | **Who may replace objects** | The same as uploading |
| Delete a file | **Who may delete objects** | The same as uploading |

Two of these surprise people:

- **Uploading and replacing are different rules.** An upload to a new key asks **Who may upload new objects**; an upload to an existing key asks **Who may replace objects**. Use that to let people add files without overwriting anyone's, including their own.
- **Listing follows reading when unset.** A **public** bucket with no list rule can therefore be **listed by anyone**, which reveals every key. Set **Who may list objects** on every public bucket. See [Public, but not browsable](#public-but-not-browsable).

Each setting is a [rule picker](/policies/rule-references): a built-in rule (*Anyone (public)*, *Signed-in users*, *Signed in with 2FA*, *Secret keys & Studio*, *Nobody*), *Users with role…* or *Users with permission…*, a named rule, or a custom condition. Storage rules must be conditions; rules written in Python code can't be used on buckets.

## What a rule can see

| Value | Meaning |
| --- | --- |
| `$object.key` | The file's key, such as `7f3…/2026/contract.pdf`. When listing, the **prefix** being listed |
| `$object.segments` | The key split on `/`: `["7f3…", "2026", "contract.pdf"]`. `$object.segments.0` is the first part |
| `$object.action` | `read`, `stat`, `list`, `write`, `update` or `delete` |
| `$auth.user_id`, `$auth.email`, `$auth.roles`, `$auth.permissions`, `$auth.aal`, `$auth.org`, `$auth.org_role`, `$auth.org_permissions`, `$auth.org_teams` | Who is asking. See [Context](/policies/context) |
| `$credential` | The key used: publishable or secret, its scopes |
| `$env` | The environment's name |

There is no record lookup in a storage rule: it decides from the key and the caller. That's why the key's layout matters.

## Design keys around rules

### Each person's own files

Put the person's id first, `<user id>/…`, and one rule protects every action:

> **Custom condition:** `$object.segments.0` **equals** `$auth.user_id`

Use it for **Who may read**, **upload new objects**, **list**, **replace** and **delete**. Then:

<CodeGroup>
```typescript TypeScript
const me = (await pawabase.auth.getCachedUser())!;
const bucket = pawabase.storage.from("documents");

await bucket.upload(`${me.id}/report.pdf`, file);          // allowed
await bucket.upload(`someone-else/report.pdf`, file);      // PermissionError (403)
await bucket.list({ prefix: `${me.id}/` });                 // allowed
await bucket.list();                                        // PermissionError: the root isn't theirs
```

```python Python
me = pb.auth.user
bucket = pb.storage.from_("documents")

bucket.upload(f"{me['id']}/report.pdf", data)       # allowed
bucket.upload("someone-else/report.pdf", data)      # ForbiddenError
bucket.list(prefix=f"{me['id']}/")                  # allowed
```
</CodeGroup>

Because listing checks the prefix, people can list only inside their own folder. Always pass `prefix` with their id.

### A team's or an organization's files

Put the organization first, `<org slug>/…`, and compare it with the session's organization:

> **Custom condition:** `$object.segments.0` **equals** `$auth.org`

The session must be [scoped to the organization](/auth/organizations): `switchOrg(slug)` in your app. For "members may read, only admins may delete", give **Who may delete objects** an extra condition on `$auth.org_role`, or choose *Users with permission…* and a permission such as `files.delete`.

### Shared read, private write

An avatar bucket where everyone sees pictures but people change only their own:

| Setting | Rule |
| --- | --- |
| **Public bucket** | On |
| **Who may list objects** | *Nobody* (or *Signed-in users*) |
| **Who may upload new objects** | `$object.segments.0` equals `$auth.user_id` |
| **Who may replace objects** | the same |
| **Who may delete objects** | the same |

### Write once

Receipts, signed documents, audit exports: people may add files but never change or remove them.

| Setting | Rule |
| --- | --- |
| **Who may upload new objects** | Signed-in users, with the owner-first condition |
| **Who may replace objects** | *Nobody* |
| **Who may delete objects** | *Nobody* |

A typo'd upload then stays forever, so name files with a fresh id each time.

### Only your server writes

For files your backend makes (generated PDFs, exports): set every write rule to *Secret keys & Studio*. Your server uses a **secret** key, and people read through signed links or a read rule.

## Public, but not browsable

**Public bucket** lets anyone with a file's address read it, which is what you want for images on a website. It doesn't have to let them find every file:

1. Set **Who may list objects** to *Signed-in users*, a role, or *Nobody*.
2. Use random keys (`crypto.randomUUID()`), not guessable ones like `1.png`.

Strangers can then open only files whose address they were given.

## What bypasses the rules

| Access | Bucket rules apply? |
| --- | --- |
| A client with a **publishable** key, signed in or not | Yes |
| A client with a **secret** key | No: secret keys pass every rule. Type and size checks still apply |
| Studio's file browser | No: Studio acts with its own authority |
| A [flow](/logic/flows) writing with the **Store file** block | No: flows write as the platform. Check the caller in the flow |
| A **signed link** | The link was checked when it was made: the maker had to be allowed. Using it needs nothing more |
| A **share link** | No: it grants that one file to anyone holding it until it ends |

So a bucket only your server writes to can still be filled from Studio, and a person you remove from a project keeps any share link you gave them until you revoke it.

## What a refusal looks like

| Answer | TypeScript | Python | Meaning |
| --- | --- | --- | --- |
| `401` | `AuthenticationError` | `AuthenticationError` | The rule needs a signed-in person, and there was none (or the session expired) |
| `403` | `PermissionError` | `ForbiddenError` | Signed in, but the rule refuses this action or key |
| `403` `quota_exceeded` | `PermissionError` | `QuotaExceededError` | The plan's storage is full |
| `404` | `NotFoundError` | `NotFoundError` | No file at this key |
| `400` | `ApiError` (status 400) | `ValidationError` | A type not in **Accepted types**, a file over **Largest file**, or a key that isn't allowed |
| `413` | `PayloadTooLargeError` | `PawabaseError` (413) | Over the environment's upload limit |

A refusal names the action ("the bucket's policy refused this replacement"), so you can tell an upload refusal from a replace refusal.

## Test your rules

Sign in as an ordinary person and try what must fail as well as what must work:

<CodeGroup>
```typescript TypeScript
import { PermissionError } from "@pawabase/client";

await pawabase.auth.signInWithPassword({ email: "tester@example.com", password });
const bucket = pawabase.storage.from("documents");

await bucket.upload(`${me.id}/ok.txt`, "x");                // must work
try {
  await bucket.upload("someone-else/x.txt", "x");
  throw new Error("expected a refusal");
} catch (error) {
  if (!(error instanceof PermissionError)) throw error;     // refused, as it should be
}
```

```python Python
import pytest
from pawabase.errors import ForbiddenError

def test_people_cannot_write_into_other_folders(pb_as_tester):
    bucket = pb_as_tester.storage.from_("documents")
    bucket.upload(f"{pb_as_tester.auth.user['id']}/ok.txt", "x")
    with pytest.raises(ForbiddenError):
        bucket.upload("someone-else/x.txt", "x")
```
</CodeGroup>

If a call fails and you think it shouldn't, find it in Studio under **Activity → Requests** with the error's `requestId` / `request_id`, and see [Debugging rules](/policies/debugging).

## Advanced

### Rules and file records together

When files belong to records (a task's attachments), a storage rule can't look at the task to decide. Two ways to keep them in step:

1. **Put the deciding value in the key**: `<project id>/<task id>/<file>`, and a rule on `$object.segments.0` that the caller belongs to that project (through their organization or teams).
2. **Keep the bucket private** (writes and reads by your server only) and hand out signed links from a [route](/logic/routes) that checks the record first.

The second is stricter: a link is only made after your own check.

### Changing rules later

Rule changes apply to new requests within seconds. They don't move or delete files. Before tightening a rule, list who could reach which files under the old rule, and move files whose keys don't fit the new layout.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `403` uploading to your own folder | The key doesn't start with your id, or the session is for another user | Build the key from `auth.getCachedUser().id` |
| `403` replacing your own file | **Who may replace objects** differs from upload | Set it to the same rule |
| `403` on `list()` | Listing the root with an owner-first rule | Pass `prefix: \`${id}/\`` |
| Anyone can list a public bucket | **Who may list objects** unset | Set it |
| `401` reading a file in `<img>` | The read rule needs a signed-in person, and images send no token | Public bucket, or a signed link |
| A team member can't read team files | The session isn't scoped to the organization | `switchOrg(slug)` |
