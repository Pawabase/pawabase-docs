A bucket has a rule for each action. When a call is refused, one of these decided it:

| Action | Rule |
| --- | --- |
| Read a file | `read` |
| Upload a new file | `write` |
| List the bucket | `list` (follows read if not set) |
| Replace an existing file | `update` (follows write) |
| Delete a file | `delete` (follows write) |

You set the rules in the dashboard under **Storage** when you create the bucket. Typical setups:

| Bucket | Rules |
| --- | --- |
| Public avatars | Anyone reads; signed-in users write |
| Private documents | Signed-in users read and write their own folder |
| Exports | Users read; only your server writes |

## Design keys around the rules

Rules can look at the file's key. If every file starts with the owner's id (`<user id>/…`), one rule says "people can only touch files under their own id". So:

```typescript
await bucket.upload(`${user.id}/report.pdf`, file);     // allowed
await bucket.upload(`someone-else/report.pdf`, file);   // refused
```

The same works for organizations: start keys with the organization's slug and let a rule compare it with the person's active organization.

## What a refusal looks like

| You get | Meaning |
| --- | --- |
| `AuthenticationError` | The rule needs a signed-in user and there was none |
| `PermissionError` (`ForbiddenError` in Python) | You are signed in but the rule refuses this action |
| `NotFoundError` | No such file, or the rule hides it |
| `PayloadTooLargeError` | Over the bucket's size limit |
| `ValidationError` | Wrong file type for the bucket |

The rule runs before the file is looked up, so a refusal never reveals whether a key exists.

## Check a rule

Try something that should fail, signed in as an ordinary user:

```typescript
await pawabase.auth.signInWithPassword({ email, password });
await pawabase.storage.from("documents").upload("someone-else/x.txt", "x");   // expect PermissionError
```

If a call fails and you think it should not, repeat it with a secret key on a server. If that works, the rule is the cause.
