Every storage call is checked against one of a bucket's rules before anything is read or written. You set the rules when you [create the bucket](/storage/buckets); this page is how to write them.

| Rule | Checked when | If unset |
| --- | --- | --- |
| `read_policy` | Reading a file | `authenticated` (anyone signed in). A `public` bucket is readable by anyone |
| `write_policy` | Uploading a **new** key | `authenticated` |
| `list_policy` | Listing | Same as `read_policy` |
| `update_policy` | Replacing an existing key | Same as `write_policy` |
| `delete_policy` | Deleting | Same as `write_policy` |

A refusal is `AuthenticationError` when the caller was not signed in and `PermissionError` (`ForbiddenError` in Python) when they were. The rule runs before the file is looked up, so a refusal tells the caller nothing about whether a key exists.

## Short names

| Name | Who it allows |
| --- | --- |
| `"public"` | Everyone, signed in or not |
| `"authenticated"` | Any signed-in user |
| `{ "role": "admin" }` | Users with that role (a list allows any of them) |
| `{ "service": true }` | Servers using a secret key, and flows. Never a browser user |

## Rules about the file's key

Rules can look at the file being touched, as `$object`, and the caller, as `$auth`. The key is split on `/` into `$object.segments`, so if you put the owner first, a rule is one comparison.

```json
{
  "write_policy": {
    "all": [
      { "truthy": "$auth.user_id" },
      { "eq": ["$object.segments.0", "$auth.user_id"] }
    ]
  }
}
```

With keys like `<user id>/avatar.png`, this lets a signed-in user write only under their own id. `$object` has `key`, `segments` and `action` (`read`, `list`, `write`, `update`, `delete`).

Combine conditions with `all` (and), `any` (or) and `not`; compare with `eq`, `ne`, `in`, `not_in`; test with `truthy` and `exists`. The wrong names (`and`, `or`, `neq`) are rejected when you save. The full language is in [Policies](/policies/overview).

## Recipes

<Tabs>
  <Tab title="Each user owns a folder">
    ```typescript
    const owner = { all: [{ truthy: "$auth.user_id" }, { eq: ["$object.segments.0", "$auth.user_id"] }] };
    await m.buckets.create({ name: "documents", read_policy: owner, write_policy: owner });
    ```
    Keys are `<user id>/<file>`. Each user reads and writes only their own.
  </Tab>
  <Tab title="Each organisation owns a folder">
    ```typescript
    const org = { all: [{ truthy: "$auth.org" }, { eq: ["$object.segments.0", "$auth.org"] }] };
    await m.buckets.create({ name: "team-files", read_policy: org, write_policy: org });
    ```
    Keys are `<org id>/<file>`. Members of one organisation cannot see another's.
  </Tab>
  <Tab title="Public images, staff upload">
    ```typescript
    await m.buckets.create({ name: "products", public: true, write_policy: { role: ["staff", "admin"] } });
    ```
  </Tab>
  <Tab title="Public files, private listing">
    ```typescript
    await m.buckets.create({ name: "assets", public: true, list_policy: "authenticated" });
    ```
    Anyone can show a file they have the URL of. Only signed-in users can browse.
  </Tab>
</Tabs>

## Test a rule

Use a client signed in as a normal user, and try something that must fail:

<CodeGroup>
```typescript TypeScript
await pawabase.auth.signInWithPassword({ email: "ada@example.com", password });
await pawabase.storage.from("documents").upload("someone-else/file.txt", "x"); // expect PermissionError
```

```python Python
pb.auth.sign_in_with_password(email="ada@example.com", password=password)
pb.storage.from_("documents").upload("someone-else/file.txt", "x")  # expect ForbiddenError
```
</CodeGroup>

If a call fails and you think it should not, repeat it with a secret key. If it then works, the rule is the cause. The dashboard's request log shows which rule refused a request.

<Note>
Operators using the dashboard act with their own authority, not through these rules. A bucket only your server may write to can still be filled by an operator.
</Note>
