---
title: "Image transformations"
description: "Resize, crop, rotate and convert images at delivery with query parameters, without touching the stored original."
icon: "image"
---

Add query parameters to an image's URL and the gateway renders a variant. The stored object is never changed.

```html
<img src="https://api.example.com/storage/v1/files/production/avatars/7/me.png?width=400&height=400&fit=cover&format=webp">
```

Transformations work on every way of reading an object: the gateway URL, the API route and [share links](/storage/share-links).

## Parameters

| Parameter | Alias | Values | Meaning |
| --- | --- | --- | --- |
| `width` | `w` | pixels | Output width |
| `height` | `h` | pixels | Output height |
| `fit` | | `contain`, `cover`, `fill` | `contain` fits inside the box keeping the ratio and never enlarges; `cover` fills the box and crops the overflow; `fill` stretches |
| `format` | `f` | `webp`, `avif`, `jpeg`, `png`, `auto` | Output format. `auto` picks AVIF or WebP when the request's `Accept` allows it |
| `quality` | `q` | 1–100 | Lossy quality (bucket default 80) |
| `rotate` | | −360–360 | Degrees, clockwise |
| `crop` | | `x,y,width,height` | Crop the original first, in source pixels |

With only one of `width`/`height`, the other follows the aspect ratio. EXIF orientation is applied. Animated sources use their first frame. With none of these, the original is served as stored.

Only raster images (PNG, JPEG, WebP, GIF, AVIF, BMP) are transformed; anything else answers `415`. SVG is never rasterised or served inline.

## Configure it per bucket

In Studio, a bucket's settings have an **Image transformations** section; over the API it is the `transforms` object:

```json
{
  "transforms": {
    "enabled": true,
    "formats": ["webp", "jpeg"],
    "fits": ["contain", "cover"],
    "auto_format": true,
    "max_width": 2048,
    "max_height": 2048,
    "max_input_pixels": 50000000,
    "max_source_bytes": 26214400,
    "max_output_bytes": 10485760,
    "quality": 80,
    "max_concurrent": 4,
    "timeout_seconds": 10
  }
}
```

Every number has a platform ceiling (for example 8192 px and 32 MB) that a bucket can lower but not raise. A request outside the bucket's limits is a `400`, an oversized source or output is a `413`, and a source that cannot be decoded is a `422`.

## Resource limits

* Input pixel count is checked before decoding, so a decompression bomb is refused cheaply.
* The source is read up to `max_source_bytes`; larger originals are not transformed.
* At most `max_concurrent` renders run per bucket per process; others wait up to `timeout_seconds` and then get `503`.
* Rendering runs in a worker thread with a time limit.

## Caching and security

Variants are cached in memory, per process, up to 64 MB, keyed by environment, bucket, key, the object's `ETag` and the exact options. Replacing an object produces a new `ETag`, so an old variant is never served, and it is also purged.

The read policy is evaluated **before** the cache is consulted, on every request. A variant is never served to a caller who could not read the original. Responses carry their own `ETag`, and `Vary: Accept` when `format=auto` is used, so a CDN in front stores the right variant per format.
