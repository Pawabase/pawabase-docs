Every object has one stable URL on your application's gateway. Put it in an `<img>`, a `<video>`, a link or an API response. It does not change if you move the environment to a different storage provider.

```
https://<your-gateway>/storage/v1/files/<environment>/<bucket>/<key>
```

Every upload returns it as `url`, and so does every listing:

```json
{
  "bucket": "avatars",
  "key": "7/me.png",
  "size": 8421,
  "content_type": "image/png",
  "etag": "9b2c…",
  "url": "https://api.example.com/storage/v1/files/production/avatars/7/me.png"
}
```

## Two ways to read

| | Gateway URL (`/storage/v1/files/…`) | API route (`/storage/v1/object/…`) |
| --- | --- | --- |
| Needs an `apikey` | No | Yes (publishable or secret) |
| Works in `<img src>` | Yes | Only with `?apikey=` |
| Who it is checked as | Anonymous, or the user whose `Authorization: Bearer` token came with the request | The key's role, plus the user token |
| Use it for | Public media, anything a browser embeds | Your app's own authenticated requests |

Both go through the same delivery code and the same bucket **read policy**. A URL is never the security: an object whose read policy requires sign-in answers `401` to an anonymous request, however well the URL is guessed.

<Note>
A secret key bypasses policies, so never put one in a URL. For restricted objects that someone without an account must open, make a [share link](/storage/share-links).
</Note>

## Status codes

| Status | Meaning |
| --- | --- |
| `200` / `206` | The object, or the byte range you asked for |
| `304` | `If-None-Match` matched the object's `ETag` |
| `401` | The read policy needs a signed-in user and the request had none |
| `403` | Signed in, but the read policy refuses this user |
| `404` | No such bucket, environment or object, or an unsafe key |
| `416` | The `Range` starts past the end of the object |
| `502` | The storage provider could not be reached |

## Content type and disposition

* `Content-Type` is what the object was **sniffed** as at upload, not what the uploader claimed.
* Images, PDFs, plain text, CSV, audio and video are sent `inline`, so browsers render them in place.
* Everything else, and anything that could run script in your origin (HTML, SVG, XML, JavaScript), is always an `attachment`, whatever the extension says.
* Add `?download=1` to force a download, or `?download=report.pdf` to choose the file name.

## Ranges and streaming

Responses carry `Accept-Ranges: bytes`. A `Range: bytes=…` request returns `206 Partial Content` with `Content-Range`, so `<video>` and `<audio>` can seek without downloading the whole file. Objects are streamed from the driver in chunks and are never loaded into memory; S3-compatible drivers pass the range to the provider, so a seek reads only what it plays.

```bash
curl -H "Range: bytes=0-1023" "$GW/storage/v1/files/production/videos/intro.mp4" -o first-kb
```

## Caching

Every response has an `ETag` and `Last-Modified`, and conditional requests return `304`.

| Object | `Cache-Control` |
| --- | --- |
| Public bucket, anonymous request | `public, max-age=<bucket cache>` |
| Anything read with credentials | `private, max-age=<bucket cache>` |

The bucket's **Browser cache** setting (`cache_max_age`, seconds) defaults to `0`: browsers revalidate each time, which is cheap with an `ETag` and safe when objects are replaced. Raise it for immutable assets, such as content-hashed file names.

## Compression

Text-like objects (`text/plain`, CSV, JSON, XML, JavaScript, SVG) are gzip-compressed when the request sends `Accept-Encoding: gzip`, and `Vary: Accept-Encoding` is set. Images, video, audio, PDFs and archives are already compressed and are sent as stored. Range requests are never compressed.

## From a flow

The `storage.read` block returns an object's contents inside a flow and runs with service rights, bypassing the read policy:

```json
{
  "id": "load_template",
  "data": { "block": "storage.read", "config": { "bucket": "templates", "key": "email/welcome.html" } }
}
```

## Signed URLs

Signed URLs (`POST /storage/v1/sign/<bucket>/<key>` and the `storage.signed_url` block) still work for API consumers and for buckets that enable them. Studio no longer uses them: it uploads and previews with its own authority, and temporary sharing is done with [share links](/storage/share-links), which can be revoked.

## Troubleshooting

<AccordionGroup>
  <Accordion title="401 or 403 on an image in the browser">
    The bucket's read policy is not public, and a browser `<img>` cannot send headers. Make the bucket public, make the read policy `public`, or generate a share link.
  </Accordion>
  <Accordion title="404 on a file I just uploaded">
    Check the environment, bucket and key exactly: all are case-sensitive and the key is the full path including prefixes.
  </Accordion>
  <Accordion title="The video will not seek">
    Something between the browser and the gateway is stripping `Range` or `Accept-Ranges`. A CDN in front must forward range requests.
  </Accordion>
</AccordionGroup>
