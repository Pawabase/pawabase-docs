You'll set up a release process that lets you build freely and ship safely: work in `development`, check in `staging` (and in a preview per pull request), and move to `production` with a review of exactly what changes, a backup first, and a way back.

**You'll use:** [environments](/environments/overview), [API keys](/environments/api-keys), [previews](/environments/previews), [promote](/environments/promote), [backups](/backups/overview).

## The setup

| Environment | Who uses it | Keys in | Data |
| --- | --- | --- | --- |
| `development` | You, building in Studio | Your laptop's `.env` | Made-up |
| `pr-<branch>` previews | CI, reviewers | The preview deployment | Seeded test data |
| `staging` | QA, demos | The staging deployment | Test data, or anonymised copies |
| `production` | Customers | The production deployment's secret store | Real |

## 1. Create the environments

**Project → Environments → New environment**: `staging`, copying from `development`; then `production`, copying from `staging`. Each comes with its own publishable and secret keys, shown once: store them in each deployment's secret store.

Make `production` the [default environment](/environments/overview#the-default-environment) if you want requests that name no environment to go there.

## 2. Point each app at its environment

```typescript
export const pawabase = createClient({
  url: import.meta.env.VITE_PAWABASE_URL,
  project: import.meta.env.VITE_PAWABASE_PROJECT,
  apiKey: import.meta.env.VITE_PAWABASE_PUBLISHABLE_KEY,
  environment: import.meta.env.VITE_PAWABASE_ENVIRONMENT,   // development | staging | production
});
```

Limit each build's key to its environment (a production key that reaches only `production`), so a staging key in a production build fails loudly instead of silently mixing data.

## 3. Things promote doesn't copy

Set these up **in each environment** by hand, once:

| Thing | Where |
| --- | --- |
| Secrets (payment keys, partner tokens) | **Secrets**; test values in development, live in production |
| Mail delivery | **Mail → Delivery**; paused or a test inbox in development |
| AI providers and models | **AI → Providers**, **AI → Models**, with the same model names |
| Connection keys | **AI → Connections** |
| Sign-in providers, redirect URLs | **Users & auth** |
| Alarms, status page | **Activity → Alarms**, **Status page** |

## 4. A preview per pull request

In CI, when a pull request opens, create a preview from `staging` and give its keys to the preview deployment. It expires by itself. See [Previews](/environments/previews#create-one-from-ci).

## 5. Release: review, back up, promote

<Steps>
  <Step title="Promote development → staging, with a review">
    **Promote** from `development` to `staging`. The dry run lists added and changed definitions, the table changes that will be applied, those that **need review** (renames, type changes, removals, which promote never applies), and anything **blocked**.
  </Step>
  <Step title="Test staging">
    Run your end-to-end tests and the rule tests from [Testing rules](/policies/testing).
  </Step>
  <Step title="Back up production">
    **Backups → Back up now**, named after the release, and **pin** it.
  </Step>
  <Step title="Promote staging → production">
    Review the dry run again: it should be what you saw in staging.
  </Step>
  <Step title="Watch">
    For the next hour, watch **Activity → Overview** and **Errors**, and compare with before.
  </Step>
</Steps>

In code, with a secret key that can manage both environments:

```typescript
const m = manage(pawabase, "staging");
const review = await m.environments.promote("production", { dryRun: true });
if (review.blocked.length) throw new Error(review.blocked.join("\n"));
await manage(pawabase, "production").backups.snapshot(`release-${version}`);
await m.environments.promote("production");
```

## 6. Changes promote won't make

Renames, type changes and removals are listed, not applied, so a release can never drop a column that holds real data. Do them deliberately:

1. **Add** the new column (promoted automatically).
2. Deploy app code that writes **both** old and new.
3. Copy existing values over (a flow, or the SQL editor after a backup).
4. Deploy code that reads only the new column.
5. Remove the old column in each environment, by hand, last.

See [Migrations and history](/database/migrations-and-history).

## 7. Rolling back

| What went wrong | Roll back by |
| --- | --- |
| A rule or flow change | Promote the previous version from staging, or fix forward in production |
| An API shape change broke old apps | Serve the old shape as a [versioned API](/environments/api-versions) |
| Data damaged | Restore the pinned backup's **Data** part (merge or replace), which first saves the current state |

## Alternatively: everything as code

If you'd rather review changes in pull requests than in Studio, keep your definitions in your repository with [infrastructure as code](/tools/iac/overview) and deploy the same code to each environment from CI ([CI/CD](/tools/iac/ci-cd)). The same rules apply: secrets, keys and data stay per environment.
