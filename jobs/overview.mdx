A **job** is one unit of background work. Instead of making a request wait while you call a payment provider, build a report or fan a notification out to a thousand users, you dispatch a job and answer immediately. The work runs on its own, with its own status, its own attempts and its own record you can look up later.

Every kind of background work in a project shares one job system: flow runs started by events and schedules, outbound webhook deliveries and email sends. That means one place to look, one set of states and one way to retry, whatever started the work.

## Get started

Jobs are dispatched from a [flow](/flows/overview) and observed from your server code with the management client (a secret key, never a browser).

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";
import { manage } from "@pawabase/client/manage";

const pawabase = createClient({
  url: "https://api.example.com",
  apiKey: process.env.PAWABASE_SECRET_KEY!,
  environment: "production",
});
const m = manage(pawabase);

// What is waiting, running or failing right now?
const queues = await m.jobs.queues();
const failed = await m.jobs.failed();

// Look at one job, then try it again.
const job = await m.jobs.detail("job_123");
await m.jobs.retry("job_123");
```

```python Python
import os
from pawabase import Pawabase

pb = Pawabase(
    "https://api.example.com",
    os.environ["PAWABASE_SECRET_KEY"],
    environment="production",
)

# What is waiting, running or failing right now?
queues = pb.manage.jobs.queues()
failed = pb.manage.jobs.failed()

# Look at one job, then try it again.
job = pb.manage.jobs.detail("job_123")
pb.manage.jobs.retry("job_123")
```
</CodeGroup>

The dispatching side is a flow block. This one hands a report to the background and returns at once:

```json
{
  "id": "dispatch_report",
  "data": {
    "block": "queue.flow",
    "config": { "flow": "generate_monthly_report", "input": { "month": "{{ input.body.month }}" } }
  }
}
```

## The queues

Work is placed on a **named queue**. A project starts with these, each used by one kind of work:

| Queue | What runs on it |
| --- | --- |
| `events` | Delivering an event to its subscribers |
| `flows` | Flow runs started by events, schedules and dispatch |
| `functions` | Function invocations |
| `webhooks` | Outbound webhook deliveries |
| `mail` | Email sends |
| `default` | Anything you dispatch without naming a queue |

A queue runs its jobs in the order they arrived. There is no priority inside one queue, so if some work must not wait behind other work, give it its own queue name when you dispatch it. See [dispatching](/jobs/dispatching#choosing-a-queue).

## When to use a job

Reach for a job when the work is slow, can fail and be tried again, or does not need to finish before you answer.

- **Use a job:** sending a receipt, syncing a customer to a CRM, generating a PDF, importing a file, calling a provider that is sometimes down.
- **Do it in the request:** reading or writing the record the caller asked for, and anything the response has to contain.
- **Use a [schedule](/jobs/schedules) instead:** work that should happen at a wall-clock time, such as every night at 03:00.

<Note>
A job that fails is not retried automatically unless you say so. This is deliberate: retrying arbitrary business logic can charge a card twice. Read [lifecycle and retries](/jobs/lifecycle-and-retries) before relying on a retry.
</Note>
