A **schedule** runs a flow by the clock instead of in response to a request or an event. Nightly rollups, hourly syncs, a reminder sweep every morning: you add a `trigger.schedule` node to a flow and give it a time rule.

## Get started

A schedule lives in the flow, as a trigger node:

```json
{
  "id": "start",
  "data": { "block": "trigger.schedule", "config": { "cron": "0 3 * * *" } }
}
```

Save the flow and the schedule is live within a few seconds. You can then see it, and run it on demand, from code:

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";
import { manage } from "@pawabase/client/manage";

const pawabase = createClient({
  url: "https://api.example.com",
  apiKey: process.env.PAWABASE_SECRET_KEY!,
  environment: "production",
});
const m = manage(pawabase);

const schedules = await m.schedules.list();
await m.schedules.run("nightly-rollup");
```

```python Python
import os
from pawabase import Pawabase

pb = Pawabase(
    "https://api.example.com",
    os.environ["PAWABASE_SECRET_KEY"],
    environment="production",
)

schedules = pb.manage.schedules.list()
pb.manage.schedules.run("nightly-rollup")
```
</CodeGroup>

`run` fires the schedule now, outside its normal time, which is the quickest way to test one.

## What a schedule carries

When it fires, the flow starts at the `trigger.schedule` node and receives:

```json
{ "scheduled_at": "2026-10-29T03:00:00Z" }
```

as its `input`. Use `scheduled_at` for time-based logic, so a run that starts a little late still works on the right window.

| Property | Meaning |
| --- | --- |
| `flow` | The flow the schedule runs |
| `node` | The `trigger.schedule` node in that flow |
| `cron` | A five-field cron expression |
| `every` | A fixed interval in seconds |
| `enabled` | Whether it is active |
| `input` | Extra input merged into the run |

Set at least one of `cron` or `every`. A flow may hold several schedule nodes; each is independent.

## A schedule is a job

A fired schedule appears as an ordinary [job](/jobs/overview) on the `flows` queue. That means it has a status, it can [fail and be retried](/jobs/failures-and-replay), and you can find it in the [job log](/jobs/monitoring).

## Changing and stopping

- **Change the time:** edit the node's `cron` or `every` and save. The new rule replaces the old one.
- **Pause:** disable the schedule. The flow stays; nothing fires.
- **Remove:** delete the trigger node.

## Patterns

### Nightly rollup

```json
{ "id": "start", "data": { "block": "trigger.schedule", "config": { "cron": "0 3 * * *" } } }
```

Use the `time.now` block with `offset_seconds: -86400` to summarise the previous day, whenever the run starts.

### Sweep for due work

Rather than scheduling one delayed job per item, run a short schedule that finds whatever is due:

```json
{ "id": "start", "data": { "block": "trigger.schedule", "config": { "every": 300 } } }
```

The flow reads records whose `due_at` has passed and `notified` is false, handles them, and marks them. A missed run only delays things until the next one.

### Heartbeat

```json
{ "id": "start", "data": { "block": "trigger.schedule", "config": { "every": 60 } } }
```

A flow that checks something every minute and emits an event when it is wrong.
