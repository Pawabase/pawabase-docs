You start background work from a flow with one of two blocks. Both return as soon as the job is stored, not when it finishes, so the flow carries on and the caller gets its response.

## Dispatch a flow

`queue.flow` runs another flow as a job.

```json
{
  "id": "dispatch_export",
  "data": {
    "block": "queue.flow",
    "config": {
      "flow": "generate_monthly_report",
      "input": { "month": "{{ input.body.month }}", "account_id": "{{ auth.org }}" },
      "queue": "default",
      "delay": 0
    }
  }
}
```

| Field | Type | Required | Default | Meaning |
| --- | --- | --- | --- | --- |
| `flow` | string | Yes | none | Name of the flow to run |
| `input` | object | No | `{}` | Becomes `input` inside the dispatched flow |
| `queue` | string | No | `"default"` | Which queue the job waits on |
| `delay` | integer, seconds | No | `0` | How long before the job may start |

The block's output is `{ "job_id": "<id>" }`. Keep it if you want to look the job up later; see [monitoring](/jobs/monitoring).

## Dispatch a function

`queue.function` does the same for a registered function.

```json
{
  "id": "sync_crm",
  "data": {
    "block": "queue.function",
    "config": {
      "function": "sync_customer_to_crm",
      "input": { "customer_id": "{{ steps.create_customer.output.id }}" },
      "queue": "default"
    }
  }
}
```

It takes the same `input`, `queue` and `delay` fields, with `function` in place of `flow`.

## Run a flow now from your code

When you want to start a flow yourself, for a test or from an admin tool, use the management client. This runs the flow once and returns its result; it is not queued.

<CodeGroup>
```typescript TypeScript
const result = await m.flows.run("generate_monthly_report", { month: "2026-09" });
```

```python Python
result = pb.manage.flows.run("generate_monthly_report", {"month": "2026-09"})
```
</CodeGroup>

Pass `asUser` (`as_user` in Python) to run it with a given identity so [policies](/policies/overview) apply as they would to that user. To make real background work from your own code, emit an [event](/events/overview) that a flow subscribes to:

<CodeGroup>
```typescript TypeScript
await m.events.emit("report.requested", { month: "2026-09" });
```

```python Python
pb.manage.events.emit("report.requested", {"month": "2026-09"})
```
</CodeGroup>

The subscribing flow runs as a job on the `flows` queue.

## Delaying a job

`delay` is a number of seconds from the moment of dispatch.

```json
{
  "flow": "send_trial_reminder",
  "input": { "account_id": "{{ steps.create_account.output.id }}" },
  "delay": 259200
}
```

That is three days. A delay is relative, so it cannot express "next Monday at 9". Use a [schedule](/jobs/schedules) for anything tied to the calendar.

<Warning>
Treat a delay as "not before", not "exactly at". For work that must happen, such as a billing reminder, prefer a schedule that looks for due items, so a missed run is picked up on the next one.
</Warning>

## Choosing a queue

Name a queue when work should not compete with other work.

| Situation | Queue choice |
| --- | --- |
| Quick, user-visible follow-up | `default` |
| Large imports or exports | A dedicated name such as `bulk` |
| Calls to a slow third party | A dedicated name such as `crm` |
| Anything latency sensitive | Leave `bulk` and `crm` work off its queue |

Queue names are free text. Dispatching to a new name creates it, and it appears in [`queues()`](/jobs/monitoring#queue-depth) once it has had a job.

## Passing input

Input is JSON. Pass identifiers, not whole records: the job should load the current row when it runs, because the row may have changed while the job waited.

```json
{ "input": { "order_id": "{{ input.event.payload.record.id }}" } }
```

Keep input small. A job with a large payload is slower to store and harder to read in the log.
