A job that runs out of attempts is kept so you can see why and decide what to do. You can work through failures from code or from [Studio](/studio/jobs-and-failures).

## List what failed

<CodeGroup>
```typescript TypeScript
const failed = await m.jobs.failed();

// Or filter the full job log
const recent = await m.jobs.list({ status: "failed", queue: "flows", limit: 50 });
```

```python Python
failed = pb.manage.jobs.failed()

# Or filter the full job log
recent = pb.manage.jobs.list(status="failed", queue="flows", limit=50)
```
</CodeGroup>

`failed()` returns the jobs that gave up. `list` accepts `status` (`queued`, `active`, `retrying`, `succeeded`, `failed`), `queue` and `limit`.

## Read one job

<CodeGroup>
```typescript TypeScript
const job = await m.jobs.detail("job_123");
```

```python Python
job = pb.manage.jobs.detail("job_123")
```
</CodeGroup>

The detail holds the queue, the input it ran with, the number of attempts and the error from the last one. Read the error before retrying: if the cause is a bug or bad input, a retry fails the same way.

## Retry one job

<CodeGroup>
```typescript TypeScript
await m.jobs.retry("job_123");
```

```python Python
pb.manage.jobs.retry("job_123")
```
</CodeGroup>

The job goes back on its queue with its original input.

<Warning>
A retry cannot know how far the first attempt got. If it created an invoice and then failed while emailing it, a retry creates a second invoice unless the work is [idempotent](/jobs/patterns#idempotent-jobs).
</Warning>

## Replay a batch

When an outage fails many jobs at once, retry them together. `replay` selects jobs by id or by filter and queues them again.

<CodeGroup>
```typescript TypeScript
// Count first, change nothing
const preview = await m.jobs.replay({ status: "failed", queue: "mail", sinceMinutes: 120, dryRun: true });

// Then do it
await m.jobs.replay({ status: "failed", queue: "mail", sinceMinutes: 120 });

// Or replay named jobs
await m.jobs.replay({ ids: ["job_1", "job_2"] });
```

```python Python
# Count first, change nothing
preview = pb.manage.jobs.replay(status="failed", queue="mail", since_minutes=120, dry_run=True)

# Then do it
pb.manage.jobs.replay(status="failed", queue="mail", since_minutes=120)

# Or replay named jobs
pb.manage.jobs.replay(ids=["job_1", "job_2"])
```
</CodeGroup>

| Option | Default | Meaning |
| --- | --- | --- |
| `ids` | none | Replay exactly these jobs |
| `status` | `failed` | Which status to select when no ids are given |
| `queue` | all | Limit to one queue |
| `job` | all | Limit to one kind of job |
| `sinceMinutes` / `since_minutes` | no limit | Only jobs from the last N minutes |
| `limit` | `200` | Most jobs one call will replay |
| `dryRun` / `dry_run` | `false` | Count the matches without queueing anything |

Always run the dry run first. A filter that is broader than you meant is the common way to replay thousands of jobs by accident.

## Dismiss a failure

When a failed job needs no further action, remove it from the failed list:

<CodeGroup>
```typescript TypeScript
await m.jobs.dismissFailed("job_123");
```

```python Python
pb.manage.jobs.dismiss_failed("job_123")
```
</CodeGroup>

## A recovery routine

A typical response to an outage on a downstream service:

1. List failures in the affected queue and read two or three errors to confirm the cause.
2. Wait until the service is back.
3. Run `replay` with `dryRun: true` over the outage window and check the count.
4. Run it for real.
5. List failures again. Anything still failing has a cause other than the outage; fix that and retry individually.
