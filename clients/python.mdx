`pawabase` is the official Python client for Pawabase.
It gives scripts, servers, workers and notebooks the same capabilities the TypeScript client gives browsers: records, authentication, storage, flows and routes, realtime, and, with a secret key, environment management and user administration.

This page is the map of the package.
It explains what a client object represents, the difference between the blocking and the `asyncio` client, what each part is for, which key to use where, and how the Python client differs from the TypeScript one.

<Info>
This section documents the `pawabase` package, version 0.3.0, from the `feat/sdk-split` branch of the `Pawabase/pawabase-python` repository.
Every method named here exists in that source.
Where the Python client behaves differently from the TypeScript client, the page says so.
</Info>

## The mental model

A Pawabase client is an HTTP client for **one environment of one project**, reached through **one gateway**, holding **one API key** and, optionally, **one signed-in user**.

The client is not a database driver and not an ORM.
It does not connect to your database, and it does not map rows to classes.
Every call is an HTTP request to the gateway; the gateway checks the key and the services apply your policies; what comes back is plain Python data: dictionaries, lists, strings and numbers.

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";

const pawabase = createClient({ url: "https://api.example.com", apiKey: "pb_pk_…", environment: "production" });

const page = await pawabase.from("orders").eq("status", "open").order("created_at", "desc").perPage(20);
for (const order of page.data) console.log(order.id, order.total_minor);
```

```python Python
from pawabase import Pawabase

pb = Pawabase("https://api.example.com", "pb_pk_…", environment="production")

page = pb.from_("orders").eq("status", "open").order("-created_at").per_page(20).execute()
for order in page:
    print(order["id"], order["total_minor"])
```

```bash cURL
curl -G "https://api.example.com/rest/v1/orders" -H "apikey: pb_pk_…" -H "x-environment: production" \
  --data-urlencode "filter[status]=eq.open" --data-urlencode "sort=-created_at" --data-urlencode "per_page=20"
```
</CodeGroup>

What the client adds on top of `httpx` is the part that is easy to get wrong:

| Concern | What the client does |
| --- | --- |
| Credentials | Sends the key on every request, and the user's access token when someone is signed in |
| Sessions | Keeps the session in a store you choose, and renews the access token before it expires or after a `401` |
| Queries | Builds the filter, sort, select, expand and paging parameters, and refuses queries the server would answer wrongly |
| Failures | Raises one exception hierarchy for every error shape the platform produces |
| Rate limits | Waits for `Retry-After` and repeats rate-limited requests |
| Retries | Repeats reads after network failures and gateway errors |
| Realtime | Publishes and reads over HTTP from any client; keeps live channels over one WebSocket on the async client |

## Two clients, one API

The package has two client classes with the same methods.

| Class | Built on | Methods return | Use in |
| --- | --- | --- | --- |
| `Pawabase` | `httpx.Client` | Values | Scripts, Django, Flask, notebooks, synchronous workers |
| `AsyncPawabase` | `httpx.AsyncClient` | Awaitables | FastAPI, Starlette, Sillo, `asyncio` workers |

<CodeGroup>
```typescript TypeScript
// TypeScript has one client; every call returns a promise.
const page = await pawabase.from("orders").eq("status", "open").perPage(20);
```

```python Python
from pawabase import AsyncPawabase

async with AsyncPawabase("https://api.example.com", "pb_pk_…", environment="production") as pb:
    page = await pb.from_("orders").eq("status", "open").per_page(20).execute()
```
</CodeGroup>

The method names, arguments and results are identical; the async client's methods are awaited.
Code written against one translates to the other by adding or removing `await`.

One capability exists only on the async client: live realtime channels, which need a WebSocket that stays open alongside other work.
Publishing, presence and history over HTTP work on both.

```bash
python -m pip install pawabase
```

```bash
python -m pip install "pawabase[realtime]"
```

The package needs Python 3.11 or later and depends only on `httpx`.
The `realtime` extra adds the `websockets` package, which live channels need; publishing, presence and history over HTTP work without it.

With `uv` or Poetry:

## The three things a client needs

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";

const pawabase = createClient({ url: "https://api.example.com", apiKey: "pb_pk_live_…", environment: "production" });
```

```python Python
from pawabase import Pawabase

pb = Pawabase(
    "https://api.example.com",
    "pb_pk_live_…",
    environment="production",
)
```

```bash cURL
curl "https://api.example.com/health/v1" -H "apikey: pb_pk_live_…" -H "x-environment: production"
```
</CodeGroup>

### The gateway URL

The first argument is the origin of your Pawabase gateway, the single public entry point for every service.
The client appends `/rest/v1`, `/auth/v1`, `/storage/v1`, `/realtime/v1`, `/flows/v1` and `/platform/v1` to it.
A trailing slash is removed.

Give the origin only, not a service path.
You find it in Studio under **Access → API keys**, in the **Health check** card.

### The API key

| Key | Prefix | Where it may live | What it can do |
| --- | --- | --- | --- |
| Publishable | `pb_pk_…` | Apps, command-line tools people run, servers acting for people | Acts as the anonymous role or the signed-in user; every policy applies |
| Secret | `pb_sk_…` | Servers, workers, CI | Bypasses policies; required for `pb.manage` and `pb.admin` |

A secret key is a root credential for one environment.
Keep it in your server's secret store, never in a repository or a notebook you share.
The client refuses to put a secret key in a URL, for social sign-in, and refuses share links and user administration to clients without one.

Keys are created in Studio under **Access → API keys**; the full key is shown once.
See [API keys](/studio/api-keys).

### The environment name

`environment` defaults to `"development"`.
That default is convenient on a laptop and dangerous everywhere else, because the Python client uses the name in more places than the TypeScript client does:

| Use | Effect of a wrong name |
| --- | --- |
| The `x-environment` header on every request | A mismatch with the key's environment can be refused |
| Social sign-in URLs | The provider sends people to the wrong environment |
| Public storage URLs from `public_url` and `transform_url` | URLs point at another environment's files |
| Realtime connections | The socket names the wrong environment |
| `pb.manage` and `pb.admin` | Management calls change another environment |

Always pass `environment=` explicitly outside local development, from the same configuration that provides the key.

## How a request travels

```text
your code
  │  pb.from_("orders").eq("status", "open").execute()
  ▼
pawabase (Python)
  │  GET /rest/v1/orders?filter[status]=eq.open
  │  apikey: pb_pk_…            x-environment: production
  │  Authorization: Bearer …     (when a user is signed in, or through as_user)
  │  user-agent: pawabase-python/0.3
  ▼
gateway: key, origin, firewall, rate limit       → 401 / 403 / 429
  ▼
data service: validation, then policy            → 422 / 401 / 403 / 404
  ▼
JSON → a Page(data, page, per_page, total)
```

A `429` from the gateway means the request did nothing, which is why the client waits and repeats it whatever the method.
A record hidden by a read policy answers `404`, not `403`, so `get()` raises `NotFoundError` for "does not exist" and "not yours" alike.

## The parts of the client

### Records

<CodeGroup>
```typescript TypeScript
const orders = pawabase.from("orders");

const order = await orders.create({ customer_id: "c_1", total_minor: 4200 });
const same = await orders.get(order.id);
await orders.update(order.id, { status: "paid" });

const openOrders = await orders.eq("status", "open").gte("total_minor", 1000).order("created_at", "desc").perPage(20);
for await (const row of orders.eq("status", "open")) { /* … */ }
```

```python Python
orders = pb.from_("orders")

order = orders.create({"customer_id": "c_1", "total_minor": 4200})
same = orders.get(order["id"])
orders.update(order["id"], {"status": "paid"})

open_orders = orders.eq("status", "open").gte("total_minor", 1000).order("-created_at").per_page(20).execute()
for row in orders.eq("status", "open").iterate():
    ...
```

```bash cURL
curl -X POST "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"customer_id": "c_1", "total_minor": 4200}'
curl -X PATCH "$PAWABASE_URL/rest/v1/orders/$ORDER_ID" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"status": "paid"}'
curl -G "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" --data-urlencode "filter[status]=eq.open" \
  --data-urlencode "filter[total_minor]=gte.1000" --data-urlencode "sort=-created_at" --data-urlencode "per_page=20"
```
</CodeGroup>

Queries are immutable: each method returns a new query.
`execute()` runs one page; `iterate()`, `all()`, `first()`, `single()`, `count()` and `exists()` are the other ways to run it.
The client refuses three kinds of query the server would answer wrongly: a second filter on the same field, `eq.false` (sent as `is.false` instead), and list values that contain commas.

### Authentication

<CodeGroup>
```typescript TypeScript
const result = await pawabase.auth.signInWithPassword({ email: "ada@example.com", password: "…" });
if (result.status === "mfa_required") await result.verify(await askForCode());

const user = await pawabase.auth.getUser();
```

```python Python
result = pb.auth.sign_in_with_password(email="ada@example.com", password="…")
if result.status == "mfa_required":
    result.verify(input("Code: "))

user = pb.auth.get_user()
```

```bash cURL
curl -X POST "$PAWABASE_URL/auth/v1/token" -H "apikey: $PAWABASE_KEY" -H "content-type: application/json" \
  -d '{"grant_type": "password", "email": "ada@example.com", "password": "…"}'
curl "$PAWABASE_URL/auth/v1/user" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN"
```
</CodeGroup>

The session lives in a session store: memory by default, or a file that survives runs with `FileSessionStore`.
The client renews the access token shortly before it expires and once after a `401`.

</CodeGroup>

The Python client builds keyless gateway URLs for public files and image transformations, and can create revocable share links with a secret key.

`pb.manage` and `pb.admin` are attributes of every client, but their calls need a secret key; with a publishable key the server refuses them.

## Choosing a key for each place Python runs

| Where the code runs | Key | Identity |
| --- | --- | --- |
| A web server rendering pages or serving an API for people | Publishable | `pb.as_user(token)` per request |
| A background worker, cron job or queue consumer | Secret | None |
| A webhook receiver for a payment provider | Secret | None, after verifying the provider's signature |
| A command-line tool a person signs in to | Publishable | The person's session, in a `FileSessionStore` |
| A data notebook exploring production data | Secret, read-only through key restrictions | None |
| A CI job that applies definitions | Secret | None |
| A test suite | Publishable for test people, secret for setup | Test users |

A server acting for people should hold a publishable key and use `as_user`.
Then policies protect data on the server exactly as they would in a browser, and a bug in your server cannot reach more than the person could.

## How many clients to create

A client owns an `httpx` connection pool.
Creating one per request throws that pool away.

| Context | Clients |
| --- | --- |
| A web server | One per process, created at startup; `as_user(token)` per request |
| A script | One, used as a context manager so it closes |
| A worker | One per process |
| Tests | One per test, with a fake transport, closed afterwards |

```python
with Pawabase(url, key, environment="production") as pb:
    print(pb.from_("orders").count())
```

`as_user` returns a lightweight view that shares the parent's connection pool.
Closing a view closes nothing; closing the parent closes the pool.

## What comes back

| Call | Returns |
| --- | --- |
| `query.execute()` | A `Page`: `data`, `page`, `per_page`, `total`, and `raw`; iterable and indexable |
| `first()` | The first row, or `None` |
| `single()` | The first row, or raises `NotFoundError` |
| `get(id)`, `create(…)`, `update(…)` | A row as a `dict` |
| `delete(id)` | `None` |
| `pb.auth.get_user()` | The user as a `dict` |
| `bucket.upload(…)` | `{"bucket", "key", "size", "content_type"}` |
| `bucket.download(key)` | `bytes` |
| `pb.flows.invoke(…)` | The flow's response body |
| `pb.manage.*`, `pb.admin.*` | The management plane's JSON |

Field names are the server's, in `snake_case`, exactly as Studio and the API Explorer show them.
Dates arrive as ISO 8601 strings; parse them with `datetime.fromisoformat` where you need `datetime` objects.
When you send `datetime`, `date` or `Decimal` values in a create or update, the client converts them to ISO strings and text.

## How the Python client differs from the TypeScript client

Both clients talk to the same API, and most calls translate directly.
These differences matter when you move code or knowledge between them.

| Area | Python | TypeScript |
| --- | --- | --- |
| Default environment | `"development"` | None; features that need it raise |
| Async model | Two classes: `Pawabase` and `AsyncPawabase` | One class; every call is a promise |
| Running a query | `execute()` | `await query` |
| Typed rows | Plain `dict`; type with generated `TypedDict`s | Generic `Database` type checks names and fields |
| Rate limits | Waits up to 8 times, 1 to 20 seconds each, for any method | Waits within `maxRetryAfterMs`, up to the retry count |
| Network failures | Retried for reads, storage uploads and signing only | Retried for safe methods, including `PUT` and `DELETE` |
| Timeouts | `NetworkError` | `TimeoutError` |
| Validation errors | `ValidationError` with the raw issue list in `detail` | `ValidationError` with `issues`, `fieldError`, `byField` |
| Walking pages with an unknown total | Stops at the first short page | Continues until empty pages |
| Session events | No `INITIAL_SESSION`; listeners get changes only | `INITIAL_SESSION` first |
| Public file URLs | Keyless gateway URLs, with `transform_url` | Object URLs with the publishable key |
| Share links | `create_share_link` on a bucket, with a secret key | Through the management module |
| Live realtime | Async client only; the socket keeps its first token | Any client; refreshed tokens are sent over the socket |

Each page in this section explains the Python behavior in full.

```typescript TypeScript
const page = await pawabase.from("orders").eq("status", "open").order("created_at", "desc").expand("customer").perPage(20);
```


```bash cURL
curl -G "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" --data-urlencode "filter[status]=eq.open" \
  --data-urlencode "sort=-created_at" --data-urlencode "expand=customer" --data-urlencode "per_page=20"
```

```python
import httpx

def list_open_orders(access_token: str | None) -> dict:
    headers = {"apikey": "pb_pk_live_…", "x-environment": "production"}
    if access_token:
        headers["Authorization"] = f"Bearer {access_token}"
    response = httpx.get(
        "https://api.example.com/rest/v1/orders",
        params={"filter[status]": "eq.open", "sort": "-created_at", "expand": "customer", "per_page": "20"},
        headers=headers,
        timeout=30,
    )
    response.raise_for_status()
    return response.json()
```

The hand-written version works, and [REST conventions](/reference/rest-conventions) documents every parameter.
What it leaves out is everything around the request:

| Concern | Plain `httpx` | `pawabase` |
| --- | --- | --- |
| An expired access token | `401`; you refresh and repeat | Renewed before sending, or once after a `401` |
| A `429` from the gateway | An exception | Waits for `Retry-After`, then repeats |
| A `503` during a deploy | An exception | Repeated for reads |
| The error body | One of several shapes | One exception class per status, with `code`, `message`, `request_id` |
| `eq.false` on a boolean | Matches the wrong rows | Sent as `is.false` |
| A second filter on one field | The first is dropped silently | `QueryError` before sending |
| Dates and decimals in bodies | `TypeError` from the JSON encoder | Converted to ISO strings and text |

## Configuring each environment

Read the URL, key and environment name from configuration, never from source code.
Name them consistently so every service and script in a project reads the same variables.

| Variable | Holds |
| --- | --- |
| `PAWABASE_URL` | The gateway origin |
| `PAWABASE_ENV` | The environment name |
| `PAWABASE_PUBLISHABLE_KEY` | A `pb_pk_…` key, for acting as people |
| `PAWABASE_SECRET_KEY` | A `pb_sk_…` key, for system work |

A small settings module keeps the rest of the code free of configuration details:

```python
# app/pawabase_client.py
import os
from functools import lru_cache

from pawabase import AsyncPawabase, Pawabase


def _required(name: str) -> str:
    value = os.environ.get(name)
    if not value:
        raise RuntimeError(f"{name} must be set")
    return value


@lru_cache
def base() -> Pawabase:
    """One publishable-key client per process, for acting as people."""
    return Pawabase(_required("PAWABASE_URL"), _required("PAWABASE_PUBLISHABLE_KEY"), environment=_required("PAWABASE_ENV"))


@lru_cache
def service() -> Pawabase:
    """One secret-key client per process, for system work."""
    return Pawabase(_required("PAWABASE_URL"), _required("PAWABASE_SECRET_KEY"), environment=_required("PAWABASE_ENV"))
```

Requiring `PAWABASE_ENV` instead of falling back to the client's `"development"` default turns a missing setting into a startup error rather than a script that quietly changes the wrong environment.

With `pydantic-settings`, the same configuration is validated and typed:


## Four application shapes

### A web application acting for its users

```text
browser ──cookie or bearer token──▶ your Python server ──(pb_pk_ + user token)──▶ gateway
```

The server holds one publishable-key client and makes a per-request view with each person's token.
Policies apply to everything the server reads and writes for that person.

```python
from fastapi import Depends, FastAPI, Header

from pawabase import AsyncPawabase

app = FastAPI()
base = AsyncPawabase(PAWABASE_URL, PUBLISHABLE_KEY, environment=PAWABASE_ENV)


def pawabase_for(authorization: str | None = Header(default=None)):
    token = authorization.removeprefix("Bearer ") if authorization else None
    return base.as_user(token) if token else base


@app.get("/orders")
async def orders(pb=Depends(pawabase_for)):
    page = await pb.from_("orders").order("-created_at").per_page(20).execute()
    return page.raw
```

`page.raw` is the response body as the server sent it, which is convenient to pass through an API unchanged.

### A worker with no user

```text

```

## What a policy sees about your client

| Context value | Publishable key, no user | Publishable key with `as_user(token)` or a session | Secret key |
| --- | --- | --- | --- |
| `$auth.authenticated` | `false` | `true` | `false` |
| `$auth.kind` | `anonymous` | `user` | `service` |
| `$auth.user_id` | empty | the person's id | empty |
| `$auth.roles` | `[]` | the person's roles | `[]` |
| `$credential.role` | `anon` | `anon` | `service` |
| `$credential.is_service` | `false` | `false` | `true` |

The default policy on resource operations, routes and flows is `authenticated`, so anonymous calls are refused until you choose otherwise.
A secret key is not a signed-in person: policies that test `$auth.user_id` never see one, because secret keys bypass policies entirely.
See [the policy context](/policies/context).

## Checking a new configuration

A short smoke test, run after each deploy, catches a wrong URL, key or environment before people do.

```python
from pawabase import AuthenticationError, NetworkError, PawabaseError, Pawabase


def smoke_test(url: str, key: str, environment: str, resources: list[str]) -> list[tuple[str, bool, str]]:
    results: list[tuple[str, bool, str]] = []
    with Pawabase(url, key, environment=environment, retries=0, timeout=10) as pb:
        try:
            pb.status()
            results.append(("gateway answers", True, ""))
        except NetworkError as error:
            return [("gateway answers", False, str(error))]
        try:
            settings = pb.auth.settings()
            results.append(("key accepted", True, f"sign-up {'on' if settings.get('signup_enabled') else 'off'}"))
        except AuthenticationError as error:
            results.append(("key accepted", False, error.message))
        for name in resources:
            try:
                page = pb.from_(name).per_page(1).execute()
                results.append((f"list {name}", True, f"total {page.total}"))
            except PawabaseError as error:
                results.append((f"list {name}", False, f"{error.status_code} {error.code or error.message}"))
    return results
```

Read failures with the request path in mind: a gateway failure is the URL or the network; a `401` on the key check is the key; a `401` on a list while signed out is the default `authenticated` policy; a `404` on a list is a wrong name or a disabled operation.

## Data shapes you will meet

### Page

| Attribute | Meaning |
| --- | --- |
| `data` | The rows, a list of dicts |
| `page` | The page number, from 1 |
| `per_page` | Rows per page, 20 unless you asked otherwise, at most 200 |
| `total` | Matching rows for this caller, or `None` when a per-row policy makes it unknowable |
| `raw` | The response body as received |
| `has_next` | Whether another page probably follows |

A `Page` iterates over its rows, supports `len()`, and indexes like a list: `page[0]`.

### Session

| Attribute | Meaning |
| --- | --- |
| `access_token` | The bearer token |
| `refresh_token` | Single-use; exchanged for a new session |
| `expires_at` | Unix time, in seconds, when the access token expires |
| `user` | The user as a dict |
| `session_id`, `org`, `org_role` | The session's id, and the organization the token is for |

### Sign-in results

| Class | Attributes |
| --- | --- |
| `SignInResult` | `status` (`signed_in` or `mfa_required`), `session`, `mfa_token`, `factors`, and `verify(code)` |
| `SignUpResult` | `user`, `session`, `verification_required` |

### A user

The user dict has `id`, `email`, `username`, `name`, `avatar_url`, `email_verified`, `user_metadata`, `app_metadata`, `roles`, `mfa_enabled`, `identities`, `created_at` and `last_sign_in_at`.
`user_metadata` is editable by the person and must never decide access; `app_metadata` is set by administrators and servers and can be trusted.

## What the client sends

| Header | Value | When |
| --- | --- | --- |
| `apikey` | Your API key | Every request except to signed URLs |
| `x-environment` | The `environment` argument, `development` by default | Every request except to signed URLs |
| `user-agent` | `pawabase-python/0.3` | Every request |
| `Authorization` | `Bearer <access token>` | With a session, an `access_token` argument, or an `as_user` view |
| `content-type` | `application/json` for JSON bodies; the file's type for uploads | When there is a body |
| Your `headers` | Whatever you passed | Every request |

The `user-agent` appears in the platform's request logs, so you can tell Python traffic from browser traffic under **Project → Activity**.

Answers carry `x-request-id`, which the client copies onto every exception as `request_id`, and `Retry-After` on `429`, which the client uses to wait.

## Sessions in long-running processes

A browser tab lives for minutes or hours; a Python process can live for weeks.
The session machinery is built for both.

| Moment | What happens |
| --- | --- |
| Client created | The session store is read on first use; nothing is sent |
| A request with less than 30 seconds left on the token | The client refreshes first, then sends |
| A request answered `401` | The client refreshes once and repeats it |
| The refresh token is refused | The session is cleared, listeners get `SIGNED_OUT`, and the request raises `AuthenticationError` |
| The process restarts | A `FileSessionStore` gives the session back; a memory store starts signed out |

There is no background timer: refreshes happen when requests need them.
A process that is idle for a week and then makes a request refreshes at that moment, if the refresh token is still valid.

On the async client, concurrent requests that all find the token expiring share one refresh.
The blocking client has no such lock, so code that makes requests for one session from several threads at once can refresh twice; since refresh tokens are single-use, the second refresh ends the session.
Keep a signed-in session to one thread, or use the async client.

## How the client treats time

| Rule | Value |
| --- | --- |
| A token counts as expiring | 30 seconds before `expires_at` |
| Default request timeout | 30 seconds, for each attempt |
| Waits after `429` | `Retry-After`, or the body's `retry_after`, at least 1 and at most 20 seconds |
| Waits between retries of reads | 0.25 s, then 0.5 s, then 1 s, at most 2 s |

`expires_at` is computed from the device's clock when the server sends only a lifetime.
A clock that runs fast refreshes early; one that runs slow gets a `401`, which triggers a refresh and a repeat.
Either way the request succeeds.

A session adopted with `set_session(access, refresh)` is given an expiry one minute ahead, because the client does not decode the token; it therefore refreshes on the first request after that minute and learns the real expiry then.

## Concurrency with asyncio

The async client shines when a task needs several independent requests.

<CodeGroup>
```typescript TypeScript
async function dashboard(pawabase: PawabaseClient) {
  const [orders, tasks, user] = await Promise.all([
    pawabase.from("orders").eq("status", "open").perPage(5),
    pawabase.from("tasks").eq("done", false).perPage(5),
    pawabase.auth.getUser(),
  ]);
  return { orders: orders.data, tasks: tasks.data, user };
}
```

```python Python
import asyncio

async def dashboard(pb):
    orders, tasks, user = await asyncio.gather(
        pb.from_("orders").eq("status", "open").per_page(5).execute(),
        pb.from_("tasks").eq("done", False).per_page(5).execute(),
        pb.auth.get_user(),
    )
    return {"orders": orders.data, "tasks": tasks.data, "user": user}
```
</CodeGroup>

For many writes, bound the concurrency so the environment's rate limit is not the thing that slows you down:

```python
async def mark_all(pb, ids: list[str], status: str, limit: int = 5):
    gate = asyncio.Semaphore(limit)

    async def one(record_id: str):
        async with gate:
            return await pb.from_("orders").update(record_id, {"status": status})

    return await asyncio.gather(*(one(i) for i in ids), return_exceptions=True)
```

`return_exceptions=True` keeps one failure from cancelling the rest; inspect the results for exceptions afterwards.
The async `create_many` does the same for creates, with `concurrency=5` by default.

## Several environments in one process

Each environment has its own keys, so each needs its own client.

```python
staging = Pawabase(URL, STAGING_SECRET, environment="staging")
production = Pawabase(URL, PRODUCTION_SECRET, environment="production")

staging_plans = {plan["code"]: plan for plan in staging.from_("plans").all()}
production_plans = {plan["code"]: plan for plan in production.from_("plans").all()}

```

For management work, `pb.manage.environment("staging")` and `pb.admin.environment("staging")` address another environment with the same client, when its key may manage that environment.

## Forked workers

Servers such as Gunicorn fork worker processes.
An `httpx` client created before the fork shares connections between processes, which corrupts them.

Create clients after the fork: lazily on first use, as the `lru_cache` functions above do, or in a post-fork hook.
Do not create clients at import time in a module that Gunicorn's `--preload` imports in the parent.

## Django

Django views are synchronous by default, so they use the blocking client.
A middleware attaches a per-request view built from the person's token, which your sign-in stored in Django's session.

```python
# myapp/middleware.py
from myapp.pawabase_client import base


class PawabaseMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        token = request.session.get("pb_access")
        request.pawabase = base().as_user(token) if token else base()
        return self.get_response(request)
```

```python
# myapp/views.py
from django.shortcuts import render


def orders(request):
    page = request.pawabase.from_("orders").order("-created_at").per_page(20).execute()
    return render(request, "orders.html", {"orders": page.data})
```

## Celery and other task queues

Task workers act for the system, with a secret key, and must be safe to run twice, because queues redeliver.

```python
from celery import shared_task

from pawabase import NetworkError, ServerError
from myapp.invoices import render_invoice
from myapp.pawabase_client import service


@shared_task(bind=True, max_retries=5, autoretry_for=(NetworkError, ServerError), retry_backoff=True)
def issue_invoice(self, order_id: str):
    order = service().from_("orders").get(order_id)
    if order.get("invoice_key"):
        return order["invoice_key"]
    pdf = render_invoice(order)
    key = f"{order['org']}/invoices/{order_id}.pdf"
    service().storage.from_("invoices").upload(key, pdf, content_type="application/pdf")
    service().from_("orders").update(order_id, {"invoice_key": key})
    return key
```

Checking whether the work is already done, and writing to a fixed key, makes a redelivered task harmless.
Retrying only on `NetworkError` and `ServerError` leaves permanent failures, such as a `NotFoundError` for a deleted order, to fail once and be seen.

## A complete async program

```python
import asyncio
import os

from pawabase import AsyncPawabase, PawabaseError


async def main() -> None:
    async with AsyncPawabase(os.environ["PAWABASE_URL"], os.environ["PAWABASE_SECRET_KEY"], environment=os.environ["PAWABASE_ENV"]) as pb:
        overdue = await pb.from_("invoices").eq("status", "unpaid").lt("due_on", "2026-10-01").all(max_records=1000)
        print(f"{len(overdue)} overdue invoices")

        gate = asyncio.Semaphore(5)

        async def remind(invoice: dict) -> None:
            async with gate:
                try:
                    await pb.flows.invoke("send-reminder", {"invoice_id": invoice["id"]})
                except PawabaseError as error:
                    print(f"reminder for {invoice['id']} failed: {error.code or error.status_code} ({error.request_id})")

        await asyncio.gather(*(remind(invoice) for invoice in overdue))
        await pb.realtime.publish("ops:billing", "reminders.sent", {"count": len(overdue)})


asyncio.run(main())
```

## Before the first production release

| Check | Why |
| --- | --- |
| `environment=` is set from configuration in every client | No accidental `development` |
| Clients are created once per process, after forking | Connection pools are reused and not shared between processes |
| Servers use `as_user` per request | Policies apply to people's data |
| Errors are logged with `request_id` | Support can find requests |
| Long walks use `iterate()` or `all(max_records=…)` | Memory stays bounded |
| Writes that may be repeated rely on unique fields | The server has no idempotency keys |
| Tasks are safe to run twice | Queues redeliver |

## Blocking or async

| Your code | Choose |
| --- | --- |
| A Django or Flask application | `Pawabase` |
| A FastAPI, Starlette or other ASGI application | `AsyncPawabase` |
| A script or notebook | `Pawabase`, unless it makes many independent requests |
| A worker that processes items one by one | `Pawabase` |
| A worker that fans out many requests at once | `AsyncPawabase` |
| Anything that needs live realtime channels | `AsyncPawabase` |

Do not mix them inside one request path.
Calling the blocking client from an async handler blocks the event loop for the length of each request, and every other request on that worker waits.

## Type checking

The package is typed, and its methods are annotated. Results are `Any`, because their shape depends on your resources. Define application models with `TypedDict`, dataclasses or Pydantic when static row types are useful.

## A client for the life of an ASGI app

ASGI frameworks have a lifespan: code that runs at startup and shutdown.
Create the async client there, so it is closed cleanly when the server stops.

```python
from contextlib import asynccontextmanager

from fastapi import FastAPI, Request

from pawabase import AsyncPawabase


@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.pawabase = AsyncPawabase(PAWABASE_URL, PUBLISHABLE_KEY, environment=PAWABASE_ENV)
    yield
    await app.state.pawabase.close()


app = FastAPI(lifespan=lifespan)


def pawabase_for(request: Request):
    base = request.app.state.pawabase
    token = request.headers.get("authorization", "").removeprefix("Bearer ") or None
    return base.as_user(token) if token else base
```

`close()` on the async client also closes its realtime connection, if one was opened.

## Rate limits and keys

The gateway counts requests per API key: every request made with one key shares one budget, 600 requests per minute by default.
When the budget runs out, the gateway answers `429` with `Retry-After`, and the client waits and repeats.

That has a practical consequence.
A batch job that shares a key with your web servers can slow every person's requests while it runs.
Give jobs, servers and CI their own keys, so each has its own budget.

## One read, followed through

A read during a brief outage, with default settings:

```text
t=0.00 s   GET /rest/v1/orders                 503
           retried read: wait 0.25 s
t=0.26 s   GET /rest/v1/orders                 429 Retry-After: 2
           rate limited: wait 2 s (any method)
t=2.27 s   GET /rest/v1/orders                 200
```

The same with a create:

```text
t=0.00 s   POST /rest/v1/orders                503
           POST is not retried → ServerError raised
```

A create that failed with a gateway error may or may not have happened.
Unique fields make a repeat by your own code safe; see [Errors and retries](/clients/python/errors-retries).

## Request ids in your own logs

Servers log many requests at once, so each log line should say which of your requests it belongs to.
`contextvars` carry a request id through async code without passing it around:

```python
import contextvars
import logging

request_id = contextvars.ContextVar("request_id", default="-")


class RequestIdFilter(logging.Filter):
    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id.get()
        return True


handler = logging.StreamHandler()
handler.addFilter(RequestIdFilter())
handler.setFormatter(logging.Formatter("%(asctime)s %(request_id)s %(name)s %(message)s"))
logging.getLogger().addHandler(handler)
```

The `httpx` log lines for Pawabase calls then carry your request id, and exceptions add Pawabase's own `request_id` when you log them.
Together they connect your logs with **Project → Activity**.

## Replacing hand-written wrappers

Projects that used Pawabase before this package often have a small wrapper around `requests` or `httpx`.
Replacing it is mostly mechanical.

| Wrapper code | Replace with |
| --- | --- |
| `session.get(f"{URL}/rest/v1/{name}", params=…)` | `pb.from_(name)` with filter methods, then `execute()` |
| Manual `filter[field]=eq.value` strings | `.eq(field, value)`, which also handles booleans and nulls |
| `raise_for_status()` and parsing error bodies | Catch `PawabaseError` subclasses |
| A loop that refreshes on `401` | Built in |
| `time.sleep` after `429` | Built in |
| Paging loops with `page += 1` | `iterate()` or `pages()` |

Move one call site at a time; both can coexist while you do.

## Serverless functions

Serverless platforms reuse a process for many invocations while it is warm.
Create the client at module level so warm invocations reuse it, and per-request views inside the handler.

```python
import json

from pawabase import Pawabase

base = Pawabase(PAWABASE_URL, PUBLISHABLE_KEY, environment=PAWABASE_ENV, timeout=8)


def handler(event, context):
    token = (event.get("headers") or {}).get("authorization", "").removeprefix("Bearer ") or None
    pb = base.as_user(token) if token else base
    page = pb.from_("orders").per_page(20).execute()
    return {"statusCode": 200, "body": json.dumps(dict(page.raw))}
```

Keep the timeout well below the platform's limit, so failures surface as clean exceptions rather than killed invocations.

## Clients and processes

A client holds open connections and, possibly, a session.
Neither survives being pickled or sent to another process.

Libraries that send work to other processes, such as `multiprocessing` and some task queues, should send ids and parameters, and let each process build its own client.
The same applies to sessions: send the access token to a process that should act as a person, and build an `as_user` view there.

## Flask

Flask applications use the blocking client, with a per-request view kept on `g`.

```python
from flask import Flask, g, jsonify, request

from myapp.pawabase_client import base

app = Flask(__name__)


@app.before_request
def attach_pawabase():
    token = request.headers.get("Authorization", "").removeprefix("Bearer ") or None
    g.pawabase = base().as_user(token) if token else base()


@app.get("/api/orders")
def orders():
    page = g.pawabase.from_("orders").order("-created_at").per_page(20).execute()
    return jsonify(dict(page.raw))
```

`g` lives for one request, so each view belongs to exactly one person.

## Django async views

Django supports `async def` views.
In them, use the async client, created once per process, so the event loop is not blocked:

```python
from django.http import JsonResponse

from myapp.pawabase_client import async_base


async def order_count(request):
    token = request.headers.get("Authorization", "").removeprefix("Bearer ") or None
    pb = async_base().as_user(token) if token else async_base()
    return JsonResponse({"open": await pb.from_("orders").eq("status", "open").count()})
```

Mixing sync and async views in one project is fine; give each its matching client.

| `pb.auth.sign_in_with_password(email=…, password=…)` | `pawabase.auth.signInWithPassword({ email, password })` |
| `pb.auth.on_auth_state_change(listener)` | `pawabase.auth.onAuthStateChange(listener)` |
| `pb.auth.oauth_url(provider)` | `pawabase.auth.signInWithOAuthUrl(provider)` |
| `bucket.public_url(key)`, `transform_url(…)` | `bucket.getPublicUrl(key)` |
| `pb.flows.invoke(name, input)` (or `run`) | `pawabase.flows.run(name, input)` |
| `pb.as_user(token)` | `pawabase.asUser(token)` |
| `pb.manage`, `pb.admin` | `manage(client)`, `admin(client)` |
| `error.status_code`, `error.request_id` | `error.status`, `error.requestId` |

## A session store of your own

`SessionStore` is a protocol with two methods: `get()` returns the stored session or `None`, and `set(session)` stores one, or forgets it when given `None`.
Any object with those methods works.

A command-line tool on a desktop can keep the session in the operating system's keychain:

```python
import json

import keyring

from pawabase import Session


class KeyringSessionStore:
    def __init__(self, service: str, account: str) -> None:
        self.service, self.account = service, account

    def get(self) -> Session | None:
        raw = keyring.get_password(self.service, self.account)
        return Session.from_dict(json.loads(raw)) if raw else None

    def set(self, session: Session | None) -> None:
        if session is None:
            try:
                keyring.delete_password(self.service, self.account)
            except keyring.errors.PasswordDeleteError:
                pass
        else:
            keyring.set_password(self.service, self.account, json.dumps(session.to_dict()))
```

`Session.to_dict()` and `Session.from_dict()` are the serialization the built-in file store uses.
A server handling many people should not keep sessions in a shared store; it uses `as_user` with each request's token instead.

## A first look at tests

The client sends every request through an `httpx` client, so tests can answer requests without a network.
The package's own tests replace the client's internal `httpx` client with one that uses `httpx.MockTransport`:

```python
import httpx

from pawabase import Pawabase


def fake_client(handler) -> Pawabase:
    pb = Pawabase("http://gateway.test", "pb_pk_test", environment="test", retries=0)
    pb._client = httpx.Client(transport=httpx.MockTransport(handler), base_url="http://gateway.test", headers=pb.headers)
    return pb


def test_open_orders_query():
    seen = []

    def handler(request: httpx.Request) -> httpx.Response:
        seen.append(request)
        return httpx.Response(200, json={"data": [], "page": 1, "per_page": 20, "total": 0})

    pb = fake_client(handler)
    pb.from_("orders").eq("status", "open").execute()
    assert seen[0].url.params["filter[status]"] == "eq.open"
```

`_client` is a private attribute, used here the way the package's own tests use it.
The `respx` library mocks `httpx` without touching private attributes, and works the same way for the async client.
The [servers and testing page](/clients/python/servers-and-testing) covers both, and integration tests against a real environment.

## Python code or a flow

Logic that reacts to data can live in your Python code or in a Pawabase flow.

| Choose a flow when | Choose Python when |
| --- | --- |
| The logic is a sequence of record operations, conditions, emails and HTTP calls | It needs Python libraries: data science, PDF generation, image processing |
| It should run on events, schedules or routes without a server of your own | You already run a server or worker where it fits naturally |
| Non-developers should be able to read and adjust it in Studio | It is complex enough to need unit tests and code review |
| Its runs should appear in **Logic → Flows** with per-block traces | Its runs are part of your own observability |

Both can work together: a flow handles the trigger and calls your Python service through `http.request`, or your Python worker emits an event that flows react to.

## What the package does not do

| You might expect | Instead |
| --- | --- |
| Joins or SQL from the client | Relations with `expand`; computed answers from a [custom route](/data/custom-routes); SQL from `pb.manage.database` with a secret key |
| Two bounds on one field in one query | Filter one bound on the server and the other in Python, or use a route |
| Transactions across calls | A flow or route that performs the steps on the server |
| Idempotency keys | Unique fields that turn a repeat into a `409` |
| Model classes for rows | Generated `TypedDict`s, or your own dataclasses or Pydantic models |
| Custom functions | Removed from the platform; flows, routes and extension routes replace them |
| Live channels on the blocking client | `AsyncPawabase` |

## Exceptions at a glance

```text
PawabaseError (RuntimeError)
├── NetworkError            no answer: DNS, refused, reset, timed out
├── AuthenticationError     401
├── ForbiddenError          403
│   └── QuotaExceededError  403 with code quota_exceeded
├── NotFoundError           404
├── ConflictError           409
├── ValidationError         400 or 422
│   └── QueryError          a query refused before sending
├── RateLimitedError        429 that outlasted the client's waiting
├── ServerError             5xx
└── RealtimeError           a realtime request refused or timed out
ConfigError (RuntimeError)  the client used in a way that cannot work
```

Every `PawabaseError` has `status_code`, `detail` (the body), `code`, `message`, `details` and `request_id`.
`ConfigError` is not a `PawabaseError`: it signals a mistake in your code, not a failed request.
See [Errors and retries](/clients/python/errors-retries).

## Common mistakes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Leaving out `environment=` in production code | Requests, URLs and management calls name `development` | Pass it from configuration |
| A secret key on a server that acts for people | Policies never apply | A publishable key with `as_user` |
| A client per request | Connection pools are created and thrown away | One per process; views per request |
| The blocking client in async handlers | The event loop stalls | `AsyncPawabase` |
| A client created before forking | Corrupted connections in workers | Create after the fork |
| `all()` without `max_records` on large tables | Memory grows without bound | `iterate()`, or a cap |
| Catching `Exception` around every call | Bugs look like network problems | Catch `PawabaseError` subclasses |

## Coming from supabase-py

| supabase-py | pawabase | Note |
| --- | --- | --- |
| `create_client(url, key)` | `Pawabase(url, key, environment=…)` | Pass the environment |
| `supabase.table("t").select("*").execute()` | `pb.from_("t").execute()` | All columns by default |
| `.select("id, author(name)")` | `.select("id").expand("author")` | Relations by name |
| `.eq("a", 1).gte("b", 2)` | Same | One filter per field |
| `.range(0, 9)` | `.page(1).per_page(10)` | Pages from 1 |
| `response.data` | `page.data`, or the row itself for single-record calls | No wrapper object for rows |
| `APIError` | `PawabaseError` subclasses | By status |
| `supabase.auth.sign_in_with_password({...})` | `pb.auth.sign_in_with_password(email=…, password=…)` | Keyword arguments; may return `mfa_required` |
| `supabase.storage.from_("b").upload(path, file)` | `pb.storage.from_("b").upload(key, file)` | Always replaces |
| `supabase.functions.invoke(…)` | `pb.flows.invoke(…)` or `pb.routes.post(…)` | Server logic is flows and routes |
| `acreate_client` | `AsyncPawabase` | Same methods, awaited |

## A complete small program

The script below signs in, lists open orders, uploads a receipt, runs a flow, and handles the errors a real script meets.

```python
from getpass import getpass
from pathlib import Path

from pawabase import FileSessionStore, NotFoundError, Pawabase, PawabaseError, ValidationError

with Pawabase(
    "https://api.example.com",
    "pb_pk_live_…",
    environment="production",
    session_store=FileSessionStore("~/.config/orders-cli/session.json"),
) as pb:
    if pb.auth.session is None:
        result = pb.auth.sign_in_with_password(email=input("Email: "), password=getpass())
        if result.status == "mfa_required":
            result.verify(input("Code: "))

    user = pb.auth.get_user()
    page = pb.from_("orders").eq("status", "open").order("-created_at").expand("customer").per_page(10).execute()
    print(f"{user['email']} has {page.total if page.total is not None else 'some'} open orders")

    if page.data:
        first = page[0]
        pb.storage.from_("receipts").upload(f"{user['id']}/{first['id']}.pdf", Path("receipt.pdf"))
        try:
            quote = pb.flows.invoke("quote-order", {"order_id": first["id"]})
            print("quote", quote)
        except ValidationError as error:
            print("refused input:", error.detail)
        except NotFoundError:
            print("no such flow")
        except PawabaseError as error:
            print(f"failed: {error.status_code} {error.code} (request {error.request_id})")
```

## Security checklist

| Check | Why |
| --- | --- |
| Secret keys live in environment variables or a secret manager | Keys in repositories and notebooks spread |
| Servers acting for people use a publishable key and `as_user` | Policies then protect data on the server too |
| `environment=` is passed explicitly everywhere but local development | The default is `development` |
| Command-line tools store sessions with `FileSessionStore` | The file is created readable only by its owner |
| Exceptions are logged by fields, not with their full `detail` | Bodies can contain personal data |
| Keys for notebooks and reports are read-only and expire | Leaked copies stop working |
| `pb.manage` and `pb.admin` run only in server code you control | They act with full authority |

## Troubleshooting the first connection

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| `NetworkError: … Could not reach` | Wrong URL, DNS, TLS, or the gateway is down | Open the URL in a browser; check proxies |
| `AuthenticationError` on every call | Wrong, revoked or expired key | Copy it again from **Access → API keys** |
| Data from the wrong environment | `environment` not passed | Pass it explicitly |
| `AuthenticationError` on a list while signed out | The default `authenticated` policy | Choose a policy that admits anonymous callers, if intended |
| `NotFoundError` on a list | Wrong resource name, or the `list` operation is off | Compare with **Data** and the API Explorer |
| `ConfigError: … needs the async client` | A live channel on `Pawabase` | Use `AsyncPawabase` |
| `ConfigError: … websockets package` | The `realtime` extra is not installed | `pip install "pawabase[realtime]"` |

## Questions developers ask

<AccordionGroup>
  <Accordion title="Can I share one client between threads?">
    Yes, for requests: `httpx.Client` is thread-safe.
    Do not share a client that holds a signed-in session between threads acting for different people; give each request its own `as_user` view.
  </Accordion>
  <Accordion title="Can I use the async client from synchronous code?">
    Use the blocking client instead.
    Wrapping the async client in `asyncio.run` for each call creates and closes a connection pool every time.
  </Accordion>
  <Accordion title="Why are rows dictionaries rather than objects?">
    The server's JSON maps directly to dictionaries, which keeps the client small and predictable.
    Use the generated `TypedDict` types for static checking, or wrap rows in your own dataclasses or Pydantic models.
  </Accordion>
  <Accordion title="Does the client work with Pydantic?">
    Yes, at the boundaries: validate rows with your models after reading, and dump models to dicts before writing.
    `model_dump(mode="json")` produces values the client sends as they are.
  </Accordion>
  <Accordion title="How do I call an endpoint the client has no method for?">
    `pb.request("GET", "/auth/v1/settings")` sends any request with the key and token, the same retries for `GET`, and the same exceptions.
  </Accordion>
  <Accordion title="Is the async client safe to share between tasks?">
    Yes.
    Requests are independent, queries are immutable, and concurrent refreshes of one session share a single refresh.
  </Accordion>
  <Accordion title="Can I pass my own httpx client?">
    Not through the constructor.
    The client builds its own from the URL, headers and timeout; proxies and certificates come from the usual environment variables.
  </Accordion>
  <Accordion title="Does closing a client sign the person out?">
    No.
    Closing releases connections.
    The session stays in its store, and the next client with the same store continues it.
  </Accordion>
</AccordionGroup>
