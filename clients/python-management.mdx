The Python SDK exposes a focused set of management-plane methods directly on `Pawabase` and
`AsyncPawabase`. There is no `pb.manage` namespace and no `pb.admin` namespace. The methods on this
page cover function deployments, function runs, events, operator-triggered automation, definition
reads, and remote runtime calls.

They do not cover every control in Studio. When a management capability is absent from this
reference, the Python SDK does not provide a convenience method for it.

<Warning>
Use a secret key only in a trusted server, local operator session, or CI secret store. A secret key
bypasses project policies. Never place it in browser code, a mobile binary, a public repository, or
output captured by a build log.
</Warning>

## Scope and route model

Management methods build routes under:

```text
/platform/v1/projects/<project>/envs/<environment>/...
```

One client is scoped to one environment. To operate on another environment, create another client
with that environment name and a suitable key.

```python
from pawabase import Pawabase

production = Pawabase(
    "https://api.example.com",
    "pb_sk_...",
    project="acme",
    environment="production",
)

staging = Pawabase(
    "https://api.example.com",
    "pb_sk_...",
    project="acme",
    environment="staging",
)
```

The SDK does not expose `pb.manage.environment("staging")`. Separate clients make the target visible
at the call site and reduce accidental production operations.

## The complete management surface

| Concern | Public methods |
| --- | --- |
| Function catalogue | `functions` |
| Deployments | `deploy_functions`, `deployments`, `deployment`, `activate_deployment`, `remove_deployment` |
| Function branches | `function_branches`, `remove_function_branch` |
| Function execution | `function_runs`, `function_logs`, `function_run`, `run_function` |
| Events and automation | `emit_event`, `events`, `run_flow`, `run_schedule` |
| Stored definitions | `definitions`, `branches` |
| Runtime bridge | `runtime_call`, `identify`, `runtime_db` |

There are no dedicated Python methods for managing users, roles, organizations, secrets, firewall
rules, backups, alarms, mail templates, storage buckets, or API keys. Do not infer methods from
Studio's navigation or from another SDK.

## Function catalogue

`functions(branch=None)` returns functions visible to the environment. The response identifies
whether each one came from an active deployment, a feature branch, or mounted project code.

```python
items = production.functions()
branch_items = production.functions(branch="checkout-rewrite")
```

This is the programmatic counterpart to **Studio → Code → Functions**. Use it when a deployment
succeeded but invocation reports that a function is missing. The call is a retryable read; a missing
branch argument is omitted from the request.

## Creating a deployment

`deploy_functions()` uploads an already-built, base64-encoded `.tar.gz` archive. Most users should
run `pawabase deploy`, which checks and bundles a function directory first. The low-level method is
for CI systems that already produce the artifact.

```python
import base64
from pathlib import Path

archive = base64.b64encode(Path("functions.tar.gz").read_bytes()).decode("ascii")

deployment = production.deploy_functions(
    archive,
    branch="main",
    manifest={"source": "ci", "commit": "abc123"},
    runtime="python3.11",
    limits={"timeout": 30},
)
```

| Argument | Meaning | Default |
| --- | --- | --- |
| `archive` | Base64 text for a `.tar.gz` function bundle | Required |
| `branch` | Function branch to activate | `main` |
| `manifest` | Artifact metadata | `{}` |
| `runtime` | Runtime identifier | `python3.11` |
| `limits` | Deployment limit overrides accepted by the server | `{}` |

The SDK does not retry this write. If the connection breaks after upload begins, inspect deployment
history before deciding whether to send it again. That avoids creating a second deployment after an
ambiguous response.

<Tip>
Prefer `pawabase deploy --dry-run` before a release and `pawabase deploy` for the upload. Call
`deploy_functions()` directly only when your tooling already owns bundling and validation.
</Tip>

## Deployment history and activation

```python
recent = production.deployments(limit=20)
branch_recent = production.deployments(branch="checkout-rewrite", limit=20)
one = production.deployment("deployment_123")
```

| Method | Purpose |
| --- | --- |
| `deployments(branch=None, limit=50)` | List recent deployments, optionally for one branch |
| `deployment(deployment_id)` | Read one deployment and its status |
| `activate_deployment(deployment_id)` | Make an earlier deployment active again |
| `remove_deployment(deployment_id)` | Remove a deployment through the public management API |

Listing and lookup are retryable reads. Activation and removal are writes and are not retried.

```python
candidate = production.deployment("deployment_123")
if candidate.get("status") == "ready":
    production.activate_deployment(candidate["id"])
```

Activation is the SDK's rollback operation. It selects an existing deployment rather than building
a new archive. Confirm the result under **Studio → Code → Functions → Deployments**. Resolve the
exact id with `deployment()` before removing anything.

## Function branches versus definition branches

```python
code_branches = production.function_branches()
definition_branches = production.branches()
```

| Method | Domain |
| --- | --- |
| `function_branches()` | Deployed function artifacts |
| `branches()` | Environment definition branches |

`remove_function_branch("checkout-rewrite")` deletes code deployed on that function branch. It
does not delete main functions and does not remove an environment definition branch.

## Function runs and logs

`function_runs()` lists invocation records. `function_logs` is an alias of the same method, not a
different endpoint or response shape.

```python
runs = production.function_runs(
    function="price-order",
    branch="main",
    status="failed",
    limit=25,
)

later = production.function_runs(
    function="price-order",
    after="2026-10-24T00:00:00Z",
    limit=50,
)

run = production.function_run("run_123")
```

| Argument | Meaning |
| --- | --- |
| `function` | Restrict results to one function name |
| `branch` | Restrict results to one function branch |
| `status` | Restrict results to a server-supported status |
| `after` | Return runs after the supplied cursor or timestamp |
| `limit` | Maximum results requested; default `50` |

`None` and empty strings are omitted from the query. These methods are retryable reads and correspond
to **Studio → Code → Functions → Runs**. The client returns dictionaries; it does not expose a run
model, stream logs, or poll until completion.

## Public invocation and operator execution

Two methods execute functions through different trust paths.

| Method | Route | Meaning |
| --- | --- | --- |
| `invoke_function()` | `/functions/v1/<name>` | Public invocation under the function's policy |
| `run_function()` | Management route | Operator execution, optionally with `as_user` |

```python
public_result = production.invoke_function(
    "price-order",
    {"sku": "A1"},
)

operator_result = production.run_function(
    "price-order",
    {"sku": "A1"},
    branch="checkout-rewrite",
)
```

An operator can supply an auth context:

```python
result = production.run_function(
    "price-order",
    {"sku": "A1"},
    as_user={
        "user_id": "user_123",
        "email": "ada@example.com",
        "roles": ["customer"],
        "permissions": [],
    },
)
```

The mapping is operator-supplied context, not a user token and not a session verified by the client.
Use it only for deliberate testing or replay. The response contains a status and either a result or
an error; the SDK does not unwrap it.

## Events

`emit_event()` publishes an application event to the environment. Subscribers and event-triggered
flows listening for the name can run.

```python
production.emit_event(
    "order.paid",
    {"order_id": "order_123", "amount": 4200},
)

all_recent = production.events(limit=20)
paid = production.events("order.paid", limit=50)
```

| Method | Retry behavior |
| --- | --- |
| `emit_event(name, payload=None)` | Not retried; subscribers may already have run |
| `events(name=None, limit=20)` | Retried as a read |

The client does not validate payloads against a schema. Use stable event names and document payload
changes for subscribers. See [Events](/events/overview).

## Operator-triggered flows

`run_flow()` executes a flow through the management plane. This differs from `invoke_flow()`, which
uses the public pathless HTTP trigger.

```python
run = production.run_flow(
    "send-receipt",
    {"order_id": "order_123"},
)
```

An operator can select an entry node or provide an auth context:

```python
run = production.run_flow(
    "send-receipt",
    {"order_id": "order_123"},
    entry="load-order",
    as_user={"user_id": "user_123", "roles": ["customer"]},
)
```

| Argument | Meaning |
| --- | --- |
| `name` | Stored flow name |
| `input` | Flow input payload |
| `as_user` | Optional operator-supplied auth context |
| `entry` | Optional node id at which execution begins |

Starting at a non-default entry can bypass earlier validation or setup nodes. Use it for debugging,
not as the application's normal route. Inspect the result under **Studio → Flows → Runs**.

## Running a schedule now

```python
production.run_schedule("nightly-rollup")
```

`run_schedule(name)` fires an existing schedule as the scheduler would. It does not create, enable,
or edit a schedule. The write is not retried. A manual run can overlap with the ordinary scheduled
run, so check **Studio → Jobs** and the related flow runs before repeating it.

## Reading stored definitions

`definitions(kind, branch=None)` is a generic read for stored definition collections.

```python
flows = production.definitions("flows")
draft_routes = production.definitions("routes", branch="checkout-rewrite")
schedules = production.definitions("schedules")
subscriptions = production.definitions("subscriptions")
inbound_hooks = production.definitions("inbound-hooks")
```

The SDK does not validate `kind` against a local enum. Known examples include `routes`, `flows`,
`schedules`, `subscriptions`, and `inbound-hooks`. A misspelling reaches the server and fails there.
`main` is omitted as a branch query value.

`definitions()` is read-only. Python 0.2.0 has no generic definition `create`, `replace`, or `remove`
methods. Edit definitions in Studio or through another documented management interface.

## Remote runtime calls

`runtime_call()` invokes one `ctx.runtime` capability through the deployment's management bridge.
The key needs the `runtime:use` scope. Arguments and results use the function kit's codec format.

```python
order = production.runtime_call(
    "resource_get",
    args=["orders", "order_123"],
)

orders = production.runtime_call(
    "resource_list",
    args=["orders"],
    kwargs={"limit": 20, "sort": "-created_at"},
    branch="checkout-rewrite",
)
```

| Argument | Meaning |
| --- | --- |
| `method` | Runtime capability name |
| `args` | Positional values, defaulting to `[]` |
| `kwargs` | Named values, defaulting to `{}` |
| `as_user` | Optional operator-supplied auth context |
| `branch` | Optional deployed function branch |

This is a privileged bridge for the emulator and trusted tooling, not a replacement for ordinary
resource APIs. An unknown method fails on the server; the client has no local catalogue or result
model.

## Identifying a token

```python
auth = production.identify(access_token)
anonymous = production.identify(None)
```

`identify(token)` asks the deployed runtime what auth context a token represents. It is intended for
development tooling and the emulator. It does not create a managed session, refresh a token, or
change the client's credentials. Normal application authorization still belongs at the gateway.

## Runtime database bridge

`runtime_db(op, **fields)` sends `{"op": op, ...fields}` to the runtime database endpoint without a
typed operation model.

```python
rows = production.runtime_db(
    "query",
    sql="select id, status from orders where status = :status",
    params={"status": "paid"},
)
```

Use this only where the runtime contract requires it. For ordinary records, prefer `list`, `get`,
`create`, `update`, and `delete`. Raw SQL has a larger review and portability burden.

## Async management

Every method on this page is also present on `AsyncPawabase` and must be awaited:

```python
from pawabase import AsyncPawabase

async with AsyncPawabase(
    "https://api.example.com",
    "pb_sk_...",
    project="acme",
    environment="production",
) as pb:
    deployments = await pb.deployments(limit=10)
    failures = await pb.function_runs(status="failed", limit=20)
    events = await pb.events("order.failed", limit=20)
```

There is no separate async namespace and no prefix on method names. The endpoint implementation is
shared; only transport and awaiting behavior differ.

## Errors and retry boundaries

Management calls raise `PawabaseError`, not typed subclasses.

```python
from pawabase import PawabaseError

try:
    production.activate_deployment("deployment_123")
except PawabaseError as error:
    print(error.status_code, error.code, error.message)
    for problem in error.problems:
        print(problem)
    raise
```

`problems` is extracted specifically from a refused deployment response. For other failures it is
empty. Inspect `.detail` for the original decoded body.

These management reads opt into automatic retries: `functions`, `deployments`, `deployment`,
`function_branches`, `function_runs`, `function_run`, `events`, `definitions`, and `branches`.
Management writes are not replayed, although a `429` can still cause any method to wait and retry.

| Ambiguous write | Read before repeating |
| --- | --- |
| Function deployment | `deployments()` |
| Deployment activation | `deployment(id)` and `functions()` |
| Function execution | `function_runs()` |
| Event emission | `events(name)` and subscriber run history |
| Flow execution | **Studio → Flows → Runs** |
| Schedule execution | **Studio → Jobs** and flow run history |

## Methods that do not exist

The following calls are intentionally invalid in Python 0.2.0:

```python
pb.manage.secrets.set("STRIPE_KEY", "...")
pb.manage.firewall.ban("203.0.113.7")
pb.manage.backups.snapshot("before-launch")
pb.admin.users.create(email="ada@example.com")
pb.admin.roles.put("editor", ["posts:write"])
pb.admin.orgs.invite("acme", email="ada@example.com")
```

They are not shorthand for hidden methods. Use Studio or a separately documented public endpoint.
Do not guess routes from internal class names or Studio's network traffic; internal APIs are not a
supported application contract.

+## Operating decisions

Management methods matter most when an earlier write has an uncertain outcome.
The cases below describe the evidence to collect and the boundary that prevents a diagnostic action from becoming another production change.

<AccordionGroup>
  <Accordion title="A deployment upload lost its response">

The absence of an HTTP response does not tell you whether the server rejected the bundle, stored it, or activated it.

Start from deployment history for the same branch and compare creation time, manifest, and artifact identity.

`deployments(branch=...)` is safe to repeat because it is a read.

Do not upload again until history rules out the first artifact; duplicate deployments make later rollback choices harder to read.

**Code → Functions → Deployments** shows the same history in Studio.

```python
recent = production.deployments(branch="main", limit=10)
```

The deciding evidence is a matching deployment record, not whether the CI request reported success.

| Question | Answer |
| --- | --- |
| Does inspection mutate platform state? | No, when the named read method is used. |
| Does a lost write response prove failure? | No. Reconcile against the relevant history. |
| Does Studio change the SDK client scope? | No. The constructor remains authoritative. |

  </Accordion>

  <Accordion title="Production needs an earlier function artifact">

Rollback here means selecting an existing deployment, not reversing source control and building during the incident.

Read the candidate by id and confirm its status before calling `activate_deployment()`.

Activation is not automatically retried, because a lost response can still mean the selection changed.

Read `functions()` after activation to confirm which implementation resolves for main.

**Code → Functions → Deployments** exposes the candidate and the active selection.

```python
candidate = production.deployment("deployment_123")\nproduction.activate_deployment(candidate["id"])
```

Keep the source fix separate from the operational rollback so the incident action remains small.

| Question | Answer |
| --- | --- |
| Does inspection mutate platform state? | No, when the named read method is used. |
| Does a lost write response prove failure? | No. Reconcile against the relevant history. |
| Does Studio change the SDK client scope? | No. The constructor remains authoritative. |

  </Accordion>

  <Accordion title="A feature branch is no longer needed">

Function branches can outlive the code review that created them and continue to resolve when explicitly invoked.

List `function_branches()` and compare it with the team’s retained review branches before removal.

`remove_function_branch()` affects deployed code on that branch, not main and not stored definition branches.

A definition branch with the same name is independent and must be reviewed through `branches()`.

Use **Code → Functions** and the environment branch selector to inspect both domains.

```python
code = production.function_branches()\ndefinitions = production.branches()
```

The safe removal decision is based on both catalogues rather than a shared-looking name.

| Question | Answer |
| --- | --- |
| Does inspection mutate platform state? | No, when the named read method is used. |
| Does a lost write response prove failure? | No. Reconcile against the relevant history. |
| Does Studio change the SDK client scope? | No. The constructor remains authoritative. |

  </Accordion>

  <Accordion title="A function caller reported a failure">

A caller status without a run id is incomplete evidence in an environment where many invocations overlap.

Narrow `function_runs()` by function, branch, status, and time, then open the exact run.

The listing and single-run lookup are retryable reads and do not rerun the function.

Quote the selected run id in incident notes so another operator sees the same record.

Use **Code → Functions → Runs** for logs and the run result.

```python
failed = production.function_runs(function="price-order", status="failed", limit=20)
```

Do not use `run_function()` merely to discover the old error; that creates new execution.

| Question | Answer |
| --- | --- |
| Does inspection mutate platform state? | No, when the named read method is used. |
| Does a lost write response prove failure? | No. Reconcile against the relevant history. |
| Does Studio change the SDK client scope? | No. The constructor remains authoritative. |

  </Accordion>

  <Accordion title="An event backfill is required">

Event emission fans out to every matching subscription, flow, and webhook behavior in the environment.

Define the event window and downstream idempotency before calling `emit_event()` in a loop.

Emission is not retried after ordinary transport failure because the first attempt may already have published.

Use `events(name)` to reconcile history, then inspect each downstream run or delivery separately.

The **Events** panel establishes publication; subscriber panels establish processing.

```python
history = production.events("order.paid", limit=50)
```

An event record proves publication and never proves that all consumers completed successfully.

| Question | Answer |
| --- | --- |

| Does a lost write response prove failure? | No. Reconcile against the relevant history. |
| Does Studio change the SDK client scope? | No. The constructor remains authoritative. |

  </Accordion>

  <Accordion title="A flow must be inspected below its trigger">

The management runner can execute a flow without using its public HTTP, event, or schedule trigger.

Run from the normal entry when reproducing application behavior; a selected `entry` is a diagnostic shortcut.

Starting at a later node can omit validation and state normally produced by earlier nodes.

An `as_user` mapping is operator-supplied context, not proof of a real current session.

Inspect the result under **Flows → Runs** and record that the run was operator-triggered.

```python

```

A successful partial-entry run does not prove that the complete triggered flow succeeds.

| Does a lost write response prove failure? | No. Reconcile against the relevant history. |
| Does Studio change the SDK client scope? | No. The constructor remains authoritative. |

  </Accordion>

  <Accordion title="A schedule needs an immediate verification run">

Manual triggering answers whether existing scheduled work can run now without changing the stored cron expression.

Check recent jobs first because an ordinary scheduler run may already be active.

`run_schedule()` is a non-retried write; reconcile an ambiguous response through job and flow history.

Repeated manual runs are safe only when the scheduled workload itself is idempotent.

Use **Jobs → Schedules** for the definition and related run views for execution.

```python

```

The operator call triggers one run and does not enable, disable, or reschedule the definition.

| Question | Answer |

| Does a lost write response prove failure? | No. Reconcile against the relevant history. |
| Does Studio change the SDK client scope? | No. The constructor remains authoritative. |

  </Accordion>

  <Accordion title="The emulator needs a deployed capability">

The remote runtime bridge exists so local function code can use deployed resources, secrets, storage, and related capabilities.

Grant the narrow `runtime:use` scope and call the exact capability expected by the function kit.

`runtime_call()` can mutate state depending on the selected method, so it is never given ordinary read retries.

Codec values cross the bridge; do not assume arbitrary Python objects can be serialized.

Use the matching Studio panel to inspect the resulting resource, event, storage object, or other state.

```python
order = production.runtime_call("resource_get", args=["orders", "order_123"])
```

Application services should use their normal public API instead of adopting the emulator bridge.

## Studio perspective

Studio and the Python client are two views of the same selected environment, but they do not share
session state. A browser operator changing Studio's environment selector has no effect on a running
Python process. The script continues to use the `project` and `environment` passed to its constructor.

Before an operator automates a management call, the relevant evidence should be visible from a read
method or from the corresponding Studio panel.

| Intended change | Identity to resolve before writing | Evidence to retain afterwards |
| --- | --- | --- |
| Upload code | Function branch and artifact manifest | Deployment id and validation status |
| Activate code | Existing deployment id | Active function catalogue |
| Remove an artifact | Exact deployment id and retention need | Updated deployment history |
| Remove branch code | Exact function branch | Updated function branch list |
| Replay a function | Function name, branch, and input source | New run id |
| Emit an event | Event name and payload provenance | Event id or history record |
| Run a flow | Flow name, normal entry, and auth context | Flow run id |
| Run a schedule | Schedule name and overlap state | Job or flow run id |
| Call the runtime | Capability name, branch, and required scope | The affected domain record |

The table is an audit discipline rather than an SDK feature. The client sends the call you request;
it does not ask for interactive confirmation, attach a change ticket, or determine whether an input
was approved. Put those controls in the operator program or CI workflow that owns the client.

<Info>
The API key identifies the calling environment, while `as_user` changes only the simulated project
user context supplied to a function or flow. It does not turn the management request into that
user's request and does not reduce the secret key's authority at the gateway.
</Info>

| Python concern | Studio location |
| --- | --- |
| Function catalogue | **Code → Functions** |
| Deployment history | **Code → Functions → Deployments** |
| Function runs and logs | **Code → Functions → Runs** |
| Flow operator runs | **Flows → Runs** |
| Schedules | **Jobs → Schedules** |
| Events | **Events** |
| Definition branches | Environment branch selector |
| API key rotation | **Settings → API Keys** |

Studio is the safer starting point when an operator does not know an exact id or name. Resolve the
target there or with a read method, then automate the repeatable operation.
