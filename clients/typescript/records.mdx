A Pawabase resource is an application-facing data model with enabled operations, validation, policies, sorting, and optional relations.
The TypeScript SDK exposes it through `ResourceClient`.
The client does not turn the resource into a local collection; every terminal operation is a policy-checked API request.

The useful mental model is:

```text
ResourceClient chooses a resource and performs writes or direct reads.
QueryBuilder describes a list request without running it.
A terminal operation sends the request and returns policy-visible data.
```

In Studio, use the resource editor to confirm enabled operations, fields, relations, and access policies.
Use **API Explorer** to inspect the currently compiled request and response shapes.

## Obtain a resource client

`from(name)` uses the generated `Database` interface when the root client has one.
`resource<Row, Insert, Update>(name)` supplies types manually.

```typescript
const posts = client.from("posts");
```

```typescript
interface Post {
  id: number;
  title: string;
  status: "draft" | "live";
  views: number;
  published_at: string | null;
}

type NewPost = Pick<Post, "title" | "status">;
type PostPatch = Partial<Pick<Post, "title" | "status" | "published_at">>;

const posts = client.resource<Post, NewPost, PostPatch>("posts");
```

Manual types describe what the application expects.
They do not alter server validation.
Generated types reduce drift because they come from the environment's OpenAPI document.

## Read one record

`get(id)` expects a visible record and throws `NotFoundError` when the API returns `404`.
`maybeGet(id)` converts that same outcome to `null`.

```typescript
const post = await posts.get(42);
const optionalPost = await posts.maybeGet(42);
```

Use `get()` when absence is exceptional, such as loading an edit screen for a known ID.
Use `maybeGet()` when absence is part of normal control flow, such as resolving an optional slug mapping.

<Info>
  A `404` does not prove that no row exists.
  A read policy can hide an existing row and deliberately produce the same observable result.
  Do not use `maybeGet()` to infer administrative existence.
</Info>

Read options can request relation expansion and set request limits.

```typescript
const post = await posts.get(42, {
  expand: ["author", "comments"],
  timeoutMs: 8_000,
  signal: controller.signal,
});
```

Only declared relations can expand.
An expansion does not bypass the related resource's visibility rules.

## Create a record

`create(row)` sends the insert shape and returns the server representation.
The result includes server-assigned IDs, timestamps, and defaults that the read policy permits.

```typescript
const created = await posts.create({
  title: "Release notes",
  status: "draft",
});
```

Do not construct the final row locally from the input.
The server may normalize fields, apply defaults, generate IDs, or reject the body.

| Failure | Meaning for create |
| --- | --- |
| `ValidationError` | The body did not satisfy the compiled create schema |
| `AuthenticationError` | A required user identity or valid credential is absent |
| `PermissionError` | Key scope or create policy refused the operation |
| `ConflictError` | A unique constraint or current state conflicts with the insert |
| `PayloadTooLargeError` | The request exceeded an accepted body limit |

## Update, replace, and delete

The three mutation methods carry different intent.

| Method | HTTP meaning | Body | Result |
| --- | --- | --- | --- |
| `update(id, patch)` | `PATCH` | Changed fields | Updated row |
| `replace(id, row)` | `PUT` | Full insert/replacement shape | Replaced row |
| `delete(id)` | `DELETE` | None | `void` |

```typescript
const updated = await posts.update(42, {
  status: "live",
  published_at: new Date().toISOString(),
});

const replaced = await posts.replace(42, {
  title: "Replacement title",
  status: "draft",
});

await posts.delete(42);
```

`PATCH` accepts `null` at the transport layer for any field.
Whether the stored field can be null and whether application state remains valid are server concerns.
Generated update types can narrow normal use, but a stale type file is not a substitute for server validation.

## List records

`list(params)` is a direct object-style list call.
It suits code that already has a parameter object.

```typescript
const page = await posts.list({
  where: {
    status: "live",
    views: { gte: 100 },
  },
  sort: ["-published_at", "id"],
  select: ["id", "title", "published_at"],
  expand: ["author"],
  page: 1,
  perPage: 25,
  signal: controller.signal,
});
```

Chained queries express the same public list endpoint with an immutable builder.

```typescript
const page = await posts
  .eq("status", "live")
  .gte("views", 100)
  .order("published_at", "desc")
  .order("id", "asc")
  .select("id", "title", "published_at")
  .expand("author")
  .page(1)
  .perPage(25);
```

Choose the style that keeps application logic readable.
Both produce policy-filtered server results.

## Query builders are descriptions

A `QueryBuilder` is immutable and promise-like.
Each modifier returns a new builder.
Awaiting it runs `execute()`.

```typescript
const live = posts.eq("status", "live");

const recent = live.order("published_at", "desc").perPage(10);
const mostViewed = live.order("views", "desc").perPage(10);

const [recentPage, viewedPage] = await Promise.all([
  recent.execute(),
  mostViewed,
]);
```

No request occurs while the builders are assembled.
This makes it safe to build a base predicate once and derive UI-specific ordering or projection.

## Filter methods

Typed methods restrict the column name to known row fields when the resource has a row type.

| Method | Operator sent | Value shape | Typical meaning |
| --- | --- | --- | --- |
| `eq(column, value)` | `eq`, or `is` for boolean/null | Field value or `null` | Exact equality |
| `neq(column, value)` | `neq`, or `isnot` for boolean/null | Field value or `null` | Inequality |
| `gt(column, value)` | `gt` | Comparable scalar or date | Greater than |
| `gte(column, value)` | `gte` | Comparable scalar or date | Greater than or equal |
| `lt(column, value)` | `lt` | Comparable scalar or date | Less than |
| `lte(column, value)` | `lte` | Comparable scalar or date | Less than or equal |
| `like(column, pattern)` | `like` | String pattern | Pattern match |
| `ilike(column, pattern)` | `ilike` | String pattern | Case-insensitive match on PostgreSQL |
| `in(column, values)` | `in` | Array | Match any listed value |
| `notIn(column, values)` | `nin` | Array | Exclude listed values |
| `is(column, value)` | `is` | `null`, `true`, or `false` | Null or boolean identity |
| `isNot(column, value)` | `isnot` | `null`, `true`, or `false` | Negated identity |
| `filter(column, op, value)` | Explicit operator | Unknown | Dynamic filters when type-safe helpers do not fit |

```typescript
const results = await posts
  .ilike("title", "release%")
  .in("status", ["draft", "live"])
  .isNot("published_at", null)
  .order("published_at", "desc");
```

`*` and `%` both represent any run of characters for pattern matching.
Database behavior determines case sensitivity for `like`.
On PostgreSQL, `ilike` is case-insensitive; on other supported databases it behaves like `like`.

## `where()`

`where()` applies several field conditions in one object.
A scalar is equality.
An operator object names the comparison.

```typescript
const results = await posts.where({
  status: "live",
  views: { gte: 10 },
  published_at: { isnot: null },
});
```

The supported keys inside a condition object are `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `like`, `ilike`, `in`, `nin`, `is`, and `isnot`.

## One filter per field

The public list grammar represents filters by field name.
If the same field appears more than once, the server keeps only the final value.
Silently dropping one side of a range is dangerous, so the SDK throws `InvalidQueryError` instead.

```typescript
// Refused by the client: the second filter repeats created_at.
const range = posts
  .gte("created_at", start)
  .lte("created_at", end);
```

This limitation means a two-sided range on one field cannot be expressed with two ordinary list filters.
Model a period suitable for one supported predicate, expose a purpose-built custom route, or perform a broader read only when its data volume and policy behavior are acceptable.

<Warning>
  Do not fall back to manually constructing duplicate query-string keys and assume both will apply.
  The server-side grammar is the reason the SDK refuses the query.
</Warning>

## Boolean and null filters

The client maps equality with booleans and null to the identity operators that Pawabase expects.

```typescript
await posts.eq("featured", false);
await posts.eq("published_at", null);
await posts.neq("featured", true);
await posts.isNot("published_at", null);
```

This mapping prevents the incorrect string interpretation that a hand-built `eq.false` query can produce.
Use `is()` and `isNot()` when the intent should be explicit in application code.

## `in` and `notIn`

List values are serialized as a comma-separated filter value by the public API grammar.
The SDK refuses any member that itself contains a comma because it cannot be represented unambiguously.

```typescript
await posts.in("id", [10, 20, 30]);
```

An empty `in` array can never match.
The SDK returns an empty result locally instead of sending a request.
This is useful for code that consumes a possibly empty set of foreign IDs.

An empty `notIn` array excludes nothing.
Keep the condition out of the query when that is the intended behavior.

## Ordering

`order(column, direction)` appends a sort term.
Call it again for deterministic tie-breakers.
Direction defaults to ascending.

```typescript
const page = await posts
  .order("published_at", "desc")
  .order("id", "asc")
  .perPage(50);
```

Stable pagination needs a deterministic order.
If many rows share `published_at`, the `id` tie-breaker prevents ambiguous ordering between requests.
Without an explicit order, the resource's primary key is the default.

## Selection

`select(...columns)` requests a projection.
The primary key is always included.
Fields not selected still appear as `null` in returned rows, so the type becomes the selected fields plus a partial form of the original row.

```typescript
const page = await posts.select("id", "title");

for (const post of page.data) {
  console.log(post.id, post.title);
  // Other declared fields may be null because they were not selected.
}
```

Selection reduces payload size.
It is not an authorization mechanism.
Use field configuration, transformers, policies, or purpose-built routes to prevent sensitive data from being exposed.

## Relation expansion

`expand(...relations)` embeds declared `belongs_to` or `has_many` relations.

```typescript
const page = await posts
  .expand("author", "comments")
  .perPage(20);
```

Generated resource types do not automatically include expanded relation values.
Define an application type for a known expansion when static access is needed.

```typescript
type PostWithAuthor = Post & {
  author: Author | null;
};

const expanded = client
  .resource<PostWithAuthor, NewPost, PostPatch>("posts")
  .expand("author");
```

Expansion can increase query cost and payload size.
Request only the relations the view uses.

## Page response

Every list execution returns `Page<Row>`.

| Field | Type | Meaning |
| --- | --- | --- |
| `data` | `Row[]` | Visible rows on this page |
| `page` | `number` | One-based page number |
| `per_page` | `number` | Requested or effective page size |
| `total` | `number \| null` | Visible match count when it can be determined safely |

The default page size is 20.
The server accepts between 1 and 200 rows per page.
`limit(count)` is an alias for `perPage(count)`; it does not create an unpaged server query.

## Why `total` can be null

A per-row policy may require evaluating visibility record by record.
In that case the server cannot safely produce a complete count from a simple database count.
It returns `total: null` rather than a misleading number.

This also means a visible page may be short or empty even when later candidate rows exist.
Do not treat `data.length < per_page` as universally equivalent to end-of-results.

## Terminal query methods

Terminal methods run the request and express the expected result shape.

| Method | Result | Empty behavior |
| --- | --- | --- |
| `execute()` or `await builder` | `Page<Row>` | Page with empty `data` |
| `first()` | `Row \| null` | `null` |
| `single()` | `Row` | Throws `NotFoundError` |
| `count()` | `number` | `0`, or throws when count is unknowable |
| `exists()` | `boolean` | `false` |
| `pages()` | Async generator of `Page<Row>` | Ends according to iteration rules |
| `all()` | `Row[]` | Empty array |
| Async iteration | Rows one at a time | Ends according to iteration rules |

`single()` means “require a first matching record,” not “prove exactly one record exists.”
Use a unique field or ID when uniqueness is an application requirement.

## Count and policy visibility

`count()` reads the page total.
It throws when the server returns `total: null` because returning a partial or guessed count would be incorrect.

```typescript
try {
  const visibleCount = await posts.eq("status", "live").count();
  renderCount(visibleCount);
} catch (error) {
  renderCountUnavailable();
}
```

If the application truly needs the number of visible rows and the dataset is bounded, use `all({ maxRecords })` and count the returned rows.
For large datasets, define a server-side route with the required policy and aggregation semantics instead of transferring every row.

## Multi-page iteration

`pages()` walks pages from the builder's current page.
`all()` collects rows into memory.
The builder itself is async iterable and yields rows lazily.

```typescript
for await (const page of posts.eq("status", "live").pages({
  pageSize: 100,
  maxRecords: 2_000,
})) {
  await indexPage(page.data);
}
```

```typescript
for await (const post of posts.eq("status", "live")) {
  await processPost(post);
}
```

| Iterate option | Default | Purpose |
| --- | --- | --- |
| `pageSize` | `100` | Rows requested per page, up to the server maximum of 200 |
| `maxRecords` | Unlimited | Hard cap on yielded or collected rows |
| `stopAfterEmptyPages` | `1` | Consecutive empty pages tolerated when `total` is unknown |
| `signal` | None | Caller cancellation |
| `timeoutMs` | Client default | Per-request timeout |

Set `maxRecords` for user-triggered exports and background jobs unless unbounded reads are explicitly intended.
`all()` holds every returned row in memory.
Prefer row or page iteration for large result sets.

## Unknown totals and empty pages

When `total` is known, the iterator can use it to determine completion.
When it is unknown, policy filtering can create an empty visible page before later visible rows.
The iterator stops after one empty page by default.

Increase `stopAfterEmptyPages` only when missing later rows is worse than the extra requests and the candidate dataset is bounded.

```typescript
const rows = await posts.all({
  pageSize: 200,
  maxRecords: 5_000,
  stopAfterEmptyPages: 3,
});
```

This option is not proof that every later row was found.
A purpose-built route is the better interface when complete policy-aware enumeration is a product requirement.

## Request options and cancellation

Use `withOptions()` to bind a signal or timeout to a builder.

```typescript
const controller = new AbortController();

const pending = posts
  .eq("status", "live")
  .withOptions({
    signal: controller.signal,
    timeoutMs: 5_000,
  })
  .all({ maxRecords: 500 });

controller.abort();
```

Caller cancellation produces `AbortError`.
An SDK deadline produces `TimeoutError`.
Keep those cases separate in UI logic: navigation cancellation normally needs no error message, while a timeout may need retry guidance.

## Bulk creation

`createMany(rows)` performs several ordinary creates with bounded concurrency.
It is not a database transaction.

```typescript
const result = await posts.createMany(inputs, {
  concurrency: 4,
  stopOnError: false,
  signal: controller.signal,
});

for (const row of result.created) {
  recordSuccess(row.id);
}

for (const failure of result.failed) {
  recordFailure(failure.index, failure.error);
}
```

| Result field | Meaning |
| --- | --- |
| `created` | Rows successfully created |
| `failed` | Original input index and error for each failed create |

With `stopOnError`, no new request starts after the first observed failure.
Requests already in flight may still complete.
The method therefore remains non-atomic.

<Warning>
  Do not use `createMany()` for an all-or-nothing business operation.
  Put that invariant in a custom route, function, or flow that owns transaction behavior, then call that public operation from the client.
</Warning>

## Retry implications for writes

`create()` and `update()` use methods that are not retried after ambiguous network and gateway failures by default.
That avoids creating or applying the same action twice when the server may have completed it before the connection failed.

`replace()` uses `PUT`, and `delete()` uses `DELETE`; these methods are treated as repeatable by the transport's default policy.
Application semantics still matter.
Observe returned IDs and design stable identifiers where repeated submission is possible.

## Policy-aware troubleshooting

| Symptom | Interpretation | Check |
| --- | --- | --- |
| `get()` returns `404` for a known ID | Missing row or read policy hides it | Resource read policy and current user/key |
| List returns fewer rows than expected | Policy filtering, filters, or pagination | **API Explorer**, policy context, `page`, and `per_page` |
| `total` is `null` | Per-row policy prevents safe count | Policy design and UI count requirement |
| `count()` throws | Same unknown-total condition | Use bounded enumeration or a custom aggregate route |
| Repeated field filter throws locally | Public grammar cannot represent both | Redesign query or add a route |
| Create returns `403` | Key scope or create policy refusal | Key scopes and resource create policy |
| Create returns `422` | Body schema failure | `ValidationError.issues` and API Explorer request schema |
| Expand fails or is absent | Relation not declared or not visible | Resource relations and related policy |
| TypeScript accepts a body the server rejects | Generated file is stale or runtime constraint is not represented | Regenerate types and inspect API Explorer |

## Scalar serialization

Filters and query parameters cross an HTTP boundary, so JavaScript values are serialized before the server evaluates them.

| Input | Wire representation | Decision |
| --- | --- | --- |
| `string` | String value | Preserve exact case unless the chosen operator changes comparison semantics |
| `number` | Decimal string | Avoid values outside JavaScript's safe integer range |
| `bigint` | Decimal string in record filters | Confirm the server field can represent it |
| `boolean` | `is.true` or `is.false` for equality helpers | Do not hand-build `eq.false` |
| `null` | `is.null` or `isnot.null` for equality helpers | Distinct from an omitted query value |
| `Date` | ISO 8601 string | Construct valid dates and be explicit about timezone |

```typescript
const after = new Date("2026-10-01T00:00:00Z");

const page = await client
  .from("events")
  .gte("created_at", after)
  .order("created_at", "asc");
```

An invalid `Date` cannot become a meaningful ISO value.
Validate dates at the application boundary instead of relying on a transport exception.

## Operator-looking strings remain data

A value that begins with text such as `gte.` or `eq.` remains an equality value when passed to `eq()` or as a scalar to `where()`.
The SDK encodes the operator separately from the value.

```typescript
await client
  .from("labels")
  .eq("value", "gte.10");
```

Do not concatenate a filter expression into the value parameter.
Choose the typed method or explicit `filter(column, op, value)`.

## Encoded resource names and identifiers

The client URL-encodes resource names and record identifiers.
An ID containing a slash remains one identifier rather than becoming another path segment.

```typescript
const document = await client
  .from("external documents")
  .get("tenant/audit/2026");
```

Encoding prevents accidental path changes.
It does not mean spaces or slashes are recommended resource names.
Stable lowercase resource names remain easier to operate and generate types for.

## Date-range alternatives

Because the public list grammar accepts one filter per field, an ordinary two-bound timestamp range cannot use both `gte` and `lt` on `created_at`.
Choose the alternative that matches the product requirement.

| Requirement | Interface |
| --- | --- |
| Everything after one instant | One `gte` filter |
| Everything before one instant | One `lt` filter |
| Named reporting period | Store or derive a period key and filter equality |
| Exact arbitrary range | Custom route with `from` and `to` parameters |
| Large export with aggregation | Server-side function or route |

```typescript
const report = await client.routes.get("reports/orders", {
  query: {
    from: start,
    to: end,
  },
});
```

A custom route can validate both boundaries and execute one server-side query without weakening record policy rules.

## Query factories

Immutable builders make it practical to centralize predicates that every application view must include.

```typescript
function accountPosts(accountId: string) {
  return client
    .from("posts")
    .eq("account_id", accountId);
}

const drafts = await accountPosts(accountId)
  .eq("status", "draft")
  .order("updated_at", "desc");
```

Do not treat a client-side tenant predicate as the security boundary.
It improves correctness and index use, while a server policy must independently enforce tenant visibility.

## `first()`, `single()`, and `exists()` cost

These terminal helpers request a page of one rather than downloading a full page.

| Helper | Use | Important limitation |
| --- | --- | --- |
| `first()` | Optional match | Default or explicit order decides which row |
| `single()` | Required match | Does not prove that only one row matches |
| `exists()` | Boolean existence check | A read policy can turn an existing hidden row into `false` |

```typescript
const latest = await client
  .from("posts")
  .eq("status", "live")
  .order("published_at", "desc")
  .first();
```

Always supply an order when “first” has domain meaning.

## Selection and application caches

Selected-out fields can appear as `null`.
Do not merge a projected row into a cache as though it were a complete replacement.

```typescript
const summary = await client
  .from("posts")
  .select("id", "title")
  .single();

summaryCache.set(summary.id, summary);
```

Keep summary and detail cache shapes separate, or record which fields were selected.
Otherwise a summary request can overwrite previously cached detail fields with projection nulls.

## Expansion ownership

An expanded response can combine one parent row with zero, one, or many related rows depending on the declared relation.
Keep expanded types query-specific.

```typescript
type PostDetail = Post & {
  author: Author | null;
  comments: Comment[];
};

const detail = client.resource<PostDetail>("posts");
const post = await detail
  .eq("id", postId)
  .expand("author", "comments")
  .single();
```

The generic is an application assertion.
Validate and test it after relation-definition changes.

## Concurrent writes

The SDK does not add optimistic concurrency headers to ordinary resource mutations.
Two callers can both read a row and later write competing updates.

Use a custom route when the domain needs compare-and-set behavior, version checks, or a transaction spanning records.

```typescript
await client.routes.patch(
  `documents/${encodeURIComponent(id)}/publish`,
  {
    expected_version: version,
  },
);
```

Map the route's conflict response to `ConflictError` and prompt the user to reload or reconcile.

## Bulk-create ordering

`createMany()` preserves useful source correlation through `failed[index]`.
Successful network requests can finish in a different order when concurrency is greater than one.
Use stable application identifiers when downstream work must restore source ordering.

```typescript
const inputs = csvRows.map((row, sourceIndex) => ({
  import_key: `${importId}:${sourceIndex}`,
  title: row.title,
}));

const result = await client
  .from("posts")
  .createMany(inputs, {
    concurrency: 6,
  });
```

The method reports partial failure; it does not roll back prior successes.
Persist an import key or reconciliation record if the job may resume.

## Read-after-write visibility

A successful create or update returns the server row for that operation.
A later list can omit it when list policy differs from create/update policy or when the query excludes the new values.

Do not assume a successful write guarantees membership in every cached list.
Use the returned row for immediate confirmation, then refetch the relevant policy-scoped query when list truth matters.

## Resource-operation enablement

The existence of a typed SDK method does not mean the resource enables that operation.
`ResourceClient` has a stable API for every resource; the environment decides which endpoints exist and which policies permit them.

| SDK call | Resource setting to verify |
| --- | --- |
| List/query | List operation enabled and read/list policy |
| `get`, `maybeGet` | Retrieve operation enabled and read policy |
| `create`, `createMany` | Create operation enabled and create policy |
| `update` | Update operation enabled and update policy |
| `replace` | Replacement operation support and policy |
| `delete` | Delete operation enabled and delete policy |

Use **API Explorer** to see the currently compiled operations.
Generated types describe shapes; they do not remove disabled-operation failures.

## Testing record integration

Unit tests can assert application query construction through a fake `fetch`.
Policy behavior requires a real environment.

Test at least these boundary cases for a policy-sensitive resource:

- anonymous list when authentication is required;
- owner reading their row;
- owner unable to read another user's row;
- owner unable to update another user's row;
- validation failure before policy-relevant persistence;
- hidden record returning `404` or `null` through `maybeGet()`;
- unknown `total` behavior when the policy cannot be pushed down;
- a deterministic secondary order for paged results.

See [server runtimes and testing](/clients/typescript/server-runtimes-testing) for transport fakes and cleanup.

## Security decisions

Types are not access control.
Selections are not field-level secrecy.
Client-side filters are not tenant isolation.
An ID hidden by `maybeGet()` is not proven absent.

Put tenant boundaries and record visibility in Pawabase policies.
Use a publishable key in untrusted applications.
Use a secret client only in controlled server code and only when policy bypass is intentional.
