Records are the rows of a resource, read and written through the data API under the resource's policies.
In the client, `pawabase.from("orders")` is the doorway to them.

This page explains how the client models a resource and a query, what each method sends and what the server does with it, and how to handle the cases that surprise people: hidden records, unknown totals, short pages, partial updates and bulk writes.

## The mental model

Three objects are involved in every records call, and keeping them apart makes the API predictable.

| Object | Created by | What it is | Sends a request? |
| --- | --- | --- | --- |
| Resource client | `pawabase.from("orders")` | A handle on one resource, with single-record methods and query starters | Only when you call a single-record method |
| Query | `orders.eq(…)`, `orders.order(…)`, `orders.query()` | An immutable description of a list request | No; it is a value |
| Terminal operation | `await query`, `first()`, `count()`, `all()`, `for await` | The moment the description becomes one or more HTTP requests | Yes |

A resource client is cheap and stateless; create one wherever it is convenient.
A query is a value you can store, share and refine; refining returns a new query and leaves the original untouched.
Only terminal operations touch the network.

<CodeGroup>
```typescript TypeScript
const orders = pawabase.from("orders");

const open = orders.eq("status", "open");          // a query, no request
const bigOpen = open.gte("total_minor", 10_000);   // another query; `open` is unchanged
const newestFirst = bigOpen.order("created_at", "desc");

const page = await newestFirst.perPage(20);        // one request
const count = await open.count();                  // another request
```

```python Python
orders = pb.from_("orders")

open_ = orders.eq("status", "open")                 # a query, no request
big_open = open_.gte("total_minor", 10_000)         # another query; open_ is unchanged
newest_first = big_open.order("created_at", "desc")

page = newest_first.per_page(20).execute()          # one request
count = open_.count()                               # another request
```

```bash cURL
curl -G "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "filter[status]=eq.open" --data-urlencode "filter[total_minor]=gte.10000" \
  --data-urlencode "sort=-created_at" --data-urlencode "per_page=20"

curl -G "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" --data-urlencode "filter[status]=eq.open" --data-urlencode "per_page=1"   # count: read "total"
```
</CodeGroup>

Under every terminal operation is one HTTP request to `/rest/v1/<resource>`, or several for operations that walk pages.
The server applies the operation's policy to each request.
What you get back is what this caller may see, never more.

## Where resources come from

A resource is defined in Studio under **Data**.
Each resource has fields, an optional set of relations, and five operations: `list`, `get`, `create`, `update` and `delete`.
Each operation can be turned off, and each has its own policy.

| Client call | Operation | HTTP request |
| --- | --- | --- |
| `await query`, `first()`, `count()`, `all()`, `pages()` | `list` | `GET /rest/v1/<resource>?…` |
| `get(id)`, `maybeGet(id)` | `get` | `GET /rest/v1/<resource>/<id>` |
| `create(row)`, `createMany(rows)` | `create` | `POST /rest/v1/<resource>` |
| `update(id, patch)`, `replace(id, row)` | `update` | `PATCH` or `PUT /rest/v1/<resource>/<id>` |
| `delete(id)` | `delete` | `DELETE /rest/v1/<resource>/<id>` |

When an operation is turned off, its route does not exist, and the client gets `404` (or `405` for a method on an existing path).
When it is on, its policy decides.
The default policy is the built-in `authenticated`, which admits any signed-in user and refuses anonymous callers.

Before you write client code for a resource, open it under **Data** and look at three things: which operations are on, what each one's policy is, and which fields are required.
Then open **Data → API Explorer**, which shows the compiled routes of this environment with their exact parameters, request bodies and example responses.
The Explorer is the ground truth for what the client can send.

## Getting a resource client

`from(name)` returns a resource client typed from your generated `Database` type.
Without a generated type, rows are `Record<string, unknown>`.

```typescript
import { createClient } from "@pawabase/client";
import type { Database } from "./database";

const pawabase = createClient<Database>({ url, apiKey });
const orders = pawabase.from("orders");
// orders.create() now accepts Insert<"orders">, and rows are Row<"orders">.
```

`resource<Row, Insert, Update>(name)` is the same, typed by hand.
Use it for a resource your application-level `Database` interface does not describe yet, or in an untyped project.

```typescript
interface Order {
  id: string;
  customer_id: string;
  status: "open" | "paid" | "cancelled";
  total_minor: number;
  note: string | null;
  created_at: string;
  updated_at: string;
}

type NewOrder = Pick<Order, "customer_id" | "total_minor"> & Partial<Pick<Order, "status" | "note">>;
type OrderPatch = Partial<Pick<Order, "status" | "note" | "total_minor">>;

const orders = pawabase.resource<Order, NewOrder, OrderPatch>("orders");
```

Hand-written types describe what your code expects.
They do not change what the server validates.
When they drift from the resource definition, the compiler stays quiet and the server answers `422`.
Keep application-owned row interfaces aligned with resource definitions to avoid that drift.

The resource name is used as a path segment and encoded for you.
Names are the resource names shown under **Data**, which are lowercase with underscores.

## Reading one record

`get(id)` reads one record by its primary key.

<CodeGroup>
```typescript TypeScript
const order = await orders.get("01JB8Z3T6K9Q");
```

```python Python
order = orders.get("01JB8Z3T6K9Q")
```

```bash cURL
curl "$PAWABASE_URL/rest/v1/orders/01JB8Z3T6K9Q" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN"
```
</CodeGroup>

It throws `NotFoundError` in three situations that the server deliberately does not distinguish:

| Situation | Server answer |
| --- | --- |
| No record has this id | `404` |
| The record exists, but the `get` policy refuses this caller | `404` |
| The record exists, but a policy filter (such as an owner condition) excludes it | `404` |

The server answers `404` for a hidden record so that a caller cannot discover which ids exist.
Your code should treat "not found" and "not yours" the same way, because from the caller's side they are the same.

`maybeGet(id)` returns `null` instead of throwing for those cases, and rethrows every other error.

<CodeGroup>
```typescript TypeScript
const order = await orders.maybeGet(orderId);
if (!order) return notFoundPage();
```

```python Python
order = orders.maybe_get(order_id)
if order is None:
    return not_found_page()
```

```bash cURL
curl -i "$PAWABASE_URL/rest/v1/orders/$ORDER_ID" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN"   # 404 for "missing" and "hidden" alike
```
</CodeGroup>

Use `get` when absence is an error, such as loading a record whose id came from your own list a moment ago.
Use `maybeGet` when absence is a normal outcome, such as an id from a URL that a user may have typed.

Both accept `expand`, to embed related records in the same request:

<CodeGroup>
```typescript TypeScript
const order = await orders.get(orderId, { expand: ["customer", "items"] });
```

```python Python
order = orders.get(order_id, expand=["customer", "items"])
```

```bash cURL
curl "$PAWABASE_URL/rest/v1/orders/$ORDER_ID?expand=customer,items" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN"
```
</CodeGroup>

And both accept `signal` and `timeoutMs`:

```typescript
const controller = new AbortController();
const order = await orders.get(orderId, { signal: controller.signal, timeoutMs: 5000 });
```

## Creating a record

`create(row)` sends `POST /rest/v1/<resource>` and returns the created row.
The server answers `201` with the record as it was stored, including the fields it assigned.

<CodeGroup>
```typescript TypeScript
const order = await orders.create({ customer_id: "c_42", total_minor: 4200 });
console.log(order.id, order.status, order.created_at);
```

```python Python
order = orders.create({"customer_id": "c_42", "total_minor": 4200})
print(order["id"], order["status"], order["created_at"])
```

```bash cURL
curl -X POST "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"customer_id": "c_42", "total_minor": 4200}'
# HTTP/1.1 201 with the stored record
```
</CodeGroup>

What the returned row contains that your input did not:

| Field | Comes from |
| --- | --- |
| The primary key | Generated by the server: an integer, a UUID or a ULID, depending on the resource |
| `created_at`, `updated_at` | Set by the server when the resource has timestamps |
| Fields with defaults | The default declared on the field, when you did not send a value |
| The owner field | Set to the signed-in user's id when the resource declares one |

The owner field deserves attention.
When a resource names an owner field, the server sets it to the caller's user id on every create and ignores what you sent.
An anonymous caller with a publishable key cannot create a record in such a resource; the server answers `401`.
A secret-key caller can, and must then set the owner explicitly if one is wanted.

The server validates the body against the resource's fields before the policy runs:

| You send | Server answer |
| --- | --- |
| A missing required field without a default | `422`, one issue per field |
| A value of the wrong type | `422` |
| A value outside a field's constraints (length, range, pattern, enum) | `422` |
| A field the resource does not declare | `422` |
| A read-only field | `422`; read-only fields cannot be written |
| A valid body the `create` policy refuses | `403` (or `401` when signed out) |
| A value that breaks a unique field | `409` with code `unique_violation` and `details.columns` |
| A value that breaks another database constraint | `422` with code `constraint_violation` |

The client turns these into `ValidationError`, `PermissionError`, `AuthenticationError` and `ConflictError`, so form code reads naturally:

<CodeGroup>
```typescript TypeScript
import { ConflictError, ValidationError } from "@pawabase/client";

try {
  await pawabase.from("customers").create({ email, name });
} catch (error) {
  if (error instanceof ValidationError) return { fieldErrors: error.byField() };
  if (error instanceof ConflictError) return { fieldErrors: { email: ["An account with this email exists."] } };
  throw error;
}
```

```python Python
from pawabase import ConflictError, ValidationError

try:
    pb.from_("customers").create({"email": email, "name": name})
except ValidationError as error:
    return {"field_errors": error.detail}
except ConflictError as error:
    return {"field_errors": {column: ["An account with this email exists."] for column in (error.details or {}).get("columns", [])}}
```

```bash cURL
curl -i -X POST "$PAWABASE_URL/rest/v1/customers" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"email": "ada@example.com", "name": "Ada"}'
# 409 {"error": "unique_violation", "message": "A record with the same email already exists.", "details": {"columns": ["email"]}}
```
</CodeGroup>

Validation runs before the policy.
An anonymous request with an invalid body gets `422`, not `401`.
Do not read a `422` as "this caller would have been allowed".

## Updating a record

`update(id, patch)` sends `PATCH` with only the fields you pass.
Fields you leave out keep their values.

<CodeGroup>
```typescript TypeScript
const paid = await orders.update(orderId, { status: "paid" });
```

```python Python
paid = orders.update(order_id, {"status": "paid"})
```

```bash cURL
curl -X PATCH "$PAWABASE_URL/rest/v1/orders/$ORDER_ID" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"status": "paid"}'
```
</CodeGroup>

The server reads the existing record first, then checks the `update` policy against it.
That order produces a specific set of answers:

| Situation | Server answer |
| --- | --- |
| No record has this id | `404` |
| The policy refuses an anonymous caller | `404` |
| The policy refuses a signed-in caller | `403` |
| The patch sets a non-nullable field to `null` | `422` |
| The patch contains an undeclared or read-only field | `422` |
| The patch breaks a unique field | `409` |

Notice the asymmetry between anonymous and signed-in refusals.
A signed-out caller learns nothing about whether the record exists; a signed-in caller is told they may not change it.

The owner field cannot be changed through `update`.
The server drops it from the patch silently, so a record cannot be handed to another user through the data API.
If your application needs ownership transfer, do it in a flow or route that checks the rules you want.

### Setting a field to null

`null` and "not sent" mean different things in a patch.
Leaving a field out keeps its value; sending `null` clears it, if the field allows `null`.

<CodeGroup>
```typescript TypeScript
await orders.update(orderId, { note: null });  // clears the note
await orders.update(orderId, {});              // changes nothing; returns the record
```

```python Python
orders.update(order_id, {"note": None})   # clears the note
orders.update(order_id, {})               # changes nothing; returns the record
```

```bash cURL
curl -X PATCH "$PAWABASE_URL/rest/v1/orders/$ORDER_ID" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"note": null}'
```
</CodeGroup>

A field accepts `null` when it is declared nullable, or when it is not required.
A required field is not nullable unless the definition says so, and a patch that sends `null` for it is refused with `422`.

## Replacing a record

`replace(id, row)` sends `PUT`.
On Pawabase, `PUT` is handled exactly like `PATCH`: fields you leave out keep their values.
The method exists for code that prefers `PUT` semantics on the wire, not to clear unspecified fields.

<CodeGroup>
```typescript TypeScript
await orders.replace(orderId, { customer_id: "c_42", total_minor: 5000, status: "open", note: null });
```

```python Python
orders.replace(order_id, {"customer_id": "c_42", "total_minor": 5000, "status": "open", "note": None})
```

```bash cURL
curl -X PUT "$PAWABASE_URL/rest/v1/orders/$ORDER_ID" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" \
  -d '{"customer_id": "c_42", "total_minor": 5000, "status": "open", "note": null}'
```
</CodeGroup>

To clear a field, send it as `null`.
To return a record to defaults, send the default values explicitly.

`PUT` is also not listed in the OpenAPI document; the API Explorer shows `PATCH` for updates.
Prefer `update` in new code.

## Deleting a record

`delete(id)` sends `DELETE` and resolves with nothing.

<CodeGroup>
```typescript TypeScript
await orders.delete(orderId);
```

```python Python
orders.delete(order_id)
```

```bash cURL
curl -X DELETE "$PAWABASE_URL/rest/v1/orders/$ORDER_ID" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN"   # 204
```
</CodeGroup>

| Situation | Server answer |
| --- | --- |
| Deleted | `204` |
| No record has this id | `404` |
| The policy refuses an anonymous caller | `404` |
| The policy refuses a signed-in caller | `403` |

A `DELETE` is safe to repeat, so the client retries it after a network failure or a gateway error.
If the first attempt deleted the record before the connection failed, the retry gets `404`.
Treat `NotFoundError` from `delete` as success when your goal is "the record is gone":

<CodeGroup>
```typescript TypeScript
import { NotFoundError } from "@pawabase/client";

async function ensureDeleted(id: string) {
  try {
    await orders.delete(id);
  } catch (error) {
    if (!(error instanceof NotFoundError)) throw error;
  }
}
```

```python Python
from pawabase import NotFoundError

def ensure_deleted(record_id: str) -> None:
    try:
        orders.delete(record_id)
    except NotFoundError:
        pass
```
</CodeGroup>

Deleting a record does not delete records that refer to it.
Pawabase does not enforce referential integrity between resources, so a deleted customer leaves its orders behind, and expanding `customer` on those orders gives `null`.
Clean up related records in a flow triggered by the delete event, or in your own code.

## Building a query

A query describes one list request.
You start one from a resource client with any filter or shape method, or with `query()`.

```typescript
const q1 = orders.eq("status", "open");
const q2 = orders.order("created_at", "desc");
const q3 = orders.query();
```

Every method returns a new query.
The original is never changed, which makes this safe:

```typescript
const base = orders.eq("customer_id", customerId);

const [open, paid] = await Promise.all([
  base.eq("status", "open").perPage(50),
  base.eq("status", "paid").perPage(50),
]);
```

### Comparison filters

| Method | Wire operator | Matches rows where the column |
| --- | --- | --- |
| `eq(column, value)` | `eq` | equals the value |
| `neq(column, value)` | `neq` | does not equal the value |
| `gt(column, value)` | `gt` | is greater than the value |
| `gte(column, value)` | `gte` | is greater than or equal to the value |
| `lt(column, value)` | `lt` | is less than the value |
| `lte(column, value)` | `lte` | is less than or equal to the value |

<CodeGroup>
```typescript TypeScript
await orders.gte("total_minor", 10_000).perPage(20);
await orders.lt("created_at", new Date("2026-10-01T00:00:00Z")).perPage(20);
```

```python Python
from datetime import datetime, timezone

orders.gte("total_minor", 10_000).per_page(20).execute()
orders.lt("created_at", datetime(2026, 10, 1, tzinfo=timezone.utc)).per_page(20).execute()
```

```bash cURL
curl -G "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" --data-urlencode "filter[total_minor]=gte.10000" --data-urlencode "per_page=20"
curl -G "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" --data-urlencode "filter[created_at]=lt.2026-10-01T00:00:00Z" --data-urlencode "per_page=20"
```
</CodeGroup>

Values are sent as text.
Numbers and bigints are written in decimal, booleans as `true` or `false`, and `Date` objects as ISO 8601 strings in UTC.

### Pattern filters

| Method | Wire operator | Behavior |
| --- | --- | --- |
| `like(column, pattern)` | `like` | Pattern match; `*` and `%` match any run of characters |
| `ilike(column, pattern)` | `ilike` | Case-insensitive on PostgreSQL; the same as `like` on other databases |

<CodeGroup>
```typescript TypeScript
await pawabase.from("customers").ilike("email", "*@example.com").perPage(50);
await pawabase.from("products").like("sku", "SHOE-%").perPage(50);
```

```python Python
pb.from_("customers").ilike("email", "*@example.com").per_page(50).execute()
pb.from_("products").like("sku", "SHOE-%").per_page(50).execute()
```

```bash cURL
curl -G "$PAWABASE_URL/rest/v1/customers" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" --data-urlencode "filter[email]=ilike.*@example.com" --data-urlencode "per_page=50"
```
</CodeGroup>

Whether `like` ignores case depends on the database and its collation.
Use `ilike` when you mean case-insensitive, and remember it is only guaranteed on PostgreSQL.

### List filters

| Method | Wire operator | Matches rows where the column |
| --- | --- | --- |
| `in(column, values)` | `in` | equals any of the values |
| `notIn(column, values)` | `nin` | equals none of the values |

<CodeGroup>
```typescript TypeScript
await orders.in("status", ["open", "paid"]).perPage(50);
await orders.notIn("customer_id", blockedCustomerIds).perPage(50);
```

```python Python
orders.in_("status", ["open", "paid"]).per_page(50).execute()
orders.not_in("customer_id", blocked_customer_ids).per_page(50).execute()
```

```bash cURL
curl -G "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" --data-urlencode "filter[status]=in.open,paid" --data-urlencode "per_page=50"
curl -G "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" --data-urlencode "filter[customer_id]=nin.c_1,c_2" --data-urlencode "per_page=50"
```
</CodeGroup>

The server splits list values on commas.
A value that contains a comma would be split into two values and match the wrong rows, so the client throws `InvalidQueryError` before sending it.

An empty list is handled locally.
`in(column, [])` matches nothing, so the client returns an empty page without a request.
`notIn(column, [])` excludes nothing, so the client drops the filter.

### Null and boolean filters

| Method | Wire operator | Matches rows where the column |
| --- | --- | --- |
| `is(column, null)` | `is.null` | is null |
| `isNot(column, null)` | `isnot.null` | is not null |
| `is(column, true)` | `is.true` | is true |
| `is(column, false)` | `is.false` | is false |
| `isNot(column, true)` | `isnot.true` | is not true |

Booleans and nulls need these operators.
The server's `eq` does not handle them correctly: `filter[done]=eq.false` matches rows where `done` is true.
The client protects you by rewriting `eq(column, false)` as `is.false`, `eq(column, null)` as `is.null`, and the same for `neq`.
You can use `eq` with booleans in your code and get the right result.

<CodeGroup>
```typescript TypeScript
await todos.eq("done", false).perPage(50);   // sent as filter[done]=is.false
await todos.is("archived_at", null).perPage(50);
```

```python Python
todos.eq("done", False).per_page(50).execute()       # sent as filter[done]=is.false
todos.is_("archived_at", None).per_page(50).execute()
```

```bash cURL
curl -G "$PAWABASE_URL/rest/v1/todos" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" --data-urlencode "filter[done]=is.false"
curl -G "$PAWABASE_URL/rest/v1/todos" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" --data-urlencode "filter[archived_at]=is.null"
```
</CodeGroup>

Passing `null` to a comparison such as `gt` throws `InvalidQueryError`, because "greater than null" has no meaning.

### Several filters at once

`where(conditions)` adds several filters from an object.
A plain value means equality; an object with one operator means that operator.

<CodeGroup>
```typescript TypeScript
await orders
  .where({
    status: "open",
    total_minor: { gte: 10_000 },
    note: null,
  })
  .perPage(20);
```

```python Python
orders.where(status="open", total_minor={"gte": 10_000}, note=None).per_page(20).execute()
```

```bash cURL
curl -G "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" --data-urlencode "filter[status]=eq.open" \
  --data-urlencode "filter[total_minor]=gte.10000" --data-urlencode "filter[note]=is.null" --data-urlencode "per_page=20"
```
</CodeGroup>

| Condition | Becomes |
| --- | --- |
| `status: "open"` | `eq("status", "open")` |
| `total_minor: { gte: 10000 }` | `gte("total_minor", 10000)` |
| `note: null` | `is("note", null)` |
| `paid: false` | `is("paid", false)` |
| `status: { in: ["open", "paid"] }` | `in("status", ["open", "paid"])` |
| `total_minor: { gte: 1, lte: 9 }` | Throws `InvalidQueryError`: two operators on one field |

`where` is convenient for filters that arrive as data, such as from a URL's query string or a saved view.

### The one-filter-per-field rule

The server applies one filter per field.
When a request filters the same field twice, the server keeps the last one and drops the others without an error.
A query such as "created between two dates" written as two filters would therefore return everything after the first date, silently ignoring the upper bound.

The client refuses to build such a query:

<CodeGroup>
```typescript TypeScript
orders.gte("created_at", start).lte("created_at", end);
// InvalidQueryError: There is already a filter on "created_at"…
```

```python Python
orders.gte("created_at", start).lte("created_at", end)
# QueryError: There is already a filter on "created_at"…
```

```bash cURL
# On the wire the second filter replaces the first; the server keeps only the last:
#   ?filter[created_at]=gte.2026-09-01&filter[created_at]=lte.2026-09-30   → only lte applies
```
</CodeGroup>

There are four honest ways to express a two-sided range:

| Approach | When to use it |
| --- | --- |
| Filter one bound on the server and the other in code | The result is small after the first bound. |
| Store a coarser field, such as `created_month`, and filter with `eq` | Ranges align with calendar periods. |
| Use a custom route backed by a flow | The range is common and the data is large. |
| Use pagination with an ordered single bound and stop when you pass the other | You are walking results in order anyway. |

The last approach is often the cleanest:

<CodeGroup>
```typescript TypeScript
const rows = [];
for await (const order of orders.gte("created_at", start).order("created_at")) {
  if (order.created_at >= end.toISOString()) break;
  rows.push(order);
}
```

```python Python
rows = []
for order in orders.gte("created_at", start).order("created_at").iterate():
    if order["created_at"] >= end.isoformat():
        break
    rows.append(order)
```
</CodeGroup>

### Filters on other fields of your rows only

Filters apply to the resource's own columns.
There is no filter on a related record's field, such as "orders whose customer's country is GH".
Store the value you need to filter on in the resource itself, or write a custom route.

## Shaping the result

### Sorting

`order(column, direction)` sorts by a column, ascending by default.

<CodeGroup>


### Selecting columns

`select(...columns)` asks for only some columns.

<CodeGroup>

## When the total is unknown

Some policies can be turned into a database filter, such as "the owner is the caller".
Others can only be decided by looking at each row, such as a condition that compares two fields of the record.
When a `list` policy has a per-row part, the server reads a page of rows from the database, then removes the rows the caller may not see.

That has three consequences you must design for:

| Consequence | Why |
| --- | --- |
| `total` is `null` | The database's count includes rows the caller may not see. |
| A page can have fewer rows than `per_page` | Some rows of the page were removed. |
| A page can be empty while later pages have rows | All rows of that page were removed. |

Code that stops at the first short page, or computes the number of pages from `total`, will stop early or crash.
The client's iteration helpers handle this case: when `total` is `null`, they keep fetching until they see an empty page, or a number of empty pages in a row that you choose.

<CodeGroup>
```typescript TypeScript
const all = await orders.all({ stopAfterEmptyPages: 3 });
```

```python Python
# The Python client stops at the first page shorter than per_page when the total is unknown.
# Walk explicitly when a per-row policy can make pages short:
rows, page_number, empty = [], 1, 0
while empty < 3:
    page = orders.page(page_number).per_page(100).execute()
    rows.extend(page.data)
    empty = empty + 1 if not page.data else 0
    page_number += 1
```
</CodeGroup>

`count()` cannot answer when `total` is `null`, and it throws `InvalidQueryError` instead of guessing.
If you need a count in that case, fetch the rows and count them, or rewrite the policy so it can be pushed into the database.
The [policy pushdown](/policies/pushdown) page explains which conditions become database filters.

## Terminal operations

| Operation | Requests | Returns |
| --- | --- | --- |
| `await query` or `query.execute()` | One | One page: `{ data, page, per_page, total }` |
| `first()` | One, with `per_page=1` | The first row, or `null` |
| `single()` | One, with `per_page=1` | The first row; throws `NotFoundError` when there is none |
| `exists()` | One, with `per_page=1` | `true` or `false` |
| `count()` | One, with `per_page=1` | The total; throws when it is unknown |
| `pages(options)` | One per page | An async iterator of pages |
| `all(options)` | One per page | Every row, as an array |
| `for await (const row of query)` | One per page, lazily | Rows one at a time |

`first()` and `single()` use the query's order.
Without an order, "first" means lowest primary key.

<CodeGroup>
```typescript TypeScript
const latest = await orders.eq("customer_id", customerId).order("created_at", "desc").first();
```

```python Python
latest = orders.eq("customer_id", customer_id).order("-created_at").first()
```

```bash cURL
curl -G "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" --data-urlencode "filter[customer_id]=eq.$CUSTOMER_ID" \
  --data-urlencode "sort=-created_at" --data-urlencode "per_page=1"
```
</CodeGroup>

`single()` does not check that only one row matches.
It is "the first row, and it must exist".
If uniqueness matters, enforce it with a unique field.

### Walking every row

`pages()`, `all()` and `for await` walk the result page by page.
They use 100 rows per page by default, or the query's `perPage`, or the `pageSize` option.

| Option | Default | Meaning |
| --- | --- | --- |
| `pageSize` | `100` | Rows per request (at most 200) |
| `maxRecords` | none | Stop after this many rows |
| `stopAfterEmptyPages` | `1` | With an unknown total, stop after this many empty pages in a row |
| `signal` | none | Cancel the walk |
| `timeoutMs` | the client's | A timeout for each page request |

<CodeGroup>
```typescript TypeScript
for await (const order of orders.eq("status", "open")) {
  await notify(order);
}
```

```python Python
for order in orders.eq("status", "open").iterate():
    notify(order)

# async client
async for order in aorders.eq("status", "open").iterate():
    await notify(order)
```
</CodeGroup>

<CodeGroup>
```typescript TypeScript
for await (const page of orders.order("id").pages({ pageSize: 200 })) {
  await bulkIndex(page.data);
}
```

```python Python
for page in orders.order("id").pages(page_size=200):
    bulk_index(page.data)
```
</CodeGroup>

<CodeGroup>
```typescript TypeScript
const recent = await orders.order("created_at", "desc").all({ maxRecords: 1000 });
```

```python Python
recent = orders.order("-created_at").all(max_records=1000)
```
</CodeGroup>

Walking with page numbers has a property you should know about.
If rows are inserted or deleted while you walk, later pages shift: a row can be skipped or seen twice.
For walks over data that is changing, sort by a stable key and filter by it instead of using page numbers:

<CodeGroup>
```typescript TypeScript
let after = "";
for (;;) {
  const page = await orders.gt("id", after).order("id").perPage(200);
  if (page.data.length === 0) break;
  await process(page.data);
  after = page.data[page.data.length - 1].id;
}
```

```python Python
after = ""
while True:
    page = orders.gt("id", after).order("id").per_page(200).execute()
    if not page.data:
        break
    process(page.data)
    after = page.data[-1]["id"]
```

```bash cURL
curl -G "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" --data-urlencode "filter[id]=gt.$AFTER" --data-urlencode "sort=id" --data-urlencode "per_page=200"
```
</CodeGroup>

This keyset pattern never skips or repeats rows, and it stays fast on large tables because each request starts where the last one ended.
With a per-row policy, an empty page in this loop can still mean "this range was all hidden"; keep going until the key range is exhausted if that matters.

`all()` loads everything into memory.
Use `maxRecords` as a safety cap whenever the table could be large.

## Choosing a read method

The read methods overlap, and the right one depends on what absence means and how many rows you expect.

| You need | Use | Why |
| --- | --- | --- |
| One record by id that must exist | `get(id)` | Absence is an error worth throwing. |
| One record by id that may not exist | `maybeGet(id)` | Absence is a normal outcome. |
| The newest or oldest matching record | `order(…).first()` | One small request; `null` when none. |
| One matching record that must exist | `single()` | Throws `NotFoundError` when none. |
| Whether anything matches | `exists()` | One row at most crosses the network. |
| How many match | `count()` | One request; throws when unknowable. |
| One screen of rows | `await query.perPage(n)` | One request, with `total` for paging controls. |
| Every row, small table | `all({ maxRecords })` | Simple; capped for safety. |
| Every row, large table | `pages()` or keyset walking | Bounded memory; resumable. |

## Choosing a write path

| You need | Use | Why |
| --- | --- | --- |
| Create one record a user submitted | `create` | Validation and policy apply; errors map to fields. |
| Change some fields | `update` | Unsent fields keep their values. |
| Remove one record | `delete` | Safe to retry; treat `404` as done. |
| Create a few hundred records from the browser | `createMany` | Bounded concurrency; per-row results. |
| Import thousands of rows | `manage().resources.importRecords` | One request with a secret key. |
| Change many records by a condition | A flow or route | The data API changes records by id only. |
| Read-modify-write a counter or balance | A flow or route | Avoids lost updates. |

## Creating many records

`createMany(rows, options)` creates records a few at a time and reports what happened to each.

<CodeGroup>
```typescript TypeScript
const result = await pawabase.from("contacts").createMany(rows, { concurrency: 5 });
```


| Option | Default | Meaning |
| --- | --- | --- |
| `concurrency` | `5` | Requests in flight at once |
| `stopOnError` | `false` | Start no new requests after the first failure |
| `signal` | none | Cancel the remaining requests |

`createMany` is not atomic.
Each row is its own request, so some can succeed while others fail.
The result lists the created rows in input order and the failures by input index.

If you need all-or-nothing, write the batch through a flow or a custom route that runs it as one server-side operation.
If you need a large import, the management module's `resources.importRecords` takes parsed rows in one request; see [Environment management](/clients/typescript/management).

Keep concurrency modest.
Each request counts against the environment's rate limit, and five parallel requests already finish a thousand rows quickly.

## Cancelling and limiting time

Every terminal operation can be cancelled with an `AbortSignal`, and given a timeout.

```typescript
import { AbortError } from "@pawabase/client";

const controller = new AbortController();
const query = orders.eq("status", "open").withOptions({ signal: controller.signal, timeoutMs: 5000 });

setTimeout(() => controller.abort(), 1000);

try {
  await query.perPage(50);
} catch (error) {
  if (error instanceof AbortError) console.log("cancelled");
}
```

`withOptions` is part of the query, so the options travel with it through `first()`, `count()` and the iteration helpers.
Cancelling a walk stops it between pages and rejects the pending request.

## How types flow through a query

With a generated `Database` type, each resource has three types, and the client uses each in a specific place.

| Type | Used for | Example |
| --- | --- | --- |
| `Row` | What reads return | `get()`, list pages, `first()`, `create()` results |
| `Insert` | What `create` and `createMany` accept | Required fields are required; fields with defaults are optional |
| `Update` | What `update` accepts | Every field optional; nullable fields accept `null` |

Filter methods take column names from `Row`, and the value's type from that column.
A typo in a column name, or a string passed for a number column, is a compile error.

```typescript
orders.eq("status", "open");        // ok
orders.eq("staus", "open");         // error: "staus" is not a column
orders.gte("total_minor", "100");   // error: string is not number
```

`select` narrows the row type: selected columns keep their types and the rest become optional.
The returned type therefore tells you the truth about what was fetched.

```typescript
const page = await orders.select("id", "status").perPage(10);
page.data[0].status;       // "open" | "paid" | "cancelled"
page.data[0].total_minor;  // number | undefined in the type; null at runtime
```

`expand` does not change the row type, because the base resource type does not describe relations.
Type expanded fields yourself where you use them:

```typescript
import type { Row } from "./database";

type OrderWithCustomer = Row<"orders"> & { customer: Row<"customers"> | null };

const page = await orders.expand("customer").perPage(20);
const rows = page.data as OrderWithCustomer[];
```

`filter(column, op, value)` and `where` with arbitrary keys accept strings, for dynamic queries built from user input.
They are checked at runtime by the server instead of at compile time by TypeScript.

## Patterns for common screens

The building blocks above combine into a handful of patterns that cover most screens.
Each pattern below explains why it is built the way it is.

### A sortable, filterable table

A table screen keeps its state in the URL, so a reload or a shared link shows the same view.
The query is rebuilt from that state on every change, which is cheap because queries are values.

```typescript
import type { Row } from "./database";

interface TableState {
  status?: "open" | "paid" | "cancelled";
  search?: string;
  sort: "created_at" | "total_minor";
  direction: "asc" | "desc";
  page: number;
}

export async function loadOrdersTable(state: TableState, signal?: AbortSignal) {
  let query = pawabase.from("orders").query();
  if (state.status) query = query.eq("status", state.status);
  if (state.search) query = query.ilike("reference", `*${state.search}*`);
  return query
    .order(state.sort, state.direction)
    .order("id", state.direction)
    .page(state.page)
    .perPage(25)
    .withOptions({ signal });
}
```

The `id` tie-breaker keeps pages stable when many rows share a sort value.
The signal lets the screen cancel a request that a newer state has made irrelevant.

The page count comes from `total`.
When `total` is `null`, show "next" and "previous" without a page count, and disable "next" after an empty page.

```typescript
function pagination(result: { page: number; per_page: number; total: number | null; data: unknown[] }) {
  if (result.total !== null) {
    const pages = Math.max(1, Math.ceil(result.total / result.per_page));
    return { pages, hasNext: result.page < pages };
  }
  return { pages: null, hasNext: result.data.length > 0 };
}
```

### Infinite scroll

Infinite scroll should not use page numbers.
Rows arriving while the user scrolls would shift every later page, producing duplicates.
Keyset pagination on a stable sort avoids that.

```typescript
export async function nextFeedPage(cursor: { createdAt: string; id: string } | null) {
  let query = pawabase.from("posts").eq("status", "live").order("created_at", "desc").order("id", "desc");
  if (cursor) query = query.lte("created_at", cursor.createdAt);
  const page = await query.perPage(30);
  const rows = cursor
    ? page.data.filter((post) => post.created_at < cursor.createdAt || (post.created_at === cursor.createdAt && post.id < cursor.id))
    : page.data;
  const last = rows[rows.length - 1];
  return { rows, cursor: last ? { createdAt: last.created_at, id: last.id } : cursor };
}
```

The server filter uses `lte` on `created_at` only, because the one-filter-per-field rule prevents a compound condition.
The client-side filter then drops the rows at the boundary that were already shown.
This is a common shape: the server narrows, your code finishes.

### A detail page from a URL

An id from a URL might not exist, might belong to someone else, or might be malformed.
All three should show the same "not found" page.

```typescript
import { NotFoundError, ValidationError } from "@pawabase/client";

export async function loadOrderPage(id: string) {
  try {
    const order = await pawabase.from("orders").maybeGet(id, { expand: ["customer", "items"] });
    return order ? { status: 200, order } : { status: 404 };
  } catch (error) {
    if (error instanceof ValidationError) return { status: 404 };
    throw error;
  }
}
```

A malformed id, such as text for an integer key, can be refused before the record is looked up, which is why the example treats a validation error as "not found" too.
Every other error is unexpected on this page and should reach your error boundary.

### A search box

A search box sends a request per keystroke unless you slow it down, and responses can arrive out of order.
Debouncing reduces the requests; cancelling the previous one prevents an old answer from overwriting a newer one.

```typescript
let controller: AbortController | null = null;
let timer: ReturnType<typeof setTimeout> | null = null;

export function searchCustomers(text: string, onResults: (rows: unknown[]) => void) {
  if (timer) clearTimeout(timer);
  timer = setTimeout(async () => {
    controller?.abort();
    controller = new AbortController();
    if (text.trim().length < 2) return onResults([]);
    try {
      const page = await pawabase
        .from("customers")
        .ilike("name", `*${text.trim()}*`)
        .select("id", "name", "email")
        .perPage(10)
        .withOptions({ signal: controller.signal });
      onResults(page.data);
    } catch (error) {
      if (!(error instanceof AbortError)) throw error;
    }
  }, 250);
}
```

A leading wildcard pattern cannot use an ordinary index, so `*text*` on a large table scans it.
For large tables, search a prefix (`text*`), or add a search route that uses the database's full-text features.

### Dashboard counts

A dashboard often shows several counts.
Each `count()` is a small request, and they run in parallel.

```typescript
export async function dashboardCounts() {
  const orders = pawabase.from("orders");
  const [open, paid, cancelled] = await Promise.all([
    orders.eq("status", "open").count(),
    orders.eq("status", "paid").count(),
    orders.eq("status", "cancelled").count(),
  ]);
  return { open, paid, cancelled };
}
```

If any count can hit a per-row policy, it throws `InvalidQueryError`.
Use `Promise.allSettled` when one unknown count should not hide the others, and show "unknown" for that tile.

For sums, averages and group-by counts, write a custom route; the data API counts rows but does not aggregate values.

### A create and edit form

A form for one record does three things with the client: load the record when editing, send only what changed, and map errors to fields.

```typescript
import { ConflictError, ValidationError } from "@pawabase/client";

export async function saveProduct(id: string | null, values: Record<string, unknown>, original?: Record<string, unknown>) {
  const products = pawabase.from("products");
  try {
    if (!id) return { ok: true, product: await products.create(values as never) };
    const changed = Object.fromEntries(Object.entries(values).filter(([key, value]) => original?.[key] !== value));
    return { ok: true, product: await products.update(id, changed as never) };
  } catch (error) {
    if (error instanceof ValidationError) return { ok: false, errors: error.byField() };
    if (error instanceof ConflictError) {
      const columns = (error.details as { columns?: string[] } | undefined)?.columns ?? [];
      return { ok: false, errors: Object.fromEntries(columns.map((column) => [column, ["Already in use."]])) };
    }
    throw error;
  }
}
```

Sending only changed fields has a practical benefit beyond less traffic.
Two people editing different fields of the same record no longer overwrite each other's changes.

## Values by field type

The server accepts several input forms for some field types and always answers in one.
Knowing the answer form tells you what to expect in code.

| Field type | Send from TypeScript | Read back as |
| --- | --- | --- |
| `string`, `text`, `email`, `url` | `string` | `string` |
| `integer` | `number` (or a numeric string) | `number` |
| `number` | `number` (or a numeric string) | `number` |
| `boolean` | `boolean` | `boolean` |
| `datetime` | An ISO 8601 string or a `Date` serialized by you | An ISO 8601 string |
| `date` | `"YYYY-MM-DD"` | `"YYYY-MM-DD"` |
| `uuid` | A UUID string | A lowercase, hyphenated UUID string |
| `json` | Any JSON value | The same value |
| `array` | An array | An array |
| `object`, `ref` | An object | An object |

A `Date` object in a create or update body is serialized by `JSON.stringify`, which produces an ISO string in UTC.
That is what a `datetime` field expects.
For a `date` field, send the calendar day yourself, because a `Date` serialized at midnight local time can land on the previous day in UTC.

<CodeGroup>
```typescript TypeScript
const today = new Date().toISOString().slice(0, 10);
await pawabase.from("tasks").create({ title: "Pay rent", due_on: today });
```

```python Python
from datetime import date

pb.from_("tasks").create({"title": "Pay rent", "due_on": date.today()})   # sent as "YYYY-MM-DD"
```

```bash cURL
curl -X POST "$PAWABASE_URL/rest/v1/tasks" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"title": "Pay rent", "due_on": "2026-10-25"}'
```
</CodeGroup>

Integers in JavaScript are exact up to 2^53.
Integer primary keys and counters stay far below that in practice, but values copied from other systems, such as payment provider ids, may not.
Store such values in `string` fields.

## Ids

A resource's primary key is an integer, a UUID or a ULID, chosen when the resource is created.

| Id type | Looks like | Ordering | Good for |
| --- | --- | --- | --- |
| `integer` | `42` | Creation order | Internal tables created in one place |
| `uuid` | `3f2b8c1e-…` | Random | Ids that must not reveal volume or order |
| `ulid` | `01JB9C2W0Q…` | Creation order, as text | Ids created anywhere that still sort by time |

The client accepts ids as `string` or `number` and encodes them into the path.
Use `number` for integer keys and `string` for the others in application-defined resource types.

ULIDs sort by creation time as plain strings, which makes `order("id")` a cheap, stable "oldest first" and an ideal keyset for walking a table.
Integer ids sort the same way.
UUIDs do not sort meaningfully; use `created_at` with `id` as a tie-breaker instead.

## Writes that reach other parts of the platform

A record written through the client is not only stored.
Depending on the resource's settings, the same write reaches other parts of the platform:

| Resource setting | What happens after your write |
| --- | --- |
| Events on | An event named `<resource>.created`, `<resource>.updated` or `<resource>.deleted` is emitted, with `{ resource, change, record }`. Flows, subscriptions and webhooks listening for it run. |
| Realtime on | The change is sent on `resource:<resource>` to each subscriber who may read the record. |
| A response cache | Cached answers for the resource are cleared. |

This is why many applications need very little server code.
The client writes a record; a flow subscribed to `orders.created` sends the confirmation email; a webhook tells the warehouse; realtime updates the dashboard.
See [Resource events](/data/resource-events) and [Event subscriptions](/events/subscriptions).

Two kinds of writes do not publish events or realtime changes: SQL statements run in the **Data → SQL** console, and changes made directly in the database outside Pawabase.
If a screen depends on realtime, make changes through the API, a flow or the records view.

## Performance

Most list requests are fast, and the ones that are not usually share a cause.

| Cause | Symptom | Fix |
| --- | --- | --- |
| Filtering or sorting on a field without an index | Lists slow down as the table grows | Mark the field `indexed` in the resource's **JSON** tab, then migrate |
| A leading wildcard in `like` or `ilike` | Search is slow on large tables | Search a prefix, or add a search route |
| Wide rows on list screens | Large responses, slow on mobile | `select` only the columns the screen shows |
| `count()` per row in a loop | Many requests | Count once with a filter, or store a counter |
| A request per row to fetch a related record | Many requests | `expand` the relation |
| `all()` on a large table | Memory and time grow without bound | Walk with `pages()`, or set `maxRecords` |
| A per-row policy on a large table | Short pages and many requests to fill a screen | Make the policy pushable so the database filters |

The management module can list a resource's indexes and show which ones exist, if you want to check from code; see [Environment management](/clients/typescript/management).
In Studio, the **Data** section shows indexes on each table.

## Testing records code

Query building and result handling can be tested without a server by giving the client a `fetch` that answers from fixtures and records what it was asked.

```typescript
import { test } from "node:test";
import assert from "node:assert/strict";
import { createClient } from "@pawabase/client";

function fakeClient(handler: (url: URL, init?: RequestInit) => unknown) {
  const calls: URL[] = [];
  const client = createClient({
    url: "https://api.example.test",
    apiKey: "pb_pk_test",
    retry: false,
    fetch: async (input, init) => {
      const url = new URL(input);
      calls.push(url);
      return new Response(JSON.stringify(handler(url, init)), {
        status: 200,
        headers: { "content-type": "application/json" },
      });
    },
  });
  return { client, calls };
}

test("open tasks query sends the right parameters", async () => {
  const { client, calls } = fakeClient(() => ({ data: [], page: 1, per_page: 50, total: 0 }));
  await client.from("tasks").eq("done", false).order("due_on").perPage(50);
  const params = calls[0].searchParams;
  assert.equal(calls[0].pathname, "/rest/v1/tasks");
  assert.equal(params.get("filter[done]"), "is.false");
  assert.equal(params.get("sort"), "due_on");
  assert.equal(params.get("per_page"), "50");
  client.dispose();
});

test("all() keeps paging while the total is unknown", async () => {
  const pages = [[{ id: "a" }], [], []];
  const { client, calls } = fakeClient((url) => {
    const page = Number(url.searchParams.get("page") ?? "1");
    return { data: pages[page - 1] ?? [], page, per_page: 1, total: null };
  });
  const rows = await client.from("tasks").all({ pageSize: 1, stopAfterEmptyPages: 2 });
  assert.deepEqual(rows, [{ id: "a" }]);
  assert.equal(calls.length, 3);
  client.dispose();
});
```

Tests like these pin down the exact wire format your screens rely on.
For policy behavior, test against a real development environment, because only the server knows what a policy allows.

## Records in server code

Server code reads and writes records with the same methods, but the identity behind the request changes what the server does.

| Identity | Policies | Owner field on create | Typical use |
| --- | --- | --- | --- |
| A user, through `asUser(token)` with a publishable key | Applied | Set to that user | Server rendering, API proxies |
| A secret key | Bypassed | Not set; send it yourself | Jobs, imports, administrative fixes |

With a secret key, nothing stops a write that a user could never make.
That is the point of the key, and also its risk.
Keep secret-key record code small, in clearly named modules, and set fields such as the owner explicitly:

<CodeGroup>
```typescript TypeScript
await service.from("tasks").create({ title: "Welcome! Start here.", user_id: newUserId });
```

```python Python
service.from_("tasks").create({"title": "Welcome! Start here.", "user_id": new_user_id})
```

```bash cURL
curl -X POST "$PAWABASE_URL/rest/v1/tasks" -H "apikey: $PAWABASE_SECRET_KEY" -H "content-type: application/json" \
  -d '{"title": "Welcome! Start here.", "user_id": "u_7"}'
```
</CodeGroup>

A backfill over a large table combines keyset walking with modest concurrency.
The loop below sets a default priority on every task that has none, 200 at a time, five updates in flight:

```typescript
async function backfillPriority() {
  const tasks = service.from("tasks");
  let after = "";
  let changed = 0;
  for (;;) {
    const page = await tasks.gt("id", after).order("id").select("id", "priority").perPage(200);
    if (page.data.length === 0) break;
    const pending = page.data.filter((task) => task.priority === null);
    for (let i = 0; i < pending.length; i += 5) {
      await Promise.all(pending.slice(i, i + 5).map((task) => tasks.update(task.id, { priority: 2 })));
    }
    changed += pending.length;
    after = page.data[page.data.length - 1].id;
  }
  return changed;
}
```

Each update emits an event and a realtime change, if the resource has them on.
For very large backfills, consider whether downstream flows and webhooks should see every change, and pause them first if they should not.

## Resources with a transformer

A resource can have a transformer, which reshapes each record on the way out: hiding fields, masking values, renaming or computing fields.
When a resource has one, two things change for client code.

The response shape is the transformer's output, not the table's columns.
The generated row type becomes an open object, `{ [column: string]: unknown }`, because the generator cannot know what the transformer produces.
Type the rows yourself from the transformer's documented output.

Filters and sorting still work on the table's columns, because they run before the transformer.
You can filter on a field the transformer hides; you cannot read it back.

```typescript
interface InvoiceSummary {
  id: number;
  number: string;
  amount_display: string;
  status: string;
}

const invoices = pawabase.resource<InvoiceSummary>("invoices");
const page = await invoices.eq("status", "unpaid").order("due_on").perPage(20);
```

See [Transformers](/data/transformers) for how they are defined.

## Server-side caching and your queries

A resource can have a response cache, configured in Studio on the resource.
When it does, list and get answers are cached on the server for the configured time, keyed by the full query string and the caller.

| Fact | Consequence for client code |
| --- | --- |
| The key includes every query parameter | Equivalent queries written differently are cached separately; keep query building consistent. |
| A write to the resource clears its cached answers | Your own writes are visible on your next read. |
| A change to a related resource does not clear an `expand` | An expanded `customer` can be stale for up to the cache time after the customer changes. |
| The cache is per process unless the installation uses Redis | Several server processes can briefly answer differently. |

If a screen must show related data fresh, fetch the related record directly instead of expanding it, or keep the resource's cache short.
See [Caching](/data/caching) for configuration.

## Rate limits and key scopes

A resource can have its own rate limit, in addition to the environment's.
When a list or a walk exceeds it, the server answers `429`, and the client waits for `Retry-After` and repeats.
A walk over a large table can therefore slow down rather than fail, which is usually what you want; set `maxRecords` or a smaller scope if it is not.

API keys can be restricted with scopes.
Records use two:

| Scope | Allows |
| --- | --- |
| `resource:read` | `list` and `get` |
| `resource:write` | `create`, `update` and `delete` |

A key with only `resource:read` gets `403` from the gateway on every write, before any policy runs.
That is a useful setting for a reporting service: even a bug cannot change data.

## Concurrent edits

The data API does not lock records or compare versions.
When two requests update the same field, the later one wins.

For most fields this is fine, especially when forms send only changed fields.
For values that must not be lost, such as a stock count or a balance, do not compute the new value in the client and write it back.
Two clients reading 10 and writing 9 leave 9, not 8.

Move such changes into a flow or custom route that performs the read and the write together on the server, and call it from the client:

```typescript
await pawabase.routes.post(`products/${productId}/reserve`, { quantity: 1 });
```

If you need "edit only if unchanged since I loaded it", compare `updated_at` in that route before writing, and return `409` when it moved.

## Keeping a list fresh with realtime

A resource with realtime turned on publishes every create, update and delete on the channel `resource:<name>`, checked per subscriber against the resource's read policy.
Combining a query with that channel keeps a screen current without polling.

```typescript
const orders = pawabase.from("orders");
let rows = (await orders.eq("status", "open").order("created_at", "desc").perPage(50)).data;

const channel = pawabase.realtime.channel("resource:orders");
channel.on("message", (message) => {
  const { change, record } = message.payload as { change: "created" | "updated" | "deleted"; record: { id: string; status: string } };
  if (change === "deleted" || record.status !== "open") {
    rows = rows.filter((row) => row.id !== record.id);
  } else if (change === "created") {
    rows = [record as never, ...rows];
  } else {
    rows = rows.map((row) => (row.id === record.id ? (record as never) : row));
  }
  render(rows);
});
await channel.subscribe();

declare function render(rows: unknown[]): void;
```

Realtime tells you about changes; it does not apply your query's filters for you.
Re-check each changed record against the screen's filters, as the example does with `status`.

After a reconnect, reload the query.
Messages sent while the socket was down are not delivered unless the channel was created with `replay`, and even then only up to the history limit.
See [Realtime](/clients/typescript/realtime).

## Coming from supabase-js queries

| supabase-js | @pawabase/client | Note |
| --- | --- | --- |
| `.from("t").select("*")` | `.from("t")` then `await` | All columns by default |
| `.select("a, b")` | `.select("a", "b")` | Separate arguments |
| `.select("*, author(*)")` | `.expand("author")` | Declared relations only |
| `.eq("a", 1)` | `.eq("a", 1)` | Same |
| `.is("a", null)` | `.is("a", null)` | Same |
| `.in("a", [1, 2])` | `.in("a", [1, 2])` | No commas inside values |
| `.not("a", "in", "(1,2)")` | `.notIn("a", [1, 2])` | |
| `.or("a.eq.1,b.eq.2")` | Not supported | Two queries, or a route |
| `.range(0, 9)` | `.page(1).perPage(10)` | Pages from 1 |
| `.order("a", { ascending: false })` | `.order("a", "desc")` | |
| `.limit(10)` | `.limit(10)` | Alias of `perPage` |
| `.single()` | `.single()` | Throws `NotFoundError` |
| `.maybeSingle()` | `.first()` | Returns `null` |
| `{ count: "exact", head: true }` | `.count()` | One request |
| `.insert([...])` | `.createMany([...])` | Not atomic |
| `.upsert(...)` | Not supported | `maybeGet` then `create` or `update`, or a route |
| `.update(...).eq("id", 1)` | `.update(1, patch)` | By primary key only |
| `.delete().eq("status", "x")` | Not supported | Delete by id; bulk deletes belong in a flow |

The last three rows reflect a design choice.
The data API changes records by primary key only, so a client cannot update or delete an unbounded set of rows with one call.
Bulk changes run on the server, where they can be reviewed, logged and limited.

## Troubleshooting

| Symptom | Cause | What to do |
| --- | --- | --- |
| `NotFoundError` from `get` for a record visible in Studio | The `get` policy hides it from this caller | Try the request as that user in the API Explorer |
| `AuthenticationError` on a list while signed out | The `list` policy is the default `authenticated` | Choose a policy that admits anonymous callers, if intended |
| `ValidationError` on create mentioning an unexpected field | The field is not declared, or is read-only | Remove it, or declare it on the resource |
| `ValidationError` when setting a field to `null` | The field is required and not nullable | Send a value, or make the field nullable |
| `ConflictError` with `unique_violation` | A unique field already has this value | Read `details.columns` and show it on the form |
| `InvalidQueryError` about a second filter | Two filters on one field | See [The one-filter-per-field rule](#the-one-filter-per-field-rule) |
| `InvalidQueryError` from `count()` | A per-row policy makes the total unknown | Count rows from `all()`, or make the policy pushable |
| A list returns fewer rows than `perPage` but `total` says more | A per-row policy removed rows from the page | Keep paging; use the iteration helpers |
| Expanded children are missing on some rows | The 200-row cap on `has_many` expansion | Query the child resource directly |
| An expanded record is out of date | The response cache does not clear on related changes | Fetch the related record directly, or shorten the cache |
| `eq("flag", false)` and the raw API disagree | The raw API's `eq.false` is wrong; the client sends `is.false` | Use the client, or `is.false` in raw requests |
| `replace()` did not clear a field | `PUT` keeps unsent fields | Send the field as `null` |
| Rows appear twice in an infinite list | Page numbers shifted while rows were added | Use keyset pagination |

## Questions developers ask

<AccordionGroup>
  <Accordion title="Can I query across two resources in one request?">
    Only through `expand`, which follows declared relations one level deep.
    For anything else, make two queries, or write a custom route that returns exactly what the screen needs.
  </Accordion>
  <Accordion title="Is there a maximum page size?">
    Yes, 200 rows.
    A larger `perPage` is refused with `422`.
    The iteration helpers default to 100 and accept up to 200.
  </Accordion>
  <Accordion title="Does `all()` respect my query's order?">
    Yes.
    It requests pages in order and concatenates them.
    Without an order, rows come in primary-key order.
  </Accordion>
  <Accordion title="Why is `created_at` a string and not a Date?">
    JSON has no date type, and the client returns what the server sends.
    Strings survive serialization in server rendering and caches unchanged.
    Convert with `new Date(value)` where you display it.
  </Accordion>
  <Accordion title="Can I filter on a JSON field's contents?">
    Not with the list filters, which compare whole column values.
    Store the values you filter on as their own fields, or use a route.
  </Accordion>
  <Accordion title="Does a policy filter make my eq filter unnecessary?">
    For security, yes: a pushed-down policy filter applies whatever you send.
    For clarity and caching, an explicit filter that matches the policy still helps, because it states what the screen shows.
  </Accordion>
  <Accordion title="How do I know if a policy can be pushed into the database?">
    Conditions made of equality tests combined with "and" can become database filters.
    Others are evaluated per row, which makes `total` unknown.
    The [pushdown](/policies/pushdown) page lists the exact rules.
  </Accordion>
</AccordionGroup>
