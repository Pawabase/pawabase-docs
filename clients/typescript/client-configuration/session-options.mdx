The `auth` option configures how the signed-in user's session is kept.
It does not affect requests made with a secret key, which have no session.

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `storage` | `SessionStorage` | `localStorage` when the browser allows it, otherwise memory | Where the session is saved between page loads or app launches |
| `storageKey` | `string` | `pawabase.auth.<host>.<first 14 characters of the key>` | The key under which the session is saved |
| `persistSession` | `boolean` | `true` | `false` keeps the session in memory only |
| `autoRefreshToken` | `boolean` | `true` | Refresh the access token before it expires |
| `refreshMarginSeconds` | `number` | `60` | How long before expiry a token counts as expiring |
| `detectSessionInUrl` | `boolean` | `true` in browsers | Read tokens a social sign-in left in the URL fragment |

### storage

A session store has three methods, each of which may be synchronous or return a promise:

```typescript
interface SessionStorage {
  getItem(key: string): string | null | Promise<string | null>;
  setItem(key: string, value: string): void | Promise<void>;
  removeItem(key: string): void | Promise<void>;
}
```

The browser's `localStorage` fits this interface, which is why it is the default.
The client probes it before use, because privacy modes and some embedded browsers throw on access; when the probe fails, the session lives in memory and the user signs in again on the next load.

Other environments need an adapter.

| Environment | A good store | Why |
| --- | --- | --- |
| Browser | The default `localStorage` | Survives reloads; shared by tabs of the same origin. |
| Browser, stricter isolation | `sessionStorage` | Each tab has its own session; closing the tab signs out. |
| React Native and Expo | `expo-secure-store` or the Keychain and Keystore | The session is a credential; the platform's secure storage protects it at rest. |
| Electron | The main process's `safeStorage`, reached over IPC | Keeps tokens out of a renderer's storage. |
| Node script that should stay signed in | A file readable only by the owner | Survives runs of a command-line tool. |
| Server handling many users | None; use `asUser(token)` | A shared store would mix users. |

The `MemoryStorage` class is exported for tests and for code that wants an explicit in-memory store:

<CodeGroup>
```typescript TypeScript
import { createClient, MemoryStorage } from "@pawabase/client";

const pawabase = createClient({
  url,
  apiKey,
  auth: { storage: new MemoryStorage() },
});
```

```python Python
from pawabase import MemorySessionStore, Pawabase

pb = Pawabase(url, key, environment="production", session_store=MemorySessionStore())
```
</CodeGroup>

A file store for a command-line tool takes a few lines:

```typescript
import { promises as fs } from "node:fs";
import type { SessionStorage } from "@pawabase/client";

export function fileStorage(path: string): SessionStorage {
  return {
    async getItem() {
      try {
        return await fs.readFile(path, "utf8");
      } catch {
        return null;
      }
    },
    async setItem(_key, value) {
      await fs.writeFile(path, value, { mode: 0o600 });
    },
    async removeItem() {
      await fs.rm(path, { force: true });
    },
  };
}
```

The store holds both tokens and the user object as JSON.
A refresh token is a long-lived credential, so treat the store with the care you would give a password.

### storageKey

The default key combines the gateway host and the first 14 characters of the API key.
Two clients with the same URL and key therefore share a stored session, and clients for different environments do not collide.

Set it explicitly when you deliberately run two independent sessions against the same environment in one browser, for example a support tool that signs in a staff member and, separately, a customer being helped.

### persistSession

`false` keeps the session in memory only.
The user signs in again after every reload.
That is appropriate for kiosks, shared devices, and high-security screens where a session should not outlive the page.

When `persistSession` is `false`, the client also stops listening for session changes from other tabs and does not take the cross-tab refresh lock, because there is nothing shared to coordinate.

### autoRefreshToken and refreshMarginSeconds

With automatic refresh on, the client schedules a timer to refresh the access token `refreshMarginSeconds` before it expires.
Independently of the timer, any request that finds the token expiring refreshes first, and any request that gets `401` refreshes once and repeats.

| Setting | When to change it |
| --- | --- |
| `autoRefreshToken: false` | When something else owns refresh, such as a server that refreshes tokens in a cookie. |
| A larger `refreshMarginSeconds` | When requests are slow to reach the server and a token that is valid when sent could expire in flight. |
| A smaller `refreshMarginSeconds` | Rarely; a smaller margin only reduces refresh traffic slightly. |

On Node, the refresh timer does not keep the process alive.
A script that finishes its work exits even if it never calls `dispose()`.

When a timed refresh fails for a reason that may pass, such as being offline, the client tries again 10 seconds later, for as long as it holds a session.
When it fails because the server refused the refresh token with `400`, `401` or `403`, the session is cleared and listeners receive `SIGNED_OUT`.

### detectSessionInUrl

After a social sign-in, the auth service redirects back to your app with the tokens in the URL fragment: `#access_token=…&refresh_token=…`.
With `detectSessionInUrl` on, the client reads them on startup, stores the session, and removes the fragment from the address bar with `history.replaceState`.

It also recognizes three other fragments the auth service can send: `#error=…`, `#mfa_required=…&mfa_token=…`, and `#linked=<provider>` after linking an identity.
Turn it off when another part of your app handles the redirect, and call `auth.getSessionFromUrl(url)` yourself.
Mobile apps turn it off and call `getSessionFromUrl` from their deep-link handler.
