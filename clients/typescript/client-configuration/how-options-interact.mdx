Most options are independent, but a few combine in ways worth knowing.

| Combination | Result |
| --- | --- |
| `accessToken` and `auth` | The stateless defaults are applied first, then your `auth` options. Passing `auth: { autoRefreshToken: true }` to a stateless client does not make it refresh, because it has no refresh token. |
| `environment` and `auth` | The client's `environment` is passed to auth, and overrides any value in `auth`. |
| `retry: false` and a per-call `retry` | A per-call policy wins for that call; it merges with the defaults, not with `false`. |
| `headers` and `environment` or `project` | Your headers are added after `x-environment` and `x-project-id`, so a header of the same name replaces them. |
| `timeoutMs: 0` and retries | No per-attempt timeout; only network failures and statuses trigger retries. |
| `fetch` and `hooks` | Hooks run around your `fetch`; your `fetch` sees the final headers, including `apikey` and `authorization`. |
| `dangerouslyAllowBrowser` and `manage()` | The browser check is skipped; `manage()` still requires a secret key. |
| `realtime.webSocket` and a stateless client | The socket opens with the API key only, whatever implementation you pass. |


## One request, followed through the options

The timeline below follows a single `pawabase.from("orders").create(row)` on a client with default options, during a moment when the gateway is restarting.

```text
t=0 ms      the session is expiring (within 60 s of expires_at)
            → POST /auth/v1/token (refresh), auth: none
t=40 ms     new session stored; listeners get TOKEN_REFRESHED
t=41 ms     POST /rest/v1/orders, attempt 0, with the new token
            onRequest(attempt 0)
t=45 ms     the connection is refused: NetworkError
            POST is not idempotent → no retry
            onError(NetworkError)
            the call rejects with NetworkError
```

The same call as `pawabase.from("orders").replace(id, row)`, which is a `PUT`:

```text
t=41 ms     PUT /rest/v1/orders/9, attempt 0
t=45 ms     NetworkError; PUT is safe to repeat; 0 < 2 retries
            onRetry(reason NetworkError, delayMs random in 0..300)
t=230 ms    PUT, attempt 1
t=236 ms    503 with Retry-After: 2
            onRetry(reason "status 503", delayMs 2000)
t=2236 ms   PUT, attempt 2
t=2290 ms   200 → the replaced row is returned
```

The difference is the method, not the resource.
When a create must survive a restart, the dependable pattern is a create that a unique field makes safe to repeat, retried by your own code after checking whether the first attempt landed.


## Testing your configuration

Configuration is code, and the transport can be tested without a server by passing a `fetch` that records what it was asked.

```typescript
import { test } from "node:test";
import assert from "node:assert/strict";
import { createClient } from "@pawabase/client";

test("sends the key, the environment and the client version", async () => {
  const seen: Array<{ url: string; headers: Headers }> = [];
  const pawabase = createClient({
    url: "https://api.example.test",
    apiKey: "pb_pk_test_123",
    environment: "staging",
    fetch: async (url, init) => {
      seen.push({ url, headers: new Headers(init?.headers) });
      return new Response(JSON.stringify({ data: [], page: 1, per_page: 20, total: 0 }), {
        status: 200,
        headers: { "content-type": "application/json" },
      });
    },
  });

  await pawabase.from("orders").perPage(20);

  assert.equal(seen.length, 1);
  assert.equal(seen[0].url, "https://api.example.test/rest/v1/orders?per_page=20");
  assert.equal(seen[0].headers.get("apikey"), "pb_pk_test_123");
  assert.equal(seen[0].headers.get("x-environment"), "staging");
  assert.match(seen[0].headers.get("x-client-info") ?? "", /^pawabase-js\//);
  pawabase.dispose();
});

test("refuses a secret key in a browser", () => {
  const g = globalThis as Record<string, unknown>;
  g.window = {};
  g.document = {};
  try {
    assert.throws(() => createClient({ url: "https://api.example.test", apiKey: "pb_sk_test_123" }), /must never run in a browser/);
  } finally {
    delete g.window;
    delete g.document;
  }
});
```

Tests like these catch the mistakes that otherwise reach production unnoticed: a missing environment, a wrong URL in one build target, a header that a refactor dropped.


## Configuration across the delivery pipeline

The same application runs on a laptop, in CI, in preview deployments and in production.
Each stage needs slightly different configuration, and getting the mapping right once prevents most "works on my machine" problems.

| Stage | URL | Key | Environment | Notes |
| --- | --- | --- | --- | --- |
| Local development against a local stack | `http://localhost:<gateway port>` | The local `development` publishable key | `development` | Plain `http:` is accepted. |
| Local development against a shared installation | The shared gateway | The `development` publishable key | `development` | Several developers share data; prefer seed data with clear owners. |
| Unit tests | Any; requests go to a fake `fetch` | Any string with the right prefix | Any | No network. |
| Integration tests in CI | The shared gateway, or a stack started in CI | A secret key for setup, a publishable key for the app under test | A preview or a dedicated `ci` environment | Clean up what the tests create. |
| Preview deployments | The shared gateway | The preview environment's publishable key | The preview's name | One preview per branch or pull request. |
| Production | The production gateway | The production publishable key | `production` | Secret keys only on servers. |

Preview deployments deserve a note.
Hosting platforms create a deployment per branch, and Pawabase can create an environment per branch.
Map one to the other with a naming rule, such as the branch name in lowercase with non-alphanumerics replaced by hyphens, and set the preview's key in the hosting platform's per-branch configuration.
The management module can create the preview environment from CI; see [Environment management](/clients/typescript/management/overview).


## Watching a client in production

Hooks are enough to answer the three questions that matter about a client in production: how fast are requests, how often do they fail, and which ones are retried.

A practical setup samples successful requests and records every failure:

```typescript
const SAMPLE = 0.05;

const pawabase = createClient({
  url,
  apiKey,
  hooks: {
    onResponse: (info) => {
      const failed = info.status >= 400;
      if (failed || Math.random() < SAMPLE) {
        telemetry.record("pawabase.response", {
          method: info.method,
          path: new URL(info.url).pathname,
          status: info.status,
          durationMs: info.durationMs,
          attempt: info.attempt,
          requestId: info.requestId,
        });
      }
    },
    onRetry: (info) => telemetry.record("pawabase.retry", { reason: info.reason, delayMs: info.delayMs }),
  },
});

declare const telemetry: { record(name: string, fields: Record<string, unknown>): void };
```

Three signals deserve alerts.
A rising share of `429` responses means you are near your rate limit and users are about to wait.
A rising number of retries with reason `status 503` means the installation is struggling.
A rising number of `401` responses after refresh means sessions are being revoked or refresh tokens reused, which can indicate two parts of your app refreshing the same session.


## The exported option types

Every option type is exported, so wrappers and configuration helpers can be typed precisely.

```typescript
import type {
  ClientOptions,
  AuthOptions,
  RealtimeOptions,
  RetryOptions,
  Hooks,
  FetchLike,
  SessionStorage,
  WebSocketConstructor,
  RequestInfo,
  ResponseInfo,
  TokenProvider,
} from "@pawabase/client";
```

| Type | Describes |
| --- | --- |
| `ClientOptions` | The whole options object of `createClient` |
| `AuthOptions` | The `auth` option |
| `RealtimeOptions` | The `realtime` option |
| `RetryOptions` | The `retry` option and per-call retry overrides |
| `Hooks` | The `hooks` option |
| `RequestInfo`, `ResponseInfo` | What hooks receive |
| `FetchLike` | The `fetch` option's function type |
| `SessionStorage` | A session store adapter |
| `WebSocketConstructor`, `WebSocketLike` | A WebSocket implementation for realtime |
| `TokenProvider` | The interface the transport uses to get and refresh tokens |

A configuration helper typed with `ClientOptions` lets a team share defaults without hiding them:

```typescript
import { createClient, type ClientOptions } from "@pawabase/client";

const teamDefaults: Partial<ClientOptions> = {
  timeoutMs: 20_000,
  retry: { retries: 2, maxRetryAfterMs: 15_000 },
  headers: { "x-app": "orders-web" },
};

export function makeClient(options: Pick<ClientOptions, "url" | "apiKey" | "environment"> & Partial<ClientOptions>) {
  return createClient({ ...teamDefaults, ...options });
}
```


## Tuning for slow or unreliable networks

The defaults assume a reasonable connection.
Many real users are on mobile networks that drop packets, switch towers, and stall for seconds at a time.
A few option changes make the client behave much better there.

| Symptom on poor networks | Option to change | Suggested value | Effect |
| --- | --- | --- | --- |
| Interactive calls hang for a long time | `timeoutMs` | `10000` to `15000` | A stalled attempt is abandoned sooner and retried if safe. |
| Reads fail on brief drops | `retry.retries` | `3` | One more chance for safe requests. |
| Retries arrive in bursts after an outage | `retry.baseDelayMs` | `500` | Wider spread between clients. |
| The realtime socket looks connected but delivers nothing | `realtime.heartbeatSeconds` | `15` | A dead link is detected after about 30 seconds instead of 50. |
| Reconnects hammer a struggling server | `realtime.reconnect.maxDelayMs` | `30000` | Clients back off further. |
| Uploads fail halfway | per-call `timeoutMs` on uploads | `0` or several minutes | Large uploads are not cut off by the interactive timeout. |

Pair these with UI that reflects state.
Show when realtime is `reconnecting`, keep forms filled after a failed submit, and let users retry a failed write explicitly.
The client retries what is safe; a person should decide about the rest.
