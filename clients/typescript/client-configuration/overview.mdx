`createClient(options)` builds one client from an options object.
The options decide four things: where requests go, which credentials they carry, how the user's session is kept, and how the client reacts when the network or the server fails.

This page explains each option by the decision it represents, then covers the parts of the client that are not about a particular service: raw requests, health checks, hooks and the client's lifecycle.

## The mental model

A client's options are fixed when it is created.
There is no `setApiKey()` or `setUrl()`.
If you need different settings, you create another client, or use `asUser(token)`, which creates a client with the same options and a different identity.

This immutability is deliberate.
A client holds a session and possibly a WebSocket, and those are only valid for the URL, key and environment they were created for.
Changing the key under a live session would send one environment's tokens to another.

The options group into five concerns:

| Concern | Options | Question it answers |
| --- | --- | --- |
| Destination | `url`, `environment`, `project` | Which gateway and which environment do requests reach? |
| Credentials | `apiKey`, `accessToken`, `dangerouslyAllowBrowser` | Who is calling, and with what authority? |
| Session | `auth` | Where is the signed-in user's session kept, and how is it refreshed? |
| Transport | `timeoutMs`, `retry`, `fetch`, `headers`, `hooks` | How are requests sent, timed, repeated and observed? |
| Realtime | `realtime` | How is the WebSocket opened, kept alive and reconnected? |


## The options at a glance

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";

const pawabase = createClient({
  url: "https://api.example.com",
  apiKey: "pb_pk_live_…",
  environment: "production",
  timeoutMs: 30_000,
  retry: { retries: 2, baseDelayMs: 300, maxDelayMs: 8000, maxRetryAfterMs: 30_000 },
  headers: { "x-app-version": "4.2.0" },
  hooks: {},
  auth: { persistSession: true, autoRefreshToken: true, refreshMarginSeconds: 60 },
  realtime: { heartbeatSeconds: 25, ackTimeoutMs: 10_000, connectTimeoutMs: 10_000 },
});
```

```python Python
from pawabase import MemorySessionStore, Pawabase

pb = Pawabase(
    "https://api.example.com",
    "pb_pk_live_…",
    environment="production",       # defaults to "development"
    timeout=30.0,                   # seconds per attempt
    retries=2,                      # extra attempts for reads after network failures and 502/503/504
    session_store=MemorySessionStore(),
    auto_refresh=True,
    headers={"x-app-version": "4.2.0"},
)
```

```bash cURL
# Options are client behavior; on the wire every request carries the same few headers:
curl "$PAWABASE_URL/rest/v1/orders" \
  -H "apikey: pb_pk_live_…" -H "x-environment: production" -H "x-app-version: 4.2.0" \
  --max-time 30
```
</CodeGroup>

| Option | Type | Default | Required |
| --- | --- | --- | --- |
| `url` | `string` | none | Yes |
| `apiKey` | `string` | none | Yes |
| `environment` | `string` | none | No, but recommended |
| `project` | `string` | none | No |
| `timeoutMs` | `number` | `30000` | No |
| `retry` | `RetryOptions \| false` | `{ retries: 2, baseDelayMs: 300, maxDelayMs: 8000, maxRetryAfterMs: 30000 }` | No |
| `fetch` | `(input, init) => Promise<Response>` | The global `fetch` | Only where there is no global `fetch` |
| `headers` | `Record<string, string>` | `{}` | No |
| `hooks` | `Hooks` | `{}` | No |
| `auth` | `AuthOptions` | See [Session options](/clients/typescript/client-configuration/session-options#session-options) | No |
| `realtime` | `RealtimeOptions` | See [Realtime options](/clients/typescript/client-configuration/transport-options#realtime-options) | No |
| `accessToken` | `string \| () => string \| null \| Promise<string \| null>` | none | No |
| `dangerouslyAllowBrowser` | `boolean` | `false` | No |

`createClient` checks the options it can check without a network call, and throws `ConfigError` immediately when something is wrong.
That makes configuration mistakes fail at startup, in the place where you can fix them.

| Problem | Error message |
| --- | --- |
| `url` is missing or empty | `createClient needs the gateway url.` |
| `apiKey` is missing or empty | `createClient needs an apiKey.` |
| `url` cannot be parsed | `"<url>" is not a valid URL.` |
| `url` is not `http:` or `https:` | `The url must start with http:// or https://.` |
| A secret key in a browser | `A secret key (pb_sk_…) must never run in a browser…` |
| No `fetch` anywhere | `No fetch is available. Pass one in the options.` |


## Destination options

### url

The origin of your Pawabase gateway.
Every service is reached through it: the data API at `/rest/v1`, auth at `/auth/v1`, storage at `/storage/v1`, realtime at `/realtime/v1`, flows at `/flows/v1`, and the management plane at `/platform/v1`.

You find it in Studio under **Access → API keys**, in the **Health check** card at the top of the page, which also tells you whether a key resolves through that gateway.
For a local stack it is the port your gateway listens on, such as `http://localhost:8080`.

The client removes trailing slashes and then appends service paths to whatever you gave it.
That has two consequences worth knowing.

A gateway served under a path prefix works.
If your reverse proxy exposes Pawabase at `https://example.com/pawabase`, pass exactly that, and the client calls `https://example.com/pawabase/rest/v1/…`.
The realtime socket URL is built the same way, keeping the prefix and switching the scheme to `wss:` or `ws:`.

A URL that already contains a service path breaks every call.
`https://api.example.com/rest/v1` produces `https://api.example.com/rest/v1/rest/v1/orders`.
If you copied a URL from the API Explorer, strip it back to the origin.

| You passed | Requests go to | Correct? |
| --- | --- | --- |
| `https://api.example.com` | `https://api.example.com/rest/v1/orders` | Yes |
| `https://api.example.com/` | `https://api.example.com/rest/v1/orders` | Yes |
| `https://example.com/pawabase` | `https://example.com/pawabase/rest/v1/orders` | Yes, for a prefixed proxy |
| `https://api.example.com/rest/v1` | `https://api.example.com/rest/v1/rest/v1/orders` | No |
| `api.example.com` | none; `ConfigError` | No |

### environment

The name of the environment the key belongs to, such as `development`, `production`, or a preview's name.

A key already identifies its environment, so for data, auth, storage and flows the gateway does not need this value.
The client still uses it in four places:

| Use | What happens |
| --- | --- |
| Every request | Sent as the `x-environment` header. |
| Social sign-in | Part of the authorization URL: `/auth/v1/authorize/<environment>/<provider>`. |
| Realtime | Added to the socket URL as `environment=<name>`. |
| `manage()` and `admin()` | The default environment of management paths: `/platform/v1/envs/<environment>/…`. |

When you omit it, social sign-in falls back to the `env` claim of the signed-in user's access token, and fails with `ConfigError` when nobody is signed in.
`manage()` and `admin()` fall back to `development`, which is almost never what a production script wants.
Pass it explicitly.

### project

The project's reference.
When given, it is sent as the `x-project-id` header.
The gateway already knows the project from the key, so this is a scope hint for proxies and logs, not an authority.
Most applications leave it out.


## Credential options

### apiKey

The key every request carries in the `apikey` header.
The [overview](/clients/javascript/overview#the-api-key) explains publishable and secret keys; this section covers how the client treats them.

The client recognizes a secret key by its prefix: `pb_sk_`, or `sk_` for keys from older installations.
It uses that recognition in four places.

| Place | Behavior with a secret key |
| --- | --- |
| `createClient` in a browser | Throws `ConfigError` unless `dangerouslyAllowBrowser` is `true`. |
| `auth.signInWithOAuthUrl()` | Throws `ConfigError`; the key would appear in a URL. |
| `storage.from(b).getPublicUrl()` | Throws `ConfigError`; the key would appear in a URL. |
| `manage()` and `admin()` | Required; with a publishable key they throw `ConfigError`. |

"In a browser" means a global `window` and a global `document` both exist.
Server-side rendering in Node has neither, so a secret key on the server side of a Next.js page is accepted.
A web worker has no `document`, so the check does not fire there; do not put secret keys in workers that run in a user's browser.

Keys can be narrowed further when they are created, independently of their type.

| Restriction | Set in Studio as | Effect on a client using the key |
| --- | --- | --- |
| Scopes | **Permissions** | Requests outside the scopes get `403` from the gateway, before any policy. |
| Expiry | **Expires** | After the date, every request gets `401 invalid_api_key`. |
| Allowed IP ranges | **Allowed IP ranges** | Requests from other addresses are refused. Useful for secret keys on servers with fixed egress. |
| Allowed routes | **Allowed routes** | Requests to other paths are refused, for example a key that may only call `GET /rest/v1/*`. |

A key can be rotated in Studio.
Rotation issues a replacement and keeps the old key working for a grace period you choose, 24 hours by default, so deployed clients can switch without downtime.
Because the key is fixed in a client, switching means deploying with the new key; there is nothing to call on a running client.

### accessToken

A user's access token to send instead of a stored session.
It accepts a string, or a function that returns a string, `null`, or a promise of either.

Setting `accessToken` puts the client in **stateless** mode.
This is the mode for code that handles one request for one user and already holds that user's token, typically from a cookie.

| Behavior | Normal client | Stateless client (`accessToken` set) |
| --- | --- | --- |
| Where the token comes from | The stored session | The `accessToken` option, read before each request |
| Session storage | `localStorage` in browsers, memory elsewhere | Memory only, empty |
| Automatic refresh | Yes | No |
| After a `401` | One refresh and one replay | The error is thrown; refreshing is your job |
| Reading the URL fragment for social sign-in | Yes, in browsers | No |
| Realtime socket | Carries the session's token, updated on refresh | Opens without a user token |

The function form is useful when a framework owns the session and the token can change during a request:

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";

const pawabase = createClient({
  url: process.env.PAWABASE_URL!,
  apiKey: process.env.PAWABASE_PUBLISHABLE_KEY!,
  environment: "production",
  accessToken: async () => (await getSessionFromFramework())?.accessToken ?? null,
});

declare function getSessionFromFramework(): Promise<{ accessToken: string } | null>;
```

```python Python
from pawabase import Pawabase

# A fixed token for one request:
pb = Pawabase(PAWABASE_URL, PUBLISHABLE_KEY, environment="production", access_token=token, auto_refresh=False)

# More often: one client per process, a view per request
view = base.as_user(token)
```

```bash cURL
curl "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_PUBLISHABLE_KEY" -H "Authorization: Bearer $ACCESS_TOKEN"
```
</CodeGroup>

`pawabase.asUser(token)` builds exactly this kind of client from an existing one, copying every other option.
It is the method you will use most of the time; the option exists for code that creates clients directly.

Note the realtime row.
A stateless client's realtime connection does not carry the user's token, so channels whose rules require a signed-in user refuse it.
Server code rarely needs a live socket; when it does, give it a normal client with a session adopted through `auth.setSession()`.

### dangerouslyAllowBrowser

Turns off the check that refuses a secret key in a browser.
The name is the documentation: a secret key in a browser can be read by anyone who opens developer tools, and it bypasses every policy.

The legitimate uses are internal tools that run on a trusted machine and never reach the public internet, such as a local data-repair page served from `localhost`.
If you are unsure whether your case is one of them, it is not.
