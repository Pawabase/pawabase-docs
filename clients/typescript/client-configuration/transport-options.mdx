### timeoutMs

The longest a single attempt may take, in milliseconds.
The default is 30 seconds; `0` disables the timeout.

The timeout applies **per attempt**, not per call.
A call that is retried twice can take up to three timeouts plus the backoff between them.

| Settings | Worst case for one call |
| --- | --- |
| `timeoutMs: 30000`, `retries: 2` | About 90 seconds plus backoff (at most 8 seconds per wait) |
| `timeoutMs: 10000`, `retries: 2` | About 30 seconds plus backoff |
| `timeoutMs: 10000`, `retry: false` | 10 seconds |

When an attempt times out, the client raises `TimeoutError`.
Timeouts are retried like network failures: only for requests that are safe to repeat.

Most queries finish in milliseconds.
A long timeout mainly matters for uploads, for flows that call slow third parties, and for management operations such as backups.
Prefer raising the timeout for those calls only:

<CodeGroup>
```typescript TypeScript
await pawabase.flows.run("generate-report", { month: "2026-09" }, { timeoutMs: 120_000 });
```

```python Python
# The Python client's timeout is set per client; use a second client for long calls.
slow = Pawabase(url, key, environment="production", timeout=120)
slow.flows.invoke("generate-report", {"month": "2026-09"})
```

```bash cURL
curl -X POST "$PAWABASE_URL/flows/v1/generate-report" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" \
  -H "content-type: application/json" -d '{"month": "2026-09"}' --max-time 120
```
</CodeGroup>

<CodeGroup>
```typescript TypeScript
await pawabase.storage.from("videos").upload("intro.mp4", file, { timeoutMs: 0 });
```

```python Python
uploads = Pawabase(url, key, environment="production", timeout=None)   # httpx: None means no timeout
uploads.storage.from_("videos").upload("intro.mp4", Path("intro.mp4"))
```

```bash cURL
curl -X PUT "$PAWABASE_URL/storage/v1/object/videos/intro.mp4" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" \
  -H "content-type: video/mp4" --data-binary @intro.mp4
```
</CodeGroup>

### retry

The policy for repeating failed requests.
`false` turns retries off for the whole client.
An object sets any of four fields; the others keep their defaults.

| Field | Default | Meaning |
| --- | --- | --- |
| `retries` | `2` | Extra attempts after the first. `0` disables retries. |
| `baseDelayMs` | `300` | The ceiling of the first backoff. |
| `maxDelayMs` | `8000` | The largest backoff. |
| `maxRetryAfterMs` | `30000` | The longest `Retry-After` the client will wait. A longer request to wait is thrown as `RateLimitError` instead. |

The client retries only what is safe to repeat:

| Failure | `GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE` | `POST`, `PATCH` |
| --- | --- | --- |
| `429` rate limited | Retried | Retried |
| `502`, `503`, `504` | Retried | Only when marked idempotent |
| Network failure | Retried | Only when marked idempotent |
| Timeout | Retried | Only when marked idempotent |
| Any other status | Not retried | Not retried |

A `429` is always safe to repeat because the gateway answers it before the request reaches a service.
A `502` after a `POST` is not: the service may have created the record before the connection failed.

`PUT` and `DELETE` are treated as safe because repeating them leaves the same final state.
Repeating a `DELETE` that succeeded the first time can produce `404` on the second attempt; the client surfaces that `404`, which you may choose to treat as success.

A request body that is a `ReadableStream` is never retried, because a stream can be read only once.

Backoff uses full jitter: each wait is a random value between zero and `min(maxDelayMs, baseDelayMs × 2^attempt)`.
Randomness spreads out clients that failed at the same moment, so they do not all return at the same moment.
When the server sends `Retry-After`, the client waits that long instead of using backoff.

Per-call options merge with the client's policy.
Several methods accept `retry` and `idempotent` through the raw request API; `flows.run` and `routes` accept `idempotent`:

```typescript
await pawabase.routes.post("carts/7/recalculate", undefined, { idempotent: true });
```

Turn retries off for the whole client in tests that assert on exact request counts, and in short-lived scripts where a fast failure is better than a slow success.

### fetch

The function the client uses to send requests, with the same signature as the global `fetch`.
The default is the global `fetch`, called through a wrapper so that environments that require `fetch` to be called unbound work.

You pass your own for four reasons.

The runtime has no global `fetch`.
Node 18 and later, Deno, Bun, browsers and React Native all have one, so this is rare today.

You want to instrument requests below the client, for example to add tracing headers or record timings in an APM tool:

```typescript
import { createClient } from "@pawabase/client";

const tracedFetch: typeof fetch = async (input, init) => {
  const headers = new Headers(init?.headers);
  headers.set("traceparent", currentTraceparent());
  return fetch(input, { ...init, headers });
};

const pawabase = createClient({ url, apiKey, fetch: tracedFetch });

declare function currentTraceparent(): string;
```

You need a framework's `fetch` extensions, for example Next.js caching options:

```typescript
const cachedFetch: typeof fetch = (input, init) =>
  fetch(input, { ...init, next: { revalidate: 60 } } as RequestInit);

const publicContent = createClient({ url, apiKey, fetch: cachedFetch });
```

Only use caching like this for data that is the same for every visitor.
A cached response to one user's request must never be served to another user.

You want a test double that answers without a network, which the [servers and testing page](/clients/typescript/server-runtimes-testing/overview) shows.

### headers

Extra headers sent on every request.
They are added after the client's own headers, so a header with the same name replaces the client's value.

Useful extras are an application version, a tenant hint your proxy routes on, or a header your firewall rules match.
Do not put credentials here; the client already sends the key and token where they belong, and a credential in `headers` would also be sent to places the client deliberately sends nothing, such as the logs of your own hooks.

Signed URLs are the exception: calls to an absolute signed URL send neither the key nor the client's extra headers.

### hooks

Four optional callbacks that observe requests.
They exist for logging, metrics and error tracking.
A hook that throws is ignored, so observability can never break a request.

| Hook | Called | Receives |
| --- | --- | --- |
| `onRequest` | Before each attempt is sent | `method`, `url`, `attempt`, `headers` with `apikey` and `authorization` masked |
| `onResponse` | After each attempt gets a response, success or not | `method`, `url`, `attempt`, `status`, `durationMs`, `requestId` |
| `onRetry` | Before waiting to repeat an attempt | `method`, `url`, `attempt`, `reason`, `delayMs` |
| `onError` | When the client is about to throw | The error, and `method`, `url`, `attempt` |

`attempt` counts from `0`.
A request that succeeded on its first try produces one `onRequest` and one `onResponse` with `attempt: 0`.

`reason` in `onRetry` is either `status 429`, `status 503` and so on, or the error class name, such as `NetworkError` or `TimeoutError`.

A small metrics bridge looks like this:

```typescript
const pawabase = createClient({
  url,
  apiKey,
  hooks: {
    onResponse: ({ method, url, status, durationMs }) => {
      const route = new URL(url).pathname.split("/").slice(0, 4).join("/");
      metrics.histogram("pawabase.request.ms", durationMs, { method, route, status: String(status) });
    },
    onRetry: ({ reason }) => metrics.increment("pawabase.request.retry", { reason }),
  },
});

declare const metrics: {
  histogram(name: string, value: number, tags: Record<string, string>): void;
  increment(name: string, tags: Record<string, string>): void;
};
```

Group URLs into routes before tagging metrics with them.
A raw URL contains record ids and query strings, and a metric with one tag value per id becomes expensive and useless.


## Realtime options

The `realtime` option configures the WebSocket connection that channels share.

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `webSocket` | A WebSocket constructor | The global `WebSocket` | The implementation to use; on Node 20, pass the `ws` package's `WebSocket` |
| `heartbeatSeconds` | `number` | `25` | Seconds between pings; a connection silent for two intervals is recycled |
| `ackTimeoutMs` | `number` | `10000` | How long to wait for the server to acknowledge a subscribe, publish or presence update |
| `connectTimeoutMs` | `number` | `10000` | How long to wait for the connection to open and be welcomed |
| `reconnect` | `false` or `{ baseDelayMs, maxDelayMs, maxAttempts }` | Reconnect forever, 500 ms to 15 s backoff | Whether and how to reconnect after a drop |
| `onProtocolError` | `(detail: string) => void` | none | Called for frames the client does not understand |

```typescript
import WebSocket from "ws";
import { createClient } from "@pawabase/client";

const pawabase = createClient({
  url,
  apiKey,
  environment: "production",
  realtime: {
    webSocket: WebSocket as unknown as import("@pawabase/client").WebSocketConstructor,
    reconnect: { baseDelayMs: 1000, maxDelayMs: 30_000, maxAttempts: 20 },
    onProtocolError: (detail) => console.warn("realtime", detail),
  },
});
```

The [realtime page](/clients/typescript/realtime/overview) explains what each of these changes for channels.
