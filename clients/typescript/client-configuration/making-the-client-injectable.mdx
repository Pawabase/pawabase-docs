Application code that imports a client module directly is hard to test, because every test then talks to whatever that module created.
Passing the client in, or reading it from a small container, keeps tests simple and makes the dependency visible.

```typescript
// orders/service.ts
import type { PawabaseClient } from "@pawabase/client";
import type { Database } from "../database";

export function ordersService(pawabase: PawabaseClient<Database>) {
  return {
    open: () => pawabase.from("orders").eq("status", "open").order("created_at", "desc").perPage(50),
    markPaid: (id: string) => pawabase.from("orders").update(id, { status: "paid" }),
  };
}
```

```typescript
// app.ts
import { pawabase } from "./lib/pawabase";
import { ordersService } from "./orders/service";

export const orders = ordersService(pawabase);
```

```typescript
// orders/service.test.ts
import { createClient } from "@pawabase/client";
import { ordersService } from "./service";

const fake = createClient({
  url: "https://api.example.test",
  apiKey: "pb_pk_test",
  fetch: async () => new Response(JSON.stringify({ data: [], page: 1, per_page: 50, total: 0 }), { status: 200 }),
});

const orders = ordersService(fake);
```

The service receives a real client whose transport is fake.
That tests your query building and result handling exactly as production runs them, without a server.


## Coming from supabase-js options

| supabase-js option | @pawabase/client option | Notes |
| --- | --- | --- |
| `createClient(url, key, options)` | `createClient({ url, apiKey, ...options })` | One options object. |
| `auth.storage` | `auth.storage` | Same three methods. |
| `auth.storageKey` | `auth.storageKey` | Different default format. |
| `auth.persistSession` | `auth.persistSession` | Same meaning. |
| `auth.autoRefreshToken` | `auth.autoRefreshToken` | Same meaning; plus `refreshMarginSeconds`. |
| `auth.detectSessionInUrl` | `auth.detectSessionInUrl` | Reads a fragment, not a query code. |
| `auth.flowType: "pkce"` | `auth.exchangeCode(code, verifier)` | PKCE is a method call, not a mode. |
| `global.fetch` | `fetch` | Top-level. |
| `global.headers` | `headers` | Top-level. |
| `db.schema` | none | Resources are named directly; there are no schemas to choose. |
| `realtime.params` | `realtime` | Different fields; see [Realtime options](/clients/typescript/client-configuration/transport-options#realtime-options). |
| `accessToken` (third-party auth) | `accessToken` | Puts the client in stateless mode. |


## Which configuration values are sensitive

Not every configuration value is a secret, and treating them all alike leads to either leaks or needless friction.

| Value | Sensitive? | Where it may appear |
| --- | --- | --- |
| Gateway URL | No | Anywhere, including browser bundles and logs |
| Environment name | No | Anywhere |
| Publishable key | No; it identifies the environment and is constrained by policies | Browser bundles, mobile binaries, logs |
| Secret key | Yes; it bypasses every policy | Server environment variables and secret managers only |
| A user's access token | Yes, for up to 15 minutes | Memory, secure storage, HTTP-only cookies |
| A user's refresh token | Yes, until used or revoked | Secure storage, HTTP-only cookies |
| Signed URLs | Yes, until they expire | Handed only to the intended recipient |

The client is careful with the sensitive values it handles.
`ConfigError` messages name the URL but never print the key.
`onRequest` receives headers with `apikey` and `authorization` replaced by `***`.
Social sign-in and public URLs refuse to put a secret key in a URL.
What the client cannot protect is your own logging of option objects; avoid `console.log(options)` in configuration code.


## Defaults and why they were chosen

| Default | Value | Reason |
| --- | --- | --- |
| Timeout | 30 seconds per attempt | Long enough for slow uploads and flows, short enough that a hung connection is noticed. |
| Retries | 2 extra attempts | Covers a brief deploy or a rate-limit window without hiding a real outage. |
| First backoff ceiling | 300 ms | A quick second try for transient failures. |
| Largest backoff | 8 seconds | Keeps a user-facing call from stalling much longer than the timeout. |
| Longest `Retry-After` honored | 30 seconds | A server asking for longer is better surfaced as an error the UI can explain. |
| Refresh margin | 60 seconds | Covers request latency and modest clock skew. |
| Heartbeat | 25 seconds | Below the idle timeout of common proxies and load balancers. |
| Realtime acknowledgement timeout | 10 seconds | Long enough for a busy server, short enough to report a stuck socket. |


## A checklist for a new client

| Question | If the answer is yes |
| --- | --- |
| Does this code run in a browser or an app binary? | Use a publishable key and the default session handling. |
| Does it act for a user on a server? | Use a publishable key and `asUser(token)` per request. |
| Does it act on its own behalf? | Use a secret key, and keep it in server configuration. |
| Does it use social sign-in, realtime, `manage()` or `admin()`? | Pass `environment`. |
| Does it run on Node 20 and use live channels? | Pass `realtime.webSocket`. |
| Does it run where `localStorage` is unavailable but sessions must persist? | Pass `auth.storage`. |
| Does it make long uploads or long-running calls? | Raise `timeoutMs` for those calls only. |
| Will it run in production? | Add `hooks` that record failures with their `requestId`. |

When every row is settled, the configuration is complete.
Write the answers down next to the client module, in a short comment, so the next person knows why each option is there.
Anything you add beyond it should answer a problem you have observed, such as a slow network or an unusual runtime, rather than one you expect.


## Troubleshooting configuration

| Symptom | Cause | Fix |
| --- | --- | --- |
| Every request is `404` | The `url` contains a service path. | Use the origin only. |
| Social sign-in throws `Social sign-in needs the environment` | `environment` was not passed and nobody is signed in. | Pass `environment` to `createClient`. |
| `manage()` changes the wrong environment | `environment` was not passed, so `development` was used. | Pass `environment`, or name it in `manage(client, name)`. |
| The session is lost on every reload | Storage is blocked, `persistSession` is `false`, or the storage key changed between builds. | Check the browser's privacy mode; keep the key and URL stable. |
| Two tabs sign each other out | Two different storage keys for the same environment, or a client created per component. | Use one client per app. |
| Requests hang for a long time before failing | A long timeout multiplied by retries. | Lower `timeoutMs` for interactive calls; use per-call timeouts for long work. |
| A realtime channel is refused on the server | The server client is stateless, so its socket has no user token. | Use a client with a session for live channels, or publish over HTTP. |
| Hooks never fire | They were passed under `auth` or `realtime` instead of at the top level. | Pass `hooks` at the top level of the options. |
| `TypeError: Failed to execute 'fetch' on 'Window': Illegal invocation` | A custom `fetch` was passed unbound, such as `window.fetch` stored in an object. | Pass `(input, init) => fetch(input, init)`. |


## Questions developers ask

<AccordionGroup>
  <Accordion title="Can I change the API key without creating a new client?">
    No.
    A client's options are fixed.
    Create a new client and dispose the old one.
    The session belongs to the old key's environment, so it does not carry over.
  </Accordion>
  <Accordion title="Does passing environment let a key reach another environment?">
    No.
    The key decides the environment for data, auth, storage and realtime.
    The management modules address environments by name, and the platform checks that the key may manage the named environment.
  </Accordion>
  <Accordion title="Are hooks called for signed URL uploads?">
    Yes.
    Calls to absolute URLs go through the same transport and call the same hooks.
    They send no API key, so there is nothing to mask.
  </Accordion>
  <Accordion title="Is the retry policy applied to realtime?">
    No.
    Realtime has its own reconnect policy, configured with `realtime.reconnect`.
    The HTTP retry policy applies to realtime's HTTP methods: `realtime.publish`, `realtime.presence` and `realtime.history`.
  </Accordion>
  <Accordion title="What happens when two clients with the same storage key refresh at once?">
    In a browser with Web Locks, refreshes for the same storage key are serialized across all clients and tabs.
    The second one finds the new tokens already stored and uses them instead of refreshing again.
  </Accordion>
  <Accordion title="Should each tenant of my SaaS get its own key?">
    Usually not.
    Tenants are organizations inside one environment, separated by policies that test `$auth.org`.
    Separate environments, and therefore separate keys, are for separate stages such as staging and production, or for tenants that need fully isolated data and users.
  </Accordion>
  <Accordion title="Can I read the configured environment back from a client?">
    Yes.
    `pawabase.options` holds the options the client was created with, including `environment`.
    Treat it as read-only; changing it does not reconfigure the client.
  </Accordion>
  <Accordion title="Does the client cache responses?">
    No.
    Each call sends a request.
    Server-side response caching is configured per resource in Pawabase; client-side caching belongs to your data layer.
  </Accordion>
  <Accordion title="Do I need to configure connection pooling?">
    No.
    The runtime's `fetch` manages connections.
    On Node, the built-in `fetch` keeps connections alive and reuses them across requests to the same gateway.
  </Accordion>
  <Accordion title="What is the smallest configuration that works?">
    A URL and a publishable key.
    Add `environment` as soon as you use social sign-in, realtime or the management modules.
  </Accordion>
  <Accordion title="Why is my custom content-type replaced?">
    It is not, as long as you set it on the call.
    The client only adds `application/json` when you send an object and set no `content-type` yourself.
  </Accordion>
</AccordionGroup>
