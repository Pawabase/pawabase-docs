The client runs anywhere `fetch` runs: Node, Bun, Deno, serverless functions, edge workers and the server half of web frameworks.
On a server, one question shapes everything: whose identity does each request carry?

This page explains how to answer that question in each kind of server code, how the common frameworks fit, what changes in serverless and edge runtimes, and how to test code that uses Pawabase, from unit tests with no network to end-to-end runs against a real environment.

## The mental model

A browser client serves one person.
A server serves many people at once, plus itself.
Mixing those identities up is the most serious mistake server code can make with a backend client.

| Server code acts as | Client | Policies |
| --- | --- | --- |
| The person who sent the request | A publishable-key base client, and `base.asUser(token)` per request | Applied, exactly as in their browser |
| Nobody in particular: the system | A secret-key client | Bypassed |
| A person, for a privileged step your code has checked | Both: `asUser` to read what they may see, the secret-key client for the step | Applied, then deliberately bypassed |

```text
request from Ada ──▶ your server ──▶ base.asUser(ada's token) ──▶ Pawabase sees Ada
request from Bob ──▶ your server ──▶ base.asUser(bob's token) ──▶ Pawabase sees Bob
nightly job      ──▶ your server ──▶ service (secret key)      ──▶ Pawabase sees the system
```

The base client is created once per process.
`asUser` returns a light, stateless client for one request: it holds that person's token, keeps no session, runs no timers, and is discarded when the request ends.

## Clients on a server

### The base client

Create one base client per process, at module scope, with a publishable key:

<CodeGroup>
```typescript TypeScript
// server/pawabase.ts
import { createClient } from "@pawabase/client";
import type { Database } from "./database";

export const base = createClient<Database>({
  url: process.env.PAWABASE_URL!,
  apiKey: process.env.PAWABASE_PUBLISHABLE_KEY!,
  environment: process.env.PAWABASE_ENV,
});
```

```python Python
# server/pawabase.py
import os

from pawabase import AsyncPawabase

base = AsyncPawabase(
    os.environ["PAWABASE_URL"],
    os.environ["PAWABASE_PUBLISHABLE_KEY"],
    environment=os.environ["PAWABASE_ENV"],
)
```
</CodeGroup>

A publishable key on a server is correct whenever the server acts for people.
It means a bug in your server cannot read or write more than the person could from their own browser.

### Per-request clients

`base.asUser(token)` gives each request a client that acts as its person:

<CodeGroup>
```typescript TypeScript
export function pawabaseFor(accessToken: string | null) {
  return accessToken ? base.asUser(accessToken) : base;
}
```

```python Python
def pawabase_for(access_token: str | None):
    return base.as_user(access_token) if access_token else base
```

```bash cURL
curl "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_PUBLISHABLE_KEY" -H "Authorization: Bearer $ACCESS_TOKEN"
```
</CodeGroup>

| Property of an `asUser` client | Value |
| --- | --- |
| Options | Copied from the base client |
| Token | The one you passed, or the value of a function you passed, read before each request |
| Session storage | Memory, empty |
| Automatic refresh | Off; a `401` is thrown |
| Realtime socket | Opens without a user token |
| Cost to create | A few objects; no network, no timers |

Never share an `asUser` client between requests, and never store one in module scope.
It holds one person's token; reusing it would let another request act as that person.

### The service client

Work that acts for the system uses a secret key, in a module only server code imports:


### A privileged step after your own check

Some actions need more authority than the person has, after a check only your server can make.
Use both clients: the person's to confirm what they may see, the service client for the step.

<CodeGroup>
```typescript TypeScript
export async function refundOrder(accessToken: string, orderId: string) {
  const asPerson = base.asUser(accessToken);
  const order = await asPerson.from("orders").get(orderId);
  if (order.status !== "paid") throw new Error("Only paid orders can be refunded.");
  const user = await asPerson.auth.getUser();
  if (!user.roles.includes("support")) throw new Error("Only support staff can refund.");
  return service.routes.post(`orders/${orderId}/refund`, { by: user.id });
}
```

```python Python
async def refund_order(access_token: str, order_id: str):
    as_person = base.as_user(access_token)
    order = await as_person.from_("orders").get(order_id)
    if order["status"] != "paid":
        raise ValueError("Only paid orders can be refunded.")
    user = await as_person.auth.get_user()
    if "support" not in user["roles"]:
        raise PermissionError("Only support staff can refund.")
    return await service.routes.post(f"orders/{order_id}/refund", {"by": user["id"]})
```
</CodeGroup>

Reading the order as the person proves they may see it; a `NotFoundError` there ends the action before anything privileged happens.
Often the same rule can live in a flow with `policy.check`, which keeps it in one place for every client; use server code when the check needs something only your server knows.

## Sessions on a server

### Where the session lives

A server-rendered application chooses where the session lives, and the choice decides how the client is used.

| Session in | Browser client | Server client | Refresh done by |
| --- | --- | --- | --- |
| The browser (`localStorage`) | Normal client | `asUser` with a token the browser sends in a header | The browser client |
| HTTP-only cookies | `persistSession: false`, or no client | `asUser` with the token from the cookie | Your server |

Pick one owner.
If the browser and the server both refresh the same session, the second refresh presents a refresh token the first already used, the auth service treats that as theft, and the session ends.

### Cookie sessions

With cookies, your server signs people in, stores tokens in cookies, refreshes them, and signs people out.
A short-lived, memory-only client does each auth step:

```typescript
import { createClient, MemoryStorage } from "@pawabase/client";

export function authClient() {
  return createClient({
    url: process.env.PAWABASE_URL!,
    apiKey: process.env.PAWABASE_PUBLISHABLE_KEY!,
    environment: process.env.PAWABASE_ENV,
    auth: { storage: new MemoryStorage(), persistSession: false, autoRefreshToken: false, detectSessionInUrl: false },
  });
}

export function sessionCookies(session: { access_token: string; refresh_token: string; expires_at: number }) {
  const flags = "Path=/; HttpOnly; Secure; SameSite=Lax";
  return [
    `pb-access=${session.access_token}; ${flags}; Expires=${new Date(session.expires_at * 1000).toUTCString()}`,
    `pb-refresh=${session.refresh_token}; ${flags}; Max-Age=${60 * 60 * 24 * 30}`,
  ];
}

export const clearedCookies = [
  "pb-access=; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=0",
  "pb-refresh=; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=0",
];
```

Refreshing, when the access cookie is missing or expired and the refresh cookie remains:

<CodeGroup>
```typescript TypeScript
export async function refresh(refreshToken: string) {
  const client = authClient();
  try {
    const wire = await client.request<{ access_token: string; refresh_token: string; expires_in: number; expires_at?: number }>(
      "POST",
      "/auth/v1/token",
      { body: { grant_type: "refresh_token", refresh_token: refreshToken } },
    );
    const expiresAt = wire.expires_at ?? Math.floor(Date.now() / 1000) + wire.expires_in;
    return { cookies: sessionCookies({ ...wire, expires_at: expiresAt }) };
  } catch {
    return { cookies: clearedCookies };
  } finally {
    client.dispose();
  }
}
```

### Refreshing in one place

Refresh tokens are single-use, so concurrent requests from the same browser must not all refresh.
Do it in one place, such as middleware that runs before handlers, and only when the access token is missing or about to expire.

```typescript
// middleware.ts (Next.js)
import { NextResponse, type NextRequest } from "next/server";
import { refresh } from "@/lib/pawabase/session";

export async function middleware(request: NextRequest) {
  const access = request.cookies.get("pb-access")?.value;
  const refreshToken = request.cookies.get("pb-refresh")?.value;
  if (access || !refreshToken) return NextResponse.next();

  const { cookies } = await refresh(refreshToken);
  const response = NextResponse.next();
  for (const cookie of cookies) response.headers.append("set-cookie", cookie);
  return response;
}
```

The access cookie expires with the token, so "missing" means "expired".
Browsers often send several requests at once after a page load; when they all arrive without an access cookie, only the first refresh succeeds.
For applications where that race matters, refresh from a single endpoint the page calls before others, or accept that the losing requests answer `401` and are repeated by the page.

## Frameworks

### Next.js with the App Router

| Place | Client |
| --- | --- |
| Server components | `pawabaseForRequest()` from the cookie |
| Server actions | `pawabaseForRequest()` |
| Route handlers | `pawabaseForRequest()`, or the service client for privileged routes |
| Middleware | Refresh only; keep data calls out of it |
| Client components | A browser client, or calls to your own server actions |

```typescript
// lib/pawabase/server.ts
import "server-only";
import { cookies } from "next/headers";
import { base } from "./base";

export async function pawabaseForRequest() {
  const token = (await cookies()).get("pb-access")?.value ?? null;
  return token ? base.asUser(token) : base;
}
```

```tsx
// app/orders/page.tsx
import { pawabaseForRequest } from "@/lib/pawabase/server";

export default async function OrdersPage() {
  const pawabase = await pawabaseForRequest();
  const { data } = await pawabase.from("orders").order("created_at", "desc").perPage(20);
  return <ul>{data.map((order) => <li key={order.id}>{order.id}</li>)}</ul>;
}
```

Responses rendered for one person must not be cached for others.
Pages that read cookies are dynamic in Next.js, which is what you want here; do not wrap per-person data calls in shared caches.

### Remix and React Router

Loaders and actions receive the request, so the per-request client comes from its cookie header:

```typescript
export async function loader({ request }: { request: Request }) {
  const pawabase = pawabaseFromRequest(request);
  return pawabase.from("orders").order("created_at", "desc").perPage(20);
}

function pawabaseFromRequest(request: Request) {
  const match = /(?:^|;\s*)pb-access=([^;]+)/.exec(request.headers.get("cookie") ?? "");
  return match ? base.asUser(decodeURIComponent(match[1])) : base;
}
```

### SvelteKit

`hooks.server.ts` builds the client once per request and puts it on `locals`:

### Express, Fastify and Hono

API servers that receive a bearer token from their own clients pass it through:

```typescript
import express from "express";

const app = express();

app.use((req, _res, next) => {
  const token = req.headers.authorization?.replace(/^Bearer /, "") ?? null;
  (req as express.Request & { pawabase: unknown }).pawabase = token ? base.asUser(token) : base;
  next();
});

app.get("/api/orders", async (req, res, next) => {
  try {
    const pawabase = (req as express.Request & { pawabase: typeof base }).pawabase;
    res.json(await pawabase.from("orders").perPage(20));
  } catch (error) {
    next(error);
  }
});
```

```typescript
import { Hono } from "hono";

const app = new Hono<{ Variables: { pawabase: typeof base } }>();

app.use("*", async (c, next) => {
  const token = c.req.header("authorization")?.replace(/^Bearer /, "") ?? null;

```

The token your clients send is a Pawabase access token from their own session.
Your server does not verify it; Pawabase does, on every request the per-request client makes.

### Serverless functions

Serverless platforms reuse a process for many invocations while it stays warm.
Create the base client outside the handler so warm invocations reuse it, and create per-request clients inside.

```typescript
const base = createClient({ url: process.env.PAWABASE_URL!, apiKey: process.env.PAWABASE_PUBLISHABLE_KEY! });

export const handler = async (event: { headers: Record<string, string | undefined> }) => {
  const token = event.headers.authorization?.replace(/^Bearer /, "") ?? null;
  const pawabase = token ? base.asUser(token) : base;
  const orders = await pawabase.from("orders").perPage(20);
  return { statusCode: 200, body: JSON.stringify(orders) };
};
```

Set timeouts below the platform's limit, with room for retries; see [Errors and retries](/clients/typescript/errors-retries#timeouts-on-edge-and-serverless-platforms).

### Edge workers

Edge workers receive configuration per request and may reuse an isolate for many requests.
Create the base client lazily from the first request's configuration:

```typescript
let base: ReturnType<typeof createClient> | null = null;

export default {
  async fetch(request: Request, env: { PAWABASE_URL: string; PAWABASE_KEY: string }) {
    base ??= createClient({ url: env.PAWABASE_URL, apiKey: env.PAWABASE_KEY, timeoutMs: 8000 });
    const token = request.headers.get("authorization")?.replace(/^Bearer /, "") ?? null;
    const pawabase = token ? base.asUser(token) : base;
    return Response.json(await pawabase.from("articles").eq("status", "live").perPage(10));
  },
};
```

### Long-running workers

A worker process that runs for days holds its clients for days.
That is fine for a secret-key client, which has no session to refresh.
A worker that signs in as a person, such as a command-line tool that runs a long sync, keeps its session refreshed by the client's timer, which does not keep the process alive on its own.

Call `dispose()` on clients you create dynamically, such as one per job, when the job ends.

## Testing: the levels

Code that uses Pawabase can be tested at four levels.
Each catches different mistakes, and a healthy project has some of each.

| Level | Talks to | Catches | Speed |
| --- | --- | --- | --- |
| Unit | A fake `fetch` | Wrong queries, wrong handling of answers and errors | Milliseconds |
| Component | A mocked network, such as MSW | Screens that render answers and errors wrongly | Fast |
| Integration | A real development or test environment | Wrong policies, wrong definitions, wrong assumptions about the server | Seconds |
| End to end | A browser driving your app against a real environment | Broken flows across pages, sessions, realtime | Slow |

Policies, channel rules and flows exist only on the server.
Only integration and end-to-end tests can check them.
Everything that is your own code, such as query building, error mapping and rendering, is cheaper to test at the first two levels.

## Unit tests with a fake server

Every client option that touches the network goes through `fetch`, so a fake `fetch` is a complete fake server.
A small helper that answers by method and path keeps tests short:

<CodeGroup>
```typescript TypeScript
// test/fake-pawabase.ts
import { createClient, type PawabaseClient } from "@pawabase/client";

type Handler = (request: { url: URL; method: string; body: unknown; headers: Headers }) => { status?: number; body?: unknown; headers?: Record<string, string> };

export function fakePawabase(routes: Record<string, Handler>) {
  const requests: Array<{ method: string; url: URL; body: unknown; headers: Headers }> = [];
  const client: PawabaseClient = createClient({
    url: "https://api.example.test",
    apiKey: "pb_pk_test",
    environment: "test",
    retry: false,
    fetch: async (input, init) => {
      const url = new URL(input);
      const method = (init?.method ?? "GET").toUpperCase();
      const headers = new Headers(init?.headers);
      const raw = init?.body;
      const body = typeof raw === "string" ? safeJson(raw) : raw;
      requests.push({ method, url, body, headers });
      const handler = routes[`${method} ${url.pathname}`];
      if (!handler) return new Response("Not found", { status: 404 });
      const answer = handler({ url, method, body, headers });
      return new Response(answer.body === undefined ? null : JSON.stringify(answer.body), {
        status: answer.status ?? 200,
        headers: { "content-type": "application/json", ...answer.headers },
      });
    },
  });
  return { client, requests, done: () => client.dispose() };
}

function safeJson(text: string) {
  try {
    return JSON.parse(text);
  } catch {
    return text;
  }
}

export const page = <T>(data: T[], total: number | null = data.length) => ({ body: { data, page: 1, per_page: 20, total } });
```

```python Python
# tests/fake_pawabase.py
import json

import httpx

from pawabase import Pawabase


class Wire:
    """A fake gateway: records requests and answers from a route table."""

    def __init__(self, routes: dict):
        self.routes, self.requests = routes, []

    def __call__(self, request: httpx.Request) -> httpx.Response:
        self.requests.append(request)
        handler = self.routes.get(f"{request.method} {request.url.path}")
        if handler is None:
            return httpx.Response(404, text="Not found")
        status, body = handler(request)
        return httpx.Response(status, json=body)


def fake_pawabase(routes: dict) -> tuple[Pawabase, Wire]:
    wire = Wire(routes)
    pb = Pawabase("http://gateway.test", "pb_pk_test", environment="test", retries=0)
    # The package's own tests swap the private httpx client for one with a MockTransport.
    pb._client = httpx.Client(transport=httpx.MockTransport(wire), base_url="http://gateway.test", headers=pb.headers)
    return pb, wire


def page(rows, total=None):
    return 200, {"data": rows, "page": 1, "per_page": 20, "total": len(rows) if total is None else total}
```

### Signed-in fakes

To test code that runs as a signed-in person, give the fake client a session first.
`setSession` fetches the user, so the fake answers `/auth/v1/user`:

```typescript
const fake = fakePawabase({
  "GET /auth/v1/user": () => ({ body: { id: "u1", email: "ada@example.com", roles: ["editor"], identities: [], user_metadata: {}, app_metadata: {} } }),
  "GET /rest/v1/tasks": ({ headers }) => (headers.get("authorization") ? page([{ id: "t1" }]) : { status: 401, body: "Authentication required" }),
});

await fake.client.auth.setSession({ access_token: fakeJwt({ exp: Math.floor(Date.now() / 1000) + 900 }), refresh_token: "r1" });

function fakeJwt(claims: Record<string, unknown>) {
  const encode = (value: unknown) => Buffer.from(JSON.stringify(value)).toString("base64url");
  return `${encode({ alg: "none" })}.${encode(claims)}.signature`;
}
```

The client reads the token's expiry from its payload without verifying the signature, so a fake token with an `exp` claim is enough in tests.
Never do this outside tests; the server verifies every real token.

## Integration tests against a real environment

Integration tests are the only way to check that policies, rules and flows do what you think.
They need an environment and keys, and they must leave the environment as they found it.

### Which environment

| Option | Pros | Cons |
| --- | --- | --- |
| A dedicated `test` environment | Isolated from developers' data; stable | Its definitions must be kept in step, by promotion |
| A preview environment per branch | Tests the branch's own definitions | Created and removed per run |
| The shared `development` environment | No setup | Tests and people disturb each other |

A dedicated environment, refreshed from development by promotion, suits most teams.
Preview environments suit teams that change definitions often in branches; the management module can create and delete them from CI.

### Test users

Tests need people with known identities and roles.
Create them with the user-administration module and a secret key, sign them in with normal clients, and delete them afterwards.

```typescript TypeScript
import { admin } from "@pawabase/client/admin";

  email: string;
  client: PawabaseClient;
```

### Testing policies as a matrix

Access rules are best tested as a table: who, what, and the expected outcome.

<CodeGroup>
```typescript TypeScript
import { test, before, after } from "node:test";

  { who: "someone else updating", act: () => bob.client.from("notes").update(noteId, { title: "x" }), expect: "PermissionError" },
];

for (const c of cases) {
  test(`notes: ${c.who}`, async () => {
    const outcome = await c.act().then(() => "ok", (error: Error) => error.name);
    assert.equal(outcome, c.expect);
  });
}
```

### Cleaning up

Tests that create data must remove it, or the environment slowly fills with leftovers that make later tests unreliable.

| Data | Clean up with |
| --- | --- |
| Records | The secret-key client, by id, in `after` hooks |
| Files | `listAll` on a per-run prefix, then `remove` |
| Users | `admin().users.deleteUser` |
| Organizations | `admin().orgs.remove` |
| Realtime | Nothing; channels disappear when unused |

Give everything a test run creates a recognizable marker, such as the run's timestamp in names and keys.
A periodic job can then remove anything older than a day with that marker, catching leftovers from crashed runs.

## End-to-end tests

End-to-end tests drive a browser through your application against a real environment.
They are slow and valuable: they are the only tests that see sessions, redirects, realtime and your interface working together.

### Signing in without the sign-in form

Signing in through the form in every test is slow and makes every test depend on the sign-in page.
Sign in once through the client, then put the session where the browser client looks for it.

The browser client stores its session in `localStorage` under `pawabase.auth.<gateway host>.<first 14 characters of the API key>`, as JSON.

```typescript
// e2e/auth.setup.ts (Playwright)
import { test as setup } from "@playwright/test";
import { createClient, MemoryStorage } from "@pawabase/client";

setup("sign in as Ada", async ({ page }) => {
  const url = process.env.PAWABASE_URL!;
  const apiKey = process.env.PAWABASE_PUBLISHABLE_KEY!;
  const client = createClient({ url, apiKey, auth: { storage: new MemoryStorage() } });
  const result = await client.auth.signInWithPassword({ email: process.env.ADA_EMAIL!, password: process.env.ADA_PASSWORD! });
  if (result.status !== "signed_in") throw new Error("Ada's test account must not require MFA");
  const storageKey = `pawabase.auth.${url.replace(/^https?:\/\//, "")}.${apiKey.slice(0, 14)}`;

  await page.goto(process.env.APP_URL!);
  await page.evaluate(([key, value]) => localStorage.setItem(key, value), [storageKey, JSON.stringify(result.session)]);
  await page.context().storageState({ path: "e2e/.auth/ada.json" });
  client.dispose();
});
```

Tests that use the saved storage state start signed in as Ada.
If your application stores sessions in cookies instead, set the cookies with the browser context's cookie API.

A storage key derived this way depends on the gateway URL and API key the application was built with.
Use exactly the same values in the setup as in the application under test.

## Test runners

The client works with every common runner.
A few settings matter.

| Runner | Notes |
| --- | --- |
| `node:test` | Built in; `mock.timers` fakes `Date` and `setTimeout` |
| Vitest | Use the `node` environment for client tests; `jsdom` adds a `window`, which makes the client behave as in a browser |
| Jest | Node 18 and later provide `fetch`; with `jsdom`, the same browser behavior applies |
| Playwright | For end-to-end tests; the client can also run in its setup files |

Two behaviors change when a test environment defines `window` and `document`, as `jsdom` does:

| Behavior | Effect in tests |
| --- | --- |
| Secret keys are refused | A test that creates a secret-key client in `jsdom` throws `ConfigError`; create it in a `node` environment, or pass `dangerouslyAllowBrowser` in that test only |
| Sessions use `localStorage` | Sessions persist between tests in the same file; use `MemoryStorage` or clear storage between tests |

Always dispose clients created in tests.
Refresh timers and realtime sockets otherwise keep running between tests, and some runners wait for them before exiting.

```typescript
import { afterEach } from "node:test";

const created: Array<{ dispose(): void }> = [];
export function track<T extends { dispose(): void }>(client: T) {
  created.push(client);
  return client;
}
afterEach(() => created.splice(0).forEach((client) => client.dispose()));
```

## Running tests in CI

| Concern | Practice |
| --- | --- |
| Keys | Store the test environment's publishable and secret keys in the CI secret store; never commit them |
| Environment | Point tests at a dedicated test or preview environment, never at production |
| Isolation | Unique names per run; parallel jobs never share records |
| Cleanup | `after` hooks, plus a scheduled sweep of leftovers |
| Rate limits | Keep concurrency modest; test traffic counts against the key's limit |
| Definitions | Promote definitions to the test environment before running tests that depend on them |

```text
jobs:
  test:
    steps:
      - npm ci
      - npm run types:check
      - npx tsc --noEmit
      - npm test                    # unit and component tests, no network
      - npm run test:integration    # against the test environment
        env: PAWABASE_URL, PAWABASE_ENV=test, PAWABASE_PUBLISHABLE_KEY, PAWABASE_SECRET_KEY
      - npx playwright test         # end to end, against a preview deployment
```

Run unit and component tests on every push, integration tests on every pull request, and end-to-end tests before releases or nightly.

### Rate limits and test traffic

The gateway's rate limit is counted per API key: every request made with one key shares one budget, 600 requests per minute by default.
A large parallel test suite can exhaust it, and a test environment shared with developers then slows down for everyone.

Give CI its own keys, so its traffic has its own budget.
The same reasoning applies in production: a server or batch job with its own key cannot use up the budget your browsers depend on.

## Flaky tests and their usual causes

| Symptom | Usual cause | Fix |
| --- | --- | --- |
| A test passes alone and fails in the suite | Shared data between tests | Unique names and ids per test |
| Random `401` failures | Two parts of the test refresh the same session | One client per test person; `persistSession: false` |
| Random `429` failures | Too much parallel traffic on one key | Lower concurrency; a separate key for CI |
| Realtime assertions time out | The screen asserted before the channel was joined | Wait for a "live" indicator first |
| Tests hang at the end | Clients not disposed | Dispose in `afterEach` |
| Lists contain unexpected rows | Leftovers from earlier runs | Filter by the run's marker; sweep leftovers |
| A policy test passes locally and fails in CI | Different definitions in the two environments | Promote before testing |

## Servers in production

### Logging with request ids

A server that calls Pawabase for its own clients should log both request ids: its own and Pawabase's.
Then one incident can be followed from your logs into **Project → Activity**.

```typescript
const base = createClient({
  url: process.env.PAWABASE_URL!,
  apiKey: process.env.PAWABASE_PUBLISHABLE_KEY!,
  hooks: {
    onResponse: ({ method, url, status, durationMs, requestId }) => {
      logger.info({ method, path: new URL(url).pathname, status, durationMs, pawabaseRequestId: requestId, requestId: currentRequestId() });
    },
  },
});

declare const logger: { info(fields: object): void };
declare function currentRequestId(): string | undefined;
```

`currentRequestId` would read your framework's per-request context, such as `AsyncLocalStorage` in Node.
Hooks are defined on the base client and inherited by every `asUser` client, so one definition covers all requests.

### Graceful shutdown

On shutdown, dispose long-lived clients so timers and sockets close cleanly:

```typescript
process.on("SIGTERM", () => {
  base.dispose();
  service.dispose();
  server.close(() => process.exit(0));
});

declare const server: { close(callback: () => void): void };
```

### Caching on servers

Server responses built from one person's data must not be cached for others.

| Data | Cacheable on your server |
| --- | --- |
| Public content read with the base client and no token | Yes, if it is the same for everyone |
| Data read through `asUser` | Only per person, keyed by the person |
| Data read with the service client | Only if your code makes it safe to share |

A shared cache keyed only by URL, in front of per-person data, is one of the most common ways data leaks between users.

### Organizations on servers

A per-request client carries whichever organization the person's token names.
A server that must act in another organization of the person needs a token issued for it, which only the person's session can request with `auth.switchOrg`.
For cookie sessions, have the browser call a server endpoint that switches organization with the refresh cookie and stores the new tokens, in the same way the refresh handler does.

## Integrations on your server

Third-party services call your application back: payment providers, email services, delivery partners.
Pawabase can receive those callbacks itself with [inbound hooks](/webhooks/inbound), which check the sender's signature and start a flow.
Receive them on your own server only when the handling needs code a flow cannot run.

```typescript
app.post("/webhooks/payments", express.raw({ type: "application/json" }), async (req, res) => {
  if (!verifyProviderSignature(req.body, req.headers["x-signature"])) return res.status(401).end();
  const event = JSON.parse(req.body.toString("utf8"));
  if (event.type === "payment.succeeded") {
    await service.from("orders").update(event.data.order_id, { status: "paid", payment_ref: event.data.id });
  }
  res.status(204).end();
});

declare function verifyProviderSignature(body: Buffer, signature: unknown): boolean;
```

Verify the signature against the raw body before parsing it.
Answer quickly, and make the handling safe to repeat, because providers retry deliveries; writing absolute values, as above, is naturally repeatable.

## Background workers

A worker process takes jobs from a queue, a schedule or a polling loop, and uses a secret-key client.
Three properties make it dependable.

| Property | How |
| --- | --- |
| Each job is safe to run twice | Absolute writes, unique keys, checks before side effects |
| Failures are classified | Transient errors are retried later; permanent ones are recorded |
| Progress is visible | Status fields on records, or messages to a person's realtime channel |

```typescript
async function processPendingInvoices() {
  for await (const invoice of service.from("invoices").eq("status", "pending").order("id")) {
    try {
      const pdf = await renderInvoice(invoice);
      const key = `${invoice.org_id}/invoices/${invoice.id}.pdf`;
      await service.storage.from("invoices").upload(key, pdf, { contentType: "application/pdf", timeoutMs: 0 });
      await service.from("invoices").update(invoice.id, { status: "issued", file_key: key });
    } catch (error) {
      if (isTransient(error)) continue;
      await service.from("invoices").update(invoice.id, { status: "failed", failure: String(error) });
    }
  }
}

declare function renderInvoice(invoice: unknown): Promise<Blob>;
declare function isTransient(error: unknown): boolean;
```

The upload goes to a fixed key and the update writes absolute values, so running the loop twice over the same invoice produces the same result.
Many workers like this can instead be flows on a schedule, which run inside Pawabase and keep their own run history; a worker earns its place when it needs libraries or runtimes a flow cannot use.

## Fetching in parallel during rendering

Server rendering waits for the slowest request on the page.
Start independent requests together:

```typescript
export async function dashboardData(pawabase: ReturnType<typeof base.asUser>) {
  const [orders, tasks, user] = await Promise.all([
    pawabase.from("orders").eq("status", "open").order("created_at", "desc").perPage(5),
    pawabase.from("tasks").eq("done", false).order("due_on").perPage(5),
    pawabase.auth.getUser(),
  ]);
  return { orders: orders.data, tasks: tasks.data, user };
}
```

With streaming frameworks, render the parts independently instead, so the fast parts appear first.
Either way, a `Promise.all` that rejects on the first failure takes the whole page down; use `Promise.allSettled` for sections that can fail on their own.

## Server keys and their safety

A secret key on a server is the credential with the most authority in your application.
Treat it accordingly.

| Practice | Why |
| --- | --- |
| Keep it in the platform's secret store, never in code or images | Keys in repositories and images spread to every copy |
| Import secret-key clients only from server-only modules | Bundlers follow imports into browser code |
| Restrict the key to your servers' addresses with **Allowed IP ranges** | A leaked key is useless from elsewhere |
| Give each service its own key | One leak or one rate-limit budget does not affect the others |
| Rotate keys with a grace period | Deployed servers switch without downtime |
| Never log option objects or headers | Keys end up in log storage |

When rotating, create the replacement with a grace period, deploy servers with the new key, and let the old one expire.
**Access → API keys** shows each key's **Last used** time, which confirms nothing still uses the old one.

## Testing server code

Server handlers that take a client as a dependency are easy to test with the fake server from the unit-test section.

```typescript
import { test } from "node:test";
import assert from "node:assert/strict";
import { fakePawabase, page } from "./fake-pawabase";

function ordersHandler(pawabaseFor: (token: string | null) => ReturnType<typeof fakePawabase>["client"]) {
  return async (request: Request) => {
    const token = request.headers.get("authorization")?.replace(/^Bearer /, "") ?? null;
    const result = await pawabaseFor(token).from("orders").perPage(20);
    return Response.json(result);
  };
}

test("the handler forwards the person's token", async () => {
  const fake = fakePawabase({ "GET /rest/v1/orders": () => page([{ id: "o1" }]) });
  const handler = ordersHandler((token) => (token ? fake.client.asUser(token) : fake.client));

  const response = await handler(new Request("https://app.test/api/orders", { headers: { authorization: "Bearer tok-1" } }));

```

`asUser` on the fake client keeps the fake transport, so the test sees exactly which token each request carried.

## Load testing

Load tests measure how your application and its Pawabase environment behave under traffic.
Two facts shape them.

| Fact | Consequence |
| --- | --- |
| The gateway's rate limit is per API key, 600 requests per minute by default | A load test on one key measures the limit, not the capacity |
| The client retries `429` after waiting | A load test that ignores retries reports slow responses instead of refusals |

Give the load test its own keys, ask your installation's operator about the limits that apply, and record retries with the `onRetry` hook so you can tell waiting from working.
Run load tests against a dedicated environment with production-like data, never against production itself.

## Tests recorded from real answers

Hand-written fixtures drift from what the server really returns.
Recording answers from a test environment once, and replaying them in unit tests, keeps fixtures honest.

```typescript
import { writeFileSync } from "node:fs";

export function recordingFetch(path: string): typeof fetch {
  const recorded: Record<string, unknown> = {};
  process.on("exit", () => writeFileSync(path, JSON.stringify(recorded, null, 2)));
  return async (input, init) => {
    const response = await fetch(input, init);
    const url = new URL(String(input));
    recorded[`${init?.method ?? "GET"} ${url.pathname}${url.search}`] = { status: response.status, body: await response.clone().json().catch(() => null) };
    return response;
  };
}
```

Run an integration test once with a client using `recordingFetch`, review the file, and commit it.
Unit tests then answer from the recording.
Re-record when definitions change so fixtures continue to match the deployed API.

Review recordings before committing them: they contain whatever the test environment returned, which must never be real people's data.

## Local development

Developers can run against a shared development environment or a Pawabase stack on their own machine.

| Setup | Pros | Cons |
| --- | --- | --- |
| A shared development environment | Nothing to install; shared definitions | Shared data; others' changes affect you |
| A local stack | Private data; works offline | Definitions must be kept in step with the shared environments |

A local stack's gateway is an `http://localhost` address, which the client accepts.
Its keys belong to the local environment, so a configuration that reads URL and key from the environment switches between the two without code changes.

## One deployment, several environments

Some products run one server deployment for several Pawabase environments, for example one per region or one per large customer.
Keep a base client per environment and choose by request:

```typescript
const bases = new Map<string, ReturnType<typeof createClient>>();

function baseFor(environment: string) {
  let client = bases.get(environment);
  if (!client) {
    const key = process.env[`PAWABASE_KEY_${environment.toUpperCase()}`];
    if (!key) throw new Error(`No key for ${environment}`);
    client = createClient({ url: process.env.PAWABASE_URL!, apiKey: key, environment });
    bases.set(environment, client);
  }
  return client;
}

export function pawabaseFor(environment: string, token: string | null) {
  const base = baseFor(environment);
  return token ? base.asUser(token) : base;
}
```

A person's token belongs to one environment.
Sending it to another environment's client fails with `401`, which protects against routing mistakes.

## Words used on this page

| Term | Meaning |
| --- | --- |
| Base client | One publishable-key client per process |
| Per-request client | `base.asUser(token)`, acting as one request's person |
| Service client | A secret-key client acting for the system |
| Session owner | The single place that refreshes a person's session |
| Test person | A user created for tests, signed in with its own client, deleted afterwards |
| Run marker | A value, such as a timestamp, added to names so a test run's data can be found and removed |

## Choosing an identity, task by task

| Task on the server | Identity | Client |
| --- | --- | --- |
| Rendering a page for a signed-in person | The person | `base.asUser(token)` |
| Rendering a public page | Anonymous | `base` |
| An API endpoint your app's browsers call | The person | `base.asUser(token)` |
| A webhook receiver for a payment provider | The system | `service` |
| A nightly report | The system | `service` |
| A support tool's "refund" button | The person to check, then the system to act | Both |
| Seeding test data | The system | `service` |
| A command-line tool a person runs | The person | A normal client with a stored session |

When a row seems to need the system, ask whether a flow with `policy.check` could do the privileged part instead.
A flow keeps the rule next to the data, where every client follows it, rather than in one server's code.

## Seeding test data

Tests and demos need data with known shapes.
A seed script with a secret key creates it, and it should be safe to run more than once.

```typescript
const plans = [
  { code: "free", name: "Free", price_minor: 0 },
  { code: "pro", name: "Pro", price_minor: 2900 },
];

export async function seedPlans() {
  for (const plan of plans) {
    const existing = await service.from("plans").eq("code", plan.code).first();
    if (existing) await service.from("plans").update(existing.id, plan);
    else await service.from("plans").create(plan);
  }
}
```

Looking up by a unique business key, here `code`, makes the script an upsert: the second run updates instead of duplicating.
For thousands of rows, the management module's `resources.importRecords(name, rows, { key: "code" })` does the same in one request; see [Environment management](/clients/typescript/management).

## Resetting a test environment

Integration suites are simpler when they start from a known state.
The management module can take a snapshot of an environment once it is seeded, and restore it before each suite run.

```typescript
import { manage } from "@pawabase/client/manage";

const m = manage(service, "test");

export async function captureBaseline() {
  return m.backups.snapshot("test-baseline", { note: "Seeded data for integration tests" });
}

export async function resetToBaseline(snapshotId: string) {
  return m.backups.restoreSnapshot(snapshotId, { strategy: "replace", confirm: "test", safetySnapshot: false });
}
```

A `replace` restore removes what the chosen parts hold before restoring, and requires the environment's name typed as `confirm`, so it cannot be run against the wrong environment by accident.
Use it only on environments that exist for testing.

## A preview environment per pull request

Teams that change definitions in pull requests can give each one its own environment, so tests run against the branch's definitions.

```typescript
const m = manage(service, "development");

export async function openPreview(prNumber: number) {
  return m.environments.createPreview(`pr-${prNumber}`, { expiresInHours: 72 });
}

export async function closePreview(prNumber: number) {
  return m.environments.deletePreview(`pr-${prNumber}`);
}
```

A preview copies its source environment's definitions and expires by itself, so a forgotten preview cleans itself up.
Previews have their own keys, and a key's secret is shown only when it is created.
Create keys for CI in the new preview with the management module, such as `manage(service, "pr-12").keys.create("ci", { role: "publishable" })`, and pass them to the test job.

## Integration tests for realtime

Channel rules can only be tested against a real environment.
Two signed-in test people, each with a client and a WebSocket, check that private channels stay private:

```typescript
import WebSocket from "ws";
import { RealtimeError, type WebSocketConstructor } from "@pawabase/client";

test("a person cannot join another person's channel", async () => {
  const ws = { realtime: { webSocket: WebSocket as unknown as WebSocketConstructor } };
  const ada = await person("ada", [], ws);
  const bob = await person("bob", [], ws);
  try {
    await ada.client.realtime.channel(`user:${ada.id}`).subscribe();
    const refused = await bob.client.realtime.channel(`user:${ada.id}`).subscribe().then(() => null, (error) => error);
    assert.ok(refused instanceof RealtimeError);
    assert.equal(refused.code, "forbidden");
  } finally {
    await Promise.all([forget(ada), forget(bob)]);
  }
});

declare function person(label: string, roles: string[], options: object): Promise<{ id: string; client: import("@pawabase/client").PawabaseClient }>;
declare function forget(p: { client: { dispose(): void } }): Promise<void>;
```

On Node 22 and later the global `WebSocket` works and the `ws` option can be dropped.
`dispose()` in `forget` closes each person's socket, which lets the test runner exit.

## A request's path through your server

```text
browser ──cookie pb-access──▶ your server
                               │ middleware: access cookie missing? refresh with pb-refresh, set new cookies
                               │ handler: pawabase = base.asUser(access token)
                               │          await pawabase.from("orders")…     ──▶ gateway ──▶ Pawabase (as the person)
                               │          await service.routes.post(…)       ──▶ gateway ──▶ Pawabase (as the system), only after checks
                               │ render with the results
                               ▼
browser ◀── HTML, set-cookie (when refreshed)
```

Each arrow into Pawabase carries exactly one identity, chosen by which client made the call.
Reading the handler's code, you can tell which identity each line uses, which is what makes the arrangement reviewable.

## Server rendering or browser calls

Some data can be fetched on the server while rendering or in the browser after the page loads.
The choice affects speed, caching and how sessions are handled.

| Consideration | Fetch on the server | Fetch in the browser |
| --- | --- | --- |
| First paint | Data is in the first HTML | A loading state first |
| Session | Cookie on the server | Session in the browser client |
| Realtime | Not possible during rendering | Natural |
| Caching per person | Your server must key caches by person | The browser holds its own data |
| Request count to Pawabase | One per page render | One per visit, then updates |

Many applications do both: the server renders the first view with `asUser`, and the browser takes over with realtime and its own client.
That works when the browser and the server agree on who owns the session, as described above.

## Readiness checks

Services that depend on Pawabase can include it in their readiness probe, so an orchestrator does not send traffic to an instance that cannot reach it.

```typescript
app.get("/ready", async (_req, res) => {
  try {
    const status = await base.status();
    res.status(status.ok ? 200 : 503).json({ pawabase: status.ok });
  } catch {
    res.status(503).json({ pawabase: false });
  }
});
```

`status()` needs no person and no policy, only an accepted key, so it tests exactly "can this instance reach Pawabase".
Keep it out of liveness probes: a Pawabase outage should stop traffic to the instance, not restart it.

## Performance on servers

| Practice | Effect |
| --- | --- |
| One base client per process | Connection reuse; no repeated setup |
| `asUser` per request | A few objects per request; no network, no timers |
| Parallel independent calls | Page time is the slowest call, not the sum |
| `select` the columns a page needs | Smaller answers, faster serialization |
| No per-request realtime connections | Sockets belong in browsers |
| Timeouts below your platform's limit | Clean errors instead of killed requests |

Creating a full client per request, instead of `asUser`, works but repeats setup work and, in browsers' absence, creates refresh machinery nobody uses.
It is the most common avoidable cost in server code.

## Common mistakes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| A secret key for everything on the server | Policies never apply; one bug exposes everyone's data | `asUser` with a publishable key for per-person work |
| An `asUser` client stored in module scope | Requests act as whoever was stored | Create per request |
| Browser and server both refreshing | Sessions end at random | One session owner |
| Caching per-person pages globally | People see each other's data | Cache per person, or not at all |
| Tests against production | Real data changed by tests | A test or preview environment |
| Clients not disposed in tests | Hanging test runs | Dispose in `afterEach` |
| One key for browsers, servers and CI | One budget for all traffic | Separate keys |

## Scripts and one-off tasks

One-off scripts, such as a data fix or a migration of records between fields, run with a secret key and change real data.
A few habits keep them safe.

```typescript
#!/usr/bin/env node
import { createClient } from "@pawabase/client";

const dryRun = !process.argv.includes("--apply");
const environment = process.env.PAWABASE_ENV!;
const service = createClient({ url: process.env.PAWABASE_URL!, apiKey: process.env.PAWABASE_SECRET_KEY!, environment });

let changed = 0;
for await (const customer of service.from("customers").is("country", null).select("id", "phone")) {
  const country = String(customer.phone ?? "").startsWith("+233") ? "GH" : null;
  if (!country) continue;
  changed += 1;
  if (!dryRun) await service.from("customers").update(customer.id, { country });
}
console.log(`${dryRun ? "Would change" : "Changed"} ${changed} customers in ${environment}.`);
service.dispose();
```

| Habit | Why |
| --- | --- |
| A dry run by default, with an explicit flag to apply | The first run shows what would change |
| The environment printed in the output | Running against the wrong environment becomes obvious |
| Absolute writes, selected by a condition the write removes | Running twice changes nothing more |
| A snapshot before large changes | `manage().backups.snapshot(…)` gives a way back |

## A testing checklist

| Check | Why |
| --- | --- |
| Query building and error mapping have unit tests with a fake server | Cheap, fast and precise |
| Screens are tested with real answer and error shapes | Rendering bugs are caught before users see them |
| Each resource's access rules have a matrix of integration tests | Policies are only tested against the server |
| Private channels are tested with two people | Channel rules are only tested against the server |
| Integration tests use their own environment and keys | Tests do not disturb people or production |
| Every test cleans up, and a sweep catches the rest | The environment stays usable |
| A few end-to-end tests cover sign-in, a core action and a live update | The pieces work together |

## What to watch on servers

| Metric | From | Tells you |
| --- | --- | --- |
| Pawabase request duration by route | `onResponse` | Which calls slow pages down |
| Retries by reason | `onRetry` | Whether the installation is struggling or limits are close |
| `401` rate after refresh | `onError` | Sessions ending unexpectedly |
| `429` rate by key | `onResponse` | How close each key is to its budget |
| Errors by class | `onError` | Regressions after releases |

## What the browser sends your server

When the browser owns the session and calls your own API, it must send the person's access token, and your server must pass it on unchanged.

```typescript
// in the browser
const token = await pawabase.auth.getAccessToken();
const response = await fetch("/api/orders", { headers: token ? { authorization: `Bearer ${token}` } : {} });
```

`getAccessToken()` refreshes first when the token is about to expire, so the server receives a token that is valid for at least the refresh margin.
Your server then builds `base.asUser(token)` from the header.

| Practice | Why |
| --- | --- |
| Send the access token only, never the refresh token | The server does not need to refresh, and should not be able to |
| Use the `authorization` header, not a query parameter | Query strings end up in logs |
| Answer `401` when the token is refused | The browser client then refreshes or signs the person out |

## Moving a browser app to server rendering

Applications often start as browser-only and add server rendering later.
The move changes where the session lives, and doing it in order avoids signing everyone out.

| Stage | Change |
| --- | --- |
| Start | Browser client with the session in `localStorage` |
| Add server reads | Browser sends its access token to your server; server uses `asUser` |
| Move the session to cookies | Server sign-in and refresh endpoints; browser client with `persistSession: false` |
| Remove token passing | Server reads tokens from cookies; the browser no longer sends them |

During the third stage, people who are signed in through `localStorage` keep that session until it ends.
Let the browser client adopt the cookie-based flow at their next sign-in rather than forcing everyone out at once.

A practical way to do that is a small migration endpoint.
On page load, a browser that still holds a `localStorage` session sends its refresh token once to your server, which exchanges it for new tokens, sets the cookies, and answers with success.
The browser then removes its stored session.
Because the exchange rotates the refresh token, the browser must stop using its old session immediately after the call, or the next refresh from either side would present a consumed token and end the session.

Remove the migration endpoint after a few weeks, when sessions older than the move have expired on their own.
Keep an eye on the `401` rate after refresh during the move; a rise means two owners are still refreshing somewhere.

| Signal during the move | Meaning |
| --- | --- |
| `SIGNED_OUT` events spike in browsers | The browser client is still refreshing a session the server now owns |
| Migration endpoint errors with `401` | The browser sent a refresh token that was already rotated |
| Pages render signed out for signed-in people | Cookies are not reaching the server: check their path and domain |

Each of these points to a specific fix, and none requires signing everyone out.
Watch them for a week after the move, then remove the migration code with the confidence that every session has a single owner.
Write down the date of the move in the code that remains, so the next person knows why cookies and tokens are handled the way they are.

## Debugging identity mix-ups

When someone reports seeing data that is not theirs, or not seeing data that is, the question is which identity each request carried.

| Step | How |
| --- | --- |
| Find the request | The Pawabase request id in your server's logs, from the `onResponse` hook |
| See who it ran as | The request in **Project → Activity** shows the caller |
| Compare with the person | If the caller differs, a client was shared or cached between requests |
| Check caches | Any cache in front of per-person data must be keyed by person |

Mix-ups almost always come from a shared `asUser` client, a module-level variable holding a token, or a cache keyed without the person.
Each is visible in code review once you know to look for it.

## Troubleshooting

| Symptom | Cause | What to do |
| --- | --- | --- |
| One person sees another's data | An `asUser` client or its result was shared between requests, or cached | Create per request; cache per person |
| `ConfigError` about secret keys in tests | The test environment defines `window` | Use a `node` environment for that test |
| Server requests fail with `401` after a while | Per-request tokens expired and nobody refreshed them | Refresh in middleware |
| Sessions end unexpectedly | The browser and the server both refresh | Choose one owner of the session |
| `429` under load from a server | All traffic shares one key's budget | Separate keys for servers and jobs; spread work |
| Edge functions time out | Client timeouts and retries exceed the platform limit | Lower `timeoutMs` and retries |
| Tests leave users and records behind | Missing cleanup, or crashes before cleanup | `after` hooks plus a scheduled sweep |

## Questions developers ask

<AccordionGroup>
  <Accordion title="Can my server verify a Pawabase access token itself?">
    The client does not verify tokens; it forwards them, and Pawabase verifies them on every request.
    A server that needs the person's identity before calling anything can call `asUser(token).auth.getUser()`, which fails with `401` for an invalid token.
  </Accordion>
  <Accordion title="Should my server use the person's token or a secret key?">
    The person's token, through `asUser`, whenever the server acts for them.
    Use a secret key only for work that is not on anyone's behalf, or for a privileged step after your own check.
  </Accordion>
  <Accordion title="Can I run integration tests against production?">
    Do not.
    Tests create and delete users and records, and a bug in a test can do real damage.
    Use a test or preview environment with the same definitions.
  </Accordion>
  <Accordion title="How do I test MFA flows?">
    Unit-test them with a fake server that answers `mfa_required`.
    For integration tests, enroll a test user's authenticator with a known secret and compute codes in the test with a TOTP library.
  </Accordion>
  <Accordion title="Can tests share one signed-in person?">
    Within one test file, yes, if the tests do not change that person's session.
    Across parallel files, give each its own person, because a sign-out or MFA change in one would affect the others.
  </Accordion>
  <Accordion title="How do I test code that uses `manage()` or `admin()`?">
    Unit-test it with the fake server, answering `/platform/v1/envs/<env>/…` paths.
    Integration-test it only against environments that exist for testing, because these modules change configuration and users.
  </Accordion>
  <Accordion title="Do per-request clients share connections?">
    Yes, through the runtime's `fetch`, which pools connections to the gateway across all clients in the process.
  </Accordion>
  <Accordion title="Can I use the client in a Node worker thread?">
    Yes.
    Each thread has its own clients and its own `fetch`; create them inside the worker.
  </Accordion>
</AccordionGroup>
