Functions, flows, and custom routes all run server-side behavior, but they are not interchangeable client aliases.
Each surface has a different public address and product meaning.

| Surface | SDK entry point | Public path family | Use |
| --- | --- | --- | --- |
| Function | `client.functions.invoke()` | `/functions/v1/<name>` | Invoke deployed project code by function name |
| Pathless HTTP flow | `client.flows.run()` | `/flows/v1/<name>` | Run a flow whose HTTP trigger has no custom path |
| Custom route | `client.routes.*()` | `/rest/v1/<path>` | Call an application-specific method and path |
| Other public endpoint | `client.request()` | Supplied gateway path | Use a documented public route without a dedicated SDK method |

The choice begins in Studio.
Inspect the deployed function, the flow's trigger, or the custom route definition and its access policy.
Use **API Explorer** for operations included in the environment's generated API document.

## Shared call options

Functions, flows, and routes share transport controls.

| Option | Type | Meaning |
| --- | --- | --- |
| `headers` | `Record<string, string>` | Per-call headers |
| `signal` | `AbortSignal` | Caller cancellation |
| `timeoutMs` | `number` | Per-attempt timeout |
| `idempotent` | `boolean` | Declares that retrying a normally unsafe call is harmless |

The configured API key and current user token are attached automatically.
Policies and key scopes still decide whether invocation is allowed.

## Invoke a function

```typescript
interface PriceInput {
  sku: string;
  quantity: number;
}

interface PriceResult {
  subtotal: number;
  currency: string;
}

const price = await client.functions.invoke<PriceResult>(
  "price",
  {
    sku: "engine-01",
    quantity: 2,
  } satisfies PriceInput,
);
```

The result generic describes the expected response for TypeScript.
It does not validate the runtime body.
Use runtime validation when function output can drift independently from the calling application.

When the public function response uses the standard `{ data: ... }` envelope, `invoke()` returns the value inside `data`.
Function error codes and structured details remain available on the thrown `ApiError`.

The key needs the relevant function invocation scope unless it is unrestricted.
The function's public access rules can also require or inspect the signed-in user.

## Function call options

```typescript
const controller = new AbortController();

const result = await client.functions.invoke(
  "build-report",
  { report_id: reportId },
  {
    timeoutMs: 45_000,
    signal: controller.signal,
    headers: {
      "x-correlation-id": correlationId,
    },
  },
);
```

Choose a timeout that matches the function's public response contract.
Long background work should normally return a job or run identifier rather than keep a browser request open without a bounded deadline.

## Run a pathless flow

`flows.run(name, input, options)` calls a flow whose HTTP trigger has no path.

```typescript
interface WelcomeResult {
  queued: boolean;
  recipient: string;
}

const result = await client.flows.run<WelcomeResult>(
  "send-welcome",
  {
    user_id: user.id,
  },
);
```

The return value is the flow's configured response body.
When the flow has no explicit response-return block, the API returns the flow result inside its documented data shape.

A flow bound to a custom path is called through `routes`, not `flows.run()`.
The trigger configuration determines the public surface.

## Call a custom route

Routes support method-specific helpers plus a general `call()`.

```typescript
const checkout = await client.routes.post<CheckoutResult>(
  "checkout/start",
  {
    cart_id: cart.id,
  },
  {
    query: {
      dry_run: false,
    },
  },
);
```

Paths are relative to `/rest/v1`.
Do not include the service prefix in the helper path.

| Method | Signature intent |
| --- | --- |
| `get(path, options?)` | Query and headers, no body option |
| `post(path, body?, options?)` | Create/action-style route |
| `put(path, body?, options?)` | Replacement or idempotent command when the route contract says so |
| `patch(path, body?, options?)` | Partial change |
| `delete(path, options?)` | Removal or delete command |
| `call(method, path, options?)` | Dynamic or less common HTTP method |

## Route query values

The `query` object accepts scalar query values and arrays supported by the shared URL serializer.

```typescript
const report = await client.routes.get<Report>("reports/activity", {
  query: {
    from: "2026-10-01",
    to: "2026-10-31",
    status: ["open", "closed"],
    include_archived: false,
  },
});
```

Use the route's documented parameter names.
The SDK serializes values but cannot infer business validation or change an undocumented parameter into a supported one.

## Dynamic methods with `call()`

```typescript
const response = await client.routes.call(
  "OPTIONS",
  "integrations/capabilities",
  {
    headers: {
      "x-integration": "accounting",
    },
  },
);
```

Prefer method-specific helpers for ordinary REST methods because they make the presence or absence of a body clear.

## Raw gateway requests

`client.request(method, path, options?)` calls another public path with shared authentication, errors, and transport policy.

```typescript
const result = await client.request<ImportStatus>(
  "GET",
  `/imports/v1/${encodeURIComponent(importId)}`,
  {
    query: {
      include_errors: true,
    },
    signal: controller.signal,
  },
);
```

Raw request options include `body`, `query`, `headers`, and `signal`.
Use a leading slash and a documented public gateway path.

Do not use `request()` to reach private service endpoints or bypass a missing SDK feature by guessing a path.
Use the public API contract as the source of truth.

## User identity on invocation

The shared client attaches the managed user's token when one exists.
A request-scoped server can use `asUser()`.

```typescript
const userClient = baseClient.asUser(accessToken);

const result = await userClient.routes.post(
  "orders/confirm",
  { order_id: orderId },
);
```

The API key and token answer different questions.
The key selects environment and scope.
The token identifies the application user.
The route, function, or flow policy may evaluate both.

## Secret-key invocation

A trusted server may use a secret key where policy bypass is intentional.

```typescript
const admin = createClient({
  url: process.env.PAWABASE_URL,
  apiKey: process.env.PAWABASE_SECRET_KEY,
});

await admin.functions.invoke("reconcile-ledger", {
  date: "2026-10-09",
});
```

Secret-key use moves the authorization boundary into your server.
Validate the caller before invoking Pawabase and restrict key scopes and deployment access.
Never proxy an unrestricted secret-powered function directly from untrusted input without an application authorization check.

## Retry safety and `idempotent`

Functions, flows, and most action routes use `POST`.
After a network failure, the client cannot know whether the server ran the action and only the response was lost.
The SDK therefore does not retry such a call by default.

Set `idempotent: true` only when repeating the exact operation is harmless.

```typescript
const result = await client.functions.invoke(
  "rebuild-derived-view",
  { view: "daily_totals" },
  {
    idempotent: true,
  },
);
```

Good candidates are operations keyed by a stable idempotency identifier or operations that set a deterministic final state.
Bad candidates include charging a card, sending an email, creating an unkeyed record, or incrementing a counter.

| Operation | Usually safe to declare idempotent? | Reason |
| --- | --- | --- |
| Recompute cache for a named date | Often | Repetition produces the same derived state |
| Upsert by a stable external ID | Often, if the route contract guarantees it | Duplicate submissions collapse to one identity |
| Charge payment | No without provider idempotency | Could charge twice |
| Send invitation email | No | Could send duplicates |
| Increment usage counter | No | Repetition changes state again |
| Start unkeyed workflow | No | Could create multiple runs |

`idempotent` is a client assertion.
It does not make server behavior idempotent.

## Cancellation

Use `AbortSignal` when a route result is no longer needed or a server process has a request deadline.

```typescript
const controller = new AbortController();

const pending = client.flows.run(
  "preview-import",
  payload,
  { signal: controller.signal },
);

controller.abort();
```

Cancellation stops the caller from waiting.
It does not prove that server execution was rolled back.
For stateful work, expose a run ID and an explicit cancel operation if the product needs cancel semantics.

## Response typing

The generic type parameter affects TypeScript only.

```typescript
interface RouteResult {
  order_id: string;
  state: "pending" | "confirmed";
}

const result = await client.routes.post<RouteResult>(
  "orders/confirm",
  { order_id: id },
);
```

Keep the type close to the public route contract.
If the route is included in generated OpenAPI but the SDK generator does not emit route method types, maintain and runtime-test the response schema explicitly.

## Error behavior

All four surfaces use the common error hierarchy.

| Error | Typical meaning here |
| --- | --- |
| `AuthenticationError` | Invalid key/token or required user absent |
| `PermissionError` | Key scope or access policy refused invocation |
| `NotFoundError` | No deployed name/path, or a policy hides it |
| `ValidationError` | Input, query, or path parameters were rejected |
| `ConflictError` | Current server state conflicts with the requested action |
| `RateLimitError` | Caller exceeded the applicable limit |
| `ServerError` | Invocation infrastructure or behavior failed with `5xx` |
| `TimeoutError` | An attempt exceeded the configured client deadline |
| `NetworkError` | No response was obtained; execution may be ambiguous for writes |

Function and flow errors may carry structured `details` and a stable server code.
Preserve `requestId` and use **Observability** to correlate a failure with platform logs and run history.

## Choosing the surface

| Requirement | Prefer |
| --- | --- |
| Execute deployed application code by stable name | Function |
| Orchestrate blocks and integrations from a no-path HTTP trigger | Flow |
| Expose a domain-specific URL and HTTP method | Custom route |
| Call a documented public API not wrapped by the package | Raw `request()` |
| Perform ordinary resource CRUD | `from(resource)` rather than any of these |
| Transfer an object | `storage` rather than a custom body proxy |

The narrowest public surface usually communicates policy and failure semantics most clearly.

## Function response envelopes

Functions use the standard invocation envelope on successful responses.
`functions.invoke<T>()` returns the value inside `data` when that envelope is present.

```json
{
  "data": {
    "subtotal": 4200,
    "currency": "USD"
  }
}
```

The application receives the inner object as `PriceResult`.
Flows differ: `flows.run<T>()` returns the public response body as sent by the flow.
Do not reuse one response-unwrapping assumption across both clients.

## Flow response design

A flow with a response-return block can define a domain-specific status and body.
A flow without one returns its result under the platform's default data response.

Client code should depend on the flow's documented public response rather than its internal block state.
Changing intermediate variables should not require a client release when the response contract remains stable.

```typescript
interface ImportAccepted {
  run_id: string;
  state: "queued";
}

const accepted = await client.flows.run<ImportAccepted>(
  "start-customer-import",
  { object_key: upload.key },
);
```

For long work, return a run identifier and let the client poll a resource/route or receive a realtime notification.

## Path ownership and encoding

Route helpers accept a relative custom path.
When a path includes a user-controlled identifier, encode that segment.

```typescript
const order = await client.routes.get<OrderResult>(
  `orders/${encodeURIComponent(orderId)}`,
);
```

Do not encode the complete path string because that would encode intended slash separators.
Do not append a query string manually when the `query` option can represent it.

## Repeated query parameters

Array values become repeated keys.

```typescript
await client.routes.get("reports/orders", {
  query: {
    status: ["pending", "paid"],
    created_after: new Date("2026-10-01T00:00:00Z"),
  },
});
```

The corresponding URL shape is conceptually:

```text
?status=pending&status=paid&created_after=2026-10-01T00%3A00%3A00.000Z
```

The route schema must define how repeated parameters are interpreted.

## Per-call headers

Use per-call headers for documented route inputs and correlation values.

```typescript
await client.routes.post(
  "integrations/dispatch",
  payload,
  {
    headers: {
      "x-idempotency-key": operationId,
      "x-correlation-id": correlationId,
    },
    idempotent: true,
  },
);
```

An idempotency header matters only when the server behavior reads it and deduplicates correctly.
The SDK's `idempotent` flag permits transport retry; it does not implement server deduplication.

## API version paths

`RoutesClient` targets `/rest/v1`.
If the application needs another published API version and the SDK has no version option for that route, use the root raw request with the explicit documented path.

```typescript
const result = await client.request(
  "GET",
  "/rest/v2/reports/summary",
);
```

Keep version choice in one application integration layer.
Mixing v1 and v2 route paths throughout UI code makes migration and error diagnosis difficult.

## Raw request body behavior

`client.request()` accepts an object body and serializes it as JSON through the shared transport.

```typescript
const response = await client.request(
  "POST",
  "/imports/v1/validate",
  {
    body: {
      object_key: objectKey,
      mode: "strict",
    },
  },
);
```

The root method intentionally returns parsed JSON and exposes the application-level option set.
Use a dedicated capability client when the response is text, bytes, a stream, or a signed transfer because those clients choose the correct parser and credential model.

## Status health versus operation health

`client.status()` can show that platform services are generally reachable.
It cannot show that a particular function is deployed, a flow trigger is enabled, a route path matches, or a caller passes policy.

```typescript
const health = await client.status();

if (!health.ok) {
  showPlatformUnavailable(health.services);
}
```

Use the actual invocation and its request ID for operation-specific evidence.

## Type-safe boundary validation

A result generic disappears at runtime.
For external or independently deployed behavior, validate before trusting the body.

```typescript
const raw = await client.routes.get<unknown>("billing/summary");
const summary = BillingSummarySchema.parse(raw);
```

This is especially important when the response controls money, permissions, navigation, or durable client state.

## Error normalization from behavior

Function and flow failures can return `{ error, message, details }`.
The SDK preserves the server code and structured details in `ApiError`.

```typescript
try {
  await client.functions.invoke("price", input);
} catch (error) {
  if (error instanceof ApiError && error.is("catalog_item_missing")) {
    showMissingSku(error.details);
    return;
  }
  throw error;
}
```

Treat only documented stable codes as application control flow.
Preserve `requestId` for all unexpected outcomes.

## Observing invocation attempts

HTTP hooks run per attempt, so a retried idempotent call can emit several request observations and one final response.

Include operation name as application context outside the hook because the generic hook sees method and URL, not the domain meaning.

```typescript
async function invokeObserved<T>(name: string, input: unknown) {
  const started = performance.now();

  try {
    return await client.functions.invoke<T>(name, input);
  } finally {
    metrics.timing(
      "pawabase.function.total_ms",
      performance.now() - started,
      { name },
    );
  }
}
```

Do not record the input by default; function and flow bodies can contain private user data or credentials for downstream integrations.

## Testing invocation clients

Unit tests should verify the public distinctions between the three clients.

| Test | Expected behavior |
| --- | --- |
| Function success envelope | Returns inner `data` |
| Flow success | Returns response body as sent |
| Custom route | Preserves method, relative path, query, and body |
| Function error | Retains server code and details |
| Unsafe POST transient failure | No retry by default |
| Explicit idempotent POST | Retries eligible transient failure |
| Caller abort | Throws `AbortError` and does not retry |

Integration tests should verify deployed names, route methods, policies, scopes, and the active environment.
See [server runtimes and testing](/clients/typescript/server-runtimes-testing).

## Studio and runtime troubleshooting

| Symptom | Check in Studio | Check in code |
| --- | --- | --- |
| Function `404` | Deployment name and active environment | Exact function name and key environment |
| Flow `404` | HTTP trigger form and whether it has a path | Use `flows.run` only for pathless trigger |
| Route `404` | Enabled route, method, path, active version | Relative path and chosen helper |
| `403` | Access policy and key scope | User session and key type |
| `422` | API Explorer request schema | Input and query names/types |
| Timeout | Observability duration and run history | `timeoutMs` and whether synchronous response is appropriate |
| Duplicate side effect | Run history and external provider log | Remove unsafe retry/idempotent assertion; add stable request identity |
