The TypeScript auth client connects two concerns that application code often confuses:

- an identity flow proves who the user is and issues a session;
- the session supplies an access token to later Pawabase calls.

Signing in does not itself grant access to resources, storage, routes, or channels.
Those operations still evaluate key scopes and policies against the resulting auth context.

In Studio, use **Users & auth** for application users and authentication configuration.
This is different from Pawabase Cloud organization membership.
`client.auth.orgs` manages organizations inside the application auth system, not the Cloud account that owns hosted projects.

## Managed-session model

By default, a browser client reads a stored session, refreshes it shortly before expiry, writes replacements back to storage, and attaches the access token to SDK requests.

```text
Stored Session
     │
     ├── access_token ──> Authorization header
     │
     ├── refresh_token ─> exchanged when access is expiring
     │
     └── user ──────────> cached UI identity
```

Refresh tokens rotate.
The client prevents concurrent calls from exchanging the same token independently.
Concurrent requests share one in-flight refresh.
Browser tabs use the Web Locks API where available to serialize refresh across tabs.

<Warning>
  Do not add an independent refresh loop around the managed client.
  Two owners can race a rotating refresh token and turn a recoverable expiry into sign-out.
</Warning>

## Auth configuration

The constructor's `auth` object controls session ownership.

| Option | Default | Decision |
| --- | --- | --- |
| `storage` | `localStorage` in a usable browser; memory elsewhere | Where serialized session state lives |
| `storageKey` | Derived from URL and key | How the session is namespaced |
| `persistSession` | `true` | Whether a restart can restore the session |
| `autoRefreshToken` | `true` | Whether the client schedules refresh |
| `refreshMarginSeconds` | `60` | How early the access token counts as expiring |
| `detectSessionInUrl` | Browser `true` | Whether redirect fragments are processed automatically |

```typescript
const client = createClient({
  url,
  apiKey,
  auth: {
    persistSession: true,
    autoRefreshToken: true,
    refreshMarginSeconds: 60,
    detectSessionInUrl: true,
  },
});
```

An `accessToken` constructor option disables the managed-session machinery.
Use it for request-scoped server work where another layer owns token refresh.

## Auth initialization

The auth client reads storage asynchronously when necessary.
Public auth methods wait for that work internally.
`initialized()` is useful when the UI must delay its first identity-dependent render.

```typescript
await client.auth.initialized();
const cachedUser = await client.auth.getCachedUser();
```

`getCachedUser()` reads the user in the stored session without a network request.
It can be stale.
`getUser()` asks the server and updates the cached session copy.

## Auth state events

`onAuthStateChange()` registers a listener and soon calls it with `INITIAL_SESSION`.
It returns an unsubscribe function.

```typescript
const subscription = client.auth.onAuthStateChange((event, session) => {
  switch (event) {
    case "INITIAL_SESSION":
    case "SIGNED_IN":
    case "TOKEN_REFRESHED":
    case "USER_UPDATED":
      renderIdentity(session?.user ?? null);
      break;
    case "SIGNED_OUT":
      renderIdentity(null);
      break;
  }
});

subscription.unsubscribe();
```

| Event | Meaning |
| --- | --- |
| `INITIAL_SESSION` | Storage initialization completed; session may be `null` |
| `SIGNED_IN` | A flow established a session |
| `SIGNED_OUT` | Local session was cleared |
| `TOKEN_REFRESHED` | Access and refresh tokens were replaced |
| `USER_UPDATED` | Profile or account state changed |

Keep listener work short.
Use application state to schedule larger data loads rather than blocking auth notifications.

## Sign up

`signUp()` creates an application account under the active environment's auth settings.

```typescript
const result = await client.auth.signUp({
  email: "ada@example.com",
  password,
  username: "ada",
  name: "Ada Lovelace",
  data: {
    theme: "dark",
  },
  redirectTo: "https://app.example.com/auth/confirmed",
});
```

| Result field | Meaning |
| --- | --- |
| `user` | Created user representation |
| `session` | Session when confirmation is not required; otherwise `null` |
| `verificationRequired` | Whether the address must be confirmed before sign-in completes |

Do not assume account creation always signs the user in.
Branch on `verificationRequired` or `session` and show the appropriate confirmation state.

`data` becomes user-editable `user_metadata`.
Never place roles, billing entitlement, tenant authority, or other trusted authorization facts there.
Use server-controlled metadata and policies for trusted decisions.

## Password sign-in and MFA

`signInWithPassword()` returns a discriminated union.

```typescript
const result = await client.auth.signInWithPassword({
  email,
  password,
});

if (result.status === "signed_in") {
  enterApplication(result.session);
} else {
  showMfaForm(async (code) => {
    const session = await result.verify(code);
    enterApplication(session);
  });
}
```

| Status | Available data | Application response |
| --- | --- | --- |
| `signed_in` | `session` | Continue with the authenticated application |
| `mfa_required` | `mfaToken`, `factors`, `verify(code)` | Collect an authenticator or recovery code |

The convenience `verify()` function captures the MFA token.
Code that stores the challenge separately can call `verifyMfa({ mfaToken, code, org? })`.

## Sessions and access tokens

`getSession()` returns the current session or `null`.
It refreshes first when the access token is near expiry.

```typescript
const session = await client.auth.getSession();

if (!session) {
  showSignIn();
}
```

`getAccessToken()` returns only the bearer value or `null` and uses the same refresh behavior.
Prefer SDK calls over extracting a token merely to call Pawabase with `fetch`; the SDK already attaches it.

The session wire shape includes:

| Field | Meaning |
| --- | --- |
| `access_token` | Short-lived bearer credential |
| `refresh_token` | Rotating credential used to renew access |
| `token_type` | `bearer` |
| `expires_in` | Issued lifetime in seconds |
| `expires_at` | Unix expiry time in seconds |
| `session_id` | Session identifier when supplied |
| `org` | Current application organization slug or `null` |
| `org_role` | Current application organization role or `null` |
| `user` | Current user snapshot |

Treat both tokens as secrets.
Do not log the session object.

## Refresh behavior

`refreshSession()` explicitly exchanges the refresh token and stores the replacement.

```typescript
const session = await client.auth.refreshSession();
```

Normal application code rarely needs to call it because accessors and the request transport refresh when necessary.
It is useful after a known authorization-context change when the server must issue new claims.

An optional `org` value requests tokens for an application organization context.

```typescript
const session = await client.auth.refreshSession({
  org: "acme",
});
```

Refresh exchange is not automatically retried after a network failure.
The server may have rotated the token even though the response was lost.
Replaying the old token can look like theft.

## Adopting a session

`setSession()` accepts both tokens from an external handoff and fetches the user before adopting them.

```typescript
const session = await client.auth.setSession({
  access_token,
  refresh_token,
});
```

Use it for a controlled mobile deep link or server-to-client handoff.
Do not accept arbitrary tokens from an untrusted message source.

## Magic links

`signInWithMagicLink()` sends a one-time sign-in email.
Its outward response does not reveal whether the account exists.

```typescript
await client.auth.signInWithMagicLink({
  email: "ada@example.com",
  redirectTo: "https://app.example.com/auth/callback",
  createUser: true,
});
```

`verifyMagicLink(token)` exchanges the emailed token and returns the same sign-in union as password sign-in because MFA can still be required.

```typescript
const result = await client.auth.verifyMagicLink(token);

if (result.status === "mfa_required") {
  await result.verify(code);
}
```

Redirect targets must be allowed by the environment's auth configuration.

## Social sign-in

Social sign-in is a browser navigation, not an ordinary JSON request.
The generated URL explicitly names the project and environment, so both constructor hints are required.

```typescript
const client = createClient({
  url,
  apiKey,
  project: "acme",
  environment: "production",
});

client.auth.signInWithOAuth("github", {
  redirectTo: "https://app.example.com/auth/callback",
});
```

`signInWithOAuthUrl()` returns the URL without navigating.
Use it when a framework router, a popup, or a mobile browser owner performs navigation.

```typescript
const authorizeUrl = client.auth.signInWithOAuthUrl("github", {
  redirectTo: callbackUrl,
});
```

After redirect, browser clients process the URL fragment automatically when `detectSessionInUrl` is enabled.
`getSessionFromUrl(url?)` exposes the same parser for manual and mobile handling.

| URL result | Meaning |
| --- | --- |
| `signed_in` | A session was stored |
| `mfa_required` | Complete the returned challenge with `verify(code)` |
| `linked` | A provider identity was linked to the signed-in user |
| `error` | The redirect carries an auth error |
| `none` | No recognized auth result is present |

The parser cleans a browser URL after consuming tokens so credentials do not remain in location history longer than necessary.

## Email verification and changes

The auth client separates initial verification from email-change confirmation.

| Method | Purpose | Result |
| --- | --- | --- |
| `resendVerification({ email, redirectTo? })` | Send the initial confirmation again | `void` |
| `verifyEmail(token)` | Confirm the initial address | A signed-in `Session` |
| `updateUser({ email })` | Start an email change | Updated `User` state |
| `confirmEmailChange(token)` | Confirm the new address | `void` |

Resend calls intentionally avoid account-enumeration detail.
Show the same outward confirmation whether or not an address is registered.

## Password recovery

Recovery has a request phase and a token-consumption phase.

```typescript
await client.auth.requestPasswordReset({
  email,
  redirectTo: "https://app.example.com/reset-password",
});
```

```typescript
const session = await client.auth.resetPassword({
  token,
  password: newPassword,
});
```

Resetting ends every other session and signs this client in with a new session.
The request phase uses an enumeration-resistant response.

## User profile

`getUser()` returns fresh server state.
`updateUser()` can change profile fields, user metadata, password, or initiate an email change.

```typescript
const user = await client.auth.updateUser({
  name: "Ada Lovelace",
  avatar_url: "https://cdn.example.com/avatars/ada.png",
  data: {
    locale: "en-GB",
  },
});
```

`data` merges into existing `user_metadata`.
Changing the password of an account that already has one requires `current_password`.

```typescript
await client.auth.updateUser({
  current_password: oldPassword,
  password: newPassword,
});
```

## User fields

Public `User` values retain API `snake_case` names.

| Field | Use |
| --- | --- |
| `id` | Stable user identifier |
| `email`, `username`, `name` | User-facing identity values |
| `avatar_url` | Optional profile image |
| `email_verified`, `email_verified_at` | Verification state |
| `user_metadata` | User-editable profile data; never authorization truth |
| `app_metadata` | Application-controlled data |
| `roles` | Issued roles |
| `mfa_enabled` | Enrollment state |
| `identities` | Linked login identities |
| `created_at`, `last_sign_in_at` | Audit-oriented timestamps |
| `aal` | Current assurance level on fresh `getUser()` responses |
| `session_id` | Current session identifier on fresh `getUser()` responses |

## MFA enrollment

MFA enrollment is not complete when the secret is created.
The user must prove the authenticator works with an initial code.

```typescript
const enrollment = await client.auth.mfa.enroll();

renderQrCode(enrollment.otpauth_uri);
showManualSecret(enrollment.secret);

const verified = await client.auth.mfa.verifyEnrollment(code);
showRecoveryCodesOnce(verified.recovery_codes);
```

| MFA method | Result |
| --- | --- |
| `status()` | Enabled state, assurance level, recovery-code count |
| `enroll()` | Factor ID, secret, and `otpauth_uri` |
| `verifyEnrollment(code)` | Enabled state and one-time recovery codes |
| `disable(code)` | New enabled state |
| `regenerateRecoveryCodes(code)` | Replacement recovery codes |

Recovery codes are returned for one-time display.
Do not write them to analytics or ordinary logs.
Regenerating invalidates the previous set.

## Devices and session history

`auth.sessions` gives the signed-in user visibility and control over active sessions.

```typescript
const sessions = await client.auth.sessions.list();
const history = await client.auth.sessions.history();

await client.auth.sessions.revoke(lostPhoneSessionId);
```

Session rows include method, assurance level, IP, user agent, created time, last refresh time, and whether the row is current.
Sign-in history includes success, method, reason, network context, and timestamp.

Revocation is an account-security action.
Confirm the intended session ID before applying it.

## Linked identities

One user can have multiple login providers.

```typescript
const identities = await client.auth.identities();
const linkUrl = await client.auth.linkIdentityUrl("google", {
  redirectTo: callbackUrl,
});

await client.auth.unlinkIdentity(identityId);
```

Linking returns a navigation URL.
The redirect parser reports `linked` on completion.
Before unlinking, ensure the user will retain another usable sign-in method.

## Application organizations

`auth.orgs` belongs to the end-user identity system.
It supports multi-tenant applications built on top of one Pawabase environment.
It does not create Pawabase projects and does not manage Cloud billing or Cloud team access.

```typescript
const org = await client.auth.orgs.create({
  slug: "analytical-engines",
  name: "Analytical Engines",
  metadata: {
    plan: "team",
  },
});
```

| Area | Methods |
| --- | --- |
| Organizations | `list`, `create`, `get`, `update`, `delete` |
| Members | `members`, `setMemberRole`, `removeMember` |
| Invitations | `invite`, `invitations`, `revokeInvitation`, `acceptInvitation` |
| Teams | `teams`, `createTeam`, `addTeamMember`, `removeTeamMember` |

Organization roles are `viewer`, `member`, `admin`, and `owner`.
Actual authorization remains policy-driven; do not assume a role name grants access unless the relevant policy uses it.

`switchOrg(slug)` issues a new session for an organization the user belongs to.
`switchOrg(null)` returns to no organization context.

```typescript
const session = await client.auth.switchOrg("analytical-engines");
console.log(session.org, session.org_role);
```

## Sign out scopes

`signOut()` defaults to the local session.

| Scope | Server effect | Local effect |
| --- | --- | --- |
| `local` | Ends the current session | Clears the local session |
| `others` | Ends every other session | Keeps the current local session |
| `global` | Ends all sessions | Clears the local session |

```typescript
await client.auth.signOut({ scope: "global" });
```

For `local` and `global`, the local session is cleared even when the server cannot be reached.
This guarantees the current application stops sending the credential, but an offline global sign-out cannot prove remote sessions were revoked.
The `others` scope keeps the current session because its purpose is to revoke other devices.

## Auth settings

`settings()` reports what the current environment offers.

```typescript
const settings = await client.auth.settings();
```

| Field | Meaning |
| --- | --- |
| `signup_enabled` | Whether public account creation is available |
| `email_verification_required` | Whether sign-up waits for confirmation |
| `magic_link_enabled` | Whether magic-link sign-in is available |
| `mfa_enabled` | Whether MFA can be used |
| `providers` | Configured social providers |
| `password_policy.kind` | Active password policy type |
| `password_policy.min_length` | Minimum accepted password length |

Use these values to adapt available UI.
The server remains authoritative; settings can change between rendering a form and submitting it.

## The unauthorized-response refresh path

Managed refresh also participates in ordinary SDK requests.
When a request returns `401` with a user token, the transport gives auth one opportunity to replace that token and replay a replayable request.

```text
request with access token
        │
        ▼
      HTTP 401
        │
        ├── no managed session ──> AuthenticationError
        │
        ├── body is a stream ────> AuthenticationError
        │
        └── refresh once
                │
                ├── new token ──> replay request once
                └── no token ───> AuthenticationError
```

Concurrent `401` responses share the refresh operation.
The transport does not enter an unlimited `401` loop.
An explicitly supplied per-call token and an `accessToken` client remain externally owned and are not refreshed by the managed session.

## Refresh failure categories

Not every refresh failure has the same session consequence.

| Failure | Client behavior | Reason |
| --- | --- | --- |
| Server rejects the refresh token | Clears the session and emits sign-out | The credential is no longer usable |
| Temporary network or server failure while access token is still valid | Keeps the session and surfaces the failure where required | A later refresh may succeed |
| Corrupt stored session | Removes it during initialization | Invalid local state cannot be trusted |
| Another browser tab already wrote a newer session | Adopts the newer value | Avoids exchanging an obsolete rotating token |

Applications should preserve a signed-in shell during a temporary refresh outage only while the client still has a valid access token.
Once the token is expired and refresh cannot complete, protected calls cannot continue.

## Browser-tab synchronization

Browser storage events tell other clients on the same origin that session state changed.
The Web Locks API, when available, serializes refresh exchange across tabs.

This is why all tabs for the same URL and key should use the same derived storage namespace unless deliberate isolation is required.
A custom `storageKey` separates them and also removes their ability to observe one shared session through that key.

The tab that signs out locally clears shared persisted state, so other listening tabs become signed out as well.
The `others` server scope keeps the calling tab's current session.

## Cached versus verified identity

Choose the user accessor according to the decision being made.

| Accessor | Network | Suitable for | Not suitable for |
| --- | --- | --- | --- |
| `getCachedUser()` | No | Initial avatar/name rendering and optimistic shell state | Sensitive authorization decisions |
| `getSession()` | Only when refresh is needed | Determining signed-in state and obtaining current tokens | Proving the server still accepts the user |
| `getUser()` | Yes | Fresh profile, AAL, and current session identity | Offline-only rendering |

Client UI state is not a server authorization boundary.
Pawabase policies evaluate the token on the actual protected operation.

## Assurance level

Fresh `getUser()` responses can include `aal`.
`aal1` represents a first-factor session and `aal2` represents a session that completed a second factor.

Use assurance information to decide whether the UI should request an MFA challenge before a sensitive application action.
The sensitive route or policy must also enforce the required assurance; hiding a button is not enforcement.

```typescript
const user = await client.auth.getUser();

if (user.aal !== "aal2") {
  showSecondFactorRequired();
}
```

## Complete organization method reference

Application organizations have several public operations beyond switching the session context.

| Method | Purpose | Important input |
| --- | --- | --- |
| `orgs.list()` | List organizations the user can see | None |
| `orgs.create(input)` | Create an organization | Required `slug` and `name`; optional metadata |
| `orgs.get(slug)` | Read one organization | Organization slug |
| `orgs.update(slug, input)` | Change name or metadata | Partial object |
| `orgs.delete(slug)` | Delete an organization | Organization slug |
| `orgs.members(slug)` | List membership | Organization slug |
| `orgs.setMemberRole(slug, userId, role)` | Change a member role | User ID and valid `OrgRole` |
| `orgs.removeMember(slug, userId)` | Remove a member | User ID |
| `orgs.invite(slug, input)` | Send an invitation | Email, optional role and redirect |
| `orgs.invitations(slug)` | List pending invitations | Organization slug |
| `orgs.revokeInvitation(slug, invitationId)` | Revoke a pending invitation | Numeric invitation ID |
| `orgs.acceptInvitation(token)` | Accept an emailed invitation | Invitation token; user must be signed in |
| `orgs.teams(slug)` | List teams | Organization slug |
| `orgs.createTeam(slug, input)` | Create a team | Team slug and name |
| `orgs.addTeamMember(slug, team, userId)` | Add a user to a team | Organization, team, and user identifiers |
| `orgs.removeTeamMember(slug, team, userId)` | Remove a user from a team | Organization, team, and user identifiers |

These methods return API `snake_case` wire types where applicable.
Organization administration requires the caller's application role and relevant policies.

## Invitation handling

Invitation acceptance has two independent requirements: a valid invitation token and a signed-in application user.

```typescript
await client.auth.orgs.acceptInvitation(invitationToken);
const session = await client.auth.switchOrg(invitedOrgSlug);
```

Accepting membership does not necessarily change the active session's organization claim.
Switch after acceptance when subsequent policy checks should use that organization context.

Invitation links are bearer tokens.
Do not place them in analytics properties or server logs.

## Identity unlink safety

Before unlinking a provider, inspect the remaining identities and whether the account has another usable sign-in method.

```typescript
const identities = await client.auth.identities();
const remaining = identities.filter((identity) => identity.id !== identityId);

if (remaining.length === 0 && !hasPasswordCredential) {
  throw new Error("Add another sign-in method before unlinking this identity.");
}

await client.auth.unlinkIdentity(identityId);
```

The server remains authoritative and can impose additional constraints.

## Redirect handling outcomes

Treat every `UrlSessionResult` variant explicitly.

```typescript
const result = await client.auth.getSessionFromUrl(callbackUrl);

switch (result.status) {
  case "signed_in":
    navigateToApplication();
    break;
  case "mfa_required":
    renderMfaChallenge(result.verify);
    break;
  case "linked":
    showIdentityLinked(result.provider);
    break;
  case "error":
    showAuthError(result.error);
    break;
  case "none":
    showInvalidCallback();
    break;
}
```

Do not interpret `none` as signed out without checking the existing session.
It only means the supplied URL did not contain a recognized callback result.

## Testing auth behavior

Auth tests should cover state changes as well as method return values.

| Scenario | Expected state evidence |
| --- | --- |
| Successful sign-up without required verification | `SIGNED_IN` and stored session |
| Verification-required sign-up | User returned, session `null` |
| MFA password sign-in | No final session until verification succeeds |
| Shared concurrent refresh | One token exchange for several callers |
| Rejected refresh token | Session cleared and `SIGNED_OUT` |
| Temporary refresh failure | Still-valid session retained |
| New client with shared storage | Existing session initialized |
| Corrupt serialized session | Storage cleared and initial session `null` |
| `signOut({ scope: "others" })` | Current session retained |
| Request-scoped `asUser()` | Token attached without refresh attempt |

Always dispose test clients so refresh timers and storage listeners do not leak.
See [server runtimes and testing](/clients/typescript/server-runtimes-testing).

## Failure handling

| Failure | Likely interpretation |
| --- | --- |
| `AuthenticationError` | Bad credentials, invalid/expired token, or no session where one is required |
| `PermissionError` | Signed in but not allowed to perform an account or organization action |
| `ValidationError` | Password, email, redirect, or body validation failure |
| `ConflictError` | Unique email/username/slug conflict or current-state conflict |
| `RateLimitError` | Too many attempts; respect `retryAfter` |
| `NetworkError` during refresh | Session state is uncertain; do not manually replay the rotating token |

Avoid showing raw server messages as the only UX.
Map known codes to stable copy, preserve the error and request ID for diagnostics, and keep sign-in and recovery responses resistant to account enumeration.

## Security boundaries

| Data or action | Rule |
| --- | --- |
| Password | Send only to the auth operation; never store or log it |
| Refresh token | Treat as a long-lived session secret |
| Access token | Treat as a bearer credential; keep lifetime and exposure small |
| `user_metadata` | User-controlled; never trust for authorization |
| `app_metadata` and roles | Server-controlled, but policies remain the enforcement point |
| OAuth redirect | Allow-list exact destinations in environment settings |
| MFA secret and recovery codes | Show through a protected UI and do not retain in ordinary application logs |
| Secret API key | Never place in user-distributed code |
