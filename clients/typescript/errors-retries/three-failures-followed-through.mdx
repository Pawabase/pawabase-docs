### A deploy during checkout

The installation restarts its services while a person is paying.

```text
t=0.0 s   GET  /rest/v1/carts/7          200      the cart loads
t=1.2 s   POST /rest/v1/carts/7/checkout 503      gateway: service restarting
          POST, not idempotent → not retried → ServerError thrown
t=1.2 s   screen: "Something went wrong on our side." [Try again]
t=4.0 s   person presses Try again
          POST /rest/v1/carts/7/checkout 200      checkout succeeds
```

A `503` from the gateway during a restart usually means the request never reached the flow, but the client cannot know that for a `POST`, so it does not guess.
The person decides to try again, which is safe here because the checkout route uses a unique attempt id; a second, duplicate checkout would fail with `409`.

Had the request been a `GET`, the client would have waited a fraction of a second and repeated it, and the person would never have known.

### A person on a train

The connection drops for twenty seconds while someone reads a list and then saves a note.

```text
t=0 s    GET  /rest/v1/notes?per_page=20       NetworkError
         safe → wait ~200 ms → NetworkError → wait ~500 ms → NetworkError
         NetworkError thrown after 3 attempts
         screen: "We could not reach the server." [Try again]
t=25 s   connection back; person presses Try again → 200
t=30 s   PATCH /rest/v1/notes/9                 200
```

Three quick attempts cover a blip; they cannot cover twenty seconds.
For screens used on the move, listen for the browser's `online` event and retry reads automatically when the connection returns, and keep unsaved input in the form so nothing is lost.

### A session that ends mid-form

A person fills in a long form, leaves the tab for a day, and submits.
Their refresh token was revoked in the meantime because they changed their password on another device.

```text
POST /rest/v1/applications            401
     session refresh → POST /auth/v1/token  401 (refresh token revoked)
     session cleared, listeners get SIGNED_OUT
AuthenticationError thrown
```

The form's values are still in memory.
Keep them, show a sign-in dialog instead of navigating away, and resubmit after `SIGNED_IN`:

<CodeGroup>
```typescript TypeScript
import { AuthenticationError } from "@pawabase/client";

export async function submitWithReauth(submit: () => Promise<unknown>, askToSignIn: () => Promise<void>) {
  try {
    return await submit();
  } catch (error) {
    if (!(error instanceof AuthenticationError)) throw error;
    await askToSignIn();
    return submit();
  }
}
```

```python Python
from pawabase import AuthenticationError


def submit_with_reauth(submit, ask_to_sign_in):
    try:
        return submit()
    except AuthenticationError:
        ask_to_sign_in()
        return submit()
```
</CodeGroup>

Losing a long form to an expired session is one of the most frustrating failures an application can have, and one of the easiest to prevent.


## Status codes at a glance

| Status | Class | Retried | Typical cause |
| --- | --- | --- | --- |
| `400` | `ValidationError` with issues, else `ApiError` | No | Malformed request, bad query parameter, body not JSON |
| `401` | `AuthenticationError` | After one refresh, when a session exists | No or invalid key or token |
| `403` | `PermissionError` | No | Policy, scope, CORS origin, firewall, plan quota |
| `404` | `NotFoundError` | No | Missing, hidden by a policy, disabled operation, unknown route |
| `405` | `ApiError` (`method_not_allowed`) | No | Wrong method for a path |
| `409` | `ConflictError` | No | Unique value taken, state conflict |
| `413` | `PayloadTooLargeError` | No | Body too large |
| `415` | `ApiError` (`unsupported_media_type`) | No | Wrong content type |
| `422` | `ValidationError` | No | Body or parameters failed validation |
| `429` | `RateLimitError` | Yes, any method | Rate limit, account lockout |
| `500` | `ServerError` | No | Unexpected failure |
| `502`, `503`, `504` | `ServerError` | For safe requests | Restart, overload, upstream timeout |


## Codes you will meet

| Code | Status | Meaning |
| --- | --- | --- |
| `invalid_api_key` | `401` | The key is unknown, revoked or expired |
| `origin_not_allowed` | `403` | A publishable key used from an origin not in the environment's list |
| `rate_limit_exceeded` | `429` | The gateway's rate limit |
| `quota_exceeded` | `403` | The project's plan does not allow more; `details` names the limit |
| `unique_violation` | `409` | A unique field already has this value; `details.columns` names it |
| `constraint_violation` | `422` | Another database constraint refused the write |
| `missing_flow` | `500` | A route names a flow that does not exist |
| `invalid` | `422` | A flow's schema validation failed; `details` lists the problems |
| Codes from `error.raise` | Chosen by the flow | Your application's own failures |


## The risk of repeating a request

Retrying is safe when sending a request twice leaves the same result as sending it once.
The table lists common calls by that property.

| Call | Repeating it | Retried by the client |
| --- | --- | --- |
| Any read | Harmless | Yes |
| `update` (`PATCH`) with absolute values | Harmless: the same values are written again | Only `429`, unless you use your own retry |
| `update` that increments a counter computed by the client | Harmful: the counter moves twice | Do not compute increments in the client |
| `replace` (`PUT`) | Harmless | Yes |
| `delete` | Harmless; the second attempt gets `404` | Yes |
| `create` | Creates a duplicate, unless a unique field stops it | Only `429` |
| An upload to a fixed key | Harmless: the same bytes replace themselves | Yes |
| A flow that charges, sends or notifies | Harmful without an attempt id | Only `429`, unless marked idempotent |
| A flow protected by a unique attempt id | Harmless: the second attempt gets `409` | When marked idempotent |

The general rule is to make writes naturally repeatable, with absolute values and unique keys, and then let the client's retries do their job.


## Retrying in your own code

The client's retries cover brief failures within one call.
Some situations need a retry at a higher level:

| Situation | Higher-level retry |
| --- | --- |
| A person presses "Try again" | Repeat the whole action, with the same attempt id if it has one |
| The device comes back online | Repeat reads that failed, and queued writes |
| A background job meets a `ServerError` | Repeat the job step later, with a longer delay |
| A batch has a few failed items | Repeat only the failed items |

Avoid stacking retries.
A loop of three in your code around a client call that already retries twice sends up to nine requests, and a data library with its own retries on top multiplies again.

<CodeGroup>
```typescript TypeScript
import { NetworkError, ServerError, TimeoutError } from "@pawabase/client";

export async function withPatience<T>(work: () => Promise<T>, attempts = 3): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    try {
      return await work();
    } catch (error) {
      const transient = error instanceof ServerError || error instanceof NetworkError || error instanceof TimeoutError;
      if (!transient || attempt >= attempts) throw error;
      await new Promise((resolve) => setTimeout(resolve, 2000 * attempt));
    }
  }
}
```

```python Python
import time

from pawabase import NetworkError, ServerError


def with_patience(work, attempts: int = 3):
    for attempt in range(1, attempts + 1):
        try:
            return work()
        except (ServerError, NetworkError):
            if attempt >= attempts:
                raise
            time.sleep(2 * attempt)
```
</CodeGroup>

Use a helper like this for background work, where waiting seconds between attempts is acceptable, and only around operations that are safe to repeat.


## Data libraries and their retries

Libraries such as TanStack Query retry failed queries by default, three times with growing delays.
Combined with the client's own retries, a failing request can be sent many times.

Tell the library not to retry what the client already retried, and never to retry what will not change:

```typescript
import { QueryClient } from "@tanstack/react-query";
import { ApiError, NetworkError, ServerError, TimeoutError } from "@pawabase/client";

export const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      retry: (failureCount, error) => {
        if (error instanceof ApiError && !(error instanceof ServerError)) return false;
        if (error instanceof NetworkError || error instanceof TimeoutError || error instanceof ServerError) return failureCount < 1;
        return false;
      },
    },
    mutations: { retry: false },
  },
});
```

Client errors such as `404`, `403` and `422` will fail the same way every time, so retrying them only delays the error message.
Mutations should not be retried by the library at all; the client already repeats the safe ones.


## When instanceof fails

`instanceof` compares against one specific class.
If two copies of `@pawabase/client` end up in a bundle, for example because two packages depend on different versions, an error created by one copy is not an instance of the other copy's classes.

| Symptom | Cause | Fix |
| --- | --- | --- |
| `error instanceof NotFoundError` is false for an obvious `404` | Two copies of the package | Deduplicate the dependency in your lockfile |
| Errors from a library wrapping the client are not recognized | The library bundles its own copy | Make the client a peer dependency of the library |

Where deduplication is not possible, check the error's `name`, which every class sets:

```typescript
function isNotFound(error: unknown) {
  return error instanceof Error && error.name === "NotFoundError";
}
```
