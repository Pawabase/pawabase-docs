An optimistic update shows the change before the server confirms it.
When the server refuses, the screen must return to the truth and say why.

```typescript
import { ConflictError, PermissionError } from "@pawabase/client";

export async function toggleDone(task: { id: string; done: boolean }, setTask: (task: { id: string; done: boolean }) => void) {
  const previous = { ...task };
  setTask({ ...task, done: !task.done });
  try {
    setTask(await pawabase.from("tasks").update(task.id, { done: !task.done }));
  } catch (error) {
    setTask(previous);
    if (error instanceof PermissionError) notify("You can no longer change this task.");
    else if (error instanceof ConflictError) notify("Someone else changed this task. It has been reloaded.");
    else notify("The change was not saved.");
  }
}

declare function notify(message: string): void;
```

Always restore from a copy taken before the optimistic change, not by applying the inverse change.
The inverse can be wrong if other changes happened in between.


## Result objects for teams that prefer them

Some teams prefer functions that return `{ ok, value }` or `{ ok, error }` instead of throwing, as supabase-js does.
A thin wrapper gives you that style without losing the error classes:

```typescript
import type { PawabaseError } from "@pawabase/client";

export type Result<T> = { ok: true; value: T } | { ok: false; error: PawabaseError };

export async function attempt<T>(work: () => Promise<T>): Promise<Result<T>> {
  try {
    return { ok: true, value: await work() };
  } catch (error) {
    if (error instanceof Error && "name" in error) return { ok: false, error: error as PawabaseError };
    throw error;
  }
}

const result = await attempt(() => pawabase.from("orders").get(orderId));
if (!result.ok) return showError(result.error);

declare function showError(error: PawabaseError): void;
```

The wrapper rethrows anything that is not an `Error`, so bugs such as thrown strings are not mistaken for API failures.


## Showing each error once

A screen that loads several things in parallel can produce several copies of the same error, such as five `NetworkError`s when the connection drops.
Showing five identical messages helps nobody.

```typescript
const shown = new Map<string, number>();

export function notifyOnce(key: string, message: string, windowMs = 5000) {
  const last = shown.get(key) ?? 0;
  if (Date.now() - last < windowMs) return;
  shown.set(key, Date.now());
  notify(message);
}

// notifyOnce(error.name, present(error).message)
declare function notify(message: string): void;
```

Keying by the error class collapses a burst of identical failures into one message.


## Validation messages in other languages

The server writes validation messages in English.
Translate them by issue `type`, and keep the server's message as a fallback:

```typescript
import type { ValidationIssue } from "@pawabase/client";

const fr: Record<string, string> = {
  missing: "Ce champ est obligatoire.",
  string_too_short: "Ce texte est trop court.",
  string_too_long: "Ce texte est trop long.",
  extra_forbidden: "Ce champ n'est pas accepté.",
};

export function messageFor(issue: ValidationIssue, table: Record<string, string>) {
  return (issue.type && table[issue.type]) || issue.message;
}
```

Constraint details such as the exact minimum length are in the issue's `input` and the field's definition, not in the type; include them in the message when the interface needs them.


## Words used on this page

| Term | Meaning |
| --- | --- |
| Attempt | One HTTP request; a call can make several |
| Safe request | One that leaves the same result when repeated: reads, `PUT`, `DELETE`, or calls marked idempotent |
| Backoff | The growing, randomized wait between attempts |
| `Retry-After` | The server's request to wait a number of seconds |
| Request id | The gateway's id for one attempt, in `x-request-id` and `requestId` |
| Transport error | A failure with no answer: network, timeout, abort |


## Cancellation and retries together

Retries and cancellation interact in ways that are easy to predict once stated.

| Moment of cancellation | Result |
| --- | --- |
| Before the first attempt is sent | `AbortError`; nothing was sent |
| During an attempt | The attempt is aborted; `AbortError` |
| While waiting before a retry | The wait ends at once; `AbortError`; no further attempts |
| After the answer arrived | No effect; the call has already returned |

A cancelled call never produces a `TimeoutError` or a retry afterwards, so cleanup code that aborts on unmount does not leave requests running in the background.


## When to show a request id

Request ids help support, but they are noise for errors people can fix themselves.

| Error | Show the id? |
| --- | --- |
| `ValidationError`, `ConflictError` | No; the message tells the person what to change |
| `AuthenticationError`, `PermissionError`, `NotFoundError` | Rarely; offer it in a "details" area |
| `ServerError`, unexpected `ApiError` | Yes, as a reference to quote |
| `NetworkError`, `TimeoutError` | There is none; the request may not have reached the gateway |

Make the id easy to copy, and keep it short on screen by showing the last eight characters with a copy button for the full value.


## Errors in the network panel

The browser's network panel shows each attempt as its own row, which explains failures the client already handled.

| What you see | What happened |
| --- | --- |
| Two rows for one call, the first `503` and the second `200` | A retry after a gateway error |
| A `401` row followed by a `token` row and a repeat of the first | A refresh and replay |
| A red row with no status and a CORS message in the console | A refused origin, surfaced as `NetworkError` |
| A row marked cancelled | An `AbortSignal` fired, or a timeout aborted the attempt |
| A `429` row followed by the same request a few seconds later | A rate limit honored with `Retry-After` |

The response headers of each row include `x-request-id`, the same value the client puts on `requestId`.
Copy it from there when a failure happens in your own browser, and search for it under **Project → Activity** to see the server's side of the same attempt.

Rows for retried attempts carry their own request ids.
When a call succeeded after a retry, the failed attempt's id is still worth a look if retries are frequent, because it shows what the server was doing at the time.
Frequent retries that always succeed are not harmless: each one adds the backoff delay to what people wait for.
Treat a steady rate of them as a performance problem to fix on the server side.


## A checklist

| Check | Why |
| --- | --- |
| Every screen that writes handles `ValidationError` field by field | People can fix their input |
| Expected codes have specific messages | People know what happened |
| Unexpected errors reach an error tracker with `requestId` | Support can find them |
| Expected outcomes are filtered out of the tracker | Real problems stay visible |
| Data-library retries do not stack on the client's | Failing requests are not multiplied |
| Non-repeatable actions use attempt ids | Retries cannot duplicate them |
| Long forms survive an expired session | Nobody loses their work |
| Error paths have been exercised with injected failures | They work when needed |

## Coming from supabase-js

| supabase-js | @pawabase/client |
| --- | --- |
| `const { data, error } = await …` | `const data = await …` inside `try` |
| `if (error) …` | `catch (error) { if (error instanceof …) }` |
| `error.code` (PostgREST codes such as `23505`) | `error.code` (`unique_violation`, `not_found`, …) |
| `error.message`, `error.details`, `error.hint` | `error.message`, `error.details` |
| `AuthApiError`, `AuthRetryableFetchError` | `AuthenticationError`, `NetworkError` |
| `FunctionsHttpError` | `ApiError` with the flow's code |
| No automatic retries for data calls | Automatic retries for safe calls |

Code moved from supabase-js often checks `if (error)` after every call.
With this client, that check disappears, and errors are handled where they mean something.


## Troubleshooting

| Symptom | Cause | What to do |
| --- | --- | --- |
| Calls take much longer than expected before failing | Retries multiplied by the timeout | Lower `timeoutMs`; use a deadline signal |
| A `POST` failed with `503` and was not retried | `POST` is not repeated without `idempotent` | Retry in your code if the action is safe, or mark it idempotent |
| Duplicate records after network trouble | A create was repeated by your own code | Use unique fields or attempt ids |
| `RateLimitError` in a batch job | The job runs faster than the limit | Lower concurrency; respect `retryAfter` |
| `AuthenticationError` immediately after sign-in | The key is wrong, or the token belongs to another environment | Check the key and environment |
| `NetworkError` only in the browser | CORS refusal | Add the origin under **Access → Networking** |
| `instanceof` checks fail | Two copies of the package | Deduplicate the dependency |
| Error tracker full of `NotFoundError` | `onError` reports expected outcomes | Filter expected classes |


## Questions developers ask

<AccordionGroup>
  <Accordion title="Can I turn retries off for one call?">
    Through the transport, yes: `pawabase.http.request({ …, retry: false })`.
    The convenience methods use the client's policy.
  </Accordion>
  <Accordion title="Does the client retry 500 errors?">
    No.
    A `500` means the request reached the service and failed there; repeating it usually fails the same way and may repeat side effects.
    `502`, `503` and `504` are retried for safe requests because they usually mean the request never reached a working service.
  </Accordion>
  <Accordion title="Why is a locked account a RateLimitError?">
    The auth service answers a locked account with `429`, because the lock is a limit on failed attempts.
    Show a message about waiting, not about the password.
  </Accordion>
  <Accordion title="Are errors serializable?">
    They are `Error` objects and lose their class when serialized.
    On a server, turn them into plain data, such as `{ code, message, requestId }`, before sending them anywhere.
  </Accordion>
  <Accordion title="Can I add my own fields to errors?">
    Wrap them instead.
    Throw your own error class with the Pawabase error as its `cause`, so the original stays available.
  </Accordion>
  <Accordion title="Does a timed-out request count against my rate limit?">
    Yes, if it reached the gateway.
    The gateway counts requests as they arrive, whatever happens to the client afterwards.
  </Accordion>
  <Accordion title="Can a request succeed on the server and still throw in the client?">
    Yes: a timeout, a dropped connection or a cancellation after the server finished.
    That is why writes that matter should be safe to repeat, or checked before repeating.
  </Accordion>
  <Accordion title="How many times will a GET be sent at most?">
    Three by default: the first attempt and two retries, plus one more after a refresh if the first answer was `401`.
  </Accordion>
</AccordionGroup>
