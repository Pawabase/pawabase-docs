Most methods accept an `AbortSignal`, and queries take one through `withOptions`.
Aborting stops the attempt in flight and any wait before the next retry, and the call rejects with `AbortError`.

```typescript
import { AbortError } from "@pawabase/client";

const controller = new AbortController();

const pending = pawabase.from("orders").eq("status", "open").withOptions({ signal: controller.signal }).perPage(50);

controller.abort();
await pending.catch((error) => {
  if (!(error instanceof AbortError)) throw error;
});
```

Signals combine with timeouts: whichever fires first ends the attempt.
Use `AbortSignal.timeout(ms)` for a deadline that covers the whole call, retries included, which the per-attempt timeout does not:

<CodeGroup>
```typescript TypeScript
const deadline = AbortSignal.timeout(15_000);
await pawabase.from("orders").withOptions({ signal: deadline }).perPage(50);
```

```python Python
import asyncio

# A deadline for the whole call, retries included (async client):
async with asyncio.timeout(15):
    page = await apb.from_("orders").per_page(50).execute()
```

```bash cURL
curl --max-time 15 "$PAWABASE_URL/rest/v1/orders?per_page=50" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN"
```
</CodeGroup>

A deadline signal that fires raises `AbortError`, not `TimeoutError`, because from the client's view your code cancelled the call.

Cancelling stops the client from waiting.
It does not stop work the server has already started, so a cancelled write may still have happened.

| Situation | Use |
| --- | --- |
| A component unmounts | An `AbortController` per component, aborted in cleanup |
| A search input changes | Abort the previous search when starting the next |
| A whole operation must finish within a time budget | `AbortSignal.timeout(ms)` |
| A person presses "Cancel" on an upload | An `AbortController` wired to the button |


## Observing failures with hooks

Hooks let you see every attempt, retry and failure without wrapping each call.
They are configured once, on the client.

| Hook | Called | Receives |
| --- | --- | --- |
| `onRequest` | Before each attempt | `method`, `url`, `attempt`, and `headers` with `apikey` and `authorization` masked |
| `onResponse` | After each attempt that got an answer | `method`, `url`, `attempt`, `status`, `durationMs`, `requestId` |
| `onRetry` | Before waiting to repeat | `method`, `url`, `attempt`, `reason`, `delayMs` |
| `onError` | When the client is about to throw | The error, with `method`, `url`, `attempt` |

`reason` in `onRetry` is either `status <n>` or the error's class name, such as `NetworkError` or `TimeoutError`.
`attempt` counts from `0`.

```typescript
import { AbortError, ApiError, createClient } from "@pawabase/client";

const pawabase = createClient({
  url,
  apiKey,
  hooks: {
    onRetry: ({ method, url, attempt, reason, delayMs }) =>
      console.info(`retry ${attempt + 1} of ${method} ${new URL(url).pathname} in ${delayMs} ms: ${reason}`),
    onError: (error, { method, url }) => {
      if (error instanceof AbortError) return;
      errorTracker.capture(error, { method, path: new URL(url).pathname, requestId: error instanceof ApiError ? error.requestId : null });
    },
  },
});

declare const errorTracker: { capture(error: unknown, context: object): void };
```

A hook that throws is ignored; observability can never break a request.
Hooks never receive response bodies, which keeps personal data out of logs by default.

`onError` runs for every error the client throws from a request, including errors your code will handle, such as a `404` from `maybeGet`.
Filter what you send to an error tracker: expected outcomes like `NotFoundError` and `ValidationError` are usually noise there.


## A structure for handling errors

Applications that handle errors well usually do it in three layers, each with a narrow job.

| Layer | Handles | Example |
| --- | --- | --- |
| The call site | Failures it expects and can act on | A `ConflictError` on sign-up means "email taken" |
| The feature | Turning remaining errors into something to show | A shared function maps classes and codes to messages |
| The application | Errors nobody expected | An error boundary reports them with the request id and shows a fallback |

```typescript
import {
  ApiError,
  AuthenticationError,
  NetworkError,
  PermissionError,
  RateLimitError,
  ServerError,
  TimeoutError,
  ValidationError,
} from "@pawabase/client";

export interface Presentable {
  message: string;
  fields?: Record<string, string[]>;
  canRetry: boolean;
  mustSignIn: boolean;
  requestId: string | null;
}

export function present(error: unknown, codes: Record<string, string> = {}): Presentable {
  const requestId = error instanceof ApiError ? error.requestId : null;
  const base = { canRetry: false, mustSignIn: false, requestId };
  if (error instanceof ApiError && codes[error.code]) return { ...base, message: codes[error.code] };
  if (error instanceof ValidationError) return { ...base, message: "Some fields need attention.", fields: error.byField() };
  if (error instanceof AuthenticationError) return { ...base, message: "Please sign in again.", mustSignIn: true };
  if (error instanceof PermissionError) return { ...base, message: "You do not have permission to do that." };
  if (error instanceof RateLimitError) return { ...base, message: "Too many requests. Wait a moment and try again.", canRetry: true };
  if (error instanceof ServerError) return { ...base, message: "Something went wrong on our side.", canRetry: true };
  if (error instanceof NetworkError || error instanceof TimeoutError) return { ...base, message: "We could not reach the server.", canRetry: true };
  if (error instanceof ApiError) return { ...base, message: error.message };
  return { ...base, message: "Something went wrong." };
}
```

In React, an error boundary is the application layer for rendering errors, and a global handler covers errors from event handlers and effects:

```tsx
import { Component, type ReactNode } from "react";
import { ApiError } from "@pawabase/client";

export class ErrorBoundary extends Component<{ children: ReactNode }, { error: unknown }> {
  state = { error: null as unknown };
  static getDerivedStateFromError(error: unknown) {
    return { error };
  }
  componentDidCatch(error: unknown) {
    errorTracker.capture(error, { requestId: error instanceof ApiError ? error.requestId : null });
  }
  render() {
    if (!this.state.error) return this.props.children;
    const requestId = this.state.error instanceof ApiError ? this.state.error.requestId : null;
    return (
      <div role="alert">
        <p>Something went wrong.</p>
        {requestId && <p>Reference: <code>{requestId}</code></p>}
      </div>
    );
  }
}

declare const errorTracker: { capture(error: unknown, context: object): void };
```


## Messages people understand

Error messages are read by people who did nothing wrong, often in a hurry.
Say what happened and what to do next, in their terms.

| Error | Say | Avoid |
| --- | --- | --- |
| `ValidationError` | The field's problem, next to the field | "Request failed with status 422" |
| `AuthenticationError` after a session ends | "Your session ended. Sign in to continue." | "401 Unauthorized" |
| `PermissionError` | "You do not have access to this." | Naming the policy |
| `NotFoundError` on a page | "This item does not exist or was removed." | "404" |
| `ConflictError` with `unique_violation` | "An account with this email already exists." | "Duplicate key value" |
| `RateLimitError` | "Please wait a few seconds and try again." | Silent failure |
| `NetworkError`, `TimeoutError` | "Check your connection." with a retry button | Infinite spinners |
| `ServerError` | "Something went wrong on our side." with the reference | The server's message |

Policy names, internal messages and stack traces belong in logs, not on screen.


## Rate limits in practice

Rate limits apply per environment at the gateway, and optionally per resource and per route.
When a limit is reached, the answer is `429` with a `Retry-After`.

| What you see | Meaning |
| --- | --- |
| Calls slow down without failing | The client waited for `Retry-After` and repeated them |
| `RateLimitError` with `retryAfter` | The server asked for a longer wait than `maxRetryAfterMs`, or retries ran out |
| `RateLimitError` on sign-in with the right password | The account is locked after failed attempts; wait it out |

The gateway also sends `X-RateLimit-Limit` and `X-RateLimit-Remaining` on answers when the limiter is active.
The client does not read them, but a custom `fetch` can, if you want to slow down before reaching the limit:

```typescript
const pawabase = createClient({
  url,
  apiKey,
  fetch: async (input, init) => {
    const response = await fetch(input, init);
    const remaining = Number(response.headers.get("x-ratelimit-remaining"));
    if (Number.isFinite(remaining) && remaining < 5) await new Promise((resolve) => setTimeout(resolve, 500));
    return response;
  },
});
```

Most applications never need this.
It helps batch jobs that run close to the limit, where slowing down a little avoids long `Retry-After` waits.


## Handling errors in server code

A server that calls Pawabase and answers its own clients should translate errors, not pass them through.
Its own clients do not need to know which service failed, and must not see internal details.

```typescript
import express from "express";
import { ApiError, NetworkError, NotFoundError, PermissionError, ValidationError } from "@pawabase/client";

const app = express();

app.get("/api/orders/:id", async (req, res, next) => {
  try {
    res.json(await pawabaseFor(req).from("orders").get(req.params.id));
  } catch (error) {
    next(error);
  }
});

app.use((error: unknown, _req: express.Request, res: express.Response, _next: express.NextFunction) => {
  const requestId = error instanceof ApiError ? error.requestId : null;
  if (error instanceof NotFoundError) return res.status(404).json({ error: "not_found" });
  if (error instanceof PermissionError) return res.status(403).json({ error: "forbidden" });
  if (error instanceof ValidationError) return res.status(422).json({ error: "invalid", fields: error.byField() });
  if (error instanceof NetworkError) return res.status(503).json({ error: "unavailable" });
  console.error("unexpected", { requestId, error });
  return res.status(500).json({ error: "internal", reference: requestId });
});

declare function pawabaseFor(req: express.Request): import("@pawabase/client").PawabaseClient;
```

Log the Pawabase request id with your own server's request id, so one incident can be followed across both.

Errors from a secret-key client deserve extra care.
A `PermissionError` there usually means a scope or IP restriction on the key, not a policy, because secret keys bypass policies.
