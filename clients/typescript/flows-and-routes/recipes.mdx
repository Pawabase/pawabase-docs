The recipes use the client's error classes:

```typescript
import { RateLimitError, ValidationError } from "@pawabase/client";
```

Each recipe below pairs the flow's behavior with the client code that calls it.
The flows are described in words rather than full graphs; build them in **Logic → Flows** with the blocks named.

### A contact form for anonymous visitors

A flow with a pathless HTTP trigger and `policy: public` accepts messages from visitors who are not signed in.
It validates the input with `validate.schema`, stores the message with `resource.create` and notifies the team with `mail.send`.
A route in front of it adds a rate limit, which matters for anything anonymous.

```typescript
export async function sendContactMessage(values: { name: string; email: string; message: string }) {
  try {
    await pawabase.routes.post("contact", values);
    return { ok: true as const };
  } catch (error) {
    if (error instanceof ValidationError) return { ok: false as const, fields: error.byField() };
    if (error instanceof RateLimitError) return { ok: false as const, message: "Please wait a moment before sending another message." };
    throw error;
  }
}
```

The publishable key is enough, and no session is needed.
The rate limit is per caller, so one visitor cannot flood the team's inbox.

### A payment checkout session

Starting a hosted checkout with a payment provider needs a secret only the server may hold.
A route flow reads the provider key with `secret.get`, calls the provider with `http.request`, records the pending payment with `resource.create`, and answers with the provider's checkout URL.

```typescript
export async function startCheckout(orderId: string) {
  const { checkout_url } = await pawabase.routes.post<{ checkout_url: string }>(`orders/${orderId}/checkout`);
  window.location.assign(checkout_url);
}
```

The provider later calls back to an [inbound hook](/webhooks/inbound), not to this route.
Inbound hooks check the provider's signature before a flow runs, which a route cannot do.

### Acting on a selection

A screen that lets people select rows and archive them should not send one request per row.
A route takes the list of ids, and its flow loads each with `resource.get`, checks that the caller may change it with `policy.check`, and updates it with `resource.update`.
The check is the flow's job: resource blocks do not apply the resource's policies by themselves.

```typescript
export async function archiveSelected(ids: string[]) {
  const answer = await pawabase.routes.post<{ archived: string[]; refused: string[] }>("tasks/archive", { ids });
  if (answer.refused.length) showMessage(`${answer.refused.length} tasks could not be archived.`);
  return answer.archived;
}
```

Reporting refused ids lets the screen tell people which rows were not theirs to change, instead of failing the whole action.
Cap the size of `ids` in the flow's input schema, so one call cannot touch an unbounded number of records.

### A computed summary

The data API counts rows but does not sum or group values.
A `GET` route whose flow lists the relevant records with `resource.list` and computes totals answers a dashboard with one call.

<CodeGroup>
```typescript TypeScript
export async function salesSummary(month: string) {
  return pawabase.routes.get<{ orders: number; revenue_minor: number; average_minor: number }>("reports/sales", { query: { month } });
}
```

```python Python
def sales_summary(month: str):
    return pb.routes.get("reports/sales", month=month)
```

```bash cURL
curl -G "$PAWABASE_URL/rest/v1/reports/sales" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" --data-urlencode "month=2026-09"
```
</CodeGroup>

If the summary is the same for everyone and changes slowly, give the route a short cache.
If it depends on the caller, do not.

### Notifying another system after a change

When a record change must reach another system, such as a CRM, the client does not call anything extra.
It writes the record, and a flow subscribed to the resource event sends it on with `http.request`.

<CodeGroup>
```typescript TypeScript
await pawabase.from("customers").update(customerId, { plan: "pro" });
```

```python Python
pb.from_("customers").update(customer_id, {"plan": "pro"})
```

```bash cURL
curl -X PATCH "$PAWABASE_URL/rest/v1/customers/$CUSTOMER_ID" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"plan": "pro"}'
```
</CodeGroup>

The person sees the update immediately; the delivery happens after, with its own retries and its own run history.
This keeps slow or unreliable partners out of the person's request entirely.


## Migrating from custom functions

Custom functions were removed from Pawabase.
Code that called them through the client needs a new target, and the right one depends on what the function did.

| The function | Replace with | Client change |
| --- | --- | --- |
| Took JSON, did a few record operations, returned JSON | A flow with a pathless HTTP trigger | `functions.invoke(name, input)` becomes `flows.run(name, input)`; unwrap `data` if the flow has no `response.return` |
| Served a REST-shaped URL with path parameters | A custom route backed by a flow | `functions.fetch(name, path, …)` becomes `routes.<method>(path, …)` |
| Needed a Python or Node library, streaming, or long computation | An extension route, written by the operator | `routes.<method>("x/…")`, or `http.request` for non-JSON answers |
| Reacted to an event | A flow with an event trigger | Remove the client call; write the record that causes the event |
| Ran on a schedule | A flow with a schedule | Remove the client call |

`functions.invoke` unwrapped a `{ data }` envelope.
`flows.run` returns the body as it is, so a flow without `response.return` needs `.data` at the call site.


## What to send

What a client sends to a flow shapes how safe and how fast the flow is.

| Send | Avoid | Why |
| --- | --- | --- |
| Ids of records | Whole records copied from the screen | The flow should read current data under policies, not trust a copy |
| The person's choices | The person's identity | Identity comes from the token, as `$auth` |
| Amounts as integers in minor units | Floating-point currency | `0.1 + 0.2` is not `0.3` |
| Dates as ISO strings | `Date` objects with local offsets | The server works in UTC |
| Small payloads | Files in JSON | Upload files to storage and send the key |

A flow that recomputes prices from ids is correct even when the screen is stale or tampered with.
A flow that trusts prices sent by the client is not.


## The wire format

| Client call | Request |
| --- | --- |
| `flows.run("quote", input)` | `POST /flows/v1/quote` with `input` as JSON |
| `routes.get("reports/sales", { query: { month } })` | `GET /rest/v1/reports/sales?month=…` |
| `routes.post("orders/1/pay", body)` | `POST /rest/v1/orders/1/pay` with `body` as JSON |
| `routes.put(path, body)`, `routes.patch(path, body)` | `PUT` or `PATCH /rest/v1/<path>` |
| `routes.delete(path)` | `DELETE /rest/v1/<path>` |
| `routes.call("OPTIONS", path)` | Any method you name |

Each request carries the API key, the person's token when signed in, and `x-client-info`, like every other call.


## Actions on mobile networks

On a phone, the network can disappear between the tap and the answer.
For actions, that leaves the screen not knowing whether the action happened.

The unique-attempt technique answers that question: retry with the same attempt id when the network returns, and either the first attempt's result or the conflict tells you the action happened once.
Store pending attempts locally, as the storage page does for uploads, so they survive the app being closed.

Show the person what is going on: "Sending…", then "Waiting for connection", then "Sent".
Silently retrying in the background is worse than saying so.


## Measuring actions

Flows and routes are where your application's important actions happen, so they deserve their own metrics.
The client's hooks see every call; tag them by action rather than by URL:

```typescript
function actionName(url: string) {
  const path = new URL(url).pathname;
  if (path.startsWith("/flows/v1/")) return `flow:${path.slice(10)}`;
  if (path.startsWith("/rest/v1/")) return `route:${path.slice(9).replace(/\/[0-9A-Za-z_-]{8,}(?=\/|$)/g, "/:id")}`;
  return null;
}

const pawabase = createClient({
  url,
  apiKey,
  hooks: {
    onResponse: ({ url, status, durationMs }) => {
      const name = actionName(url);
      if (name) metrics.timing("action", durationMs, { name, ok: String(status < 400) });
    },
  },
});

declare const metrics: { timing(name: string, ms: number, tags: Record<string, string>): void };
```

Replacing ids with `:id` keeps one metric per action instead of one per record.


## Shaping answers for screens

A flow can answer with anything, so answer with what the screen needs.
Returning whole records copied from resource blocks has two costs.

The first is exposure.
Resource blocks read with service rights, so a record they return can contain fields the person could never read through the data API, such as write-only fields or another person's details.
Pick the fields with `transform.pick`, or build the body explicitly in `response.return`.

The second is coupling.
A screen that reads `answer.order.internal_notes` breaks when someone renames the field, even though the screen never needed it.

| Instead of | Answer with |
| --- | --- |
| `{ "order": "{{ steps.paid.output }}" }` | `{ "order": { "id": "…", "status": "…", "total_minor": … } }` |
| The list of every matching record | The page the screen shows, and a count |
| An internal error message | A code and a sentence written for people |


## Lists from routes

A route that returns a list should page it, and the simplest contract is the data API's own envelope.
Client code can then reuse the same pagination helpers for resources and routes.

```typescript
interface Page<T> {
  data: T[];
  page: number;
  per_page: number;
  total: number | null;
}

export async function searchCustomers(text: string, page = 1) {
  return pawabase.routes.get<Page<{ id: string; name: string }>>("customers/search", {
    query: { q: text, page, per_page: 20 },
  });
}

export async function* everyMatch(text: string) {
  for (let page = 1; ; page++) {
    const result = await searchCustomers(text, page);
    yield* result.data;
    if (result.data.length === 0 || (result.total !== null && page * result.per_page >= result.total)) return;
  }
}
```

The flow reads `page` and `per_page` from the request's query, passes them to `resource.list`, and answers with the same four fields.
