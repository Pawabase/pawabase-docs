Some actions take a file: an import, an avatar crop, a document to sign.
Upload the file to storage first, then call the route with its key.

```typescript
export async function importContacts(file: File) {
  const user = await pawabase.auth.getCachedUser();
  const key = `${user!.id}/imports/${Date.now()}.csv`;
  await pawabase.storage.from("imports").upload(key, file, { contentType: "text/csv", timeoutMs: 0 });
  return pawabase.routes.post<{ id: string; status: string }>("imports", { key });
}
```

The flow reads the file through its storage blocks and answers `202` with an import record to follow.
Flows and routes take JSON; files travel through storage, which has the limits, policies and streaming built for them.


## A public settings route

Many applications need configuration before anyone signs in: feature switches, contact details, maintenance notices.
A `GET` route with a `public` policy and a short cache serves it to every visitor cheaply.

```typescript
export async function loadPublicSettings() {
  try {
    return await pawabase.routes.get<{ maintenance: boolean; support_email: string; features: string[] }>("settings/public");
  } catch {
    return { maintenance: false, support_email: "support@example.com", features: [] };
  }
}
```

The fallback keeps the application usable if the route fails, which matters for something every page loads.


## Flows from scripts and CI

Scripts can call flows and routes with a secret key, which admits them through `authenticated` policies as a service.
That is useful for maintenance actions you already built as flows, such as "recompute balances for a customer".

For operator tasks, the management module is often the better door.
`manage(client).flows.run(name, input, { asUser })` runs a flow as an operator, optionally as a chosen person, regardless of its HTTP trigger, and returns the run's status, result, response and per-block trace.
That trace makes it the right tool for scripts that need to know exactly what happened.

| Need | Use |
| --- | --- |
| Call the action as an application would | `flows.run` or `routes.*` with a secret key |
| Run a flow as a specific person and see its trace | `manage(client).flows.run(name, input, { asUser })` |
| Run a flow that has no HTTP trigger | `manage(client).flows.run` |
| Check a flow definition before saving it | `manage(client).flows.validate(definition)` |


## Reading error details

Besides a code and a message, a flow error can carry `details`: structured information such as the fields that failed validation, the limit that was hit, or the record that conflicted.
The client exposes it as `error.details`, and keeps the whole response body in `error.body`.

<CodeGroup>
```typescript TypeScript
try {
  await pawabase.flows.run("reserve-seats", { event_id, seats: 4 });
} catch (error) {
  if (error instanceof ApiError && error.is("not_enough_seats")) {
    const { available } = (error.details ?? {}) as { available?: number };
    showMessage(available ? `Only ${available} seats are left.` : "Not enough seats are left.");
  } else throw error;
}
```

```python Python
from pawabase import PawabaseError

try:
    pb.flows.invoke("reserve-seats", {"event_id": event_id, "seats": 4})
except PawabaseError as error:
    if error.code != "not_enough_seats":
        raise
    available = (error.details or {}).get("available")
    show_message(f"Only {available} seats are left." if available else "Not enough seats are left.")
```
</CodeGroup>

Treat `details` as optional and check its shape.
It is part of a flow's contract only when the flow documents it.


## Words used on this page

| Term | Meaning |
| --- | --- |
| Direct flow call | `POST /flows/v1/<name>` to a flow whose HTTP trigger has no path |
| Custom route | An endpoint under `/rest/v1`, defined in **Logic → Routes**, handled by a flow |
| Extension route | A Python route mounted by the operator, usually under `/rest/v1/x/…` |
| Trigger policy | The condition on a flow's `trigger.http` that decides who may call it directly |
| Route policy | The condition on a route that decides who may call it |
| `response.return` | The block that sets a flow's status, headers and body |
| `error.raise` | The block that ends a flow with an error status, code and message |
| Service rights | How resource blocks run inside a flow: without applying resource policies |


## When a record operation is enough

Not every action needs a flow.
If an action is "create, change or delete one record, and the resource's policy already says who may", the data API does it with less to build and maintain.

| Action | A record operation is enough when | A flow or route is needed when |
| --- | --- | --- |
| Create a comment | The comment's fields come from the person, and the policy covers who may comment | A notification must go out, or a counter must change, in the same action |
| Mark a task done | The owner may change `done` | Completing the task must also update a project's progress atomically |
| Cancel an order | The customer may set `status` to `cancelled` | Cancelling must refund a payment and restock items |

A useful middle ground is a record operation plus an event: the client writes the record, and a flow subscribed to the resource's event does the follow-up work.
The person gets an immediate answer, and the follow-up is still reliable and visible.


## Messages in the person's language

Flows should answer with codes, and clients should turn codes into words.
That keeps translation where the rest of the interface's text lives.

```typescript
import type { ApiError } from "@pawabase/client";

const messages: Record<string, Record<string, string>> = {
  en: { coupon_expired: "This coupon has expired.", out_of_stock: "One of the items just sold out." },
  fr: { coupon_expired: "Ce coupon a expiré.", out_of_stock: "Un des articles vient d'être épuisé." },
};

export function messageFor(error: ApiError, locale: string) {
  return messages[locale]?.[error.code] ?? messages.en[error.code] ?? error.message;
}
```

The flow's own `message` is a fallback for codes the client does not know yet, written in the language of your team.


## Changing a flow's contract

Clients in the field keep calling a flow after you change it: mobile apps update slowly, and open browser tabs run yesterday's code.
Change contracts the way you would change any API.

| Change | Safe for existing clients? | How |
| --- | --- | --- |
| Add an optional input field | Yes | Give it a default in the flow |
| Add a field to the success answer | Yes | Clients ignore what they do not read |
| Add a new error code | Mostly | Old clients show the fallback message |
| Rename or remove an input or answer field | No | Add the new one, keep the old one until clients have moved |
| Change a code's meaning | No | Add a new code |
| Change a route's path | No | Add the new route, keep the old one for a while |

For larger changes, publish a new [API version](/studio/environments-and-promotion) and move clients to it deliberately.


## Developing flows across environments

Flows are definitions, like resources and policies, and they live in each environment.
A common workflow:

| Stage | What happens |
| --- | --- |
| Build | Create or change the flow in the `development` environment in Studio, and call it from a local build of the app |
| Review | Work on a branch of the definitions, so the change can be reviewed before it reaches the main definitions |
| Test | Promote to a staging or preview environment and run the app's tests against it |
| Release | Promote to `production`; clients see the new behavior immediately |

The client code does not change between stages; only the environment's URL, key and name do.
See [Environments and promotion](/studio/environments-and-promotion).


## Common mistakes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Trusting resource blocks to enforce policies | Anyone who may call the flow can act on any record | `policy.check` or `auth.require` in the flow |
| Reading identity from the input | People act as each other | Use `$auth` |
| Answering with whole records | Hidden fields leak | Pick fields in `response.return` |
| No codes on errors | Screens show raw messages or generic failures | `error.raise` with specific codes |
| Marking non-repeatable actions `idempotent` | Double charges after a retry | Only mark actions that are safe to repeat |
| Long work inside the request | Timeouts and uncertain outcomes | Start, track with a record, and follow |
| Caching per-person `GET` routes | One person sees another's answer | Cache only answers that are the same for everyone |


## From the browser or from your server

A browser can call flows and routes directly with a publishable key and the person's session.
Some applications route these calls through their own server instead.
Both are valid; the trade-offs are about what sits between the person and the action.

| Question | Call from the browser | Call from your server |
| --- | --- | --- |
| Where does the token live? | In the browser | In an HTTP-only cookie on your server |
| Latency | One hop to the gateway | Two hops |
| Extra checks before the action | Only what the route and flow do | Anything your server adds |
| Combining several calls into one | Several requests from the browser | One request from the browser, several from the server |
| Exposure of the route's URL | Visible in the browser's network panel | Hidden behind your own endpoint |

Hiding a route's URL is not security: anyone with a session can call the route directly, so the route and its flow must be safe on their own.
Choose the server path for the token handling and the composition, not for obscurity.


## What the person sees while an action runs

An action has a short lifetime on screen, and each moment of it should be visible.

| Moment | Show | Avoid |
| --- | --- | --- |
| Before | An enabled button with a clear verb, such as "Pay 42.00" | A vague "Submit" |
| Running | The button disabled, with "Paying…" | Allowing a second click |
| Succeeded | The result, such as the updated order | A toast that hides what changed |
| Failed with a code | The message for that code, and what to do next | The raw error message |
| Failed without an answer | "We could not confirm the payment. Check your orders before trying again." | Offering to repeat a non-repeatable action blindly |

The last row is the important one.
After a timeout or a network failure, the action may have happened.
Point the person to where they can see the outcome, or check it in code, before letting them repeat it.


## A checklist for client code that calls actions

| Check | Why |
| --- | --- |
| Each action has a typed wrapper with its path, input and answer | Shapes stay in one place |
| Each wrapper maps the action's codes to messages | Screens stay short and consistent |
| Buttons disable while the action runs | Fewer double submissions |
| Non-repeatable actions carry an attempt id | Retries cannot duplicate work |
| Unexpected errors are reported with `requestId` | Support can find the run |
| Long actions follow a tracking record | Outcomes survive reloads and closed tabs |


## Actions and realtime together

An action changes records, and other screens showing those records should update.
When the resources involved have realtime on, the changes a flow makes are published on `resource:<name>` like any other write, to each subscriber who may read the record.

That gives a clean division of work:

| Part | Responsibility |
| --- | --- |
| The screen that started the action | Shows the answer from the route or flow |
| Other screens, and other people's screens | Update from realtime messages |
| The flow | Writes records; it does not need to notify anyone itself |

```typescript
const channel = pawabase.realtime.channel("resource:orders");
channel.on("message", (message) => {
  const { change, record } = message.payload as { change: string; record: { id: string; status: string } };
  if (change === "updated") updateOrderRow(record.id, record.status);
});
await channel.subscribe();

declare function updateOrderRow(id: string, status: string): void;
```

The person who paid sees "Paid" from the route's answer; a colleague watching the orders list sees the row change a moment later.
