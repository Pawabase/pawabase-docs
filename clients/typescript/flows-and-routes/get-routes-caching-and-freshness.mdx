A `GET` route can cache its answers on the server for a configured time.
Cached answers are keyed by the full URL, including the query string.

| Fact | Consequence |
| --- | --- |
| Identical `GET` requests within the cache time get the same answer | Fast, cheap reads for data that changes slowly |
| The route cache is not cleared when records change | A cached answer can be stale for up to the cache time |
| Every query parameter is part of the key | Equivalent queries written differently are cached separately |
| `POST`, `PUT`, `PATCH` and `DELETE` are never cached | Actions always run |

Use route caching for answers that are the same for everyone and tolerate staleness, such as a product catalogue or public statistics.
Do not cache answers that depend on the caller; a cache keyed by URL alone could serve one person's answer to another.


## Versioned APIs

An environment can publish its definitions as numbered API versions.
A release makes a frozen revision of resources and routes answer under its own prefix, such as `/rest/v2`, while `/rest/v1` keeps serving the previous contract.

`pawabase.routes` always calls `/rest/v1`.
To call a route in another API version, use a raw request:

<CodeGroup>
```typescript TypeScript
const v2 = await pawabase.request("POST", `/rest/v2/orders/${orderId}/pay`);
```

```python Python
v2 = pb.request("POST", f"/rest/v2/orders/{order_id}/pay")
```

```bash cURL
curl -X POST "$PAWABASE_URL/rest/v2/orders/$ORDER_ID/pay" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN"
```
</CodeGroup>

Resource queries through `from()` use `/rest/v1` too.
Applications that move to a new API version usually do so all at once, at a release, so a small wrapper that holds the prefix is enough.
See [Releases and API versions](/studio/environments-and-promotion).


## Calls or events

Not every action needs an answer.
"Send the welcome email", "recompute the leaderboard" and "notify the warehouse" can happen after the request that caused them, without the person waiting.

| Pattern | When | How |
| --- | --- | --- |
| A call | The screen needs the result to continue | `flows.run` or `routes.*` |
| A record change that triggers work | The work follows from data the client writes anyway | Write the record; a flow subscribed to `<resource>.created` does the rest |
| An emitted event | A server knows something happened and others should react | `manage(service).events.emit(name, payload)` with a secret key |

The second pattern is often the best.
The client creates an `orders` record, and flows subscribed to `orders.created` send the confirmation, reserve stock and notify the warehouse, each visible in its own run history.
The client's job ends at "create the record", and adding a reaction later needs no client change.


## Security inside flows

A flow is server code, even when it is a graph.
The same rules apply as for any endpoint.

| Rule | Why |
| --- | --- |
| Check the caller's rights explicitly with `policy.check` or `auth.require` | Resource blocks run with service rights and do not apply resource policies |
| Take identity from `$auth`, never from the input | Anyone can send `{ "user_id": "someone-else" }` |
| Validate input that reaches money, permissions or other people | The client is not trusted |
| Read secrets with the secret block, never send them in answers | Answers reach browsers and logs |
| Keep the trigger or route policy as narrow as the action | `authenticated` admits every signed-in person and every secret key |
| Return error codes, not internal details | Messages are shown to people and attackers alike |

The client helps with the last point by surfacing `error.code` and `error.message` only; the flow decides what those contain.


## Debugging a call

When a flow or route call fails unexpectedly, three places together tell the whole story.

| Place | What it shows |
| --- | --- |
| The thrown error | `status`, `code`, `message`, `details`, and `requestId` |
| **Project → Activity**, searched by request id | The request, its duration, its logs and, for a server error, the traceback |
| **Logic → Flows**, the flow's runs | Each block's input, output, duration and error for that run |

Record `requestId` with every unexpected error in your error tracker.
With it, the path from "a user saw an error" to "this block failed with this input" takes a minute.

Operators can also run a flow on demand from code, as a chosen user, and get its trace back, with the management module:

<CodeGroup>
```typescript TypeScript
import { manage } from "@pawabase/client/manage";

const run = await manage(service).flows.run("pay-order", { params: { id: orderId } }, { asUser: { user_id: "u_7" } });
console.log(run.status, run.result, run.trace);
```

```python Python
run = service.manage.flows.run("pay-order", {"params": {"id": order_id}}, as_user={"user_id": "u_7"})
print(run["status"], run["result"], run["trace"])
```

```bash cURL
curl -X POST "$PAWABASE_URL/platform/v1/envs/production/flows/pay-order/run" -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" -d '{"input": {"params": {"id": "o1"}}, "as_user": {"user_id": "u_7"}, "entry": null}'
```
</CodeGroup>

That is the fastest way to reproduce a failure a particular person saw.
See [Environment management](/clients/typescript/management/overview).


## Testing code that calls flows and routes

Client-side code that calls flows and routes can be tested with a fake `fetch` that answers by path:

```typescript
import { test } from "node:test";
import assert from "node:assert/strict";
import { createClient } from "@pawabase/client";

function fakeServer(answers: Record<string, { status: number; body: unknown }>) {
  return createClient({
    url: "https://api.example.test",
    apiKey: "pb_pk_test",
    retry: false,
    fetch: async (input, init) => {
      const key = `${init?.method ?? "GET"} ${new URL(input).pathname}`;
      const answer = answers[key] ?? { status: 404, body: "Not found" };
      return new Response(JSON.stringify(answer.body), { status: answer.status, headers: { "content-type": "application/json" } });
    },
  });
}

test("payOrder maps order_not_found", async () => {
  const pawabase = fakeServer({
    "POST /rest/v1/orders/o1/pay": { status: 404, body: { error: "order_not_found", message: "no such order" } },
  });
  await assert.rejects(pawabase.routes.post("orders/o1/pay"), (error: any) => error.code === "order_not_found" && error.status === 404);
  pawabase.dispose();
});

test("a direct flow answer without response.return is wrapped in data", async () => {
  const pawabase = fakeServer({ "POST /flows/v1/quote-cart": { status: 200, body: { data: { total_minor: 900 } } } });
  const body = await pawabase.flows.run<{ data: { total_minor: number } }>("quote-cart", { cart_id: "c1" });
  assert.equal(body.data.total_minor, 900);
  pawabase.dispose();
});
```

The flows themselves are tested in Studio, with test runs in **Logic → Flows**, and against a development environment.
Before saving a changed flow from code, the management module's `flows.validate(definition)` reports problems node by node without saving.


## Designing a flow's contract

A flow that clients call is an API, even when only your own app calls it.
Deciding its contract before building the graph saves rework on both sides.

| Part of the contract | Decide | Example |
| --- | --- | --- |
| Input | The fields, their types, which are required | `{ cart_id: string, coupon?: string }` |
| Success answer | Status and body | `200 { total_minor, currency, discount_minor }` |
| Expected failures | One code per failure the screen handles differently | `coupon_unknown`, `coupon_expired`, `cart_empty` |
| Status for each failure | The HTTP category | `404` for unknown, `409` for already applied, `422` for invalid input |
| Who may call | The policy | `authenticated` |

Choose statuses by what the client should do, not by what went wrong inside:

| Situation | Status | Why |
| --- | --- | --- |
| The input is malformed or fails a rule | `422` | The person must change what they sent |
| The thing referred to does not exist, or is not theirs | `404` | Nothing to act on |
| The action conflicts with the current state | `409` | Reload and decide again |
| The caller may not do this | `403` | Asking again will not help |
| A partner service failed | `502` | The client may try again later |
| Accepted, finishing in the background | `202` | Follow the tracking record |

Codes are lowercase words joined by underscores, specific to one situation.
`coupon_expired` tells the screen what to say; `error` or `failed` does not.
