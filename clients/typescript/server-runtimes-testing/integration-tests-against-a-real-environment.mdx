Integration tests are the only way to check that policies, rules and flows do what you think.
They need an environment and keys, and they must leave the environment as they found it.

### Which environment

| Option | Pros | Cons |
| --- | --- | --- |
| A dedicated `test` environment | Isolated from developers' data; stable | Its definitions must be kept in step, by promotion |
| A preview environment per branch | Tests the branch's own definitions | Created and removed per run |
| The shared `development` environment | No setup | Tests and people disturb each other |

A dedicated environment, refreshed from development by promotion, suits most teams.
Preview environments suit teams that change definitions often in branches; the management module can create and delete them from CI.

### Test users

Tests need people with known identities and roles.
Create them with the user-administration module and a secret key, sign them in with normal clients, and delete them afterwards.

<CodeGroup>
```typescript TypeScript
// test/people.ts
import { createClient, MemoryStorage, type PawabaseClient } from "@pawabase/client";
import { admin } from "@pawabase/client/admin";

const url = process.env.PAWABASE_URL!;
const environment = process.env.PAWABASE_ENV ?? "test";
const service = createClient({ url, apiKey: process.env.PAWABASE_SECRET_KEY!, environment });
const users = admin(service).users;

export interface TestPerson {
  id: string;
  email: string;
  client: PawabaseClient;
}

export async function person(label: string, roles: string[] = []): Promise<TestPerson> {
  const email = `${label}+${Date.now()}@test.example.com`;
  const password = `pw-${crypto.randomUUID()}`;
  const created = await users.create({ email, password, roles, emailVerified: true });
  const client = createClient({
    url,
    apiKey: process.env.PAWABASE_PUBLISHABLE_KEY!,
    environment,
    auth: { storage: new MemoryStorage(), persistSession: false },
  });
  await client.auth.signInWithPassword({ email, password });
  return { id: String(created.id), email, client };
}

export async function forget(p: TestPerson) {
  p.client.dispose();
  await users.deleteUser(p.id).catch(() => undefined);
}

export { service };
```

```python Python
# tests/people.py
import os
import time
import uuid
from dataclasses import dataclass

from pawabase import MemorySessionStore, Pawabase

URL = os.environ["PAWABASE_URL"]
ENV = os.environ.get("PAWABASE_ENV", "test")
service = Pawabase(URL, os.environ["PAWABASE_SECRET_KEY"], environment=ENV)


@dataclass
class TestPerson:
    id: str
    email: str
    client: Pawabase


def person(label: str, roles: tuple[str, ...] = ()) -> TestPerson:
    email = f"{label}+{int(time.time() * 1000)}@test.example.com"
    password = f"pw-{uuid.uuid4()}"
    created = service.admin.users.create(email=email, password=password, roles=roles, email_verified=True)
    client = Pawabase(URL, os.environ["PAWABASE_PUBLISHABLE_KEY"], environment=ENV, session_store=MemorySessionStore())
    client.auth.sign_in_with_password(email=email, password=password)
    return TestPerson(str(created["id"]), email, client)


def forget(p: TestPerson) -> None:
    p.client.close()
    try:
        service.admin.users.delete_user(p.id)
    except Exception:
        pass
```
</CodeGroup>

Unique emails per run let tests run in parallel and survive leftovers from a crashed run.

### Testing policies as a matrix

Access rules are best tested as a table: who, what, and the expected outcome.

<CodeGroup>
```typescript TypeScript
import { test, before, after } from "node:test";
import assert from "node:assert/strict";
import { person, forget, service, type TestPerson } from "./people";

let ada: TestPerson;
let bob: TestPerson;
let noteId: string;

before(async () => {
  [ada, bob] = await Promise.all([person("ada"), person("bob")]);
  noteId = String((await ada.client.from("notes").create({ title: "Ada's note", body: "private" })).id);
});

after(async () => {
  await service.from("notes").delete(noteId).catch(() => undefined);
  await Promise.all([forget(ada), forget(bob)]);
});

const cases = [
  { who: "owner", act: () => ada.client.from("notes").get(noteId), expect: "ok" },
  { who: "someone else", act: () => bob.client.from("notes").get(noteId), expect: "NotFoundError" },
  { who: "owner updating", act: () => ada.client.from("notes").update(noteId, { title: "x" }), expect: "ok" },
  { who: "someone else updating", act: () => bob.client.from("notes").update(noteId, { title: "x" }), expect: "PermissionError" },
];

for (const c of cases) {
  test(`notes: ${c.who}`, async () => {
    const outcome = await c.act().then(() => "ok", (error: Error) => error.name);
    assert.equal(outcome, c.expect);
  });
}
```

```python Python
import pytest

from tests.people import forget, person, service


@pytest.fixture(scope="module")
def world():
    ada, bob = person("ada"), person("bob")
    note = ada.client.from_("notes").create({"title": "Ada's note", "body": "private"})
    yield ada, bob, note["id"]
    service.from_("notes").delete(note["id"])
    forget(ada)
    forget(bob)


@pytest.mark.parametrize("who, act, expected", [
    ("owner", lambda ada, bob, nid: ada.client.from_("notes").get(nid), "ok"),
    ("someone else", lambda ada, bob, nid: bob.client.from_("notes").get(nid), "NotFoundError"),
    ("owner updating", lambda ada, bob, nid: ada.client.from_("notes").update(nid, {"title": "x"}), "ok"),
    ("someone else updating", lambda ada, bob, nid: bob.client.from_("notes").update(nid, {"title": "x"}), "ForbiddenError"),
])
def test_notes_access(world, who, act, expected):
    ada, bob, note_id = world
    try:
        act(ada, bob, note_id)
        outcome = "ok"
    except Exception as error:
        outcome = type(error).__name__
    assert outcome == expected
```
</CodeGroup>

The table reads like the policy's specification, and a policy change that breaks it fails a named case.
Include the anonymous case, with a client that has no session, for every resource that should not be public.

### Cleaning up

Tests that create data must remove it, or the environment slowly fills with leftovers that make later tests unreliable.

| Data | Clean up with |
| --- | --- |
| Records | The secret-key client, by id, in `after` hooks |
| Files | `listAll` on a per-run prefix, then `remove` |
| Users | `admin().users.deleteUser` |
| Organizations | `admin().orgs.remove` |
| Realtime | Nothing; channels disappear when unused |

Give everything a test run creates a recognizable marker, such as the run's timestamp in names and keys.
A periodic job can then remove anything older than a day with that marker, catching leftovers from crashed runs.

### Calling flows in integration tests

Flows can be tested through the doors clients use, or run directly by the management module with a chosen identity and their trace returned:

<CodeGroup>
```typescript TypeScript
import { manage } from "@pawabase/client/manage";

const run = await manage(service).flows.run("pay-order", { params: { id: orderId } }, { asUser: { user_id: ada.id } });
assert.equal(run.status, "succeeded");
```

```python Python
run = service.manage.flows.run("pay-order", {"params": {"id": order_id}}, as_user={"user_id": ada.id})
assert run["status"] == "succeeded"
```
</CodeGroup>

Running through the client checks the route or trigger policy too; running through the management module checks the flow's logic in isolation, and its `trace` shows each block when a test fails.
