`signUp(input)` creates an account.

<CodeGroup>
```typescript TypeScript
const result = await pawabase.auth.signUp({
  email: "ada@example.com",
  password: "correct horse battery staple",
  name: "Ada Lovelace",
  data: { plan: "free", referral: "newsletter" },
  redirectTo: "https://app.example.com/welcome",
});

if (result.verificationRequired) {
  showMessage(`We sent a confirmation link to ${result.user.email}.`);
} else {
  navigate("/app");
}
```

```python Python
result = pb.auth.sign_up(
    email="ada@example.com",
    password="correct horse battery staple",
    name="Ada Lovelace",
    data={"plan": "free", "referral": "newsletter"},
    redirect_to="https://app.example.com/welcome",
)

if result.verification_required:
    show_message(f"We sent a confirmation link to {result.user['email']}.")
```

```bash cURL
curl -X POST "$PAWABASE_URL/auth/v1/signup" -H "apikey: $PAWABASE_KEY" -H "content-type: application/json" -d '{
  "email": "ada@example.com", "password": "correct horse battery staple", "name": "Ada Lovelace",
  "data": {"plan": "free"}, "redirect_to": "https://app.example.com/welcome"
}'
# → a session, or {"verification_required": true, "user": {…}}
```
</CodeGroup>

| Input | Required | Meaning |
| --- | --- | --- |
| `email` | Yes | The account's address |
| `password` | Yes | Checked against the environment's password policy |
| `username` | No | A username, if the environment uses them |
| `name` | No | The display name |
| `data` | No | The initial `user_metadata`, which the user can edit later |
| `redirectTo` | No | Where the confirmation link sends the user; must be an allowed redirect URL |

| Result field | Meaning |
| --- | --- |
| `user` | The new user |
| `session` | The session, or `null` when the address must be confirmed first |
| `verificationRequired` | `true` when a confirmation email was sent and no session was created |

When verification is not required, the user is signed in immediately and listeners get `SIGNED_IN`.

`data` becomes `user_metadata`, which the user can change at any time.
Never put anything in it that grants access.
A plan, a role or a tenant that controls what the user may do belongs in `app_metadata` or roles, set by an administrator or a server; see [User administration](/clients/typescript/user-administration/overview).

| Error | Cause |
| --- | --- |
| `PermissionError`, `sign-up is disabled` | The environment does not allow sign-up |
| `ValidationError` | The email is malformed or the password does not meet the policy |
| `RateLimitError` | Too many sign-ups from this address in a short time |


## Signing in with a password

`signInWithPassword({ email, password, org? })` returns one of two results.

<CodeGroup>
```typescript TypeScript
const result = await pawabase.auth.signInWithPassword({ email, password });

if (result.status === "signed_in") {
  navigate("/app");
} else {
  // result.status === "mfa_required"
  showMfaPrompt(result.factors, (code) => result.verify(code));
}
```

```python Python
result = pb.auth.sign_in_with_password(email=email, password=password)

if result.status == "signed_in":
    go_to_app()
else:  # "mfa_required"
    show_mfa_prompt(result.factors, result.verify)
```

```bash cURL
curl -X POST "$PAWABASE_URL/auth/v1/token" -H "apikey: $PAWABASE_KEY" -H "content-type: application/json" -d '{"grant_type": "password", "email": "ada@example.com", "password": "…"}'
```
</CodeGroup>

| `status` | Fields | Meaning |
| --- | --- | --- |
| `signed_in` | `session` | The user is signed in; listeners got `SIGNED_IN` |
| `mfa_required` | `mfaToken`, `factors`, `verify(code)` | The password was right; a second factor is needed |

`org` asks for tokens issued for one of the user's organizations from the start, so policies that test `$auth.org` work on the first request.

The answers that are not a success are worth handling one by one, because each needs a different message:

| Server answer | Client error | What to tell the person |
| --- | --- | --- |
| `401` | `AuthenticationError` | The email or password is wrong |
| `403 this account is disabled` | `PermissionError` | The account is not available; offer support |
| `403 confirm your email address first` | `PermissionError` | Check your email, with a resend button |
| `429 too many failed attempts` | `RateLimitError` | The account is temporarily locked; try again later |

A locked account answers `429` even when the password is right.
The lock is a counter of failed attempts on the account, shared by passwords and second-factor codes, and it expires on its own after a period the installation sets.
The client treats `429` as retryable, so it repeats the request up to twice before throwing; while the account is locked, every attempt is refused the same way, and nothing worse happens.

### Finishing a sign-in that needs MFA

When `status` is `mfa_required`, the password was correct and the auth service is waiting for a second factor.
`factors` lists what the account has, such as `["totp"]` or `["email"]`.

`verify(code)` finishes the sign-in with a code from an authenticator app, a code from the email factor, or one of the account's recovery codes.

<CodeGroup>
```typescript TypeScript
const session = await result.verify("492817");
```

```python Python
session = result.verify("492817")
```

```bash cURL
curl -X POST "$PAWABASE_URL/auth/v1/token" -H "apikey: $PAWABASE_KEY" -H "content-type: application/json" -d '{"grant_type": "mfa", "mfa_token": "…", "code": "492817"}'
```
</CodeGroup>

For the email factor, the code must be sent first:

<CodeGroup>
```typescript TypeScript
if (result.factors.includes("email")) {
  await pawabase.auth.mfa.challenge(result.mfaToken);
}
```

```python Python
if "email" in result.factors:
    pb.auth.mfa.challenge(result.mfa_token)
```

```bash cURL
curl -X POST "$PAWABASE_URL/auth/v1/mfa/challenge" -H "apikey: $PAWABASE_KEY" -H "content-type: application/json" -d '{"mfa_token": "…"}'
```
</CodeGroup>

`verifyMfa({ mfaToken, code, org? })` is the same as `verify`, for code that kept the token rather than the result object.

The MFA token authorizes nothing on its own.
It cannot be sent as a bearer token; it only finishes this sign-in.

### When the environment requires MFA

An environment can require a second factor for everyone.
A person who has none yet then signs in with a password and is held until they set one up.

<CodeGroup>
```typescript TypeScript
await pawabase.auth.mfa.startSetup({ mfaToken: result.mfaToken, method: "totp" });
// show the QR code from the response, ask for the first code
const done = await pawabase.auth.mfa.completeSetup({ mfaToken: result.mfaToken, code });
```

```python Python
pb.auth.mfa.start_setup(mfa_token=result.mfa_token, method="totp")
# show the QR code from the response, ask for the first code
done = pb.auth.mfa.complete_setup(mfa_token=result.mfa_token, code=code)
# The Python client stores the new session itself when the answer carries tokens.
```

```bash cURL
curl -X POST "$PAWABASE_URL/auth/v1/mfa/setup/start" -H "apikey: $PAWABASE_KEY" -H "content-type: application/json" -d '{"mfa_token": "…", "method": "totp"}'
curl -X POST "$PAWABASE_URL/auth/v1/mfa/setup/complete" -H "apikey: $PAWABASE_KEY" -H "content-type: application/json" -d '{"mfa_token": "…", "code": "123456"}'
```
</CodeGroup>

`startSetup` begins enrolment for `totp` or `email` and returns what the user needs to enroll.
`completeSetup` confirms the first code and returns the new tokens and the one-time recovery codes.

`completeSetup` returns the tokens but does not store them.
Adopt them with `setSession` so the client keeps the new session:

```typescript
const done = (await pawabase.auth.mfa.completeSetup({ mfaToken, code })) as {
  access_token?: string;
  refresh_token?: string;
  recovery_codes?: string[];
};
if (done.access_token && done.refresh_token) {
  await pawabase.auth.setSession({ access_token: done.access_token, refresh_token: done.refresh_token });
}
showRecoveryCodesOnce(done.recovery_codes ?? []);
```
