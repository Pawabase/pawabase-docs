Organizations let one person belong to several groups, such as companies, teams or households, with a role in each.
They are how multi-tenant applications are usually built on Pawabase: records carry an organization, and policies compare it with the organization in the caller's token.

`pawabase.auth.orgs` is the signed-in person's view of their organizations.
What they may do in each depends on their role there.

| Role | Typical rights |
| --- | --- |
| `viewer` | Read the organization |
| `member` | Read, and take part in what the application allows members to do |
| `admin` | Manage members and invitations |
| `owner` | Everything, including deleting the organization |

### Listing and creating

<CodeGroup>
```typescript TypeScript
const orgs = await pawabase.auth.orgs.list();
for (const org of orgs) console.log(org.slug, org.name, org.role);

const acme = await pawabase.auth.orgs.create({ slug: "acme", name: "Acme Ltd" });
```

```python Python
for org in pb.auth.orgs.list():
    print(org["slug"], org["name"], org["role"])

acme = pb.auth.orgs.create(slug="acme", name="Acme Ltd")
```

```bash cURL
curl "$PAWABASE_URL/auth/v1/orgs" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN"
curl -X POST "$PAWABASE_URL/auth/v1/orgs" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"slug": "acme", "name": "Acme Ltd"}'
```
</CodeGroup>

The person who creates an organization becomes its owner.
`get(slug)`, `update(slug, { name, metadata })` and `delete(slug)` read, change and remove one, subject to the caller's role.

```bash cURL
curl -X PUT "$PAWABASE_URL/auth/v1/orgs/acme/members/$USER_ID" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"role": "admin"}'

```
</CodeGroup>

Each member has `user_id`, `email`, `name` and `role`.

### Invitations

An admin invites someone by email.
The invitation email carries a token; the invited person signs in, or signs up, and accepts it.

<CodeGroup>
```typescript TypeScript
await pawabase.auth.orgs.invite("acme", { email: "grace@example.com", role: "member", redirectTo: "https://app.example.com/join" });

const pending = await pawabase.auth.orgs.invitations("acme");
await pawabase.auth.orgs.revokeInvitation("acme", pending[0].id);
```

```python Python
pb.auth.orgs.invite("acme", email="grace@example.com", role="member", redirect_to="https://app.example.com/join")

pending = pb.auth.orgs.invitations("acme")
pb.auth.orgs.revoke_invitation("acme", pending[0]["id"])
```

```bash cURL
curl -X POST "$PAWABASE_URL/auth/v1/orgs/acme/invitations" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"email": "grace@example.com", "role": "member"}'
```
</CodeGroup>

<CodeGroup>
```typescript TypeScript
// On the page the invitation link opens, after the person is signed in:
await pawabase.auth.orgs.acceptInvitation(tokenFromLink);
await pawabase.auth.switchOrg("acme");
```

```python Python
pb.auth.orgs.accept_invitation(token_from_link)
pb.auth.switch_org("acme")
```

```bash cURL
curl -X POST "$PAWABASE_URL/auth/v1/invitations/accept" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"token": "…"}'
```
</CodeGroup>

Accepting requires a signed-in person.
If they arrive signed out, keep the token, take them through sign-in or sign-up, then accept.
`redirectTo` must be one of the environment's allowed redirect URLs.

### The organization in the token

An access token is issued for at most one organization at a time.
The session's `org` and `org_role` fields say which, and policies see them as `$auth.org` and `$auth.org_role`.

`switchOrg(slug)` asks for new tokens for another organization the person belongs to, or for none with `null`.
It is a refresh with an extra parameter, so it rotates the refresh token like any refresh and emits `TOKEN_REFRESHED`.

<CodeGroup>
```typescript TypeScript
const session = await pawabase.auth.switchOrg("acme");
console.log(session.org, session.org_role); // "acme", "admin"
```

```python Python
session = pb.auth.switch_org("acme")
print(session.org, session.org_role)   # "acme", "admin"
```

```bash cURL
curl -X POST "$PAWABASE_URL/auth/v1/token" -H "apikey: $PAWABASE_KEY" -H "content-type: application/json" -d '{"grant_type": "refresh_token", "refresh_token": "…", "org": "acme"}'
```
</CodeGroup>

You can also choose the organization at sign-in, with the `org` option of `signInWithPassword`, so the first token already carries it.

An application with an organization switcher typically:

| Moment | Call |
| --- | --- |
| After sign-in | `orgs.list()` to fill the switcher |
| The person picks an organization | `switchOrg(slug)`, then reload the screen's data |
| The page loads | Read `session.org` to know which organization is active |

Data loaded before a switch belongs to the previous organization.
Clear it, or key your data cache by organization, so one tenant's records never appear under another's name.


## Sessions on a server

Server-rendered applications often keep the session in HTTP-only cookies, so that no script in the browser can read the tokens.
The server then performs sign-in, stores the tokens in cookies, refreshes them, and acts for the person with `asUser`.

The client supports this with a short-lived, memory-only client per sign-in request.

```typescript
import { createClient, MemoryStorage, AuthenticationError } from "@pawabase/client";

function authClient() {
  return createClient({
    url: process.env.PAWABASE_URL!,
    apiKey: process.env.PAWABASE_PUBLISHABLE_KEY!,
    environment: process.env.PAWABASE_ENV,
    auth: { storage: new MemoryStorage(), persistSession: false, autoRefreshToken: false, detectSessionInUrl: false },
  });
}

export async function signInHandler(email: string, password: string) {
  const client = authClient();
  try {
    const result = await client.auth.signInWithPassword({ email, password });
    if (result.status === "mfa_required") return { mfaToken: result.mfaToken, factors: result.factors };
    return { cookies: sessionCookies(result.session.access_token, result.session.refresh_token, result.session.expires_at) };
  } catch (error) {
    if (error instanceof AuthenticationError) return { error: "Wrong email or password." };
    throw error;
  } finally {
    client.dispose();
  }
}

function sessionCookies(access: string, refresh: string, expiresAt: number) {
  const secure = "Path=/; HttpOnly; Secure; SameSite=Lax";
  return [
    `pb-access=${access}; ${secure}; Expires=${new Date(expiresAt * 1000).toUTCString()}`,
    `pb-refresh=${refresh}; ${secure}; Max-Age=${60 * 60 * 24 * 30}`,
  ];
}
```

Refreshing on the server uses the same short-lived client, seeded with the stored tokens:

```typescript
export async function refreshHandler(accessToken: string, refreshToken: string) {
  const client = authClient();
  try {
    await client.auth.setSession({ access_token: accessToken, refresh_token: refreshToken });
    const session = await client.auth.refreshSession();
    return { cookies: sessionCookies(session.access_token, session.refresh_token, session.expires_at) };
  } catch (error) {
    if (error instanceof AuthenticationError) return { signedOut: true };
    throw error;
  } finally {
    client.dispose();
  }
}
```

`setSession` needs a valid access token, because it fetches the user with it.
If the stored access token has already expired, call the token endpoint directly with the refresh token:

<CodeGroup>
```typescript TypeScript
const fresh = await client.request<{ access_token: string; refresh_token: string; expires_in: number }>(
  "POST",
  "/auth/v1/token",
  { body: { grant_type: "refresh_token", refresh_token: refreshToken } },
);
```

```python Python
fresh = client.request("POST", "/auth/v1/token", json={"grant_type": "refresh_token", "refresh_token": refresh_token})
```

```bash cURL
curl -X POST "$PAWABASE_URL/auth/v1/token" -H "apikey: $PAWABASE_KEY" -H "content-type: application/json" -d '{"grant_type": "refresh_token", "refresh_token": "…"}'
```
</CodeGroup>

The rotation rule applies on servers too.
Two concurrent requests that both refresh the same cookie will end the session.
Refresh in one place, such as middleware that runs before handlers, and make concurrent requests wait for it, or refresh only when a request actually receives `401`.
