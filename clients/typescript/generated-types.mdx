Generated types make the client aware of resource names and each resource's read, create, and update shapes.
They are a development-time view of one environment's compiled OpenAPI document.
They do not change runtime validation, policies, or the deployed schema.

The mental model is a one-way snapshot:

```text
Studio resource definitions
        │
        ▼
Environment OpenAPI document
        │
        ▼
pawabase-types
        │
        ▼
Database interface used by createClient<Database>()
```

When the environment changes, regenerate the file.

## What becomes typed

| SDK expression | Generated check |
| --- | --- |
| `client.from("posts")` | Resource name exists |
| `create(body)` | Required and allowed create fields |
| `update(id, patch)` | Allowed update fields and values |
| `eq("status", value)` | Field exists and value fits row field type |
| `order("created_at")` | Field exists |
| `select("id", "title")` | Selected fields exist |
| Returned row | Resource read shape |

The generator does not make runtime data trustworthy.
Server validation and application runtime validation still matter at external boundaries.

## Source from the gateway

The command can fetch the environment's OpenAPI document when public generated docs are enabled.

```bash
npx pawabase-types \
  --url https://api.example.com \
  --project acme \
  --env production \
  --out src/pawabase.types.ts
```

The gateway URL is the origin.
`--project` is the project reference.
`--env` is the environment name.
The command reads `/docs/v1/<project>/<env>/openapi.json`.

If the endpoint requires an API key, supply it through the option or environment variable.

```bash
PAWABASE_API_KEY=pb_pk_… npx pawabase-types \
  --url https://api.example.com \
  --project acme \
  --env production \
  --out src/pawabase.types.ts
```

Avoid putting secret keys directly in shell history.

## Source from a file

When public docs are disabled, save the OpenAPI document from Studio's **API Explorer** and generate locally.

```bash
npx pawabase-types \
  --file openapi.json \
  --out src/pawabase.types.ts
```

The file path workflow keeps the API document private.
It is also useful for reproducible builds where the exact specification is already an artifact.

## Command options

| Option | Short | Environment variable | Meaning |
| --- | --- | --- | --- |
| `--url` | `-u` | `PAWABASE_URL` | Gateway origin |
| `--project` | `-p` | `PAWABASE_PROJECT` | Project reference |
| `--env` | `-e` | `PAWABASE_ENV` | Environment name |
| `--api-key` | `-k` | `PAWABASE_API_KEY` | Key sent as `apikey` when fetching |
| `--file` | `-f` | None | Local OpenAPI document instead of gateway fetch |
| `--out` | `-o` | None | Output file; defaults to `pawabase.types.ts`; `-` writes stdout |
| `--name` | None | None | Root interface name; defaults to `Database` |
| `--check` | None | None | Exit nonzero when existing output is stale; write nothing |
| `--help` | `-h` | None | Print usage |

The fetch mode needs URL, project, and environment.
The file mode needs only the document path.

## Use the generated interface

```typescript
import { createClient } from "@pawabase/client";
import type { Database } from "./pawabase.types";

export const client = createClient<Database>({
  url: import.meta.env.PUBLIC_PAWABASE_URL,
  apiKey: import.meta.env.PUBLIC_PAWABASE_KEY,
});
```

The `Database` shape has a `resources` property.
Each resource supplies `Row`, `Insert`, and `Update` types.

```typescript
export interface Database {
  resources: {
    posts: {
      Row: Posts;
      Insert: PostsInsert;
      Update: PostsUpdate;
    };
  };
}
```

The exact generated field definitions come from the OpenAPI schemas, not from this illustrative excerpt.

## Read, insert, and update shapes differ

One interface cannot correctly represent every operation.

| Shape | Represents | Why it differs |
| --- | --- | --- |
| `Row` | API response | Includes IDs, timestamps, defaults, and nullable projection behavior |
| `Insert` | Create request | Required fields reflect the create schema; server-generated fields may be absent |
| `Update` | Patch request | Fields are generally optional because only changed values are sent |

```typescript
await client.from("posts").create({
  title: "Typed create",
});

await client.from("posts").update(42, {
  title: "Typed patch",
});
```

Reusing `Row` as a create body would incorrectly require generated values or allow read-only fields.
The generator preserves the operation-specific distinction.

## Nullability and selection

The read document marks response fields nullable because a `select` can leave unselected fields represented as `null`.
The generator also uses the create schema to distinguish required create fields from values that may be absent or null.

This means an apparently required stored field can still appear nullable in a broad row type.
Application code that selects a known set of fields gets a narrowed selection result, but must still respect the response contract.

```typescript
const page = await client
  .from("posts")
  .select("id", "title");
```

## Compile-time failures

With a current generated file, TypeScript can catch mistakes such as:

```typescript
client.from("postz");
// Resource name does not exist.
```

```typescript
await client.from("posts").create({
  views: 3,
});
// Required create fields are missing.
```

```typescript
client.from("posts").eq("publshed", true);
// Column name does not exist.
```

These are editor or build errors.
They do not replace server errors caused by policies, runtime constraints, data races, or a stale file.

## Check drift in continuous integration

`--check` regenerates in memory and compares the meaningful generated body with the existing output.
It writes nothing and exits with status 1 when stale.

```bash
npx pawabase-types \
  --url "$PAWABASE_URL" \
  --project "$PAWABASE_PROJECT" \
  --env "$PAWABASE_ENV" \
  --out src/pawabase.types.ts \
  --check
```

A typical workflow commits the generated file and runs this check after resource changes.
The generated header includes source/version information, while the drift comparison focuses on the generated body.

## Environment alignment

Types belong to one compiled environment.
Using production types against development is safe only while those environments have the same public schemas.

| Mismatch | Possible result |
| --- | --- |
| Types contain a field not deployed in target | Server rejects a request or never returns the field |
| Target requires a new field absent from types | TypeScript accepts an incomplete body; server returns `422` |
| Resource renamed in target | Client receives `404` despite compiling |
| Field type changed | Runtime value violates application assumptions |
| Operation disabled in target | Typed method exists but server refuses or has no route |

Generate from the environment used by the build or enforce schema promotion discipline so the shared file remains valid.

## Public docs setting

Gateway generation requires the environment's public generated documentation setting.
When it is off, the fetch endpoint returns `404` by design.
Use the file exported from **API Explorer** rather than turning on public docs merely for a private CI job if the schema should remain private.

<Note>
  An OpenAPI document can reveal resource names, fields, constraints, and routes even when policies protect the data.
  Decide whether public docs are appropriate for the application threat model.
</Note>

## Relation expansions

Expanded relations are not added automatically to generated row types.
The base document describes the resource row, while an `expand` response depends on the requested relation set.

Define a local composition for a stable expansion.

```typescript
type Post = Database["resources"]["posts"]["Row"];
type Author = Database["resources"]["authors"]["Row"];

type PostWithAuthor = Post & {
  author: Author | null;
};

const posts = client.resource<PostWithAuthor>("posts");
const page = await posts.expand("author");
```

This manual declaration is an assertion about the relation response.
Keep it close to the query and test it against the intended environment.

## Manually typed resources

`resource<Row, Insert, Update>()` is available when generation is unavailable or when an application wants a view-specific type.

```typescript
interface AuditRow {
  id: string;
  action: string;
  created_at: string;
}

const audit = client.resource<AuditRow>("audit_events");
```

Manual types are useful for gradual adoption, but they drift silently.
Generated roots are preferable for the base database contract.

## Custom root name

Use `--name` when a repository has multiple Pawabase environments or multiple generated clients.

```bash
npx pawabase-types \
  --file customer-openapi.json \
  --name CustomerDatabase \
  --out src/customer-pawabase.types.ts
```

Choose names that make environment or service ownership clear.

## Write to standard output

`--out -` prints generated text.

```bash
npx pawabase-types --file openapi.json --out -
```

This is useful for review and pipeline composition.
Avoid shell pipelines that can partially replace a committed file when the generator fails; generate to a temporary location and move it only after success in build tooling.

## Programmatic generation

The package exports `generateTypes(spec, options?)` for build tools that already own an OpenAPI object.

```typescript
import { generateTypes } from "@pawabase/client";

const source = generateTypes(openapi, {
  name: "Database",
  source: "checked-in openapi.json",
});
```

The result is file text.
`name` controls the root interface and `source` controls the header description.
The command-line tool remains the simpler choice for most applications.

## Generated helper aliases

The output includes aliases for extracting operation shapes by resource name.

```typescript
import type {
  Database,
  Insert,
  Row,
  Update,
} from "./pawabase.types";

type Post = Row<"posts">;
type NewPost = Insert<"posts">;
type PostPatch = Update<"posts">;
```

These aliases are useful in component props, form adapters, queues, and test factories where a root client generic is not in scope.

## Schema-to-TypeScript mapping

The generator intentionally uses a small, predictable mapping.

| OpenAPI schema | Generated TypeScript |
| --- | --- |
| `integer` | `number` |
| `number` | `number` |
| `string` | `string` |
| `boolean` | `boolean` |
| `null` | `null` |
| `enum` | Union of literal values |
| Array | `T[]` or `Array<A \| B>` |
| Object | `Record<string, unknown>` |
| `anyOf` / `oneOf` | Union when every variant is known |
| Missing or unsupported schema | `unknown` |

Formats such as date-time remain strings because the JSON wire value is a string.
The generator does not turn them into JavaScript `Date` objects at runtime.

```typescript
const createdAt = new Date(post.created_at);
```

Validate parsing before using date arithmetic.

## Enums

An OpenAPI enum becomes a literal union.

```typescript
type Status = "draft" | "review" | "live";
```

This catches unsupported values in source code.
Runtime data still needs server validation, and a newly deployed enum member can reach an old client before its generated file is updated.

Use an exhaustive switch with an operational fallback at external boundaries.

```typescript
switch (post.status) {
  case "draft":
  case "review":
  case "live":
    renderKnownStatus(post.status);
    break;
  default:
    renderUnknownStatus(post.status);
}
```

## Unusual names

Resource and field names that are not valid TypeScript identifiers are emitted as quoted properties.

```typescript
interface ExampleRow {
  "display-name": string;
  "2026_value": number | null;
}
```

Access them with bracket notation.

```typescript
console.log(row["display-name"]);
```

The generated interface remains valid, but conventional lowercase resource names and identifier-style fields produce easier application code.

## Interface-name normalization

Resource names are converted to PascalCase for generated interface names.
Separators split words.

```text
order_items   → OrderItemsRow
audit-events  → AuditEventsRow
```

Avoid resource names that normalize to the same PascalCase value.
The public resource names can be distinct while their generated interface identifiers collide.

## Row-field guarantees

The generator uses the insert schema to decide which response fields are guaranteed non-null.
A create-required field is non-null in the generated row.
A field with a non-null create default is also treated as guaranteed.
Other response fields include `null` because projection and existing data can omit them.

System timestamps are added as optional strings when the read schema does not declare them.
This keeps common generated server fields available without claiming every response must contain them.

## Update nullability

Generated update fields are optional because a patch may omit them.
Known values also include `null` because the public patch transport accepts null.

```typescript
type Patch = {
  title?: string | null;
};
```

Server field constraints remain authoritative.
Type generation cannot infer every database or custom validation rule that rejects a null update.

## Resource discovery

The generator recognizes collection paths shaped like `/rest/v<version>/<resource>` when the list or create operation exposes a row schema.
Custom routes without a resource row model are not added to `Database.resources`.

This boundary is why the generated root types records but does not create strongly typed wrappers for every custom route, function, or flow.
Maintain explicit request/response types and runtime schemas for those surfaces.

## Reference resolution

OpenAPI component references are followed when discovering row and body schemas.
Reference chains are bounded so a malformed or cyclic document cannot cause unbounded resolution.

If an expected resource is missing, inspect the actual collection path and its `200` list or `201` create schema in **API Explorer** rather than adding it by hand to the generated file.

## Generated-file ownership

The header states that the file is generated and should not be hand-edited.
Treat changes in three categories:

| Diff | Meaning |
| --- | --- |
| New or removed resource | Public collection contract changed |
| Insert requiredness changed | Create callers may need source changes |
| Row field type/nullability changed | Read consumers and caches may need changes |
| Update field changed | Edit forms and patch producers may need changes |
| Only header source/version changed | Document source changed; meaningful body may be identical |

Review the generated diff with the Studio definition change that caused it.

## Multiple environments in one repository

When application code intentionally calls environments with different schemas, generate separate roots.

```bash
npx pawabase-types \
  --file customer-openapi.json \
  --name CustomerDatabase \
  --out src/pawabase.customer.types.ts

npx pawabase-types \
  --file operations-openapi.json \
  --name OperationsDatabase \
  --out src/pawabase.operations.types.ts
```

Do not combine incompatible resources into one hand-edited root.
Separate types make the chosen client and deployment boundary visible.

## CI without public docs

A private-document workflow can still check drift.
Export the OpenAPI document as a protected build artifact, then run `--file --check`.

```bash
npx pawabase-types \
  --file artifacts/openapi.json \
  --out src/pawabase.types.ts \
  --check
```

Protect the artifact according to the sensitivity of resource names and schemas.
Do not print the full document in public CI logs.

## Type generation in application tests

Compile-time fixture tests can assert that expected source code type-checks and intentionally invalid examples fail.
Runtime integration tests should also call the active environment because a generated file can be current at build time and the deployment can change later.

Useful drift tests include:

- every expected resource remains present;
- required create fields compile as required;
- enum literals reject unsupported values;
- selected fields have the expected projection type;
- manually composed expansion types still match real responses;
- `--check` passes against the intended environment document.

See [server runtimes and testing](/clients/typescript/server-runtimes-testing) for the broader test boundary.

## What generation does not guarantee

| Not guaranteed | Why |
| --- | --- |
| Current runtime schema | The file can be stale or generated from another environment |
| Authorization | Policies are evaluated at runtime per request |
| Record existence | Data changes independently of types |
| Valid expanded relation shape | Expansions are request-specific and not generated |
| Function, flow, and arbitrary route response types | The database generator focuses on resource schemas |
| Runtime validation of `downloadJson<T>()` or generic call results | Type erasure means generics do not inspect JSON |
| Successful operation | Key scopes, operation enablement, constraints, and server state still apply |

## Troubleshooting

| Symptom | Cause | Resolution |
| --- | --- | --- |
| Fetch returns `404` | Public docs disabled or project/environment wrong | Export from API Explorer or correct scope |
| Fetch returns `401` | Key missing, invalid, or wrong environment | Supply the correct environment key |
| Generator says URL/project/env required | Neither complete fetch input nor `--file` was supplied | Provide all fetch fields or a file |
| `--check` fails | Checked-in types differ from current document | Review schema change and regenerate |
| Editor still shows old fields | Import path or TypeScript cache points to old file | Confirm import and restart language service if needed |
| Server rejects a compiled request | Stale or cross-environment types, or runtime-only rule | Regenerate and inspect API Explorer/error issues |
| Expanded relation is missing in type | Relations are not generated into base row | Compose a query-specific type |

## Repository practice

Commit the generated type file when application builds should not depend on a live Pawabase endpoint.
Regenerate in the resource-change workflow.
Review generated diffs as API-contract changes.
Use `--check` against the intended environment in CI where network and credentials are acceptable.

Do not hand-edit a generated file to silence a type error.
Fix the Studio definition, regenerate, or add a separate application composition for behavior that OpenAPI does not express.
