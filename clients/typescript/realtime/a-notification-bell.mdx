A notification bell needs an accurate unread count on first load, and immediate updates afterwards.
Records give the first; realtime gives the second.

```typescript
export async function startBell(userId: string, render: (unread: number) => void) {
  const notifications = pawabase.from("notifications");
  let unread = await notifications.eq("read", false).count();
  render(unread);

  const changes = pawabase.realtime.channel("resource:notifications");
  changes.on("message", (message) => {
    const { change, record } = message.payload as { change: string; record: { read: boolean } };
    if (change === "created" && !record.read) unread += 1;
    if (change === "updated" && record.read) unread = Math.max(0, unread - 1);
    render(unread);
  });
  changes.on("subscribed", async () => {
    unread = await notifications.eq("read", false).count();
    render(unread);
  });
  await changes.subscribe();
}
```

The `notifications` resource's read policy limits both the count and the changes to the person's own notifications, so the bell never counts someone else's.
Recounting on `subscribed` corrects any drift after a reconnect.


## Sending over the socket or over HTTP

| | `channel.send` | `realtime.publish` |
| --- | --- | --- |
| Needs a joined channel | No; it needs an open connection | No |
| Transport | The shared WebSocket | One HTTP request |
| Typical caller | A browser or app on the channel | A server, a job, or a browser that is not subscribed |
| Retried by the client | No | No, after a network failure; yes, after `429` |
| Answer | `{ id }` when accepted | `{ id, channel, event }` when accepted |

Browsers that are already on a channel should use `send`; it is faster and uses the open connection.
Servers should use `publish`, which needs no socket.


## How channels come and go

A channel is not created or deleted by anyone.
It exists while there are subscribers or recent messages to keep, and the server forgets it afterwards.

| Moment | What exists |
| --- | --- |
| Nobody has joined `chat:42` yet | Nothing; a subscribe brings it into being |
| People are subscribed | The channel, its subscribers, its presence and its recent history |
| The last subscriber leaves | Recent history may still be kept, in memory or, for durable rules, in the database |
| A durable channel's retention passes | Its stored messages are purged |

You can therefore use as many channel names as your data has things, such as one per document, without managing them.
Each project's plan may limit how many channels can be active at once.

## Designing channel names

Channel names are the vocabulary your rules speak.
A consistent scheme makes rules short and mistakes visible.

| Principle | Example | Why |
| --- | --- | --- |
| Start with the kind of channel | `chat:…`, `user:…`, `doc:…` | One rule per kind, matched with `kind:*` |
| Put the access boundary next | `org:acme:…`, `user:u_7` | Templated rules and segment checks can compare it |
| End with the specific thing | `org:acme:chat:general` | Many channels share one rule |
| Use ids, not names | `doc:01JB9C2W`, not `doc:Q3 plan` | Names change and contain characters channels do not allow |
| Keep resource changes on `resource:<name>` | `resource:orders` | The platform publishes there; do not reuse the prefix |

### Rule order matters

Rules are tried from the top, and the first match wins.
A general rule placed above a specific one hides it.

| Order | Channel `chat:staff` | Effect |
| --- | --- | --- |
| `chat:*` (authenticated), then `chat:staff` (role staff) | Matches `chat:*` first | Every signed-in person can join the staff room |
| `chat:staff` (role staff), then `chat:*` (authenticated) | Matches `chat:staff` first | Only staff can join |

Put specific patterns first and general ones after.
After changing rules, test a channel of each kind as a person who should be refused, not only as one who should be admitted.


## Presence in depth

Presence answers "who is here now", and its details decide whether that answer is accurate.

| Situation | What presence shows | What to do |
| --- | --- | --- |
| One person, two tabs | Two members with the same `user_id` | Group by `user_id` for "who is here" |
| A tab is closed | The member leaves after the server notices the connection is gone | Expect a short delay |
| A laptop sleeps | The member stays until the connection times out, then leaves | Do not treat presence as proof of attention |
| A person updates their data | A `presence` event with the member in `joins` | Replace by `presence_ref` |
| A person without a session | A member with `user_id: null` | Show "guest", or require sign-in by rule |

Everything in presence data is visible to everyone on the channel.
Do not put email addresses or other private details there unless every member may see them.

`presenceState()` returns the client's view, rebuilt from the server's `presence_state` frame when you join and updated from each `presence_diff`.
`realtime.presence(channel)` asks the server directly over HTTP, which is useful for a server that wants a count without joining.

```typescript
function uniquePeople(members: Array<{ user_id: string | null; meta: { name?: string } }>) {
  const byUser = new Map<string, string>();
  let guests = 0;
  for (const member of members) {
    if (member.user_id) byUser.set(member.user_id, member.meta.name ?? "Someone");
    else guests += 1;
  }
  return { people: [...byUser.values()], guests };
}
```


## Durable channels

A rule whose kind is `durable` keeps its channels' messages in the database, not only in memory.
History then survives a server restart, for the rule's retention period or the installation's default of seven days.

| | Default kind | `durable` |
| --- | --- | --- |
| History after a restart | Lost | Kept for the retention period |
| History length | The rule's `history` | The rule's `history` |
| Cost per message | Memory | A database write |
| Fits | Chat cursors, typing, transient updates | Activity feeds, announcements, anything people catch up on |

The server can make a repeated publish to a durable channel harmless when the publish carries a client message id.
The TypeScript client does not send one, so a send that is retried by your own code after a timeout can produce two messages.
Retry sends to durable channels only after checking history for the first attempt, or accept the occasional duplicate.


## Realtime on mobile

Mobile operating systems suspend apps in the background and close their sockets.
The client reconnects when the app runs again, but a few habits make the experience better.

| Habit | Why |
| --- | --- |
| Disconnect when the app goes to the background, and connect when it returns | Avoids a stream of failed reconnects while suspended, and saves battery |
| Reload screen data on `subscribed` after returning | Messages sent while suspended are not delivered live |
| Keep `heartbeatSeconds` at the default or higher | Each ping wakes the radio |
| Use `replay` on channels people read like a feed | Short absences are filled without reloading |

```typescript
import { AppState } from "react-native";

AppState.addEventListener("change", (state) => {
  if (state === "active") void pawabase.realtime.connect();
  else pawabase.realtime.disconnect();
});
```

Channels keep their listeners across `disconnect()` and are rejoined on the next `connect()`.


## Realtime and server rendering

A server rendering a page has no use for a live socket; the page is sent once.
Open realtime connections in the browser only, after the page has hydrated.

In React, subscribe inside `useEffect`, which does not run on the server.
In other frameworks, use their client-only lifecycle hook.
A server that creates a client per request and touches `realtime.channel(…).subscribe()` would open a socket per request and never use it.


## Cost and scale

Every message is delivered to every subscriber of its channel, so the work grows with both.

| Factor | Effect | Lever |
| --- | --- | --- |
| Subscribers per channel | Each message is sent that many times | Split broad channels into narrower ones |
| Message size | Bandwidth per delivery | Send ids and small diffs, not whole documents |
| Message rate | Deliveries per second | Throttle typing, cursors and progress updates |
| Resource change channels | One delivery per change per permitted subscriber, with a read check each | Turn on realtime only for resources that need it |

The **Delivered** count in **Services → Realtime** shows which channels carry the most traffic.
Projects also have plan limits on realtime messages and channels; refusals for those say which limit was reached.


## Debugging realtime

Realtime problems are easier to diagnose with the connection's own story in front of you.

```typescript
const pawabase = createClient({
  url,
  apiKey,
  environment: "development",
  realtime: { onProtocolError: (detail) => console.debug("[realtime] notice", detail) },
});

pawabase.realtime.onStatusChange((status) => console.debug("[realtime] status", status));

room.on("error", (error) => console.warn("[realtime] refused", error.code, error.message));
room.on("closed", ({ reason }) => console.debug("[realtime] closed", reason));
```

The browser's developer tools show WebSocket frames: open the network panel, select the `socket` request, and read the messages in both directions.
Each refused request appears as an `ack` frame with `ok: false`, an `error` and a `reason`.

On the server side, **Services → Realtime** lists open connections with their user and channels, which answers "is this person actually connected, and to what".


## Realtime, events and webhooks

Three features move information when something happens, and they are easy to mix up.

| Feature | Who receives | Delivery | Use for |
| --- | --- | --- | --- |
| Realtime | Connected clients | Immediate, at most once | Screens that update live |
| Events and flows | Your server-side logic | Reliable, with retries and run history | Work that must happen |
| Outbound webhooks | Other systems over HTTP | Reliable, with retries and delivery history | Telling partners |

A single record change can feed all three: realtime updates screens, a flow sends the email, and a webhook tells the warehouse.
Choose by who must know and how sure you need to be that they did.


## Security checklist for realtime

| Check | Why |
| --- | --- |
| Every channel kind has a rule; the default policy is not relied on | A missing rule falls back to the environment default, which may be broader than intended |
| Specific rules come before general ones | The first match wins |
| Per-person and per-organization channels use templates or segment checks | Guessable names must not be joinable by others |
| Publishing is restricted where only servers should speak | Notifications and announcements must not be forgeable |
| Presence data contains only what every member may see | Presence is broadcast to the channel |
| Resources with realtime have read policies you have reviewed | Change delivery follows the read policy |
| Secret keys never reach browsers | They bypass every channel rule |
