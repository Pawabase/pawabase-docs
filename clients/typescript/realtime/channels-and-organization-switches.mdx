Organization channels, such as `org:acme:activity`, are authorized against the organization in the person's token.
After `auth.switchOrg`, the token names a different organization, and channels of the previous one should be left.

```typescript
let current: import("@pawabase/client").RealtimeChannel | null = null;

pawabase.auth.onAuthStateChange(async (_event, session) => {
  const org = session?.org ?? null;
  const wanted = org ? `org:${org}:activity` : null;
  if (current?.name === wanted) return;
  await current?.unsubscribe();
  current = wanted ? pawabase.realtime.channel(wanted, { replay: 50 }) : null;
  await current?.subscribe();
});
```

The new token reaches the open connection automatically, and the server re-checks existing subscriptions against it.
Leaving the old channel yourself makes the change immediate and keeps the screen from showing another organization's activity.


## Designing message payloads

A message's `event` and `payload` are a small protocol between your senders and receivers.
Designing them like an API keeps old and new clients working together.

| Principle | Example |
| --- | --- |
| Name events by what happened | `order.shipped`, `member.joined` |
| Send ids and the few fields the screen shows | `{ "order_id": "o1", "status": "shipped" }` |
| Add fields; do not rename or remove them | Old clients ignore new fields |
| Mark a breaking change with a new event name | `order.shipped.v2` alongside `order.shipped` |
| Keep secrets and personal data out | Everyone on the channel sees the payload |

Receivers should ignore events they do not recognize, so senders can add new ones without breaking anyone.


## Common mistakes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Treating realtime as the source of truth | Gaps after reconnects leave screens wrong | Load from records; use realtime to update |
| One broad channel for everything | Every client receives everything | One channel per thing people watch |
| Sending on every keystroke or pointer move | Rate limiting and wasted bandwidth | Throttle and use presence for high-frequency state |
| Unsubscribing a shared channel from one component | Other components stop receiving | Subscribe in one place, listen in many |
| Rules ordered general before specific | Restricted channels become open | Specific patterns first |
| Ignoring `channel_closed` | Screens silently stop updating | Handle it through `onProtocolError` |
| Secret keys in browser realtime clients | Every rule is bypassed | Publishable keys in browsers |


## Realtime in end-to-end tests

End-to-end tests that drive a browser can check live behavior with two browser contexts signed in as different people.
One acts, the other watches, and the test waits for the watcher's screen to change.

| Step in the test | What it proves |
| --- | --- |
| Watcher opens the screen and waits for the live indicator | The connection opens and the channel is joined |
| Actor changes a record through the interface | The change is published |
| Watcher's screen shows the change within a few seconds | Delivery and the read policy work for that person |
| A third person who may not read the record sees nothing | The read policy filters delivery |

Wait for the change with a timeout of a few seconds rather than a fixed sleep.
Delivery is usually immediate, but test machines are slow in ways production is not.

Give each test run its own channel or record ids, such as a suffix with the run's timestamp.
Parallel runs then cannot see each other's messages, and a failure in one run does not leave the next run with stale presence or history.

Run these tests against a development or preview environment with realtime turned on for the resources involved, and with the same channel rules as production.
A rule that differs between environments is the most common reason a live screen works in testing and not after release.
Promoting rules along with the rest of the definitions keeps the environments in step.


## Before shipping a live screen

| Check | Why |
| --- | --- |
| The screen loads its data from records first | Realtime only carries changes |
| It reloads or catches up on `subscribed` | Reconnects leave gaps |
| It shows `reconnecting` and `closed` states | People should know when the screen is not live |
| It unsubscribes when the screen closes | Channels count against limits and keep receiving |
| High-frequency updates are throttled | Rate limits and bandwidth |
| The channel's rule has been tested as a person who should be refused | Access mistakes are silent otherwise |
| `onProtocolError` is wired to logging | Server notices such as `channel_closed` are visible |


## Words used on this page

| Term | Meaning |
| --- | --- |
| Connection | One WebSocket between a client and the realtime service |
| Channel | A named topic; exists while used |
| Rule | A pattern with subscribe and publish policies, presence and history settings |
| Presence | The set of members on a channel, each with a small piece of shared data |
| History | The recent messages a channel keeps |
| Replay | The client fetching recent history after a reconnect to fill gaps |
| Durable | A rule kind whose messages are stored in the database for a retention period |
| Resource channel | `resource:<name>`, where the platform publishes a resource's changes |

## Troubleshooting

| Symptom | Cause | What to do |
| --- | --- | --- |
| `ConfigError: No WebSocket implementation found` | Node 20 without a WebSocket | Pass `realtime.webSocket` |
| Status goes to `closed` immediately | Close code `4001`: the key was refused | Check the key and the gateway URL |
| `RealtimeError` `forbidden` on subscribe | A rule refused | Read the message; check the channel's rule in Studio |
| `this channel belongs to someone else` | A templated rule and another person's channel name | Use the caller's own id or organization in the name |
| Messages stop arriving after a while, with no error | The server closed the channel after a rule change or token expiry | Handle `channel_closed` in `onProtocolError` |
| Messages are missing after a reconnect | They were sent while disconnected | Use `replay`, or reload data on `subscribed` |
| Every send is refused | Client publishing is off for the environment | Publish from a server or flow instead |
| `payload_too_large` | Over 64 KiB, or presence over 2 KiB | Send ids and fetch details, or trim presence data |
| Frequent reconnects with `4429` | Too many connections for this person | Close unused tabs or share one connection per tab |
| Resource changes never arrive | Realtime is off for the resource, or the changes are made in the SQL console | Turn on realtime; make changes through the API |
| The server's channels refuse a server-side client | The client is stateless and connects without a token | Publish over HTTP with a secret key, or adopt a session |


## Questions developers ask

<AccordionGroup>
  <Accordion title="How many channels should one screen use?">
    As few as the screen needs, usually one or two.
    A connection may join up to 100, and each joined channel costs a little on both sides.
  </Accordion>
  <Accordion title="Can a signed-out visitor use realtime?">
    Yes, on channels whose rules admit anonymous callers, such as a rule with `public` subscribe.
    The connection carries only the publishable key.
  </Accordion>
  <Accordion title="Do I need realtime to keep a list up to date?">
    No; polling a query works and is simpler.
    Realtime is worth it when updates must appear within a second, or when many people watch the same data.
  </Accordion>
  <Accordion title="Are messages encrypted?">
    The connection to the gateway is encrypted with TLS when the gateway URL is `https:`.
    Messages are visible to the server and to everyone the channel's rule admits.
  </Accordion>
  <Accordion title="Can I send binary data?">
    No.
    Frames are JSON text.
    Upload files to storage and send their keys.
  </Accordion>
  <Accordion title="Does `send` guarantee delivery?">
    It guarantees the server accepted the message.
    Subscribers connected at that moment receive it; others can find it in history while the channel keeps it.
  </Accordion>
  <Accordion title="Can a server subscribe to channels?">
    Yes, with a client that has a WebSocket and a session or key.
    Most servers do not need to: they publish over HTTP, and react to data changes through events and flows, which are reliable where a socket is not.
  </Accordion>
  <Accordion title="What happens to my channels when I call `auth.signOut()`?">
    The connection continues as anonymous.
    Channels that require a signed-in person are closed by the server; public channels keep working.
  </Accordion>
  <Accordion title="Can I subscribe to changes of one record only?">
    Subscribe to `resource:<name>` and filter by id in your handler.
    Delivery is already limited to records the person may read.
  </Accordion>
</AccordionGroup>
