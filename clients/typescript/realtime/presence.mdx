Presence lets members of a channel share a small piece of data about themselves, such as a name or a cursor position, and see who else is there.

<CodeGroup>
```typescript TypeScript
const room = pawabase.realtime.channel<unknown, { name: string; typing: boolean }>("chat:lobby", {
  presence: { name: "Ada", typing: false },
});

room.on("presence", ({ joins, leaves, members }) => {
  renderMembers(members.map((member) => member.meta.name));
  for (const left of leaves) showLeft(left.meta.name);
});

await room.subscribe();
await room.track({ name: "Ada", typing: true });
```

```python Python
room = apb.realtime.channel("chat:lobby", presence={"name": "Ada", "typing": False})

def on_presence(joins, leaves):
    render_members([member["meta"]["name"] for member in room.presence_state()])
    for member in leaves:
        show_left(member["meta"]["name"])

room.on_presence(on_presence)
await room.subscribe()
await room.track({"name": "Ada", "typing": True})
```

```text WebSocket
{"type": "presence", "channel": "chat:lobby", "meta": {"name": "Ada", "typing": true}, "ref": "4"}
# ← {"type": "presence_diff", "channel": "chat:lobby", "joins": [...], "leaves": []}
```
</CodeGroup>

| Method or event | Meaning |
| --- | --- |
| `presence` option | Your initial presence data, sent when you subscribe |
| `track(meta)` | Change your presence data; subscribe first |
| `presenceState()` | Everyone present, as last reported by the server |
| `presence` event | `{ joins, leaves, members }` after every change |

A presence member has these fields:

| Field | Meaning |
| --- | --- |
| `presence_ref` | Unique per connection and channel; one person with two tabs has two |
| `user_id` | The person's id, or `null` for an anonymous member |
| `meta` | The presence data they shared |
| `online_at` | When they joined |

Presence must be enabled by the channel's rule, which it is by default.
Presence data is limited to 2 KiB per member.
Count people by `user_id` rather than by members when the same person may have several tabs open.

Presence is not durable.
When a connection drops, its members leave after a short delay, and they join again when the connection returns.


## History

Each channel keeps its most recent messages, as many as its rule's `history` allows.
A client can read them to show what happened before it joined.

<CodeGroup>
```typescript TypeScript
const recent = await room.history(20);
for (const message of recent) appendToChat(message.from, message.payload.text, message.sent_at);
```

```python Python
recent = await room.history(20)            # over the socket
recent = pb.realtime.history("chat:lobby", 20)   # over HTTP, on either client
```

```bash cURL
curl "$PAWABASE_URL/realtime/v1/channels/chat:lobby/history?limit=20" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN"
```
</CodeGroup>

`room.history(limit)` reads over the socket; `realtime.history(channel, limit)` reads over HTTP without joining.
Both return messages oldest first, with a `seq` number on each.

The number returned is the smaller of what you ask for and what the rule keeps.
History is kept in memory unless the rule's kind is `durable`, in which case messages survive a restart for the rule's retention period, seven days by default.

History for `resource:<name>` channels is filtered like live delivery: a change to a record you cannot read is not returned.

### Catching up after a reconnect

A channel created with `replay: n` fetches up to `n` recent messages after every reconnect and delivers those it has not delivered before.
The client remembers the ids of the last 1000 messages per channel, so a message is never delivered twice.

```typescript
const feed = pawabase.realtime.channel("org:acme:activity", { replay: 100 });
```

Replay fills short gaps.
After a long disconnection, more messages may have been sent than the channel keeps, and some are lost.
Screens that must be exact, such as a list of orders, should reload their data after a reconnect instead of relying on replay.


## Live resource changes

A resource with realtime turned on publishes each create, update and delete on the channel `resource:<name>`.
Each subscriber receives a change only if the resource's read policy allows them to read that record, checked against the record and the subscriber's identity.

<CodeGroup>
```typescript TypeScript
const orders = pawabase.realtime.channel("resource:orders");

orders.on("message", (message) => {
  const change = message.payload as {
    resource: string;
    change: "created" | "updated" | "deleted";
    record: Record<string, unknown>;
    changed?: string[];
    source?: "database";
  };
  if (change.change === "deleted") removeRow(change.record.id);
  else upsertRow(change.record);
});

await orders.subscribe();
```

```python Python
orders = apb.realtime.channel("resource:orders")

def on_change(message):
    change = message["payload"]
    if change["change"] == "deleted":
        remove_row(change["record"]["id"])
    else:
        upsert_row(change["record"])

orders.on(None, on_change)
await orders.subscribe()
```

```text WebSocket
# A live channel is a WebSocket, for example with websocat:
websocat "wss://api.example.com/realtime/v1/socket?apikey=$PAWABASE_KEY&token=$TOKEN&environment=production"
{"type": "subscribe", "channel": "resource:orders", "ref": "1"}
# ← {"type": "message", "channel": "resource:orders", "event": "updated", "payload": {"resource": "orders", "change": "updated", "record": {…}, "changed": ["status"]}}
```
</CodeGroup>

| Payload field | Meaning |
| --- | --- |
| `resource` | The resource's name |
| `change` | `created`, `updated` or `deleted`; also the message's `event` |
| `record` | The record as an API read would show it: write-only fields and undeclared columns removed |
| `changed` | For updates, the fields whose values changed |
| `source` | `database` for a change captured from the database rather than made through the API |

Changes made through the API, flows and Studio's records view are published.
Statements run in the SQL console are not.

Clients cannot publish to `resource:` channels; only the platform does.


## When the connection drops

Networks drop connections: a phone changes towers, a laptop sleeps, a proxy times out an idle socket, a server restarts.
The client is built to recover without your code doing anything, and to tell you when it cannot.

### What the client does

```text
open ──drop──▶ reconnecting ──backoff──▶ connecting ──welcome──▶ open
                    ▲                                              │
                    └──────────── another drop ◀───────────────────┘
after "open": every channel that was joined is joined again,
              presence is sent again, and channels with `replay` catch up
```

| Step | Behavior |
| --- | --- |
| Detecting a drop | The socket closes, or two heartbeat intervals pass with no traffic at all, which recycles a link that died silently |
| Waiting | A random delay between zero and a ceiling that doubles each attempt, from 500 ms up to 15 s |
| Reconnecting | A new socket with the current access token |
| Rejoining | Every channel you subscribed to and did not unsubscribe is joined again, with its presence data |
| Catching up | Channels with `replay` fetch recent history and deliver what they missed, without duplicates |

Messages sent while the connection was down are not delivered live.
Only `replay`, or reloading data, recovers them.

### Close codes

The server ends a connection with a close code that says why, and the client reacts to each differently.

| Code | Meaning | Client reaction |
| --- | --- | --- |
| `4001` | No API key, or the key was refused | Stops; status `closed`. Fix the key. |
| `4003` | The access token was refused | Refreshes the session once, then reconnects; if refresh fails, stops |
| `4008` | The connection kept sending faster than allowed | Reconnects with backoff |
| `4429` | Too many connections for the environment, or for this person | Reconnects with backoff |
| `1012` | The server is restarting | Reconnects with backoff |
| Anything else | The network or a proxy closed the socket | Reconnects with backoff |

`4429` most often means a person has too many tabs or devices connected; the default ceiling is 20 connections per person.
A reconnect succeeds as soon as another of their connections closes.

### Tuning reconnection

```typescript
const pawabase = createClient({
  url,
  apiKey,
  environment: "production",
  realtime: {
    reconnect: { baseDelayMs: 1000, maxDelayMs: 30_000, maxAttempts: 50 },
    heartbeatSeconds: 20,
  },
});
```

| Setting | Default | Effect |
| --- | --- | --- |
| `reconnect.baseDelayMs` | `500` | The first backoff ceiling |
| `reconnect.maxDelayMs` | `15000` | The largest backoff |
| `reconnect.maxAttempts` | unlimited | Give up and set status `closed` after this many attempts |
| `reconnect: false` | | Never reconnect |
| `heartbeatSeconds` | `25` | Ping interval; a connection silent for two intervals is recycled |
| `connectTimeoutMs` | `10000` | How long to wait for a new connection to be welcomed |
| `ackTimeoutMs` | `10000` | How long to wait for the server to acknowledge a subscribe, publish or presence change |

After `maxAttempts`, the client stops.
Call `connect()` again, for example when the browser reports it is back online, to start over.

```typescript
window.addEventListener("online", () => {
  if (pawabase.realtime.status === "closed") void pawabase.realtime.connect();
});
```

### Waiting for the connection

`realtime.whenOpen(ms)` resolves when the socket is really open, connecting first if the client is idle.
`send`, `track` and `history` use it internally, so a call made during a short reconnect waits instead of failing.
If the connection does not open in time, they reject with `RealtimeError` code `not_connected`.
