`admin(client)` manages the people who sign in to your application: creating and disabling accounts, assigning roles and permissions, running organizations, ending sessions, and reading sign-in activity.
It is what Studio's **Access → Users & auth** page does, as typed calls for your servers, support tools and scripts.

This page explains who these users are and how the module reaches them, then covers each service, what each action changes about a person's access, and when the change takes effect.

## The mental model

Two different groups of people touch a Pawabase project.

| Group | Who they are | Managed with |
| --- | --- | --- |
| Your project's team | Developers and operators who use Studio | The installation's organization settings |
| Your application's users | The people who sign in to what you built | `admin()`, and **Access → Users & auth** |

`admin()` is about the second group only.
Every call is scoped to one environment: a user of `development` is a different person from a user of `production` with the same email, with a separate password, roles and sessions.

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";
import { admin } from "@pawabase/client/admin";

const service = createClient({
  url: process.env.PAWABASE_URL!,
  apiKey: process.env.PAWABASE_SECRET_KEY!,
  environment: "production",
});

const a = admin(service);
const created = await a.users.create({ email: "ada@example.com", roles: ["editor"] });
await a.users.update(created.id, { disabled: true });
```

```python Python
import os

from pawabase import Pawabase

service = Pawabase(os.environ["PAWABASE_URL"], os.environ["PAWABASE_SECRET_KEY"], environment="production")

a = service.admin
created = a.users.create(email="ada@example.com", roles=["editor"])
a.users.update(created["id"], disabled=True)
```

```bash cURL
curl -X POST "$PAWABASE_URL/platform/v1/envs/production/auth/users" -H "apikey: $PAWABASE_SECRET_KEY" -H "content-type: application/json" \
  -d '{"email": "ada@example.com", "name": "", "email_verified": true, "roles": ["editor"], "user_metadata": {}, "app_metadata": {}}'
curl -X PATCH "$PAWABASE_URL/platform/v1/envs/production/auth/users/$USER_ID" -H "apikey: $PAWABASE_SECRET_KEY" -H "content-type: application/json" -d '{"disabled": true}'
```
</CodeGroup>

| Rule | Consequence |
| --- | --- |
| It needs a secret key | `admin()` throws `ConfigError` for a publishable key |
| It is bound to one environment | The client's `environment`, the name you pass, or `development` |
| It returns JSON documents | Lists are `{ data: [...] }` or the service's own shape |
| It acts with full authority | Policies do not apply; your code decides who may use it |

The last row matters most.
An endpoint in your application that calls `admin()` must check, in your own code, that the person asking is allowed to do what they ask.
The module itself will do whatever the secret key permits.

## A first script

Start with a script that only reads, to confirm the key, the environment and the module before any change.

```typescript
import { createClient } from "@pawabase/client";
import { admin } from "@pawabase/client/admin";

const environment = process.env.PAWABASE_ENV ?? "staging";
const service = createClient({ url: process.env.PAWABASE_URL!, apiKey: process.env.PAWABASE_SECRET_KEY!, environment });
const a = admin(service, environment);

const [stats, roles, firstPage] = await Promise.all([a.insight.stats(), a.roles.list(), a.users.search({ limit: 5 })]);
console.log(`environment: ${environment}`);
console.log("stats:", stats);
console.log("roles:", roles);
console.log("first users:", firstPage);
service.dispose();
```

| If it fails with | Check |
| --- | --- |
| `ConfigError` | The key is a secret key, starting with `pb_sk_` |
| `AuthenticationError` | The key is valid for this installation |
| `NotFoundError` or `PermissionError` | The environment name, and the key's restrictions |

When the output matches what **Access → Users & auth** shows for the environment, the setup is right.

## Which identity staff tools should use

| Tool | Identity | Why |
| --- | --- | --- |
| Screens that show a customer's data to support | The staff member, through policies that grant the `support` role read access | Every read is attributable and limited |
| Actions such as unlock and MFA reset | Your server's secret key, after checking the staff member's role | Those actions have no self-service form |
| Reports and reconciliations | A scheduled job with its own secret key | No person is involved |

## Choosing the environment

`admin(client, environment?)` uses the name you pass, then the client's `environment`, then `development`.
Pass it explicitly in every script; a support tool that disables a user in the wrong environment fails silently from the user's point of view.

```typescript
const production = admin(service, "production");
const staging = production.withEnvironment("staging");
```

## The services

| Service | Manages |
| --- | --- |
| `users` | Accounts: search, create, update, disable, delete, history, MFA reset, permissions, sessions, devices, personal keys |
| `roles` | Roles and their permissions |
| `orgs` | Organizations and their members, invitations |
| `invitations` | Invitations across organizations |
| `sessions` | Active sessions across users |
| `apiKeys` | Personal API keys users made |
| `devices` | Devices people signed in from |
| `insight` | Auth events, statistics, identity backup and restore, hosted page previews |

## Users

### Finding people

`users.search(options)` lists accounts, filtered and paged.

<CodeGroup>
```typescript TypeScript
const page = await a.users.search({ search: "ada", status: "locked", limit: 50, offset: 0 });
```

```python Python
page = a.users.search(search="ada", status="locked", limit=50, offset=0)
```

```bash cURL
curl -G "$PAWABASE_URL/platform/v1/envs/production/auth/users" -H "apikey: $PAWABASE_SECRET_KEY" --data-urlencode "search=ada" --data-urlencode "status=locked" --data-urlencode "limit=50" --data-urlencode "offset=0"
```
</CodeGroup>

| Option | Meaning |
| --- | --- |
| `search` | Matches email, username and name |
| `status` | `disabled`, `unverified`, `locked`, `mfa` or `no_mfa` |
| `limit`, `offset` | Paging; 50 per page by default |

`users.getUser(id)` reads one account with the fields only administrators see.

| Field | Meaning |
| --- | --- |
| `id`, `email`, `username`, `name`, `avatar_url` | Identity and profile |
| `email_verified`, `email_verified_at` | Whether and when the address was confirmed |
| `user_metadata` | Data the person can edit; never trust it for access |
| `app_metadata` | Data only administrators and servers can edit |
| `roles` | Role names |
| `permissions` | Effective permissions, from roles and direct grants |
| `mfa_enabled` | Whether a confirmed second factor exists |
| `identities` | Linked sign-in providers |
| `disabled`, `disabled_at` | Whether and when the account was disabled |
| `locked_until` | When a lockout after failed attempts ends, or `null` |
| `has_password` | Whether password sign-in is possible |
| `last_sign_in_at`, `last_sign_in_ip`, `created_at` | Activity |

### Creating accounts

`users.create(user)` creates an account without the sign-up restrictions.
Allow-lists and the sign-up switch do not apply; the password policy does.

<CodeGroup>
```typescript TypeScript
const user = await a.users.create({
  email: "grace@example.com",
  name: "Grace Hopper",
  roles: ["staff"],
  appMetadata: { plan: "enterprise", account_id: "acc_381" },
});
```

```python Python
user = a.users.create(
    email="grace@example.com",
    name="Grace Hopper",
    roles=["staff"],
    app_metadata={"plan": "enterprise", "account_id": "acc_381"},
)
```

```bash cURL
curl -X POST "$PAWABASE_URL/platform/v1/envs/production/auth/users" -H "apikey: $PAWABASE_SECRET_KEY" -H "content-type: application/json" -d '{"email": "grace@example.com", "name": "Grace Hopper", "roles": ["staff"],
  "email_verified": true, "user_metadata": {}, "app_metadata": {"plan": "enterprise", "account_id": "acc_381"}}'
```
</CodeGroup>

| Field | Default | Meaning |
| --- | --- | --- |
| `email` | required | Unique within the environment; a duplicate is `409` |
| `password` | none | Without one, the account has no usable password; the person sets one through a recovery link |
| `username` | Generated from the email | Unique within the environment |
| `name` | `""` | Display name |
| `emailVerified` | `true` | Accounts you create are considered verified |
| `userMetadata` | `{}` | Profile data the person can edit later |
| `appMetadata` | `{}` | Administrator data, visible to policies as `$auth.claims.app.*` |
| `roles` | `[]` | Added to any default roles the environment grants |

Creating accounts without a password is the safer default for invitations and migrations.
Follow it with a password-reset email from your application, so the person chooses their own password and proves they own the address.

<CodeGroup>
```typescript TypeScript
await service.auth.requestPasswordReset({ email: user.email, redirectTo: "https://app.example.com/welcome" });
```

```python Python
service.auth.request_password_reset(email=user["email"], redirect_to="https://app.example.com/welcome")
```

```bash cURL
curl -X POST "$PAWABASE_URL/auth/v1/recover" -H "apikey: $PAWABASE_KEY" -H "content-type: application/json" \
  -d '{"email": "grace@example.com", "redirect_to": "https://app.example.com/welcome"}'
```
</CodeGroup>

### Changing accounts

`users.update(id, changes)` changes what you pass and leaves the rest.

| Change | Effect |
| --- | --- |
| `name` | The display name |
| `emailVerified` | `true` stamps verification now; `false` clears it, which blocks password sign-in when the environment requires verification |
| `disabled` | `true` blocks sign-in and ends the person's sessions; `false` re-enables |
| `password` | Sets a new password; the policy applies |
| `userMetadata`, `appMetadata` | Replace the stored metadata |
| `roles` | Replaces the person's roles |
| `unlock` | `true` clears a lockout after failed attempts |

<CodeGroup>
```typescript TypeScript
await a.users.update(userId, { roles: ["editor", "billing"] });
await a.users.update(userId, { unlock: true });
await a.users.update(userId, { appMetadata: { plan: "pro" } });
```

```python Python
a.users.update(user_id, roles=["editor", "billing"])
a.users.update(user_id, unlock=True)
a.users.update(user_id, app_metadata={"plan": "pro"})
```

```bash cURL
curl -X PATCH "$PAWABASE_URL/platform/v1/envs/production/auth/users/$USER_ID" -H "apikey: $PAWABASE_SECRET_KEY" -H "content-type: application/json" -d '{"roles": ["editor", "billing"]}'
curl -X PATCH "$PAWABASE_URL/platform/v1/envs/production/auth/users/$USER_ID" -H "apikey: $PAWABASE_SECRET_KEY" -H "content-type: application/json" -d '{"unlock": true}'
```
</CodeGroup>

`roles` replaces the whole list, and the metadata fields replace the stored object.
Read the user first when you want to add one role or one key, and send the combined value.

<CodeGroup>
```typescript TypeScript
const current = await a.users.getUser(userId);
await a.users.update(userId, { roles: [...new Set([...(current.roles ?? []), "billing"])] });
```

```python Python
current = a.users.get_user(user_id)
a.users.update(user_id, roles=sorted({*(current.get("roles") or []), "billing"}))
```
</CodeGroup>

### When changes take effect

Access tokens are verified by signature, without asking the auth service each time.
A change to a person's account therefore reaches their requests in two steps.

| Change | New sign-ins and refreshes | Requests with a token already issued |
| --- | --- | --- |
| Disable | Blocked at once | Still accepted until the token expires, 15 minutes by default |
| Roles or permissions | Next token carries them | Old token keeps the old roles until it expires or is refreshed |
| `appMetadata` | Next token carries it | Old token keeps the old values |
| Revoke sessions | Refreshes fail at once | Still accepted until the token expires |
| Delete | Blocked at once | Still accepted until the token expires |

For most changes, a quarter of an hour is acceptable.
When it is not, for example when removing someone who is acting maliciously, combine disabling with steps that bite immediately: revoke their personal API keys, ban their address at the firewall if appropriate, and change anything they may have learned.

A person whose roles you granted can see the change at once if their application calls `auth.refreshSession()`, which issues a new token.

### Disabling compared with deleting

| | Disable | Delete |
| --- | --- | --- |
| Reversible | Yes, with `disabled: false` | No |
| Account and history | Kept | History kept and attributable; email address released for re-use |
| Second factors and linked identities | Kept | Removed |
| Sessions | Ended | Ended |
| Records the person owns | Unchanged | Unchanged; their owner field still holds the old id |

Disable when access should stop and might return: an employee on leave, an unpaid account, an investigation.
Delete when the person asked to be forgotten or the account should not exist, and handle the records they own as part of the same process.

<CodeGroup>
```typescript TypeScript
await a.users.deleteUser(userId);
```

```python Python
a.users.delete_user(user_id)
```

```bash cURL
curl -X DELETE "$PAWABASE_URL/platform/v1/envs/production/auth/users/$USER_ID" -H "apikey: $PAWABASE_SECRET_KEY"
```
</CodeGroup>

Deleting a user does not delete their records in your resources.
If your privacy obligations require removing personal data, delete or anonymize the person's records in the same job, before or after deleting the account.

### History

`users.history(id)` returns the person's recent sign-ins and security events, with outcomes and reasons.

<CodeGroup>
```typescript TypeScript
const history = await a.users.history(userId);
console.log(JSON.stringify(history, null, 2));
```

```python Python
history = a.users.history(user_id)
```

```bash cURL
curl "$PAWABASE_URL/platform/v1/envs/production/auth/users/$USER_ID/history" -H "apikey: $PAWABASE_SECRET_KEY"
```
</CodeGroup>

| Event | Reason | Meaning |
| --- | --- | --- |
| `sign_in` | wrong password, unknown email | A failed attempt |
| `sign_in` | `locked` | The lockout threshold was reached; the password may have been right |
| `sign_in` | `disabled` | An administrator disabled the account |

History is the first thing to read when someone says they cannot sign in.
It usually answers the question in one line.

### Second factors

`users.resetMfa(id)` removes the person's second factors, so they can sign in with their password alone and enroll again.

<CodeGroup>
```typescript TypeScript
await a.users.resetMfa(userId);
```

```python Python
a.users.reset_mfa(user_id)
```

```bash cURL
curl -X POST "$PAWABASE_URL/platform/v1/envs/production/auth/users/$USER_ID/mfa/reset" -H "apikey: $PAWABASE_SECRET_KEY"
```
</CodeGroup>

Use it when someone lost their authenticator and their recovery codes.
Verify their identity through another channel first: resetting MFA for whoever asks defeats the point of MFA.

A reset does not clear a lockout.
If repeated wrong codes locked the account, also send `unlock: true`.

### Permissions granted directly

Permissions usually come from roles.
`users.grant(id, permissions)` and `users.revoke(id, permissions)` give or remove permissions for one person, beyond their roles.

<CodeGroup>
```typescript TypeScript
await a.users.grant(userId, ["reports:export"]);
await a.users.revoke(userId, ["reports:export"]);
```

```python Python
a.users.grant(user_id, ["reports:export"])
a.users.revoke(user_id, ["reports:export"])
```

```bash cURL
curl -X POST "$PAWABASE_URL/platform/v1/envs/production/auth/users/$USER_ID/permissions" -H "apikey: $PAWABASE_SECRET_KEY" -H "content-type: application/json" -d '{"permissions": ["reports:export"]}'
curl -X DELETE "$PAWABASE_URL/platform/v1/envs/production/auth/users/$USER_ID/permissions" -H "apikey: $PAWABASE_SECRET_KEY" -H "content-type: application/json" -d '{"permissions": ["reports:export"]}'
```
</CodeGroup>

Permissions are `resource:action` strings with `*` wildcards, such as `posts:write` or `billing:*`.
Policies test them with the `permission` shorthand, and they appear in `$auth.permissions`.

Direct grants are convenient for exceptions and hard to audit at scale.
Prefer a role when more than a few people need the same permission.

### Sessions, devices and personal keys of one person

| Method | Purpose |
| --- | --- |
| `revokeSessions(id)` | Sign the person out everywhere |
| `revokeSession(id, sessionId)` | End one session |
| `devices(id)` | Devices the person signed in from |
| `forgetDevice(id, deviceId)` | Forget one device |
| `apiKeys(id)` | The personal API keys the person made, never their secrets |

`revokeSessions` is the right response to "I think someone else is using my account", together with a password reset.
Their other devices will need to sign in again when their current tokens expire.

## Roles

`roles` manages the environment's roles and the permissions each grants.

<CodeGroup>
```typescript TypeScript
const { data } = await a.roles.list();
await a.roles.define("editor", ["posts:read", "posts:write", "media:*"], { description: "Writes and publishes posts" });
await a.roles.remove("intern");
```

```python Python
roles = a.roles.list()
a.roles.put("editor", ["posts:read", "posts:write", "media:*"], description="Writes and publishes posts")
a.roles.remove("intern")
```

```bash cURL
curl -X PUT "$PAWABASE_URL/platform/v1/envs/production/auth/roles" -H "apikey: $PAWABASE_SECRET_KEY" -H "content-type: application/json" -d '{"name": "editor", "description": "Writes and publishes posts", "permissions": ["posts:read", "posts:write", "media:*"]}'
```
</CodeGroup>

| Method | Purpose |
| --- | --- |
| `list()` | Roles with their permissions |
| `define(name, permissions, { description })` | Create or replace a role |
| `remove(name)` | Delete a role |

Role names are lowercase, such as `editor` or `org:billing`.
`define` replaces a role's permissions entirely; read the role first to add to it.

Roles reach requests through tokens: a person's roles are written into each access token they receive.
Changing a role's permissions affects everyone with the role, starting with their next token.

## Organizations

`orgs` manages organizations, the groups your users belong to, as an administrator.
A member's role in an organization is separate from their environment roles: it is `owner`, `admin` or `member`, and policies see it as `$auth.org_role`.

| Method | Purpose |
| --- | --- |
| `list()`, `getOrg(slug)` | Organizations |
| `create(slug, name, { ownerEmail, metadata })` | A new organization, optionally with an owner |
| `update(slug, { name, metadata })` | Change one |
| `remove(slug)` | Delete one |
| `addMember(slug, { email, role })` | Add an existing user directly |
| `setMemberRole(slug, userId, role)` | Change a member's role |
| `removeMember(slug, userId)` | Remove a member |
| `invite(slug, { email, role, redirectTo })` | Email an invitation |

<CodeGroup>
```typescript TypeScript
await a.orgs.create("acme", "Acme Ltd", { ownerEmail: "ada@example.com", metadata: { plan: "business" } });
await a.orgs.addMember("acme", { email: "grace@example.com", role: "admin" });
```

```python Python
a.orgs.create("acme", "Acme Ltd", owner_email="ada@example.com", metadata={"plan": "business"})
a.orgs.add_member("acme", email="grace@example.com", role="admin")
```

```bash cURL
curl -X POST "$PAWABASE_URL/platform/v1/envs/production/auth/orgs" -H "apikey: $PAWABASE_SECRET_KEY" -H "content-type: application/json" -d '{"slug": "acme", "name": "Acme Ltd", "owner_email": "ada@example.com", "metadata": {"plan": "business"}}'
curl -X POST "$PAWABASE_URL/platform/v1/envs/production/auth/orgs/acme/members" -H "apikey: $PAWABASE_SECRET_KEY" -H "content-type: application/json" -d '{"email": "grace@example.com", "role": "admin"}'
```
</CodeGroup>

`addMember` adds an existing user without asking them, which suits migrations and accounts you manage.
`invite` emails the person and waits for them to accept, which suits people joining by choice.
`redirectTo` must be one of the environment's allowed redirect URLs.

## Invitations

`invitations` manages invitations across all organizations.

| Method | Purpose |
| --- | --- |
| `list()` | Pending and past invitations |
| `resend(id, { redirectTo })` | Send the email again |
| `revoke(id)` | Cancel an invitation |

Resend when someone says the email never arrived, after checking the mail log; revoke when an invitation went to the wrong address.

## Sessions, keys and devices across users

| Service | Method | Purpose |
| --- | --- | --- |
| `sessions` | `list({ limit })` | Active sessions across users |
| `sessions` | `revoke(family)` | End one session and all its refresh tokens |
| `apiKeys` | `list({ limit })` | Personal keys users made |
| `apiKeys` | `revoke(id)` | End one |
| `devices` | `list({ limit })` | Recent devices across users |

A session is identified by its token family: every refresh token issued for one sign-in belongs to the same family.
Revoking the family ends the session, however many times it was refreshed.

## Insight

`insight` reads authentication activity and statistics, and backs up and restores identities.

| Method | Purpose |
| --- | --- |
| `events({ kind, failed, limit })` | Authentication events: sign-ins, sign-ups, resets, MFA; `failed: true` for failures only |
| `stats()` | Counts of users, sign-ins, MFA use and failures |
| `backup()` | Every identity as a document: users, organizations, roles, factors |
| `restore(identities, { replace, dryRun })` | Apply a backup's identities; `dryRun` reports what would change |
| `hostedSource(page, { branding, form })` | The HTML a hosted sign-in page would serve with given branding |

<CodeGroup>
```typescript TypeScript
const failures = await a.insight.events({ kind: "sign_in", failed: true, limit: 200 });
const stats = await a.insight.stats();
```

```python Python
failures = a.insight.events(kind="sign_in", failed=True, limit=200)
stats = a.insight.stats()
```

```bash cURL
curl -G "$PAWABASE_URL/platform/v1/envs/production/auth/events" -H "apikey: $PAWABASE_SECRET_KEY" --data-urlencode "kind=sign_in" --data-urlencode "failed=true" --data-urlencode "limit=200"
```
</CodeGroup>

A sudden rise in failed sign-ins from many accounts is the signature of credential stuffing: attackers trying leaked passwords from other sites.
The lockout protects individual accounts; the firewall's rate limits on the token endpoint protect the environment.
`events` is how you notice it from a script.

An identity backup is a complete copy of who your users are and what they belong to.
Take one before risky migrations, and store it as carefully as a database dump: it contains everything about every account.

```typescript
const backup = await a.insight.backup();
const preview = await a.withEnvironment("staging").insight.restore(backup.identities ?? backup, { dryRun: true });
console.log(preview);
```

`hostedSource` previews how a hosted sign-in page looks with branding you are editing, which is useful when branding is managed from code.

## A support tool

Most teams eventually build an internal tool for support staff: find a person, see what is wrong, fix it.
The module provides every operation; your tool provides the checks and the record of who did what.

### The server side

Each operation is an endpoint that checks the caller is support staff, performs one action, and records it.

```typescript
import express from "express";
import { admin } from "@pawabase/client/admin";

const a = admin(service, "production");
const support = express.Router();

support.use(async (req, res, next) => {
  const token = req.headers.authorization?.replace(/^Bearer /, "") ?? null;
  if (!token) return res.status(401).end();
  try {
    const staff = await base.asUser(token).auth.getUser();
    if (!staff.roles.includes("support")) return res.status(403).end();
    res.locals.staff = staff;
    next();
  } catch {
    res.status(401).end();
  }
});

support.get("/users", async (req, res) => {
  res.json(await a.users.search({ search: String(req.query.q ?? ""), limit: 25 }));
});

support.get("/users/:id", async (req, res) => {
  const [user, history] = await Promise.all([a.users.getUser(req.params.id), a.users.history(req.params.id)]);
  res.json({ user, history });
});

support.post("/users/:id/unlock", async (req, res) => {
  await a.users.update(req.params.id, { unlock: true });
  await recordAction(res.locals.staff.id, "unlock", req.params.id, req.body?.reason);
  res.status(204).end();
});

support.post("/users/:id/reset-mfa", async (req, res) => {
  if (!req.body?.reason) return res.status(422).json({ error: "A reason is required." });
  await a.users.resetMfa(req.params.id);
  await a.users.update(req.params.id, { unlock: true });
  await recordAction(res.locals.staff.id, "reset_mfa", req.params.id, req.body.reason);
  res.status(204).end();
});

support.post("/users/:id/sign-out-everywhere", async (req, res) => {
  await a.users.revokeSessions(req.params.id);
  await recordAction(res.locals.staff.id, "revoke_sessions", req.params.id, req.body?.reason);
  res.status(204).end();
});

async function recordAction(staffId: string, action: string, userId: string, reason?: string) {
  await service.from("support_actions").create({ staff_id: staffId, action, user_id: userId, reason: reason ?? "" });
}

declare const base: import("@pawabase/client").PawabaseClient;
```

The staff check uses the staff member's own token with a publishable-key client, so being "support" is a role in the same environment, managed like any other.
The secret key never leaves the server, and every action leaves a record your team can review.

### Which actions to offer

| Situation | Action | Notes |
| --- | --- | --- |
| "I cannot sign in" | Read history | Usually answers it: wrong password, locked, disabled, unverified |
| Locked after too many attempts | `update(id, { unlock: true })` | Safe; it only clears the counter |
| Never received the confirmation email | `update(id, { emailVerified: true })` after checking identity, or resend from the app | Check the mail log first |
| Lost authenticator and recovery codes | `resetMfa(id)` and `unlock` | Verify identity through another channel first |
| "Someone else is in my account" | `revokeSessions(id)`, then a password reset | Also check their personal API keys |
| Wrong plan after a billing change | `update(id, { appMetadata })` | The person sees it at their next token |
| Leaving the company | Disable, revoke sessions and keys | See offboarding below |

Actions that weaken security, such as MFA resets, deserve a required reason and a second person's approval in larger teams.

## Importing users from another system

Moving to Pawabase from another identity system means creating accounts for existing people without knowing their passwords.
The pattern is: create each account without a password, keep the old system's id in `appMetadata`, and let people set a password through a reset email when they first arrive.

```typescript
import { ConflictError } from "@pawabase/client";

interface LegacyUser {
  legacy_id: string;
  email: string;
  name: string;
  roles: string[];
}

export async function importUsers(people: LegacyUser[], concurrency = 4) {
  const queue = [...people];
  const report = { created: 0, existing: 0, failed: [] as Array<{ email: string; error: string }> };

  async function worker() {
    for (let person = queue.shift(); person; person = queue.shift()) {
      try {
        await a.users.create({
          email: person.email,
          name: person.name,
          roles: person.roles,
          appMetadata: { legacy_id: person.legacy_id, imported_at: new Date().toISOString() },
        });
        report.created += 1;
      } catch (error) {
        if (error instanceof ConflictError) report.existing += 1;
        else report.failed.push({ email: person.email, error: String(error) });
      }
    }
  }

  await Promise.all(Array.from({ length: concurrency }, worker));
  return report;
}
```

A `409` means the email already exists in the environment, which makes the import safe to run again after a partial failure.
Keep concurrency modest; every create counts against the key's rate limit.

Records from the old system usually refer to people by the old id.
After the import, map old ids to new ones by reading `app_metadata.legacy_id`, and update owner fields on your records with a secret-key job.

Do not send a reset email to everyone at once.
Send them when people next visit, or in batches, so a wave of emails does not look like phishing and your mail provider does not throttle you.

## Offboarding

When someone must lose access, such as an employee leaving a customer's organization, several actions together close every door.

```typescript
export async function offboard(userId: string, orgSlug: string, transferTo: string) {
  await a.orgs.removeMember(orgSlug, userId);
  await a.users.revokeSessions(userId);
  const keys = await a.users.apiKeys(userId);
  for (const key of (keys.data ?? []) as Array<{ id: string }>) await a.apiKeys.revoke(key.id);

  for await (const doc of service.from("documents").eq("owner_id", userId).eq("org", orgSlug).select("id")) {
    await service.from("documents").update(doc.id, { owner_id: transferTo });
  }
}
```

| Step | Why |
| --- | --- |
| Remove from the organization | Policies based on membership stop admitting them at their next token |
| Revoke sessions | No refresh can extend their access |
| Revoke personal API keys | Keys are a separate door that sessions do not close |
| Transfer owned records | Their work stays with the organization |

Whether to also disable the account depends on whether the person uses your application elsewhere, for example in another organization.
Removing them from one organization should not lock them out of another.

The owner field cannot be changed through the data API as a person, which is why the transfer uses the service client.

## Plans and entitlements

Many applications grant features by plan.
`appMetadata` is the right place for a plan: only administrators and servers can change it, it appears in tokens as `app`, and policies can trust it.

```typescript
// in the billing webhook handler, after verifying the provider's signature
await a.users.update(userId, { appMetadata: { ...current.app_metadata, plan: "pro", plan_renews_at: renewsAt } });
```

A policy can then admit only paying users:

```json
{ "eq": ["$auth.claims.app.plan", "pro"] }
```

The person's next token carries the new plan.
For an immediate change, the application can call `auth.refreshSession()` after it learns the payment succeeded, for example from a realtime message on the person's channel.

Never put plans in `user_metadata`.
The person can change it with `auth.updateUser`, and a policy that trusts it lets anyone upgrade themselves.

For organization plans, store the plan in the organization's `metadata` and check membership plus plan in a flow or route, since tokens carry the organization's slug and role, not its metadata.

## Data requests and erasure

People can ask what you hold about them, and ask you to delete it.
Answering needs both the account and the records your resources hold.

```typescript
export async function exportPerson(userId: string) {
  const [user, history] = await Promise.all([a.users.getUser(userId), a.users.history(userId)]);
  const orders = await service.from("orders").eq("customer_id", userId).all({ maxRecords: 10_000 });
  const tickets = await service.from("tickets").eq("user_id", userId).all({ maxRecords: 10_000 });
  return { account: user, signInHistory: history, orders, tickets };
}

export async function erasePerson(userId: string) {
  for await (const ticket of service.from("tickets").eq("user_id", userId).select("id")) {
    await service.from("tickets").delete(ticket.id);
  }
  for await (const order of service.from("orders").eq("customer_id", userId).select("id")) {
    await service.from("orders").update(order.id, { customer_name: "Deleted customer", customer_email: null });
  }
  await a.users.deleteUser(userId);
}
```

Which records to delete and which to anonymize depends on what you must keep: orders and invoices often have legal retention periods, while support tickets and profiles usually do not.
Write the rules down per resource, and keep the export and erasure functions next to them so they change together.

Files in storage need the same treatment.
If keys start with the user's id, a walk with `listAll({ prefix: userId + "/" })` finds them.

## Designing roles and permissions

Roles and permissions are an interface between your product's rules and your policies.
A little structure keeps them understandable as the product grows.

| Guideline | Example |
| --- | --- |
| Name permissions as `resource:action` | `invoices:read`, `invoices:approve` |
| Use wildcards for whole areas | `reports:*` for everything about reports |
| Name roles after jobs, not people or features | `accountant`, `support`, `editor` |
| Keep environment roles for the whole application, and organization roles for membership | `support` is an environment role; `admin` of `acme` is an organization role |
| Check permissions, not role names, in policies | `{ "permission": "invoices:approve" }` survives role changes |

Policies that test permissions let you reshape roles without editing policies: move `invoices:approve` from `accountant` to `finance_lead`, and every policy follows.

## Working with every user

`users.search` pages with `limit` and `offset`.
A loop over pages visits every account, for reports and bulk changes.

<CodeGroup>
```typescript TypeScript
export async function* everyUser(filters: { search?: string; status?: string } = {}) {
  const limit = 100;
  for (let offset = 0; ; offset += limit) {
    const page = await a.users.search({ ...filters, limit, offset });
    const users = (page.data ?? page.users ?? []) as Array<Record<string, any>>;
    yield* users;
    if (users.length < limit) return;
  }
}

let withoutMfa = 0;
for await (const user of everyUser({ status: "no_mfa" })) withoutMfa += 1;
console.log(`${withoutMfa} accounts have no second factor`);
```

### Bulk role changes

Granting or removing a role for many people is a loop over ids with modest concurrency, reading each person's roles before writing them:

```typescript
export async function addRoleToAll(userIds: string[], role: string) {
  for (const id of userIds) {
    const user = await a.users.getUser(id);
    const roles = new Set<string>(user.roles ?? []);
    if (roles.has(role)) continue;
    roles.add(role);
    await a.users.update(id, { roles: [...roles] });
  }
}
```

Skipping people who already have the role makes the script safe to run again.
If many people need the same new permission, adding it to an existing role is a single call and reaches all of them at their next token.

## Provisioning a customer organization

Business products often set up an organization for each new customer: an owner, a few admins, a plan in the metadata, and invitations for the rest of the team.

```typescript
import { ConflictError } from "@pawabase/client";

export async function provisionOrganization(input: {
  slug: string;
  name: string;
  ownerEmail: string;
  admins: string[];
  invitees: string[];
  plan: string;
}) {
  for (const email of [input.ownerEmail, ...input.admins]) {
    await a.users.create({ email }).catch((error) => {
      if (!(error instanceof ConflictError)) throw error;
    });
  }
  await a.orgs.create(input.slug, input.name, { ownerEmail: input.ownerEmail, metadata: { plan: input.plan } });
  for (const email of input.admins) await a.orgs.addMember(input.slug, { email, role: "admin" });
  for (const email of input.invitees) {
    await a.orgs.invite(input.slug, { email, role: "member", redirectTo: "https://app.example.com/join" });
  }
}
```

Creating accounts for the owner and admins, and inviting everyone else, matches who you know needs access on day one and who chooses to join.
Accounts created without a password get a reset email from your application when the customer is ready to start.

## Watching account security

A short daily job turns the module's data into a picture of account security.

```typescript
export async function securityDigest() {
  const [stats, failures, locked] = await Promise.all([
    a.insight.stats(),
    a.insight.events({ kind: "sign_in", failed: true, limit: 500 }),
    a.users.search({ status: "locked", limit: 100 }),
  ]);
  return { stats, recentFailures: failures, lockedAccounts: locked };
}
```

| Signal | Possible meaning |
| --- | --- |
| Many failed sign-ins across many accounts | Credential stuffing with leaked passwords |
| Many failures on one account | Someone guessing one person's password |
| A rising number of locked accounts | An attack, or a broken sign-in form |
| Low share of accounts with MFA | An opportunity to encourage enrolment |

React to attacks at the firewall, with rate limits on the token endpoint; react to individual targeting by contacting the person.

## Sessions at scale

`sessions.list` shows active sessions across users, and `sessions.revoke(family)` ends one.
Two uses come up.

After a security incident, such as a leaked signing secret or a compromised device fleet, ending many sessions forces everyone to sign in again.
Per person, `users.revokeSessions(id)` is the clearer call; across everyone, an installation-level action may be more appropriate than looping over sessions.

For compliance requirements such as "no session older than thirty days", a job can read sessions and revoke the old ones:

```typescript
const sessions = await a.sessions.list({ limit: 500 });
const cutoff = Date.now() - 30 * 24 * 3600 * 1000;
for (const session of (sessions.data ?? []) as Array<{ family?: string; id?: string; created_at?: string }>) {
  const created = session.created_at ? Date.parse(session.created_at) : Date.now();
  const family = session.family ?? session.id;
  if (family && created < cutoff) await a.sessions.revoke(family);
}
```

Print one listing first; the field that identifies a session's family may be named differently in your installation's version.

## Email addresses

The administration module does not change a person's email address.
Email changes go through the person, with `auth.updateUser({ email })`, which sends a confirmation to the new address, so an address cannot be changed to one the person does not control.

When an email must change and the person cannot do it, for example after a company renamed its domain, the safe sequence is: create a new account for the new address, move roles, memberships and owned records to it, and disable the old one.

## Self-service or administration

Many things this module does, people can also do for themselves through `auth`, under their own permissions.
Choosing the right one keeps secret keys out of everyday features.

| Task | Self-service, with `auth` | Administration, with `admin()` |
| --- | --- | --- |
| Change my name or profile | `auth.updateUser` | `users.update` |
| Sign out my other devices | `auth.signOut({ scope: "others" })` | `users.revokeSessions` |
| Manage my organization's members | `auth.orgs.members`, `setMemberRole`, `removeMember`, as an org admin | `orgs.setMemberRole`, `orgs.removeMember` |
| Invite someone to my organization | `auth.orgs.invite`, as an org admin | `orgs.invite` |
| Revoke my personal API key | `auth.apiKeys.revoke` | `apiKeys.revoke` |
| Unlock an account, reset MFA, disable someone | Not possible | `users.update`, `users.resetMfa` |

Build features on the self-service column whenever it covers them.
Those calls run with the person's own token and their organization role, so the platform enforces who may do what, and your server needs no secret key for them.
Reserve `admin()` for your own staff and for system processes.

## Organization admin screens

A customer's organization admins usually manage their own team inside your application.
That is self-service: the screens use the admin's own session, and the platform checks their organization role.

```typescript
import { PermissionError } from "@pawabase/client";

export async function loadTeam(slug: string) {
  const [members, invitations, teams] = await Promise.all([
    pawabase.auth.orgs.members(slug),
    pawabase.auth.orgs.invitations(slug),
    pawabase.auth.orgs.teams(slug),
  ]);
  return { members, invitations, teams };
}

export async function changeRole(slug: string, userId: string, role: "viewer" | "member" | "admin" | "owner") {
  try {
    await pawabase.auth.orgs.setMemberRole(slug, userId, role);
```

No secret key is involved, so a bug in these screens cannot affect other organizations.
Your support staff use `admin()` for the rare cases an organization cannot solve itself, such as an organization whose only owner left.

## The life of an account

```text
created ──(email confirmed, or created verified)──▶ active
   │                                                  │
   │                    failed attempts ──▶ locked ──(time passes, or unlock)──▶ active
   │                                                  │
   │                                     disabled ◀──(disable)──┤──(enable)──▶ active
   │                                                  │
   └──────────────────────────────────────────────────┴──(delete)──▶ deleted (email released)
```

| State | Can sign in | How to leave it |
| --- | --- | --- |
| Created, unverified | Not with a password, when verification is required | The person confirms; or `update(id, { emailVerified: true })` |
| Active | Yes | |
| Locked | No, until the lockout ends | Time, or `update(id, { unlock: true })` |
| Disabled | No | `update(id, { disabled: false })` |
| Deleted | No | Not reversible; a new account can use the email |

Support conversations become shorter when everyone uses these names: "the account is locked" and "the account is disabled" need different actions.

## Copying identities between environments

Sometimes a staging environment needs real accounts, for example to reproduce a problem an organization reports.
Identity backups and restores copy accounts deliberately.

```typescript
const productionAdmin = admin(service, "production");
const stagingAdmin = productionAdmin.withEnvironment("staging");

const backup = await productionAdmin.insight.backup();
const preview = await stagingAdmin.insight.restore(backup.identities ?? backup, { dryRun: true });
console.log(preview);
```

A restore with `replace: false` adds and updates; with `replace: true`, it removes identities not in the backup.
Run `dryRun` first, and read what would change.

Copying production identities into a less protected environment copies personal data.
Prefer copying one organization's accounts, with their consent, or creating realistic test accounts instead.

## Accountability

The platform's audit trail records management actions with the key that made them.
When your support tool makes a change, the trail shows the support tool's key, not the staff member who pressed the button.

| Record | Holds |
| --- | --- |
| The platform's audit trail (`manage().health.audit`) | Which key changed what, and when |
| Your own `support_actions` resource | Which staff member asked, and why |

Keep both, and link them by time and user id.
An auditor asking "who disabled this account?" then gets a name and a reason, not a key id.

## An account recovery policy

Account recovery is where security and kindness pull in different directions.
Writing the policy down before the first difficult request keeps support consistent.

| Situation | Recommended response |
| --- | --- |
| Forgot password | Self-service reset; support only resends |
| Lost authenticator, has recovery codes | Self-service; the person signs in with a recovery code |
| Lost authenticator and codes | Identity check through a channel you trust, then `resetMfa` and `unlock` |
| Lost access to the email address | Identity check, then a new account with transferred roles and records; disable the old one |
| Suspects someone else is in the account | `revokeSessions`, a password reset, and a review of personal API keys and history |

The identity check is the hard part.
For business customers, confirmation from the organization's owner is often the best available; for consumers, knowledge of recent activity is better than knowledge of personal details that may be public.

## People in several organizations

In business products, one person often belongs to several organizations: their employer, a client, a partner.
The account is one; the memberships are many; the token names one organization at a time.

| Concern | How it works |
| --- | --- |
| Which organization a request acts in | The token's `org`, chosen at sign-in or with `auth.switchOrg` |
| What the person may do there | Their organization role, `$auth.org_role`, and policies that test it |
| Where their data lives | Records carry the organization, and policies compare it with `$auth.org` |
| Removing them from one organization | `orgs.removeMember`; their other memberships are untouched |

Administration follows the same shape.
`orgs.removeMember(slug, userId)` removes one membership; `users.update(id, { disabled: true })` blocks the person everywhere.
Choose deliberately: an employer removing a contractor should not lock the contractor out of their other clients.

## An invitation from start to finish

| Step | Who | Call |
| --- | --- | --- |
| Invite | An org admin in your app, or your staff | `auth.orgs.invite` or `admin().orgs.invite` |
| Email | The platform | Sent from the environment's invitation template, linking to `redirectTo` with a token |
| Arrive | The invited person | Your page keeps the token and asks them to sign in or sign up |
| Accept | The invited person, signed in | `auth.orgs.acceptInvitation(token)` |
| Switch | The invited person | `auth.switchOrg(slug)` so the token names the organization |
| Track | Admins | `orgs.invitations(slug)`, `admin().invitations.list()` |

Invitations expire.
When one has expired, `invitations.resend(id)` sends a fresh email; when it went to the wrong address, `invitations.revoke(id)` cancels it and a new invitation goes to the right one.

The [authentication page](/clients/typescript/authentication#an-invitation-landing-page) shows the landing page that keeps the token across sign-in.

## Removing abandoned sign-ups

Environments that require email verification collect accounts that never confirmed: typos, bots, people who changed their mind.
A periodic job can remove those older than a few weeks.

```typescript
export async function removeStaleUnverified(days = 30) {
  const cutoff = Date.now() - days * 24 * 3600 * 1000;
  const stale: string[] = [];
  for await (const user of everyUser({ status: "unverified" })) {
    if (user.created_at && Date.parse(user.created_at) < cutoff && !user.last_sign_in_at) stale.push(user.id);
  }
  console.log(`removing ${stale.length} unverified accounts older than ${days} days`);
  for (const id of stale) await a.users.deleteUser(id);
}
```

Deleting frees the addresses, so a real person who mistyped can sign up again.
Run it with a printout and no deletes the first time, and keep the threshold generous.

## Reading effective permissions

When a policy refuses someone who should be allowed, compare what the policy requires with what the person has.
`users.getUser(id)` returns `roles` and the effective `permissions`, which combine role permissions and direct grants.

```typescript
const user = await a.users.getUser(userId);
console.log({ roles: user.roles, permissions: user.permissions, mfa: user.mfa_enabled });
```

| Policy requires | Check |
| --- | --- |
| A role | `roles` contains it |
| A permission | `permissions` contains it, or a wildcard that covers it |
| `aal2` | `mfa_enabled`, and that the person signed in with their second factor |
| An organization role | The person's membership, and that their token was issued for that organization |

If the person has what the policy requires but is still refused, their token is older than the change; a refresh fixes it.

## A support tool's front end

The support tool's screens call your own server endpoints, never `admin()` directly, because the browser must not hold a secret key.

```tsx
export function UserPanel({ userId, token }: { userId: string; token: string }) {
  const [state, setState] = useState<{ user?: any; history?: any; message?: string }>({});

  useEffect(() => {
    fetch(`/support/users/${userId}`, { headers: { authorization: `Bearer ${token}` } })
      .then((response) => response.json())
      .then((data) => setState(data));
  }, [userId, token]);

  async function act(path: string, reason?: string) {
    const response = await fetch(`/support/users/${userId}/${path}`, {
      method: "POST",
      headers: { authorization: `Bearer ${token}`, "content-type": "application/json" },
      body: JSON.stringify({ reason }),
    });
    setState((current) => ({ ...current, message: response.ok ? "Done." : `Refused (${response.status}).` }));
  }

  if (!state.user) return <p>Loading…</p>;
  return (
    <section>
      <h2>{state.user.email}</h2>
      <p>{state.user.disabled ? "Disabled" : state.user.locked_until ? `Locked until ${state.user.locked_until}` : "Active"}</p>
      <button onClick={() => act("unlock")}>Unlock</button>
      <button onClick={() => act("sign-out-everywhere", prompt("Reason?") ?? undefined)}>Sign out everywhere</button>
      <button onClick={() => act("reset-mfa", prompt("Reason for MFA reset?") ?? undefined)}>Reset MFA</button>
      {state.message && <p role="status">{state.message}</p>}
    </section>
  );
}

declare function useState<T>(initial: T): [T, (value: T | ((current: T) => T)) => void];
declare function useEffect(effect: () => void, deps: unknown[]): void;
```

Show the account's state in words, from the fields described above, so staff choose the right action.
Ask for a reason on actions that weaken security, and send it to the server, which records it.

## Default roles and new accounts

An environment can grant default roles to every new account.
Roles you pass to `users.create` are added to the defaults, not used instead of them.

| You want | Do |
| --- | --- |
| Every new person to have a role | Set it as a default role in the environment's sign-in configuration |
| A specific person to also be `staff` | `create({ roles: ["staff"] })` |
| A person without the default role | Create, then `update(id, { roles: [...] })` with the exact list |

## Organization reports

Customer-facing teams ask questions such as "which customers have the most members" or "which organizations have nobody with MFA".

```typescript
export async function organizationReport() {
  const orgs = await a.orgs.list();
  const rows = [];
  for (const org of (orgs.data ?? []) as Array<{ slug: string; name: string }>) {
    const detail = await a.orgs.getOrg(org.slug);
    rows.push({ slug: org.slug, name: org.name, members: (detail.members ?? []).length });
  }
  return rows.sort((x, y) => y.members - x.members);
}
```

Print one `getOrg` answer to see what it includes in your installation before building on its fields.
For large numbers of organizations, run reports from a job and store the result, rather than computing them on request.

## What belongs in app metadata

`app_metadata` travels in every access token, as the `app` claim.
That makes it fast for policies, and it also means every byte is sent with every request.

| Put in `app_metadata` | Keep in a resource |
| --- | --- |
| The plan, and flags policies test | Billing history, invoices |
| An external customer id needed for routing | Profile details shown on screens |
| A small set of feature switches | Preferences with many fields |
| Values that change rarely | Values that change often |

A value that changes often in `app_metadata` reaches requests only at the next token, so it is stale for up to the token's lifetime.
Values that must be current on every request belong in records, read by the flow or policy that needs them.

## Keeping plans in step with billing

Billing systems are the source of truth for plans, and webhooks from them can be missed.
A nightly reconciliation compares the billing system with `app_metadata` and fixes differences.

```typescript
export async function reconcilePlans(billingPlans: Map<string, string>) {
  let fixed = 0;
  for await (const user of everyUser()) {
    const expected = billingPlans.get(user.id) ?? "free";
    const current = user.app_metadata?.plan ?? "free";
    if (current !== expected) {
      await a.users.update(user.id, { appMetadata: { ...(user.app_metadata ?? {}), plan: expected } });
      fixed += 1;
    }
  }
  return fixed;
}
```

Writing the whole `appMetadata` object, built from the current one, keeps other keys intact.
A small number of fixes each night is normal; a large number means webhooks are failing.

## Temporary access

Support staff sometimes need extra access for a day, or a contractor needs a permission for a week.
The platform does not expire grants by itself, so pair each temporary grant with a record of when it ends, and a scheduled job that removes it.

```typescript
export async function grantTemporarily(userId: string, permissions: string[], hours: number) {
  await a.users.grant(userId, permissions);
  await service.from("temporary_grants").create({
    user_id: userId,
    permissions,
    expires_at: new Date(Date.now() + hours * 3600 * 1000).toISOString(),
  });
}

export async function revokeExpiredGrants() {
  const now = new Date().toISOString();
  for await (const grant of service.from("temporary_grants").lt("expires_at", now)) {
    await a.users.revoke(String(grant.user_id), grant.permissions as string[]);
    await service.from("temporary_grants").delete(grant.id as string);
  }
}
```

The grant reaches the person at their next token; the revocation likewise.
For access that must end at an exact minute, also revoke their sessions when the grant ends.

## Who has which role

Access reviews ask a simple question: who holds each role, and should they?
A report from `everyUser` answers it.

```typescript
export async function roleReport() {
  const holders = new Map<string, string[]>();
  for await (const user of everyUser()) {
    for (const role of user.roles ?? []) {
      holders.set(role, [...(holders.get(role) ?? []), user.email]);
    }
  }
  return Object.fromEntries([...holders.entries()].sort(([x], [y]) => x.localeCompare(y)));
}
```

Run it quarterly for privileged roles such as `staff`, `support` and `admin`, and send each list to the person responsible for that role.
Removing access nobody needs is the cheapest security improvement there is.

## Instead of impersonation

Support teams sometimes ask to "log in as" a customer to see what they see.
The module deliberately has no such action: signing in as someone else blurs every audit trail.

| Need | Alternative |
| --- | --- |
| See the data a person sees | Run the query with the API Explorer's application-user authentication, as that person |
| Reproduce a flow failure for a person | `manage().flows.run(name, input, { asUser })`, which returns the trace |
| Understand a refusal | Compare `getUser(id)` roles and permissions with the policy |
| See their screen | Ask the person to share their screen |

Each alternative leaves the person's own sessions untouched and records who looked.

## A checklist for admin features

| Check | Why |
| --- | --- |
| The feature runs on a server, never in a browser | `admin()` needs a secret key |
| The caller's right to the action is checked in your code | The module does not check |
| Sensitive actions require a reason and are recorded | Accountability beyond the key |
| The environment is explicit | No accidental changes elsewhere |
| Self-service alternatives are used where they exist | Fewer secret-key code paths |
| Bulk actions print what they will do before doing it | Mistakes are caught before they happen |

## Coming from Supabase's auth admin API

| Supabase | `admin()` | Note |
| --- | --- | --- |
| `auth.admin.listUsers({ page, perPage })` | `users.search({ limit, offset })` | Also filters by text and status |
| `auth.admin.getUserById(id)` | `users.getUser(id)` | Includes admin-only fields |
| `auth.admin.createUser({ email, password, email_confirm })` | `users.create({ email, password, emailVerified })` | Verified by default |
| `auth.admin.updateUserById(id, { app_metadata, ban_duration })` | `users.update(id, { appMetadata, disabled })` | No timed bans; disable and re-enable |
| `auth.admin.deleteUser(id)` | `users.deleteUser(id)` | Soft delete; the email is released |
| `auth.admin.inviteUserByEmail(email)` | `orgs.invite(slug, { email })`, or `create` plus a reset email | Invitations belong to organizations |
| `auth.admin.signOut(jwt)` | `users.revokeSessions(id)` or `sessions.revoke(family)` | |
| `auth.admin.mfa.deleteFactor` | `users.resetMfa(id)` | Removes all factors |
| Custom roles in a table with RLS | `roles` and permissions, tested by policies | Built in |

Supabase bans have a duration; here, disabling lasts until you re-enable, so time-limited bans need a scheduled job, like temporary grants.

## Sign-up and sign-in trends

`insight.events` returns authentication events, which are enough for simple trends without an analytics product.

```typescript
export async function signUpsPerDay(limit = 1000) {
  const events = await a.insight.events({ kind: "sign_up", limit });
  const perDay = new Map<string, number>();
  for (const event of (events.data ?? []) as Array<{ at?: string; created_at?: string }>) {
    const day = (event.at ?? event.created_at ?? "").slice(0, 10);
    if (day) perDay.set(day, (perDay.get(day) ?? 0) + 1);
  }
  return [...perDay.entries()].sort();
}
```

Event kinds and their timestamp field are worth confirming from one printed answer before building a report on them.
For product analytics beyond counts, send your own events from the application to the tool your team uses.

## Deleting an organization

`orgs.remove(slug)` deletes an organization and its memberships.
The accounts of its members remain, with their other memberships.

| What | After deletion |
| --- | --- |
| Member accounts | Unchanged |
| Memberships and invitations of the organization | Removed |
| Tokens issued for the organization | Valid until they expire; refreshes no longer name it |
| Records tagged with the organization's slug | Unchanged; your code decides what to do with them |

Treat organization deletion like account deletion: export what the customer may want, remove or archive their records, then delete the organization.
Deleting first and cleaning up later leaves records that no policy can reach.

## Studio or a script

The **Users** tab in Studio and this module call the same routes.

| Use Studio when | Use a script when |
| --- | --- |
| Handling one person's request | The same action applies to many people |
| Looking around to understand a problem | The action must be repeatable and reviewed |
| A support case needs judgment | A process runs on a schedule, such as reconciliation or clean-up |

Studio actions appear in the audit trail with the operator's identity; script actions appear with the key's.
Both are fine, as long as your own records connect script actions to the people who asked for them.

## A support case, followed through

A customer writes: "I can't get into my account since yesterday."

| Step | Call | Finding |
| --- | --- | --- |
| Find the account | `users.search({ search: "ada@example.com" })` | One account, `mfa_enabled: true` |
| Read the history | `users.history(id)` | Five failed MFA codes yesterday evening, then `locked` |
| Read the account | `users.getUser(id)` | `locked_until` is this morning, now passed; `disabled: false` |
| Ask the person | Email | They got a new phone; the authenticator did not move with it |
| Verify identity | Your recovery policy | Confirmed through their organization's owner |
| Fix | `users.resetMfa(id)`, `users.update(id, { unlock: true })` | They can sign in with their password and enroll again |
| Record | Your `support_actions` resource | Reason: "New phone, identity confirmed by org owner" |

Without the history, the case looks like a forgotten password, and a password reset would not have helped.
With it, the cause was clear in one call.

## Passwords set by administrators

`users.create({ password })` and `users.update(id, { password })` set a password directly, under the environment's password policy.
A password that does not meet the policy is refused with `ValidationError`.

Setting passwords for people is occasionally necessary, for example for shared kiosk accounts.
For individual people it is a poor default: the administrator knows the password, it travels through whatever channel you use to share it, and the person may never change it.
Prefer creating accounts without a password and sending a reset email, which lets the person choose.

## Usernames

Every account has a username, unique within the environment.
When you do not set one, it is generated from the email address.

Usernames matter only if your application shows them or lets people sign in with them.
If it does, set them deliberately at creation; changing them later breaks links and mentions that used the old one.

## Administration from serverless functions

`admin()` works in serverless functions and edge workers like the rest of the client.
Two considerations apply.

The secret key must be available to the function as a secret, never bundled into code that also ships to browsers.
And bulk operations that loop over many users can exceed a function's time limit; run them as background jobs or split them into batches the function processes one at a time.

## Effects on a person's open screens

Administrative changes reach a person's open application in different ways, and knowing them helps you tell people what to expect.

| Change | What the person sees |
| --- | --- |
| Disabled | Their next refresh fails and the app signs them out, within the token's remaining lifetime |
| Sessions revoked | The same: signed out at the next refresh |
| Roles added | New access appears after the next refresh, without signing out |
| Roles removed | Requests needing the role start failing after the next refresh |
| Removed from an organization | Requests in that organization start failing after the next refresh; `switchOrg` to it is refused |
| MFA reset | Nothing until they next sign in, when no second factor is asked |
| Unlocked | They can sign in again at once |

Realtime connections follow the same rhythm: when a token expires without a refresh, the connection continues as anonymous and channels that need the person are closed.

An application can shorten these delays by refreshing the session when it receives a nudge, for example a message on the person's own realtime channel published by your admin code after a change.
That is worth doing for role grants, which people wait for, and rarely for removals, which they do not.

```typescript
// after granting a role on the server
await a.users.update(userId, { roles: [...roles, "editor"] });
await service.realtime.publish(`user:${userId}`, "account.changed", { reason: "roles" });

// in the person's app
inbox.onEvent("account.changed", () => void pawabase.auth.refreshSession());

declare const roles: string[];
declare const inbox: import("@pawabase/client").RealtimeChannel;
```

The message carries no sensitive data; it only tells the app to fetch a fresh token, which then carries the new roles.
A channel rule that lets only servers publish to `user:<id>` channels keeps anyone else from sending such nudges.
Even a forged nudge would do little harm, because refreshing a session only fetches what the person is already entitled to.

| Without a nudge | With a nudge |
| --- | --- |
| New roles apply within the token's lifetime, 15 minutes by default | New roles apply within a second |
| No extra moving parts | A channel rule and a listener |

Most applications start without and add the nudge when people notice the delay.

## Safety

| Practice | Why |
| --- | --- |
| Check the caller in your own code before every `admin()` call made on someone's behalf | The module acts with full authority |
| Record who did what, with a reason, for sensitive actions | The audit trail shows the key, not the staff member |
| Pass the environment explicitly | A support action in the wrong environment helps nobody |
| Verify identity before MFA resets and email-related help | Social engineering targets support |
| Prefer disabling over deleting until you are sure | Disabling can be undone |
| Keep identity backups encrypted and access-controlled | They describe every account |

## Troubleshooting

| Symptom | Cause | What to do |
| --- | --- | --- |
| A disabled person still uses the app | Their current access token has not expired | Wait up to its lifetime, or shorten token lifetimes |
| New roles do not apply | The person's token predates the change | They get them at the next refresh; `auth.refreshSession()` makes it immediate |
| `ConflictError` on create | The email already exists in this environment | Search for it; it may be a disabled or earlier account |
| An invited person never received the email | Mail delivery, or the address | Check `manage().mail.log()`, then `invitations.resend` |
| Someone is still locked after an MFA reset | Reset does not clear lockouts | `update(id, { unlock: true })` |
| Changes appear in development | No environment passed | Pass it |
| `roles` lost after an update | `roles` replaces the list | Read, combine, then write |

## Questions developers ask

<AccordionGroup>
  <Accordion title="Can I sign in as a user to see what they see?">
    Not with this module.
    To reproduce what a person experiences with data, use the management module's `flows.run` with `asUser`, or the API Explorer's application-user authentication, both of which act as the person without their password.
  </Accordion>
  <Accordion title="Can I set a user's password?">
    Yes, with `update(id, { password })`, and the password policy applies.
    Prefer sending a reset email, so only the person knows their password.
  </Accordion>
  <Accordion title="Do users of one environment exist in another?">
    No.
    Environments have separate users; promoting definitions does not copy accounts.
    Use identity backups and restores to copy users deliberately.
  </Accordion>
  <Accordion title="Is there a read-only key for this module?">
    Restrict a key's allowed routes to `GET` requests on the auth administration paths to make one.
    Without such a restriction, any secret key can perform every action.
  </Accordion>
  <Accordion title="How do organization roles relate to environment roles?">
    They are separate.
    Environment roles come from `roles` and apply everywhere; an organization role applies within that organization and appears as `$auth.org_role` when the token is issued for it.
  </Accordion>
  <Accordion title="Can I schedule an account to be disabled later?">
    Not with a setting.
    Record the date in your own resource and disable the account from a scheduled job, as with temporary grants.
  </Accordion>
  <Accordion title="Do admin actions send emails to the person?">
    Only actions that are emails by nature, such as invitations.
    Disabling, role changes and MFA resets are silent; tell the person yourself when they should know.
  </Accordion>
  <Accordion title="What happens to a deleted user's records?">
    Nothing automatically.
    Their owner field keeps the old id, and the records remain until your code deletes, anonymizes or transfers them.
  </Accordion>
</AccordionGroup>
