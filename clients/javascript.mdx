`@pawabase/client` is the official TypeScript client for Pawabase.
It runs in browsers, in Node, and in any runtime that has the standard `fetch` API.
It has no runtime dependencies.

This page is the map of the whole package.
It explains what a client object represents, what each part of it is for, which key you give it in which place, and what the package deliberately does not do.
The pages after it go deep on one part each.

<Info>
This section documents `@pawabase/client` 0.1.0 as it exists on the `feat/sdk-split` branch of the `Pawabase/pawabase-js` repository.
Every method named in this section exists in that source.
When a page says "the server does X", the behavior was observed against a running Pawabase stack, not inferred from the client.
</Info>

## The mental model

A Pawabase client is a typed HTTP client for **one environment of one project**, reached through **one gateway**, holding **one API key** and, optionally, **one signed-in user**.

Everything else follows from that sentence.

The client is not a database driver.
It does not open a connection to your database, it does not cache rows, and it does not run queries locally.
Every method that touches data sends an HTTP request to the gateway.
The gateway checks the key, and the service behind it checks the policies.
The answer you get back is exactly what the server decided this caller may see.

The client is also not an ORM.
Rows come back as plain objects with the field names your resource declares, in the server's `snake_case`.
There are no model classes, no change tracking, and no lazy relations.
When you want related records, you ask for them in the same request with `expand`.

What the client does add on top of plain `fetch` is the part that is tedious and easy to get wrong by hand:

| Concern | What the client does for you |
| --- | --- |
| Credentials | Sends the API key on every request and the user's access token when someone is signed in. |
| Sessions | Stores the session, refreshes it before it expires, and refreshes it only once at a time. |
| Queries | Builds the `filter[…]`, `sort`, `select`, `expand`, `page` and `per_page` parameters, and refuses queries the server would answer wrongly. |
| Failures | Turns every error body shape the platform produces into one error class hierarchy. |
| Retries | Retries rate limits and gateway failures with backoff, and only when repeating the request is safe. |
| Realtime | Keeps one WebSocket per client, reconnects, rejoins channels, and removes duplicate messages. |
| Types | Checks resource names, row fields and filter values against types generated from your project. |

If you keep this model in mind, most questions answer themselves.
"Why did a record I can see in Studio come back as a `404`?" is a policy question, because the client only reports what the server returned.
"Why is my list total `null`?" is a server question about per-row policies, and the client tells you so instead of guessing.
"Why can't I join two tables in one query?" is because the data API serves resources, and resources expose relations through `expand`, not through SQL.

## What the package contains

One install gives you the main client, two optional subpath modules for server-side administration, and a command-line type generator.

| Import | What it is | Who uses it |
| --- | --- | --- |
| `createClient` from `@pawabase/client` | The client: records, auth, storage, flows, routes, realtime | Every application |
| `manage` from `@pawabase/client/manage` | The management plane of an environment: resources, policies, flows, secrets, keys, firewall, backups and more | Servers, scripts and CI with a secret key |
| `admin` from `@pawabase/client/admin` | Administration of your application's users, roles and organizations | Servers and back-office tools with a secret key |

The two subpaths are separate entry points on purpose.
A browser bundle that imports only `@pawabase/client` never contains the management or user-administration code.
Those modules only work with a secret key, and a secret key must never reach a browser, so there is no reason for a bundler to ship them there.

The client object itself has these members:

| Member | Purpose | Page |
| --- | --- | --- |
| `from(name)` | Records of a resource, typed from your generated `Database` type | [Records and queries](/clients/typescript/records) |
| `resource<Row, Insert, Update>(name)` | Records of a resource, typed by hand | [Records and queries](/clients/typescript/records) |
| `auth` | Sign-up, sign-in, sessions, MFA, organizations, devices, personal API keys | [Authentication](/clients/typescript/authentication) |
| `storage` | Buckets, uploads, downloads, signed URLs | [Storage](/clients/typescript/storage) |
| `flows` | Flows that have an HTTP trigger without a path | [Flows and routes](/clients/typescript/flows-and-routes) |
| `routes` | Custom routes you defined under `/rest/v1` | [Flows and routes](/clients/typescript/flows-and-routes) |
| `realtime` | Channels, presence, history, publishing | [Realtime](/clients/typescript/realtime) |
| `asUser(token)` | A client that acts as one user for one server-side request | [Servers and testing](/clients/typescript/server-runtimes-testing) |
| `request(method, path, options)` | A raw request to any gateway path, with keys, retries and typed errors | [Client configuration](/clients/typescript/client-configuration) |
| `status()` | The health of the services behind the gateway | [Client configuration](/clients/typescript/client-configuration) |
| `dispose()` | Stops the refresh timer and closes the realtime connection | [Client configuration](/clients/typescript/client-configuration) |
| `http` | The underlying transport, for advanced use | [Errors and retries](/clients/typescript/errors-retries) |

<Note>
The client object also has a `functions` member.
Custom functions were removed from the Pawabase platform, so that member calls endpoints that no longer exist and is not documented here.
Server-side logic that used to live in a function belongs in a [flow](/flows/overview), a [custom route](/data/custom-routes), or an extension route.
</Note>

## Installing

The package is named `@pawabase/client`.
It is built from source when installed from its Git repository, so you do not need a separate build step.

```bash
npm install github:Pawabase/pawabase-js
```

```bash
pnpm add github:Pawabase/pawabase-js
```

```bash
bun add github:Pawabase/pawabase-js
```

After installation, imports use the package name, not the repository name:

```typescript
import { createClient } from "@pawabase/client";
```

The package ships both ES modules and CommonJS, each with type declarations.
A `require("@pawabase/client")` in an older Node project and an `import` in a Vite project resolve to the same API.

### What the runtime must provide

The client relies on web-standard APIs and nothing else.

| API | Needed for | Where it exists |
| --- | --- | --- |
| `fetch`, `Request`, `Response`, `Headers` | Every HTTP call | Browsers, Node 18 and later, Deno, Bun, Cloudflare Workers, React Native |
| `AbortController` | Timeouts and cancellation | The same places |
| `WebSocket` | Live realtime channels only | Browsers, Node 22 and later, Deno, Bun; on Node 20 pass the `ws` package |
| `localStorage` | Keeping a browser session between page loads | Browsers; elsewhere the session is kept in memory unless you supply storage |
| `navigator.locks` (Web Locks) | Serializing token refresh across tabs | Modern browsers; elsewhere refresh is serialized inside one client |

The package declares Node 20 as its minimum.
On Node 20, everything except a live realtime socket works out of the box.
For realtime on Node 20 you pass a WebSocket implementation in the options, which the [realtime page](/clients/typescript/realtime) shows.

If your runtime has no global `fetch` at all, you pass one in the `fetch` option.
The same option is how you add instrumentation or a test double, so it is worth knowing even when your runtime has `fetch`.

## The three things a client needs

A client needs a gateway URL and an API key.
Most clients also want the environment name.

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";

export const pawabase = createClient({
  url: "https://api.example.com",
  apiKey: "pb_pk_live_…",
  environment: "production",
});
```

```python Python
from pawabase import Pawabase

pb = Pawabase(
    "https://api.example.com",
    "pb_pk_live_…",
    environment="production",
)
```

```bash cURL
# Every request carries the key; the environment is a header hint.
export PAWABASE_URL="https://api.example.com"
export PAWABASE_KEY="pb_pk_live_…"

curl "$PAWABASE_URL/v1/status" -H "apikey: $PAWABASE_KEY" -H "x-environment: production"
```
</CodeGroup>

### The gateway URL

The URL is the origin of your Pawabase gateway: the single public entry point in front of the data, auth, storage and realtime services.
It is the same for every environment of an installation.
The client appends service paths such as `/rest/v1`, `/auth/v1`, `/storage/v1` and `/realtime/v1` to it.

Give the origin only.
`https://api.example.com` is right.
`https://api.example.com/rest/v1` is wrong, because the client would then call `/rest/v1/rest/v1/…`.
A trailing slash is removed for you.

The client refuses a URL it cannot parse and a URL whose scheme is not `http:` or `https:`, by throwing `ConfigError` from `createClient`.
It does this at construction time, so a misconfigured deployment fails at startup, not on the first user action.

### The API key

The API key decides which project and environment a request belongs to, and with which ceiling of authority.
Pawabase has two kinds of project keys, and the difference matters more than anything else on this page.

| Key | Prefix | Where it may live | What it can do |
| --- | --- | --- | --- |
| Publishable | `pb_pk_…` | Browsers, mobile apps, anywhere | Acts as the anonymous role, or as the signed-in user. Every policy applies. |
| Secret | `pb_sk_…` | Servers, scripts and CI only | Bypasses every policy. Can use the management and user-administration modules. |

A publishable key is not a secret.
It identifies your environment and lets the gateway apply the environment's CORS origins and rate limits.
Everything it can reach is decided by policies, so publishing it in a web page is the intended use.

A secret key is a root credential for one environment.
Anyone who holds it can read and change every record and every setting of that environment.
The client protects you from the most common way of leaking one: when it detects a browser and a key that starts with `pb_sk_` (or the older `sk_`), `createClient` throws `ConfigError`.
The option `dangerouslyAllowBrowser: true` turns that check off.
There are very few legitimate reasons to use it, and they are all internal tools that never leave a trusted machine.

You create and copy keys in Studio under **Access → API keys**.
The **New API key** sheet asks for a **Name**, a **Key type**, optional **Permissions** (scopes), and **Limits** such as **Expires**, **Allowed IP ranges** and **Allowed routes**.
The full key is shown once, in the **Your new key** dialog, and never again.
See [API keys](/studio/api-keys) for scopes, rotation and revocation.

### The environment name

A key already belongs to exactly one environment, so data, auth, storage and realtime calls work without naming it.
The client still accepts an `environment` option, and you should pass it, because three features need the name itself rather than the key:

| Feature | Why it needs the environment name |
| --- | --- |
| Social sign-in | The provider authorization URL is `/auth/v1/authorize/<environment>/<provider>`. |
| Realtime | The socket URL carries the environment as a query parameter. |
| `manage()` and `admin()` | Management paths are `/platform/v1/envs/<environment>/…`. |

When you pass `environment`, the client also sends an `x-environment` header with every request.
When you pass `project`, it sends `x-project-id`.
The gateway treats these as hints; the key remains the authority on which environment you reach.

## How a request travels

Knowing the path of one request explains most error messages you will meet.

```text
your code
  │  pawabase.from("orders").eq("status", "open")
  ▼
@pawabase/client
  │  GET /rest/v1/orders?filter[status]=eq.open
  │  apikey: pb_pk_…              (always)
  │  authorization: Bearer <jwt>   (when a user is signed in)
  │  x-client-info: pawabase-js/0.1.0
  ▼
gateway
  │  key valid?            no  → 401 invalid_api_key
  │  origin allowed?       no  → 403 origin_not_allowed   (publishable keys)
  │  firewall rule?        yes → 403 or 429
  │  rate limit left?      no  → 429 rate_limit_exceeded
  │  scope allows route?   no  → 403
  ▼
data service
  │  body valid?           no  → 422 with a list of field issues
  │  policy allows?        no  → 401, 403 policy '…' refused, or 404
  ▼
database
  │
  ▼
JSON response → the client parses it → your code gets a plain object
```

Three things in that diagram matter for client code.

First, the gateway answers some failures before your resource is involved at all.
A `429` from the gateway means the request did nothing, which is why the client may safely repeat any `429`, even a `POST`.

Second, a request can fail validation before its policy runs.
An anonymous request with a malformed body gets `422`, not `401`.
Do not read a `422` as "this caller is allowed".

Third, a read policy that hides a record answers `404`, not `403`.
The server does not reveal that a record exists to someone who may not read it.
The client mirrors this: `get()` throws `NotFoundError`, and `maybeGet()` returns `null`, for both "does not exist" and "exists but hidden".

## The parts of the client

Each part of the client is a thin, typed layer over one family of gateway paths.
This section explains what each part is for and when you would reach for it, so you can find the right page.

### Records

`pawabase.from("orders")` returns a resource client for the `orders` resource.
It can create, read, update, replace and delete single records, and it can start a query.

<CodeGroup>
```typescript TypeScript
const orders = pawabase.from("orders");

const order = await orders.create({ customer_id: "c_1", total_minor: 4200 });
const same = await orders.get(order.id);
await orders.update(order.id, { status: "paid" });

const open = await orders
  .eq("status", "open")
  .gte("total_minor", 1000)
  .order("created_at", "desc")
  .perPage(20);
```

```python Python
orders = pb.from_("orders")

order = orders.create({"customer_id": "c_1", "total_minor": 4200})
same = orders.get(order["id"])
orders.update(order["id"], {"status": "paid"})

open_orders = orders.eq("status", "open").gte("total_minor", 1000).order("created_at", "desc").per_page(20).execute()
```

```bash cURL
curl -X POST "$PAWABASE_URL/rest/v1/orders" \
  -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" \
  -d '{"customer_id": "c_1", "total_minor": 4200}'

curl "$PAWABASE_URL/rest/v1/orders/$ORDER_ID" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN"

curl -X PATCH "$PAWABASE_URL/rest/v1/orders/$ORDER_ID" \
  -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" \
  -d '{"status": "paid"}'

curl -G "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "filter[status]=eq.open" --data-urlencode "filter[total_minor]=gte.1000" \
  --data-urlencode "sort=-created_at" --data-urlencode "per_page=20"
```
</CodeGroup>

A query is an immutable value.
Each method returns a new query, so a base query can be shared and refined without surprises.
A query is also a promise: `await` runs it and returns one page.

The query builder knows three server behaviors that would otherwise return wrong data silently, and it refuses to send those queries:

| Server behavior | What the client does |
| --- | --- |
| The server keeps only the last filter when a field is filtered twice. | A second filter on the same field throws `InvalidQueryError`. |
| `filter[flag]=eq.false` matches the wrong rows. | `eq(column, false)` is sent as `is.false`. |
| `in` lists are split on commas. | An `in` value that contains a comma throws `InvalidQueryError`. |

The [records page](/clients/typescript/records) covers every filter, selection, expansion, pagination and bulk method, and what each one sends.

### Authentication

`pawabase.auth` is everything about the person using your application: signing up, signing in by password, magic link or a social provider, multi-factor authentication, sessions on other devices, organizations they belong to, and keys they create for themselves.

<CodeGroup>
```typescript TypeScript
const result = await pawabase.auth.signInWithPassword({ email, password });

if (result.status === "mfa_required") {
  await result.verify(codeFromUser);
}

pawabase.auth.onAuthStateChange((event, session) => {
  console.log(event, session?.user.email);
});
```

```python Python
result = pb.auth.sign_in_with_password(email=email, password=password)

if result.status == "mfa_required":
    result.verify(code_from_user)

pb.auth.on_auth_state_change(lambda event, session: print(event, session and session.user["email"]))
```

```bash cURL
curl -X POST "$PAWABASE_URL/auth/v1/token" -H "apikey: $PAWABASE_KEY" -H "content-type: application/json" \
  -d '{"grant_type": "password", "email": "ada@example.com", "password": "…"}'
# → {"access_token": …, "refresh_token": …, "expires_in": 900, "user": {…}}
# or {"mfa_required": true, "mfa_token": "…", "factors": ["totp"]}, finished with:
curl -X POST "$PAWABASE_URL/auth/v1/token" -H "apikey: $PAWABASE_KEY" -H "content-type: application/json" \
  -d '{"grant_type": "mfa", "mfa_token": "…", "code": "123456"}'
```
</CodeGroup>

The most valuable thing `auth` does is invisible.
Pawabase rotates refresh tokens on every use and treats a refresh token presented twice as theft, which ends the whole session family.
Two requests that both notice an expired token and both refresh would sign the user out.
The client makes every caller in one client share a single refresh, and in browsers it serializes refreshes across tabs with the Web Locks API.
A `401` on any request triggers one refresh and one replay.

The [authentication page](/clients/typescript/authentication) explains the session lifecycle, every sign-in method, MFA, organizations, and how sessions are stored.

### Storage

`pawabase.storage` uploads and downloads files in the environment's buckets.
Each bucket has its own policies for reading, writing, listing and deleting, and its own limits on content types and size.

<CodeGroup>
```typescript TypeScript
const avatars = pawabase.storage.from("avatars");

await avatars.upload(`${userId}/me.png`, file);
const { url } = await avatars.createSignedUrl(`${userId}/me.png`, { expiresIn: 300 });
```

```python Python
avatars = pb.storage.from_("avatars")

avatars.upload(f"{user_id}/me.png", Path("me.png"))
url = avatars.create_signed_url(f"{user_id}/me.png", expires_in=300)["url"]
```

```bash cURL
curl -X PUT "$PAWABASE_URL/storage/v1/object/avatars/$USER_ID/me.png" \
  -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: image/png" \
  --data-binary @me.png

curl -X POST "$PAWABASE_URL/storage/v1/sign/avatars/$USER_ID/me.png" \
  -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" \
  -d '{"method": "GET", "expires_in": 300}'
```
</CodeGroup>

Signed URLs carry their own authority.
A signed upload URL lets a browser send a file straight to storage without ever holding a key that could do anything else.
The [storage page](/clients/typescript/storage) covers uploads, downloads, listings, public URLs and signed URLs.

### Flows and routes

`pawabase.flows.run(name, input)` runs a [flow](/flows/overview) that has an HTTP trigger without a path.
`pawabase.routes.get(path)`, `post`, `put`, `patch` and `delete` call [custom routes](/data/custom-routes) you defined under `/rest/v1`.

<CodeGroup>
```typescript TypeScript
const quote = await pawabase.flows.run<{ total: number }>("price-cart", { cart_id: "cart_9" });
const receipt = await pawabase.routes.post("orders/42/refund", { reason: "damaged" });
```

```python Python
quote = pb.flows.invoke("price-cart", {"cart_id": "cart_9"})
receipt = pb.routes.post("orders/42/refund", {"reason": "damaged"})
```

```bash cURL
curl -X POST "$PAWABASE_URL/flows/v1/price-cart" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" \
  -H "content-type: application/json" -d '{"cart_id": "cart_9"}'

curl -X POST "$PAWABASE_URL/rest/v1/orders/42/refund" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" \
  -H "content-type: application/json" -d '{"reason": "damaged"}'
```
</CodeGroup>

These are the way an application calls server-side logic that is more than a single record operation.
The [flows and routes page](/clients/typescript/flows-and-routes) explains what each returns and how their errors arrive.

### Realtime

`pawabase.realtime.channel(name)` gives you a channel on the environment's realtime service.
A channel delivers messages, tracks who is present, and keeps recent history.
A resource with realtime turned on publishes its changes on `resource:<name>`, filtered per subscriber by the resource's read policy.

<CodeGroup>
```typescript TypeScript
const changes = pawabase.realtime.channel("resource:orders");
changes.on("message", (message) => console.log(message.event, message.payload));
await changes.subscribe();
```

```python Python
async with AsyncPawabase(url, key, environment="production") as apb:
    changes = apb.realtime.channel("resource:orders")
    changes.on("message", lambda message: print(message["event"], message["payload"]))
    await changes.subscribe()
```

```bash cURL
# Live channels are a WebSocket: wss://<gateway>/realtime/v1/socket?apikey=…&token=…&environment=…
# Recent messages and publishing also work over HTTP:
curl "$PAWABASE_URL/realtime/v1/channels/resource:orders/history?limit=20" \
  -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN"
```
</CodeGroup>

The client keeps one WebSocket for all channels, sends heartbeats, reconnects with backoff, rejoins channels, can replay what was missed, and removes duplicates by message id.
The [realtime page](/clients/typescript/realtime) covers channels, presence, history, rules and reconnection.

### Errors and retries

Every failure the client raises is a `PawabaseError`.
Failures the server answered are `ApiError` subclasses with a `status`, a stable `code`, the `requestId`, and, for validation failures, a list of field issues.

<CodeGroup>
```typescript TypeScript
import { NotFoundError, ValidationError } from "@pawabase/client";

try {
  await pawabase.from("orders").create(input);
} catch (error) {
  if (error instanceof ValidationError) showFieldErrors(error.byField());
  else throw error;
}
```

```python Python
from pawabase import NotFoundError, ValidationError

try:
    pb.from_("orders").create(values)
except ValidationError as error:
    show_field_errors(error.detail)   # the server's list of issues
```

```bash cURL
curl -i -X POST "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_KEY" -H "Authorization: Bearer $TOKEN" \
  -H "content-type: application/json" -d '{"total_minor": "abc"}'
# HTTP/1.1 422
# x-request-id: req_…
# [{"type": "missing", "loc": ["body", "customer_id"], "msg": "Field required"}, …]
```
</CodeGroup>

The [errors and retries page](/clients/typescript/errors-retries) lists every class, the retry rules, timeouts, cancellation and observability hooks.

### Management and user administration

With a secret key, a server can do anything Studio does.

<CodeGroup>
```typescript TypeScript
import { manage } from "@pawabase/client/manage";
import { admin } from "@pawabase/client/admin";

const m = manage(pawabase);
await m.secrets.set("PAYSTACK_SECRET", process.env.PAYSTACK_SECRET!);

const a = admin(pawabase);
await a.users.update(userId, { disabled: true });
```

```python Python
service = Pawabase(url, "pb_sk_…", environment="production")

service.manage.secrets.set("PAYSTACK_SECRET", os.environ["PAYSTACK_SECRET"])
service.admin.users.update(user_id, disabled=True)
```

```bash cURL
curl -X PUT "$PAWABASE_URL/platform/v1/envs/production/secrets/PAYSTACK_SECRET" \
  -H "apikey: $PAWABASE_SECRET_KEY" -H "content-type: application/json" -d '{"value": "sk_live_…", "description": ""}'

curl -X PATCH "$PAWABASE_URL/platform/v1/envs/production/auth/users/$USER_ID" \
  -H "apikey: $PAWABASE_SECRET_KEY" -H "content-type: application/json" -d '{"disabled": true}'
```
</CodeGroup>

`manage()` covers the environment's definitions and operations.
`admin()` covers the people who sign in to your application.
They are documented on [Environment management](/clients/typescript/management) and [User administration](/clients/typescript/user-administration).

## Choosing a key for each place your code runs

The single most important decision in a Pawabase client is which key it holds.
The table below is the decision for the places TypeScript usually runs.

| Where the code runs | Key | User identity | Why |
| --- | --- | --- | --- |
| A browser single-page app | Publishable | The signed-in user's session | Anyone can read browser code, so the key must be one that policies constrain. |
| A React Native or Capacitor app | Publishable | The user's session, stored with the platform's secure storage | Same reason; app binaries are readable. |
| A server-rendered page (Next.js, Remix, SvelteKit) | Publishable | The user's token, per request, through `asUser` | The page acts for the visitor, so the visitor's policies must apply. |
| An API server acting for a user | Publishable | The user's token, per request | Same as above; the server is a proxy for one person. |
| A background worker, cron job or webhook receiver | Secret | None | No person is involved; the job needs full access to do its work. |
| A CI pipeline or migration script | Secret | None | It changes definitions and data across the environment. |
| A back-office tool for staff | Secret, server-side only | Staff identity checked by your own server | Staff need more than end-user policies allow, but the key stays on the server. |

Two patterns follow from this table.

A server that renders pages for users should hold a **publishable** key, not a secret one.
It is tempting to use a secret key "because it is a server", but then every policy is bypassed and the server must re-implement access control by hand.
Using the user's token with a publishable key lets the same policies that protect your browser app protect your server.

A server that does privileged work for users, such as issuing a refund that users cannot do themselves, should hold **two** clients: a publishable one for acting as the user, and a secret one for the privileged step after your own check.
This keeps the privileged surface small and visible in code review.

## How many clients to create

A client holds a session, a refresh timer and possibly a WebSocket.
Creating one per request or per component throws away that state and wastes connections.

| Context | How many clients | Notes |
| --- | --- | --- |
| Browser app | One, created at module load and imported where needed | The session is shared across the app and across tabs. |
| React app | The same single client, provided through context if you prefer | Do not create a client inside a component body; it would be recreated on each render. |
| Node server acting for users | One base client for the process, plus `asUser(token)` per request | `asUser` returns a lightweight client with no stored session and no timers. |
| Node worker with a secret key | One for the process | There is no session to refresh. |
| Tests | One per test, disposed after | Call `dispose()` so timers and sockets do not keep the test runner alive. |
| Hot module reload in development | Dispose the previous client before creating a new one | Otherwise you accumulate refresh timers. |

## What comes back from a call

The client returns what the server sends, parsed from JSON, with as little reshaping as possible.
This is a deliberate design choice: the field names you see in Studio, in the API Explorer and in the docs are the names you read in code.

| Call | Returns |
| --- | --- |
| A list query (`await query`) | `{ data, page, per_page, total }` |
| `first()` | The first row, or `null` |
| `single()` | The first row, or throws `NotFoundError` |
| `get(id)` | The row |
| `create(row)` | The created row, including server-assigned fields |
| `update(id, patch)` | The updated row |
| `delete(id)` | `undefined` |
| `auth.getUser()` | A `User` object with `snake_case` fields such as `email_verified` and `user_metadata` |
| `storage.from(b).upload(...)` | `{ bucket, key, size, content_type, etag? }` |
| `flows.run(name)` | The flow's response body |
| `manage()` and `admin()` methods | The management plane's JSON document; lists are `{ data: [...] }` |

The client does not wrap results in a `{ data, error }` envelope.
A failed call throws.
This keeps the success path free of checks and puts the failure path in a `catch` where TypeScript can narrow error classes.

Dates arrive as ISO 8601 strings, as the server sends them.
The client does not convert them to `Date` objects, because a string survives JSON serialization, server-side rendering and caching unchanged.
Convert at the edge of your UI when you need a `Date`.

## What the SDK does not do

Some features people expect from a backend client are not part of this one.
Knowing them up front saves design time.

| You might expect | What to do instead |
| --- | --- |
| Joins or arbitrary SQL from the browser | Declare relations on the resource and use `expand`; for computed results, write a [custom route](/data/custom-routes) backed by a flow. |
| Two bounds on one field in one list query (`gte` and `lte` on `created_at`) | Filter one bound on the server and the other in code, store a period field, or add a route. The client refuses the two-filter form because the server would silently drop one. |
| Transactions across several requests | Put the multi-step write in a flow or route, where it runs as one server-side operation. |
| Idempotency keys | The server does not support them. Use natural unique fields so a repeated create fails with `409` instead of duplicating. |
| An offline cache or optimistic updates | Use your UI framework's data layer (TanStack Query, SWR, Apollo-style caches) on top of the client. |
| Custom functions | Removed from the platform. Use flows, custom routes, or extension routes. |
| Automatic retries of every failure | Only safe repeats are retried. A `POST` that failed with a network error is not repeated unless you mark it idempotent. |

## Coming from supabase-js

Many developers arrive from Supabase.
The shapes are close enough to feel familiar and different enough to cause bugs if you translate by habit.

| supabase-js | @pawabase/client | The difference that matters |
| --- | --- | --- |
| `createClient(url, anonKey)` | `createClient({ url, apiKey })` | Options object. The key is `pb_pk_…`, not a JWT. |
| `const { data, error } = await …` | `const data = await …` in `try`/`catch` | Errors are thrown as classes. |
| `.from("t").select("*")` | `.from("t")` then `await` | Selecting all columns is the default. |
| `.select("id, author(name)")` | `.select("id").expand("author")` | Relations are named, not embedded in a select string. |
| `.range(0, 9)` | `.page(1).perPage(10)` | Pages are numbered from 1; at most 200 rows per page. |
| `.eq("done", false)` | `.eq("done", false)` | Same call; the client sends `is.false` because `eq.false` misbehaves on the server. |
| `.gte("d", a).lte("d", b)` | Not allowed | One filter per field; the client throws instead of dropping a bound. |
| `.single()` | `.single()` | Throws `NotFoundError` when there is no row. |
| `{ count: "exact" }` | `.count()` | Throws when a per-row policy makes the count unknowable. |
| `supabase.auth.signInWithPassword` | `pawabase.auth.signInWithPassword` | Returns `{ status }`, which may be `mfa_required`. |
| `supabase.functions.invoke` | `pawabase.flows.run` or `pawabase.routes.post` | Server logic lives in flows and routes. |
| `supabase.channel("x").on("broadcast", …)` | `pawabase.realtime.channel("x").on("message", …)` | Channel access is decided by channel rules configured in Studio. |
| Row Level Security | Policies | Policies are named, reusable conditions attached to operations, not SQL. |

The Supabase comparison and the migration guide go further.

## A complete small program

The program below uses most parts of the client together.
It signs a user in, lists their open orders, uploads a receipt, runs a flow, and listens for changes.

```typescript
import {
  createClient,
  NotFoundError,
  PermissionError,
  ValidationError,
} from "@pawabase/client";
import type { Database } from "./database";

const pawabase = createClient<Database>({
  url: "https://api.example.com",
  apiKey: "pb_pk_live_…",
  environment: "production",
});

async function main() {
  const signIn = await pawabase.auth.signInWithPassword({
    email: "ada@example.com",
    password: "correct horse battery staple",
  });

  if (signIn.status === "mfa_required") {
    await signIn.verify(await askForCode());
  }

  const user = await pawabase.auth.getUser();

  const openOrders = await pawabase
    .from("orders")
    .eq("status", "open")
    .order("created_at", "desc")
    .expand("customer")
    .perPage(10);

  console.log(`${user.email} has ${openOrders.total ?? "some"} open orders`);

  const first = openOrders.data[0];
  if (!first) return;

  const receipts = pawabase.storage.from("receipts");
  await receipts.upload(`${user.id}/${first.id}.pdf`, await loadPdf(), {
    contentType: "application/pdf",
  });

  try {
    const quote = await pawabase.flows.run<{ total_minor: number }>("quote-order", {
      order_id: first.id,
    });
    console.log("quote", quote.total_minor);
  } catch (error) {
    if (error instanceof ValidationError) console.error(error.byField());
    else if (error instanceof PermissionError) console.error("refused by", error.policy);
    else if (error instanceof NotFoundError) console.error("no such flow");
    else throw error;
  }

  const changes = pawabase.realtime.channel("resource:orders");
  changes.on("message", (message) => {
    console.log(message.event, message.payload);
  });
  await changes.subscribe();
}

declare function askForCode(): Promise<string>;
declare function loadPdf(): Promise<Blob>;

main().catch((error) => {
  console.error(error);
  pawabase.dispose();
});
```

Each line in that program is covered on a later page in this section.
The order of the pages follows the order a typical application meets them: configuration, records, authentication, storage, flows and routes, realtime, types, errors, servers and tests, then the server-only management and administration modules.

## Security checklist for client code

The client makes the safe path the default, but some decisions are yours.

| Check | Why |
| --- | --- |
| Only `pb_pk_…` keys appear in browser and mobile code. | A secret key bypasses every policy. |
| Secret keys come from environment variables or a secret manager on servers. | Keys in source control end up in forks, logs and screenshots. |
| The environment's allowed CORS origins list your real web origins. | Publishable-key requests from other origins get `403 origin_not_allowed`. |
| Every resource operation the browser uses has a policy you have read. | The client sends whatever your code asks for; policies are the boundary. |
| Server-rendered pages use `asUser(token)` with a publishable key. | The visitor's policies then apply on the server too. |
| Secret-key clients are not exported from shared modules that browser code imports. | A bundler follows imports; one stray import can ship a secret. |
| Social sign-in uses a publishable key. | The key travels in the authorization URL; the client refuses to put a secret key there. |
| Signed URLs have short expiries. | Anyone holding the URL has its authority until it expires. |
| `dangerouslyAllowBrowser` is not set in application code. | It exists for trusted internal tools only. |

The [security model](/auth/security-model) and [API keys](/studio/api-keys) pages explain the platform side of each item.

## Before the first production release

The security checklist protects data.
This one protects users from the failures that only appear under real traffic.

| Check | Why it matters in production |
| --- | --- |
| The production build reads the production key and environment name. | A development key in production sends real users to development data. |
| Error tracking records `requestId` for every `ApiError`. | Support can then find the failing request under **Project → Activity**. |
| Loading states wait for `INITIAL_SESSION`. | Signed-in users are not bounced to the sign-in page on reload. |
| Long lists use `pages()` or `all({ maxRecords })`, not unbounded loops. | A per-row policy can make `total` unknown, and a loop that trusts it never ends or ends early. |
| Writes that users can repeat rely on unique fields. | The server has no idempotency keys; a unique constraint turns a double submit into a `409`. |
| Realtime screens handle `closed` and resubscribe states. | Mobile networks drop sockets often; the UI should show it. |
| `dispose()` runs where clients are created dynamically. | Leaked timers and sockets accumulate in long-running processes. |

Run the smoke test from [Checking a new configuration](#checking-a-new-configuration) against production after every deploy.
It takes seconds and catches a wrong key or a missing origin before your users do.

## Troubleshooting the first connection

Most first-connection problems come from the URL, the key or the browser origin.
The client's errors are specific enough to tell them apart.

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| `ConfigError: createClient needs the gateway url.` | The URL environment variable is empty in this build. | Check how your bundler exposes environment variables (`import.meta.env`, `process.env`, a public prefix). |
| `ConfigError: … is not a valid URL.` | The URL has no scheme, or contains spaces. | Use the full origin, such as `https://api.example.com`. |
| `ConfigError: A secret key (pb_sk_…) must never run in a browser` | A secret key reached browser code. | Use a publishable key in the browser; keep the secret key on the server. |
| `NetworkError: Could not reach https://…` | DNS, TLS, or the gateway is down; or a browser blocked the request. | Open the gateway URL in a browser; check the console for a CORS message. |
| `AuthenticationError` with code `invalid_api_key` | The key is wrong, revoked or expired, or belongs to another installation. | Copy the key again from **Access → API keys**. |
| `PermissionError` with code `origin_not_allowed` | The page's origin is not in the environment's CORS list. | Add the origin under **Access → Networking**. |
| `NotFoundError` on a list | The resource name is wrong, or the `list` operation is disabled. | Check the name and operations under **Data**; compare with the API Explorer. |
| `RateLimitError` during development | A loop is calling faster than the limit allows. | Read `retryAfter`; the client already waited and retried before throwing. |
| `TimeoutError` | A request ran longer than `timeoutMs` (30 seconds by default). | Find the slow request by id under **Project → Activity**; raise the timeout only if the work is legitimately long. |

When none of these fit, call `pawabase.status()`.
It asks the gateway for the health of the services behind it without needing a valid user, and it tells you whether the problem is your code or the installation.

The hand-written version works, and the [REST conventions](/reference/rest-conventions) page documents every parameter it uses.
What it leaves out is everything around the request:

| Concern | Hand-written `fetch` | `@pawabase/client` |
| --- | --- | --- |
| An expired access token | `401`; your code must refresh and repeat | Refreshed before sending, or after one `401`, once |
| Two components refreshing at once | Both refresh; the second reuse ends the session | One shared refresh |
| A `429` from the gateway | An exception, or a retry loop you write | Waits for `Retry-After` and repeats |
| A `503` during a deploy | An exception | Retried with backoff for safe methods |
| The error body | One of several shapes; you parse it | One class hierarchy with `status`, `code`, `requestId` |
| `eq.false` on a boolean | Silently matches the wrong rows | Sent as `is.false` |
| A second filter on `status` | The first is dropped silently | `InvalidQueryError` before sending |
| A typo in a field name | Found at runtime, if at all | A compile error with an application-defined `Database` interface |

Use raw `fetch` when you want to see the protocol, or when a tiny script does not justify a dependency.
Use the client when correctness under concurrency, expiry and failure matters, which is most applications.

## Checking a new configuration

When you set up a new environment or deploy to a new host, a short smoke test catches the common mistakes before a user does.
It checks that the gateway answers, that the key is accepted, that the origin is allowed, and that the resources your app needs are reachable with the identity it will use.

```typescript
import { createClient, ApiError, NetworkError } from "@pawabase/client";

export async function smokeTest(options: { url: string; apiKey: string; environment: string; resources: string[] }) {
  const pawabase = createClient({ ...options, retry: false, timeoutMs: 10_000 });
  const report: Array<{ check: string; ok: boolean; detail?: string }> = [];

  try {
    const health = await pawabase.status();
    report.push({ check: "gateway answers", ok: health.ok });
  } catch (error) {
    report.push({ check: "gateway answers", ok: false, detail: String(error) });
    return report;
  }

  try {
    const settings = await pawabase.auth.settings();
    report.push({ check: "key accepted", ok: true, detail: `sign-up ${settings.signup_enabled ? "on" : "off"}` });
  } catch (error) {
    const detail = error instanceof ApiError ? `${error.status} ${error.code}` : String(error);
    report.push({ check: "key accepted", ok: false, detail });
  }

  for (const name of options.resources) {
    try {
      const page = await pawabase.from(name).perPage(1);
      report.push({ check: `list ${name}`, ok: true, detail: `total ${page.total ?? "unknown"}` });
    } catch (error) {
      if (error instanceof NetworkError) report.push({ check: `list ${name}`, ok: false, detail: "network" });
      else if (error instanceof ApiError) report.push({ check: `list ${name}`, ok: false, detail: `${error.status} ${error.code}` });
      else throw error;
    }
  }

  pawabase.dispose();
  return report;
}
```

Read the results with the request path above in mind.
A failing `gateway answers` is DNS, TLS or the installation.
A failing `key accepted` with `401` is the key.
A `list` failing with `401` while signed out is the default `authenticated` policy, which may be exactly what you want.
A `list` failing with `404` is a wrong resource name or a disabled `list` operation.

Run the same test in a browser once, too.
Only a browser sends an `Origin` header, so only a browser run reveals a missing CORS origin.

## Logging requests from day one

Production problems are much easier to solve when every failed request in your logs carries its request id.
The client's hooks make that a few lines of setup, and they never fail a request even if your logging throws.

```typescript
import { createClient, ApiError } from "@pawabase/client";

export const pawabase = createClient({
  url: import.meta.env.VITE_PAWABASE_URL,
  apiKey: import.meta.env.VITE_PAWABASE_KEY,
  environment: import.meta.env.VITE_PAWABASE_ENV,
  hooks: {
    onResponse: ({ method, url, status, durationMs, requestId }) => {
      if (status >= 500 || durationMs > 2000) {
        console.warn("pawabase", { method, url, status, durationMs, requestId });
      }
    },
    onRetry: ({ method, url, attempt, reason, delayMs }) => {
      console.info("pawabase retry", { method, url, attempt, reason, delayMs });
    },
    onError: (error, { method, url }) => {
      const requestId = error instanceof ApiError ? error.requestId : null;
      reportToErrorTracker(error, { method, url, requestId });
    },
  },
});

declare function reportToErrorTracker(error: unknown, context: Record<string, unknown>): void;
```

The `onRequest` hook receives the headers with `apikey` and `authorization` masked, so it is safe to log.
Response bodies are not passed to hooks; that keeps personal data out of logs by default.

## Guarding signed-in screens

Because the session loads asynchronously, a route guard needs three states, not two: unknown, signed out, and signed in.
Treating "unknown" as "signed out" sends signed-in users to the sign-in page on every reload.

```typescript
import { useEffect, useState } from "react";
import type { Session } from "@pawabase/client";
import { pawabase } from "./lib/pawabase";

type AuthState = { status: "loading" } | { status: "signed_out" } | { status: "signed_in"; session: Session };

export function useAuthState(): AuthState {
  const [state, setState] = useState<AuthState>({ status: "loading" });
  useEffect(() => {
    const { unsubscribe } = pawabase.auth.onAuthStateChange((_event, session) => {
      setState(session ? { status: "signed_in", session } : { status: "signed_out" });
    });
    return unsubscribe;
  }, []);
  return state;
}
```

A guard component then renders a placeholder while loading, redirects when signed out, and renders the page when signed in.
The listener also fires on `SIGNED_OUT` in another tab and when a refresh token is refused, so the guard reacts to a session ending anywhere.

Remember that a route guard is a user-experience feature.
The security boundary is still the policy on each resource, which applies whatever the browser renders.

## What a policy sees about your client

A policy decides each request using a context that the gateway and the auth service build from the request's credentials.
Your client controls only two inputs to that context: the API key it holds, and the user token it attaches.
Everything else in the context is derived on the server and cannot be forged from the client.

The table lists the parts of the context that change depending on how you configured the client.

| Context value | With a publishable key and no user | With a publishable key and a signed-in user | With a secret key |
| --- | --- | --- | --- |
| `$auth.authenticated` | `false` | `true` | `false` |
| `$auth.kind` | `anonymous` | `user` | `service` |
| `$auth.user_id` | empty | the user's id | empty |
| `$auth.roles` | `[]` | the user's roles | `[]` |
| `$auth.org` | empty | the organization the token was issued for | empty |
| `$auth.aal` | empty | `aal1`, or `aal2` after a second factor | empty |
| `$credential.role` | `anon` | `anon` | `service` |
| `$credential.is_service` | `false` | `false` | `true` |
| `$credential.scopes` | the key's scopes | the key's scopes | the key's scopes |

Three consequences matter for client code.

The default policy on resource operations, routes, flows and buckets is the built-in `authenticated`.
A new resource therefore refuses anonymous callers until you choose otherwise.
If a signed-out page in your app gets `AuthenticationError` on a list, the fix is a policy decision in Studio, not a client option.

A secret key is not a signed-in user.
It bypasses policies entirely, so a policy that tests `$auth.user_id` never runs for it.
If server code needs "the current user" while holding a secret key, it must take the user's id from somewhere it trusts and pass it explicitly, or it should use a publishable key with `asUser(token)` instead.

`$auth.org` comes from the token, and the token is issued for one organization at a time.
`auth.switchOrg(slug)` asks for new tokens for another organization.
Until you call it, policies that test `$auth.org` see the organization of the current token.

The [policy context reference](/policies/context) lists every variable.

## Response headers worth knowing

The client reads a few response headers for you and exposes them where they are useful.
Knowing them helps when you inspect traffic in the browser's network panel or in a proxy.

| Header | Sent by | Meaning | Where the client surfaces it |
| --- | --- | --- | --- |
| `x-request-id` | Gateway, on every response | The id of this request in the platform's logs | `ApiError.requestId`; the `onResponse` hook's `requestId` |
| `Retry-After` | Gateway on `429`; services on some `503` | Seconds (or an HTTP date) to wait before repeating | Used by the retry policy; `ApiError.retryAfter` |
| `X-RateLimit-Limit` | Gateway, when the limiter is active | The request budget for the current window | Not parsed; read it with the `fetch` option or a raw response |
| `X-RateLimit-Remaining` | Gateway, when the limiter is active | Requests left in the window | Not parsed; read it the same way |
| `etag` | Storage downloads | The stored object's version | `downloadResponse()` returns the raw `Response` |
| `content-type` | Every response | JSON for API answers; the object's type for downloads | Used to parse; available on raw responses |

The headers the client sends are fixed and few:

| Header | Value | When |
| --- | --- | --- |
| `apikey` | Your API key | Every request except calls to a signed URL |
| `authorization` | `Bearer <access token>` | When a user is signed in, or when you passed `accessToken` |
| `x-client-info` | `pawabase-js/0.1.0` | Every request except calls to a signed URL |
| `x-environment` | The `environment` option | When the option is set |
| `x-project-id` | The `project` option | When the option is set |
| `accept` | `application/json`, or `*/*` for downloads | Every request |
| `content-type` | `application/json` for object bodies; the declared type for uploads | When there is a body |

Anything you pass in the `headers` option is added to every request after these, so it can override them.
That is occasionally useful in tests and rarely a good idea in production.

## Reading the browser's network panel

When you open the network panel in browser developer tools, you will see more requests than your code made.
This is expected, and understanding it saves time when you debug.

The client sends custom headers, `apikey` and `x-client-info`, and usually `authorization`.
A browser treats a cross-origin request with custom headers as "not simple", so before the real request it sends an `OPTIONS` request, called a preflight, asking the gateway whether those headers are allowed from your origin.

| Row in the network panel | Method | What it is |
| --- | --- | --- |
| `orders?filter[status]=eq.open` | `OPTIONS` | The preflight; the gateway answers with the allowed origin, methods and headers |
| `orders?filter[status]=eq.open` | `GET` | The real request |
| `token` | `OPTIONS` then `POST` | A token refresh, with its own preflight |
| `socket?apikey=…` | `GET` (status `101`) | The realtime WebSocket upgrade; it stays open |

Browsers cache a preflight answer for a while, so you do not pay for it on every call to the same URL.
When the origin is not allowed, the preflight fails and the browser blocks the real request.
The client then sees a network failure, not a `403`, because the browser hides the response from JavaScript.
That is why a CORS problem appears in your code as `NetworkError` while the console shows a CORS message.

If you see `NetworkError` only in the browser and never from a server or `curl`, check **Access → Networking** for the page's origin before anything else.
See [rate limits and CORS](/reference/rate-limits-and-cors) for how origins are matched.

## Configuring each environment

You will run the same code against at least two environments, usually `development` and `production`, and often short-lived previews.
The URL is normally the same for all of them; the key and the environment name change.

The safest arrangement is to read all three from configuration and never write a key in source code.
Each framework exposes configuration to browser code differently, and only variables with the framework's public prefix reach the bundle.

| Framework | Browser-visible variable names | Server-only variable names | Notes |
| --- | --- | --- | --- |
| Vite (React, Vue, Svelte) | `VITE_PAWABASE_URL`, `VITE_PAWABASE_KEY`, `VITE_PAWABASE_ENV` | Any name without `VITE_` | Read with `import.meta.env`. |
| Next.js | `NEXT_PUBLIC_PAWABASE_URL`, `NEXT_PUBLIC_PAWABASE_KEY` | `PAWABASE_SECRET_KEY` | Read with `process.env`; public values are inlined at build time. |
| SvelteKit | `PUBLIC_PAWABASE_URL`, `PUBLIC_PAWABASE_KEY` | `PAWABASE_SECRET_KEY` | Import from `$env/static/public` or `$env/static/private`. |
| Remix and React Router | Pass values from a loader to the page | `process.env.*` on the server | There is no build-time public prefix; you choose what to send. |
| Expo | `EXPO_PUBLIC_PAWABASE_URL`, `EXPO_PUBLIC_PAWABASE_KEY` | Not applicable | Everything in an app binary is public. |
| Node, Bun, Deno | Not applicable | `PAWABASE_URL`, `PAWABASE_SECRET_KEY`, `PAWABASE_ENV` | Read from `process.env`, `Bun.env` or `Deno.env`. |
| Cloudflare Workers | Not applicable | Bindings declared in `wrangler.toml` and secrets | Read from the `env` argument of the handler. |

A publishable key in a browser-visible variable is fine.
A secret key in a browser-visible variable is a leak, even if no code reads it, because the bundler inlines it.
Name secret keys without the public prefix so that the framework itself refuses to expose them.

A small configuration module keeps the rest of the code free of environment details:

```typescript
// src/lib/pawabase.ts (Vite)
import { createClient } from "@pawabase/client";
import type { Database } from "./database";

const url = import.meta.env.VITE_PAWABASE_URL;
const apiKey = import.meta.env.VITE_PAWABASE_KEY;
const environment = import.meta.env.VITE_PAWABASE_ENV ?? "development";

if (!url || !apiKey) {
  throw new Error("VITE_PAWABASE_URL and VITE_PAWABASE_KEY must be set for this build.");
}

export const pawabase = createClient<Database>({ url, apiKey, environment });
```

```typescript
// lib/pawabase-server.ts (Next.js, server-only)
import "server-only";
import { createClient } from "@pawabase/client";
import type { Database } from "./database";

export const pawabaseService = createClient<Database>({
  url: process.env.PAWABASE_URL!,
  apiKey: process.env.PAWABASE_SECRET_KEY!,
  environment: process.env.PAWABASE_ENV ?? "production",
});
```

```typescript
// worker.ts (Cloudflare Workers)
import { createClient } from "@pawabase/client";

interface Env {
  PAWABASE_URL: string;
  PAWABASE_SECRET_KEY: string;
  PAWABASE_ENV: string;
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const pawabase = createClient({
      url: env.PAWABASE_URL,
      apiKey: env.PAWABASE_SECRET_KEY,
      environment: env.PAWABASE_ENV,
    });
    const open = await pawabase.from("orders").eq("status", "open").count();
    return Response.json({ open });
  },
};
```

The `server-only` import in the Next.js module makes the build fail if a client component imports it.
That is the cheapest protection against shipping a secret-key client to the browser.

Preview environments created for a branch or pull request have their own keys.
A preview's name is what you pass as `environment`.
See [environments and promotion](/studio/environments-and-promotion) for how previews are created and removed.

## Four application shapes

Most TypeScript applications built on Pawabase take one of four shapes.
Each one uses the client a little differently, and choosing the shape early avoids rewriting authentication later.

### A browser application talking to Pawabase directly

```text
browser ──(pb_pk_ + user token)──▶ gateway ──▶ Pawabase services
```

The browser holds a publishable key and the user's session.
Policies are the only access control, and they are enough when every rule can be written as a condition on the user, their roles, their organization, or the record.

This is the shortest path to a working product.
It is the right shape for dashboards, internal tools, and consumer apps whose rules are about ownership and membership.

```typescript
import { pawabase } from "./lib/pawabase";

export async function loadMyProjects() {
  const user = await pawabase.auth.getCachedUser();
  if (!user) return [];
  return pawabase.from("projects").eq("owner_id", user.id).order("updated_at", "desc").all();
}
```

The policy on `projects.list` should restrict rows to the owner, for example with the `owner` shorthand.
The `eq("owner_id", …)` filter in the code is for the UI, not for security; a different user who removes it still sees only their own rows.

### A server-rendered application

```text
browser ──cookie──▶ your server ──(pb_pk_ + user token)──▶ gateway
```

The server renders pages and holds the user's tokens in an HTTP-only cookie.
It uses a publishable key and `asUser(token)` per request, so the same policies apply on the server.

This shape keeps tokens out of browser JavaScript and lets you render authenticated pages on the first response.
It is the natural shape for Next.js, Remix, SvelteKit and Nuxt applications.

```typescript
import { cookies } from "next/headers";
import { createClient } from "@pawabase/client";

const base = createClient({
  url: process.env.PAWABASE_URL!,
  apiKey: process.env.PAWABASE_PUBLISHABLE_KEY!,
  environment: process.env.PAWABASE_ENV,
});

export async function ordersPage() {
  const token = (await cookies()).get("pb-access")?.value ?? null;
  const pawabase = token ? base.asUser(token) : base;
  return pawabase.from("orders").order("created_at", "desc").perPage(20);
}
```

Refreshing tokens is your server's job in this shape, because the client created by `asUser` keeps no session.
The [servers and testing page](/clients/typescript/server-runtimes-testing) shows a refresh handler.

### A mobile application

```text
app ──(pb_pk_ + user token)──▶ gateway
```

A mobile app is a browser application with different storage.
It holds a publishable key, and its session must survive the app being killed.
You give the client a storage adapter backed by the platform's secure storage.

```typescript
import * as SecureStore from "expo-secure-store";
import { createClient } from "@pawabase/client";

export const pawabase = createClient({
  url: process.env.EXPO_PUBLIC_PAWABASE_URL!,
  apiKey: process.env.EXPO_PUBLIC_PAWABASE_KEY!,
  environment: process.env.EXPO_PUBLIC_PAWABASE_ENV,
  auth: {
    storage: {
      getItem: (key) => SecureStore.getItemAsync(key),
      setItem: (key, value) => SecureStore.setItemAsync(key, value),
      removeItem: (key) => SecureStore.deleteItemAsync(key),
    },
    detectSessionInUrl: false,
  },
});
```

Social sign-in on mobile returns through a deep link.
Your deep-link handler passes the URL to `auth.getSessionFromUrl(url)`, which reads the tokens from its fragment.
The [mobile guide](/clients/mobile) covers platform details.

### A worker or integration with no user

```text
cron, queue consumer or webhook receiver ──(pb_sk_)──▶ gateway
```

A process that acts on its own behalf holds a secret key.
There is no session and no policy evaluation.
This shape fits nightly jobs, data imports, synchronization with another system, and receivers for third-party webhooks.

```typescript
import { createClient } from "@pawabase/client";

const pawabase = createClient({
  url: process.env.PAWABASE_URL!,
  apiKey: process.env.PAWABASE_SECRET_KEY!,
  environment: "production",
});

export async function closeStaleCarts(now = new Date()) {
  const cutoff = new Date(now.getTime() - 24 * 3600 * 1000);
  const stale = await pawabase.from("carts").eq("status", "open").lt("updated_at", cutoff).all({ maxRecords: 5000 });
  const results = await Promise.allSettled(stale.map((cart) => pawabase.from("carts").update(cart.id, { status: "abandoned" })));
  return results.filter((result) => result.status === "rejected").length;
}
```

Much of what workers used to do can now be a [flow](/flows/overview) with a [schedule](/jobs/schedules) instead, which runs inside Pawabase and appears in **Project → Activity** with its run history.
A worker is the better choice when the logic depends on libraries or services that a flow block cannot reach.

## The life of a browser session

A browser session goes through the same stages every time.
Knowing them helps you place loading states and redirects correctly.

```text
page load
  │  createClient(): reads the stored session from localStorage (async)
  │  if the URL fragment has #access_token=… (a social sign-in returning):
  │      store that session, clean the URL
  ▼
onAuthStateChange listeners receive INITIAL_SESSION (session or null)
  │
  ├─ signed out ──▶ sign-in form ──▶ signInWithPassword() ──▶ SIGNED_IN
  │
  └─ signed in
       │  a timer refreshes the access token ~60 s before it expires ──▶ TOKEN_REFRESHED
       │  another tab refreshes first ──▶ this tab adopts its tokens ──▶ TOKEN_REFRESHED
       │  a request gets 401 ──▶ one refresh, one replay
       │  updateUser() ──▶ USER_UPDATED
       │  the refresh token is refused (revoked, reused) ──▶ SIGNED_OUT
       ▼
signOut() ──▶ SIGNED_OUT (also in other tabs)
```

The stored session is read asynchronously, because some storage adapters are asynchronous.
Until it has been read, the client does not know whether anyone is signed in.
Show a neutral loading state until the first `INITIAL_SESSION` event, rather than flashing the sign-in form.

```typescript
pawabase.auth.onAuthStateChange((event, session) => {
  if (event === "INITIAL_SESSION") setReady(true);
  setUser(session?.user ?? null);
});
```

Every data method waits for the stored session to be read before sending.
A request made during page load therefore carries the user's token when there is one, without extra code.

Access tokens live 15 minutes by default.
The refresh timer is unreferenced on Node, so a script that forgets to call `dispose()` still exits, but tests should still dispose clients to avoid timers firing between tests.

## How the client treats time

Session expiry is a comparison between a timestamp and the device's clock, and device clocks are sometimes wrong.
The client is built so that a wrong clock costs a little efficiency, not a broken session.

| Situation | What happens |
| --- | --- |
| The server sends `expires_at` | The client keeps it as given. |
| The server sends only `expires_in` | The client computes `expires_at` from its own clock at the moment it received the tokens. |
| A session is adopted with `setSession()` | `expires_at` is read from the access token's `exp` claim. |
| The token is within 60 seconds of `expires_at` | It counts as expiring; the next request refreshes first. The margin is the `refreshMarginSeconds` option. |
| The device clock is ahead | Tokens look expired early; the client refreshes more often than necessary. |
| The device clock is behind | Tokens look valid after they expired; the server answers `401`, and the client refreshes once and repeats the request. |

The `401` replay is what makes a slow clock harmless.
It is also why you should not catch `401` errors and sign the user out yourself: by the time your code sees an `AuthenticationError`, the client has already tried a refresh and failed.

Timestamps in rows are a separate matter.
The server writes `created_at` and `updated_at` with its own clock, in UTC.
Compare them with other server timestamps, not with `Date.now()` on a device, when the difference matters.

## What each import adds to a bundle

Bundlers include the modules your code imports and the modules those import.
The client is organized so that a browser application pays only for what it uses.

| Import | Contains | Typical environment |
| --- | --- | --- |
| `@pawabase/client` | The client, records, auth, storage, flows, routes, realtime, errors and the type generator | Browser and server |
| `@pawabase/client/manage` | Thirty-one management services | Server only |
| `@pawabase/client/admin` | Eight user-administration services | Server only |

Type-only imports add nothing to a bundle.
An `import type { Database } from "./database"` is erased at compile time.

If you see management code in a browser bundle analysis, some shared module imports `@pawabase/client/manage`.
Move that import into a server-only file.

## Several environments in one process

Most processes talk to one environment.
Tools that compare or copy between environments, such as a promotion script or a data-sync job, need clients for several at once.

Each environment has its own keys, so each needs its own client:

```typescript
import { createClient } from "@pawabase/client";

const staging = createClient({
  url: process.env.PAWABASE_URL!,
  apiKey: process.env.PAWABASE_STAGING_SECRET!,
  environment: "staging",
});

const production = createClient({
  url: process.env.PAWABASE_URL!,
  apiKey: process.env.PAWABASE_PRODUCTION_SECRET!,
  environment: "production",
});

const [stagingPlans, productionPlans] = await Promise.all([
  staging.from("plans").all(),
  production.from("plans").all(),
]);

const missing = stagingPlans.filter((plan) => !productionPlans.some((p) => p.code === plan.code));
console.log("plans in staging but not production:", missing.map((plan) => plan.code));
```

The management module is the exception.
`manage(client, "staging")` and `admin(client, "staging")` address another environment through the same key, which works when that key is allowed to manage the other environment.
For copying definitions between environments, prefer the platform's own promotion, described on [environments and promotion](/studio/environments-and-promotion), over writing your own copy loop.

## Upgrading the client

The client is installed from Git, so an upgrade is a change to the commit your lockfile records.

```bash
npm install github:Pawabase/pawabase-js#<commit-or-tag>
```

Read the changes between the two commits before upgrading a production application.
Pay attention to three kinds of change: renamed methods, changes to what a method returns, and changes to retry behavior.
Your compiler finds the first two when your application defines its resource types and strict mode is on.
The third shows up only at runtime, so it deserves a test against a development environment.

A newer client can rely on type shapes that an older generated file does not have.

## Questions developers ask

<AccordionGroup>
  <Accordion title="Can I use the client without TypeScript?">
    Yes.
    The package is plain JavaScript with type declarations alongside.
    In a JavaScript project you lose compile-time checks, and everything else behaves the same.
  </Accordion>
  <Accordion title="Does the client work in a service worker or a web worker?">
    It needs `fetch` and, for realtime, `WebSocket`, both of which workers have.
    Workers have no `localStorage`, so the default session store there is memory.
    Pass an IndexedDB-backed storage adapter if a worker must keep a session.
  </Accordion>
  <Accordion title="Why does my list return 401 when no one is signed in?">
    The default policy for resource operations is `authenticated`.
    A publishable key alone is anonymous.
    Open the resource under **Data**, choose the operation, and give it a policy that admits anonymous callers, such as `public`, if that is what you intend.
  </Accordion>
  <Accordion title="Why do I get 404 for a record that exists?">
    A read policy that refuses a caller answers `404` so that it does not reveal the record exists.
    Check the `get` operation's policy for the identity you are using.
    The API Explorer under **Data → API Explorer** can send the request as a chosen user.
  </Accordion>
  <Accordion title="Can two clients share one session?">
    Two clients in the same browser that use the same URL and key share the stored session, because the storage key is derived from both.
    They do not share an in-memory refresh lock, so prefer one client per app.
  </Accordion>
  <Accordion title="Is it safe to call the client during server-side rendering and again in the browser?">
    Yes, if each side creates its own client.
    The server should use `asUser(token)` from the request's cookie; the browser client reads its own session.
    Do not serialize a client object into page props.
  </Accordion>
  <Accordion title="How do I call an endpoint the client has no method for?">
    Use `pawabase.request(method, path, { body, query })`.
    It sends the key and the user's token, applies the retry policy, and throws the same typed errors as every other method.
  </Accordion>
  <Accordion title="Can I cancel a request when a component unmounts?">
    Yes.
    Queries accept a signal through `withOptions({ signal })`, and most other methods accept `signal` in their options.
    An aborted request rejects with `AbortError`, which you can ignore in the unmount path.
  </Accordion>
  <Accordion title="Does the client batch or deduplicate identical requests?">
    No.
    Two identical queries made at the same time send two requests.
    Put a cache such as TanStack Query in front of the client if many components read the same data.
  </Accordion>
  <Accordion title="What happens to a request made while the user is signing out?">
    It carries whichever token the client had when it was sent.
    If that token has been revoked, the server answers `401`; the refresh attempt then fails, the session is cleared, and the request throws `AuthenticationError`.
  </Accordion>
  <Accordion title="Can I point the client at a local Pawabase stack?">
    Yes.
    Use the local gateway's origin, such as `http://localhost:8080`, with a key from that stack's development environment.
    Plain `http:` is accepted for exactly this case.
  </Accordion>
  <Accordion title="Is the client safe to use from several async tasks at once?">
    Yes.
    Requests are independent, refreshes are shared, and query builders are immutable values.
    The one shared piece of state is the session, which only the auth methods change.
  </Accordion>
  <Accordion title="Why does `select()` still return columns I did not ask for?">
    The server returns every declared column and sets the unselected ones to `null`.
    The client types the result so that unselected columns are optional, which keeps the compiler honest about it.
  </Accordion>
  <Accordion title="How do I see what the client sent?">
    Pass `hooks.onRequest` and `hooks.onResponse` when creating the client.
    The hooks receive the method, URL, attempt number, status and request id, with the key and token masked.
  </Accordion>
</AccordionGroup>

| Request id | The gateway's `x-request-id`, used to find a request under **Project → Activity**. |
