When you set up a new environment or deploy to a new host, a short smoke test catches the common mistakes before a user does.
It checks that the gateway answers, that the key is accepted, that the origin is allowed, and that the resources your app needs are reachable with the identity it will use.

```typescript
import { createClient, ApiError, NetworkError } from "@pawabase/client";

export async function smokeTest(options: { url: string; apiKey: string; environment: string; resources: string[] }) {
  const pawabase = createClient({ ...options, retry: false, timeoutMs: 10_000 });
  const report: Array<{ check: string; ok: boolean; detail?: string }> = [];

  try {
    const health = await pawabase.status();
    report.push({ check: "gateway answers", ok: health.ok });
  } catch (error) {
    report.push({ check: "gateway answers", ok: false, detail: String(error) });
    return report;
  }

  try {
    const settings = await pawabase.auth.settings();
    report.push({ check: "key accepted", ok: true, detail: `sign-up ${settings.signup_enabled ? "on" : "off"}` });
  } catch (error) {
    const detail = error instanceof ApiError ? `${error.status} ${error.code}` : String(error);
    report.push({ check: "key accepted", ok: false, detail });
  }

  for (const name of options.resources) {
    try {
      const page = await pawabase.from(name).perPage(1);
      report.push({ check: `list ${name}`, ok: true, detail: `total ${page.total ?? "unknown"}` });
    } catch (error) {
      if (error instanceof NetworkError) report.push({ check: `list ${name}`, ok: false, detail: "network" });
      else if (error instanceof ApiError) report.push({ check: `list ${name}`, ok: false, detail: `${error.status} ${error.code}` });
      else throw error;
    }
  }

  pawabase.dispose();
  return report;
}
```

Read the results with the request path above in mind.
A failing `gateway answers` is DNS, TLS or the installation.
A failing `key accepted` with `401` is the key.
A `list` failing with `401` while signed out is the default `authenticated` policy, which may be exactly what you want.
A `list` failing with `404` is a wrong resource name or a disabled `list` operation.

Run the same test in a browser once, too.
Only a browser sends an `Origin` header, so only a browser run reveals a missing CORS origin.


## Logging requests from day one

Production problems are much easier to solve when every failed request in your logs carries its request id.
The client's hooks make that a few lines of setup, and they never fail a request even if your logging throws.

```typescript
import { createClient, ApiError } from "@pawabase/client";

export const pawabase = createClient({
  url: import.meta.env.VITE_PAWABASE_URL,
  apiKey: import.meta.env.VITE_PAWABASE_KEY,
  environment: import.meta.env.VITE_PAWABASE_ENV,
  hooks: {
    onResponse: ({ method, url, status, durationMs, requestId }) => {
      if (status >= 500 || durationMs > 2000) {
        console.warn("pawabase", { method, url, status, durationMs, requestId });
      }
    },
    onRetry: ({ method, url, attempt, reason, delayMs }) => {
      console.info("pawabase retry", { method, url, attempt, reason, delayMs });
    },
    onError: (error, { method, url }) => {
      const requestId = error instanceof ApiError ? error.requestId : null;
      reportToErrorTracker(error, { method, url, requestId });
    },
  },
});

declare function reportToErrorTracker(error: unknown, context: Record<string, unknown>): void;
```

The `onRequest` hook receives the headers with `apikey` and `authorization` masked, so it is safe to log.
Response bodies are not passed to hooks; that keeps personal data out of logs by default.


## Guarding signed-in screens

Because the session loads asynchronously, a route guard needs three states, not two: unknown, signed out, and signed in.
Treating "unknown" as "signed out" sends signed-in users to the sign-in page on every reload.

```typescript
import { useEffect, useState } from "react";
import type { Session } from "@pawabase/client";
import { pawabase } from "./lib/pawabase";

type AuthState = { status: "loading" } | { status: "signed_out" } | { status: "signed_in"; session: Session };

export function useAuthState(): AuthState {
  const [state, setState] = useState<AuthState>({ status: "loading" });
  useEffect(() => {
    const { unsubscribe } = pawabase.auth.onAuthStateChange((_event, session) => {
      setState(session ? { status: "signed_in", session } : { status: "signed_out" });
    });
    return unsubscribe;
  }, []);
  return state;
}
```

A guard component then renders a placeholder while loading, redirects when signed out, and renders the page when signed in.
The listener also fires on `SIGNED_OUT` in another tab and when a refresh token is refused, so the guard reacts to a session ending anywhere.

Remember that a route guard is a user-experience feature.
The security boundary is still the policy on each resource, which applies whatever the browser renders.


## What a policy sees about your client

A policy decides each request using a context that the gateway and the auth service build from the request's credentials.
Your client controls only two inputs to that context: the API key it holds, and the user token it attaches.
Everything else in the context is derived on the server and cannot be forged from the client.

The table lists the parts of the context that change depending on how you configured the client.

| Context value | With a publishable key and no user | With a publishable key and a signed-in user | With a secret key |
| --- | --- | --- | --- |
| `$auth.authenticated` | `false` | `true` | `false` |
| `$auth.kind` | `anonymous` | `user` | `service` |
| `$auth.user_id` | empty | the user's id | empty |
| `$auth.roles` | `[]` | the user's roles | `[]` |
| `$auth.org` | empty | the organization the token was issued for | empty |
| `$auth.aal` | empty | `aal1`, or `aal2` after a second factor | empty |
| `$credential.role` | `anon` | `anon` | `service` |
| `$credential.is_service` | `false` | `false` | `true` |
| `$credential.scopes` | the key's scopes | the key's scopes | the key's scopes |

Three consequences matter for client code.

The default policy on resource operations, routes, flows and buckets is the built-in `authenticated`.
A new resource therefore refuses anonymous callers until you choose otherwise.
If a signed-out page in your app gets `AuthenticationError` on a list, the fix is a policy decision in Studio, not a client option.

A secret key is not a signed-in user.
It bypasses policies entirely, so a policy that tests `$auth.user_id` never runs for it.
If server code needs "the current user" while holding a secret key, it must take the user's id from somewhere it trusts and pass it explicitly, or it should use a publishable key with `asUser(token)` instead.

`$auth.org` comes from the token, and the token is issued for one organization at a time.
`auth.switchOrg(slug)` asks for new tokens for another organization.
Until you call it, policies that test `$auth.org` see the organization of the current token.

The [policy context reference](/policies/context) lists every variable.


## Response headers worth knowing

The client reads a few response headers for you and exposes them where they are useful.
Knowing them helps when you inspect traffic in the browser's network panel or in a proxy.

| Header | Sent by | Meaning | Where the client surfaces it |
| --- | --- | --- | --- |
| `x-request-id` | Gateway, on every response | The id of this request in the platform's logs | `ApiError.requestId`; the `onResponse` hook's `requestId` |
| `Retry-After` | Gateway on `429`; services on some `503` | Seconds (or an HTTP date) to wait before repeating | Used by the retry policy; `ApiError.retryAfter` |
| `X-RateLimit-Limit` | Gateway, when the limiter is active | The request budget for the current window | Not parsed; read it with the `fetch` option or a raw response |
| `X-RateLimit-Remaining` | Gateway, when the limiter is active | Requests left in the window | Not parsed; read it the same way |
| `etag` | Storage downloads | The stored object's version | `downloadResponse()` returns the raw `Response` |
| `content-type` | Every response | JSON for API answers; the object's type for downloads | Used to parse; available on raw responses |

The headers the client sends are fixed and few:

| Header | Value | When |
| --- | --- | --- |
| `apikey` | Your API key | Every request except calls to a signed URL |
| `authorization` | `Bearer <access token>` | When a user is signed in, or when you passed `accessToken` |
| `x-client-info` | `pawabase-js/0.1.0` | Every request except calls to a signed URL |
| `x-environment` | The `environment` option | When the option is set |
| `x-project-id` | The `project` option | When the option is set |
| `accept` | `application/json`, or `*/*` for downloads | Every request |
| `content-type` | `application/json` for object bodies; the declared type for uploads | When there is a body |

Anything you pass in the `headers` option is added to every request after these, so it can override them.
That is occasionally useful in tests and rarely a good idea in production.


## Reading the browser's network panel

When you open the network panel in browser developer tools, you will see more requests than your code made.
This is expected, and understanding it saves time when you debug.

The client sends custom headers, `apikey` and `x-client-info`, and usually `authorization`.
A browser treats a cross-origin request with custom headers as "not simple", so before the real request it sends an `OPTIONS` request, called a preflight, asking the gateway whether those headers are allowed from your origin.

| Row in the network panel | Method | What it is |
| --- | --- | --- |
| `orders?filter[status]=eq.open` | `OPTIONS` | The preflight; the gateway answers with the allowed origin, methods and headers |
| `orders?filter[status]=eq.open` | `GET` | The real request |
| `token` | `OPTIONS` then `POST` | A token refresh, with its own preflight |
| `socket?apikey=…` | `GET` (status `101`) | The realtime WebSocket upgrade; it stays open |

Browsers cache a preflight answer for a while, so you do not pay for it on every call to the same URL.
When the origin is not allowed, the preflight fails and the browser blocks the real request.
The client then sees a network failure, not a `403`, because the browser hides the response from JavaScript.
That is why a CORS problem appears in your code as `NetworkError` while the console shows a CORS message.

If you see `NetworkError` only in the browser and never from a server or `curl`, check **Access → Networking** for the page's origin before anything else.
See [rate limits and CORS](/reference/rate-limits-and-cors) for how origins are matched.
