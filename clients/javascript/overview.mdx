`@pawabase/client` is the official TypeScript client for Pawabase.
It runs in browsers, in Node, and in any runtime that has the standard `fetch` API.
It has no runtime dependencies.

This page is the map of the whole package.
It explains what a client object represents, what each part of it is for, which key you give it in which place, and what the package deliberately does not do.
The pages after it go deep on one part each.

<Info>
This section documents `@pawabase/client` 0.1.0 as it exists on the `feat/sdk-split` branch of the `Pawabase/pawabase-js` repository.
Every method named in this section exists in that source.
When a page says "the server does X", the behavior was observed against a running Pawabase stack, not inferred from the client.
</Info>

## The mental model

A Pawabase client is a typed HTTP client for **one environment of one project**, reached through **one gateway**, holding **one API key** and, optionally, **one signed-in user**.

Everything else follows from that sentence.

The client is not a database driver.
It does not open a connection to your database, it does not cache rows, and it does not run queries locally.
Every method that touches data sends an HTTP request to the gateway.
The gateway checks the key, and the service behind it checks the policies.
The answer you get back is exactly what the server decided this caller may see.

The client is also not an ORM.
Rows come back as plain objects with the field names your resource declares, in the server's `snake_case`.
There are no model classes, no change tracking, and no lazy relations.
When you want related records, you ask for them in the same request with `expand`.

What the client does add on top of plain `fetch` is the part that is tedious and easy to get wrong by hand:

| Concern | What the client does for you |
| --- | --- |
| Credentials | Sends the API key on every request and the user's access token when someone is signed in. |
| Sessions | Stores the session, refreshes it before it expires, and refreshes it only once at a time. |
| Queries | Builds the `filter[…]`, `sort`, `select`, `expand`, `page` and `per_page` parameters, and refuses queries the server would answer wrongly. |
| Failures | Turns every error body shape the platform produces into one error class hierarchy. |
| Retries | Retries rate limits and gateway failures with backoff, and only when repeating the request is safe. |
| Realtime | Keeps one WebSocket per client, reconnects, rejoins channels, and removes duplicate messages. |
| Types | Checks resource names, row fields and filter values against types generated from your project. |

If you keep this model in mind, most questions answer themselves.
"Why did a record I can see in Studio come back as a `404`?" is a policy question, because the client only reports what the server returned.
"Why is my list total `null`?" is a server question about per-row policies, and the client tells you so instead of guessing.
"Why can't I join two tables in one query?" is because the data API serves resources, and resources expose relations through `expand`, not through SQL.


## What the package contains

One install gives you the main client, two optional subpath modules for server-side administration, and a command-line type generator.

| Import | What it is | Who uses it |
| --- | --- | --- |
| `createClient` from `@pawabase/client` | The client: records, auth, storage, flows, routes, realtime | Every application |
| `manage` from `@pawabase/client/manage` | The management plane of an environment: resources, policies, flows, secrets, keys, firewall, backups and more | Servers, scripts and CI with a secret key |
| `admin` from `@pawabase/client/admin` | Administration of your application's users, roles and organizations | Servers and back-office tools with a secret key |

The two subpaths are separate entry points on purpose.
A browser bundle that imports only `@pawabase/client` never contains the management or user-administration code.
Those modules only work with a secret key, and a secret key must never reach a browser, so there is no reason for a bundler to ship them there.

The client object itself has these members:

| Member | Purpose | Page |
| --- | --- | --- |
| `from(name)` | Records of a resource, typed from your generated `Database` type | [Records and queries](/data/records/overview) |
| `resource<Row, Insert, Update>(name)` | Records of a resource, typed by hand | [Records and queries](/data/records/overview) |
| `auth` | Sign-up, sign-in, sessions, MFA, organizations, devices, personal API keys | [Authentication](/clients/typescript/authentication/overview) |
| `storage` | Buckets, uploads, downloads, signed URLs | [Storage](/storage/overview) |
| `flows` | Flows that have an HTTP trigger without a path | [Flows and routes](/clients/typescript/flows-and-routes/overview) |
| `routes` | Custom routes you defined under `/rest/v1` | [Flows and routes](/clients/typescript/flows-and-routes/overview) |
| `realtime` | Channels, presence, history, publishing | [Realtime](/realtime/overview) |
| `asUser(token)` | A client that acts as one user for one server-side request | [Servers and testing](/clients/typescript/server-runtimes-testing/overview) |
| `request(method, path, options)` | A raw request to any gateway path, with keys, retries and typed errors | [Client configuration](/clients/typescript/client-configuration/overview) |
| `status()` | The health of the services behind the gateway | [Client configuration](/clients/typescript/client-configuration/overview) |
| `dispose()` | Stops the refresh timer and closes the realtime connection | [Client configuration](/clients/typescript/client-configuration/overview) |
| `http` | The underlying transport, for advanced use | [Errors and retries](/clients/typescript/errors-retries/overview) |

<Note>
The client object also has a `functions` member.
Custom functions were removed from the Pawabase platform, so that member calls endpoints that no longer exist and is not documented here.
Server-side logic that used to live in a function belongs in a [flow](/flows/overview), a [custom route](/data/custom-routes/overview), or an extension route.
</Note>


## Installing

The package is named `@pawabase/client`.
It is built from source when installed from its Git repository, so you do not need a separate build step.

```bash
npm install github:Pawabase/pawabase-js
```

```bash
pnpm add github:Pawabase/pawabase-js
```

```bash
bun add github:Pawabase/pawabase-js
```

After installation, imports use the package name, not the repository name:

```typescript
import { createClient } from "@pawabase/client";
```

The package ships both ES modules and CommonJS, each with type declarations.
A `require("@pawabase/client")` in an older Node project and an `import` in a Vite project resolve to the same API.

### What the runtime must provide

The client relies on web-standard APIs and nothing else.

| API | Needed for | Where it exists |
| --- | --- | --- |
| `fetch`, `Request`, `Response`, `Headers` | Every HTTP call | Browsers, Node 18 and later, Deno, Bun, Cloudflare Workers, React Native |
| `AbortController` | Timeouts and cancellation | The same places |
| `WebSocket` | Live realtime channels only | Browsers, Node 22 and later, Deno, Bun; on Node 20 pass the `ws` package |
| `localStorage` | Keeping a browser session between page loads | Browsers; elsewhere the session is kept in memory unless you supply storage |
| `navigator.locks` (Web Locks) | Serializing token refresh across tabs | Modern browsers; elsewhere refresh is serialized inside one client |

The package declares Node 20 as its minimum.
On Node 20, everything except a live realtime socket works out of the box.
For realtime on Node 20 you pass a WebSocket implementation in the options, which the [realtime page](/realtime/overview) shows.

If your runtime has no global `fetch` at all, you pass one in the `fetch` option.
The same option is how you add instrumentation or a test double, so it is worth knowing even when your runtime has `fetch`.


## The three things a client needs

A client needs a gateway URL and an API key.
Most clients also want the environment name.

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";

export const pawabase = createClient({
  url: "https://api.example.com",
  apiKey: "pb_pk_live_…",
  environment: "production",
});
```

```python Python
from pawabase import Pawabase

pb = Pawabase(
    "https://api.example.com",
    "pb_pk_live_…",
    environment="production",
)
```

```bash cURL
# Every request carries the key; the environment is a header hint.
export PAWABASE_URL="https://api.example.com"
export PAWABASE_KEY="pb_pk_live_…"

curl "$PAWABASE_URL/v1/status" -H "apikey: $PAWABASE_KEY" -H "x-environment: production"
```
</CodeGroup>

### The gateway URL

The URL is the origin of your Pawabase gateway: the single public entry point in front of the data, auth, storage and realtime services.
It is the same for every environment of an installation.
The client appends service paths such as `/rest/v1`, `/auth/v1`, `/storage/v1` and `/realtime/v1` to it.

Give the origin only.
`https://api.example.com` is right.
`https://api.example.com/rest/v1` is wrong, because the client would then call `/rest/v1/rest/v1/…`.
A trailing slash is removed for you.

The client refuses a URL it cannot parse and a URL whose scheme is not `http:` or `https:`, by throwing `ConfigError` from `createClient`.
It does this at construction time, so a misconfigured deployment fails at startup, not on the first user action.

### The API key

The API key decides which project and environment a request belongs to, and with which ceiling of authority.
Pawabase has two kinds of project keys, and the difference matters more than anything else on this page.

| Key | Prefix | Where it may live | What it can do |
| --- | --- | --- | --- |
| Publishable | `pb_pk_…` | Browsers, mobile apps, anywhere | Acts as the anonymous role, or as the signed-in user. Every policy applies. |
| Secret | `pb_sk_…` | Servers, scripts and CI only | Bypasses every policy. Can use the management and user-administration modules. |

A publishable key is not a secret.
It identifies your environment and lets the gateway apply the environment's CORS origins and rate limits.
Everything it can reach is decided by policies, so publishing it in a web page is the intended use.

A secret key is a root credential for one environment.
Anyone who holds it can read and change every record and every setting of that environment.
The client protects you from the most common way of leaking one: when it detects a browser and a key that starts with `pb_sk_` (or the older `sk_`), `createClient` throws `ConfigError`.
The option `dangerouslyAllowBrowser: true` turns that check off.
There are very few legitimate reasons to use it, and they are all internal tools that never leave a trusted machine.

You create and copy keys in Studio under **Access → API keys**.
The **New API key** sheet asks for a **Name**, a **Key type**, optional **Permissions** (scopes), and **Limits** such as **Expires**, **Allowed IP ranges** and **Allowed routes**.
The full key is shown once, in the **Your new key** dialog, and never again.
See [API keys](/studio/api-keys) for scopes, rotation and revocation.

### The environment name

A key already belongs to exactly one environment, so data, auth, storage and realtime calls work without naming it.
The client still accepts an `environment` option, and you should pass it, because three features need the name itself rather than the key:

| Feature | Why it needs the environment name |
| --- | --- |
| Social sign-in | The provider authorization URL is `/auth/v1/authorize/<environment>/<provider>`. |
| Realtime | The socket URL carries the environment as a query parameter. |
| `manage()` and `admin()` | Management paths are `/platform/v1/envs/<environment>/…`. |

When you pass `environment`, the client also sends an `x-environment` header with every request.
When you pass `project`, it sends `x-project-id`.
The gateway treats these as hints; the key remains the authority on which environment you reach.


## How a request travels

Knowing the path of one request explains most error messages you will meet.

```text
your code
  │  pawabase.from("orders").eq("status", "open")
  ▼
@pawabase/client
  │  GET /rest/v1/orders?filter[status]=eq.open
  │  apikey: pb_pk_…              (always)
  │  authorization: Bearer <jwt>   (when a user is signed in)
  │  x-client-info: pawabase-js/0.1.0
  ▼
gateway
  │  key valid?            no  → 401 invalid_api_key
  │  origin allowed?       no  → 403 origin_not_allowed   (publishable keys)
  │  firewall rule?        yes → 403 or 429
  │  rate limit left?      no  → 429 rate_limit_exceeded
  │  scope allows route?   no  → 403
  ▼
data service
  │  body valid?           no  → 422 with a list of field issues
  │  policy allows?        no  → 401, 403 policy '…' refused, or 404
  ▼
database
  │
  ▼
JSON response → the client parses it → your code gets a plain object
```

Three things in that diagram matter for client code.

First, the gateway answers some failures before your resource is involved at all.
A `429` from the gateway means the request did nothing, which is why the client may safely repeat any `429`, even a `POST`.

Second, a request can fail validation before its policy runs.
An anonymous request with a malformed body gets `422`, not `401`.
Do not read a `422` as "this caller is allowed".

Third, a read policy that hides a record answers `404`, not `403`.
The server does not reveal that a record exists to someone who may not read it.
The client mirrors this: `get()` throws `NotFoundError`, and `maybeGet()` returns `null`, for both "does not exist" and "exists but hidden".
