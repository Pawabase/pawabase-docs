The program below uses most parts of the client together.
It signs a user in, lists their open orders, uploads a receipt, runs a flow, and listens for changes.

```typescript
import {
  createClient,
  NotFoundError,
  PermissionError,
  ValidationError,
} from "@pawabase/client";
import type { Database } from "./database";

const pawabase = createClient<Database>({
  url: "https://api.example.com",
  apiKey: "pb_pk_live_…",
  environment: "production",
});

async function main() {
  const signIn = await pawabase.auth.signInWithPassword({
    email: "ada@example.com",
    password: "correct horse battery staple",
  });

  if (signIn.status === "mfa_required") {
    await signIn.verify(await askForCode());
  }

  const user = await pawabase.auth.getUser();

  const openOrders = await pawabase
    .from("orders")
    .eq("status", "open")
    .order("created_at", "desc")
    .expand("customer")
    .perPage(10);

  console.log(`${user.email} has ${openOrders.total ?? "some"} open orders`);

  const first = openOrders.data[0];
  if (!first) return;

  const receipts = pawabase.storage.from("receipts");
  await receipts.upload(`${user.id}/${first.id}.pdf`, await loadPdf(), {
    contentType: "application/pdf",
  });

  try {
    const quote = await pawabase.flows.run<{ total_minor: number }>("quote-order", {
      order_id: first.id,
    });
    console.log("quote", quote.total_minor);
  } catch (error) {
    if (error instanceof ValidationError) console.error(error.byField());
    else if (error instanceof PermissionError) console.error("refused by", error.policy);
    else if (error instanceof NotFoundError) console.error("no such flow");
    else throw error;
  }

  const changes = pawabase.realtime.channel("resource:orders");
  changes.on("message", (message) => {
    console.log(message.event, message.payload);
  });
  await changes.subscribe();
}

declare function askForCode(): Promise<string>;
declare function loadPdf(): Promise<Blob>;

main().catch((error) => {
  console.error(error);
  pawabase.dispose();
});
```

## Security checklist for client code

The client makes the safe path the default, but some decisions are yours.

| Check | Why |
| --- | --- |
| Only `pb_pk_…` keys appear in browser and mobile code. | A secret key bypasses every policy. |
| Secret keys come from environment variables or a secret manager on servers. | Keys in source control end up in forks, logs and screenshots. |
| The environment's allowed CORS origins list your real web origins. | Publishable-key requests from other origins get `403 origin_not_allowed`. |
| Every resource operation the browser uses has a policy you have read. | The client sends whatever your code asks for; policies are the boundary. |
| Server-rendered pages use `asUser(token)` with a publishable key. | The visitor's policies then apply on the server too. |
| Secret-key clients are not exported from shared modules that browser code imports. | A bundler follows imports; one stray import can ship a secret. |
| Social sign-in uses a publishable key. | The key travels in the authorization URL; the client refuses to put a secret key there. |
| Signed URLs have short expiries. | Anyone holding the URL has its authority until it expires. |
| `dangerouslyAllowBrowser` is not set in application code. | It exists for trusted internal tools only. |

The [security model](/auth/security-model/overview) and [API keys](/studio/api-keys) pages explain the platform side of each item.


## Before the first production release

The security checklist protects data.
This one protects users from the failures that only appear under real traffic.

| Check | Why it matters in production |
| --- | --- |
| The production build reads the production key and environment name. | A development key in production sends real users to development data. |
| Error tracking records `requestId` for every `ApiError`. | Support can then find the failing request under **Project → Activity**. |
| Loading states wait for `INITIAL_SESSION`. | Signed-in users are not bounced to the sign-in page on reload. |
| Long lists use `pages()` or `all({ maxRecords })`, not unbounded loops. | A per-row policy can make `total` unknown, and a loop that trusts it never ends or ends early. |
| Writes that users can repeat rely on unique fields. | The server has no idempotency keys; a unique constraint turns a double submit into a `409`. |
| Realtime screens handle `closed` and resubscribe states. | Mobile networks drop sockets often; the UI should show it. |
| `dispose()` runs where clients are created dynamically. | Leaked timers and sockets accumulate in long-running processes. |

Run the smoke test from [Checking a new configuration](/clients/javascript/checking-a-new-configuration#checking-a-new-configuration) against production after every deploy.
It takes seconds and catches a wrong key or a missing origin before your users do.


## Troubleshooting the first connection

Most first-connection problems come from the URL, the key or the browser origin.
The client's errors are specific enough to tell them apart.

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| `ConfigError: createClient needs the gateway url.` | The URL environment variable is empty in this build. | Check how your bundler exposes environment variables (`import.meta.env`, `process.env`, a public prefix). |
| `ConfigError: … is not a valid URL.` | The URL has no scheme, or contains spaces. | Use the full origin, such as `https://api.example.com`. |
| `ConfigError: A secret key (pb_sk_…) must never run in a browser` | A secret key reached browser code. | Use a publishable key in the browser; keep the secret key on the server. |
| `NetworkError: Could not reach https://…` | DNS, TLS, or the gateway is down; or a browser blocked the request. | Open the gateway URL in a browser; check the console for a CORS message. |
| `AuthenticationError` with code `invalid_api_key` | The key is wrong, revoked or expired, or belongs to another installation. | Copy the key again from **Access → API keys**. |
| `PermissionError` with code `origin_not_allowed` | The page's origin is not in the environment's CORS list. | Add the origin under **Access → Networking**. |
| `NotFoundError` on a list | The resource name is wrong, or the `list` operation is disabled. | Check the name and operations under **Data**; compare with the API Explorer. |
| `RateLimitError` during development | A loop is calling faster than the limit allows. | Read `retryAfter`; the client already waited and retried before throwing. |
| `TimeoutError` | A request ran longer than `timeoutMs` (30 seconds by default). | Find the slow request by id under **Project → Activity**; raise the timeout only if the work is legitimately long. |

When none of these fit, call `pawabase.status()`.
It asks the gateway for the health of the services behind it without needing a valid user, and it tells you whether the problem is your code or the installation.

<CodeGroup>
```typescript TypeScript
const health = await pawabase.status();
console.log(health.ok, health.services);
```

```python Python
health = pb.status()   # the Python client asks GET /health/v1
```

```bash cURL
curl "$PAWABASE_URL/v1/status" -H "apikey: $PAWABASE_KEY"
```
</CodeGroup>


## The same call without the client

It helps to see what the client saves you from by writing one call by hand.
The query below lists a signed-in user's open orders, newest first, with the customer embedded.

```typescript
const page = await pawabase
  .from("orders")
  .eq("status", "open")
  .order("created_at", "desc")
  .expand("customer")
  .perPage(20);
```

The equivalent with plain `fetch` looks like this:

<CodeGroup>
```typescript TypeScript
async function listOpenOrders(session: { access_token: string } | null) {
  const params = new URLSearchParams({
    "filter[status]": "eq.open",
    sort: "-created_at",
    expand: "customer",
    per_page: "20",
  });
  const response = await fetch(`https://api.example.com/rest/v1/orders?${params}`, {
    headers: {
      apikey: "pb_pk_live_…",
      accept: "application/json",
      ...(session ? { authorization: `Bearer ${session.access_token}` } : {}),
    },
  });
  if (!response.ok) {
    const text = await response.text();
    throw new Error(`HTTP ${response.status}: ${text}`);
  }
  return response.json();
}
```

```python Python
import httpx

def list_open_orders(access_token: str | None) -> dict:
    headers = {"apikey": "pb_pk_live_…", "accept": "application/json"}
    if access_token:
        headers["Authorization"] = f"Bearer {access_token}"
    response = httpx.get(
        "https://api.example.com/rest/v1/orders",
        params={"filter[status]": "eq.open", "sort": "-created_at", "expand": "customer", "per_page": "20"},
        headers=headers,
    )
    response.raise_for_status()
    return response.json()
```

```bash cURL
curl -G "https://api.example.com/rest/v1/orders" \
  -H "apikey: pb_pk_live_…" -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "filter[status]=eq.open" --data-urlencode "sort=-created_at" \
  --data-urlencode "expand=customer" --data-urlencode "per_page=20"
```
</CodeGroup>

The hand-written version works, and the [REST conventions](/reference/rest-conventions) page documents every parameter it uses.
What it leaves out is everything around the request:

| Concern | Hand-written `fetch` | `@pawabase/client` |
| --- | --- | --- |
| An expired access token | `401`; your code must refresh and repeat | Refreshed before sending, or after one `401`, once |
| Two components refreshing at once | Both refresh; the second reuse ends the session | One shared refresh |
| A `429` from the gateway | An exception, or a retry loop you write | Waits for `Retry-After` and repeats |
| A `503` during a deploy | An exception | Retried with backoff for safe methods |
| The error body | One of several shapes; you parse it | One class hierarchy with `status`, `code`, `requestId` |
| `eq.false` on a boolean | Silently matches the wrong rows | Sent as `is.false` |
| A second filter on `status` | The first is dropped silently | `InvalidQueryError` before sending |
| A typo in a field name | Found at runtime, if at all | A compile error with an application-defined `Database` interface |

Use raw `fetch` when you want to see the protocol, or when a tiny script does not justify a dependency.
Use the client when correctness under concurrency, expiry and failure matters, which is most applications.
