You will run the same code against at least two environments, usually `development` and `production`, and often short-lived previews.
The URL is normally the same for all of them; the key and the environment name change.

The safest arrangement is to read all three from configuration and never write a key in source code.
Each framework exposes configuration to browser code differently, and only variables with the framework's public prefix reach the bundle.

| Framework | Browser-visible variable names | Server-only variable names | Notes |
| --- | --- | --- | --- |
| Vite (React, Vue, Svelte) | `VITE_PAWABASE_URL`, `VITE_PAWABASE_KEY`, `VITE_PAWABASE_ENV` | Any name without `VITE_` | Read with `import.meta.env`. |
| Next.js | `NEXT_PUBLIC_PAWABASE_URL`, `NEXT_PUBLIC_PAWABASE_KEY` | `PAWABASE_SECRET_KEY` | Read with `process.env`; public values are inlined at build time. |
| SvelteKit | `PUBLIC_PAWABASE_URL`, `PUBLIC_PAWABASE_KEY` | `PAWABASE_SECRET_KEY` | Import from `$env/static/public` or `$env/static/private`. |
| Remix and React Router | Pass values from a loader to the page | `process.env.*` on the server | There is no build-time public prefix; you choose what to send. |
| Expo | `EXPO_PUBLIC_PAWABASE_URL`, `EXPO_PUBLIC_PAWABASE_KEY` | Not applicable | Everything in an app binary is public. |
| Node, Bun, Deno | Not applicable | `PAWABASE_URL`, `PAWABASE_SECRET_KEY`, `PAWABASE_ENV` | Read from `process.env`, `Bun.env` or `Deno.env`. |
| Cloudflare Workers | Not applicable | Bindings declared in `wrangler.toml` and secrets | Read from the `env` argument of the handler. |

A publishable key in a browser-visible variable is fine.
A secret key in a browser-visible variable is a leak, even if no code reads it, because the bundler inlines it.
Name secret keys without the public prefix so that the framework itself refuses to expose them.

A small configuration module keeps the rest of the code free of environment details:

```typescript
// src/lib/pawabase.ts (Vite)
import { createClient } from "@pawabase/client";
import type { Database } from "./database";

const url = import.meta.env.VITE_PAWABASE_URL;
const apiKey = import.meta.env.VITE_PAWABASE_KEY;
const environment = import.meta.env.VITE_PAWABASE_ENV ?? "development";

if (!url || !apiKey) {
  throw new Error("VITE_PAWABASE_URL and VITE_PAWABASE_KEY must be set for this build.");
}

export const pawabase = createClient<Database>({ url, apiKey, environment });
```

```typescript
// lib/pawabase-server.ts (Next.js, server-only)
import "server-only";
import { createClient } from "@pawabase/client";
import type { Database } from "./database";

export const pawabaseService = createClient<Database>({
  url: process.env.PAWABASE_URL!,
  apiKey: process.env.PAWABASE_SECRET_KEY!,
  environment: process.env.PAWABASE_ENV ?? "production",
});
```

```typescript
// worker.ts (Cloudflare Workers)
import { createClient } from "@pawabase/client";

interface Env {
  PAWABASE_URL: string;
  PAWABASE_SECRET_KEY: string;
  PAWABASE_ENV: string;
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const pawabase = createClient({
      url: env.PAWABASE_URL,
      apiKey: env.PAWABASE_SECRET_KEY,
      environment: env.PAWABASE_ENV,
    });
    const open = await pawabase.from("orders").eq("status", "open").count();
    return Response.json({ open });
  },
};
```

The `server-only` import in the Next.js module makes the build fail if a client component imports it.
That is the cheapest protection against shipping a secret-key client to the browser.

Preview environments created for a branch or pull request have their own keys.
A preview's name is what you pass as `environment`.
See [environments and promotion](/studio/environments-and-promotion) for how previews are created and removed.


## Four application shapes

Most TypeScript applications built on Pawabase take one of four shapes.
Each one uses the client a little differently, and choosing the shape early avoids rewriting authentication later.

### A browser application talking to Pawabase directly

```text
browser ──(pb_pk_ + user token)──▶ gateway ──▶ Pawabase services
```

The browser holds a publishable key and the user's session.
Policies are the only access control, and they are enough when every rule can be written as a condition on the user, their roles, their organization, or the record.

This is the shortest path to a working product.
It is the right shape for dashboards, internal tools, and consumer apps whose rules are about ownership and membership.

```typescript
import { pawabase } from "./lib/pawabase";

export async function loadMyProjects() {
  const user = await pawabase.auth.getCachedUser();
  if (!user) return [];
  return pawabase.from("projects").eq("owner_id", user.id).order("updated_at", "desc").all();
}
```

The policy on `projects.list` should restrict rows to the owner, for example with the `owner` shorthand.
The `eq("owner_id", …)` filter in the code is for the UI, not for security; a different user who removes it still sees only their own rows.

### A server-rendered application

```text
browser ──cookie──▶ your server ──(pb_pk_ + user token)──▶ gateway
```

The server renders pages and holds the user's tokens in an HTTP-only cookie.
It uses a publishable key and `asUser(token)` per request, so the same policies apply on the server.

This shape keeps tokens out of browser JavaScript and lets you render authenticated pages on the first response.
It is the natural shape for Next.js, Remix, SvelteKit and Nuxt applications.

```typescript
import { cookies } from "next/headers";
import { createClient } from "@pawabase/client";

const base = createClient({
  url: process.env.PAWABASE_URL!,
  apiKey: process.env.PAWABASE_PUBLISHABLE_KEY!,
  environment: process.env.PAWABASE_ENV,
});

export async function ordersPage() {
  const token = (await cookies()).get("pb-access")?.value ?? null;
  const pawabase = token ? base.asUser(token) : base;
  return pawabase.from("orders").order("created_at", "desc").perPage(20);
}
```

Refreshing tokens is your server's job in this shape, because the client created by `asUser` keeps no session.
The [servers and testing page](/clients/typescript/server-runtimes-testing/overview) shows a refresh handler.

### A mobile application

```text
app ──(pb_pk_ + user token)──▶ gateway
```

A mobile app is a browser application with different storage.
It holds a publishable key, and its session must survive the app being killed.
You give the client a storage adapter backed by the platform's secure storage.

```typescript
import * as SecureStore from "expo-secure-store";
import { createClient } from "@pawabase/client";

export const pawabase = createClient({
  url: process.env.EXPO_PUBLIC_PAWABASE_URL!,
  apiKey: process.env.EXPO_PUBLIC_PAWABASE_KEY!,
  environment: process.env.EXPO_PUBLIC_PAWABASE_ENV,
  auth: {
    storage: {
      getItem: (key) => SecureStore.getItemAsync(key),
      setItem: (key, value) => SecureStore.setItemAsync(key, value),
      removeItem: (key) => SecureStore.deleteItemAsync(key),
    },
    detectSessionInUrl: false,
  },
});
```

Social sign-in on mobile returns through a deep link.
Your deep-link handler passes the URL to `auth.getSessionFromUrl(url)`, which reads the tokens from its fragment.
The [mobile guide](/clients/mobile) covers platform details.

### A worker or integration with no user

```text
cron, queue consumer or webhook receiver ──(pb_sk_)──▶ gateway
```

A process that acts on its own behalf holds a secret key.
There is no session and no policy evaluation.
This shape fits nightly jobs, data imports, synchronization with another system, and receivers for third-party webhooks.

```typescript
import { createClient } from "@pawabase/client";

const pawabase = createClient({
  url: process.env.PAWABASE_URL!,
  apiKey: process.env.PAWABASE_SECRET_KEY!,
  environment: "production",
});

export async function closeStaleCarts(now = new Date()) {
  const cutoff = new Date(now.getTime() - 24 * 3600 * 1000);
  const stale = await pawabase.from("carts").eq("status", "open").lt("updated_at", cutoff).all({ maxRecords: 5000 });
  const results = await Promise.allSettled(stale.map((cart) => pawabase.from("carts").update(cart.id, { status: "abandoned" })));
  return results.filter((result) => result.status === "rejected").length;
}
```

Much of what workers used to do can now be a [flow](/flows/overview) with a [schedule](/jobs/schedules) instead, which runs inside Pawabase and appears in **Project → Activity** with its run history.
A worker is the better choice when the logic depends on libraries or services that a flow block cannot reach.


## The life of a browser session

A browser session goes through the same stages every time.
Knowing them helps you place loading states and redirects correctly.

```text
page load
  │  createClient(): reads the stored session from localStorage (async)
  │  if the URL fragment has #access_token=… (a social sign-in returning):
  │      store that session, clean the URL
  ▼
onAuthStateChange listeners receive INITIAL_SESSION (session or null)
  │
  ├─ signed out ──▶ sign-in form ──▶ signInWithPassword() ──▶ SIGNED_IN
  │
  └─ signed in
       │  a timer refreshes the access token ~60 s before it expires ──▶ TOKEN_REFRESHED
       │  another tab refreshes first ──▶ this tab adopts its tokens ──▶ TOKEN_REFRESHED
       │  a request gets 401 ──▶ one refresh, one replay
       │  updateUser() ──▶ USER_UPDATED
       │  the refresh token is refused (revoked, reused) ──▶ SIGNED_OUT
       ▼
signOut() ──▶ SIGNED_OUT (also in other tabs)
```

The stored session is read asynchronously, because some storage adapters are asynchronous.
Until it has been read, the client does not know whether anyone is signed in.
Show a neutral loading state until the first `INITIAL_SESSION` event, rather than flashing the sign-in form.

```typescript
pawabase.auth.onAuthStateChange((event, session) => {
  if (event === "INITIAL_SESSION") setReady(true);
  setUser(session?.user ?? null);
});
```

Every data method waits for the stored session to be read before sending.
A request made during page load therefore carries the user's token when there is one, without extra code.

Access tokens live 15 minutes by default.
The refresh timer is unreferenced on Node, so a script that forgets to call `dispose()` still exits, but tests should still dispose clients to avoid timers firing between tests.
