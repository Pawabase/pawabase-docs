The single most important decision in a Pawabase client is which key it holds.
The table below is the decision for the places TypeScript usually runs.

| Where the code runs | Key | User identity | Why |
| --- | --- | --- | --- |
| A browser single-page app | Publishable | The signed-in user's session | Anyone can read browser code, so the key must be one that policies constrain. |
| A React Native or Capacitor app | Publishable | The user's session, stored with the platform's secure storage | Same reason; app binaries are readable. |
| A server-rendered page (Next.js, Remix, SvelteKit) | Publishable | The user's token, per request, through `asUser` | The page acts for the visitor, so the visitor's policies must apply. |
| An API server acting for a user | Publishable | The user's token, per request | Same as above; the server is a proxy for one person. |
| A background worker, cron job or webhook receiver | Secret | None | No person is involved; the job needs full access to do its work. |
| A CI pipeline or migration script | Secret | None | It changes definitions and data across the environment. |
| A back-office tool for staff | Secret, server-side only | Staff identity checked by your own server | Staff need more than end-user policies allow, but the key stays on the server. |

Two patterns follow from this table.

A server that renders pages for users should hold a **publishable** key, not a secret one.
It is tempting to use a secret key "because it is a server", but then every policy is bypassed and the server must re-implement access control by hand.
Using the user's token with a publishable key lets the same policies that protect your browser app protect your server.

A server that does privileged work for users, such as issuing a refund that users cannot do themselves, should hold **two** clients: a publishable one for acting as the user, and a secret one for the privileged step after your own check.
This keeps the privileged surface small and visible in code review.


## How many clients to create

A client holds a session, a refresh timer and possibly a WebSocket.
Creating one per request or per component throws away that state and wastes connections.

| Context | How many clients | Notes |
| --- | --- | --- |
| Browser app | One, created at module load and imported where needed | The session is shared across the app and across tabs. |
| React app | The same single client, provided through context if you prefer | Do not create a client inside a component body; it would be recreated on each render. |
| Node server acting for users | One base client for the process, plus `asUser(token)` per request | `asUser` returns a lightweight client with no stored session and no timers. |
| Node worker with a secret key | One for the process | There is no session to refresh. |
| Tests | One per test, disposed after | Call `dispose()` so timers and sockets do not keep the test runner alive. |
| Hot module reload in development | Dispose the previous client before creating a new one | Otherwise you accumulate refresh timers. |

A browser client created at module scope looks like this:

```typescript
// src/lib/pawabase.ts
import { createClient } from "@pawabase/client";
import type { Database } from "./database";

export const pawabase = createClient<Database>({
  url: import.meta.env.VITE_PAWABASE_URL,
  apiKey: import.meta.env.VITE_PAWABASE_KEY,
  environment: import.meta.env.VITE_PAWABASE_ENV,
});
```

A server that acts for each request's user looks like this:

<CodeGroup>
```typescript TypeScript
// server/pawabase.ts
import { createClient } from "@pawabase/client";
import type { Database } from "./database";

const base = createClient<Database>({
  url: process.env.PAWABASE_URL!,
  apiKey: process.env.PAWABASE_PUBLISHABLE_KEY!,
  environment: process.env.PAWABASE_ENV,
});

export function pawabaseFor(accessToken: string | null) {
  return accessToken ? base.asUser(accessToken) : base;
}
```

```python Python
# server/pawabase.py
import os

from pawabase import AsyncPawabase

base = AsyncPawabase(os.environ["PAWABASE_URL"], os.environ["PAWABASE_PUBLISHABLE_KEY"], environment=os.environ["PAWABASE_ENV"])


def pawabase_for(access_token: str | None):
    return base.as_user(access_token) if access_token else base
```

```bash cURL
# On the wire, acting as a person is the person's token beside the publishable key:
curl "$PAWABASE_URL/rest/v1/orders" -H "apikey: $PAWABASE_PUBLISHABLE_KEY" -H "Authorization: Bearer $ACCESS_TOKEN"
```
</CodeGroup>

## What comes back from a call

The client returns what the server sends, parsed from JSON, with as little reshaping as possible.
This is a deliberate design choice: the field names you see in Studio, in the API Explorer and in the docs are the names you read in code.

| Call | Returns |
| --- | --- |
| A list query (`await query`) | `{ data, page, per_page, total }` |
| `first()` | The first row, or `null` |
| `single()` | The first row, or throws `NotFoundError` |
| `get(id)` | The row |
| `create(row)` | The created row, including server-assigned fields |
| `update(id, patch)` | The updated row |
| `delete(id)` | `undefined` |
| `auth.getUser()` | A `User` object with `snake_case` fields such as `email_verified` and `user_metadata` |
| `storage.from(b).upload(...)` | `{ bucket, key, size, content_type, etag? }` |
| `flows.run(name)` | The flow's response body |
| `manage()` and `admin()` methods | The management plane's JSON document; lists are `{ data: [...] }` |

The client does not wrap results in a `{ data, error }` envelope.
A failed call throws.
This keeps the success path free of checks and puts the failure path in a `catch` where TypeScript can narrow error classes.

Dates arrive as ISO 8601 strings, as the server sends them.
The client does not convert them to `Date` objects, because a string survives JSON serialization, server-side rendering and caching unchanged.
Convert at the edge of your UI when you need a `Date`.


## Where things live in Studio

The client mirrors concepts you configure in Studio.
When a call behaves unexpectedly, the answer is usually on one of these Studio pages.

| You are working with | Studio location | What to check there |
| --- | --- | --- |
| Resources and their fields | **Data** | Which operations are enabled, field types, required fields, defaults, relations |
| The exact request and response shapes | **Data → API Explorer** | The compiled routes, parameters and example bodies for this environment |
| Policies | **Access → Policies** | The condition that decides who may read or write |
| Keys | **Access → API keys** | Key type, scopes, expiry, allowed IP ranges and routes |
| Users, roles and organizations | **Access → Users & auth** | Tabs **Users**, **Roles**, **Organizations**, **Sign-in activity**, **Configuration** |
| CORS origins and firewall | **Access → Networking** | Allowed origins for publishable keys, firewall rules, bans |
| Flows | **Logic → Flows** | The flow graph, its HTTP trigger and the policy on that trigger |
| Custom routes | **Logic → Routes** | Method, path and the flow that handles the route |
| Buckets | **Services → Storage** | Bucket policies, accepted types, size limits, objects |
| Channels | **Services → Realtime** | Channel rules for subscribe, publish and presence |
| What happened to a request | **Project → Activity** | Requests by id, logs, errors, jobs and events |

Every `ApiError` carries `requestId`, the gateway's `x-request-id`.
Search for it under **Project → Activity** to see the request's logs, its database calls and, for a server error, the traceback.
This is the fastest way to turn "the client threw" into "this policy refused" or "this flow failed at this block".


## What the SDK does not do

Some features people expect from a backend client are not part of this one.
Knowing them up front saves design time.

| You might expect | What to do instead |
| --- | --- |
| Joins or arbitrary SQL from the browser | Declare relations on the resource and use `expand`; for computed results, write a [custom route](/data/custom-routes/overview) backed by a flow. |
| Two bounds on one field in one list query (`gte` and `lte` on `created_at`) | Filter one bound on the server and the other in code, store a period field, or add a route. The client refuses the two-filter form because the server would silently drop one. |
| Transactions across several requests | Put the multi-step write in a flow or route, where it runs as one server-side operation. |
| Idempotency keys | The server does not support them. Use natural unique fields so a repeated create fails with `409` instead of duplicating. |
| An offline cache or optimistic updates | Use your UI framework's data layer (TanStack Query, SWR, Apollo-style caches) on top of the client. |
| Custom functions | Removed from the platform. Use flows, custom routes, or extension routes. |
| Automatic retries of every failure | Only safe repeats are retried. A `POST` that failed with a network error is not repeated unless you mark it idempotent. |


## Coming from supabase-js

Many developers arrive from Supabase.
The shapes are close enough to feel familiar and different enough to cause bugs if you translate by habit.

| supabase-js | @pawabase/client | The difference that matters |
| --- | --- | --- |
| `createClient(url, anonKey)` | `createClient({ url, apiKey })` | Options object. The key is `pb_pk_…`, not a JWT. |
| `const { data, error } = await …` | `const data = await …` in `try`/`catch` | Errors are thrown as classes. |
| `.from("t").select("*")` | `.from("t")` then `await` | Selecting all columns is the default. |
| `.select("id, author(name)")` | `.select("id").expand("author")` | Relations are named, not embedded in a select string. |
| `.range(0, 9)` | `.page(1).perPage(10)` | Pages are numbered from 1; at most 200 rows per page. |
| `.eq("done", false)` | `.eq("done", false)` | Same call; the client sends `is.false` because `eq.false` misbehaves on the server. |
| `.gte("d", a).lte("d", b)` | Not allowed | One filter per field; the client throws instead of dropping a bound. |
| `.single()` | `.single()` | Throws `NotFoundError` when there is no row. |
| `{ count: "exact" }` | `.count()` | Throws when a per-row policy makes the count unknowable. |
| `supabase.auth.signInWithPassword` | `pawabase.auth.signInWithPassword` | Returns `{ status }`, which may be `mfa_required`. |
| `supabase.functions.invoke` | `pawabase.flows.run` or `pawabase.routes.post` | Server logic lives in flows and routes. |
| `supabase.channel("x").on("broadcast", …)` | `pawabase.realtime.channel("x").on("message", …)` | Channel access is decided by channel rules configured in Studio. |
| Row Level Security | Policies | Policies are named, reusable conditions attached to operations, not SQL. |

The Supabase comparison and the migration guide go further.


## Versions and compatibility

The package exports its version as `VERSION`, and sends it on every request in the `x-client-info` header as `pawabase-js/<version>`.
That header appears in request logs under **Project → Activity**, so you can tell which client version made a request.

<CodeGroup>
```typescript TypeScript
import { VERSION } from "@pawabase/client";

console.log(VERSION); // "0.1.0"
```

```python Python
import pawabase

print(pawabase.__version__)  # "0.3.0"
```

```bash cURL
# Each client names itself on every request:
#   x-client-info: pawabase-js/0.1.0      (TypeScript)
#   user-agent: pawabase-python/0.3       (Python)
```
</CodeGroup>

The client talks to the gateway's versioned paths (`/rest/v1`, `/auth/v1`, `/storage/v1`, `/realtime/v1`, `/flows/v1`, `/platform/v1`).
When your environment publishes a new [API version](/studio/environments-and-promotion) of its resource definitions, the paths a client uses stay the same; what changes is which release of your definitions answers.

Pin the dependency to a commit or tag in production.
Installing from a Git branch takes whatever is on the branch at install time, and a lockfile is what keeps two installs identical.
