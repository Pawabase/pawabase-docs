The types below are exported from the package.
They keep the wire's `snake_case` field names.

### A page of records

| Field | Type | Meaning |
| --- | --- | --- |
| `data` | `Row[]` | The rows on this page |
| `page` | `number` | The page number, starting at 1 |
| `per_page` | `number` | Rows per page; 20 unless you asked for another size (1 to 200) |
| `total` | `number \| null` | Rows matching for this caller; `null` when a per-row policy makes it unknowable |

When `total` is `null`, a page can hold fewer rows than `per_page`, or none, and still have more rows after it.
Iteration helpers account for this; code that computes "last page" from `total` must not.

### A user

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | `string` | The user's id |
| `email` | `string` | The primary email address |
| `username` | `string` | The username, if the environment uses them |
| `name` | `string` | The display name |
| `avatar_url` | `string \| null` | A profile image URL |
| `email_verified` | `boolean` | Whether the address was confirmed |
| `user_metadata` | `object` | Profile data the user may edit; never base access on it |
| `app_metadata` | `object` | Data only the application can edit, with a secret key or in Studio |
| `roles` | `string[]` | The user's roles in the environment |
| `mfa_enabled` | `boolean` | Whether a second factor is set up |
| `identities` | `Identity[]` | Linked sign-in providers |
| `created_at`, `last_sign_in_at` | `string \| null` | ISO timestamps |
| `aal`, `session_id` | `string \| null` | Present on `getUser()`: the current session's assurance level and id |

### A session

| Field | Type | Meaning |
| --- | --- | --- |
| `access_token` | `string` | The bearer token sent with requests |
| `refresh_token` | `string` | Single-use; exchanged for a new pair |
| `token_type` | `"bearer"` | Always bearer |
| `expires_in` | `number` | Seconds the access token was issued for |
| `expires_at` | `number` | Unix time in seconds when the access token expires |
| `session_id` | `string` | The session's id, when the server sent one |
| `org`, `org_role` | `string \| null` | The organization the token was issued for, and the user's role in it |
| `user` | `User` | The user as of the last sign-in, refresh or `getUser()` |

### A stored object and a signed URL

| Shape | Fields |
| --- | --- |
| `StoredObject` | `bucket`, `key`, `size`, `content_type`, `etag` (optional) |
| `FileListing` | `files` (each `key`, `size`, `content_type`, `modified`), `prefixes`, `cursor` |
| `SignedUrl` | `url`, `expires_at` (Unix seconds), `method` (`GET` or `PUT`) |
| `StorageBucket` | `name`, `public`, `accepts`, `max_bytes` |

### A realtime message and a presence member

| Shape | Fields |
| --- | --- |
| `ChannelMessage` | `type` (`"message"`), `id`, `channel`, `event`, `payload`, `from` (a user id, or `"server"`), `sent_at`, `seq` (history only) |
| `PresenceMember` | `presence_ref`, `user_id`, `meta`, `online_at` |


## How the client treats time

Session expiry is a comparison between a timestamp and the device's clock, and device clocks are sometimes wrong.
The client is built so that a wrong clock costs a little efficiency, not a broken session.

| Situation | What happens |
| --- | --- |
| The server sends `expires_at` | The client keeps it as given. |
| The server sends only `expires_in` | The client computes `expires_at` from its own clock at the moment it received the tokens. |
| A session is adopted with `setSession()` | `expires_at` is read from the access token's `exp` claim. |
| The token is within 60 seconds of `expires_at` | It counts as expiring; the next request refreshes first. The margin is the `refreshMarginSeconds` option. |
| The device clock is ahead | Tokens look expired early; the client refreshes more often than necessary. |
| The device clock is behind | Tokens look valid after they expired; the server answers `401`, and the client refreshes once and repeats the request. |

The `401` replay is what makes a slow clock harmless.
It is also why you should not catch `401` errors and sign the user out yourself: by the time your code sees an `AuthenticationError`, the client has already tried a refresh and failed.

Timestamps in rows are a separate matter.
The server writes `created_at` and `updated_at` with its own clock, in UTC.
Compare them with other server timestamps, not with `Date.now()` on a device, when the difference matters.


## What each import adds to a bundle

Bundlers include the modules your code imports and the modules those import.
The client is organized so that a browser application pays only for what it uses.

| Import | Contains | Typical environment |
| --- | --- | --- |
| `@pawabase/client` | The client, records, auth, storage, flows, routes, realtime, errors and the type generator | Browser and server |
| `@pawabase/client/manage` | Thirty-one management services | Server only |
| `@pawabase/client/admin` | Eight user-administration services | Server only |

Type-only imports add nothing to a bundle.
An `import type { Database } from "./database"` is erased at compile time.

If you see management code in a browser bundle analysis, some shared module imports `@pawabase/client/manage`.
Move that import into a server-only file.


## Several environments in one process

Most processes talk to one environment.
Tools that compare or copy between environments, such as a promotion script or a data-sync job, need clients for several at once.

Each environment has its own keys, so each needs its own client:

```typescript
import { createClient } from "@pawabase/client";

const staging = createClient({
  url: process.env.PAWABASE_URL!,
  apiKey: process.env.PAWABASE_STAGING_SECRET!,
  environment: "staging",
});

const production = createClient({
  url: process.env.PAWABASE_URL!,
  apiKey: process.env.PAWABASE_PRODUCTION_SECRET!,
  environment: "production",
});

const [stagingPlans, productionPlans] = await Promise.all([
  staging.from("plans").all(),
  production.from("plans").all(),
]);

const missing = stagingPlans.filter((plan) => !productionPlans.some((p) => p.code === plan.code));
console.log("plans in staging but not production:", missing.map((plan) => plan.code));
```

The management module is the exception.
`manage(client, "staging")` and `admin(client, "staging")` address another environment through the same key, which works when that key is allowed to manage the other environment.
For copying definitions between environments, prefer the platform's own promotion, described on [environments and promotion](/studio/environments-and-promotion), over writing your own copy loop.


## Upgrading the client

The client is installed from Git, so an upgrade is a change to the commit your lockfile records.

```bash
npm install github:Pawabase/pawabase-js#<commit-or-tag>
```

Read the changes between the two commits before upgrading a production application.
Pay attention to three kinds of change: renamed methods, changes to what a method returns, and changes to retry behavior.
Your compiler finds the first two when your application defines its resource types and strict mode is on.
The third shows up only at runtime, so it deserves a test against a development environment.

A newer client can rely on type shapes that an older generated file does not have.


## Questions developers ask

<AccordionGroup>
  <Accordion title="Can I use the client without TypeScript?">
    Yes.
    The package is plain JavaScript with type declarations alongside.
    In a JavaScript project you lose compile-time checks, and everything else behaves the same.
  </Accordion>
  <Accordion title="Does the client work in a service worker or a web worker?">
    It needs `fetch` and, for realtime, `WebSocket`, both of which workers have.
    Workers have no `localStorage`, so the default session store there is memory.
    Pass an IndexedDB-backed storage adapter if a worker must keep a session.
  </Accordion>
  <Accordion title="Why does my list return 401 when no one is signed in?">
    The default policy for resource operations is `authenticated`.
    A publishable key alone is anonymous.
    Open the resource under **Data**, choose the operation, and give it a policy that admits anonymous callers, such as `public`, if that is what you intend.
  </Accordion>
  <Accordion title="Why do I get 404 for a record that exists?">
    A read policy that refuses a caller answers `404` so that it does not reveal the record exists.
    Check the `get` operation's policy for the identity you are using.
    The API Explorer under **Data → API Explorer** can send the request as a chosen user.
  </Accordion>
  <Accordion title="Can two clients share one session?">
    Two clients in the same browser that use the same URL and key share the stored session, because the storage key is derived from both.
    They do not share an in-memory refresh lock, so prefer one client per app.
  </Accordion>
  <Accordion title="Is it safe to call the client during server-side rendering and again in the browser?">
    Yes, if each side creates its own client.
    The server should use `asUser(token)` from the request's cookie; the browser client reads its own session.
    Do not serialize a client object into page props.
  </Accordion>
  <Accordion title="How do I call an endpoint the client has no method for?">
    Use `pawabase.request(method, path, { body, query })`.
    It sends the key and the user's token, applies the retry policy, and throws the same typed errors as every other method.
  </Accordion>
  <Accordion title="Can I cancel a request when a component unmounts?">
    Yes.
    Queries accept a signal through `withOptions({ signal })`, and most other methods accept `signal` in their options.
    An aborted request rejects with `AbortError`, which you can ignore in the unmount path.
  </Accordion>
  <Accordion title="Does the client batch or deduplicate identical requests?">
    No.
    Two identical queries made at the same time send two requests.
    Put a cache such as TanStack Query in front of the client if many components read the same data.
  </Accordion>
  <Accordion title="What happens to a request made while the user is signing out?">
    It carries whichever token the client had when it was sent.
    If that token has been revoked, the server answers `401`; the refresh attempt then fails, the session is cleared, and the request throws `AuthenticationError`.
  </Accordion>
  <Accordion title="Can I point the client at a local Pawabase stack?">
    Yes.
    Use the local gateway's origin, such as `http://localhost:8080`, with a key from that stack's development environment.
    Plain `http:` is accepted for exactly this case.
  </Accordion>
  <Accordion title="Is the client safe to use from several async tasks at once?">
    Yes.
    Requests are independent, refreshes are shared, and query builders are immutable values.
    The one shared piece of state is the session, which only the auth methods change.
  </Accordion>
  <Accordion title="Why does `select()` still return columns I did not ask for?">
    The server returns every declared column and sets the unselected ones to `null`.
    The client types the result so that unselected columns are optional, which keeps the compiler honest about it.
  </Accordion>
  <Accordion title="How do I see what the client sent?">
    Pass `hooks.onRequest` and `hooks.onResponse` when creating the client.
    The hooks receive the method, URL, attempt number, status and request id, with the key and token masked.
  </Accordion>
</AccordionGroup>


## Words used in this section

| Term | Meaning in these pages |
| --- | --- |
| Gateway | The public entry point of a Pawabase installation; every client request goes to it. |
| Environment | One isolated copy of a project's definitions, data, users and keys, such as `development` or `production`. |
| Resource | A table your API serves, with fields, operations and policies. |
| Operation | One of `list`, `get`, `create`, `update`, `delete` on a resource, each with its own policy. |
| Policy | A named condition that decides whether a caller may perform an operation, read a file, or join a channel. |
| Publishable key | A `pb_pk_…` key; anonymous until a user signs in; every policy applies. |
| Secret key | A `pb_sk_…` key; bypasses policies; servers only. |
| Session | A user's access token, refresh token and user record, kept by the client. |
| Access token | A short-lived signed token that proves which user is calling. |
| Refresh token | A single-use token exchanged for a new session. |
| Flow | A graph of blocks that runs on a trigger such as an HTTP call, an event or a schedule. |
| Custom route | An endpoint you define under `/rest/v1` that runs a flow. |
| Channel | A named realtime topic, authorized by channel rules. |
| Request id | The gateway's `x-request-id`, used to find a request under **Project → Activity**. |
