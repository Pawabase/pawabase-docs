The client has no hook system of its own.
It uses `httpx`, which logs each request at the `INFO` level on the `httpx` logger:

```python
import logging

logging.basicConfig(level=logging.INFO, format="%(asctime)s %(name)s %(message)s")
logging.getLogger("httpx").setLevel(logging.INFO)
```

```text
2026-10-25 10:14:03 httpx HTTP Request: GET https://api.example.com/rest/v1/orders?per_page=20 "HTTP/1.1 200 OK"
```

The log line shows the method, URL and status, not headers, so keys and tokens stay out of logs.
For failures, log the exception's `status_code`, `code` and `request_id`; the request id finds the request under **Project → Activity**.

```python
import logging

from pawabase import PawabaseError

log = logging.getLogger("app")

try:
    pb.from_("orders").create(values)
except PawabaseError as error:
    log.warning("pawabase refused", extra={"status": error.status_code, "code": error.code, "request_id": error.request_id})
    raise
```


## Checking a new configuration

A short smoke test, run after each deploy, catches a wrong URL, key or environment before people do.

```python
from pawabase import AuthenticationError, NetworkError, PawabaseError, Pawabase


def smoke_test(url: str, key: str, environment: str, resources: list[str]) -> list[tuple[str, bool, str]]:
    results: list[tuple[str, bool, str]] = []
    with Pawabase(url, key, environment=environment, retries=0, timeout=10) as pb:
        try:
            pb.status()
            results.append(("gateway answers", True, ""))
        except NetworkError as error:
            return [("gateway answers", False, str(error))]
        try:
            settings = pb.auth.settings()
            results.append(("key accepted", True, f"sign-up {'on' if settings.get('signup_enabled') else 'off'}"))
        except AuthenticationError as error:
            results.append(("key accepted", False, error.message))
        for name in resources:
            try:
                page = pb.from_(name).per_page(1).execute()
                results.append((f"list {name}", True, f"total {page.total}"))
            except PawabaseError as error:
                results.append((f"list {name}", False, f"{error.status_code} {error.code or error.message}"))
    return results
```

Read failures with the request path in mind: a gateway failure is the URL or the network; a `401` on the key check is the key; a `401` on a list while signed out is the default `authenticated` policy; a `404` on a list is a wrong name or a disabled operation.


## Data shapes you will meet

### Page

| Attribute | Meaning |
| --- | --- |
| `data` | The rows, a list of dicts |
| `page` | The page number, from 1 |
| `per_page` | Rows per page, 20 unless you asked otherwise, at most 200 |
| `total` | Matching rows for this caller, or `None` when a per-row policy makes it unknowable |
| `raw` | The response body as received |
| `has_next` | Whether another page probably follows |

A `Page` iterates over its rows, supports `len()`, and indexes like a list: `page[0]`.

### Session

| Attribute | Meaning |
| --- | --- |
| `access_token` | The bearer token |
| `refresh_token` | Single-use; exchanged for a new session |
| `expires_at` | Unix time, in seconds, when the access token expires |
| `user` | The user as a dict |
| `session_id`, `org`, `org_role` | The session's id, and the organization the token is for |

### Sign-in results

| Class | Attributes |
| --- | --- |
| `SignInResult` | `status` (`signed_in` or `mfa_required`), `session`, `mfa_token`, `factors`, and `verify(code)` |
| `SignUpResult` | `user`, `session`, `verification_required` |

### A user

The user dict has `id`, `email`, `username`, `name`, `avatar_url`, `email_verified`, `user_metadata`, `app_metadata`, `roles`, `mfa_enabled`, `identities`, `created_at` and `last_sign_in_at`.
`user_metadata` is editable by the person and must never decide access; `app_metadata` is set by administrators and servers and can be trusted.


## What the client sends

| Header | Value | When |
| --- | --- | --- |
| `apikey` | Your API key | Every request except to signed URLs |
| `x-environment` | The `environment` argument, `development` by default | Every request except to signed URLs |
| `user-agent` | `pawabase-python/0.3` | Every request |
| `Authorization` | `Bearer <access token>` | With a session, an `access_token` argument, or an `as_user` view |
| `content-type` | `application/json` for JSON bodies; the file's type for uploads | When there is a body |
| Your `headers` | Whatever you passed | Every request |

The `user-agent` appears in the platform's request logs, so you can tell Python traffic from browser traffic under **Project → Activity**.

Answers carry `x-request-id`, which the client copies onto every exception as `request_id`, and `Retry-After` on `429`, which the client uses to wait.


## Sessions in long-running processes

A browser tab lives for minutes or hours; a Python process can live for weeks.
The session machinery is built for both.

| Moment | What happens |
| --- | --- |
| Client created | The session store is read on first use; nothing is sent |
| A request with less than 30 seconds left on the token | The client refreshes first, then sends |
| A request answered `401` | The client refreshes once and repeats it |
| The refresh token is refused | The session is cleared, listeners get `SIGNED_OUT`, and the request raises `AuthenticationError` |
| The process restarts | A `FileSessionStore` gives the session back; a memory store starts signed out |

There is no background timer: refreshes happen when requests need them.
A process that is idle for a week and then makes a request refreshes at that moment, if the refresh token is still valid.

On the async client, concurrent requests that all find the token expiring share one refresh.
The blocking client has no such lock, so code that makes requests for one session from several threads at once can refresh twice; since refresh tokens are single-use, the second refresh ends the session.
Keep a signed-in session to one thread, or use the async client.


## How the client treats time

| Rule | Value |
| --- | --- |
| A token counts as expiring | 30 seconds before `expires_at` |
| Default request timeout | 30 seconds, for each attempt |
| Waits after `429` | `Retry-After`, or the body's `retry_after`, at least 1 and at most 20 seconds |
| Waits between retries of reads | 0.25 s, then 0.5 s, then 1 s, at most 2 s |

`expires_at` is computed from the device's clock when the server sends only a lifetime.
A clock that runs fast refreshes early; one that runs slow gets a `401`, which triggers a refresh and a repeat.
Either way the request succeeds.

A session adopted with `set_session(access, refresh)` is given an expiry one minute ahead, because the client does not decode the token; it therefore refreshes on the first request after that minute and learns the real expiry then.


## Proxies and certificates

The client uses `httpx` with its default settings, so the usual environment variables apply:

| Variable | Effect |
| --- | --- |
| `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` | Route requests through a proxy, or not |
| `SSL_CERT_FILE`, `SSL_CERT_DIR` | Trust a corporate certificate authority |

A gateway on a private network with its own certificate authority works once the authority is trusted this way, with no code change.


## Concurrency with asyncio

The async client shines when a task needs several independent requests.

<CodeGroup>
```typescript TypeScript
async function dashboard(pawabase: PawabaseClient) {
  const [orders, tasks, user] = await Promise.all([
    pawabase.from("orders").eq("status", "open").perPage(5),
    pawabase.from("tasks").eq("done", false).perPage(5),
    pawabase.auth.getUser(),
  ]);
  return { orders: orders.data, tasks: tasks.data, user };
}
```

```python Python
import asyncio

async def dashboard(pb):
    orders, tasks, user = await asyncio.gather(
        pb.from_("orders").eq("status", "open").per_page(5).execute(),
        pb.from_("tasks").eq("done", False).per_page(5).execute(),
        pb.auth.get_user(),
    )
    return {"orders": orders.data, "tasks": tasks.data, "user": user}
```
</CodeGroup>

For many writes, bound the concurrency so the environment's rate limit is not the thing that slows you down:

```python
async def mark_all(pb, ids: list[str], status: str, limit: int = 5):
    gate = asyncio.Semaphore(limit)

    async def one(record_id: str):
        async with gate:
            return await pb.from_("orders").update(record_id, {"status": status})

    return await asyncio.gather(*(one(i) for i in ids), return_exceptions=True)
```

`return_exceptions=True` keeps one failure from cancelling the rest; inspect the results for exceptions afterwards.
The async `create_many` does the same for creates, with `concurrency=5` by default.


## Several environments in one process

Each environment has its own keys, so each needs its own client.

```python
staging = Pawabase(URL, STAGING_SECRET, environment="staging")
production = Pawabase(URL, PRODUCTION_SECRET, environment="production")

staging_plans = {plan["code"]: plan for plan in staging.from_("plans").all()}
production_plans = {plan["code"]: plan for plan in production.from_("plans").all()}
missing = sorted(set(staging_plans) - set(production_plans))
print("plans in staging but not production:", missing)
```

For management work, `pb.manage.environment("staging")` and `pb.admin.environment("staging")` address another environment with the same client, when its key may manage that environment.


## Forked workers

Servers such as Gunicorn fork worker processes.
An `httpx` client created before the fork shares connections between processes, which corrupts them.

Create clients after the fork: lazily on first use, as the `lru_cache` functions above do, or in a post-fork hook.
Do not create clients at import time in a module that Gunicorn's `--preload` imports in the parent.
