Records are accessed through the data plane at `/rest/v1/<resource>`. The Python SDK provides five methods on `Pawabase` and `AsyncPawabase`: `list()`, `get()`, `create()`, `update()`, `delete()`. They do not create model classes, do not track changes, do not provide a fluent query builder, and do not load relations by default. You pass wire-level parameters as `**params` to `list()` or as `json` to mutations. The gateway enforces policies; the client only shapes requests, applies retries where appropriate, and converts failures to `PawabaseError`.

This page explains the method signatures, request shapes, pagination, filtering and sorting conventions as used by the gateway, automatic retries, errors, and concrete patterns. Policy details are covered in [Policies](/policies/overview); filtering syntax in [Filtering](/data/filtering).

<Info>
All record methods go through `request()` or the underlying `_call()`. `list()` and `get()` use `request()` with `retry=True` for GET. Mutations do not retry by default.
</Info>

## The mental model

A resource is a table or view exposed by the gateway. Rows come back as plain Python dicts with field names as the server returns them (typically `snake_case`). There are no relationships loaded unless you ask for them with `expand`. The client sends `apikey`, `x-project-id`, `x-environment`, and any `Authorization` header from `as_user()`. What you see is exactly what policies allow the caller to see. A record visible in Studio may return 404 or be filtered by policies depending on the key and context.

The SDK does not validate field names, operators, or response shapes. It does not coerce types. It passes values through as provided and lets the gateway decide.

## Method reference

| Method | HTTP | Path | Body/Params | Retry | Notes |
| --- | --- | --- | --- | --- | --- |
| `list(resource, **params)` | `GET` | `/rest/v1/{resource}` | Query params | Yes (GET) | Returns decoded JSON. Does not auto-paginate. Params passed as-is. |
| `get(resource, record_id)` | `GET` | `/rest/v1/{resource}/{record_id}` | None | Yes (GET) | Returns single record or raises on error. |
| `create(resource, values)` | `POST` | `/rest/v1/{resource}` | `json=dict(values)` | No | Creates record. Returns created record as gateway returns it. |
| `update(resource, record_id, values)` | `PATCH` | `/rest/v1/{resource}/{record_id}` | `json=dict(values)` | No | Partial update. Always uses PATCH. |
| `delete(resource, record_id)` | `DELETE` | `/rest/v1/{resource}/{record_id}` | None | No | Deletes record. May return None or response body. |

All methods are available on both `Pawabase` and `AsyncPawabase`. Async versions return awaitables.

## Listing records

```python
posts = pb.list(
    "posts",
    **{
        "filter[status]": "eq.live",
        "sort": "-created_at",
        "page": 1,
        "per_page": 20,
        "select": "id,title,status,created_at",
        "expand": "author",
    },
)
```

Python does not allow `[` and `]` in keyword argument names, so you must pass parameters as a dictionary expanded with `**`. The client passes them directly to `httpx` as query parameters.

### Common parameters

| Parameter | Type | Meaning | Notes |
| --- | --- | --- | --- |
| `filter[<field>]` | `str` | Filter expression like `eq.value`, `neq.x`, `gt.10`, `gte.10`, `lt.10`, `lte.10`, `in.a,b`, `nin.a,b`, `like.%x%`, `ilike.%x%`, `is.null`, `is.not.null`. | Syntax defined by gateway. See [Filtering](/data/filtering). |
| `sort` | `str` | Sort field. Prefix `-` for descending. Multiple sorts may be comma-separated or repeated depending on gateway. | Order matters. |
| `select` | `str` | Comma-separated list of fields to return. | Reduces payload size. |
| `expand` | `str` | Comma-separated relations to expand. | Only works where relations are exposed. |
| `page` | `int` | Page number. | 1-based in many cases; check gateway behavior. |
| `per_page` | `int` | Items per page. | May be limited by gateway. |
| `limit` | `int` | Alternative to page/per_page. | Depends on gateway. |
| `offset` | `int` | Offset for offset-based pagination. | Less common; page/per_page more typical. |

### Pagination behavior

The client does not follow pages automatically. `list()` makes one request and returns whatever the gateway returns. The response shape varies: it may be a plain list, or an object with keys like `data`/`items` and pagination metadata. Totals may be `null` when per-row policies prevent counting all rows. The client cannot know the shape in advance; inspect the actual response for your resources.

To fetch all pages, you must loop manually based on the gateway's pagination scheme:

```python
all_posts = []
page = 1
while True:
    batch = pb.list("posts", **{"filter[status]": "eq.live", "page": page, "per_page": 100})
    if not batch:
        break
    # adjust if batch is wrapped
    items = batch if isinstance(batch, list) else batch.get("data", [])
    all_posts.extend(items)
    if len(items) < 100:
        break
    page += 1
```

This is a pattern, not something the SDK does for you.

### Retries on list
`list()` calls `request("GET", f"/rest/v1/{resource}", params=params)`. `request()` sets `retry=True` for GET. The client will retry on transport errors and on `502`, `503`, `504`. It will honor `429` with backoff up to limits. Mutations are not retried.

## Getting a single record

```python
post = pb.get("posts", "post_123")
```

Calls `GET /rest/v1/posts/post_123`. Returns the record if found and permitted. If not found or not permitted, the gateway typically returns 404 and `PawabaseError` is raised.

## Creating records

```python
created = pb.create("posts", {"title": "Notes", "status": "draft", "author_id": "user_1"})
```

Calls `POST /rest/v1/posts` with `json=dict(values)`. The gateway validates, applies defaults, applies policies, and returns the created record. The client does not validate required fields or types.

## Updating records

```python
updated = pb.update("posts", created["id"], {"status": "live"})
```

Calls `PATCH /rest/v1/posts/{id}` with `json=dict(values)`. Always PATCH. Partial updates are typical. The client does not merge with existing data; it sends exactly what you pass.

## Deleting records

```python
pb.delete("posts", updated["id"])
```

Calls `DELETE /rest/v1/posts/{id}`. The response may be empty (body `None`) or may return the deleted record depending on the gateway. The client returns whatever `_body()` returns.

## Using expand and select together

```python
post = pb.get("posts", "post_123")
# or
posts = pb.list("posts", **{"select": "id,title,author_id", "expand": "author"})
```

`expand` fetches related records in the same request where supported. Not all relations are expandable. Policies apply to expanded relations too. Overusing expand can increase payload size.

## Using request() for non-standard calls

```python
# Custom path
result = pb.request("GET", "/rest/v1/posts", params={"filter[status]": "eq.live", "select": "id,title"})

# With headers via view
view = pb.as_user(token)
result = view.request("GET", "/rest/v1/posts/post_123")
```

Use `request()` when you need behavior not covered by the five methods, or when calling routes with unusual shapes.

## Errors

Record operations raise `PawabaseError` on failures:

| Status | Typical meaning | Notes |
| --- | --- | --- |
| 400 | Bad request / invalid filter | Check filter syntax. |
| 401 | Unauthenticated | Check key/token. |
| 403 | Forbidden / policy denied | Check policies. |
| 404 | Not found | May mean no access (policies can hide rows). |
| 409 | Conflict | Duplicate or constraint violation. |
| 422 | Validation error | Invalid field values. Check `e.problems()`. |
| 429 | Rate limited | Client retries with backoff. |
| 502/503/504 | Gateway errors | Client retries if conditions met. |
| 0 | Network unreachable | Transport error. |

```python
from pawabase import PawabaseError

try:
    pb.get("posts", "missing")
except PawabaseError as e:
    print(e.status_code)
    print(e.message)
    print(e.code)
    print(e.problems())
    print(e.detail)
```

## Async usage

```python
async with AsyncPawabase(url, key, project="acme") as pb:
    posts = await pb.list("posts", **{"filter[status]": "eq.live", "per_page": 10})
    created = await pb.create("posts", {"title": "Hi"})
    post = await pb.get("posts", created["id"])
    updated = await pb.update("posts", post["id"], {"status": "live"})
    await pb.delete("posts", updated["id"])
```

All methods are awaitables. Error handling is the same.

## Practical notes

- The SDK does not enforce row-level security locally; the gateway does.
- Policies can make rows appear non-existent (404) rather than forbidden in some cases.
- `list()` does not follow pagination; implement your own loop if needed.
- Mutations are not retried; if you need idempotency, handle it yourself or use idempotency keys if the gateway supports them.
- Use `select` to limit fields. Use `expand` sparingly.
- Field names are case-sensitive as returned by the gateway.
- Pass all values as JSON-serializable types.


## Deep dive: list() behavior

`list(resource, **params)` calls `self.request("GET", f"/rest/v1/{resource}", params=params)`. The resource name is interpolated directly into the path. It is not URL-encoded by the SDK beyond what `httpx` does. The params dict is passed as-is to `httpx` as query parameters.

Python does not allow brackets in keyword names, so always use `**{...}`:
```python
pb.list("posts", **{"filter[status]": "eq.live", "sort": "-created_at"})
```

The method returns whatever `request()` returns after `_body()` processes the response. For a GET request, `request()` sets `retry=True`, so `list()` benefits from retry logic on transport errors and 502/503/504.

## Deep dive: pagination patterns

The gateway's pagination behavior depends on configuration. Common patterns:

### Page-based pagination
```python
def fetch_all(pb, resource, filters=None, per_page=100):
    all_items = []
    page = 1
    while True:
        params = {"page": page, "per_page": per_page}
        if filters:
            params.update(filters)
        result = pb.list(resource, **params)
        if isinstance(result, list):
            items = result
        elif isinstance(result, dict):
            items = result.get("data") or result.get("items") or []
        else:
            break
        if not items:
            break
        all_items.extend(items)
        if len(items) < per_page:
            break
        page += 1
    return all_items
```

### Offset-based pagination
Some gateways use `offset` and `limit`. Check the actual API.

### Cursor-based pagination
Less common in this SDK's patterns; check gateway docs.

The client never assumes pagination structure. You must adapt to what the gateway returns.

## Deep dive: filtering

Filters use bracket notation: `filter[field]=operator.value`. The SDK passes them through unchanged. Operators vary by gateway and field type. Common operators: `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `like`, `ilike`, `in`, `nin`, `is`, `fts`, `plfts`, `phfts`, `wfts`. Values may need URL encoding which `httpx` handles.

Multiple filters can be combined:
```python
posts = pb.list("posts", **{
    "filter[status]": "eq.published",
    "filter[created_at]": "gte.2024-01-01T00:00:00Z",
    "filter[author_id]": "in.user1,user2,user3"
})
```

```python
# Descending
pb.list("posts", **{"sort": "-created_at"})

# Ascending
pb.list("posts", **{"sort": "title"})

# Multiple sorts (if supported)
pb.list("posts", **{"sort": "-created_at,title"})
```

## Deep dive: selecting fields

```python
pb.list("posts", **{"select": "id,title,created_at"})
```

Reduces payload size. Some fields may be required by policies.

## Deep dive: expanding relations

```python
pb.list("posts", **{"expand": "author,comments"})
pb.get("posts", "post_123", **{"expand": "author"})
```

Note: `get()` in the SDK takes `(resource, record_id)` only. To pass params to get, use `request()`:
```python
post = pb.request("GET", "/rest/v1/posts/post_123", params={"expand": "author"})
```

## Mutations in detail

### create()
```python
created = pb.create("posts", {"title": "Hello", "status": "draft"})
```
Sends `POST /rest/v1/posts` with JSON body `{"title": "Hello", "status": "draft"}`. Returns created record. Does not retry.

### update()
```python
updated = pb.update("posts", "post_123", {"status": "published"})
```
Sends `PATCH /rest/v1/posts/post_123`. Partial update. Does not retry.

### delete()
```python
pb.delete("posts", "post_123")
```
Sends `DELETE /rest/v1/posts/post_123`. May return None if response has no content. Does not retry.

## Error handling details

```python
from pawabase import PawabaseError

try:
    result = pb.create("posts", {"title": "x"})
except PawabaseError as e:
    if e.status_code == 400:
        # Bad request
        pass
    elif e.status_code == 422:
        # Validation error
        print(e.problems())
    elif e.status_code == 403:
        # Policy denied
        pass
    elif e.status_code == 409:
        # Conflict
        pass
```

## Performance considerations

- Use `select` to limit fields
- Use pagination to avoid large responses
- Avoid unnecessary `expand`
- Use GET requests which are retryable for safety
- The client reuses connections via httpx

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| 404 on existing record | Policy denies access | Check policies or use different key |
| Empty list but records exist | Filters too strict or policies | Check filters and policies |

## Deep dive: Query builder behavior

The query builder in the Python SDK is immutable in style - each method returns a new query object. This matches the behavior described: `open_` remains unchanged when creating derived queries. The builder accumulates filters, ordering, pagination parameters, and other options.

Looking at how it works in the SDK patterns, the builder stores state and `execute()` or `execute_async()` serializes it into the appropriate REST call.

### Filter methods

Common filter methods (based on API patterns and TS SDK parity):
- `eq(field, value)` - equals
- `neq(field, value)` - not equals  
- `gt(field, value)`, `gte(field, value)` - greater than / greater or equal
- `lt(field, value)`, `lte(field, value)` - less than / less or equal
- `like(field, pattern)`, `ilike(field, pattern)` - pattern matching
- `in_(field, values)` - in list
- `is_null(field)`, `not_null(field)` - null checks
- `contains(field, value)`, `contained_by(field, value)`, etc. - array/JSON operations

Each filter call adds to the query's filter set without mutating previous queries.

### Ordering

```python
orders = pb.from_("orders").order("created_at", "desc")
```

The order method takes field name and direction ("asc" or "desc").

### Pagination

```python
page = query.per_page(20).page(1).execute()
# or
page = query.limit(20).offset(0).execute()
```

The SDK supports pagination through `per_page()` and related methods. The exact parameter names depend on the API convention.

### Counting

```python
count = query.count()
```

Counting executes a request optimized for count (often with `per_page=1` and reading total from response metadata).

### Single record retrieval

```python
order = query.get("order_id")  # or maybe_get
```

## The REST mapping

Under the hood, each operation maps to REST calls:

| Operation | HTTP | Endpoint |
|-----------|------|----------|
| list/query/execute | GET | `/rest/v1/<resource>` with query params for filters, sort, pagination |
| get | GET | `/rest/v1/<resource>/<id>` |
| create | POST | `/rest/v1/<resource>` with JSON body |
| create_many | POST | `/rest/v1/<resource>` with array body |
| update | PATCH/PUT | `/rest/v1/<resource>/<id>` |
| delete | DELETE | `/rest/v1/<resource>/<id>` |

Query parameters encode filters (often as `filter[field]=op.value`), sorting (`sort=-created_at` or similar), and pagination.

## Policies and permissions

Resources have operations (list, get, create, update, delete). Each operation can be enabled/disabled in Studio under **Data > [Resource] > Operations**. Each operation has a policy that determines access.

The default policy is `authenticated` - requires a signed-in user. Anonymous requests are refused by default. Use `as_user(token)` to act as a specific user.

When an operation is disabled, requests return 404 or 405. When enabled but policy denies, you get 403 or similar depending on the API's error model.

## Error cases

- **404 Not Found**: Resource doesn't exist or operation is disabled
- **401 Unauthorized**: Missing or invalid auth when required
- **403 Forbidden**: Authenticated but policy denies access
- **422 Unprocessable Entity**: Validation errors on create/update
- **429 Too Many Requests**: Rate limited (client handles with backoff)

All errors are wrapped in `PawabaseError` with status code and message.

## Relations and expanding

If relations are configured, they may be expandable. The API and SDK patterns follow the REST conventions set up in Studio. Check the resource configuration in Studio under **Data** for relation details.

## Best practices

1. **Build queries immutably** - Don't reuse modified builders expecting side effects
2. **Check Studio first** - Verify operations are enabled and policies before coding
3. **Use as_user for user-scoped operations** - Respect RLS/policies
4. **Handle pagination properly** - Use `.pages()` or iterate with page/per_page
5. **Count separately** - Counting may be a separate call depending on API design
6. **Type your responses** - Use TypedDict/Pydantic for better safety
