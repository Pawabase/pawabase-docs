The Python SDK provides methods to invoke HTTP-triggered flows and functions, to trigger flows and schedules as an operator (typically with a secret key), and a generic `request()` method to call any custom route. There is no `routes` namespace object like the TypeScript SDK.

This page explains each method, when to use it, paths, authentication, and practical patterns.

## The mental model

Flows and functions can be triggered in different ways:
- **HTTP-triggered**: Exposed via `/flows/v1/<name>` or `/functions/v1/<name>`. Called with publishable or secret keys subject to trigger policies.
- **Operator-triggered**: Called via management endpoints under `/platform/v1/.../flows/{name}/run` or `/schedules/{name}/run`. Typically requires a secret key and runs with operator privileges (possibly impersonating a user via `as_user`).

Custom routes defined on the gateway can be called with `request()`.

## HTTP-triggered flows

```python
receipt = pb.invoke_flow("checkout", {"cart_id": "cart_123"})
```

- Method: `invoke_flow(name: str, input: Any = None)`
- HTTP: `POST /flows/v1/{name}`
- Body: `json=input` (passed as-is)
- Retry: No (not set)
- Auth: API key as configured; subject to flow HTTP trigger policy

## HTTP-triggered functions

```python
price = pb.invoke_function("price-order", {"sku": "A1", "quantity": 2})
price_branch = pb.invoke_function("price-order", {"sku": "A1", "quantity": 2}, branch="checkout-rewrite")
```

- Method: `invoke_function(name: str, input: Any = None, *, branch: str | None = None)`
- HTTP: `POST /functions/v1/{quote(name)}`
- Body: `json=input`
- Query: `branch` added only if provided and `branch != "main"`
- Retry: No
- Auth: Subject to function policy and key scope

## Operator-triggered flows (secret key)

```python
result = pb.run_flow("checkout", {"cart_id": "cart_123"})
result = pb.run_flow("checkout", {"cart_id": "cart_123"}, as_user={"id": "user_1"})
result = pb.run_flow("checkout", {"cart_id": "cart_123"}, entry="start")
```

- Method: `run_flow(name: str, input: Any = None, *, as_user: Mapping[str, Any] | None = None, entry: str | None = None)`
- HTTP: `POST /platform/v1/projects/{project}/envs/{environment}/flows/{name}/run`
- Body: `{"input": input, "as_user": dict(as_user) if as_user else None, "entry": entry}`
- Retry: No
- Auth: Secret key required. Runs as operator or impersonates user.

## Operator-triggered schedules (secret key)

```python
pb.run_schedule("daily-report")
```

- Method: `run_schedule(name: str)`
- HTTP: `POST /platform/v1/projects/{project}/envs/{environment}/schedules/{name}/run`
- Retry: No
- Auth: Secret key required. Fires schedule immediately as if triggered by scheduler.

## Custom routes

Use `request()` for routes defined on the gateway:

```python
result = pb.request("POST", "/rest/v1/custom/action", json={"x": 1})
result = pb.request("GET", "/rest/v1/custom/data", params={"limit": 10})
```

You can also use views with `as_user()` for user-scoped custom routes.

## Errors

All methods raise `PawabaseError` on failure. Check `status_code`, `message`, `detail`.

```python
from pawabase import PawabaseError

try:
    pb.invoke_flow("missing-flow", {})
except PawabaseError as e:
    print(e.status_code)
```

## Async usage

```python
async with AsyncPawabase(url, key, project="acme") as pb:
    price = await pb.invoke_function("price-order", {"sku": "A1"})
    receipt = await pb.invoke_flow("checkout", {"cart_id": "c1"})
```

## Notes

- HTTP-triggered methods are for public/triggered endpoints; operator methods are for management
- Branch parameter only affects `invoke_function()` query when not `"main"`
- `run_flow()` can impersonate users with `as_user`
- Use secret keys for operator methods


## Deep dive: invoke_function

```python
result = pb.invoke_function("process-order", {"order_id": "ord_123", "items": [...]})
```

Calls `POST /functions/v1/process-order` with JSON body `{"order_id": "ord_123", "items": [...]}`. If `branch` is provided and not `"main"`, adds query parameter `branch=...`. The function's HTTP trigger policy determines if the call is allowed. The key's scopes may also apply.

Response is the function's return value as JSON.

## Deep dive: invoke_flow

```python
receipt = pb.invoke_flow("checkout", {"cart_id": "cart_456", "payment_method": "card"})
```

Calls `POST /flows/v1/checkout`. Flows may run synchronously or asynchronously depending on configuration. The response depends on the flow.

## Deep dive: run_function (operator)

```python
result = pb.run_function("process-job", {"job_id": "j1"}, branch="main")
# result = {"status": "completed", "result": {...}} or {"status": "failed", "error": {...}}
```

Calls `POST /platform/v1/projects/{project}/envs/{environment}/functions/{name}/invoke` with body `{"input": input, "branch": branch, "as_user": dict(as_user) if as_user else None}`. This bypasses HTTP trigger policies and runs as operator. Requires secret key with appropriate scopes.

Can impersonate a user:
```python
result = pb.run_function("send-notification", {"message": "Hi"}, as_user={"id": "user_123"})
```

## Deep dive: run_flow (operator)

```python
result = pb.run_flow("cleanup", {"older_than_days": 7}, as_user={"id": "admin_1"}, entry="start")
```

Runs a flow as operator. Can specify entry point and impersonate user.

## Deep dive: run_schedule

```python
pb.run_schedule("daily-report")
```

Fires a scheduled job immediately as if the scheduler triggered it. Useful for testing.

## Deep dive: custom routes

```python
# GET route
data = pb.request("GET", "/rest/v1/custom/stats", params={"period": "week"})

# POST route
result = pb.request("POST", "/rest/v1/custom/action", json={"action": "sync"})

# With user context
view = pb.as_user(token)
result = view.request("POST", "/rest/v1/custom/user-action", json={...})
```

Custom routes follow your gateway's routing configuration. Use `request()` for flexibility.

## Error handling

```python
from pawabase import PawabaseError

try:
    result = pb.invoke_function("risky-function", {})
except PawabaseError as e:
    if e.status_code == 404:
        print("Function not found")
    elif e.status_code == 403:
        print("Not allowed")
    elif e.status_code == 500:
        print("Function error")
```

## Use cases

| Method | Use case |
| --- | --- |
| `invoke_function` | Call HTTP-triggered functions from apps |
| `invoke_flow` | Trigger flows from apps |
| `run_function` | Run functions as admin/CI |
| `run_flow` | Trigger flows as admin/CI with user context |
| `run_schedule` | Manually trigger scheduled jobs |
| `request()` | Call custom endpoints |

## Async patterns

```python
async with AsyncPawabase(url, key, project="acme") as pb:
    # Call multiple functions
    import asyncio
    r1, r2 = await asyncio.gather(
        pb.invoke_function("func1", {}),
        pb.invoke_function("func2", {})
    )
```

## Deep dive: Calling routes and flows

Routes and flows are configured in Studio under **Routes/Flows**. They provide server-side logic, can be protected by policies, and are invoked via HTTP.

### Calling routes

Use `pb.call_route(path, method="GET", json=None, params=None)` or `pb.request()` for more control.

```python
# GET route
result = pb.call_route("/parent/dashboard")

# POST route with body
result = pb.call_route("/enrollments", method="POST", json={"student_id": "123"})
```

Routes are served under `/rest/v1` as noted in the school-management example - `Route("/parent/dashboard", ...)` means accessible at that path.

### Flow invocation

Flows can be invoked similarly. They may be triggered by events, schedules, or called directly depending on configuration.

### Authentication and policies

Routes/flows can be protected by policies (like `guardians_only`, `authenticated`, etc.). Use `as_user(token)` when calling protected routes as a specific user.

```python
pb_guardian = pb.as_user(guardian_token)
dashboard = pb_guardian.call_route("/parent/dashboard")
```

### Error handling

Routes return errors as defined by their implementation. The client will return the error body/raise `PawabaseError` based on status codes.

### Best practices

1. **Check policies in Studio** - Know if auth is required
2. **Use as_user when needed** - Match the caller context
3. **Handle errors gracefully** - Routes may return different error shapes
4. **Cache considerations** - Some routes may have caching as configured
