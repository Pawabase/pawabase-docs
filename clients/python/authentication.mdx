The Python SDK exposes a small set of auth endpoints on `Pawabase` and `AsyncPawabase`: `sign_in()`, `sign_up()`, `refresh_session()`, `sign_out()`, `request_password_reset()`, `reset_password()`, `auth_settings()`. It does not manage sessions, store tokens, auto-refresh them, or provide nested auth objects. To make requests as a signed-in user, create a view with `as_user(access_token)`. The SDK is explicit about token handling because servers need to control where tokens are stored and when they are refreshed.

This page documents each method, request shapes, typical responses, how to act as a user, errors, and practical patterns.

## The mental model

Authentication is handled by the gateway at `/auth/v1/*`. The client sends the project API key and headers on every request. Auth endpoints exchange credentials for tokens and return user/session information. The SDK does not persist anything between calls. You are responsible for storing `access_token` and `refresh_token` securely and calling `refresh_session()` when the access token expires. For server-side operations acting on behalf of a user, `as_user(access_token)` adds `Authorization: Bearer <token>` to requests made through that view.

## Method reference

| Method | HTTP | Path | Body | Retry | Notes |
| --- | --- | --- | --- | --- | --- |
| `sign_in(email, password)` | `POST` | `/auth/v1/token` | `{"grant_type": "password", "email": ..., "password": ...}` | No | Returns session or MFA challenge. |
| `sign_up(email, password, *, name=None, data=None)` | `POST` | `/auth/v1/signup` | `{"email", "password", "name"?, "data"?}` | No | Creates user. May require confirmation. |
| `refresh_session(refresh_token)` | `POST` | `/auth/v1/token` | `{"grant_type": "refresh_token", "refresh_token": ...}` | No | Returns new session tokens. |
| `sign_out()` | `POST` | `/auth/v1/logout` | `{"scope": "local"}` | No | Signs out. |
| `request_password_reset(email, *, redirect_to=None)` | `POST` | `/auth/v1/recover` | `{"email", "redirect_to"?}` | No | Sends reset email if enabled. |
| `reset_password(token, password)` | `POST` | `/auth/v1/recover/confirm` | `{"token", "password"}` | No | Confirms reset. |
| `auth_settings()` | `GET` | `/auth/v1/settings` | — | Yes | Public auth settings. |

## Sign in

```python
session = pb.sign_in("user@example.com", "password")
```

Typical response on success:
```python
{
  "access_token": "...",
  "refresh_token": "...",
  "expires_in": 3600,
  "token_type": "bearer",
  "user": {...}
}
```

If MFA is required, the gateway may return:
```python
{
  "mfa_required": true,
  "mfa_token": "...",
  "factors": [{"id": "...", "type": "totp"}]
}
```

The SDK does not implement MFA challenge/verification methods. Handle MFA flows according to the gateway's auth API.

## Sign up

```python
result = pb.sign_up("user@example.com", "password", name="Alex", data={"plan": "free"})
```

Behavior depends on auth settings:
- If email confirmation is disabled, may return a session similar to sign_in.
- If email confirmation is enabled, may return a message indicating confirmation is required and no session tokens.
- The `data` field is passed as `data` in the body if provided.

## Refresh session

```python
new_session = pb.refresh_session(old_refresh_token)
access_token = new_session["access_token"]
refresh_token = new_session.get("refresh_token", old_refresh_token)
```

The SDK does not detect expiry or refresh automatically. You must track token expiry and call `refresh_session()` when needed. Store tokens securely (not in logs).

## Sign out

```python
pb.sign_out()
```

Sends a logout request with `scope: "local"`. Behavior depends on the gateway configuration.

## Password reset

```python
pb.request_password_reset("user@example.com", redirect_to="https://app.example.com/reset")
pb.reset_password(reset_token, "new_password")
```

`request_password_reset()` sends an email if the gateway has password recovery enabled. `reset_password()` confirms the reset using the token from the email.

## Auth settings

```python
settings = pb.auth_settings()
```

Returns public auth configuration (providers, MFA settings, etc.). This is a GET request with `retry=True`.

## Acting as a signed-in user with `as_user`

```python
session = pb.sign_in("user@example.com", "password")
view = pb.as_user(session["access_token"])
profile = view.request("GET", "/auth/v1/user")
```

The view adds `Authorization: Bearer <token>` to every request made through it. The same connection pool is used. Closing the view does nothing. You can pass additional headers: `pb.as_user(token, x_client_id="app1")`.

Use this pattern in servers where you hold one client per process and need to make requests on behalf of different users per request.

## Identifying a token

The management method `identify(token)` can verify a token:

```python
identity = pb.identify(access_token)
# Returns auth context or indicates anonymous/invalid
```

This is useful on the server side to understand who a token belongs to.

## What the SDK does not do

| Item | Explanation |
| --- | --- |
| No session storage | Tokens are not persisted. You must store them. |
| No auto-refresh | You must call `refresh_session()` yourself. |
| No nested auth object | No `pb.auth.*`. Methods are flat on the client. |
| No MFA helpers | No methods to challenge/verify MFA factors. |
| No OAuth helpers | Use gateway OAuth flows directly or via web. |
| No token rotation management | You handle token lifecycle. |

## Errors

Auth operations raise `PawabaseError` on failure:

| Status | Typical meaning |
| --- | --- |
| 400 | Bad request / invalid grant |
| 401 | Invalid credentials / invalid token |
| 422 | Validation error |
| 429 | Rate limited |

```python
from pawabase import PawabaseError

try:
    pb.sign_in("user@example.com", "wrong")
except PawabaseError as e:
    print(e.status_code, e.message)
```

## Deep dive: sign_in

```python
session = pb.sign_in("user@example.com", "password")
```

The method calls `self._call("POST", "/auth/v1/token", json={"grant_type": "password", "email": email, "password": password})`. No retry is set. The response is returned as-is from `_body()`.

Possible responses:
1. Success with session: `{"access_token": "...", "refresh_token": "...", "expires_in": 3600, "token_type": "bearer", "user": {...}}`
2. MFA required: `{"mfa_required": true, "mfa_token": "...", "factors": [...]}`

Store tokens securely. Never log them.

## Deep dive: sign_up

```python
result = pb.sign_up("user@example.com", "password123", name="Alex Chen", data={"plan": "free", "source": "web"})
```

Builds body with email, password, optional name and data. The `data` dict is passed as `{"data": dict(data)}` if provided. Behavior depends on auth configuration:
- If email confirmation disabled and signup allowed: may return session
- If email confirmation enabled: may return success message requiring confirmation
- If signup disabled: raises `PawabaseError`

## Deep dive: refresh_session

```python
try:
    new_session = pb.refresh_session(refresh_token)
    access_token = new_session["access_token"]
    refresh_token = new_session.get("refresh_token", refresh_token)
    # update stored tokens
except PawabaseError as e:
    if e.status_code == 401:
        # refresh token invalid/expired, re-authenticate
        pass
```

Uses `grant_type: "refresh_token"`. The gateway may rotate refresh tokens; always use the new refresh token if returned.

## Deep dive: acting as user

```python
# After sign in
session = pb.sign_in(email, password)
user_view = pb.as_user(session["access_token"])

# Make requests as user
profile = user_view.request("GET", "/auth/v1/user")
posts = user_view.list("posts")  # subject to user's policies
```

The view shares the connection pool. You can also add extra headers:
```python
view = pb.as_user(token, x_app_version="1.0.0")
```

## Token management patterns

```python
class AuthManager:
    def __init__(self, pb):
        self.pb = pb
        self.access_token = None
        self.refresh_token = None
    
    def sign_in(self, email, password):
        session = self.pb.sign_in(email, password)
        self.access_token = session["access_token"]
        self.refresh_token = session["refresh_token"]
        return session
    
    def get_view(self):
        return self.pb.as_user(self.access_token)
    
    def refresh(self):
        session = self.pb.refresh_session(self.refresh_token)
        self.access_token = session["access_token"]
        if "refresh_token" in session:
            self.refresh_token = session["refresh_token"]
        return session
```

## MFA handling

If `sign_in` returns `{"mfa_required": true, ...}`, the SDK does not handle MFA. You need to:
1. Detect MFA required
2. Prompt user for MFA code
3. Call the appropriate MFA verification endpoint via `request()`
4. Get session tokens

Check gateway docs for MFA endpoints.

## Security considerations

- Never log tokens
- Store tokens securely (encrypted at rest)
- Use HTTPS
- Refresh tokens before expiry
- Clear tokens on sign out
- Use `as_user()` in servers, not in browsers
- Rotate tokens regularly

## Deep dive: as_user behavior

The `as_user()` method is the key to impersonating users. It creates a shallow copy of the client instance and adds authentication headers.

```python
view = pb.as_user(token)  # returns shallow copy
# view shares httpx client with original
```

The implementation (from source):
```python
def as_user(self, token: str | None, **headers: str) -> Any:
    import copy
    view = copy.copy(self)
    view._extra = {**({"Authorization": f"Bearer {token}"} if token else {}), **{k.replace("_", "-"): v for k, v in headers.items()}}
    view._borrowed = True
    return view
```

Key points:
- Uses `copy.copy()` (shallow copy) - the httpx client is shared between original and copy
- `_extra` stores additional headers to merge into requests
- If token is None, no Authorization header is added
- Custom headers passed as kwargs: underscores become hyphens
- Sets `_borrowed = True` flag

When making requests, the client merges `self._extra` headers. This allows acting as different users without creating new client instances.

## Authentication flows

### Sign in with email/password

If the API has auth endpoints, you might call them via `pb.request()` or through specific methods. Check the actual API - in general, auth operations go through the REST/auth endpoints as configured in Studio.

### Using tokens

Once you have a token (from login, session, etc.), use `as_user(token)` to make authenticated requests.

```python
pb_user = pb.as_user(user_token)
orders = pb_user.from_("orders").execute()  # as that user
```

### Anonymous access

Without `as_user()`, requests use only the API key headers. Depending on policies, this may be allowed or denied.

### Service accounts

For backend operations, use a service key (`pb_sk_*`) - but be careful about where it runs. Only use in server-side code, never in browsers.

## Session management

The SDK takes a `session_store` parameter. `MemorySessionStore` is available. The store manages session state if the client handles auth sessions. For the basic request patterns shown, explicit `as_user()` is the primary mechanism.

## Security considerations

1. **Never expose secret keys** - Only use `pb_pk_*` keys in client-side code
2. **Use HTTPS in production** - The SDK will send keys over the network
3. **Tokens are sensitive** - Handle user tokens securely, don't log them
4. **Least privilege** - Use tokens with appropriate scopes/permissions
5. **Token rotation** - Implement refresh logic as needed

## Common patterns

```python
# Act as authenticated user
pb_auth = pb.as_user(access_token)
profile = pb_auth.from_("profiles").eq("user_id", user_id).execute()

# Multiple user contexts
pb_admin = pb.as_user(admin_token)
pb_user = pb.as_user(user_token)

# Anonymous
results = pb.from_("public_posts").execute()
```

## Troubleshooting auth issues

| Issue | Cause | Solution |
|-------|-------|----------|
| 401 on authenticated endpoint | Missing/wrong token or not using as_user | Use `pb.as_user(token)` with valid token |
| 403 Forbidden | Policy denies access for this user/role | Check resource policy in Studio, verify user permissions |
| Token not sent | Using wrong method | Ensure using the `as_user()` copy |
