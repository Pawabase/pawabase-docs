When your code sees `status: "paid"`, money moved. This page lists every check behind that, so you can trust it and explain it.

The short version: a webhook from Bachs is only a **nudge**. Pawabase never marks a payment paid because someone told it to. It marks a payment paid after it has **asked Bachs itself** and the answer matches what was recorded when the payment started.

## The five checks

A payment becomes `paid` only after all of these.

<Steps>
  <Step title="The delivery is genuine">
    Bachs signs every delivery: an HMAC-SHA256 of the timestamp and the raw body, with the signing secret. Pawabase checks the signature and refuses anything unsigned, wrongly signed, or more than five minutes old, before anything else happens. A refused delivery answers `401` and does not even count as received. During a secret rotation, either secret is accepted.
  </Step>
  <Step title="It is new">
    Every Bachs event id is handled once. A repeat is acknowledged and does nothing, so Bachs retrying a delivery cannot double anything.
  </Step>
  <Step title="Bachs confirms it">
    The delivery names a checkout, nothing more. Pawabase asks Bachs for that checkout with your key, and requires it to be **completed** and its payment **succeeded**. What the delivery body claims is not trusted.
  </Step>
  <Step title="It is the right payment">
    The checkout's reference and currency must be the ones recorded when the payment was started, and its amount must equal the recorded amount (`5000` and `5000.00` are equal). If Bachs completed a checkout that does not match, the payment is marked `flagged` for you to review, and is never marked paid.
  </Step>
  <Step title="It moves once, forward">
    Only a `pending` payment is settled, and the database moves it out of pending in a single step. Two deliveries, or a delivery and a read, arriving at the same moment cannot both mark it paid, and only the one that won announces the event, so your flow runs once. A `paid` payment is never changed by anything that arrives later.
  </Step>
</Steps>

Reading a payment (`payments.get`, `payments.waitFor`) and **Check with Bachs** in Studio run the same settlement, so a payment becomes `paid` even if the webhook never arrives.

## What a client cannot do

| A client tries to | What happens |
| --- | --- |
| Create a payment row, or change a payment's status, through the API | There is no create, update or delete route on `bachs_payments` |
| Read another person's payment | `404`: reads are limited to the person who started it, and a reference cannot be guessed |
| Send its own price | Only if you have not set a [before-start flow](/builtin/bachs/react#price-or-refuse-a-payment-on-your-server). With one, the price comes from your server |
| Fake a webhook | The signature fails, and the delivery is refused with `401` |
| Replay a real webhook | The event id was already handled, and nothing changes |
| Start a second payment by retrying | An [idempotency key](/builtin/bachs/sdk#retries-and-idempotency) gives back the first payment |

## Statuses

| Status | Meaning |
| --- | --- |
| `pending` | Started and waiting for the buyer. A failed card attempt leaves it pending, because the checkout stays open for another try |
| `paid` | Bachs confirmed it, and the amount, currency and reference matched |
| `flagged` | Bachs completed the checkout but the amount, currency or reference does not match. Look at it before doing anything |
| `expired` | The checkout expired unpaid |
| `cancelled` | Cancelled before it was completed |
| `failed` | Bachs refused to create the checkout |

`pending` is the only status that can still change.

## Security

| Protection | How |
| --- | --- |
| Your Bachs key never leaves the server | It is sealed at rest, is not in your secrets, is never shown again (only its start and end), and is only ever sent to Bachs. The address is worked out from the key (`sk_sandbox_` or `sk_live_`), never read from anything stored |
| Live means https | With a live key, `success_url` and `cancel_url` must be https |
| Abuse is slowed | Starting a payment is rate limited, and one person can only have a set number of unpaid payments open |
| Bookkeeping stays private | The idempotency key and settlement columns are never returned by the API |

### What is up to you

The Overview tab shows these as a checklist.

- **Price on your server.** If you set nothing, the amount the buyer's app sends is the amount charged. Use a [before-start flow](/builtin/bachs/react#price-or-refuse-a-payment-on-your-server) that works the price out from your own data.
- **Limit return addresses** to your own hosts, so a payment cannot send buyers elsewhere afterwards.
- **Limit currencies and amounts** to what you really accept.
- **Fulfil from the event**, not from the redirect. A buyer can close the tab before the redirect; the `bachs.payment.paid` event still fires.
