Both official SDKs ship a `bachs` client. It wraps the [REST endpoints](/builtin/bachs/rest-api) so you call `payments.create(...)` instead of building requests, and it handles the details that are easy to get wrong: the Idempotency-Key, retrying only when it is safe, and waiting for a payment to settle.

| | TypeScript | Python |
| --- | --- | --- |
| Package | `@pawabase/client` 0.9.0 or later | `pawabase` 0.11.0 or later |
| Entry | `pawabase.bachs.payments` | `pb.bachs.payments` |
| Async | Every method returns a promise | Same methods on `AsyncPawabase`, awaited |

<Note>
The client starts payments and reads what Pawabase recorded. It never decides a payment is paid: only Pawabase does, after it has asked Bachs. See [How a payment is verified](/builtin/bachs/verification).
</Note>

## Set up the client

Use a publishable key in an app, with the buyer signed in. Payments belong to the person who starts them, so the client needs a signed-in person (or a server acting as one). For a public checkout with no accounts, the project can allow [guest payments](/builtin/bachs/react#guest-payments).

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";

const pawabase = createClient({
  url: "https://api.example.com",
  project: "01JC4…",
  apiKey: "pb_pk_…",
});
await pawabase.auth.signInWithPassword({ email, password });
```

```python Python
from pawabase import Pawabase, AsyncPawabase

pb = Pawabase("https://api.example.com", "pb_pk_…", project="01JC4…")
pb.auth.sign_in_with_password(email="ada@example.com", password="…")

# asyncio
async with AsyncPawabase("https://api.example.com", "pb_pk_…", project="01JC4…") as apb:
    await apb.auth.sign_in_with_password(email="ada@example.com", password="…")
```
</CodeGroup>

## Start a payment

<CodeGroup>
```typescript TypeScript
const started = await pawabase.bachs.payments.create({
  amount: "5000.00",
  currency: "NGN",
  successUrl: "https://shop.example.com/thanks",
  cancelUrl: "https://shop.example.com/cart",
  email: "ada@example.com",
  name: "Ada Obi",
  description: "Order 77",
  metadata: { orderId: "77" },
  idempotencyKey: "order-77",
});

started.checkoutUrl; // send the buyer here
started.reference;   // keep it: it finds the payment later
started.replayed;    // true when this key had already started the payment
```

```python Python
started = pb.bachs.payments.create(
    amount="5000.00",
    currency="NGN",
    success_url="https://shop.example.com/thanks",
    cancel_url="https://shop.example.com/cart",
    email="ada@example.com",
    name="Ada Obi",
    description="Order 77",
    metadata={"order_id": "77"},
    idempotency_key="order-77",
)

started["checkout_url"]   # send the buyer here
started["reference"]      # keep it: it finds the payment later
started["replayed"]       # True when this key had already started the payment
```
</CodeGroup>

| Option | | |
| --- | --- | --- |
| `amount` | required | A decimal such as `"5000.00"`. A number is sent as its text |
| `currency` | required | Three letters, such as `NGN` |
| `successUrl` / `success_url` | required | Where Bachs sends the buyer after paying |
| `cancelUrl` / `cancel_url` | optional | Where Bachs sends a buyer who leaves |
| `email`, `name`, `description` | optional | Prefill the checkout and are kept on the payment |
| `metadata` | optional | Any JSON object, kept on the payment and returned on its events |
| `idempotencyKey` / `idempotency_key` | optional | See [Retries](#retries-and-idempotency) |

What comes back:

| Field | Meaning |
| --- | --- |
| `paymentId` / `payment_id` | The payment's id in your `bachs_payments` table |
| `reference` | The payment's reference, unique, used to read it |
| `status` | `pending` for a new payment |
| `checkoutUrl` / `checkout_url` | The Bachs checkout to send the buyer to |
| `expiresAt` / `expires_at` | When the checkout stops accepting payment |
| `replayed` | `true` when an earlier request with the same key made this payment |

TypeScript results use camelCase for what the client returns and takes. Python uses snake_case throughout. The payment rows you read back are rows of your table, so their columns are snake_case in both.

## Read a payment

<CodeGroup>
```typescript TypeScript
const payment = await pawabase.bachs.payments.get("bp_Qz…");
payment.status;         // "pending" | "paid" | "flagged" | "expired" | "cancelled" | "failed"
payment.paid_at;
payment.payment_method;
payment.metadata;
```

```python Python
payment = pb.bachs.payments.get("bp_Qz…")
payment["status"]
payment["paid_at"]
payment["payment_method"]
payment["metadata"]
```
</CodeGroup>

`get` reads one of the signed-in person's own payments. If the payment is still `pending`, Pawabase asks Bachs before answering, so the result is right even when the webhook has not arrived yet. Another person's reference answers `404`.

## Wait for the outcome

`waitFor` / `wait_for` calls `get` every couple of seconds until the payment is no longer pending, then returns it.

<CodeGroup>
```typescript TypeScript
import { TimeoutError } from "@pawabase/client";

try {
  const payment = await pawabase.bachs.payments.waitFor(reference, {
    until: ["paid", "expired", "cancelled"],
    intervalMs: 2000,
    timeoutMs: 120_000,
  });
  if (payment.status === "paid") showReceipt(payment);
} catch (error) {
  if (error instanceof TimeoutError) showStillWaiting();
  else throw error;
}
```

```python Python
try:
    payment = pb.bachs.payments.wait_for(
        reference,
        until=["paid", "expired", "cancelled"],
        interval=2.0,
        timeout=120.0,
    )
except TimeoutError:
    show_still_waiting()
```
</CodeGroup>

| Option | Default | |
| --- | --- | --- |
| `until` | any status other than `pending` | Stop at these statuses instead |
| `timeoutMs` / `timeout` | 120 seconds | How long to wait before giving up |
| `intervalMs` / `interval` | 2 seconds | Time between checks |
| `signal` (TypeScript) | none | An `AbortSignal` to stop waiting |

Each check goes through Pawabase to Bachs, so `waitFor` does not depend on the webhook. It is a good fit for the page a buyer lands on after paying. For fulfilment (granting access, shipping), react to the [event](/builtin/bachs/react#react-to-a-payment) on the server instead: it fires once, even if the buyer never comes back.

## List payments

<CodeGroup>
```typescript TypeScript
const page = await pawabase.bachs.payments.list({ status: "paid", page: 1, perPage: 20 });
for (const payment of page.data) console.log(payment.reference, payment.amount);
```

```python Python
page = pb.bachs.payments.list(status="paid", page=1, per_page=20)
for payment in page.data:
    print(payment["reference"], payment["amount"])
```
</CodeGroup>

Newest first, and only the signed-in person's own payments. For anything beyond this, query the `bachs_payments` table like any other: `pawabase.from("bachs_payments")`.

## Retries and idempotency

Networks drop responses and people double-click. The client makes starting a payment safe to repeat.

- Every `create` sends an `Idempotency-Key`. If you do not pass one, the client makes one.
- Because the key makes a repeat harmless, the client **retries** a `create` after a dropped connection or a `502`, `503` or `504`, with the same key. The retry gives back the payment the first attempt made, never a second one.
- Asking again with the same key and the same payment returns the first payment with `replayed` true.
- The same key for a *different* payment (another amount, say) is refused with `409` and the code `idempotency_conflict`, and nothing is created.

A key made for you protects the client's own retries. To protect a retry made by *your* code (a job that runs twice, a form submitted twice), pass a key that comes from the thing being bought:

<CodeGroup>
```typescript TypeScript
await pawabase.bachs.payments.create({ amount, currency, successUrl, idempotencyKey: `order-${order.id}` });
```

```python Python
pb.bachs.payments.create(amount=amount, currency=currency, success_url=url, idempotency_key=f"order-{order.id}")
```
</CodeGroup>

A key is 1 to 128 letters, digits and `_ . : -`, and belongs to the person who sent it.

<Warning>
On an install that has not taken [the latest update](/builtin/bachs/operate#updates), the table cannot store the key, so the key is ignored and a repeat can start a second payment. Update Bachs in Studio to switch idempotency on.
</Warning>

## Errors

A refused request throws. Check `status` and `code` to decide what to tell the buyer.

<CodeGroup>
```typescript TypeScript
import { ApiError } from "@pawabase/client";

try {
  await pawabase.bachs.payments.create({ amount, currency, successUrl });
} catch (error) {
  if (error instanceof ApiError && error.status === 422) showMessage(error.message); // a rule refused it, and says which
  else throw error;
}
```

```python Python
from pawabase import PawabaseError

try:
    pb.bachs.payments.create(amount=amount, currency=currency, success_url=url)
except PawabaseError as error:
    if error.status_code == 422:  # a rule refused it, and says which
        show_message(error.message)
    else:
        raise
```
</CodeGroup>

| Status | Meaning |
| --- | --- |
| `401` | Nobody is signed in, and guest payments are off |
| `403` | Your [before-start flow](/builtin/bachs/react#price-or-refuse-a-payment-on-your-server) refused the payment |
| `404` | Bachs is not installed here, or the reference is not the signed-in person's |
| `409` | `idempotency_conflict`, or `idempotency_in_progress` while a first attempt is still starting |
| `422` | A [setting](/builtin/bachs/react#settings) refused it (currency, amount range, redirect host, missing email), or the body is invalid. The message says which |
| `429` | Too many payments started, or too many unpaid ones open |
| `502` | Pawabase could not reach Bachs. Nothing was recorded as paid: try again |
| `500` | `before_start_missing`: the before-start flow you chose was deleted |
| `503` | Bachs is not connected here |

## A complete server-side flow

A common shape: the browser asks your server to start a payment, so the server sets the price from your own data.

<CodeGroup>
```typescript TypeScript
// server.ts: acts as the signed-in buyer, using their access token
import { createClient } from "@pawabase/client";

export async function startCheckout(accessToken: string, orderId: string) {
  const pawabase = createClient({ url, project, apiKey: process.env.PAWABASE_PUBLISHABLE_KEY!, accessToken });
  const order = await loadOrder(orderId);

  return pawabase.bachs.payments.create({
    amount: order.total,
    currency: order.currency,
    successUrl: `https://shop.example.com/orders/${orderId}/thanks`,
    metadata: { orderId },
    idempotencyKey: `order-${orderId}`,
  });
}
```

```python Python
# server.py: acts as the signed-in buyer, using their access token
from pawabase import Pawabase

def start_checkout(access_token: str, order_id: str):
    pb = Pawabase(URL, PUBLISHABLE_KEY, project=PROJECT).as_user(access_token)
    order = load_order(order_id)

    return pb.bachs.payments.create(
        amount=order.total,
        currency=order.currency,
        success_url=f"https://shop.example.com/orders/{order_id}/thanks",
        metadata={"order_id": order_id},
        idempotency_key=f"order-{order_id}",
    )
```
</CodeGroup>

Even better, let the amount be decided inside Pawabase with a [before-start flow](/builtin/bachs/react#price-or-refuse-a-payment-on-your-server), so a client can never choose its own price.
