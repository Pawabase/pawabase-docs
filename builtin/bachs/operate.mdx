## Updates

Pawabase improves the Bachs integration over time. An install **keeps working as it is** until you choose to update, and opening Bachs, using it or receiving a webhook never changes your tables. See [Updates never break an install](/builtin/how-they-work#updates-never-break-an-install) for the guarantee.

When a newer release exists, the Bachs page shows **An update is available for Bachs**, describes what changes, and waits. Choose **Update Bachs** when you are ready.

An update adds columns to your `bachs_payments` table and keeps every row. If one of your tables has been changed so that it cannot be updated (a column deleted by hand, say), Pawabase says which and changes nothing.

### Releases

| Release | What it adds |
| --- | --- |
| 2 | Safe retries (an `Idempotency-Key` never starts a second payment) and settlement the database applies once. Adds four internal columns to `bachs_payments`: `idempotency_key`, `request_hash`, `settle_token`, `checkout_request`. They are never returned by the API |
| 1 | The first release |

Until an install updates to release 2, payments start, read and settle as before; only the new safeguards are off.

<Tip>
You can also update from the API: `POST /platform/v1/envs/{env}/integrations/bachs/update`, with a key that can manage the environment.
</Tip>

## Going live

Install with a sandbox key while you build. When you are ready:

1. Open **Connection**, paste the live key (`sk_live_…`) and choose **Replace key**. Bachs checks the key first, and Pawabase switches to Bachs's live address with it.
2. Bachs's sandbox and live environments share nothing, so open **Webhook** and create the endpoint again for live.
3. Check **Settings**: with a live key, `success_url` and `cancel_url` must be https.

Do this in your production environment, which has its own connection. Your development environment keeps its sandbox key.

## Disconnecting

**Connection → Disconnect** stops the payment endpoints and refuses Bachs's webhook. Your two tables and every payment in them are kept. You can install again later, and Pawabase reuses the tables.

## If something does not work

| You see | Because |
| --- | --- |
| "Bachs does not accept this key" | The key is wrong, or it is a live key where a sandbox one is expected, or the reverse |
| "This key can't read or create payments" | The key lacks the payments scopes |
| "Bachs can't be installed here because these are already in use" | A table called `bachs_payments` or `bachs_events` exists and does not fit. The message says what is missing or wrong; fix it or rename the table |
| The webhook says "manual" | Your server is not reachable over https from the internet, or the key cannot manage webhooks. Add the endpoint in Bachs and paste its signing secret |
| A payment stays `pending` after paying | Look at **Events** for the delivery and **Webhook** for the count of genuine deliveries. Reading the payment, or **Check with Bachs**, also settles it |
| `502 bachs_unavailable` | Pawabase could not reach Bachs to confirm. Nothing was marked paid; try again |
| A payment is `flagged` | Bachs completed a checkout whose amount, currency or reference does not match what was recorded. Open it on the **Payments** tab and compare with Bachs before doing anything |
| `409 idempotency_conflict` | The same `Idempotency-Key` was used for a different payment. Use a new key per thing bought |
| A repeated key started a second payment | The install has not taken release 2, so the table cannot store the key. Update Bachs |
| The table `bachs_payments` is shown as missing | Someone deleted it. Restore it from **Data → Tables → Recently deleted**, or install again |

## Not covered yet

This integration takes one-off payments. Subscriptions, refunds and payouts are separate Bachs features that it does not use yet.
