The SDKs call these endpoints for you ([SDK](/builtin/bachs/sdk)). Use them directly from any language that can send HTTP.

Every request to `/rest/v1` carries your project's headers, and the buyer's access token:

```bash
-H "apikey: $PAWABASE_KEY" -H "x-project-id: $PAWABASE_PROJECT" -H "Authorization: Bearer $ACCESS_TOKEN"
```

## Start a payment

`POST /rest/v1/bachs/payments`

```bash
curl -X POST "$URL/rest/v1/bachs/payments" \
  -H "apikey: $PAWABASE_KEY" -H "x-project-id: $PAWABASE_PROJECT" \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H "content-type: application/json" \
  -H "Idempotency-Key: order-77" \
  -d '{"amount":"5000.00","currency":"NGN","success_url":"https://shop.example.com/thanks","email":"ada@example.com","metadata":{"order_id":"77"}}'
```

| Field | | |
| --- | --- | --- |
| `amount` | required | A decimal string above zero, such as `"5000.00"` |
| `currency` | required | Three letters |
| `success_url` | required | Where Bachs sends the buyer after paying. Bachs adds `?checkout_id=…`, which is a token from the hosted checkout address, not the `chk_…` id. Look the payment up by your own `reference`, never by that value |
| `cancel_url` | optional | Where Bachs sends a buyer who leaves |
| `email` | optional | Prefills the checkout. Required if the [setting](/builtin/bachs/react#settings) says so |
| `name`, `description` | optional | Kept on the payment |
| `metadata` | optional | A JSON object up to about 4 KB |
| `idempotency_key` | optional | The same as the `Idempotency-Key` header |

Answer, `201`:

```json
{
  "payment_id": "01JC4…",
  "reference": "bp_Qz…",
  "status": "pending",
  "checkout_url": "https://checkout.bachs.io/…",
  "expires_at": "2026-11-20T12:00:00Z"
}
```

A repeat of the same key for the same payment answers `200` with the same body, an `Idempotent-Replayed: true` header, and `"replayed": true`.

| Status | Code | Meaning |
| --- | --- | --- |
| `401` | `unauthenticated` | Nobody is signed in, and the project has not allowed [guest payments](/builtin/bachs/react#guest-payments) |
| `403` | | The before-start flow refused it |
| `409` | `idempotency_conflict` | The key was used for a different payment |
| `409` | `idempotency_in_progress` | The first attempt with this key is still starting |
| `422` | `invalid` | A rule refused it; the message says which |
| `429` | `too_many_pending` | The person has too many unpaid payments open |
| `429` | | Starting payments is rate limited |
| `500` | `before_start_missing` | The before-start flow was deleted |
| `502` | `bachs_unavailable` | Bachs could not be reached; the payment is recorded as `failed` and can be retried with the same key |
| `503` | `not_connected` | Bachs is not connected here |

## Read a payment

`GET /rest/v1/bachs/payments/{reference}`

```json
{
  "payment": {
    "id": "01JC4…",
    "reference": "bp_Qz…",
    "user_id": "…",
    "email": "ada@example.com",
    "amount": "5000.00",
    "currency": "NGN",
    "status": "paid",
    "checkout_id": "…",
    "checkout_url": "https://checkout.bachs.io/…",
    "expires_at": "…",
    "charge_id": "…",
    "payment_method": "card",
    "paid_at": "…",
    "failure": null,
    "metadata": { "order_id": "77" }
  }
}
```

Only the person who started the payment can read it; anyone else gets `404`. If the payment is `pending`, Pawabase asks Bachs and settles it before answering.

## List payments

The `bachs_payments` table is an ordinary resource with only `list` and `get`, limited to the signed-in person's own rows:

```bash
curl "$URL/rest/v1/bachs_payments?filter[status]=eq.paid&sort=-created_at&per_page=20" \
  -H "apikey: $PAWABASE_KEY" -H "x-project-id: $PAWABASE_PROJECT" -H "Authorization: Bearer $ACCESS_TOKEN"
```

Its internal columns (the idempotency key and settlement bookkeeping) are never returned. There is no create, update or delete route, so a client cannot write a payment.

## The webhook

Bachs delivers to `POST /hooks/v1/{env}/bachs`. Pawabase handles it; you never call it. Its address is on the **Webhook** tab. It answers `200` when a delivery was handled (or was a repeat), and `401` for a signature that does not check, so Bachs does not retry a forgery. It answers `409`, `502` or similar when Bachs should try again.

The events it acts on are `collection.succeeded`, `collection.failed`, `checkout.completed` and `checkout.expired`. Anything else is recorded in `bachs_events` and ignored. How a delivery is trusted is on [How a payment is verified](/builtin/bachs/verification).
