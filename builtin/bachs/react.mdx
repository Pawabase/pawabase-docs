The Bachs logic is built into Pawabase, so you do not edit it. You shape it through three interfaces: **settings** it checks every payment against, a **before-start flow** you write, and **events** your flows react to.

## Settings

Set these on the **Settings** tab. Every payment is checked against them before Bachs is asked, whether it came from your app or from the Studio test.

| Setting | Meaning | Default |
| --- | --- | --- |
| Accepted currencies | Such as NGN and USD. A payment in another currency is refused | any currency Bachs supports |
| Smallest and largest amount | A payment outside the range is refused | none |
| Allowed redirect hosts | `success_url` and `cancel_url` must be on one of these hosts | any |
| Checkout stays open for | Minutes, 1 to 1440 | 60 |
| Require the buyer's email | Refuse a payment started without one | off |
| Unpaid payments one person may have open | A person at this number cannot start another until one is paid or expires. `0` is no limit. A guest is counted by the email they gave | 20 |
| Allow guest payments | Let someone who is **not signed in** start a payment: see [Guest payments](#guest-payments) | off |
| Guest payment starts per minute | With guest payments on: how many payments one address may start in a minute without signing in (1 to 60). Signed-in people may start 20 | 5 |

A refused payment answers `422` and says which rule it broke. Nothing is recorded, and Bachs is not asked.

## Guest payments

By default only a **signed-in person** (a user of your own app) can start a payment, and each payment belongs to that person: only they can read it, and the `bachs_payments` table only shows them their own rows. A request with nobody signed in is answered `401`.

That is the wrong shape for a public checkout, a donation page or an invoice link, where the buyer has no account. Turn on **Allow guest payments** in Settings (or send `"allow_guest_payments": true` to the settings endpoint) and anyone can start a payment:

<CodeGroup>
```bash HTTP
# No Authorization header: only your project's publishable key
curl -s https://api.example.com/rest/v1/bachs/payments \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-1042" \
  -d '{"amount": "2500.00", "currency": "NGN", "email": "ada@example.com", "success_url": "https://shop.example.com/thanks"}'
# → 201 {"reference": "bp_…", "checkout_url": "https://checkout.bachs.io/c/…", "status": "pending", …}
```

```typescript TypeScript (SDK)
// A client with only a publishable key and nobody signed in
const pawabase = createClient({ url, project, apiKey: "pb_pk_…" });
const { checkoutUrl, reference } = await pawabase.bachs.payments.create({ amount: "2500.00", currency: "NGN", email: "ada@example.com", successUrl: "https://shop.example.com/thanks" });
```
</CodeGroup>

What changes for a guest payment, and what does not:

| | Signed-in payment | Guest payment |
| --- | --- | --- |
| Owner | The person who started it (`user_id` is set) | Nobody (`user_id` is empty) |
| Who can read it | Only that person | Anyone who holds its `reference`, through `GET /rest/v1/bachs/payments/{reference}`. The reference is a long random token, so treat it like a receipt link |
| In the table API | The person's own rows | Not listed to anyone: read it by reference, or in Studio |
| Open-payment limit | Per account | Per email (a guest who gives no email is held back only by the rate limit) |
| Rate limit on starting | 20 a minute per person | **5 a minute per address** by default (`guest_starts_per_minute`), counted apart from signed-in people |
| Idempotency keys | Belong to the person | Belong to the email, so two guests can reuse the same key without meeting |
| Verified and marked paid | By Pawabase, after asking Bachs | **The same.** Who the buyer is has no part in it |

Turning the setting off again stops new guests but does not lock anyone out of a receipt link they already have.

<Warning>
An open start route lets anyone create checkouts. When you allow guests, also **require the buyer's email**, **price the payment in a [before-start flow](#price-or-refuse-a-payment-on-your-server)** so the browser doesn't decide the amount, and limit currencies and amounts. Guests also get a stricter rate limit of their own, **5 payment starts a minute per address** by default: lower it with `guest_starts_per_minute` if your checkout needs fewer. Past it, a start is answered `429` with `Retry-After`.
</Warning>

## Price or refuse a payment on your server

Choose one of your own flows as the **before-start flow**. Pawabase asks it about every payment before the payment begins. Start it with a **Manual** trigger and end it with a **Respond** block (or a **Fail** block to refuse).

It receives:

| Input | Meaning |
| --- | --- |
| `amount`, `currency` | What the buyer's app asked for |
| `email`, `name`, `description`, `metadata` | As sent |
| `success_url`, `cancel_url` | As sent |
| `user_id` | Who is paying |
| `studio` | `true` for the Studio test payment |

It may return:

| Return | Effect |
| --- | --- |
| `{"amount": "250.00", "currency": "NGN"}` | The payment is for that, whatever the buyer's app said. Work it out from your own database here |
| `{"metadata": {"order_id": "…"}}` | Added to the payment's metadata |
| `{"allow": false, "message": "Sold out"}` | Refused with `403` and that message |
| A **Fail** block (`status`, `message`) | Refused with that status and message |

What it returns is held to the [settings](#settings) above, so a flow cannot price a payment outside your limits. If the flow you chose is later deleted, payments stop with a `500` `before_start_missing` error instead of starting without your rule.

A typical use is pricing from an order the buyer sent only the id of:

<CodeGroup>
```typescript TypeScript
// The buyer's app sends no price at all: only what it is buying.
await pawabase.bachs.payments.create({
  amount: "1", // replaced by the flow
  currency: "NGN",
  successUrl: "https://shop.example.com/thanks",
  metadata: { orderId: "77" },
});
```

```python Python
pb.bachs.payments.create(
    amount="1",  # replaced by the flow
    currency="NGN",
    success_url="https://shop.example.com/thanks",
    metadata={"order_id": "77"},
)
```
</CodeGroup>

The flow reads `metadata.order_id`, looks the order up, and returns its real `amount` and `currency`.

## React to a payment

Pawabase emits an event for each outcome. Build a flow that starts on it (a `trigger.event` block) to fulfil the order, send a receipt or grant access.

| Event | When |
| --- | --- |
| `bachs.payment.created` | A payment was started and has a checkout |
| `bachs.payment.paid` | A payment was confirmed |
| `bachs.payment.flagged` | A completed checkout did not match |
| `bachs.payment.expired` | A checkout expired |
| `bachs.payment.cancelled` | A checkout was cancelled |

Each carries `reference`, `payment_id`, `user_id`, `email`, `amount`, `currency`, `status` and your `metadata`. `bachs.payment.paid` also carries `charge_id`.

`bachs.payment.paid` fires **once** per payment, even if Bachs delivers the webhook twice, the buyer refreshes, and a read settles it at the same moment. It is the right place to do things that must not happen twice: grant access, ship, email a receipt.

`bachs.payment.flagged` is the one to alert on: Bachs says it was paid but the amount, currency or reference is not what Pawabase recorded. Look at it before doing anything.

## Build on the table

`bachs_payments` is yours. Join it to your orders, report on it, or trigger flows from its rows.

```sql
select o.id, o.customer, p.amount, p.paid_at
from orders o
join bachs_payments p on p.metadata ->> 'order_id' = o.id::text
where p.status = 'paid';
```

You can read it in SQL and over REST. You cannot create, edit or delete rows through the API, which is what keeps `status` trustworthy.
