An **integration** replaces code you would otherwise write. Taking a payment, for example, is not one API call: you start a checkout, store the payment, receive a webhook, check that it is genuine, guard against a repeat, and only then mark the order paid. Every project that takes payments writes that same code, and a mistake in it costs money.

An integration is that code, written once by Pawabase, tested, and installed into your project from Studio. You paste the service's key, and the rest exists.

## Where they are

Open **Integrations** in Studio's sidebar. Each integration is a card with its logo, what it does and its tags. Choose one to connect it, and once it is installed the same page becomes its workspace: its overview, its data, what it is receiving, its settings and how to call it from your app.

| Integration | What it does for you |
| --- | --- |
| [Bachs](/builtin/bachs/get-started) | Take payments with [Bachs](https://bachs.io): hosted checkout, verified webhooks, safe retries, and a payment is marked paid only after Bachs confirms it |

More are on the way. They all follow the shape described here.

## What an integration is made of

<CardGroup cols={2}>
  <Card title="A connection" icon="key">The service's key, sealed and kept by Pawabase. It is never shown again, never placed in your project's secrets, and only ever sent to that service.</Card>
  <Card title="Logic that is Pawabase's" icon="shield-check">The endpoints, the webhook and the checks run as Pawabase's own code. They are not flows, routes or webhooks in your project, so nothing in your project can change or delete them by accident.</Card>
  <Card title="Tables that are yours" icon="table">The data lives in ordinary tables in your database. You read them, query them, join them and build on them like any other table.</Card>
  <Card title="Interfaces for your rules" icon="sliders-horizontal">Settings, a flow that is asked before something happens, and events that tell your flows what happened. This is how a project shapes the integration without editing it.</Card>
</CardGroup>

Read [How integrations work](/builtin/how-they-work) for the reasoning, and for what happens when an integration is updated.

## Use one from your app

Each integration has a small client in the Pawabase SDKs, so you call it by name instead of writing HTTP requests.

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";

const pawabase = createClient({ url, project, apiKey });

const { checkoutUrl, reference } = await pawabase.bachs.payments.create({
  amount: "5000.00",
  currency: "NGN",
  successUrl: "https://shop.example.com/thanks",
});
```

```python Python
from pawabase import Pawabase

pb = Pawabase(url, api_key, project=project)

started = pb.bachs.payments.create(
    amount="5000.00",
    currency="NGN",
    success_url="https://shop.example.com/thanks",
)
```
</CodeGroup>

The integration must be installed in the environment you are calling: until then its endpoints do not exist.

<Note>
`pawabase.bachs` needs `@pawabase/client` 0.9.0 or later, and `pb.bachs` needs the Python `pawabase` package 0.11.0 or later.
</Note>

## What you can and cannot change

| You can | You cannot |
| --- | --- |
| Set the rules it exposes (currencies, limits, where buyers are sent back) | Edit its endpoints or its checks |
| Give it a flow of yours to ask before it acts | Replace its endpoints with a route of your own: the path is reserved |
| React to its events with your own flows | Write to the fields it owns, such as a payment's status, through the API |
| Read, query and report on its tables | Delete its tables while it is installed without it noticing: Studio shows the table as missing |
| Disconnect it, keeping your data | |
