This page explains the design behind every integration. You do not need it to use one, but it answers the questions that come up once you build on one: where the code is, what you may edit, and what happens when Pawabase releases a new version.

## The logic is not in your project

An integration's endpoints and checks are built into Pawabase. Your project's **Flows**, **Routes** and **Webhooks** pages do not list them, and installing one adds nothing to those pages.

That is deliberate. Code a project can edit is code a project can break, and for something like settling a payment, a small edit can mean marking unpaid orders paid. Keeping the logic in Pawabase means:

- It is tested once, for everyone.
- It cannot be deleted or changed by accident, by a teammate or by an automated edit.
- A route you define cannot take the place of one of its endpoints. Defining a route on a reserved path is refused when the environment compiles, with a message naming the integration.
- A fix reaches every project through an [update](#updates-never-break-an-install) that you choose to apply.

## The data is yours

Installing an integration creates ordinary tables in your database. Bachs creates `bachs_payments` and `bachs_events`. They appear in **Data → Tables** and behave like any table you made:

- Read them through the REST API, subject to the access rules the integration set (a person can read only their own payments).
- Query them in SQL, join them to your own tables, and report on them.
- Build flows that trigger on their rows.

What you cannot do is write the fields the integration owns. The tables have no create, update or delete route, so a browser cannot write a payment's status. Only the integration's own code does, and only through the checks described on its page.

### Tables you already have

If a table with the integration's name already exists, Pawabase looks at it before refusing:

| What it finds | What happens |
| --- | --- |
| No such table | It is created |
| A table that has every column the integration writes, with the right types, and does not let clients create, change or delete rows | It is **reused**, with its data. Nothing is overwritten |
| A table that does not fit | Installing stops and says exactly why (a missing column, a wrong type, or an API that lets clients write rows). Nothing is changed |

If you deleted a table's definition earlier and its database table is still there, Studio explains that too, instead of leaving you with a conflict you cannot see.

## Interfaces: how you shape it

Instead of editing the logic, you are given places to put your own rules.

| Interface | What it is | Example (Bachs) |
| --- | --- | --- |
| **Settings** | Values the integration checks every request against | Accepted currencies, smallest and largest amount, allowed redirect hosts |
| **A before-start flow** | One of your flows, asked before the integration acts. It can refuse, or fill in values on the server | Price a payment from your own database, or refuse one |
| **Events** | What the integration announces, for your flows to react to | `bachs.payment.paid` |
| **Your tables** | The data, to query and join | `bachs_payments` |

If a flow you chose is deleted, the integration fails closed: it stops with an error rather than carrying on without your rule.

## Updates never break an install

Pawabase will release newer versions of an integration: a new safeguard, a new field. Two promises hold for every release.

**Nothing changes until you choose.** Each install remembers the release it was installed at. Opening the integration, using it, or receiving a webhook never alters your tables. When a newer release exists, Studio shows an **update is available** notice that says what the release changes, and waits. The tables change only when you press **Update**.

**An install keeps working while it waits.** Newer releases only ever add to your tables, never remove or retype what an earlier release created, and the integration's code works without what a release adds. A project that has not updated runs exactly as it did, minus the newer safeguards.

When you do update, Pawabase adds the new columns to your table and keeps every row. If one of your tables has been changed in a way that stops the update (a column deleted, say), it tells you which and changes nothing.

<Note>
For Bachs, release 2 added safe retries and database-level settlement. Until you update an older install, a repeated `Idempotency-Key` is ignored (the table has nowhere to keep it) and settlement uses a per-payment lock inside one server process rather than the database. Everything else works.
</Note>

## Disconnecting

Disconnecting stops the integration's endpoints and refuses its webhook. Your tables and everything in them stay, and you can install again later; an install that finds its own tables reuses them.

## Where the key lives

The service's key and any signing secret are sealed by Pawabase. They are not part of your project's secrets, so they do not appear in **Secrets**. Studio shows only the start and end of a key. Each environment has its own connection, so a sandbox key in development and a live key in production never mix.
