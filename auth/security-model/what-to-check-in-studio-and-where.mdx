Every setting referenced above is editable in Studio. The page is **Users &
auth**, and the settings live under the **Configuration** tab.

<Steps>
  <Step title="The Sign-up section decides who can get an account">

The section is described as *"Who can create an account, and whether their email
must be confirmed first."*

Two switches: **Sign-up enabled**, hinted *"Turn off to invite-only new
accounts."*, and **Require email verification**, hinted *"Unverified users can't
sign in until they confirm."*

Turning sign-up off is the single highest-value switch for a public-facing
application that should only have invited users. With it off, `POST /auth/v1/signup`
is a `403` and the social callback will not create accounts either — both paths
respect it.

  </Step>

  <Step title="The Passwords section is where lifetimes and policy live">

Described as *"Password strength and how long sessions last."* This is where
**Policy** (segmented **Basic** / **Strict**), **Minimum length**, **Access token
lifetime** and **Refresh token lifetime** are set.

Access token lifetime is the one to think hardest about: it is your revocation
latency against every service, because verification is local. Fifteen minutes is a
reasonable default for anything sensitive.

  </Step>

  <Step title="The Sign-in methods section gates what users can enrol in">

**Magic links**, hinted *"Passwordless sign-in by emailed one-time link."*, and
**MFA (TOTP)**, hinted *"Let users add an authenticator app for aal2."*

Turning MFA off here does not remove MFA from users who already enrolled — it
means they are no longer *challenged*. If you want the factors gone, that is an
administrative action per user, not a switch.

  </Step>

  <Step title="The URLs section is the redirect allowlist">

Described as *"Where a browser is allowed to land after an OAuth or magic-link
redirect."* **Site URL** takes your application's base URL, and **Additional
allowed redirect URLs** takes the extra prefixes.

This is where the prefix-matching rule bites. A redirect to a path under your site
URL is allowed; a redirect to a lookalike domain is not, and does not become
allowed by being similar.

  </Step>

  <Step title="The Sign-in activity tab is your compromise early-warning system">

Columns **When**, **Event**, **Email**, **Result**, **IP**, with a **failures
only** checkbox.

The Result badge renders `ok` in green for a success and the `reason` string in
red for anything else. Reuse-detection messages appear here and nowhere else,
which makes this the only place a stolen-token replay is visible.

  </Step>
</Steps>

<Warning>
Auth configuration is cached for **10 seconds**. A change made in Studio can take
that long to affect new tokens, which regularly looks like a failed edit. It also
means the cache is shared: a change affects every environment user whose key
matches, not just your own session.
</Warning>

### Configuration keys that do not exist

Worth listing explicitly, because several of these are named in older material
and hunting for them in Studio wastes an afternoon:

| Not a real setting | What is real instead |
| --- | --- |
| `refresh_token_rotation` | Rotation is unconditional; nothing to configure |
| No `require_aal` or `min_aal` setting | Check the `aal` claim yourself in a policy |
| `recovery_token_ttl` | The `recovery` purpose's lifetime is 1 hour, fixed |
| `magic_link_ttl` | The `magic` purpose's lifetime is 15 minutes, fixed |
| `mfa_failed_attempts_lockout` | Failed MFA codes use the same `lockout_threshold` |
| `access_token_ttl` / `refresh_token_ttl` | `access_ttl` / `refresh_ttl` |
| A `RevokedToken` table | Revocation lives in `jwt_tokens` and `akz_sessions` |
| A `theft_detected` session flag | Revocation plus the `session.reuse_detected` event |


## Events to subscribe to

The complete set of events the auth service emits. Subscribing to a name that is
not here is a silent no-op, so this list is worth keeping.

| Event | Emitted when |
| --- | --- |
| `user.created` | An account is created — by sign-up, social, or admin |
| `user.updated` | A self-service profile update; payload carries what changed |
| `user.deleted` | An account is deleted by an administrator |
| `user.verified` | An email address is confirmed |
| `user.email_changed` | A pending address change is confirmed |
| `user.password_changed` | A password is changed by the user |
| `user.password_reset` | A password is set through a recovery link |
| `user.signed_in` | A session starts; payload carries the method |
| `user.mfa_enabled` | TOTP enrolment is confirmed |
| `user.mfa_disabled` | MFA is turned off with a current code |
| `user.mfa_reset` | An administrator removes a user's factors |
| `user.disabled` / `user.enabled` | An administrator disables or re-enables an account |
| `session.revoked` | A session, or all sessions, are revoked |
| `session.reuse_detected` | A consumed or revoked refresh token was presented |
| `identity.linked` / `identity.unlinked` | An external identity is attached or removed |
| `organization.created` / `organization.deleted` | Organization lifecycle |
| `invitation.created` / `invitation.accepted` | Invitation lifecycle |

<Warning>
Three events people expect and that **do not exist**: there is no
`token.issued`, no `token.refreshed`, and no `rate_limit_exceeded`. A successful
refresh emits nothing — it is routine, and emitting on every one would flood your
stream. If you need refresh telemetry, read the login-event history instead.
</Warning>


## Verifying the model, rather than trusting the page

A short set of behaviours that are worth confirming against your own deployment,
because each of them is the thing that would hurt most to get wrong. None of them
require reading source; all of them are observable.

<AccordionGroup>
  <Accordion title="A staging token must be rejected by production">
  Sign in against staging, take the `access_token`, and send it to a production
  endpoint. It must be rejected. If it is not, environment isolation is not doing
  what this page claims.

The rejection should come from the `prj`/`env` check, not from a missing session —
which is why the error is indistinguishable from any other authentication failure.
  </Accordion>

  <Accordion title="A revoked session must be unable to refresh">
  Revoke a session, then attempt a refresh with its token. It must fail. This is
  the property that makes revocation meaningful, and it is the one that holds even
  though the old access token still works.

If a revoked session can still refresh, something is wrong with the family
revocation rather than with your client.
  </Accordion>

  <Accordion title="An unknown email must be indistinguishable from a wrong password">
  Compare the two responses closely — status, body, and shape. They should be
  identical. A difference in either is an enumeration oracle, and it is the most
  common finding in an auth review of this kind.
  </Accordion>

  <Accordion title="A consumed refresh token must revoke the family">
  Refresh once, then refresh again with the original token. The second attempt must
  fail **and** the first refresh's token must now also be dead.

The second half is what distinguishes real theft detection from simply rejecting a
stale token, and it is easy to miss when testing.
  </Accordion>

  <Accordion title="Disabling an account must prevent new sign-ins">
  Disable a user and attempt to sign in. It must be refused, and every session must
  be revoked.

Note that access tokens already issued keep working until they expire. That is
expected and is not a failure of the disable.
  </Accordion>

  <Accordion title="An unapproved redirect must not receive tokens">
  Pass a `redirect_to` pointing at a domain you do not control, on the sign-up and
  OAuth paths. Both must refuse it.

For the OAuth callback specifically, the expected behaviour is that the redirect is
silently dropped rather than rejected — so the flow completes with no redirect
target. Confirming it lands nowhere is the point.
  </Accordion>

  <Accordion title="A user must not be able to promote themselves">
  Set a value in `user_metadata` through `PATCH /auth/v1/user`, then read it back
  from the `meta` claim. It will be there, and a policy reading `meta` would trust
  it.

The same value in `app_metadata`, set through the admin route, is not user-writable.
Confirming that asymmetry is what makes the guidance actionable.
  </Accordion>
</AccordionGroup>

<Info>
Every one of these is a two-minute check with curl and a browser. A deployment that
has never had them run is not verified, however well the defaults are set.
</Info>


## Where the boundaries are, summarised

The most compact statement of the whole model:

**Cryptographic and always current** — the signature, the audience, the token type,
the project and environment it belongs to, and its expiry.

**A snapshot, up to `access_ttl` stale** — roles, permissions, organization and
organization role, the assurance level, and anything in `meta` or `app`.

**Enforced immediately, for new sessions only** — account disablement, session
revocation, MFA removal.

**Not enforced at all, because it cannot be** — anything requiring a live lookup:
whether a token was revoked thirty seconds ago, whether an account still exists,
whether the client IP matches the one at sign-in.

**Yours to enforce** — CSRF protection for your own application, XSS resistance,
refresh serialisation, maximum session age, and any MFA requirement, since there is
no declarative way to demand an assurance level.

<Warning>
If you take one thing from this page: the system is deliberately built so that
verification needs no database. Everything that design implies — stale
authorization, bounded revocation latency, no device binding — follows from that
single choice, and each of them is a thing you have to decide about explicitly.
</Warning>
