The complete set, with where it lives and what depends on it. Everything on this
list is in one of three places, and the third is the one people miss.

| Setting | Lives in | Default | Governs |
| --- | --- | --- | --- |
| `signup_enabled` | Environment auth config | `true` | Whether accounts can be created at all |
| `require_email_verification` | Environment auth config | `false` | Whether unverified users may sign in |
| `password_policy` | Environment auth config | `basic` | Strength rule |
| `password_min_length` | Environment auth config | `8` | Length floor |
| `access_ttl` | Environment auth config | `900` | Revocation latency |
| `refresh_ttl` | Environment auth config | `2592000` | How long a token is worth stealing for |
| `magic_link_enabled` | Environment auth config | `true` | Passwordless sign-in |
| `mfa_enabled` | Environment auth config | `true` | Whether enrolment is possible |
| `site_url` | Environment auth config | `""` | The redirect allowlist's primary entry |
| `redirect_urls` | Environment auth config | `[]` | Additional allowed prefixes |
| `default_roles` | Environment auth config | `[]` | Least privilege for a new account |
| `lockout_threshold` | **Installation settings** | `10` | Failed attempts before lockout |
| `lockout_minutes` | **Installation settings** | `15` | Lockout duration |
| `config_ttl` | **Installation settings** | `10` | Auth-config cache lifetime, in seconds |
| `internal_secret` | **Installation settings** | development value | Context tokens, OAuth state, link signatures |
| `jwt_master_secret` | **Installation settings** | development value | Every user-token signing key |
| `master_key` | **Installation settings** | development value | Sealed secrets and TOTP factors |

<Warning>
The split between the last two groups is worth remembering. Password policy is per
environment, so you can give staging a stricter one than production. Lockout
settings are **installation-wide**, so you cannot — changing the threshold changes it
for every environment on that instance at once.
</Warning>

### The cache lag, stated precisely

Auth configuration is cached per environment for `config_ttl` seconds. Everything in
the first block of that table is subject to it.

The consequence worth planning for: **a change is not atomic with your next
request.** After you save a shorter `access_ttl` in Studio, requests for up to ten
seconds still mint tokens under the old value. After you disable sign-up, sign-up
attempts still succeed for up to ten seconds.

The cache is keyed by project and environment, not by user, so a change also shifts
what other administrators observe — you are not testing it in isolation.

<Note>
An unset key silently falls back to its default rather than being an error, which is
the answer to "why didn't turning this off work". `/auth/configuration` covers the
full set and where each one is edited.
</Note>

## Misleading errors, and what they hide

The auth surface deliberately collapses several different causes into one response.
That is right for security and wrong for debugging, so a table of what each message
is really saying earns its place.

| What you see | What it might actually be |
| --- | --- |
| `400 invalid email or password` | Unknown email **or** wrong password |
| `401 invalid refresh token` | Expired, malformed, consumed, revoked, wrong environment, or deleted account |
| `403 this account is disabled` | Also covers accounts deactivated by a soft delete |
| `403 you are not a member of that organization` | Organization does not exist **or** you are not a member |
| `400 the link is invalid or has expired` | Wrong, used, expired, or wrong-purpose token |
| `429 too many failed attempts` | Account lockout; **not** the rate limit |
| `429 rate_limit_exceeded` | The IP bucket; **not** the account |
| `401 the account is not available` | Disabled **or** soft-deleted |
| `401 the session was revoked` | Minted after rotation, then discarded |
| `400 the challenge is no longer valid` | The user behind the MFA challenge was disabled mid-flow |

<Warning>
The two `429`s are the most confusable pair, because the remedies are unrelated.
`too many failed attempts` is per-account and clears by unlocking or waiting.
`rate_limit_exceeded` is per-IP and clears by waiting; retrying harder makes it
worse, and it arrives with a `Retry-After` header and a structured body rather than
a `detail` string.
</Warning>

The resolving technique is the same in every case: the login-event history carries
the specific reason string. `/auth/managing-users` covers reading it per user, and
the environment-wide events route covers it across all users.

### Three footguns that look like platform bugs

**A `200` from the token endpoint that contains no token.** The password grant
returns `mfa_required` instead when MFA applies, so a client that reads
`access_token` without checking finds `undefined`.

**A `201` from sign-up that contains no session.** With verification required the
response carries `user`, `session: null` and `verification_required: true`.

**A user who exists in one environment and not another.** Every lookup is scoped by
project and environment, so "the account is missing" is frequently "the account is
in the other environment".

All three follow from the same design rather than being defects, and all three are
worth checking before anyone concludes something is broken.

Studio's own operators live in a reserved environment whose configuration is
hardcoded rather than editable, and it is stricter than any project environment:
sign-up off, strict password policy, a ten-character minimum, one-hour access
tokens and seven-day refresh tokens.

It matters for two reasons. An operator session behaves differently from a user
session in ways that look like misconfiguration. And no configuration key changes
it, so there is nothing to look up.

`/reference/environment-settings` covers how configuration is carried between
environments, and `/operate/environments-and-promotion` covers promotion.
**Your move:** protect the master above everything else in this document.


## Security outside the auth service

Authentication ends at the boundary of the auth service; what happens with the
resulting identity is where most real-world incidents actually occur. The joins
below are the ones worth reasoning about deliberately.

### Policies are the trust boundary

A policy is the mechanism that turns a verified token into an access decision, and
the claims it reads are the same ones this document has been describing. Three
things follow from that.

First, a policy reading `meta` is not merely weaker than one reading `app` — it is
**fully user-controlled**, because the user can edit that field themselves. Second, a
policy reading a key that does not exist evaluates to a comparison between two empty
values, which is **true**, so a typo in a claim name produces a condition that admits
everyone. Third, `$auth.authenticated` should gate any condition that compares
another `$auth` key, because every key is empty for a signed-out caller.

<Warning>
The failure mode worth naming explicitly: a typo'd claim name does not throw and does
not deny. It admits. A policy that silently fails open is the worst kind, and it is
invisible until someone tests the boundary deliberately. `/policies/debugging` covers
how to check this.
</Warning>

### Storage turns claims into isolation

Bucket policies get `$object` alongside `$auth`, which is how per-user and
per-tenant isolation is expressed without a database lookup. Keys shaped
`<user_id>/<filename>` scope a user to their own prefix by comparing
`$object.segments.0` to `$auth.user_id`; keys shaped `<org>/<filename>` do the same
with `$auth.org`.

Both patterns require a `truthy` check on the claim first. Without it, an anonymous
caller's empty `$auth.org` matches an empty prefix — the same fail-open shape as
above. `/storage/access` covers the patterns.

### Realtime evaluates channel rules with the token

A realtime connection carries the same token, so channel access is decided from the
same claims. The consequence to plan for is timing: channel membership is evaluated
with the claim as of the token's issue, so removing a member from an organization
changes their channel access when they next refresh, not immediately.
`/realtime/channel-rules` covers the rule language.

### Flows and jobs have no user by default

Flows triggered by platform events run as themselves. Jobs and schedules run with
service authority and **no user token at all**. That has a direct security
consequence:

<Warning>
Disabling an account revokes its sessions, but it does not stop an unattended job
that acts on that user's behalf. Pairing a subscription to the account-disabled event
with cancelling the relevant schedule is the only way to stop the work itself.
`/jobs/schedules` covers scheduling; `/flows/triggers` covers subscriptions.
</Warning>

### Webhooks do not carry user identity

An outbound webhook carries a signature rather than a token, and an inbound webhook
is authenticated as itself. Do not design a system where a webhook handler assumes it
is acting for a specific user — it is not, and the only user-associated data it has is
whatever the payload contained. `/webhooks/signatures` covers both directions.

### Service keys cross every boundary at once

A secret key is not scoped to the auth service. The same credential that reaches the
admin routes can read and write application data, because it bypasses policies by
role. That is the single fact that most changes how service keys should be handled:
they are not "auth credentials with extra rights", they are a platform-wide
superuser.

`/operate/api-keys` covers issuing and scoping them, and `/operate/secrets` covers
storing them.


## What an attacker needs, ranked by cost

A useful inversion of the whole model: what would an attacker actually have to
compromise to reach an account, cheapest first.

| What they take | What they gain | How to make it expensive |
| --- | --- | --- |
| A user's password | Sign-in, then an MFA challenge | Enforce MFA; a stolen password alone is insufficient |
| A user's refresh token | One use, then the session dies | Short `refresh_ttl`; the window is the lifetime |
| A user's access token | That user, until expiry | Short `access_ttl`; httpOnly storage |
| A password database dump | Offline guessing against hashes | Strong policy; the hash is the only defence here |
| One environment's derived key | Forge tokens for that environment | Keep the master secret far away from it |
| The `jwt_master_secret` | Forge tokens for **every** environment | The crown jewel; this is the one that matters |
| The `master_key` | Decrypt every stored secret and TOTP factor | Back it up, and never export it |
| A service key | Full administrative access, no scoping | Secret manager; rotation on personnel change |
| An XSS in your frontend | Whatever the session can do | Not solvable by token design — solve it in the frontend |

<Info>
The bottom row is the honest answer to "what is the weakest link". Nothing in the
token design prevents a script running on your page from acting as the user. Every
row above it can be hardened by configuration; that one cannot.
</Info>

## Responding to a suspected compromise

The sequence, and why each step is in that order. This is the part of the model
that gets improvised under pressure, so it is worth having written down.

Revoke the sessions first. `POST {base}/users/{id}/sessions/revoke` ends every
session in that environment immediately, and refreshes become impossible. It costs
nothing and it is reversible in effect — the user signs in again.

Disable the account if the compromise is not yet understood, or if you need the
user out of the system rather than merely logged out. Disabling also revokes
sessions, so it subsumes the first step; do it second only when you want the
softer action first.

Reset MFA if the account had it. This does **not** revoke sessions, which is exactly
why it comes after rather than instead of the revocation — the reverse order leaves
the attacker's sessions alive.

Rotate `jwt_master_secret` only if you suspect the platform itself is compromised.
It signs out every user in every environment on the installation, so it is a
last resort with a large blast radius, not a routine response.

<Warning>
Order matters in one specific way: **resetting MFA before revoking sessions leaves
the attacker in.** The reset only removes the factors; the sessions they already hold
remain valid, including ones carrying the old assurance level.
</Warning>

### What to capture while you still can

Before deleting anything, three things are cheap to collect and impossible to
reconstruct afterwards:

- The user's full history, which holds the reason strings the API deliberately
  hides — including any refresh-theft messages.
- The session list, with IPs and user agents, while the sessions still exist. Deleting
  the account destroys this.
- The environment's failure events, if other accounts may be involved.

<Note>
Deleting an account rewrites its email to a placeholder and removes its identities and
factors. It preserves the user row so events stay attributable, but it does **not**
preserve the session rows. Capture first.
</Note>

### After containment

Sign-in events and authentication events are durable and read-only, so the timeline
survives everything above. If you revoked rather than deleted, the user re-enrols in
MFA from scratch — new secret, new provisioning URI, new recovery codes — because the
old ones were removed rather than invalidated.

Then watch `failures_24h` and the `session.reuse_detected` event for a week. A
compromised credential usually shows continued use after containment, and the
revocation only stops new sessions.
