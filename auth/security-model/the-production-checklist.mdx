Ordered by how much damage getting it wrong causes, rather than by topic. Each
item names the concrete setting or behaviour to verify, because "review your auth
config" is not actionable.

<AccordionGroup>
  <Accordion title="Secrets, before anything else">
  - `internal_secret`, `jwt_master_secret` and `master_key` are **not** their
    development defaults. Services refuse to start in production while they are,
    which means the check is enforced rather than advisory.
  - `master_key` is backed up with the database. Losing it makes stored secrets and
    every TOTP factor permanently unreadable, locking out every user who enrolled
    MFA.
  - Secret keys are in a secret manager, not in source, not in committed files, and
    not in client-side code.
  - Keys in use are rotated on a schedule, and the old ones are known to be retired
    rather than merely replaced.
  </Accordion>

  <Accordion title="Environment configuration">
  - `signup_enabled` is `false` unless the application is genuinely open. This is
    the highest-value single switch.
  - `require_email_verification` is `true` anywhere unverified addresses matter.
  - `site_url` is set, and `redirect_urls` contains only URLs you control.
  - `redirect_urls` is empty rather than holding a wildcard-looking placeholder.
  - `default_roles` grants the least privilege a new account needs to be useful.
  - Provider entries all have a `client_id`, so they appear in the settings response
    rather than silently 404-ing.
  </Accordion>

  <Accordion title="Token lifetimes">
  - `access_ttl` is short enough that revocation latency is acceptable. Fifteen
    minutes is the default and a sound choice.
  - `refresh_ttl` is short enough that a lost device stops being useful. Thirty days
    is the default; consider shorter for sensitive applications.
  - You accept that shortening `access_ttl` obliges your client to refresh
    reliably, and that it does.
  </Accordion>

  <Accordion title="Password policy">
  - `password_policy` is `strict` rather than `basic` for anything handling real
    data. `basic` is a length rule only.
  - `password_min_length` is set deliberately — 8 is the default, 10 or more is a
    better floor.
  - Your client renders **all** entries in `problems`, not just the first.
  - The lockout threshold and duration suit your user base, knowing they are
    installation-wide rather than per-environment.
  </Accordion>

  <Accordion title="MFA">
  - `mfa_enabled` is `true`, so users can enrol at all.
  - Users who need a second factor actually have one. Enrolment is opt-in and
    nothing forces it.
  - Recovery codes are distributed securely, understanding they are shown **once**
    and are unrecoverable afterwards.
  - The admin MFA reset route is available, and you know when to use it — it
    deletes factors *and* recovery codes.
  - Recovery links are treated as account takeover if intercepted.
  </Accordion>

  <Accordion title="Client behaviour">
  - The refresh token is stored where page scripts cannot read it.
  - Refreshes are serialised — one in flight, with other requests waiting on it.
  - A failed refresh never retries with the same token. It signs in again.
  - `mfa_required` is checked before assuming a token is present.
  - The `org` field is omitted rather than sent as `null`, if the app is
    org-scoped.
  </Accordion>

  <Accordion title="Monitoring">
  - You have reviewed the **Sign-in activity** tab and know your normal failure
    rate.
  - Something watches for `session.reuse_detected` — the only signal that a refresh
    token was replayed.
  - `user.disabled`, `user.deleted` and `user.mfa_reset` are subscribed to, so
    administrative actions are visible to whoever is accountable.
  - You have accepted that failed sign-ins and successful refreshes emit no events,
    and use the login-event table for that history.
  </Accordion>

  <Accordion title="Data handling">
  - Backups containing identities are treated as credential archives, because they
    include password hashes. Access to them is restricted accordingly.
  - You understand `master_key` is what protects sealed TOTP secrets, which is why
    that key's protection is the whole ballgame.
  - Deleted accounts are understood to be soft-deleted, with the email rewritten to
    a non-routable address so the original is released for re-use.
  </Accordion>
</AccordionGroup>


## Common mistakes, and what they actually cause

| Mistake | What really happens | Instead |
| --- | --- | --- |
| Retrying a refresh after a timeout | Family revoked; user signed out | Treat as terminal; sign in again |
| Two tabs refreshing at once | Family revoked by theft detection | Serialise refreshes |
| Sending `"org": null` from an absent value | Session silently leaves its organization | Omit the key |
| Setting `access_ttl` to an hour | Disabled accounts usable elsewhere for an hour | Keep it near the default |
| Reading `meta` in a policy | User can grant themselves the claim | Read `app` |
| Assuming a `201` from sign-up means signed in | `undefined` token when verification is required | Check `verification_required` |
| Turning off MFA in config to remove factors | Factors remain; users simply are not challenged | Admin MFA reset per user |
| Expecting `revoked_at` to invalidate tokens at once | Old access tokens work until expiry | Accept the `access_ttl` window |
| Hard-coding providers or sign-up flags in the UI | Breaks when the environment is edited | Read `GET /auth/v1/settings` |
| Looking for a `theft_detected` field | It does not exist | Read the events |
| Setting a session absolute expiry | No such field exists | Enforce from `created_at` yourself |

<Info>
Most of that table is one lesson stated repeatedly: local token verification means
anything derived from the database is a snapshot, and anything you want enforced
continuously has to be enforced by you.
</Info>

## The attack surface, worked through

Each threat below names the mechanism that addresses it and, just as importantly,
the limit of that mechanism. Knowing both is what tells you where to put your own
controls.

### Credential guessing

**Addressed by** rate limiting on the auth bucket, plus a per-account lockout counter
that clears on success.

**Limit:** both are per-IP or per-account, never per-human, and a distributed
attacker with many addresses is bounded only by the lockout. Nothing detects a
low-and-slow attempt that stays under the threshold — nine failures a day for a week
is invisible, and the account is unlocked again each morning.

**Your move:** password policy and MFA. Neither rate limiting nor lockout
substitutes for a password that is not guessable from a breach.

### Credential stuffing

**Addressed by** the password hash. bcrypt by default, so an offline attack against a
stolen hash table is expensive per guess.

**Limit:** it does nothing about an attacker using a *real* password list against
your endpoint. In that case lockout and rate limits are the only controls, and both
are evadable.

**Your move:** MFA. A stuffed password is worthless against an account with a second
factor, which is why it is the single highest-value control on this list.

### Refresh token theft

**Addressed by** single-use rotation with family revocation on reuse.

**Limit:** a stolen refresh token works exactly once before the session dies — but
that one use yields a fresh access token, and nothing revokes the access tokens
already minted from the family. Theft is detected, not prevented.

**Your move:** the transport. Rotation bounds the value of a stolen token; it does
not stop it being stolen. `httpOnly` cookie storage, short `access_ttl`, and TLS
between your server and the auth endpoint are the actual defences.

### Access token theft

**Addressed by** short lifetime. Fifteen minutes by default, and you can shorten it.

**Limit:** during its remaining life the token is indistinguishable from a legitimate
one, to every service, because verification is local and there is no revocation
check. If you hold it in `localStorage`, one XSS reads it.

**Your move:** `access_ttl` and storage. Halving the lifetime halves the window.
Nothing else shortens it, because there is no deny list to consult.

### Session hijacking via a leaked identifier

**Addressed by** the session id being the token family, and by there being nothing to
guess — it is 32 bytes of random hex.

**Limit:** if a user pastes a full token into a support chat, that is a bearer
credential for the remainder of its life, and it can be used to mint new tokens for
the whole refresh window. Support should treat any pasted token as compromised and
revoke the session.

**Your move:** revoke on sight.

### Account enumeration

**Addressed by** uniform responses on sign-in, on the emailed-link routes, on one-time
token consumption, and on organization slugs.

**Limit:** the uniformity is only as good as the routes you built. A route of your own
that returns a different status for "no such user" reintroduces the oracle, and
nothing in the auth service can catch that.

**Your move:** keep your own error paths uniform too.

### Redirect abuse

**Addressed by** prefix matching against `site_url` and `redirect_urls`, applied to
every `redirect_to`.

**Limit:** the allowlist is checked against configured prefixes, so a mistake in the
configuration is a mistake everywhere. And on the OAuth **callback** an unapproved
target is dropped rather than rejected, so the flow completes — with no redirect,
not with an error.

**Your move:** keep the allowlist short, and prefer `site_url` plus specific paths
over a broad prefix.

### Privilege escalation through claims

**Addressed by** the split between `meta` and `app`. Only `app` is administrator-
writable, and only `app` should carry access decisions.

**Limit:** the split is only a defence if you use it. A policy reading `user_metadata`
is not merely weaker — it is fully user-controlled, because the user can edit that
field themselves through the profile route.

**Your move:** audit your policies for `meta` reads. `/policies/context` is explicit
that these must not gate access.

### Cross-environment confusion

**Addressed by** the derived per-environment key and the `prj`/`env` claim check.

**Limit:** it contains a leaked per-environment key, not a leaked master. Rotating
`jwt_master_secret` signs everyone out everywhere at once, because tokens carry no key
id to distinguish generations.
