Passwords are not the only way in. This page covers four more things you can do with the SDK, each of which needs a switch turned on for the environment before it works:

| Feature | What it gives you | Turn on |
| --- | --- | --- |
| [Emailed codes](#emailed-codes) | Sign in with six digits from an email: no password, no link to open. | Email codes |
| [Passkeys](#passkeys) | Sign in with a fingerprint, face or device PIN, using WebAuthn. | Passkeys, and your site's domain |
| [Guest sessions](#guest-sessions) | Let someone use your app before they sign up, then keep what they made. | Guest sign-in |
| [Integration tokens](#integration-tokens) | Hand another service a short-lived token that says who the user is. | A token profile |

Read [`settings()`](/auth/overview#find-out-what-is-enabled) to know which are on: `email_code_enabled`, `passkeys_enabled` and `anonymous_enabled`. Calling one that is off fails with 403, for example "email codes are disabled".

## Emailed codes

An emailed code is the simplest passwordless method: the person types their address, receives six digits, and types them back. Unlike a [magic link](/auth/magic-links) it works across devices, because nothing has to be opened on the device that asked.

<CodeGroup>
```typescript TypeScript
await pawabase.auth.sendEmailCode({ email: "ada@example.com" });

// the person reads the email, then:
const result = await pawabase.auth.verifyEmailCode({ email: "ada@example.com", code: "123456" });

if (result.status === "mfa_required") await result.verify(authenticatorCode);
```

```python Python
pb.auth.send_email_code(email="ada@example.com")

# the person reads the email, then:
result = pb.auth.verify_email_code(email="ada@example.com", code="123456")

if result.status == "mfa_required":
    result.verify(authenticator_code)
```
</CodeGroup>

### `sendEmailCode`

| Parameter | Default | Notes |
| --- | --- | --- |
| `email` | required | Where the code is sent. |
| `createUser` / `create_user` | `true` | Whether an address with no account may get one. With `false`, only existing accounts can use a code. |

The call always answers the same way, `{ sent: true }`, whether or not the address has an account, and whether or not an email was actually sent. That is deliberate: it cannot be used to discover who is registered. If you need to tell the person something specific, say only "If that address can sign in, a code is on its way."

Details that matter when you design the screen:

- A code is **six digits** and lives **10 minutes**.
- An address has **one live code**. Asking again replaces the previous one, so a "resend" button should call `sendEmailCode` again.
- Sending is rate limited to 10 requests a minute per client.
- A disabled account gets no email. A new address gets one only when sign-up is enabled and `createUser` is not `false`.

### `verifyEmailCode`

The result has the same shape as a password sign-in: `signed_in` with a session the SDK has already stored, or `mfa_required` with a `verify` function when the account has a second factor.

- Spaces in the code are ignored, so "123 456" works.
- **Five wrong guesses** spend the code, even if the right one follows; the person must ask for a new one.
- Every failure, wrong, expired or already used, is the same 400, "the code is invalid or has expired". Show one message for all of them.
- On success the address counts as confirmed. If the address had no account and sign-up is enabled, one is created at this moment. That is how emailed codes double as sign-up.

<CodeGroup>
```typescript TypeScript
import { ApiError, PermissionError } from "@pawabase/client";

try {
  await pawabase.auth.verifyEmailCode({ email, code });
} catch (error) {
  if (error instanceof PermissionError) showMessage("Email codes are not available.");
  else if (error instanceof ApiError && error.status === 400) showMessage("That code is wrong or has expired. Request a new one.");
  else throw error;
}
```

```python Python
from pawabase import ForbiddenError, ValidationError

try:
    pb.auth.verify_email_code(email=email, code=code)
except ForbiddenError:
    show_message("Email codes are not available.")
except ValidationError:
    show_message("That code is wrong or has expired. Request a new one.")
```
</CodeGroup>

### A complete screen

<CodeGroup>
```typescript TypeScript
async function signInWithCode(email: string) {
  const { email_code_enabled } = await pawabase.auth.settings();
  if (!email_code_enabled) throw new Error("Use another method.");

  await pawabase.auth.sendEmailCode({ email, createUser: false });
  const code = await promptForCode();                       // your UI
  const result = await pawabase.auth.verifyEmailCode({ email, code });
  return result.status === "signed_in" ? result.session : await result.verify(await promptForCode());
}
```

```python Python
def sign_in_with_code(email: str):
    if not pb.auth.settings()["email_code_enabled"]:
        raise RuntimeError("Use another method.")

    pb.auth.send_email_code(email=email, create_user=False)
    result = pb.auth.verify_email_code(email=email, code=prompt_for_code())   # your UI
    return result.session if result.status == "signed_in" else result.verify(prompt_for_code())
```
</CodeGroup>

## Passkeys

A passkey replaces the password with a key pair held by the person's device. They approve with a fingerprint, face or PIN, and nothing secret is ever sent to your app or to Pawabase. There is nothing to phish or leak, and passkeys sync across a person's devices through their platform's keychain.

A passkey sign-in is treated as two factors at once: the device holds the key and the person proved they are present. So a passkey session is `aal2`, and the person is **not** asked for a second code afterwards.

### Before you start

Passkeys are bound to a **domain**. Set the environment's passkey domain (the *relying party*) in Studio under Users & auth. A page can use a passkey only when its address is that domain or one of its subdomains, so a passkey made for `example.com` works on `app.example.com` and not on `example.org`. When no domain is set, the environment's site address is used.

In the browser, WebAuthn also requires a **secure context**: HTTPS, or `localhost` in development.

### In a browser (TypeScript)

The TypeScript client runs the whole ceremony. Call `register` while the person is signed in, and `signIn` from your login screen. Both must be triggered by a click or tap, because browsers refuse to show the prompt otherwise.

```typescript
// settings page, signed in
const passkey = await pawabase.auth.passkeys.register({ name: "MacBook" });

// login page
const session = await pawabase.auth.passkeys.signIn();                    // the device offers its passkeys
const forAda = await pawabase.auth.passkeys.signIn({ email: "ada@example.com" });   // only that account's
```

| Method | Returns | Notes |
| --- | --- | --- |
| `register({ name? })` | `Passkey` | Adds a passkey to the signed-in account. `name` is a label for the list, up to 100 characters. |
| `signIn({ email? })` | `Session` | Signs in and stores the session, emitting `SIGNED_IN`. With an `email` only that account's passkeys are offered; without one the device offers whichever it holds for your domain. |

When the browser has no WebAuthn, both throw a `ConfigError`. Check support before drawing a "Use a passkey" button:

```typescript
const supported = typeof PublicKeyCredential !== "undefined";
```

If the person cancels the system prompt, the browser rejects with a `NotAllowedError` from the platform, not a Pawabase error. Treat that as "they changed their mind" and do nothing.

### Manage a user's passkeys

<CodeGroup>
```typescript TypeScript
const passkeys = await pawabase.auth.passkeys.list();
// [{ id, name, device_type, backed_up, transports, created_at, last_used_at }]

await pawabase.auth.passkeys.remove(passkeys[0].id);
```

```python Python
passkeys = pb.auth.passkeys.list()
# [{"id", "name", "device_type", "backed_up", "transports", "created_at", "last_used_at"}]

pb.auth.passkeys.remove(passkeys[0]["id"])
```
</CodeGroup>

| Field | Meaning |
| --- | --- |
| `device_type` | `singleDevice` or `multiDevice`: whether the passkey can sync between devices. |
| `backed_up` | Whether it is currently backed up by the platform. |
| `transports` | How the device was reached (`internal`, `usb`, `hybrid`…). |

Let people name and remove passkeys, and encourage a second one, so losing a phone does not lock anyone out. Removing the last passkey from an account that has no password leaves it with no way to sign in except [recovery](/auth/password-recovery), so warn before you allow it.

### Outside a browser (Python, native apps, tests)

Python and other non-browser clients cannot show the system prompt. The SDK carries both ends of the ceremony over the wire, and you give the options to whatever component holds the key, such as a native platform API or a test authenticator. TypeScript exposes the same low-level pairs for React Native and similar.

**Register** (signed in):

<CodeGroup>
```typescript TypeScript
const { ticket, options } = await pawabase.auth.passkeys.requestRegistration();

const credential = await createCredentialSomehow(options);        // base64url-encoded, in WebAuthn JSON form

const { passkey } = await pawabase.auth.passkeys.finishRegistration({ ticket, credential, name: "Pixel" });
```

```python Python
challenge = pb.auth.passkeys.register_options()
ticket, options = challenge["ticket"], challenge["options"]

credential = create_credential_somehow(options)                   # base64url-encoded, in WebAuthn JSON form

result = pb.auth.passkeys.register_verify(ticket=ticket, credential=credential, name="Pixel")
```
</CodeGroup>

**Sign in**:

<CodeGroup>
```typescript TypeScript
const { ticket, options } = await pawabase.auth.passkeys.requestSignIn({ email: "ada@example.com" });

const credential = await getAssertionSomehow(options);

const session = await pawabase.auth.passkeys.finishSignIn({ ticket, credential });
```

```python Python
challenge = pb.auth.passkeys.authenticate_options(email="ada@example.com")

credential = get_assertion_somehow(challenge["options"])

session = pb.auth.passkeys.authenticate_verify(ticket=challenge["ticket"], credential=credential)
```
</CodeGroup>

The `ticket` ties your answer to the challenge the server issued; it expires after a short time and is single-use. A stale ticket fails with 400, "the link is invalid or has expired". With an `email`, the options list only that account's passkeys; an address with no passkeys, or no account, receives the same open prompt, so the call does not reveal who is registered.

### Passkey errors

| Situation | Status | Meaning |
| --- | --- | --- |
| Passkeys are off | 403 | "passkeys are disabled". Turn them on first. |
| Registering without a session | 401 | Sign in first. |
| Passkey already registered on this account | 409 | "this passkey is already registered". |
| Stale or reused ticket | 400 | Start the ceremony again. |
| The assertion does not verify | 400/401 | The device, domain or challenge did not match. Check the passkey domain. |
| Too many attempts | 429 | Passkey calls are limited to 30 a minute per client. |

## Guest sessions

A guest session lets someone use your app immediately, with no email and no password, and become a real user later without losing what they did. Think of a shop cart, a draft document, or a game that should be playable before sign-up.

<CodeGroup>
```typescript TypeScript
const session = await pawabase.auth.signInAnonymously();
session.user.is_anonymous;           // true

await pawabase.from("carts").create({ owner: session.user.id });   // their data is theirs, as for any user
```

```python Python
session = pb.auth.sign_in_anonymously()
session.user["is_anonymous"]         # True

pb.from_("carts").create(owner=session.user["id"])
```
</CodeGroup>

A guest is a real account in every other respect. It has a user id, a session that renews, and rows it owns, and your [policies](/policies/overview) apply to it exactly as they do to anyone else. It has no email, so you cannot reach it, and there is no password or link to get back in. **If the person clears their storage or signs out, the account is gone for good.** Keep that in mind when deciding what a guest may do.

Starting guests is limited to 10 a minute per client, and the environment must have guest sign-in enabled, or the call fails with 403 "guest sign-in is disabled".

### Upgrade a guest

When the person is ready to keep their work, turn the guest into a full account. The user id does not change, so everything they created stays theirs:

<CodeGroup>
```typescript TypeScript
const { user, verification_sent } = await pawabase.auth.upgradeAnonymous({
  email: "ada@example.com",
  password: "correct horse battery staple",
  name: "Ada Lovelace",
  redirectTo: "https://app.example.com/welcome",
});
```

```python Python
result = pb.auth.upgrade_anonymous(
    email="ada@example.com",
    password="correct horse battery staple",
    name="Ada Lovelace",
    redirect_to="https://app.example.com/welcome",
)
user, verification_sent = result["user"], result["verification_sent"]
```
</CodeGroup>

| Parameter | Notes |
| --- | --- |
| `email` | Required. Must not belong to another account. |
| `password` | Optional. Leave it out to let the person choose [emailed codes](#emailed-codes) or a [passkey](#passkeys) instead. When given, it must meet the [password policy](/auth/passwords#the-password-policy). |
| `name` | Optional display name. |
| `redirectTo` / `redirect_to` | Where the confirmation link sends the person. Must be an allowed redirect URL. |

The call must be made while the guest session is signed in. A verification email is sent to the new address, and the SDK updates the stored user and emits `USER_UPDATED`.

| Situation | Status |
| --- | --- |
| Already a full account | 409, "this is already a full account" |
| The email belongs to someone else | 409, "an account with this email already exists" |
| The address is not allowed by the environment's rules | 403 |
| Redirect URL not allowed | 400 |

<Tip>
A common pattern: start a guest on first launch, store a flag like `isGuest` from `user.is_anonymous`, show a gentle "Save your work" prompt after the first meaningful action, and call `upgradeAnonymous` from it.
</Tip>

### A guest who already has an account

If a visitor starts as a guest but already has an account, they can sign in to it. The guest's data does not merge automatically into the existing account; if you need that, move the rows yourself from a server (with a secret key) before discarding the guest. Design for it only if your app really invites that situation.

## Integration tokens

Sometimes another service, such as your billing API, an analytics tool or a separate backend, needs to know who your signed-in user is. You should not hand it the user's Pawabase access token: that token is valid for your whole project. Instead, an **integration token** is a separate short-lived signed token, shaped for that one service, carrying only the claims you chose.

You define a **token profile** in Studio under Users & auth: a name, the audience the receiving service checks, a lifetime (30 seconds to one hour), and the claims to include. Claims can come from the user (`user.id`, `user.email`, `user.name`, `user.email_verified`, `user.avatar_url`), the organization (`organization.slug`, `membership.role`), `roles`, `permissions`, the session level `session.aal`, a value from `user.app_metadata.<key>`, or a fixed value you write. A profile can require that the user is in an organization, or has completed a second factor.

### Issue a token

While the user is signed in:

<CodeGroup>
```typescript TypeScript
const { token, expires_in, audience } = await pawabase.auth.issueToken("billing");

await fetch("https://billing.example.com/invoices", {
  headers: { authorization: `Bearer ${token}` },
});
```

```python Python
issued = pb.auth.issue_token("billing")

requests.get(
    "https://billing.example.com/invoices",
    headers={"authorization": f"Bearer {issued['token']}"},
)
```
</CodeGroup>

The answer is `{ token, token_type, expires_in, expires_at, audience }`. Request a fresh token when `expires_at` is near rather than storing one. The call needs an active session and fails with 401 otherwise; a profile that does not exist is 404 "no such token profile", and a profile that requires an organization or second factor the session lacks is refused with 422, and the message says which.

The token looks like this once decoded, for a profile named `billing` with the claims `user_id`, `email` and a fixed `plan`:

```json
{
  "user_id": "01M64C42GB1RR68PBB8KEET3KY",
  "email": "ada@example.com",
  "plan": "pro",
  "sub": "01M64C42GB1RR68PBB8KEET3KY",
  "iss": "https://api.example.com/auth/v1/token-profiles/production",
  "aud": "https://billing.example.com",
  "iat": 1793299927,
  "nbf": 1793299927,
  "exp": 1793300227,
  "jti": "QP4y7dFoGBLYzU58y5Zdog",
  "sid": "ac800921ed1d875f…",
  "env": "production",
  "typ": "integration",
  "profile": "billing",
  "aal": "aal1"
}
```

`sub`, `iss`, `aud`, `iat`, `nbf`, `exp`, `jti`, `sid`, `env`, `typ`, `profile` and `aal` are set by Pawabase; your claim names may not reuse them. The token is signed with EdDSA (Ed25519).

### Verify it in the receiving service

The receiving service does not need to call Pawabase. It checks the signature against the environment's **public keys**, which anyone can fetch:

<CodeGroup>
```typescript TypeScript
// the receiving service, using the `jose` package
import { createRemoteJWKSet, jwtVerify } from "jose";

const jwks = createRemoteJWKSet(new URL("https://api.example.com/auth/v1/token-keys/production/jwks"));

export async function authenticate(token: string) {
  const { payload } = await jwtVerify(token, jwks, { audience: "https://billing.example.com" });
  return payload;                                  // payload.user_id, payload.plan, …
}
```

```python Python
# the receiving service, using PyJWT with the `cryptography` package
import jwt

jwks = jwt.PyJWKClient("https://api.example.com/auth/v1/token-keys/production/jwks")

def authenticate(token: str) -> dict:
    key = jwks.get_signing_key_from_jwt(token)
    return jwt.decode(token, key.key, algorithms=["EdDSA"], audience="https://billing.example.com")
```
</CodeGroup>

From a client that already has the SDK, `pawabase.auth.jwks()` (`pb.auth.jwks()` in Python) returns the same key set as `{ keys: [...] }`. Each key has a `kid`, which the token header names, so keys can be rotated without breaking verifiers.

Always check three things: the **signature**, the **audience** (so a token meant for one service is not accepted by another), and the **expiry**. The libraries above do all three when you pass `audience`. Also check `typ` is `integration` if the service accepts other token kinds.

### Preview what a profile produces

From a server with a secret key, you can see the exact claims a profile would put in a token for a given user (and organization) without issuing one, which is useful while designing profiles. See [Managing users](/auth/managing-users).

## Design the login screen

A good passwordless screen asks for as little as possible and has an obvious way out. This version tries a passkey first, falls back to an emailed code, and never shows an option the environment has turned off.

```typescript
export async function chooseMethods() {
  const settings = await pawabase.auth.settings();
  const passkeys = settings.passkeys_enabled && typeof PublicKeyCredential !== "undefined";
  return {
    passkey: passkeys,
    emailCode: settings.email_code_enabled,
    password: true,
    social: settings.providers,
    guest: settings.anonymous_enabled,
  };
}

export async function signInWithBestMethod(email: string) {
  const methods = await chooseMethods();

  if (methods.passkey) {
    try {
      return await pawabase.auth.passkeys.signIn({ email });       // one tap on most devices
    } catch {
      // cancelled or no passkey here: fall through to the next method
    }
  }
  if (methods.emailCode) {
    await pawabase.auth.sendEmailCode({ email, createUser: false });
    return "code-sent";                                              // show the code field
  }
  return "use-password";
}
```

Rules of thumb:

1. Ask for the email first, then offer methods. It lets `passkeys.signIn({ email })` offer only that account's passkeys and keeps the next screen short.
2. Always leave a visible way to choose another method. A cancelled passkey prompt is not an error.
3. Do not tell the person whether the address has an account. Use "If that address can sign in, we sent a code."
4. After sign-in, offer to add a passkey if they signed in another way and their device supports it.

## Choosing between them

| If you need… | Use |
| --- | --- |
| The simplest possible sign-in, any device | [Emailed codes](#emailed-codes) |
| The strongest phishing-resistant sign-in | [Passkeys](#passkeys), with a fallback |
| A one-tap link in the same browser | [Magic links](/auth/magic-links) |
| People using the app before signing up | [Guest sessions](#guest-sessions) |
| Another service trusting your users | [Integration tokens](#integration-tokens) |
| One-click sign-in with an existing account | [Social login](/auth/social-login) |

These combine freely. A common setup is passkeys with an emailed-code fallback, plus a [second factor](/auth/mfa) for account changes. All of them end in the same session, so everything after sign-in, from [renewal](/auth/tokens-and-sessions) to your [policies](/auth/auth-in-policies), works the same.

## From guest to member, end to end

A realistic flow: start as a guest, do some work, then keep it by adding a passkey, with an emailed code as the fallback on other devices.

```typescript
// 1. first launch
const settings = await pawabase.auth.settings();
if (settings.anonymous_enabled && !(await pawabase.auth.getSession())) {
  await pawabase.auth.signInAnonymously();
}

// 2. later, when the person chooses to keep their work
await pawabase.auth.upgradeAnonymous({ email });          // no password: a verification link is emailed
// ...they confirm the address from the email...
await pawabase.auth.passkeys.register({ name: "This device" });

// 3. on another device
await pawabase.auth.sendEmailCode({ email, createUser: false });
const result = await pawabase.auth.verifyEmailCode({ email, code });
```

The user id is the same from step 1 to step 3, so everything the guest made is still theirs. This works because an upgrade changes the account in place, and because a code or passkey proves the same person on the next device.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `sendEmailCode` answers `sent: true` but no email arrives | The address has no account and `createUser` is `false`, the account is disabled, or the mail is in spam. | The answer is identical on purpose. Check the spelling, and the environment's mail log in Studio. |
| `verifyEmailCode` fails with "invalid or has expired" | Wrong code, older than 10 minutes, already used, or five wrong guesses. | Send a new code. |
| `passkeys.signIn()` rejects with `NotAllowedError` | The person cancelled, the prompt timed out, or the page was not a secure context. | Treat as cancelled; check you are on HTTPS or `localhost`. |
| The browser offers no passkeys | None exist for this domain on this device, or the passkey domain in Studio does not match the page. | Register one first; confirm the domain setting. |
| Registration fails with 409 | This device already registered a passkey for the account. | Offer to remove the old one first. |
| `signInAnonymously` fails with 403 | Guest sign-in is off. | Turn it on, or require sign-up. |
| `upgradeAnonymous` fails with 409 | The address belongs to another account. | Ask the person to sign in to that account instead. |
| `issueToken` fails with 404 | There is no profile with that name, or it is disabled. | Check the profile name in Studio. |
| The receiving service rejects the token | Wrong audience, expired, or verifying against another environment's keys. | Match `aud` to the profile's audience and use the right environment's key set. |
