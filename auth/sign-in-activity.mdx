**Sign-in activity** is the environment's log of authentication events: every sign-in by any method, the failures and why, second steps, password changes and resets, passkeys, failed refreshes, profile edits and bot-protection refusals. It answers "did Ada really sign in from there?", "is someone guessing passwords?" and "why can't this person get in?".

## In Studio

**Users & auth → Records → Sign-in activity** shows the latest events across the environment: **When, Event, Email, Result** (`ok`, or the failure reason) and **IP**. Tick **failures only** to see what went wrong.

For one person, open them (**Users & auth → People → Users**) and use the **Activity** tab: their sign-ins together with account changes and the API requests they made. See [A person's activity](/auth/users#a-persons-activity).

## What each entry holds

| Field | Meaning |
| --- | --- |
| `at` | When |
| `user_id`, `email` | Who. A failed sign-in for an address with no account has an `email` but no `user_id` |
| `kind` | What happened (below) |
| `method` | How (below) |
| `success` | Whether it worked |
| `reason` | Why it failed (below), or a detail for some successes |
| `ip`, `user_agent` | Where it came from, and the browser or app |

### Event kinds

| `kind` | Logged when |
| --- | --- |
| `sign_in` | A sign-in by any method, successful or not |
| `sign_out` | A person signed out (`method` is the scope: `local`, `others`, `global`) |
| `refresh` | A refresh was **refused** (expired, revoked, reused); successful refreshes aren't logged |
| `mfa_challenge` | The password was right and a second step was asked for; the `sign_in` entry follows once it's answered |
| `mfa_verify` | A second-step code was wrong |
| `mfa_enrolled` | A second factor was set up |
| `passkey_added`, `passkey_removed` | A passkey was registered or removed |
| `password_changed` | The person changed their password while signed in |
| `recovery_requested` | Someone asked for a password reset link |
| `password_reset` | A reset link was used to set a new password |
| `profile_updated` | The person changed their profile (`reason` says what: `picture`, `profile details`, …) |
| `captcha` | [Bot protection](/auth/bot-protection) refused a request (`method` is the protected action, `reason` the verdict). Repeats from one address are logged at most once a minute |

### Methods

`password`, `magic_link`, `email_code`, `passkey`, `anonymous` (guest), `totp` (authenticator code), `recovery` (reset link or recovery code), `email_verification`, `refresh_token`, `setup` (finishing a required second-factor setup), `api` (a call from the person's app), or the name of a social or enterprise provider (`google`, `github`, `acme-sso`, …).

### Failure reasons

| `reason` | Meaning |
| --- | --- |
| `wrong password` | The address exists; the password didn't match. Counts toward [lockout](/auth/attack-protection) |
| `unknown email` | No account with that address |
| `locked` | Refused because the account is locked |
| `disabled` | Refused because an administrator disabled the account |
| `wrong code` | A second-step code didn't match. Counts toward lockout |
| `unknown passkey` | A passkey that isn't registered in this environment |
| `Refresh token expired`, `… possible token theft`, … | Why a refresh was refused. A theft message means the session was revoked ([Sessions](/auth/sessions#theft-protection)) |

## Read it from code

With a secret key:

<CodeGroup>
```typescript TypeScript
import { admin } from "@pawabase/client/admin";

const a = admin(secretClient);
const { data: failures } = await a.insight.events({ kind: "sign_in", failed: true, limit: 500 });
const stats = await a.insight.stats();
const ada = await a.users.history(userId);            // one person's entries
```

```python Python
failures = pb.admin.insight.events(kind="sign_in", failed=True, limit=500)["data"]
stats = pb.admin.insight.stats()
ada = pb.admin.users.history(user_id)
```
</CodeGroup>

| Option | Meaning |
| --- | --- |
| `kind` | Only this kind |
| `failed` | Only failures |
| `limit` | Newest first; default 100, at most 500 |

There's no paging or date filter: for analysis over longer periods, export on a schedule (below).

`stats` answers:

| Field | Meaning |
| --- | --- |
| `users`, `verified`, `mfa`, `disabled` | Account counts |
| `signups_24h` | Accounts created in the last 24 hours |
| `sign_ins_24h` | Successful sign-ins in the last 24 hours |
| `failures_24h` | Failed events of any kind in the last 24 hours |
| `organizations` | Organizations in the environment |
| `providers` | `[{ provider, n }]`: linked accounts per social or enterprise provider |

## Show people their own activity

A "Recent activity" list on the account page lets people spot sign-ins they don't recognise:

<CodeGroup>
```tsx TypeScript
const events = await pawabase.auth.sessions.history();   // the person's latest 50 entries

<ul>
  {events.map((e) => (
    <li key={e.at + e.kind}>
      {new Date(e.at).toLocaleString()} · {e.kind} · {e.method} · {e.success ? "ok" : `failed (${e.reason})`}
    </li>
  ))}
</ul>
```

```python Python
for e in pb.auth.sessions.history():
    print(e["at"], e["kind"], e["method"], "ok" if e["success"] else f"failed ({e['reason']})")
```
</CodeGroup>

Each entry has `kind`, `method`, `success`, `reason`, `ip`, `user_agent` and `at`. A person only sees their own entries, and failed sign-ins for an address are tied to the account only when the account exists. Pair the list with **Sign out everywhere** ([Sessions](/auth/sessions)).

## How long it's kept

Your plan sets the retention: 3 days on Free, 30 on Starter, 90 on Pro, 180 on Business and 365 on Scale ([Plans and limits](/cloud/plans-and-limits)). Older entries are deleted once a day. [Erasing a person](/auth/data-requests) keeps their entries as counts but clears who, the email, IP, browser and reason.

To keep more, copy it out on a schedule: a [schedule](/automation/schedules) or a cron job on your server calls `insight.events({ limit: 500 })` daily and stores what's new.

## Spotting attacks

| Pattern | Likely | Do |
| --- | --- | --- |
| Many `wrong password` for **one** address | Guessing one account | Lockout handles it; tell the person if it continues |
| `wrong password` and `unknown email` across **many** addresses from few IPs | Credential stuffing (leaked passwords from elsewhere) | Turn on [bot protection](/auth/bot-protection) for sign-in, and the [breach check](/auth/password-policy) |
| Many `unknown email` | Someone listing which addresses have accounts | Bot protection; keep your sign-in error messages generic |
| `refresh` failures with "token theft" | A stolen refresh token was replayed | The session was already revoked; ask the person to change their password |
| Many `captcha` refusals | Bots being stopped | Working as intended; check one address isn't a real user behind a shared IP |
| `failures_24h` far above normal | Any of the above | Look at the log, then the patterns here |

To be told in real time instead of reading the log, subscribe a [flow](/automation/overview) to `session.reuse_detected`, or run a [schedule](/automation/schedules) that checks `stats().failures_24h` and emails your team above a threshold. See [Auth webhooks](/auth/auth-webhooks).

## A weekly routine

1. Filter to failures; look for repeats against one account or from one address.
2. Open **Users** with **MFA off** and ask people with admin roles to set up a second factor.
3. Check **Locked** users ([Attack protection](/auth/attack-protection)).
4. Review [user API keys](/auth/user-api-keys) and revoke ones nobody recognises.
