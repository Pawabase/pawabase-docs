Verification proves a person owns the address they gave. It protects against typos, fake accounts and someone registering with another person's email.

## In Studio

**Users & auth → Sign-in → Sign-in & registration → Registration → Verify email before sign-in.** *A new account must open the link in its confirmation email first.* Also **Restrictions → Require a verified email**.

The message is **Confirm your email** in [Email templates](/auth/email-templates).

<CodeGroup>
```typescript TypeScript
await m.environments.update("production", { auth: { require_email_verification: true } });
```

```python Python
pb.manage.environments.update("production", auth={"require_email_verification": True})
```
</CodeGroup>

Without it, people sign in straight after sign-up and the address stays **unverified** (`user.email_verified` is false) until they confirm.

## The flow

1. `signUp` returns `verificationRequired: true` and no session.
2. Show "Check your inbox" with a resend button.
3. The person clicks the link and lands on your `redirectTo` page.
4. That page confirms the token and the person is signed in.

<CodeGroup>
```typescript TypeScript
// 1–2. After sign-up
await pawabase.auth.resendVerification({ email, redirectTo: "https://myapp.com/verified" });

// 4. On the landing page
const token = new URL(location.href).searchParams.get("token")!;
const session = await pawabase.auth.verifyEmail(token);
```

```python Python
pb.auth.resend_verification(email=email, redirect_to="https://myapp.com/verified")

session = pb.auth.verify_email(token)
```
</CodeGroup>

`verifyEmail` confirms the address and returns a session. The `redirectTo` page must be on your [redirect list](/auth/redirect-urls).

## Other ways an address becomes verified

- Using an [email code](/auth/email-codes) or [sign-in link](/auth/sign-in-links) proves the inbox.
- A social provider may report the address as verified.
- An administrator creates the user with `emailVerified: true` (the default for admin-created accounts).
- **Company sign-in** connections have **Trust the email address** to treat the provider's email as verified.

## Show verification status

```tsx
function VerifyBanner() {
  const { user } = useAuth();
  if (!user || user.email_verified) return null;
  return (
    <p>
      Please confirm your email.{" "}
      <button onClick={() => pawabase.auth.resendVerification({ email: user.email })}>Resend</button>
    </p>
  );
}
```

Require `email_verified` for sensitive actions through an [access rule](/policies/recipes-ownership), not only the UI.

## Changing the email later

When someone changes their address with `updateUser({ email })`, a link goes to the **new** address, and the change happens when it's clicked:

<CodeGroup>
```typescript TypeScript
await pawabase.auth.updateUser({ email: "new@example.com" });

// On the page the link opens
await pawabase.auth.confirmEmailChange(token);
```

```python Python
pb.auth.update_user(email="new@example.com")
pb.auth.confirm_email_change(token)
```
</CodeGroup>

The old address keeps working until the new one is confirmed. The `user.email_changed` event fires on confirmation, and `user.verified` when an address is confirmed.

## Make landing pages robust

- Links are single-use and expire. If `verifyEmail` throws, show "This link has expired" with a button to send a new one.
- Don't show or log the token.
- After success, send the person where they were going.

```typescript
try {
  await pawabase.auth.verifyEmail(token);
  navigate("/");
} catch {
  setMessage("This link has expired. We can send you a new one.");
}
```
