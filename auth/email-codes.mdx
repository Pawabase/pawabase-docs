An **email code** is a six-digit number sent to the person's address. They type it into your app and are signed in. No password to remember, and unlike a [sign-in link](/auth/sign-in-links), a code works where links don't: in-app browsers, mobile apps where opening a link would leave the app, a different device from the one reading the email, and inboxes whose security scanners open links before the person does.

| | Email code | Sign-in link |
| --- | --- | --- |
| The person | Types six digits | Clicks |
| Works on another device than the inbox | Yes | No: the link signs in whichever browser opens it |
| Survives link-scanning email filters | Yes | A scanner can use the link up |
| Lifetime | 10 minutes | 15 minutes |
| Needs a callback page in your app | No | Yes, with a Site URL ([Redirect URLs](/auth/redirect-urls)) |

## Turn it on

**Users & auth → Sign-in → Sign-in & registration → Ways to sign in → Email code.** It's also on **Authentication flow** as **Email one-time code**. When it's off, both calls answer `403` "email codes are disabled".

The message is **Sign-in code** in [Email templates](/auth/email-templates). It receives `code` and `minutes` (10). Make sure the environment can send mail ([Mail](/mail/overview)).

## The flow

<CodeGroup>
```typescript TypeScript
// 1. Ask for a code.
await pawabase.auth.sendEmailCode({ email: "ada@example.com" });

// 2. When the person types it:
const result = await pawabase.auth.verifyEmailCode({ email: "ada@example.com", code: "123456" });
if (result.status === "mfa_required") {
  await result.verify(authenticatorCode);   // their second step
}
// result.status === "signed_in": the session is stored and SIGNED_IN fires
```

| Option | Meaning |
| --- | --- |
| `createUser` / `create_user` | Default `true`: an address with no account gets a code, and the account is made when the code is used. `false` signs in existing accounts only |
| `captchaToken` / `captcha_token` | The token from a [bot-protection](/auth/bot-protection) widget, when sending codes is protected |

Spaces in the typed code are ignored, so `123 456` works.

## New accounts

With `createUser` on and sign-up allowed in the environment, a first-time address gets a code like anyone else. The account is created only when the code is **used**, not when it's sent, so mistyped addresses don't leave empty accounts behind. The new account:

- has no password (they can add one later, or keep using codes);
- has its email **verified**, because typing the code proves they read that inbox;
- fires `user.created` with `method: "email_code"`, and gets the environment's [default roles](/auth/sign-up-restrictions);
- is subject to [sign-up restrictions](/auth/sign-up-restrictions): a refused domain gets `403` at verify time.

When sign-up is turned off, unknown addresses simply get no code.

Existing accounts whose address wasn't verified yet become verified when they sign in with a code.

## How codes expire and are spent

| Rule | Detail |
| --- | --- |
| Lifetime | **10 minutes** from sending. Not configurable |
| One live code per address | Asking again retires the previous code: only the newest works |
| Wrong guesses | Each wrong code counts against that code. After **5**, it's spent and the person must ask for a new one |
| Single use | A code works once. Two simultaneous attempts with the right code: one wins, the other gets `400` |
| Storage | Only a keyed hash of the digits is kept; the digits exist only in the email |
| Rate limits | Both calls share the sign-in limit of 30 requests a minute per address |

Wrong codes don't count toward the account's [lockout](/auth/attack-protection), which covers passwords and second-step codes. Five guesses per code, a new code each time and the rate limit make guessing a 1-in-a-million code impractical.

## Nothing is revealed

`sendEmailCode` answers the same way whether or not the address has an account, whether sign-up is allowed, and whether the account is disabled: no code is sent in those cases, and the answer still says it was. Your form should say "If that address can sign in, we've sent a code", never "no such account".

## Errors

| Call | Status | Message | TypeScript | Python |
| --- | --- | --- | --- | --- |
| either | `403` | "email codes are disabled" | `PermissionError` | `ForbiddenError` |
| `sendEmailCode` | `403` | `captcha_required` or `captcha_failed`: [bot protection](/auth/bot-protection) wants a (new) check. `429` `too_many_attempts` when it blocks the address | `PermissionError` | `ForbiddenError` |
| either | `429` | Too many requests | `RateLimitError` | `RateLimitedError` |
| `verifyEmailCode` | `400` | "the code is invalid or has expired": wrong, expired, retired by a newer code, spent after 5 tries, or never sent | `ValidationError` | `ValidationError` |
| `verifyEmailCode` | `403` | "this account is disabled", or the address's domain is refused for new accounts | `PermissionError` | `ForbiddenError` |
| `verifyEmailCode` | `403` | The person's organization requires its [company login](/auth/enterprise-sign-in) | `PermissionError` | `ForbiddenError` |

Every code failure is the same `400` on purpose: nothing tells an attacker whether they were close or whether the code expired.

## A complete form

```tsx
import { useState } from "react";
import { ValidationError } from "@pawabase/client";
import { pawabase } from "./pawabase";

export function CodeSignIn() {
  const [step, setStep] = useState<"email" | "code" | "second-step">("email");
  const [email, setEmail] = useState("");
  const [code, setCode] = useState("");
  const [error, setError] = useState("");
  const [cooldown, setCooldown] = useState(0);
  const [finish, setFinish] = useState<((code: string) => Promise<unknown>) | null>(null);

  async function send() {
    setError("");
    await pawabase.auth.sendEmailCode({ email });
    setStep("code");
    setCooldown(30);
    const timer = setInterval(() => setCooldown((s) => (s <= 1 ? (clearInterval(timer), 0) : s - 1)), 1000);
  }

  async function verify() {
    setError("");
    try {
      const result = await pawabase.auth.verifyEmailCode({ email, code });
      if (result.status === "mfa_required") {
        setFinish(() => result.verify);
        setStep("second-step");
      }
    } catch (e) {
      if (e instanceof ValidationError) setError("That code didn't work. Check it, or send a new one.");
      else throw e;
    }
  }

  if (step === "email") {
    return (
      <form onSubmit={(e) => { e.preventDefault(); send(); }}>
        <input type="email" autoComplete="email" required value={email} onChange={(e) => setEmail(e.target.value)} />
        <button>Email me a code</button>
      </form>
    );
  }
  if (step === "second-step" && finish) {
    return <SecondStepForm onSubmit={finish} />;   // your authenticator-code form
  }
  return (
    <form onSubmit={(e) => { e.preventDefault(); verify(); }}>
      <p>If {email} can sign in, we've sent it a code. It works for 10 minutes.</p>
      <input inputMode="numeric" autoComplete="one-time-code" pattern="[0-9 ]*" maxLength={7}
             value={code} onChange={(e) => setCode(e.target.value)} />
      <button>Sign in</button>
      <button type="button" disabled={cooldown > 0} onClick={send}>
        {cooldown > 0 ? `Send a new code in ${cooldown}s` : "Send a new code"}
      </button>
      <button type="button" onClick={() => setStep("email")}>Use a different address</button>
      {error && <p role="alert">{error}</p>}
    </form>
  );
}
```

- `autoComplete="one-time-code"` lets phones fill the code from the email notification.
- The "send a new code" pause keeps people under the rate limit, and reminds them that a new code replaces the old one.
- Keep the address on screen so people don't retype it, and offer another way in (password, link, social).

## In a mobile or desktop app

Codes are the simplest passwordless option outside the browser: no deep links, no callback URLs. Keep the address in memory between the two screens, and send a [device id](/auth/devices#sending-a-device-id) so new-device emails and device limits work.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| No email arrives | Mail isn't set up, the address has no account (with sign-up off or `createUser: false`), the account is disabled, or it's in spam | Check **Mail** in Studio for the message; check sign-up settings |
| The right code is refused | A newer code was requested, it's older than 10 minutes, or 5 wrong tries spent it | Send a new code and use only the newest |
| New people can't sign up with a code | Sign-up is off, or their domain is restricted | [Sign-up restrictions](/auth/sign-up-restrictions) |
| Asked for a second step after the code | The account has [two-step verification](/auth/two-step-verification) | Expected: the code replaces the password, not the second factor |
