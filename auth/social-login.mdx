Social sign-in looks like the simplest thing in the authentication section: a row of buttons, a redirect to a provider, a redirect back, a session. That appearance is misleading. The moment a provider profile comes back, Pawabase has to answer one hard question — *is this person an account I already know, and if so which one?* — and that question is where the real behaviour lives. Getting it wrong does not produce an error. It produces a successful sign-in to the wrong account.

This page documents the real provider set, the account-resolution decision tree in full, the verified-email rule that keeps strangers out of existing accounts, and the exact shape of what arrives back in the browser.

## Where social login sits in the layered model

Pawabase authentication is three cooperating layers, and social sign-in touches all three in a specific order. Understanding which layer does what is what stops the OAuth routes from looking arbitrary.

| Layer | What social login asks of it |
| --- | --- |
| **Akountz** (identity) | Owns users and `Identity` rows. Exchanges the code, fetches the profile, decides which account it belongs to, starts the session. |
| **The API** (project config) | Owns the environment's `auth.providers` block, including the client IDs and secrets. Akountz reads it; it never writes it. |
| **Gateway / `pawabase_core`** | Verifies the bearer token afterwards, like any other request. It is not involved in the OAuth conversation at all. |

Two consequences follow immediately.

First, **a provider is configured per environment**, not per installation. The same Akountz can have Google enabled in `acme/production` and not in `acme/staging`, because it reads a different `providers` block for each. This follows from the tenancy rule that governs the whole section: every user, and every `Identity`, belongs to exactly one `project` + `env` pair.

Second, **an OAuth callback is a browser navigation, not a context-scoped API call.** Everything else under `/auth/v1` reads `project` and `env` from the request context header. The OAuth routes cannot, because a browser following a redirect sends no context token. That is why `project` and `env` are in the path for these two routes and not the others — a genuine structural difference, not an inconsistency.

<Info>
If you have not read [Authentication](/auth/overview) yet, do that first. This page assumes the three-layer model and the per-environment tenancy rule.
</Info>

## The providers that actually ship

Pawabase ships four providers, each backed by a class in the OAuth library. The `providers` key you write in an environment's `auth` block selects one of them by name.

| Key | Class | Notes |
| --- | --- | --- |
| `google` | `GoogleOAuthProvider` | |
| `github` | `GithubOAuthProvider` | |
| `discord` | `DiscordOAuthProvider` | |
| `microsoft` | `MicrosoftOAuthProvider` | Accepts a `tenant` setting. |

<Warning>
**There is no Apple provider, no Facebook provider and no LinkedIn provider.** A configuration naming `apple`, `facebook` or `linkedin` does not select a built-in integration — it falls through to the generic path and fails with `provider 'apple' needs authorize, token and userinfo endpoints` unless you also supply all three endpoints yourself. If you need one of those, you are configuring a generic provider by hand, not switching on something that already works.
</Warning>

Worth stating plainly, because documentation for other products lists those providers by default and a reader arriving with that expectation will lose time to a 500 that reads like a configuration typo.

### Generic providers

Any name that is not one of the four becomes a generic `OAuthProvider`. It speaks OAuth 2.0, or OpenID Connect when `openid` appears among the scopes.

Three endpoints are mandatory, and all three must be non-empty:

| Required setting | What it is |
| --- | --- |
| `authorize_endpoint` | Where the browser is sent to obtain consent. |
| `token_endpoint` | Where the authorization code is traded for tokens. |
| `userinfo_endpoint` | Where the profile is read from. |

If any one is missing, the request fails with a `500` and the detail `provider 'name' needs authorize, token and userinfo endpoints`. The check happens when the provider object is built, not when the provider is contacted, so a missing endpoint fails the *first* redirect rather than the callback. That distinction is useful when reading logs: a 500 at `/authorize` is a configuration problem, whereas a failure at `/callback` is a conversation problem.

A generic provider also needs whatever scopes its userinfo endpoint requires to return a usable profile. In practice that almost always means a scope that grants email access, because without one there is no email to match or create against.

```json
{
  "providers": {
    "gitlab": {
      "enabled": true,
      "client_id": "gitlab-client-id",
      "client_secret": "secret://GITLAB_SECRET",
      "authorize_endpoint": "https://gitlab.com/oauth/authorize",
      "token_endpoint": "https://gitlab.com/oauth/token",
      "userinfo_endpoint": "https://gitlab.com/api/v4/user",
      "scopes": ["read_user"]
    }
  }
}
```

<Info>
A shipped provider may still be given the three endpoint keys, in which case they override that class's defaults. This is occasionally useful when a provider offers a regional endpoint, but it is a genuine override — a wrong value here breaks a provider that would otherwise have worked untouched.
</Info>

## What you may configure per provider

The reason to read this table before editing anything is that most of these keys are invisible once set. There is no validation pass that tells you a key was ignored, and the failure surfaces later as a confusing symptom — a provider that 404s, or an MFA challenge that never arrives.

| Setting | Default | Applies to | Meaning |
| --- | --- | --- | --- |
| `enabled` | `True` | all | When false, the provider is not built at all. |
| `client_id` | — | all | **Required.** Its absence hides the provider from clients. |
| `client_secret` | `""` | all | May be a `secret://NAME` reference. |
| `tenant` | — | `microsoft` | Passed only when set. Selects the directory. |
| `scopes` | provider default | all | Overrides the class's default scope list. |
| `authorize_params` | — | all | Extra query parameters on the authorize URL. |
| `authorize_endpoint` | provider default | all | Overrides, including for shipped providers. |
| `token_endpoint` | provider default | all | Overrides. |
| `userinfo_endpoint` | provider default | all | Overrides. Mandatory for generic providers. |

Two of these deserve more than a table row.

**`client_id` is what makes a provider real.** A provider entry with credentials but no `client_id` is not merely misconfigured — it is *invisible*. The list of enabled providers is computed by filtering on the switch being on and a `client_id` being present, so a provider missing its client ID never appears in `GET /auth/v1/settings` and never appears in a client's button list. A sign-in screen built from the settings endpoint will simply not render the button.

**`enabled` defaults to on, and that default is about the value, not the key.** An entry that sets no `enabled` key is treated as enabled. This is the same permissive-default pattern as the rest of the auth configuration: absence is not a decision, and the decision made is the permissive one.

```json
{
  "providers": {
    "google": {
      "enabled": true,
      "client_id": "google-client-id",
      "client_secret": "secret://GOOGLE_SECRET"
    },
    "microsoft": {
      "enabled": true,
      "client_id": "microsoft-client-id",
      "client_secret": "secret://MICROSOFT_SECRET",
      "tenant": "common"
    }
  }
}
```

<Warning>
Credentials are referenced as `secret://NAME`, never pasted into the configuration. Studio's Client secret field shows the placeholder `secret://GITHUB_SECRET` for exactly this reason. See [Secrets](/operate/secrets) for how the reference resolves, and [Authentication configuration](/auth/configuration) for how the block reaches the API.
</Warning>

### Microsoft and tenants

`tenant` is accepted only by the Microsoft provider, and only when set — an absent `tenant` leaves the class to choose its own default. It selects which directory the login is resolved against, and the difference decides whether employees of one tenant can sign in at all.

| `tenant` | Who can sign in |
| --- | --- |
| `common` | Accounts from any Microsoft directory. The usual choice for a public sign-in button. |
| `organizations` | Only accounts in the directory that registered the application. |
| `consumers` | Only personal Microsoft accounts. |
| A directory ID | Only that one directory. |

<Info>
`tenant` is not exposed as a field in Studio's provider card. It is written in the environment's `auth` payload directly. If you need it, you are editing configuration as JSON rather than through the Configuration tab.
</Info>
## What the client is told about providers

Before rendering social buttons, a client asks the environment what it offers. `GET /auth/v1/settings` is the canonical answer, and the `providers` value is a sorted list of names — not objects, not credentials, no secrets.

```json
{
  "signup_enabled": true,
  "email_verification_required": false,
  "magic_link_enabled": true,
  "mfa_enabled": true,
  "providers": ["discord", "github", "google"],
  "password_policy": { "kind": "basic", "min_length": 8 }
}
```

The list is built by filtering the configured providers on exactly two conditions: the enabled switch being on, and a `client_id` being set.

| Response field | Type | Where it comes from |
| --- | --- | --- |
| `signup_enabled` | bool | `signup_enabled` |
| `email_verification_required` | bool | `require_email_verification` |
| `magic_link_enabled` | bool | `magic_link_enabled` |
| `mfa_enabled` | bool | `mfa_enabled` |
| `providers` | list[str] | enabled providers, sorted |
| `password_policy.kind` | str | `password_policy` |
| `password_policy.min_length` | int | `password_min_length` |

<Warning>
Do not hardcode the provider list into a sign-in screen. Render from `providers`, and re-read it rather than caching it for the life of the app: a provider can be added to an environment without any client deployment.
</Warning>

<Info>
Remember the config cache. Each environment's settings are cached for a short window, so a provider you just enabled in Studio can take up to ten seconds to appear in this response. A test that enables a provider and immediately reloads will intermittently show the old list. See [Authentication configuration](/auth/configuration).
</Info>

## The two routes

Social sign-in is two routes, and the second one is hidden from the OpenAPI schema because it is only ever reached by a provider redirecting a browser.

| Route | Method | In the schema | Purpose |
| --- | --- | --- | --- |
| `/auth/v1/authorize/{project}/{env}/{provider}` | GET | yes | Starts the flow: builds the provider URL, sets the state cookie, redirects the browser. |
| `/auth/v1/callback/{project}/{env}/{provider}` | GET | no | Finishes it: exchanges the code, resolves the account, starts the session, redirects back. |

The callback URL registered with the provider is derived, not configured by hand:

```text
{public_url}/auth/v1/callback/{project}/{env}/{provider}
```

`public_url` is the environment's own setting, falling back to Akountz's installation-wide setting when the environment leaves it empty. This is the same `public_url` that magic links and the Akountz-hosted link pages use, which is why an environment that has not set it can produce OAuth redirects pointing somewhere unexpected.

<Warning>
`project` and `env` are part of the callback path, so the value registered with the provider must match the environment exactly, including which environment you meant. A provider application configured for `acme/production` cannot serve `acme/staging`, because the redirect URI differs by environment. Register one application per environment, or one application with several registered redirect URIs.
</Warning>

### What the authorize route accepts

| Query parameter | Meaning |
| --- | --- |
| `redirect_to` | Where to land afterwards. Falls back to `site_url` when absent. |
| `link_token` | Links the resulting identity to the current user instead of signing in. |

`redirect_to` is checked against the allowlist before the redirect is issued. If it is not an allowed URL, the request is rejected with `400 redirect_to is not an allowed URL` — it is not silently ignored at this point.

### What the allowlist actually allows

The allowed set is the environment's `site_url` plus every entry in `redirect_urls`. A URL is permitted if it equals a base exactly, starts with the base followed by `/`, or starts with the base followed by `?`.

| Base | Permitted URL | Allowed |
| --- | --- | --- |
| `https://app.example.com` | `https://app.example.com` | yes |
| `https://app.example.com` | `https://app.example.com/auth/callback` | yes |
| `https://app.example.com` | `https://app.example.com?next=/x` | yes |
| `https://app.example.com` | `https://app.example.com.evil.test/` | no |
| `https://app.example.com` | `https://app.example.com/` | yes |
| — | `http://localhost:3000/callback` | only if listed in `redirect_urls` |

The subdomain case is the one to internalise: because the separator must be `/` or `?`, `https://app.example.com.evil.test` cannot pass a check against `https://app.example.com`. A trailing-slash mismatch is the more common real annoyance — a base written with a trailing slash is handled, but a base written as a bare host must match at the host boundary.

<Info>
Local development is the usual reason `redirect_urls` exists. `http://localhost:3000` matches no production base, so a local callback URL has to be listed explicitly. See [Authentication configuration](/auth/configuration) for how the list is edited.
</Info>
## The account-resolution decision tree

This is the core of social sign-in, and the part worth reading twice.

The callback receives a verified profile from the provider. That profile is not a user. It carries a provider name, a stable subject identifier, and whatever else the provider chose to expose. Turning it into a Pawabase account is the callback's job, and it resolves in a fixed order. Every branch below either lands on a user or produces a specific error code.

| Branch | Condition | Result |
| --- | --- | --- |
| 1 | `link_token` present in state | Consume it; the identity is attached to *that* user's account. |
| 2 | An `Identity` exists for `(project, env, provider, subject)` | Sign in as the user that identity belongs to. |
| 3 | No identity, and `profile.email_verified` is true, and an account holds that email | Sign in as that account, creating the identity. |
| 4 | No identity and no match | Create an account, if the environment allows it. |
| 5 | The resolved user is disabled | Refuse, with `account_disabled`. |

The branches are sequential, and each is skipped when its condition does not hold. Walking them as prose:

**A linking ticket wins first.** If the state carries a link token, the flow is not signing anyone in — it is attaching a provider to an account that is already signed in. The ticket is consumed, and the user it names becomes the account. If an identity for that provider and subject already exists and belongs to a *different* user, the request fails with `identity_already_linked`. This guard is what stops one person from claiming an identity that another account already holds.

**Otherwise the identity is the lookup key.** The callback looks up `Identity` by the four-part key `(project, env, provider, subject)` — the environment matters, so a Google sign-in in staging and the same Google account in production produce two independent `Identity` rows and two independent Pawabase accounts. That is the tenancy rule applied to social login.

**Only then does email come into it, and only when the provider says it is verified.** If no identity matched, and the profile carries an email that the provider marked verified, Pawabase looks for an existing account holding that address and attaches the identity to it.

**Otherwise an account is created** — subject to the environment's rules, each of which can refuse. Creation requires sign-up to be enabled and an email to be present.

**And finally, a resolved user who is disabled is refused**, regardless of which branch found them.
### Why the verified-email rule is the security line

Branch 3 is guarded by `profile.email_verified` being true, and this single condition is what stops an unverified provider email from silently attaching itself to somebody else's account.

The reasoning is about who controls the address, not about the address itself. Many providers will hand back whatever email a profile claims, and plenty of profiles claim an address the person has not proven they own. If an unverified address could join an existing account, then anyone who could set `email` on a profile at a permissive provider could walk into any Pawabase account that address belonged to. No password, no second factor, no interaction with the real owner.

So the rule is: **an unverified address never attaches a new identity to an existing account.** It is not a weaker path; it is not a path.

What happens instead depends on whether an account already holds that address, which is where the error codes diverge:

| Situation at branch 4 | Result |
| --- | --- |
| No account holds the email | A new account is created. Unverified, unless the provider said otherwise. |
| An account already holds the email | `email_unverified_conflict` — refused. |
| The profile has no email at all | `email_required` — refused. |
| Sign-up is disabled in this environment | `signup_disabled` — refused. |

<Warning>
The refusal here is deliberate and correct. A user who already has an account with that email will occasionally try to "just sign in with Google" and be refused with `email_unverified_conflict`. The fix is to sign in with a password or magic link first and link the provider from the signed-in account, not to relax the check. See [Linking a provider to an existing account](#linking-a-provider-to-an-existing-account) below.
</Warning>

Note also what `email_verified` *false* means at the provider boundary: it conflates "the provider says this address is unverified" with "the provider did not say anything about it". A provider that omits the claim entirely reports false, and Pawabase treats it the same way. That is the correct default, and it is why adding a new provider that does not expose a verification claim can appear to work for new users while silently failing to match returning ones.

### How the account is created

When an account does have to be created, a few details of that creation are worth knowing:

| Aspect | What happens |
| --- | --- |
| Password | None. The account gets an unusable password. |
| Username | Derived from the provider's username or the email local part, with collisions resolved. |
| Name | The provider's display name, or empty. |
| Verification | Set immediately if the provider verified the email; otherwise unverified. |
| Avatar | The provider's avatar URL is stored on the account. |

The unusable password is not an oversight. An account created through social sign-in has no password, and password sign-in cannot succeed against it until someone sets one. This is also the normal state for an account an administrator created in Studio. See [Managing users](/auth/managing-users).

<Info>
The username is derived by stripping every character outside `a-z0-9_.-` from the provider's username or the email's local part, truncating to 40 characters, falling back to `user`. On collision, a random number is appended. The result is deterministic enough to be predictable, which is worth remembering if you treat usernames as meaningful — they are generated, not chosen.
</Info>
## Linking a provider to an existing account

Linking is the flow for someone who already has a Pawabase account and wants to add social sign-in to it. The callback handles it through the same decision tree, but branch 1 takes precedence, so the account is never chosen by email.

The signed-in user asks for a URL, passing the provider name and optionally a `redirect_to`:

```bash
curl -X POST "https://api.example.com/auth/v1/identities/link?provider=google" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "X-Pawabase-Context: $CONTEXT"
```

The response is a single URL the browser is sent to:

```json
{
  "url": "https://auth.example.com/auth/v1/authorize/acme/production/google?link_token=..."
}
```

The ticket in that URL is a one-time token with the `link` purpose. When the callback comes back carrying it, the token is consumed and the identity is attached to the user the ticket names. A provider whose subject already belongs to a different account produces `identity_already_linked`.

A successful link does not start a session — that would be wrong, since the person is already signed in. The browser is redirected with `#linked=<provider>` instead, or receives `{"linked": "google"}` as a plain response if there is no redirect target.

### Unlinking

An identity is removed with its id. Ids are ULIDs and are matched case-insensitively, so a lowercased id from a client works unchanged.

```bash
curl -X DELETE "https://api.example.com/auth/v1/identities/01HQ8X4M2K9P7R3T6V0YB5ZCNDA" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "X-Pawabase-Context: $CONTEXT"
```

| Condition | Result |
| --- | --- |
| The identity belongs to another user, or does not exist | `404 no such identity` |
| The user has no usable password and this is their only identity | `409 set a password before removing your only sign-in method` |
| Otherwise | Removed. `204` with no body. |

That 409 is a lockout guard, not a strictness quirk. An account whose only sign-in method is a social identity and which has no password would be unreachable if the identity were removed, so the request is refused. The escape is to set a password first, which the account can do through password recovery.

## Results come back in the fragment

Once the callback resolves the account, the browser has to be delivered a session — or told why it did not get one. Both travel in the **URL fragment**, the part after `#`.

```text
https://app.example.com/auth/callback#access_token=...&refresh_token=...&expires_in=900&token_type=bearer
```

The reason is worth understanding, because it determines what your client code has to do. A fragment is not sent to any server. When the browser lands on `https://app.example.com/auth/callback#access_token=...`, the request that reaches your server contains only the part before the `#`. The token never appears in that request line, which means it cannot be written to an access log, cannot land in a proxy log along the way, and cannot be picked up by a referrer header on a subsequent navigation.

Query parameters have none of those protections. `?access_token=...` would be recorded in your web server's access log, in every intermediary's log, and potentially in a `Referer` header. The fragment is used deliberately for that reason, not because it is convenient.

<Info>
The consequence for your code: the tokens are **not** available to server-side rendering on the first request. Your `/auth/callback` page must read `window.location.hash` in the browser, parse it, store it, and then clean the URL. This is inherent to the design, not an oversight to work around with a query parameter.
</Info>
### What arrives on success

Only four keys are put into the fragment. The session's `session_id`, its `org`, its `org_role` and the user record are not among them.

| Fragment key | Meaning |
| --- | --- |
| `access_token` | The bearer token. |
| `refresh_token` | The rotation token. |
| `expires_in` | Seconds until the access token expires. |
| `token_type` | Always `bearer`. |

Because `session_id` is absent, a client that starts from a social sign-in does not learn the session id from the redirect. `GET /auth/v1/user` reports it, and so does `GET /auth/v1/sessions`, both of which mark the current session. See [Tokens and sessions](/auth/tokens-and-sessions).

### What arrives on failure

A failure that has somewhere to go becomes a redirect carrying a single key:

```text
https://app.example.com/auth/callback#error=signup_disabled
```

With no redirect target, the same failure is raised as `400 sign-in failed: <code>` instead. So the code is identical either way; only the delivery differs. A client should read `error` from the fragment, and a server-side caller should read `detail` from the 400.

### The error codes

These are the real codes, from both the OAuth library's failures and the callback's own decisions.

| Code | Meaning | Where it comes from |
| --- | --- | --- |
| `denied` | The person declined consent at the provider. | Provider returned `access_denied`. |
| `provider_error` | The provider refused for some other reason. | Provider returned an error. |
| `state_mismatch` | The callback could not be tied to a redirect this server started. | Missing, forged or mismatched state cookie. |
| `state_expired` | The state was valid but too old. | The consent screen was left open. |
| `exchange_failed` | The authorization code could not be traded for a token. | Stale code, or a redirect URI mismatch. |
| `profile_failed` | A token was obtained but the profile could not be read. | Userinfo rejected the token, or no subject claim. |
| `provider_misconfigured` | The provider object cannot support the requested step. | A programming error, not a user-facing condition. |
| `signup_disabled` | No matching account and sign-up is off. | Account creation. |
| `email_required` | No matching account and the profile has no email. | Account creation. |
| `email_unverified_conflict` | No matching account, and an existing account holds that unverified email. | Account creation. |
| `account_disabled` | The resolved account is disabled. | Account resolution. |
| `identity_already_linked` | A linking ticket named an identity already owned by another user. | Linking. |

`denied` and `state_expired` are the two you will see most, and neither is a fault. A person who closes the consent tab and a person who left it open overnight produce these, and both are best answered with "try again" rather than an error page.

<Warning>
Do not show the raw code to a person. The codes exist so your client can branch on them; each maps to copy you write. `account_disabled` in particular is an administrative state, and rendering the code as an error message tells a user something they should not be told about an account they cannot see.
</Warning>

<Warning>
The local-development case is worth calling out, because the failure is silent. Running the authorize flow over plain `http://localhost` means the state cookie is set without the `secure` attribute, and some browsers will then refuse to return it on the provider's cross-site redirect back. Every callback fails as `state_mismatch`, and the reason is not in the code you control. Terminate TLS locally, or use a tunnel, rather than debugging the state handling.
</Warning>

## MFA after a social sign-in

If the resolved account has MFA enrolled and the environment allows MFA, the callback does not issue a session. It issues an MFA challenge and redirects with that instead.

```text
https://app.example.com/auth/callback#mfa_required=true&mfa_token=...
```

The account has been identified; only the second factor is outstanding. From the client's side this is the same two-step shape as password sign-in returning `mfa_required`, and the completion call is the same endpoint:

```bash
curl -X POST "https://api.example.com/auth/v1/token" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "content-type: application/json" \
  -d '{"grant_type": "mfa", "mfa_token": "...", "code": "123456"}'
```

The session that comes back is issued at `aal2` and records its method as `oauth:<provider>`. So in the session list you can tell a social sign-in from a password one, and see which provider was used. See [Multi-factor authentication](/auth/mfa) for the full elevation path.

<Warning>
The fragment for the MFA challenge carries a `mfa_token`, not an access token. A client whose callback page assumes `access_token` is always present will store `undefined` and look like a mysterious auth failure. Branch on `mfa_required` first.
</Warning>
## Events emitted

Social sign-in emits through the same event system as every other auth path, so a webhook or event consumer sees it without special handling.

| Event | When | Payload |
| --- | --- | --- |
| `identity.linked` | An `Identity` row is created for a user. | `user_id`, `provider` |
| `identity.unlinked` | An identity is removed. | `user_id`, `provider` |
| `user.created` | An account was created by the callback. | `user_id`, `email`, `method` (`oauth:<provider>`) |
| `user.signed_in` | A session was started. | `user_id`, `method` |
| `mfa_required` is not an event | — | The MFA branch issues a challenge without starting a session. |

`user.created` is emitted only when the callback created the account. Signing in an existing account through a provider emits `identity.linked` the first time that provider is used and nothing account-level afterwards — which is the behaviour to expect when reconciling a user list against a billing system.

See [Events](/events/overview) for delivery and [Sign-in activity](#what-studio-shows) for the audit trail.

## What Studio shows

Studio's **Users & auth** page, under the **Configuration** tab, holds every provider setting. Open the environment, then **Configuration**, and scroll to the section titled **OAuth providers**, described in the interface as *"Social sign-in. Reference credentials as secret://NAME rather than pasting them here."*

Each configured provider is a card. Shipped providers show two fields; anything else shows five.

| Control | Label | Applies to |
| --- | --- | --- |
| Switch | **Enabled** | all |
| Field | **Client ID** | all |
| Field | **Client secret** (placeholder `secret://GITHUB_SECRET`) | all |
| Field | **Authorize endpoint** | generic only |
| Field | **Token endpoint** | generic only |
| Field | **Userinfo endpoint** | generic only |
| Field | **Scopes** | all |

To add one, either pick from the **Add a provider…** dropdown — which lists the shipped providers not yet configured — or type a name into the box with the `custom-provider-name` placeholder and press **Add**. Both paths produce the same entry; the second is the only way to create a generic provider. With no providers configured the section reads *"No providers configured."*

  </Step>

  </Step>

  </Step>

## What the Sign-in activity tab shows

Every callback outcome lands in the sign-in audit trail, including the failures. The **Sign-in activity** tab has a failures-only checkbox and columns **When**, **Event**, **Email**, **Result** and **IP**. The Result badge renders `ok` in green when the attempt succeeded, and the reason string in red when it did not.

For an OAuth failure the reason is the error code from the table above — `denied`, `state_mismatch`, `exchange_failed` and so on — and the Event column records the method as `oauth:<provider>`. This is usually the fastest way to answer "did the person actually get through Google, or did they stop at the consent screen", because a denied consent is logged as a failure against an email that may not exist yet.

<Info>
Failures that never reach the callback are not in this tab. A `404 the 'google' provider is not enabled` or a `500` about missing endpoints happens at the authorize step, before any profile exists, so there is no login event to record.
</Info>

## Troubleshooting

Most social-login problems are one of four kinds, and telling them apart is most of the work.

**The provider is not enabled.** The request fails with `404 the 'google' provider is not enabled`, raised when the provider is built. Two different configurations produce this identically: `enabled` set to false, and no `client_id`. The second is the surprising one, because the entry looks configured. Check the settings response — if the name is absent from `providers`, this is your problem.

**The provider is generic and incomplete.** A `500` naming the provider and saying it needs authorize, token and userinfo endpoints means one of the three is missing or empty. This one fails at `/authorize`, before any conversation with the provider.

**The callback cannot find an account.** The error code in the fragment says which case you are in. `email_required` means the scopes do not grant email access. `email_unverified_conflict` means an account already holds that address and the provider did not verify it — the user needs to sign in by password or magic link and link the provider instead. `signup_disabled` means the environment is invite-only.

**The callback fails before resolution.** These are the OAuth library's codes: `state_mismatch`, `state_expired`, `exchange_failed`, `profile_failed`, `denied`, `provider_error`. `state_mismatch` after a configuration change usually means the state secret was rotated mid-flow; `exchange_failed` usually means the redirect URI registered with the provider does not match the one derived, which is the common symptom of pointing a staging callback at a production provider application.

| Symptom | Cause | What to check |
| --- | --- | --- |
| Provider missing from `GET /auth/v1/settings` | No `client_id`, or `enabled: false`. | The client ID, not the secret. |
| `404 the 'x' provider is not enabled` | Same condition as above. | Same. |
| `500 provider 'x' needs authorize, token and userinfo endpoints` | Generic provider missing an endpoint. | All three keys are present and non-empty. |
| `#error=state_mismatch` | The state cookie did not come back. | `public_url` scheme, and whether the provider is echoing `state`. |
| `#error=state_expired` | The consent screen sat open. | Nothing — this is normal. |
| `#error=exchange_failed` | Code rejected, or a redirect URI mismatch. | The registered callback URI matches `{public_url}/auth/v1/callback/{project}/{env}/{provider}`. |
| `#error=profile_failed` | Userinfo rejected the token or returned no subject. | Scopes, and that the userinfo endpoint is correct. |
| `#error=denied` | The person declined consent. | Nothing. |
| `#error=email_required` | The profile carries no email. | Scopes that grant email. |
| `#error=email_unverified_conflict` | An existing account holds that unverified address. | Link the provider from a signed-in session instead. |
| `#error=signup_disabled` | Invite-only environment. | `signup_enabled`, or create the user in Studio. |
| `#error=account_disabled` | The account is disabled. | An administrator must re-enable it. |
| `#error=identity_already_linked` | That provider identity is on another account. | Unlink it there first. |
| `409 set a password before removing your only sign-in method` | Unlinking would leave the account unreachable. | Set a password first. |
| Sign-in succeeds but no `session_id` in the fragment | Only four keys are sent. | Read it from `GET /auth/v1/user`. |
| Token stored as `undefined` | The redirect carried `mfa_required`, not `access_token`. | Branch on `mfa_required` first. |
| Works in staging, fails in production | Different provider application, or a different callback URI. | One provider application per environment. |
| Just saved a provider, not showing up | The config is cached. | Wait up to ten seconds. |
| Every callback is `state_mismatch` on localhost | The state cookie needs HTTPS. | Terminate TLS locally, or use a tunnel. |
## How this interacts with the rest of the system

A few cross-cutting consequences of social sign-in that show up elsewhere.

**Sessions record their origin.** Every social sign-in produces a session row whose method is `oauth:<provider>`, which is how a session list distinguishes it from a password or magic-link session. Combined with `ip` and `user_agent`, it is the same row the **Sign-in activity** tab renders. See [Tokens and sessions](/auth/tokens-and-sessions).

**A social-only account cannot use a password sign-in.** Accounts created here have an unusable password, so `POST /auth/v1/token` with `grant_type=password` cannot succeed against them. This is the same state as an account an administrator created in Studio, and it is resolved the same way — a password recovery link. See [Password recovery](/auth/password-recovery).

**Organization scoping is read at issue time.** A social sign-in issues tokens for the session's organization exactly as a password sign-in does, and a `null` org role collapses `org` and `org_role` to `null` in the token rather than failing. There is no way to name an organization in the OAuth redirect; a social sign-in starts unscoped and the client refreshes into an organization afterwards if it needs one. See [Organizations](/auth/organizations).

**Roles come from the environment, not the provider.** A new account created here is granted whatever the environment's `default_roles` lists. Nothing from the provider's groups or teams is imported — the callback stores the provider's profile under the identity's own data, not as roles. See [Roles and permissions](/auth/roles-and-permissions).

**Every other service sees only the token.** Once the fragment is parsed and the tokens stored, a social sign-in is indistinguishable from any other sign-in at the gateway. No service knows or cares which provider was used; that fact lives in the session row and the sign-in events. See [Auth in policies](/auth/auth-in-policies).

<AccordionGroup>
  <Accordion title="The callback is excluded from the OpenAPI schema — should I worry?">
    No. It is excluded because it is only ever reached by a provider redirecting a browser, and it takes `code` and `state` as query parameters rather than a JSON body. The route still exists and works. The path is documented above and in the provider consoles you register it with.
  </Accordion>
  <Accordion title="What happens to the tokens in the fragment if the user never returns?">
    Nothing is stored server-side for a social sign-in that completes without the browser reaching your callback page. The tokens were only ever in the fragment of a redirect the browser followed. There is no orphaned copy to clean up — but equally, no session was created, so the person must sign in again.
  </Accordion>
  <Accordion title="Can I offer a provider the environment has not configured?">
    Not through the normal flow. Rendering a button for a provider that is not in `GET /auth/v1/settings` produces a `404 the 'name' provider is not enabled` at the authorize step. The fix is configuration, not client code. Rendering from the settings response is what prevents this.
  </Accordion>
  <Accordion title="Does linking require the provider to have a verified email?">
    No. When a linking ticket is present, the account is named by the ticket rather than resolved by email, so the verified-email condition never gates it. The email still has to be absent or verified to *create* an account, but an existing account being linked is not an email match.
  </Accordion>
</AccordionGroup>

### The two halves of the flow, and why they differ

The authorize route and the callback route do different jobs, and conflating them is a common source of confusion when reading the code.

| | Authorize route | Callback route |
| --- | --- | --- |
| Who calls it | Your browser, via a link or a form. | The provider, by redirecting the browser. |
| What it does | Builds the provider URL, stores the state cookie, redirects. | Verifies state, exchanges the code, reads the profile, resolves the account. |
| Credentials involved | Only the public client ID. | The client secret, at the token endpoint. |
| Can fail on config | Yes — 404 or 500 here. | Rarely; a config error surfaces as `exchange_failed`. |
| Writes to the database | Nothing. | The identity, possibly the account, the session. |

The asymmetry in the last two rows is the practical takeaway. **A configuration mistake almost always shows up at `/authorize`, not at `/callback`.** If the callback is failing, the configuration was almost certainly fine enough to get the person to the provider, and the problem is in the conversation, the profile, or the account resolution.

<Info>
Because the authorize route writes nothing, a person who clicks your sign-in button and then abandons the consent screen leaves no trace in the database — no session, no identity, no login event. That is correct behaviour, and it is why a `denied` result appears in sign-in activity only once the provider actually redirects back.
</Info>

### Why the callback is not in the schema

The callback route is excluded from the generated OpenAPI schema. It takes `code` and `state` as query parameters, and it is only ever reached by a provider redirecting a browser rather than by a client making an API call. Excluding it keeps generated clients from producing a method that no one should ever call directly.

The practical consequence is that the path must be registered in the provider's console by hand, and it is the single most common thing to get subtly wrong, because the path includes both the project and the environment:

```text
https://auth.example.com/auth/v1/callback/acme/production/google
         └─── Akountz ───┘ └── /auth/v1 ──┘ └─ project ─┘ └env┘ └prov┘
```

A callback registered without the environment segment will never be hit, and the provider will report the request as an invalid redirect URI.

<Warning>
When registering a callback URI, the environment name must be the one in the path you are actually serving. `production` and `staging` produce different URIs and both must be registered if one provider application serves both — or, more usually, one provider application is created per environment.
</Warning>
## What the flow actually protects against

Before the decision tree it helps to know which attacks the design is aimed at, because every branch either serves one of these or exists to prevent one.

| Threat | What stops it |
| --- | --- |
| Someone replays a callback URL to sign in as the person who used it | The state cookie must come back with the callback. A bare callback URL has no cookie and fails as `state_mismatch`. |
| Someone forges a state value to redirect a victim | The state value is signed and bound to this environment and provider. |
| Someone claims an identity that belongs to another account | The `(project, env, provider, subject)` lookup finds the real owner and signs them in as themselves, not the claimant. |
| Someone registers a provider profile with a victim's email and steals the account | The verified-email rule. An unverified address never joins an existing account. |
| Someone steals a refresh token and uses it after the real client has rotated it | Rotation is single-use. A reused token revokes the entire family rather than merely failing. |
| Someone replays a TOTP code they saw over a shoulder | The accepted time step is recorded, so the same code cannot be used twice within its window. |
| Someone takes a bearer token out of a log | Tokens are returned in a fragment, which is never sent to a server. |

The first three are handled by the OAuth library and the identity lookup. The fourth is Pawabase's own decision, and it is the one specific to this page.

<Info>
The two layers divide cleanly: the library owns the conversation with the provider, and Akountz owns what the resulting profile *means*. That separation is why adding a generic provider is a configuration exercise rather than a code change, and why the security property that matters most — the verified-email rule — lives in the callback rather than in any provider class.
</Info>

## Scope handling per provider

Scopes are the most common cause of a social sign-in that technically works and practically fails. The pattern is always the same: the user consents, the code exchanges, and then the profile comes back without the field you matched on.

| Provider | Default scopes | What you usually need to add |
| --- | --- | --- |
| `google` | OpenID Connect basics | An email scope, if the default does not include the address. |
| `github` | The provider's default set | An email scope; the private address is not returned without one. |
| `discord` | The provider's default set | An email scope. Discord also has a distinct `identity` scope. |
| `microsoft` | OpenID Connect basics | An email scope for the address. |
| Generic | None | Whatever the provider's userinfo endpoint requires, usually an email scope. |

<Warning>
Adding `openid` to a generic provider's scopes switches it to OpenID Connect mode. That is usually what you want when the provider supports it, but it changes how the profile is read: the identity comes from the ID token rather than from userinfo claims in the general case. If a generic provider starts returning a profile with no subject after you add `openid`, that is why.
</Warning>

### Provider profile fields

Whatever the provider, the callback works from a normalised profile with the same shape.

| Profile field | Used for | Consequence when absent |
| --- | --- | --- |
| `subject` | The identity key. | `profile_failed` — this is the only genuinely required field. |
| `email` | Account matching and creation. | `email_required` when no account matches. |
| `email_verified` | Gates the email match. Treated as false when absent. | Returning users are not matched by email. |
| `name` | The account's display name. | The name is stored empty. |
| `username` | The generated username seed. | The email local part is used instead. |
| `avatar_url` | The account's avatar. | No avatar is stored. |
| `raw` | Stored on the identity. | — |

The row about `email_verified` is the one to hold onto. A provider that does not expose a verification claim will still work perfectly for new sign-ups, because creating an account does not require verification. It will fail only for the *returning* user whose email matches an existing account, and it will fail with `email_unverified_conflict` — which reads like an account problem and is actually a provider configuration problem.
## Worked scenarios

The decision tree is easier to trust once you have walked it in concrete situations. Each of these is a real path through the callback, and each lands somewhere different.

### A brand new person signs in with Google

The profile carries a subject nobody has seen, and an email Google says it verified.

The identity lookup finds nothing. The verified-email branch looks for an account holding that address and finds none either, because the person has never used Pawabase. So account creation runs: sign-up is enabled, an email is present, and no account holds it. An account is created with an unusable password, verified immediately, carrying the provider's name and avatar. The identity is written, `identity.linked` and `user.created` are emitted, and a session starts with method `oauth:google`.

The person is signed in and can now use the account however they like. If they later want a password, they request a recovery link — see [Password recovery](/auth/password-recovery).

### A returning person signs in with Google

Same person, same provider, weeks later.

The identity lookup finds the `Identity` row, because the provider's subject for them is unchanged. Branch 2 resolves immediately and the account is found without ever consulting the email. This is the path that matters most: **returning sign-ins are keyed on the provider's subject, not on the email address.**

That is deliberate. Email addresses get reassigned and people change them. A subject is stable. If matching were by email, a person who changes their provider email would silently become a new account the next time they signed in — or worse, would land in somebody else's account if their old address was reused.

### A person has a password account and tries Google

The person already has an account, created with a password, and clicks "Continue with Google". Their Google profile has the same email, and Google verifies it.

Branch 2 finds nothing, because they have never linked Google. Branch 3 finds their existing account, because the email matches and it is verified. The identity is attached and they are signed in as themselves.

**This is the good version of account merging, and it depends entirely on the provider verifying the email.** When it is verified, a person who has both a password account and a Google account gets one account rather than two, which is what almost every application wants.
### The same person, but the provider does not verify the email

Identical to the previous scenario except the provider reports the address as unverified — or says nothing, which reads the same way.

Branch 2 finds nothing. Branch 3 does not run, because its condition fails. Branch 4 looks for an existing account holding that address, finds one, and refuses with `email_unverified_conflict`.

The person is told, in effect, that they already have an account. They are not told which one, and they are not signed in. The correct resolution is for them to sign in with their password and then link Google from the signed-in account — at which point branch 1 applies, the account is named by the linking ticket rather than by email, and the link succeeds.

<Warning>
If you are tempted to "fix" `email_unverified_conflict` by relaxing the verified-email check, understand what you are opening: any person who can set an arbitrary email on a profile at a permissive provider could then take over any account in your system. The conflict is the security property working, not a bug in it.
</Warning>

### An invite-only environment, brand new person

Same as the first scenario, but sign-up is off for this environment.

Branch 2 and branch 3 both find nothing. Branch 4 runs and refuses immediately with `signup_disabled`, before it even looks at the email.

The person must be created by an administrator first, or invited. See [Managing users](/auth/managing-users) and [Organizations](/auth/organizations) for the invitation path.

### An invite-only environment, invited person

The administrator created the account, or an invitation created it. The person's Google email matches the account they were invited with, and Google verified it.

Branch 3 finds the account by verified email, attaches the identity, and signs them in. **An invited account is not a special case in the callback** — it is the ordinary verified-email match, working.

The one thing to know is that an admin-created account typically has an unusable password, so the person's only usable sign-in method until they link a provider is whatever the invitation gave them. See [Managing users](/auth/managing-users).

### The same Google account in two environments

A person signs in with Google in `acme/production`, then in `acme/staging`.

Each environment has its own `Identity` table keyed on `(project, env, provider, subject)`. The staging lookup does not see the production row, so staging runs through account creation and creates a *separate* account with the same email.

This is correct, not a bug, and it falls directly out of the tenancy rule. The two accounts have separate passwords, separate sessions, and separate roles — [Authentication](/auth/overview) covers why the system is built this way. It also means `signup_enabled` being on in staging is what lets that second account exist; turning it off makes staging refuse instead.

### A disabled account tries to sign in socially

Every branch above resolves to a user, and then branch 5 refuses with `account_disabled`.

The check is last and unconditional, so it applies however the user was found — by identity, by verified email, or by a linking ticket. A disabled account cannot be reached by any social path.

<Info>
A social sign-in failure logs an event with the method recorded as `oauth:<provider>` and the reason recorded as the error code. That is the same row the **Sign-in activity** tab renders in its Result column, so an administrator can see that `account_disabled` is an administrative state rather than a credentials problem.
</Info>

## Configuration that works, end to end

A complete environment auth block with social sign-in, magic links and MFA on, written the way the code reads it.

```json
{
  "name": "production",
  "public_url": "https://auth.example.com",
  "auth": {
    "signup_enabled": true,
    "require_email_verification": true,
    "magic_link_enabled": true,
    "mfa_enabled": true,
    "password_policy": "strict",
    "password_min_length": 12,
    "access_ttl": 900,
    "refresh_ttl": 2592000,
    "site_url": "https://app.example.com",
    "redirect_urls": [
      "https://app.example.com/auth/callback",
      "http://localhost:3000/auth/callback"
    ],
    "default_roles": ["member"],
    "providers": {
      "google": {
        "enabled": true,
        "client_id": "1234567890-abc.apps.googleusercontent.com",
        "client_secret": "secret://GOOGLE_SECRET"
      },
      "github": {
        "enabled": true,
        "client_id": "Iv1.0123456789abcdef",
        "client_secret": "secret://GITHUB_SECRET",
        "scopes": ["read:user", "user:email"]
      },
      "gitlab": {
        "enabled": true,
        "client_id": "gitlab-client-id",
        "client_secret": "secret://GITLAB_SECRET",
        "authorize_endpoint": "https://gitlab.com/oauth/authorize",
        "token_endpoint": "https://gitlab.com/oauth/token",
        "userinfo_endpoint": "https://gitlab.com/api/v4/user",
        "scopes": ["read_user"]
      }
    },
    "emails": {
      "magic": {
        "subject": "Your Acme sign-in link",
        "text": "Sign in to Acme with this link. It works once, for 15 minutes:\n\n{link}"
      }
    }
  }
}
```

Things worth noticing in that block, because each one is a decision with a consequence:

**`site_url` is what makes the callback predictable.** It is the base the browser is sent back to when no `redirect_to` is supplied, and it is the first entry in the allowlist. Without it the OAuth flow has no default landing page at all.

**`redirect_urls` carries the local development callback.** `http://localhost:3000/auth/callback` matches nothing in the production set, so it has to be listed explicitly.

**Every secret is a reference, not a value.** `secret://GOOGLE_SECRET` and friends resolve through the secret store. There is no place in this block where a raw client secret belongs. See [Secrets](/operate/secrets).

**The generic provider has all three endpoints.** GitLab is spelled out in full precisely because it is not one of the four shipped providers. Remove any one of the three and it fails as a 500 at the authorize step.

**`default_roles` grants the new account its starting role.** Accounts created by the social callback receive it. Nothing from the provider's own groups or teams is imported.

<Warning>
Remember the ten-second config cache when editing this block through Studio or the API. A change saved now may not be the change a request reads immediately afterwards.
</Warning>
Studio reflects the same list. The provider picker in the Configuration tab offers exactly `google`, `github`, `discord` and `microsoft`, and the free-text box beside it, whose placeholder is `custom-provider-name`, is where a generic provider comes from.

### The shape of a session that social sign-in creates

It is worth being concrete about what the callback writes, because two of these rows are what you will go looking for when a session "does not remember" that it came from a provider.

| Field | Value for a social sign-in |
| --- | --- |
| `family` | The token family hex string. This is what `session_id` in a token response refers to. |
| `method` | `oauth:<provider>`. |
| `aal` | `aal1`, unless MFA ran, in which case `aal2`. |
| `org` | The session's organization, or null. A social sign-in starts unscoped. |
| `ip`, `user_agent` | Taken from the callback request. |
| `last_refreshed_at` | Null until the first refresh. |
| `revoked_at` | Null while the session is live. |

The `method` value is the one to rely on if you want to distinguish social sessions from password sessions in the UI. It is the same value reported by `GET /auth/v1/sessions`, and it is the same value an administrator sees in Studio.

### Rate limits on the social path

| Bucket | Limit | Window | Applies to |
| --- | --- | --- | --- |
| `akz:auth` | 30 | 60 seconds | `/signup` and `/token`. |
| `akz:links` | 10 | 60 seconds | The endpoints that send email, including a magic-link request. |
| `akz:mfa` | 10 | 60 seconds | The MFA verification endpoints. |

The OAuth routes themselves are not in that table. That is not an oversight — a browser navigation is not something a client can retry cheaply, and the natural rate limiting for the flow is the state cookie's own expiry plus the provider's consent screen.

<Info>
If you build a test that drives the whole social flow repeatedly, the limit that will bite you is the ten-per-minute bucket on MFA completion, not anything on the OAuth routes. See [Rate limits](/reference/limits).
</Info>

### Reading the raw provider payload

The identity stores the provider's untouched userinfo response under its `data` column, alongside the normalised fields.

| Stored on the identity | Purpose |
| --- | --- |
| `provider` | The provider key this identity belongs to. |
| `subject` | The provider's stable identifier for the person. |
| `email`, `email_verified` | A snapshot of what the provider said at link time. |
| `data` | The raw profile payload, refreshed on each sign-in. |
| `last_sign_in_at` | Updated on every subsequent sign-in. |

The normalised columns are what the decision tree reads. The `data` column is not read for matching — it is kept so you can inspect what a provider actually returned when a profile looks wrong.

<Warning>
Do not build account matching on `data`, or on `email` as stored on the identity, rather than on the live profile. The identity's email is a snapshot from a past sign-in and is not re-verified against the account on later visits. The decision tree reads the profile from the current callback, which is why a provider-side email change does not retroactively move an identity between accounts.
</Warning>

### Several providers, one person

A person may end up with one account and three identities on it — Google, GitHub and a generic provider. Each is a separate `Identity` row with its own subject, all pointing at the same user.

| Situation | Result |
| --- | --- |
| They sign in with any of them. | Branch 2 finds their identity, signs them into the same account. |
| They sign in with a fourth, new provider. | Branch 3 matches by verified email, if the provider verified it. |
| They unlink one. | Only that identity is removed. The others still work. |
| They unlink their last one, with no password. | `409` — the account would be unreachable. |

This is the shape a mature account takes, and it is worth designing for: an account's sign-in methods are a set, and the password is just another member of it.

<Warning>
Because branch 3 matches by verified email, adding a new provider to an environment that existing users already have accounts for will quietly attach those users' new identity to their existing account. That is usually what you want, but it does mean enabling a provider is a user-visible change, not only a configuration one. The `user.created` events distinguish genuine new accounts from matches if you need to tell them apart afterwards.
</Warning>

## Answering the questions people actually ask

### Why did my provider vanish from the sign-in page?

Because `enabled_providers()` filters on exactly two conditions — the enabled switch being on, and a `client_id` being set. The most common cause by a wide margin is a provider entry with credentials but no client ID, which is invisible everywhere: it does not appear in the settings response, it does not appear in Studio's enabled list, and using it returns a 404.

The second cause is the config cache. A provider you enabled seconds ago may not be in the response yet.

### Why can I not find the callback URL to paste into the provider console?

It is derived, not configured. It is `{public_url}/auth/v1/callback/{project}/{env}/{provider}`, and both `public_url` and the environment are inputs. If you cannot recall what `public_url` resolves to, check whether the environment sets its own or is inheriting Akountz's installation-wide setting — that inheritance is a common surprise in a multi-environment deployment.

### Can I offer Apple sign-in?

Not as a built-in provider. Apple is not one of the four that ship, so an `apple` entry is a generic provider and needs all three endpoints supplied by hand. The same applies to Facebook and LinkedIn. This is worth repeating because it is the single most common incorrect expectation carried over from other products' documentation.

### Should I match accounts by email?

You already are, and the system already guards it. Branch 3 of the decision tree matches by email, and only when the provider verified it. You do not need to add anything to your own code, and you should not try to relax the condition — the guard is the security property, not a limitation.

### Why did a user get `email_unverified_conflict` instead of an account?

Because they already have one. Their provider reported the address as unverified, so the callback refused to attach a new identity to the existing account. The resolution is for them to sign in by password or magic link and link the provider from the signed-in account, which takes a path that does not depend on email verification.

### Does a social sign-in count as verified for email verification requirements?

It depends on the provider, and the answer is per account rather than per flow. When the callback creates an account from a profile whose email the provider verified, the account is marked verified immediately — so it can sign in even in an environment that requires verification. When the provider did not verify, the account is created unverified, and in an environment requiring verification that account cannot sign in normally until it confirms the address.

<Warning>
This is a genuine difference between providers, and it means `require_email_verification` behaves differently depending on which provider a person used. Google and Microsoft generally verify; some generic providers never do. If you require verification and offer a provider that does not verify, accounts arriving through it will be stuck.
</Warning>

### Can a social sign-in be scoped to an organization?

Not in the redirect. A social sign-in starts a session unscoped. To scope it, the client completes whatever it was doing and then refreshes with an `org`, which switches the session's organization the same way it does for a password session. See [Organizations](/auth/organizations).

### What happens if I remove a provider from configuration?

Existing identities remain, and sign-in through that provider stops working because the provider can no longer be built. Anyone relying on it as their only sign-in method loses access through no fault of their own, so removing a provider is a user-visible change worth announcing. Their other methods — another provider, or a password — continue to work.

### Do the tokens arrive in a query string anywhere?

No. Social sign-in returns tokens in a fragment, and the magic-link hosted page does the same when it redirects. Query parameters are used for the one-time token in an emailed link, which is a different thing: that token is a signed reference to a database row that must travel to a server, whereas a session token must not. See [Magic links](/auth/magic-links).

<AccordionGroup>
  <Accordion title="Why does my generic provider work for new users but fail for existing ones?">
    Almost always the verified-email rule. Creating an account does not require the provider to have verified the address. Matching an existing account does. So a provider that exposes no verification claim will happily create accounts and then refuse to attach those same accounts on their second visit, with `email_unverified_conflict`.
  </Accordion>
  <Accordion title="Should I store the provider's access token?">
    The callback does not keep it on the account. It is available during the callback if you need it, but nothing in the authentication flow requires storing it, and an expired provider token is of no use to Pawabase. Store it only if your application has a real reason to call the provider's API later.
  </Accordion>
  <Accordion title="Can two environments share one provider application?">
    They can, if you register both callback URIs, since each environment produces a different path. It is simpler and less error-prone to use one application per environment, and it keeps revoking one environment's access from affecting the other.
  </Accordion>
</AccordionGroup>
### Provider registration checklist

The values you need from a provider's developer console, and what each one is used for. This is the same for all four shipped providers and for any generic one.

| Value | Where it goes | Notes |
| --- | --- | --- |
| Client ID | `client_id` | Public. Safe in configuration. |
| Client secret | `client_secret` | Reference it as `secret://NAME`. |
| Callback URL | Registered at the provider, not here. | Must match exactly, including the environment segment. |
| Scopes | `scopes` | Usually needs an email scope. |
| Provider-specific extras | `tenant` for Microsoft. | Only read by the provider that accepts it. |

The callback URL is the value with no tolerance at all. Providers compare it exactly, and the derived form includes the project and environment, so an environment that has not been given its own provider application cannot reuse another environment's registration.

```bash
# The exact URI to register for one environment and provider
echo "https://auth.example.com/auth/v1/callback/acme/production/google"
```

<Info>
Register the callback for the environment you are testing. A registration for staging does not accept a callback arriving for production, and the provider reports the mismatch rather than reaching Pawabase — so you never see a Pawabase log line explaining it.
</Info>

### Choosing which providers to enable

A short, opinionated guide, because enabling everything is a common first instinct and a bad one.

| Consideration | Guidance |
| --- | --- |
| Which providers verify email | Prefer them. Without verification, returning users cannot be matched by email and get `email_unverified_conflict`. |
| Enterprise directories | Microsoft with `tenant` set is the usual answer for a company-only deployment. |
| Provider availability per region | Enabling a provider a region cannot reach adds a button that fails for those users. |
| Provider outage behaviour | With only one provider, an outage is an outage. Two providers is genuine redundancy. |
| Support burden | Each provider is a configuration surface with its own scopes, secrets and console. |

<Warning>
Enabling a provider for an environment where existing users already have accounts is a user-visible change. Branch 3 will attach those users' new identity to their existing account by verified email, which is usually what you want — but if you did not expect the merge, it will surprise people who already had an account.
</Warning>

### Server-to-server and CLI sign-in

The social routes are browser navigations, so they are not usable from a script. A backend process cannot "sign in with Google" — it has no browser, no consent screen, and no state cookie.

What it can do is act as an operator or a service. An admin can create a user from the **New user** modal in Studio's **Users & auth** page, or call the admin routes with a service key, and the resulting account signs in through the normal password or magic-link path. See [Managing users](/auth/managing-users) and [API keys](/operate/api-keys).

<Info>
If you are automating a pipeline that needs to act as a person, this is the usual answer: create the account server-side with a service key, then sign in with the password grant from that script, rather than trying to drive the social flow. The interactive flows are browser navigations and are not scriptable; see [Managing users](/auth/managing-users) for the admin routes and [API keys](/operate/api-keys).
</Info>
### Browser-side integration, end to end

Putting the pieces together, because the fragment handling is the part most worth getting right and it is easy to get subtly wrong.

The application needs three things: a sign-in page that renders buttons, a callback page that reads the fragment, and somewhere to keep the session. The flow between them:

```text
1. GET  /auth/v1/settings              -> which providers to render
2. 302  /auth/v1/authorize/acme/production/google
3. ...  the provider's consent screen, which the person sees
4. 302  https://auth.example.com/auth/v1/callback/acme/production/google
5. 302  https://app.example.com/auth/callback#access_token=...
6. the callback page reads location.hash and stores the session
```

Reading the fragment is straightforward, but two details matter:

```text
// Runs only in the browser. The server that served this page never saw the tokens.
const raw = window.location.hash.replace(/^#/, "");
if (raw) {
  const params = new URLSearchParams(raw);
  if (params.has("error")) {
    // signup_disabled, denied, state_mismatch, email_unverified_conflict, ...
    showError(params.get("error"));
  } else if (params.get("mfa_required") === "true") {
    // Not a session yet. Prompt for the second factor.
    promptForCode(params.get("mfa_token"));
  } else {
    // Four keys only. No session_id, no user record.
    storeSession({
      access_token: params.get("access_token"),
      refresh_token: params.get("refresh_token"),
      expires_in: Number(params.get("expires_in")),
    });
    // The session id and the user record come from the API, not the fragment.
    hydrateFromApi();
  }
  // Clean the URL so the tokens are not left in history or a copied link.
  history.replaceState(null, "", window.location.pathname);
}
```

| Detail | Why it matters |
| --- | --- |
| Read `location.hash`, not a query string. | The fragment is where the tokens are. |
| Check `error` first. | A failure redirect carries `error` and nothing else. |
| Check `mfa_required` before reading a token. | The MFA redirect carries no `access_token` at all. |
| Expect only four keys on success. | `session_id`, `org` and the user record are not in the fragment. |
| Clean the URL afterwards. | Otherwise the tokens sit in browser history and in any copied link. |
| `href` in the body, not just JavaScript. | Without it, the sign-in page cannot offer the button at all. |

<Warning>
Do not render social buttons as plain links to a URL you hardcoded. The authorize path includes the project and the environment, both of which change between deployments, and the provider set changes per environment. Render from the settings response and build the path from the project's own context.
</Warning>

See [Client integration](/auth/client-integration) for how to store the session and refresh it, and [Tokens and sessions](/auth/tokens-and-sessions) for the full token lifecycle.

<Info>
If you need the person back on a specific page after signing in, pass that page as `redirect_to` on the authorize request and make sure it is inside the allowlist. A URL outside the allowlist is refused at the authorize step rather than ignored, which is the safer failure — but it does surface as a `400` rather than as a sensible error in the browser.
</Info>

### What the account looks like afterwards

| Question | Answer |
| --- | --- |
| Does the account have a password? | No. It has an unusable password until someone sets one. |
| Is the email verified? | Only if the provider said it was. |
| What roles does it have? | The environment's `default_roles`. |
| Is it a member of any organization? | Not unless an invitation or an admin action added it. |
| What can it sign in with? | Any linked provider, and password or magic link once set up. |
| Where is the session listed? | In the environment's sessions, with method `oauth:<provider>`. |

That last row and the first are the pair people are surprised by. A social sign-in produces a completely ordinary session and an account that is missing exactly one thing — a password — which most applications never need.

### Migrating to a different provider set

Social login configuration changes have effects that outlive the change itself, and it is worth being deliberate about them.

**Turning a provider off stops sign-in without touching anyone.** Existing identity rows stay. Anyone whose only method was that provider simply cannot sign in through it, and the failure is a 404 at the authorize step rather than a refusal at the callback — because a provider that is not enabled is never built.

**Turning a provider on merges accounts.** This is the one that surprises people. Existing users whose verified provider email matches an account get that identity attached to the account they already had, by branch 3. If you expected a separate account per provider, that is not what happens, and it is not configurable.

**Changing a client ID orphans the old identities.** The identity key is `(project, env, provider, subject)`. A subject is the provider's identifier *within that provider's own installation*, so replacing the client ID typically produces different subjects for the same people. The old identities stop matching, and the accounts behind them become reachable only by their other methods. If you rotate a client ID, expect to re-link.

**Changing the callback host strands in-flight logins.** Anyone mid-flow when `public_url` or `site_url` changes will come back to a host that is no longer registered, and the provider rejects the request before Pawabase sees it.

| Change | Who notices | What to do |
| --- | --- | --- |
| Disable a provider | That provider's users, at sign-in. | Announce it; offer an alternative method. |
| Enable a provider | Nobody breaks. Accounts may merge. | Tell users their Google account now works. |
| Replace a client ID | Existing users of that provider. | Expect re-linking; keep the old method available meanwhile. |
| Change `site_url` | Nobody, once saved. | Confirm the allowlist still matches the new host. |
| Change `public_url` | In-flight logins only. | Update the provider's registered callback. |

<Warning>
Removing the last sign-in method from an account is not blocked by the system unless the account has no usable password — that guard applies to a user removing their own identity. An administrator disabling or deleting accounts is a separate action with separate consequences. See [Managing users](/auth/managing-users).
</Warning>

### Auditing a social sign-in after the fact

Both the event stream and the login history answer "what happened", from different angles.

| Source | Records | Use it for |
| --- | --- | --- |
| `user.signed_in` | Successful sessions, with `method`. | Confirming a sign-in occurred. |
| `identity.linked` | A provider attached to an account. | Confirming a link, and when. |
| `user.created` | A new account from a provider. | Separating new accounts from email matches. |
| `user.verified` | Not emitted by social login. | Only password-verification flows. |
| `LoginEvent` rows | Every attempt, success or failure, with `reason`. | Investigating a specific failure. |

For a specific person's history, `GET /auth/v1/history` returns their recent attempts for the signed-in user — the last fifty, each with its kind, method, outcome, IP and user agent. For an environment-wide view, the **Sign-in activity** tab in Studio shows the same records with a failures-only filter.

```bash
curl "https://api.example.com/auth/v1/history" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "X-Pawabase-Context: $CONTEXT"
```

```json
{
  "data": [
    {
      "kind": "sign_in",
      "method": "oauth:google",
      "success": true,
      "reason": null,
      "ip": "203.0.113.9",
      "user_agent": "Mozilla/5.0",
      "at": "2025-06-01T10:15:00+00:00"
    }
  ]
}
```

<Info>
The `method` field is the fastest way to answer "did they come through the provider or the password form", and the `reason` field on a failure carries the error code from this page — so a login history is often a better diagnostic than the event stream when you are chasing one specific failure.
</Info>

### Error codes by cause, grouped

The same twelve codes appear in two places on this page; grouping them by what you should do about them is the form that helps at 2am.

**The person did something ordinary.** Nothing is broken.

| Code | What happened | Response |
| --- | --- | --- |
| `denied` | Closed the consent screen. | Send them back to the sign-in page. |
| `state_expired` | Left the consent screen open. | Send them back; say it timed out. |

**The person did something plausible and it failed.**

| Code | What happened | Response |
| --- | --- | --- |
| `email_unverified_conflict` | Provider did not verify an email that already has an account. | Tell them to sign in normally, then link the provider. |
| `email_required` | Scopes did not include an email. | Fix the provider's scopes. |
| `identity_already_linked` | The identity belongs to another account. | Unlink it there first. |
| `account_disabled` | An administrator disabled the account. | Point them at an administrator. |

**You have a configuration problem.**

| Code | What happened | Response |
| --- | --- | --- |
| `signup_disabled` | Environment is invite-only. | Expected. Create the user, or invite them. |
| `exchange_failed` | Code rejected, or a redirect URI mismatch. | Check the registered callback path. |
| `profile_failed` | Userinfo failed, or no subject claim. | Check scopes and the userinfo endpoint. |
| `provider_error` | The provider refused for another reason. | Read the provider's own logs. |
| `state_mismatch` | No usable state cookie. | Usually HTTPS, or a rotated secret mid-flow. |

**Something is wrong in a way you should not expect to see.**

| Code | What happened | Response |
| --- | --- | --- |
| `provider_misconfigured` | A programming error reached a redirect. | Look at the code, not the user's account. |

<Info>
The distinction that saves the most time: `denied` and `state_expired` mean the provider conversation completed and produced nothing. `state_mismatch` means it never started properly. The first two are a user, the third is you.
</Info>

### What a provider entry looks like when it is wrong

Three misconfigurations produce a 404, and they look different in configuration but identical in behaviour.

| Configuration | What is wrong | Why it 404s |
| --- | --- | --- |
| `{"enabled": false, "client_id": "x"}` | Deliberately disabled. | The enabled check fails. |
| `{"client_id": "", "client_secret": "secret://X"}` | Client ID never filled in. | The client ID check fails. |
| `{"enabled": true}` | Credentials never added. | The client ID check fails. |
| Not present at all | No entry. | No settings to read. |

The second and third are the same failure and are by far the most common. The card looks configured in Studio because it exists, and the **Enabled** switch is on, because the default is on.

<Warning>
If a provider 404s, check the client ID before anything else. The secret being wrong produces a very different failure — the redirect works and the callback fails at the token exchange with `exchange_failed`.
</Warning>

### Enabling social login without breaking what exists

The order that avoids surprises, given the branch structure described above.

| Consideration | Why the order matters |
| --- | --- |
| Confirm the callback URI with the provider first. | A wrong URI means nothing can be tested end to end. |
| Set `site_url` before enabling providers. | It is the default landing page and the first allowlist entry. |
| Confirm sign-up is on *only* if new accounts are wanted. | Otherwise the flow will refuse unknown people, which is a valid configuration but surprises users. |
| Enable one provider, test the returning-user path. | The returning path exercises branch 3, which is where scope problems appear. |
| Add the rest. | Each is independent once the first works. |

<Info>
The returning-user test is the one people skip, and it is the one that finds scope and verification problems. A brand new email address passes with almost any scope configuration; a second sign-in with an address that already has an account is what actually proves the provider verified the email.
</Info>

### Every field in the provider block, with an example value

The complete set of keys a provider entry accepts, so nothing here is a surprise.

```json
{
  "providers": {
    "microsoft": {
      "enabled": true,
      "client_id": "00000000-1111-2222-3333-444444444444",
      "client_secret": "secret://MICROSOFT_SECRET",
      "tenant": "common",
      "scopes": ["openid", "email", "profile"],
      "authorize_params": { "prompt": "select_account" },
      "authorize_endpoint": "https://login.microsoftonline.com/common/oauth2/v2.0/authorize",
      "token_endpoint": "https://login.microsoftonline.com/common/oauth2/v2.0/token",
      "userinfo_endpoint": "https://graph.microsoft.com/oidc/userinfo"
    }
  }
}
```

| Key | Type | Required | Read by | Effect |
| --- | --- | --- | --- | --- |
| `enabled` | bool | no | all | False removes the provider entirely. |
| `client_id` | str | **yes** | all | Absent means invisible and 404. |
| `client_secret` | str | no | all | Empty is allowed; some flows are public. |
| `tenant` | str | no | Microsoft only | Ignored by every other provider. |
| `scopes` | list | no | all | Replaces the class default entirely when set. |
| `authorize_params` | dict | no | all | Extra parameters on the authorize URL. |
| `authorize_endpoint` | str | generic only | all | Overrides the class default. |
| `token_endpoint` | str | generic only | all | Overrides the class default. |
| `userinfo_endpoint` | str | generic only | all | Overrides the class default. |

Two of these have consequences that are easy to miss.

**`scopes` replaces rather than extends.** When you set `scopes`, the list you supply is what is requested — it is not merged with the provider class's defaults. A provider that needed an email scope by default will stop asking for it if you supply a shorter list.

**`authorize_params` is for things scopes cannot express.** Provider-specific prompt behaviour, a login hint, a domain hint. It goes on the authorize URL only and never reaches the token exchange.

<Warning>
Every key in this table other than `enabled` and `client_id` is inert for the provider that does not read it. Setting `tenant` on Google, or `userinfo_endpoint` on GitHub, does nothing at all — no warning, no error. It is worth matching keys to providers when editing configuration by hand.
</Warning>

### The `authorize` and `callback` pair as one unit

The two URLs, in the order they are used, for one environment.

```text
Start (your browser goes here):
  https://auth.example.com/auth/v1/authorize/acme/production/google
      ?redirect_to=https://app.example.com/auth/callback

Return (registered at the provider, the provider sends the browser here):
  https://auth.example.com/auth/v1/callback/acme/production/google

Land (where the person ends up, tokens in the fragment):
  https://app.example.com/auth/callback#access_token=...
```

| Segment | Value | Where it comes from |
| --- | --- | --- |
| Host | `auth.example.com` | `public_url`, falling back to Akountz's own setting. |
| `/auth/v1/authorize/` | Fixed prefix | The route. |
| `acme` | The project slug. | The path — not the context header. |
| `production` | The environment. | The path. |
| `google` | The provider key. | The path. |
| `redirect_to` | Optional query parameter. | Must be inside the allowlist. |

This is the clearest illustration of the tenancy rule in one block of URLs. The project and environment appear **in the URL** rather than in a header, because a redirecting browser carries no context — and that is exactly why a token minted by one environment is meaningless in another. See [Authentication](/auth/overview).

<Info>
If you host the authorize route behind a different hostname than the callback, the state cookie will not come back and every callback will fail as `state_mismatch`. Both URLs must be on the same host, since the state cookie is set on whichever host handled the first request.
</Info>

### Choosing where the browser lands

The landing page is yours, and the only constraint is that it must be inside the allowlist.

| Landing choice | Consequence |
| --- | --- |
| `{site_url}` | The browser returns to your app's base URL. You handle the fragment there. |
| `{site_url}/auth/callback` | A dedicated page that reads the fragment and nothing else. |
| A URL in `redirect_urls` | Allowed, and the fragment still carries the tokens. |
| A URL outside the allowlist | Refused at the authorize step with a 400. |
| No target at all | The callback returns JSON instead of redirecting. Useful for testing. |

The last row is worth knowing about: with no `redirect_to` and no `site_url`, a successful social sign-in returns the four keys as a JSON body instead of a fragment. That is the simplest way to test a provider end to end with curl, since you can see the response directly.

```bash
# Start a sign-in with no redirect target. The callback returns JSON.
curl -sD- -o /dev/null "https://auth.example.com/auth/v1/authorize/acme/production/google" | head -20
```

<Warning>
Without a `site_url`, magic links and email verification also fall back to Akountz-hosted pages rather than your application. The two features share the same setting, so the decision is made once. See [Magic links](/auth/magic-links).
</Warning>

### Account resolution as a lookup table

The decision tree restated as the exhaustive table of inputs and outcomes, for when you want to predict a result rather than understand the rule.

| Identity found | Link ticket | Email verified | Account holds email | Outcome |
| --- | --- | --- | --- | --- |
| yes | — | — | — | Sign in as the identity's user. |
| no | yes | — | — | Attach to the ticket's user. |
| no | yes | — | — | `identity_already_linked`, if the identity belongs to someone else. |
| no | no | yes | yes | Sign in as that account; create the identity. |
| no | no | yes | no | Create an account. |
| no | no | no | yes | `email_unverified_conflict`. |
| no | no | no | no | Create an account, unverified. |
| no | no | — | no email at all | `email_required`. |

The last two rows are worth separating mentally, because they behave differently in an environment that requires verification: an account created from an unverified profile cannot then sign in normally, while an account created from a verified one can.

<Info>
Rows two and three share a row because the outcome depends on which user the identity currently belongs to. In every other case the link ticket simply names the account and the check that can fail is the ownership one.
</Info>

### What each session record tells you afterwards

Once a social sign-in has happened, the session is the durable record of it. These are the questions people ask about a session and where the answer lives.

| Question | Where to look |
| --- | --- |
| Which provider did this session use? | `method`, as `oauth:<provider>`. |
| Did MFA happen? | `aal` is `aal2` rather than `aal1`. |
| Which organization is it scoped to? | `org`, null when unscoped. |
| When did it last refresh? | `last_refreshed_at`. |
| Has it been revoked? | `revoked_at`. |
| Where did it come from? | `ip` and `user_agent`, from the callback request. |
| Which user? | The `user` field. |

The `method` and `aal` pair is the one worth internalising: together they tell you both how someone authenticated and how strongly, from a single row, without consulting the event stream.

### Distinguishing a social session in a policy

If you want to require a second factor for some operations, `aal` is the claim to branch on. It is read from the token at issue time and rides along with every request, so no service needs to call back to Akountz.

```json
{
  "claims": {
    "sub": "01HQ8X4M2K9P7R3T6V0YB5ZCNDA",
    "prj": "acme",
    "env": "production",
    "typ": "access",
    "aal": "aal2",
    "sid": "9f2c1ab4e7d84f0c9b3a5e61d2c4807f6a9e3b5c1d0f28496ab7c3e5d1f0a2b4c6"
  }
}
```

| Assurance level | How it is reached |
| --- | --- |
| `aal1` | Any password, magic-link or social sign-in that did not complete MFA. |
| `aal2` | A sign-in that completed an MFA challenge, or enrolment on a live session. |

A social sign-in does not reach `aal2` on its own. It reaches it exactly as a password sign-in does — by returning an MFA challenge when the account has a factor and the environment allows it, and by the client completing that challenge. See [Multi-factor authentication](/auth/mfa) and [Auth in policies](/auth/auth-in-policies).

<Warning>
`aal` is written into the token when it is issued. Elevating a session's assurance does not retroactively change access tokens that already exist — the elevated session mints new ones. If a policy needs `aal2`, a client holding a pre-elevation token will still present `aal1`.
</Warning>

### Keeping the two flows consistent

Social sign-in, password sign-in and magic-link sign-in all converge on the same session shape. Knowing where they agree and where they differ saves a lot of duplicated client logic.

| Aspect | Password | Magic link | Social |
| --- | --- | --- | --- |
| Endpoint | `POST /auth/v1/token` | `POST /auth/v1/magic-link/verify` | `GET /auth/v1/callback/...` |
| Where the result arrives | JSON body | JSON body | URL fragment |
| Can challenge for MFA | yes | yes | yes |
| Session `method` | `password` | `magic_link` | `oauth:<provider>` |
| Reaches `aal2` | with a challenge | with a challenge | with a challenge |
| Scoped to an org | at request time | not at request time | not at request time |
| May create an account | yes, via `/signup` | yes, by default | yes, if sign-up is on |

The two rows that differ most in practice are the second and the sixth. Social sign-in is the only one that delivers tokens through a browser redirect, and the only one that cannot be scoped to an organization at the moment it starts — both consequences of it being a browser navigation rather than an API call.

<Info>
Because all three converge on the same session response, everything downstream of sign-in — refresh, revocation, session listing, `aal`, org scoping — behaves identically regardless of how the person got there. The `method` field is the only lasting difference.
</Info>

### Verifying a provider works, without a browser

The callback returns JSON when there is no redirect target, which makes the whole flow testable with a cookie jar.

```bash
# Start the flow. -c keeps the state cookie the callback will require.
curl -sc jar.txt -o /dev/null -w '%{redirect_url}\n' \
  "https://auth.example.com/auth/v1/authorize/acme/production/google"
```

That prints the provider's authorize URL. Follow it, consent, and the provider will redirect the browser to the callback. To capture the result without a browser, take the `code` from the callback URL and replay the callback with the same cookie jar:

```bash
# The callback, with the cookie jar from the start step.
curl -sb jar.txt "https://auth.example.com/auth/v1/callback/acme/production/google?code=THE_CODE&state=THE_STATE"
```

```json
{
  "access_token": "...",
  "refresh_token": "...",
  "expires_in": 900,
  "token_type": "bearer"
}
```

| What you learn from this | How |
| --- | --- |
| The provider is configured correctly. | A 404 or 500 means it is not; nothing else runs. |
| The token exchange works. | `exchange_failed` means the secret or the callback URI is wrong. |
| The profile is readable. | `profile_failed` means the scopes or the userinfo endpoint. |
| Account resolution works. | Any `error` code is from the decision tree, not the provider. |

<Warning>
The state cookie is required. Running the callback without the cookie from the start step always fails as `state_mismatch`, which is the flow working correctly rather than anything being misconfigured.
</Warning>

### Reading an `Identity` row directly

When you need to know why an account is not being matched, the identity table is the place to look.

| Column | What it tells you |
| --- | --- |
| `project`, `env` | Which environment owns this identity. A row for another environment is irrelevant here. |
| `provider` | The provider key used. |
| `subject` | The provider's identifier for this person. |
| `email` | A snapshot from the last time this identity signed in. |
| `email_verified` | What the provider said at that time. |
| `last_sign_in_at` | Whether this identity is still in use. |

```sql
SELECT provider, subject, email, email_verified, last_sign_in_at
FROM akz_identities
WHERE project = 'acme' AND env = 'production';
```

The `subject` column is the join key. If a person is not matching on their second sign-in, comparing the subject stored here against the subject the provider returned this time tells you whether the provider's identifier moved — which happens when a client ID is replaced, or when the provider re-keys accounts.

<Warning>
Do not treat the `email` column as authoritative for matching. It is a snapshot of what the provider said at link time, and the decision tree deliberately does not read it. A provider-side email change does not move an identity between accounts.
</Warning>

### What a correct setup looks like in Studio

The end state, so you can check your work against something concrete. Under **Users & auth**, **Configuration**:

| Section | What it should show |
| --- | --- |
| **Sign-up** | **Sign-up enabled** reflecting your intent. **Default roles** populated. |
| **URLs** | **Site URL** set, so the browser has somewhere to land. |
| **OAuth providers** | One card per provider, each with a **Client ID** and a `secret://` reference. Shipped providers show no endpoint fields. |
| **Sign-in methods** | **MFA (TOTP)** on if you want second factors available. |
| **Email templates** | Magic-link and password copy, if you have changed them. |

And under **Users**, a user who signed in socially shows an MFA status matching what they enrolled, and a session list whose entries carry the provider as their method.

<Info>
After saving, give the config cache up to ten seconds before testing. A sign-in attempt in that window reads the previous configuration, which is a frequent cause of "my change did nothing".
</Info>

### Common provider-specific notes

Where a shipped provider behaves in a way worth knowing before you support it.

**GitHub and the private address.** A GitHub profile has a public email that may differ from the address on the account, and the private one requires the email scope. Without the email scope the profile comes back without a usable address, and you get `email_required` for new users rather than a matching failure for returning ones.

**Discord and identity.** Discord distinguishes basic identity from a verified email address, and the scopes are separate. A Discord login configured with only the basic scope returns a profile whose `email_verified` is false, which means every Discord sign-in either creates a new account or fails with `email_unverified_conflict` on the second visit.

**Google and Microsoft.** Both verify addresses as a matter of course, which is why they are the two providers most likely to work with no scope configuration at all. Microsoft additionally needs `tenant` decided deliberately — `common` accepts anyone, `organizations` accepts only your own directory.

**Microsoft's `tenant` is not a Studio field.** It is the one provider-specific setting that cannot be set from the Configuration tab, so it belongs in hand-written configuration. See [Microsoft and tenants](#microsoft-and-tenants).

| Provider | Verifies email by default | Scope configuration usually needed | Provider-specific settings |
| --- | --- | --- | --- |
| `google` | yes | usually none | none |
| `github` | when the email scope is granted | yes, for the address | none |
| `discord` | with the email scope | yes | none |
| `microsoft` | yes | usually none | `tenant` |
| Generic | depends entirely | yes | the three endpoints |

<Warning>
The pattern across all four is the same: the thing that goes wrong is almost always the email scope, and the symptom is always an account that behaves correctly the first time and fails the second.
</Warning>
