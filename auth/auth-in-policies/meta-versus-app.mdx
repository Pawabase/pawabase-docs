The token carries two optional metadata objects, and the difference between them is the single most important security property in the whole system.

From `issue_user_token`'s own documentation:

```python
extra: Additional public claims (``user_metadata``), as ``meta``. Users can
    edit these, so policies must not trust them.
app: Administrator-controlled claims (``app_metadata``), as ``app``. Only
    admins can change them, so policies may rely on them.
```

The minting reflects it:

```python
if extra:
    payload["meta"] = extra
if app:
    payload["app"] = app
```

and in `_access_token`:

```python
extra=user.user_metadata or None,
app=user.app_metadata or None,
```

| | `meta` claim | `app` claim |
| --- | --- | --- |
| Source | `AuthUser.user_metadata` | `AuthUser.app_metadata` |
| Who may write it | The user themselves | An administrator or service key |
| Reachable at | `$auth.claims.meta.*` | `$auth.claims.app.*` |
| Trustworthy for access decisions | **No** | **Yes** |

<Warning>
The claim names are **`meta`** and **`app`**. There are no `user_metadata` or `app_metadata` claims, and no `$auth.claims.user` — `user` is a *subject* prefix in token verification, not a claim name here. `{"eq": ["$auth.claims.user.tier", "premium"]}` resolves to `None` and refuses, which fails closed but for the wrong reason.
</Warning>

A user edits their own metadata through `PATCH /auth/v1/user`:

```python
if body.data is not None:
    user.user_metadata = {**(user.user_metadata or {}), **body.data}
    changed.append("user_metadata")
```

That is a shallow merge, so a user can add, overwrite or remove any top-level key in their own `user_metadata` — including one your UI uses to decide what to show. Nothing stops them calling the endpoint directly.

The safe pattern is therefore: write the value an administrator controls, and read it from `app`.

```json
{ "eq": ["$auth.claims.app.tier", "premium"] }
```

If you *must* use `meta` — say, a display preference — treat it as untrusted input, not as an authorisation input. A user who can set `{"department": "finance"}` on themselves can set it to anything.

<Info>
`create_account` accepts `app_metadata` as a parameter, but the public `SignUp` body does not expose it — `SignUp` only takes `data`, which becomes `user_metadata`. `app_metadata` is settable through admin routes and flows, not through sign-up.
</Info>


## Python policies

When JSON cannot express the rule — a database lookup, a clock-and-hash comparison, an ownership chain — you register a Python function:

```python
from pawabase_core.policies import policy

@policy("same-team", description="Callers on the record's team")
async def same_team(context):
    team = await lookup_team(context["record"]["team_id"])
    return context["auth"]["user_id"] in team.members
```

The registry:

```python
def policy(
    name: str, *, description: str = ""
) -> Callable[[Callable[..., Any]], Callable[..., Any]]:
    """Register a Python policy under *name*."""

    def decorator(func: Callable[..., Any]) -> Callable[..., Any]:
        _registry[name] = Policy(
            name=name, handler=func, description=description or (func.__doc__ or "").strip()
        )
        return func

    return decorator
```

Rules that follow from the engine:

<AccordionGroup>
  <Accordion title="The handler receives the full context, not just $auth">
    `context` is the whole evaluation context — `auth`, `credential`, `request`, `project`, `env`, `record`, `input`. The registry's example reads `context["record"]` and `context["auth"]`.
  </Accordion>
  <Accordion title="Sync or async both work">
    `check` awaits the result if `inspect.isawaitable(result)`, so a plain `def` returning a bool is fine.
  </Accordion>
  <Accordion title="You get a shallow copy">
    The engine calls `policy.handler(dict(context))`. Mutating the top level is safe; mutating a nested dict is not.
  </Accordion>
  <Accordion title="A Python policy cannot be combined in a list reference">
    `resolve_ref` raises `PolicyError("Python policies cannot be combined in a list; call them from Python")`. Call it from another Python policy, or combine at the resource level with `all`.
  </Accordion>
  <Accordion title="On a list, it becomes the residual">
    `plan` returns `ListPlan(True, residual=policy, …)` with no filters, so the whole table is read and the handler is called per row.
  </Accordion>
  <Accordion title="Returning a non-bool is coerced">
    `allowed = bool(result)`. Return something truthy and it allows; return `None` and it refuses.
  </Accordion>
</AccordionGroup>

```python
from pawabase_core.policies import policy, lookup


@policy("billing-admin")
async def billing_admin(context):
    """Account owners may change billing; support staff may too."""
    if context["auth"]["kind"] != "user":
        return False
    return context["auth"]["user_id"] == context["record"].get("billing_contact_id")


@policy("published-or-owner")
async def published_or_owner(context):
    record = context["record"]
    if record.get("status") == "published":
        return True
    return record.get("owner_id") == context["auth"]["user_id"]
```


## Storage policies

The storage layer asks its policy two questions, and Pawabase answers the first with the same JSON conditions:

```python
class PolicyStorage:
    """A Sillo storage policy backed by Pawabase policies.

    Args:
        engine: Resolves references.
        read: Policy reference for reading and listing.
        write: Policy reference for uploads and deletes.
        credential: The request's credential context (service keys bypass).
        signed_reads: Whether signed URLs may grant reads.
        signed_writes: Whether signed URLs may grant uploads.
    """

    def __init__(
        self,
        engine: PolicyEngine,
        *,
        read: Any = "authenticated",
        write: Any = "authenticated",
        credential: dict[str, Any] | None = None,
        project: str | None = None,
        env: str | None = None,
        signed_reads: bool = True,
        signed_writes: bool = True,
    ) -> None:
        self.engine = engine
        self.read_policy = engine.resolve_ref(read)
        self.write_policy = engine.resolve_ref(write)
        for resolved in (self.read_policy, self.write_policy):
            if resolved.handler is not None:
                raise ValueError("storage policies must be JSON conditions")
        self.credential = credential or {"is_service": False, "role": "anon", "scopes": []}
        self.project = project
        self.env = env
        self.signed_reads = signed_reads
        self.signed_writes = signed_writes

    def allows(self, action: Any, key: str, user: Any = None) -> bool:
        if self.credential.get("is_service"):
            return True
        name = getattr(action, "value", str(action))
        policy = self.read_policy if name in ("read", "list", "stat") else self.write_policy
        context = {
            "auth": policy_auth(user),
            "credential": self.credential,
            "project": self.project,
            "env": self.env,
            "object": {"key": key, "segments": key.split("/"), "action": name},
        }
        return evaluate(policy.condition, context)

    def signable(self, action: Any) -> bool:
        name = getattr(action, "value", str(action))
        return self.signed_reads if name in ("read", "list", "stat") else self.signed_writes
```

Three things to know:

<AccordionGroup>
  <Accordion title="There is an `$object` path, not `$record`">
    The object key and its path segments are exposed as `$object.key`, `$object.segments` (a list) and `$object.action`. This is the storage equivalent of `$record`.
  </Accordion>
  <Accordion title="Numeric segments index the list">
    Because `segments` is a real list, `$object.segments.0` is the first path component. A `users/<id>/…` layout is written `{"eq": ["$object.segments.0", "users"]}` and `{"eq": ["$object.segments.1", "$auth.user_id"]}`.
  </Accordion>
  <Accordion title="Python policies are rejected at construction">
    `raise ValueError("storage policies must be JSON conditions")`. The storage API is synchronous at the policy boundary. A Python policy is enforced in the storage routes instead, before the bucket is called.
  </Accordion>
</AccordionGroup>

```json
{
  "all": [
    { "authenticated": true },
    { "eq": ["$object.segments.0", "users"] },
    { "eq": ["$object.segments.1", "$auth.user_id"] }
  ]
}
```

Note that `read`, `list` and `stat` share the read policy, and everything else — upload, delete, and any action added later — falls to the write policy. New action names are write-by-default.
