A role, in Pawabase, is a **group with permissions attached**. That is the whole idea, and it is worth saying precisely because the word "role" suggests a model that does not exist here.

There is no `Role` model. There is no `RoleAssignment`. A role is a row in `perm_groups` together with rows in `perm_group_permissions`, and belonging to one is a row in `perm_user_groups`. Permissions can also be attached to a person directly, through `user_permissions`, with no group involved at all.

Everything else on this page follows from that. Two people can have identical effective access while holding entirely different records — one through a group, one through direct grants — because nothing requires access to arrive in a particular shape.

  <Card title="A group plus permissions" icon="users">`Group` is the role. `GroupPermission` is what it carries. There is no separate role table.</Card>
  <Card title="Two ways to be allowed" icon="key">Direct grants through `UserPermission`, or inherited from every group a person belongs to. Effective access is the union.</Card>
  <Card title="Names are environment-scoped" icon="globe">A role named `editor` in staging and one named `editor` in production are different rows, because names carry their environment as a prefix.</Card>
</CardGroup>

## Where this sits in the layered model

| Layer | What it does for permissions |
| --- | --- |
| **Akountz** (identity) | Owns the five tables. Defines roles, assigns them, resolves effective permissions, and stamps them into tokens. |
| **The API** (project config) | Owns `default_roles` — the roles granted at sign-up. Nothing else. |
| **Gateway / `pawabase_core`** | Verifies the token and exposes the claims. It never queries the permission tables. |

The permissions in an access token were read when the token was issued. No service re-reads the tables on each request, which is what makes enforcement cheap and also what makes a change take time to land. Both facts matter throughout this page.

<Info>
If you have not read [Authentication](/auth/overview), do that first — in particular the per-environment tenancy rule, since it is what makes the name-scoping rule below necessary.
</Info>

## The five tables

Sillo provides the permission model; Akountz re-keys it to ULIDs and renames the tables. Same columns, same methods, different primary key.

| Model | Table | What a row is |
| --- | --- | --- |
| `Permission` | `permissions` | A named capability, such as `posts:write`. |
| `Group` | `perm_groups` | A named collection of permissions. This is what a role is. |
| `UserPermission` | `user_permissions` | A capability granted straight to one person. |
| `UserGroup` | `perm_user_groups` | Membership: this person belongs to that group. |
| `GroupPermission` | `perm_group_permissions` | One capability inside one group. |

Two constraints are load-bearing:

| Model | Uniqueness |
| --- | --- |
| `UserGroup` | `(user_id, group)` — a person cannot join the same group twice. |
| `GroupPermission` | `(group, permission)` — a group cannot hold the same permission twice. |

Both prevent the duplicate rows that would otherwise make a member count wrong or a permission list noisy. They are enforced by the database rather than by the application, so they hold however the rows were created.

<Note>
`AuthUser` inherits Sillo's `PermissionMixin`, which supplies the relation methods these tables rely on. The mixin is why `Permission.of(user)` and `Group.of_user(user)` exist without any of that being written in Akountz.
</Note>

## Why names carry their environment

Sillo's `Permission` and `Group` names are unique across the whole database. Akountz serves many projects and environments from one installation, so a bare name would collide — a `editor` in staging could not exist alongside an `editor` in production.

The solution is a prefix, applied on the way in and stripped on the way out.

```text
Stored:     acme/production/editor      Returned:   editor
Stored:     acme/staging/editor         Returned:   editor
```

The prefix is `{project}/{env}/`, applied by one function and removed by another. Both are in `app/rbac.py`, and every name crossing the API boundary goes through them.

| Property | How the prefix delivers it |
| --- | --- |
| Two environments can both have `editor`. | Different stored names, so no collision. |
| Listing one environment's roles is a prefix query. | `name__startswith="acme/production/"`. |
| A user only sees their own environment's roles. | The strip function drops anything without the prefix. |
| A role name is never ambiguous in the database. | The prefix makes it globally unique. |

The strip function is worth reading closely, because it filters rather than trusting:

```python
def _strip(project: str, env: str, names: list[str]) -> list[str]:
    prefix = f"{project}/{env}/"
    return sorted({name[len(prefix):] for name in names if name.startswith(prefix)})
```

Names without the prefix are dropped, so a caller cannot be shown another environment's role even if such a row existed. And the result is deduplicated and sorted, so the order is stable regardless of insertion order.

<Warning>
This is a filter, not a permission check. If a user somehow belonged to a group in another environment, that group would be hidden from `roles_of` rather than reported as an error. The tenancy rule prevents the situation arising; this code makes the failure mode silent rather than leaky.
</Warning>

### Permissions follow the same rule

Permission names are prefixed identically, so a permission granted in staging does not satisfy a check for the same name in production. A policy checking `posts:write` sees only permissions belonging to the environment that issued the token.

## Defining a role

A role is a name, an optional description, and a list of permission names. The definition is **declarative**: the list you send becomes the role's permission set.

| Input | Meaning |
| --- | --- |
| `name` | Must match `^[a-z][a-z0-9_:-]{0,62}$` — a lowercase letter, then up to 62 characters of lowercase letters, digits, underscore, colon or hyphen. |
| `description` | Free text. Defaults to empty. |
| `permissions` | A list of names. An empty list is meaningful: it creates a role granting nothing. |

What the definition does, in order:

1. Finds or creates the group, named with the environment prefix.
2. Reads the group's current permissions.
3. Defines any permission in the new list that does not exist yet.
4. Adds the new ones and removes those no longer listed.
5. Updates the description if it changed.

The list is therefore the desired end state, not a set of additions. Omitting a permission removes it from the role.

<Warning>
That is the behaviour to watch when editing in Studio. Removing a name from the comma-separated field and saving takes that permission away from everyone in the role, for every session they refresh into. There is no confirmation step and no history.
</Warning>

### Permissions are created on demand

Naming `reports:export` in a role creates the `permissions` row if it is missing, so there is no separate "create the permission first" step.

The name is stored with the environment prefix, and no pattern is enforced on it — the pattern above applies to role names only. A permission can be any string, including one with uppercase letters or spaces, though naming conventions are worth keeping consistent yourself.

<Note>
Because permissions are created implicitly, a typo becomes a real permission that nobody holds. A policy checking `post:write` while the role grants `posts:write` fails, and nothing reports the near-miss. Read the permission badges on the role when you verify, rather than trusting your own spelling.
</Note>

## Assigning and revoking

| Operation | What it does |
| --- | --- |
| Assign a role | Adds a `UserGroup` row. Creates the group first if it does not exist. |
| Revoke a role | Removes the `UserGroup` row. Does nothing if the row is absent. |
| Grant permissions | Defines each named permission if needed, then attaches it to the person directly. |
| Revoke permissions | Removes the direct grant. Does nothing if absent. |

Two behaviours here catch people out, and both follow directly from the code.

**Assigning a role that does not exist creates it.** The assignment function looks the group up, and if it finds nothing it defines a new one with no permissions and then adds the person to it. So a typo in a role name silently produces an empty role rather than an error.

<Warning>
This is the single most common way to end up with a role that grants nothing. A user listed as `edior` is a member of an empty group called `edior`, and the real `editor` role is untouched. Check the Roles tab for the environment — an unexpectedly empty role is the evidence.
</Warning>

**Revoking is silent.** Neither revoke operation reports whether anything was removed. A typo in the name being revoked is a no-op, not a 404.

### Assigning a whole set

When an administrator saves a user's roles, the update route computes the difference: roles in the new set that the user lacks are assigned, and roles the user holds that are absent from the new set are revoked.

That means the field is the **desired full list**, not a set of additions. To add `payroll` to someone who should remain an employee, `employee` has to stay in the field.

### Granting directly

Direct grants exist for the exception case — one person needs one extra capability, and creating a role for it would be noise. The grant function defines each permission if it is missing and then attaches it to the person.

Direct grants and group permissions are indistinguishable at enforcement time. Both appear in the same `perms` claim, and a policy cannot tell which produced an entry.

## Effective access

A person's access is the union of two sources: their direct grants, and the permissions of every group they belong to.

```python
async def permissions_of(user: AuthUser) -> list[str]:
    direct = await Permission.of(user)
    via_groups: list[str] = []
    for group in await Group.of_user(user):
        via_groups.extend(await group.get_permissions())
    return _strip(user.project, user.env, [*direct, *via_groups])
```

| Property | What it means in practice |
| --- | --- |
| Union, not intersection. | A permission from any group suffices. |
| No inheritance between roles. | Being in `manager` does not imply `employee`. Assign both, or repeat the permissions. |
| No deny rules. | Nothing subtracts a permission. Removing it from every source is the only way. |
| Deduplicated and sorted. | A permission reached two ways appears once. |
| Environment-filtered. | Anything without the prefix is dropped. |

<Warning>
There is no deny mechanism anywhere in this model. If you need "everyone can read posts except contractors", you express it by not granting the permission and then handling the exception separately — not by granting it broadly and subtracting it.
</Warning>

### No inheritance

Roles are flat. A manager who should also be able to do what employees do needs both roles assigned, or the employee's permissions repeated in the manager role.

| Structure | Result |
| --- | --- |
| `manager` holds `reports:export`; person is in both `employee` and `manager`. | Works. |
| `manager` holds `reports:export`; person is in `manager` only. | Works for the export, but nothing employee-level. |
| `manager` holds `reports:export` and every employee permission. | Works, but the two roles must be kept in step by hand. |

The second row is the trap. It looks like it works until someone tests an employee-level action and finds it denied, because the role name implied a hierarchy that does not exist.

### Reading a user's access

The admin view of a user — what Studio and service keys get — includes both `roles` and `permissions`:

```json
{
  "id": "01JQ7Z3M9K4YB2XQ8V0N5T6RJPD",
  "email": "grace@example.com",
  "roles": ["employee", "manager"],
  "permissions": [
    "expenses:approve",
    "expenses:submit",
    "leave:review",
    "leave:submit",
    "reports:export"
  ]
}
```

The `permissions` array is the resolved union, with the environment prefix removed. It is the authoritative answer to "what can this person do", and it is worth using rather than recomputing it from roles in your own tooling.

The ordinary user-facing view includes `roles` but **not** `permissions`. A signed-in person asking who they are sees their roles and their own profile, not the resolved capability list.

## In the access token

Permissions reach downstream services as two claims, and both are read at issue time.

| Claim | Source |
| --- | --- |
| `roles` | The groups the person belongs to, prefixed and stripped. |
| `perms` | The resolved union, prefixed and stripped. |

Also on the token, and relevant to authorization decisions: `aal` for the assurance level, and `org` with `org_role` for the organization's membership role.

<Warning>
Because the claims are a snapshot, a permission change does not take effect until the person's token is refreshed. With the default 15-minute access lifetime, that is up to 15 minutes of the old access remaining valid. Revoking a person's access is therefore not instant — it requires either waiting, or revoking the sessions explicitly.
</Warning>

### The three-way refresh behaviour

Refreshing re-reads roles and permissions, so a grant lands on the next refresh. The `org` field on the refresh request has a three-way behaviour that is easy to get wrong, because it is expressed with a sentinel rather than a null:

| What you send | What happens |
| --- | --- |
| An organization slug | Switches the session to that organization. |
| `null` explicitly | Clears the organization. |
| The field omitted entirely | Keeps the current one. |

The module-level sentinel that expresses the third case is used because "not provided" and "explicitly null" are different in JSON but would otherwise be indistinguishable once parsed.

## Enforcing in policies

Policies read the verified claims. No policy ever queries the permission tables, and none can.

### The shorthand

A permission check is a shorthand that expands into a condition:

```json
{ "permission": "reports:export" }
```

which is equivalent to:

```json
{
  "all": [
    {
      "any": [
        { "contains": ["$auth.permissions", "reports:export"] },
        { "contains": ["$auth.permissions", "*"] }
      ]
    }
  ]
}
```

The `any` against the wildcard is worth pausing on. A permission check passes if the caller holds that permission **or** holds `*`, so the wildcard is checked by the permission shorthand itself. The `role` shorthand has no such branch — it is a plain membership test against `$auth.roles`, so a caller holding `*` does **not** satisfy a role check.

<Warning>
That asymmetry matters when you write a policy that mixes the two. `{ "permission": "reports:export" }` passes for a caller holding `*`; `{ "role": "manager" }` does not. If your superuser account holds only `*` and your policy gates on a role name, that account is denied.
</Warning>

<Note>
Inside Pawabase services, the same rule appears in the principal's own permission check, which returns true when the caller holds the named permission or `*`. That path additionally returns true for a service or operator whose roles include `admin` — a separate convenience that does not exist for project users. See [Auth in policies](/auth/auth-in-policies) for how the three caller kinds differ.
</Note>

### Other shorthands worth knowing

| Shorthand | Expands to a test on |
| --- | --- |
| `authenticated` | `$auth.authenticated` equals the given boolean. |
| `role` | `$auth.roles` contains any of the given names. |
| `permission` | `$auth.permissions` contains each named permission, or `*`. |
| `owner` | The record's owner column equals `$auth.user_id`. |
| `service` | `$credential.is_service` equals the given boolean. |
| `kind` | `$auth.kind` equals `user`, `operator` or `service`. |
| `scope` | `$credential.scopes` contains the named scope. |
| `aal` | `$auth.aal` equals `aal1` or `aal2`. |

Full detail in [Policy shorthands](/policies/shorthands) and [Policy conditions](/policies/conditions).

## Roles are not organization roles

Two different things in Pawabase are called a role, and confusing them produces bugs that are hard to see.

| | Application roles | Organization roles |
| --- | --- | --- |
| What they are | A group plus permissions. | A string on a membership row. |
| Where they live | `perm_groups` and `perm_group_permissions`. | `Membership.role`, table `akz_memberships`. |
| Which values | Anything matching the name pattern. | Exactly `owner`, `admin`, `member`, `viewer`. |
| What they control | Access to your data, through policies. | Nothing by themselves. They are a label your application reads. |
| Where they appear | The `roles` claim. | The `org_role` claim. |

Organization roles are **not enforced by the platform**. The four values are validated on the way in, but nothing checks them in a policy. If your application wants only owners to delete an organization, you write that condition yourself against `$auth.org_role`.

<Warning>
There is a fourth thing also called a role: Studio operators, who are people who administer Pawabase itself rather than users of your project. They are an entirely separate concept, live in the reserved `_platform` environment, and have nothing to do with either table above.
</Warning>

### The org claims

`org` and `org_role` are read at issue time and describe the organization the session is scoped to.

| Claim | Value |
| --- | --- |
| `org` | The slug, or `null`. |
| `org_role` | The person's role in that organization, or `null`. |

There are two cases where both come back null even when an organization was named. If the user is not a member, the role is null — and the organization is nulled too, rather than reported as an error. The exception is when the organization was named on the request, where membership is required and a non-member is refused with a 403 before any token is minted.

<Note>
Because the role is read at issue time, promoting someone from `member` to `admin` does not change their existing tokens. It lands on the next refresh, like any other permission change.
</Note>

## Studio's Roles tab

Roles are managed under **Users & auth → Roles**. The card is titled **Roles** and its empty state reads *"No roles yet."*

| Element | Label |
| --- | --- |
| Create button | **New role** |
| Table columns | **Role**, **Description**, **Permissions**, **Members** |
| Modal title when creating | **New role** |
| Modal title when editing | The role's name |
| Modal fields | **Name**, **Description**, **Permissions** |
| Modal actions | **Delete**, **Save** |
| Toast on save | **Saved** |
| Toast on delete | **Deleted** |

The **Name** field's placeholder is `editor`. It is disabled when editing an existing role, because a rename would mean creating a different group and moving every membership across.

The **Permissions** field is a comma-separated text input whose hint reads *"Comma-separated, e.g. posts:write, posts:publish. `*` grants everything."* The hint is accurate: `*` satisfies every permission check, and the wildcard is what makes a single broad role possible.

### The Members column

It shows a count, from the group's member count. Note what it does **not** count: direct permission grants. A person holding `reports:export` directly appears in no role's member count, because they belong to no group.

<Note>
A member count of zero on a role that people clearly have does not mean the role is broken. It means the access is arriving by direct grant, which is invisible in this table. Check the user view's **Direct permissions** list to confirm.
</Note>

### Creating a role

<Steps>
  <Step title="Open the Roles tab">
    Go to **Users & auth → Roles** for the environment you intend to change. Roles are per environment, and the tab shows only the selected one.
  </Step>
  <Step title="Click New role">
    The modal opens with an empty name, no description and no permissions. It is titled **New role**, which is how you tell it apart from editing.
  </Step>
  <Step title="Fill in the name">
    Lowercase first letter, then lowercase letters, digits, underscore, colon or hyphen. The placeholder shows `editor`. A name with a capital or a space is rejected.
  </Step>
  <Step title="Add a description">
    Free text. It is shown in the table and is never evaluated, so it is worth writing for the next person who opens this screen.
  </Step>
  <Step title="List the permissions">
    Comma-separated, names you choose — `expenses:approve, reports:export` works. Typing a name that does not exist yet creates it.
  </Step>
  <Step title="Save">
    The list you typed becomes the role's complete permission set. Omitted permissions are removed from the role and from everyone in it.
  </Step>
</Steps>

### Assigning roles to a person

Roles are assigned from the **Users** tab, not the Roles tab. Open the person, and the **Roles** field carries the hint *"Comma-separated role names from the Roles tab."*

| Fact | Consequence |
| --- | --- |
| The field is the full desired list. | Keep existing role names in it when adding one. |
| Saving computes the difference. | Roles you left out are revoked. |
| A name that does not exist is created, empty. | A typo produces a silent no-op role rather than an error. |
| `null` leaves the field out of the update. | Roles are untouched when you save some other field. |

Below the roles field, the user modal has a **Direct permissions** list. Each entry is a badge with a small cross that revokes it, and beside it a text input with the placeholder `posts:write` and a **Grant** button. Revoking and granting here touch `user_permissions` only; they do not change any role.

## The admin routes

Studio and service keys reach the same operations over HTTP. Every one takes the project and environment in its path and requires a service token, because these are administrative operations on an environment's identities.

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `{base}/roles` | List the environment's roles, plus every permission defined in it. |
| PUT | `{base}/roles` | Create or replace a role. |
| DELETE | `{base}/roles/{name}` | Delete a role and its memberships. |
| POST | `{base}/users/{id}/permissions` | Grant direct permissions. |
| DELETE | `{base}/users/{id}/permissions` | Revoke direct permissions. |

`{base}` is `/projects/{project}/envs/{env}`.

The listing route returns both the roles and the environment's full permission set, which is what lets Studio's modal offer a complete picture rather than only the names currently in use.

### Creating or replacing

```bash
curl -X PUT "https://api.example.com/auth/v1/projects/acme/envs/production/roles" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" \
  -d '{
    "name": "payroll",
    "description": "Payroll staff",
    "permissions": ["expenses:approve", "reports:export"]
  }'
```

The name is validated against the pattern. A name that fails is a `422` from the request model, which is one of the few places where a bad role name produces a clear error rather than silent behaviour.

### Deleting

Deleting a role removes its memberships and then the group itself. The permission rows it held are **not** deleted, so they remain defined and available for other roles or for direct grants.

<Warning>
Deleting a role does not rewrite policies that reference its name. A policy checking `role: "payroll"` will deny everyone once the role is gone, and it will do so silently. Find the policies before deleting.
</Warning>

### Granting and revoking directly

```bash
curl -X POST "https://api.example.com/auth/v1/projects/acme/envs/production/users/01JQ7Z3M9K4YB2XQ8V0N5T6RJPD/permissions" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" \
  -d '{"permissions": ["reports:export"]}'
```

Both take the same body shape, a list of permission names. Granting defines any that do not exist yet. Revoking removes the direct grants only and leaves group permissions untouched — so revoking a permission someone also gets from a role changes nothing, which is the behaviour to expect.

## Roles in backups

An environment's backup includes its roles, their descriptions and their permissions, each user's role assignments, and each user's direct permissions. So the whole authorization model travels with the identities.

| In the backup | Restored as |
| --- | --- |
| Each role's name and description | A role defined with those values. |
| Each role's permission list | Permissions attached to that role. |
| Each user's roles | Group memberships, added if missing. |
| Each user's direct permissions | Direct grants. |
| Password hashes | Preserved, so people keep their passwords. |

Restoring with `replace` first removes every role in the environment, then rebuilds from the document — which makes a restore the moment when role definitions actually change rather than merely being re-applied.

<Note>
Because permissions are created on demand, a restore never fails on a missing permission; it creates it. That makes restores forgiving, and also means a backup taken with a typo in a permission name restores the typo rather than correcting it.
</Note>

## Default roles

`default_roles` is the one authorization setting in the environment's `auth` block. It lists the roles granted to every account at creation.

```json
{ "auth": { "default_roles": ["customer"] } }
```

| Property | Consequence |
| --- | --- |
| Applied at account creation. | Not at verification, and not at first sign-in. |
| Not retroactive. | Existing accounts are unaffected when you change the list. |
| Applies to every creation path. | Sign-up, magic-link creation, and accounts created in Studio. |
| Names are environment-prefixed like all others. | The same list means different roles in different environments. |

<Warning>
If a name in `default_roles` does not exist, it is created empty and the person is added to it. So a typo in this setting gives every new account a role that grants nothing, silently, and the Roles tab will show a role with a plausible name and an empty permission list.
</Warning>

## Designing a permission set

Because a permission is just a name you choose, the useful work is choosing well rather than configuring.

| Convention | Why |
| --- | --- |
| `resource:action`, such as `expenses:approve`. | Groups related capabilities so a wildcard or a prefix rule has something to work with. |
| Lowercase, colon-separated. | Matches the character set role names allow, so nothing looks out of place. |
| Same string in the role and the policy. | The only thing that makes a check pass. There is no normalisation. |
| Verb at the end, not the start. | `expenses:approve` groups better than `approve:expenses` when scanning a list. |

A worked example, for an expense product:

| Role | Permissions | Who gets it |
| --- | --- | --- |
| `employee` | `expenses:submit` | Everyone. |
| `manager` | `expenses:approve` | Approvers. Note: no employee permissions implied. |
| `payroll` | `reports:export`, `expenses:export` | Payroll staff. |
| `auditor` | `reports:read` | Read-only reviewers. |

The flatness of that table is the point. `manager` does not include `employee`, so a manager needs both roles to do everything a manager should be able to do. That is a deliberate choice to make, and making it deliberately beats discovering it.

<Warning>
Keep `*` out of `default_roles`. A wildcard in the default role grants every new account every permission, and the only way back is to find each account and remove it individually.
</Warning>

## What goes wrong

### The user has the role and the action is denied

Check in this order:

| Check | How |
| --- | --- |
| Is the permission spelled the same in the role and the policy? | Compare the role's badges with the condition's argument, character by character. |
| Did the role actually contain it? | Open the role. An empty role usually means a typo created a second role. |
| Is the policy testing a role name rather than a permission? | A role name is not a permission. They are separate claims. |
| Has their session refreshed since the change? | Claims are a snapshot. Wait for the access token to expire, or revoke the session. |
| Are there additional conditions? | Ownership, organization and `aal` conditions all still apply. |
| Is this the right environment? | Permissions are environment-scoped in both directions. |

### The user still has access after a role was removed

| Possible reason | How to confirm |
| --- | --- |
| Another role grants it. | Look at the resolved `permissions` array, not the roles. |
| A direct grant remains. | The **Direct permissions** list on the user. |
| Their token predates the change. | Claims are read at issue time. |
| They hold `*` somewhere. | The wildcard satisfies every permission check. |

### The role exists in staging but not in production

Roles are per environment, and the name-prefixing makes them genuinely separate rows. Promotion of your *data* does not promote roles or users — those live in Akountz, and the identities backup is what carries them. Provision the roles in production explicitly, or restore the identities.

### A role appeared that nobody created

Almost always a typo in a user's roles field or in `default_roles`. Assigning a role that does not exist creates it. Look for a role whose permission list is empty, because that is the signature.

### Hiding a button did not prevent the request

Client-side visibility is not enforcement. A permission in the token tells your frontend what to show; only a policy on the route or operation stops the request itself. See [Enforcement points](/policies/enforcement-points).

### User metadata is not a grant

A person can edit their own `user_metadata`, and that data is carried in the token's `meta` claim. A profile field called `is_admin` or `role` is therefore attacker-controlled and must never gate anything. Only `app_metadata`, which only an administrator or a service key can write, is safe to rely on.

## A worked example

Building an approval flow end to end, from empty environment to enforced policy.

### The goal

In an expenses product, an employee may submit, a manager may approve, and payroll may export. Only members of the owning organization may act on that organization's expenses.

### Defining the roles

In **Users & auth → Roles** for `acme/production`:

| Role | Permissions field | Description |
| --- | --- | --- |
| `employee` | `expenses:submit` | Everyone who has an account |
| `manager` | `expenses:approve` | Approvers |
| `payroll` | `reports:export`, `expenses:export` | Payroll staff |

Save each. The permissions do not exist yet; typing them creates the rows.

Note what is *not* in `manager`: `expenses:submit`. A manager who should also file their own expenses needs both roles, and that is the honest cost of a flat model.

### Assigning

Open the manager in **Users**, and set **Roles** to `employee, manager`. Both names, because the field is the full desired list. The resulting claims on their next token are:

```json
{
  "roles": ["employee", "manager"],
  "perms": ["expenses:approve", "expenses:submit"]
}
```

Give payroll the same treatment with `employee, payroll`.

### The policies

Attach these to the operations themselves, not to custom routes around them.

Approve:

```json
{ "permission": "expenses:approve" }
```

Export:

```json
{ "permission": "reports:export" }
```

Read, restricted to the record's own organization:

```json
{
  "all": [
    { "permission": "reports:read" },
    { "eq": ["$record.org", "$auth.org"] }
  ]
}
```

The second policy is the one that shows why permissions and organization roles are different things: the permission grants the capability, and the organization condition confines it. Neither does the other's job.

### Testing it

| Test | Expected |
| --- | --- |
| Sign in as an employee, approve an expense. | Denied. `expenses:approve` is absent from their token. |
| Sign in as a manager, approve an expense in their own organization. | Allowed. |
| Sign in as a manager, approve an expense in another organization. | Denied by the `org` condition, not by the permission. |
| Sign in as payroll, export. | Allowed. |
| Remove `manager` from the manager, refresh their session, retry. | Denied. |
| Give an employee `reports:export` directly, refresh, retry. | Allowed — and note no role's member count changed. |

Use publishable keys and real user sessions for all of these. A service key bypasses the conditions you are trying to verify.

### Rolling it out safely

Turn on the policy **after** the roles are assigned. The reverse order denies everyone for as long as it takes to notice, and because the denial is a policy result rather than an error, it may not surface in any log you are watching.

## Inspecting the state

Four tables, and the queries are simple because the prefixing means each environment's rows are contiguous.

### The roles of one environment

```sql
SELECT name, description
FROM perm_groups
WHERE name LIKE 'acme/production/%'
ORDER BY name;
```

Strip the prefix when reading the results, and that is exactly what the API does.

### What a role holds

```sql
SELECT g.name AS role, gp.permission
FROM perm_group_permissions AS gp
JOIN perm_groups AS g ON g.id = gp.group_id
WHERE g.name = 'acme/production/editor'
ORDER BY gp.permission;
```

An empty result for a role people are assigned is the signature of a role that was created by a typo and never given any permissions.

### Who holds what

```sql
SELECT u.email, g.name AS role
FROM perm_user_groups AS ug
JOIN perm_groups AS g ON g.id = ug.group_id
JOIN akz_users AS u ON u.id = ug.user_id
WHERE g.name LIKE 'acme/production/%'
ORDER BY u.email, g.name;
```

Direct grants are invisible here by design. Join `user_permissions` as well when auditing, because access can arrive by either route.

<Warning>
Every query needs the environment prefix. Without it you are reading every project's roles on the installation, and a `LIKE 'editor'` without the prefix matches nothing while a prefix-less join returns everything.
</Warning>

## The subclassing hazard

There is one detail in `framework.py` that is worth knowing before you extend anything here.

Sillo's own `Group.get_or_create` implementation calls `super(cls, cls)`. On a subclass, that expression resolves back to the override in the subclass rather than to Sillo's original — so calling it would recurse. Akountz's subclass works around this by holding a reference to Sillo's class and calling through that explicitly:

```python
group, _ = await super(_SilloGroup, cls).get_or_create(
    name=name, defaults={"description": description}
)
```

The practical consequence is narrow but real: **if you subclass `Group` yourself and call `get_or_create`, you will hit infinite recursion.** Call `define_role` from `app/rbac.py` instead, which is the path everything else in the system uses.

<Note>
The same module re-points Sillo's own classes at these ULID-keyed subclasses through an `adopt()` call at import time. That is what makes `Permission.assign` and `JWTToken.revoke_family` operate on these tables rather than on Sillo's originals, which are never registered with the database.
</Note>

## Security properties

### The wildcard

`*` satisfies every permission check, and the permission shorthand expands to accept it explicitly. There is no wildcard support in the role shorthand, so a caller holding only `*` is not in any role.

| Check | A caller holding `*` |
| --- | --- |
| `{ "permission": "anything" }` | passes |
| `{ "role": "manager" }` | fails |
| A hand-written `contains` on `$auth.permissions` | fails, unless it also tests for `*` |

The last row is the one that bites. A policy you write by hand against `$auth.permissions` does not get the wildcard for free; only the shorthand adds it.

<Warning>
Grant `*` to as few accounts as you can, and prefer granting specific capabilities instead. A wildcard means any future permission is also granted, including ones you have not written yet — so a permission added next quarter is silently live for that account from the moment it exists.
</Warning>

### Service keys and operators are not users

Two other kinds of caller reach your services, and neither is governed by the role tables described on this page.

| Caller kind | Where its access comes from |
| --- | --- |
| `user` | A project environment's account. Governed by groups and permissions. |
| `operator` | A Studio administrator. Governed by Akountz's own configuration. |
| `service` | Another Pawabase service or a secret key. Governed by scopes. |

A service credential bypasses user authorization entirely, and a policy that does not exclude services may be satisfied by one. Write the exclusion deliberately: the `service` shorthand exists for exactly this.

### Claims are trusted, metadata is not

The claims on a verified token are trustworthy because the signature was checked with the environment's key. Two of them are not user-writable, and one is:

| Claim | Who can change it | Safe to gate on |
| --- | --- | --- |
| `roles`, `perms` | An administrator, through the role tables. | Yes. |
| `app_metadata`, as `app` | An administrator or a service key. | Yes. |
| `user_metadata`, as `meta` | The person themselves. | No. |

<Warning>
The `meta` claim is in the token the person holds. Anything a policy reads from it can be changed by editing a profile field, which the person controls. Never gate on a value from `meta`, whatever its name suggests.
</Warning>

## Models and tables

| Model | Table | Unique on |
| --- | --- | --- |
| `Permission` | `permissions` | the name |
| `Group` | `perm_groups` | the name |
| `UserPermission` | `user_permissions` | — |
| `UserGroup` | `perm_user_groups` | `(user_id, group)` |
| `GroupPermission` | `perm_group_permissions` | `(group, permission)` |

All five use a ULID primary key rather than an auto-increment integer. The same module also re-keys `JWTToken` to `jwt_tokens` and `TokenBlacklist` to `token_blacklist`.

### No deny rules

Nothing in the model subtracts a permission. If you need an exception, you have three honest options:

| Approach | Trade-off |
| --- | --- |
| Do not grant the broad permission; grant a narrower one. | Best, but requires designing the permission set well. |
| Use a policy condition alongside the permission. | Fine — the permission grants the capability, the condition constrains it. |
| Add a condition that excludes the exception. | Works, and grows unwieldy as exceptions accumulate. |

Do not rely on an ordering of roles to subtract anything, because there is no ordering and no subtraction.

### Revocation is not instant

Because `roles` and `perms` are snapshotted at issue, removing a permission does not affect an access token that is already in flight. With the default 15-minute access lifetime, that is the worst-case window.

For an urgent revocation, revoke the sessions rather than only editing the role:

| Scope | How |
| --- | --- |
| One session | `DELETE /auth/v1/sessions/{session_id}` |
| Every session, by the person | `POST /auth/v1/logout` with `scope` set to `global` |
| Every session, by an operator | **Signed out everywhere** in the user view |

<Note>
Revoking a session invalidates the refresh token as well, so the access token's remaining minutes are the only window left. After that the person cannot mint a new one.
</Note>

## Choosing a model for your product

The model is the same everywhere, so the choice is not about the system. It is about how much ceremony your team wants.

### Just direct grants

Grant each person what they need, one permission at a time. Simple to operate, and the only option that needs no role design at all.

It works well for small teams and internal tools. It degrades badly at any scale, because there is no way to ask who holds a permission, and every new person is an exercise in archaeology.

### Roles with a small permission set

A handful of permissions, grouped into a handful of roles, assigned per cohort. This is the model the system is built around and the one Studio is designed for.

The cost is designing the permission set well. Names that are too coarse (`write`) force policies to add conditions; names that are too fine (`expenses:approve`) multiply the work of onboarding.

| Too coarse | Just right | Too fine |
| --- | --- | --- |
| `write` | `expenses:approve` | `expenses:approve_pending` |
| — | `reports:export` | `reports:export_csv` |
| — | `posts:publish` | `posts:publish_draft` |

The middle column is the useful one, because each name is a thing the product actually does and a policy can test it alone.

### Roles plus a wildcard for support staff

The usual shape in practice: explicit permissions for everyone, and a single role holding `*` for the two or three people who need to fix anything.

<Warning>
A wildcard role is convenient right up until a permission is added that nobody wanted the support team to have. Everything added after that is granted to them automatically. Reserve it, document who holds it, and review it when the team changes.
</Warning>

### Organizing by organization instead

If your product's real boundary is the organization rather than the job function, lean on the organization model and keep roles few: one role, or none at all, with the organization condition doing the work.

That is a legitimate design. It simply means your policies carry conditions rather than permissions, and a person who belongs to two organizations gets the union of what each allows.

| If your boundary is | Lean on | Why |
| --- | --- | --- |
| Job function. | Permissions and roles. | The capability is the same wherever the person works. |
| Organization membership. | The organization condition. | Access follows the membership, not the job. |
| Both. | Both, together. | Permission for the capability, condition for the scope. |

The last row is where most real products end up, and it is why the two systems are separate rather than merged.

## Operating roles day to day

The recurring work, and the small number of habits that keep it clean.

### Habits worth keeping

| Habit | Why |
| --- | --- |
| Define a role before assigning it. | Assigning an undefined name creates an empty role rather than an error. |
| Read a role's permission badges after saving. | A typo creates a real permission that nobody holds. |
| Check the Members column after a role change. | A role whose count drops to zero is being removed from everyone at once. |
| Revoke sessions after an urgent removal. | Claims are a snapshot; editing a role alone is not enough. |
| Keep `*` to one role, with a documented holder. | A wildcard grants permissions that do not exist yet. |

The first is the one people skip, and it is the one that produces the confusing artefacts. Defining the role is a separate, deliberate act; assigning it is not.

### Auditing access

There is no built-in "who has permission X" query, so an audit is a join or a loop. The useful shape is: for each environment, list the roles with their permissions and counts, then list the users with their roles and direct grants.

That gives you two questions answered at once: who holds a capability, and what a given person can do. Anything needing both answers — "who can export reports, and who else can do what they can" — needs the second list cross-referenced.

<Warning>
Include the wildcard when auditing. A role whose permission list contains `*` matches every capability, so a per-permission report that only counts exact names will miss it entirely.
</Warning>

### Offboarding

The order matters, because the last step invalidates everything before it.

| Order | Action | Why here |
| --- | --- | --- |
| 1 | Revoke the person's sessions. | Stops the access immediately, whatever happens next. |
| 2 | Remove their roles and direct grants. | Cleans up the records. |
| 3 | Disable the account. | Stops any future sign-in. |
| 4 | Delete the account, if that is the policy. | Releases the address and removes the row from queries. |

Step 1 before step 2 because the access is in the token, not in the tables. Editing the grants first leaves up to fifteen minutes of access that the tables no longer justify.

<Note>
Deleting is a soft delete: the row is stamped, the address and username are rewritten to reserved values derived from the user's id, and identities and MFA factors are removed. The address is released for re-use; the history stays attributable.
</Note>

### The service-key question

Some recurring tasks sound like they need a service key and do not. Most of the identity surface is reachable with a publishable key and a real session, and using a service key changes what you are testing.

| Task | Needs a service key? |
| --- | --- |
| Creating a role. | Yes. The admin routes require one. |
| Assigning a role to a person. | Yes, through the admin route. |
| Reading your own resolved permissions. | No. |
| Testing whether a policy allows an action. | No, and using one will mislead you. |

<Warning>
A service credential satisfies conditions a user would not, so a green test against a policy using one proves nothing about the people you actually built it for.
</Warning>

## Migrating an authorization model

Moving from something else to this model, and moving between environments, both have sharp edges that are worth planning for.

### Coming from a flat permission list

If you arrived with a single list of permissions on a user, the direct-grant path already exists and needs no migration: each entry becomes a `UserPermission` row, and every service can enforce it the moment the API reports it.

What direct grants do not give you is a way to answer "who has this?". There is no reverse lookup from a permission to the people holding it, so an audit means iterating users rather than iterating permissions.

| Need | Direct grants | Roles |
| --- | --- | --- |
| One person, one extra capability. | Yes, quickly. | Overkill. |
| "Who can export reports?" | No. | Yes, via the role's member count. |
| "What can this person do?" | Yes. | Yes. |
| Onboarding a cohort. | No. | Yes, via `default_roles`. |
| Surviving a permission rename. | No. | No — both use the same strings. |

### Moving roles between environments

Roles are not part of a data promotion. Whatever you do, the sequence is: export the identities of the source environment, and restore them into the target.

| Property | Consequence |
| --- | --- |
| Role definitions travel in the backup. | Restoring creates them in the target. |
| Users travel in the backup, with their memberships. | Memberships are recreated in the target. |
| Direct permissions travel too. | Nothing is silently lost. |
| The target keeps its own rows. | A restore with `replace` deletes the target's roles first. |

<Warning>
A restore with `replace` removes **every** role in the target environment before rebuilding. If the target has roles that the source document does not mention, they are gone, along with their memberships. Take a backup of the target before restoring into it.
</Warning>

### Renaming a permission

There is no rename operation. A permission is a name, and the name is the key. To rename one you must create the new name, attach it where the old one was used, update every policy that references the old string, then clean up the old grant.

The order that avoids a gap:

1. Add the new permission name to every role that had the old one. Now both exist.
2. Update the policies to check the new name.
3. Confirm it works for anyone holding the role.
4. Remove the old name from the roles.
5. Revoke the old direct grants.

<Warning>
Step 2 is the one that strands people. A policy updated to a name nobody holds denies everyone from the moment it is saved, and the denial is a policy result rather than an error. Add the new name first, always.
</Warning>

## How the pieces fit together

A single request's path through the authorization system, end to end.

```text
1. The client sends a bearer token.
2. The gateway verifies it with the environment's key.
3. It reads prj and env, and refuses the token if either differs.
4. The verified claims become a principal on the request.
5. The policy engine reads roles and permissions from those claims.
6. The condition is evaluated and the request proceeds or is denied.
```

Step 3 is the tenancy rule doing its job. Step 5 is the only place permissions are read, and it reads a snapshot rather than the database. Steps 5 and 6 together are why authorization is cheap and why changes are not immediate.

<Note>
No service in this path queries `perm_*`. That is deliberate: enforcement must not depend on the identity service being available, or an outage there would become an outage everywhere.
</Note>

### Where roles are read, and where they are not

| Component | Reads roles? |
| --- | --- |
| The gateway, verifying a token. | No. It checks the signature and the environment only. |
| The policy engine. | Yes, from the claims. |
| Akountz, when issuing a token. | Yes, from the tables. |
| Akountz, when starting a session. | Yes, to record the session row. |
| Studio's user view. | Yes, from the tables, for display. |
| Studio's Roles tab. | Yes, from the tables, for editing. |

Two readers of the tables — one for display, one for enforcement input — and they can disagree for as long as a token lives. That is the whole of the staleness question.

## Common role sets

Three worked shapes, drawn from products people actually build, with the trade-off named for each.

### Support and operations

```json
{
  "name": "support",
  "description": "Can read anything and act on accounts; cannot delete data",
  "permissions": [
    "accounts:read",
    "accounts:disable",
    "reports:read"
  ]
}
```

The point of not granting `*` here is that the next permission your product adds — a delete, a payout, a bulk export — is not automatically live for the support team on the day you write it.

<Warning>
The temptation to give support `*` because it is faster is the most common long-term mistake in this area. It feels safe because nobody has been hurt yet, and it is exactly the arrangement that turns a small new permission into an incident.
</Warning>

### Two tiers and an override

```json
{ "name": "viewer",  "permissions": ["records:read"] }
{ "name": "editor",  "permissions": ["records:read", "records:write"] }
{ "name": "admin",   "permissions": ["records:read", "records:write", "records:delete"] }
```

Note that `editor` repeats `records:read` rather than inheriting it, because there is no inheritance. That repetition is the price of a flat model, and it is small until you have twenty permissions and five tiers — at which point you should reduce the number of tiers rather than automate the copying.

### Least privilege by cohort

```json
{ "name": "customer",   "permissions": ["orders:read:own", "orders:create"] }
{ "name": "staff",      "permissions": ["orders:read", "orders:update"] }
{ "name": "auditor",    "permissions": ["orders:read"] }
```

Encoding the scope in the permission name — `orders:read:own` rather than `orders:read` plus a condition — pushes the rule into the permission itself. It is more names to manage, but each policy stays a single test and there is nothing to forget to add.

| Approach | Cost |
| --- | --- |
| Scope in the permission name. | More names; each policy is one term. |
| Scope in a policy condition. | Fewer names; every policy must remember the condition. |

<Note>
If you choose the second, write the condition into a reusable form rather than retyping it. A policy that checks the permission but forgets the ownership test is the classic half-implemented authorization bug.
</Note>

### An override that is really a direct grant

One contractor needs `reports:export` for a month. Creating a role for it leaves a role with one member that nobody remembers to remove later.

### An override that is really a direct grant

| | A role for one person | A direct grant |
| --- | --- | --- |
| Visible on the user. | As a role badge. | In its own list, labelled. |
| Easy to find later. | No — check every role's members. | Yes — one list on one user. |
| Reversible. | Remove them from the role. | Click the cross. |
| Scales past one person. | Yes. | You end up with a role anyway. |

## Frequently asked questions, second pass

<AccordionGroup>
  <Accordion title="Does a role need to exist before a user can be assigned to it?">
    No, and that is a trap. Assigning an undefined name creates the role with no permissions and adds the person to it, so the assignment "succeeds" and grants nothing.
  </Accordion>
  <Accordion title="Can two roles hold the same permission?">
    Yes. There is a uniqueness constraint on the pair within a group, not on the permission across groups. Two roles may both hold `reports:read`, and a person in both still sees it once in their resolved list.
  </Accordion>
  <Accordion title="Can a person belong to a role twice?">
    No. Membership is unique on the person and group, so a second assignment is a no-op rather than a duplicate row.
  </Accordion>
  <Accordion title="What does the admin roles listing return besides roles?">
    It returns the environment's full set of defined permissions as well, which is what lets the editing form show you every permission in this environment rather than only the ones currently in use.
  </Accordion>
  <Accordion title="Are permissions ever deleted?">
    Not by editing a role or by deleting one. Deleting a role removes its memberships and the group; the permission rows survive so they can be reused. Pruning unused permission rows is a database-level decision, not an API one.
  </Accordion>
  <Accordion title="Is a role name case-sensitive?">
    It is stored as given and compared exactly, so `Editor` and `editor` would be different groups — except that the name pattern requires a lowercase first letter, so `Editor` is rejected at the route.
  </Accordion>
  <Accordion title="Can I set a role's name from a script after creating it?">
    Not by updating the field: the name is the key of a create-or-replace operation and the field is disabled in Studio. Create the new one, move the members, delete the old one.
  </Accordion>
  <Accordion title="Why does the resolved permissions list look sorted?">
    Because the resolver deduplicates and sorts as its last step. Do not rely on the order for anything; it is stable, not meaningful.
  </Accordion>
  <Accordion title="Does a user's roles list appear in the access token?">
    Yes, as `roles`, with the environment prefix removed. The user-facing profile endpoint returns it too, so a client can render a role-based interface without decoding the token.
  </Accordion>
  <Accordion title="Does the user-facing profile include permissions?">
    No. The profile returns `roles`; the resolved `permissions` array is part of the admin view, used by Studio and by service keys.
  </Accordion>
  <Accordion title="Are the permissions themselves deleted with a role?">
    No. The permission rows survive, so they remain available to other roles and to direct grants. Only the group and its memberships go.
  </Accordion>
  <Accordion title="Can I rename a role?">
    Not by editing the name field — it is disabled for an existing role, and the admin route takes the name as the key of a create-or-replace operation. To rename, create the new role, assign it to the same people, then delete the old one.
  </Accordion>
  <Accordion title="Do I need to define a permission before using it in a policy?">
    No. A policy can name a permission that does not exist; it simply never matches. Definition happens implicitly when a role or a grant mentions it.
  </Accordion>
  <Accordion title="Why does the user view show permissions I never granted?">
    Because it shows the resolved union across every group the person belongs to. Look at the roles to explain it, and at **Direct permissions** to find anything that did not come from a role.
  </Accordion>
  <Accordion title="Can a role name be the same in two environments?">
    Yes, and that is the point of the prefix. They are separate groups with separate memberships and separate permissions, and neither can be seen from the other.
  </Accordion>
  <Accordion title="Is there a way to make a change take effect immediately?">
    Not for an access token that already exists. Revoke the person's sessions, which ends the refresh path; the current access token then has only its remaining lifetime. Otherwise the change lands on the next refresh.
  </Accordion>
</AccordionGroup>

## Permissions in every policy

The permission claims as policies see them, and what each one is for.

| Path | Type | Source |
| --- | --- | --- |
| `$auth.permissions` | A list of strings. | The resolved union at issue time. |
| `$auth.roles` | A list of strings. | Group memberships at issue time. |
| `$auth.authenticated` | A boolean. | Whether a caller was verified at all. |
| `$auth.kind` | A string. | `user`, `operator`, `service`, or `anonymous`. |
| `$auth.aal` | A string. | `aal1`, or `aal2` after a second factor. |
| `$auth.org` | A string or null. | The session's organization slug. |
| `$auth.org_role` | A string or null. | The caller's role in that organization. |
| `$auth.user_id` | A string. | The caller's id. |
| `$auth.email` | A string or null. | The address the token was issued for. |
| `$auth.claims` | The raw claims. | Everything above, plus anything else. |

For an anonymous caller the same paths exist and every one of them is null or empty, which is why a policy written only with permission checks denies anonymous callers without needing an explicit test.

### Choosing between a role check and a permission check

| | `{ "role": "manager" }` | `{ "permission": "reports:export" }` |
| --- | --- | --- |
| Answers | Is this person a manager? | Can this person export reports? |
| Survives a role rename. | No. | Yes, if the permission name is unchanged. |
| Satisfied by `*`. | No. | Yes. |
| Can be granted ad hoc. | Only by creating the role. | Yes, directly. |
| Reads better in the policy. | Sometimes. | Usually. |

The third row is the one that decides it most often. Gating on a role name means a wildcard does not help, so your support account needs that role created and assigned before it can do anything.

<Tip>
Prefer permission checks in policies and use roles as the delivery mechanism. The policy then states what the action requires, and how people come to hold it stays an administrative question.
</Tip>

### Combining with other conditions

A permission check is rarely the whole answer. The usual shapes:

```json
{ "all": [ { "permission": "records:write" }, { "owner": true } ] }
```

```json
{ "any": [ { "permission": "records:delete" }, { "owner": true } ] }
```

The first says only the owner may write. The second says anyone with the permission may, and otherwise the owner may. Both are common, and they are not interchangeable — the second is the one people mean by "editors and owners", and writing the first by mistake locks the editors out.

<Warning>
When a permission is a capability and a condition is a scope, write both. A permission alone grants the action everywhere; a condition alone relies on whatever grants access to anyone at all, which includes every other role and the wildcard.
</Warning>

### Supporting a request

A worked policy, because the pieces are clearer once they are assembled.

Suppose an expense can be approved by anyone holding `expenses:approve`, but only for expenses in the organization their session is scoped to, and only if they are actually signed in with a second factor.

```json
{
  "all": [
    { "authenticated": true },
    { "service": false },
    { "permission": "expenses:approve" },
    { "eq": ["$record.org", "$auth.org"] },
    { "aal": "aal2" }
  ]
}
```

Reading it line by line:

| Term | Why it is there |
| --- | --- |
| `authenticated` | Rejects anonymous callers before anything else is evaluated. |
| `service: false` | Stops a service credential from satisfying the rest, if one should never approve. |
| `permission` | The capability itself. Satisfied by the role or by a direct grant, and by `*`. |
| `eq` on `$record.org` | The scope. Uses the session's organization, which is set at sign-in or at refresh. |
| `aal: aal2` | Requires the second factor, because this action moves money. |

Every term maps to one of the four things a real authorization decision needs: who is calling, what they may do, where they may do it, and how strongly they proved themselves.

<Warning>
The `$auth.org` term is null for any session that was never scoped to an organization. With the `eq` above, a null org will not equal a record's org, so an unscoped session is denied. That is the right default, and it is worth being deliberate about: if your sign-in flow does not always set an organization, some legitimate users will fail here.
</Warning>

### The same decision without a policy

Akountz does not enforce application permissions. It resolves them, stamps them into a token, and stops. Everything above is your policy's job.

| Layer | What it decides |
| --- | --- |
| Akountz | Who the caller is, what they hold, and whether their token is valid for this environment. |
| The gateway | Whether the token verifies at all. |
| Your policy | Whether this particular action is allowed. |

<Note>
This division is why an authorization bug is a policy bug. If Akountz resolved the permissions correctly and stamped them correctly, and the policy still denied the action, the defect is in the policy — which means it is also in a file you can read and test.
</Note>

### Testing a policy directly

A policy that denies everyone in production and everyone in staging looks identical from the outside, which is why testing it against a real user session matters more than reading it.

| Test | What it catches |
| --- | --- |
| A user holding the permission. | A misspelled permission name. |
| A user without it. | A condition that passes too easily. |
| The same user, unscoped organization. | An `eq` on `$auth.org` behaving as null. |
| The same user, `aal1` instead of `aal2`. | An assurance check that is not being evaluated. |
| A service credential. | A missing `service: false`. |

## Assorted questions

<AccordionGroup>
  <Accordion title="Can I use a permission name with spaces or capitals?">
    Yes. No pattern is enforced on permission names, only on role names. It would work, and it would be a bad idea — the name has to be typed identically in every role and every policy, so anything requiring care raises the chance of a mismatch.
  </Accordion>
  <Accordion title="Is there a length limit on a permission name?">
    None beyond the column's. In practice, keep them short enough to read in a badge in the Roles table.
  </Accordion>
  <Accordion title="What happens if I grant a permission to someone who already has it directly?">
    Nothing visible. The resolved list is deduplicated, and the grant table has a uniqueness constraint, so there is no second entry to see or remove.
  </Accordion>
  <Accordion title="If I revoke a direct grant someone also gets from a role, does their access change?">
    No. Effective access is the union, so the role's copy remains. This is the usual explanation for "I removed that permission and they still have it".
  </Accordion>
  <Accordion title="Does assigning a role send a notification?">
    No. Nothing in the role surface emits an event. If you need to tell someone their access changed, build it from your own event subscription or do it out of band.
  </Accordion>
  <Accordion title="Are role changes audited?">
    Not in the platform audit log, which covers configuration and administration rather than identity records. The tables change, and the effect appears on the next token issued.
  </Accordion>
  <Accordion title="Does the user's session survive a role change?">
    The session survives. Its access token keeps carrying the old claims until it expires, and the refresh token is unaffected — refreshing is what picks up the new state.
  </Accordion>
  <Accordion title="Why did the resolved permissions list not change after I saved the role?">
    Usually a cached profile rather than a stale permission. If you read the permissions from an access token or from a cached `/auth/v1/user` response, both are snapshots. Re-read after a refresh.
  </Accordion>
  <Accordion title="Can a role hold a permission that no policy ever checks?">
    Yes, and it will sit there indefinitely. Nothing reconciles permissions against policies, so an unused permission is invisible until someone audits.
  </Accordion>
  <Accordion title="Do I need the platform environment to have roles?">
    No. The reserved `_platform` environment holds Studio's operators and is configured separately, because the API does not host it. Your project environments have their own roles.
  </Accordion>
</AccordionGroup>

<Warning>
Test all five. A policy that passes the first and fails the second is the common case, and one that passes both but ignores the assurance level will look correct until the day it matters.
</Warning>

Step 3 is the tenancy rule doing its job. Step 5 is the only place permissions are read, and it reads a snapshot rather than the database. Steps 5 and 6 together are why authorization is cheap and why changes are not immediate.
### The order of a change that touches many people

Three roles and thirty people are about to lose a permission. The order below avoids the two failure modes that produce support tickets.

| Order | Action | What it prevents |
| --- | --- | --- |
| 1 | Note who currently holds the affected roles. | Discovering afterwards that someone was affected and you did not know. |
| 2 | Add the replacement to the roles, keeping the old one. | A gap where nobody has the capability. |
| 3 | Update the policies to check the new name. | A window where the policy names something nobody holds. |
| 4 | Confirm it works for a holder of each affected role. | Discovering a typo in the new name at step 5. |
| 5 | Revoke sessions for anyone whose access must change now. | Carrying old claims for the access-token lifetime. |
| 6 | Remove the old name from the roles. | Nothing, at this point — it is the actual change. |
| 7 | Revoke the old direct grants. | Leaving a permission nothing checks, in a badge list forever. |

<Warning>
Step 5 is optional in the sense that it is not required for correctness — the change lands on the next refresh either way. It is required when someone should lose access today rather than within the access-token lifetime.
</Warning>

### The order for removing access entirely

Different shape, because there is no replacement to stage.

```text
1. Revoke the sessions        → access stops now
2. Remove roles and grants    → the records are cleaned up
3. Disable the account        → no future sign-in
```

Each step is independently useful, and doing them in this order means the access is gone before any of the tidying. Doing them in reverse leaves a window in which the records say one thing and the tokens say another, which is the hardest state to investigate afterwards.

### When a policy is the thing you are changing

The reverse consideration applies: turning a policy **on** denies everyone who lacks the permission, immediately, including your own test account if it lacks one.

| Change | Safe order |
| --- | --- |
| Adding a permission requirement. | Grant first, then enforce. |
| Removing a permission requirement. | Relax first, then remove the grant. |
| Adding an `aal2` requirement. | Enrol everyone first, then enforce. |
| Narrowing an existing condition. | Expect breakage; test with the affected group. |

<Note>
Every one of these is the same rule: change what people have before you change what is required, or change what is required before you change what people have if you want them to keep working. Decide which, deliberately.
</Note>

<Note>
No service in this path queries `perm_*`. That is deliberate: enforcement must not depend on the identity service being available, or an outage there would become an outage everywhere.
</Note>

### Where roles are read, and where they are not

| Component | Reads roles? |
| --- | --- |
| The gateway, verifying a token. | No. It checks the signature and the environment only. |
| The policy engine. | Yes, from the claims. |
| Akountz, when issuing a token. | Yes, from the tables. |
| Akountz, when starting a session. | Yes, to record the session row. |
### The one-page version

If you have read nothing else on this page, this is the whole model.

```text
A role      = a group row, plus the permission rows attached to it
Membership  = a row joining a person to a group
A grant     = a permission row joined straight to a person
Effective   = every direct grant, unioned with every group they belong to
Enforcement = the union, snapshotted into the token when it is issued
```

And the four things that surprise people:

| Surprise | Why |
| --- | --- |
| Assigning a role that does not exist creates it, empty. | The assignment path defines the group when it cannot find one. |
| No inheritance. `manager` does not include `employee`. | Groups hold permissions, not other groups. |
| No deny rules. Nothing subtracts a permission. | The model has positive grants only. |
| Changes are not instant. | The token is a snapshot, so a change lands on the next refresh. |

Everything else — the prefixing, the tables, the Studio screen — is mechanics in service of those four.

<Note>
If you are looking for a model with first-class role records and a separate assignment table, it does not exist here, and the closest mental model is "groups with permissions", which is exactly what it is called in the database.
</Note>

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Is there a Role table I can query directly?">
    No. Roles are rows in `perm_groups`. Query that table, filter on the environment prefix, and strip it, which is exactly what the listing operation does.
  </Accordion>
  <Accordion title="Can a role include another role?">
    No. Groups hold permissions only, and permissions are plain strings. To give a manager everything an employee has, put the person in both, or repeat the permissions in the manager role.
  </Accordion>
  <Accordion title="What happens to members when a role is deleted?">
    The memberships are deleted with it. Nobody is left pointing at a group that no longer exists, and nobody keeps the role's permissions.
  </Accordion>
</AccordionGroup>

## Worked numbers

A worked example, so the token contents are concrete rather than abstract.

Suppose `acme/production` has three roles and two permissions defined:

```text
acme/production/customer   → orders:read, orders:create
acme/production/staff      → orders:read, orders:update
acme/production/auditor    → orders:read
### Two ways to grant the same thing

Two people who can both export reports may have entirely different records, and neither record tells you more than the other.

```text
Person A:  member of a role holding reports:export
Person B:  direct grant of reports:export
```

Both resolve to the same entry in `perms`, so no policy can distinguish them, and neither should. The difference matters in three operational places:

| | Role | Direct grant |
| --- | --- | --- |
| Visible in the Roles tab. | Yes, with a member count. | No. |
| Visible on the user. | As a role badge. | In its own labelled list. |
| Changes if the role is edited. | Yes, immediately, for everyone. | No. |
| Changes if the grant is revoked. | Only for the person whose grant it is. | Yes. |

That third row is why a direct grant is often the safer place for a temporary exception: editing the role does not touch it.

<Warning>
The inverse is also true, and it is the more common problem: granting a permission directly to someone who already gets it from a role achieves nothing that survives an edit of that role, and leaves a badge suggesting the grant is load-bearing.
</Warning>

### Finding the source of an unexpected permission

When someone can do something you did not intend to allow, work backwards from the resolved list:

```text
perms contains reports:export
  → is reports:export in any role they hold?     check their roles
  → is it in their direct grants?                check the user's list
  → do they hold a role with *?                  check for the wildcard
  → is the policy checking something else?       read the condition
```

The fourth step is the one people skip. A policy can allow an action through a path you did not consider — an `any` branch, a second policy on the same operation, or a condition that passes for a reason unrelated to the permission.

<Tip>
When an action is allowed unexpectedly, check for a second policy before hunting the permission tables. Two policies on one operation is a supported arrangement, and either one alone may permit it.
</Tip>

```

Grace belongs to `customer` and `staff`, and additionally holds `reports:export` directly.

```text
Direct:   acme/production/reports:export
Via groups:
  acme/production/customer  →  acme/production/orders:read,  acme/production/orders:create
  acme/production/staff     →  acme/production/orders:read,  acme/production/orders:update
```

After prefixing is stripped and the list is deduplicated and sorted, her claims are:

```json
{
  "roles": ["customer", "staff"],
  "perms": [
    "orders:create",
    "orders:read",
    "orders:update",
    "reports:export"
  ]
}
```

Five points to draw from that.

**`orders:read` appears once.** It came from both groups. The union is deduplicated, so the size of the token does not grow with the number of routes to a permission.

**`orders:read` is absent from `auditor`'s badge list on her account but present in her permissions.** No — it is present in both places; the point is that it arrived via two groups, and nothing in the token records which.

**`reports:export` is indistinguishable from the rest.** A policy cannot tell that this one came from a direct grant rather than a role, and does not need to.

**`auditor` does not appear at all.** She is not in it. The role exists in the environment and is irrelevant to her.

**Removing `staff` changes two entries.** Her next token loses `orders:update` and drops `staff` from `roles`. It keeps `orders:read`, because `customer` also grants it — which is the behaviour people expect from roles but have to learn applies here.

### The same person, two environments

```json
{ "prj": "acme", "env": "staging", "roles": ["tester"], "perms": ["*"] }
```

and

```json
{ "prj": "acme", "env": "production", "roles": ["customer", "staff"], "perms": ["orders:create", "orders:read", "orders:update"] }
```

Same address, same installation, entirely separate worlds. The staging token is refused by production at the environment check, before any claim is read — and the production token would fail the same way in staging.

<Warning>
That is the failure mode behind "I gave them the role but it does not work". The role was assigned in staging, and the request is going to production. Compare the `prj` and `env` claims before looking at anything else.
</Warning>

### The wildcard, concretely

If `tester` held `*` instead of a list, her token would carry `perms: ["*"]` — a single entry, not an expansion. Nothing expands it at issue time. Every policy that checks a permission finds the wildcard at evaluation, which is why the token stays small and why the wildcard also satisfies permissions that do not exist yet.


## Reference summary

### Models and tables

| Model | Table | Unique on |
| --- | --- | --- |
| `Permission` | `permissions` | the name |
| `Group` | `perm_groups` | the name |
| `UserPermission` | `user_permissions` | — |
| `UserGroup` | `perm_user_groups` | `(user_id, group)` |
| `GroupPermission` | `perm_group_permissions` | `(group, permission)` |

Every row above uses a ULID primary key rather than an auto-increment integer. The same module also re-keys `JWTToken` to `jwt_tokens` and `TokenBlacklist` to `token_blacklist`.

### Operations

| Operation | Effect |
| --- | --- |
| Define a role | Creates or replaces the group and its permission set. |
| Delete a role | Removes memberships and the group. Permissions survive. |
| Assign a role | Adds a membership, creating the group if absent. |
| Revoke a role | Removes the membership, silently. |
| Grant permissions | Defines them if needed, then attaches directly. |
| Revoke permissions | Removes the direct grant, silently. |

### Names

| Rule | Detail |
| --- | --- |
| Role name pattern | `^[a-z][a-z0-9_:-]{0,62}$`. |
| Permission name pattern | None enforced. |
| Storage form | `{project}/{env}/{name}`. |
| Returned form | `{name}`, filtered by prefix. |

### Claims

| Claim | Source | Snapshotted at |
| --- | --- | --- |
| `roles` | The person's group memberships. | Issue. |
| `perms` | Direct grants unioned with group permissions. | Issue. |
| `aal` | `aal1`, or `aal2` after MFA. | Issue. |
| `org`, `org_role` | The session's organization membership. | Issue. |

### Configuration

| Key | Default | Effect |
| --- | --- | --- |
| `default_roles` | `[]` | Roles granted to every account at creation. |

That is the whole authorization surface of the environment's `auth` block. There is no policy expression syntax to learn, because policies are JSON and roles are groups.
