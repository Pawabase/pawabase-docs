A **sign-in link** (also called a magic link) is a one-click way in. The person gives their email, Pawabase sends a link, and clicking it signs them in on your site. There is no password to remember or leak.

## In Studio

**Users & auth → Sign-in → Sign-in & registration → Ways to sign in → Sign-in link**. It is on by default. Set your **Site URL** and add the addresses you pass as `redirectTo` to the [redirect list](/auth/redirect-urls), since the link must return somewhere.

Change the wording under [Email templates → Sign-in link](/auth/email-templates).

## Request a link

<CodeGroup>
```typescript TypeScript
await pawabase.auth.signInWithMagicLink({
  email: "ada@example.com",
  redirectTo: "https://myapp.com/auth/callback",
  createUser: true,
});
```

```python Python
pb.auth.sign_in_with_magic_link(
    email="ada@example.com",
    redirect_to="https://myapp.com/auth/callback",
    create_user=True,
)
```
</CodeGroup>

`createUser` decides what happens for an address with no account: create one (the default), or do nothing. Pass `false` for an app where only existing people may sign in. In either case the call returns without saying whether the address exists.

## Finish on the landing page

Where the link takes the person depends on whether the environment has a **Site URL** ([Redirect URLs and email links](/auth/redirect-urls#where-email-links-go)):

| Site URL | The link opens | What your app does |
| --- | --- | --- |
| **Set** (recommended) | `<Site URL>/auth/callback?token=…&type=magic&redirect_to=…` | Your `/auth/callback` route reads `token` and calls `verifyMagicLink`, then goes on to `redirect_to` |
| **Not set** | A Pawabase page that checks the link, then sends the person to your `redirectTo` with the session in the URL fragment | Nothing: the browser client reads the fragment on load, stores the session and fires `SIGNED_IN` |

With a Site URL, finish the sign-in like this:

<CodeGroup>
```typescript TypeScript
const params = new URLSearchParams(location.search);
if (params.get("type") === "magic") {
  const result = await pawabase.auth.verifyMagicLink(params.get("token") ?? "");
  history.replaceState(null, "", location.pathname);           // keep the token out of the address bar
  if (result.status === "mfa_required") await result.verify(await askForCode());
  location.replace(params.get("redirect_to") ?? "/");
}
```

```python Python
result = pb.auth.verify_magic_link(token)
if result.status == "mfa_required":
    result.verify(code_from_user)
```
</CodeGroup>

The same `/auth/callback` route handles the other email links (confirmations, resets, invitations); see the full handler in [Redirect URLs and email links](/auth/redirect-urls#handling-the-callback-in-your-app).

## A complete page

```tsx
function LinkSignIn() {
  const [sent, setSent] = useState(false);
  const [email, setEmail] = useState("");

  async function request() {
    await pawabase.auth.signInWithMagicLink({ email, redirectTo: `${location.origin}/` });
    setSent(true);
  }

  return sent ? (
    <p>We sent a link to {email}. It works once, so open it on this device.</p>
  ) : (
    <>
      <input type="email" value={email} onChange={(e) => setEmail(e.target.value)} />
      <button onClick={request}>Email me a link</button>
    </>
  );
}
```

## Things to know

- A link works **once** and expires. If it fails, show "this link has expired" with a button to send a new one.
- It signs the person in on the device that opens it. Email apps that open links in an internal browser can confuse people; that is when [codes](/auth/email-codes) are better.
- Opening the link proves the inbox is theirs, so the address becomes verified.
- If the account has two-step verification, the link leads to `mfa_required` like any other first step.

## Errors

| Call | Answer | Message | TypeScript | Python |
| --- | --- | --- | --- | --- |
| `signInWithMagicLink` | `403` | "magic links are disabled" | `PermissionError` | `ForbiddenError` |
| `signInWithMagicLink` | `400` | "redirect_to is not an allowed URL" | `ApiError`, status 400 | `ValidationError` |
| `verifyMagicLink` | `400` | "the link is invalid or has expired" | `ApiError`, status 400 | `ValidationError` |
| either | `429` | rate limited | `RateLimitError` | `RateLimitedError` |

Requesting a link answers the same way whether or not the address has an account. On the landing page, treat a `400` from `verifyMagicLink` as "this link has expired or was already used" and offer to send a new one.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| No email arrives | Check spam; check the [mail log](/mail/overview) for a failed send; check the sending address |
| The link opens the wrong page | `redirectTo` missing or not on the [redirect list](/auth/redirect-urls) |
| "Link already used" | Corporate email scanners may open links first. Use [codes](/auth/email-codes) for those users |
| Works on desktop, not in-app browsers | Use codes |
