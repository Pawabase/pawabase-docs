Every Auth setting can be changed in two places that edit the **same data**: the Studio screens, and a script using the management client. Use Studio to explore and make quick changes. Use code when you want changes reviewed, repeated for every environment, or applied by a deployment.

## In Studio

1. Open your project and choose an environment (`development`, `production`, and so on).
2. Under **Access**, choose **Users & auth**.
3. Use the sidebar to open a page, such as **Sign-in & registration** or **Password policy**.
4. Change the settings. A page that edits settings shows a **Save** bar when you have unsaved changes. Nothing is applied until you save, and **Discard** drops your edits.

Settings belong to an environment. Changing `development` never touches `production`.

## In code

Settings are one JSON object, `auth`, on the environment. `environments.update` **merges** the keys you send into it, so you only mention what you change.

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";
import { manage } from "@pawabase/client/manage";

const m = manage(
  createClient({
    url: process.env.PAWABASE_URL!,
    apiKey: process.env.PAWABASE_SECRET_KEY!,      // a secret key, on a server only
    environment: "production",
  }),
);

await m.environments.update("production", {
  auth: {
    signup_enabled: true,
    require_email_verification: true,
    magic_link_enabled: true,
    passkeys_enabled: true,
  },
});

const env = await m.environments.getOne("production");
console.log(env.auth);
```

```python Python
import os
from pawabase import Pawabase

pb = Pawabase(os.environ["PAWABASE_URL"], os.environ["PAWABASE_SECRET_KEY"], environment="production")

pb.manage.environments.update(
    "production",
    auth={
        "signup_enabled": True,
        "require_email_verification": True,
        "magic_link_enabled": True,
        "passkeys_enabled": True,
    },
)

env = pb.manage.environments.get_one("production")
print(env["auth"])
```
</CodeGroup>

Nested groups such as `directory` are merged one level deep: send the whole `directory.mfa` object when you change it, not a single field of it.

## The settings, in one place

| Key | Studio page | Meaning | Default |
| --- | --- | --- | --- |
| `signup_enabled` | Sign-in & registration | Anyone may create an account | `true` |
| `require_email_verification` | Sign-in & registration | Must confirm email before the first sign-in | `false` |
| `magic_link_enabled` | Sign-in & registration | Offer "email me a link" | `true` |
| `email_code_enabled` | Sign-in & registration | Offer "email me a code" | `false` |
| `passkeys_enabled`, `passkey_rp_id` | Sign-in & registration | Passkeys, and the domain they belong to | `false` |
| `anonymous_enabled` | Sign-in & registration | Guest sign-in | `false` |
| `signup_form` | Sign-in & registration, Attributes | What sign-up asks for | email only |
| `password_policy`, `password_min_length`, `password_rules` | Password policy | Strength rules | basic, 8 |
| `mfa_enabled` | Multi-factor | Allow two-step verification | `true` |
| `access_ttl`, `refresh_ttl`, `max_sessions` | Sessions | Token lifetimes and device limit | 900 s, 30 days, unlimited |
| `site_url`, `redirect_urls` | Domains | Where emails and sign-ins may send people back | none |
| `default_roles` | Restrictions | Roles given to new accounts | none |
| `allowed_email_domains`, `blocked_email_domains` | Restrictions | Limit who can sign up | any |
| `lockout_threshold`, `lockout_minutes` | Attack protection | Lock after repeated failures | installation default |
| `providers` | Social providers | Credentials per provider | none |
| `emails` | Email templates | Wording for each message | defaults |
| `token_profiles` | Token profiles | Tokens for other services | none |
| `directory.passwords` | Password policy | Max length, history, expiry, breach check | see page |
| `directory.mfa` | Multi-factor | Methods, backup codes, requirement | see page |
| `directory.recovery` | Account recovery | Reset link lifetime and safety | see page |
| `directory.devices` | Devices | Tracking and remembered devices | see page |
| `directory.api_keys` | User API keys | Personal keys | off |

Each setting is explained, with its Studio screen, on its own page.

## Ask the project what is on

Your app can read the public part of the configuration to decide what to show:

<CodeGroup>
```typescript TypeScript
const settings = await pawabase.auth.settings();
if (settings.passkeys_enabled) showPasskeyButton();
if (settings.magic_link_enabled) showLinkOption();
if (!settings.signup_enabled) hideSignUp();
```

```python Python
settings = pb.auth.settings()
if settings["passkeys_enabled"]:
    show_passkey_button()
```
</CodeGroup>

## Keep environments consistent

A reliable pattern:

1. Describe your Auth settings once in a script (a plain object).
2. Apply it to `development` while you build, then to `staging`, then to `production`.
3. Keep **secrets** (provider client secrets, signing keys) out of the script; reference them from Studio's **Secrets** page with `secret://NAME`.

```typescript
const authSettings = { signup_enabled: true, require_email_verification: true /* … */ };

for (const env of ["development", "staging", "production"]) {
  await m.environments.update(env, { auth: authSettings });
}
```

Differences between environments are usually deliberate: `development` may allow unverified emails for quick testing, `production` should not.
