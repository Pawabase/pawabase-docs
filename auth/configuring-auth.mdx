You configure Auth in Studio. Each environment has its own settings, so changing `development` never touches `production`.

## Open it

1. Choose your project and an environment (`development`, `production`…) from the top bar.
2. In the sidebar, under **Security**, choose **Users & auth**.
3. Its tabs are in five groups:

| Group | Tabs |
| --- | --- |
| **People** | Users, Organizations, Organization roles, Invitations, Roles |
| **Sign-in** | Authentication flow, Sign-in & registration, Email templates, Attributes, Social providers, OAuth servers |
| **Protection** | Password policy, Multi-factor, Account recovery, Devices, Sessions, Attack protection, Restrictions, Domains |
| **Access** | Token profiles, User API keys, Machines & agents, Auth webhooks |
| **Records** | Sign-in activity, Data requests, Import & export |

**Enterprise sign-in** and **Bot protection** are separate pages in the same menu.

## How saving works

A page that edits settings shows a **Save** bar when you have unsaved changes. Nothing is applied until you save, and **Discard** drops your edits. Saving a page saves that page's settings; other pages are untouched.

Changes apply to new sign-ins at once. People already signed in keep the access token they have until it expires (15 minutes by default; refresh tokens last 30 days), so a change such as requiring two-step verification reaches everyone within one token lifetime. To apply it to someone at once, end their sessions: one by one on **Protection → Sessions** (**End session**), or all of a person's at once with **Sign out everywhere** on their page under **People → Users**.

## Where each setting is

| I want to… | Go to |
| --- | --- |
| Turn self-registration, email verification, guests, codes, links, passkeys on or off | **Sign-in → Sign-in & registration** |
| See the whole flow at a glance | **Sign-in → Authentication flow** |
| Choose what sign-up asks for | **Sign-in → Attributes**, **Sign-in & registration** |
| Add Google, GitHub, Apple… | **Sign-in → Social providers** |
| Connect a customer's SAML/OIDC login | **Users & auth → Enterprise sign-in** (its own page, beside Bot protection) |
| Set where emails and sign-ins may return | **Protection → Domains** |
| Change the wording of emails | **Sign-in → Email templates** |
| Set password rules | **Protection → Password policy** |
| Turn on two-step, require it | **Protection → Multi-factor** |
| Control password resets | **Protection → Account recovery** |
| Track and limit devices | **Protection → Devices** |
| Set token lifetimes, sessions per person | **Protection → Sessions** |
| Lock accounts after failures | **Protection → Attack protection** |
| Limit who can sign up | **Protection → Restrictions** |
| Issue tokens for another service | **Access → Token profiles** |
| Let people make personal API keys | **Access → User API keys** |
| Give services and AI agents their own identity | **Access → Machines & agents** |
| Send auth events to your system | **Access → Auth webhooks** |
| Answer data access and erasure requests | **Records → Data requests** |
| Back up or move users | **Records → Import & export** |

Each page of this section follows the same screen.

## Ask the project what is on

Your app can read the public part of the configuration to decide what to show:

<CodeGroup>
```typescript TypeScript
const settings = await pawabase.auth.settings();
if (settings.passkeys_enabled) showPasskeyButton();
if (settings.magic_link_enabled) showLinkOption();
if (!settings.signup_enabled) hideSignUp();
```

```python Python
settings = pb.auth.settings()
if settings["passkeys_enabled"]:
    show_passkey_button()
```
</CodeGroup>

## Keep environments consistent

1. Build and test your sign-in design in `development`.
2. Make the same changes in `production`, page by page, using this checklist: **Domains** (real site address), **Sign-in & registration**, **Password policy**, **Multi-factor**, **Sessions**, **Restrictions**, **Social providers** (production credentials), **Email templates**.
3. Keep **secrets** (provider client secrets, signing keys) on Studio's **Secrets** page and refer to them as `secret://NAME`. They are per environment; production has its own values.

Differences between environments are usually deliberate: `development` may allow unverified emails for quick testing, `production` should not. See [Environments](/environments/overview).
