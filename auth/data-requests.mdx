When someone asks what you hold about them, or asks you to delete it (a right under GDPR, CCPA and similar laws), you need to answer quickly and be able to show you did. **Data requests** do both for the data Pawabase's sign-in service keeps, and leave a record that holds no personal data.

| Request | What it does | Reversible? |
| --- | --- | --- |
| **Export** | Gathers what is held about the person into one JSON document | Nothing changes |
| **Erase** | Deletes the account and clears what could identify the person | **No** |

## What each covers

| Data | Export | Erase |
| --- | --- | --- |
| Profile: email, username, name, picture, verification, public and private metadata, roles, last sign-in | Included, as an administrator sees it (phone isn't in the export) | Account deleted; name, picture, phone, metadata and last sign-in IP cleared; the email becomes `deleted+<id>@pawabase.invalid` so the real address can sign up again |
| Uploaded profile picture | Its address, in the profile | The file is deleted from the avatars bucket |
| Linked accounts (social and enterprise sign-in) | Provider, subject, email, dates | Removed |
| Sessions | Method, assurance level, IP, browser, dates (also ended ones) | Every session ended |
| Devices | Label, browser, first and last IP, sign-in count, dates | Removed |
| Passkeys | Name, device type, dates | Removed |
| Personal API keys | Name, prefix, scopes, dates, use count (never the key) | Removed |
| Second factors and password history | Not included (secrets) | Removed |
| Organization memberships | Organization, role, joined | Removed |
| Organization audit entries they made | Not included | Kept; their email is cleared from each entry |
| Sign-in history | Every entry: kind, method, outcome, reason, IP, browser, time | Kept as counts: the person, email, IP, browser and reason are cleared |
| Requests they made with their token | The total, and the latest 5,000: method, path, status, duration, IP, country, browser, time | Kept as counts: the person, IP, country and browser are cleared |
| Emails sent to them | Not included | Kept as delivery records: their address is removed from the recipients, and the body, template data and attachments are cleared |

Password hashes, key values and factor secrets are **never** exported.

### What neither covers

<Warning>
Erasure only reaches what the sign-in service keeps. These stay as they are, and are yours to handle:

- **Rows in your own tables** (an order, a review, a message), including anything that stores the person's id or email.
- **Files** they uploaded to your [storage](/storage/overview) buckets (other than their profile picture).
- **Events, flow runs and webhook deliveries** whose payloads mention them (a `user.created` event carries the email). These are deleted by your plan's retention periods.
- **Copies elsewhere**: your own logs, analytics, a CRM a webhook sent the address to, [backups](/backups/overview) taken before the erasure.
</Warning>

## In Studio

**Users & auth → Records → Data requests** lists every request handled in the environment: when, export or erasure, the person's id, and what was found or removed.

To make a request, open the person (**Users & auth → People → Users**), go to **Security**, and find **Data requests**:

- **Export their data** downloads the JSON document.
- **Erase their data…** asks you to type their email address. **Erase for good** stays disabled until it matches, so a misclick can't erase the wrong person.

## The record

Every request leaves a record, so you can show it was handled:

| Field | Value |
| --- | --- |
| `kind` | `export` or `erase` |
| `status` | `completed` |
| `subject_id` | The person's user id |
| `subject_hash` | A SHA-256 hash of the email address they had, so you can answer "did you handle my request?" by hashing the address they give you |
| `requested_by` | `admin` |
| `result` | Counts: for an export, sign-ins, requests, sessions and linked accounts found; for an erasure, how many sessions, linked accounts, passkeys, devices, API keys, past passwords, memberships, sign-in records, requests, organization audit entries and emails were removed or cleared |
| `created_at`, `completed_at` | When |

The record holds no personal data, so it's safe to keep indefinitely. Exports themselves are never stored: the document is returned once, to you.

## From your server

All three calls need a **secret key**.

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";
import { admin } from "@pawabase/client/admin";

const a = admin(createClient({ url, project, apiKey: process.env.PAWABASE_SECRET_KEY, environment: "production" }));

const { data, request } = await a.users.exportData(userId);   // data: the document to hand over
await a.users.eraseData(userId, "ada@example.com");           // final: confirm with their email address
const handled = await a.privacy.requests({ limit: 20 });     // newest first, up to 200
```

```python Python
import os
from pawabase import Pawabase

pb = Pawabase(url, os.environ["PAWABASE_SECRET_KEY"], project=project, environment="production")

answer = pb.admin.users.export_data(user_id)                   # answer["data"]: the document to hand over
pb.admin.users.erase_data(user_id, confirm="ada@example.com")  # final: confirm with their email address
handled = pb.admin.privacy.requests(limit=20)
```
</CodeGroup>

| Call | REST | Answer |
| --- | --- | --- |
| Export | `POST /admin/v1/envs/{env}/users/{id}/privacy/export` | `{ request, data }` |
| Erase | `POST /admin/v1/envs/{env}/users/{id}/privacy/erase` with `{ "confirm": "<email>" }` | `{ request }` |
| List | `GET /admin/v1/envs/{env}/privacy/requests?limit=50` | `{ data: [request, …] }` |

Refusals: `404` when there's no such person (or they're already erased), `400` "confirm must be this user's email address" when `confirm` doesn't match. The match ignores case and surrounding spaces.

## A routine for requests

<Steps>
  <Step title="Check who's asking">
    A request by email should come from the address on the account. If it doesn't, ask them to send it from that address or sign in and ask from your app.
  </Step>
  <Step title="Export, if they asked for their data">
    Export, add the rows your own tables hold for them (query by their user id), and send both. Most laws give you about a month.
  </Step>
  <Step title="For an erasure, clear your own data first">
    Delete or anonymize the person's rows in your tables and their files in storage **while you still know their id and email**. A [flow](/automation/overview) on `user.erased` can't help with lookups by email: by then the address is gone.
  </Step>
  <Step title="Erase the account">
    In Studio or with `eraseData`. The person is signed out everywhere at once.
  </Step>
  <Step title="Keep the record">
    It's your proof, and it holds nothing personal. Reply to the person that it's done.
  </Step>
</Steps>

### Self-service

To let people request their own export or deletion from your app, add a route on your server that checks the signed-in person and calls the admin API with your secret key. Never put the secret key in the app itself. For deletion, ask them to confirm (type their email, or re-enter their password), then run the same routine.

## Events

| Event | Payload |
| --- | --- |
| `user.data_exported` | `user_id`, `request_id` |
| `user.erased` | `user_id`, `request_id` |

Use `user.erased` to clean up by **user id** in places your server can reach (a search index, a CRM). See [Auth webhooks](/auth/auth-webhooks).

## Erase or delete?

| | Erase | Delete user |
| --- | --- | --- |
| Account | Gone, profile cleared | Gone, but name, phone and metadata stay on the deleted row |
| Uploaded profile picture | Deleted | Deleted |
| Sign-in history, request logs | Kept, with the person cleared | Kept as they are |
| Emails sent to them | Address and content cleared | Kept as they are |
| Record of the request | Yes | No |
| Confirmation | Their email, typed | None |

Use **erase** whenever the reason is the person's request or privacy. Use delete for test accounts and clean-up.
