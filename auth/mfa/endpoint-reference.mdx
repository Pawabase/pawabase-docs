Every MFA route, with what it needs and what it returns.

| Method | Path | Needs a code | Rate limit | Returns |
| --- | --- | --- | --- | --- |
| POST | `/auth/v1/mfa/totp/enroll` | no | none | `factor_id`, `secret`, `otpauth_uri` |
| POST | `/auth/v1/mfa/totp/verify` | yes | `akz:mfa` | `enabled`, `recovery_codes` |
| POST | `/auth/v1/mfa/disable` | yes | `akz:mfa` | `enabled` |
| POST | `/auth/v1/mfa/recovery-codes` | yes, TOTP only | `akz:mfa` | `recovery_codes` |
| GET | `/auth/v1/mfa` | no | none | `enabled`, `aal`, `recovery_codes_remaining` |
| POST | `/auth/v1/token` | yes | `akz:auth` | The token response at `aal2` |

### Request bodies

Two of the routes take a body, and both validate the code's shape before looking at it.

```json
{
  "code": "123456"
}
```

| Constraint | Applies to |
| --- | --- |
| Minimum length 6 | Every code body. |
| Maximum length 32 | Every code body. |

<Info>
The minimum length of six is why a recovery code fits the same body as a TOTP code — the hyphenated form is exactly ten characters. One field, either method, no client-side discrimination needed.
</Info>

### Errors

| Status | Detail | Cause |
| --- | --- | --- |
| 400 | `the code is not valid` | Wrong code, expired challenge, or a replayed TOTP step. |
| 400 | `a current authenticator code is required` | Regenerating codes with a recovery code instead of a TOTP code. |
| 400 | `mfa_token and code are required` | The MFA grant sent without both fields. |
| 400 | `the challenge is no longer valid` | The user was deleted or disabled after the challenge was issued. |
| 403 | `MFA is disabled for this project` | Enrolment attempted where `mfa_enabled` is off. |
| 429 | `too many failed attempts; try again later` | The account is locked out. |

<Warning>
`the code is not valid` covers several distinct causes — a wrong code, an expired challenge, a replayed TOTP code, an already-spent recovery code — and they are indistinguishable from outside. That is deliberate. Giving a user a precise reason would let someone probe which recovery codes are already used.
</Warning>

## Configuring MFA

There is exactly one setting, and it decides two different things.

```json
{
  "auth": {
    "mfa_enabled": true
  }
}
```

| What `mfa_enabled` controls | Effect when false |
| --- | --- |
| Enrolment | `POST /mfa/totp/enroll` returns `403 MFA is disabled for this project`. |
| Sign-in challenge | Existing enrolments stop being challenged at sign-in. |

That second row is the surprising one, and it is a genuinely useful behaviour: **turning MFA off stops requiring it without destroying it.** A user who enrolled an authenticator keeps their factor and their recovery codes, they simply stop being challenged. Turning it back on restores the challenge immediately.

<Warning>
`mfa_enabled` is a per-environment setting and defaults to **on**. An environment that has never been configured has MFA available and enabled, and anyone can enrol. The platform's own reserved environment is the exception — it has `signup_enabled` off and a stricter policy set, and magic links disabled.
</Warning>

### There is no directive to require MFA

This is worth stating directly, because it is a common assumption carried over from other systems.

**There is no `require_aal` setting, and there is no `require_mfa` setting.** Neither exists. There is also **no TOML anywhere in authentication configuration** — the environment's auth block is JSON, as it is everywhere else in Pawabase.

If you are looking for a way to force every user in an environment to have MFA, that is not a configuration setting. The two available approaches are:

| Approach | How |
| --- | --- |
| Require `aal2` in a policy. | Branch on the token's `aal` claim at the operation that needs it. See [Auth in policies](/auth/auth-in-policies/overview). |
| Enrol users administratively. | There is no admin route to enrol on a user's behalf; an administrator resets MFA rather than setting it up. |

<Warning>
Pawabase has no directive that forces enrolment. If your product needs "every account must have MFA before it can do X", express that as a policy on `aal`, and treat an un-enrolled user's `aal1` as the case you are rejecting. This is the intended design: assurance is a property of the session, not a flag on the account.
</Warning>

<Info>
Remember the ten-second configuration cache. Turning MFA off in Studio does not take effect on sign-in attempts made in the next few seconds. See [Authentication configuration](/auth/configuration/overview).
</Info>

### Policies are JSON too

If you are expressing the assurance requirement in a policy, the shape is JSON like everything else.

```json
{
  "require": {
    "aal": "aal2"
  }
}
```

The `aal` claim is available to conditions, exactly like the other identity claims. See [Conditions](/policies/conditions) for the full condition vocabulary and [Auth in policies](/auth/auth-in-policies/overview) for how this is applied.


## What Studio shows

MFA appears in three places in Studio's **Users & auth** page, and they answer three different questions.

### The environment switch

Under the **Configuration** tab, the **Sign-in methods** section holds **MFA (TOTP)**, whose hint reads *"Let users add an authenticator app for aal2."* That is the `mfa_enabled` setting, described in the interface in exactly the assurance-level terms this page uses.

It sits beside **Magic links**, described as *"Passwordless sign-in by emailed one-time link"*, in a section with no description of its own. Two switches, two sign-in methods, one tab.

<Info>
The hint text names `aal2` explicitly, which is a good confirmation that the assurance level is the concept the product is built around rather than an implementation detail.
</Info>

### Per user

Under the **Users** tab, a user's modal shows whether MFA is on. For a user who has it enabled, the modal offers a **Reset MFA** action.

That reset is the administrative escape hatch for a user who has lost both their authenticator and their recovery codes. It deletes the factor and the recovery codes and clears the flag, returning the account to a state where they can sign in with one factor and enrol again.

<Warning>
MFA reset removes the user's ability to verify themselves. Before offering it as a support action, treat it as an account-recovery event: confirm the person's identity by whatever means your support process requires, and record that you did.
</Warning>

### The audit trail

Under the **Sign-in activity** tab, MFA produces its own event rows alongside ordinary sign-ins.

| Event | When |
| --- | --- |
| `mfa_challenge` | A challenge is issued instead of a session. |
| `mfa_verify` | A challenge is answered. Recorded with success or failure and a reason. |
| `mfa_enrolled` | A factor is confirmed. |

A failed `mfa_verify` carries the reason `wrong code`, and renders in the Result column like any other failure. Watching for repeated failures on one account is the practical way to spot someone who cannot get into their account.

<Info>
The **failures only** checkbox on that tab is the fastest way to review MFA problems across an environment.
</Info>

## Building the user interface

The three screens an MFA feature needs, and the decisions that are easy to get wrong in each.

### Enrolment

The screen has one job: get the secret into an authenticator app and prove it works before the account is committed.

| Element | Notes |
| --- | --- |
| QR code | Rendered from `otpauth_uri`. The path most users take. |
| The secret as text | For users who cannot scan. Show it; do not hide it. |
| A code input | Confirms the enrolment. |
| A warning about losing the device | Before they commit, not after. |

<Warning>
The most common enrolment failure is a user who scans the QR code, does not complete the confirmation step, and navigates away. Because unconfirmed factors are deleted on the next enrolment attempt but not by abandoning, an abandoned attempt leaves a pending factor that does not affect the account. The user simply tries again and gets a new secret.
</Warning>

### The recovery codes screen

This is the screen most products get wrong, because the easy implementation is a toast.

| Decision | Why it matters |
| --- | --- |
| Make it blocking | The codes exist once. A dismissible toast loses them. |
| Show all ten at once | There is no way to fetch them later, so a partial view is a partial loss. |
| Offer a download | Users lose phones. A `.txt` file in their password manager is the realistic path. |
| Offer a print | Some users will print them. |
| Do not auto-advance | Let them leave only when they have said they have them. |
| Show the count later | `recovery_codes_remaining` is the warning that arrives too late otherwise. |

<Warning>
If you offer a "remind me later" option, it must not pretend the codes can be retrieved. There is no endpoint that returns them. The honest options are: they saved them, or they need to enrol again.
</Warning>

### The challenge prompt

One field, because both methods are accepted by the same endpoint.

| Element | Notes |
| --- | --- |
| A single code input | Accepts a six-digit TOTP code or a hyphenated recovery code. |
| Label | Should not say "enter your authenticator code" — that excludes recovery-code users. |
| A recovery-code affordance | A link explaining that they can use a saved code instead. |
| No `autocomplete` guessing | Do not let a browser offer to fill this in. |

<Warning>
The replay protection means a user who submits a valid code twice sees the second one rejected. If your form allows resubmission, make the error message distinguish this case — "that code was already used, wait for the next one" saves a support ticket that "invalid code" reliably generates.
</Warning>

### Clock skew, from the user's side

TOTP depends on the device clock agreeing with the server. Roughly thirty seconds of drift in either direction is tolerated, so ordinary clock drift is not a problem — but a device whose clock is badly wrong is.

| Symptom | Likely cause |
| --- | --- |
| Codes rejected while the server's own codes work | The phone's clock is wrong. |
| Codes rejected intermittently | Timezone confusion, or a device that has been offline. |
| Codes accepted, then immediately rejected | Replay protection, after a double submit. |

<Info>
If a whole class of users reports invalid codes, check the clock before suspecting the secret. The tolerance window exists precisely so that normal clock differences do not matter, which means a failure means the difference is not normal.
</Info>

## Worked examples

### A first sign-in with MFA

The user posts their email and password. The credentials are correct, and the account has MFA on.

No session is issued. A challenge comes back carrying a token valid for five minutes, recording that this was a password sign-in. The user types the six-digit code from their app. The grant `mfa` is sent with that code.

The code matches a window the factor has not consumed, so the step is recorded and the token spent. A session is created with the original method — `password` — and `aal2`, because a second factor was presented. The response carries `mfa_method: "totp"`.

The sign-in history records the challenge, the verification, and the session.

### Signing in with a recovery code

Identical, except the user types `a3f9c-2e1d4` instead.

The TOTP check fails — it is not six digits — so the recovery check runs. The code normalises, hashes, and matches an unused row. The conditional update marks it used and succeeds, so the challenge is satisfied.

The session is the same, at `aal2`, with `mfa_method: "recovery_code"`. `recovery_codes_remaining` is now one lower, and a recovery-code user who has just used their last code should be prompted to enrol a new authenticator.

### A user who enrolled on their phone and then lost it

They have their recovery codes. The sign-in challenge accepts one, and they are in.

They can then enrol a new factor, which deletes the old one and produces a fresh set of recovery codes.

### A user who lost the phone and the codes

Neither path works. No code can be produced, and the codes cannot be regenerated — that requires a TOTP code, precisely to stop a stolen session doing it.

**This is the one situation MFA cannot resolve, and it is why the administrative reset exists.** An administrator uses **Reset MFA** on the user in Studio, which deletes the factor and the codes and clears the flag. The user signs in with one factor and enrols again.

<Warning>
Design your support process around this case explicitly, because it will happen and it is indistinguishable from an attacker with a stolen session. That ambiguity is inherent to any second factor, and resolving it is an identity-verification decision, not a technical one.
</Warning>

### Enrolling while already signed in

The user is signed in at `aal1` and enrols an authenticator app. Confirmation marks the account as having MFA and elevates the current session to `aal2`.

Their existing access token still says `aal1`, because it was minted before the elevation. Their next refresh produces tokens carrying `aal2`, and a policy requiring `aal2` starts passing.

<Info>
If your application checks its own session's `aal` from a cached token rather than from the API, it will keep reporting the old level until it refreshes. `GET /auth/v1/mfa` is the authoritative answer at any moment.
</Info>
