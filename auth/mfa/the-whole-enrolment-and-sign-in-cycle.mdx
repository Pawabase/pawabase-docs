The sequences in one place, because the individual endpoints are clearer once you have seen them end to end.

### Enrolling, from the user's point of view

```text
  signed in at aal1
        |
        |  POST /mfa/totp/enroll
        v
  factor_id, secret, otpauth_uri          <- shown once; never returned again
        |
        |  the user scans the QR code into their app
        v
  they read a 6-digit code from the app
        |
        |  POST /mfa/totp/verify   {code}
        v
  {enabled: true, recovery_codes: [...]}   <- shown once; never returned again
        |
        |  the user saves the codes somewhere durable
        v
  session elevated to aal2, mfa_enabled set
```

Two responses in that sequence contain credentials the user will never be able to obtain again: the secret and the recovery codes. Everything else is retrievable or derivable.

<Warning>
If your application logs responses, both of those responses must be excluded. A structured logger that captures bodies at debug level will persist the secret and the codes, and neither can be rotated retroactively without invalidating every enrolled user.
</Warning>

### Signing in, when MFA is on

```text
  POST /token  {grant_type: password, email, password}
        |
        |  credentials check out; account has MFA; no session is issued
        v
  {mfa_required: true, mfa_token: "...", factors: [totp, recovery_code]}
        |
        |  the user types either a 6-digit code or one recovery code
        v
  POST /token  {grant_type: mfa, mfa_token, code}
        |
        |  code verified; challenge consumed; session created
        v
  the token response at aal2, plus mfa_method
```

### Signing in, when MFA is off

```text
  POST /token  {grant_type: password, email, password}
        |
        v
  the token response at aal1
```

No challenge, no second round trip. The difference between these two diagrams is the entire observable effect of a user's MFA enrolment on the sign-in flow.

### Locking yourself out with MFA

The lockout mechanism is shared with passwords, which surprises people who assume a second factor deserves its own budget.

```text
  wrong password x N   ──┐
  wrong MFA code x N  ──┼──>  failed_logins increments
                        │    at the threshold the account locks
                        │    for lockout_minutes
                        v
  429 too many failed attempts; try again later
```

The counters are per account and the thresholds are installation settings, not per-environment ones. A user who mistypes their authenticator repeatedly can lock themselves out exactly as they could by mistyping their password, and an administrator's MFA reset does not clear the lockout — only the expiry or a successful sign-in does.

<Warning>
Recovery from a lockout caused by MFA confusion is not achieved with **Reset MFA**. That removes the factor and the codes but leaves the account locked. Wait for the lockout to expire, or clear it administratively.
</Warning>

<Info>
The rate limit on the MFA endpoints is a second, independent brake: ten requests per minute. It bounds how fast codes can be guessed per caller without the account being locked at all, which is what makes the forty-bit recovery codes safe against online guessing.
</Info>

### What an administrator can and cannot do

The admin surface is deliberately narrow.

| Action | Available | Effect |
| --- | --- | --- |
| See whether MFA is on | yes | In the user modal. |
| Reset MFA | yes | Deletes the factor and codes, clears the flag. |
| See a user's recovery codes | no | Hashed, one-way. |
| Enrol on a user's behalf | no | There is no route for it. |
| Set a user's assurance level | no | It follows from the factor. |
| Revoke a user's sessions | yes | Separate action, and the real fix after a reset. |

<Warning>
An administrator resetting MFA does not revoke that user's sessions, and does not clear a lockout. If you are responding to a suspected compromise, reset the factor **and** revoke their sessions **and** wait out or clear the lockout. See [Managing users](/auth/managing-users/overview).
</Warning>

### Answering the questions people ask

**Can I move my authenticator to a new phone?**
Yes, by enrolling again. The new enrolment deletes the old factor and issues a fresh secret and codes. There is no transfer endpoint.

**Does enrolment need a password?**
No. It needs a signed-in session. Because confirming enrolment requires producing a code from the new secret, the proof of the second factor is the enrolment itself.

**Can I have MFA without a password?**
Yes. An account created socially or by an administrator can enrol. That is the normal shape for a social-only account.

**Why is my session still aal1 after a refresh?**
It should not be. If it is, the session row's level was never elevated — which happens when the enrolment confirmation ran without a live session, or the account's flag and factor disagree. Check `GET /auth/v1/mfa`.

**Can I disable MFA for someone else?**
You can reset it, which is not the same as disabling: reset clears the flag and deletes the factor, so the account is left without MFA and able to enrol again. There is no separate administrative disable.

**Why does my recovery code work when I mistyped it?**
It does not. Recovery codes are hashed, so a mistyped code produces a different hash and fails. What is forgiving is the hyphen and the case, because both are normalised away before hashing.

### Data you can inspect

When diagnosing an MFA problem, these are the columns that answer the question, in the order worth checking.

| Question | Column | Where |
| --- | --- | --- |
| Is the account flagged? | `AuthUser.mfa_enabled` | `akz_users` |
| Does a factor exist? | `MfaFactor` rows for the user | `akz_mfa_factors` |
| Is it confirmed? | `confirmed_at` | `akz_mfa_factors` |
| Has a code been replayed? | `last_used_step` | `akz_mfa_factors` |
| How many codes are left? | Unused `RecoveryCode` rows | `akz_recovery_codes` |
| Has a code been spent? | `used_at` | `akz_recovery_codes` |
| What level is the session at? | `SessionInfo.aal` | `akz_sessions` |

```sql
-- Everything about one account's MFA state in one result.
SELECT
  u.email,
  u.mfa_enabled,
  f.confirmed_at,
  f.last_used_step,
  (SELECT count(*) FROM akz_recovery_codes c
    WHERE c.user_id = u.id AND c.used_at IS NULL) AS codes_left
FROM akz_users u
LEFT JOIN akz_mfa_factors f ON f.user_id = u.id
WHERE u.project = 'acme' AND u.env = 'production'
  AND u.email = 'ada@example.com';
```

<Warning>
`secret_ciphertext` is encrypted. Selecting it into a log, a terminal, or a support ticket leaks a live credential — anyone with the secret can generate valid codes until the factor is replaced. Select only the boolean and timestamp columns above.
</Warning>

### Consistency, and the states you can find

The flag, the factor and the codes are maintained by code rather than by a constraint, so it is worth knowing which inconsistent states are reachable and what each means.

| State | What it means | What to do |
| --- | --- | --- |
| Flag false, no factor, no codes | Normal. Never enrolled. | Nothing. |
| Flag true, confirmed factor, ten unused codes | Normal, healthy. | Nothing. |
| Flag true, factor unconfirmed | Should not persist. An abandoned enrolment. | Re-enrol; the pending factor is replaced. |
| Flag true, no factor | Reachable transiently; sign-in would challenge with nothing to verify. | Disable and re-enrol, or reset. |
| Flag false, factor present | Reachable after a partial failure. Not challenged at sign-in. | Re-enrol to restore, or leave it if MFA is intentionally off. |
| Flag true, no unused codes | Possible after ten failed or burnt recoveries. | Warn the user; they can still regenerate with a TOTP code. |

<Info>
In practice the interesting state is the second-to-last: an account with MFA flagged on and no codes left. It still signs in with a working authenticator, but a single lost phone ends it. Surfacing a warning at that threshold is the reason `recovery_codes_remaining` exists.
</Info>

### Rate limits in detail

MFA endpoints sit under a tighter bucket than the general auth endpoints, for the obvious reason that a code is guessable.

| Bucket | Limit | Window | Endpoints |
| --- | --- | --- | --- |
| `akz:mfa` | 10 | 60 seconds | `/mfa/totp/verify`, `/mfa/disable`, `/mfa/recovery-codes` |
| `akz:auth` | 30 | 60 seconds | `/token`, including the `mfa` grant |
| `akz:links` | 10 | 60 seconds | Endpoints that send email |

<Warning>
Because the `mfa` grant goes through `/token`, an attempt to brute-force a code is subject to both buckets — ten per minute on the MFA limit and thirty on the auth limit. With forty bits of entropy in a recovery code and six digits in a TOTP code, neither budget is a meaningful attack surface over the short term.
</Warning>

### Why six-digit codes are still safe here

A TOTP code is six digits, which is about twenty bits of entropy, and that number deserves a moment of scepticism.

The safety does not come from the entropy. It comes from three properties of the design:

| Property | Effect |
| --- | --- |
| The code changes every 30 seconds. | An attacker has one shot per window, and must know the time. |
| The last accepted step is recorded. | A guess that succeeds cannot be retried, and a correct guess is consumed. |
| Repeated failures lock the account. | A sustained attack costs the attacker the account. |

An attacker who guesses correctly gets one `aal2` session and then triggers the lockout. In practice the lockout is what stops the attack, not the entropy.

<Info>
This is also why disabling replay protection would be a serious regression: it would let an observer who saw a single code replay it inside its window, and it would quietly weaken the lockout's value by making each attempt a coin flip rather than a single-shot.
</Info>

### Client integration, end to end

The sequence in code, because the two-response enrolment is the part that gets built wrong.

```text
// Enrolling. The session must already exist.
const start = await fetch("/auth/v1/mfa/totp/enroll", {
  method: "POST",
  headers: authHeaders(),
});

// The secret exists only in this response. Render it, then let it go.
renderQrCode(start.otpauth_uri);
showSecretForManualEntry(start.secret);

const confirmed = await fetch("/auth/v1/mfa/totp/verify", {
  method: "POST",
  headers: { ...authHeaders(), "content-type": "application/json" },
  body: JSON.stringify({ code: enteredCode }),
});

// These ten codes exist only in this response. Block until acknowledged.
await showRecoveryCodes(confirmed.recovery_codes, { downloadable: true });
```

```text
// Signing in. The MFA branch is a 200, not an error.
const res = await fetch("/auth/v1/token", {
  method: "POST",
  headers: { ...contextHeaders(), "content-type": "application/json" },
  body: JSON.stringify({ grant_type: "password", email, password }),
});
const body = await res.json();

if (body.mfa_required) {
  // Both a TOTP code and a recovery code are accepted by the same call.
  const code = await promptForAnyFactor(body.factors);
  const done = await fetch("/auth/v1/token", {
    method: "POST",
    headers: { ...contextHeaders(), "content-type": "application/json" },
    body: JSON.stringify({ grant_type: "mfa", mfa_token: body.mfa_token, code }),
  });
  storeSession(await done.json());
} else {
  storeSession(body);
}
```

| Decision | Why |
| --- | --- |
| Treat `mfa_required` as a branch, not a failure. | It is a `200` with correct credentials. |
| One input for both factor types. | `factors` lists both; the endpoint accepts both. |
| Block on the recovery codes. | They are not retrievable. |
| Never log either enrolment response. | Both contain one-time credentials. |
| Read the level from the API when it matters. | A cached token may predate an elevation. |

<Warning>
When using raw HTTP, `storeSession` is yours to write, including refresh storage and replay. The
TypeScript SDK manages that session lifecycle; the Python SDK does not expose user auth. See
[Client integration](/auth/client-integration/overview) for the wire behavior.
</Warning>

### Enrolment without JavaScript

Not every application has a browser. The same three requests work from anything that can make HTTP calls, with the secret rendered as text rather than a QR code.

```bash
# Enrol. Read the secret from the response.
curl -sX POST "$BASE/auth/v1/mfa/totp/enroll" -H "Authorization: Bearer $TOKEN"

# Confirm with a code the authenticator app produces.
curl -sX POST "$BASE/auth/v1/mfa/totp/verify" \
  -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"code":"123456"}'
```

The second response is where the recovery codes come from, and in a non-browser context there is no one to show them to. Store them in the caller's secret store immediately, because that is the only copy.

<Info>
An account that has a factor but no saved recovery codes is materially weaker than one that has both, and there is no reminder mechanism that will reach a user who never saw them. If your enrolment flow can be automated, store the codes as part of the flow rather than leaving them to a person.
</Info>

### Migrating an existing deployment to MFA

The order that avoids locking anyone out, given that enrolment is entirely voluntary.

| Consideration | Guidance |
| --- | --- |
| MFA is off by default per environment | Nothing breaks by enabling the switch. |
| Enrolment is voluntary | Enabling `mfa_enabled` does not challenge anyone who has not enrolled. |
| Existing sessions are unaffected | Their level stays `aal1`; nothing is invalidated. |
| Policies are the enforcement point | Add `aal2` requirements only after users have had a chance to enrol. |

<Warning>
The order matters: turning on a policy that requires `aal2` before your users can enrol will lock out everyone who has not. The switch, the enrolment surface, and then the policy — in that order, with time in between.
</Warning>

### Verifying the setup

Two checks confirm MFA is wired correctly, and both are quick.

```bash
# 1. Enrol, confirm, and check the status. Codes should read 10, then 9 after one is spent.
curl -s "$BASE/auth/v1/mfa" -H "Authorization: Bearer $TOKEN"

# 2. Sign out, sign in, and confirm a challenge comes back rather than a session.
curl -sX POST "$BASE/auth/v1/token" \
  -H 'content-type: application/json' \
  -d '{"grant_type":"password","email":"ada@example.com","password":"..."}'
```

| What the checks tell you | Good result |
| --- | --- |
| Enrolment completed | `enabled: true`, `aal: "aal2"`, ten codes left. |
| The challenge fires | `mfa_required: true` on a fresh sign-in. |
| A code is accepted | A token response at `aal2`, with `mfa_method`. |
| A recovery code is accepted | The same, with `recovery_codes_remaining` decremented. |
| Replay is refused | The same code fails on a second attempt. |

<Info>
Testing the replay refusal is worth doing once, deliberately. It is the property most likely to surprise a user later, and knowing it works means the error message you wrote for it will not be the first time you see it.
</Info>

### Sign-in events, in detail

The login history is the only place the MFA story of a sign-in is recorded end to end, and the three events it writes are worth distinguishing.

| Event | Written when | Success value | Reason on failure |
| --- | --- | --- | --- |
| `mfa_challenge` | A challenge is issued instead of a session. | — | — |
| `mfa_verify` | A challenge is answered. | true or false | `wrong code` |
| `sign_in` | The session is created. | true | as usual |

A single MFA sign-in therefore produces three rows: a challenge, a verification, and a sign-in. Reading them in order tells you the whole story, including whether the code was accepted first time.

<Info>
The `mfa_verify` failure reason is always `wrong code`, regardless of whether the code was wrong, replayed, or already spent. That is deliberate — see [Endpoint reference](/auth/mfa/endpoint-reference#errors).
</Info>

### Recovery codes as an operational signal

The count of unused codes is a better health metric for an account than the binary "has MFA", and it is cheap to expose.

| Count | What it suggests |
| --- | --- |
| 10 | Enrolled, no codes used. |
| 6–9 | Normal attrition. |
| 2–5 | Worth prompting the user to regenerate. |
| 1 | The account is one lost phone from an outage. |
| 0 | Still signable with the authenticator, but no fallback exists. |

```bash
curl -s "$BASE/auth/v1/mfa" -H "Authorization: Bearer $TOKEN" | python3 -c "import json,sys; print(json.load(sys.stdin)['recovery_codes_remaining'])"
```

<Warning>
Prompting a user to regenerate requires a TOTP code, so the prompt cannot be sent from a background job with no user present. It has to be a nudge inside the application, triggered by the count the status endpoint reports.
</Warning>

### Comparing the two storage strategies once more

Because the asymmetry is the most frequently questioned design decision on this page, it is worth stating the reasoning in its simplest form.

A recovery code's only job is to answer one question: *does this submitted string match a code this user holds?* That is a comparison, and a comparison can be performed against a hash. Nothing ever needs the original back.

A TOTP secret's job is different: it must *produce* the code that the user's device is showing. That is generation, not comparison, so the original must be recoverable, and hashing makes it impossible.

| Need | Storage | Consequence of the choice |
| --- | --- | --- |
| Compare submitted codes | Hash | Codes are unrecoverable by design. |
| Generate codes | Encrypt | The secret must be decryptable. |

<Info>
If you are ever asked to "add a way to see the recovery codes", the answer is that no such way can exist without storing them reversibly, which would make the table a liability equal to the password table. The product answer is the administrative reset, not a lookup.
</Info>

### The three questions to have answered before shipping

A short checklist, because MFA is the feature most often shipped with one of these wrong.

| Question | If you cannot answer it |
| --- | --- |
| Where does the user see their recovery codes, and can they dismiss without saving them? | They will lose them. Make the screen blocking. |
| What does your app show when a code is rejected? | "Invalid code" generates tickets for replayed codes. Distinguish them. |
| What is the path when a user loses both factors? | Without one, they contact you and someone improvises. Decide it deliberately. |

The third is the one most teams defer, and it is the one that determines whether a lost phone is a two-minute support interaction or an outage.

### What happens when the environment turns MFA off

A scenario worth walking through, because the behaviour is non-destructive and people expect it to be destructive.

```text
  environment has mfa_enabled = true
  Ada is enrolled, has a factor and ten codes, signs in at aal2
        |
        |  an administrator turns MFA (TOTP) off
        v
  Ada's next sign-in returns a session directly, at aal1
  her factor is untouched
  her recovery codes are untouched
  her existing aal2 sessions continue at aal2 until they end
        |
        |  the administrator turns MFA back on
        v
  Ada is challenged again, at her next sign-in
  her factor is still the one she enrolled
  nothing had to be re-enrolled
```

| Thing | Affected by turning MFA off |
| --- | --- |
| Enrolment | Refused, with `403 MFA is disabled for this project`. |
| Sign-in challenge | Not issued, even for enrolled users. |
| Existing factors | Untouched. |
| Existing recovery codes | Untouched. |
| Existing sessions | Untouched, including their assurance level. |
| Turning it back on | Everything resumes as it was. |

<Info>
This is what makes the switch safe to use as a temporary measure during an incident — you can stop requiring a second factor without destroying anyone's ability to use one.
</Info>

### What happens when the environment turns MFA on

The mirror image, and equally unintrusive.

| Situation | Result after enabling |
| --- | --- |
| User never enrolled | Not challenged. Signs in at `aal1` exactly as before. |
| User is enrolled | Challenged at the next sign-in. |
| User is mid-sign-in | Depends on the config cache; the current attempt may complete without a challenge. |
| User has a live session | Unaffected until it ends or refreshes. |

<Warning>
Because each environment's configuration is cached for a short window, turning MFA on does not take effect instantly. A sign-in in the seconds immediately after saving may complete without a challenge, which makes this look unreliable when testing. See [Authentication configuration](/auth/configuration/overview).
</Warning>

### Enrolling in one environment does not enrol in another

The tenancy rule applied to MFA, and worth stating because it surprises people who have enrolled once and then deploy.

| Environment | Ada's MFA state |
| --- | --- |
| `acme/production` | Enrolled, factor and codes present. |
| `acme/staging` | Nothing. She is not enrolled. |
| `acme/development` | Nothing. |

Factors and codes belong to an account in one `project` + `env` pair, because the account itself does. Promoting an environment between staging and production promotes **configuration** — including whether MFA is enabled — but never users, and therefore never their factors.

<Info>
The practical consequence for a launch checklist: if you require `aal2` by policy in production, every user must enrol there too. There is no way to carry a factor across from staging, and no reason to expect one to.
</Info>

<AccordionGroup>
  <Accordion title="Why does my code get rejected immediately after a successful one?">
    Replay protection. The time step the code belonged to has been recorded on the factor, and any step at or below it is refused. Wait for the next 30-second window and use the new code. If your form allows resubmission, say this in the error message rather than reporting an invalid code.
  </Accordion>
  <Accordion title="Can I use the same secret on two phones?">
    Yes — enrol once, then enter the secret manually on the second device. But do not run a second enrolment: confirming one deletes the other factor and issues a new secret, so the first phone stops working.
  </Accordion>
  <Accordion title="Why does enrolment return codes instead of asking me to set a password?">
    Enrolment is an account-level setting, not a sign-in method. The account may already have a password, or may be social-only, or may have been created by an administrator. Adding a second factor does not change any of that.
  </Accordion>
  <Accordion title="Does the MFA reset in Studio revoke sessions?">
    No. It deletes the factor and the recovery codes and clears the account's flag. Sessions that already exist keep working, including at `aal2`. If you are responding to a compromise, revoke their sessions separately.
  </Accordion>
</AccordionGroup>

### Every error, and what it means

The complete set, grouped by which layer produced it.

**From the challenge lifecycle.**

| Status | Detail | Meaning | Response |
| --- | --- | --- | --- |
| 400 | `mfa_token and code are required` | The `mfa` grant arrived incomplete. | A client bug. |
| 400 | `the challenge is no longer valid` | The account was deleted or disabled after the challenge was issued. | Restart the sign-in. |
| 400 | `the code is not valid` | Wrong, replayed, expired challenge, or spent code. | Let them try the next code. |

**From enrolment.**

| Status | Detail | Meaning | Response |
| --- | --- | --- | --- |
| 403 | `MFA is disabled for this project` | `mfa_enabled` is off. | Hide the enrolment surface. |
| 400 | `the code is not valid` | The confirmation code did not match. | The secret or the clock is wrong. |

**From the code-management routes.**

| Status | Detail | Meaning | Response |
| --- | --- | --- | --- |
| 400 | `a current authenticator code is required` | A recovery code was used where a TOTP code is required. | Ask for the authenticator code. |
| 400 | `the code is not valid` | The supplied code failed. | Ask for a fresh one. |

**From the session layer, affecting MFA like everything else.**

| Status | Detail | Meaning |
| --- | --- | --- |
| 401 | `sign in first` | No usable session on a route that needs one. |
| 401 | `the account is not available` | The account is disabled or gone. |
| 429 | `too many failed attempts; try again later` | The account is locked out. |

<Info>
Every one of these is a `detail` string rather than a machine-readable code, so branch on the status and treat the detail as diagnostic rather than as a branch condition. That is the opposite of the OAuth flow, where stable codes travel in the fragment precisely so a client can branch on them.
</Info>

### Response shapes, complete

Every MFA response in one place, so nothing has to be guessed.

```json
{ "factor_id": "01HQ...", "secret": "JBSWY3DPEHPK3PXP", "otpauth_uri": "otpauth://totp/..." }
```

```json
{ "enabled": true, "recovery_codes": ["a3f9c-2e1d4", "..."] }
```

```json
{ "enabled": false }
```

```json
{ "recovery_codes": ["a3f9c-2e1d4", "..."] }
```

```json
{ "enabled": true, "aal": "aal2", "recovery_codes_remaining": 10 }
```

```json
{ "mfa_required": true, "mfa_token": "...", "factors": ["totp", "recovery_code"] }
```

| Response | From | Contains a one-time secret |
| --- | --- | --- |
| Enrolment | `/mfa/totp/enroll` | **yes** — the TOTP secret |
| Confirmation | `/mfa/totp/verify` | **yes** — the recovery codes |
| Disable | `/mfa/disable` | no |
| Regenerate | `/mfa/recovery-codes` | **yes** — a new set of codes |
| Status | `/mfa` | no |
| Challenge | `/token` (password grant) | **yes** — the challenge token |

<Warning>
Three of the six responses carry a credential that exists exactly once. Any logging, error reporting or session-replay tool that captures response bodies will retain them permanently, and neither the secret nor the codes can be rotated for one user without affecting them.
</Warning>

### The fields that matter, in one table

A final consolidation, for readers who want the whole surface without the prose.

| Field | Where | Type | Notes |
| --- | --- | --- | --- |
| `enabled` | Most responses | bool | The account's MFA flag. |
| `aal` | Status, token response | str | `aal1` or `aal2`. |
| `recovery_codes` | Confirmation, regeneration | list[str] | Ten codes, plain text, once. |
| `recovery_codes_remaining` | Status | int | Unused rows. |
| `factor_id` | Enrolment | str | The factor's ULID. |
| `secret` | Enrolment | str | The TOTP secret, once. |
| `otpauth_uri` | Enrolment | str | Render as a QR code. |
| `mfa_required` | Challenge | bool | Always true in that response. |
| `mfa_token` | Challenge | str | Valid five minutes. |
| `factors` | Challenge | list[str] | Both methods are always listed. |
| `mfa_method` | Token response | str | Which method satisfied the challenge. |
| `code` | Request bodies | str | Six to thirty-two characters. |

<Info>
Every field above is real and every one is documented here. There is no enrolment token, no factor list endpoint, no backup-code regeneration key — the surface is these routes and these fields.
</Info>

### One-time token lifetimes, for comparison

The challenge is the shortest-lived of the one-time tokens, which reflects how it is used.

| Purpose | Lifetime |
| --- | --- |
| `mfa` | 300 seconds |
| `link` | 600 seconds |
| `magic` | 900 seconds |
| `recovery` | 3600 seconds |
| `verify`, `email_change` | 24 hours |
| `invite` | 7 days |

<Info>
The MFA challenge is short because it is answered immediately. A magic link at fifteen minutes and a recovery link at an hour exist because people find those in an inbox minutes or hours later; nobody leaves a code prompt open for five minutes and comes back to it.
</Info>
