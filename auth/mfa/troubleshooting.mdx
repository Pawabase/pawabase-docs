MFA problems are few and each has one real cause, so the table is short and worth reading in full.

| Symptom | Cause | Fix |
| --- | --- | --- |
| `the code is not valid`, code is right | Already consumed by an earlier attempt. | Wait for the next 30-second window. |
| `the code is not valid`, always | The device clock is wrong. | Correct the device's time. |
| `the code is not valid`, on one device only | That device has not been given the current secret. | Re-enrol; the old factor is deleted. |
| `the code is not valid`, code copied from the confirmation screen | Those were recovery codes, not an authenticator code. | Use the authenticator app for TOTP. |
| `a current authenticator code is required` | A recovery code was used to regenerate. | Supply a TOTP code. |
| `MFA is disabled for this project` | `mfa_enabled` is off in that environment. | Turn **MFA (TOTP)** on in the Configuration tab. |
| User is never challenged | Their `mfa_enabled` flag is false, or the environment's is off. | Check `GET /auth/v1/mfa`. |
| Challenge expires | Five minutes elapsed. | Start the sign-in again. |
| `429 too many failed attempts` | The account's lockout threshold was hit. | Wait out the lockout, or an administrator clears it. |
| Codes rejected for a whole team | Device clocks, or a misconfigured environment. | Check `mfa_enabled` and the users' clocks. |
| Nothing happens after confirming enrolment | A code was submitted twice and the second was a replay. | Use the next code. |

<Warning>
If a user cannot recover with either factor, the support path is **Reset MFA** in Studio. Nothing else in the product will produce a working code for them, and no amount of retrying with the same secret will change that.
</Warning>

<AccordionGroup>
  <Accordion title="Can I see a user's recovery codes?">
    No. Only the hashes are stored, and they cannot be reversed. This is the intended design — an administrator with database access gains nothing from the recovery codes. The only ways forward are the user spending one, or an administrator resetting MFA.
  </Accordion>
  <Accordion title="Can a user have two authenticator apps?">
    Not through the normal flow. Confirming an enrolment deletes any other factor for that account, so an account has exactly one. A user who wants the same secret on two devices should enrol once and enter the secret manually on the second device — the secret is shown at enrolment for exactly this.
  </Accordion>
  <Accordion title="Does an MFA challenge work across environments?">
    No. The challenge token is bound to one project and environment, and it names a user in that environment. A challenge issued in staging cannot be completed against production.
  </Accordion>
  <Accordion title="Why is my aal still aal1 after enrolling?">
    Because the token you are holding was issued before the elevation, and tokens are immutable. Refresh and it will be `aal2`. `GET /auth/v1/mfa` reports the session's actual level at any moment.
  </Accordion>
  <Accordion title="Does turning mfa_enabled off delete anything?">
    No. It stops enrolment and stops the sign-in challenge. Factors and recovery codes remain, and turning it back on restores them. The way to actually delete them is for the user to disable MFA, or for an administrator to reset it.
  </Accordion>
</AccordionGroup>

## How MFA interacts with the other sign-in methods

MFA is not tied to passwords. Whichever way a person authenticates, the same challenge comes back and the same code satisfies it.

| Sign-in method | Challenged? | Session method | Reaches `aal2` |
| --- | --- | --- | --- |
| Password | yes | `password` | via the challenge |
| Magic link | yes | `magic_link` | via the challenge |
| Social | yes | `oauth:<provider>` | via the challenge |
| Email verification | no | `email_verification` | no — it is not a sign-in method users return from |
| Password recovery | no | `recovery` | no, but the flow has already proven email control |

The last two rows are worth reading twice. Confirming an email address issues a session, and resetting a password issues a session, but neither challenges for a second factor. A user who resets their password from an email link is signed in without one.

<Warning>
That is worth understanding before you rely on `aal` as a guarantee. A user who used a recovery link has a session at `aal1`, because proving control of an email inbox is the only factor checked. If an operation must require `aal2`, a policy on the claim is the enforcement point — not the assumption that reaching the account implies a second factor.
</Warning>

Social sign-in deserves particular mention: a social sign-in that returns `mfa_required` does so **through the URL fragment**, like any other social result, so a browser-based client has to handle the MFA branch in its callback page. See [Social login](/auth/social-login/overview).

### Where MFA sits relative to email verification

The two are independent, and the order they are checked in at sign-in is fixed.

| Check | When | Failure |
| --- | --- | --- |
| Credentials | First. | `invalid email or password` |
| Disabled account | Second. | `403 this account is disabled` |
| Email verification | Third. | `403 confirm your email address first` |
| MFA challenge | Last. | Returns `mfa_required`. |

Verification is checked before MFA, so an unverified user in an environment that requires it is told to confirm their address and never sees a code prompt. That ordering is deliberate: there is no point asking for a second factor from someone whose first factor is not yet trusted.

### What the assurance level does not mean

`aal2` means one thing: a second factor was presented during this session's authentication, or during enrolment on it. It is worth being precise about what that does not imply, because the name suggests more assurance than it delivers.

| `aal2` implies | `aal2` does not imply |
| --- | --- |
| A TOTP code or a recovery code was accepted. | The account's email address is verified. |
| The session is more than single-factor. | The person is the account's owner in any stronger sense. |
| Recovery codes cannot be regenerated without the authenticator. | The device holding the authenticator is trustworthy. |
| Elevated sessions will keep the level until they end. | The session will be revoked if the factor is later removed. |

The first row is the one that catches people. A user can reach `aal2` with an unverified email address, because the MFA challenge does not check verification. If an operation needs both, the policy has to require both.

| Second factor removed | Effect on a live `aal2` session |
| --- | --- |
| The user disables MFA | The session keeps `aal2` until it expires or is revoked. |
| An administrator resets MFA | Same. The account's flag is cleared; existing sessions are untouched. |

<Warning>
MFA reset removes the account's ability to verify itself, but it does not end sessions that already exist at `aal2`. If you need those gone, revoke the user's sessions as a separate action. See [Tokens and sessions](/auth/tokens-and-sessions).
</Warning>

### Requiring a second factor in a policy

Because there is no configuration directive for it, this is where the requirement actually lives. The condition reads the `aal` claim, which is present on every user token.

```json
{
  "conditions": [
    { "fact": "aal", "operator": "equals", "value": "aal2" }
  ]
}
```

| Deployment shape | How to express it |
| --- | --- |
| Some operations need a second factor. | Require `aal2` on those routes only. |
| Everything needs it. | Require `aal2` globally — a user who has not enrolled cannot do anything. |
| High-risk records only. | Require `aal2` on those tables' routes. |

<Warning>
Requiring `aal2` globally in an environment where enrolment is optional locks out every user who has not enrolled, with no error explaining why. If you go that way, make sure your application offers enrolment and explains the requirement, or you will generate support tickets with no diagnostic in the logs.
</Warning>

See [Auth in policies](/auth/auth-in-policies/overview) and [Conditions](/policies/conditions) for the full vocabulary.

### Storage and its consequences

Two fields, two storage strategies, and the reasoning behind each. This is the part of MFA that matters if you ever need to reason about a breach.

| | TOTP secret | Recovery code |
| --- | --- | --- |
| Storage | Encrypted at rest with the platform secret box. | SHA-256 hash. |
| Recoverable? | Yes, by decrypting. | No. |
| Randomness per value | 160 bits. | 40 bits. |
| Why | Must be able to recompute a code from it. | Only ever compared, never recomputed. |
| Blast radius of a leak | An attacker who can decrypt can generate valid codes. | An attacker learns nothing useful. |

The entropy difference is the important part. A recovery code has five bytes of randomness, which is far too little to brute-force *forwards* through SHA-256 in any practical sense against a rate-limited interface — but note the qualifier: forwards. The reason one-way hashing is safe here is that the check is a lookup of the submitted code's hash against stored hashes, not an attempt to invert the stored ones.

<Info>
This is the ordinary argument for hashing high-entropy secrets, and it is the reason the recovery code table is not a liability in the way the TOTP table is. If you are ever tempted to "decrypt" a recovery code for support purposes, that is the wrong instinct — it is not encrypted and never was.
</Info>

### Sessions at each level

A table of what a session looks like at each level, since the difference is mostly in claims and the session row.

| Aspect | `aal1` | `aal2` |
| --- | --- | --- |
| Claim | `"aal": "aal1"` | `"aal": "aal2"` |
| Session row `aal` | `aal1` | `aal2` |
| How it was reached | Any single-factor sign-in | A completed challenge, or enrolment |
| Extra token field | — | `mfa_method`, on the response that created it |
| Refresh keeps it | yes | yes |
| Revocable | yes | yes |

<Warning>
Refresh preserves the assurance level by reading it from the stored session, which means an `aal2` session stays `aal2` for its whole life — up to `refresh_ttl`, thirty days by default. Revocation is the only way to end it early.
</Warning>
