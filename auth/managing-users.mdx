Administering users in Pawabase means acting on an account in **one project and
one environment**. Every admin route takes the environment from its path, and
every user lookup is scoped by it. An account in `acme/production` is a different
row from the same address in `acme/staging`, and no admin operation crosses that
boundary.

That single rule explains most of the confusing results. "The user does not exist"
usually means they do not exist *in that environment*.

Two further things to know before you start, because they shape what the controls
actually do:

**Disable and delete are very different.** Disabling keeps the account and its
history and revokes its sessions; it can be undone. Deleting is a soft delete that
rewrites the email address to free it for re-use, and it removes factors and
linked identities. They are not two strengths of the same action.

**Administrative actions are not instant for existing sessions.** A revoked or
disabled user's access tokens keep working until they expire, because services
verify signatures locally. New sign-ins and all refreshes are blocked immediately.

## The admin routes

All of them live under `/projects/{project}/envs/{env}` and all of them require a
service token. Studio calls them with its own management key.

| Route | Method | Purpose |
| --- | --- | --- |
| `/users` | GET | Search and list users |
| `/users` | POST | Create a user |
| `/users/{user_id}` | GET | One user, with their active sessions |
| `/users/{user_id}` | PATCH | Update, verify, disable, unlock, set password |
| `/users/{user_id}` | DELETE | Delete a user |
| `/users/{user_id}/sessions/revoke` | POST | Sign out everywhere |
| `/users/{user_id}/sessions/{session_id}` | DELETE | End one session |
| `/users/{user_id}/mfa/reset` | POST | Remove a user's second factors |
| `/users/{user_id}/history` | GET | A user's sign-in history |
| `/users/{user_id}/permissions` | POST | Grant direct permissions |
| `/users/{user_id}/permissions` | DELETE | Revoke direct permissions |

There is also a context-scoped variant, `GET /users/{user_id}`, which takes the
environment from the request context rather than the path — the form another
Pawabase service uses.

<Warning>
Every route here requires a service token, and none of them are scoped. A
credential that can reach these routes can create and delete users, reset MFA and
change roles. Treat it as full administrative access to the environment's
identities, store it in a secret manager, and rotate it when someone leaves.
</Warning>
## Listing and searching users

`GET {base}/users` returns `{"data": [...], "total": N}`. Every row is a full
**admin** view of the user, which is a superset of what the user sees about
themselves.

| Query parameter | Effect |
| --- | --- |
| `search` | Case-insensitive match against **email**, **username** or **name** |
| `status` | `disabled` for accounts with a disable timestamp; `unverified` for those with no verification stamp |
| `limit` | Page size, default 50, capped at 200 |
| `offset` | Rows to skip, default 0 |

Results are ordered newest first, which for a ULID key is also creation order.

The `search` behaviour is worth knowing because it is broader than it first
appears: one parameter matches across three fields, so searching a name fragment
can return users whose email merely contains that fragment.

`GET {base}/users/{user_id}` returns the same view plus a `sessions` array, which
is what makes the detail panel a single request.

## Creating a user

`POST {base}/users` creates an account. Two fields deserve attention before you
call it.

<ResponseField name="email">Required. Normalised; a duplicate in this environment is a `409`.</ResponseField>
<ResponseField name="password">Optional. **Omit it and the account gets an unusable password** — the user sets one via a recovery link.</ResponseField>
<ResponseField name="username">Optional. Auto-generated from the email if absent.</ResponseField>
<ResponseField name="name">Optional display name.</ResponseField>
<ResponseField name="user_metadata">Initial user metadata. User-editable afterwards.</ResponseField>
<ResponseField name="app_metadata">Initial app metadata. Admin-only afterwards.</ResponseField>
<ResponseField name="email_verified">**Defaults to `true`.** Admin-created users are pre-verified.</ResponseField>
<ResponseField name="roles">Roles to assign. Added to any default roles the environment grants.</ResponseField>

<Warning>
`email_verified` defaults to **true** on the admin create route, which is the
opposite of what a public sign-up does. That is usually what you want for an
employee you have just created — but if you are importing unverified leads, set it
to `false` explicitly or you will have skipped the verification your policy
assumes is happening.
</Warning>

Two behaviours to be aware of:

**`roles` is additive with the environment's defaults.** A created user receives
`default_roles` from the auth configuration *and* whatever you pass. Passing an
empty list does not mean "no roles".

**Role names that do not exist are created.** Assigning a role the environment has
not defined creates it, with no permissions. That is convenient and occasionally
surprising — a typo produces a valid, empty role rather than an error.

The route returns the created admin user view with a `201`.

### Username generation

When no username is supplied, one is derived: the email's local part, or the
supplied name, lowercased, with every character outside `a-z0-9_.-` stripped,
truncated to 40 characters, defaulting to `"user"` if nothing survives. On
collision, a random number below 10,000 is appended and the check repeats.

So `Ada.Lovelace+news@Example.com` with no username becomes something like
`adalovelacenews`, and a second such user gets a numeric suffix. Uniqueness is
enforced per environment.

## Updating a user

`PATCH {base}/users/{user_id}` does all of update, verify, disable, unlock and
password setting. It is one route with several optional fields, and only the fields
you send are touched.

<ResponseField name="name">Sets the display name.</ResponseField>
<ResponseField name="email_verified">`true` stamps the verification now; `false` clears it — which re-blocks sign-in if the environment requires verification.</ResponseField>
<ResponseField name="disabled">`true` disables and revokes all sessions; `false` re-enables.</ResponseField>
<ResponseField name="password">Sets the password directly, after the environment's policy check. Bypasses any recovery flow.</ResponseField>
<ResponseField name="user_metadata">Replaces the whole object. Not merged.</ResponseField>
<ResponseField name="app_metadata">Replaces the whole object. Not merged.</ResponseField>
<ResponseField name="roles">Sets the user's roles to exactly this list — roles not in it are removed.</ResponseField>
<ResponseField name="unlock">`true` clears `failed_logins` and `locked_until`.</ResponseField>

<Warning>
`roles` on this route is **authoritative, not additive**. Sending a list removes
every role the user has that is not in it. If you read the roles, add one, and
send back the union, you get the expected result; if you send only the new role,
you strip the others.
</Warning>

<Warning>
`user_metadata` and `app_metadata` are **replaced, not merged**. Sending
`{"tier": "gold"}` for a user whose metadata is `{"tier": "free", "referral": "x"}`
leaves them with only `{"tier": "gold"}`. Read, merge, write.
</Warning>

The self-service route, `PATCH /auth/v1/user`, behaves differently and the
difference matters: it **merges** `data` into `user_metadata` rather than replacing
it, and it requires `current_password` before changing a password on an account
that has one.

### Disable is the blunt instrument

Disabling sets a disable timestamp **and revokes every session the user has**. That
combination is what makes it the right response to a suspected compromise, and it
is why it is not reversible in the way it looks — re-enabling restores the account
but does not restore the sessions.

<Warning>
Disabling does not invalidate access tokens that are already issued. Services
verify those signatures locally, so a disabled user's existing tokens keep working
until they expire — up to `access_ttl`. Disable stops new sign-ins and all refreshes
immediately; it does not reach tokens already in a service's hands.
</Warning>

Disabling and enabling each emit an event — `user.disabled` or `user.enabled` — so
an audit trail exists independently of the login-event history.

### Unlock is separate from disable

A locked account is one whose `locked_until` is set and in the future, which
happens after ten failed attempts by default. It is **not** disabled: it is
refused with `429`, and a correct password still fails until the window passes.

`{"unlock": true}` clears both the counter and the timestamp, immediately. There is
no wait and no cooldown — it is an administrative override, so treat it as a
deliberate act rather than a routine one.

<Note>
Because the lockout threshold and duration are installation settings while the
counters are per user per environment, unlocking one user in staging does not
affect the same address in production. They are separate accounts with separate
counters.
</Note>

### Setting a password directly

Setting `password` on the update route applies the environment's policy check
first, so a password the environment would refuse at sign-up is refused here too —
with the same `422` and the same list of problems.

It also makes the password **usable**, converting an account that had an unusable
one into one that can sign in with a password. That is the mechanism behind the
"Set password" button in Studio for OAuth-only accounts.

<Warning>
This route bypasses the recovery flow entirely. There is no emailed confirmation and
no `user.password_reset` event — it is a `user.password_changed`-style change made
by an administrator. If your process requires the user to prove control of their
email, use recovery instead and let them set their own password.
</Warning>

## Deleting a user

`DELETE {base}/users/{user_id}` is a **soft delete**, and the detail matters for
anyone deciding whether it is the right tool.

What it does:

- Revokes every session.
- Deletes the user's linked external identities.
- Removes all MFA factors and recovery codes.
- Marks the account inactive and stamps a deletion timestamp.
- **Rewrites the email to a placeholder** derived from the user id and project.
## Sessions: signing a user out

Three levels of intervention, and the difference between them is one of scope.

| Route | Effect |
| --- | --- |
| `POST .../sessions/revoke` | Revokes **every** session for the user, returns `{"revoked": N}` |
| `DELETE .../sessions/{session_id}` | Revokes **one** session; a bad id is a `404` |
| `PATCH {"disabled": true}` | Disables the account **and** revokes every session |

The revoke-all route is the one to reach for in an incident. The count it returns
is the number of token families that were live, which is a useful confirmation that
sessions actually existed.

<Warning>
`revoked` counts token families, not access tokens. Revoking a user with three
devices returns `3`, and each of those devices may still hold an access token
that works for up to `access_ttl`. The count tells you sessions died; it does not
tell you access stopped immediately.
</Warning>

### The session list is narrower than it looks

The sessions array on the user detail view is built by **intersecting two tables**.
A session appears only if it has an unrevoked `SessionInfo` row *and* its family
still has an unrevoked, unconsumed, unexpired refresh token.

The practical effect: a session whose refresh tokens have all expired does not
appear, even though its row still exists. The list shows *resumable* sessions.

| You see | It means |
| --- | --- |
| No active sessions | No resumable sessions — not that the user never signed in |
| Sessions present, all old | Last activity was long enough ago that refresh expired |

If you need the full record of what happened, read the history instead.

### Session entries

Each session carries `id` (the family string), `method`, `aal`, `ip`, `user_agent`,
`created_at`, `last_refreshed_at` and `current`.

`method` records **how the session started**, not how it is being continued — a
Google sign-in reads `oauth:google` for its whole life. `current` is computed
against the caller, and is therefore always `false` in an admin view of someone
else's sessions.

## Resetting MFA

`POST .../mfa/reset` removes a user's second factors entirely: the factors
themselves, all their recovery codes, and the enabled flag. It returns
`{"mfa_enabled": false}` and emits `user.mfa_reset`.

This is the route for a user who has lost their authenticator and their recovery
codes. There is no partial reset — you cannot remove the factor and leave the
codes, and there is no administrative way to issue a single replacement recovery
code.

<Warning>
MFA reset does not revoke sessions. A user whose MFA you just removed keeps their
existing sessions, and a session created before the reset is still `aal2` in its
token. If the reason for resetting is that you believe the account is compromised,
**reset the MFA and revoke the sessions** — the reset alone leaves the existing
sessions valid.
</Warning>

After a reset, the user re-enrols from scratch: a new secret, a new provisioning
URI, and a fresh set of ten recovery codes. The old codes are gone, not
invalidated-but-kept.

## Reading a user's sign-in history

`GET .../history` returns up to **100** of the user's most recent authentication
events, newest first. Each entry carries `id`, `user_id`, `email`, `kind`,
`method`, `success`, `reason`, `ip`, `user_agent` and `at`.

This is the richest diagnostic surface in the admin API, and the `reason` field is
why. The API deliberately returns one generic message for several different
failures — but the reason recorded internally distinguishes them.

| `kind` | Typical `reason` when it fails | What it tells you |
| --- | --- | --- |
| `sign_in` | `unknown email` | No account for that address in **this** environment |
| `sign_in` | `wrong password` | The account exists; the password was wrong |
| `sign_in` | `locked` | Threshold reached; the password may have been right |
| `sign_in` | `disabled` | An administrator disabled the account |
| `refresh` | The theft messages | A consumed or revoked refresh token came back |
| `refresh` | `Invalid refresh token` | The signature did not verify |
| `mfa_challenge` | — | A challenge was issued, so the password was correct |
| `mfa_verify` | `wrong code` | The TOTP or recovery code was wrong |
| `password_reset` | — | A recovery link was completed |
| `sign_out` | — | The method is the scope: `local`, `others`, `global` |

<Info>
`mfa_challenge` appearing immediately before `mfa_verify` is how you distinguish
"the password was wrong" from "the password was fine and the second factor was
wrong". That distinction saves a great deal of support time.
</Info>

The 100-event cap is worth remembering: a user signing in repeatedly can push
anything interesting off the end quickly. For a broader view, `GET {base}/events`
covers the whole environment.
- **Rewrites the username** to `deleted-{id}`.

What it preserves: the user row itself, so historical events remain attributable
to the id rather than becoming orphaned.

<Warning>
The email is rewritten so the original address is **released for re-use**. Someone
can sign up with it immediately. That is usually what you want after an account is
closed — but it means the old account and the new one are unrelated, and any data
you kept keyed by email is now ambiguous.
</Warning>

<Info>
Deleted users are excluded from every normal lookup — search, listing, and the
email-uniqueness check all filter them out. The uniqueness constraint therefore
does not fire when you re-create an account with a released address.
</Info>

Deletion emits `user.deleted`. Unlike disabling, it cannot be undone from the UI,
which is why disable is usually the better first move.

## The Studio Users tab

Studio's page for this is **Users & auth**, described as *"End users of this
environment, managed by Akountz: accounts, sessions, MFA, roles and
organizations."* It carries five tabs in order: **Users**, **Roles**,
**Organizations**, **Sign-in activity**, **Configuration**.

Everything on this page is the same admin API described above, driven with the
management key. There is nothing Studio can do that a service key cannot.

### The statistics strip

Above the table, a row of stat tiles rendered from the environment's stats route.
The counts are `users`, `verified`, `mfa`, `disabled`, `signups_24h`,
`sign_ins_24h`, `failures_24h`, `organizations`, plus per-provider identity counts.

Labels are the raw keys with underscores replaced by spaces, so `sign_ins_24h`
reads as **sign ins 24h**. Worth knowing before you go looking for a polished
label that does not exist.

`failures_24h` is the number to watch: it counts **all** failed events, not just
failed sign-ins, so a refresh loop or a client bug moves it as readily as an attack.

### Finding a user

The search input placeholder reads **"Search email or name"**, and next to it a
status dropdown with three options: **all**, **disabled**, **unverified**.

Both map directly to the query parameters on the list route. The dropdown has no
"locked" or "enrolled in MFA" option, which is a real gap — those users have to be
found by search and inspected individually.

### The user table

Five columns, and what each one is actually showing:

| Column | Renders |
| --- | --- |
| **Email** | The address, in bold |
| **Name** | The display name |
| **Roles** | One badge per role; empty if they have none |
| **State** | Badges describing account status |
| **Last sign-in** | Relative time from the last successful sign-in |

**State** is the column to read carefully, because it composes up to three badges:

| Badge | Condition | Meaning |
| --- | --- | --- |
| **disabled** (red) | `disabled` is true | Disabled by an administrator |
| **active** (green) | not disabled | The default state |
| **unverified** (yellow) | `email_verified` is false | No verification stamp |
| **MFA** (blue) | `mfa_enabled` | A confirmed factor exists |

Note that **active** means "not disabled", not "verified" and not "signed in". A
row showing **active** and **unverified** together is normal for an environment
where verification is not required.

Clicking any row opens that user's detail panel.

### Creating a user from Studio

The **New user** button in the card header opens a modal with three fields:
**Email**, **Name**, and **Password**.

The Password hint reads *"Leave empty to have the user set one through a recovery
link."* That is not a cosmetic suggestion — leaving it empty is what creates an
account with an unusable password, and the user must then use a recovery link
before password sign-in works.

The button in the footer is **Create**, and it toasts **User created**. It is
disabled until an email is present.

<Note>
The modal exposes only three fields, so it cannot set `user_metadata`,
`app_metadata`, `username` or `email_verified`. The route accepts all of them; the
UI does not offer them. Use the API for anything the modal cannot express.
</Note>

<Note>
A username you supply explicitly is not normalised the same way — it is only
lowercased and checked for uniqueness. The stripping and truncation apply to the
generated path.
</Note>
### The user detail panel

Clicking a row opens a wide modal titled with the user's email. Its action row is
the operational core of the page.

| Button | Shown when | Calls | Toast |
| --- | --- | --- | --- |
| **Disable** / **Enable** | Always, alternating | `PATCH {"disabled": ...}` | **Disabled** / **Enabled** |
| **Mark verified** | Only when unverified | `PATCH {"email_verified": true}` | **Marked verified** |
| **Sign out everywhere** | Always | `POST .../sessions/revoke` | **Signed out everywhere** |
| **Reset MFA** | Only when `mfa_enabled` | `POST .../mfa/reset` | **MFA reset** |
| **Set password** | Always | `PATCH {"password": ...}` | **Password set** |
| **Delete** | Always | `DELETE .../users/{id}` | **Deleted** |

Three of these prompt before acting. **Set password** raises a browser `prompt`
labelled **New password**. **Delete** raises a `confirm` naming the user's email,
and on success closes the panel rather than leaving it open on a deleted account.

<Warning>
**Set password** uses a browser prompt, so the new password is visible on screen
and cannot be masked or strength-checked. It also skips the recovery flow entirely.
For any account where audit matters, set the password through the API and let your
own tooling handle it.
</Warning>

The order of the buttons encodes the severity gradient: reversible actions first,
**Delete** last and styled as destructive. **Disable** deliberately sits first
because it is the action you want most often in an incident, and it is reversible.

<Note>
**Reset MFA** only appears when the user actually has MFA enabled. There is no way
to reset a user who does not, which is consistent with there being nothing to
remove.
</Note>

### Roles and direct permissions in the panel

Below the action row is a **Roles** field — a comma-separated text input, hinted
*"Comma-separated role names from the Roles tab."* — with a **Save roles** button
that toasts **Roles saved**.

<Warning>
This maps to the `roles` field on the update route, which is **authoritative**.
Saving a list removes every role the user has that is not in it. The field is
pre-filled with the user's current roles, so a plain save is safe — but if you
clear it to "start fresh", you are removing all of them, not just adding one.
</Warning>

Direct permissions appear as individual badges, each with a **✕** that revokes that
one permission and toasts **Revoked**. Alongside them is a free-text input and a
**Grant** button, which toasts **Granted** and clears the field.

Permissions granted this way are **direct** — they sit on the user, not on a role.
The list shown includes permissions inherited through roles as well, so a **✕** on a
badge may remove a direct grant that happens to duplicate an inherited one, after
which the permission still appears because the role still confers it.

### Sessions in the panel

A **Sessions** heading above a table with columns **Session**, **Device**, **IP**,
**Last active**, and an unnamed final column holding a per-row **Revoke** button.

**Session** renders only the first eight characters of the family — enough to
recognise, not enough to use. **Device** is the raw user-agent string. **Last
active** prefers a last-seen value and falls back to the creation time.

The empty state is **"No active sessions."** Seeing it for a user you believe is
signed in is usually the intersection rule rather than a bug.

**Revoke** calls the per-session delete and toasts **Session revoked**.

### History in the panel

Below the sessions, a **History** table with columns **When**, **Event**, **OK**
and **IP**, empty state **"No activity."**

The **OK** column is a badge: green `ok` on success, red carrying the `reason`
string on failure. That is what makes a user's failure reason visible without
reading the API — `unknown email`, `wrong password`, `locked`, `wrong code` and the
refresh theft messages all appear here verbatim.

<Info>
This is the most useful panel for support work. When a user says "it keeps telling
me my account is locked" or "I get signed out randomly", the History table usually
answers it in one click.
</Info>

## Worked examples

The composite operations, because the individual routes are simple but the
combinations are where the mistakes live.

### Offboarding an employee

The order matters, and the reason is that some actions are irreversible.

The account should be **disabled** first. That revokes every session immediately
and blocks new sign-ins, and it keeps the row intact so the audit history stays
attributable.

If the person had MFA enrolled, reset it — but note this does **not** revoke
sessions, which is why disabling came first. Their existing access tokens remain
valid until they expire regardless.

Revoking sessions is redundant after disabling, and the count returned will be
zero, since disabling already revoked them.

If the account should no longer be reachable by anyone, **delete** it. That releases
the email address for re-use, removes linked identities and factors, and cannot be
undone.

<Warning>
If you need the address preserved — because it is a shared or role-based account, or
because you are deleting a duplicate — do not delete. Disable leaves the address
taken, which is what you want when identity continuity matters.
</Warning>

### Investigating "someone keeps getting signed out"

The symptom has one overwhelmingly common cause, and the history route identifies
it.

Read the user's history and look for repeated `refresh` events whose `reason`
contains a theft message. That pattern is the signature of a client presenting the
same refresh token twice — two tabs, a retry after a timeout, or a race between
concurrent requests.

The fix is on the client, not the server: serialise refreshes and never retry a
failed refresh with the same token. The server's behaviour is correct; it cannot
tell a racing client from a thief.

If instead the history shows `sign_in` with `locked`, the account is locked out and
`{"unlock": true}` clears it immediately.

<Info>
Because the theft message is written to the login-event history, this diagnosis is
available to you and invisible to the user — their client only ever receives a
generic `401`.
</Info>

### Granting a role safely

The failure mode is sending a partial role list, which strips everything not in it.

Read the user's current `roles`, add the new one, and send the union. The Studio
**Roles** field is pre-filled for exactly this reason, and a plain **Save roles**
is safe; editing it to contain only the new role is not.

<Warning>
Assigning a role name that does not exist **creates** it, with no permissions. A
typo produces a valid, empty role rather than an error, and the user appears to
have a role that grants nothing. Check the **Roles** tab for the exact spelling.
</Warning>

### Finding every user with a stale role

Because roles are read into the token at issue time, a role change only lands on
each user's **next refresh**. There is no bulk "log everyone out so they pick up
their new roles" action, and building one means revoking sessions.

The practical approach for a permission change you need to take effect promptly is
to revoke sessions for the affected users — for example via
`POST .../sessions/revoke` each. That forces a refresh, and the new token carries
the new permissions.

<Info>
This is also why a permission change and a role change have different urgency. A
role change is advisory until users refresh; revoking sessions makes it immediate.
</Info>

## The self-service routes, for contrast

It is easy to confuse the admin routes with the ones a user calls for themselves.
The distinction is not only about authentication — the **merge semantics differ**,
and getting that wrong is a real bug.

| Concern | Admin route | Self-service route |
| --- | --- | --- |
| Authentication | Service token | The user's own access token |
| Environment | In the path | From the request context |
| `user_metadata` | **Replaced** | **Merged** |
| Password change | No current password needed | `current_password` required if one is set |
| Session access | Any user's | Only the caller's |
| History | Any user's, 100 events | Only the caller's, 50 events |

The metadata difference is the one to remember. If you port an admin integration to
the self-service route expecting replacement, you will silently accumulate keys
instead, and vice versa.

<Note>
The self-service password change requires `current_password` only when the account
already has a usable password. An account with an unusable one — OAuth-only — can
set its first password without supplying one.
</Note>

A related asymmetry: the self-service email change does not apply immediately. It
issues a confirmation link, and the address changes only when that link is
followed. The admin route has no equivalent ceremony, because an administrator
setting an address is not the same trust decision as a user changing their own.

## Auditing what has been done

Every administrative action that changes state emits an event, and the
login-event table is the durable record. For an audit, the events to watch are:

| Event | Raised by |
| --- | --- |
| `user.created` | Sign-up, social sign-in, or an admin create |
| `user.disabled` / `user.enabled` | The update route |
| `user.deleted` | The delete route |
| `user.mfa_reset` | The MFA reset route |
| `user.verified` | A verification link, or an admin marking verified |
| `user.password_changed` | A self-service password change |
| `user.password_reset` | A completed recovery link |
| `user.updated` | A self-service profile update, carrying what changed |
| `session.revoked` | Any session revocation, carrying the scope |
| `session.reuse_detected` | A replayed refresh token |

Note the asymmetry: **`user.disabled` carries `actor="admin"`**, as do
`user.created` from the admin route, `user.deleted` and `user.mfa_reset`. Those
events name an administrator as the actor, while self-service events name the user.
So the actor field distinguishes "a person in Studio did this" from "a user did
this to themselves" — which is usually the question an audit is asking.

<Warning>
There is **no** event for disabling and re-enabling being the *same* action as
revoking sessions, and no aggregate "account compromised" marker. If your incident
process needs to know that MFA was reset **and** sessions revoked together, derive
it from the correlated events rather than expecting one event for it.
</Warning>

## Provisioning patterns

Two approaches, and the trade-off between them is about how much you trust the
identity of whoever is provisioning.

**Admins create users directly.** One call, immediate, no email round trip, and the
user is pre-verified by default. Appropriate when the provisioning system already
knows the person's work address and there is no ambiguity about identity.

**Admins create users without a password.** The account exists, `has_password` is
false, and the user sets their own password through a recovery link. This is the
right choice when you want the user to prove control of the address, and it is why
Studio's New user modal hints *"Leave empty to have the user set one through a
recovery link."*

| Approach | User verified | Proves control of email | Requires email to work |
| --- | --- | --- | --- |
| Create with password | Yes, by default | No | No |
| Create without password | Yes, by default | Yes | Yes |

<Info>
Neither approach is wrong; they answer different questions. If your threat model
includes an insider provisioning an account under someone else's address, the
second is the one that leaves an audit trail you can trust.
</Info>

## Bulk operations, and their absence

There is no bulk endpoint. Not for disabling many users, not for revoking many
sessions, not for setting a role across a group. Every operation is per user.

<Warning>
This matters during an incident. If a shared credential has been compromised and
two hundred accounts might have used it, there is no single call that ends all of
them. You will need to iterate — read the user list, then disable or revoke per
user.
</Warning>

The practical mitigation is the search and pagination already on the list route:
page through with a generous `limit` (its maximum is 200) and act on each id.
Doing that concurrently is reasonable, since these are independent per-user
operations with no shared lock — but be aware that the rate limits on the auth
bucket do not apply to admin routes, so the limiting factor will be the database.

<Info>
For a genuinely large user base, the better answer is usually preventive — a short
`refresh_ttl` means a compromised refresh token stops working sooner, without
anyone having to enumerate accounts.
</Info>

## Tenancy: why an admin action can appear to do nothing

The single most common confusion in user administration is an action that reports
success against the wrong account. It is nearly always the environment.

Every user lookup filters on **both** `project` and `env`. A user id is a ULID, and
while the id is globally unique as an identifier, the *lookup* is scoped: an id
from production, used against staging, finds nothing and returns `404 no such user`.

The same address in two environments is two accounts, with separate:

- Passwords
- Roles and permissions
- Sessions and lockout counters
- MFA enrolment
- Metadata

So "I disabled them" and "they can still sign in" are usually both true, referring
to different accounts.

| Symptom | Most likely explanation |
| --- | --- |
| `404` for a user you can see in another environment | Wrong environment in the path |
| User signs in but does not appear in your list | Different environment |
| Their password does not work here | Different account, different password |
| Disabling here did not stop them | They signed in to the other environment |
| Duplicate email was rejected, but they exist | A different environment, or a released address |

<Warning>
Promoting a database from one environment to another without promoting its auth
configuration is the usual way people create this confusion by accident. Accounts
arrive, the configuration does not, and sign-in behaves in ways that look like bugs.
</Warning>

## Verifying an administrative action took effect

Because some of these actions are not instantaneous everywhere, it is worth knowing
what "done" looks like for each.

| Action | Immediate effect | Delayed effect |
| --- | --- | --- |
| Disable | New sign-ins refused; all sessions revoked | Existing access tokens until `access_ttl` |
| Enable | Sign-in permitted again | The **disabled** badge clears immediately |
| Revoke sessions | All refreshes refused | Existing access tokens until `access_ttl` |
| Revoke one session | That session cannot refresh | Its current access token until `exp` |
| Unlock | Sign-in permitted; lockout cleared | The **locked_until** field clears |
| Reset MFA | Factors and codes gone; flag cleared | Existing `aal2` tokens keep their claim |
| Set password | `has_password` becomes true | Nothing |
| Mark verified | `email_verified` becomes true | The **unverified** badge clears |
| Change roles | `roles` updated in the view | The new roles appear in **tokens** on next refresh |
| Delete | Row hidden from all lookups | Nothing — it is immediate |

The pattern worth internalising: **the user view updates immediately, while tokens
update on the next refresh.** When you change a role and the user's app still shows
the old permissions, nothing has gone wrong — the token is a snapshot.

<Info>
The one genuinely confusing case is MFA reset: the view says MFA is off, but a
session created before the reset still carries `aal2`. The view is authoritative
going forward; the existing token is not rewritten.
</Info>

## Request and response shapes in full

The wire formats, so an integration can be written without reading the source.

### Creating a user

```bash
curl -X POST https://api.example.com/projects/acme/envs/production/users \
  -H 'apikey: sk_live_...' \
  -H 'Content-Type: application/json' \
  -d '{
        "email": "ada@acme.com",
        "name": "Ada Lovelace",
        "password": null,
        "email_verified": false,
        "roles": ["editor"]
      }'
```

A `201` returns the admin user view. `"password": null` is what creates the
unusable-password state, and `"email_verified": false` overrides the default.

### Searching

```bash
curl 'https://api.example.com/projects/acme/envs/production/users?search=ada&status=unverified&limit=50' \
  -H 'apikey: sk_live_...'
```

```json
{
  "data": [
    {
      "id": "01HQ8K2M4N7P9R3S5T7V9W1X3Y",
      "email": "ada@acme.com",
      "username": "ada",
      "name": "Ada Lovelace",
      "email_verified": false,
      "roles": ["editor"],
      "mfa_enabled": false,
      "disabled": false,
      "has_password": false,
      "permissions": ["posts:write"]
    }
  ],
  "total": 1
}
```

`total` is the count **after** filtering, not the whole environment — so it is the
number your pagination needs, not the number of users.

### A partial update

One route covers several actions, and combining fields is normal:

```bash
curl -X PATCH https://api.example.com/projects/acme/envs/production/users/01HQ8K2M4N7P9R3S5T7V9W1X3Y \
  -H 'apikey: sk_live_...' \
  -H 'Content-Type: application/json' \
  -d '{"email_verified": true, "roles": ["editor", "reviewer"]}'
```

Note that `roles` here must be the **complete** intended list. Sending only
`["reviewer"]` removes `editor`.

### Granting and revoking a permission

Both use the same route with different methods, and both return the resulting
effective permission set:

```bash
# Grant
curl -X POST https://api.example.com/projects/acme/envs/production/users/01HQ8K2M4N7P9R3S5T7V9W1X3Y/permissions \
  -H 'apikey: sk_live_...' -H 'Content-Type: application/json' \
  -d '{"permissions": ["posts:write", "posts:publish"]}'

# Revoke
curl -X DELETE https://api.example.com/projects/acme/envs/production/users/01HQ8K2M4N7P9R3S5T7V9W1X3Y/permissions \
  -H 'apikey: sk_live_...' -H 'Content-Type: application/json' \
  -d '{"permissions": ["posts:publish"]}'
```

`DELETE` with a body is unusual enough to be worth flagging: some HTTP clients drop
it. If yours does, the request arrives with no permissions and revokes nothing.

### Reading history

```json
{
  "data": [
    {
      "id": "01HQ8K5M2N9P4R7S9T1V3W5X7Y",
      "user_id": "01HQ8K2M4N7P9R3S5T7V9W1X3Y",
      "email": "ada@acme.com",
      "kind": "refresh",
      "method": "refresh_token",
      "success": false,
      "reason": "Refresh token already consumed — possible token theft",
      "ip": "203.0.113.42",
      "user_agent": "Mozilla/5.0",
      "at": "2026-09-14T08:37:12+00:00"
    }
  ]
}
```

That one row is the entire diagnostic surface for a "randomly signed out" report.

### The statistics route

`GET {base}/stats` returns the counts behind the Studio tiles, which is the
simplest way to monitor an environment without polling the user list:

```json
{
  "users": 1284,
  "verified": 1190,
  "mfa": 412,
  "disabled": 17,
  "signups_24h": 23,
  "sign_ins_24h": 461,
  "failures_24h": 8,
  "organizations": 6,
  "providers": [{ "provider": "google", "n": 340 }]
}
```

The 24-hour windows are rolling and computed at call time, so they are suitable for
alerting on — `failures_24h` in particular, as a sudden rise is the earliest
signal of credential stuffing.

<Warning>
`failures_24h` counts every failed event, not only failed sign-ins. A client stuck
refreshing produces failures too, so alert on the *shape* of the change rather than
the absolute number.
</Warning>

## Organizations and the Organizations tab

Organizations are managed separately from users, though the two are related enough
to be confused.

The **Organizations** tab lists them with columns **Name**, **Slug**, **Members**
and **Created**, and its empty state is the useful sentence *"No organizations.
Users create them through /auth/v1/orgs."* That is the key point: organizations are
created by **users**, not by administrators, so the tab starts empty in a fresh
environment and fills as your application uses them.

Clicking an organization opens its detail, showing members with their roles and the
teams inside it.

| Route | Purpose |
| --- | --- |
| `GET {base}/orgs` | All organizations with member counts |
| `GET {base}/orgs/{slug}` | One organization, with members and teams |

Membership changes happen through the user-facing org routes — a user creates an
organization, invites members, and an invitee accepts. The admin surface here is
read-only, which is worth knowing before you go looking for an "add member" control
that does not exist.

<Info>
Because an organization's membership determines the `org` and `org_role` claims, a
membership change is invisible to services until the affected user refreshes.
`/auth/organizations` covers the full membership model.
</Info>
## Choosing between the routes

A short guide to picking the right action, since several of them look similar from
a distance.

| You want to | Use | Not |
| --- | --- | --- |
| Stop one device | `DELETE .../sessions/{id}` | Revoke-all, which is overkill |
| Stop all devices | `POST .../sessions/revoke` | Deleting the account |
| Stop sign-in, keep the record | `PATCH {"disabled": true}` | Deleting |
| Free the email address | `DELETE` | Disabling, which keeps it taken |
| Clear a lockout | `PATCH {"unlock": true}` | Waiting, or disabling |
| Force a password | `PATCH {"password": ...}` | Recovery, if proof of email matters |
| Have the user set their own | A recovery link | Setting it for them |
| Remove a second factor | `POST .../mfa/reset` | Turning MFA off in config |
| Make someone verified | `PATCH {"email_verified": true}` | Sending a verification email |

<Note>
The distinction between the last two rows is the one people get wrong most often.
Turning `mfa_enabled` off in the environment configuration stops users being
*challenged* but leaves their factors in place. Only the admin reset route actually
removes them.
</Note>

## Permissions and roles from the admin API

Beyond per-user management, the admin base exposes the role definitions themselves.

| Route | Method | Purpose |
| --- | --- | --- |
| `/roles` | GET | Roles with their permissions, plus every known permission |
| `/roles` | PUT | Create or replace a role |
| `/roles/{name}` | DELETE | Delete a role and its memberships |

A role name must match `^[a-z][a-z0-9_:-]{0,62}$` — lowercase, starting with a
letter. `PUT` on an existing name **replaces** its permission set rather than
adding to it, which is the same authoritative semantics as user roles.

The GET response returns both the roles and the flat list of permissions defined in
the environment, which is what a UI needs to offer a permission picker.

<Warning>
Deleting a role removes its memberships. Users assigned only that role end up with no
roles — and since they may still hold a token carrying the old role until their
next refresh, the visible effect lags the actual change.
</Warning>

### The Roles tab, briefly

Roles are edited in Studio's **Roles** tab rather than on the user panel. A
**New role** button opens a modal with **Name**, **Description** and
**Permissions** fields, the last hinted *"Comma-separated, e.g.
posts:write, posts:publish. `*` grants everything."* The table lists each role with
its description, its permissions as badges, and a member count.

The Name field is **disabled when editing an existing role** — renaming is therefore
a delete-and-create, not an edit, which is worth knowing before you try.

Roles and permissions are covered in full at
[/auth/roles-and-permissions](/auth/roles-and-permissions).

## What goes wrong, and why

| Symptom | Cause | Fix |
| --- | --- | --- |
| `404` on any user route | The id is not a ULID, or belongs to another environment | Check the environment; ids are environment-scoped |
| `404 no such user` after deleting | Deleted users are excluded from lookups | Expected; the row is retained but hidden |
| `409` on create | An account with that email exists in this environment | Search first, or accept the released address |
| User has no sessions in Studio | No resumable refresh token remains | Expected; the list shows resumable sessions only |
| Disabled user still has a working token | Access tokens verify locally | Wait out `access_ttl`, or revoke at your gateway |
| Saved roles removed other roles | `roles` is authoritative | Send the full intended list |
| Metadata edit lost other keys | Metadata is replaced, not merged | Read, merge, write |
| `Set password` shows the password on screen | Studio uses a browser prompt | Use the API for anything auditable |
| `Reset MFA` did not end sessions | Reset and revocation are separate | Revoke sessions as well |
| New role grants nothing | The name was undefined, so it was created empty | Define it on the Roles tab with permissions |
| Role change not taking effect | Tokens carry a snapshot | Revoke sessions to force a refresh |
| A user "does not exist" | They exist in a different environment | Accounts are per project and environment |
| Created user is already verified | `email_verified` defaults to `true` here | Pass `false` for unverified users |
| Reset email never arrives | The account has an unusable password | Set one via the update route first |

<Info>
Most of that table is one recurring theme: these routes are authoritative — they set
values rather than merging them — and everything they affect is scoped to a single
project and environment.
</Info>
## Relationship to the rest of the system

**User administration is environment-scoped throughout.** Every route takes the
environment from the path, every lookup filters by it, and email uniqueness is
enforced within it.

**Studio is a client of the same API.** Every button described here maps to a route
a service key can call. If the UI cannot express something — metadata, granular
permissions, a dry run — the route still can.

**Backups include what these routes manage.** An export contains roles, users with
their password hashes, and organizations, so a backup is a credential archive and
deserves the handling of one.

**Authorization changes are not access changes.** Revoking a session forces a
refresh; it does not change what the refreshed token will contain.


## A support playbook

Five situations that recur, and the shortest path through each. These are the
flows the Studio Users tab exists for.

### "My account is locked"

Check the user view's `locked_until`, or the History table's `locked` reason. Lockout
is ten failed attempts by default, and it lasts fifteen minutes.

Click **Enable** only if the account was *disabled* — a lockout is a different
state. For a lockout, send `{"unlock": true}`; the immediate alternative is to wait
out the window.

<Warning>
A locked account returns `429` even with the correct password, because the lock is
checked first. Users frequently report this as "my password stopped working" rather
than as a lockout, which sends people looking in the wrong place.
</Warning>

### "I keep getting signed out"

Look for repeated `refresh` events with a theft message in the History table. That
is a client presenting one refresh token twice, which the server treats as theft
and answers by revoking the session.

There is nothing to fix server-side — the response is correct. The client must
serialise refreshes and must not retry a failed refresh with the same token. If it
is your own frontend, that is where the bug is.

If instead the history shows a single `refresh` with `Invalid refresh token`, the
token was malformed or the environment's signing key changed.

### "They can't sign in but they exist"

Three candidates, distinguishable from the History table:

| History shows | Meaning | Action |
| --- | --- | --- |
| `unknown email` | No account in **this** environment | Check the environment |
| `disabled` | Administratively disabled | **Enable** |
| `locked` | Lockout | **Enable** is wrong; unlock |

A `404` when you look the user up points at the environment rather than the
account.

### "They lost their authenticator"

**Reset MFA** in the user panel. It removes the factor, the recovery codes and the
flag in one action.

Then **revoke their sessions**. Reset alone leaves existing sessions valid,
including any still carrying `aal2`. Resetting and revoking together is the complete
answer, and doing only the first leaves a hole.

### "I need to get into their account"

The honest answer is that **Set password** is the mechanism, and it should be a
deliberate, auditable act rather than a support reflex.

Two things to be aware of before using it: the Studio button shows the password in
a browser prompt, unmasked, so prefer the API; and it bypasses the recovery flow, so
there is no proof the user controls the address.

The user needs to re-enrol MFA afterwards if they had it — resetting the password
does not clear the `mfa_enabled` flag, so they will be challenged for a code they no
longer have. Reset the MFA too, or you will lock them out of their own account.

<Warning>
That last point is the most common support mistake on this page: changing a
password for a user who has MFA enabled without resetting their MFA leaves them
unable to sign in, because they are correctly being challenged for a factor they
have lost. Reset both, or neither.
</Warning>

### Field-by-field on the two write models

`AdminUserCreate` — everything except `email` is optional:

| Field | Type | Default | Notes |
| --- | --- | --- | --- |
| `email` | string | required | Normalised; a duplicate here is a `409` |
| `password` | string or null | null | Null means an unusable password |
| `username` | string or null | null | Generated from the email when absent |
| `name` | string | `""` | |
| `user_metadata` | object | `{}` | User-editable thereafter |
| `app_metadata` | object | `{}` | Admin-only thereafter |
| `email_verified` | boolean | **true** | Pre-verified, unlike a public sign-up |
| `roles` | list | `[]` | Additive with the environment's `default_roles` |

`AdminUserUpdate` — every field is optional and only what you send is touched:

| Field | Type | Effect |
| --- | --- | --- |
| `name` | string or null | Sets the display name |
| `email_verified` | boolean or null | Stamps or clears verification |
| `disabled` | boolean or null | Disabling also revokes every session |
| `password` | string or null | Policy-checked, bypasses recovery |
| `user_metadata` | object or null | **Replaces** the object |
| `app_metadata` | object or null | **Replaces** the object |
| `roles` | list or null | **Authoritative** — removes anything absent |
| `unlock` | boolean or null | Clears `failed_logins` and `locked_until` |

<Warning>
Three fields on the update model are replace-not-merge: `roles`, `user_metadata`
and `app_metadata`. The session revocations triggered by `disabled` are the one
place a PATCH has a side effect beyond the user's own row, and it is not
represented in the response.
</Warning>

### The environment-wide events route

`GET {base}/events` is the route behind the **Sign-in activity** tab, and it is
distinct from a user's history in two ways: it spans the whole environment, and it
is filterable.

| Query parameter | Effect |
| --- | --- |
| `kind` | Exact match on the event kind, such as `sign_in` |
| `failed` | `true` selects only failures |
| `limit` | Defaults to 100, capped at 500 |

It returns the same event shape as a user's history, plus the id and user id.

<Info>
`failed=true` is the cheapest way to detect a problem. A rising failure count that
is not credential stuffing is usually a broken client — a retry loop presenting the
same refresh token, for instance.
</Info>

## Organizations on the admin surface

The admin routes expose organizations **read-only**. This surprises people who
expect parity with users, and it is deliberate: organizations are created by users
through their own routes, and the admin view exists to report on them.

| Route | Returns |
| --- | --- |
| `GET {base}/orgs` | `id`, `slug`, `name`, `members` count, `created_at` |
| `GET {base}/orgs/{slug}` | `slug`, `name`, `metadata`, members with roles, teams |

Because the listing annotates a member count rather than loading memberships, a
large environment's org list stays cheap — useful when you only need to know which
organizations exist.

### The invariants the user-facing routes enforce

These explain the errors you will meet when they are eventually enforced, and they
are worth knowing because they are the only place in the auth system where a `409`
protects data integrity rather than signalling a conflict.

| Rule | Error when broken |
| --- | --- |
| Slugs match `^[a-z0-9][a-z0-9-]{1,62}$` | `422` at validation |
| Slugs are unique per environment | `409` on create |
| Roles must be one of `owner`, `admin`, `member`, `viewer` | `422` naming the allowed set |
| Only owners may grant or remove ownership | `403` |
| Only owners and admins may remove members | `403` |
| An organization keeps at least one owner | `409` |

<Warning>
"An organization keeps at least one owner" is the interesting one. It means an
organization cannot be orphaned by demoting or removing its last owner, and it is
enforced on both the role-change and member-removal paths. If you find yourself
unable to remove a member, check whether they are the last owner.
</Warning>

Note the role list is a **closed set of four**. Membership roles are validated
against it, unlike permission role names, which are free-form and created on demand.
The two "role" concepts in this system are genuinely different things: an
organization role is a membership level from a fixed list, while a role in the
permissions system is a named bundle you define.

<Note>
`/auth/organizations` covers the membership routes in full, including invitations
and their seven-day lifetime.
</Note>

## Backup and restore of identities

Two routes, and they are the reason an identities export deserves the handling of a
credential archive.

`GET {base}/backup` returns every role, every user **with password hashes**, and
every organization, in a versioned document format.

`POST {base}/restore` applies one back, with three fields:

<ResponseField name="identities">The exported document.</ResponseField>
<ResponseField name="replace">When true, overwrite rather than merge.</ResponseField>
<ResponseField name="dry_run">Report what would happen without writing.</ResponseField>

Three behaviours make this safer than it first appears. A document whose format
version does not match is rejected outright with `422`, so a backup from an
incompatible release cannot half-apply. `dry_run` returns the counts without
touching anything, which is the right first call against a production environment.
And roles and organizations are restored alongside users, because a user without
their roles is a different account from the one that was backed up.

<Warning>
`dry_run` before `replace` is not optional caution. A `replace` restore overwrites
the environment's identities wholesale, and the exported document contains password
hashes — so the backup file itself is sensitive and should be stored accordingly.
`/operate/backup-and-restore` covers the wider backup story.
## The five emails, and when they are sent

Account administration reaches users by email in five cases, and each has a
different lifetime and a different trigger. Knowing which is which explains why a
user who "didn't get the reset email" may in fact have completed a reset you never
sent.

| Kind | Sent when | Link lifetime |
| --- | --- | --- |
| `verify` | Sign-up with verification required, or a re-request | 24 hours |
| `recovery` | A reset request | 1 hour |
| `magic` | A magic-link sign-in request | 15 minutes |
| `invite` | Someone is invited to an organization | 7 days |
| `email_change` | A user requests a new address | 24 hours |

Two of these are administrative in practice. `invite` is the only one a user
generates for someone else, and `email_change` is the only one that does **not**
grant access — completing it changes the address and nothing else.

### Defaults and overrides

Each kind has a built-in subject and body, and an environment can replace either
under `emails: {kind: {subject, text}}` in its auth configuration. The defaults
name the real lifetimes in the copy itself — the recovery message says the link
"works once, for an hour", and the magic message says fifteen minutes — so if you
override the text, keep that promise accurate.

Placeholders available in subject and body:

| Placeholder | Available in |
| --- | --- |
| `{project}` | All five |
| `{email}` | All five |
| `{link}` | All five |
| `{organization}` | `invite` only |
| `{role}` | `invite` only |

<Info>
An unknown placeholder is left in the message **literally** rather than raising an
error. So a typo shows up as visible `{organiztion}` text in the delivered mail
instead of failing silently — which is a deliberate choice, and a genuinely useful
one when debugging a template.
</Info>

Delivery goes through the platform's mail service, so it uses the environment's own
SMTP settings. The plain-text body is also HTML-escaped, newlines become `<br>`,
and the `{link}` value is turned into an anchor — so one template serves both
plain-text and HTML mail. `/mail/templates` covers the wider template system.

<Warning>
Overriding a template replaces the whole subject or body; it is not merged with the
default. If you supply a subject and no body, the built-in body still applies — so a
half-written override produces a message whose text contradicts its subject.
</Warning>

### What the default recovery message tells you

The built-in recovery copy states that the link works once and for an hour, and
that an unsolicited request means the password is unchanged. Both halves are
load-bearing, and both are visible to the user:

- "works once" is enforced by the row's `used_at`, not just by the signature.
- "your password is unchanged" is accurate because a request does not modify the
  account — only completing the link does.

That is why requesting a reset for someone who has no account, or for a disabled
one, produces the same outward response and no email at all: the enumeration defence
is not a cosmetic uniform response, it is what actually happens.

## Where user administration meets everything else

The admin routes manage identity; the rest of the platform consumes it. The joins
below are where a change in one shows up in the other.

### Policies read what you grant

A permission you grant on a user is only useful if a policy checks it. The claim is
`$auth.permissions`, and the token's own name is `perms` — the same rename that
appears across the platform.

Because the claim is read at token issue, a permission granted now reaches the user
on their **next refresh**. A policy that denies a permission will keep allowing the
user until then, which reads as a policy bug and is actually a token snapshot.

`/policies/context` documents the claim namespace, including why a wrong key name
produces a condition that passes for everyone.

### Storage scopes by user and organization

Per-user and per-tenant storage policies read `$auth.user_id` and `$auth.org`
directly. Removing a member from an organization therefore narrows their storage
access on their next refresh — the same refresh-lag rule as everywhere else.

`/storage/access` covers the bucket policy patterns.

### Flows and jobs react to user events

The events this page's routes emit are ordinary platform events, so a flow can
trigger on them:

| Event | A flow might use it to |
| --- | --- |
| `user.created` | Provision default records, or start an onboarding sequence |
| `user.verified` | Activate the account in application-side tables |
| `user.disabled` | Suspend a subscription or cancel scheduled work |
| `user.deleted` | Purge application data you keyed by that user id |
| `user.mfa_reset` | Require re-verification before trusting the account again |

`user.created` carries `method`, so a flow can distinguish an admin-provisioned
account from a self sign-up and apply different onboarding.

<Warning>
Disabling an account revokes sessions but does not stop a **scheduled job** that acts
on that user's data. Jobs run with service authority and no user token, so pairing a
`user.disabled` subscription with cancelling the relevant schedule is the only way to
stop unattended work. `/flows/triggers` covers the subscription mechanics.
</Warning>

### Auditing what happened

Every state-changing action here emits an event, and `/operate/audit-log` covers
the platform-wide view. For authentication specifically, the environment events route
and the per-user history are the two granular sources, and both are read-only —
there is no way to alter an event, which is what makes them useful as evidence.

### The four actions worth scripting

If you are automating any of this, these are the ones that come up, and the
detail that matters for each:

**Provisioning** needs an explicit `email_verified`, because the route defaults it to
true and a script that omits it produces verified accounts by accident.

**Offboarding** should send `{"disabled": true}` rather than deleting, so the
account and its history survive. Add an MFA reset only if the user actually had MFA
enrolled — resetting unconditionally is harmless but emits a misleading event.

**Lockout clearing** is `{"unlock": true}`, which is idempotent and safe to send
speculatively. It clears both the counter and the timestamp.

**Role changes** need the full list. Read the user's current roles, add, and send
the union — because the field is authoritative and a partial list silently strips
the rest.

<Warning>
Script **Disable** rather than **Delete** by default. Deletion releases the email
address and cannot be undone, which is rarely what an automation script should
decide on its own. Make deletion a deliberate, separately confirmed step.
</Warning>
