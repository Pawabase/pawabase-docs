The whole flow against a configured environment, including the parts that are easy to get wrong.

Assume `acme/production` has `password_policy: "strict"`, `password_min_length: 12`, and `site_url: "https://app.acme.test"`.

### The request

A person on the sign-in screen clicks "Forgot your password", enters `Grace@Example.com`, and submits.

```bash
curl -X POST "https://api.example.com/auth/v1/recover" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{"email": "Grace@Example.com", "redirect_to": "https://app.acme.test/welcome"}'
```

The address is normalised to `grace@example.com`, matched against production's accounts, and found. The account is not disabled, so a `recovery` token is issued with `expires_at` an hour out, and the message is handed to the environment's mail service.

The response is the same body a nonexistent address would get:

```json
{ "sent": true, "message": "If the address has an account, a message is on its way." }
```

Your interface now shows *"If that address has an account, a message is on its way."* — which is true, and is the only claim it can safely make.

### The link

```text
https://app.acme.test/auth/callback?token=UmVjb3Zlcnkt…&type=recovery&redirect_to=https%3A%2F%2Fapp.acme.test%2Fwelcome
```

Three query parameters, and your page reads all three:

| Parameter | Use |
| --- | --- |
| `token` | Post it to `/auth/v1/recover/confirm`. |
| `type` | Dispatch. `recovery` selects the new-password form. |
| `redirect_to` | Where to send the person after a successful reset. Already allowlist-checked when the request was made. |

### A first attempt that fails the policy

The person types `hunter2hunter2` — fifteen characters, but the strict validator has other requirements.

```bash
curl -X POST "https://api.example.com/auth/v1/recover/confirm" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{"token": "UmVjb3Zlcnkt…", "password": "hunter2hunter2"}'
```

```json
{
  "detail": {
    "message": "the password does not meet the policy",
    "problems": ["Password must be at least 12 characters.", "Password must not be a common password."]
  }
}
```

The policy check ran before the consume, so **the token is still valid**. Your form stays open, shows the problems, and lets them try again with the same link. This is the behaviour that separates a usable recovery flow from an unusable one.

### A second attempt that succeeds

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "bearer",
  "expires_in": 900,
  "expires_at": 1750000900,
  "session_id": "a41c8f0d3e7b49a2",
  "org": null,
  "org_role": null,
  "user": {
    "id": "01JQ7Z3M9K4YB2XQ8V0N5T6RJPD",
    "email": "grace@example.com",
    "username": "grace",
    "email_verified": true,
    "roles": ["customer"],
    "mfa_enabled": false
  }
}
```

What just happened, in order:

| Step | Result |
| --- | --- |
| Password replaced | A new hash, written through the user model. |
| Lockout cleared | `failed_logins` zero, `locked_until` null. |
| Every session revoked | Including the one this device might have had. |
| Activity recorded | A `password_reset` event, method `recovery`. |
| Event published | `user.password_reset`. |
| New session issued | Returned in the response above. |

Your page stores the tokens and sends them to `https://app.acme.test/welcome`. They are signed in, and every other device is signed out.

### A third attempt, from a stale tab

The person has the link open in two tabs. They complete the reset in the first, then submit the old form in the second.

```bash
curl -X POST "https://api.example.com/auth/v1/recover/confirm" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{"token": "UmVjb3Zlcnkt…", "password": "another-long-one"}'
```

```json
{ "detail": "the link is invalid or has expired" }
```

Correct behaviour. The token was spent by the first reset. Your page should say the link is no longer valid and offer a new one — not tell them their new password failed, which is a different problem with a different fix.

<Warning>
This is the case that produces the worst support tickets, because from the person's point of view they did nothing wrong and the link says it is broken. Phrase it as "This link has already been used", which is accurate, and give the sign-in link rather than a resend — their password has probably already been changed successfully.
</Warning>

### Checking the result

Studio's **Sign-in activity** tab will show the request and the reset as two rows:

| When | Event | Email | Result | IP |
| --- | --- | --- | --- | --- |
| 09:14:02 | `recovery_requested` | `grace@example.com` | `ok` | 198.51.100.17 |
| 09:16:40 | `password_reset` | `grace@example.com` | `ok` | 198.51.100.17 |

An administrator-triggered password set leaves no row in this tab at all, which is worth knowing when auditing. If you need to distinguish the two paths, subscribe to `user.password_reset`: the recovery link emits it and the administrator path does not.


## Studio

Recovery has no tab of its own, because a reset is something a person does rather than something an operator manages. What an operator needs is the ability to see that it happened and to fix the cases it cannot reach.

Open **Users & auth**. The tabs are **Users**, **Roles**, **Organizations**, **Sign-in activity**, and **Configuration**.

### The user view

In the **Users** tab, open the account. The admin view carries the fields that answer recovery questions:

| Field | Reading it |
| --- | --- |
| `has password` | False means the account has never had one and password sign-in can never work. Recovery is the fix. |
| `locked_until` | A timestamp while the account is locked out. Recovery clears it. |
| `disabled` | True means no reset message will be sent. Recovery cannot fix this; **Enable** can. |

The actions available on the user are **Disable**, **Enable**, **MFA reset**, **Signed out everywhere**, **Session revoked**, **Password set**, **New role**, and **Verify email**.

**Password set** is the operator's path to the same outcome as a recovery link: it replaces the password, subject to the same policy check. It is the right tool when someone has lost access to their mailbox entirely.

Three differences from a recovery reset are worth knowing, because they change what a support agent can promise:

| | Recovery link | **Password set** |
| --- | --- | --- |
| Proves control of the mailbox. | Yes. | No. |
| Clears `failed_logins` and `locked_until`. | Yes, always. | Only if **unlock** is also sent. |
| Revokes existing sessions. | Yes, every one of them. | No. Use **Signed out everywhere** separately. |
| Writes a `password_reset` activity event. | Yes. | No. |
| Emits | `user.password_reset` | nothing. |

<Warning>
**Password set** is the broadest action available on a user, and it bypasses the mailbox check completely. If you use it, follow it with **Signed out everywhere** — otherwise a suspected compromise remains a valid session even though the password has changed.
</Warning>

### The Sign-in activity tab

The tab has a failures-only checkbox and columns **When**, **Event**, **Email**, **Result**, **IP**. The two rows that matter for recovery are:

| Event | Meaning | Result when it succeeds |
| --- | --- | --- |
| `recovery_requested` | A reset message was genuinely produced and sent. | `ok` |
| `password_reset` | A password was replaced, by link or by an administrator. | `ok` |

A `recovery_requested` row is proof that a message left the platform. The absence of one, for an address someone says they requested, means nothing was sent — because that event is written only on the branch that actually sends.

Because an administrator's **Password set** writes no activity event, a `password_reset` row in this tab always means a mailbox recovery link was used. That makes the tab a reliable answer to "did they use the link, or did an operator change it?"

<Note>
Failures of the *confirmation* step do not produce a login event. A mistyped password that fails the policy check is a `422` and writes nothing, because nothing about the account changed. That is why a person can retry several times without filling the activity log.
</Note>

### The backup angle

An environment's backup covers users with their password hashes, so a restore into a fresh environment preserves everyone's ability to sign in. It also preserves which accounts had no password, because that is a property of the stored hash rather than of the flow. See [Backup and restore](/studio/backups).


## What goes wrong

### "The link is invalid or has expired" on a link that was just sent

The causes, most likely first:

| Cause | How to tell |
| --- | --- |
| Wrong environment on the confirming request. | The context header's project/env differs from the environment the message came from. |
| The token was already consumed. | A `password_reset` event exists at about that time. |
| More than an hour has passed. | Check `expires_at` in `akz_one_time_tokens`. |
| The signing secret was rotated. | Every outstanding link across every environment fails at once. |
| A mail client's link preview fetched it. | The row has a `used_at` with no matching `password_reset` event. |

That last row is worth understanding. A preview fetch consumes the token without resetting anything, so the row shows as used and no reset event exists. It is the most confusing failure mode because the token was spent by something that looked like success.

### The message never arrives

Nothing about the flow tells you which of these it is, so check in order:

1. Is the account disabled? The route sends nothing and says nothing.
2. Does the address have an account in *this* environment? A staging account gets a staging reset.
3. Is the environment's mail configured? The transport lives in the API.
4. Was the rate limit hit? Ten per minute, and a burst from a shared NAT can exhaust it.

### The password is rejected and the person is sure it is right

The policy check runs before the consume, so a rejected password means the policy, not the token. Read the `problems` array — under `strict` there is more than one thing that can be wrong, and the array tells you which.

A frequent source of confusion: staging and production have different policies. A password that worked in staging can be rejected in production by the same form, at the same moment, from the same person.

### The person cannot sign in after a successful reset

| Symptom | Cause | Fix |
| --- | --- | --- |
| `403 this account is disabled` | The account was disabled before the reset. | **Enable** in Studio. |
| `429 too many failed attempts` | Only possible if the reset did not happen — the reset clears this. | Wait, or **Enable**. |
| `400 invalid email or password`, `has password` false | The reset did not complete. | Request a fresh link. |
| `400 invalid email or password`, `has password` true | The wrong password, or the account is in another environment. | Check which environment. |

### The form says it worked but nothing happens

Almost always the `400` on a second submit, described in the worked example. The fix is a redirect to sign-in rather than an error message, because the password has probably already changed.

### Recovery seems to do nothing at all

Check the shape of the address. Recovery normalises to lowercase, so an address that exists only with capitals in the database will not match — although Akountz normalises on write, so this should only appear in data imported from elsewhere.

### The session in detail

Three things about the returned session are worth knowing before you build against it.

**`org` and `org_role` are null.** The recovery flow never asks for an organization, so a session started this way is always org-less. If your product scopes data by organization, the person will need to refresh with an `org` to switch the session over. See [Organizations](/auth/organizations/overview).

**`roles` and `perms` are read at issue time.** They reflect the account's grants at the moment of the reset. A role changed an hour ago appears; one changed a second ago does not, until the next refresh.

**The refresh token is long-lived.** Its lifetime is the environment's `refresh_ttl`, 30 days by default. It is an ordinary refresh token in every respect, and rotating it later follows the standard path.
