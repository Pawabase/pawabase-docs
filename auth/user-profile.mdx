The profile is what you know about a person: name, picture, email and any extra details. People edit their own from your app; you and your team can edit anyone's in Studio.

## Read the profile

<CodeGroup>
```typescript TypeScript
const user = await pawabase.auth.getUser();
user.name; user.email; user.avatar_url; user.user_metadata; user.roles; user.identities;
```

```python Python
user = pb.auth.get_user()
user["name"], user["email"], user["avatar_url"], user["user_metadata"]
```
</CodeGroup>

`getUser` asks the server; the session's `user` is a cached copy that can be a few minutes old.

## Update it

<CodeGroup>
```typescript TypeScript
await pawabase.auth.updateUser({
  name: "Ada Lovelace",
  avatar_url: "https://…/ada.png",
  data: { theme: "dark", notifications: { email: true } },   // merged into user_metadata
});
```

```python Python
pb.auth.update_user(
    name="Ada Lovelace",
    avatar_url="https://…/ada.png",
    data={"theme": "dark", "notifications": {"email": True}},
)
```
</CodeGroup>

`data` is **merged** into `user_metadata` one level deep: top-level keys you send replace those keys, others stay. A nested object is replaced as a whole, so send all of `notifications`, not just the part that changed. Setting a key to `null` stores `null`; the key itself stays (your server can remove keys by replacing the whole object with the admin client).

A successful update fires `USER_UPDATED`, so components listening with `onAuthStateChange` refresh themselves. The server event is `user.updated`, with `changed` listing what changed (`name`, `avatar_url`, `user_metadata`, `password`, `email (pending confirmation)`). Profile edits also appear in the person's [sign-in activity](/auth/sign-in-activity) as `profile_updated`.

Values in `data` are checked against your [sign-up form](/auth/sign-up-form-and-attributes): only the keys you send, and nothing is required. Problems answer `422` with every message in `problems`:

```json
{ "message": "the profile is not valid", "problems": ["Website must be a web address starting with https://", "plan can only be changed by an administrator"] }
```

Attributes marked admin-only can't be changed by the person once they have a value.

| Field | Limit |
| --- | --- |
| `name` | 200 characters |
| `avatar_url` | 2,048 characters. Any address; use `setAvatar` to upload instead |
| `data` | Checked as above |

## Two kinds of custom data

| Field | Who can change it | Use it for |
| --- | --- | --- |
| `user_metadata` (Public metadata in Studio) | The person | Preferences, display settings, onboarding state |
| `app_metadata` and `roles` (Private metadata) | Only your server and Studio | Plans, permissions, anything a rule trusts |

Never base access on `user_metadata`.

## An avatar

Send the picture to Pawabase and it does the rest: it stores the image in a public `avatars` bucket (made for you the first time, if the environment has none), points `avatar_url` at it, and removes the previous picture.

<CodeGroup>
```typescript TypeScript
// `file` is a File from <input type="file">, or any Blob
const user = await pawabase.auth.setAvatar(file);
user.avatar_url;   // https://…/storage/v1/files/production/avatars/<user id>/….png

await pawabase.auth.removeAvatar();
```

```python Python
user = pb.auth.set_avatar(open("ada.png", "rb"))   # bytes, an open file or a Path
user["avatar_url"]

pb.auth.remove_avatar()
```
</CodeGroup>

The picture must be a PNG, JPEG, WebP or GIF, and at most 2 MB. A wrong type is `415`, a file that is too large is `413`, and the bucket also checks what the file really is, not only what it is called. Pictures are served from the gateway with no key, so an `<img src={user.avatar_url}>` just works. A sign-in with Google or GitHub still fills `avatar_url` with the provider's picture until the person uploads their own; a picture you did not upload is never deleted.

An administrator can do the same for anyone with the secret key: `PUT` or `DELETE /admin/v1/envs/{env}/users/{id}/avatar`.

### Where pictures live, and changing it

The bucket is a normal [storage bucket](/storage/overview), so you can open it in Studio and change its size limit, image types or caching, or rename it. Only the server writes to it: its write policy is `service`, so your app cannot upload there directly and one person cannot overwrite another's picture. Reads are public.

Three settings under the environment's `auth.directory.avatars` control it:

| Setting | Default | What it does |
|---|---|---|
| `enabled` | `true` | Turn profile pictures off. Uploads answer `403`; `avatar_url` can still be set to an address. |
| `bucket` | `avatars` | The bucket to use. Point it at a bucket of your own and it is used as it is; nothing is created. |
| `max_kb` | `2048` | The largest picture, from 16 to 10240 KB. |

<CodeGroup>
```typescript TypeScript
await manage(pawabase).environments.update("production", {
  auth: { directory: { avatars: { bucket: "profile-pictures", max_kb: 1024 } } },
});
```

```python Python
pb.manage.environments.update("production", auth={"directory": {"avatars": {"bucket": "profile-pictures", "max_kb": 1024}}})
```
</CodeGroup>

`pawabase` / `pb` are clients made with the environment's **secret** key. In [infrastructure as code](/iac/overview) the same settings live in `EnvironmentSettings(auth=Auth(...))`.

Changes take effect within about ten seconds.

## Change the email

<CodeGroup>
```typescript TypeScript
await pawabase.auth.updateUser({ email: "new@example.com" });
```

```python Python
pb.auth.update_user(email="new@example.com")
```
</CodeGroup>

Nothing changes yet: a **Confirm a new address** link goes to the new address, and the email changes when it's opened (within 24 hours). The answer's `changed` includes `email (pending confirmation)`. An address another account uses answers `409` "that email is in use". See [Email verification](/auth/email-verification#changing-the-email-later) and [Redirect URLs](/auth/redirect-urls) for handling the link.

## Change the password

Pass the current password with the new one (required for accounts that have one):

<CodeGroup>
```typescript TypeScript
await pawabase.auth.updateUser({ current_password: "old", password: "a new long passphrase" });
```

```python Python
pb.auth.update_user(current_password="old", password="a new long passphrase")
```
</CodeGroup>

- `current_password` is required when the account already has a password; a wrong one answers `400` "current_password is wrong". An account without one (signed up with a link, code or social sign-in) can set a first password without it.
- The new password must satisfy the [password policy](/auth/password-policy), including previous-password rules; refusals are `422` with `problems`.
- `user.password_changed` fires, and the person gets the **Password changed** email unless **Users & auth → Protection → Account recovery → Email the person when their password is changed or reset** is off.
- Other sessions stay signed in. To sign them out too, follow with `signOut({ scope: "others" })` ([Sessions](/auth/sessions)), or offer it as a checkbox.

### What a user API key can't change

A request made with a [user API key](/auth/user-api-keys) can update the name, picture and metadata, but changing the **password or email** answers `403` "an API key cannot change a password or email": those need a real sign-in.

## A profile form

```typescript
import { ValidationError } from "@pawabase/client";

async function save(form: { name: string; theme: string }): Promise<string[]> {
  try {
    await pawabase.auth.updateUser({ name: form.name, data: { theme: form.theme } });
    return [];
  } catch (e) {
    if (e instanceof ValidationError) {
      const problems = (e.body as { problems?: string[] })?.problems;
      return problems ?? Object.values(e.byField()).flat();   // form rules, or a malformed field such as a too-long name
    }
    throw e;
  }
}
```

## In Studio

**Users & auth → People → Users →** the person **→ Profile.** Edit the name; upload, change or remove the picture; edit **Public metadata** and **Private metadata** as JSON (each saved separately, replacing the whole object). Email and username are shown read-only: the person changes their email themselves, with confirmation.
