Authentication is the part of a backend you touch from every surface at once: a browser tab, a phone, a cron job, and your own API. This page is the integration guide for all four — what to send, where to keep the tokens, how to refresh them, and what happens when something goes wrong.

<Note>
**This page documents the wire protocol so it remains useful outside the TypeScript SDK.** The
official `@pawabase/client` package manages authentication and refresh for JavaScript and TypeScript;
see [JavaScript and TypeScript](/clients/javascript). The official Python client is server-oriented
and does not implement application-user auth. Mobile and Python auth integrations therefore use the
REST exchange described here with their platform HTTP client.
</Note>

<CardGroup cols={3}>
  <Card title="One endpoint" icon="key-round">`POST /auth/v1/token` handles sign-in, refresh and MFA. There is no `/oauth/token`.</Card>
  <Card title="Rotation is mandatory" icon="refresh">Every refresh returns a new refresh token and consumes the old one. Store both, atomically.</Card>

## What you are building on

Three layers, and it matters which one you are talking to.

| Layer | What it does for a client | What it issues |
| --- | --- | --- |
| The gateway | Resolves your API key, enforces CORS and rate limits, forwards the request | Nothing |
| Akountz | Verifies credentials, runs the session lifecycle, owns `akz_*` tables | The token pair |
| Every other service | Verifies the bearer token on each request | Nothing |

A client only ever talks to the gateway. Akountz is reachable at `/auth/v1/*` through the same public address; it is never a separate host you configure.

Two headers, two questions:

| Header | Answers | When |
| --- | --- | --- |
| `apikey` | Which project and environment, and with what role | Every request, always |
| `Authorization: Bearer <access_token>` | Who specifically is calling | Only when a policy needs identity |

```text
GET /auth/v1/user HTTP/1.1
Host: api.yourapp.com
apikey: pb_pk_9f2c3d1a4b8e...
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

<Warning>
Never send a **secret** key (`pb_sk_…`) from a browser, a mobile binary, or any repository. It is a service credential: the policy engine allows every request made with it before evaluating anything. A leaked secret key makes every policy in your project irrelevant. The [publishable key](/clients/overview#the-two-kinds-of-api-key) is designed to be public — leak that one and the worst case is a caller acting as an ordinary signed-in user, which your policies already handle.
</Warning>

## The one endpoint

`POST /auth/v1/token` is the entire grant surface:

```python
class TokenRequest(BaseModel):
    grant_type: Literal["password", "refresh_token", "mfa"] = "password"
    email: str | None = None
    password: str | None = None
    refresh_token: str | None = None
    mfa_token: str | None = None
    code: str | None = None
    #: An organization slug the tokens should be issued for. On refresh, switches
    #: the session's organization (``null`` leaves it); omit to keep it.
    org: str | None = Field(default=None, max_length=63)
```

Three grants, three field sets:

| `grant_type` | Requires | Use for |
| --- | --- | --- |
| `password` | `email`, `password` | Signing in |
| `refresh_token` | `refresh_token` | Getting a new pair, and switching organization |
| `mfa` | `mfa_token`, `code` | Completing a second factor |

`grant_type` may also be given as a **query parameter**, which takes precedence over the body — the route reads `ctx.query_params.get("grant_type") or body.grant_type`. Both work; pick one and be consistent.

There is no `grant_type=authorization_code`. There is no `/oauth/token`. There is no client-credentials grant for your own application — that is what the secret key is for.

### The response

Every successful grant returns the same body:

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "refresh_token": "8f2c9e4a7b1d...",
  "token_type": "bearer",
  "expires_in": 900,
  "expires_at": 1772000000,
  "session_id": "9f2c4a7b1d3e5f6a8b0c2d4e6f8a1b3c5d7e9f1a3b5c7d9e1f3a5b7c9d1e3f5a7b",
  "org": null,
  "org_role": null,
  "user": {
    "id": "01JX9K2M4P7Q8R3S5T6U7V8W9X",
    "email": "ada@example.com",
    "username": "ada",
    "name": "Ada Lovelace",
    "email_verified": true,
    "roles": ["editor"],
    "mfa_enabled": false,
    "…": "…"
  }
}
```

| Field | Use |
| --- | --- |
| `access_token` | The `Authorization: Bearer` value. Short-lived |
| `refresh_token` | Exchange for a new pair. **Changes every refresh** |
| `expires_in` | Seconds until the access token expires |
| `expires_at` | Absolute expiry as a Unix timestamp — easier to compare than adding `expires_in` |
| `session_id` | The token family id, reported as the `sid` claim |
| `org`, `org_role` | The selected organization and your role in it |
| `user` | The full user view — handy for populating a UI without a second request |

<Note>
`expires_at` is `int(datetime.now(UTC).timestamp()) + config.access_ttl`, computed on the server. Comparing against it in the client avoids clock-skew problems that arise from adding `expires_in` to the browser's own clock.
</Note>

## Signing in

```bash
curl -X POST "$GW/auth/v1/token?grant_type=password" \
  -H "apikey: $PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{"email": "ada@example.com", "password": "correct horse battery staple"}'
```

### Sign-up first

`POST /auth/v1/signup` creates the account and, unless verification is required, signs the user straight in:

```python
@r.post("/signup", request_model=SignUp, middleware=limits, summary="Create an account")
async def signup(ctx: HttpContext, body: SignUp):
    config = await config_for(akountz, ctx)
    if not config.signup_enabled:
        raise HTTPException(status_code=403, detail="sign-up is disabled")
    if body.redirect_to and not config.redirect_allowed(body.redirect_to):
        raise HTTPException(status_code=400, detail="redirect_to is not an allowed URL")
    user = await create_account(
        config,
        email=body.email,
        password=body.password,
        username=body.username,
        name=body.name,
        user_metadata=body.data,
    )
    await akountz.emit(
        config.project,
        config.env,
        "user.created",
        {"user_id": str(user.id), "email": user.email, "method": "password"},
        actor=str(user.id),
    )
    if config.require_email_verification:
        token = await links.issue(akountz, config, "verify", user=user)
        await emails.send(
            akountz,
            config,
            "verify",
            user.email,
            link=links.link(config, "verify", token, body.redirect_to),
        )
        return created(
            {"user": await user_view(user), "session": None, "verification_required": True}
        )
    session = await start_session(akountz, config, user, method="password", ctx=ctx)
    return created({**session, "verification_required": False})
```

Two shapes come back, and a client must handle both:

```json
{ "user": { "…": "…" }, "session": null, "verification_required": true }
```

```json
{ "access_token": "…", "refresh_token": "…", "…": "…", "verification_required": false }
```

<Warning>
The `session` key is **`null`** when verification is required. A client that reads `response.session.access_token` unconditionally will throw on the verification path. Branch on `verification_required`, or on `session === null`.
</Warning>

The sign-up body:

```python
class SignUp(BaseModel):
    email: str = Field(max_length=255)
    password: str = Field(min_length=1, max_length=1024)
    username: str | None = Field(default=None, max_length=150)
    name: str = Field(default="", max_length=200)
    data: dict[str, Any] = Field(default_factory=dict, description="Initial user_metadata")
    redirect_to: str | None = None
```

`data` becomes `user_metadata`, which the user can later edit themselves — so never use it for an entitlement. See [`meta` versus `app`](/auth/auth-in-policies#meta-versus-app).

### What sign-in can refuse, and how

The order of checks in the `password` grant determines which error you get:

```python
email = normalise_email(body.email)
user = await find_by_email(config.project, config.env, email)
refusal = HTTPException(status_code=400, detail="invalid email or password")
if user is None:
    await log_event(..., reason="unknown email", ctx=ctx)
    raise refusal
if is_locked(user):
    await log_event(..., reason="locked", ctx=ctx)
    raise HTTPException(status_code=429, detail="too many failed attempts; try again later")
if not user.check_password(body.password):
    await record_failure(
        user, akountz.settings.lockout_threshold, akountz.settings.lockout_minutes
    )
    await log_event(..., reason="wrong password", ctx=ctx)
    raise refusal
if user.is_disabled:
    await log_event(..., reason="disabled", ctx=ctx)
    raise HTTPException(status_code=403, detail="this account is disabled")
if config.require_email_verification and user.email_verified_at is None:
    raise HTTPException(status_code=403, detail="confirm your email address first")
```

| Status | Detail | What the client should do |
| --- | --- | --- |
| `400` | `invalid email or password` | Wrong credentials — the same message for an unknown email and a wrong password, deliberately |
| `422` | `a valid email address is required` | The email failed normalisation; a client bug, not a user error |
| `429` | `too many failed attempts; try again later` | Locked out. Back off; do not retry in a loop |
| `403` | `this account is disabled` | Show the message, offer support |
| `403` | `confirm your email address first` | Send them to the verification flow |
| `200` | `{ "mfa_required": true, … }` | Not an error — continue to the MFA branch |

<Note>
An unknown email and a wrong password produce the **identical** `400 invalid email or password`. That is correct: a different response for "no such account" is an account-enumeration oracle.
</Note>

### The MFA branch

If the user has MFA enabled and the environment allows it, a successful password check returns a challenge instead of a token pair:

```python
if user.mfa_enabled and config.mfa_enabled:
    await require_membership(config, user, body.org)
    challenge = await links.issue(
        akountz, config, "mfa", user=user, data={"method": "password", "org": body.org}
    )
    await log_event(config.project, config.env, "mfa_challenge", user=user, ctx=ctx)
    return {
        "mfa_required": True,
        "mfa_token": challenge,
        "factors": ["totp", "recovery_code"],
    }
```

Complete it with the `mfa` grant:

```json
{ "grant_type": "mfa", "mfa_token": "…", "code": "123456" }
```

```python
async def _complete_mfa(ctx: HttpContext, config: AuthConfig, body: TokenRequest):
    if not body.mfa_token or not body.code:
        raise HTTPException(status_code=400, detail="mfa_token and code are required")
    row = await links.consume(akountz, config, "mfa", body.mfa_token, peek=True)
    user = row.user
    if user is None or user.is_disabled:
        raise HTTPException(status_code=400, detail="the challenge is no longer valid")
    used = await mfa.verify(akountz, user, body.code)
    if used is None:
        await record_failure(
            user, akountz.settings.lockout_threshold, akountz.settings.lockout_minutes
        )
        await log_event(..., kind="mfa_verify", reason="wrong code", success=False, ctx=ctx)
        raise HTTPException(status_code=400, detail="the code is not valid")
    ...
    session = await start_session(
        akountz, config, user, method=method, ctx=ctx, aal="aal2", org=org
    )
    session["mfa_method"] = used
    return session
```

Three things a client must know:

1. **`mfa_token` is single-use and expires in five minutes** — `LIFETIMES["mfa"] = 300`. A wrong code does *not* consume it, so the user keeps their remaining attempts; a successful one does, so a retry after success returns `400 the challenge is no longer valid`.
2. **A wrong MFA code counts toward account lockout** — `record_failure` is called, the same counter as a wrong password.
3. **The success response has an extra `mfa_method`**, either `"totp"` or `"recovery_code"`.

```json
{
  "access_token": "…",
  "refresh_token": "…",
  "aal": "…",
  "mfa_method": "totp",
  "org": null,
  "org_role": null
}
```

## Refreshing, and what rotation really means

There is **no background refresh**. Nothing in the gateway renews your access token for you. When it expires, every request with it returns `401`, and the client is responsible for exchanging the refresh token and retrying.

### Rotation

`refresh_token_pair` issues a brand-new pair inside the *same* family:

```python
async def refresh_token_pair(
    self, refresh_token: str, secret: str, algorithm: str = "HS256"
) -> dict:
    token = _jwt_token()
    tokens = TokenForUser(self, secret=secret, algorithm=algorithm)
    try:
        payload = tokens.verify_no_expire(refresh_token)
    except Exception:
        raise ValueError("Invalid refresh token") from None
    existing = await token.filter(token_jti=payload.get("jti", refresh_token)).first()
    if existing is None or existing.token_type != "refresh":
        raise ValueError("Unknown refresh token")
    if existing.revoked:
        await token.revoke_family(existing.token_family)
        raise ValueError("Token family has been revoked — possible token theft")
    if existing.consumed_at is not None:
        await token.revoke_family(existing.token_family)
        raise ValueError("Refresh token already consumed — possible token theft")
    await existing.consume()
    access_ttl, refresh_ttl = timedelta(minutes=15), timedelta(days=7)
    access_jti, refresh_jti = secrets.token_hex(16), secrets.token_hex(16)
    access = tokens.access_token(access_ttl, jti=access_jti)
    refresh = tokens.refresh_token(refresh_ttl, jti=refresh_jti)
    now = datetime.now(UTC)
    await self._record_pair(
        existing.token_family, (access_jti, now + access_ttl), (refresh_jti, now + refresh_ttl)
    )
    return {
        "access_token": access,
        "refresh_token": refresh,
        "token_type": "bearer",
        "token_family": existing.token_family,
    }
```

Note `token_family: existing.token_family` — the family id is **stable** across the session's whole life. `session_id` in your responses never changes; the two tokens inside it change every time.

<Warning>
The old refresh token is **consumed**, not merely replaced. If your client sends the same refresh token twice — two tabs racing, a retry after a timeout, a duplicated request — the second one hits the `consumed_at is not None` branch and takes down the entire family.
</Warning>

### Theft detection

That second-refresh case is treated as theft, deliberately. Two branches revoke the whole family:

| Condition | Raised |
| --- | --- |
| `existing.revoked` | `Token family has been revoked — possible token theft` |
| `existing.consumed_at is not None` | `Refresh token already consumed — possible token theft` |

Both call `revoke_family` before raising. And `refresh_session` reacts to it:

```python
try:
    pair = await user.refresh_token_pair(
        refresh_token, akountz.refresh_secret(config.project, config.env)
    )
except ValueError as exc:
    await log_event(
        config.project,
        config.env,
        "refresh",
        user=user,
        method="refresh_token",
        success=False,
        reason=str(exc),
        ctx=ctx,
    )
    if "theft" in str(exc):
        row = await JWTToken.filter(token_jti=claims.get("jti") or "").first()
        if row is not None:
            await SessionInfo.filter(family=row.token_family).update(
                revoked_at=datetime.now(UTC)
            )
        await akountz.emit(
            config.project,
            config.env,
            "session.reuse_detected",
            {"user_id": str(user.id)},
            actor=str(user.id),
        )
    raise HTTPException(status_code=401, detail="invalid refresh token") from exc
```

Three things to notice:

1. **The client always sees the same `401 invalid refresh token`.** The internal distinction — bad signature, unknown token, revoked family, consumed token — is not leaked. You cannot tell from the response whether theft was detected.
2. **`session.reuse_detected` is emitted.** This is your signal to alert on, and to tell the user their other sessions were signed out.
3. **The `SessionInfo` row is revoked too**, so the session listing in Studio immediately reflects it.

<Warning>
This is the single most important operational fact on this page: **a duplicate refresh is indistinguishable, from the client's side, from a stolen token, and it logs the user out everywhere.** If your client can fire two refreshes concurrently — a React app with two components both hitting a `401`, a mobile app with a background retry, a server handling parallel requests for one user — you must serialise refreshes yourself. See [Serialising refresh](#serialising-concurrent-refreshes).
</Warning>

### When to refresh

Two strategies, both fine:

| Strategy | How | Cost |
| --- | --- | --- |
| Reactive | Wait for a `401`, then refresh and retry once | One failed request per refresh |
| Proactive | Refresh when `expires_at` is within a skew window | No failed requests; more refreshes |

The skew window exists because clocks disagree. Refresh at `expires_at - 60` rather than at `expires_at`:

```text
const SKEW_SECONDS = 60;
function shouldRefresh(session) {
  if (!session?.access_token) return true;
  const secondsLeft = session.expires_at - Math.floor(Date.now() / 1000);
  return secondsLeft <= SKEW_SECONDS;
}
```

A hybrid is common and best: refresh proactively when the skew window is entered, but still handle a `401` by refreshing once and retrying, because a token can be revoked out from under you (an admin signing the user out, a family revocation).

<Info>
Never retry a failed request more than once. If the refresh itself succeeded and the retry still returns `401`, the session is genuinely dead — sign the user out rather than looping.
</Info>

## In a browser

Everything here is plain `fetch`. If you are on JavaScript or TypeScript and would rather not write this yourself, the official `@pawabase/client` package already does all of it — see [JavaScript and TypeScript](/clients/javascript). The code below is the reference implementation, and is what you need on a platform without that package.

### Storing the tokens

The tradeoff, stated honestly:

| Store | Survives reload | Readable by injected script | Verdict |
| --- | --- | --- | --- |
| Module variable | No | No | Best, if you can re-authenticate on reload |
| `sessionStorage` | Per tab | Yes | Reasonable middle ground |
| `localStorage` | Yes, shared across tabs | Yes | Common, weakest against XSS |
| httpOnly cookie set by *your* server | Yes | **No** | Best, if you have a server |

If you have no backend of your own, the honest options are memory or `localStorage`, and the difference is real: **anything in `localStorage` is readable by any script running on your page**, including a successful XSS payload, and a stolen refresh token is valid for `refresh_ttl` — 30 days by default — not for the next hour.

```text
const SKEW_SECONDS = 60;
const STORAGE_KEY = "pawabase.session";

export class PawabaseAuth {
  constructor({ baseUrl, apiKey }) {
    this.baseUrl = baseUrl.replace(/\/$/, "");
    this.apiKey = apiKey;
    this.session = this.#load();
    this.#inflight = null;   // the single-flight promise
  }

  #load() {
    const raw = sessionStorage.getItem(STORAGE_KEY);
    return raw ? JSON.parse(raw) : null;
  }

  #save(session) {
    this.session = session;
    if (session) sessionStorage.setItem(STORAGE_KEY, JSON.stringify(session));
    else sessionStorage.removeItem(STORAGE_KEY);
    return session;
  }

  #expired() {
    if (!this.session?.access_token) return true;
    return this.session.expires_at - Math.floor(Date.now() / 1000) <= SKEW_SECONDS;
  }

  async #post(body) {
    const response = await fetch(`${this.baseUrl}/auth/v1/token`, {
      method: "POST",
      headers: { apikey: this.apiKey, "content-type": "application/json" },
      body: JSON.stringify(body),
    });
    const payload = await response.json().catch(() => null);
    if (!response.ok) {
      const error = new Error(payload?.detail ?? `auth failed (${response.status})`);
      error.status = response.status;
      error.detail = payload?.detail ?? null;
      throw error;
    }
    return payload;
  }

  async signIn({ email, password, org }) {
    // `org` is omitted entirely when there is none — sending null is different.
    const body = { grant_type: "password", email, password };
    if (org) body.org = org;
    const result = await this.#post(body);
    if (result.mfa_required) return result;      // caller must complete MFA
    return this.#save(result);
  }

  async completeMfa({ mfaToken, code }) {
    return this.#save(
      await this.#post({ grant_type: "mfa", mfa_token: mfaToken, code }),
    );
  }

  async #refresh() {
    if (!this.session?.refresh_token) throw new Error("no session");
    return this.#post({
      grant_type: "refresh_token",
      refresh_token: this.session.refresh_token,
    });
  }

  /**
   * Single-flight refresh. Concurrent callers share one in-flight request, so
   * the refresh token is only ever presented once.
   */
  async refresh({ force = false } = {}) {
    if (!force && !this.#expired()) return this.session;
    if (!this.#inflight) {
      this.#inflight = this.#refresh()
        .then((next) => this.#save(next))
        .catch((error) => {
          // 401 here means the family is gone: revoked, or reuse was detected.
          if (error.status === 401) this.clear();
          throw error;
        })
        .finally(() => { this.#inflight = null; });
    }
    return this.#inflight;
  }

  async fetch(path, { method = "GET", body, headers = {}, retry = true } = {}) {
    await this.refresh();
    const token = this.session?.access_token;
    const response = await fetch(`${this.baseUrl}${path}`, {
      method,
      headers: {
        apikey: this.apiKey,
        ...(token ? { authorization: `Bearer ${token}` } : {}),
        ...(body ? { "content-type": "application/json" } : {}),
        ...headers,
      },
      body: body ? JSON.stringify(body) : undefined,
    });

    if (response.status === 401 && retry && this.session?.refresh_token) {
      await this.refresh({ force: true });
      return this.fetch(path, { method, body, headers, retry: false });
    }
    return response;
  }

  clear() {
    this.session = null;
    sessionStorage.removeItem(STORAGE_KEY);
  }
}
```

<Warning>
`sessionStorage` is per-tab and per-origin, which has a useful side effect: two tabs each hold their own copy of the session, and a refresh in one does not invalidate the other's refresh token. `localStorage` is shared, so two tabs refreshing from one stored token will trigger theft detection. If you use `localStorage`, you **must** implement single-flight refresh with cross-tab coordination, or you will log users out at random.
</Warning>

### Signing out

Sign-out is a separate endpoint, not a grant on `/token`:

```python
class Logout(BaseModel):
    scope: Literal["local", "global", "others"] = "local"
```

```python
@r.post(
    "/logout",
    request_model=Logout,
    summary="Sign out this session, all sessions, or all others",
)
async def logout(ctx: HttpContext, body: Logout):
    user, principal = await signed_in_user(ctx)
    current = principal.claims.get("sid")
    if body.scope == "global":
        await revoke_all(user)
    elif body.scope == "others":
        from app.sessions import list_sessions

        for session in await list_sessions(user):
            if session["id"] != current:
                await revoke_session(user, session["id"])
    elif current:
        await revoke_session(user, current)
    await log_event(user.project, user.env, "sign_out", user=user, method=body.scope, ctx=ctx)
    await akountz.emit(
        user.project,
        user.env,
        "session.revoked",
        {"user_id": str(user.id), "scope": body.scope},
        actor=str(user.id),
    )
    return {"signed_out": True, "scope": body.scope}
```

| Scope | Effect |
| --- | --- |
| `local` (default) | Revokes this session only |
| `others` | Revokes every session except this one |
| `global` | Revokes all sessions, including this one |

```text
async signOut(scope = "local") {
  try {
    await fetch(`${this.baseUrl}/auth/v1/logout`, {
      method: "POST",
      headers: {
        apikey: this.apiKey,
        authorization: `Bearer ${this.session.access_token}`,
        "content-type": "application/json",
      },
      body: JSON.stringify({ scope }),
    });
  } finally {
    // Always clear locally, even if the network call failed.
    this.clear();
  }
}
```

```bash
curl -X POST "$GW/auth/v1/logout" \
  -H "apikey: $PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "content-type: application/json" \
  -d '{"scope": "others"}'
```

<Info>
`signOut` needs a **valid access token** — the route calls `signed_in_user`, which refuses with `401 sign in first` without one. If the access token has already expired, sign-out will fail and the session stays alive on the server. In that case, clear locally and let the refresh token lapse, or call it before the token expires.
</Info>

### Reading the current user


## Serialising concurrent refreshes

Because a duplicate refresh revokes the family, this is not an optimisation — it is a correctness requirement for any client that can issue requests in parallel.

### In one tab

The `#inflight` promise in the class above is the whole mechanism. Ten components hitting `401` at once produce **one** network refresh, because the first caller sets `#inflight` and the other nine `await` the same promise.

### Across tabs

`localStorage` is shared, so tabs race. The cheapest correct fix is a storage lock with a short expiry:

```text
const LOCK_KEY = "pawabase.refresh.lock";
const LOCK_TTL_MS = 10_000;

const waitFor = (predicate, timeoutMs) =>
  new Promise((resolve, reject) => {
    const started = Date.now();
    const tick = () => {
      if (predicate()) return resolve();
      if (Date.now() - started > timeoutMs) return reject(new Error("refresh lock timeout"));
      setTimeout(tick, 50);
    };
    tick();
  });

async function withRefreshLock(fn) {
  const now = Date.now();
  const held = JSON.parse(localStorage.getItem(LOCK_KEY) || "null");

  if (held && now < held.until) {
    // Another tab is refreshing. Wait for it to publish a new session.
    await waitFor(() => localStorage.getItem(STORAGE_KEY) !== held.token, 5000);
    return JSON.parse(localStorage.getItem(STORAGE_KEY));
  }

  const lock = { token: localStorage.getItem(STORAGE_KEY), until: now + LOCK_TTL_MS };
  localStorage.setItem(LOCK_KEY, JSON.stringify(lock));
  try {
    return await fn();
  } finally {
    localStorage.removeItem(LOCK_KEY);
  }
}
```

<Info>
Storage locks are advisory — they work because every tab in your app runs this same code. They do not protect against a genuinely malicious script, which would not bother taking the lock. That is precisely why an httpOnly cookie held by your own server is the stronger answer where you have one.
</Info>

### On a server

A server acting on behalf of one user has the same hazard and the same fix: one refresh per user at a time, keyed by user id, with everyone else awaiting the result.

```python
import asyncio
import time
import httpx

REFRESH_LOCKS: dict[str, asyncio.Lock] = {}
SKEW_SECONDS = 60


def _lock_for(user_id: str) -> asyncio.Lock:
    lock = REFRESH_LOCKS.get(user_id)
    if lock is None:
        lock = REFRESH_LOCKS[user_id] = asyncio.Lock()
    return lock


async def get_access_token(user_id: str, session: dict, client: httpx.AsyncClient) -> str:
    """Return a live access token, refreshing at most once per user."""
    async def live() -> bool:
        return session.get("expires_at", 0) - int(time.time()) > SKEW_SECONDS

    if await live():
        return session["access_token"]

    async with _lock_for(user_id):
        # Re-check inside the lock: another coroutine may have refreshed
        # while we waited, and the old refresh token is now consumed.
        if await live():
            return session["access_token"]
        response = await client.post(
            f"{client.base_url}/auth/v1/token",
            headers={"apikey": client.api_key},
            json={"grant_type": "refresh_token", "refresh_token": session["refresh_token"]},
        )
        response.raise_for_status()
        session.update(response.json())
        return session["access_token"]
```

<Warning>
That re-check inside the lock is the part people leave out. Without it, two coroutines queue on the lock, the first refreshes and rotates the token, and the second — using a stale in-memory `session` — presents the consumed refresh token and triggers theft detection against itself.
</Warning>

## On a server with `httpx`

A server-to-server client uses the **secret** key and usually no user token at all. If it does act for a specific user, it forwards that user's access token rather than minting one.

```python
import time
import httpx
from typing import Any


class PawabaseError(Exception):
    def __init__(self, status: int, detail: Any):
        super().__init__(f"Pawabase returned {status}: {detail}")
        self.status = status
        self.detail = detail


def _detail_of(response: httpx.Response) -> Any:
    """Akountz returns the detail as the whole JSON body."""
    try:
        return response.json()
    except ValueError:
        return response.text


class Pawabase:
    """A small, hand-written client. No SDK required."""

    def __init__(self, base_url: str, api_key: str, *, timeout: float = 10.0):
        self.base_url = base_url.rstrip("/")
        self.api_key = api_key
        self._http = httpx.Client(timeout=timeout)

    def close(self) -> None:
        self._http.close()

    def __enter__(self) -> "Pawabase":
        return self

    def __exit__(self, *exc: object) -> None:
        self.close()

    def request(
        self,
        method: str,
        path: str,
        *,
        json: dict | None = None,
        token: str | None = None,
        params: dict | None = None,
    ) -> httpx.Response:
        headers = {"apikey": self.api_key}
        if token:
            headers["authorization"] = f"Bearer {token}"
        response = self._http.request(
            method,
            f"{self.base_url}{path}",
            headers=headers,
            json=json,
            params=params,
        )
        if response.status_code >= 400:
            raise PawabaseError(response.status_code, _detail_of(response))
        return response

    def token(self, **body: Any) -> dict:
        """Any grant on POST /auth/v1/token."""
        body.setdefault("grant_type", "password")
        return self.request("POST", "/auth/v1/token", json=body).json()

    def sign_in(self, email: str, password: str) -> dict:
        return self.token(grant_type="password", email=email, password=password)

    def refresh(self, refresh_token: str, *, org: str | None = None) -> dict:
        body: dict[str, Any] = {
            "grant_type": "refresh_token",
            "refresh_token": refresh_token,
        }
        # Only add `org` when switching. Sending null clears the selection.
        if org is not None:
            body["org"] = org
        return self.token(**body)

    def me(self, access_token: str) -> dict:
        return self.request("GET", "/auth/v1/user", token=access_token).json()

    def sign_out(self, access_token: str, scope: str = "local") -> dict:
        return self.request(
            "POST", "/auth/v1/logout", json={"scope": scope}, token=access_token
        ).json()
```

## On a phone

Mobile has one advantage over a browser — a real secure store — and one hazard that browser tabs do not have: **background execution**.

### Where to store

| Platform | Store | Notes |
| --- | --- | --- |
| iOS | Keychain, `kSecClassInternetPassword` or `kSecClassGenericPassword` | Survives reinstall only if you set `kSecAttrAccessibleAfterFirstUnlock`; excluded from iCloud by default |
| Android | `EncryptedSharedPreferences`, or `EncryptedFile` | Backed by the Android Keystore; invalidated if the user changes their lock screen |
| Both | In-memory only | Fine for short sessions; the user signs in again after a cold start |

The rule is the same as on the web but with a better substrate: **never `UserDefaults`, `SharedPreferences` in plain text, or a file in app storage.** Those are readable on a rooted or backed-up device. The system keystore-backed stores are not.

```text
import Security
import Foundation

enum Keychain {
    static let service = "com.example.app.pawabase"

    static func save(_ session: [String: Any]) throws {
        guard let data = try? JSONSerialization.data(withJSONObject: session) else { return }
        let query: [String: Any] = [
            kSecClass as String: kSecClassGenericPassword,
            kSecAttrService as String: service,
            kSecAttrAccount as String: "session",
        ]
        SecItemDelete(query as CFDictionary)
        var insert = query
        insert[kSecValueData as String] = data
        insert[kSecAttrAccessible as String] = kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly
        SecItemAdd(insert as CFDictionary, nil)
    }

    static func load() -> [String: Any]? {
        let query: [String: Any] = [
            kSecClass as String: kSecClassGenericPassword,
            kSecAttrService as String: service,
            kSecAttrAccount as String: "session",
            kSecReturnData as String: true,
            kSecMatchLimit as String: kSecMatchLimitOne,
        ]
        var item: CFTypeRef?
        guard SecItemCopyMatching(query as CFDictionary, &item) == errSecSuccess,
              let data = item as? Data,
              let session = try? JSONSerialization.jsonObject(with: data) as? [String: Any]
        else { return nil }
        return session
    }

    static func clear() {
        let query: [String: Any] = [
            kSecClass as String: kSecClassGenericPassword,
            kSecAttrService as String: service,
            kSecAttrAccount as String: "session",
        ]
        SecItemDelete(query as CFDictionary)
    }
}
```

`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` is the important attribute: it lets a background refresh work after a reboot, but keeps the item off iCloud and off other devices.

### Background refresh is the hazard

An iOS background fetch or an Android WorkManager job that wakes up and refreshes while the foreground app also refreshes will present the same refresh token twice — and sign the user out everywhere, including on their other devices.

Two mitigations, and you want both:

<Steps>
  <Step title="Prefer the access token in the background">
    If the stored access token has not expired, use it. Only fall back to a refresh when it has.
  </Step>
  <Step title="Never refresh from a background task at all if you can avoid it">
    A background sync that needs fresh data can use the last known access token and let the foreground app refresh. If you must refresh in the background, take a cross-process lock — on iOS, a `dispatch_semaphore` around the refresh; on Android, a `Mutex` in a singleton repository.
  </Step>
  <Step title="Handle the 401 by signing out, not by retrying">
    A `401 invalid refresh token` from a background task means the family is gone. Clear the store and let the UI prompt for sign-in.
  </Step>
</Steps>

```text
// One repository, one mutex, one refresh — for the whole process.
class SessionRepository(private val store: SecureStore) {
    private val mutex = Mutex()
    @Volatile var session: Session? = store.load()

    suspend fun accessToken(): String {
        session?.takeIf { !it.isExpiringSoon() }?.let { return it.accessToken }
        return mutex.withLock {
            // Re-check inside the lock: someone may have refreshed while we waited.
            session?.takeIf { !it.isExpiringSoon() }?.let { return@withLock it.accessToken }
            val fresh = PawabaseApi.refresh(session!!.refreshToken)
            session = fresh.also { store.save(it) }
            fresh.accessToken
        }
    }
}
```

## The BFF pattern

If you have a backend of your own, the strongest arrangement is to keep both tokens off the client entirely: an httpOnly cookie holds the refresh token, your server holds nothing at all, and the browser only ever sees the access token in memory.

```text
// Browser: no tokens in storage at all.
async function api(path: string, init: RequestInit = {}) {
  const response = await fetch(path, {
    ...init,
    credentials: "include",          // send the httpOnly cookie
    headers: { "content-type": "application/json", ...init.headers },
  });
  if (response.status === 401) {
    // The cookie expired or was revoked. One refresh attempt, no token in JS.
    await fetch("/auth/refresh", { method: "POST", credentials: "include" });
    return fetch(path, { ...init, credentials: "include" });
  }
  return response;
}
```

```python
# Your server: exchanges the cookie's refresh token, sets a new cookie.
@app.post("/auth/refresh")
async def refresh(request: Request, response: Response):
    token = request.cookies.get("pb_refresh")
    if not token:
        response.delete_cookie("pb_refresh")
        raise HTTPException(401, "no session")

    async with httpx.AsyncClient(timeout=10.0) as client:
        upstream = await client.post(
            f"{GATEWAY}/auth/v1/token",
            headers={"apikey": PUBLISHABLE_KEY},
            json={"grant_type": "refresh_token", "refresh_token": token},
        )

    if upstream.status_code == 401:
        # The family is gone — revoked, or reuse was detected upstream.
        response.delete_cookie("pb_refresh")
        raise HTTPException(401, "session ended")

    upstream.raise_for_status()
    session = upstream.json()
    response.set_cookie(
        "pb_refresh",
        session["refresh_token"],
        httponly=True,          # not readable by JavaScript
        secure=True,            # https only
        samesite="lax",         # not sent on cross-site POSTs
        max_age=60 * 60 * 24 * 7,
        path="/auth",           # only sent to your auth routes
    )
    return {"user": session["user"], "org": session["org"], "org_role": session["org_role"]}
```

Why this is worth the extra hop:

- An XSS payload cannot read the refresh token, so it cannot escalate a one-request compromise into a 30-day one.
- Scoping the cookie to `path="/auth"` means it is not attached to every API call.
- `SameSite=Lax` blocks the cookie from cross-site POSTs, which closes the CSRF hole that comes with cookie auth.
- Your server can serialise refreshes per user, which is the only reliable place to do it when several tabs exist.

<Warning>
You are now holding the publishable key on your server and proxying, or using the secret key. Use the **publishable** key and forward the user's access token, so your policies still apply. A secret key here would make your backend a full-access service, and every request through it would bypass policies.
</Warning>

## CORS

CORS applies only to **publishable** keys from a browser, where an `Origin` header is present. The gateway enforces it before your backend is reached:

```python
origin = headers.get("origin")
if context.role == "anon" and origins and origin and origin not in origins:
    await _json(
```

```json
{ "error": "origin_not_allowed", "message": "https://evil.example may not use this key." }
```

with status `403`. Four details that matter:

<AccordionGroup>
  <Accordion title="Only when the list is non-empty">
    `and origins` — an empty allow-list means no restriction. Convenient in development, worth tightening before you ship.
  </Accordion>
  <Accordion title="Only for `anon` role keys">
    `context.role == "anon"` — a secret key is not checked, because a secret key is not a browser credential.
  </Accordion>
  <Accordion title="Only when an Origin is actually sent">
    `and origin` — a server-side call with no `Origin` header passes through regardless of the list.
  </Accordion>
  <Accordion title="It is exact string matching">
    `origin not in origins`. No wildcard handling, no subdomain suffix matching, no `*.example.com`. List each exact origin, including scheme and port.
  </Accordion>
</AccordionGroup>

```json
["http://localhost:5173", "https://app.yourapp.com"]
```

`https://app.yourapp.com` and `https://app.yourapp.com:443` are the same origin to a browser but different strings to this check. Use the form your browser sends.

<Info>
Nothing about CORS is configured client-side. The browser sends `Origin` automatically and the gateway's response headers decide whether the preflight succeeds. If your dev server runs on an unusual port, add that exact origin to the list rather than looking for a way to disable the check.
</Info>

## The error shape you actually have to handle

There are **two** error formats, and a client that assumes one will break on the other.

### Gateway errors — an object

The gateway always returns this shape, and these are the only errors with a stable `code`:

```json
{ "error": "missing_api_key", "message": "Send a valid project API key in the apikey header." }
{ "error": "invalid_api_key", "message": "…" }
{ "error": "origin_not_allowed", "message": "https://evil.example may not use this key." }
{ "error": "rate_limit_exceeded", "retry_after": 42 }
```

Note the third key: `retry_after` is a **number of seconds**, not a timestamp, and there is no `message` on the rate-limit form.

```python
await _json(
    send,
    429,
    {"error": "rate_limit_exceeded", "retry_after": max(int(result.retry_after), 1)},
    [(b"retry-after", str(max(int(result.retry_after), 1)).encode())],
)
```

### Akountz errors — the detail *is* the body

This is the part that trips people up. When a Sillo `HTTPException` is raised, the handler returns the detail as the entire JSON body — not wrapped in an `error`/`message` envelope:

```python
async def http_exception(
    self, ctx: HttpContext, exc: HTTPException
) -> BaseResponse:
    """Handle an HTTPException by producing an appropriate error response.
    ...
    """
    assert isinstance(exc, HTTPException)
    if exc.status_code in {204, 304}:
        return BaseResponse(
            body=b"", status_code=exc.status_code, headers=exc.headers
        )
    return json(exc.detail, status_code=exc.status_code, headers=exc.headers)
```

So a failed sign-in is **not** `{"error": "invalid_email_or_password"}`. It is:

```json
"invalid email or password"
```

A bare JSON string. A `403` on organization switching is:

```json
"you are not a member of that organization"
```

<Warning>
A client that reads `body.error` for every non-2xx response gets `undefined` on every Akountz error, and a client that assumes `body.message` gets `undefined` too. Read the body **once**, and handle both shapes: an object with `error` (gateway) or a bare string (service).
</Warning>

There is one exception inside Akountz: the password policy failure carries a nested object, because its `detail` is a dict:

```python
raise HTTPException(
    status_code=422,
    detail={"message": "the password does not meet the policy", "problems": problems},
)
```

```json
{
  "message": "the password does not meet the policy",
  "problems": ["Password must be at least 12 characters."]
}
```

And request-body validation failures come from a different handler entirely:

```python
return json({"detail": exc.errors}, status_code=422)
```

```json
{
  "detail": [
    { "loc": ["query", "page"], "msg": "...", "type": "..." }
  ]
}
```

So a `422` from Akountz is one of **three** shapes depending on which layer rejected the request. Read `problems` if present, fall back to `detail`, and never assume a fixed key.

### A defensive error reader

```text
export class PawabaseError extends Error {
  constructor(status, body) {
    const message =
      typeof body === "string"
        ? body                                        // Akountz: detail is the body
        : body?.message                              // gateway, or password policy
        ?? body?.detail?.message
        ?? body?.error
        ?? `request failed (${status})`;
    super(message);
    this.name = "PawabaseError";
    this.status = status;
    this.body = body;
    this.code = body?.error ?? null;                 // gateway only
    this.retryAfter = body?.retry_after ?? null;      // 429 only
    this.problems = body?.problems ?? null;           // password policy only
  }
}

export async function readError(response) {
  const body = await response.json().catch(() => null);
  return new PawabaseError(response.status, body);
}
```

```python
class PawabaseError(Exception):
    def __init__(self, status: int, body):
        self.status = status
        self.body = body
        super().__init__(f"{status}: {_message(status, body)}")


def _message(status: int, body) -> str:
    if isinstance(body, str):
        return body                                   # Akountz detail
    if isinstance(body, dict):
        if "problems" in body:                        # password policy
            return "; ".join(body["problems"])
        if "message" in body:
            return body["message"]
        if "error" in body:
            return body["error"]
        if "detail" in body:
            return str(body["detail"])
    return f"request failed ({status})"
```

### The statuses a client must branch on

| Status | Meaning | Retry? |
| --- | --- | --- |
| `400` | Malformed request, bad credentials, invalid or used link | No — fix the request |
| `401` | No token, expired token, wrong environment, revoked session | Refresh once, then sign out |
| `403` | Authenticated but refused: policy, disabled account, unverified email, wrong org | No |
| `404` | Not found — or "no such organization", which also covers "not a member" | No |
| `409` | Conflict — slug taken, last owner, already a member | No |
| `422` | Validation or password policy | No — show `problems` |
| `429` | Rate limited | Yes, after `retry_after` seconds |
| `500`+ | Server fault | Yes, with backoff |

The two `401`s are worth separating. A `401` from **your API** means the access token expired — refresh and retry. A `401` from **`/auth/v1/token`** means the refresh token is dead — do not retry, sign the user out. The endpoint tells them apart.

A `401` from the API can also mean a **wrong-environment** token, and no amount of refreshing will fix that:

```python
def verify_user_token(token: str, master: str, *, project: str, env: str) -> dict[str, Any]:
    """Verify a user access token for *project*/*env*. Raises :class:`TokenInvalid`."""
    claims = _decode(token, derive_env_secret(master, project, env), audience=USER_AUDIENCE)
    if claims.get("typ") != "access":
        raise TokenInvalid("not an access token")
    if claims.get("prj") != project or claims.get("env") != env:
        raise TokenInvalid("token belongs to another environment")
    return claims
```

If refreshing succeeds and the retried request still returns `401`, suspect this: your client is pointed at staging with a production token, or the API key and the token belong to different environments.

## Rate limits

Two independent limiters can apply.

The gateway limits per key, or per client IP when there is no key:

```python
result = await self.limiter.check(HttpContext(scope, receive))
if result is not None and not result.allowed:
    self.stats["rate_limited"] += 1
    note("rate_limited", True)
    await _json(
        send,
        429,
        {"error": "rate_limit_exceeded", "retry_after": max(int(result.retry_after), 1)},
        [(b"retry-after", str(max(int(result.retry_after), 1)).encode())],
    )
    return
```

Akountz limits its own auth routes:

```python
limits = rate_limit_middleware(
    {"limit": 30, "window": 60}, "akz:auth", akountz.settings.redis_url
)
```

applied to `POST /signup` and `POST /token`. MFA endpoints use `{"limit": 10, "window": 60}` under the `akz:mfa` namespace. The backing store is `redis_url` when configured, otherwise an in-process counter — so a multi-worker deployment without Redis gets a per-worker limit, not a global one.

Route-level limits answer with a slightly different body and helpful headers:

```python
return json_response(
    {
        "error": "rate_limit_exceeded",
        "message": "Too many requests. Slow down and retry later.",
        "retry_after": retry_after,
    },
    status_code=429,
    headers={
        "Retry-After": str(retry_after),
        "X-RateLimit-Limit": str(result.limit),
        "X-RateLimit-Remaining": "0",
    },
)
```

So `429` from the gateway has **no `message`**, and `429` from an Akountz route **does**. Read `retry_after`, falling back to the `Retry-After` header.

<Warning>
`POST /auth/v1/token` shares a 30-per-60-seconds budget with `POST /auth/v1/signup`. A client that refreshes on every request — rather than on expiry — will exhaust it. Refresh on a schedule, not per request.
</Warning>

```text
async function withBackoff(fn, { attempts = 3 } = {}) {
  for (let i = 0; i < attempts; i++) {
    const response = await fn();
    if (response.status !== 429) return response;
    const error = await readError(response);
    const wait = error.retryAfter
      ?? Number(response.headers.get("retry-after"))
      ?? 2 ** i;
    if (i === attempts - 1) return response;
    await new Promise((resolve) => setTimeout(resolve, wait * 1000));
  }
}
```

## Per-environment configuration

The client should read the environment's capabilities rather than hard-coding assumptions. `GET /auth/v1/settings` is public and returns what the environment offers:

```python
@r.get("/settings", summary="What this environment offers for sign-in")
async def settings(ctx: HttpContext):
    config = await config_for(akountz, ctx)
    return {
        "signup_enabled": config.signup_enabled,
        "email_verification_required": config.require_email_verification,
        "magic_link_enabled": config.magic_link_enabled,
        "mfa_enabled": config.mfa_enabled,
        "providers": config.enabled_providers(),
        "password_policy": {
            "kind": config.password_policy,
            "min_length": config.password_min_length,
        },
    }
```

```bash
curl "$GW/auth/v1/settings" -H "apikey: $PUBLISHABLE_KEY"
```

```json
{
  "signup_enabled": true,
  "email_verification_required": false,
  "magic_link_enabled": true,
  "mfa_enabled": true,
  "providers": ["google", "github"],
  "password_policy": { "kind": "strict", "min_length": 12 }

```

This lets a sign-in screen render only the affordances that will work, and a sign-up form validate the length client-side before a round trip. `enabled_providers()` filters on both `enabled` and the presence of a `client_id`:

```python
def enabled_providers(self) -> list[str]:
    return sorted(
        name
        for name, conf in self.providers.items()
        if conf.get("enabled", True) and conf.get("client_id")
    )
```

<Warning>
This endpoint reads a **cached** configuration:

```python
key = f"authcfg:{project}:{env}"
cached = await akountz.cache_get(key)
```

A configuration change made in Studio is not visible immediately. If you cache the settings client-side, use a short TTL and expect the change to land within `config_ttl` seconds.
</Warning>

## Putting it together: a checklist

<Steps>
  <Step title="One base URL, one API key per environment">
    Never share a key across environments. A token is valid only for the environment that issued it, and `verify_user_token` rejects a mismatch outright.
  </Step>
  <Step title="Two headers, always">
    `apikey` on every request. `Authorization: Bearer` once someone is signed in. The publishable key in clients, the secret key only on servers.
  </Step>
  <Step title="Store both tokens as one unit">
    They are written together and read together. A refresh that stores only the access token leaves you unable to refresh again.
  </Step>
  <Step title="Serialise refresh">
    One in-flight refresh per tab, per process, or per user. A duplicate is treated as theft and revokes the family.
  </Step>
  <Step title="Refresh on a skew window, retry a 401 exactly once">
    Proactive at `expires_at - 60`, reactive as a fallback. Never loop.
  </Step>
  <Step title="Read both error shapes">
    Gateway `{"error": …}` and Akountz bare-string detail. One reader that handles both.
  </Step>
  <Step title="Sign out on a `401` from the token endpoint">
    Do not retry it. Clear local state and send the user back to sign-in.
  </Step>
  <Step title="Never put the secret key in a client">
    Not in a bundle, not in a mobile binary, not in an environment variable that a build tool inlines.
  </Step>
</Steps>

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Every request returns `401`, even right after signing in | Token and API key are from different environments | `verify_user_token` compares `prj` and `env`. Use one environment's pair throughout |
| Users are logged out at random | Two concurrent refreshes — same token presented twice | Serialise refresh; the second one revoked the family |
| A `session.reuse_detected` event fired and nobody stole anything | Almost always a client bug: a retry, a double-mounted effect, a background task | Fix the duplicate refresh; the event is your only signal |
| `body.error` is `undefined` on a sign-in failure | Akountz returns the detail as the whole body, a bare string | Read the body and handle both shapes |
| `mfa_required: true` and the client crashed reading the session | The `password` grant returns a challenge, not a pair | Branch on `mfa_required` before touching `access_token` |
| `session` is `null` after sign-up | Email verification is required in this environment | Send the user to the verification flow; do not expect a token |
| `403 you are not a member of that organization` | The `org` slug has no membership for this user here | Confirm with `GET /orgs`; have them accept an invitation |
| The active organization reset to none | The client sent `org: null` on a refresh | Omit the key — `null` clears the selection, omission keeps it |
| A role change is not reflected in the UI | The access token predates the change | Refresh; `org_role` and `roles` are read at issue time |
| `429` shortly after a page load | Several components each triggered a refresh | One shared session with single-flight refresh, not per-component state |
| `429` on refresh specifically | `/token` shares a 30-per-minute budget with `/signup` | Refresh on a schedule, not per request |
| `403 origin_not_allowed` in development | The dev server's exact origin is not on the list | Add the exact origin including scheme and port |
| `401` after signing out | Sign-out requires the access token it is revoking | Sign out before the token expires, or accept that the session lapses |
| `422` with no useful message | One of three different `422` shapes | Read `problems`, then `detail`, then fall back |
| Password accepted at sign-up, rejected at sign-in | The account was created without a password — `set_unusable_password()` | Use a recovery link to set one; password sign-in cannot succeed until then |
| A user cannot sign in with a password at all after an OAuth login | Same cause — OAuth-created accounts have no usable password | Expected. Set a password through recovery |

<AccordionGroup>
  <Accordion title="Why is my refresh token different every time?">
    Because rotation is mandatory: `refresh_token_pair` consumes the old row and issues a new one inside the same family. `session_id` is stable; the tokens are not. Store both from every response.
  </Accordion>
  <Accordion title="Can I keep using the same refresh token forever?">
    No. Presenting a consumed token revokes the entire family, logs every device out, and emits `session.reuse_detected`. There is no non-rotating mode.
  </Accordion>
  <Accordion title="How long does a stolen refresh token last?">
    Until `refresh_ttl` — 30 days by default — or until it is used once (which revokes the family and strands the thief too, though the legitimate client then also fails). That asymmetry is why the refresh token is the thing worth protecting.
  </Accordion>
  <Accordion title="Do I need a CSRF token?">
    Only if you move to cookie authentication. With `Authorization: Bearer` on every request, a third-party site cannot make your client attach a credential. The BFF pattern introduces the cookie, and with it the need for `SameSite` and/or a CSRF token.
  </Accordion>
  <Accordion title="Can I verify tokens myself instead of calling the API?">
    No — and you should not try. `derive_env_secret` derives a per-environment key from a master secret your installation holds, and no verification endpoint is exposed. Verification happens at the services.
  </Accordion>
  <Accordion title="Should the client decode the JWT?">
    You may read the claims for UI decisions, but never make an authorization decision from them. The server verifies the signature; a client-decoded claim is only as trustworthy as the connection it arrived over.
  </Accordion>
  <Accordion title="What about a service key and no user token?">
    That is the normal shape for a backend. Send `apikey` only, no `Authorization`. Be aware that it bypasses every policy, so scope the key if the integration does not need full access.
  </Accordion>
</AccordionGroup>
