### Why did my provider vanish from the sign-in page?

Because `enabled_providers()` filters on exactly two conditions — the enabled switch being on, and a `client_id` being set. The most common cause by a wide margin is a provider entry with credentials but no client ID, which is invisible everywhere: it does not appear in the settings response, it does not appear in Studio's enabled list, and using it returns a 404.

The second cause is the config cache. A provider you enabled seconds ago may not be in the response yet.

### Why can I not find the callback URL to paste into the provider console?

It is derived, not configured. It is `{public_url}/auth/v1/callback/{project}/{env}/{provider}`, and both `public_url` and the environment are inputs. If you cannot recall what `public_url` resolves to, check whether the environment sets its own or is inheriting Akountz's installation-wide setting — that inheritance is a common surprise in a multi-environment deployment.

### Can I offer Apple sign-in?

Not as a built-in provider. Apple is not one of the four that ship, so an `apple` entry is a generic provider and needs all three endpoints supplied by hand. The same applies to Facebook and LinkedIn. This is worth repeating because it is the single most common incorrect expectation carried over from other products' documentation.

### Should I match accounts by email?

You already are, and the system already guards it. Branch 3 of the decision tree matches by email, and only when the provider verified it. You do not need to add anything to your own code, and you should not try to relax the condition — the guard is the security property, not a limitation.

### Why did a user get `email_unverified_conflict` instead of an account?

Because they already have one. Their provider reported the address as unverified, so the callback refused to attach a new identity to the existing account. The resolution is for them to sign in by password or magic link and link the provider from the signed-in account, which takes a path that does not depend on email verification.

### Does a social sign-in count as verified for email verification requirements?

It depends on the provider, and the answer is per account rather than per flow. When the callback creates an account from a profile whose email the provider verified, the account is marked verified immediately — so it can sign in even in an environment that requires verification. When the provider did not verify, the account is created unverified, and in an environment requiring verification that account cannot sign in normally until it confirms the address.

<Warning>
This is a genuine difference between providers, and it means `require_email_verification` behaves differently depending on which provider a person used. Google and Microsoft generally verify; some generic providers never do. If you require verification and offer a provider that does not verify, accounts arriving through it will be stuck.
</Warning>

### Can a social sign-in be scoped to an organization?

Not in the redirect. A social sign-in starts a session unscoped. To scope it, the client completes whatever it was doing and then refreshes with an `org`, which switches the session's organization the same way it does for a password session. See [Organizations](/auth/organizations/overview).

### What happens if I remove a provider from configuration?

Existing identities remain, and sign-in through that provider stops working because the provider can no longer be built. Anyone relying on it as their only sign-in method loses access through no fault of their own, so removing a provider is a user-visible change worth announcing. Their other methods — another provider, or a password — continue to work.

### Do the tokens arrive in a query string anywhere?

No. Social sign-in returns tokens in a fragment, and the magic-link hosted page does the same when it redirects. Query parameters are used for the one-time token in an emailed link, which is a different thing: that token is a signed reference to a database row that must travel to a server, whereas a session token must not. See [Magic links](/auth/magic-links/overview).

<AccordionGroup>
  <Accordion title="Why does my generic provider work for new users but fail for existing ones?">
    Almost always the verified-email rule. Creating an account does not require the provider to have verified the address. Matching an existing account does. So a provider that exposes no verification claim will happily create accounts and then refuse to attach those same accounts on their second visit, with `email_unverified_conflict`.
  </Accordion>
  <Accordion title="Should I store the provider's access token?">
    The callback does not keep it on the account. It is available during the callback if you need it, but nothing in the authentication flow requires storing it, and an expired provider token is of no use to Pawabase. Store it only if your application has a real reason to call the provider's API later.
  </Accordion>
  <Accordion title="Can two environments share one provider application?">
    They can, if you register both callback URIs, since each environment produces a different path. It is simpler and less error-prone to use one application per environment, and it keeps revoking one environment's access from affecting the other.
  </Accordion>
</AccordionGroup>
### Provider registration checklist

The values you need from a provider's developer console, and what each one is used for. This is the same for all four shipped providers and for any generic one.

| Value | Where it goes | Notes |
| --- | --- | --- |
| Client ID | `client_id` | Public. Safe in configuration. |
| Client secret | `client_secret` | Reference it as `secret://NAME`. |
| Callback URL | Registered at the provider, not here. | Must match exactly, including the environment segment. |
| Scopes | `scopes` | Usually needs an email scope. |
| Provider-specific extras | `tenant` for Microsoft. | Only read by the provider that accepts it. |

The callback URL is the value with no tolerance at all. Providers compare it exactly, and the derived form includes the project and environment, so an environment that has not been given its own provider application cannot reuse another environment's registration.

```bash
# The exact URI to register for one environment and provider
echo "https://auth.example.com/auth/v1/callback/acme/production/google"
```

<Info>
Register the callback for the environment you are testing. A registration for staging does not accept a callback arriving for production, and the provider reports the mismatch rather than reaching Pawabase — so you never see a Pawabase log line explaining it.
</Info>

### Choosing which providers to enable

A short, opinionated guide, because enabling everything is a common first instinct and a bad one.

| Consideration | Guidance |
| --- | --- |
| Which providers verify email | Prefer them. Without verification, returning users cannot be matched by email and get `email_unverified_conflict`. |
| Enterprise directories | Microsoft with `tenant` set is the usual answer for a company-only deployment. |
| Provider availability per region | Enabling a provider a region cannot reach adds a button that fails for those users. |
| Provider outage behaviour | With only one provider, an outage is an outage. Two providers is genuine redundancy. |
| Support burden | Each provider is a configuration surface with its own scopes, secrets and console. |

<Warning>
Enabling a provider for an environment where existing users already have accounts is a user-visible change. Branch 3 will attach those users' new identity to their existing account by verified email, which is usually what you want — but if you did not expect the merge, it will surprise people who already had an account.
</Warning>

### Server-to-server and CLI sign-in

The social routes are browser navigations, so they are not usable from a script. A backend process cannot "sign in with Google" — it has no browser, no consent screen, and no state cookie.

What it can do is act as an operator or a service. An admin can create a user from the **New user** modal in Studio's **Users & auth** page, or call the admin routes with a service key, and the resulting account signs in through the normal password or magic-link path. See [Managing users](/auth/managing-users/overview) and [API keys](/studio/api-keys).

<Info>
If you are automating a pipeline that needs to act as a person, this is the usual answer: create the account server-side with a service key, then sign in with the password grant from that script, rather than trying to drive the social flow. The interactive flows are browser navigations and are not scriptable; see [Managing users](/auth/managing-users/overview) for the admin routes and [API keys](/studio/api-keys).
</Info>
### Browser-side integration, end to end

Putting the pieces together, because the fragment handling is the part most worth getting right and it is easy to get subtly wrong.

The application needs three things: a sign-in page that renders buttons, a callback page that reads the fragment, and somewhere to keep the session. The flow between them:

```text
1. GET  /auth/v1/settings              -> which providers to render
2. 302  /auth/v1/authorize/acme/production/google
3. ...  the provider's consent screen, which the person sees
4. 302  https://auth.example.com/auth/v1/callback/acme/production/google
5. 302  https://app.example.com/auth/callback#access_token=...
6. the callback page reads location.hash and stores the session
```

Reading the fragment is straightforward, but two details matter:

```text
// Runs only in the browser. The server that served this page never saw the tokens.
const raw = window.location.hash.replace(/^#/, "");
if (raw) {
  const params = new URLSearchParams(raw);
  if (params.has("error")) {
    // signup_disabled, denied, state_mismatch, email_unverified_conflict, ...
    showError(params.get("error"));
  } else if (params.get("mfa_required") === "true") {
    // Not a session yet. Prompt for the second factor.
    promptForCode(params.get("mfa_token"));
  } else {
    // Four keys only. No session_id, no user record.
    storeSession({
      access_token: params.get("access_token"),
      refresh_token: params.get("refresh_token"),
      expires_in: Number(params.get("expires_in")),
    });
    // The session id and the user record come from the API, not the fragment.
    hydrateFromApi();
  }
  // Clean the URL so the tokens are not left in history or a copied link.
  history.replaceState(null, "", window.location.pathname);
}
```

| Detail | Why it matters |
| --- | --- |
| Read `location.hash`, not a query string. | The fragment is where the tokens are. |
| Check `error` first. | A failure redirect carries `error` and nothing else. |
| Check `mfa_required` before reading a token. | The MFA redirect carries no `access_token` at all. |
| Expect only four keys on success. | `session_id`, `org` and the user record are not in the fragment. |
| Clean the URL afterwards. | Otherwise the tokens sit in browser history and in any copied link. |
| `href` in the body, not just JavaScript. | Without it, the sign-in page cannot offer the button at all. |

<Warning>
Do not render social buttons as plain links to a URL you hardcoded. The authorize path includes the project and the environment, both of which change between deployments, and the provider set changes per environment. Render from the settings response and build the path from the project's own context.
</Warning>

See [Client integration](/auth/client-integration/overview) for how to store the session and refresh it, and [Tokens and sessions](/auth/tokens-and-sessions) for the full token lifecycle.

<Info>
If you need the person back on a specific page after signing in, pass that page as `redirect_to` on the authorize request and make sure it is inside the allowlist. A URL outside the allowlist is refused at the authorize step rather than ignored, which is the safer failure — but it does surface as a `400` rather than as a sensible error in the browser.
</Info>

### What the account looks like afterwards

| Question | Answer |
| --- | --- |
| Does the account have a password? | No. It has an unusable password until someone sets one. |
| Is the email verified? | Only if the provider said it was. |
| What roles does it have? | The environment's `default_roles`. |
| Is it a member of any organization? | Not unless an invitation or an admin action added it. |
| What can it sign in with? | Any linked provider, and password or magic link once set up. |
| Where is the session listed? | In the environment's sessions, with method `oauth:<provider>`. |

That last row and the first are the pair people are surprised by. A social sign-in produces a completely ordinary session and an account that is missing exactly one thing — a password — which most applications never need.

### Migrating to a different provider set

Social login configuration changes have effects that outlive the change itself, and it is worth being deliberate about them.

**Turning a provider off stops sign-in without touching anyone.** Existing identity rows stay. Anyone whose only method was that provider simply cannot sign in through it, and the failure is a 404 at the authorize step rather than a refusal at the callback — because a provider that is not enabled is never built.

**Turning a provider on merges accounts.** This is the one that surprises people. Existing users whose verified provider email matches an account get that identity attached to the account they already had, by branch 3. If you expected a separate account per provider, that is not what happens, and it is not configurable.

**Changing a client ID orphans the old identities.** The identity key is `(project, env, provider, subject)`. A subject is the provider's identifier *within that provider's own installation*, so replacing the client ID typically produces different subjects for the same people. The old identities stop matching, and the accounts behind them become reachable only by their other methods. If you rotate a client ID, expect to re-link.

**Changing the callback host strands in-flight logins.** Anyone mid-flow when `public_url` or `site_url` changes will come back to a host that is no longer registered, and the provider rejects the request before Pawabase sees it.

| Change | Who notices | What to do |
| --- | --- | --- |
| Disable a provider | That provider's users, at sign-in. | Announce it; offer an alternative method. |
| Enable a provider | Nobody breaks. Accounts may merge. | Tell users their Google account now works. |
| Replace a client ID | Existing users of that provider. | Expect re-linking; keep the old method available meanwhile. |
| Change `site_url` | Nobody, once saved. | Confirm the allowlist still matches the new host. |
| Change `public_url` | In-flight logins only. | Update the provider's registered callback. |

<Warning>
Removing the last sign-in method from an account is not blocked by the system unless the account has no usable password — that guard applies to a user removing their own identity. An administrator disabling or deleting accounts is a separate action with separate consequences. See [Managing users](/auth/managing-users/overview).
</Warning>

### Auditing a social sign-in after the fact

Both the event stream and the login history answer "what happened", from different angles.

| Source | Records | Use it for |
| --- | --- | --- |
| `user.signed_in` | Successful sessions, with `method`. | Confirming a sign-in occurred. |
| `identity.linked` | A provider attached to an account. | Confirming a link, and when. |
| `user.created` | A new account from a provider. | Separating new accounts from email matches. |
| `user.verified` | Not emitted by social login. | Only password-verification flows. |
| `LoginEvent` rows | Every attempt, success or failure, with `reason`. | Investigating a specific failure. |

For a specific person's history, `GET /auth/v1/history` returns their recent attempts for the signed-in user — the last fifty, each with its kind, method, outcome, IP and user agent. For an environment-wide view, the **Sign-in activity** tab in Studio shows the same records with a failures-only filter.

```bash
curl "https://api.example.com/auth/v1/history" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "X-Pawabase-Context: $CONTEXT"
```

```json
{
  "data": [
    {
      "kind": "sign_in",
      "method": "oauth:google",
      "success": true,
      "reason": null,
      "ip": "203.0.113.9",
      "user_agent": "Mozilla/5.0",
      "at": "2025-06-01T10:15:00+00:00"
    }
  ]
}
```

<Info>
The `method` field is the fastest way to answer "did they come through the provider or the password form", and the `reason` field on a failure carries the error code from this page — so a login history is often a better diagnostic than the event stream when you are chasing one specific failure.
</Info>

### Error codes by cause, grouped

The same twelve codes appear in two places on this page; grouping them by what you should do about them is the form that helps at 2am.

**The person did something ordinary.** Nothing is broken.

| Code | What happened | Response |
| --- | --- | --- |
| `denied` | Closed the consent screen. | Send them back to the sign-in page. |
| `state_expired` | Left the consent screen open. | Send them back; say it timed out. |

**The person did something plausible and it failed.**

| Code | What happened | Response |
| --- | --- | --- |
| `email_unverified_conflict` | Provider did not verify an email that already has an account. | Tell them to sign in normally, then link the provider. |
| `email_required` | Scopes did not include an email. | Fix the provider's scopes. |
| `identity_already_linked` | The identity belongs to another account. | Unlink it there first. |
| `account_disabled` | An administrator disabled the account. | Point them at an administrator. |

**You have a configuration problem.**

| Code | What happened | Response |
| --- | --- | --- |
| `signup_disabled` | Environment is invite-only. | Expected. Create the user, or invite them. |
| `exchange_failed` | Code rejected, or a redirect URI mismatch. | Check the registered callback path. |
| `profile_failed` | Userinfo failed, or no subject claim. | Check scopes and the userinfo endpoint. |
| `provider_error` | The provider refused for another reason. | Read the provider's own logs. |
| `state_mismatch` | No usable state cookie. | Usually HTTPS, or a rotated secret mid-flow. |

**Something is wrong in a way you should not expect to see.**

| Code | What happened | Response |
| --- | --- | --- |
| `provider_misconfigured` | A programming error reached a redirect. | Look at the code, not the user's account. |

<Info>
The distinction that saves the most time: `denied` and `state_expired` mean the provider conversation completed and produced nothing. `state_mismatch` means it never started properly. The first two are a user, the third is you.
</Info>

### What a provider entry looks like when it is wrong

Three misconfigurations produce a 404, and they look different in configuration but identical in behaviour.

| Configuration | What is wrong | Why it 404s |
| --- | --- | --- |
| `{"enabled": false, "client_id": "x"}` | Deliberately disabled. | The enabled check fails. |
| `{"client_id": "", "client_secret": "secret://X"}` | Client ID never filled in. | The client ID check fails. |
| `{"enabled": true}` | Credentials never added. | The client ID check fails. |
| Not present at all | No entry. | No settings to read. |

The second and third are the same failure and are by far the most common. The card looks configured in Studio because it exists, and the **Enabled** switch is on, because the default is on.

<Warning>
If a provider 404s, check the client ID before anything else. The secret being wrong produces a very different failure — the redirect works and the callback fails at the token exchange with `exchange_failed`.
</Warning>

### Enabling social login without breaking what exists

The order that avoids surprises, given the branch structure described above.

| Consideration | Why the order matters |
| --- | --- |
| Confirm the callback URI with the provider first. | A wrong URI means nothing can be tested end to end. |
| Set `site_url` before enabling providers. | It is the default landing page and the first allowlist entry. |
| Confirm sign-up is on *only* if new accounts are wanted. | Otherwise the flow will refuse unknown people, which is a valid configuration but surprises users. |
| Enable one provider, test the returning-user path. | The returning path exercises branch 3, which is where scope problems appear. |
| Add the rest. | Each is independent once the first works. |

<Info>
The returning-user test is the one people skip, and it is the one that finds scope and verification problems. A brand new email address passes with almost any scope configuration; a second sign-in with an address that already has an account is what actually proves the provider verified the email.
</Info>

### Every field in the provider block, with an example value

The complete set of keys a provider entry accepts, so nothing here is a surprise.

```json
{
  "providers": {
    "microsoft": {
      "enabled": true,
      "client_id": "00000000-1111-2222-3333-444444444444",
      "client_secret": "secret://MICROSOFT_SECRET",
      "tenant": "common",
      "scopes": ["openid", "email", "profile"],
      "authorize_params": { "prompt": "select_account" },
      "authorize_endpoint": "https://login.microsoftonline.com/common/oauth2/v2.0/authorize",
      "token_endpoint": "https://login.microsoftonline.com/common/oauth2/v2.0/token",
      "userinfo_endpoint": "https://graph.microsoft.com/oidc/userinfo"
    }
  }
}
```

| Key | Type | Required | Read by | Effect |
| --- | --- | --- | --- | --- |
| `enabled` | bool | no | all | False removes the provider entirely. |
| `client_id` | str | **yes** | all | Absent means invisible and 404. |
| `client_secret` | str | no | all | Empty is allowed; some flows are public. |
| `tenant` | str | no | Microsoft only | Ignored by every other provider. |
| `scopes` | list | no | all | Replaces the class default entirely when set. |
| `authorize_params` | dict | no | all | Extra parameters on the authorize URL. |
| `authorize_endpoint` | str | generic only | all | Overrides the class default. |
| `token_endpoint` | str | generic only | all | Overrides the class default. |
| `userinfo_endpoint` | str | generic only | all | Overrides the class default. |

Two of these have consequences that are easy to miss.

**`scopes` replaces rather than extends.** When you set `scopes`, the list you supply is what is requested — it is not merged with the provider class's defaults. A provider that needed an email scope by default will stop asking for it if you supply a shorter list.

**`authorize_params` is for things scopes cannot express.** Provider-specific prompt behaviour, a login hint, a domain hint. It goes on the authorize URL only and never reaches the token exchange.

<Warning>
Every key in this table other than `enabled` and `client_id` is inert for the provider that does not read it. Setting `tenant` on Google, or `userinfo_endpoint` on GitHub, does nothing at all — no warning, no error. It is worth matching keys to providers when editing configuration by hand.
</Warning>

### The `authorize` and `callback` pair as one unit

The two URLs, in the order they are used, for one environment.

```text
Start (your browser goes here):
  https://auth.example.com/auth/v1/authorize/acme/production/google
      ?redirect_to=https://app.example.com/auth/callback

Return (registered at the provider, the provider sends the browser here):
  https://auth.example.com/auth/v1/callback/acme/production/google

Land (where the person ends up, tokens in the fragment):
  https://app.example.com/auth/callback#access_token=...
```

| Segment | Value | Where it comes from |
| --- | --- | --- |
| Host | `auth.example.com` | `public_url`, falling back to Akountz's own setting. |
| `/auth/v1/authorize/` | Fixed prefix | The route. |
| `acme` | The project slug. | The path — not the context header. |
| `production` | The environment. | The path. |
| `google` | The provider key. | The path. |
| `redirect_to` | Optional query parameter. | Must be inside the allowlist. |

This is the clearest illustration of the tenancy rule in one block of URLs. The project and environment appear **in the URL** rather than in a header, because a redirecting browser carries no context — and that is exactly why a token minted by one environment is meaningless in another. See [Authentication](/auth/overview).

<Info>
If you host the authorize route behind a different hostname than the callback, the state cookie will not come back and every callback will fail as `state_mismatch`. Both URLs must be on the same host, since the state cookie is set on whichever host handled the first request.
</Info>

### Choosing where the browser lands

The landing page is yours, and the only constraint is that it must be inside the allowlist.

| Landing choice | Consequence |
| --- | --- |
| `{site_url}` | The browser returns to your app's base URL. You handle the fragment there. |
| `{site_url}/auth/callback` | A dedicated page that reads the fragment and nothing else. |
| A URL in `redirect_urls` | Allowed, and the fragment still carries the tokens. |
| A URL outside the allowlist | Refused at the authorize step with a 400. |
| No target at all | The callback returns JSON instead of redirecting. Useful for testing. |

The last row is worth knowing about: with no `redirect_to` and no `site_url`, a successful social sign-in returns the four keys as a JSON body instead of a fragment. That is the simplest way to test a provider end to end with curl, since you can see the response directly.

```bash
# Start a sign-in with no redirect target. The callback returns JSON.
curl -sD- -o /dev/null "https://auth.example.com/auth/v1/authorize/acme/production/google" | head -20
```

<Warning>
Without a `site_url`, magic links and email verification also fall back to Akountz-hosted pages rather than your application. The two features share the same setting, so the decision is made once. See [Magic links](/auth/magic-links/overview).
</Warning>

### Account resolution as a lookup table

The decision tree restated as the exhaustive table of inputs and outcomes, for when you want to predict a result rather than understand the rule.

| Identity found | Link ticket | Email verified | Account holds email | Outcome |
| --- | --- | --- | --- | --- |
| yes | — | — | — | Sign in as the identity's user. |
| no | yes | — | — | Attach to the ticket's user. |
| no | yes | — | — | `identity_already_linked`, if the identity belongs to someone else. |
| no | no | yes | yes | Sign in as that account; create the identity. |
| no | no | yes | no | Create an account. |
| no | no | no | yes | `email_unverified_conflict`. |
| no | no | no | no | Create an account, unverified. |
| no | no | — | no email at all | `email_required`. |

The last two rows are worth separating mentally, because they behave differently in an environment that requires verification: an account created from an unverified profile cannot then sign in normally, while an account created from a verified one can.

<Info>
Rows two and three share a row because the outcome depends on which user the identity currently belongs to. In every other case the link ticket simply names the account and the check that can fail is the ownership one.
</Info>

### What each session record tells you afterwards

Once a social sign-in has happened, the session is the durable record of it. These are the questions people ask about a session and where the answer lives.

| Question | Where to look |
| --- | --- |
| Which provider did this session use? | `method`, as `oauth:<provider>`. |
| Did MFA happen? | `aal` is `aal2` rather than `aal1`. |
| Which organization is it scoped to? | `org`, null when unscoped. |
| When did it last refresh? | `last_refreshed_at`. |
| Has it been revoked? | `revoked_at`. |
| Where did it come from? | `ip` and `user_agent`, from the callback request. |
| Which user? | The `user` field. |

The `method` and `aal` pair is the one worth internalising: together they tell you both how someone authenticated and how strongly, from a single row, without consulting the event stream.

### Distinguishing a social session in a policy

If you want to require a second factor for some operations, `aal` is the claim to branch on. It is read from the token at issue time and rides along with every request, so no service needs to call back to Akountz.

```json
{
  "claims": {
    "sub": "01HQ8X4M2K9P7R3T6V0YB5ZCNDA",
    "prj": "acme",
    "env": "production",
    "typ": "access",
    "aal": "aal2",
    "sid": "9f2c1ab4e7d84f0c9b3a5e61d2c4807f6a9e3b5c1d0f28496ab7c3e5d1f0a2b4c6"
  }
}
```

| Assurance level | How it is reached |
| --- | --- |
| `aal1` | Any password, magic-link or social sign-in that did not complete MFA. |
| `aal2` | A sign-in that completed an MFA challenge, or enrolment on a live session. |

A social sign-in does not reach `aal2` on its own. It reaches it exactly as a password sign-in does — by returning an MFA challenge when the account has a factor and the environment allows it, and by the client completing that challenge. See [Multi-factor authentication](/auth/mfa/overview) and [Auth in policies](/auth/auth-in-policies/overview).

<Warning>
`aal` is written into the token when it is issued. Elevating a session's assurance does not retroactively change access tokens that already exist — the elevated session mints new ones. If a policy needs `aal2`, a client holding a pre-elevation token will still present `aal1`.
</Warning>

### Keeping the two flows consistent

Social sign-in, password sign-in and magic-link sign-in all converge on the same session shape. Knowing where they agree and where they differ saves a lot of duplicated client logic.

| Aspect | Password | Magic link | Social |
| --- | --- | --- | --- |
| Endpoint | `POST /auth/v1/token` | `POST /auth/v1/magic-link/verify` | `GET /auth/v1/callback/...` |
| Where the result arrives | JSON body | JSON body | URL fragment |
| Can challenge for MFA | yes | yes | yes |
| Session `method` | `password` | `magic_link` | `oauth:<provider>` |
| Reaches `aal2` | with a challenge | with a challenge | with a challenge |
| Scoped to an org | at request time | not at request time | not at request time |
| May create an account | yes, via `/signup` | yes, by default | yes, if sign-up is on |

The two rows that differ most in practice are the second and the sixth. Social sign-in is the only one that delivers tokens through a browser redirect, and the only one that cannot be scoped to an organization at the moment it starts — both consequences of it being a browser navigation rather than an API call.

<Info>
Because all three converge on the same session response, everything downstream of sign-in — refresh, revocation, session listing, `aal`, org scoping — behaves identically regardless of how the person got there. The `method` field is the only lasting difference.
</Info>

### Verifying a provider works, without a browser

The callback returns JSON when there is no redirect target, which makes the whole flow testable with a cookie jar.

```bash
# Start the flow. -c keeps the state cookie the callback will require.
curl -sc jar.txt -o /dev/null -w '%{redirect_url}\n' \
  "https://auth.example.com/auth/v1/authorize/acme/production/google"
```

That prints the provider's authorize URL. Follow it, consent, and the provider will redirect the browser to the callback. To capture the result without a browser, take the `code` from the callback URL and replay the callback with the same cookie jar:

```bash
# The callback, with the cookie jar from the start step.
curl -sb jar.txt "https://auth.example.com/auth/v1/callback/acme/production/google?code=THE_CODE&state=THE_STATE"
```

```json
{
  "access_token": "...",
  "refresh_token": "...",
  "expires_in": 900,
  "token_type": "bearer"
}
```

| What you learn from this | How |
| --- | --- |
| The provider is configured correctly. | A 404 or 500 means it is not; nothing else runs. |
| The token exchange works. | `exchange_failed` means the secret or the callback URI is wrong. |
| The profile is readable. | `profile_failed` means the scopes or the userinfo endpoint. |
| Account resolution works. | Any `error` code is from the decision tree, not the provider. |

<Warning>
The state cookie is required. Running the callback without the cookie from the start step always fails as `state_mismatch`, which is the flow working correctly rather than anything being misconfigured.
</Warning>

### Reading an `Identity` row directly

When you need to know why an account is not being matched, the identity table is the place to look.

| Column | What it tells you |
| --- | --- |
| `project`, `env` | Which environment owns this identity. A row for another environment is irrelevant here. |
| `provider` | The provider key used. |
| `subject` | The provider's identifier for this person. |
| `email` | A snapshot from the last time this identity signed in. |
| `email_verified` | What the provider said at that time. |
| `last_sign_in_at` | Whether this identity is still in use. |

```sql
SELECT provider, subject, email, email_verified, last_sign_in_at
FROM akz_identities
WHERE project = 'acme' AND env = 'production';
```

The `subject` column is the join key. If a person is not matching on their second sign-in, comparing the subject stored here against the subject the provider returned this time tells you whether the provider's identifier moved — which happens when a client ID is replaced, or when the provider re-keys accounts.

<Warning>
Do not treat the `email` column as authoritative for matching. It is a snapshot of what the provider said at link time, and the decision tree deliberately does not read it. A provider-side email change does not move an identity between accounts.
</Warning>

### What a correct setup looks like in Studio

The end state, so you can check your work against something concrete. Under **Users & auth**, **Configuration**:

| Section | What it should show |
| --- | --- |
| **Sign-up** | **Sign-up enabled** reflecting your intent. **Default roles** populated. |
| **URLs** | **Site URL** set, so the browser has somewhere to land. |
| **OAuth providers** | One card per provider, each with a **Client ID** and a `secret://` reference. Shipped providers show no endpoint fields. |
| **Sign-in methods** | **MFA (TOTP)** on if you want second factors available. |
| **Email templates** | Magic-link and password copy, if you have changed them. |

And under **Users**, a user who signed in socially shows an MFA status matching what they enrolled, and a session list whose entries carry the provider as their method.

<Info>
After saving, give the config cache up to ten seconds before testing. A sign-in attempt in that window reads the previous configuration, which is a frequent cause of "my change did nothing".
</Info>

### Common provider-specific notes

Where a shipped provider behaves in a way worth knowing before you support it.

**GitHub and the private address.** A GitHub profile has a public email that may differ from the address on the account, and the private one requires the email scope. Without the email scope the profile comes back without a usable address, and you get `email_required` for new users rather than a matching failure for returning ones.

**Discord and identity.** Discord distinguishes basic identity from a verified email address, and the scopes are separate. A Discord login configured with only the basic scope returns a profile whose `email_verified` is false, which means every Discord sign-in either creates a new account or fails with `email_unverified_conflict` on the second visit.

**Google and Microsoft.** Both verify addresses as a matter of course, which is why they are the two providers most likely to work with no scope configuration at all. Microsoft additionally needs `tenant` decided deliberately — `common` accepts anyone, `organizations` accepts only your own directory.

**Microsoft's `tenant` is not a Studio field.** It is the one provider-specific setting that cannot be set from the Configuration tab, so it belongs in hand-written configuration. See [Microsoft and tenants](/auth/social-login/overview#microsoft-and-tenants).

| Provider | Verifies email by default | Scope configuration usually needed | Provider-specific settings |
| --- | --- | --- | --- |
| `google` | yes | usually none | none |
| `github` | when the email scope is granted | yes, for the address | none |
| `discord` | with the email scope | yes | none |
| `microsoft` | yes | usually none | `tenant` |
| Generic | depends entirely | yes | the three endpoints |

<Warning>
The pattern across all four is the same: the thing that goes wrong is almost always the email scope, and the symptom is always an account that behaves correctly the first time and fails the second.
</Warning>
