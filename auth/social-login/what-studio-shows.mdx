Studio's **Users & auth** page, under the **Configuration** tab, holds every provider setting. Open the environment, then **Configuration**, and scroll to the section titled **OAuth providers**, described in the interface as *"Social sign-in. Reference credentials as secret://NAME rather than pasting them here."*

Each configured provider is a card. Shipped providers show two fields; anything else shows five.

| Control | Label | Applies to |
| --- | --- | --- |
| Switch | **Enabled** | all |
| Field | **Client ID** | all |
| Field | **Client secret** (placeholder `secret://GITHUB_SECRET`) | all |
| Field | **Authorize endpoint** | generic only |
| Field | **Token endpoint** | generic only |
| Field | **Userinfo endpoint** | generic only |
| Field | **Scopes** | all |
| Icon button | **Remove {name}** | all |

The endpoint fields are hidden for the four shipped providers, because their endpoints are already known. That is the clearest signal of which providers are built in: if Studio is showing you endpoint fields, you built a generic provider.

To add one, either pick from the **Add a provider…** dropdown — which lists the shipped providers not yet configured — or type a name into the box with the `custom-provider-name` placeholder and press **Add**. Both paths produce the same entry; the second is the only way to create a generic provider. With no providers configured the section reads *"No providers configured."*

<Steps>
  <Step title="The provider appears in the card grid">
    Adding a provider creates a card named after the key, with the **Enabled** switch on and empty credentials. Nothing is usable yet, because there is no client ID.
  </Step>
  <Step title="Credentials go in as secret references">
    The **Client ID** is pasted from the provider's console. The **Client secret** is entered as `secret://NAME`, referencing a secret rather than storing the value in configuration.
  </Step>
  <Step title="The provider becomes visible to clients once it has a client ID">
    Saving with a client ID is the moment the provider starts appearing in `GET /auth/v1/settings`. Saving without one leaves it configured but invisible — see [What the client is told about providers](/auth/social-login/overview#what-the-client-is-told-about-providers).
  </Step>
</Steps>

<Info>
Changes take up to ten seconds to take effect, because each environment's auth configuration is cached. If a provider you just saved does not appear in the settings response immediately, wait and re-read rather than re-saving.
</Info>

### Related configuration in the same tab

Two other sections on the Configuration tab change social sign-in behaviour without being provider settings:

| Section | Control | Effect on social login |
| --- | --- | --- |
| **URLs** | **Site URL** | Where the browser lands when no `redirect_to` is given. |
| **URLs** | **Additional allowed redirect URLs** | Extra bases the allowlist accepts. |
| **Sign-up** | **Sign-up enabled** | Whether the callback may create an account. |
| **Sign-in methods** | **MFA (TOTP)** | Whether an MFA challenge is issued after resolution. |

The **URLs** section is described in the interface as *"Where a browser is allowed to land after an OAuth or magic-link redirect"*, which is the same redirect machinery both flows use. The **Sign-up** switch carries the hint *"Turn off to invite-only new accounts."*, which is the control that produces `signup_disabled`.

## What the Sign-in activity tab shows

Every callback outcome lands in the sign-in audit trail, including the failures. The **Sign-in activity** tab has a failures-only checkbox and columns **When**, **Event**, **Email**, **Result** and **IP**. The Result badge renders `ok` in green when the attempt succeeded, and the reason string in red when it did not.

For an OAuth failure the reason is the error code from the table above — `denied`, `state_mismatch`, `exchange_failed` and so on — and the Event column records the method as `oauth:<provider>`. This is usually the fastest way to answer "did the person actually get through Google, or did they stop at the consent screen", because a denied consent is logged as a failure against an email that may not exist yet.

<Info>
Failures that never reach the callback are not in this tab. A `404 the 'google' provider is not enabled` or a `500` about missing endpoints happens at the authorize step, before any profile exists, so there is no login event to record.
</Info>


## Troubleshooting

Most social-login problems are one of four kinds, and telling them apart is most of the work.

**The provider is not enabled.** The request fails with `404 the 'google' provider is not enabled`, raised when the provider is built. Two different configurations produce this identically: `enabled` set to false, and no `client_id`. The second is the surprising one, because the entry looks configured. Check the settings response — if the name is absent from `providers`, this is your problem.

**The provider is generic and incomplete.** A `500` naming the provider and saying it needs authorize, token and userinfo endpoints means one of the three is missing or empty. This one fails at `/authorize`, before any conversation with the provider.

**The callback cannot find an account.** The error code in the fragment says which case you are in. `email_required` means the scopes do not grant email access. `email_unverified_conflict` means an account already holds that address and the provider did not verify it — the user needs to sign in by password or magic link and link the provider instead. `signup_disabled` means the environment is invite-only.

**The callback fails before resolution.** These are the OAuth library's codes: `state_mismatch`, `state_expired`, `exchange_failed`, `profile_failed`, `denied`, `provider_error`. `state_mismatch` after a configuration change usually means the state secret was rotated mid-flow; `exchange_failed` usually means the redirect URI registered with the provider does not match the one derived, which is the common symptom of pointing a staging callback at a production provider application.

| Symptom | Cause | What to check |
| --- | --- | --- |
| Provider missing from `GET /auth/v1/settings` | No `client_id`, or `enabled: false`. | The client ID, not the secret. |
| `404 the 'x' provider is not enabled` | Same condition as above. | Same. |
| `500 provider 'x' needs authorize, token and userinfo endpoints` | Generic provider missing an endpoint. | All three keys are present and non-empty. |
| `#error=state_mismatch` | The state cookie did not come back. | `public_url` scheme, and whether the provider is echoing `state`. |
| `#error=state_expired` | The consent screen sat open. | Nothing — this is normal. |
| `#error=exchange_failed` | Code rejected, or a redirect URI mismatch. | The registered callback URI matches `{public_url}/auth/v1/callback/{project}/{env}/{provider}`. |
| `#error=profile_failed` | Userinfo rejected the token or returned no subject. | Scopes, and that the userinfo endpoint is correct. |
| `#error=denied` | The person declined consent. | Nothing. |
| `#error=email_required` | The profile carries no email. | Scopes that grant email. |
| `#error=email_unverified_conflict` | An existing account holds that unverified address. | Link the provider from a signed-in session instead. |
| `#error=signup_disabled` | Invite-only environment. | `signup_enabled`, or create the user in Studio. |
| `#error=account_disabled` | The account is disabled. | An administrator must re-enable it. |
| `#error=identity_already_linked` | That provider identity is on another account. | Unlink it there first. |
| `409 set a password before removing your only sign-in method` | Unlinking would leave the account unreachable. | Set a password first. |
| Sign-in succeeds but no `session_id` in the fragment | Only four keys are sent. | Read it from `GET /auth/v1/user`. |
| Token stored as `undefined` | The redirect carried `mfa_required`, not `access_token`. | Branch on `mfa_required` first. |
| Works in staging, fails in production | Different provider application, or a different callback URI. | One provider application per environment. |
| Just saved a provider, not showing up | The config is cached. | Wait up to ten seconds. |
| Every callback is `state_mismatch` on localhost | The state cookie needs HTTPS. | Terminate TLS locally, or use a tunnel. |

## How this interacts with the rest of the system

A few cross-cutting consequences of social sign-in that show up elsewhere.

**Sessions record their origin.** Every social sign-in produces a session row whose method is `oauth:<provider>`, which is how a session list distinguishes it from a password or magic-link session. Combined with `ip` and `user_agent`, it is the same row the **Sign-in activity** tab renders. See [Tokens and sessions](/auth/tokens-and-sessions).

**A social-only account cannot use a password sign-in.** Accounts created here have an unusable password, so `POST /auth/v1/token` with `grant_type=password` cannot succeed against them. This is the same state as an account an administrator created in Studio, and it is resolved the same way — a password recovery link. See [Password recovery](/auth/password-recovery/overview).

**Organization scoping is read at issue time.** A social sign-in issues tokens for the session's organization exactly as a password sign-in does, and a `null` org role collapses `org` and `org_role` to `null` in the token rather than failing. There is no way to name an organization in the OAuth redirect; a social sign-in starts unscoped and the client refreshes into an organization afterwards if it needs one. See [Organizations](/auth/organizations/overview).

**Roles come from the environment, not the provider.** A new account created here is granted whatever the environment's `default_roles` lists. Nothing from the provider's groups or teams is imported — the callback stores the provider's profile under the identity's own data, not as roles. See [Roles and permissions](/auth/roles-and-permissions/overview).

**Every other service sees only the token.** Once the fragment is parsed and the tokens stored, a social sign-in is indistinguishable from any other sign-in at the gateway. No service knows or cares which provider was used; that fact lives in the session row and the sign-in events. See [Auth in policies](/auth/auth-in-policies/overview).

<AccordionGroup>
  <Accordion title="The callback is excluded from the OpenAPI schema — should I worry?">
    No. It is excluded because it is only ever reached by a provider redirecting a browser, and it takes `code` and `state` as query parameters rather than a JSON body. The route still exists and works. The path is documented above and in the provider consoles you register it with.
  </Accordion>
  <Accordion title="What happens to the tokens in the fragment if the user never returns?">
    Nothing is stored server-side for a social sign-in that completes without the browser reaching your callback page. The tokens were only ever in the fragment of a redirect the browser followed. There is no orphaned copy to clean up — but equally, no session was created, so the person must sign in again.
  </Accordion>
  <Accordion title="Can I offer a provider the environment has not configured?">
    Not through the normal flow. Rendering a button for a provider that is not in `GET /auth/v1/settings` produces a `404 the 'name' provider is not enabled` at the authorize step. The fix is configuration, not client code. Rendering from the settings response is what prevents this.
  </Accordion>
  <Accordion title="Does linking require the provider to have a verified email?">
    No. When a linking ticket is present, the account is named by the ticket rather than resolved by email, so the verified-email condition never gates it. The email still has to be absent or verified to *create* an account, but an existing account being linked is not an email match.
  </Accordion>
</AccordionGroup>

### The two halves of the flow, and why they differ

The authorize route and the callback route do different jobs, and conflating them is a common source of confusion when reading the code.

| | Authorize route | Callback route |
| --- | --- | --- |
| Who calls it | Your browser, via a link or a form. | The provider, by redirecting the browser. |
| What it does | Builds the provider URL, stores the state cookie, redirects. | Verifies state, exchanges the code, reads the profile, resolves the account. |
| Credentials involved | Only the public client ID. | The client secret, at the token endpoint. |
| Can fail on config | Yes — 404 or 500 here. | Rarely; a config error surfaces as `exchange_failed`. |
| Writes to the database | Nothing. | The identity, possibly the account, the session. |

The asymmetry in the last two rows is the practical takeaway. **A configuration mistake almost always shows up at `/authorize`, not at `/callback`.** If the callback is failing, the configuration was almost certainly fine enough to get the person to the provider, and the problem is in the conversation, the profile, or the account resolution.

<Info>
Because the authorize route writes nothing, a person who clicks your sign-in button and then abandons the consent screen leaves no trace in the database — no session, no identity, no login event. That is correct behaviour, and it is why a `denied` result appears in sign-in activity only once the provider actually redirects back.
</Info>

### Why the callback is not in the schema

The callback route is excluded from the generated OpenAPI schema. It takes `code` and `state` as query parameters, and it is only ever reached by a provider redirecting a browser rather than by a client making an API call. Excluding it keeps generated clients from producing a method that no one should ever call directly.

The practical consequence is that the path must be registered in the provider's console by hand, and it is the single most common thing to get subtly wrong, because the path includes both the project and the environment:

```text
https://auth.example.com/auth/v1/callback/acme/production/google
         └─── Akountz ───┘ └── /auth/v1 ──┘ └─ project ─┘ └env┘ └prov┘
```

A callback registered without the environment segment will never be hit, and the provider will report the request as an invalid redirect URI.

<Warning>
When registering a callback URI, the environment name must be the one in the path you are actually serving. `production` and `staging` produce different URIs and both must be registered if one provider application serves both — or, more usually, one provider application is created per environment.
</Warning>

## What the flow actually protects against

Before the decision tree it helps to know which attacks the design is aimed at, because every branch either serves one of these or exists to prevent one.

| Threat | What stops it |
| --- | --- |
| Someone replays a callback URL to sign in as the person who used it | The state cookie must come back with the callback. A bare callback URL has no cookie and fails as `state_mismatch`. |
| Someone forges a state value to redirect a victim | The state value is signed and bound to this environment and provider. |
| Someone claims an identity that belongs to another account | The `(project, env, provider, subject)` lookup finds the real owner and signs them in as themselves, not the claimant. |
| Someone registers a provider profile with a victim's email and steals the account | The verified-email rule. An unverified address never joins an existing account. |
| Someone steals a refresh token and uses it after the real client has rotated it | Rotation is single-use. A reused token revokes the entire family rather than merely failing. |
| Someone replays a TOTP code they saw over a shoulder | The accepted time step is recorded, so the same code cannot be used twice within its window. |
| Someone takes a bearer token out of a log | Tokens are returned in a fragment, which is never sent to a server. |

The first three are handled by the OAuth library and the identity lookup. The fourth is Pawabase's own decision, and it is the one specific to this page.

<Info>
The two layers divide cleanly: the library owns the conversation with the provider, and Akountz owns what the resulting profile *means*. That separation is why adding a generic provider is a configuration exercise rather than a code change, and why the security property that matters most — the verified-email rule — lives in the callback rather than in any provider class.
</Info>


## Scope handling per provider

Scopes are the most common cause of a social sign-in that technically works and practically fails. The pattern is always the same: the user consents, the code exchanges, and then the profile comes back without the field you matched on.

| Provider | Default scopes | What you usually need to add |
| --- | --- | --- |
| `google` | OpenID Connect basics | An email scope, if the default does not include the address. |
| `github` | The provider's default set | An email scope; the private address is not returned without one. |
| `discord` | The provider's default set | An email scope. Discord also has a distinct `identity` scope. |
| `microsoft` | OpenID Connect basics | An email scope for the address. |
| Generic | None | Whatever the provider's userinfo endpoint requires, usually an email scope. |

<Warning>
Adding `openid` to a generic provider's scopes switches it to OpenID Connect mode. That is usually what you want when the provider supports it, but it changes how the profile is read: the identity comes from the ID token rather than from userinfo claims in the general case. If a generic provider starts returning a profile with no subject after you add `openid`, that is why.
</Warning>

### Provider profile fields

Whatever the provider, the callback works from a normalised profile with the same shape.

| Profile field | Used for | Consequence when absent |
| --- | --- | --- |
| `subject` | The identity key. | `profile_failed` — this is the only genuinely required field. |
| `email` | Account matching and creation. | `email_required` when no account matches. |
| `email_verified` | Gates the email match. Treated as false when absent. | Returning users are not matched by email. |
| `name` | The account's display name. | The name is stored empty. |
| `username` | The generated username seed. | The email local part is used instead. |
| `avatar_url` | The account's avatar. | No avatar is stored. |
| `raw` | Stored on the identity. | — |

The row about `email_verified` is the one to hold onto. A provider that does not expose a verification claim will still work perfectly for new sign-ups, because creating an account does not require verification. It will fail only for the *returning* user whose email matches an existing account, and it will fail with `email_unverified_conflict` — which reads like an account problem and is actually a provider configuration problem.
