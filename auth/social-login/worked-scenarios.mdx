The decision tree is easier to trust once you have walked it in concrete situations. Each of these is a real path through the callback, and each lands somewhere different.

### A brand new person signs in with Google

The profile carries a subject nobody has seen, and an email Google says it verified.

The identity lookup finds nothing. The verified-email branch looks for an account holding that address and finds none either, because the person has never used Pawabase. So account creation runs: sign-up is enabled, an email is present, and no account holds it. An account is created with an unusable password, verified immediately, carrying the provider's name and avatar. The identity is written, `identity.linked` and `user.created` are emitted, and a session starts with method `oauth:google`.

The person is signed in and can now use the account however they like. If they later want a password, they request a recovery link — see [Password recovery](/auth/password-recovery/overview).

### A returning person signs in with Google

Same person, same provider, weeks later.

The identity lookup finds the `Identity` row, because the provider's subject for them is unchanged. Branch 2 resolves immediately and the account is found without ever consulting the email. This is the path that matters most: **returning sign-ins are keyed on the provider's subject, not on the email address.**

That is deliberate. Email addresses get reassigned and people change them. A subject is stable. If matching were by email, a person who changes their provider email would silently become a new account the next time they signed in — or worse, would land in somebody else's account if their old address was reused.

### A person has a password account and tries Google

The person already has an account, created with a password, and clicks "Continue with Google". Their Google profile has the same email, and Google verifies it.

Branch 2 finds nothing, because they have never linked Google. Branch 3 finds their existing account, because the email matches and it is verified. The identity is attached and they are signed in as themselves.

**This is the good version of account merging, and it depends entirely on the provider verifying the email.** When it is verified, a person who has both a password account and a Google account gets one account rather than two, which is what almost every application wants.
### The same person, but the provider does not verify the email

Identical to the previous scenario except the provider reports the address as unverified — or says nothing, which reads the same way.

Branch 2 finds nothing. Branch 3 does not run, because its condition fails. Branch 4 looks for an existing account holding that address, finds one, and refuses with `email_unverified_conflict`.

The person is told, in effect, that they already have an account. They are not told which one, and they are not signed in. The correct resolution is for them to sign in with their password and then link Google from the signed-in account — at which point branch 1 applies, the account is named by the linking ticket rather than by email, and the link succeeds.

<Warning>
If you are tempted to "fix" `email_unverified_conflict` by relaxing the verified-email check, understand what you are opening: any person who can set an arbitrary email on a profile at a permissive provider could then take over any account in your system. The conflict is the security property working, not a bug in it.
</Warning>

### An invite-only environment, brand new person

Same as the first scenario, but sign-up is off for this environment.

Branch 2 and branch 3 both find nothing. Branch 4 runs and refuses immediately with `signup_disabled`, before it even looks at the email.

The person must be created by an administrator first, or invited. See [Managing users](/auth/managing-users/overview) and [Organizations](/auth/organizations/overview) for the invitation path.

### An invite-only environment, invited person

The administrator created the account, or an invitation created it. The person's Google email matches the account they were invited with, and Google verified it.

Branch 3 finds the account by verified email, attaches the identity, and signs them in. **An invited account is not a special case in the callback** — it is the ordinary verified-email match, working.

The one thing to know is that an admin-created account typically has an unusable password, so the person's only usable sign-in method until they link a provider is whatever the invitation gave them. See [Managing users](/auth/managing-users/overview).

### The same Google account in two environments

A person signs in with Google in `acme/production`, then in `acme/staging`.

Each environment has its own `Identity` table keyed on `(project, env, provider, subject)`. The staging lookup does not see the production row, so staging runs through account creation and creates a *separate* account with the same email.

This is correct, not a bug, and it falls directly out of the tenancy rule. The two accounts have separate passwords, separate sessions, and separate roles — [Authentication](/auth/overview) covers why the system is built this way. It also means `signup_enabled` being on in staging is what lets that second account exist; turning it off makes staging refuse instead.

### A disabled account tries to sign in socially

Every branch above resolves to a user, and then branch 5 refuses with `account_disabled`.

The check is last and unconditional, so it applies however the user was found — by identity, by verified email, or by a linking ticket. A disabled account cannot be reached by any social path.

<Info>
A social sign-in failure logs an event with the method recorded as `oauth:<provider>` and the reason recorded as the error code. That is the same row the **Sign-in activity** tab renders in its Result column, so an administrator can see that `account_disabled` is an administrative state rather than a credentials problem.
</Info>


## Configuration that works, end to end

A complete environment auth block with social sign-in, magic links and MFA on, written the way the code reads it.

```json
{
  "name": "production",
  "public_url": "https://auth.example.com",
  "auth": {
    "signup_enabled": true,
    "require_email_verification": true,
    "magic_link_enabled": true,
    "mfa_enabled": true,
    "password_policy": "strict",
    "password_min_length": 12,
    "access_ttl": 900,
    "refresh_ttl": 2592000,
    "site_url": "https://app.example.com",
    "redirect_urls": [
      "https://app.example.com/auth/callback",
      "http://localhost:3000/auth/callback"
    ],
    "default_roles": ["member"],
    "providers": {
      "google": {
        "enabled": true,
        "client_id": "1234567890-abc.apps.googleusercontent.com",
        "client_secret": "secret://GOOGLE_SECRET"
      },
      "github": {
        "enabled": true,
        "client_id": "Iv1.0123456789abcdef",
        "client_secret": "secret://GITHUB_SECRET",
        "scopes": ["read:user", "user:email"]
      },
      "gitlab": {
        "enabled": true,
        "client_id": "gitlab-client-id",
        "client_secret": "secret://GITLAB_SECRET",
        "authorize_endpoint": "https://gitlab.com/oauth/authorize",
        "token_endpoint": "https://gitlab.com/oauth/token",
        "userinfo_endpoint": "https://gitlab.com/api/v4/user",
        "scopes": ["read_user"]
      }
    },
    "emails": {
      "magic": {
        "subject": "Your Acme sign-in link",
        "text": "Sign in to Acme with this link. It works once, for 15 minutes:\n\n{link}"
      }
    }
  }
}
```

Things worth noticing in that block, because each one is a decision with a consequence:

**`site_url` is what makes the callback predictable.** It is the base the browser is sent back to when no `redirect_to` is supplied, and it is the first entry in the allowlist. Without it the OAuth flow has no default landing page at all.

**`redirect_urls` carries the local development callback.** `http://localhost:3000/auth/callback` matches nothing in the production set, so it has to be listed explicitly.

**Every secret is a reference, not a value.** `secret://GOOGLE_SECRET` and friends resolve through the secret store. There is no place in this block where a raw client secret belongs. See [Secrets](/studio/secrets).

**The generic provider has all three endpoints.** GitLab is spelled out in full precisely because it is not one of the four shipped providers. Remove any one of the three and it fails as a 500 at the authorize step.

**`default_roles` grants the new account its starting role.** Accounts created by the social callback receive it. Nothing from the provider's own groups or teams is imported.

<Warning>
Remember the ten-second config cache when editing this block through Studio or the API. A change saved now may not be the change a request reads immediately afterwards.
</Warning>
Studio reflects the same list. The provider picker in the Configuration tab offers exactly `google`, `github`, `discord` and `microsoft`, and the free-text box beside it, whose placeholder is `custom-provider-name`, is where a generic provider comes from.

### The shape of a session that social sign-in creates

It is worth being concrete about what the callback writes, because two of these rows are what you will go looking for when a session "does not remember" that it came from a provider.

| Field | Value for a social sign-in |
| --- | --- |
| `family` | The token family hex string. This is what `session_id` in a token response refers to. |
| `method` | `oauth:<provider>`. |
| `aal` | `aal1`, unless MFA ran, in which case `aal2`. |
| `org` | The session's organization, or null. A social sign-in starts unscoped. |
| `ip`, `user_agent` | Taken from the callback request. |
| `last_refreshed_at` | Null until the first refresh. |
| `revoked_at` | Null while the session is live. |

The `method` value is the one to rely on if you want to distinguish social sessions from password sessions in the UI. It is the same value reported by `GET /auth/v1/sessions`, and it is the same value an administrator sees in Studio.

### Rate limits on the social path

| Bucket | Limit | Window | Applies to |
| --- | --- | --- | --- |
| `akz:auth` | 30 | 60 seconds | `/signup` and `/token`. |
| `akz:links` | 10 | 60 seconds | The endpoints that send email, including a magic-link request. |
| `akz:mfa` | 10 | 60 seconds | The MFA verification endpoints. |

The OAuth routes themselves are not in that table. That is not an oversight — a browser navigation is not something a client can retry cheaply, and the natural rate limiting for the flow is the state cookie's own expiry plus the provider's consent screen.

<Info>
If you build a test that drives the whole social flow repeatedly, the limit that will bite you is the ten-per-minute bucket on MFA completion, not anything on the OAuth routes. See [Rate limits](/reference/limits).
</Info>

### Reading the raw provider payload

The identity stores the provider's untouched userinfo response under its `data` column, alongside the normalised fields.

| Stored on the identity | Purpose |
| --- | --- |
| `provider` | The provider key this identity belongs to. |
| `subject` | The provider's stable identifier for the person. |
| `email`, `email_verified` | A snapshot of what the provider said at link time. |
| `data` | The raw profile payload, refreshed on each sign-in. |
| `last_sign_in_at` | Updated on every subsequent sign-in. |

The normalised columns are what the decision tree reads. The `data` column is not read for matching — it is kept so you can inspect what a provider actually returned when a profile looks wrong.

<Warning>
Do not build account matching on `data`, or on `email` as stored on the identity, rather than on the live profile. The identity's email is a snapshot from a past sign-in and is not re-verified against the account on later visits. The decision tree reads the profile from the current callback, which is why a provider-side email change does not retroactively move an identity between accounts.
</Warning>

### Several providers, one person

A person may end up with one account and three identities on it — Google, GitHub and a generic provider. Each is a separate `Identity` row with its own subject, all pointing at the same user.

| Situation | Result |
| --- | --- |
| They sign in with any of them. | Branch 2 finds their identity, signs them into the same account. |
| They sign in with a fourth, new provider. | Branch 3 matches by verified email, if the provider verified it. |
| They unlink one. | Only that identity is removed. The others still work. |
| They unlink their last one, with no password. | `409` — the account would be unreachable. |

This is the shape a mature account takes, and it is worth designing for: an account's sign-in methods are a set, and the password is just another member of it.

<Warning>
Because branch 3 matches by verified email, adding a new provider to an environment that existing users already have accounts for will quietly attach those users' new identity to their existing account. That is usually what you want, but it does mean enabling a provider is a user-visible change, not only a configuration one. The `user.created` events distinguish genuine new accounts from matches if you need to tell them apart afterwards.
</Warning>
