Pawabase's authentication is layered, and almost every security question is
answered by knowing which layer you are asking about. Three layers, three
different jobs:

| Layer | Owns | Security role |
| --- | --- | --- |
| **Akountz** | Users, passwords, identities, sessions, MFA, orgs, roles | The only layer that issues user tokens. Holds every credential. |
| **The API** | Each environment's `auth` settings block | Owns policy configuration. Akountz reads it and never writes it. |
| **Gateway / `pawabase_core`** | Verification at every other service | Issues nothing. Confirms tokens locally, with no network call. |

Two consequences run through everything on this page.

**Verification is local, so revocation is not immediate.** Services verify
signatures with a key derived from the master secret. Nothing asks Akountz whether
a token was revoked at request time. A revoked, disabled or deleted account keeps
working against other services until its access token expires — which is why
`access_ttl` is the most security-relevant number in your configuration.

**A token is only valid for the environment that issued it.** Every user token
carries its `project` and `env`, the signing key is derived per environment, and
both claims are re-checked after the signature verifies. A staging token cannot be
used against production even though the algorithm is identical.

  <Card title="What is not" icon="eye">XSS, a leaked service key, a compromised host, or a client that races its own refreshes.</Card>

## Credential stuffing and password guessing

Two attacks, two defences, and they are worth separating because they act at
different layers.

**Password guessing** is bounded by rate limiting and account lockout, both of
which are real and neither of which is optional:

| Control | Value | Where it lives |
| --- | --- | --- |
| Auth rate limit | 30 requests per 60 seconds, per IP | The `akz:auth` bucket, covering `/signup` and `/token` |
| Link rate limit | 10 per 60 seconds, per IP | The `akz:links` bucket |
| MFA rate limit | 10 per 60 seconds, per IP | The `akz:mfa` bucket |
| Lockout threshold | 10 failed attempts (default) | Installation setting, not per-environment |
| Lockout duration | 15 minutes (default) | Installation setting, not per-environment |

The failed-attempt counter is **per user, per environment**; the threshold and
duration that act on it are **global to the installation**. You cannot give
staging a stricter lockout than production.

**Credential stuffing** — replaying leaked username/password pairs at scale —
is bounded less by lockout than by the password hash. Passwords are hashed with
Sillo's hashing layer, which uses **bcrypt by default** and falls back to
`pbkdf2_sha256` when bcrypt is not installed.

<Warning>
The bcrypt cost factor is a property of the hashing library's own defaults, not of
anything Pawabase configures. There is no auth-config key for it, and no value to
set in Studio. If you need a specific cost factor, it is set where the hashing
library is configured, not in your environment's `auth` block.
</Warning>

Other schemes are supported by the hashing layer — argon2, scrypt, and pbkdf2 in
both SHA-256 and SHA-512 variants — but only the default is selected
automatically. Which one is in use is a deployment concern, not an auth-config
concern.

### The lockout behaviour that surprises people

A locked account returns `429` **even when the password is correct**, because the
lock check runs before the password check. A user whose password genuinely works
will still be refused until the window passes.

The counter resets on a successful sign-in, and also when an administrator unlocks
the account or when the user completes a password reset. MFA failures increment
the **same** counter, so a user fumbling their authenticator can lock themselves
out of password sign-in too.

### Unusable passwords are a real state

An account created without a password — by an admin, or by an OAuth provider —
has an **unusable password**, not an empty one. Password sign-in cannot succeed
for such an account at all; it has to go through a recovery link to set one. This
is the normal state for social-only accounts, and `has_password` in the admin
user view tells you whether it applies.

<Note>
Because the password hash column still holds a value for an unusable password,
"has a password" is a property of the model, not something you can infer from the
row existing. The admin user view exposes it as `has_password`.
</Note>

## Account enumeration

Enumeration is when an attacker learns which addresses have accounts, by watching
responses differ. Pawabase defends this in four places, and all four matter.

**Sign-in returns one message for two different failures.** An unknown email and a
wrong password both produce `400 invalid email or password`. Nothing in the status
code or body distinguishes them.

**The emailed link flows always succeed.** Requesting a recovery link, a magic
link or a verification link returns success whether or not the address exists.
Sending a real email to a real owner and a silent no-op to everyone else is the
whole defence — the attacker learns nothing from the response because there is
nothing to learn.

**One-time token failures are indistinguishable.** A token that is unknown,
already used, expired, or signed for a different purpose all produce the same
error: `the link is invalid or has expired`. There is no way to ask "was this link
already clicked?" and get a different answer from "did this link ever exist?".

**Organization slugs are not an oracle either.** Naming an organization you are
not a member of, and naming one that does not exist, both produce `403 you are not
a member of that organization`.

### Where enumeration *is* visible, deliberately

Two surfaces do tell you things, and both are administrative rather than public:

The **Sign-in activity** tab distinguishes `unknown email` from `wrong password`
in its Result column. That is for you, not for end users.

The **`user_view` difference between self and admin** is real: the admin view
includes `disabled`, `disabled_at`, `locked_until`, `last_sign_in_ip`,
`has_password` and `permissions`. None of that is exposed to the signed-in user,
who gets `GET /auth/v1/user`.

<Warning>
Rate limiting is not an enumeration defence. It bounds how fast an attacker can
probe, but the responses are already uniform. Do not rely on the limit to
compensate for a difference in your own error handling.
</Warning>

## Token replay and theft

This is the area where Pawabase's design is strongest, and also where the
sharpest edges are.

### Rotation is single-use and not optional

Every refresh token is consumed the first time it is presented. There is no
setting to change this. A second presentation of the same token is treated as
possible theft and **revokes the entire token family**.

That single design decision is what bounds replay. A stolen refresh token is
useful exactly once, and using it destroys the legitimate user's session in the
process — which is the intended outcome, not a bug.

<Warning>
The failure mode to understand is that Pawabase cannot tell the thief from the
real user, so it revokes for both. If your client ever presents a refresh token
twice — through a retry, a double-submit, or two tabs refreshing simultaneously —
the session dies. Clients must serialise refreshes and must never retry a failed
refresh with the same token.
</Warning>

### Why families, not tokens

Revocation operates on the **token family**, not on individual tokens. A family
is created at sign-in and survives every rotation, so one operation kills every
token ever issued under it — current, previous, and any that have not yet expired.

The alternative would be revoking only the presented token, which leaves a
legitimate client holding a token the attacker also holds. Killing the family is
the only response that makes both unusable.

### Theft detection is an event, not a flag

When reuse is detected the server revokes the family, stamps the session's
`revoked_at`, and emits `session.reuse_detected`. It does **not** email the user
and does **not** disable the account.

| What happens | What does not |
| --- | --- |
| Family revoked | No notification email |
| Session row stamped | No account disablement |
| `session.reuse_detected` emitted | No `theft_detected` flag to query |
| Client gets a generic `401` | No distinction between theft and a bad token |

To find out whether a session was compromised, read the login-event history for a
theft message. The Studio **History** table per user shows exactly that, in its
**OK** column.

### The exposure window you cannot close

Because access tokens verify locally:

- Revoking a family does not un-issue access tokens already minted from it.
- Disabling an account does not un-issue its tokens.
- Deleting an account does not un-issue its tokens.

Only the refresh path consults the database, which is why a revoked session is
definitively dead even while its last access token still works. Your revocation
latency against other services **is** `access_ttl`.

| `access_ttl` | Revocation takes effect within |
| --- | --- |
| 300s | 5 minutes |
| 900s (default) | 15 minutes |
| 3600s | 1 hour |

<Warning>
This is the strongest argument for a shorter access lifetime and the strongest
argument against a very long one. Fifteen minutes is a reasonable default for a
sensitive application; an hour means a compromised account stays useful against
every other service for an hour after you disable it.
</Warning>

## Redirects, CSRF and OAuth

### Redirect allowlisting is the real control

Any URL that will receive tokens must be validated against an allowlist before it
is used. The environment's `site_url` plus any `redirect_urls` form that
allowlist, and matching is **prefix-based**:

- The URL equals an allowed base exactly, or
- It begins with the base plus `/`, or
- It begins with the base plus `?`

That rule applies to the OAuth `redirect_to` parameter, the magic-link
`redirect_to`, and the sign-up `redirect_to`. A URL that is not allowed is
rejected — for OAuth it is a `400`, and for the sign-up path likewise.

Where the OAuth flow starts, an unapproved `redirect_to` is a hard error. Where
the callback resolves the target, an unapproved one is **silently replaced with
nothing**, so the flow continues without a redirect target rather than leaking the
tokens to an attacker's page.

<Warning>
The allowlist is checked against `site_url` and `redirect_urls` only. It is not
influenced by `cors_origins`, which is a gateway setting for browser origins —
different purpose, different scope. Confusing the two is a common cause of "why is
my redirect being rejected".
</Warning>

### Where tokens travel in the OAuth flow

Both the success payload and the errors travel in the **URL fragment**, not the
query string:

```
redirect to https://app.example.com/callback#access_token=...&mfa_required=true
redirect to https://app.example.com/callback#error=account_disabled
```

Fragments are not sent to servers and are not written to access logs on the
redirect hop, so a token in a fragment is not captured by the redirecting server's
logs. This is a genuine defence and it costs nothing.

Error codes travel the same way. Without a redirect target, the flow raises
`400 sign-in failed: {code}` instead.

### CSRF in the OAuth flow itself

The social sign-in flow uses a `state` value and PKCE, both provided by the
underlying OAuth library. The `state` is what stops an attacker from feeding their
own authorisation response into your callback.

### CSRF for your own application

This is worth being blunt about: **CSRF protection for your application is your
job, not the auth service's.** If you hold the refresh token in a cookie, the
browser attaches it to cross-site requests automatically and you must defend
against that yourself — with `SameSite`, a CSRF token, or both.

If you hold tokens in a header and send them from JavaScript, you are not exposed
to classical CSRF, but you *are* exposed to XSS. That is the actual trade-off:
cookies move the risk from CSRF to XSS-resistance, headers move it to XSS. Neither
is free.

<Info>
Pawabase's own browser-facing routes use cookies for OAuth state. Your
application's session storage is a separate decision, and the auth service has no
opinion on it. `/auth/client-integration` covers the mechanics.
</Info>

## Sessions and what they are trusted with

### What is recorded, and what is enforced

`SessionInfo` records an IP and a user-agent for each session. Those are **records
for inspection, not enforcement**. There is no IP binding, no device fingerprint,
and no mechanism that refuses a legitimate token because it arrived from a new
address.

The IP comes from `X-Forwarded-For` when that header is present — the first entry
in the list. If your clients can set that header themselves, or you are not behind
a proxy that normalises it, the recorded value is whatever was sent. Treat the
column as a debugging aid.

A sudden change of IP or user-agent on a session is a signal worth noticing when
reviewing the session list in Studio. It is not a signal the system acts on.

### No absolute session expiry

A session has no independent `expires_at`. It ends when its refresh tokens expire
and stop being refreshable, or when something revokes it.

If your application needs a maximum session age — eight hours, say, regardless of
activity — you have to enforce it yourself from the session's `created_at`. The
data is there; the enforcement is yours.

<Accordion title="What the assurance level does and does not gate">
`aal` is `"aal1"` for a password-only session and `"aal2"` once MFA has passed. It
travels in the token and on the session row.

What exists: the claim is available to you, and MFA is required for a session to
reach `aal2` when the user has it enabled.

What does not exist: there is **no `require_aal` directive, no `min_aal` config
key, and no way to demand a minimum assurance level declaratively.** If an
operation must require MFA, you check the `aal` claim yourself in a policy
condition or in your handler.
</Accordion>

## Claims you can and cannot trust

The token carries two metadata blobs and they are not equivalent. This is the
single most consequential distinction in the whole claim set.

| Claim | Source | Who can change it | Trust it for |
| --- | --- | --- | --- |
| `meta` | `user_metadata` | **The user**, via `PATCH /auth/v1/user` | Nothing security-relevant |
| `app` | `app_metadata` | Service keys and Studio only | Anything |

If a policy decides "is this user an employee" from a claim, and that claim came
from `meta`, the user granted it to themselves. The same information in `app` is
only writable by an administrator.

The other claims have their own character:

| Claim | Trust | Because |
| --- | --- | --- |
| `sub`, `email`, `username` | High | Server-owned, user cannot change the id |
| `roles`, `perms` | High, with staleness | Server-derived; changes land on next refresh |
| `org`, `org_role` | High, with staleness | Read at issue time from the membership row |
| `aal` | High, with staleness | Server-set; MFA state changes land on next refresh |
| `exp` | High | Cryptographically protected |

Everything except `exp` is a **snapshot**. The token is correct as of the moment it
was minted and can be up to `access_ttl` out of date by the time it is used. For
roles and permissions that is a deliberate performance trade-off. For organization
membership it is the thing to watch, because a removed member keeps their claims
until their next refresh.

<Warning>
Do not build a policy that reads `meta` to decide access. The moment a user can
edit a claim, that claim is an input they control.
</Warning>

## Passwords: what the policy actually enforces

Two policies, and the difference between them is larger than it looks.

| Policy | Behaviour |
| --- | --- |
| `basic` (default) | Length only, against `password_min_length` (default 8) |
| `strict` | The full validator, which returns a **list** of problems |

Either way a password over 1024 characters adds `"Password is too long."` to the
problem list.

When the policy fails, the response is a `422` whose body is a *list*:

```json
{
  "message": "the password does not meet the policy",
  "problems": ["Password must be at least 12 characters."]
}
```

<Warning>
`problems` is a list, not a string. A client that renders only the first problem
hides the rest, and users fix one issue at a time. Render all of them.
</Warning>

Studio exposes this as a **Policy** segmented control — **Basic** or **Strict** —
next to **Minimum length**, under **Users & auth → Configuration → Passwords**.

### Email normalisation

Addresses are stripped and lowercased, then must match a simple pattern and be at
most 255 characters, or they are rejected with `422 a valid email address is
required`. Because of the lowercasing, **all lookups are case-insensitive** — which
is a security property worth having and a source of confusion when you are
comparing strings yourself.

## MFA specifics worth knowing

The implementation details that have security consequences, rather than the
enrolment flow itself.

**TOTP secrets are encrypted at rest.** They are sealed with the platform's
secret box, which is keyed by `master_key`. They are never stored in plaintext,
and `master_key` must be backed up with the database — rotating it without that
backup makes every stored secret and TOTP factor unreadable.

**A TOTP code is accepted exactly once.** The last accepted time step is recorded,
and a step at or below it is rejected. This is why a code observed over a shoulder
cannot be replayed within its thirty-second window. A small window of clock drift
on either side is tolerated.

**Recovery codes are stored hashed and shown once.** They are generated as random
values, stored as SHA-256 hashes, and the raw codes are returned only at
generation. Ten are issued. There is no way to recover them — a user who loses
them uses the admin MFA reset route.

<Info>
Storing them hashed is what makes a database dump insufficient for account
takeover on the MFA path. It is the reason recovery codes are not a weaker
credential than the TOTP secret they replace.
</Info>

**MFA is opt-in per user, and gated per environment.** The `mfa_enabled` flag on
the environment lets users enrol; the flag on the user says whether they have. A
user with MFA enrolled does not get a challenge if the environment has MFA turned
off — the check is both, not either.

**Disabling MFA requires a current code.** Someone holding a session cannot
quietly remove the second factor. The same applies to replacing recovery codes,
which additionally requires a TOTP code rather than a recovery code.

### Password recovery is the strongest single credential

A recovery link sets the password, clears the lockout counters, and **revokes
every existing session**. That last part is what makes recovery safe: if the reset
was initiated because the account was compromised, the attacker's sessions die
with the legitimate ones.

What recovery does *not* do is require MFA re-enrolment. If the user had MFA
enabled, it stays enabled, and the recovery-completed session is a normal `aal1`
session that will be challenged at the next sign-in where MFA applies.

<Warning>
The recovery link is valid for one hour. Treat possession of an unopened recovery
email as account takeover, and do not forward it. Because recovery does not
require a second factor, it is the weakest link in an otherwise strong chain —
which is the argument for enabling MFA for anything that matters.
</Warning>

## Magic links and social sign-in

### Magic links

A magic link is a single-use, signed, time-limited token that carries the user.
It lives **15 minutes**, it cannot be reused, and it is consumed by a conditional
update so two concurrent clicks produce one success and one failure.

The security property is that there is no shared secret to phish — but the link
itself is a bearer credential for its lifetime. Anyone who obtains the email can
use it. A magic link arriving at `aal1` is not a second factor.

Completing a magic link also marks the address verified, so an unverified user who
signs in by magic link ends up verified. That is deliberate: proving control of the
inbox is the same proof.

### Social sign-in

The security-relevant rule in the social callback is about account linking: **an
unverified provider email never attaches itself to an existing account.** Only a
profile whose email is marked verified by the provider will match an existing
account by address.

Without that rule, anyone who could register an OAuth account with a victim's
unverified email address would be silently signed in as that victim. It is the
single most important line in the callback's account-resolution order.

The full order, in case you need to reason about an edge case:

1. If the flow is a **linking** flow, the link token is consumed and the identity
   attaches to that user. If it already belongs to someone else, the flow fails
   with `identity_already_linked`.
2. Otherwise look up the identity by provider and subject within this
   environment. Found — sign in.
3. Not found, and the provider email is **verified** — match an existing account
   by address.
4. Not found — create an account, but only if sign-up is enabled. Otherwise
   `signup_disabled`. An address already in use but unverified gives
   `signup_unverified_conflict`; a provider profile with no email gives
   `email_required`.
5. The resolved account is disabled — `account_disabled`.

<Warning>
Step 3 is the security boundary, and step 4's `signup_unverified_conflict` is what
stops a fresh OAuth attempt from colliding with an existing unverified signup.
Neither is configurable, and both are load-bearing.
</Warning>
## Sign-in methods compared on security properties

What each method actually buys you, stated without marketing. The useful question
for any of them is: **what is the credential, and who can present it?**

| Method | Credential | Factors | `aal` | Main weakness |
| --- | --- | --- | --- | --- |
| Password | A shared secret the user knows | 1 | `aal1` | Phishable, reusable, guessable at scale |
| Magic link | Possession of the email | 1 | `aal1` | The link is a bearer credential for 15 minutes |
| Social | An assertion from the provider | 1 | `aal1` | Depends entirely on the provider's own assurance |
| Any of the above + TOTP | The above, plus a rotating code | 2 | `aal2` | The code is phishable; no phishing-resistant factor exists |

Two observations that the table makes obvious.

**Adding a second factor changes the credential, not the first one.** TOTP makes
guessing the password insufficient, but it does nothing about phishing — an
attacker who relays both the password and a live code in real time still gets in.
There is no hardware-key or WebAuthn factor in this system to raise the bar
further.

**Only two of these can reach `aal2` without a password at all** — magic link and
social, both completed through the MFA challenge. What matters for policy is the
`aal` claim, not which method produced the session.

<Info>
A recovery-completed session is `aal1` even for a user who has MFA enabled,
because recovery does not challenge. If your application treats `aal2` as
"required for this operation", a user who reset their password is temporarily back
to `aal1` — which is correct behaviour, and worth designing around.
</Info>

## Authorization is a snapshot; authentication is not

Worth separating, because the two fail differently.

**Authentication** is checked cryptographically on every request and is always
current as far as the signature goes. A valid signature is a valid signature.

**Authorization** — roles, permissions, org membership — was read from the database
when the token was minted. It can be up to `access_ttl` stale, and nothing
revalidates it.

| Change | When it takes effect |
| --- | --- |
| Disabling an account | Immediately for new sign-ins; existing tokens until expiry |
| Revoking a session | Immediately for refresh; existing access tokens until expiry |
| Adding or removing a role | Next refresh |
| Changing an org membership or role | Next refresh |
| Turning off MFA for a user | Next refresh |

<Warning>
This asymmetry bites hardest on revocation of access. Roles disappear quickly;
account disablement does not, because a service verifying a signature has no way to
know the account is gone. If you need immediate cut-off, revoke at the gateway or
in your own middleware rather than relying on the auth service.
</Warning>

The practical rule: **use claims for gating, use the routes for decisions.** A
claim is right for deciding whether to show a menu item or which variant of a screen
to render. It is not right for deciding whether to move a large amount of money or
grant a permission — read the current state for those.

## What Pawabase cannot protect you from

Being explicit about this is more useful than a reassuring summary.

**A compromised service key is a full account.** A secret key can create, update
and delete users, manage sessions, reset MFA and change roles. There is no
scoping below "full access" on the auth admin routes. Treat a secret key the way
you would treat root on a database, store it in a secret manager, and rotate it
when someone leaves.

**XSS defeats cookie and header storage alike.** An `httpOnly` cookie keeps the
refresh token out of reach of JavaScript, but an XSS can still make authenticated
requests as the user. The storage decision buys you one class of defence, not
immunity.

**A compromised host is game over.** If `master_key` or `jwt_master_secret`
leaks, the derived keys can be regenerated and forged tokens minted for any
environment. These are the two secrets that matter most, and both are checked at
startup — services refuse to start in production while development defaults are in
place.

**Your own client bugs.** The largest single source of real auth incidents in a
system with rotation is a client that races its own refreshes. That is not an
attack, and no server-side control can distinguish it from theft.

## Environment isolation as a security property

The tenancy rule deserves its own treatment, because it is a containment boundary
rather than a feature.

Every user belongs to exactly one `project` + `env` pair, and that pair is part of
every query and every token. The practical consequences:

- An email address with an account in `acme/staging` has no account in
  `acme/production`. The staging password does not work there, and there is no
  account to attack.
- A staging session cannot be used against production. The signing key is derived
  per environment, and the `prj` and `env` claims are re-checked after the
  signature verifies.
- "Revoke every session" for a user means every session **in that environment**.
  Other environments are untouched.

<Warning>
This containment works in one direction. A compromise of `jwt_master_secret` is
**not** contained, because every environment's key is derived from it. Environment
isolation reduces the blast radius of a leaked per-environment secret; it does
nothing for the master.
</Warning>

This is why staging should be treated as a genuine separate system rather than a
copy that shares credentials, and why promoting a database between environments
without promoting its auth configuration produces confusing results.

## Key rotation, and what it does and does not fix

There are three secrets with different rotation properties, and conflating them
causes real problems.

| Secret | Derives | Rotating it means |
| --- | --- | --- |
| `internal_secret` | Context tokens, OAuth state, one-time link signatures | Unissued links and in-flight OAuth flows stop validating |
| `jwt_master_secret` | Every environment's user-token signing key | **Every access and refresh token in every environment stops verifying** |
| `master_key` | Sealed secrets and TOTP factors | Every stored secret and MFA factor becomes unreadable |

<Warning>
Rotating `jwt_master_secret` signs everyone out of every environment on the
installation at once, because there is no key id in the tokens to select between
old and new. Rotating `master_key` without a backup is worse — it permanently
locks out every user who enrolled MFA, with no recovery path.
</Warning>

The per-environment keys themselves cannot be rotated independently, because they
are *derived* from the master rather than stored. That is the deliberate trade:
deterministic derivation means every service can verify a token without calling
Akountz, at the cost of making the master the single point of rotation.

<Info>
This is also why `master_key` and `jwt_master_secret` are checked at startup in
production. A development default for either is not a code smell to be cleaned up
later — it is a condition the platform refuses to run in.
</Info>

## Data at rest

Two categories of sensitive material, handled differently.

**Passwords** are hashed by the platform's hashing layer, bcrypt by default with a
fallback to `pbkdf2_sha256`. Hashes are one-way; recovering a password is not
possible, by design.

**TOTP secrets** cannot be hashed, because the authenticator app needs to reproduce
a code from them on every use. They are therefore **encrypted** with the platform's
secret box, keyed by `master_key`. This is the one piece of authentication state
where secrecy depends entirely on a single key.

| Material | Protection | If compromised |
| --- | --- | --- |
| Password hashes | Hashed, bcrypt by default | Offline guessing becomes feasible |
| Recovery codes | SHA-256 hashed | Usable as MFA bypass without the TOTP secret |
| TOTP secrets | Encrypted with `master_key` | MFA is bypassable |
| One-time link tokens | Signed reference to a row | Forgery needs the internal secret |

The recovery-code row is the interesting one: because those codes are stored
hashed, a stolen database yields nothing usable on the MFA path. It is the reason
recovery codes are not the weak link they usually are.

## The admin surface is a full-privilege surface

Every route under the auth admin base is authenticated as a service, and none of
them are scoped. A credential that can reach them can do all of this:

- Create, update and delete any user
- Disable and re-enable accounts
- Reset any user's MFA
- Revoke any session, including all of them
- Set passwords directly, bypassing the user's recovery flow
- Grant and revoke roles and permissions
- Export a backup containing password hashes

There is no read-only key, and no per-collection scoping on these routes.

<Warning>
This is why "sign out everywhere" and "disable" are not equivalent tools. Disabling
is the blunt one — it also revokes sessions, and it takes effect on new sign-ins
immediately, while existing access tokens live out their remaining lifetime.
Prefer disabling for a compromised account and revoking for a routine
device-loss case.
</Warning>

The soft-delete behaviour is worth knowing before you use it: deleting a user
revokes sessions, deletes their identities and factors, marks them inactive, and
**rewrites the email to a non-routable placeholder** so the original address is
released for re-use. The history stays attributable; the address does not.

## Rate limiting, precisely

Three buckets, all keyed by IP against the installation's Redis, and all three are
per-IP rather than per-account. That distinction matters: a shared office NAT puts
many legitimate users behind one address, and a determined attacker rotates
addresses easily.

| Bucket | Limit | Window | Applies to |
| --- | --- | --- | --- |
| `akz:auth` | 30 | 60s | `/signup` and `/token`, all three grants |
| `akz:mfa` | 10 | 60s | MFA verify, disable and recovery-code replacement |
| `akz:links` | 10 | 60s | The emailed one-time link flows |

Two consequences worth internalising.

**The `/token` bucket is shared across grants.** A client stuck in a refresh loop
can exhaust the same 30-per-minute allowance that sign-in draws on, and you will
see a `429` on a request you would not expect to be limited.

**Per-IP plus per-account is the effective bound on guessing.** Neither mechanism
knows about the other. A distributed attacker gets 30 attempts a minute from each
address, and the per-account lockout is what actually stops a single account being
grounded down — which is why the lockout counter exists at all.

<Info>
Account lockout is the only per-account control in the system. Everything else is
per-IP, so anything that depends on rate limiting alone is bypassable by an
attacker with addresses.
</Info>

## The one-time link model

Emailed links are the least obvious part of the security model, because they are
neither JWTs nor session credentials.

A link token is a **signed reference to a database row**. The signature makes it
unforgeable and time-limited; the row makes it single-use and revocable. Both
halves are necessary — a signature alone would be replayable, and a row id alone
would be guessable.

| Purpose | Lifetime |
| --- | --- |
| `verify` | 24 hours |
| `recovery` | 1 hour |
| `magic` | 15 minutes |
| `mfa` | 5 minutes |
| `email_change` | 24 hours |
| `invite` | 7 days |
| `link` | 10 minutes |

Three properties make this design safe:

**Consumption is a conditional update.** The row is updated with a condition that
it is still unused; if the update matches nothing, someone else already spent it.
Two simultaneous clicks on the same emailed link produce one success and one
failure, and neither double-spends.

**Every failure is the same error.** Unknown, used, expired and wrong-purpose all
produce one identical response. An attacker cannot distinguish "already clicked"
from "never existed" — which would otherwise be an account-existence oracle.

**Purpose is baked into the signing.** A token signed for `verify` does not
validate as a `recovery` token, so a link from one flow cannot be replayed into
another.

<Warning>
The five-minute MFA challenge is the tightest of these, and it is worth
understanding why a wrong code does not consume it: the server peeks the token to
find the user, verifies the code, and consumes only on success. Users get the full
five minutes to try again, bounded instead by the lockout counter and the MFA rate
limit.
</Warning>

## Where Akountz-hosted pages differ

One configuration detail has a visible security consequence. The URL a message
links to depends on whether the environment has a `site_url`:

- **With `site_url`**, the link goes to your application, which completes the flow
  by calling the API.
- **Without one**, the link goes to Akountz's own hosted page, which completes the
  flow server-side.

So an environment with no `site_url` has Akountz rendering forms that handle
passwords and codes directly. That is a real difference in where credentials are
typed, and it is worth deciding deliberately rather than by omission.

<Info>
The hosted pages exist so an environment is usable before anyone has built a
frontend. They are a starting point, not a default to keep in production.
</Info>

## What to check in Studio, and where

Every setting referenced above is editable in Studio. The page is **Users &
auth**, and the settings live under the **Configuration** tab.

<Steps>
  <Step title="The Sign-up section decides who can get an account">

The section is described as *"Who can create an account, and whether their email
must be confirmed first."*

Two switches: **Sign-up enabled**, hinted *"Turn off to invite-only new
accounts."*, and **Require email verification**, hinted *"Unverified users can't
sign in until they confirm."*

Turning sign-up off is the single highest-value switch for a public-facing
application that should only have invited users. With it off, `POST /auth/v1/signup`
is a `403` and the social callback will not create accounts either — both paths
respect it.

  </Step>

  <Step title="The Passwords section is where lifetimes and policy live">

Described as *"Password strength and how long sessions last."* This is where
**Policy** (segmented **Basic** / **Strict**), **Minimum length**, **Access token
lifetime** and **Refresh token lifetime** are set.

Access token lifetime is the one to think hardest about: it is your revocation
latency against every service, because verification is local. Fifteen minutes is a
reasonable default for anything sensitive.

  </Step>

  <Step title="The Sign-in methods section gates what users can enrol in">

**Magic links**, hinted *"Passwordless sign-in by emailed one-time link."*, and
**MFA (TOTP)**, hinted *"Let users add an authenticator app for aal2."*

Turning MFA off here does not remove MFA from users who already enrolled — it
means they are no longer *challenged*. If you want the factors gone, that is an
administrative action per user, not a switch.

  </Step>

  <Step title="The URLs section is the redirect allowlist">

Described as *"Where a browser is allowed to land after an OAuth or magic-link
redirect."* **Site URL** takes your application's base URL, and **Additional
allowed redirect URLs** takes the extra prefixes.

This is where the prefix-matching rule bites. A redirect to a path under your site
URL is allowed; a redirect to a lookalike domain is not, and does not become
allowed by being similar.

  </Step>

  <Step title="The Sign-in activity tab is your compromise early-warning system">

Columns **When**, **Event**, **Email**, **Result**, **IP**, with a **failures
only** checkbox.

The Result badge renders `ok` in green for a success and the `reason` string in
red for anything else. Reuse-detection messages appear here and nowhere else,
which makes this the only place a stolen-token replay is visible.

  </Step>
</Steps>

<Warning>
Auth configuration is cached for **10 seconds**. A change made in Studio can take
that long to affect new tokens, which regularly looks like a failed edit. It also
means the cache is shared: a change affects every environment user whose key
matches, not just your own session.
</Warning>

The complete set of events the auth service emits. Subscribing to a name that is

| Event | Emitted when |

## Verifying the model, rather than trusting the page

A short set of behaviours that are worth confirming against your own deployment,
because each of them is the thing that would hurt most to get wrong. None of them
require reading source; all of them are observable.

<AccordionGroup>
  <Accordion title="A staging token must be rejected by production">
  Sign in against staging, take the `access_token`, and send it to a production
  endpoint. It must be rejected. If it is not, environment isolation is not doing
  what this page claims.

The rejection should come from the `prj`/`env` check, not from a missing session —
which is why the error is indistinguishable from any other authentication failure.
  </Accordion>

  <Accordion title="A revoked session must be unable to refresh">
  Revoke a session, then attempt a refresh with its token. It must fail. This is
  the property that makes revocation meaningful, and it is the one that holds even
  though the old access token still works.

If a revoked session can still refresh, something is wrong with the family
revocation rather than with your client.
  </Accordion>

  <Accordion title="An unknown email must be indistinguishable from a wrong password">
  Compare the two responses closely — status, body, and shape. They should be
  identical. A difference in either is an enumeration oracle, and it is the most
  common finding in an auth review of this kind.
  </Accordion>

  <Accordion title="A consumed refresh token must revoke the family">
  Refresh once, then refresh again with the original token. The second attempt must
  fail **and** the first refresh's token must now also be dead.

The second half is what distinguishes real theft detection from simply rejecting a
stale token, and it is easy to miss when testing.
  </Accordion>

  <Accordion title="Disabling an account must prevent new sign-ins">
  Disable a user and attempt to sign in. It must be refused, and every session must
  be revoked.

Note that access tokens already issued keep working until they expire. That is
expected and is not a failure of the disable.
  </Accordion>

  <Accordion title="An unapproved redirect must not receive tokens">
  Pass a `redirect_to` pointing at a domain you do not control, on the sign-up and
  OAuth paths. Both must refuse it.

For the OAuth callback specifically, the expected behaviour is that the redirect is
silently dropped rather than rejected — so the flow completes with no redirect
target. Confirming it lands nowhere is the point.
  </Accordion>

  <Accordion title="A user must not be able to promote themselves">
  Set a value in `user_metadata` through `PATCH /auth/v1/user`, then read it back
  from the `meta` claim. It will be there, and a policy reading `meta` would trust
  it.

The same value in `app_metadata`, set through the admin route, is not user-writable.
Confirming that asymmetry is what makes the guidance actionable.
  </Accordion>
</AccordionGroup>

<Info>
Every one of these is a two-minute check with curl and a browser. A deployment that
has never had them run is not verified, however well the defaults are set.
</Info>

## Where the boundaries are, summarised

The most compact statement of the whole model:

**Cryptographic and always current** — the signature, the audience, the token type,
the project and environment it belongs to, and its expiry.

**A snapshot, up to `access_ttl` stale** — roles, permissions, organization and
organization role, the assurance level, and anything in `meta` or `app`.

**Enforced immediately, for new sessions only** — account disablement, session
revocation, MFA removal.

**Not enforced at all, because it cannot be** — anything requiring a live lookup:
whether a token was revoked thirty seconds ago, whether an account still exists,
whether the client IP matches the one at sign-in.

**Yours to enforce** — CSRF protection for your own application, XSS resistance,
refresh serialisation, maximum session age, and any MFA requirement, since there is
no declarative way to demand an assurance level.

<Warning>
If you take one thing from this page: the system is deliberately built so that
verification needs no database. Everything that design implies — stale
authorization, bounded revocation latency, no device binding — follows from that
single choice, and each of them is a thing you have to decide about explicitly.
</Warning>
## The production checklist

Ordered by how much damage getting it wrong causes, rather than by topic. Each
item names the concrete setting or behaviour to verify, because "review your auth
config" is not actionable.

<AccordionGroup>
  <Accordion title="Secrets, before anything else">
  - `internal_secret`, `jwt_master_secret` and `master_key` are **not** their
    development defaults. Services refuse to start in production while they are,
    which means the check is enforced rather than advisory.
  - `master_key` is backed up with the database. Losing it makes stored secrets and
    every TOTP factor permanently unreadable, locking out every user who enrolled
    MFA.
  - Secret keys are in a secret manager, not in source, not in committed files, and
    not in client-side code.
  - Keys in use are rotated on a schedule, and the old ones are known to be retired
    rather than merely replaced.
  </Accordion>

  <Accordion title="Environment configuration">
  - `signup_enabled` is `false` unless the application is genuinely open. This is
    the highest-value single switch.
  - `require_email_verification` is `true` anywhere unverified addresses matter.
  - `site_url` is set, and `redirect_urls` contains only URLs you control.
  - `redirect_urls` is empty rather than holding a wildcard-looking placeholder.
  - `default_roles` grants the least privilege a new account needs to be useful.
  - Provider entries all have a `client_id`, so they appear in the settings response
    rather than silently 404-ing.
  </Accordion>

  <Accordion title="Token lifetimes">
  - `access_ttl` is short enough that revocation latency is acceptable. Fifteen
    minutes is the default and a sound choice.
  - `refresh_ttl` is short enough that a lost device stops being useful. Thirty days
    is the default; consider shorter for sensitive applications.
  - You accept that shortening `access_ttl` obliges your client to refresh
    reliably, and that it does.
  </Accordion>

  <Accordion title="Password policy">
  - `password_policy` is `strict` rather than `basic` for anything handling real
    data. `basic` is a length rule only.
  - `password_min_length` is set deliberately — 8 is the default, 10 or more is a
    better floor.
  - Your client renders **all** entries in `problems`, not just the first.
  - The lockout threshold and duration suit your user base, knowing they are
    installation-wide rather than per-environment.
  </Accordion>

  <Accordion title="MFA">
  - `mfa_enabled` is `true`, so users can enrol at all.
  - Users who need a second factor actually have one. Enrolment is opt-in and
    nothing forces it.
  - Recovery codes are distributed securely, understanding they are shown **once**
    and are unrecoverable afterwards.
  - The admin MFA reset route is available, and you know when to use it — it
    deletes factors *and* recovery codes.
  - Recovery links are treated as account takeover if intercepted.
  </Accordion>

  <Accordion title="Client behaviour">
  - The refresh token is stored where page scripts cannot read it.
  - Refreshes are serialised — one in flight, with other requests waiting on it.
  - A failed refresh never retries with the same token. It signs in again.
  - `mfa_required` is checked before assuming a token is present.
  - The `org` field is omitted rather than sent as `null`, if the app is
    org-scoped.
  </Accordion>

  <Accordion title="Monitoring">
  - You have reviewed the **Sign-in activity** tab and know your normal failure
    rate.
  - Something watches for `session.reuse_detected` — the only signal that a refresh
    token was replayed.
  - `user.disabled`, `user.deleted` and `user.mfa_reset` are subscribed to, so
    administrative actions are visible to whoever is accountable.
  - You have accepted that failed sign-ins and successful refreshes emit no events,
    and use the login-event table for that history.
  </Accordion>

  <Accordion title="Data handling">
  - Backups containing identities are treated as credential archives, because they
    include password hashes. Access to them is restricted accordingly.
  - You understand `master_key` is what protects sealed TOTP secrets, which is why
    that key's protection is the whole ballgame.
  - Deleted accounts are understood to be soft-deleted, with the email rewritten to
    a non-routable address so the original is released for re-use.
  </Accordion>
</AccordionGroup>

## Common mistakes, and what they actually cause

| Mistake | What really happens | Instead |
| --- | --- | --- |
| Retrying a refresh after a timeout | Family revoked; user signed out | Treat as terminal; sign in again |
| Two tabs refreshing at once | Family revoked by theft detection | Serialise refreshes |
| Sending `"org": null` from an absent value | Session silently leaves its organization | Omit the key |
| Setting `access_ttl` to an hour | Disabled accounts usable elsewhere for an hour | Keep it near the default |
| Reading `meta` in a policy | User can grant themselves the claim | Read `app` |
| Assuming a `201` from sign-up means signed in | `undefined` token when verification is required | Check `verification_required` |
| Turning off MFA in config to remove factors | Factors remain; users simply are not challenged | Admin MFA reset per user |
| Expecting `revoked_at` to invalidate tokens at once | Old access tokens work until expiry | Accept the `access_ttl` window |
| Hard-coding providers or sign-up flags in the UI | Breaks when the environment is edited | Read `GET /auth/v1/settings` |
| Looking for a `theft_detected` field | It does not exist | Read the events |
| Setting a session absolute expiry | No such field exists | Enforce from `created_at` yourself |

<Info>
Most of that table is one lesson stated repeatedly: local token verification means
anything derived from the database is a snapshot, and anything you want enforced
continuously has to be enforced by you.
</Info>

## The attack surface, worked through

Each threat below names the mechanism that addresses it and, just as importantly,
the limit of that mechanism. Knowing both is what tells you where to put your own
controls.

### Credential guessing

**Addressed by** rate limiting on the auth bucket, plus a per-account lockout counter
that clears on success.

**Limit:** both are per-IP or per-account, never per-human, and a distributed
attacker with many addresses is bounded only by the lockout. Nothing detects a
low-and-slow attempt that stays under the threshold — nine failures a day for a week
is invisible, and the account is unlocked again each morning.

**Your move:** password policy and MFA. Neither rate limiting nor lockout
substitutes for a password that is not guessable from a breach.

### Credential stuffing

**Addressed by** the password hash. bcrypt by default, so an offline attack against a
stolen hash table is expensive per guess.

**Limit:** it does nothing about an attacker using a *real* password list against
your endpoint. In that case lockout and rate limits are the only controls, and both
are evadable.

**Your move:** MFA. A stuffed password is worthless against an account with a second
factor, which is why it is the single highest-value control on this list.

### Refresh token theft

**Addressed by** single-use rotation with family revocation on reuse.

**Limit:** a stolen refresh token works exactly once before the session dies — but
that one use yields a fresh access token, and nothing revokes the access tokens
already minted from the family. Theft is detected, not prevented.

**Your move:** the transport. Rotation bounds the value of a stolen token; it does
not stop it being stolen. `httpOnly` cookie storage, short `access_ttl`, and TLS
between your server and the auth endpoint are the actual defences.

### Access token theft

**Addressed by** short lifetime. Fifteen minutes by default, and you can shorten it.

**Limit:** during its remaining life the token is indistinguishable from a legitimate
one, to every service, because verification is local and there is no revocation
check. If you hold it in `localStorage`, one XSS reads it.

**Your move:** `access_ttl` and storage. Halving the lifetime halves the window.
Nothing else shortens it, because there is no deny list to consult.

### Session hijacking via a leaked identifier

**Addressed by** the session id being the token family, and by there being nothing to
guess — it is 32 bytes of random hex.

**Limit:** if a user pastes a full token into a support chat, that is a bearer
credential for the remainder of its life, and it can be used to mint new tokens for
the whole refresh window. Support should treat any pasted token as compromised and
revoke the session.

**Your move:** revoke on sight.

### Account enumeration

**Addressed by** uniform responses on sign-in, on the emailed-link routes, on one-time
token consumption, and on organization slugs.

**Limit:** the uniformity is only as good as the routes you built. A route of your own
that returns a different status for "no such user" reintroduces the oracle, and
nothing in the auth service can catch that.

**Your move:** keep your own error paths uniform too.

### Redirect abuse

**Addressed by** prefix matching against `site_url` and `redirect_urls`, applied to
every `redirect_to`.

**Limit:** the allowlist is checked against configured prefixes, so a mistake in the
configuration is a mistake everywhere. And on the OAuth **callback** an unapproved
target is dropped rather than rejected, so the flow completes — with no redirect,
not with an error.

**Your move:** keep the allowlist short, and prefer `site_url` plus specific paths
over a broad prefix.

### Privilege escalation through claims

**Addressed by** the split between `meta` and `app`. Only `app` is administrator-
writable, and only `app` should carry access decisions.

**Limit:** the split is only a defence if you use it. A policy reading `user_metadata`
is not merely weaker — it is fully user-controlled, because the user can edit that
field themselves through the profile route.

**Your move:** audit your policies for `meta` reads. `/policies/context` is explicit
that these must not gate access.

### Cross-environment confusion

**Addressed by** the derived per-environment key and the `prj`/`env` claim check.

**Limit:** it contains a leaked per-environment key, not a leaked master. Rotating
`jwt_master_secret` signs everyone out everywhere at once, because tokens carry no key
id to distinguish generations.

### The cache lag, stated precisely

Auth configuration is cached per environment for `config_ttl` seconds. Everything in
the first block of that table is subject to it.

The consequence worth planning for: **a change is not atomic with your next
request.** After you save a shorter `access_ttl` in Studio, requests for up to ten
seconds still mint tokens under the old value. After you disable sign-up, sign-up
attempts still succeed for up to ten seconds.

The cache is keyed by project and environment, not by user, so a change also shifts
what other administrators observe — you are not testing it in isolation.

<Note>
An unset key silently falls back to its default rather than being an error, which is
the answer to "why didn't turning this off work". `/auth/configuration` covers the
full set and where each one is edited.
</Note>

## Misleading errors, and what they hide

The auth surface deliberately collapses several different causes into one response.
That is right for security and wrong for debugging, so a table of what each message
is really saying earns its place.

| What you see | What it might actually be |
| --- | --- |
| `400 invalid email or password` | Unknown email **or** wrong password |
| `401 invalid refresh token` | Expired, malformed, consumed, revoked, wrong environment, or deleted account |
| `403 this account is disabled` | Also covers accounts deactivated by a soft delete |
| `403 you are not a member of that organization` | Organization does not exist **or** you are not a member |
| `400 the link is invalid or has expired` | Wrong, used, expired, or wrong-purpose token |
| `429 too many failed attempts` | Account lockout; **not** the rate limit |
| `429 rate_limit_exceeded` | The IP bucket; **not** the account |
| `401 the account is not available` | Disabled **or** soft-deleted |
| `401 the session was revoked` | Minted after rotation, then discarded |
| `400 the challenge is no longer valid` | The user behind the MFA challenge was disabled mid-flow |

<Warning>
The two `429`s are the most confusable pair, because the remedies are unrelated.
`too many failed attempts` is per-account and clears by unlocking or waiting.
`rate_limit_exceeded` is per-IP and clears by waiting; retrying harder makes it
worse, and it arrives with a `Retry-After` header and a structured body rather than
a `detail` string.
</Warning>

The resolving technique is the same in every case: the login-event history carries
the specific reason string. `/auth/managing-users` covers reading it per user, and
the environment-wide events route covers it across all users.

### Three footguns that look like platform bugs

**A `200` from the token endpoint that contains no token.** The password grant
returns `mfa_required` instead when MFA applies, so a client that reads
`access_token` without checking finds `undefined`.

**A `201` from sign-up that contains no session.** With verification required the
response carries `user`, `session: null` and `verification_required: true`.

**A user who exists in one environment and not another.** Every lookup is scoped by
project and environment, so "the account is missing" is frequently "the account is
in the other environment".

All three follow from the same design rather than being defects, and all three are
worth checking before anyone concludes something is broken.

Studio's own operators live in a reserved environment whose configuration is
hardcoded rather than editable, and it is stricter than any project environment:
sign-up off, strict password policy, a ten-character minimum, one-hour access
tokens and seven-day refresh tokens.

It matters for two reasons. An operator session behaves differently from a user
session in ways that look like misconfiguration. And no configuration key changes
it, so there is nothing to look up.

`/reference/environment-settings` covers how configuration is carried between
environments, and `/operate/environments-and-promotion` covers promotion.
**Your move:** protect the master above everything else in this document.

## Security outside the auth service

Authentication ends at the boundary of the auth service; what happens with the
resulting identity is where most real-world incidents actually occur. The joins
below are the ones worth reasoning about deliberately.

### Policies are the trust boundary

A policy is the mechanism that turns a verified token into an access decision, and
the claims it reads are the same ones this document has been describing. Three
things follow from that.

First, a policy reading `meta` is not merely weaker than one reading `app` — it is
**fully user-controlled**, because the user can edit that field themselves. Second, a
policy reading a key that does not exist evaluates to a comparison between two empty
values, which is **true**, so a typo in a claim name produces a condition that admits
everyone. Third, `$auth.authenticated` should gate any condition that compares
another `$auth` key, because every key is empty for a signed-out caller.

<Warning>
The failure mode worth naming explicitly: a typo'd claim name does not throw and does
not deny. It admits. A policy that silently fails open is the worst kind, and it is
invisible until someone tests the boundary deliberately. `/policies/debugging` covers
how to check this.
</Warning>

### Storage turns claims into isolation

Bucket policies get `$object` alongside `$auth`, which is how per-user and
per-tenant isolation is expressed without a database lookup. Keys shaped
`<user_id>/<filename>` scope a user to their own prefix by comparing
`$object.segments.0` to `$auth.user_id`; keys shaped `<org>/<filename>` do the same
with `$auth.org`.

Both patterns require a `truthy` check on the claim first. Without it, an anonymous
caller's empty `$auth.org` matches an empty prefix — the same fail-open shape as
above. `/storage/access` covers the patterns.

### Realtime evaluates channel rules with the token

A realtime connection carries the same token, so channel access is decided from the
same claims. The consequence to plan for is timing: channel membership is evaluated
with the claim as of the token's issue, so removing a member from an organization
changes their channel access when they next refresh, not immediately.
`/realtime/channel-rules` covers the rule language.

### Flows and jobs have no user by default

Flows triggered by platform events run as themselves. Jobs and schedules run with
service authority and **no user token at all**. That has a direct security
consequence:

<Warning>
Disabling an account revokes its sessions, but it does not stop an unattended job
that acts on that user's behalf. Pairing a subscription to the account-disabled event
with cancelling the relevant schedule is the only way to stop the work itself.
`/jobs/schedules` covers scheduling; `/flows/triggers` covers subscriptions.
</Warning>

### Webhooks do not carry user identity

An outbound webhook carries a signature rather than a token, and an inbound webhook
is authenticated as itself. Do not design a system where a webhook handler assumes it
is acting for a specific user — it is not, and the only user-associated data it has is
whatever the payload contained. `/webhooks/signatures` covers both directions.

### Service keys cross every boundary at once

A secret key is not scoped to the auth service. The same credential that reaches the
admin routes can read and write application data, because it bypasses policies by
role. That is the single fact that most changes how service keys should be handled:
they are not "auth credentials with extra rights", they are a platform-wide
superuser.

`/operate/api-keys` covers issuing and scoping them, and `/operate/secrets` covers
storing them.

## What an attacker needs, ranked by cost

A useful inversion of the whole model: what would an attacker actually have to
compromise to reach an account, cheapest first.

| What they take | What they gain | How to make it expensive |
| --- | --- | --- |
| A user's password | Sign-in, then an MFA challenge | Enforce MFA; a stolen password alone is insufficient |
| A user's refresh token | One use, then the session dies | Short `refresh_ttl`; the window is the lifetime |
| A user's access token | That user, until expiry | Short `access_ttl`; httpOnly storage |
| A password database dump | Offline guessing against hashes | Strong policy; the hash is the only defence here |
| One environment's derived key | Forge tokens for that environment | Keep the master secret far away from it |
| The `jwt_master_secret` | Forge tokens for **every** environment | The crown jewel; this is the one that matters |
| The `master_key` | Decrypt every stored secret and TOTP factor | Back it up, and never export it |
| A service key | Full administrative access, no scoping | Secret manager; rotation on personnel change |
| An XSS in your frontend | Whatever the session can do | Not solvable by token design — solve it in the frontend |

<Info>
The bottom row is the honest answer to "what is the weakest link". Nothing in the
token design prevents a script running on your page from acting as the user. Every
row above it can be hardened by configuration; that one cannot.
</Info>
## Responding to a suspected compromise

The sequence, and why each step is in that order. This is the part of the model
that gets improvised under pressure, so it is worth having written down.

Revoke the sessions first. `POST {base}/users/{id}/sessions/revoke` ends every
session in that environment immediately, and refreshes become impossible. It costs
nothing and it is reversible in effect — the user signs in again.

Disable the account if the compromise is not yet understood, or if you need the
user out of the system rather than merely logged out. Disabling also revokes
sessions, so it subsumes the first step; do it second only when you want the
softer action first.

Reset MFA if the account had it. This does **not** revoke sessions, which is exactly
why it comes after rather than instead of the revocation — the reverse order leaves
the attacker's sessions alive.

Rotate `jwt_master_secret` only if you suspect the platform itself is compromised.
It signs out every user in every environment on the installation, so it is a
last resort with a large blast radius, not a routine response.

<Warning>
Order matters in one specific way: **resetting MFA before revoking sessions leaves
the attacker in.** The reset only removes the factors; the sessions they already hold
remain valid, including ones carrying the old assurance level.
</Warning>

### What to capture while you still can

Before deleting anything, three things are cheap to collect and impossible to
reconstruct afterwards:

- The user's full history, which holds the reason strings the API deliberately
  hides — including any refresh-theft messages.
- The session list, with IPs and user agents, while the sessions still exist. Deleting
  the account destroys this.
- The environment's failure events, if other accounts may be involved.

<Note>
Deleting an account rewrites its email to a placeholder and removes its identities and
factors. It preserves the user row so events stay attributable, but it does **not**
preserve the session rows. Capture first.
</Note>

### After containment

Sign-in events and authentication events are durable and read-only, so the timeline
survives everything above. If you revoked rather than deleted, the user re-enrols in
MFA from scratch — new secret, new provisioning URI, new recovery codes — because the
old ones were removed rather than invalidated.

Then watch `failures_24h` and the `session.reuse_detected` event for a week. A
compromised credential usually shows continued use after containment, and the
revocation only stops new sessions.
