There are **two** error formats, and a client that assumes one will break on the other.

### Gateway errors — an object

The gateway always returns this shape, and these are the only errors with a stable `code`:

```json
{ "error": "missing_api_key", "message": "Send a valid project API key in the apikey header." }
{ "error": "invalid_api_key", "message": "…" }
{ "error": "origin_not_allowed", "message": "https://evil.example may not use this key." }
{ "error": "rate_limit_exceeded", "retry_after": 42 }
```

Note the third key: `retry_after` is a **number of seconds**, not a timestamp, and there is no `message` on the rate-limit form.

```python
await _json(
    send,
    429,
    {"error": "rate_limit_exceeded", "retry_after": max(int(result.retry_after), 1)},
    [(b"retry-after", str(max(int(result.retry_after), 1)).encode())],
)
```

### Akountz errors — the detail *is* the body

This is the part that trips people up. When a Sillo `HTTPException` is raised, the handler returns the detail as the entire JSON body — not wrapped in an `error`/`message` envelope:

```python
async def http_exception(
    self, ctx: HttpContext, exc: HTTPException
) -> BaseResponse:
    """Handle an HTTPException by producing an appropriate error response.
    ...
    """
    assert isinstance(exc, HTTPException)
    if exc.status_code in {204, 304}:
        return BaseResponse(
            body=b"", status_code=exc.status_code, headers=exc.headers
        )
    return json(exc.detail, status_code=exc.status_code, headers=exc.headers)
```

So a failed sign-in is **not** `{"error": "invalid_email_or_password"}`. It is:

```json
"invalid email or password"
```

A bare JSON string. A `403` on organization switching is:

```json
"you are not a member of that organization"
```

<Warning>
A client that reads `body.error` for every non-2xx response gets `undefined` on every Akountz error, and a client that assumes `body.message` gets `undefined` too. Read the body **once**, and handle both shapes: an object with `error` (gateway) or a bare string (service).
</Warning>

There is one exception inside Akountz: the password policy failure carries a nested object, because its `detail` is a dict:

```python
raise HTTPException(
    status_code=422,
    detail={"message": "the password does not meet the policy", "problems": problems},
)
```

```json
{
  "message": "the password does not meet the policy",
  "problems": ["Password must be at least 12 characters."]
}
```

And request-body validation failures come from a different handler entirely:

```python
return json({"detail": exc.errors}, status_code=422)
```

```json
{
  "detail": [
    { "loc": ["query", "page"], "msg": "...", "type": "..." }
  ]
}
```

So a `422` from Akountz is one of **three** shapes depending on which layer rejected the request. Read `problems` if present, fall back to `detail`, and never assume a fixed key.

### A defensive error reader

```text
export class PawabaseError extends Error {
  constructor(status, body) {
    const message =
      typeof body === "string"
        ? body                                        // Akountz: detail is the body
        : body?.message                              // gateway, or password policy
        ?? body?.detail?.message
        ?? body?.error
        ?? `request failed (${status})`;
    super(message);
    this.name = "PawabaseError";
    this.status = status;
    this.body = body;
    this.code = body?.error ?? null;                 // gateway only
    this.retryAfter = body?.retry_after ?? null;      // 429 only
    this.problems = body?.problems ?? null;           // password policy only
  }
}

export async function readError(response) {
  const body = await response.json().catch(() => null);
  return new PawabaseError(response.status, body);
}
```

```python
class PawabaseError(Exception):
    def __init__(self, status: int, body):
        self.status = status
        self.body = body
        super().__init__(f"{status}: {_message(status, body)}")


def _message(status: int, body) -> str:
    if isinstance(body, str):
        return body                                   # Akountz detail
    if isinstance(body, dict):
        if "problems" in body:                        # password policy
            return "; ".join(body["problems"])
        if "message" in body:
            return body["message"]
        if "error" in body:
            return body["error"]
        if "detail" in body:
            return str(body["detail"])
    return f"request failed ({status})"
```

### The statuses a client must branch on

| Status | Meaning | Retry? |
| --- | --- | --- |
| `400` | Malformed request, bad credentials, invalid or used link | No — fix the request |
| `401` | No token, expired token, wrong environment, revoked session | Refresh once, then sign out |
| `403` | Authenticated but refused: policy, disabled account, unverified email, wrong org | No |
| `404` | Not found — or "no such organization", which also covers "not a member" | No |
| `409` | Conflict — slug taken, last owner, already a member | No |
| `422` | Validation or password policy | No — show `problems` |
| `429` | Rate limited | Yes, after `retry_after` seconds |
| `500`+ | Server fault | Yes, with backoff |

The two `401`s are worth separating. A `401` from **your API** means the access token expired — refresh and retry. A `401` from **`/auth/v1/token`** means the refresh token is dead — do not retry, sign the user out. The endpoint tells them apart.

A `401` from the API can also mean a **wrong-environment** token, and no amount of refreshing will fix that:

```python
def verify_user_token(token: str, master: str, *, project: str, env: str) -> dict[str, Any]:
    """Verify a user access token for *project*/*env*. Raises :class:`TokenInvalid`."""
    claims = _decode(token, derive_env_secret(master, project, env), audience=USER_AUDIENCE)
    if claims.get("typ") != "access":
        raise TokenInvalid("not an access token")
    if claims.get("prj") != project or claims.get("env") != env:
        raise TokenInvalid("token belongs to another environment")
    return claims
```

If refreshing succeeds and the retried request still returns `401`, suspect this: your client is pointed at staging with a production token, or the API key and the token belong to different environments.


## Rate limits

Two independent limiters can apply.

The gateway limits per key, or per client IP when there is no key:

```python
result = await self.limiter.check(HttpContext(scope, receive))
if result is not None and not result.allowed:
    self.stats["rate_limited"] += 1
    note("rate_limited", True)
    await _json(
        send,
        429,
        {"error": "rate_limit_exceeded", "retry_after": max(int(result.retry_after), 1)},
        [(b"retry-after", str(max(int(result.retry_after), 1)).encode())],
    )
    return
```

Akountz limits its own auth routes:

```python
limits = rate_limit_middleware(
    {"limit": 30, "window": 60}, "akz:auth", akountz.settings.redis_url
)
```

applied to `POST /signup` and `POST /token`. MFA endpoints use `{"limit": 10, "window": 60}` under the `akz:mfa` namespace. The backing store is `redis_url` when configured, otherwise an in-process counter — so a multi-worker deployment without Redis gets a per-worker limit, not a global one.

Route-level limits answer with a slightly different body and helpful headers:

```python
return json_response(
    {
        "error": "rate_limit_exceeded",
        "message": "Too many requests. Slow down and retry later.",
        "retry_after": retry_after,
    },
    status_code=429,
    headers={
        "Retry-After": str(retry_after),
        "X-RateLimit-Limit": str(result.limit),
        "X-RateLimit-Remaining": "0",
    },
)
```

So `429` from the gateway has **no `message`**, and `429` from an Akountz route **does**. Read `retry_after`, falling back to the `Retry-After` header.

<Warning>
`POST /auth/v1/token` shares a 30-per-60-seconds budget with `POST /auth/v1/signup`. A client that refreshes on every request — rather than on expiry — will exhaust it. Refresh on a schedule, not per request.
</Warning>

```text
async function withBackoff(fn, { attempts = 3 } = {}) {
  for (let i = 0; i < attempts; i++) {
    const response = await fn();
    if (response.status !== 429) return response;
    const error = await readError(response);
    const wait = error.retryAfter
      ?? Number(response.headers.get("retry-after"))
      ?? 2 ** i;
    if (i === attempts - 1) return response;
    await new Promise((resolve) => setTimeout(resolve, wait * 1000));
  }
}
```
