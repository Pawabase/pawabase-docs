Password recovery is how a person who cannot remember their password gets back in. They ask for a link, the link arrives in the mailbox they control, they choose a new password, and the old one stops working — along with every session it had.

It is the same machinery as email verification and magic links, with a different lifetime and a much more consequential set of side effects. The token is the shared one-time token; the 1-hour lifetime is the `recovery` purpose's own setting; the single-use property comes from the same conditional update. What is unique here is everything the reset does after the token is consumed.

<CardGroup cols={3}>
  <Card title="One hour, once" icon="clock">The `recovery` token lives for 3600 seconds and is consumed by the first successful reset. A second attempt with the same link gets the same undifferentiated 400 as an expired one.</Card>
  <Card title="A reset ends every session" icon="lock">Every token family the account holds is revoked, so a person who reset because they think someone else is in is not still leaving that person in.</Card>
  <Card title="Two steps, and the first is free" icon="list">Confirmation can be peeked to show a form without spending the token, so a mistyped password does not cost the person their link.</Card>
</CardGroup>

## Where this sits in the layered model

| Layer | What it does for recovery |
| --- | --- |
| **Akountz** (identity) | Owns the token row, sends the message, checks the new password against the policy, writes the hash, revokes sessions, starts a session, writes the activity event. |
| **The API** (project config) | Owns `site_url`, `redirect_urls`, `password_policy`, `password_min_length`, and the `recovery` message override. |
| **Gateway / `pawabase_core`** | Verifies the session that the reset starts. It plays no part in the reset itself. |

The tenancy rule applies without exception: a recovery token is scoped to one `project` and `env`, so a link generated in staging cannot set a password in production even if the addresses match.

<Info>
If you have not read [Authentication](/auth/overview), do that first. The layered model and the per-environment tenancy rule are assumed throughout.
</Info>

## The two routes

| Route | Method | Purpose |
| --- | --- | --- |
| `/auth/v1/recover` | POST | Send the reset link. Answers identically in every case. |
| `/auth/v1/recover/confirm` | POST | Set the new password. |
| `/auth/v1/links/{project}/{env}/recovery` | GET | The hosted page. Only reachable when `site_url` is empty. |
| `/auth/v1/links/{project}/{env}/recovery` | POST | The hosted page's form target. Also only used without a `site_url`. |

Both schema routes are context-scoped: the environment comes from the request context, not from the URL. The two hosted routes carry the environment in the path, because a link opened from a mail client arrives with no API key and no context header.

### Asking for a link

```bash
curl -X POST "https://api.example.com/auth/v1/recover" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{"email": "Ada@Example.com"}'
```

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `email` | string | required | The address. Stripped, lowercased, validated. |
| `redirect_to` | string | `null` | Where the link should land. Must be allowlisted. |

The response is the same in every case:

```json
{ "sent": true, "message": "If the address has an account, a message is on its way." }
```

A message actually goes out only when the address has an account in this environment **and that account is not disabled**. That second condition is the difference from the verification route, which has no such check.

<Warning>
The uniform response is what prevents this endpoint from being a membership oracle. A script that POSTs a million addresses learns nothing, because the answer is a constant. Do not "improve" it by returning 404 for unknown addresses, and do not disable the button in your client based on the response.
</Warning>

The route is limited to **10 requests per 60 seconds** per caller under the key `akz:links`, backed by Akountz's `redis_url`. Sign-up and password sign-in have a separate budget of 30 per 60 seconds under `akz:auth`.

When a message is genuinely sent, a `recovery_requested` event is written to the activity log. When nothing is sent, nothing is written — so an activity trail that shows a request is evidence that a message was really produced.

### Setting the new password

```bash
curl -X POST "https://api.example.com/auth/v1/recover/confirm" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "token": "UmVjb3Zlcnktbm90LWEtcmVhbC10b2tlbg.hT3m9Q.kJ8vB2nQ4s",
    "password": "a-longer-one-than-before"
  }'
```

| Field | Type | Meaning |
| --- | --- | --- |
| `token` | string | 10 to 2048 characters. The `token` value from the link. |
| `password` | string | 1 to 1024 characters before the policy check. |

The order of operations inside this route determines what a mistake costs:

| Order | Step | On failure |
| --- | --- | --- |
| 1 | Peek the token: verify the signature and the row, without consuming. | `400 the link is invalid or has expired` |
| 2 | Check the new password against the environment's policy. | `422` with a list of problems. The token is untouched. |
| 3 | Consume the token. | `400`. |
| 4 | Set the password, clear `failed_logins`, clear `locked_until`. | — |
| 5 | Revoke every session for the account. | — |
| 6 | Write a `password_reset` activity event and emit `user.password_reset`. | — |
| 7 | Start a session with the method `recovery`, and return the tokens. | — |

Step 2 before step 3 is the design decision that makes the two-step flow safe. A password that fails the policy does not consume the token, so the person can try again with the same link. A token is spent only when a password actually passed.

### About the peek

The shared completion function has a branch for confirming a token with no password, which returns `{"valid": true}` and leaves the token unspent. It exists, and it is not reachable through any public route: both recovery confirmation routes require a `password` in the body, and the hosted page does not call it before showing its form.

So in practice a failed policy check never costs the person their link, because the policy is checked before the consume — but there is no endpoint that will tell you a recovery token is still good before you have a password to submit with it.

## The one-hour token

The `recovery` purpose is one entry in a single lifetime table. Knowing the table explains why recovery is short and email change is long.

| Purpose | Lifetime | Used by |
| --- | --- | --- |
| `verify` | 24 hours | [Email verification](/auth/email-verification). |
| `recovery` | 1 hour | This page. |
| `magic` | 15 minutes | [Magic links](/auth/magic-links). |
| `invite` | 7 days | Organization invitations. |
| `mfa` | 5 minutes | The second-factor challenge issued before a session. |
| `email_change` | 24 hours | Confirming a change of address. |
| `link` | 10 minutes | Linking an OAuth provider to a signed-in account. |

One hour is longer than a magic link and much shorter than a verification link, and the reason is the risk being managed. A magic link is redeemed by someone already at the browser. A recovery link authorises a destructive, account-taking action, so the window is kept tight while still being generous enough for someone who has to find an old password manager or ask a colleague for the address they signed up with.

<Warning>
An hour is measured from issuance, not from when the person opens the message. A message that sat in an inbox for two hours contains a dead link. If your product's users receive mail slowly, say so in the body — the default message already says the link works once, for an hour.
</Warning>

### The row and the signature

The token is a timed signature over the id of an `akz_one_time_tokens` row, using a secret derived for that project and environment with a salt that includes the purpose.

| Field | Role in recovery |
| --- | --- |
| `purpose` | `recovery`. A verification token presented here fails at the signature check. |
| `project`, `env` | Part of the row lookup, so a staging link cannot be used in production. |
| `user` | The account whose password is being set. Always set for recovery. |
| `email` | The address the message went to. |
| `expires_at` | Issuance plus one hour. |
| `used_at` | Set by the first successful reset. |
| `data` | Empty. Recovery records nothing extra. |

The token string itself is never stored. Only the row is, and the row's id is the token's payload rather than the token — so reading the database does not let anyone construct a working reset link.

### Single use, and what that means for the person

The consume is a conditional update on `used_at`, exactly as for verification. Two things follow.

First, a link works once. If the person reloads the page after a successful reset, they get `400`, not their new session again — which is correct, because the session was already returned once and revoking it on a second call would be surprising.

Second, two simultaneous submits produce exactly one success. One gets the session, the other gets `400`. A double-clicked Save button is therefore safe, and the person should retry from the sign-in page rather than from the link.

## Where the link lands

As with every other emailed link, one setting decides: `site_url`.

| Environment state | The link points at |
| --- | --- |
| `site_url` is set | `{site_url}/auth/callback?token=...&type=recovery` |
| `site_url` is empty | `{public_url}/auth/v1/links/{project}/{env}/recovery?token=...` |

### With a `site_url`

Your application gets the link. The page you build must do two things: show a password form, and post the submitted password to `/auth/v1/recover/confirm`.

```text
1. Read `token` from the query string.
2. Render a new-password form. Never render the form without a token present.
3. On submit, POST {token, password} to /auth/v1/recover/confirm.
4. On success, store the returned session and send the person into the application.
5. On 422, show the policy problems and keep the form filled in with the same token.
6. On 400, say the link is no longer valid and offer to request a new one.
```

Step 5 is the one that matters. A `422` means the token is still good, so your form must not tell the person to request a new link — that would send them in a circle.

### Without one

Akountz serves the page itself. It is a minimal form: a password input with `minlength` of 8, a **Save** button, and a script that POSTs the token and the password to the same hosted route with no API key.

The response handling on that page is worth knowing because it is the shape you will end up copying:

| Situation | What the page says |
| --- | --- |
| Success | *"Your password was changed. You can sign in now."* |
| Policy failure | The `problems` list from the `422` detail, joined into one line. |

The hosted page does not sign the person in, even though the API did start a session for the caller. It discards those tokens. So someone who resets through it must sign in again with the new password — which the confirmation text does tell them.

<Warning>
That page's behaviour is a reasonable default and a poor product experience. It is unstyled, it does not use your fonts, and it ends with a second sign-in step. If you have a frontend, set `site_url` and build the page.
</Warning>

### The allowlist

`redirect_to` is checked against `site_url` plus `redirect_urls`, matched on exact equality or on a `/` or `?` boundary.

| Candidate | With `site_url` = `https://app.acme.test` |
| --- | --- |
| `https://app.acme.test` | allowed |
| `https://app.acme.test/reset` | allowed |
| `https://app.acme.test/reset?x=1` | allowed |
| `https://app.acme.test.evil.example/` | refused |
| `https://app.acme.testbackup.example/` | refused |

The boundary rule exists because prefix matching without it would accept an attacker-chosen domain that begins with yours.

## The password policy check

The new password is checked against the environment's policy **before** the token is consumed. Understanding the two policies matters, because they behave very differently.

| `password_policy` | What is checked | Typical failure |
| --- | --- | --- |
| `basic` (the default) | Length only, against `password_min_length`, which defaults to 8. Plus an absolute cap of 1024. | One problem, about length. |
| `strict` | Sillo's full validator, with the same `min_length` as its floor. | Several problems, listed together. |

A failure is a `422` whose detail carries both a message and a list:

```json
{
  "detail": {
    "message": "the password does not meet the policy",
    "problems": ["Password must be at least 12 characters."]
  }
}
```

The `problems` array is the part your form should render. It is already phrased for display.

<Note>
`strict` is a real validator, not a longer length rule — it checks structure as well as size. What exactly it requires is Sillo's business rather than Pawabase's, and it can tighten between versions. Do not hardcode the expectation that it will accept a specific shape.
</Note>

### The two policies compared

The password policy is per environment configuration, which means it can differ between staging and production. That has one consequence worth planning for: a password accepted in staging can be rejected in production by the same person at the same form. If your staging environment is meant to mirror production, set the policy to `strict` there too.

<Warning>
The reserved `_platform` environment — Studio's own operators — uses `strict` with a minimum of 10, regardless of what your project environments are configured with. That is configured in Akountz rather than in the API, because the API does not host it.
</Warning>

### Where recovery meets an account with no password

An account created through a magic link or through an administrator has no usable password — it was given an unusable one at creation. Password sign-in against it can never succeed, and `check_password` reports the failure as a wrong password.

Recovery is the way such an account gains a password. The person requests a link, chooses one, and from that moment password sign-in works. The **has password** field in Studio's user view tells you whether an account is in this state, and it is the fastest way to explain to someone why their password never works.

## What a reset actually does

The side effects are the reason this flow deserves care. Five things happen, and all of them are deliberate.

### 1. The password is replaced

`set_password` writes the new hash through Sillo's user model, which uses `passlib` — bcrypt by default, with a `pbkdf2_sha256` fallback. The old hash is gone; there is no grace period and no copy.

### 2. The lockout counters are cleared

`failed_logins` is set to zero and `locked_until` to null, in the same write as the password.

This is the part that is easy to miss, and it matters for the most common support case. Someone who has typed the wrong password five times, been locked, and then used a recovery link is now able to sign in. A locked account does not need an administrator once recovery is available.

It also means recovery is a way around the lockout threshold — deliberately. The mailbox is a stronger credential than a password someone has already failed with, so possession of it re-establishes trust.

<Warning>
Treat "requested a reset" as a security event in your own product. A support agent who cannot explain a lockout should check whether someone recently used a recovery link on that account. It means the account's password was changed, and any other sessions it had were ended.
</Warning>

### 3. Every session is revoked

`revoke_all` ends every token family the account holds: the `JWTToken` rows are revoked and the `SessionInfo` rows are stamped. This covers every device, every browser, and every refresh token ever issued.

The reasoning is direct. A person who resets their password is usually doing it because they think someone else has access. Leaving the other sessions alive would defeat the purpose of the reset entirely — the intruder would keep their session while the legitimate owner changed the password underneath them.

| Situation | After the reset |
| --- | --- |
| The attacker's session on another device | Revoked. Their next request fails. |
| The owner's session on this device | Revoked too — and then replaced by the new session the flow returns. |
| A refresh token captured earlier | Revoked. It cannot be redeemed. |
| Someone replaying a consumed refresh token | Detected as reuse, and the whole family is revoked again. |

### 4. Two records are written

| Record | Where | Contents |
| --- | --- | --- |
| A login event | `akz_login_events` | kind `password_reset`, method `recovery`, success true, with IP and user agent. |
| An event | the event bus and the API's event endpoint | `user.password_reset` with the user id, actor the user. |

Both exist and they answer different questions. The login event is per environment and visible in Studio's **Sign-in activity** tab; it is the record for support and audit. The published event is what other services subscribe to.

<Note>
The event name is `user.password_reset`, not `user.password_changed`. The latter is emitted by the signed-in profile update route when a person changes their own password while signed in. Two different flows, two different events — useful if you want to alert only on the destructive one.
</Note>

### 5. A session is started

The flow returns a full session with the method recorded as `recovery`. So a successful reset leaves the person signed in, on whichever device they opened the link.

That is convenient, and it is worth being deliberate about whether you want it. A frontend that ignores the returned tokens and then redirects to sign-in still works; a frontend that stores them is signed in immediately. Either is fine, but pick one deliberately, because storing them means a reset becomes a login.

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "bearer",
  "expires_in": 900,
  "expires_at": 1750000900,
  "session_id": "a41c8f0d3e7b49a2",
  "org": null,
  "org_role": null,
  "user": { "...": "the user object" }
}
```

<Warning>
MFA is not consulted on this path. A person with a second factor enabled who resets their password gets an `aal1` session, not a challenge, because the mailbox link is treated as sufficient proof. If your product requires `aal2` for sensitive operations, gate on `$auth.aal` in a policy rather than expecting the reset flow to ask.
</Warning>

## Building it into a frontend

The three screens a recovery flow needs, and the failure handling each one owes the person.

### Screen one: "forgot your password"

Ask for an address, then say something that is true regardless of the outcome.

```text
If that address has an account, a message is on its way.
It usually arrives within a minute.
```

Do not say "we sent you an email", because for an unregistered address that is false and the person will find out an hour later. Do not offer a link to sign up, because that turns the page into a membership oracle.

The resend control should be on a timer rather than disabled by a response. A 30-second cooldown is polite and stays well under the 10-per-minute limit.

### Screen two: the new-password form

This is the page at `/auth/callback` when `type=recovery`. The cases you must handle:

| Case | What to render |
| --- | --- |
| No `token` in the query string | An explanation that the link is incomplete, with a link back to screen one. |
| A `422` from the submit | The `problems` list. Keep the form open and keep the token. |
| A `400` from the submit | "This link is no longer valid", with a button to request a new one. |
| Success | Store the session, then send the person into the application. |

The `422` and `400` cases are the ones that get conflated, and conflating them strands people. A `422` means the link is fine and the password is not; telling that person to request a new link costs them a round trip through their inbox for no reason.

```bash
curl -X POST "https://api.example.com/auth/v1/recover/confirm" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{"token": "'"$TOKEN"'", "password": "'"$NEW_PASSWORD"'"}'
```

<Note>
Send the API key from the frontend as a publishable key, exactly as for every other auth route. The reset route needs no secret of your own, and treating it as if it did is a common source of leaked keys.
</Note>

### Screen three: done

If you stored the returned tokens, go straight in. If you did not, send them to sign-in and say so: *"Your password is changed. Sign in with it."*

Do not say *"You're all set"* unless they are actually signed in. That is precisely the confusion the hosted page causes, and it is worth avoiding in your own version.

### A note on double submission

A reset is not idempotent, because the token is single-use. If your form can be submitted twice — a double click, a retried request, a flaky connection — the second attempt returns `400` even though the first succeeded.

The reliable pattern is to disable the button on submit and, on a `400`, check whether the reset actually completed before telling the person it failed. If you have a session stored from a first success, you know it did. If you do not, redirect to sign-in and let the outcome speak for itself: either the new password works, or it does not.

## The message

The `recovery` message is the second of five kinds. Its defaults are:

| Part | Default |
| --- | --- |
| Subject | `Reset your {project} password` |
| Body | Says someone asked to reset the password for `{email}`, invites the reader to choose a new one, and states that the link works once, for an hour. It closes by saying an unexpected message can be ignored and the password is unchanged. |

Two details in that default body are doing real work. It names the address the message went to, so a person with several accounts can tell which one it concerns. And it says the link works once, for an hour — which is precisely true, and sets the expectation that a second attempt will fail.

<Note>
The body does not say the person's name. It cannot, because recovery has no name to interpolate. Every message kind takes `{project}`, `{email}` and `{link}`, and only invitations add `{organization}` and `{role}`. An unknown placeholder is left literal rather than raising, so a template that references a name will show the braces in the delivered message.
</Note>

### A message with a name in it

The recovery body has one placeholder that is deliberately absent: the person's name.

```text
Someone asked to reset the password for {email}.
```

That is the whole greeting. There is no `{name}`, because the recovery function has a user row and nothing else to interpolate from, and the platform does not invent placeholders that have no value.

<Warning>
Adding `{name}` to a recovery template does not fail — it delivers the literal text `{name}` to the inbox, because an unknown placeholder survives rather than raising. The subject and body both send, the reset works, and the message looks obviously wrong to the reader. Check the delivered message rather than trusting a successful send.
</Warning>

The practical workaround, if you want the name in the message, is to override the template with copy that does not need it. The address is usually enough for someone to recognise the account, which is why the default uses it.

### The confirmation people expect

A reset message arrives, it looks like it came from your product, and it asks for a new password. People will read it as their account being at risk, and the first thing many will do is ask an administrator.

Three sentences in your copy remove most of that friction, and all three are in the default body:

| Sentence | What it prevents |
| --- | --- |
| *"If this was not you, ignore this message."* | The panic email, and the ticket that follows it. |
| *"your password is unchanged."* | The assumption that someone is already in. |
| *"the link works once, for an hour."* | Someone trying an expired link repeatedly, and reporting it as broken. |

The reassurance is not decoration. A reset message is one of the few emails a person receives that implies their account may be compromised, and the fastest way to defuse that is to say what did *not* happen.

<Warning>
Keep the reassurance even when you shorten the message for a mobile screen. It is the part that gets read, and the part that determines whether the message produces a support ticket.
</Warning>

### What "deleted" means

Akountz does not remove a user row. `DELETE` on a user stamps `deleted_at` and rewrites the address and username to reserved values derived from the user's own id.

| Field | Before | After |
| --- | --- | --- |
| `email` | `grace@example.com` | `deleted+01JQ7Z3M9K4YB2XQ8V0N5T6RJPD@acme.invalid` |
| `username` | `grace` | `deleted-01JQ7Z3M9K4YB2XQ8V0N5T6RJPD` |
| `deleted_at` | `null` | The current time. |
| `is_active` | `true` | `false`. |

Three things follow from that, and all of them are deliberate.

**The address is released.** Because the stored address no longer matches, a new account can sign up with `grace@example.com` in the same environment. Two people can therefore have used the same address at different times without colliding.

**The history stays attributable.** The row remains, so the login events that reference the old user id still point at something real. A soft delete keeps an audit trail that a hard delete would destroy.

**Linked identities and MFA factors are removed.** Those are deleted outright, so a deleted account cannot be reached through a provider it was linked to or through an old authenticator.

<Warning>
The reserved username and address are derived from the id, which means they are predictable from the deleted row. That is fine — they exist to be un-claimable, not to be secret.
</Warning>

### Recovery and a deleted account

A soft-deleted account is invisible to the recovery route, because every user lookup filters out rows with `deleted_at` set. Requesting a reset for its old address behaves exactly as it does for an address that never registered: the uniform response, no message, no token.

So if someone reports that a reset link does nothing, check whether the account was deleted before spending time on the mail configuration.

<Note>
The same filter applies to every user-facing lookup, not just recovery. A deleted account cannot sign in, cannot be found by search, and does not appear in Studio's user list. If an operator needs it visible for an audit, that is a database question rather than an API one.
</Note>

### The three checks, in the order they bite

Before the flow is exercised at all, three things can send it wrong, and each produces an error that looks like a later one.

**The email resolves to no account.** Recovery lowercases the address before looking it up, and every user query is scoped to one project and environment. An address that exists in staging is not found in production, and the route answers exactly as it does for an address that never existed — which means the failure is invisible from the client's side.

**The account is disabled.** The route checks the flag before issuing anything. A disabled account receives nothing, and so does the person who legitimately needs it. This is the check most often missed when writing a runbook, because a disabled account looks completely normal in the user list until you notice the state.

**The rate limit is exhausted.** Ten per minute under `akz:links`. A person who clicked resend repeatedly, or a shared address behind a corporate proxy, can exhaust the budget without any single client misbehaving.

<Note>
None of these produce an error. They produce a missing message, which is indistinguishable from a delivery problem. That is the practical reason the diagnostics start with the activity log rather than with the mail logs.
</Note>

### Peeking versus consuming

The completion function distinguishes checking a token from spending it, and the distinction is used twice in recovery.

When no password is supplied, the token is peeked and the function returns `{"valid": true}` without touching `used_at`. That is the shape a "is this link still good" endpoint would take.

When a password is supplied, the policy is checked first and the token is then consumed for real. The peek in that path is what guarantees a rejected password does not spend the link.

<Warning>
No public route reaches the peek-only branch, because both confirmation routes require a `password`. If you are writing an internal tool that wants to check a link before showing a form, there is no route for it — and adding one would need care, since a peek endpoint is a probe for whether a token is real.
</Warning>

### The hosted form's client

The hosted page is a single HTML document with an inline script. There is no framework, no bundle, and no external request: it posts to a route in the same service with the token and the password, and renders the outcome as text.

| Situation | What it renders |
| --- | --- |
| `ok` | *"Your password was changed. You can sign in now."* |
| Not `ok` | `b.detail.problems` joined, or `b.detail` if there is no array. |

Two details are worth copying if you build your own. The success text tells the person to sign in, because the session the API returned is discarded. And the failure path reads `detail.problems` before falling back to `detail`, so a policy failure shows its list rather than a bare object.

<Note>
The page carries a `minlength` of 8 on the input. That is the default minimum rather than the environment's, so a stricter environment will reject submissions the browser considered acceptable.
</Note>

### Overriding it

```json
{
  "auth": {
    "emails": {
      "recovery": {
        "subject": "Your {project} password",
        "text": "A password reset was requested for {email}.\n\nChoose a new one here:\n\n{link}\n\nThe link works once, for one hour. If you did not ask for this, nothing has changed and no action is needed."
      }
    }
  }
}
```

Keep the reassurance in the last paragraph. A reset message is alarming by nature, and telling a person plainly that ignoring it changes nothing is what stops a shared mailbox from becoming a support incident.

### Delivery

Delivery goes through the API's mail service, using the environment's own SMTP settings. The template comes from the same environment's `auth.emails` block, and the link inside it is built by Akountz. A staging environment therefore produces a different message from production, sent through different infrastructure.

There is a plain text part and a simple HTML alternative part, built by escaping the text, converting newlines to breaks, and wrapping the link in an anchor. It is functional rather than designed.

<Tip>
Because the message is the only thing standing between a confused person and a support call, override it with your own copy and your own mail tooling if this flow matters to your product. Keep the Akountz message enabled as the functional path — but note that there is no public route that hands out a recovery token without also sending this message, so a replacement is a subscription on `user.password_reset` rather than a swap.
</Tip>

<Warning>
A subscription on `user.password_reset` fires *after* the reset, not when the link is requested. To send your own branded request message you would need a token, and no public route issues one without also sending the built-in message. In practice the built-in message is the one that must work.
</Warning>

## Recovering an account that has no password

This is the flow's most useful side job, and it is a different problem from "forgot my password".

An account created by a magic link, or created for someone by an administrator, has an unusable password from the moment it exists. Password sign-in against it always fails, and Studio reports the state as **has password: false**.

| How the account came to exist | Has a password? |
| --- | --- |
| Sign-up with a password. | Yes. |
| Magic link with `create_user`. | No. |
| Social sign-in. | No. |
| Created in Studio without a password. | No. |

For all four, the same recovery link works, and after a successful reset the account has a password and password sign-in succeeds. The person never had to know the difference.

<Warning>
A support agent asked to explain a rejected password should check **has password** first. If it is false, the answer is "this account has never had a password" rather than "that is the wrong password", and the fix is a reset rather than a reissued secret.
</Warning>

### Disabled and deleted accounts

A disabled account receives nothing: the request route checks the flag and sends no message, then answers the same way it always does. There is no route to reset a disabled account's password, which is correct — the flag is the control, and a mailbox link should not be a way around it.

A deleted account is not found at all, because every user query filters out rows with `deleted_at` set. Recovery behaves exactly as it does for an address that never registered.

### Locked accounts

A locked account **can** recover, and the reset clears the lock. That is the single most useful fact on this page for support, and it is why a locked person does not need an administrator as long as they can reach their mailbox.

## Security properties

### Forgery and scope

A recovery token is a timed signature over a row id, under a secret derived for one project and environment, with the purpose in the salt. An attacker cannot mint one without the secret, cannot use a staging one in production, and cannot reuse a verification token here.

### Replay

The single-use property comes from the conditional update on `used_at`. A link in a forwarded message is worth exactly one reset, and the conditional update means two simultaneous submits produce exactly one success rather than two racing writes.

### Revocation

A reset ends every session the account holds. That is the strongest property of the flow, and it is what makes it the correct remedy for suspected compromise rather than merely an inconvenience.

### Enumeration

Two separate protections, both worth naming:

| Protection | Where |
| --- | --- |
| The request route's response is constant. | `POST /auth/v1/recover` returns the same body whether or not anything was sent. |
| The confirmation route's error is constant. | Every failure — expired, used, wrong environment, forged — is the same `400`. |

Neither leaks whether an address has an account, nor whether a token was ever valid.

<Warning>
Preserving both is an ongoing obligation. A change that returns 404 for an unknown address on the request route, or that distinguishes "expired" from "already used" on the confirmation route, reintroduces an oracle or a token-probing channel. Both are the kind of change that looks helpful and is not.
</Warning>

### What an attacker with the mailbox gets

Full account access, and that is the design. The mailbox is treated as a recovery factor of equal standing to the password. The mitigating properties are that the mailbox holder must also be able to read mail within the hour, and that the act is recorded — a `password_reset` activity event and a published `user.password_reset`, both with the user's id as the actor.

<Note>
If you need account recovery to require more than the mailbox, that is a decision for your application rather than for Akountz. Options include requiring MFA after the reset by refusing `aal1` sessions on sensitive operations, or requiring an administrator to approve resets in your own workflow.
</Note>

### What an attacker without the mailbox gets

Nothing. They cannot trigger a reset that reaches the owner in a way that helps them, they cannot read the token, and they cannot brute-force it — the token is not a short code, it is a signature whose search space is the signing secret.

They can, however, flood the request route. That is what the 10-per-minute limit is for, and why your frontend's resend control should be on a cooldown.

### Password storage

New hashes are written through Sillo's user model using `passlib`, with bcrypt by default and `pbkdf2_sha256` as a fallback. No configuration knob exposes a cost factor, and none should be claimed. See [Passwords](/auth/passwords).

### Constant-time comparison

Password verification runs through Sillo's model, which uses a constant-time comparison. Do not implement your own comparison in a custom route, and do not add a "is this close" check.

## The lockout interaction in detail

Lockout and recovery are separate mechanisms that happen to compose in a useful way, and the composition is worth stating precisely.

| | Lockout | Recovery |
| --- | --- | --- |
| What it is | A counter on the account: `failed_logins` plus `locked_until`. | A one-hour token in the mailbox. |
| Where it is configured | Akountz installation settings: threshold 10, duration 15 minutes. | The environment's `auth` block, for the token's lifetime. |
| Scope | One instance's threshold across all its environments; counters per account, per environment. | Per environment, like everything else. |
| How it is cleared | A successful sign-in, or an administrator's **Enable**. | The reset writes zero and null in the same save as the password. |

Two consequences follow.

**Recovery is a lockout escape hatch.** Someone who has exhausted their ten attempts can recover and sign in immediately, because the reset clears the counters.

**A reset is not enough to unlock a disabled account.** The disabled flag is separate and is checked on the sign-in path, so after a reset the person is unlocked but still disabled. An administrator has to re-enable them.

<Warning>
If you are writing a support runbook, put these two questions in order: is the account disabled, and is it locked? They produce different symptoms — a disabled account gets `403 this account is disabled`, a locked one gets `429 too many failed attempts; try again later` — and only the second is fixed by a reset.
</Warning>

## A worked example

The whole flow against a configured environment, including the parts that are easy to get wrong.

Assume `acme/production` has `password_policy: "strict"`, `password_min_length: 12`, and `site_url: "https://app.acme.test"`.

### The request

A person on the sign-in screen clicks "Forgot your password", enters `Grace@Example.com`, and submits.

```bash
curl -X POST "https://api.example.com/auth/v1/recover" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{"email": "Grace@Example.com", "redirect_to": "https://app.acme.test/welcome"}'
```

The address is normalised to `grace@example.com`, matched against production's accounts, and found. The account is not disabled, so a `recovery` token is issued with `expires_at` an hour out, and the message is handed to the environment's mail service.

The response is the same body a nonexistent address would get:

```json
{ "sent": true, "message": "If the address has an account, a message is on its way." }
```

Your interface now shows *"If that address has an account, a message is on its way."* — which is true, and is the only claim it can safely make.

### The link

```text
https://app.acme.test/auth/callback?token=UmVjb3Zlcnkt…&type=recovery&redirect_to=https%3A%2F%2Fapp.acme.test%2Fwelcome
```

Three query parameters, and your page reads all three:

| Parameter | Use |
| --- | --- |
| `token` | Post it to `/auth/v1/recover/confirm`. |
| `type` | Dispatch. `recovery` selects the new-password form. |
| `redirect_to` | Where to send the person after a successful reset. Already allowlist-checked when the request was made. |

### A first attempt that fails the policy

The person types `hunter2hunter2` — fifteen characters, but the strict validator has other requirements.

```bash
curl -X POST "https://api.example.com/auth/v1/recover/confirm" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{"token": "UmVjb3Zlcnkt…", "password": "hunter2hunter2"}'
```

```json
{
  "detail": {
    "message": "the password does not meet the policy",
    "problems": ["Password must be at least 12 characters.", "Password must not be a common password."]
  }
}
```

The policy check ran before the consume, so **the token is still valid**. Your form stays open, shows the problems, and lets them try again with the same link. This is the behaviour that separates a usable recovery flow from an unusable one.

### A second attempt that succeeds

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "bearer",
  "expires_in": 900,
  "expires_at": 1750000900,
  "session_id": "a41c8f0d3e7b49a2",
  "org": null,
  "org_role": null,
  "user": {
    "id": "01JQ7Z3M9K4YB2XQ8V0N5T6RJPD",
    "email": "grace@example.com",
    "username": "grace",
    "email_verified": true,
    "roles": ["customer"],
    "mfa_enabled": false
  }
}
```

What just happened, in order:

| Step | Result |
| --- | --- |
| Password replaced | A new hash, written through the user model. |
| Lockout cleared | `failed_logins` zero, `locked_until` null. |
| Every session revoked | Including the one this device might have had. |
| Activity recorded | A `password_reset` event, method `recovery`. |
| Event published | `user.password_reset`. |
| New session issued | Returned in the response above. |

Your page stores the tokens and sends them to `https://app.acme.test/welcome`. They are signed in, and every other device is signed out.

### A third attempt, from a stale tab

The person has the link open in two tabs. They complete the reset in the first, then submit the old form in the second.

```bash
curl -X POST "https://api.example.com/auth/v1/recover/confirm" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{"token": "UmVjb3Zlcnkt…", "password": "another-long-one"}'
```

```json
{ "detail": "the link is invalid or has expired" }
```

Correct behaviour. The token was spent by the first reset. Your page should say the link is no longer valid and offer a new one — not tell them their new password failed, which is a different problem with a different fix.

<Warning>
This is the case that produces the worst support tickets, because from the person's point of view they did nothing wrong and the link says it is broken. Phrase it as "This link has already been used", which is accurate, and give the sign-in link rather than a resend — their password has probably already been changed successfully.
</Warning>

### Checking the result

Studio's **Sign-in activity** tab will show the request and the reset as two rows:

| When | Event | Email | Result | IP |
| --- | --- | --- | --- | --- |
| 09:14:02 | `recovery_requested` | `grace@example.com` | `ok` | 198.51.100.17 |
| 09:16:40 | `password_reset` | `grace@example.com` | `ok` | 198.51.100.17 |

An administrator-triggered password set leaves no row in this tab at all, which is worth knowing when auditing. If you need to distinguish the two paths, subscribe to `user.password_reset`: the recovery link emits it and the administrator path does not.

## Studio

Recovery has no tab of its own, because a reset is something a person does rather than something an operator manages. What an operator needs is the ability to see that it happened and to fix the cases it cannot reach.

Open **Users & auth**. The tabs are **Users**, **Roles**, **Organizations**, **Sign-in activity**, and **Configuration**.

### The user view

In the **Users** tab, open the account. The admin view carries the fields that answer recovery questions:

| Field | Reading it |
| --- | --- |
| `has password` | False means the account has never had one and password sign-in can never work. Recovery is the fix. |
| `locked_until` | A timestamp while the account is locked out. Recovery clears it. |
| `disabled` | True means no reset message will be sent. Recovery cannot fix this; **Enable** can. |

The actions available on the user are **Disable**, **Enable**, **MFA reset**, **Signed out everywhere**, **Session revoked**, **Password set**, **New role**, and **Verify email**.

**Password set** is the operator's path to the same outcome as a recovery link: it replaces the password, subject to the same policy check. It is the right tool when someone has lost access to their mailbox entirely.

Three differences from a recovery reset are worth knowing, because they change what a support agent can promise:

| | Recovery link | **Password set** |
| --- | --- | --- |
| Proves control of the mailbox. | Yes. | No. |
| Clears `failed_logins` and `locked_until`. | Yes, always. | Only if **unlock** is also sent. |
| Revokes existing sessions. | Yes, every one of them. | No. Use **Signed out everywhere** separately. |
| Writes a `password_reset` activity event. | Yes. | No. |
| Emits | `user.password_reset` | nothing. |

<Warning>
**Password set** is the broadest action available on a user, and it bypasses the mailbox check completely. If you use it, follow it with **Signed out everywhere** — otherwise a suspected compromise remains a valid session even though the password has changed.
</Warning>

### The Sign-in activity tab

The tab has a failures-only checkbox and columns **When**, **Event**, **Email**, **Result**, **IP**. The two rows that matter for recovery are:

| Event | Meaning | Result when it succeeds |
| --- | --- | --- |
| `recovery_requested` | A reset message was genuinely produced and sent. | `ok` |
| `password_reset` | A password was replaced, by link or by an administrator. | `ok` |

A `recovery_requested` row is proof that a message left the platform. The absence of one, for an address someone says they requested, means nothing was sent — because that event is written only on the branch that actually sends.

Because an administrator's **Password set** writes no activity event, a `password_reset` row in this tab always means a mailbox recovery link was used. That makes the tab a reliable answer to "did they use the link, or did an operator change it?"

<Note>
Failures of the *confirmation* step do not produce a login event. A mistyped password that fails the policy check is a `422` and writes nothing, because nothing about the account changed. That is why a person can retry several times without filling the activity log.
</Note>

### The backup angle

An environment's backup covers users with their password hashes, so a restore into a fresh environment preserves everyone's ability to sign in. It also preserves which accounts had no password, because that is a property of the stored hash rather than of the flow. See [Backup and restore](/operate/backup-and-restore).

## What goes wrong

### "The link is invalid or has expired" on a link that was just sent

The causes, most likely first:

| Cause | How to tell |
| --- | --- |
| Wrong environment on the confirming request. | The context header's project/env differs from the environment the message came from. |
| The token was already consumed. | A `password_reset` event exists at about that time. |
| More than an hour has passed. | Check `expires_at` in `akz_one_time_tokens`. |
| The signing secret was rotated. | Every outstanding link across every environment fails at once. |
| A mail client's link preview fetched it. | The row has a `used_at` with no matching `password_reset` event. |

That last row is worth understanding. A preview fetch consumes the token without resetting anything, so the row shows as used and no reset event exists. It is the most confusing failure mode because the token was spent by something that looked like success.

### The message never arrives

Nothing about the flow tells you which of these it is, so check in order:

1. Is the account disabled? The route sends nothing and says nothing.
2. Does the address have an account in *this* environment? A staging account gets a staging reset.
3. Is the environment's mail configured? The transport lives in the API.
4. Was the rate limit hit? Ten per minute, and a burst from a shared NAT can exhaust it.

### The password is rejected and the person is sure it is right

The policy check runs before the consume, so a rejected password means the policy, not the token. Read the `problems` array — under `strict` there is more than one thing that can be wrong, and the array tells you which.

A frequent source of confusion: staging and production have different policies. A password that worked in staging can be rejected in production by the same form, at the same moment, from the same person.

### The person cannot sign in after a successful reset

| Symptom | Cause | Fix |
| --- | --- | --- |
| `403 this account is disabled` | The account was disabled before the reset. | **Enable** in Studio. |
| `429 too many failed attempts` | Only possible if the reset did not happen — the reset clears this. | Wait, or **Enable**. |
| `400 invalid email or password`, `has password` false | The reset did not complete. | Request a fresh link. |
| `400 invalid email or password`, `has password` true | The wrong password, or the account is in another environment. | Check which environment. |

### The form says it worked but nothing happens

Almost always the `400` on a second submit, described in the worked example. The fix is a redirect to sign-in rather than an error message, because the password has probably already changed.

### Recovery seems to do nothing at all

Check the shape of the address. Recovery normalises to lowercase, so an address that exists only with capitals in the database will not match — although Akountz normalises on write, so this should only appear in data imported from elsewhere.

### The session in detail

Three things about the returned session are worth knowing before you build against it.

**`org` and `org_role` are null.** The recovery flow never asks for an organization, so a session started this way is always org-less. If your product scopes data by organization, the person will need to refresh with an `org` to switch the session over. See [Organizations](/auth/organizations).

**`roles` and `perms` are read at issue time.** They reflect the account's grants at the moment of the reset. A role changed an hour ago appears; one changed a second ago does not, until the next refresh.

**The refresh token is long-lived.** Its lifetime is the environment's `refresh_ttl`, 30 days by default. It is an ordinary refresh token in every respect, and rotating it later follows the standard path.

## Inspecting the state

Three tables answer almost every question about a recovery, and the queries are simple because every one is scoped by project and environment.

### Outstanding and spent tokens

```sql
SELECT id, user_id, email, created_at, expires_at, used_at
FROM akz_one_time_tokens
WHERE project = 'acme' AND env = 'production' AND purpose = 'recovery'
ORDER BY id DESC
LIMIT 50;
```

| What you see | What it means |
| --- | --- |
| `used_at` null, `expires_at` in the future. | A live link. Someone could use it right now. |
| `used_at` set, and a `password_reset` event exists. | A normal completed reset. |
| `used_at` set, and no `password_reset` event exists. | A mail client's preview consumed it. |
| `used_at` null, `expires_at` past. | Expired, never used. |

The third row is the one that explains a support report of "the link says it is invalid but nobody used it".

### Accounts that cannot sign in

```sql
SELECT id, email, failed_logins, locked_until, disabled_at
FROM akz_users
WHERE project = 'acme' AND env = 'production' AND deleted_at IS NULL
  AND (locked_until IS NOT NULL OR disabled_at IS NOT NULL)
ORDER BY id DESC;
```

Every row here is a person who cannot sign in with a password. A reset fixes the first condition and not the second.

<Warning>
Do not clear `used_at` on a spent row to make an old link work again. That makes a genuinely consumed link live a second time, and nothing records that you did it. Request a fresh link through the API.
</Warning>

### Resets and requests, together

```sql
SELECT kind, success, reason, ip, user_agent, created_at
FROM akz_login_events
WHERE project = 'acme' AND env = 'production'
  AND kind IN ('recovery_requested', 'password_reset')
ORDER BY id DESC
LIMIT 100;
```

`recovery_requested` rows are proof a message went out. `password_reset` rows are proof a mailbox link was used. Nothing else produces either.

## Rolling out a reset flow

Most teams inherit a reset page from a starter kit and never revisit it. These are the changes that repay the review.

### The minimum viable flow

| Screen | What it must do |
| --- | --- |
| Request | Collect an address. Say the conditional sentence. Offer a cooldown-gated resend. |
| Set password | Read the token. Show the policy problems on a `422`. Say "no longer valid" on a `400`. |
| Done | Either store the session or send them to sign in — and say which. |

Everything else on this page is an improvement to that.

### Improvements, by value

**Distinguish the two failures properly.** The single most common bug. A `422` means the link is good; a `400` means it is not. Collapsing them makes people request new links unnecessarily, or lose hope when they did not need to.

**Include the lifetime in your copy.** The default message says "works once, for an hour". Matching that in your own interface means a person who clicks an old link knows what happened.

**Name the address in the confirmation.** "If that address has an account" is safe but vague for someone with several accounts. Echoing what they typed, normalised, helps without leaking anything.

**Store the session and skip the second sign-in.** The API returns one; most integrations discard it and send people back to the login form for no reason.

**Say what happens to other devices.** After a reset, every session ends. Telling the person that other devices have been signed out converts a confusing support call into an expected outcome.

### Changes to avoid

| Tempting | Why not |
| --- | --- |
| Return 404 for unknown addresses. | It creates a membership oracle. |
| Add an `already_registered` flag. | Same problem, in a subtler form. |
| Extend the token lifetime for convenience. | It is a code-level table, not configuration. Asking for it invites a patch that weakens every purpose at once. |
| Send the reset from your own service with a short code. | Then it is your flow, with your token store and your rate limiting. The built-in one is stronger than most hand-rolled versions. |
| Verify the person before resetting. | You would need something they can present, which is the problem recovery solves. |

### Testing before launch

Run the whole thing against a staging environment with a real mailbox you control.

| Test | Expected |
| --- | --- |
| Request for a real address. | A message arrives within a minute. |
| Request for an unregistered address. | The same response. No message. |
| Complete the reset. | A session comes back; other sessions stop working. |
| Submit the same link again. | `400`. |
| Submit a too-short password. | `422` with problems, and the link still works afterwards. |
| Request a second link, then use the first. | Both work, once each. |
| Redeem a staging link with the production context. | `400`. |
| Sign in with the old password. | `400 invalid email or password`. |
| Sign in with the new password. | A session. |

<Warning>
Run the last two. A reset that does not actually change the password is the failure that reaches production, because every earlier test in the list can pass without it.
</Warning>

## Recovery and the other sign-in methods

Recovery is one of five ways into an account, and they interact in ways that are worth a table.

| Method | Needs the mailbox? | Verifies the address? | Can unlock an account? | Creates an account? |
| --- | --- | --- | --- | --- |
| Password | No | No | No. | No. |
| Password reset | Yes | No. It is already verified or not, unchanged. | Yes. | No. |
| Magic link | Yes | Yes. | No. | Optionally, yes. |
| Social sign-in | At the provider | Only if the provider says so. | No. | Yes. |
| Studio operator | No | Whatever they choose. | Yes. | Yes. |

### The row that surprises: a reset does not verify anything

Recovery leaves `email_verified_at` exactly as it was. A reset proves control of the mailbox, and control of the mailbox is exactly what verification asks — but the reset does not act on that, because verification is a separate flag with a separate purpose and a separate message.

In practice this rarely matters, because in an environment that requires verification, an unverified account cannot have requested a reset — it cannot sign in. But in an environment that does not require verification, an unverified account can recover, and it will still be unverified afterwards.

<Warning>
If your product relies on `email_verified` as a proxy for "we have a working, owned mailbox", remember that a password reset does not change it. Check the flag, do not infer it from the fact that a reset succeeded.
</Warning>

### Recovery combined with MFA

An account with a second factor enabled can still recover; the link is not blocked by MFA. What differs is what comes back: an `aal1` session, because the recovery path does not issue a challenge.

| Flow | Second factor | Result |
| --- | --- | --- |
| Password sign-in | Enabled | `mfa_required`, a challenge, then `aal2`. |
| Magic link | Enabled | `mfa_required`, a challenge, then `aal2`. |
| Password reset | Enabled | A session, `aal1`, immediately. |

<Warning>
The reset path is the one case where possession of the mailbox alone yields a working session, even on an account that has a second factor. That is a deliberate design choice — the mailbox link and the second factor are alternatives — but if your threat model does not accept it, gate sensitive operations on `aal2` rather than assuming MFA always applies.
</Warning>

### Recovery and social sign-in

An account that signed in through a provider and never had a password can recover, which gives it one. Nothing about the provider identity is disturbed: the linked identity row survives, and both routes now work.

The reverse also holds — recovering does not unlink a provider. If you want someone to stop signing in through a provider, unlink the identity rather than changing the password.

### Recovery and magic links

Two routes into the same account, both requiring the mailbox. A person who cannot receive the mail is equally stuck on either, so the fix is the same in both cases: an administrator setting a password, or a support agent verifying identity out of band.

<Note>
That shared dependency is the reason to keep **Password set** available to operators even in a product where recovery is fully built. It is the only path for someone who has lost the mailbox entirely.
</Note>

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Can I request a reset for an address that has no account?">
    Yes, and the response is identical. Nothing is created and nothing is sent. There is no route that creates an account from a reset request.
  </Accordion>
  <Accordion title="Does requesting a reset invalidate previous links?">
    No. Each request creates an independent token row. An older link stays valid until it is used or its hour passes, so two outstanding links can both be redeemed — once each.
  </Accordion>
  <Accordion title="Does a failed password attempt consume the link?">
    No. The policy check runs before the consume. A password that does not meet the policy returns a `422` and leaves the token untouched, so the same link can be used again straight away.
  </Accordion>
  <Accordion title="Why did the policy check run before the token was used up?">
    So a person who misjudges their own password strength does not lose their only link to the account. The cost is that an invalid token still reaches the policy check; since the check needs no database state, that costs nothing.
  </Accordion>
  <Accordion title="What happens to the old sessions?">
    All of them are revoked. Both the token rows and the session rows, so a refresh token captured earlier cannot be redeemed.
  </Accordion>
  <Accordion title="Why am I not signed in after using the hosted page?">
    Because the hosted page discards the tokens the API returned. A reset through it changes the password and then tells you to sign in. With your own `site_url` page you control this, and storing the tokens signs the person straight in.
  </Accordion>
  <Accordion title="Can recovery be disabled?">
    Not by configuration. The route exists in every environment. If you need to prevent it, refuse the request in your own frontend — which loses the uniform-response property, so weigh that carefully.
  </Accordion>
  <Accordion title="Does a reset appear in the audit log?">
    Not in the platform audit log, which records configuration and administration rather than identity events. It appears in the identity activity as a `password_reset` event, and to subscribers as `user.password_reset`. Both are scoped to the environment.
  </Accordion>
  <Accordion title="Does a reset work for an account created through social sign-in?">
    Yes, and it is the standard way to give such an account a password. The provider identity stays linked, so nothing is lost.
  </Accordion>
</AccordionGroup>
## What a reset looks like from the outside

The observable effects, in the order a person or an operator would notice them.

### On the person's devices

| Device | What happens |
| --- | --- |
| The one that completed the reset. | Signed in, if the page stored the returned tokens. Otherwise signed out, and told to sign in. |
| Every other device they were signed in on. | Signed out at the next request, because the refresh token is revoked. |
| A browser tab left open elsewhere. | Its access token keeps working until it expires. Then it fails. |
| A mobile app in the background. | Same. The refresh fails and the app should send them to sign in. |

That third row is the only one with a delay, and it is bounded by the access lifetime — 15 minutes by default. It is not a defect: an access token cannot be revoked individually, only the family that mints new ones can.

<Warning>
This is the single most common surprise after a reset: "the other device still works". It works until the access token expires, and then it does not. If your product shows a reset confirmation, saying *"you have been signed out on all other devices"* is more accurate than saying they have been, because of that window.
</Warning>

### On the account record

| Field | Before | After |
| --- | --- | --- |
| `password` | The old hash. | A new hash. The old one is gone. |
| `failed_logins` | Possibly non-zero. | Zero. |
| `locked_until` | Possibly a future timestamp. | Null. |
| `disabled_at` | Unchanged. | Unchanged. A reset does not re-enable anyone. |
| `email_verified_at` | Unchanged. | Unchanged. |
| `mfa_enabled` | Unchanged. | Unchanged. The factor survives a password reset. |

The last two rows matter for support. A reset is not a re-enable, not a verification, and not an MFA reset — three separate actions with three separate buttons in Studio.

### On the activity trail

```text
09:14:02  recovery_requested   ok
09:16:40  password_reset       ok
09:16:40  sign_in              ok   (method: recovery)
```

Three rows, all at the same moment for the last two, because the session is started as part of the reset rather than as a separate act.

<Tip>
If you are building a security dashboard, key on `password_reset` rather than on `sign_in`. A reset is a deliberate, meaningful act; a sign-in is routine.
</Tip>

### On the mail

Exactly one message, sent once. A reset does not send a confirmation to the old address, does not notify other devices, and does not tell the person which sessions ended.

<Warning>
That last point is a gap you may want to fill yourself. The built-in message cannot know about your other systems, and a subscriber on `user.password_reset` fires after the fact rather than at the moment of request. If your product has connected accounts, a separate notification is worth building.
</Warning>

## Why the order of operations is what it is

The seven steps inside the confirmation route look arbitrary until you see what each ordering choice buys. This section is about those choices, because they explain most of the behaviour on this page.

### Peek, check, then consume

```text
peek the token   →  check the password  →  consume the token
     ↓                    ↓                      ↓
  400 if bad          422 if bad              400 if spent
  token intact        token intact           token spent
```

If the order were consume-then-check, a person who mistyped their password twice would lose their link and have to start the whole flow over. That is an unpleasant thing to inflict on someone who has already proved they control the mailbox.

### Password before revocation

The password is written before sessions are revoked. If revocation came first and then the write failed, the person would be signed out everywhere with the old password still in place — worse than doing nothing.

### Revocation before the session

Sessions are revoked before the new session is issued. The order ensures the new session is not itself caught by the revocation, and that the person is not briefly signed in with both the old and new credentials.

### Activity before the response

The `password_reset` event is written before the session starts, so by the time the client holds a working token the record already exists. An observer watching either the activity log or the event stream sees the same moment.

## Operations

The recurring tasks, and the numbers worth watching.

### Rate limit headroom

The link-request budget is 10 per 60 seconds per caller. Two patterns exhaust it:

| Pattern | Why it happens |
| --- | --- |
| A shared NAT. | Many users behind one address share one budget. |
| A retry loop. | A frontend that retries on failure turns one click into several requests. |

Neither is visible in the response — the limit refuses the request, and the client sees a failure it cannot interpret. That is another reason to put a cooldown in the frontend rather than relying on the server to say no.

<Warning>
Because a refused request looks like any other failure, a retrying client will keep hammering. If your resend button loops on error rather than on a timer, you have built a limiter that fights itself.
</Warning>

### Mail volume

Each accepted request that has an account and a message to send produces one message. There is no queue visible to you and no delivery receipt, so the only measure you have is the count of `recovery_requested` events.

A rising count with a flat success rate of resets is worth a look: it means links are being issued and not used, which usually points at deliverability rather than at people.

### The stuck-token pattern

A token that is never redeemed leaves a row with `used_at` null forever, at the code level. Nothing prunes them on a schedule you should rely on, so the table grows with every issued link.

That is fine at ordinary volumes and worth planning for at large ones: a busy environment issuing thousands of resets a day accumulates thousands of rows a day. If the table matters for size, index `project`, `env` and `purpose` together, because that is the only access pattern in the codebase.

### Clock skew

Two clocks decide whether a link works: the signature's max age and the row's `expires_at`. Both come from the Akountz host. A host whose clock is more than an hour behind accepts links that should have expired; one more than an hour ahead rejects every link immediately.

<Warning>
"Every reset link fails instantly" on a host that was recently restored or migrated is a clock problem until proven otherwise. Check the host's time before checking anything else.
</Warning>

### After an Akountz upgrade

Nothing about recovery's behaviour should change across a minor version. Two things to verify after a major one:

| Check | Why |
| --- | --- |
| The reset round trip still works end to end. | The route's shape is stable, but the test proves it. |
| Outstanding links from before the upgrade still work. | They depend on the internal secret being unchanged. |

<Note>
If the internal secret did change as part of the upgrade, every outstanding link in every environment fails at once with the same 400. There is no way to make them work again; the only remedy is to issue new ones.
</Note>

<Note>
None of these orderings are documented behaviour anyone should depend on beyond what is written here. They are, however, the reason the observable behaviour is what it is — so a future change to them is a behaviour change.
</Note>

### What each ordering lets you conclude

| Observation | Safe conclusion |
| --- | --- |
| A `422` was returned. | The token was valid at that moment and still is. |
| A `400` was returned. | Nothing about the account changed. |
| A session came back. | The password was changed and every old session is dead. |
| A `password_reset` event exists. | A mailbox link was used, not an administrator. |
| A `recovery_requested` event exists. | A message was genuinely produced. |

The first row is the one to design your interface around. It is the only way a client can know it is safe to let the person try again.

## Environments and recovery
## Environments and recovery

Recovery is more environment-sensitive than most flows, because the person doing it is usually not looking at an environment selector.

| Situation | What happens |
| --- | --- |
| A staging user asks for a reset while signed in to production. | Nothing. The account is not in production. |
| A production link is opened with a staging context. | `400`. |
| The same address exists in both environments. | Two independent accounts, two independent resets, two independent passwords. |
| A reset is performed in staging. | Production's session is untouched. |

The second and fourth rows are the tenancy rule, and they are why "I reset it but the old password still works" is almost always answered by *that was a different environment*.

<Note>
Because the accounts are separate, resetting in staging does not disturb production and cannot be used to change a production password. There is no route that crosses environments.
</Note>

### Promotion and recovery

A promoted database brings users with it, and a user keeps their password. So a person who signed up in staging can sign in to production with the same password after promotion — which is either convenient or alarming depending on your intent.

If it is alarming, the fix is to promote the database into an empty production environment, so production's identities start empty, and to provision accounts deliberately.

<Warning>
Recovery cannot help in that situation, because the addresses do not exist in production until you restore them. Bringing identities across is a backup-and-restore operation, not an authentication one. See [Backup and restore](/operate/backup-and-restore).
</Warning>

## Support runbook

The order of questions to ask, and why this order saves time.

### Someone says "I can't get in"

| Order | Question | What each answer means |
| --- | --- | --- |
| 1 | Is the account disabled? | If yes, no reset message will be sent. Fix: **Enable**. |
| 2 | Does it have a password? | If no, the answer to "wrong password" is "there is no password". Fix: a reset. |
| 3 | Is it locked? | If yes, ten failed attempts. A reset clears it, or wait fifteen minutes. |
| 4 | Did a reset message arrive? | If no, walk the request conditions below. |
| 5 | Did the link work when clicked? | If it errored, go to the token diagnostics. |
| 6 | Does the new password sign in? | If not, check which environment, and whether verification is required. |

Asking in this order shortens most conversations, because the first three questions are all answerable from Studio without touching the inbox.

### Walking the request conditions

If no message arrived, four things decide it, and only the second and third are non-obvious:

| Condition | How to check |
| --- | --- |
| The account exists in this environment. | The **Users** tab for the selected environment. A staging account is not a production account. |
| The account is not disabled. | The user's **Disable**/**Enable** state. |
| The address matches after normalisation. | The message goes to the stored, lowercased address, not to what was typed. |
| The rate limit was not exhausted. | Ten per minute under `akz:links`. |

## Frequently asked questions, second pass

<AccordionGroup>
  <Accordion title="Why is the hosted page's password field limited to 8 characters?">
    It carries a `minlength` of 8 as a browser-side hint. That is the default minimum, not the environment's — if yours is 12, the hosted form will let someone submit 8 characters and the API will refuse them with a 422. Only your own page can reflect the real minimum, which is one more reason to set `site_url`.
  </Accordion>
  <Accordion title="Does the hosted page tell you the password policy failed?">
    It joins the `problems` array into a single line of text. So it is accurate, but it is not formatted, and it appears below the button rather than beside the field.
  </Accordion>
  <Accordion title="Can I redirect to my app after using the hosted page?">
    Yes, if a `redirect_to` was supplied with the request and it is allowlisted. The tokens then arrive in the URL fragment of the redirect. Without a `redirect_to`, the page shows its confirmation and signs nobody in.
  </Accordion>
  <Accordion title="Why did my redirect not happen even though I set site_url?">
    Because a `site_url` means the link goes to your page, and your page is responsible for the redirect. The hosted page's redirect behaviour only applies when `site_url` is empty.
  </Accordion>
  <Accordion title="Is the reset token ever exposed in a server log?">
    On your page, yes, if you put it in a URL — which you must, because the link carries it. That is why the hosted page's redirect uses a fragment for tokens, and why your page should post the token in a body and then discard it from the address bar with a history replace.
  </Accordion>
  <Accordion title="Can two people reset the same account at once?">
    Yes, if both requested links before either was used. Each gets an independent token, and each works once. The second reset wins, and the first person's new password stops working.
  </Accordion>
  <Accordion title="Does a reset sign out the person on the machine doing it?">
    Not if the page stores the returned session — that session is new. If the page discards it, the person is signed out along with everything else and must sign in again.
  </Accordion>
  <Accordion title="Why is the token valid for an hour when verification gets 24?">
    Because the consequences differ. A verification link grants an address claim; a reset link replaces a credential. The shorter window is the more conservative of the two.
  </Accordion>
</AccordionGroup>

| --- | --- |
| No row for that email at all. | The message was never sent. Go back to the request conditions. |

Never clear `used_at` to rescue a link. The next request through the API issues a fresh one, which is both safer and auditable.
</Warning>

## Each other's tables

Every one of these queries is scoped by `project` and `env`, because that is how every query in the identity layer is scoped. A query that omits them returns rows across environments, and it will eventually return somebody else's user.

| Question | Table |
| --- | --- |
| Has anyone outstanding recovery links? | `akz_one_time_tokens`, purpose `recovery`. |
| Who cannot sign in? | `akz_users`, filtered on `locked_until` or `disabled_at`. |
| Who has no password? | `akz_users`, where the stored hash is unusable. |
| Did a reset happen? | `akz_login_events`, kind `password_reset`. |
| Was a message really sent? | `akz_login_events`, kind `recovery_requested`. |
| Which devices were signed out? | `akz_sessions`, `revoked_at` set for that user. |
| Is the address verified? | `akz_users.email_verified_at`. |

Six tables, and the join from a reset to its consequences runs across three of them: the token row, the login event, and the session rows.

<Tip>
If you are building an internal support tool, the most useful single query is probably the `akz_login_events` one restricted to the two recovery kinds, ordered by `id` descending. It is short, it is already scoped, and it answers most of the questions a support agent asks.
</Tip>

### Why the activity log is the better starting point

The token table answers "what happened to this link". The activity log answers "what happened to this account", which is usually the better question, because people report account problems and rarely report link problems specifically.

A support conversation generally goes: the person says they cannot get in; you look up the account; you find either a recent reset, a lock, or a disable. The reset explains it, the lock explains it, the disable explains it. Reaching for the token table is only necessary when the account record and the activity log both look fine.

<Note>
The activity log is per environment and ordered newest first, with a default limit of 100 on the admin route and 50 on the user-facing history route. Raise the limit on the admin route when investigating; the user-facing one is capped and meant for a settings screen.
</Note>

## Building the client, concretely

The pseudocode for the three screens, written out rather than described.

### Requesting a link

```text
on submit(email):
  POST /auth/v1/recover  { email, redirect_to: currentUrl }
  always show:
    "If that address has an account, a message is on its way."

The `redirect_to` you send is the page that will handle the reset, so the link lands where your form lives. It is checked against the allowlist when the request is made, so an error here surfaces immediately rather than when the person clicks.

### Handling the link

on load at /auth/callback:
  token     = query.token
  type      = query.type
  redirect  = query.redirect_to

  if type != "recovery":  hand off to the other link handlers
  if not token:           show "this link is incomplete" + a request form

### Bringing your own mail

The built-in message is plain, functional, and always available. Replacing it is worth doing if the flow matters to your product, and worth not doing carelessly.

| Option | What you control | What you give up |
| --- | --- | --- |
| Keep the built-in message, restyle nothing. | Nothing. | Branding, timing, delivery reporting. |
| Override `emails.recovery`. | Subject and body. | Still the built-in sender and transport. |
| Subscribe to events and send your own. | Everything, including branding. | The token, because no public route hands one out. |

The third row is the constraint that decides it. A `user.password_reset` subscription fires *after* the reset completes, so it can notify someone that their password changed; it cannot be the message that carries the link.

<Warning>
Do not build a "request a reset, then send your own link" flow on top of this. There is no public route that issues a recovery token without also sending the built-in message, so your version would produce two messages and the person would not know which link to use.
</Warning>

### If you override the template

Two things to keep in it:

**State the lifetime.** The default says the link works once, for an hour. Whatever you write should match, or people will try a dead link and assume something broke.

**Say that ignoring it is safe.** The default closes by saying the password is unchanged. That single sentence is what stops a shared mailbox becoming an incident.

```json
{
  "auth": {
    "emails": {
      "recovery": {
        "subject": "Reset your {project} password",
        "text": "Someone asked to reset the password for {email}.\n\nChoose a new one here:\n\n{link}\n\nThe link works once and is good for one hour. If this was not you, ignore this message — your password has not changed."
      }
    }
  }
}
```

<Tip>
Test template changes by reading the delivered message, not by checking that the send succeeded. An unknown placeholder survives as literal braces, so a typo produces a message that sends fine and looks wrong.
</Tip>

### If you add a second message

A product that emails both a security notice and a reset link should sequence them so only one is actionable. Two links in one person's inbox, from two different systems, is a good way to have the wrong one clicked.

### Submitting a new password

```text
on submit(password):
  disable the button
  POST /auth/v1/recover/confirm  { token, password }

  200 → store the session; go to redirect or your sign-in route
  422 → show detail.problems; keep the form open; keep the token

Two details in that sketch carry most of the weight. The `422` branch keeps the token, which is the difference between a person trying again and a person starting over. And the `400` branch says the link is no longer valid rather than that the password is wrong, because the latter is almost never true at that point.

### Storing what comes back

If you store the tokens, the person is signed in and you redirect into the application. If you do not, redirect to sign-in and say so explicitly.
### What recovery does not do

A short list, because several of these are assumed rather than checked.

| It does not | It does instead |
| --- | --- |
| Verify the email address. | Leaves `email_verified_at` untouched. |
| Re-enable a disabled account. | Leaves `disabled_at` untouched. |
| Remove an MFA factor. | The factor survives; only **MFA reset** removes it. |
| Change roles or permissions. | Grants and memberships are untouched. |
| Confirm who requested it. | Anyone who knows the address gets the same outcome if they hold the mailbox. |
| Notify the account owner separately. | One message, to the address itself. |
| Extend the refresh lifetime. | The new session uses the environment's existing `refresh_ttl`. |
| Sign the person in with a second factor. | The session is `aal1`. |

<Warning>
The MFA row is the one to internalise. A person whose second factor is enrolled still gets an `aal1` session from a reset. If your product treats `aal2` as required for anything sensitive, enforce that with a policy rather than expecting the reset to challenge.
</Warning>

### Where it sits among the flows

| Flow | Its own token lifetime | Changes the password | Revokes sessions |
| --- | --- | --- | --- |
| Password sign-in | none | No | No. |
| Password reset | 1 hour. | Yes. | All of them. |
| Magic link | 15 minutes. | No. | No. |
| Social sign-in | none. | No. | No. |
| A signed-in password change | none. | Yes. | No, unless you ask. |
| An administrator setting a password | none. | Yes. | Only if you also sign them out. |

Two rows carry a surprise. A signed-in password change does not revoke sessions, so a person who changes their password from their profile leaves any other device signed in — worth knowing if you build a "change password" screen and assume it is a security action. And an administrator setting a password revokes nothing unless followed by **Signed out everywhere**.

<Note>
Both of those are correct for what they are. A profile change is a convenience; a reset is a security response. Treating them the same would mean a person could not change their password without signing out every device.
</Note>

### The flow, in order

| # | Step | On failure |
| --- | --- | --- |
| 1 | `POST /auth/v1/recover`, rate limited to 10 per 60 seconds. | Nothing. Always the same response. |
| 2 | Address normalised, account found, not disabled. | Message silently not sent. |
| 3 | A `recovery` token is issued, expiring in an hour. | — |
| 4 | The message goes out through the environment's mail service. | `recovery_requested` is written only when this happens. |
| 5 | The link opens your page, or Akountz's hosted form. | — |
| 6 | `POST /auth/v1/recover/confirm` with the token and a new password. | `400`, or `422` on the policy. |
| 7 | Password set, lockout cleared, every session revoked, events written. | — |
| 8 | A session is returned, with the method `recovery`. | — |

| Method | Path | Purpose | Rate limited |
| --- | --- | --- | --- |

| POST | `/auth/v1/recover/confirm` | Set the new password. | no |
| GET | `/auth/v1/links/{project}/{env}/recovery` | The hosted form, when `site_url` is empty. | no |
| POST | `/auth/v1/links/{project}/{env}/recovery` | The hosted form's target. | no |
| POST | `/auth/v1/token` | Password sign-in with the new password. | 30/60s, `akz:auth` |

| --- | --- | --- |

| Status | Detail | Cause |
| --- | --- | --- |
| 400 | `the link is invalid or has expired` | Any redemption failure. |
| 400 | `redirect_to is not an allowed URL` | The target is outside the allowlist. |
