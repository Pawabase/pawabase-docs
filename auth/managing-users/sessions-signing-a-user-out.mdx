Three levels of intervention, and the difference between them is one of scope.

| Route | Effect |
| --- | --- |
| `POST .../sessions/revoke` | Revokes **every** session for the user, returns `{"revoked": N}` |
| `DELETE .../sessions/{session_id}` | Revokes **one** session; a bad id is a `404` |
| `PATCH {"disabled": true}` | Disables the account **and** revokes every session |

The revoke-all route is the one to reach for in an incident. The count it returns
is the number of token families that were live, which is a useful confirmation that
sessions actually existed.

<Warning>
`revoked` counts token families, not access tokens. Revoking a user with three
devices returns `3`, and each of those devices may still hold an access token
that works for up to `access_ttl`. The count tells you sessions died; it does not
tell you access stopped immediately.
</Warning>

### The session list is narrower than it looks

The sessions array on the user detail view is built by **intersecting two tables**.
A session appears only if it has an unrevoked `SessionInfo` row *and* its family
still has an unrevoked, unconsumed, unexpired refresh token.

The practical effect: a session whose refresh tokens have all expired does not
appear, even though its row still exists. The list shows *resumable* sessions.

| You see | It means |
| --- | --- |
| No active sessions | No resumable sessions — not that the user never signed in |
| Sessions present, all old | Last activity was long enough ago that refresh expired |

If you need the full record of what happened, read the history instead.

### Session entries

Each session carries `id` (the family string), `method`, `aal`, `ip`, `user_agent`,
`created_at`, `last_refreshed_at` and `current`.

`method` records **how the session started**, not how it is being continued — a
Google sign-in reads `oauth:google` for its whole life. `current` is computed
against the caller, and is therefore always `false` in an admin view of someone
else's sessions.


## Resetting MFA

`POST .../mfa/reset` removes a user's second factors entirely: the factors
themselves, all their recovery codes, and the enabled flag. It returns
`{"mfa_enabled": false}` and emits `user.mfa_reset`.

This is the route for a user who has lost their authenticator and their recovery
codes. There is no partial reset — you cannot remove the factor and leave the
codes, and there is no administrative way to issue a single replacement recovery
code.

<Warning>
MFA reset does not revoke sessions. A user whose MFA you just removed keeps their
existing sessions, and a session created before the reset is still `aal2` in its
token. If the reason for resetting is that you believe the account is compromised,
**reset the MFA and revoke the sessions** — the reset alone leaves the existing
sessions valid.
</Warning>

After a reset, the user re-enrols from scratch: a new secret, a new provisioning
URI, and a fresh set of ten recovery codes. The old codes are gone, not
invalidated-but-kept.


## Reading a user's sign-in history

`GET .../history` returns up to **100** of the user's most recent authentication
events, newest first. Each entry carries `id`, `user_id`, `email`, `kind`,
`method`, `success`, `reason`, `ip`, `user_agent` and `at`.

This is the richest diagnostic surface in the admin API, and the `reason` field is
why. The API deliberately returns one generic message for several different
failures — but the reason recorded internally distinguishes them.

| `kind` | Typical `reason` when it fails | What it tells you |
| --- | --- | --- |
| `sign_in` | `unknown email` | No account for that address in **this** environment |
| `sign_in` | `wrong password` | The account exists; the password was wrong |
| `sign_in` | `locked` | Threshold reached; the password may have been right |
| `sign_in` | `disabled` | An administrator disabled the account |
| `refresh` | The theft messages | A consumed or revoked refresh token came back |
| `refresh` | `Invalid refresh token` | The signature did not verify |
| `mfa_challenge` | — | A challenge was issued, so the password was correct |
| `mfa_verify` | `wrong code` | The TOTP or recovery code was wrong |
| `password_reset` | — | A recovery link was completed |
| `sign_out` | — | The method is the scope: `local`, `others`, `global` |

<Info>
`mfa_challenge` appearing immediately before `mfa_verify` is how you distinguish
"the password was wrong" from "the password was fine and the second factor was
wrong". That distinction saves a great deal of support time.
</Info>

The 100-event cap is worth remembering: a user signing in repeatedly can push
anything interesting off the end quickly. For a broader view, `GET {base}/events`
covers the whole environment.

What it preserves: the user row itself, so historical events remain attributable
to the id rather than becoming orphaned.

<Warning>
The email is rewritten so the original address is **released for re-use**. Someone
can sign up with it immediately. That is usually what you want after an account is
closed — but it means the old account and the new one are unrelated, and any data
you kept keyed by email is now ambiguous.
</Warning>

<Info>
Deleted users are excluded from every normal lookup — search, listing, and the
email-uniqueness check all filter them out. The uniqueness constraint therefore
does not fire when you re-create an account with a released address.
</Info>

Deletion emits `user.deleted`. Unlike disabling, it cannot be undone from the UI,
which is why disable is usually the better first move.
