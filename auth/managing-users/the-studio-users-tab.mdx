Studio's page for this is **Users & auth**, described as *"End users of this
environment, managed by Akountz: accounts, sessions, MFA, roles and
organizations."* It carries five tabs in order: **Users**, **Roles**,
**Organizations**, **Sign-in activity**, **Configuration**.

Everything on this page is the same admin API described above, driven with the
management key. There is nothing Studio can do that a service key cannot.

### The statistics strip

Above the table, a row of stat tiles rendered from the environment's stats route.
The counts are `users`, `verified`, `mfa`, `disabled`, `signups_24h`,
`sign_ins_24h`, `failures_24h`, `organizations`, plus per-provider identity counts.

Labels are the raw keys with underscores replaced by spaces, so `sign_ins_24h`
reads as **sign ins 24h**. Worth knowing before you go looking for a polished
label that does not exist.

`failures_24h` is the number to watch: it counts **all** failed events, not just
failed sign-ins, so a refresh loop or a client bug moves it as readily as an attack.

### Finding a user

The search input placeholder reads **"Search email or name"**, and next to it a
status dropdown with three options: **all**, **disabled**, **unverified**.

Both map directly to the query parameters on the list route. The dropdown has no
"locked" or "enrolled in MFA" option, which is a real gap — those users have to be
found by search and inspected individually.

### The user table

Five columns, and what each one is actually showing:

| Column | Renders |
| --- | --- |
| **Email** | The address, in bold |
| **Name** | The display name |
| **Roles** | One badge per role; empty if they have none |
| **State** | Badges describing account status |
| **Last sign-in** | Relative time from the last successful sign-in |

**State** is the column to read carefully, because it composes up to three badges:

| Badge | Condition | Meaning |
| --- | --- | --- |
| **disabled** (red) | `disabled` is true | Disabled by an administrator |
| **active** (green) | not disabled | The default state |
| **unverified** (yellow) | `email_verified` is false | No verification stamp |
| **MFA** (blue) | `mfa_enabled` | A confirmed factor exists |

Note that **active** means "not disabled", not "verified" and not "signed in". A
row showing **active** and **unverified** together is normal for an environment
where verification is not required.

Clicking any row opens that user's detail panel.

### Creating a user from Studio

The **New user** button in the card header opens a modal with three fields:
**Email**, **Name**, and **Password**.

The Password hint reads *"Leave empty to have the user set one through a recovery
link."* That is not a cosmetic suggestion — leaving it empty is what creates an
account with an unusable password, and the user must then use a recovery link
before password sign-in works.

The button in the footer is **Create**, and it toasts **User created**. It is
disabled until an email is present.

<Note>
The modal exposes only three fields, so it cannot set `user_metadata`,
`app_metadata`, `username` or `email_verified`. The route accepts all of them; the
UI does not offer them. Use the API for anything the modal cannot express.
</Note>

<Note>
A username you supply explicitly is not normalised the same way — it is only
lowercased and checked for uniqueness. The stripping and truncation apply to the
generated path.
</Note>
### The user detail panel

Clicking a row opens a wide modal titled with the user's email. Its action row is
the operational core of the page.

| Button | Shown when | Calls | Toast |
| --- | --- | --- | --- |
| **Disable** / **Enable** | Always, alternating | `PATCH {"disabled": ...}` | **Disabled** / **Enabled** |
| **Mark verified** | Only when unverified | `PATCH {"email_verified": true}` | **Marked verified** |
| **Sign out everywhere** | Always | `POST .../sessions/revoke` | **Signed out everywhere** |
| **Reset MFA** | Only when `mfa_enabled` | `POST .../mfa/reset` | **MFA reset** |
| **Set password** | Always | `PATCH {"password": ...}` | **Password set** |
| **Delete** | Always | `DELETE .../users/{id}` | **Deleted** |

Three of these prompt before acting. **Set password** raises a browser `prompt`
labelled **New password**. **Delete** raises a `confirm` naming the user's email,
and on success closes the panel rather than leaving it open on a deleted account.

<Warning>
**Set password** uses a browser prompt, so the new password is visible on screen
and cannot be masked or strength-checked. It also skips the recovery flow entirely.
For any account where audit matters, set the password through the API and let your
own tooling handle it.
</Warning>

The order of the buttons encodes the severity gradient: reversible actions first,
**Delete** last and styled as destructive. **Disable** deliberately sits first
because it is the action you want most often in an incident, and it is reversible.

<Note>
**Reset MFA** only appears when the user actually has MFA enabled. There is no way
to reset a user who does not, which is consistent with there being nothing to
remove.
</Note>

### Roles and direct permissions in the panel

Below the action row is a **Roles** field — a comma-separated text input, hinted
*"Comma-separated role names from the Roles tab."* — with a **Save roles** button
that toasts **Roles saved**.

<Warning>
This maps to the `roles` field on the update route, which is **authoritative**.
Saving a list removes every role the user has that is not in it. The field is
pre-filled with the user's current roles, so a plain save is safe — but if you
clear it to "start fresh", you are removing all of them, not just adding one.
</Warning>

Direct permissions appear as individual badges, each with a **✕** that revokes that
one permission and toasts **Revoked**. Alongside them is a free-text input and a
**Grant** button, which toasts **Granted** and clears the field.

Permissions granted this way are **direct** — they sit on the user, not on a role.
The list shown includes permissions inherited through roles as well, so a **✕** on a
badge may remove a direct grant that happens to duplicate an inherited one, after
which the permission still appears because the role still confers it.

### Sessions in the panel

A **Sessions** heading above a table with columns **Session**, **Device**, **IP**,
**Last active**, and an unnamed final column holding a per-row **Revoke** button.

**Session** renders only the first eight characters of the family — enough to
recognise, not enough to use. **Device** is the raw user-agent string. **Last
active** prefers a last-seen value and falls back to the creation time.

The empty state is **"No active sessions."** Seeing it for a user you believe is
signed in is usually the intersection rule rather than a bug.

**Revoke** calls the per-session delete and toasts **Session revoked**.

### History in the panel

Below the sessions, a **History** table with columns **When**, **Event**, **OK**
and **IP**, empty state **"No activity."**

The **OK** column is a badge: green `ok` on success, red carrying the `reason`
string on failure. That is what makes a user's failure reason visible without
reading the API — `unknown email`, `wrong password`, `locked`, `wrong code` and the
refresh theft messages all appear here verbatim.

<Info>
This is the most useful panel for support work. When a user says "it keeps telling
me my account is locked" or "I get signed out randomly", the History table usually
answers it in one click.
</Info>


## Worked examples

The composite operations, because the individual routes are simple but the
combinations are where the mistakes live.

### Offboarding an employee

The order matters, and the reason is that some actions are irreversible.

The account should be **disabled** first. That revokes every session immediately
and blocks new sign-ins, and it keeps the row intact so the audit history stays
attributable.

If the person had MFA enrolled, reset it — but note this does **not** revoke
sessions, which is why disabling came first. Their existing access tokens remain
valid until they expire regardless.

Revoking sessions is redundant after disabling, and the count returned will be
zero, since disabling already revoked them.

If the account should no longer be reachable by anyone, **delete** it. That releases
the email address for re-use, removes linked identities and factors, and cannot be
undone.

<Warning>
If you need the address preserved — because it is a shared or role-based account, or
because you are deleting a duplicate — do not delete. Disable leaves the address
taken, which is what you want when identity continuity matters.
</Warning>

### Investigating "someone keeps getting signed out"

The symptom has one overwhelmingly common cause, and the history route identifies
it.

Read the user's history and look for repeated `refresh` events whose `reason`
contains a theft message. That pattern is the signature of a client presenting the
same refresh token twice — two tabs, a retry after a timeout, or a race between
concurrent requests.

The fix is on the client, not the server: serialise refreshes and never retry a
failed refresh with the same token. The server's behaviour is correct; it cannot
tell a racing client from a thief.

If instead the history shows `sign_in` with `locked`, the account is locked out and
`{"unlock": true}` clears it immediately.

<Info>
Because the theft message is written to the login-event history, this diagnosis is
available to you and invisible to the user — their client only ever receives a
generic `401`.
</Info>

### Granting a role safely

The failure mode is sending a partial role list, which strips everything not in it.

Read the user's current `roles`, add the new one, and send the union. The Studio
**Roles** field is pre-filled for exactly this reason, and a plain **Save roles**
is safe; editing it to contain only the new role is not.

<Warning>
Assigning a role name that does not exist **creates** it, with no permissions. A
typo produces a valid, empty role rather than an error, and the user appears to
have a role that grants nothing. Check the **Roles** tab for the exact spelling.
</Warning>

### Finding every user with a stale role

Because roles are read into the token at issue time, a role change only lands on
each user's **next refresh**. There is no bulk "log everyone out so they pick up
their new roles" action, and building one means revoking sessions.

The practical approach for a permission change you need to take effect promptly is
to revoke sessions for the affected users — for example via
`POST .../sessions/revoke` each. That forces a refresh, and the new token carries
the new permissions.

<Info>
This is also why a permission change and a role change have different urgency. A
role change is advisory until users refresh; revoking sessions makes it immediate.
</Info>
