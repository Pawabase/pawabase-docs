Administering users in Pawabase means acting on an account in **one project and
one environment**. Every admin route takes the environment from its path, and
every user lookup is scoped by it. An account in `acme/production` is a different
row from the same address in `acme/staging`, and no admin operation crosses that
boundary.

That single rule explains most of the confusing results. "The user does not exist"
usually means they do not exist *in that environment*.

Two further things to know before you start, because they shape what the controls
actually do:

**Disable and delete are very different.** Disabling keeps the account and its
history and revokes its sessions; it can be undone. Deleting is a soft delete that
rewrites the email address to free it for re-use, and it removes factors and
linked identities. They are not two strengths of the same action.

**Administrative actions are not instant for existing sessions.** A revoked or
disabled user's access tokens keep working until they expire, because services
verify signatures locally. New sign-ins and all refreshes are blocked immediately.

## The admin routes

All of them live under `/projects/{project}/envs/{env}` and all of them require a
service token. Studio calls them with its own management key.

| Route | Method | Purpose |
| --- | --- | --- |
| `/users` | GET | Search and list users |
| `/users` | POST | Create a user |
| `/users/{user_id}` | GET | One user, with their active sessions |
| `/users/{user_id}` | PATCH | Update, verify, disable, unlock, set password |
| `/users/{user_id}` | DELETE | Delete a user |
| `/users/{user_id}/sessions/revoke` | POST | Sign out everywhere |
| `/users/{user_id}/sessions/{session_id}` | DELETE | End one session |
| `/users/{user_id}/mfa/reset` | POST | Remove a user's second factors |
| `/users/{user_id}/history` | GET | A user's sign-in history |
| `/users/{user_id}/permissions` | POST | Grant direct permissions |
| `/users/{user_id}/permissions` | DELETE | Revoke direct permissions |

There is also a context-scoped variant, `GET /users/{user_id}`, which takes the
environment from the request context rather than the path — the form another
Pawabase service uses.

<Warning>
Every route here requires a service token, and none of them are scoped. A
credential that can reach these routes can create and delete users, reset MFA and
change roles. Treat it as full administrative access to the environment's
identities, store it in a secret manager, and rotate it when someone leaves.
</Warning>

## Listing and searching users

`GET {base}/users` returns `{"data": [...], "total": N}`. Every row is a full
**admin** view of the user, which is a superset of what the user sees about
themselves.

| Query parameter | Effect |
| --- | --- |
| `search` | Case-insensitive match against **email**, **username** or **name** |
| `status` | `disabled` for accounts with a disable timestamp; `unverified` for those with no verification stamp |
| `limit` | Page size, default 50, capped at 200 |
| `offset` | Rows to skip, default 0 |

Results are ordered newest first, which for a ULID key is also creation order.

The `search` behaviour is worth knowing because it is broader than it first
appears: one parameter matches across three fields, so searching a name fragment
can return users whose email merely contains that fragment.

### The admin user view

This is the payload behind both the list rows and the detail panel. The fields the
self-service view does not have are marked.

<ResponseField name="id">The user's ULID.</ResponseField>
<ResponseField name="email">Normalised, lowercased, unique within this environment.</ResponseField>
<ResponseField name="username">Unique within this environment; auto-generated if not supplied.</ResponseField>
<ResponseField name="name">Display name. Free text.</ResponseField>
<ResponseField name="avatar_url">Optional.</ResponseField>
<ResponseField name="email_verified">Boolean, derived from whether a verification stamp exists.</ResponseField>
<ResponseField name="email_verified_at">Timestamp, or `null`.</ResponseField>
<ResponseField name="user_metadata">User-editable JSON. Lands in the `meta` claim.</ResponseField>
<ResponseField name="app_metadata">Admin-only JSON. Lands in the `app` claim.</ResponseField>
<ResponseField name="roles">Role names, unprefixed.</ResponseField>
<ResponseField name="mfa_enabled">Whether a confirmed factor exists.</ResponseField>
<ResponseField name="identities">Linked external providers, with `last_sign_in_at`.</ResponseField>
<ResponseField name="created_at">Timestamp.</ResponseField>
<ResponseField name="last_sign_in_at">From the last successful sign-in.</ResponseField>
<ResponseField name="disabled">**Admin only.** True when disabled or inactive.</ResponseField>
<ResponseField name="disabled_at">**Admin only.** When it was disabled.</ResponseField>
<ResponseField name="locked_until">**Admin only.** Lockout expiry, or `null`.</ResponseField>
<ResponseField name="last_sign_in_ip">**Admin only.** From the last successful sign-in.</ResponseField>
<ResponseField name="has_password">**Admin only.** Whether password sign-in is possible at all.</ResponseField>
<ResponseField name="permissions">**Admin only.** Effective permissions, direct and via roles.</ResponseField>

<Warning>
`has_password` is the field to check before offering a password reset flow. An
account created by an OAuth provider has an **unusable password**, not an empty
one — password sign-in cannot succeed for it, and a reset link is the only way to
set one.
</Warning>

`GET {base}/users/{user_id}` returns the same view plus a `sessions` array, which
is what makes the detail panel a single request.


## Creating a user

`POST {base}/users` creates an account. Two fields deserve attention before you
call it.

<ResponseField name="email">Required. Normalised; a duplicate in this environment is a `409`.</ResponseField>
<ResponseField name="password">Optional. **Omit it and the account gets an unusable password** — the user sets one via a recovery link.</ResponseField>
<ResponseField name="username">Optional. Auto-generated from the email if absent.</ResponseField>
<ResponseField name="name">Optional display name.</ResponseField>
<ResponseField name="user_metadata">Initial user metadata. User-editable afterwards.</ResponseField>
<ResponseField name="app_metadata">Initial app metadata. Admin-only afterwards.</ResponseField>
<ResponseField name="email_verified">**Defaults to `true`.** Admin-created users are pre-verified.</ResponseField>
<ResponseField name="roles">Roles to assign. Added to any default roles the environment grants.</ResponseField>

<Warning>
`email_verified` defaults to **true** on the admin create route, which is the
opposite of what a public sign-up does. That is usually what you want for an
employee you have just created — but if you are importing unverified leads, set it
to `false` explicitly or you will have skipped the verification your policy
assumes is happening.
</Warning>

Two behaviours to be aware of:

**`roles` is additive with the environment's defaults.** A created user receives
`default_roles` from the auth configuration *and* whatever you pass. Passing an
empty list does not mean "no roles".

**Role names that do not exist are created.** Assigning a role the environment has
not defined creates it, with no permissions. That is convenient and occasionally
surprising — a typo produces a valid, empty role rather than an error.

The route returns the created admin user view with a `201`.

### Username generation

When no username is supplied, one is derived: the email's local part, or the
supplied name, lowercased, with every character outside `a-z0-9_.-` stripped,
truncated to 40 characters, defaulting to `"user"` if nothing survives. On
collision, a random number below 10,000 is appended and the check repeats.

So `Ada.Lovelace+news@Example.com` with no username becomes something like
`adalovelacenews`, and a second such user gets a numeric suffix. Uniqueness is
enforced per environment.


## Updating a user

`PATCH {base}/users/{user_id}` does all of update, verify, disable, unlock and
password setting. It is one route with several optional fields, and only the fields
you send are touched.

<ResponseField name="name">Sets the display name.</ResponseField>
<ResponseField name="email_verified">`true` stamps the verification now; `false` clears it — which re-blocks sign-in if the environment requires verification.</ResponseField>
<ResponseField name="disabled">`true` disables and revokes all sessions; `false` re-enables.</ResponseField>
<ResponseField name="password">Sets the password directly, after the environment's policy check. Bypasses any recovery flow.</ResponseField>
<ResponseField name="user_metadata">Replaces the whole object. Not merged.</ResponseField>
<ResponseField name="app_metadata">Replaces the whole object. Not merged.</ResponseField>
<ResponseField name="roles">Sets the user's roles to exactly this list — roles not in it are removed.</ResponseField>
<ResponseField name="unlock">`true` clears `failed_logins` and `locked_until`.</ResponseField>

<Warning>
`roles` on this route is **authoritative, not additive**. Sending a list removes
every role the user has that is not in it. If you read the roles, add one, and
send back the union, you get the expected result; if you send only the new role,
you strip the others.
</Warning>

<Warning>
`user_metadata` and `app_metadata` are **replaced, not merged**. Sending
`{"tier": "gold"}` for a user whose metadata is `{"tier": "free", "referral": "x"}`
leaves them with only `{"tier": "gold"}`. Read, merge, write.
</Warning>

The self-service route, `PATCH /auth/v1/user`, behaves differently and the
difference matters: it **merges** `data` into `user_metadata` rather than replacing
it, and it requires `current_password` before changing a password on an account
that has one.

### Disable is the blunt instrument

Disabling sets a disable timestamp **and revokes every session the user has**. That
combination is what makes it the right response to a suspected compromise, and it
is why it is not reversible in the way it looks — re-enabling restores the account
but does not restore the sessions.

<Warning>
Disabling does not invalidate access tokens that are already issued. Services
verify those signatures locally, so a disabled user's existing tokens keep working
until they expire — up to `access_ttl`. Disable stops new sign-ins and all refreshes
immediately; it does not reach tokens already in a service's hands.
</Warning>

Disabling and enabling each emit an event — `user.disabled` or `user.enabled` — so
an audit trail exists independently of the login-event history.

### Unlock is separate from disable

A locked account is one whose `locked_until` is set and in the future, which
happens after ten failed attempts by default. It is **not** disabled: it is
refused with `429`, and a correct password still fails until the window passes.

`{"unlock": true}` clears both the counter and the timestamp, immediately. There is
no wait and no cooldown — it is an administrative override, so treat it as a
deliberate act rather than a routine one.

<Note>
Because the lockout threshold and duration are installation settings while the
counters are per user per environment, unlocking one user in staging does not
affect the same address in production. They are separate accounts with separate
counters.
</Note>

### Setting a password directly

Setting `password` on the update route applies the environment's policy check
first, so a password the environment would refuse at sign-up is refused here too —
with the same `422` and the same list of problems.

It also makes the password **usable**, converting an account that had an unusable
one into one that can sign in with a password. That is the mechanism behind the
"Set password" button in Studio for OAuth-only accounts.

<Warning>
This route bypasses the recovery flow entirely. There is no emailed confirmation and
no `user.password_reset` event — it is a `user.password_changed`-style change made
by an administrator. If your process requires the user to prove control of their
email, use recovery instead and let them set their own password.
</Warning>


## Deleting a user

`DELETE {base}/users/{user_id}` is a **soft delete**, and the detail matters for
anyone deciding whether it is the right tool.

What it does:

- Revokes every session.
- Deletes the user's linked external identities.
- Removes all MFA factors and recovery codes.
- Marks the account inactive and stamps a deletion timestamp.
- **Rewrites the email to a placeholder** derived from the user id and project.
