It is easy to confuse the admin routes with the ones a user calls for themselves.
The distinction is not only about authentication — the **merge semantics differ**,
and getting that wrong is a real bug.

| Concern | Admin route | Self-service route |
| --- | --- | --- |
| Authentication | Service token | The user's own access token |
| Environment | In the path | From the request context |
| `user_metadata` | **Replaced** | **Merged** |
| Password change | No current password needed | `current_password` required if one is set |
| Session access | Any user's | Only the caller's |
| History | Any user's, 100 events | Only the caller's, 50 events |

The metadata difference is the one to remember. If you port an admin integration to
the self-service route expecting replacement, you will silently accumulate keys
instead, and vice versa.

<Note>
The self-service password change requires `current_password` only when the account
already has a usable password. An account with an unusable one — OAuth-only — can
set its first password without supplying one.
</Note>

A related asymmetry: the self-service email change does not apply immediately. It
issues a confirmation link, and the address changes only when that link is
followed. The admin route has no equivalent ceremony, because an administrator
setting an address is not the same trust decision as a user changing their own.


## Auditing what has been done

Every administrative action that changes state emits an event, and the
login-event table is the durable record. For an audit, the events to watch are:

| Event | Raised by |
| --- | --- |
| `user.created` | Sign-up, social sign-in, or an admin create |
| `user.disabled` / `user.enabled` | The update route |
| `user.deleted` | The delete route |
| `user.mfa_reset` | The MFA reset route |
| `user.verified` | A verification link, or an admin marking verified |
| `user.password_changed` | A self-service password change |
| `user.password_reset` | A completed recovery link |
| `user.updated` | A self-service profile update, carrying what changed |
| `session.revoked` | Any session revocation, carrying the scope |
| `session.reuse_detected` | A replayed refresh token |

Note the asymmetry: **`user.disabled` carries `actor="admin"`**, as do
`user.created` from the admin route, `user.deleted` and `user.mfa_reset`. Those
events name an administrator as the actor, while self-service events name the user.
So the actor field distinguishes "a person in Studio did this" from "a user did
this to themselves" — which is usually the question an audit is asking.

<Warning>
There is **no** event for disabling and re-enabling being the *same* action as
revoking sessions, and no aggregate "account compromised" marker. If your incident
process needs to know that MFA was reset **and** sessions revoked together, derive
it from the correlated events rather than expecting one event for it.
</Warning>


## Provisioning patterns

Two approaches, and the trade-off between them is about how much you trust the
identity of whoever is provisioning.

**Admins create users directly.** One call, immediate, no email round trip, and the
user is pre-verified by default. Appropriate when the provisioning system already
knows the person's work address and there is no ambiguity about identity.

**Admins create users without a password.** The account exists, `has_password` is
false, and the user sets their own password through a recovery link. This is the
right choice when you want the user to prove control of the address, and it is why
Studio's New user modal hints *"Leave empty to have the user set one through a
recovery link."*

| Approach | User verified | Proves control of email | Requires email to work |
| --- | --- | --- | --- |
| Create with password | Yes, by default | No | No |
| Create without password | Yes, by default | Yes | Yes |

<Info>
Neither approach is wrong; they answer different questions. If your threat model
includes an insider provisioning an account under someone else's address, the
second is the one that leaves an audit trail you can trust.
</Info>


## Bulk operations, and their absence

There is no bulk endpoint. Not for disabling many users, not for revoking many
sessions, not for setting a role across a group. Every operation is per user.

<Warning>
This matters during an incident. If a shared credential has been compromised and
two hundred accounts might have used it, there is no single call that ends all of
them. You will need to iterate — read the user list, then disable or revoke per
user.
</Warning>

The practical mitigation is the search and pagination already on the list route:
page through with a generous `limit` (its maximum is 200) and act on each id.
Doing that concurrently is reasonable, since these are independent per-user
operations with no shared lock — but be aware that the rate limits on the auth
bucket do not apply to admin routes, so the limiting factor will be the database.

<Info>
For a genuinely large user base, the better answer is usually preventive — a short
`refresh_ttl` means a compromised refresh token stops working sooner, without
anyone having to enumerate accounts.
</Info>


## Tenancy: why an admin action can appear to do nothing

The single most common confusion in user administration is an action that reports
success against the wrong account. It is nearly always the environment.

Every user lookup filters on **both** `project` and `env`. A user id is a ULID, and
while the id is globally unique as an identifier, the *lookup* is scoped: an id
from production, used against staging, finds nothing and returns `404 no such user`.

The same address in two environments is two accounts, with separate:

- Passwords
- Roles and permissions
- Sessions and lockout counters
- MFA enrolment
- Metadata

So "I disabled them" and "they can still sign in" are usually both true, referring
to different accounts.

| Symptom | Most likely explanation |
| --- | --- |
| `404` for a user you can see in another environment | Wrong environment in the path |
| User signs in but does not appear in your list | Different environment |
| Their password does not work here | Different account, different password |
| Disabling here did not stop them | They signed in to the other environment |
| Duplicate email was rejected, but they exist | A different environment, or a released address |

<Warning>
Promoting a database from one environment to another without promoting its auth
configuration is the usual way people create this confusion by accident. Accounts
arrive, the configuration does not, and sign-in behaves in ways that look like bugs.
</Warning>


## Verifying an administrative action took effect

Because some of these actions are not instantaneous everywhere, it is worth knowing
what "done" looks like for each.

| Action | Immediate effect | Delayed effect |
| --- | --- | --- |
| Disable | New sign-ins refused; all sessions revoked | Existing access tokens until `access_ttl` |
| Enable | Sign-in permitted again | The **disabled** badge clears immediately |
| Revoke sessions | All refreshes refused | Existing access tokens until `access_ttl` |
| Revoke one session | That session cannot refresh | Its current access token until `exp` |
| Unlock | Sign-in permitted; lockout cleared | The **locked_until** field clears |
| Reset MFA | Factors and codes gone; flag cleared | Existing `aal2` tokens keep their claim |
| Set password | `has_password` becomes true | Nothing |
| Mark verified | `email_verified` becomes true | The **unverified** badge clears |
| Change roles | `roles` updated in the view | The new roles appear in **tokens** on next refresh |
| Delete | Row hidden from all lookups | Nothing — it is immediate |

The pattern worth internalising: **the user view updates immediately, while tokens
update on the next refresh.** When you change a role and the user's app still shows
the old permissions, nothing has gone wrong — the token is a snapshot.

<Info>
The one genuinely confusing case is MFA reset: the view says MFA is off, but a
session created before the reset still carries `aal2`. The view is authoritative
going forward; the existing token is not rewritten.
</Info>
