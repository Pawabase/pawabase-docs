Auth events let the rest of your system react to what happens to accounts: add a sign-up to your CRM, alert on a disabled admin, email a welcome. You can send events to a **URL** you control (a signed webhook) or run a **flow**.

## In Studio

**Users & auth → Developers → Auth webhooks.** An empty page says *No auth webhooks yet*; **New** opens the editor.

**Target:** choose *When an event happens* → **URL** or **Flow**.

| Field | Meaning |
| --- | --- |
| **Name** | Lowercase letters, numbers, dashes and underscores, such as `auth_to_crm` |
| **Description** | `Keeps the CRM in step with accounts` |
| **URL** | Must answer within a few seconds. Deliveries carry a signature header your server should verify |
| **Flow** | Run this flow. The event's payload is the flow's input |
| **Auth events** | Pick events or **Families**. Wildcards cover a whole family: `user.*` is every user event |
| **Attempts** | Retries after the first failure |
| **Enabled** | Pause without deleting |
| **Signing secret** | Shown for URL webhooks. Use it to verify each delivery |

Under the hood these are ordinary [webhooks and event subscriptions](/automation/webhooks) restricted to auth events, so deliveries appear on the **Webhooks → Deliveries** page and retries work the same way.

## The events

| Event | When |
| --- | --- |
| `user.created` | Someone registers, accepts an invitation or is created by an operator |
| `user.signed_in` | Every successful sign-in, including refresh-token reuse warnings |
| `user.verified` | An email address is confirmed |
| `user.updated` | A profile or metadata changes |
| `user.disabled` | An operator blocks a person |
| `user.enabled` | An operator unblocks a person |
| `user.deleted` | An account is removed |
| `user.password_changed` | A person chooses a new password while signed in |
| `user.password_reset` | A recovery link is used |
| `user.email_changed` | A new email address is confirmed |
| `user.mfa_enabled` | A second factor is added |
| `user.mfa_disabled` | A second factor is removed |
| `user.mfa_reset` | An operator clears someone's factors |
| `user.passkey_added` | A passkey is registered |
| `user.api_key_created` | A personal API key is issued |
| `user.api_key_revoked` | A personal API key is revoked |
| `user.upgraded` | A guest account gains an email address |
| `session.revoked` | A session ends: signed out, expired or revoked |
| `session.reuse_detected` | A stolen refresh token was replayed; the family is revoked |
| `identity.linked` | A social or company identity is attached |
| `identity.unlinked` | A social or company identity is detached |
| `organization.created` | An organization is created |
| `organization.deleted` | An organization is removed |
| `invitation.accepted` | An invited person joins |

## Examples

- **Welcome email:** `user.created` → flow that sends a [mail template](/mail/overview).
- **CRM sync:** `user.created`, `user.updated`, `user.deleted` → your URL.
- **Security alerts:** `user.mfa_disabled`, `user.disabled`, `session.reuse_detected` → Slack or email to your team.
- **Audit trail:** `user.*` and `identity.*` → append to a log table.
- **Billing:** `organization.created` → create a customer at your payment provider.

## Tips

- Deliveries are at least once. Treat the event `id` as the idempotency key.
- Keep handlers fast: answer `2xx` immediately and work in the background.
- Don't put personal data in the logs of your receiving service.
