Email and password is the sign-in method most apps start with, and every other method (magic links, social providers, passkeys, a completed second factor) ends the same way: a [session](/auth/tokens-and-sessions) kept by the SDK. This page covers the whole life of a password account: creating it, signing in, the rules a password must meet, what happens after repeated failures, and how a user changes their details.

The examples use the clients created in the [overview](/auth/overview#set-up-a-client): `pawabase` in TypeScript and `pb` in Python.

## Create an account

<CodeGroup>
```typescript TypeScript
const { user, session, verificationRequired } = await pawabase.auth.signUp({
  email: "ada@example.com",
  password: "correct horse battery staple",
  name: "Ada Lovelace",
  data: { plan: "free" },
  redirectTo: "https://app.example.com/welcome",
});
```

```python Python
outcome = pb.auth.sign_up(
    email="ada@example.com",
    password="correct horse battery staple",
    name="Ada Lovelace",
    data={"plan": "free"},
    redirect_to="https://app.example.com/welcome",
)
user, session, needs_confirmation = outcome.user, outcome.session, outcome.verification_required
```
</CodeGroup>

| Parameter | Required | Notes |
| --- | --- | --- |
| `email` | yes | Must be a valid address. Stored lower-cased; two accounts cannot share an address in one environment. |
| `password` | yes | Must meet the [password policy](#the-password-policy). |
| `username` | no | A unique handle. When you leave it out, one is derived from the email. |
| `name` | no | Display name. |
| `data` | no | Initial `user_metadata`. The user can edit this later, so never use it to grant access. |
| `redirectTo` / `redirect_to` | no | Where the confirmation link sends the person. It must be on the environment's list of allowed redirect URLs, or the call fails with 400. |
| `accepted_terms` | no | Python only. Pass `True` when your sign-up form had a terms checkbox and the environment records acceptance. |

### Two outcomes

What comes back depends on whether the environment requires confirmed email addresses.

| Setting | Result | What to do |
| --- | --- | --- |
| Confirmation **not** required | `session` is set and the person is signed in. `verificationRequired` is `false`. | Go straight into your app. |
| Confirmation required | `session` is `null`; `verificationRequired` is `true`. A link was emailed. | Show a "check your inbox" screen. The person signs in after following the link. |

<CodeGroup>
```typescript TypeScript
const result = await pawabase.auth.signUp({ email, password });

if (result.verificationRequired) {
  showCheckYourInbox(result.user.email);
} else {
  goToApp(result.user);
}
```

```python Python
result = pb.auth.sign_up(email=email, password=password)

if result.verification_required:
    show_check_your_inbox(result.user["email"])
else:
    go_to_app(result.user)
```
</CodeGroup>

Confirming the address is covered in [Email verification](/auth/email-verification), including resending the link.

### New accounts get default roles

When the environment defines default roles, a new user receives them automatically. A role you forget to list is not granted, and a new user then cannot do what you expected; the first thing to check when "new users can't do anything". See [Roles and permissions](/auth/roles-and-permissions).

### Registering is open to anyone with your publishable key

Anyone who can reach your app can call sign-up, so treat it as a public endpoint. The environment can turn sign-up off (`signup_enabled`, readable from [`settings()`](/auth/overview#find-out-what-is-enabled)), cap the number of users, and restrict which email domains may register. A refused sign-up is a 403 with a message such as "sign-up is disabled" or "the environment user limit has been reached".

If you want invitation-only access, turn sign-up off and create accounts from your server with [`admin.users.create`](/auth/managing-users) or send [organization invitations](/auth/organizations).

## The password policy

Every password, at sign-up and when changed, is checked against the environment's policy. Read it from `settings()` to validate before sending:

<CodeGroup>
```typescript TypeScript
const { password_policy } = await pawabase.auth.settings();
// { kind: "basic", min_length: 8 }

const tooShort = password.length < password_policy.min_length;
```

```python Python
policy = pb.auth.settings()["password_policy"]
# {"kind": "basic", "min_length": 8}

too_short = len(password) < policy["min_length"]
```
</CodeGroup>

| `kind` | What it enforces |
| --- | --- |
| `basic` (default) | A minimum length (`min_length`, default 8) and nothing else. |
| `strict` | A strength assessment with the same minimum. It reports every weakness it finds, and it is a strength check, not a composition rule: a long passphrase can pass where a short mangled word cannot. |

Under both, a password longer than **1,024 characters** is refused. Switching a live environment from `basic` to `strict` only affects new and changed passwords: existing users keep theirs until they change it.

### Reading a policy failure

A password that fails the policy returns **422** with every problem in one response, so a form can show them all at once:

```json
{
  "message": "the password does not meet the policy",
  "problems": ["Password must be at least 8 characters."]
}
```

<CodeGroup>
```typescript TypeScript
import { ValidationError } from "@pawabase/client";

try {
  await pawabase.auth.signUp({ email, password });
} catch (error) {
  if (error instanceof ValidationError) {
    const problems: string[] = (error.body as { problems?: string[] }).problems ?? [error.message];
    showProblems(problems);
  }
}
```

```python Python
from pawabase import ValidationError

try:
    pb.auth.sign_up(email=email, password=password)
except ValidationError as error:
    problems = error.detail.get("problems") if isinstance(error.detail, dict) else None
    show_problems(problems or [error.message])
```
</CodeGroup>

<Tip>
Check length in your form as well, so people see the problem before they submit. The server remains the authority: a stricter policy can reject what your form allowed.
</Tip>

## Sign in

<CodeGroup>
```typescript TypeScript
const result = await pawabase.auth.signInWithPassword({
  email: "ada@example.com",
  password: "correct horse battery staple",
});

if (result.status === "signed_in") {
  goToApp(result.session.user);
} else {
  askForCode(result.factors);              // ["totp"]
  const session = await result.verify(code);
}
```

```python Python
result = pb.auth.sign_in_with_password(email="ada@example.com", password="correct horse battery staple")

if result.status == "signed_in":
    go_to_app(result.session.user)
else:
    ask_for_code(result.factors)           # ["totp"]
    session = result.verify(code)
```
</CodeGroup>

| Parameter | Notes |
| --- | --- |
| `email`, `password` | Required. |
| `org` | Optional organization slug. Signs the person in scoped to that organization (see [Organizations](/auth/organizations)). Leave it out unless you mean it. |
| `remember_device` | Python only. Trust this device so a second factor is not asked again on it, when the environment allows remembered devices. |

### Two possible results

| `status` | Meaning |
| --- | --- |
| `signed_in` | The session is ready and already kept by the SDK. Your listeners receive `SIGNED_IN`. |
| `mfa_required` | The password was right but the account has a second factor. `factors` lists what the person can use. Collect a code and call `result.verify(code)`; the session is kept when it succeeds. |

If you need to finish the challenge later, for instance after navigating to a code screen, keep the token and use `verifyMfa`:

<CodeGroup>
```typescript TypeScript
if (result.status === "mfa_required") {
  sessionStorage.setItem("mfa", result.mfaToken);
}

// on the code screen
const session = await pawabase.auth.verifyMfa({ mfaToken: sessionStorage.getItem("mfa")!, code });
```

```python Python
if result.status == "mfa_required":
    token = result.mfa_token

# on the code screen
session = pb.auth.verify_mfa(mfa_token=token, code=code)
```
</CodeGroup>

The code can be from an authenticator app or one of the person's recovery codes. A challenge expires after a short time; a stale one fails with 400 "the challenge is no longer valid", and the person signs in again. More in [Multi-factor authentication](/auth/mfa).

### What sign-in checks, in order

1. The account exists and has a password. Otherwise: 400 "invalid email or password".
2. The password is right. A wrong one counts toward [lockout](#lockout-and-rate-limits).
3. The account is not locked (429) or disabled (403 "this account is disabled").
4. The email is confirmed, when the environment requires it (403 "confirm your email address first").
5. If a second factor is enrolled, the result is `mfa_required` instead of a session.

An unknown email and a wrong password get the identical answer on purpose. Do not try to tell them apart in your UI.

## Handle failures

| Situation | Status | Message | TypeScript | Python |
| --- | --- | --- | --- | --- |
| Wrong email or password | 400 | invalid email or password | `ApiError` | `ValidationError` |
| Invalid email address | 422 | a valid email address is required | `ValidationError` | `ValidationError` |
| Password fails the policy | 422 | the password does not meet the policy | `ValidationError` | `ValidationError` |
| Email already registered | 409 | an account with this email already exists | `ConflictError` | `ConflictError` |
| Username taken | 409 | that username is taken | `ConflictError` | `ConflictError` |
| Redirect URL not allowed | 400 | redirect_to is not an allowed URL | `ApiError` | `ValidationError` |
| Sign-up turned off, or user limit reached | 403 | sign-up is disabled | `PermissionError` | `ForbiddenError` |
| Account disabled | 403 | this account is disabled | `PermissionError` | `ForbiddenError` |
| Email not confirmed yet | 403 | confirm your email address first | `PermissionError` | `ForbiddenError` |
| Too many failed attempts | 429 | too many failed attempts; try again later | `RateLimitError` | `RateLimitedError` |
| Missing or wrong API key | 401 | Send a valid API key in the apikey header | `AuthenticationError` | `AuthenticationError` |

A sign-up that conflicts is the one place where the endpoint reveals that an address is registered. It has to, or nobody could register; if that matters to you, route sign-up through [magic links or emailed codes](/auth/passkeys-and-codes), which answer the same way either way.

<CodeGroup>
```typescript TypeScript
import { ApiError, PermissionError, RateLimitError } from "@pawabase/client";

async function signIn(email: string, password: string) {
  try {
    return await pawabase.auth.signInWithPassword({ email, password });
  } catch (error) {
    if (error instanceof RateLimitError) return fail("Too many attempts. Wait a few minutes and try again.");
    if (error instanceof PermissionError) return fail(error.message);          // disabled, or unconfirmed
    if (error instanceof ApiError && error.status === 400) return fail("Wrong email or password.");
    throw error;
  }
}
```

```python Python
from pawabase import ForbiddenError, RateLimitedError, ValidationError

def sign_in(email: str, password: str):
    try:
        return pb.auth.sign_in_with_password(email=email, password=password)
    except RateLimitedError:
        return fail("Too many attempts. Wait a few minutes and try again.")
    except ForbiddenError as error:
        return fail(error.message)                       # disabled, or unconfirmed
    except ValidationError:
        return fail("Wrong email or password.")
```
</CodeGroup>

## Lockout and rate limits

Two separate controls protect sign-in, and they stop different attacks.

| Control | Scope | Default | What it stops |
| --- | --- | --- | --- |
| Rate limit | Per client | 30 sign-up and sign-in requests per minute, shared | One client trying many accounts, or enumerating addresses. |
| Account lockout | Per account | 10 failed passwords, then 15 minutes | Guessing at a single account. |

Second-factor codes have their own, tighter limit of 10 attempts a minute, and wrong codes count toward the same account lockout. A successful sign-in, including a completed second factor, resets the failure count.

When either control trips, the answer is **429**. The right response is to tell the person to wait. Never wrap sign-in in an automatic retry loop: every refused attempt restarts the wait and the user stays locked out. Both SDKs already wait out a 429 a couple of times, as long as the server asks; a lockout lasts minutes, so those waits end in the error and you should not add your own. The error carries `retryAfter` (`retry_after` in Python) in seconds when the server provides one.

<Warning>
Sign-up and sign-in share one rate-limit allowance. A script that creates many accounts through sign-up spends the same allowance your real users need to sign in. Create accounts in bulk from a server with a secret key instead: see [Managing users](/auth/managing-users).
</Warning>

An operator can clear a lock early from [Managing users](/auth/managing-users); the person then gets a fresh set of attempts.

## Change profile, password or email

A signed-in user edits their own record with `updateUser` / `update_user`. Everything is optional; send only what changes.

<CodeGroup>
```typescript TypeScript
await pawabase.auth.updateUser({
  name: "Ada King",
  avatar_url: "https://cdn.example.com/ada.png",
  data: { theme: "dark" },
});

await pawabase.auth.updateUser({
  password: "a new, longer passphrase",
  current_password: "correct horse battery staple",
});

await pawabase.auth.updateUser({ email: "ada.king@example.com" });
```

```python Python
pb.auth.update_user(
    name="Ada King",
    avatar_url="https://cdn.example.com/ada.png",
    data={"theme": "dark"},
)

pb.auth.update_user(
    password="a new, longer passphrase",
    current_password="correct horse battery staple",
)

pb.auth.update_user(email="ada.king@example.com")
```
</CodeGroup>

| Field | Behaviour |
| --- | --- |
| `name`, `avatar_url` | Replaced. |
| `data` | **Merged** into `user_metadata`; keys you do not mention are kept. |
| `password` | Must meet the policy. With an existing password, `current_password` is required: a wrong or missing one fails with 400 "current_password is wrong". |
| `email` | Starts a change, see below. The address does not change yet. |

Note the TypeScript field names: `avatar_url` and `current_password` are snake_case, matching the wire format. Python uses the same names as keyword arguments.

`updateUser` returns the updated user and emits `USER_UPDATED` to listeners.

### Setting a first password

An account created through a social provider, a magic link or a passkey may have no password. Such a user can set one with `updateUser({ password })` without `current_password`. From then on the password is required to change it.

### Changing the email address

A new address is not trusted until its owner proves it. `updateUser({ email })` emails a confirmation link to the **new** address; the old one stays in force until the link is followed. The link carries a token you finish with `confirmEmailChange`:

<CodeGroup>
```typescript TypeScript
await pawabase.auth.confirmEmailChange(tokenFromLink);
```

```python Python
pb.auth.confirm_email_change(token_from_link)
```
</CodeGroup>

If the address is already used by another account, the change fails with 409 "that email is in use".

### Calls made with an API key cannot change credentials

A request authenticated only by an API key, with no signed-in user, cannot change a password or an email: it fails with 403. Credentials change only on behalf of the signed-in person. To reset someone's password from a server, send them a [recovery email](/auth/password-recovery).

## After a password change

Changing a password does not sign anyone out by itself. If you want a clean slate after a password change or a suspected compromise, end the user's other sessions:

<CodeGroup>
```typescript TypeScript
await pawabase.auth.updateUser({ password, current_password });
await pawabase.auth.signOut({ scope: "others" });
```

```python Python
pb.auth.update_user(password=password, current_password=current_password)
pb.auth.sign_out(scope="others")
```
</CodeGroup>

`scope` is `local` (this session), `others` (every other session of the user) or `global` (all of them, including this one). See [Tokens and sessions](/auth/tokens-and-sessions#sign-out-and-revoke).

## Testing your forms

- Create a throwaway environment, or use `development`, and turn email confirmation off so sign-up returns a session at once.
- To test lockout without waiting, use a test account and keep a note that the lock clears after 15 minutes, or ask an operator to clear it.
- To test the confirmation flow without a real mailbox, read the message from the environment's mail log in Studio, or call [`mail`](/mail/overview) with a test address you control.
- Run a [`strict`](#the-password-policy) policy in staging to catch weak-password handling before production.

## Security notes

- Passwords are salted and hashed with a deliberately slow algorithm. There is no API that returns a password or its hash, and none that lets you set a hash directly.
- The password travels only in the request body, over HTTPS. Never put one in a URL or log it. The SDK never logs request bodies.
- Do not store the password client-side. The session keeps tokens, not credentials.
- Use [multi-factor authentication](/auth/mfa) for accounts that hold anything valuable, and [email verification](/auth/email-verification) so an address cannot be claimed by someone else.
- Rate limits are per client and lockout is per account. Together they slow guessing; they do not make a weak password safe, so choose the `strict` policy.

## A sign-up form, end to end

This pairs the checks above into one flow: validate locally, create the account, then either continue or ask the person to confirm their address.

<CodeGroup>
```typescript TypeScript
import { ConflictError, ValidationError } from "@pawabase/client";

export async function register(form: { email: string; password: string; name: string }) {
  const { password_policy, signup_enabled, email_verification_required } = await pawabase.auth.settings();
  if (!signup_enabled) return { status: "closed" as const };
  if (form.password.length < password_policy.min_length) {
    return { status: "invalid" as const, problems: [`Use at least ${password_policy.min_length} characters.`] };
  }

  try {
    const result = await pawabase.auth.signUp({ ...form, redirectTo: `${location.origin}/welcome` });
    return result.verificationRequired
      ? { status: "check-inbox" as const, email: result.user.email }
      : { status: "signed-in" as const, user: result.user };
  } catch (error) {
    if (error instanceof ConflictError) return { status: "taken" as const };
    if (error instanceof ValidationError) {
      const body = error.body as { problems?: string[] };
      return { status: "invalid" as const, problems: body.problems ?? [error.message] };
    }
    throw error;
  }
}
```

```python Python
from pawabase import ConflictError, ValidationError


def register(email: str, password: str, name: str, origin: str):
    settings = pb.auth.settings()
    if not settings["signup_enabled"]:
        return {"status": "closed"}
    minimum = settings["password_policy"]["min_length"]
    if len(password) < minimum:
        return {"status": "invalid", "problems": [f"Use at least {minimum} characters."]}

    try:
        result = pb.auth.sign_up(email=email, password=password, name=name, redirect_to=f"{origin}/welcome")
    except ConflictError:
        return {"status": "taken"}
    except ValidationError as error:
        problems = error.detail.get("problems") if isinstance(error.detail, dict) else None
        return {"status": "invalid", "problems": problems or [error.message]}

    if result.verification_required:
        return {"status": "check-inbox", "email": result.user["email"]}
    return {"status": "signed-in", "user": result.user}
```
</CodeGroup>

## Questions people ask

**Can people sign in with a username?** No. Sign-in takes an email and a password. A `username` is a handle you can store and show, and it must be unique, but it is not a sign-in credential.

**Is the email case-sensitive?** No. Addresses are lower-cased when stored and when looked up, so `Ada@Example.com` and `ada@example.com` are the same account.

**Can the same person have two accounts with one address?** Not within one environment. In different environments they are independent accounts.

**Can I import existing users with their passwords?** Create them from your server with [`admin.users.create`](/auth/managing-users). Send people a [recovery email](/auth/password-recovery) so they choose a new password, rather than moving hashes between systems.

**Why does sign-in say "confirm your email address first"?** The environment requires confirmed addresses and this one has not been confirmed. Call `resendVerification` and see [Email verification](/auth/email-verification).

**How do I make sign-in friendlier after a failure?** Keep the email the person typed, clear only the password, and put the focus back in the password field. Do not reveal which half was wrong.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `signUp` returns `verificationRequired: true` and no session | The environment requires confirmed addresses. | Show a check-your-inbox screen; the person signs in after confirming. |
| `signUp` fails with 403 "sign-up is disabled" | Registration is switched off for the environment. | Turn it on, or create the account from your server. |
| `signUp` fails with 400 "redirect_to is not an allowed URL" | `redirectTo` is not on the allowed list. | Add the exact origin, scheme and port included, in Studio. |
| The password is rejected but looks fine | The policy is `strict`, which assesses strength. | Offer a longer passphrase; show every message in `problems`. |
| Sign-in works in one environment and not another | Accounts do not carry across environments. | Sign up in each, or create the account from a server. |
| Password change fails with 400 "current_password is wrong" | The old password was missing or mistyped. | Ask for it again. Accounts with no password can omit it. |
| Password change fails with 403 | The call had no signed-in user (an API key alone). | Sign the user in first and call `updateUser` as them. |
| Signed out right after changing the password | You called `signOut` with `global` scope. | Use `others` to keep this device signed in. |

## A friendlier form

Small choices in the form decide whether sign-in feels reliable.

- Use the browser's own fields: `type="email"` with `autocomplete="email"`, and `autocomplete="current-password"` on sign-in or `new-password` on sign-up. Password managers rely on them.
- Let people see what they typed with a show-password toggle. It prevents more failed attempts than any rule you can write.
- Disable the submit button while a request is in flight. A double submit spends two of the 30 requests a minute, and may count as two wrong passwords.
- After a 429, disable the form for a few minutes and say why, instead of letting people keep trying.
- Never put the password in a query string, a log line or an error report. If your tooling captures request bodies, exclude `/auth/v1/signup`, `/auth/v1/token` and the profile-update call.
- Keep the email field filled after a failure. Clear only the password.
- On sign-up, validate length as the person types, but wait for the server's answer before treating the password as accepted: the policy can be stricter than your form.
