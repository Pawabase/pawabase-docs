The password grant is the reference case for Pawabase authentication. Every other sign-in method — magic links, social providers, a completed MFA challenge — arrives at the same place: the same token pair, the same session, the same `Principal`. Passwords are simply the path where you already know what to write, which makes them the right place to understand the model.

What this page covers is the whole lifecycle of that one credential. How an account comes into existence, what the policy allows and how you learn it failed, how the password is stored, how sign-in decides, what happens when it is wrong repeatedly, and how a user changes or forgets it.

  <Card title="One grant shape" icon="key-round">Every grant type ends at the same token response, so there is one code path in your client regardless of how the user proved who they were.</Card>

## Where passwords sit in the layered model

Before the mechanics, the position — because most password problems are not password problems.

Akountz owns the credential. It stores the hash, compares the submitted password against it, maintains the failure counter, and decides whether the account is locked. Nothing else ever sees the password. Your application submits it to `POST /auth/v1/token` and receives tokens or a refusal; it never reads, stores, or re-checks the password itself.

The environment owns the policy. Whether sign-up is allowed, how strong a password must be, and how long tokens last are all keys in the environment's `auth` block, which Akountz reads. That is why changing the policy takes up to ten seconds to take effect, and why an unset key means a permissive default rather than "off".

The gateway never touches the password. It verifies tokens on resource requests and has no involvement in sign-in at all. If you are debugging a problem that only appears when attaching a token to a resource call, the password layer is not involved.

| Layer | Its involvement in a password sign-in |
| --- | --- |
| Akountz | Owns the credential, the policy, the counter, and the lock. |
| The API | Owns the policy values in the environment's `auth` block. |
| Gateway | None at sign-in. Verifies the resulting token afterwards. |

<Warning>
If you find yourself storing passwords in your own database, or sending them to a custom route for validation, that work is duplicated and the copy is a liability you have taken on. The password belongs in one place.
</Warning>

## The account before the password

An account is identified by `(project, env, email)`, and the email is normalised before anything else happens. Normalisation strips surrounding whitespace, lowercases the whole address, and then requires a shape with an `@`, no whitespace on either side of it, and at least one dot after the `@`. An address that fails the shape check, or that exceeds 255 characters, is rejected with a 422 before any lookup occurs.

<Warning>
Because normalisation lowercases before storing, **every lookup is lowercase**. A user who typed `Ada@Example.com` is stored as `ada@example.com`. If your client searches for the string the user typed, it will find nothing — and you will conclude the account does not exist when it plainly does. Normalise on your side too, or better, let the server do the normalising by searching on the value it gave you back.
</Warning>

Duplicates are refused within one `project` + `env` pair with a 409. The same address in two environments is not a duplicate, because those are different accounts.

Alongside the email, every account gets a username. It is derived rather than chosen, which is why you will see values that look mechanical:

| Input | Derived username |
| --- | --- |
| `ada@example.com`, no name | `ada` |
| `ada+work@example.com`, no name | `adawork` |
| Name `Ada Lovelace` | `adalovelace` |
| Name `Zoë Ðağ` | `z` — everything outside the allowed set is stripped |
| A name that reduces to nothing | `user` |
| A derived name already taken | The base plus a random number below 10,000 |

The allowed set is `a-z`, `0-9`, `_`, `.` and `-`, and the result is truncated to forty characters. The collision suffix is random rather than sequential, so usernames carry no ordering information and should not be parsed for one.

<Note>
The collision check is scoped to one environment. Two environments can derive the same username for the same person without either noticing. If you want usernames to be unique across your whole installation, that is not what this guarantees.
</Note>

### An account can exist without a password

If a password is not supplied, the account gets an **unusable** password rather than an empty one. An unusable password can never match any input, so password sign-in fails cleanly — whereas an empty string would, in principle, match an empty submission.

This is the normal state for accounts created through a social provider, through a magic link, or by an operator who left the field blank. It is not a broken account and it is not something to repair; it is an account that has not chosen a password yet.

| How the account was created | Has a password? |
| --- | --- |
| `POST /auth/v1/signup` | Yes. The field is required. |
| Studio **New user** with a password | Yes. |
| Studio **New user**, password left blank | No. Unusable until one is set. |
| First sign-in through a provider | No. |
| First sign-in through a magic link | No. |

## Creating an account

`POST /auth/v1/signup` creates an account and, depending on the environment, either signs the user in immediately or stops and asks them to confirm their address.

```bash
curl -X POST https://api.example.com/auth/v1/signup \
  -H "apikey: pk_live_..." \
  -H "content-type: application/json" \
  -d '{"email":"ada@example.com","password":"correct horse battery","name":"Ada Lovelace"}'
```

| Field | Required | Notes |
| --- | --- | --- |
| `email` | Yes | Normalised. Must satisfy the shape check, and be unique in this environment. |
| `password` | Yes | Checked against the policy before the account is written. Between 1 and 1024 characters at the request level. |
| `username` | No | Supplied explicitly it must be free; if omitted it is derived. |
| `name` | No | Free text, up to 200 characters. Used to derive the username when one is not supplied. |
| `data` | No | Becomes the initial `user_metadata`. Note this is user-editable, so do not put anything in it that a policy must trust. |
| `redirect_to` | No | Where the verification link lands. Must be an allowed URL, or the request is refused with a 400. |

<ResponseField name="409">An account with that email already exists in this environment.</ResponseField>
<ResponseField name="409">A username you supplied explicitly is already taken.</ResponseField>
<ResponseField name="422">The email is not a valid address, or is over 255 characters.</ResponseField>
<ResponseField name="422">The password does not meet the policy. The body carries a list of problems.</ResponseField>
<ResponseField name="403">Sign-up is disabled for this environment.</ResponseField>
<ResponseField name="400">`redirect_to` is not an allowed URL.</ResponseField>

<Warning>
The duplicate-email 409 is the one place where the anti-enumeration property does not apply. It has to be, or nobody could ever register — but it does mean the endpoint confirms whether an address is registered. Rate limiting is what bounds that, at thirty a minute shared with sign-in.
</Warning>

On success the account is written, any roles listed in the environment's `default_roles` are assigned, and a `user.created` event is emitted. Then the environment's verification setting decides what happens next.

### Two different success responses

Sign-up returns one of two shapes, and the difference is not cosmetic — it decides whether your client shows a "welcome" screen or a "check your email" screen.

**When verification is not required**, the response is a complete session: the token shape plus `verification_required: false`. The user is signed in.

**When verification is required**, the account exists but there is no session. The response carries the user, a `session` of `null`, and `verification_required: true`. A verification email has been sent.

```json
{
  "user": { "id": "01J8Z...", "email": "ada@example.com" },
  "session": null,
  "verification_required": true
}
```

<Warning>
This is the second "signed in but not finished" state, and it is easy to mishandle. A client that checks for `access_token` and treats its absence as a failure will tell a brand-new user that sign-up failed, when in fact it succeeded completely. Check `verification_required` explicitly.
</Warning>

The account is usable in the sense that it exists and its roles are assigned — but it cannot sign in until the address is confirmed, if the environment requires that.

### Default roles arrive automatically

Whatever the environment lists in `default_roles` is assigned at creation, before the response is sent. This is how a new customer gets the `customer` role without your application doing anything.

Two things follow. First, a role you forget to list will not be granted, and the user has to be assigned it separately — a common cause of "new users can't do anything". Second, changing `default_roles` affects only accounts created afterwards; it never back-fills existing ones.

<Info>
Default roles are created-if-missing by assignment, so a `default_roles` entry naming a role that does not exist yet does not fail sign-up. It assigns a name. Make sure the role exists, or your users will carry a role that grants nothing.
</Info>

### The verification gate

If the environment sets `require_email_verification`, sign-in refuses an unverified account with a 403 and the message asking them to confirm their address first. Note that this is checked *after* the password has been verified — an unverified user with a wrong password gets the generic refusal, not the verification message, so the gate leaks nothing about which addresses are unverified.

Your client should recognise this state and show instructions rather than an error. The account exists and the password is correct; the user simply needs to open their inbox.

<Info>
Because verification is a per-environment setting, the same deployment can behave differently in development and production. A sign-in that works locally and 403s in production is very often this, not a credential problem. The environment selector in Studio, and the setting under **Sign-up** in the Configuration tab, are where to look.
</Info>

## Signing in

`POST /auth/v1/token` with `grant_type` set to `password` — which is the default, so it can be omitted — and an email and password.

```bash
curl -X POST https://api.example.com/auth/v1/token \
  -H "apikey: pk_live_..." \
  -H "content-type: application/json" \
  -d '{"grant_type":"password","email":"ada@example.com","password":"correct horse battery"}'
```

| Field | Required | Notes |
| --- | --- | --- |
| `grant_type` | No | `password` by default. A query parameter of the same name takes precedence over the body. |
| `email` | Yes | Normalised before lookup, so case does not matter. |
| `password` | Yes | Compared against the stored hash. |
| `org` | No | An organization slug to scope the session to. Membership is required or the request is refused. |

<Info>
Omit `org` entirely unless you are deliberately scoping the session. Sending `org: null` is different from omitting it, and the distinction matters most on refresh — see [Tokens and sessions](/auth/tokens-and-sessions).
</Info>

Both `email` and `password` are required at the request level, and omitting either is a 400 before any lookup happens. Beyond that, the checks below decide the outcome.

### The order the checks run in

The sequence matters as much as the checks themselves, because it determines what a caller can learn. Reading it top to bottom also explains why some errors are distinguishable and others are not.

| Order | Check | Failure | Counter affected? |
| --- | --- | --- | --- |
| 1 | Both fields present | 400, `email and password are required` | No |
| 2 | Email normalises | 422, `a valid email address is required` | No |
| 3 | An account exists here | 400, the generic refusal. Logged as `unknown email` | No — there is no account to count against |
| 4 | Not locked | 429, too many failed attempts. Logged as `locked` | No — the lock is already applied |
| 5 | Password matches | 400, the generic refusal. Logged as `wrong password` | **Yes** |
| 6 | Account not disabled | 403, `this account is disabled`. Logged as `disabled` | No |
| 7 | Email verified, if required | 403, confirm your email first | No |
| 8 | MFA enrolled, if enabled | *Not a failure.* Returns a challenge | Resets on success |
| 9 | Session starts | — | **Reset** |

Two things fall out of this that are worth stating plainly.

**The counter only moves on a wrong password.** An unknown email, a locked account, a disabled account, and an unverified address all leave `failed_logins` alone. That is the sensible design: there is nothing to count against in the unknown-email case, and the others are not credential guesses at all.

**An unknown email and a wrong password are indistinguishable to the caller.** Both are a 400 with the same message. Only the event log separates them, and the event log is for operators.

### The complete request

For reference, the whole thing in one place:

```bash
curl -X POST https://api.example.com/auth/v1/token \
  -H "apikey: pk_live_..." \
  -H "content-type: application/json" \
  -d '{
        "grant_type": "password",
        "email": "ada@example.com",
        "password": "correct horse battery staple"
      }'
```

No project or environment is in the body or the path — the key determines both, and the user is looked up inside that environment only. That is the tenancy rule made concrete at the HTTP level.

### What a password sign-in returns

On success you get the standard token response — `access_token`, `refresh_token`, `token_type`, `expires_in`, `expires_at`, `session_id`, `org`, `org_role`, and the user. It is byte-for-byte the same shape a magic link produces and the same shape a refresh produces, which is the whole point: your client has one place that handles "signed in".

Two fields come from the environment rather than the credential. `expires_in` and `expires_at` reflect `access_ttl` as read at this moment, so two clients signing in either side of a configuration change can see different values.

A successful sign-in also does three things behind the scenes that are worth knowing because they are visible in Studio:

- Resets the failure counter and clears any lock.
- Records `last_login` and the address the sign-in came from.
- Writes a `sign_in` row to the event log and emits a `user.signed_in` event.

<Note>
`session_id` is the token family hex, not a database id. If you show users a list of their sessions and want to revoke one, that value is what you revoke against. See [Tokens and sessions](/auth/tokens-and-sessions).
</Note>

### When sign-in returns a challenge instead

If the user has MFA enrolled *and* the environment allows it, a correct password does not produce tokens. It produces a challenge:

```json
{
  "mfa_required": true,
  "mfa_token": "...",
  "factors": ["totp", "recovery_code"]
}
```

Both conditions must hold — an enrolled user in an environment with `mfa_enabled` off signs in normally. Note the response carries no access token, which makes this the third "not quite signed in" state alongside pending verification and pending account creation.

Complete it by posting the `mfa_token` and the user's code with `grant_type` set to `mfa`. The resulting session is `aal2`.

<Warning>
An `mfa_token` authorises nothing. It cannot be attached to resource requests, and treating it as an access token produces a confusing 401 rather than an obvious failure. See [MFA](/auth/mfa).
</Warning>

## The password policy

Two settings decide what a password may be: `password_policy`, which chooses between a length rule and the full validator, and `password_min_length`, which supplies the floor. Both live in the environment's `auth` block, both default to the permissive end, and both are edited in Studio under **Configuration** → **Passwords**, where the control is labelled **Policy** with a **Basic** / **Strict** segmented choice and a **Minimum length** field hinted *"Characters."*

The choice is not cosmetic. `basic` and `strict` are genuinely different validators, and a password accepted under one can be rejected under the other.

| `password_policy` | What it enforces |
| --- | --- |
| `basic` (default) | The length rule only. Nothing else. |
| `strict` | The full validator, with `password_min_length` as its floor. |

<Warning>
Switching from `basic` to `strict` affects **new** passwords only. Existing hashes are not re-validated, so every current user keeps their old password until they change it. If you are hardening a live system, plan for that: use [Password recovery](/auth/password-recovery) to force resets, or accept that the policy applies going forward.
</Warning>

### Under `basic`

`basic` checks one thing: length. Shorter than `password_min_length` and you get a single problem naming the required length. Eight characters is the default, which under `basic` genuinely means "any eight characters" — `aaaaaaaa` satisfies it.

That is the default because the environment ships permissive and expects you to tighten it. For an internal tool on a development environment it is fine. For anything holding real user data it is not, and the fix is switching **Policy** to **Strict** rather than merely raising the minimum length.

<Info>
The reserved `_platform` environment is the exception: its operator accounts are held to `strict` with a ten-character minimum regardless of what your environments say. Operators get the strong default out of the box; your users do not.
</Info>

### Under `strict`

`strict` runs the full validator, with `password_min_length` as its floor. This is the same validator the platform uses for its own operator accounts, so it is the setting to choose for a production environment holding real accounts.

The validator is a strength check rather than a composition rule. It assesses the submitted password and reports every weakness it finds, which is why the response body is a list.

<Warning>
Do not assume `strict` requires a symbol, a digit, and an uppercase letter. It is a strength assessment, and a long passphrase can pass while a short mangled word cannot. If you need to *know* your users are satisfying a specific composition rule, this is not the mechanism that enforces it — the validator will not be checking for the characters you had in mind.
</Warning>

### The one rule that applies under both

Independently of the policy, a password over **1024 characters** is rejected with the problem `Password is too long.` This is appended to the problem list rather than replacing it, so an over-long password under `strict` can report several problems at once.

The ceiling exists because the hash is deliberately slow, and an unbounded input multiplied by a deliberately expensive hash is an easy denial-of-service against your own sign-in endpoint. The rate limit helps, but the ceiling is the direct answer.

<Note>
Because the ceiling is checked with `len()` rather than in bytes, "characters" means characters. A password made entirely of astral-plane emoji can be 1024 characters and several thousand bytes, and still pass the check.
</Note>

### `password_min_length`

The floor, defaulting to eight characters. It is the only thing `basic` checks, and the floor the full validator also respects.

In Studio the **Minimum length** field accepts values from 6 to 128 and is hinted *"Characters."* Values outside that range are clamped by the control rather than rejected.

<Warning>
Raising the minimum does not affect existing passwords. An account created when the minimum was eight keeps its eight-character password indefinitely, and no sign-in will fail because of a change you made afterwards. The policy is enforced at the moment a password is *set*, not at the moment it is *used*.
</Warning>

That property cuts both ways. It means a policy change is safe to deploy, and it means a policy change is not a way to force everyone to upgrade. If you need that, use recovery to expire their sessions and require a reset.

### How a policy failure is reported

A rejected password produces a 422 whose body is a **list of problems**, not a single string. This is the single most useful thing to get right in your sign-up and password-change forms, because under `strict` a user will routinely have several weaknesses at once.

```json
{
  "message": "the password does not meet the policy",
  "problems": [
    "Password must be at least 12 characters.",
    "Password is too long."
  ]
}
```

The `message` is a fixed string. The `problems` array is what you render, one line each.

<Warning>
A client that shows only `message` tells a user "the password does not meet the policy" and nothing else — while the server has told you precisely what is wrong. That is the whole payload being thrown away. Render every entry in `problems`.
</Warning>

| Situation | What `problems` contains |
| --- | --- |
| Too short under `basic` | One entry, naming the required length. |
| Too short under `strict` | The length problem, plus anything the validator found. |
| Over 1024 characters | `Password is too long.` |
| Over 1024 characters *and* too weak | Both, together. |

The length problem's wording depends on which validator ran: under `basic` it is generated from the configured minimum, and under `strict` it comes from the validator with the same minimum passed in. The text is not a stable API to match on — render the string you were given.

### Reading the policy in your client

`GET /auth/v1/settings` reports the configured policy so your form can match the server rather than guess at it:

```json
{
  "password_policy": { "kind": "strict", "min_length": 12 }
}
```

Use it to set your input's `minlength` and to word the hint. Do not use it as the validation itself — the server is the authority, and a client-only check will always be a slightly stale approximation of a policy that can change under you at any moment.

<Info>
Reading `settings` also means your form adapts automatically when an operator tightens the policy. Without it, you are hardcoding a minimum that was correct on the day you wrote the form and quietly wrong ever since, in a way that shows up as support complaints rather than as an error.
</Info>

| Reading | Do this |
| --- | --- |
| `kind` | Word your hint accordingly. Under `basic` promise length only; do not promise strength. |
| `min_length` | Set the input's `minlength` and say so in the label. |
| Either | Still handle the 422. The server can reject what the client accepted. |

## How passwords are stored

Passwords are hashed with `passlib`, using bcrypt by default and falling back to `pbkdf2_sha256`. The stored value is a hash, never the password, and there is no path that returns one — not through an API, not through Studio, not through a user view.

The choice of a deliberately slow hash is the whole defence against an offline attack on a leaked database. Hashing that is fast enough to be convenient for the server makes cracking a stolen hash file cheap for an attacker. bcrypt's cost is paid on every sign-in, which is exactly the trade you want: negligible for a legitimate user, expensive for someone grinding through a dump.

<Warning>
Do not claim a specific cost factor. The configuration is whatever the hash implementation reports, and a document that names a number ages into being wrong. What matters is that the hash is deliberately expensive and salted.
</Warning>

The fallback to `pbkdf2_sha256` exists for environments where bcrypt is unavailable. Both are salted, so identical passwords produce different hashes across accounts — which means you cannot tell from the database whether two users chose the same password, and should not try to build a feature that does.

<Info>
Salting is why the derived username is not derived from the password, and why nothing in the system can tell you that two accounts share a credential. If your threat model needs to detect password reuse across accounts, this design does not give you that, and building it yourself would mean handling plaintext you should not have.
</Info>

### What the user view shows, and what it withholds

A user record looks similar whether you fetch it as yourself or as an operator, and the difference is deliberate. The operator view adds administrative fields; neither view includes the hash.

The fields every view includes:

| Field | Notes |
| --- | --- |
| `id` | A ULID. This is the identity policies compare against. |
| `email` | Always normalised lowercase. |
| `username` | Derived or supplied. |
| `name` | Free text. |
| `avatar_url` | Optional. |
| `email_verified`, `email_verified_at` | Both, so you can render a badge from one. |
| `user_metadata` | User-editable. Do not trust it in a policy. |
| `app_metadata` | Admin-controlled. Safe to trust. |
| `roles` | Role names, environment prefix already stripped. |
| `mfa_enabled` | Whether any factor is confirmed. |
| `identities` | Each provider identity with its email and last sign-in. |
| `created_at`, `last_sign_in_at` | Timestamps. |

The operator view adds:

| Field | Notes |
| --- | --- |
| `disabled`, `disabled_at` | The account's state. |
| `locked_until` | When any lock expires. `null` when not locked. |
| `last_sign_in_ip` | The address of the last successful sign-in. |
| `has_password` | Whether a usable password exists. This is how you spot an OAuth-only account. |
| `permissions` | The effective permission set, resolved from roles and direct grants. |

<Warning>
`has_password` is the field to check before sending someone to a password login screen. An OAuth-only account will fail password sign-in every time with the generic refusal, and the user will think their password is wrong rather than that they never had one. Offer them a magic link or a provider instead.
</Warning>

The `identities` array is also what you need to explain "I use Google but it created a second account" — it shows which providers are actually attached.

### Why unusable rather than empty

The distinction is small and worth being precise about, because "no password" has two possible implementations and only one of them is safe.

An **unusable** password is a sentinel meaning "there is no credential here". It cannot be matched by any input, including an empty submission. An **empty** password is a credential whose value is the empty string, and a request submitting an empty password would match it.

Which is why an account created without a password through Studio, or through a provider, or through a magic link, cannot be signed into with a blank password field. The request looks like a submission of `""`, and the stored value matches nothing.

<Warning>
An operator-created account with no password is therefore a genuinely safe provisioning step. There is no window in which it can be signed into, by anyone, including the operator who created it. The user sets a password through a recovery link, which also confirms they control the address.
</Warning>

Setting a password on such an account works from either side: the user through a recovery link, or an operator through Studio's **Set password** action. Both go through the same policy check, so neither can install a password the environment would have rejected.

## When the account has no username worth keeping

The derivation produces values that are unique but not chosen, and there are three situations where that becomes awkward rather than merely ugly.

**A display name is not an identifier.** Because the name feeds the derivation, two people called "Alex Chen" both want `alexchen`, and the second gets a random suffix. Nothing in the username carries the original intent, so do not use it as a display value — use `name`, which is preserved exactly as entered.

**Stripping is lossy.** Anything outside `a-z`, `0-9`, `_`, `.` and `-` is removed before truncation, so international names lose most of their characters. `Zoë Ðağ` becomes `z`. The `name` field still holds the original; only the username is affected.

**Truncation can collide more than you expect.** Two long names sharing a forty-character prefix both truncate to the same value, and the second gets a suffix. Not a bug, but it explains the suffixes you will see on accounts created by a bulk import of a real user list.

| If you need | Use |
| --- | --- |
| A stable external identifier | The user's ULID, from `id`. |
| A human-readable handle | `username`, accepting that it is derived. |
| A person's actual name | `name`. |
| A verified contact address | `email`, plus `email_verified`. |

<Note>
The only way to influence the derivation is to supply a name or an explicit username at creation. Both are one-shot: there is no route to change a username later, so a value derived from a temporary name — a placeholder like "test" — stays with the account for good. Choose real names at import time.
</Note>

## Lockout

Repeated wrong passwords eventually stop being accepted, and the mechanism is deliberately simple. A counter on the user increments on each wrong password; when it reaches the threshold, the account is locked for a fixed duration **and the counter resets to zero**.

| Setting | Default | Scope |
| --- | --- | --- |
| `lockout_threshold` | 10 | Failed sign-ins before the account locks. |
| `lockout_minutes` | 15 | How long the lock lasts. |

An account is locked exactly when `locked_until` is set and in the future. A stale value in the past is simply ignored — there is no separate flag to clear, and no background job expiring locks.

<Warning>
These are Akountz **installation** settings, not per-environment auth configuration. You will not find `lockout_threshold` next to `password_min_length` in the `auth` block, and you cannot give one environment a stricter policy than another. The lockout policy is global to the installation while the counters it acts on are per environment.
</Warning>

### Why the counter resets on lock

The reset is the part that looks like a bug and is not. If the counter were left at the threshold, the account would lock again the moment the lock expired — and stay locked, indefinitely, for a user who cannot remember their password. That is a denial-of-service anyone can trigger against any known account.

Resetting means an attacker gets a fresh window every threshold attempts, which bounds the damage while never permanently locking a legitimate user out. The cost is that lockout slows guessing rather than stopping it; it is one layer alongside the rate limit, not a replacement for it.

<Info>
Because the counter resets, a user who is genuinely struggling — a typo repeated eleven times — recovers after fifteen minutes without intervention. That is the intended outcome.
</Info>

### What the client sees, and what it should say

A locked account produces a 429 with a message about too many failed attempts. It is the only sign-in failure that is unambiguously distinguishable — and it is distinguishable because at that point the user has already proven the address is theirs.

The message should tell the user to wait. The common mistake is rendering a 429 as a generic error, which leaves people retrying and locking themselves out repeatedly, resetting the window each time.

| Failure | Status | What to show the user |
| --- | --- | --- |
| Unknown email, or wrong password | 400 | One message covering both. Do not distinguish them. |
| Locked | 429 | Wait, and roughly how long. |
| Disabled | 403 | The account is not available. Offer support or an alternative method. |
| Unverified | 403 | Instructions for confirming the address. |
| MFA required | 200 | The code field. |

<Warning>
Never render the 429 as a retryable error with an automatic retry. Because the counter resets on lock, an automatic retry loop keeps the user in a state where every attempt is refused — and if the client is retrying hard enough it will also be consuming the shared rate-limit allowance that legitimate users need.
</Warning>

### MFA failures feed the same counter

A wrong MFA code increments the same failure counter and records a `wrong code` event. There is no separate MFA lockout and no separate threshold.

That is a deliberate simplification: one counter, one lock, one place to look when an account stops working. The consequence is that a user who is enrolled in MFA and struggling with their authenticator can lock themselves out of password sign-in too, since the challenge is only issued after the password has already been accepted.

<Note>
A successful sign-in — including a completed MFA challenge — resets the counter. So an enrolled user who fumbles their code once and then succeeds has that attempt forgotten.
</Note>

### Clearing a lock early

An operator can clear a lock without waiting. The admin route that updates a user handles unlocking as part of its update, and in Studio the same action is available on the user's record.

Clearing the lock resets the counter as well, so the user gets a full threshold of attempts again. That is the right behaviour when an operator has verified the person is who they claim to be — the lock was a speed bump against guessing, and it has served its purpose.

<Note>
Clearing a lock does not clear a disabled account. Those are independent states, and a user who is both locked and disabled needs both addressed. The State badges in Studio's user list show `disabled` and the operator view's `locked_until` shows the lock separately for exactly this reason.
</Note>

### The rate limit sits alongside all of this

Lockout is per account. The rate limit is per client, and the two answer different attacks:

| Control | Scope | Stops |
| --- | --- | --- |
| Rate limit, `akz:auth` | Per client. Thirty requests a minute, shared between sign-up and sign-in. | Distributed guessing across many accounts, and enumeration. |
| Account lockout | Per account. Ten failures, then fifteen minutes. | Repeated guessing at one account. |

Both are needed. The lockout alone does nothing to an attacker spraying one common password across ten thousand addresses; the rate limit alone lets an attacker keep grinding at a single account indefinitely.

The counters live in Redis when a Redis URL is configured. Without one they fall back to per-process counters, so with more than one instance the effective global limit is multiplied by the instance count. See [Rate limits and CORS](/operate/rate-limits-and-cors).

### One bucket for sign-up and sign-in

The `akz:auth` namespace covers `POST /auth/v1/signup` and `POST /auth/v1/token` together, at thirty requests per sixty seconds. They share the allowance rather than each having their own, which has one consequence worth planning for: a launch-day traffic spike full of sign-ups will consume the budget that sign-ins need.

The MFA endpoints have their own, tighter namespace — `akz:mfa`, ten per sixty seconds — because guessing a short code is cheap per attempt and a human has no trouble typing ten a minute.

<Warning>
The shared bucket is the reason "sign-in started returning 429s right after we ran a migration that created accounts" happens. Creating accounts through the sign-up endpoint spends the same allowance your users need to sign in. Bulk-provision through the admin routes instead, which are not under this limit.
</Warning>

## Changing a password

A signed-in user changes their own password through `PATCH /auth/v1/user`. The interesting part is that `current_password` is required only in one case.

| Situation | Is `current_password` required? |
| --- | --- |
| The account has a usable password | **Yes.** Omitting it or getting it wrong is a 400. |
| The account has no usable password | No. There is nothing to check against. |

That second row is the OAuth-only and operator-created case. The user setting their first password does not need to prove they know one, because they never had one. The rule is derived from the account's state rather than being asked for explicitly.

```bash
curl -X PATCH https://api.example.com/auth/v1/user \
  -H "apikey: pk_live_..." \
  -H "Authorization: Bearer eyJhbGciOi..." \
  -H "content-type: application/json" \
  -d '{"password":"a much better passphrase"}'
```

The response is the updated user plus a `changed` array naming what moved, which makes it easy to confirm what actually took effect:

```json
{
  "id": "01J8Z...",
  "email": "ada@example.com",
  "changed": ["password"]
}
```

<ResponseField name="400">`current_password` was wrong, or was required and absent.</ResponseField>
<ResponseField name="422">The new password does not meet the policy, with a `problems` list.</ResponseField>

<Warning>
Changing a password does **not** end the user's other sessions. The session that made the change keeps working, and so does every other one the user holds. If your product promises "changing your password signs you out everywhere", you have to revoke the sessions yourself after the update.
</Warning>

A password change emits a `user.password_changed` event, and a `user.updated` event listing the changed fields. See [Events](/events/overview).

### Setting one without the old

The same endpoint works for an account with no usable password, and it is also what the admin route uses when an operator sets one. In that path no `current_password` is checked at all, because an operator is not the user and does not know it.

The policy check applies identically. There is no route that installs a password the environment's policy would have rejected — not through Studio's **Set password**, not through the admin route, not through recovery.

<Warning>
Because an operator can set any user's password, operator access to an environment is equivalent to the ability to impersonate any account in it. That is a property of the design, not a flaw to work around, but it belongs in your threat model: Studio operator credentials deserve the same care as production database credentials.
</Warning>

### Updating the rest of the profile

The same `PATCH /auth/v1/user` route updates the profile, and the field names are worth knowing because two of them behave in ways that are not obvious from their names.

| Field | Behaviour |
| --- | --- |
| `name` | Replaced. |
| `avatar_url` | Replaced. |
| `data` | **Merged** into `user_metadata`, not replaced. Keys you omit are preserved. |
| `password` | As above, with `current_password`. |
| `current_password` | Checked only when the account has a usable password. |
| `email` | Special. See below. |

<Info>
`data` merging rather than replacing is a deliberate difference from the other fields, and it is easy to get backwards in a client. Sending `{"data": {"theme": "dark"}}` updates the theme and leaves every other key alone. If you meant to clear the metadata, this route will not do it.
</Info>

The response lists what actually changed, which is the reliable way to confirm a merge worked:

```json
{ "changed": ["name", "user_metadata"] }
```

### Changing the email address is deferred

`email` is the odd one out. It does not take effect immediately — a new address has to be confirmed first.

The old address stays in place until the new one is confirmed. The new address is sent a confirmation link with a one-day lifetime, and it only replaces the old one when that link is used. In the meantime the change is reported as pending:

```json
{ "changed": ["email (pending confirmation)"] }
```

If somebody never clicks that link, nothing changes and the old address remains. That is the desired behaviour — it means a hijacked session cannot quietly move an account to an address the attacker controls.

| Failure | Status |
| --- | --- |
| The new address is already in use in this environment | 409 |
| The new address is not a valid address | 422 |

<Warning>
The 409 here does leak that the address is registered, unlike sign-in's generic refusal. That is unavoidable — you cannot move to an address that is taken — but it means the email-change form should avoid gratuitous attempts and expect that boundary to exist.
</Warning>

## When password sign-in is the wrong screen

Knowing when *not* to show a password form saves more support burden than any policy tweak.

| The user | What they actually need |
| --- | --- |
| Signed up through a provider | A provider button, or a magic link. Their account has no usable password. |
| Created by an operator with the password left blank | A recovery link, so they can set one. |
| Signed in through a magic link only | The same. |
| Has lost their password | The recovery flow, not the sign-in form. |
| Is locked | A wait, then the sign-in form again. |
| Is unverified | Confirmation instructions, not another password attempt. |
| Is disabled | Nothing helps until an operator re-enables the account. |

Check `has_password` in the operator view before assuming a user has a credential. It is the field that answers the question directly.

<Warning>
The most common support ticket in a provider-enabled product is "my password does not work" from someone who signed up with Google and never had a password. Every one of those attempts is a guaranteed failure with a message that says the email or password is invalid — which reads as "I typed it wrong", not "this method is not available to you". Offering a magic link alongside the form removes the dead end.
</Warning>

### `user_metadata` and `app_metadata`

Both reach the token, and only one of them is safe to authorise on. The distinction is the most security-relevant thing about profile updates.

| | `user_metadata` | `app_metadata` |
| --- | --- | --- |
| Set by | The user, through `PATCH /auth/v1/user` and at sign-up | An operator, through the admin routes |
| Reaches the token as | `meta` | `app` |
| A policy may trust it? | **No.** The user can write it. | Yes. Only admins can change it. |

<Warning>
The field name does not signal the trust level, which is the trap. `meta` looks like internal data and is entirely user-controlled. Anything a policy uses to make an access decision must come from `app`, from a role, from a permission, or from a field on the resource itself — never from `meta`.
</Warning>

This is also why the `data` field at sign-up carries the same warning. Handing a client `user_metadata` and then branching on it in a policy is handing the user the policy.

### The MFA interruption, in detail

It is worth being precise about where the challenge sits in the sequence, because it determines what your client has to preserve.

By the time the challenge is issued, everything has already succeeded: the account exists in this environment, it is not locked, the password is correct, it is not disabled, and the email is verified if required. The password is proven. What is missing is the second factor.

```json
{
  "mfa_required": true,
  "mfa_token": "...",
  "factors": ["totp", "recovery_code"]
}
```

| Field | Notes |
| --- | --- |
| `mfa_required` | The flag your client branches on. |
| `mfa_token` | Identifies the pending challenge. A one-time token with a five-minute lifetime. |
| `factors` | Which kinds of code to accept. Always these two. |

The challenge token also carries the original method and organization, so completing it produces a session equivalent to the one that was interrupted rather than a generic one.

<Warning>
Do not discard the `mfa_token` while the user is typing their code. It has a five-minute lifetime and is single-use, and a user who mistypes a six-digit code three times may need a fresh sign-in if the token expires in between.
</Warning>

| Failure | Status | Cause |
| --- | --- | --- |
| Missing `mfa_token` or `code` | 400 | The request is incomplete. |
| The challenge is expired, used, or unknown | 400 | Start the sign-in again. |
| The code is wrong | 400 | Increments the failure counter. |

The account-disabled check happens again at completion, so an account disabled between the challenge and the code is refused with the challenge no longer being valid.

### Sign-up when verification is required

The account is created, its default roles are assigned, and **no session is issued**. A verification link goes out with a twenty-four-hour lifetime, and the response tells you so.

This is the one case where a successful sign-up produces no tokens at all. Your client has to handle it as a success — it is a success — while having nothing to store.

```json
{
  "user": { "id": "01J8Z...", "email": "ada@example.com", "email_verified": false },
  "session": null,
  "verification_required": true
}
```

<Warning>
The most common sign-up bug in a client is treating the absence of `access_token` as a failure. A new user is told their registration did not work, tries again, and gets a 409 because the account now exists — a confusing dead end caused entirely by misreading a success.
</Warning>

| `signup_enabled` | `require_email_verification` | Result |
| --- | --- | --- |
| `true` | `false` | Account created, session issued. |
| `true` | `true` | Account created, no session, verification email sent. |
| `false` | Either | 403. Sign-up is disabled. |

## The full error catalogue

Every failure the password path can produce, with the status and what it actually means. Grouped by where it comes from, because the group tells you where to look.

### Sign-up

| Status | Meaning |
| --- | --- |
| 400 | `redirect_to` is not an allowed URL. |
| 403 | Sign-up is disabled for this environment. |
| 409 | An account with that email already exists here. |
| 409 | The username you supplied is taken. |
| 422 | The email is not a valid address. |
| 422 | The password does not meet the policy. The body has a `problems` list. |
| 429 | The shared `akz:auth` rate limit. |

### Sign-in

| Status | Meaning |
| --- | --- |
| 400 | `email` or `password` missing from the request. |
| 400 | The generic refusal: unknown email, or wrong password. Indistinguishable. |
| 400 | `refresh_token` missing, on a refresh grant. |
| 400 | `mfa_token` or `code` missing, on an MFA grant. |
| 400 | The code was wrong. Increments the counter. |
| 400 | The challenge is expired, used, or unknown. |
| 401 | An invalid, revoked, or consumed refresh token. |
| 401 | The session was revoked. |
| 403 | The account is disabled. |
| 403 | Confirm your email address first. |
| 403 | You are not a member of that organization. |
| 429 | The account is locked, or the shared rate limit. |

### Profile and password

| Status | Meaning |
| --- | --- |
| 400 | `current_password` was wrong, or required and absent. |
| 409 | That email address is already in use here. |
| 422 | The email is not a valid address. |
| 422 | The password does not meet the policy. |
| 401 | Sign in first, or the account is no longer available. |

<Warning>
A 401 on `PATCH /auth/v1/user` does not only mean "no token". If a token is present but the account has since been disabled, you get the same status with a different message. Both mean the same thing to your client: sign the user out.
</Warning>

### Statuses that mean different things on different routes

Three cases where the status alone is misleading, and the message is what disambiguates.

**A 429** is either the shared rate limit or an individual account lockout. The message tells you which: a lockout names too many failed attempts. Your client should treat both as "wait and do not retry immediately", but only a lockout is worth telling the user about — a rate limit is your infrastructure's problem, not theirs.

**A 403** is sign-up disabled, account disabled, email unverified, or not an organization member. Four unrelated conditions sharing a status. The message is the only way to tell them apart, and your client has to read it.

**A 401** is a missing token, an invalid refresh token, a revoked session, or a since-disabled account. Your client should treat every one of them as "this session is over; sign in again", which is convenient because they do not need distinguishing.

| Status | Read the message? | Action |
| --- | --- | --- |
| 400 | Yes, for sign-in. | Show it, except for the generic refusal where you supply your own wording. |
| 401 | No. | Sign out and return to sign-in. |
| 403 | Yes. | It is one of four different situations. |
| 409 | No. | Show a duplicate-account message. |
| 422 | Yes — render `problems`. | Show every entry. |
| 429 | Yes. | Wait. Do not auto-retry. |

### Not distinguishing unknown from wrong

The single most important client behaviour on this page is *not* doing something. A sign-in that returns a 400 must show the same message whether the email is unregistered or the password is wrong.

This is not a convenience or a stylistic choice. The two cases return an identical status and an identical message precisely so the endpoint cannot be used to build a list of who has an account. Any client that inspects the response and words the two differently has undone that, whether it means to or not.

The event log is where the distinction legitimately lives, because it is visible to an operator and not to an attacker. The **Sign-in activity** tab in Studio renders `unknown email` and `wrong password` in the Result column, which is exactly the right place for the knowledge.

<Warning>
Do not add a "no account with this email" fast path, and do not vary the message by timing how long the response took. Both re-open the enumeration hole the uniform refusal exists to close. Your form should show one message for both, and offer the recovery flow — which is itself uniform — as the next step for someone who cannot get in.
</Warning>

| The client shows | The consequence |
| --- | --- |
| "No account with that email." | Anyone can enumerate your user base from the sign-in form. |
| "Wrong password." | Anyone can confirm which addresses are registered. |
| One message for both. | The form gives nothing away. |

### Resetting vs changing

The two paths are easy to confuse and differ in who may invoke them and in what they do afterwards.

| | Change | Reset |
| --- | --- | --- |
| Who | The signed-in user | Anyone with the emailed link |
| Proves identity by | `current_password` | Possession of a valid, unused, unexpired token |
| Link lifetime | — | One hour |
| Ends other sessions | No | Yes |
| Available when disabled | No | No |
| Event | `user.password_changed` | `user.password_reset` |

<Warning>
Because reset revokes every session, a user who triggers it to get back in will find themselves signed out everywhere — including on their phone. That is the correct behaviour after a suspected compromise and an unwelcome surprise after a fat-finger. Say so in the confirmation message.
</Warning>

### Choosing which to offer

Offer the reset link from the sign-in form as the only route when the user cannot remember the password. Do not offer "change password" there — that route requires a session, which is exactly what a locked-out user does not have.

If you want to force every user onto a new password — after tightening the policy, say — recovery is the mechanism, because the policy change alone will not touch existing credentials.

## Passwords and social sign-in together

A user who first signs in through a provider has no password. Offering only a password form to them is a dead end that looks to them like a wrong password.

The path that works is magic link, which needs no stored credential at all. Alternatively, they can set a password through recovery, after which both methods work on the same account.

| The user signed up with | Can they now use a password? |
| --- | --- |
| A provider only | Not until they set one. |
| A magic link only | Not until they set one. |
| A provider and later a password | Yes, and both continue working. |

<Warning>
The same email signing in through two different providers creates two accounts, not one — unless the provider reports the address as verified, in which case they are matched. A user who "already has an account" and is told the email is taken by social sign-in has usually hit this. Linking an identity to an existing account is the fix, and it is an explicit action rather than something that happens automatically. See [Social login](/auth/social-login).
</Warning>

## Creating a user in Studio

The **New user** modal has exactly three fields, and the third one carries the hint that explains the unusable-password behaviour:

| Field | Label | Hint |
| --- | --- | --- |
| 1 | **Email** | — |
| 2 | **Name** | — |
| 3 | **Password** | *"Leave empty to have the user set one through a recovery link."* |

Creating the account reports the toast **User created**. The email is normalised and lowercased exactly as at sign-up, so a mixed-case entry is stored lowercase and will not be found by searching for what you typed.

<Warning>
There is no Username field. The username is derived from the name, or from the email's local part if the name is blank — so a user created with the name "Ada Lovelace" becomes `adalovelace`, not something you chose. If you need a specific username, this modal cannot set it.
</Warning>

The **Password** field is the decision point. Leaving it blank produces an account nobody can sign into yet, which is the right choice for a real user: they set their own password through a recovery link, which also proves they control the address. Filling it in produces an account that can sign in immediately, which is appropriate for a shared kiosk login or a seeded test account in a throwaway environment — and a liability if it is a real person's account, because you now know their password.

| Leaving it blank | Filling it in |
| --- | --- |
| The user chooses their own credential. | You choose the credential. |
| The address gets proven on first use. | Nothing proves the address belongs to them. |
| Cannot be signed into until recovery completes. | Immediately usable. |
| The right default for real users. | For test accounts and kiosks. |

### Finding an account

The search input's placeholder is **"Search email or name"**. Beside it is a status filter with three options: all, disabled, and unverified.

The State badges in the list are the fastest way to diagnose a sign-in problem without opening anything:

| Badge | Meaning |
| --- | --- |
| Green **active** | Not disabled. |
| Red **disabled** | Sign-in is refused with a 403. |
| Yellow **unverified** | Sign-in is refused with a 403 if the environment requires verification. |
| Blue **MFA** | A factor is enrolled, so sign-in will be interrupted by a challenge. |

The **unverified** filter is the direct answer to "why can't these people sign in", and the blue **MFA** badge is the direct answer to "why does my form skip the token step".

<Note>
A locked account carries no badge. The lock is not part of the state group — it lives in the operator view's `locked_until` field, visible once you open the user. If someone reports being locked out and the row looks fine in the list, that field is where the answer is.
</Note>

Search is by email or name only. There is no search by username and no search by user id, which means finding a user whose email you no longer have requires the id from a backup, an event payload, or an export.

### The buttons on a user

The modal is titled with the user's email, so you can see at a glance whose account you are in. The action row reports a different toast from its label in several cases, which is worth knowing before you conclude an action did nothing.

| Button | Toast | Effect |
| --- | --- | --- |
| **Disable** | **Disabled** | Refuses further sign-in. |
| **Enable** | **Enabled** | Lifts that refusal. |
| **Mark verified** | **Marked verified** | Confirms the address without sending anything. Shown only when unverified. |
| **Sign out everywhere** | **Signed out everywhere** | Revokes every session. |
| **Reset MFA** | **MFA reset** | Deletes factors *and* recovery codes. Shown only when MFA is on. |
| **Set password** | **Password set** | Prompts and sets one. |
| **Delete** | **Deleted** | Removes the account, after a confirmation naming the user. |

<Warning>
**Disable** stops sign-in but does not end existing sessions. An access token the user already holds keeps working until it expires, and their refreshes stop producing new ones. For a compromised account, use **Sign out everywhere** as well — and understand that neither reaches a token already in flight.
</Warning>

**Mark verified** skips the proof of address ownership entirely. It is right for a seeded test account and wrong for a real user, because it means nobody has demonstrated that the address belongs to the person using it.

**Reset MFA** is heavier than it looks: it removes the authenticator factors *and* invalidates every recovery code. A user who was relying on a recovery code as their backup has just lost that too. Warn them rather than doing it silently.

### Setting a password as an operator

**Set password** opens a plain prompt and applies the value on submit, reporting **Password set**.

Two properties follow from how it works. First, no `current_password` is involved — an operator is not the user and does not know it. Second, the environment's policy is still enforced, so an operator cannot install a password the environment would have rejected.

<Warning>
Because an operator can set any user's password, access to an environment's users is equivalent to the ability to impersonate any account in it. That is inherent to the design rather than a flaw, but it belongs in your threat model: Studio operator credentials deserve the same handling as production database credentials, and an operator's actions in an environment are attributable to them in the event log.
</Warning>

Because the prompt is a browser `prompt()` rather than a form field, the value is not masked on screen. That is a deliberate simplicity in the tool, and it means an operator setting a password over someone's shoulder is exposing it visually. For the same reason, prefer leaving the field blank at creation and letting the user choose.

See [Managing users](/auth/managing-users) for the admin routes behind these buttons.

## The policy in Studio

The **Configuration** tab's **Passwords** section is described as *"Password strength and how long sessions last."* It holds four controls, and they map one-to-one onto the config keys:

| Studio control | Config key | Default |
| --- | --- | --- |
| **Policy**, segmented **Basic** / **Strict** | `password_policy` | Basic |
| **Minimum length**, hint *"Characters."* | `password_min_length` | 8 |
| **Access token lifetime**, hint *"Seconds. How long a bearer token works before it needs refreshing."* | `access_ttl` | 900 |
| **Refresh token lifetime**, hint *"Seconds. How long a signed-out-of-band session stays resumable."* | `refresh_ttl` | 2592000 |

The two lifetime fields sit in the same section as the policy because they share a rationale — how much friction and how much exposure — even though they govern different things.

<Info>
The lifetime hints are unusually explicit, and the access-token one is worth reading twice: a bearer token works until it needs refreshing. That is a direct statement that the token is usable by anyone who obtains it, for its whole lifetime, with no further check.
</Info>

The **Minimum length** control accepts values from 6 to 128. The **Policy** segmented control is a two-way choice, which is the clearest signal in the UI that these are different validators rather than a single dial.

<Warning>
The Save button is disabled until something changes, and saving writes the whole block back. Confirm the environment selector before saving — a policy applied to the wrong environment changes nothing about the environment you are testing, which is exactly what makes it confusing rather than merely annoying.
</Warning>

Remember that changes take up to ten seconds to take effect, because each environment's config is cached.

## What goes wrong, and why

The failures that come up repeatedly, ordered roughly by how often they occur.

### "Sign-in says the email is unknown, but the user exists"

Nearly always the wrong environment. Users are scoped to `project` + `env`, and the lookup filters on both. If the key you are using resolves to a different environment than the one you are inspecting, the account genuinely is not there.

The second cause is case. Emails are lowercased before storage, so searching for `Ada@Example.com` finds nothing when the row holds `ada@example.com`.

The third is a soft-deleted account, which disappears from lookups while its row remains.

### "Sign-in returns a 429 and retrying makes it worse"

Either the shared `akz:auth` rate limit or an individual account lockout. Both mean wait; neither means retry. An automatic retry loop keeps a locked account locked, because each cycle resets the counter at the threshold.

Check the event log: a lockout produces a `locked` row, while a rate limit produces nothing at all because the request never reached the sign-in logic.

### "The user says MFA is on but they never enrolled"

The blue **MFA** badge is per user, and the environment's `mfa_enabled` switch is separate. Both must be on for a challenge. Check the Configuration tab's **Sign-in methods** section — if **MFA (TOTP)** is off, no enrolled user is challenged, and the badge will still be showing.

### "My form shows only the generic message"

Usually one of three things. The client is rendering `message` instead of the `problems` list on a 422. The client is treating a missing `access_token` as a failure and swallowing the verification-required or MFA-challenge state. Or the client is branching on the 400 to distinguish an unknown email from a wrong password, which it should not do.

### "Changing the minimum length did nothing"

Two possibilities, and they are worth separating. If existing passwords are shorter than the new minimum, that is expected — the policy applies when a password is *set*, not when it is *used*. If even *new* passwords are being accepted below the minimum, the change has not reached Akountz yet, which takes up to ten seconds. Or you saved to a different environment.

### "The user is disabled but sign-in still works"

It is not, if you are testing properly. Sign-in is refused with a 403 and a `disabled` event row. What still works is any resource request using an access token they already hold, which lasts out its remaining lifetime. To end that, revoke the sessions too.

## Reading the event log

Every attempt writes a row, and the reason strings are short, stable, and specific enough to be worth recognising. This is the vocabulary of the Result column in Studio's **Sign-in activity** tab.

| Reason | Kind | What happened |
| --- | --- | --- |
| `unknown email` | `sign_in` | No account with that normalised email in this environment. |
| `wrong password` | `sign_in` | The account exists; the password did not match. The counter incremented. |
| `locked` | `sign_in` | The account was locked. No counter change. |
| `disabled` | `sign_in` | The password was correct, but the account is disabled. |
| `wrong code` | `mfa_verify` | The MFA code did not match. The counter incremented. |
| *(no reason)* | `mfa_challenge` | A challenge was issued. A success, with no reason. |
| *(refresh failure text)* | `refresh` | The underlying rotation error, including theft detection. |

<Warning>
A `refresh` row carrying text about possible token theft is not a password problem and will not be fixed by resetting a password. It means a refresh token was presented twice. Find out whether that was an attack or — far more likely — two tabs in the same browser refreshing at the same moment.
</Warning>

### Using it to answer "was this an attack?"

Ticking **failures only** and reading the IP column answers most cases:

| Pattern | Reading |
| --- | --- |
| One IP, one email, many `wrong password` rows | Brute force against one account. The lockout is handling it. |
| Many IPs, many emails, `unknown email` | Credential stuffing. The rate limit is the control. |
| `unknown email` and `wrong password` on the same address | Somebody guessing whether the account exists. Expected noise. |
| One IP, alternating `unknown email` and `wrong password` | A user typing their own address inconsistently, or an attacker probing. |
| `wrong code` repeatedly, one user | MFA fumbling, not an attack. Short codes are not worth attacking at ten a minute. |
| A `refresh` theft row | See above. Usually a client race. |

The recorded address is the first entry in the forwarding header when present, otherwise the socket peer. If every row shows your own proxy's address, the forwarding header is not being set and this table is useless for attribution.

## When the user cannot remember it

Recovery is the counterpart to the password, and it exists because the anti-enumeration guarantee that protects sign-in would make a "reset my password" form useless if it behaved differently.

The flow is deliberately uniform:

| Stage | What happens |
| --- | --- |
| Request | `POST /auth/v1/recover` with the address. The response is identical whether or not an account exists. |
| Link | If an account exists, a link is emailed. One-hour lifetime, single-use. |
| Set | `POST /auth/v1/recover/confirm` with the token and the new password. The policy is checked. |

The uniformity is the whole design. A form that said "we sent you a link" for registered addresses and "no such user" for others would be an enumeration oracle with a worse disguise than sign-in's, because the attacker would not need a password attempt at all.

<Warning>
The one-hour lifetime is short relative to a day. A user who requests a reset at the end of a workday and clicks the next morning will find it invalid, and will request another. There is no way to lengthen it — it is not configurable. If your users are likely to request resets away from their desk, say "the link lasts an hour" in the confirmation message.
</Warning>

| Failure | Status |
| --- | --- |
| The token is expired, used, or unknown | 400, the same message for all three |
| The new password fails the policy | 422, with a `problems` list |

Recovery revokes the account's existing sessions, so a reset genuinely ends whoever was holding them. That is the behaviour you want after a suspected compromise, and it is also why recovery is not a neutral action to suggest casually to a user who "cannot get in" but has not actually forgotten anything.

### Confirming the address

Verification is the gate that makes `require_email_verification` mean something, and its lifetime is generous — a full day — precisely because it blocks sign-in and users do not check their inbox immediately.

| Aspect | Behaviour |
| --- | --- |
| Lifetime | Twenty-four hours. |
| Required? | Only when the environment sets `require_email_verification`. |
| Resend | `POST /auth/v1/verify/request`. |
| Consequence if skipped | Sign-in is refused with a 403 until it is confirmed. |

Once confirmed, the address is marked verified and sign-in proceeds normally. A confirmed address does not end sessions or change anything else.

<Note>
Confirmation is also the mechanism that proves an operator-created account really belongs to the person it was created for. The **Mark verified** button in Studio skips that proof entirely — which is legitimate for a seeded test account and wrong for a real user, because it means nobody has demonstrated they control the address.
</Note>

## The password path and MFA

MFA does not replace the password; it raises the session's assurance level after it. A user with an enrolled factor signs in with their password exactly as before, receives a challenge instead of tokens, and completes it to get an `aal2` session.

Two conditions must both hold for the interruption to happen: the user has a confirmed factor, and the environment's `mfa_enabled` is on. That second half surprises people who expect an enrolled user to always be challenged — turn the environment switch off and every enrolled user signs in at `aal1` regardless.

| User enrolled? | `mfa_enabled` | Result |
| --- | --- | --- |
| No | Either | A normal session at `aal1`. |
| Yes | `true` | A challenge, then an `aal2` session. |
| Yes | `false` | A normal session at `aal1`. |

<Warning>
The environment switch governs enrolment and challenge together. Turning `mfa_enabled` off does not merely stop new enrolment — it also stops challenging users who already enrolled, dropping them to `aal1`. Any policy requiring `aal2` will start denying them.
</Warning>

A session's `aal` is a property of the session, not of the user, and it survives refresh — a refresh reads the existing session's level rather than resetting it to `aal1`. So a user who completed a challenge stays at `aal2` for the life of that session.

See [MFA](/auth/mfa) for enrolment and the challenge in full.

## Building the client

The states a password sign-in screen has to handle, and what each looks like on the wire. This is the practical summary of everything above.

| State | How you detect it | What to render |
| --- | --- | --- |
| Signed in | `access_token` present | The application. |
| Verification pending | `verification_required: true` | "Check your email." Not an error. |
| MFA required | `mfa_required: true` | The code field. Keep the `mfa_token`. |
| Bad credentials | 400 with the generic message | One message covering unknown-email and wrong-password. |
| Locked | 429 naming failed attempts | Wait, with a rough duration. |
| Disabled | 403 | Not available. Offer an alternative route. |
| Unverified | 403 asking for confirmation | "Confirm your email first." |
| Policy failure | 422 with `problems` | Every entry in the list. |

<Warning>
The two "success without tokens" states are the ones that break clients. A branch written as `if (response.access_token) { ... } else { showError() }` reports failure for both, and in the verification case the user then retries and hits a 409 duplicate. Check the specific flags.
</Warning>

### Refreshing afterwards

The access token expires and the refresh token rotates. The client requirements are short and non-negotiable:

```bash
curl -X POST https://api.example.com/auth/v1/token \
  -H "apikey: pk_live_..." \
  -H "content-type: application/json" \
  -d '{"grant_type":"refresh_token","refresh_token":"..."}'
```

- Store the returned refresh token immediately. The one you sent is consumed.
- Send it exactly once. A repeat is treated as theft and kills the family.
- Allow one in-flight refresh. Concurrent refreshes cause exactly that.
- Omit `org` to keep the session's organization. Sending `org: null` removes it.

See [Client integration](/auth/client-integration) for the full pattern and [Tokens and sessions](/auth/tokens-and-sessions) for the rotation reference.

## Metadata and what a policy may trust

The profile route writes to two metadata stores, and the difference between them is the single most security-relevant thing on this page.

| | `user_metadata` | `app_metadata` |
| --- | --- | --- |
| Written by | The user, via `data` | An operator, via the admin routes |
| Merged or replaced | Merged | Replaced |
| Appears in the token as | `meta` | `app` |
| Safe for access decisions | **No** | Yes |

The `data` field at sign-up writes `user_metadata`, so a sign-up form that accepts arbitrary fields from the client is accepting policy input from an untrusted source.

<Warning>
The naming actively misleads here. `meta` sounds internal and is entirely under the user's control; `app` sounds incidental and is the trustworthy one. If a policy branches on `$auth.claims.meta.something`, the user wrote that branch's input.
</Warning>

What a policy *should* authorise on, in rough order of preference: a field on the resource itself, a permission from the verified claim list, a role, or `app_metadata`. See [Auth in policies](/auth/auth-in-policies).

## How this connects to the rest of the system

The credential establishes identity; the claims it produces are what everything else consumes. These are the hand-offs worth being aware of.

| Consumer | What it takes from sign-in |
| --- | --- |
| Resource policies | `user_id`, `roles`, `permissions`, `org`, `org_role`, `aal` from the token. |
| Storage rules | The user id, compared against ownership fields on the object. |
| Realtime channels | The same auth context, evaluated at subscribe time. |
| Events | `user.created`, `user.signed_in`, `user.password_changed`, `user.password_reset`, `user.verified`, and the rest. |

| Producer | What it controls about sign-in |
| --- | --- |
| The environment config | Whether sign-up exists, how strong the password must be, how long tokens last. |
| Studio's Roles tab | What a new account gets through `default_roles`, and what any account can do. |
| The mail service | Whether a confirmation or reset link is deliverable at all. |

<Warning>
A successful sign-in grants nothing on its own. Every operation still needs a policy, and a frontend that hides a button is a usability measure rather than a security one — anyone with the token can call the route directly. See [Policies](/policies/overview).
</Warning>

Roles reach the token at issue time, so a role granted seconds ago is not in the token you are holding. Refresh before asserting new permissions, or you will conclude a role change did not apply.

## Depth, on demand

Four topics that matter to some readers and nobody else. Each is a genuine edge of the design rather than filler.

<AccordionGroup>
  <Accordion title="Why the counter resets on lock, in more detail">
    The failure mode it avoids is a permanent denial of service. If the counter stayed at the threshold, then the instant a lock expired the next attempt would re-apply it — so ten wrong guesses would lock an account forever, and anyone who knew a user's email could do it to them at will.

    Resetting trades that for a bounded attack: an attacker gets a fresh threshold-sized window every cycle instead of being locked out permanently, but a legitimate user recovers on their own after the lock expires. The design optimises for the user being able to get back in, at the cost of not stopping a determined attacker — which the rate limit and monitoring are there to do instead.
  </Accordion>
  <Accordion title="Why an unverified address is refused after the password is checked">
    The order looks odd until you consider what each check leaks. Checking verification before the password would tell anyone that a given address is unverified — which is most registered accounts, and a useful signal before you have any credential at all.

    Checking it after means an unauthenticated caller cannot distinguish "this address needs confirming" from "this password is wrong" without already knowing the password. The cost is that a user with a forgotten password and an unverified address gets the generic message first and the verification prompt only after they fix it. That ordering is the right trade, and it is deliberate.
  </Accordion>
  <Accordion title="Why a failed sign-in records the reason even though the caller is not told it">
    The event log exists for operators investigating a report, and the reason is the single most useful field in it. Without it, "the user says they cannot sign in" gives you nothing beyond a timestamp and an address.

    Storing `unknown email` versus `wrong password` is what lets an operator distinguish a user with a typo from an attacker enumerating, and a support question that took ten minutes from a table that would otherwise have taken an hour. The information stays where it cannot help an attacker.
  </Accordion>
  <Accordion title="Why the policy is checked at set time rather than at use time">
    Validating on every sign-in would mean re-running the validator against a value you no longer have — the hash is one-way. The only way to check a password against a policy is to have the plaintext in hand, and the only moments you have it are sign-up, change, and reset.

    That is why the policy is a property of when a password was chosen rather than a filter applied continuously. It also means the policy can be tightened at any time without invalidating anything, and that no amount of tightening reaches users who never change theirs.
  </Accordion>
</AccordionGroup>

## The account lifecycle, one environment at a time

Following a single person through one environment makes the settings' effects concrete. The sequence is identical everywhere; only the configuration differs.

**A visitor reads the settings.** Sign-up on, verification off, magic links on, MFA on, one provider, `basic` at eight characters. The client renders a registration form, a password form, a magic-link option, and one provider button — all from that response rather than from hardcoded assumptions.

**They register.** The account is written, `customer` arrives from `default_roles`, and because verification is off the response is a full session. Their token already carries the role, so the first request is authorised correctly.

**They use the product.** Policies compare `user_id`, `roles`, and `permissions` from the token. Nothing queries the identity service per request.

**Somebody grants them `editor`.** Their existing token is unchanged. The next refresh picks up both roles. This is the staleness window, bounded by `access_ttl`.

**They enrol an authenticator.** Permitted, because `mfa_enabled` is on. The blue **MFA** badge appears in Studio.

**They sign in on a laptop.** The password is right, the enrolment means a challenge rather than tokens, and completing it yields an `aal2` session. The failure counter resets on success.

**They forget the password.** The request returns the same response as it would for an unregistered address. The link lives an hour. The new password passes the policy, and every session they had ends — phone included.

**They change their email.** The old address stays for a day, until the new one is confirmed.

**Their colleague disables the account** after they leave. Sign-in stops immediately. An access token already issued keeps working until it expires — which is what `access_ttl` bounds.

| Setting changed at this point | Who is affected | Who is not |
| --- | --- | --- |
| `signup_enabled` off | Prospective users | Existing accounts |
| `require_email_verification` on | Users with unconfirmed addresses | Confirmed accounts |
| `password_policy` to `strict` | Anyone setting a password | Everyone else |
| `password_min_length` raised | New passwords only | Existing credentials |
| `mfa_enabled` off | Enrolled users, at next sign-in | Unenrolled users |
| `site_url` changed | Future redirects only | Links already emailed |
| `access_ttl` lowered | Tokens issued after the change | Tokens already issued |

That last column is the recurring theme of this page: configuration changes what happens next, not what is already true.

## What to take away

Six things, and they cover the failures you will actually meet.

**Emails are lowercased.** Store and search on the normalised value, or you will look for an account that exists under a spelling you did not type.

**An account can have no password.** Provider and magic-link sign-ups, and operator-created users with the password left blank, all have an unusable password. They cannot sign in with a password at all, and `has_password` in the operator view tells you which.

**The policy is enforced when a password is set, not when it is used.** Changing `password_min_length` or switching to `strict` does nothing to existing credentials. If you need to force a change, use recovery.

**A policy failure is a list.** Render every entry in `problems`. Showing only `message` throws away the entire payload.

**Lockout resets its counter.** A user locked out recovers after the lock expires without intervention, and an automatic retry loop is what prevents them from ever getting there.

**Two successful outcomes have no access token.** Pending verification and an MFA challenge are both successes. A client that treats a missing token as a failure will misreport both.
