Pawabase gives every environment a complete account system: sign-up and sign-in with passwords, magic links, emailed codes, passkeys and social providers; sessions that renew themselves; second factors; roles; and organizations. You use all of it from the SDK. Your users are separate from your team: they belong to the app you are building, not to your Pawabase account.

This page shows how to set up a client, sign someone up and in, and read back who is signed in. It also maps every sign-in method to the page that covers it.

## Set up a client

Install the SDK for your language and create one client for your app. Authentication uses a **publishable key** (`pb_pk_…`), which is safe to ship in a browser or mobile app. A **secret key** (`pb_sk_…`) is for servers only and is what you use to manage other people's accounts; see [Managing users](/auth/managing-users/overview).

<CodeGroup>
```bash TypeScript
npm install @pawabase/client
```

```bash Python
pip install pawabase
```
</CodeGroup>

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";

export const pawabase = createClient({
  url: "https://api.example.com",
  apiKey: "pb_pk_…",
  environment: "production",
});
```

```python Python
from pawabase import Pawabase

pb = Pawabase("https://api.example.com", "pb_pk_…", environment="production")
```
</CodeGroup>

`url` is your project's API address, shown on the project page in the dashboard. `environment` names the environment the app talks to. The key already identifies one, so you can leave it out for most calls, but social sign-in, passkey and token helpers, realtime and the management clients use it, so it is good practice to always set it.

The Python client has an async twin, `AsyncPawabase`, with the same methods returning awaitables. Everything on this page works on both; examples show the blocking client.

<Note>
Accounts are scoped to one environment. The same email address can have a separate account in `staging` and in `production`, with different passwords, roles and sessions. If a user "exists" but sign-in says the email is unknown, you are almost always pointing at the wrong environment.
</Note>

## Sign up, sign in, sign out

<CodeGroup>
```typescript TypeScript
const { session, verificationRequired } = await pawabase.auth.signUp({
  email: "ada@example.com",
  password: "correct horse battery staple",
  name: "Ada Lovelace",
});

const result = await pawabase.auth.signInWithPassword({
  email: "ada@example.com",
  password: "correct horse battery staple",
});

if (result.status === "mfa_required") {
  await result.verify(codeFromAuthenticator);
}

const user = await pawabase.auth.getUser();
await pawabase.auth.signOut();
```

```python Python
outcome = pb.auth.sign_up(
    email="ada@example.com",
    password="correct horse battery staple",
    name="Ada Lovelace",
)
# outcome.session, outcome.verification_required

result = pb.auth.sign_in_with_password(email="ada@example.com", password="correct horse battery staple")

if result.status == "mfa_required":
    result.verify(code_from_authenticator)

user = pb.auth.get_user()
pb.auth.sign_out()
```
</CodeGroup>

That is the whole loop. After a successful sign-in the SDK keeps the session, sends the access token on every request, and renews it before it expires. You do not handle tokens yourself unless you want to; see [Tokens and sessions](/auth/tokens-and-sessions).

The details of each step, including what happens when a project requires email confirmation, are in [Passwords](/auth/passwords).

## Find out what is enabled

Which methods work depends on how the environment is configured. Ask the API instead of hard-coding it, so one build of your app works against every environment:

<CodeGroup>
```typescript TypeScript
const settings = await pawabase.auth.settings();

settings.signup_enabled;
settings.email_verification_required;
settings.magic_link_enabled;
settings.email_code_enabled;
settings.anonymous_enabled;
settings.passkeys_enabled;
settings.mfa_enabled;
settings.providers;                      // ["github", "google"]
settings.password_policy.min_length;     // 8
```

```python Python
settings = pb.auth.settings()

settings["signup_enabled"]
settings["email_verification_required"]
settings["magic_link_enabled"]
settings["email_code_enabled"]
settings["anonymous_enabled"]
settings["passkeys_enabled"]
settings["mfa_enabled"]
settings["providers"]                    # ["github", "google"]
settings["password_policy"]["min_length"]  # 8
```
</CodeGroup>

This call needs only the publishable key, so you can make it before anyone signs in. A provider with no credentials configured is left out of `providers`, so a button you render from this list always works.

| Field | Meaning |
| --- | --- |
| `signup_enabled` | New accounts may be created. When `false`, `signUp` fails with 403. |
| `email_verification_required` | A new account must confirm its email before it can sign in. |
| `magic_link_enabled` | [Magic links](/auth/magic-links/overview) are available. |
| `email_code_enabled` | [Emailed codes](/auth/passkeys-and-codes#emailed-codes) are available. |
| `anonymous_enabled` | [Guest sessions](/auth/passkeys-and-codes#guest-sessions) are available. |
| `passkeys_enabled` | [Passkeys](/auth/passkeys-and-codes#passkeys) are available. |
| `mfa_enabled` | Users may enrol a [second factor](/auth/mfa/overview). |
| `providers` | Social providers with working credentials ([Social login](/auth/social-login/overview)). |
| `password_policy` | The rule a new password must meet: `kind` (`basic` or `strict`) and `min_length`. |

## Settings that need the dashboard

Most of authentication is code. A few switches are project configuration, and you set them once in Studio under **Users & auth** before the matching SDK call will work:

| You want to… | Configure first |
| --- | --- |
| Let people register | Turn on sign-up. |
| Require email confirmation | Turn on email verification, and add your app's address to the allowed redirect URLs. |
| Use magic links, emailed codes, guests or passkeys | Turn the method on. Passkeys also need your site's domain. |
| Offer social sign-in | Add the provider's client id and secret, and allow your redirect URL. |
| Set a stronger password rule | Choose the `strict` policy and a minimum length. |
| Add roles | Create the roles and default roles you want new users to get. |

[Authentication configuration](/auth/configuration/overview) explains each setting and what the SDK sees when it changes. Anything not listed here, you do in code.

## The user

`getUser()` returns the signed-in person, fresh from the server. The same object is cached on the session as `session.user`.

| Field | Type | Notes |
| --- | --- | --- |
| `id` | string | Stable identifier. Use it as the foreign key in your own tables. |
| `email` | string | Lower-cased. `null` for a guest. |
| `username` | string | Optional; derived from the email when you do not set one. |
| `name`, `avatar_url` | string | Profile fields the user can edit. |
| `email_verified`, `email_verified_at` | boolean, time | Whether the address was confirmed. |
| `user_metadata` | object | Profile data the **user** may edit. Never use it for authorization. |
| `app_metadata` | object | Data only your server (a secret key) or Studio can edit. Safe for authorization. |
| `roles` | string[] | Roles granted to the user. |
| `mfa_enabled` | boolean | Whether a second factor is on. |
| `identities` | array | Linked sign-in methods (a password, GitHub, and so on). |
| `created_at`, `last_sign_in_at` | time | |
| `is_anonymous` | boolean | `true` for a guest session. |

`getUser()` also reports `aal` (the assurance level: `aal1` after a password, `aal2` after a second factor) and `session_id` for the current session.

Update the profile with `updateUser`; see [Passwords](/auth/passwords#change-profile-password-or-email).

## The session

A successful sign-in produces a session:

| Field | Notes |
| --- | --- |
| `access_token` | A short-lived signed token (15 minutes by default) sent on every request. |
| `refresh_token` | Used once to get the next pair. The SDK handles it. |
| `expires_in`, `expires_at` | Lifetime in seconds, and the Unix time it ends. |
| `session_id` | Identifies this sign-in; use it to list and revoke sessions. |
| `org`, `org_role` | The organization the token was issued for, and the user's role in it, when the user works inside one. |
| `user` | The user object above. |

## Handle errors

Failures arrive as typed errors in both SDKs, so you branch on the class or the status rather than parsing a message.

| Situation | Status | TypeScript | Python |
| --- | --- | --- | --- |
| Missing or invalid API key | 401 | `AuthenticationError` | `AuthenticationError` |
| Wrong email or password | 400 | `ApiError` (`status === 400`) | `ValidationError` |
| Password too weak, invalid email | 422 | `ValidationError` | `ValidationError` |
| Email already registered | 409 | `ConflictError` | `ConflictError` |
| Sign-up disabled, account disabled, unverified | 403 | `PermissionError` | `ForbiddenError` |
| Too many attempts | 429 | `RateLimitError` | `RateLimitedError` |

<CodeGroup>
```typescript TypeScript
import { ApiError, ConflictError, RateLimitError, ValidationError } from "@pawabase/client";

try {
  await pawabase.auth.signUp({ email, password });
} catch (error) {
  if (error instanceof ConflictError) showMessage("That email already has an account.");
  else if (error instanceof ValidationError) showMessage(error.message);
  else if (error instanceof RateLimitError) showMessage("Please wait a moment and try again.");
  else if (error instanceof ApiError) showMessage(error.message);
  else throw error;
}
```

```python Python
from pawabase import ConflictError, RateLimitedError, ValidationError, PawabaseError

try:
    pb.auth.sign_up(email=email, password=password)
except ConflictError:
    show_message("That email already has an account.")
except ValidationError as error:
    show_message(error.message)
except RateLimitedError:
    show_message("Please wait a moment and try again.")
except PawabaseError as error:
    show_message(error.message)
```
</CodeGroup>

Sign-in deliberately answers the same way for an unknown email and a wrong password (400, "invalid email or password"), so the form cannot be used to find out who has an account. Show one message for both. Every error carries a `requestId` (`request_id` in Python) you can quote to support. The full catalogue is in [Errors](/reference/client-errors).

## Limits to design for

| Limit | Value |
| --- | --- |
| Access token lifetime | 15 minutes |
| Sign-up and sign-in requests per client | 30 per minute, shared |
| Second-factor attempts per client | 10 per minute |
| Failed password attempts before an account locks | 10, then locked for 15 minutes |
| Longest accepted password | 1,024 characters |

A locked account answers 429. Do not retry in a loop: tell the person to wait. See [Passwords](/auth/passwords#lockout-and-rate-limits) for how the two limits differ.

## Security checklist

- Ship only the publishable key in browsers and apps. Keep secret keys on servers.
- Show one message for "wrong email" and "wrong password".
- Treat `user_metadata` as untrusted input. Put anything that grants access in `app_metadata` or in roles.
- Restrict redirect URLs to your own origins; the API refuses any address that is not on the list.
- Choose the `strict` password policy for anything holding real data, and offer a second factor.
- Call `signOut({ scope: "global" })` after a password change if you want other devices signed out.

## A complete sign-in screen

This is the shape most apps end up with: read what the environment offers, try the method the person chose, finish a second factor if one is asked for, and land on one result. It uses only calls covered in this section.

<CodeGroup>
```typescript TypeScript
import { ApiError, PermissionError, RateLimitError, ValidationError } from "@pawabase/client";

type Outcome = { ok: true; user: { id: string; email: string } } | { ok: false; message: string };

export async function signIn(email: string, password: string, askForCode: () => Promise<string>): Promise<Outcome> {
  try {
    let result = await pawabase.auth.signInWithPassword({ email, password });
    if (result.status === "mfa_required") {
      const session = await result.verify(await askForCode());
      return { ok: true, user: session.user };
    }
    return { ok: true, user: result.session.user };
  } catch (error) {
    if (error instanceof RateLimitError) return { ok: false, message: "Too many attempts. Wait a few minutes." };
    if (error instanceof PermissionError) return { ok: false, message: error.message };
    if (error instanceof ValidationError || (error instanceof ApiError && error.status === 400)) {
      return { ok: false, message: "Wrong email or password." };
    }
    throw error;
  }
}
```

```python Python
from pawabase import ForbiddenError, RateLimitedError, ValidationError


def sign_in(email: str, password: str, ask_for_code):
    try:
        result = pb.auth.sign_in_with_password(email=email, password=password)
        if result.status == "mfa_required":
            session = result.verify(ask_for_code())
            return {"ok": True, "user": session.user}
        return {"ok": True, "user": result.session.user}
    except RateLimitedError:
        return {"ok": False, "message": "Too many attempts. Wait a few minutes."}
    except ForbiddenError as error:
        return {"ok": False, "message": error.message}
    except ValidationError:
        return {"ok": False, "message": "Wrong email or password."}
```
</CodeGroup>

Two details are worth copying. The function returns a message for every expected failure and rethrows anything else, so a genuine bug (a network failure, a 500) is not shown to the user as "wrong password". And it never says which of the email or the password was wrong.

## Run it anywhere

The same client works on every runtime. What changes is where the session lives and which key you use.

| Where your code runs | Key | Session storage | Notes |
| --- | --- | --- | --- |
| Browser app (React, Vue, plain JS) | Publishable | `localStorage` (default) | Renewal runs on a timer. Several tabs share one session. |
| Mobile app (React Native) | Publishable | Pass `auth.storage` backed by secure storage | `localStorage` does not exist; see [Client integration](/auth/client-integration/overview). |
| Server rendering, API route, edge function | Publishable, with the caller's token | None: pass `accessToken` per request | One client per request, or per process with a token function. See [Tokens and sessions](/auth/tokens-and-sessions#use-sessions-on-a-server). |
| Background job or script acting for itself | Secret | None needed | Use it for [`admin`](/auth/managing-users/overview) and [`manage`](/studio/api-keys), never to sign people in. |
| Command-line tool or desktop app | Publishable | `FileSessionStore` (Python) or your own storage | The user signs in once and stays signed in between runs. |
| Tests | Publishable | In memory | Create a fresh client per test and `dispose()` it (TypeScript) so timers stop. |

<Warning>
A secret key bypasses your policies and can manage every account. The TypeScript client refuses to start with one in a browser unless you set `dangerouslyAllowBrowser`, and you should never set it. If a secret key has been in client code, revoke it and create a new one.
</Warning>

## Authentication and the rest of Pawabase

Signing in changes what every other Pawabase service does for the caller, because they all read the same signed-in user. You do not pass the token around yourself.

<CodeGroup>
```typescript TypeScript
await pawabase.auth.signInWithPassword({ email, password });

const { data: mine } = await pawabase.from("orders");                       // rows your policy lets this user read
await pawabase.storage.from("avatars").upload("me.png", file);              // uploads as this user
const room = pawabase.realtime.channel("chat:lobby");                        // joins with this user's identity
await room.subscribe();
```

```python Python
pb.auth.sign_in_with_password(email=email, password=password)

mine = pb.from_("orders").execute()                                          # rows your policy lets this user read
pb.storage.from_("avatars").upload("me.png", open("me.png", "rb"))           # uploads as this user
# realtime channels (async client): pb.realtime.channel("chat:lobby")
```
</CodeGroup>

| Service | What the signed-in user changes |
| --- | --- |
| [Data](/data/resources/overview) | [Policies](/policies/overview) read the user's id, roles and organization, so the same query returns different rows for different people. |
| [Storage](/storage/overview) | Bucket rules can limit access to the owner or to a role. |
| [Realtime](/realtime/overview) | Channel rules decide who may subscribe and publish; presence shows the user. |
| [Flows](/flows/overview) | A route can require a signed-in user, and the flow sees who called. |
| [Webhooks](/webhooks/outbound) and [events](/events/overview) | Account events such as `user.created` can start flows and be delivered to your servers. |

When a signed-out client makes one of these calls, it is the anonymous caller: your policies decide whether that is allowed. See [Auth in policies](/auth/auth-in-policies/overview).

## When something does not work

| Symptom | Likely cause | What to check |
| --- | --- | --- |
| Every call answers 401 "Send a valid API key" | The key is missing, mistyped, or from another environment. | Print the key prefix (`pb_pk_`) and confirm `url` and `environment`. |
| A user exists but sign-in says "invalid email or password" | You are pointing at a different environment than the one the account is in. | Compare the `environment` and key in your client with where the account was created. |
| Sign-up returns no session | The environment requires confirmed email addresses. | Read `verificationRequired`, then see [Email verification](/auth/email-verification/overview). |
| The sign-up call fails with 403 | Sign-up is switched off, or the user limit is reached. | Read `settings().signup_enabled`. |
| `redirect_to is not an allowed URL` | The address is not on the environment's list. | Add the exact origin in Studio, including the scheme and port. |
| A social button shows but nothing happens | The provider lacks credentials or the redirect URL is not allowed. | See [Social login](/auth/social-login/overview). |
| A user is signed out unexpectedly | The refresh token was revoked, used twice, or storage was cleared. | See [Failure behaviour](/auth/tokens-and-sessions#failure-behaviour). |
| A role you recently granted has no effect | The token still carries the old roles. | Call `refreshSession()`, or have the user sign in again. |
| 429 on sign-in | The shared rate limit or the account lock. | Wait; see [Lockout and rate limits](/auth/passwords#lockout-and-rate-limits). |
| Works locally, fails in production | A different environment, key or redirect list. | Treat each environment's configuration as separate. |

Every error includes a request id (`error.requestId`, `error.request_id`). Quote it in a support request and the request can be found exactly.

## Where to keep what

A user record has two places for your own data, and a third place that is yours entirely. Choosing well early avoids a security bug later.

| Kind of data | Put it in | Why |
| --- | --- | --- |
| Display preferences, theme, onboarding progress | `user_metadata` | The user can edit it, which is what you want for things they control. |
| Anything that grants access: a plan, a staff flag, a tenant id | `app_metadata` or a [role](/auth/roles-and-permissions/overview) | Only your server (with a secret key) or Studio can change it, so a user cannot promote themselves. |
| Application data about people: addresses, orders, histories | Your own [resource](/data/resources/overview) with a `user_id` column | It can grow, be queried and filtered, and be protected by [policies](/policies/overview). |

Write `app_metadata` from a server:

<CodeGroup>
```typescript TypeScript
import { admin } from "@pawabase/client/admin";

const accounts = admin(pawabaseWithSecretKey);
await accounts.users.update(userId, { appMetadata: { plan: "pro" } });
```

```python Python
pb_server.admin.users.update(user_id, app_metadata={"plan": "pro"})
```
</CodeGroup>

The change reaches the user's next token (within 15 minutes, or immediately after `refreshSession()`), and [policies](/auth/auth-in-policies/overview) can read it. See [Managing users](/auth/managing-users/overview) for the full admin API.

<Warning>
Never decide access from `user_metadata`. A signed-in user can write anything to it with `updateUser({ data })`, including `{ "role": "admin" }`.
</Warning>

## Choosing sign-in methods

Offer fewer methods, done well. A typical consumer app uses one primary method and one fallback; a business app often uses a password with a second factor, or social sign-in with the company's provider.

| Your users are… | Offer |
| --- | --- |
| The general public, on phones | A [passkey](/auth/passkeys-and-codes#passkeys) first, [emailed codes](/auth/passkeys-and-codes#emailed-codes) as the fallback. |
| Employees of one company | [Social login](/auth/social-login/overview) with the company's provider, with a second factor enforced there. |
| Developers | GitHub, plus an email and password. |
| Anyone, with no friction at first | [Guest sessions](/auth/passkeys-and-codes#guest-sessions) that upgrade later. |
| Accounts holding money or sensitive records | A password or passkey **and** a [second factor](/auth/mfa/overview). |

Whatever you choose, plan the way back in. People lose phones and forget passwords, so a recovery path ([password recovery](/auth/password-recovery/overview), a second passkey, or an emailed code) must exist before you launch.
