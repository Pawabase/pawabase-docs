Magic links are passwordless sign-in by emailed one-time link. The user gives an email address, a message arrives with a link in it, and following that link signs them in — no password is ever created, typed, or stored for them.

The mechanism is small: a token with the `magic` purpose, an email built from a template, and a link whose destination depends on one configuration setting. Almost every surprising behaviour on this page falls out of that last part. An environment with a `site_url` sends people to your application. An environment without one sends them to a page hosted by Akountz itself, and the two paths complete the sign-in differently.

## Where magic links sit in the layered model

Magic links are entirely an identity-layer feature, with one configuration dependency.

| Layer | What magic links ask of it |
| --- | --- |
| **Akountz** (identity) | Owns the `OneTimeToken` row, sends the message, consumes the token, starts the session. |
| **The API** (project config) | Owns `magic_link_enabled`, `site_url`, and the `magic` email template. |
| **Gateway / `pawabase_core`** | Verifies the resulting token, like any other. Not involved in the flow. |

The tenancy rule applies as everywhere: a token is scoped to one `project` + `env` pair, so a magic link issued in staging cannot be redeemed in production even if the email addresses match.

<Info>
If you have not read [Authentication](/auth/overview) first, do that — this page assumes the layered model and the per-environment tenancy rule.
</Info>


## The two requests

There are only two routes, and the split between them is what makes the flow feel magic: asking for a link is context-scoped and looks like an ordinary API call, while redeeming it depends on where the link points.

| Route | Method | Purpose |
| --- | --- | --- |
| `/auth/v1/magic-link` | POST | Email a sign-in link. Always answers the same way. |
| `/auth/v1/magic-link/verify` | POST | Redeem the token and get a session. |

The hosted page, when there is no `site_url`, uses a third route that is not in the schema:

| Route | Method | Purpose |
| --- | --- | --- |
| `/auth/v1/links/{project}/{env}/magic` | GET | Redeem the token and either redirect or show a page. |

### Asking for a link

```bash
curl -X POST "https://api.example.com/auth/v1/magic-link" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "content-type: application/json" \
  -d '{"email": "ada@example.com"}'
```

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `email` | string | required | The address to send to. Normalised to lowercase. |
| `create_user` | bool | `true` | Whether an unknown address creates an account. |
| `redirect_to` | string | null | Where to land afterwards. Must be allowlisted. |

The response is the same whether or not the address has an account:

```json
{ "sent": true, "message": "If the address has an account, a message is on its way." }
```

<Warning>
That identical response is deliberate and is the point. If the endpoint answered differently for a registered and an unregistered address, it would be a membership oracle — a script could enumerate which addresses have accounts in your environment. Every endpoint that emails a link in Pawabase answers this way.
</Warning>

### What `create_user` actually does

This flag has more reach than its name suggests, and it interacts with two other settings.

The account is only created when **all** of these hold:

| Condition | Setting |
| --- | --- |
| The address has no account. | — |
| `create_user` is true. | the request |
| Sign-up is enabled in this environment. | `signup_enabled` |
| The account is not disabled. | — |

If sign-up is off, an unknown address simply receives nothing, and the response is unchanged. The user sees "check your email" forever, which is the correct behaviour for a membership oracle but a poor experience for someone who genuinely expected an account.

<Warning>
An account created this way gets **no password**. Password sign-in cannot succeed against it until someone sets one through a recovery link. This is the normal state for a magic-link-only user, not a fault. See [Managing users](/auth/managing-users/overview).

## Where the link lands

This is the decision that most often surprises people, and it comes down to one setting: `site_url`.

Every emailed link in Pawabase is built the same way. The handler takes the kind, the token and an optional redirect target, and then chooses a destination:

| Environment state | The link points at |
| --- | --- |
| `site_url` is set | `{site_url}/auth/callback?token=...&type=magic` |
| `site_url` is empty | `{public_url}/auth/v1/links/{project}/{env}/magic?token=...` |

Both carry the same token. What differs is **who completes the flow**.

**With a `site_url`, your application does the work.** The link opens a page on your domain with the token in the query string. That page is yours: you read the token, post it to `/auth/v1/magic-link/verify`, store the session, and decide what the user sees next. You control the page, the styling, and what happens after sign-in.

**Without one, Akountz hosts the page.** The link opens a page served by the identity service itself. It redeems the token server-side and shows a plain confirmation — *"You're all set"* — or, if a `redirect_to` was supplied and is allowlisted, redirects to it with the tokens in the URL fragment.

The second path works perfectly well for an internal tool or a proof of concept. The difference is that you get no page of your own, no control over the post-sign-in experience, and a page whose look is not yours.

<Warning>
The setting is shared with every other emailed link — verification, recovery, email change. Setting `site_url` to get magic links pointing at your app changes where **all** of them point. That is usually what you want, and it is worth knowing before you expect one flow to behave differently from another.
</Warning>

<Info>
If `site_url` is empty and `public_url` is also empty, the hosted link is built from an empty base and will not work. Both being unset is a misconfiguration rather than a supported mode — set at least one.
</Info>

### The allowlist, again

`redirect_to` is checked against the same allowlist used by OAuth: `site_url` plus `redirect_urls`, matched on exact equality or a `/` or `?` boundary.

| Base | `redirect_to` | Allowed |
| --- | --- | --- |
| `https://app.example.com` | `https://app.example.com/welcome` | yes |
| `https://app.example.com` | `https://app.example.com.evil.test/` | no |
| — | `http://localhost:3000/after` | only if listed in `redirect_urls` |

An allowlisted `redirect_to` is added to the link itself, so the hosted page knows where to send the user afterwards.

<Info>
A `redirect_to` that fails the allowlist is rejected at the request stage with `400 redirect_to is not an allowed URL`, rather than being quietly dropped. That is the safer failure, but it does mean a misconfigured client sees a 400 rather than a link that "did nothing".
</Info>

## The token

The link carries a one-time token: a signature over the id of a `magic` row, with the row making it single-use.

| Purpose | Lifetime |
| --- | --- |
| `magic` | **900 seconds** — fifteen minutes |

For context, this is the shortest-lived emailed token in the system:

| Purpose | Lifetime | Why |
| --- | --- | --- |
| `mfa` | 300 seconds | Answered immediately. |
| `link` | 600 seconds | A linking ticket. |
| `magic` | **900 seconds** | Answered immediately, in the same sitting. |
| `recovery` | 3600 seconds | Found in an inbox minutes later. |
| `verify`, `email_change` | 24 hours | Deliberately forgiving. |
| `invite` | 7 days | Arrives with an onboarding flow. |

Fifteen minutes is deliberately short. The person who asked for the link is sitting in front of a page waiting for it, so the window only has to cover their attention span. A magic link that stayed valid for an hour would be a credential sitting in an inbox for an hour.

<Warning>
The copy the user receives says *"It works once, for 15 minutes"*, and that is accurate. If you override the template, keep that promise true — a custom subject promising longer does not make the token longer.
</Warning>

### Single use, and what that means under pressure

The token can be redeemed exactly once. Redemption uses a conditional update — an update that applies only while the row is unused — and if it matched no rows, someone else got there first.

That matters in a specific and common scenario: **the user opens the link twice.**

| What happened | Result |
| --- | --- |
| First click. | Redeemed. A session is created. |
| Second click — same tab, or a refresh. | Fails. The link is spent. |

The first redemption already worked, so the user is signed in and may not notice the second failure. But if the first response was lost — a closed tab, a dropped connection, a navigation away before the request landed — the token is consumed and the user must ask for another.

<Info>
There is no "resume this sign-in" behaviour and no second redemption. Design the callback page to store the session as its first action, not after a round trip to your own backend, so a failure between the two does not strand a user who has already spent their token.
</Info>

### Every failure is the same error

A magic token that is already used, expired, malformed, signed for another environment, or simply wrong produces one identical failure: a `400` whose detail is *"the link is invalid or has expired"*.

| Condition | Same error? |
| --- | --- |
| Already redeemed | yes |
| Expired | yes |
| Signature does not verify | yes |
| Row missing | yes |
| Token from another environment | yes |

<Warning>
Do not try to distinguish these in your error handling. There is no information in the distinction that helps a legitimate user, and several of them are exactly what an attacker probing the endpoint wants to learn.
</Warning>

## Redeeming the token

### With a `site_url` — your page does the work

Your callback page reads the token from the query string and posts it.

```text
// Your /auth/callback page.
const params = new URLSearchParams(window.location.search);
const token = params.get("token");

if (token) {
  const res = await fetch("/auth/v1/magic-link/verify", {
    method: "POST",
    headers: { "content-type": "application/json", "X-Pawabase-Context": CONTEXT },
    body: JSON.stringify({ token }),
  });
  const body = await res.json();

  if (res.ok && body.access_token) {
    storeSession(body);
    history.replaceState(null, "", "/");
  } else if (body.mfa_required) {
    promptForCode(body.mfa_token);
  } else {
    // "the link is invalid or has expired" -- send them back to request another.
  }
}
```

```bash
curl -X POST "https://api.example.com/auth/v1/magic-link/verify" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "content-type: application/json" \
  -d '{"token": "..."}'
```

The response is the standard token response — the same shape as a password sign-in, which is what makes magic links droppable into an existing client:

```json
{
  "access_token": "...",
  "refresh_token": "...",
  "token_type": "bearer",
  "expires_in": 900,
  "expires_at": 1750000000,
  "session_id": "9f2c1ab4e7d84f0c9b3a5e61d2c4807f6a9e3b5c1d0f28496ab7c3e5d1f0a2b4c6",
  "org": null,
  "org_role": null,
  "user": { }
}
```

### Without a `site_url` — the hosted page does the work

The browser lands on the Akountz-hosted link. It redeems the token itself and then does one of two things:

| Situation | What the user sees |
| --- | --- |
| No `redirect_to`, or the result has no tokens | A plain *"You're all set"* page. |
| `redirect_to` present, allowlisted, and a session resulted | A redirect carrying the tokens in the fragment. |

```text
https://app.example.com/welcome#access_token=...&refresh_token=...&expires_in=900&token_type=bearer
```

<Warning>
Tokens arrive in the **fragment** on this path, not in the query string — the same protection as the OAuth callback, for the same reason. A page that reads them must read `location.hash` in the browser, and cannot render them server-side. See [Social login](/auth/social-login/overview) for the fragment-handling pattern.
</Warning>
</Warning>

<Info>
There is one more case worth knowing: if the account has MFA enrolled, redemption returns a challenge rather than a session, and there are no tokens to redirect with. The hosted page will show its confirmation rather than a code prompt — which is a good reason to set a `site_url` and own the callback page if you offer magic links to users who have enrolled MFA.
</Info>

### What redemption does to the account

Beyond starting the session, completing a magic link has two effects that are easy to miss.

| Effect | Condition | Why it matters |
| --- | --- | --- |
| The email is marked verified. | Always, if not already. | Holding the link proves control of the inbox. |
| MFA is challenged. | The account has MFA and the environment allows it. | Returns `mfa_required` instead of a session. |

The first is the important one. **A magic link verifies the email address**, without a separate confirmation step. Opening the link is the proof.

<Info>
This means magic links and email verification do not conflict. A user who signs up with verification required can confirm their address simply by completing a magic-link sign-in. It also means the two messages are genuinely interchangeable evidence of inbox control.
</Info>
