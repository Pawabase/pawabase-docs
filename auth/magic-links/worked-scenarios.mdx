### A known user requests a link

The address matches an account, the account is not disabled, and `create_user` is irrelevant because there is nothing to create.

A `magic` token is issued and the message is sent. The response is the standard "sent" body, identical to what an unknown address would have received.

The user clicks. The token is redeemed, the email is marked verified if it was not already, and a session is created with its method recorded as a magic-link sign-in. No MFA challenge unless the account has a factor.

### An unknown address requests a link

Two branches, decided by `create_user` and `signup_enabled`.

| `create_user` | `signup_enabled` | Result |
| --- | --- | --- |
| true | true | An account is created, `user.created` is emitted, and a link is sent. |
| true | false | Nothing is created and no message is sent. |
| false | true | Nothing is created and no message is sent. |
| false | false | Nothing is created and no message is sent. |

In all four cases the **response is identical**. The user cannot tell from the response whether they now have an account, and neither can anyone else.

<Warning>
The rows where nothing is sent are the ones that generate support tickets. A user who requests a link, gets "check your email", and has no account is the expected behaviour of a membership-oracle-safe endpoint in an invite-only environment. Your interface should say "if that address has an account, a message is on its way", not "we sent you a link".
</Warning>

### A disabled account requests a link

The address matches an account, but the account is disabled, so no token is issued and no message is sent. The response is the same one.

If the user already holds an unexpired link from before the account was disabled, redemption refuses with `403 this account is disabled`. The flag is checked at redemption as well as at issue, so disabling an account closes both doors.

### A user with MFA completes a magic link

The token is redeemed successfully. The account has MFA, so **no session is issued**. A challenge comes back instead:

```json
{ "mfa_required": true, "mfa_token": "..." }
```

The client posts that to `/auth/v1/token` with `grant_type=mfa` and a code, and gets the session at `aal2`.

| Where the link landed | What the user sees |
| --- | --- |
| Your app, with a `site_url` | Whatever your callback page renders. Handle the branch. |
| The hosted page | *"You're all set"*, and they are **not** actually signed in. |

<Warning>
The second row is a genuine trap. A user with MFA who uses an Akountz-hosted magic link is told everything is fine and ends up signed out. If you offer magic links to users who enrol MFA — which you should — set a `site_url` so your own page handles the challenge.
</Warning>
### The link is clicked twice

First click redeems it and creates a session. Second click fails with the generic expired-or-invalid error.

If the user was on your callback page and the session was stored on the first load, they are signed in and the second failure is invisible. If the first response never reached the client, the token is gone and they need a new link.

<Info>
There is no way to make a magic link survive a second click. The single-use property is what makes it safe to send through mail infrastructure that might prefetch it.
</Info>

### A local developer follows a magic link

Two distinct failures, both common and both confusing.

| Symptom | Cause |
| --- | --- |
| The link opens a page that is not styled like yours. | No `site_url`, so the hosted page is used. |
| The hosted link 404s. | `public_url` is empty, so the link was built from an empty base. |
| Your callback page says the link is invalid or has expired. | The environment does not match the one that issued the link. |
| `redirect_to is not an allowed URL`. | `http://localhost` is not in the allowlist. |

<Warning>
The third row catches people who copy a magic link between environments, which is easy to do while testing because the token looks environment-agnostic. It is not: the signature and the row are both bound to one project and environment.
</Warning>

### Verifying the setup

Two checks confirm magic links are wired correctly.

```bash
# 1. Request one. The response is identical whether or not the address exists.
curl -sX POST "$BASE/auth/v1/magic-link" \
  -H 'content-type: application/json' \
  -d '{"email":"ada@example.com"}'

# 2. Redeem the token from the message. Expect the standard token response.
curl -sX POST "$BASE/auth/v1/magic-link/verify" \
  -H 'content-type: application/json' -d '{"token":"..."}'

# 3. Try it a second time. Expect the invalid-or-expired error.
```

| What it tells you | Good result |
| --- | --- |
| The endpoint is enabled | A "sent" body, not a 403. |
| The link landed where you expected | Your domain, if `site_url` is set. |
| Redemption works | The standard token response. |
| Single use holds | The second attempt fails. |

<Info>
Testing the double redemption once is worth doing. It is the failure a user will hit first, and knowing the exact error shape means the message you write for it will be right.
</Info>


## Choosing between the sign-in methods

Magic links are one of four ways in, and the choice between them is a product decision with real trade-offs.

| | Magic link | Password | Magic link + password | Social |
| --- | --- | --- | --- | --- |
| Credentials stored | none | one, hashed | one, hashed | none |
| User must type something at sign-in | no | yes | yes | no |
| Reset needed if forgotten | ask for a new link | email a link | email a link | nothing |
| Phishing exposure | a real login link is a real credential | password is a real credential | both | the provider's login |
| Works without an authenticator app | yes | yes | yes | yes |
| Survives the inbox being compromised | no | yes | no | no |
| Best for | convenience, infrequent use | repeat use, high security | repeat use | accounts that would rather not have a password |

<Warning>
The honest summary is that a magic link trades a durable secret for an expiring one. That is a genuine improvement for an occasional user, and a genuine downgrade for a user whose inbox is the weakest link in their security. If you offer both, most people use the password after the first few sign-ins.
</Warning>

### Offering both

The methods are not mutually exclusive, and the settings are independent.

| Setting | Controls |
| --- | --- |
| `magic_link_enabled` | Whether the link is offered. |
| `password_policy`, `password_min_length` | Whether passwords are set, and how strong. |

An account created by a magic link has **no usable password**, so a sign-in screen offering both will show a password field that cannot succeed until the user sets one. That is the normal state, and the resolution is a password recovery link — the same mechanism that creates the first password.

<Info>
There is no separate "set a password" flow for passwordless accounts. Password recovery is it, which is one reason the recovery message says the link works once, for an hour.
</Info>

### Sign-in surfaces

A sign-in screen should be built from `GET /auth/v1/settings` rather than from hardcoded assumptions, because every method on it is per environment.

```json
{
  "signup_enabled": true,
  "email_verification_required": false,
  "magic_link_enabled": true,
  "mfa_enabled": true,
  "providers": ["google"],
  "password_policy": { "kind": "basic", "min_length": 8 }
}
```

| Field | What your UI should do |
| --- | --- |
| `magic_link_enabled` | Show or hide the "email me a link" option. |
| `providers` | Render one button per name. |
| `signup_enabled` | Whether to offer registration. |
| `email_verification_required` | Whether to explain the confirmation step. |
| `password_policy` | Whether to show strength hints on a password field. |

<Warning>
Do not show a magic-link option because you assume the feature exists. It defaults to **on**, so an environment with a stale or inherited configuration may be offering a flow whose mail does not arrive.
</Warning>


## Deployment considerations

### Environments and mail

Delivery goes through the API's mail service using each environment's own SMTP settings. This matters more for magic links than for other email, because the link is the entire credential.

| Environment | What happens |
| --- | --- |
| Sandbox SMTP | Links are caught by the sandbox and never arrive. |
| A catch-all inbox | Links arrive, but to an address nobody reads. |
| No SMTP configured | The request succeeds and no message is sent. |

<Warning>
A request returning "sent" does not mean a message was delivered — only that a token was issued and handed to the mail service. There is no delivery confirmation to read back. When testing magic links, confirm the message actually arrived rather than trusting the response.
</Warning>

### Promotion

Magic links are configuration, so they promote with the environment. Accounts do not promote at all.

| Promoted | Not promoted |
| --- | --- |
| `magic_link_enabled` | Users |
| `site_url` | One-time tokens |
| `emails.magic` | Sessions |
| `signup_enabled` | |

<Info>
Promoting staging to production carries the magic-link settings with it, which is usually what you want. It also means a staging-only `site_url` can land in production, sending production's sign-in links to a staging host. Check it after a promotion.
</Info>

### Rate limits

| Bucket | Limit | Window | Applies to |
| --- | --- | --- | --- |
| `akz:links` | 10 | 60 seconds | The magic-link request. |
| `akz:auth` | 30 | 60 seconds | `/token`, including MFA completion. |

Ten requests a minute per caller is the limit on how fast links can be requested. It is the second brake behind the identical-response design: a script cannot enumerate accounts by watching which requests succeed, because none of them do.

<Info>
A resend button that fires on every click will hit this quickly. Cooldown the button client-side rather than discovering the limit through a 429.
</Info>

### What a magic-link session can do

The session that comes back is an ordinary session, so everything downstream behaves the same as any other sign-in.

| Aspect | Value |
| --- | --- |
| Assurance level | `aal1`, or `aal2` if MFA was challenged. |
| Lifetime | The environment's access and refresh TTLs, 15 minutes and 30 days by default. |
| Refresh | Normal rotation, with the same theft detection. |
| Revocation | Normal — it appears in the session list like any other. |
| Organization scoping | Starts unscoped; refresh with an `org` to switch. |
| Roles | Read at issue time from the account. |

<Warning>
Because the session is ordinary, a lost or abandoned link leaves no residue to clean up. The token is consumed or expires, and nothing else was created.
</Warning>
