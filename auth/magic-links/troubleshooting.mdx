Magic-link problems are almost always one of a handful of causes, and the error text points at which.

| Symptom | Cause | Fix |
| --- | --- | --- |
| `403 magic links are disabled` | `magic_link_enabled` is false. | Turn **Magic links** on in the Configuration tab. |
| The link says invalid or expired, immediately. | A mail scanner fetched it. | Ask IT to exempt your domain. |
| The same, after fifteen minutes. | The window elapsed. | Request a new one. |
| The same, on the second click. | Already redeemed. | Expected. Check whether the first attempt worked. |
| The same, straight away in development. | Wrong environment. | The token is bound to one project and environment. |
| `400 redirect_to is not an allowed URL` | The target is not in the allowlist. | Add it, or use `site_url`. |
| No email arrives. | Mail service, or no account and no sign-up. | Check SMTP, and whether the address exists. |
| The email arrives with `{link}` in it. | A placeholder typo in an override. | Fix the template. |
| The hosted page returns 404. | `public_url` is empty. | Set `site_url`, or set `public_url`. |
| The hosted page says "You're all set" but I am not signed in. | MFA was challenged and the page cannot prompt. | Set a `site_url` and handle the challenge. |
| No link appears in the sign-in screen. | Hardcoded assumptions, or a stale config cache. | Render from the settings response. |
| `429` on repeated requests. | Ten per minute. | Cooldown the resend button. |

<Warning>
The two that generate the most confusion are the mail scanner and the double click, because both present as "the link is invalid or has expired" with no further detail. That is the error the design intends — see [Every failure is the same error](/auth/magic-links/overview#every-failure-is-the-same-error) — so diagnosing them means knowing your users' mail setup.
</Warning>

<AccordionGroup>
  <Accordion title="Why did my user get no email?">
    Three possibilities, in the order worth checking: the address has no account and `create_user` is false or sign-up is off; the account is disabled; or the mail service is not delivering. The response is identical in all three, by design. The audit trail will tell you whether an account was created for that request.
  </Accordion>
  <Accordion title="Can I resend the same link?">
    There is no resend that reuses a token. Each request issues a fresh one, and each is independently valid and single-use. Two valid links existing at once is expected, not a bug.
  </Accordion>
  <Accordion title="Does a magic link confirm the email address?">
    Yes. Completing one marks the address verified if it was not already, because holding the message is the proof. This is why magic links can substitute for a separate verification message.
  </Accordion>
  <Accordion title="Why is the session aal1?">
    Because a magic link is one factor. It is exactly as strong as a password session, and exactly as deserving of an `aal2` policy if your users have enrolled MFA.
  </Accordion>
  <Accordion title="Can a user sign in with a magic link and a password?">
    Only once they have a password. An account created by a magic link has none, so password sign-in fails until one is set through password recovery. Offering both methods in a UI is normal; the password field simply does not work yet.
  </Accordion>
</AccordionGroup>
### Two valid links at once

Requesting two links for the same address issues two independent tokens, both valid, both single-use.

| Consequence | Detail |
| --- | --- |
| Either one can sign in. | They are not related to each other. |
| Using one does not invalidate the other. | Redemption marks one row, not the account. |
| Both can produce sessions. | Separate sessions, in separate token families. |
| Each counts separately for the rate limit. | Ten requests a minute regardless. |

<Warning>
Two concurrent valid links means a forwarded link remains usable after the recipient has already signed in with their own. There is no mechanism to revoke a single outstanding magic token, which is another way of seeing that the security here rests on the fifteen-minute window rather than on revocation.
</Warning>

### Diagnosing a token that will not verify

When you need to know why a specific token failed, the row answers it.

```sql
SELECT purpose, expires_at, used_at, user_id
FROM akz_one_time_tokens
WHERE project = 'acme' AND env = 'production'
ORDER BY id DESC LIMIT 5;
```

| What the row shows | Diagnosis |
| --- | --- |
| `used_at` is set | Someone redeemed it — possibly a mail scanner, possibly the user. |
| `used_at` null, `expires_at` in the past | It aged out. |
| No row at all | The signature did not verify, or it was issued for another environment. |
| A row with the right purpose | The failure is on the client side. |

<Warning>
The row is only findable by id, and the id is inside the signed payload. If you have the token, you can decode it to get the id without verifying the signature, then look the row up directly — which tells you whether the problem is the signature or the row.
</Warning>

### What to build, in summary

The interface decisions that matter, gathered.

| Decision | Recommendation |
| --- | --- |
| Render the option from settings | Not hardcoded. The feature defaults to on. |
| The request's copy | "If that address has an account, a message is on its way." |
| The callback page | Store the session as its first action. |
| Token handling | Read it from the query string; clean the URL afterwards. |
| Expired or invalid | Offer another link. Do not diagnose further. |
| `mfa_required` | Handle the branch, or do not offer magic links to enrolled users. |
| The resend button | Cooldown it. |
| Session storage | The same as any other sign-in. |

<Info>
Every one of these is a consequence of something documented above rather than a separate opinion: the identical response is why the copy is cautious, the single use is why the callback must store first, and the MFA branch is why a `site_url` matters more than it first appears.
</Info>
