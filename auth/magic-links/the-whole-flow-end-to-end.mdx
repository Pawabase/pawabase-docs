The complete sequence in one place, for both destination modes, because the branching is the part worth having in your head.

### With a `site_url` — your application completes the flow

```text
  user enters an email address
        |
        |  POST /auth/v1/magic-link  {email}
        v
  {sent: true, message: "If the address has an account..."}
        |                      (identical in every case)
        |  a `magic` token is issued: signed, 900s, tied to project+env
        v
  the message arrives, carrying
  https://app.example.com/auth/callback?token=...&type=magic
        |
        |  the user clicks
        v
  YOUR /auth/callback page
        |
        |  POST /auth/v1/magic-link/verify  {token}
        v
  the row is consumed by a conditional update
  the email is marked verified
        |
        +-- MFA enrolled? --> {mfa_required, mfa_token} --> POST /token grant_type=mfa
        |
        v
  the standard token response, method "magic_link"
```

### Without a `site_url` — Akountz completes the flow

```text
  user enters an email address
        |
        |  POST /auth/v1/magic-link  {email}
        v
  {sent: true, ...}
        |
        v
  the message arrives, carrying
  https://auth.example.com/auth/v1/links/acme/production/magic?token=...&type=magic
        |
        |  the user clicks; AKOUNTZ redeems the token
        v
  the email is marked verified; MFA is checked
        |
        +-- redirect_to allowlisted AND a session resulted
        |      --> redirect to your page with #access_token=...
        |
        +-- otherwise
               a plain "You're all set" page
```

<Warning>
The two diagrams are identical up to the last hop. Everything a user experiences about *arriving* is the same; what differs is who redeems the token and what page they see afterwards.
</Warning>

### What each layer contributes

A table attributing each step, because when something breaks the layer tells you where to look.

| Step | Layer | If it fails |
| --- | --- | --- |
| Reading the config | API, cached by Akountz | Settings ignored; check the cache. |
| The request itself | Akountz | `403` or `400`. |
| Account lookup and creation | Akountz | Silent — same response. |
| Issuing the token | Akountz | Silent — same response. |
| Sending the message | The API's mail service | Silent — same response. |
| The recipient's inbox | External | Link never arrives, or a scanner ate it. |
| Clicking the link | Browser | Nothing happens. |
| Redeeming | Akountz or your page | The invalid-or-expired error. |
| The session | Akountz | Standard token failures. |

<Info>
The four steps that fail **silently** are the ones worth checking first when a user reports that nothing happened, because the response was a success in every case.
</Info>

### Data you can inspect

The token row is the only place a magic-link question can be answered definitively, and it holds more than the obvious columns.

```sql
SELECT purpose, email, user_id, expires_at, used_at
FROM akz_one_time_tokens
WHERE project = 'acme' AND env = 'production'
  AND purpose = 'magic'
ORDER BY id DESC LIMIT 10;
```

| Column | What it answers |
| --- | --- |
| `purpose` | Whether this is a magic token at all. |
| `project`, `env` | Which environment issued it. |
| `user_id` | Which account it belongs to. Null means the address had no account. |
| `email` | Where it was sent. |
| `expires_at` | When it stopped being usable. |
| `used_at` | Whether it was redeemed, and when. |

<Warning>
A row with a null `user_id` is normal for a flow where the address had no account and none was created — the token still exists because it was issued before the branch that sends mail. A row that was issued and never used is what a scanner leaves behind.
</Warning>

### The signature, in one paragraph

The token in the link is a signed payload, not a random string. The signature is what makes it unforgeable, and the timestamp inside it is what makes it expire; the row is a separate thing that makes it single-use. Verifying the signature only proves the token was issued by this system for this environment and purpose — it says nothing about whether the token has already been used, which is why the row check comes after.

| Property | Provided by |
| --- | --- |
| Cannot be forged | The signature. |
| Expires after 900 seconds. | The signature's age, checked against the purpose's lifetime. |
| Cannot be used twice. | The row, marked by a conditional update. |
| Bound to one environment. | The row, filtered by project and environment. |
| Bound to one purpose. | The serializer is keyed by purpose. |

<Info>
A token signed for one purpose cannot be redeemed as another. A `verify` token is not a `magic` token, which is what stops a verification link being used to sign someone in.
</Info>

### Asking the right question of the audit trail

Because the request endpoint is silent about outcomes, the sign-in history is where you learn what happened.

| Question | Where to look |
| --- | --- |
| Did a link complete a sign-in? | A sign-in event with the magic-link method. |
| Was an account created by a request? | A `user.created` event with the magic-link method. |
| Was the email verified by redemption? | A `user.verified` event. |
| Did someone ask for a link and never use it? | The token row, unused. |
| Why did redemption fail? | The redemption endpoint's error, not the request. |

<Info>
There is no login event for a *request*. A row is issued and a message is sent, and until someone redeems a token there is no sign-in to record. That is why "the user says they never got the email" is answered by the token row rather than the activity tab.
</Info>

### Migrating between the two modes

Moving an environment from Akountz-hosted pages to your own application, which is the usual direction of travel.

| Step | Why |
| --- | --- |
| Set `site_url`. | The switch that moves every emailed link. |
| Deploy your callback page. | It must handle `token`, `mfa_required`, and the invalid case. |
| Add local redirect bases if you develop locally. | `http://localhost` is not in the allowlist otherwise. |
| Verify the token request in your page. | A wrong context header produces a redemption failure. |

Going the other way — removing `site_url` to use hosted pages — needs no code change, and your callback page simply stops being used. Links in flight keep pointing at whatever they were built with.

<Warning>
Links already sent are unaffected by a `site_url` change. Each message carries the URL it was built with, so a user who requested a link before the change lands on the old destination and finds it still working.
</Warning>

### A complete configuration

A magic-link environment configured for real use, with the settings that actually matter.

```json
{
  "name": "production",
  "public_url": "https://auth.example.com",
  "auth": {
    "signup_enabled": true,
    "require_email_verification": true,
    "magic_link_enabled": true,
    "mfa_enabled": true,
    "site_url": "https://app.example.com",
    "redirect_urls": ["http://localhost:3000/auth/callback"],
    "emails": {
      "magic": {
        "subject": "Your Acme sign-in link",
        "text": "Sign in to Acme with this link. It works once, for 15 minutes:\n\n{link}\n\nIf you did not request this, ignore this message."
      }
    }
  }
}
```

| Setting | Why it is there |
| --- | --- |
| `site_url` | Links land on your callback page, not the hosted one. |
| `public_url` | The base for any hosted page, and for the OAuth callback. |
| `redirect_urls` | Local development only. |
| `magic_link_enabled` | Explicit, though it is the default. |
| `require_email_verification` | On, and satisfied by a magic-link redemption. |
| `emails.magic` | A subject with the product name and a body that says the window. |

<Warning>
The override's body keeps the *"works once, for 15 minutes"* sentence from the default, and adds a line for people who did not request it. Both are worth copying into any template you write — the first is a promise you are making, and the second prevents a forwarded link from being opened out of curiosity.
</Warning>

### Comparing the three emailed links

The three link-based flows share their machinery entirely, and confusing them is easy when diagnosing a failure.

| | Magic | Verification | Recovery |
| --- | --- | --- | --- |
| Purpose | `magic` | `verify` | `recovery` |
| Lifetime | 15 minutes | 24 hours | 1 hour |
| Signs someone in | yes | yes | yes, after setting a password |
| Marks email verified | yes | yes | no |
| Creates an account | optionally | no | no |
| Needs the user to supply a new password | no | no | yes |
| Revokes other sessions | no | no | **yes** |

Two of those rows carry real consequences.

**Verification signs the user in.** Completing a verification link returns a session, not just a confirmation. That is a design choice: the person proved control of the inbox, which is exactly the factor a sign-in requires, so there is no reason to make them type a password afterwards.

**Recovery revokes every other session.** Setting a new password ends all existing sessions for that account, because a password reset is the remedy for a suspected compromise and leaving the old sessions alive would defeat the point. See [Password recovery](/auth/password-recovery/overview).

<Info>
Because the three flows share the same token and link machinery, a mixed-up purpose fails with the same invalid-or-expired error as an expired one. If a user reports that a *verification* email did not work, the most likely explanations are expiry at twenty-four hours or a second click.
</Info>

### How the flows share code

The same handler completes all of them, branching on the kind. That is why the behaviours above are consistent rather than individually implemented.

| Kind | Branch behaviour |
| --- | --- |
| `magic` | Marks email verified, challenges MFA, starts a session. |
| `verify` | Marks email verified, starts a session. |
| `recovery` | Peeks first to validate, then sets a password and starts a session. |
| `email_change` | Changes the address, marks it verified, returns no session. |

The recovery branch is the interesting one, because it runs twice: once with `peek` to check the token is good enough to render a form, and once to consume it. The peek does not mark the row used, which is what allows a form to be shown and then submitted.

<Warning>
The consequence is that a recovery token survives being rendered on a page but not being submitted. If a user loads the form and walks away, the link still works — up to an hour from issue. Do not assume loading a link has spent it.
</Warning>

### What the `type` parameter is for

The link carries `type` alongside `token`, and it names which flow the token belongs to.

| Field | Purpose |
| --- | --- |
| `token` | The signed one-time token. |
| `type` | The kind, so a shared callback page can route. |
| `redirect_to` | Present only when one was supplied and allowed. |

Your callback page can therefore dispatch on `type` before deciding which endpoint to call, rather than posting every token to every endpoint and relying on the errors.

```text
const { token, type, redirect_to: redirectTo } = Object.fromEntries(
  new URLSearchParams(window.location.search)
);

const endpoints = {
  magic: "/auth/v1/magic-link/verify",
  verify: "/auth/v1/verify",
  recovery: "/auth/v1/recover/confirm",
  email_change: "/auth/v1/email/confirm",
};
const endpoint = endpoints[type];
```

<Info>
A shared callback page is worth doing if you offer more than one link flow. Each token is only valid for its own purpose, so a mismatched dispatch produces an invalid error rather than a wrong action — safe, but confusing to users.
</Info>

### Account creation through a magic link

The details of the branch that creates an account, because it produces a specific kind of user.

| Aspect | Result |
| --- | --- |
| Password | None. An unusable password is set. |
| Username | Derived from the email local part. |
| Email verification | Not set by creation. Set when the link is redeemed. |
| Roles | The environment's `default_roles`. |
| Organizations | None, unless invited separately. |
| Event | `user.created`, with the magic-link method. |

The verification row is worth pausing on: an account created by a request is **unverified**, and becomes verified only when the link is redeemed. So in an environment requiring verification, the account exists but cannot sign in normally until the link is followed.

<Warning>
If `require_email_verification` is on and the user never follows the link, an account exists in the system that has never verified anything. That is expected, and it is why the **Users** tab in Studio can be filtered for unverified accounts — they are pending, not broken. See [Managing users](/auth/managing-users/overview).
</Warning>

### Setting a password afterwards

A magic-link account has no usable password, and password sign-in fails against it until one exists. The route to a password is password recovery, which works because the flow never required a password in the first place.

```bash
curl -X POST "$BASE/auth/v1/recover" \
  -H 'content-type: application/json' \
  -d '{"email": "ada@example.com"}'
```

The recovery link sets a password, revokes every other session — including the magic-link session the user may currently hold — and signs them in again.

<Warning>
Because recovery revokes all sessions, a user who sets a password while signed in via magic link will be signed out and back in. That is correct behaviour and it surprises people the first time.
</Warning>

### Testing the flow properly

Magic links are unusually hard to test end to end, because the link leaves your server. Three techniques cover it.

**Read the token out of the mail sink.** With a sandbox SMTP service, the message is captured rather than sent, so you can copy the token directly and test redemption without an inbox.

```bash
# Request, then extract the token from the captured message.
curl -sX POST "$BASE/auth/v1/magic-link" \
  -H 'content-type: application/json' -d '{"email":"ada@example.com"}'

# Redeem it. Expect the standard token response.
curl -sX POST "$BASE/auth/v1/magic-link/verify" \
  -H 'content-type: application/json' -d '{"token":"..."}'
```

**Decode the link without verifying it.** The token is a signed payload, and decoding it — without verifying the signature — gives you the id, which is enough to find the row and answer most questions.

**Test the failure paths deliberately.** Expiry, double redemption, and a token from another environment all produce the same error, so you cannot tell them apart by testing one and assuming the others behave.

| Path | How to force it |
| --- | --- |
| Expired | Wait fifteen minutes, or edit the row's expiry. |
| Already used | Redeem twice. |
| Wrong environment | Redeem a staging token against production. |
| Not allowed | Send a `redirect_to` outside the allowlist. |
| Disabled | Disable the account, then request. |

<Info>
Because the failure is deliberately uniform, a test suite that asserts on specific errors for specific causes will fail — and that failure is the design working. Assert on the status and the fact that it is the same message.
</Info>

### Load and abuse resistance

| Protection | Value | What it stops |
| --- | --- | --- |
| Request limit | 10 per 60 seconds | Request floods. |
| Identical response | always | Account enumeration. |
| Short lifetime | 900 seconds | A stale link in an inbox. |
| Single use | once | Replay after redemption. |
| Bound to environment | yes | Cross-environment use. |

<Warning>
The identical response means you cannot build a "this address is not registered, sign up?" prompt on top of this endpoint. If your product needs that reassurance, the answer is a separate flow that also does not leak — an invitation, or an account-recovery page that behaves the same way.
</Warning>

### Comparison with the other one-time tokens

Every one-time token in the system, and what its lifetime is chosen for.

| Purpose | Lifetime | Consumed by | Revocable individually |
| --- | --- | --- | --- |
| `mfa` | 5 minutes | A code entry | no |
| `link` | 10 minutes | A provider callback | no |
| `magic` | 15 minutes | A sign-in | no |
| `recovery` | 1 hour | A password form | no |
| `verify` | 24 hours | A confirmation | no |
| `email_change` | 24 hours | A confirmation | no |
| `invite` | 7 days | An acceptance | no |

The pattern is the lifetime tracks how long a person plausibly takes between receiving and using the message, and nothing longer. An invitation gets a week because it may arrive as part of an onboarding sequence; a magic link gets fifteen minutes because the person asked for it and is waiting.

<Info>
None of them can be revoked individually, which is worth knowing for the long-lived ones. An invitation that should not have been sent cannot be cancelled by revoking the token — you revoke the invitation itself. See [Organizations](/auth/organizations/overview).
</Info>

### A browser implementation, complete

A callback page that handles every branch, since the branches are what get missed.

```text
// /auth/callback?token=...&type=magic
const params = new URLSearchParams(window.location.search);
const token = params.get("token");
const type = params.get("type");

async function redeem(kind, value, extra = {}) {
  const res = await fetch(`/auth/v1/${kind}`, {
    method: "POST",
    headers: {
      "content-type": "application/json",
      "X-Pawabase-Context": CONTEXT,
    },
    body: JSON.stringify({ token: value, ...extra }),
  });
  return { ok: res.ok, body: await res.json() };
}

if (!token) {
  renderError("This link is missing its token.");
} else {
  const { ok, body } =
    type === "recovery"
      ? await redeem("recover/confirm", token, { password: await promptForPassword() })
      : type === "magic"
      ? await redeem("magic-link/verify", token)
      : await redeem(type, token);

  if (!ok) {
    // Every failure is "the link is invalid or has expired" -- so say that,
    // offer another link, and stop. Do not try to work out which it was.
    renderExpired(body.detail);
  } else if (body.mfa_required) {
    // The account has MFA. Nothing was signed in yet.
    promptForCode(body.mfa_token);
  } else if (body.access_token) {
    // Store FIRST, then clean the URL. A failure after this point strands
    // the user with a spent token.
    storeSession(body);
    history.replaceState(null, "", "/");
  } else {
    // email_change returns {email, changed} and signs nobody in.
    renderChanged(body.email);
  }
}
```

| Branch | Shape | Action |
| --- | --- | --- |
| Invalid or expired | `{detail}` | Offer another link. Do not diagnose. |
| MFA required | `{mfa_required, mfa_token}` | Prompt for a code. |
| A session | the token response | Store, then clean the URL. |
| Email change | `{email, changed}` | Confirm. No session. |

<Warning>
The ordering in the success branch is deliberate and is the single most important line on this page. Storing the session before anything else that could fail is what stops a user ending up with a consumed token and no session.
</Warning>

<Info>
The same page handles verification and email change because the flows share the token machinery. Dispatching on `type` is what makes that safe — a token for one purpose cannot be redeemed as another.
</Info>

### Without JavaScript, or without a page

Some deployments have no application to land on, and that is a legitimate configuration rather than a compromise.

| You have | What happens |
| --- | --- |
| No `site_url`, a `public_url` | Akountz-hosted pages complete every link flow. |
| No `site_url`, no `public_url` | The link is built from an empty base and will not work. |
| A `site_url` but no page deployed | The link lands on a 404. |

The middle row is the only genuinely broken state, and it produces a link that looks right in the inbox and fails when clicked.

<Warning>
Setting a `site_url` before deploying the page that handles it is the most common sequencing mistake. In that window every magic link goes to a 404, and the only remedy is requesting a new one after the page is live.
</Warning>

### Frequently asked, with short answers

**Should I offer magic links and passwords together?**
Yes, if you want both kinds of user. They do not conflict; a magic-link account simply has no password until it sets one.

**Does a magic link create an account?**
Only when the address has none, `create_user` is true, and sign-up is enabled. Otherwise nothing is created and no message is sent — with an identical response either way.

**Why does the response not tell me whether the address exists?**
Because that would make the endpoint a membership oracle, letting anyone enumerate which addresses have accounts in your environment. Every endpoint that emails a link answers the same way.

**Can the user land on a specific page afterwards?**
Yes, with `redirect_to`, if it is inside the allowlist. Anything else is rejected when the link is requested.

**How long is the link valid?**
Fifteen minutes, once. The default email says so.

**Does it work if the user clicks twice?**
No. The second click fails, and the error says invalid or expired. The first click already worked.

**Is it safe with a mail scanner?**
Not reliably — a scanner that prefetches links will consume the token. Ask for an exemption for your domain.

**Does it verify the email address?**
Yes. Completing the link is the proof of inbox control.

**Does it work for a user with MFA?**
Yes, but it returns a challenge rather than a session, and you need a `site_url` so your page can prompt for the code.

**Which session level does it produce?**
`aal1` — one factor, exactly like a password sign-in.

**Where do I turn it on?**
**Magic links** in the **Sign-in methods** section of the **Configuration** tab. It is on by default.

### The response shapes, complete

Every body involved, so nothing has to be inferred.

```json
{ "sent": true, "message": "If the address has an account, a message is on its way." }
```

```json
{
  "access_token": "...",
  "refresh_token": "...",
  "token_type": "bearer",
  "expires_in": 900,
  "expires_at": 1750000000,
  "session_id": "9f2c1ab4e7d84f0c9b3a5e61d2c4807f6a9e3b5c1d0f28496ab7c3e5d1f0a2b4c6",
  "org": null,
  "org_role": null,
  "user": { }
}
```

```json
{ "mfa_required": true, "mfa_token": "..." }
```

```json
{ "detail": "the link is invalid or has expired" }
```

| Body | From | Branch on |
| --- | --- | --- |
| The sent acknowledgement | the request | nothing — it is always this |
| The token response | redemption | `access_token` present |
| The challenge | redemption | `mfa_required` |
| The error | any failure | status only |

<Warning>
The request response has no variant. If your client branches on it to decide whether to show a different message, one of those branches will be wrong for users whose address simply does not exist.
</Warning>

### Errors, exhaustively

| Status | Detail | From | Meaning |
| --- | --- | --- | --- |
| 403 | `magic links are disabled` | request | `magic_link_enabled` is false. |
| 400 | `redirect_to is not an allowed URL` | request | The target is not allowlisted. |
| 400 | `the link is invalid or has expired` | redemption | Spent, expired, malformed, or wrong environment. |
| 403 | `this account is disabled` | redemption | The account was disabled after the link was issued. |
| 422 | `a valid email address is required` | request | The address failed normalisation. |
| 429 | rate limited | request | Ten per minute. |

The 422 is worth noting because it is the one failure the endpoint does distinguish. A malformed address is refused outright rather than being silently accepted, because normalising it would be guesswork — and no message is sent, so nothing leaks.

<Info>
A `422` is the only request-time failure that depends on the *input* rather than on whether the address exists. Everything else about an address is answered identically.
</Info>

### Operating a magic-link deployment

The recurring tasks, and what each of them needs.

| Task | Where | Notes |
| --- | --- | --- |
| Confirm the flow works | A sandbox mail service | The only reliable end-to-end check. |
| Turn it on | **Magic links** in Configuration | On by default; be explicit. |
| Change the destination | **Site URL** | Moves every emailed link. |
| Change the copy | **Email templates** | Keep the fifteen-minute promise. |
| Find who used it | **Sign-in activity** | Successes show the method. |
| Find who requested and did not use it | The token table | There is no event for it. |
| Reset someone who lost everything | **New password** in the user modal | The only recovery path. |

<Warning>
The gap in that table is worth naming. A user who requested a link and never used it leaves **no trace in the activity tab**, because there was no sign-in. The token row is the only record. If you are chasing "did they get the email", that row is where the answer is.
</Warning>

### The three questions to answer before offering magic links

| Question | Why it matters |
| --- | --- |
| Where does the link land? | Decides whether you own the callback and whether MFA can be prompted. |
| What does the request say to the user? | It cannot confirm an account exists, and the copy has to reflect that. |
| What happens if mail is scanned? | Their link will be dead on arrival. Decide whether to raise this with IT. |

The third is the one that generates the most user reports and the least engineering work, because nothing in your code can fix it.

### A note on naming

The feature is called magic links because the credential is the message rather than something the user knows. The same mechanism is described elsewhere as a passwordless link, an email OTP, or a one-time sign-in link, and all four names refer to the same thing here: a `magic`-purpose token delivered by email and redeemed once.

<Info>
If you are reading documentation from another product that uses one of those names, check which purpose it maps to before assuming the behaviour matches. The distinguishing features here are the fifteen-minute window, the identical request response, and the account creation controlled by `create_user`.
</Info>

### The request, exhaustively

Every field, every constraint, and what each one actually governs.

| Field | Type | Required | Default | Governs |
| --- | --- | --- | --- | --- |
| `email` | string | yes | — | Where the link goes. Normalised to lowercase. |
| `create_user` | bool | no | `true` | Whether an unknown address creates an account. |
| `redirect_to` | string | no | `null` | Where the user lands afterwards. Must be allowlisted. |

| Condition | Result |
| --- | --- |
| `magic_link_enabled` is false. | `403`, before anything else is considered. |
| `redirect_to` fails the allowlist. | `400`, before any token is issued. |
| The address is malformed. | `422`, before any lookup. |
| Otherwise. | A token is issued if there is somewhere to send it. |

<Info>
The order of those checks is what you want: the feature check, the redirect check, the address check, and only then the lookup. It means a misconfigured client is told so, rather than being answered with a cheerful acknowledgement that will fail later.
</Info>

### `create_user`, restated precisely

The flag interacts with two things, and the interaction is not obvious from the name.

| `signup_enabled` | `create_user` | Unknown address |
| --- | --- | --- |
| true | true | Account created, link sent. |
| true | false | No account, no message. |
| false | true | No account, no message. |
| false | false | No account, no message. |

So in an invite-only environment, `create_user` makes no difference at all — sign-up being off already prevents creation. The flag only has an effect where sign-up is on, where it lets you let *some* users self-serve and not others.

<Warning>
Because three of the four rows are identical and share a response with the fourth, a client cannot tell a user that magic links will not create them an account. If your product needs to say that, the setting that decides it is `signup_enabled`, and it should be explained before they type their address.
</Warning>
