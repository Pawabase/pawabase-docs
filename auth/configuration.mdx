Authentication configuration decides what one environment offers: whether people can create accounts, whether they must confirm an address, how strong a password must be, which sign-in methods work, where a browser may land afterwards, and how long a session lasts. Getting it right before you build a sign-in screen saves a category of bugs that are painful to diagnose later.

The single most important thing on this page is that **an unset key is not "off". It is the default, and the defaults are permissive.** Sign-up, magic links, and MFA all default on. That one behaviour explains most of the confusion people have with this system.

<CardGroup cols={3}>
  <Card title="Config is JSON" icon="file-code">There is no TOML, no DSL, and no expression syntax anywhere in auth configuration. Studio writes JSON and so can you.</Card>
  <Card title="Defaults are permissive" icon="unlock">Sign-up on, verification off, magic links on, MFA on. Turning something off requires setting it to false, not removing it.</Card>
  <Card title="Changes lag by ten seconds" icon="clock">Each environment's config is cached. A save followed by an immediate retry can read the old values.</Card>
</CardGroup>

## Who owns this configuration

Before the fields, the ownership, because it explains every surprising behaviour on this page.

The `auth` block belongs to **the API**, as part of the environment payload. Akountz — the identity service that actually enforces these settings — never writes it. It reads it, caches it briefly, and fills in defaults for whatever is missing. The gateway never sees it at all; it only verifies tokens.

| Layer | Relationship to the `auth` block |
| --- | --- |
| The API | Owns it. Stores it as part of each environment. |
| Akountz | Reads it. Applies defaults. Never writes it. |
| The gateway | Uninvolved. Verifies tokens, not settings. |

So there is exactly one writable copy of these settings, it belongs to the environment, and the component that enforces them is a consumer of it. That is why an unset key is dangerous rather than merely untidy: the enforcing component has no way to tell "deliberately off" from "nobody decided", and it resolves the ambiguity the permissive way.

<Info>
This also means an environment's auth settings travel with its definition when you promote between environments — as configuration, not as users. Accounts are per environment and never promoted.
</Info>

## The real `AuthConfig`

These are the actual fields, with the actual defaults. This is the reference the rest of the page expands on, and it is worth reading as a whole before changing anything.

| Field | Type | Default | What it governs |
| --- | --- | --- | --- |
| `project` | str | — | The project slug. Not part of the payload; supplied by the caller. |
| `env` | str | — | The environment name. Same. |
| `project_name` | str | `""` | Display name used in email subjects and copy. |
| `signup_enabled` | bool | `True` | Whether `POST /auth/v1/signup` creates accounts. |
| `require_email_verification` | bool | `False` | Whether unverified users are refused at sign-in. |
| `password_policy` | str | `"basic"` | `basic` is a length rule; `strict` is the full validator. |
| `password_min_length` | int | `8` | Characters. |
| `access_ttl` | int | `900` | Seconds. Fifteen minutes. |
| `refresh_ttl` | int | `2592000` | Seconds. Thirty days. |
| `magic_link_enabled` | bool | `True` | Whether passwordless link sign-in is offered. |
| `mfa_enabled` | bool | `True` | Whether users may enrol TOTP. |
| `site_url` | str | `""` | The application's base URL. Redirects land here. |
| `redirect_urls` | list[str] | `[]` | Extra allowed redirect prefixes. |
| `providers` | dict | `{}` | Per-provider OAuth config, keyed by name. |
| `default_roles` | list[str] | `[]` | Roles granted at account creation. |
| `emails` | dict | `{}` | Per-message subject and text overrides. |
| `public_url` | str | `""` | Where Akountz itself is reachable. Falls back to its own setting. |

<Warning>
Two different kinds of field are mixed in that table, and the difference determines what you can write where. `project`, `env`, `project_name`, and `public_url` are **not** read from the `auth` object. Everything else is. Writing `"project": "acme"` inside `auth` does nothing at all.
</Warning>

`project` and `env` are how the configuration is *looked up* in the first place, which is why they cannot also come from the thing being looked up. `project_name` and `public_url` come from the surrounding environment payload rather than from the `auth` sub-object — they are properties of the environment, not of its authentication settings.

<Info>
`refresh_ttl`'s default is written as `30 * 24 * 3600` in source. That is 2,592,000 seconds — thirty days, not thirty. It is a common misreading in configuration files and audits.
</Info>

## How the payload becomes a config

The rule that governs every field is one line of logic, and it explains the unset-key behaviour completely.

Values are copied out of the environment payload's `auth` object, taking only the keys Akountz knows about, and **skipping any whose value is `null`**. Everything skipped falls back to the dataclass default.

| You wrote | Akountz sees |
| --- | --- |
| `"signup_enabled": false` | `False` |
| `"signup_enabled": true` | `True` |
| `"signup_enabled": null` | The default, which is `True` |
| key absent | The default |
| `"signup_enabled": "false"` | The string `"false"` — truthy, so enabled |
| A key Akountz does not know | Ignored entirely |

<Warning>
That last row matters if you are writing configuration by hand or through an API: unknown keys are silently dropped rather than rejected. A typo like `magiclink_enabled` produces no error and no effect, and the feature stays on because the real key was never set to false.
</Warning>

Three consequences follow directly:

**A key explicitly set to null is the same as absent.** This is the one that catches people. Setting a value to null in a configuration editor does not disable the feature; it restores the default, which for most features means on.

**Types are not coerced.** A quoted number is not a number, and a quoted boolean is a truthy string. If you write configuration as JSON by hand, the types in the table above are the types you need.

**There is no validation of unknown or malformed values here.** The block is trusted input from the API that owns it. Errors surface when a feature is used, not when the config is loaded.

<Info>
This also means the config is a poor place to keep anything sensitive. Provider secrets belong behind `secret://NAME` references, not inline, because the block is readable, exportable, and included in environment definitions.
</Info>

## The default block

This is every configurable key at its default value. It is also what Studio writes when you save an untouched form, so comparing it against yours shows you every deliberate change at once.

```json
{
  "signup_enabled": true,
  "require_email_verification": false,
  "password_policy": "basic",
  "password_min_length": 8,
  "access_ttl": 900,
  "refresh_ttl": 2592000,
  "magic_link_enabled": true,
  "mfa_enabled": true,
  "site_url": "",
  "redirect_urls": [],
  "providers": {},
  "default_roles": [],
  "emails": {}
}
```

Thirteen keys. `project`, `env`, `project_name`, and `public_url` are absent because they are not read from this object.

<Warning>
Read that block as a security posture, because it is one. Out of the box, anybody can create an account, nobody has to prove they own their address, and magic links and MFA are available. That is a reasonable starting point for a development environment and a poor one for production holding real data.
</Warning>

### The defaults that surprise people

| Key | Default | Why it surprises |
| --- | --- | --- |
| `signup_enabled` | `true` | Open registration is on by default. |
| `require_email_verification` | `false` | Sign-up returns a usable session immediately. |
| `password_policy` | `"basic"` | Eight characters of anything. `aaaaaaaa` passes. |
| `magic_link_enabled` | `true` | Passwordless sign-in is available without being asked for. |
| `mfa_enabled` | `true` | Available, though nobody is enrolled until they choose to be. |
| `refresh_ttl` | 30 days | A stolen refresh token is useful for a month unless rotated. |

<Info>
`mfa_enabled: true` does not mean users must use MFA. It means they *may* enrol, and that an enrolled user is challenged. Requiring a second factor is a policy decision in your own routes, using the `aal` claim.
</Info>

### What a production block tends to look like

Not prescriptive — the right values depend on your product. The shape of a tightened environment is `signup_enabled` false so nobody can register anonymously, `require_email_verification` true so an address means something, `strict` at twelve characters, and `refresh_ttl` dropped from thirty days to seven. The full block appears under [Configuring an environment from scratch](#configuring-an-environment-from-scratch).

## Sign-up and verification

Studio groups these under **Sign-up**, described as *"Who can create an account, and whether their email must be confirmed first."* That description is the whole design intent in one line: the two settings are about the same moment.

### `signup_enabled`

Whether `POST /auth/v1/signup` creates accounts. When false, the endpoint returns a 403 and no account is written. Nothing else changes — existing accounts, existing sessions, and every other sign-in method are untouched.

The Studio control is a **Sign-up enabled** switch with the hint *"Turn off to invite-only new accounts."*

| Use | Value |
| --- | --- |
| An open product anyone can register for | `true` |
| An internal tool with a known user list | `false` |
| Staging, while testing an existing configuration | `false` |

<Warning>
Turning this off does not stop account creation by other routes. A magic link with `create_user` enabled, a first social sign-in, and an operator using **New user** will all still produce accounts. If your intent is "no new accounts in this environment at all", `signup_enabled` alone is not sufficient.
</Warning>

### `require_email_verification`

Whether an unverified address is refused at sign-in. The control is **Require email verification**, hinted *"Unverified users can't sign in until they confirm."*

This is the setting that makes an email address mean something. Without it, anybody can register with an address they do not own and receive password resets and magic links for it — which, in a product where those links grant access, is a takeover of any address you can guess.

| Combination | What happens |
| --- | --- |
| `false` | Sign-up returns a usable session. Sign-in works immediately. |
| `true` | Sign-up returns no session and sends a link. Sign-in is refused until confirmed. |

The link lasts twenty-four hours and is single-use. Resending is a separate route and does not invalidate the first link.

<Info>
Turning this on after accounts already exist does not lock anybody out — it applies to accounts that have not yet been confirmed, and everyone who signed up while it was off has a verified address already. Which is why it is a safe setting to enable late, and why it does nothing for the accounts created before it.
</Info>

### `default_roles`

A list of role names granted to every account at creation, before any session is issued. The Studio control is **Default roles**, hinted *"Granted automatically at sign-up."*

This is how a new account ends up with the permissions your product assumes. Omitting it is a common cause of "new users can sign in but can't do anything".

| Property | Behaviour |
| --- | --- |
| Applied at | Account creation only |
| Back-fills existing accounts? | No |
| A missing role name | Assigned by name; grants nothing until the role exists |
| Order | Before the response is returned, so the first token already carries it |

<Warning>
Changing `default_roles` affects only accounts created afterwards. If you add a role that existing users should have, assign it to them — either through Studio's **Role** field on each user or through the grant routes. Nothing back-fills.
</Warning>

### Why sign-up alone is not a closed door

Worth being blunt about, because "invite-only" is what the Studio hint promises and one switch does not deliver.

| Route that creates an account | Governed by `signup_enabled`? |
| --- | --- |
| `POST /auth/v1/signup` | **Yes.** Returns 403 when off. |
| Magic link with `create_user` | No. Creates the account if the address is unknown. |
| First social sign-in | Yes. The callback refuses to create an account when it is off. |
| Studio **New user** | No. It is an operator action, deliberately outside the setting. |
| An organization invitation | No. That is the point of an invitation. |

Magic link creation is the exception that matters: it is a request parameter with its own default rather than something the environment setting covers.

<Info>
So "invite-only" holds for the password and provider paths. If you also need it to hold for magic links, pass `create_user: false` on that request from your own code — it is a request field, not an environment setting, which means the environment cannot enforce it for you.
</Info>

### Verification and existing accounts

Enabling `require_email_verification` on an environment that already has accounts only affects the ones that were never confirmed. Every account created while the setting was off has a verified address, so none of them are locked out when you switch it on.

That makes it a safe setting to enable late, and it is also why it cannot retroactively fix anything: an account created with a spoofed address while verification was off stays spoofed, and nothing in the configuration reaches it.

## Passwords and lifetimes

Studio groups four controls under **Passwords**, described as *"Password strength and how long sessions last."* They sit together because the reasoning is shared — how much friction, how much exposure — even though they govern different things.

### `password_policy`

Two values, and they are genuinely different validators rather than points on a scale:

| Value | What it checks |
| --- | --- |
| `"basic"` (default) | Length only. Nothing else. |
| `"strict"` | The full strength validator, with `password_min_length` as its floor. |

The Studio control is **Policy**, a segmented **Basic** / **Strict** choice.

<Warning>
Under `basic`, eight characters of anything passes — `aaaaaaaa` is a valid password. If you read the default as "the platform enforces reasonable passwords", that is not what it is doing. Switching to **Strict** is a one-click change and is almost always what you want for production.
</Warning>

Switching policy affects new passwords only. Existing hashes are never re-validated, so every current user keeps whatever they chose. Tightening the policy is safe to deploy and is not a way to force anyone to change.

### `password_min_length`

The floor, default eight. Under `basic` it is the *only* rule; under `strict` it is the minimum the validator also respects.

Studio's **Minimum length** field accepts 6 to 128 and is hinted *"Characters."*

| Consider | Because |
| --- | --- |
| Raising it without switching to `strict` | You get length, not strength. |
| Raising it above 12 or so | Research and practice both favour length over composition. `strict` will handle the rest. |
| Lowering it below 8 | Studio's control will not let you go below 6, and there is little reason to. |

### `access_ttl`

How long an access token works, in seconds. Default 900 — fifteen minutes. Studio's **Access token lifetime** field is hinted *"Seconds. How long a bearer token works before it needs refreshing."*

Read that hint as a security statement: for the whole lifetime, whoever holds the token can use it, with no further check.

| Value | Consequence |
| --- | --- |
| Lower | More frequent refreshes, less exposure per token, more load. |
| Default 900 | A reasonable balance for most products. |
| Higher | Fewer refreshes, but a leaked token is useful for longer — and a removed role keeps working for that long. |

<Warning>
This is the setting that bounds how long a revoked permission still works. Roles are read at issue time, so removing a role does not reach an already-issued token; `access_ttl` is the size of that window. Fifteen minutes is the default; if your compliance requirements say shorter, this is the lever.
</Warning>

### `refresh_ttl`

How long a session stays resumable without re-entering credentials, in seconds. Default 2,592,000 — thirty days. Studio's **Refresh token lifetime** is hinted *"Seconds. How long a signed-out-of-band session stays resumable."*

The asymmetry with `access_ttl` is deliberate. The access token is short because it is self-contained and reusable; the refresh token is long because it is presented to one service, is tracked row by row, and is single-use.

| Consideration | Effect of a longer `refresh_ttl` |
| --- | --- |
| A stolen refresh token | Useful for longer, until it is used |
| Users re-authenticating | Less often, which is usually better UX |
| Rotation | The defence is rotation and theft detection, not the lifetime |

Seven days is a common production value. Thirty days is fine for a low-risk internal tool.

<Info>
Both lifetimes are read at issue time, so an existing session keeps the values it was created with until it refreshes. Lowering `access_ttl` does not shorten tokens that are already out there — it applies from the next refresh onward.
</Info>

## Sign-in methods

Studio groups two controls under **Sign-in methods**, the only section with no description of its own. Both are switches, and both are about which sign-in routes exist rather than how strict they are.

### `magic_link_enabled`

Whether passwordless sign-in by emailed link is offered. Default on. The Studio control is **Magic links**, hinted *"Passwordless sign-in by emailed one-time link."*

A magic link grants access without a stored credential, which makes it the strongest of the available methods against credential stuffing — there is no password to steal from a breached database. It depends entirely on email delivery, and the link is short-lived: fifteen minutes, single-use.

The setting is reported to clients, so turning it off removes the option from a well-built sign-in screen without any client change.

| Value | Effect |
| --- | --- |
| `true` | The link request succeeds and the option is advertised. |
| `false` | The request is refused and the option is not advertised. |

### `mfa_enabled`

Whether users may enrol an authenticator app. Default on. The control is **MFA (TOTP)**, hinted *"Let users add an authenticator app for aal2."*

Read the hint carefully: the setting governs *enrolment and challenge*, not enforcement. Nobody is required to use a second factor by this setting. Requiring one is a decision in your own code, comparing the `aal` claim.

| User enrolled? | `mfa_enabled` | Sign-in result |
| --- | --- | --- |
| No | Either | A normal `aal1` session |
| Yes | `true` | A challenge, then an `aal2` session |
| Yes | `false` | A normal `aal1` session |

<Warning>
Turning `mfa_enabled` off does not merely stop new enrolment. It also stops challenging users who already enrolled, dropping them to `aal1`. Any policy of yours that requires `aal2` will start denying exactly the users who did the right thing.
</Warning>

This is the counter-intuitive case in the whole configuration, and it is worth being sure about before you flip the switch: it affects enrolled users negatively and unenrolled users not at all.

## URLs

Studio groups two controls under **URLs**, described as *"Where a browser is allowed to land after an OAuth or magic-link redirect."* The description is precise: these govern where a *browser* may end up, which is a different question from where your API lives.

### `site_url`

Your application's base URL. Default empty. The **Site URL** field's placeholder is `https://app.example.com`.

It is the base for two things: the landing point for magic-link and OAuth redirects, and the allowlist against which `redirect_to` is checked. Set it to your application's origin, without a trailing path unless your app genuinely lives at one.

| `site_url` | Where a magic-link or OAuth redirect lands |
| --- | --- |
| Set | Your application, at `{site_url}/auth/callback?token=...&type=...` |
| Empty | Akountz's own hosted page, at `{public_url}/auth/v1/links/{project}/{env}/{kind}?...` |

<Warning>
An environment with no `site_url` works, but users land on an Akountz-hosted page rather than inside your application. It is unbranded and does not share your session handling. If you are seeing a Pawabase-branded page where you expected your app, this field is empty.
</Warning>

The empty default is what makes the Akountz-hosted fallback reachable at all, which is why it is not simply an error. It is a usable configuration for a proof of concept and a wrong one for anything real.

### `redirect_urls`

Extra allowlisted bases, as a list. Default empty. The control is **Additional allowed redirect URLs**, with a placeholder of `https://staging.example.com/auth/callback`.

These are prefixes rather than exact strings, and the matching rule has three cases. A URL is allowed if it equals a base exactly, starts with the base followed by a slash, or starts with the base followed by a question mark. Anything else is refused with a 400.

<Info>
Because they are prefixes, allowlisting `https://app.example.com` also allows everything beneath it. That is usually what you want. Allowlisting something with a path narrows it to that subtree.
</Info>

### `site_url` and `redirect_urls` together

The two fields do overlapping jobs, and the relationship is worth being clear about.

`site_url` is both a **destination** and the **first entry in the allowlist**. `redirect_urls` is only an allowlist — it adds permitted targets, but nothing ever redirects *to* a `redirect_urls` entry on its own. Redirects land on `site_url`, or on Akountz's hosted pages when it is empty.

| Situation | `site_url` | `redirect_urls` |
| --- | --- | --- |
| One application, one origin | The origin | Empty |
| Several environments, one origin | The origin | Per-environment callbacks, if needed |
| Two applications, one origin | The main app | The second app's callback path |
| No `site_url` at all | Empty | Still used to validate `redirect_to` |

<Warning>
Setting `redirect_urls` without setting `site_url` gives you a validated `redirect_to` but still lands magic-link and OAuth users on Akountz's hosted pages. If your users are landing somewhere you did not expect, `site_url` is the field that is empty — not `redirect_urls`.
</Warning>

### The redirect rule, exactly

This is worth being exact about, because getting it wrong produces a 400 at sign-up or at the OAuth start that is hard to diagnose.

A URL is permitted if **any** of these holds for **any** allowlisted base:

| Condition | Example |
| --- | --- |
| It equals the base exactly. | `https://app.example.com` |
| It starts with the base plus `/`. | `https://app.example.com/anything/deep` |
| It starts with the base plus `?`. | `https://app.example.com?next=/x` |

The allowlist is `site_url` first, then every entry in `redirect_urls`. Empty entries are skipped, and an empty `site_url` contributes nothing — which is why an environment with no `site_url` and no `redirect_urls` permits nothing.

Two behaviours follow that are easy to miss. A `redirect_to` that is absent is always allowed — there is nothing to check. And a base with a trailing slash is handled, because the slash is stripped before the prefix comparison.

<Warning>
The check is a string comparison, not a URL parse. It does not normalise, resolve, or canonicalise. `https://app.example.com.evil.com` does not start with `https://app.example.com/`, so it is refused — but the rule that saves you is the required slash or question mark, not any sophistication. Do not expect subdomain handling you have not allowlisted.
</Warning>

### Worked examples

With `site_url` set to `https://app.example.com` and `redirect_urls` containing `https://app.example.com/auth/callback`:

| `redirect_to` | Allowed? |
| --- | --- |
| `https://app.example.com` | Yes — exact match on `site_url` |
| `https://app.example.com/reset` | Yes — beneath `site_url` |
| `https://app.example.com/auth/callback` | Yes — exact match on an allowlisted base |
| `https://app.example.com/auth/callback/extra?x=1` | Yes — beneath an allowlisted base |
| `https://app.example.com?next=/x` | Yes — the query-string form |
| `https://app.example.com.evil.com` | **No** |
| `https://evil.com/?r=https://app.example.com` | **No** |
| `http://app.example.com` | **No** — scheme differs, and it is a string comparison |

That last row is the one worth internalising: **include the scheme in every allowlisted base.** A bare `app.example.com` will not match `https://app.example.com`, because the comparison is textual.

<Info>
Allowlisting an entire origin is the usual choice and is safe, because everything beneath your own origin is already yours. Allowlisting a specific path is the choice to make when a different application on the same origin should not be a redirect target.
</Info>

## OAuth providers

The `providers` object is keyed by provider name, and each entry is that provider's configuration. Studio renders one card per entry under a section described as *"Social sign-in. Reference credentials as secret://NAME rather than pasting them here."*

### The providers that ship

Four providers have built-in knowledge of their endpoints and scopes. Anything else is a generic provider and must supply its own.

| Key | Class | Extra |
| --- | --- | --- |
| `google` | `GoogleOAuthProvider` | — |
| `github` | `GithubOAuthProvider` | — |
| `discord` | `DiscordOAuthProvider` | — |
| `microsoft` | `MicrosoftOAuthProvider` | Accepts a `tenant` setting. |

<Warning>
There is no Apple, Facebook, or LinkedIn provider. If you need one, it is a generic provider and you supply all three endpoints yourself. Readers arriving with a list of providers in mind should treat that list as shorter than they expect.
</Warning>

OIDC is used when `openid` appears among the scopes, which is how you get an identity token rather than plain OAuth. Microsoft's `tenant` narrows which tenant the login is accepted from — `common` accepts any, and a specific tenant id restricts it.

### Generic providers

Any name outside those four becomes a generic OAuth provider, and it must supply three endpoints:

| Required key | Without it |
| --- | --- |
| `authorize_endpoint` | A 500 naming the provider and saying it needs the endpoints |
| `token_endpoint` | The same |
| `userinfo_endpoint` | The same |

```json
{
  "providers": {
    "gitlab": {
      "enabled": true,
      "client_id": "...",
      "client_secret": "secret://GITLAB_SECRET",
      "authorize_endpoint": "https://gitlab.com/oauth/authorize",
      "token_endpoint": "https://gitlab.com/oauth/token",
      "userinfo_endpoint": "https://gitlab.com/api/v4/user",
      "scopes": ["read_user"]
    }
  }
}
```

<Info>
The failure mode is unhelpful in an instructive way: the 500 appears when the provider is *used*, not when it is configured or listed. A generic provider missing an endpoint will therefore look like a broken button rather than a configuration error, because it lists fine and only fails on click.
</Info>

A shipped provider can still be given the three endpoint keys, and doing so overrides the built-in values. That is the escape hatch for a provider whose endpoints have changed.

### Every provider key

| Key | Type | Default | Meaning |
| --- | --- | --- | --- |
| `enabled` | bool | `true` when absent | Whether the provider is available. |
| `client_id` | str | — | The OAuth client id. **Required for the provider to appear at all.** |
| `client_secret` | str | — | A `secret://NAME` reference, not a literal. |
| `scopes` | list[str] | Provider defaults | Requested scopes. `openid` selects OIDC. |
| `tenant` | str | — | Microsoft only. Which tenant to accept. |
| `authorize_endpoint` | str | Shipped value | Generic providers must set it. |
| `token_endpoint` | str | Shipped value | Generic providers must set it. |
| `userinfo_endpoint` | str | Shipped value | Generic providers must set it. |

`enabled` defaults to enabled when the key is absent, which is a second place where an unset key means "on". A provider card with the switch off and no `enabled` key at all behaves differently, and only the first is what the switch shows you.

<Warning>
Because `enabled` is read as "not explicitly false", writing `"enabled": null` leaves the provider **enabled**. If you are generating this block programmatically, emit a real boolean or omit the key deliberately — do not emit null.
</Warning>

### Credentials as references

**Credentials are referenced as `secret://NAME`, never pasted.** The **Client secret** field's placeholder is `secret://GITHUB_SECRET`, which is the intended shape of the value.

| Approach | Consequence |
| --- | --- |
| `"client_secret": "secret://GITHUB_SECRET"` | The value is resolved at use time from the installation's secrets. |
| `"client_secret": "ghp_abc123..."` | The literal sits in the environment definition, in every export, and in every backup. |

The configuration block is readable, promotable, and included in environment definitions — which makes it the wrong place for anything secret, regardless of how the environment is secured.

<Warning>
A `secret://` reference that does not resolve behaves like a missing credential, which means the provider stops being reported to clients — the same invisible state as an empty `client_id`. Check that the secret exists in *this* environment; a reference that resolves in development may dangle in production.
</Warning>

### What makes a provider "enabled"

This is the rule that produces the most confusing provider symptom, so it is worth stating on its own.

A provider counts as enabled if **both** conditions hold:

1. `enabled` is not explicitly `false` — so absent, `true`, or `null` all pass.
2. `client_id` is present and non-empty.

Both the settings endpoint and the provider builder apply this same filter, which means there is **no partially enabled state**. A provider either appears in the client and works, or it does not appear and 404s when used.

<Warning>
A provider card with every field filled in except the client id looks complete. The switch is on. It simply does not exist as far as any client is concerned, and the failure mode is a *missing button* rather than an error — which is why this is so often misdiagnosed as a client bug.
</Warning>

| In the block | Reported to clients? | Usable? |
| --- | --- | --- |
| `enabled: true`, `client_id` set | Yes | Yes |
| `enabled: true`, no `client_id` | **No** | No — 404 on use |
| `enabled: false`, `client_id` set | No | No — 404 on use |
| `enabled` absent, `client_id` set | Yes | Yes |
| `enabled: null`, `client_id` set | Yes | Yes |

The last two rows are the same shape of surprise as the unset-key rule elsewhere, and the same fix applies: emit a real boolean, or omit it deliberately.

<Info>
Because the filter is on both sides, you cannot have a provider that is listed but broken. That is a good property: a client that renders exactly what it is told will never offer a button that cannot work.
</Info>

### The callback URL

The callback is `{public_url}/auth/v1/callback/{project}/{env}/{provider}`. Both the project and the environment are **in the path**, unlike every other route.

That is because these are browser navigations. A browser cannot carry the gateway-signed context header that every other route uses to learn the environment, so the environment has to be in the URL.

The consequence for configuration is that the same provider has a different callback URL in each environment, and each one must be registered with the provider. `public_url` comes from the environment payload or falls back to Akountz's own setting, which is why it is worth checking after moving an installation behind a different hostname.

## Email templates

The `emails` object overrides the subject and body of each auth message, keyed by kind. Exactly five kinds exist, and each has a default subject and body you can see in Studio.

| Kind | Default subject |
| --- | --- |
| `verify` | `Confirm your email for {project}` |
| `recovery` | `Reset your {project} password` |
| `magic` | `Your {project} sign-in link` |
| `invite` | `You are invited to {organization} on {project}` |
| `email_change` | `Confirm your new email for {project}` |

```json
{
  "emails": {
    "verify": {
      "subject": "Confirm your Acme account",
      "text": "Hi,\n\nConfirm your address to finish setting up Acme:\n\n{link}\n\nIf you did not sign up, ignore this message."
    }
  }
}
```

<Warning>
An unknown kind is ignored rather than rejected, exactly like an unknown top-level key. A typo such as `verifcation` produces no error and no effect — the built-in default is used instead, and you will see your old copy in the inbox.
</Warning>

### Placeholders

Each template may use these, and no others:

| Placeholder | Available in |
| --- | --- |
| `{project}` | All five kinds. The project display name. |
| `{link}` | All five kinds. The action link, already formatted. |
| `{email}` | All five kinds. The address involved. |
| `{organization}` | `invite` only. |
| `{role}` | `invite` only. The role the invite would grant. |

<Info>
An unknown placeholder is **left in the message literally** rather than raising an error. A typo therefore shows up as visible stray text in the delivered mail — `{lnik}` appearing in the body, for instance — rather than as a failed send.
</Info>

That behaviour is a deliberate choice about where a bug should be visible. A template that silently dropped an unknown placeholder would produce a mail with a missing link and no explanation; one that leaves it literal produces a visibly broken mail that somebody notices immediately. The cost is that you will not get a validation error at configuration time.

<Warning>
The plain-text template is also HTML-escaped when the HTML part is generated, and newlines become line breaks, with the `{link}` value wrapped in an anchor. Raw HTML in your template will appear escaped — `<b>` shows as `<b>` rather than rendering bold.
</Warning>

### Delivery

Email goes through the API's mail service, which means it uses the **environment's** SMTP settings. This is the most common cause of "auth emails never arrive", and it is not a template problem.

| Step | Requirement | Symptom if missing |
| --- | --- | --- |
| 1 | The environment's mail service works. | The request succeeds and nothing is delivered. |
| 2 | `site_url` is set. | The mail arrives, on Akountz's own domain. |
| 3 | The address has an account, where relevant. | The response is identical either way, by design. |

<Warning>
A successful response from a recovery or magic-link request proves nothing about delivery — those endpoints answer identically whether or not the address exists, which is the anti-enumeration property. Watch the SMTP side to confirm a message was actually sent.
</Warning>

### Where the link points

`site_url` decides this, and it is worth being clear because the difference is visible to users and confusing the first time you see it.

| `site_url` | Destination |
| --- | --- |
| Set | Your application, at `{site_url}/auth/callback?token=...&type=...` |
| Empty | Akountz's own hosted page, at `{public_url}/auth/v1/links/{project}/{env}/{kind}?...` |

The `type` parameter tells your callback which flow the token belongs to, so one route can dispatch verification, recovery, and magic-link completion without guessing.

When there is no `site_url`, Akountz serves its own page and the flow still completes — the token is consumed and the session issued. It is a working configuration, not a broken one. What you lose is your own branding and your own session handling, because the user never reaches your application.

<Warning>
An environment can be fully functional with no `site_url` and still surprise everybody who expected to land in the product. If you are demoing and users report landing on a Pawabase page, this field is empty — and the fix is **Configuration** → **URLs** → **Site URL**.
</Warning>

### One-time token lifetimes

The links your templates point at are backed by single-use, time-limited tokens, and the lifetime is fixed per purpose rather than configurable:

| Purpose | Lifetime |
| --- | --- |
| `magic` | 15 minutes |
| `mfa` | 5 minutes |
| `link` | 10 minutes |
| `recovery` | 1 hour |
| `verify` | 24 hours |
| `email_change` | 24 hours |
| `invite` | 7 days |

They are ordered by how much the user can be trusted to act promptly. A sign-in link is short because it grants access; a verification link is long because the user may not check their inbox for hours and the link only confirms an address.

Already used, expired, and unknown all produce the same error, which means a double-clicked link and a prefetched one are indistinguishable to the user.

## The configuration cache

Each environment's config is fetched once and cached under a key naming the project and environment, for a TTL that defaults to **ten seconds**.

This is the reason a save in Studio followed by an immediate retry can read the old values. It is short enough to be easy to forget and long enough to reliably catch you in a test script or a fast manual retry.

| Property | Value |
| --- | --- |
| Cache key | `authcfg:{project}:{env}` |
| TTL | `config_ttl`, default 10 seconds |
| Scope | Installation-wide setting, not per environment |
| Cleared by editing? | No. It expires. |

<Warning>
Editing auth settings in Studio can take up to ten seconds to take effect. Any test that saves a setting and immediately asserts on the result will fail intermittently — which is worse than a consistent failure, because it looks like a flake rather than a cache.
</Warning>

Because `config_ttl` is an installation setting rather than an environment setting, you cannot give one environment a shorter cache than another. It also applies to every consumer of the config equally.

<Info>
The cache is why the unset-key behaviour is safe to rely on and also why it is worth checking: the config you inspect may not be the config in force, and neither may be what you just saved.
</Info>

## The platform environment

Not every environment is yours to configure. There is one reserved environment, `_platform`, which holds Studio's own operators — the accounts you sign into Studio with.

It is configured inside Akountz rather than in the API, because the API does not host it. That makes it **hardcoded and not editable from Studio's Configuration tab**. Its values differ from the ordinary defaults, and every difference is deliberate:

| Setting | Ordinary default | Platform value |
| --- | --- | --- |
| `signup_enabled` | `true` | `false` |
| `password_policy` | `"basic"` | `"strict"` |
| `password_min_length` | `8` | `10` |
| `access_ttl` | `900` | `3600` |
| `refresh_ttl` | 30 days | 7 days |
| `magic_link_enabled` | `true` | `false` |

<Info>
Read that table as a statement about what operators are. Nobody self-registers. Passwords must satisfy the full validator at ten characters minimum. Magic-link sign-in — which depends on unattended email delivery to an address that is not the user's day-to-day contact — is off. Sessions last an hour rather than fifteen minutes because an operator session expiring mid-deploy is an operational problem, but not a week because the credential is high-value.
</Info>

<Warning>
If you are looking for a `strict` policy with a ten-character minimum and cannot find where to set it, you are probably looking at the wrong environment's settings. Operators get those values from code, not from a configuration block you can edit.
</Warning>

The first operator is created at startup from installation settings when no operator exists yet. There is no sign-up path into this environment, which is why **signing into Studio does not test your application's sign-in** and vice versa. A Studio operator and an application user are different accounts in different environments with different access. See [Managing users](/auth/managing-users).

## What is not in this configuration

Several settings that look like they belong here are actually installation-wide, configured on the Akountz service rather than per environment. Confusing the two is a frequent dead end.

| Setting | Default | Why it is not here |
| --- | --- | --- |
| `lockout_threshold` | 10 | One lockout policy across every environment on the instance. |
| `lockout_minutes` | 15 | Same. |
| `config_ttl` | 10 | The config cache is a property of the service. |
| `redis_url` | — | Where rate-limit counters live. Infrastructure. |
| `public_url` | — | Where Akountz is reachable. Falls back from the payload. |
| `jwt_master_secret` | — | The secret every per-environment key derives from. Never in a config block. |

<Warning>
The lockout settings are the ones people look for hardest, because the failure counters they operate on are per environment while the thresholds are global. So the *state* is scoped and the *policy* is not, and there is no way to give production a stricter threshold than staging on the same installation.
</Warning>

There is also no `require_aal` key. Requiring a second factor is not an environment setting — it is a decision in your own routes, comparing the `aal` claim on the token.

<Info>
If you need something on this page and it is not here, it is probably either an installation setting or something the environment config has no opinion about because it is enforced elsewhere. The `auth` block governs what the environment *offers*; it does not govern what your policies *allow*.
</Info>

## In Studio

Every one of these keys is edited in one place: your project, your environment, **Users & auth**, then the **Configuration** tab.

The card is titled **"Akountz configuration"** and holds six sections in a fixed order. Its name is deliberate — it says which service these settings govern, which is the ownership point from the start of this page.

<Warning>
The whole page is scoped to the selected environment. Saving in the wrong environment is the single most consequential mistake available in this UI, and nothing warns you about it. Check the selector before you save, every time.
</Warning>

### The six sections

| Section | Studio's own description |
| --- | --- |
| **Sign-up** | *"Who can create an account, and whether their email must be confirmed first."* |
| **Passwords** | *"Password strength and how long sessions last."* |
| **Sign-in methods** | *(no description)* |
| **URLs** | *"Where a browser is allowed to land after an OAuth or magic-link redirect."* |
| **OAuth providers** | *"Social sign-in. Reference credentials as secret://NAME rather than pasting them here."* |
| **Email templates** | *"Subject and body for each auth email. Leave blank to use the built-in default."* |

The descriptions are worth reading once, because they state intent rather than mechanics — and two of them, the OAuth and email ones, tell you the rule you would otherwise get wrong by pasting a literal secret or assuming a blank field is an error.

<Info>
Note that no section exposes raw JSON. Every field has its own control, and the Save button writes the whole block. That is deliberate: a form that only accepted JSON would be one typo away from silently disabling a security feature, and a typo in JSON produces no error at all.
</Info>

### Control by control

Every control, its exact label, its hint, and the key behind it. This is the mapping you want when you are looking at the form and trying to remember which key a field writes.

**Sign-up**

| Label | Type | Hint | Key |
| --- | --- | --- | --- |
| **Sign-up enabled** | Switch | *"Turn off to invite-only new accounts."* | `signup_enabled` |
| **Require email verification** | Switch | *"Unverified users can't sign in until they confirm."* | `require_email_verification` |
| **Default roles** | Tag input | *"Granted automatically at sign-up."* | `default_roles` |

**Passwords**

| Label | Type | Hint | Key |
| --- | --- | --- | --- |
| **Policy** | Segmented **Basic** / **Strict** | — | `password_policy` |
| **Minimum length** | Number, 6–128 | *"Characters."* | `password_min_length` |
| **Access token lifetime** | Number, min 60 | *"Seconds. How long a bearer token works before it needs refreshing."* | `access_ttl` |
| **Refresh token lifetime** | Number, min 3600 | *"Seconds. How long a signed-out-of-band session stays resumable."* | `refresh_ttl` |

**Sign-in methods**

| Label | Type | Hint | Key |
| --- | --- | --- | --- |
| **Magic links** | Switch | *"Passwordless sign-in by emailed one-time link."* | `magic_link_enabled` |
| **MFA (TOTP)** | Switch | *"Let users add an authenticator app for aal2."* | `mfa_enabled` |

<Info>
The number inputs have minimums that quietly protect you: access lifetime cannot go below sixty seconds, and refresh lifetime cannot go below an hour. A value the control rejects is a value that would have produced a broken or unusable session, so the floor is a guard rather than an arbitrary limit.
</Info>

### The Save button

The Save button in the card header is **disabled until something has actually changed**, and it writes the whole block rather than a diff.

Two behaviours follow, and both are worth knowing before your first save.

**Nothing is saved until you save.** Editing fields does not apply anything. If you navigate away without pressing Save, the changes are gone — there is no draft state and no warning on navigation.

**Saving writes everything.** Because the whole block goes back to the environment, a field you did not look at is written with whatever it currently holds. This is safe when the form has loaded the current values, which it does.

<Warning>
Because saving writes the whole block and the page is environment-scoped, a Save performed while the wrong environment is selected is silent and complete. Read the selector, then read the block, then save.
</Warning>

The toast on success reads **Saved**.

<Info>
After saving, remember the cache: the change may not be in force for up to ten seconds. If you are testing by hand, that pause is short enough to be unnoticeable and long enough to make you think the save failed.
</Info>

### The URLs section

Two fields, and the placeholders are the most useful part of it:

| Label | Placeholder | Key |
| --- | --- | --- |
| **Site URL** | `https://app.example.com` | `site_url` |
| **Additional allowed redirect URLs** | `https://staging.example.com/auth/callback` | `redirect_urls` |

The second is a tag input, so each entry is a separate value rather than a comma-separated string. Adding one and saving makes it an additional allowlisted base — it does not become a redirect destination.

<Warning>
Enter the full origin including the scheme. `app.example.com` will not match `https://app.example.com`, because the comparison is textual and the scheme is part of the string. A bare hostname looks right in the field and permits nothing.
</Warning>

### The providers section

Each configured provider gets its own sunken card, with the provider name as the heading and a small row of controls above its fields.

| Label | Type | Key |
| --- | --- | --- |
| **Enabled** | Switch | `enabled` |
| **Scopes** | Tag input, placeholder `openid` | `scopes` |
| **Client ID** | Text | `client_id` |
| **Client secret** | Text, placeholder `secret://GITHUB_SECRET` | `client_secret` |
| **Authorize endpoint** | Text, generic providers only | `authorize_endpoint` |
| **Token endpoint** | Text, generic providers only | `token_endpoint` |
| **Userinfo endpoint** | Text, generic providers only | `userinfo_endpoint` |

The three endpoint fields are hidden for the four shipped providers and shown for anything else, which mirrors the underlying rule exactly: there is nothing to configure for a provider whose endpoints are known.

Removing a provider uses an icon button labelled **Remove {name}**. Adding one uses a dropdown of the shipped providers that are not yet configured, plus a free-text field with the placeholder `custom-provider-name` and an **Add** button for a generic one.

<Warning>
The **Client secret** placeholder is `secret://GITHUB_SECRET`, and that is the shape of value the field wants. A literal pasted here ends up in the environment definition, in every export, and in every backup. Reference the secret instead.
</Warning>

<Info>
The provider name heading is capitalised for display, so a provider you named `gitlab` shows as `Gitlab`. The key in the JSON stays lowercase — the name is a key, and it is matched exactly.
</Info>

### The email templates section

One tab per message kind, then two fields. The tab labels differ slightly from the internal keys, which is worth knowing so you can match them:

| Tab label | Key | Default subject |
| --- | --- | --- |
| **Verify email** | `verify` | `Confirm your email for {project}` |
| **Password recovery** | `recovery` | `Reset your {project} password` |
| **Magic link** | `magic` | `Your {project} sign-in link` |
| **Organization invite** | `invite` | `You are invited to {organization} on {project}` |

</Info>

## Configuring through an API

Studio is a form over the environment's `auth` block, and the block is part of the environment payload. Anything the form can do, an API call can do — which matters for scripted setup and for infrastructure-as-code.

The important constraint is that you must write **whole values for the keys you care about**, and that nulls do not mean what they look like they mean.

```json
{
  "auth": {
    "signup_enabled": false,
    "require_email_verification": true,
    "password_policy": "strict",
    "password_min_length": 12,
    "access_ttl": 900,
    "refresh_ttl": 604800,
    "magic_link_enabled": true,
    "mfa_enabled": true,
    "site_url": "https://app.example.com",
    "redirect_urls": [],
    "providers": {
      "github": {
        "enabled": true,
        "client_id": "Iv1.abc123",
        "client_secret": "secret://GITHUB_SECRET",
        "scopes": ["read:user"]
      }
    },
    "default_roles": ["customer"],
    "emails": {}
  }
}
```

| Writing this | Means |
| --- | --- |
| A boolean `false` | Disabled. |
| An empty list `[]` | No additional redirect bases. |
| An empty object `{}` | No providers, or no email overrides. |
| `null` | **The default**, not "none". |
| An unknown key | Silently ignored. |

<Warning>
Because Studio's Save writes the entire block, an API write that sends only the keys you want to change may replace the rest depending on how the endpoint merges. Read the current block, modify what you need, and write the whole thing back — that is exactly what the UI does and it avoids the ambiguity.
</Warning>

## Per-environment configuration

The `auth` block belongs to one environment, which means each of your environments can behave differently — and usually should.

| Setting | Development | Staging | Production |
| --- | --- | --- | --- |
| `site_url` | `http://localhost:5173` | `https://staging.example.com` | `https://app.example.com` |
| `signup_enabled` | `true` | Mirror production | Product-specific |
| `require_email_verification` | `false` for speed | `true` | `true` |
| Provider `client_id` / `secret` | Your own app | Your own app | The real app |
| `emails` | Defaults | Production copy | Production copy |

The provider case is the one that catches people. OAuth applications are registered per callback URL, and the callback contains the project and environment, so **each environment needs its own registration with the provider**. A staging environment reusing production's client id will fail at the callback with a redirect mismatch.

<Warning>
A `secret://NAME` reference must resolve in the environment that reads it. A secret that exists in development and not in production produces a provider that is silently absent from clients rather than an error — the same invisible state as a missing client id.
</Warning>

### What promotion does and does not carry

Promoting a definition moves configuration between environments. It does not move users, and it does not necessarily move secrets.

| Carried by promotion | Not carried |
| --- | --- |
| The `auth` block, as configuration | Users, in any environment |
| Routes, functions, policies | Sessions |
| Data definitions | Secrets referenced by `secret://` |

<Info>
This is why a production environment that looks correctly configured on paper can still have no users, no working provider, and no deliverable email. Configuration is promoted; the things that depend on it are provisioned.
</Info>

## A security reading of the defaults

Reading the default block as a posture rather than a starting point, because that is what it is in production.

| Default | Risk in production | Change to |
| --- | --- | --- |
| `signup_enabled: true` | Anyone can create an account in your product. | `false` for an invite-only product. |
| `require_email_verification: false` | Addresses are unproven, so recovery and magic links can be aimed at a victim's inbox by whoever registered first. | `true`. |
| `password_policy: "basic"` | Eight characters of anything. | `strict`. |
| `password_min_length: 8` | Low, on its own. | 12 or more. |
| `refresh_ttl: 30 days` | A stolen refresh token is useful for a month. | 604800, or shorter. |
| `site_url: ""` | Links land on Akountz's own domain. | Your origin. |
| `providers: {}` | No provider compromise risk. | Fine as-is. |

<Warning>
`require_email_verification: false` combined with `magic_link_enabled: true` is the pair worth examining hardest. Magic links grant access by email, so an unverified address means anybody who registers with somebody else's address can receive a link that signs them in as that address's owner.
</Warning>

Two defaults deserve defence rather than change. `mfa_enabled: true` is good — it permits enrolment, which costs nothing and lets users opt in. `access_ttl: 900` is a reasonable balance; lower it if your compliance requirements demand faster revocation, and understand that it is the bound on how long a removed role keeps working.

## Before you launch

Not a numbered procedure — a set of things that are each individually easy to miss and collectively account for most of the authentication problems that reach production.

**`password_policy` is `strict`.** Not `basic` with a longer minimum. Under `basic`, length is the only rule, and length alone is a weak control.

**`require_email_verification` is on** for anything with real user data, and especially if magic links are available.

**`site_url` is your production origin**, with the scheme, and users landing on your application rather than Akountz's.

**Provider secrets are `secret://` references**, and each environment has its own OAuth registration with a matching callback.

**`default_roles` names roles that exist**, or new accounts will carry a role that grants nothing.

**The environment's mail service works.** Every flow that depends on a link — verification, recovery, magic link, invitations, email change — depends on it, and none of them report delivery failures in their responses.

**`refresh_ttl` is shorter than thirty days** if the data warrants it.

**`access_ttl` matches your revocation requirements**, because it is the bound on how long a removed permission keeps working.

**You have read the block back** after saving, and compared it against the defaults above to see every deliberate change.

<Warning>
The last item is the one people skip. Reading the block back is the only way to catch a typo'd key, since unknown keys are silently ignored and a key you meant to disable may never have been written at all.
</Warning>

## What goes wrong, and why

The configuration failures that recur, ordered roughly by how often they are reported.

### "I turned it off and nothing changed"

Three causes, and they are distinguishable.

**The key was never set to false.** Removing a key, or setting it to `null`, restores the default — and the default is on for sign-up, magic links, and MFA. This is the most common cause by a wide margin.

**The cache.** The change may not have reached Akountz yet. Wait ten seconds and retry before concluding anything.

**It was typed rather than toggled.** A quoted `"false"` is a non-empty string, which is truthy. Use a real boolean.

<Warning>
There is no error for any of these. A feature that stays on after you disabled it produces exactly the same response as a feature that never heard of your change. Compare your block against the defaults table and the difference will be obvious — usually the key you are looking at is simply absent.
</Warning>

### "The client shows no provider buttons"

`GET /auth/v1/settings` reports only providers that are enabled *and* have a client id, and using one that is missing from that list returns a 404 saying it is not enabled. There is no state in between, so the button simply is not rendered.

| Cause | How to confirm |
| --- | --- |
| The provider is absent from the block. | **Configuration** → **OAuth providers**. |
| **Enabled** is off. | The switch in the provider card. |
| **Client ID** is empty. | The card looks otherwise complete. |
| The `secret://` reference does not resolve. | Behaves like a missing secret. |
| You are looking at a different environment. | The selector. |
| The client cached the settings response. | Re-fetch and compare. |

<Warning>
The third case is the one that gets misdiagnosed as a client bug. A provider card with every field filled in except the client id looks finished, and the switch is on. But the provider does not exist as far as any client is concerned, and the only symptom is a missing button.
</Warning>

### "Redirects land on the wrong page"

Almost always `site_url`, and the symptom tells you which way it is wrong.

| Symptom | Cause |
| --- | --- |
| Users land on an Akountz-hosted page. | `site_url` is empty. |
| Users land on your staging app from production. | `site_url` was promoted from staging. |
| A 400 saying the redirect is not allowed. | The target is outside the allowlist. |
| A 400 only for one specific page. | That path is not beneath an allowlisted base. |

The last two are the allowlist rule rather than the destination, and they are distinguished by whether the *base* is right while a particular *target* beneath it is not.

<Warning>
Promoting `site_url` from staging to production is a real and common mistake, because the value looks correct in staging and is silently wrong in production. If users reach the wrong application, compare `site_url` against the environment you are actually serving.
</Warning>

### "Auth emails never arrive"

Three independent requirements, and a successful response tells you none of them.

**The environment's mail service works.** Delivery goes through the API's mail service using the environment's SMTP settings. If it is not configured, the request succeeds and nothing is sent. Editing a template does not help.

**`site_url` is set.** Otherwise the message is delivered but points at Akountz's own hosted page, which is a different symptom — the mail arrives.

**The address has an account,** where the flow requires one. The recovery and magic-link endpoints answer identically either way, by design.

<Warning>
A 200 from a recovery or magic-link request is not a delivery receipt. That uniformity is the anti-enumeration property described under `require_email_verification`, and it is worth remembering before concluding from an API response that a mail went out.
</Warning>

When the mail arrives but the link fails, it is nearly always the single-use rule. Already used, expired, and unknown produce the same error, so a double-click or a mail-client prefetcher is indistinguishable from an expiry.

### "New users have no permissions"

The account was created and signed in successfully, and then every operation is denied.

Almost always `default_roles` — either empty, or naming a role that does not exist. A role name that does not exist is assigned by name without error, so the user carries a role granting nothing and nothing tells you.

The second possibility is timing. Roles are read when a token is issued, so a role added to `default_roles` does not appear on accounts created before the change. Nothing back-fills.

<Warning>
Check the role exists in the **Roles** tab of the same environment before assuming the configuration is wrong. `default_roles` is not validated against the role list at save time, so a typo produces no warning and produces useless accounts.
</Warning>

### "Enrolled users stopped being challenged"

You turned `mfa_enabled` off, or promoted an environment where it is off. Enrolled users are no longer challenged and their sessions drop to `aal1`, while unenrolled users notice nothing.

This is the one switch whose effect is backwards from intuition: it harms the users who did the right thing and is invisible to everybody else.

<Warning>
If any of your policies require `aal2`, turning `mfa_enabled` off will start denying exactly the users who enrolled. Check your `aal` requirements before touching this switch.
</Warning>

### "The setting is right in Studio but the API disagrees"

Confirm which environment you are looking at before anything else. The Configuration tab, the API key you are calling with, and the endpoint you are hitting are three independent selectors, and the most common version of this bug is a configuration in one environment being tested with a key from another.

After that, wait out the cache. And then read the block back from the API rather than trusting the form — unknown keys are dropped silently, so the form may be showing a value the payload never received.

## Depth, on demand

Three questions that come up repeatedly and are worth answering properly rather than approximately.

<AccordionGroup>
  <Accordion title="Why are the defaults permissive rather than safe?">
    Because the config is consumed by a service that cannot distinguish "deliberately set" from "never decided", and it resolves the ambiguity toward the option that does less harm if wrong in the other direction. Sign-up on means a developer who forgot to configure anything can still sign a user up; sign-up off means a developer who forgot to configure anything has shipped a product nobody can register for, which they will notice immediately.

    The cost is that a deployment nobody looked at is wide open. That is the right trade for a default, and it is why the security reading above exists — but it does mean the configuration is something to review rather than something to accept.
  </Accordion>
  <Accordion title="Why does turning mfa_enabled off affect only enrolled users?">
    Because the switch does not decide whether a second factor exists — the user's enrolment does. The switch decides whether enrolment is permitted and whether an enrolled user is challenged. Turning it off leaves every factor in place and stops asking for it.

    That produces the counter-intuitive outcome where the users who protected themselves are the only ones affected. It also means turning it back on restores the challenge immediately, with no re-enrolment, because the factors were never removed.
  </Accordion>
  <Accordion title="Why does Studio write the whole block rather than a diff?">
    Because the block is small, the form loads the current values before you edit anything, and a whole-block write has no merge semantics to get wrong. A diff would need to define what a key's absence means on an update — and given that absence already means "the default", the two cases would be indistinguishable.

    The practical consequence is that reading the block back after saving is worth doing, and that an API write should follow the same discipline: read, modify, write back the whole thing.
  </Accordion>
</AccordionGroup>

## Configuring an environment from scratch

A worked shape, for an environment nobody has configured yet. The order is not a procedure — it is roughly the order in which dependencies bite.

**An application URL, so redirects have somewhere to land.** `site_url` set to the application's origin, with the scheme. Nothing else in the configuration works properly without it, and an empty value produces Akountz-hosted pages that look like a bug.

**A password policy worth the name.** `strict`, with a minimum of twelve or more. The `basic` default is a length check and nothing else.

**Verification, if the product holds real data.** `require_email_verification` on, because every link-based flow depends on the address belonging to whoever holds it.

**Sign-up, deliberately.** Either off for an invite-only product, or on with `default_roles` naming roles that actually exist — the second row of that pair is the one that gets skipped, and it is what produces accounts that can sign in and do nothing.

**Lifetimes matched to the risk.** `access_ttl` sized against how long a removed permission may keep working; `refresh_ttl` sized against how long a stolen refresh token is acceptable.

**Providers, only if you need them.** Four shipped names, credentials as `secret://` references, and a separate OAuth registration per environment because the callback URL contains the project and environment.

**Email copy, once the flows work.** Overrides per kind, with placeholders checked. Editing templates before mail delivery works just moves the failure.

**Then read the block back.** Thirteen keys, and comparing what you wrote against the defaults shows every deliberate change and every typo'd key at once.

```json
{
  "signup_enabled": false,
  "require_email_verification": true,
  "password_policy": "strict",
  "password_min_length": 12,
  "access_ttl": 900,
  "refresh_ttl": 604800,
  "magic_link_enabled": true,
  "mfa_enabled": true,
  "site_url": "https://app.example.com",
  "redirect_urls": [],
  "providers": {
    "github": {
      "enabled": true,
      "client_id": "Iv1.abc123",
      "client_secret": "secret://GITHUB_SECRET",
      "scopes": ["read:user"]
    }
  },
  "default_roles": ["customer"],
  "emails": {}
}
```

<Warning>
The one thing this block cannot express is whether `customer` exists. `default_roles` is not validated against the role list, so a typo produces accounts carrying a role that grants nothing, and no error anywhere. Create the roles first, in the **Roles** tab of the same environment.
</Warning>

## The route surface, for reference

Which endpoints read these settings, and which of them consult which key. Useful when you are tracing "which setting controls this behaviour".

| Route | Settings it reads |
| --- | --- |
| `GET /auth/v1/settings` | `signup_enabled`, `require_email_verification`, `magic_link_enabled`, `mfa_enabled`, `enabled_providers()`, `password_policy`, `password_min_length` |
| `POST /auth/v1/signup` | `signup_enabled`, `redirect_allowed`, `require_email_verification`, `default_roles`, the password policy, `access_ttl`, `refresh_ttl` |
| `POST /auth/v1/token` | `require_email_verification`, `mfa_enabled`, `password_*` at change time only, `access_ttl`, `refresh_ttl` |
| `POST /auth/v1/recover` | `emails.recovery`, and `site_url` for the link |
| `POST /auth/v1/recover/confirm` | The password policy |
| `POST /auth/v1/magic-link` | `magic_link_enabled`, `emails.magic`, `site_url` |
| `POST /auth/v1/verify/request` | `emails.verify`, `site_url` |
| `GET /auth/v1/authorize/...` | `providers`, `redirect_allowed`, `public_url` |
| `GET /auth/v1/callback/...` | `providers`, `signup_enabled`, `site_url` |
| `GET /auth/v1/user`, `PATCH` | The password policy, `emails.email_change`, `site_url` |
| `POST /auth/v1/identities/link` | `providers`, `site_url` |

Two patterns in that table are worth naming.

**The settings endpoint is deliberately incomplete.** It reports what a client needs in order to render a sign-in screen, and nothing else. There is no list of roles, no user, and no token — it is a public description of the environment, callable before sign-in.

**`site_url` appears wherever a link is built.** Verification, recovery, magic link, invitations, email change, and identity linking all consult it, because all of them produce a URL that a browser will follow.

<Info>
The admin routes under `/projects/{project}/envs/{env}` do not read most of these keys, because they act on users rather than admitting them. Creating a user applies the password policy; everything else about an account's sign-in behaviour comes from the settings above.
</Info>

## Choosing values deliberately

The defaults are a starting point. These are the decisions worth making consciously rather than inheriting.

| Decision | The tension |
| --- | --- |
| Sign-up on or off | Open growth versus who may hold an account. |
| Verification required | Deliverability risk versus address ownership. |
| `basic` or `strict` | Onboarding friction versus credential strength. |
| Minimum length | Longer is better, up to the point users reuse a shorter one anyway. |
| `access_ttl` | Refresh load versus how long a removed permission survives. |
| `refresh_ttl` | Convenience versus exposure of a stolen credential. |
| Magic links on | Removes credential risk; adds dependence on mail delivery. |
| MFA available | Costs nothing until users opt in; requires offering enrolment. |
| `default_roles` | Convenience versus a wrong name granting nothing. |

Three of these have consequences that are not obvious from the setting itself:

**Verification versus deliverability.** Requiring confirmation means a user cannot use the product until they find the mail. If your mail service is flaky, you have converted a delivery problem into a sign-up problem.

**Length versus composition.** Raising `password_min_length` under `basic` buys length without strength. The same characters under `strict` buy both, because the validator assesses the whole password rather than counting it.

**Refresh lifetime versus convenience.** A long `refresh_ttl` means users are not asked to sign in again for weeks. It also means a stolen refresh token is useful for weeks — until it is used, at which point the whole family dies and both parties are signed out.

<Warning>
Whichever values you choose, they belong in the environment's `auth` block rather than in your client. A client that hardcodes an assumption about the policy, the lifetimes, or which methods exist will break the moment an operator changes any of them — and it will break in the environment you did not test.
</Warning>

## Auditing an environment

When you inherit an environment, or review one before a launch, the useful move is to compare the live block against the defaults rather than reading it top to bottom. Every difference is either a decision somebody made or a mistake, and the defaults tell you which features are running unexamined.

| If you find | It means |
| --- | --- |
| `password_policy` absent or `"basic"` | Nobody chose a policy. Eight characters of anything is in force. |
| `require_email_verification` absent | Addresses are unproven, and every emailed link flow inherits that. |
| `site_url` empty | Redirects land on Akountz's own pages. |
| A provider with no `client_id` | A provider that looks configured and is invisible to every client. |
| `default_roles` naming an unknown role | New accounts carry a role granting nothing. |
| `emails` empty | Users receive the built-in copy, which mentions the project name only. |
| `access_ttl` very high | Removed permissions stay live for that long. |
| `refresh_ttl` at 2592000 | The thirty-day default, which is long for anything sensitive. |

Three questions settle most of it:

**Which keys are absent?** Anything absent is running on a default you did not choose. In a block where several keys are absent, the environment has been partially configured rather than deliberately set up.

**Which keys are present but null?** Null means the default, so a key that looks configured is not. This is the failure the config format makes possible and the one a visual review is most likely to miss.

**Do the role names exist?** `default_roles` is not validated against the Roles tab, so this needs checking by hand. It is the only item on this list where the configuration is silently wrong rather than silently default.

<Warning>
An audit that reads the block in Studio can miss a null, because the form renders a null as its default value. Read the block through an API if you are auditing rather than editing — the form tells you what the controls would write, not necessarily what is stored.
</Warning>

## Promotion and drift

Promoting a definition from one environment to another moves the `auth` block. That is convenient until the environments are supposed to differ, at which point the promotion either overwrites a deliberate difference or is blocked by one.

The keys that normally *should* differ, because they name the environment itself:

| Key | Why it differs |
| --- | --- |
| `site_url` | The application's origin differs per environment. |
| `providers.*.client_id` | Each environment registers its own OAuth application. |
| `providers.*.client_secret` | A `secret://` reference that must resolve per environment. |
| `emails` | Often tuned to the environment — a staging notice, a real domain. |

The keys that normally should *not* differ, because a difference is a bug:

| Key | A difference means |
| --- | --- |
| `password_policy`, `password_min_length` | Staging accepts passwords production rejects, so staging tests mislead. |
| `require_email_verification` | Same, for the verification flow. |
| `signup_enabled` | Legitimate to differ, but often accidental. |
| `access_ttl`, `refresh_ttl` | Different session security between environments, usually unintended. |

<Warning>
`site_url` promoted from staging to production is the single most consequential drift in this block: the value is correct in the environment it came from and silently wrong in the one it lands in, and users reach the wrong application without any error.
</Warning>

| What promotion carries | What it does not |
| --- | --- |
| The `auth` block | Users, in any environment |
| Routes, functions, policies | Sessions |
| Data definitions | Secrets referenced by `secret://` |
| — | Anything provisioned per environment |

<Info>
The practical consequence is that a correctly promoted environment can still have no users, no working provider, and no deliverable email, and look entirely correct in a config review. Configuration is promoted; the things that depend on it are provisioned.
</Info>

### Secrets do not travel

A `secret://NAME` reference is a name, not a value. The name travels with the configuration; whether it *resolves* is a property of the environment that reads it.

That produces the same failure mode as a missing `client_id`: the provider stops being reported to clients and 404s on use, with no error anywhere in the configuration. The distinction is that the configuration looks entirely correct.

| Situation | Result |
| --- | --- |
| The secret exists in both environments. | Works after promotion. |
| The secret exists in development only. | The provider is silently absent in production. |
| The reference is misspelled. | Same, in every environment. |

<Warning>
A dangling `secret://` reference and an empty `client_id` produce the identical symptom — a missing provider button — for entirely different reasons. If a provider is invisible, check both, and check them in the environment you are actually serving rather than the one you configured.
</Warning>

## Terms, precisely

| Term | Means |
| --- | --- |
| **`AuthConfig`** | One environment's authentication settings, with defaults applied. |
| **`auth` block** | The settings object inside an environment payload. Thirteen configurable keys. |
| **Akountz** | The identity service. Reads the `auth` block; never writes it. |
| **Environment** | One `project` + `env` pair. The unit of tenancy and of configuration. |
| **Platform environment** | The reserved `_platform` environment holding Studio's operators. Not configurable. |
| **`redirect_allowed`** | Whether a URL may receive tokens: the site URL or an allowlisted prefix. |
| **`enabled_providers()`** | The providers reported to clients — enabled *and* with a client id. |
| **`secret://NAME`** | A reference to a stored secret, used instead of a literal credential. |
| **`config_ttl`** | Seconds an environment's config is cached. Default 10. Installation setting. |
| **`aal`** | Authentication assurance level. `aal1` normally, `aal2` after MFA. |

<Warning>
`signup_enabled`, `magic_link_enabled`, and `mfa_enabled` all default to **on**, and all three treat an explicit `null` as absent. That single behaviour, repeated across the block, is responsible for most of the confusion this page exists to prevent.
</Warning>

## What to take away

Five things.

**An unset key is the default, not "off".** And `null` counts as unset. The permissive defaults mean that clearing a value is not the same as disabling it.

**Only the API writes this block; Akountz only reads it.** That is why there is no validation on unknown keys and no error when a feature you disabled stays on.

**Configuration is cached for ten seconds.** A save followed by an immediate retry can read the old values, and no test should assert on a setting in the same breath as changing it.

**The platform environment is not yours.** `_platform` is hardcoded, holds Studio's operators, and is why signing into Studio does not test your application's sign-in.

**Each environment needs its own everything.** Site URL, OAuth registrations, secret references, and users. Promotion moves configuration and nothing else.
