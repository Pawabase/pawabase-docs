A role, in Pawabase, is a **group with permissions attached**. That is the whole idea, and it is worth saying precisely because the word "role" suggests a model that does not exist here.

There is no `Role` model. There is no `RoleAssignment`. A role is a row in `perm_groups` together with rows in `perm_group_permissions`, and belonging to one is a row in `perm_user_groups`. Permissions can also be attached to a person directly, through `user_permissions`, with no group involved at all.

Everything else on this page follows from that. Two people can have identical effective access while holding entirely different records — one through a group, one through direct grants — because nothing requires access to arrive in a particular shape.

## Where this sits in the layered model

| Layer | What it does for permissions |
| --- | --- |
| **Akountz** (identity) | Owns the five tables. Defines roles, assigns them, resolves effective permissions, and stamps them into tokens. |
| **The API** (project config) | Owns `default_roles` — the roles granted at sign-up. Nothing else. |
| **Gateway / `pawabase_core`** | Verifies the token and exposes the claims. It never queries the permission tables. |

The permissions in an access token were read when the token was issued. No service re-reads the tables on each request, which is what makes enforcement cheap and also what makes a change take time to land. Both facts matter throughout this page.

<Info>
If you have not read [Authentication](/auth/overview), do that first — in particular the per-environment tenancy rule, since it is what makes the name-scoping rule below necessary.
</Info>


## The five tables

Sillo provides the permission model; Akountz re-keys it to ULIDs and renames the tables. Same columns, same methods, different primary key.

| Model | Table | What a row is |
| --- | --- | --- |
| `Permission` | `permissions` | A named capability, such as `posts:write`. |
| `Group` | `perm_groups` | A named collection of permissions. This is what a role is. |
| `UserPermission` | `user_permissions` | A capability granted straight to one person. |
| `UserGroup` | `perm_user_groups` | Membership: this person belongs to that group. |
| `GroupPermission` | `perm_group_permissions` | One capability inside one group. |

Two constraints are load-bearing:

| Model | Uniqueness |
| --- | --- |
| `UserGroup` | `(user_id, group)` — a person cannot join the same group twice. |
| `GroupPermission` | `(group, permission)` — a group cannot hold the same permission twice. |

Both prevent the duplicate rows that would otherwise make a member count wrong or a permission list noisy. They are enforced by the database rather than by the application, so they hold however the rows were created.

<Note>
`AuthUser` inherits Sillo's `PermissionMixin`, which supplies the relation methods these tables rely on. The mixin is why `Permission.of(user)` and `Group.of_user(user)` exist without any of that being written in Akountz.
</Note>


## Why names carry their environment

Sillo's `Permission` and `Group` names are unique across the whole database. Akountz serves many projects and environments from one installation, so a bare name would collide — a `editor` in staging could not exist alongside an `editor` in production.

The solution is a prefix, applied on the way in and stripped on the way out.

```text
Stored:     acme/production/editor      Returned:   editor
Stored:     acme/staging/editor         Returned:   editor
```

The prefix is `{project}/{env}/`, applied by one function and removed by another. Both are in `app/rbac.py`, and every name crossing the API boundary goes through them.

| Property | How the prefix delivers it |
| --- | --- |
| Two environments can both have `editor`. | Different stored names, so no collision. |
| Listing one environment's roles is a prefix query. | `name__startswith="acme/production/"`. |
| A user only sees their own environment's roles. | The strip function drops anything without the prefix. |
| A role name is never ambiguous in the database. | The prefix makes it globally unique. |

The strip function is worth reading closely, because it filters rather than trusting:

```python
def _strip(project: str, env: str, names: list[str]) -> list[str]:
    prefix = f"{project}/{env}/"
    return sorted({name[len(prefix):] for name in names if name.startswith(prefix)})
```

Names without the prefix are dropped, so a caller cannot be shown another environment's role even if such a row existed. And the result is deduplicated and sorted, so the order is stable regardless of insertion order.

<Warning>
This is a filter, not a permission check. If a user somehow belonged to a group in another environment, that group would be hidden from `roles_of` rather than reported as an error. The tenancy rule prevents the situation arising; this code makes the failure mode silent rather than leaky.
</Warning>

### Permissions follow the same rule

Permission names are prefixed identically, so a permission granted in staging does not satisfy a check for the same name in production. A policy checking `posts:write` sees only permissions belonging to the environment that issued the token.


## Defining a role

A role is a name, an optional description, and a list of permission names. The definition is **declarative**: the list you send becomes the role's permission set.

| Input | Meaning |
| --- | --- |
| `name` | Must match `^[a-z][a-z0-9_:-]{0,62}$` — a lowercase letter, then up to 62 characters of lowercase letters, digits, underscore, colon or hyphen. |
| `description` | Free text. Defaults to empty. |
| `permissions` | A list of names. An empty list is meaningful: it creates a role granting nothing. |

What the definition does, in order:

1. Finds or creates the group, named with the environment prefix.
2. Reads the group's current permissions.
3. Defines any permission in the new list that does not exist yet.
4. Adds the new ones and removes those no longer listed.
5. Updates the description if it changed.

The list is therefore the desired end state, not a set of additions. Omitting a permission removes it from the role.

<Warning>
That is the behaviour to watch when editing in Studio. Removing a name from the comma-separated field and saving takes that permission away from everyone in the role, for every session they refresh into. There is no confirmation step and no history.
</Warning>

### Permissions are created on demand

Naming `reports:export` in a role creates the `permissions` row if it is missing, so there is no separate "create the permission first" step.

The name is stored with the environment prefix, and no pattern is enforced on it — the pattern above applies to role names only. A permission can be any string, including one with uppercase letters or spaces, though naming conventions are worth keeping consistent yourself.

<Note>
Because permissions are created implicitly, a typo becomes a real permission that nobody holds. A policy checking `post:write` while the role grants `posts:write` fails, and nothing reports the near-miss. Read the permission badges on the role when you verify, rather than trusting your own spelling.
</Note>


## Assigning and revoking

| Operation | What it does |
| --- | --- |
| Assign a role | Adds a `UserGroup` row. Creates the group first if it does not exist. |
| Revoke a role | Removes the `UserGroup` row. Does nothing if the row is absent. |
| Grant permissions | Defines each named permission if needed, then attaches it to the person directly. |
| Revoke permissions | Removes the direct grant. Does nothing if absent. |

Two behaviours here catch people out, and both follow directly from the code.

**Assigning a role that does not exist creates it.** The assignment function looks the group up, and if it finds nothing it defines a new one with no permissions and then adds the person to it. So a typo in a role name silently produces an empty role rather than an error.

<Warning>
This is the single most common way to end up with a role that grants nothing. A user listed as `edior` is a member of an empty group called `edior`, and the real `editor` role is untouched. Check the Roles tab for the environment — an unexpectedly empty role is the evidence.
</Warning>

**Revoking is silent.** Neither revoke operation reports whether anything was removed. A typo in the name being revoked is a no-op, not a 404.

### Assigning a whole set

When an administrator saves a user's roles, the update route computes the difference: roles in the new set that the user lacks are assigned, and roles the user holds that are absent from the new set are revoked.

That means the field is the **desired full list**, not a set of additions. To add `payroll` to someone who should remain an employee, `employee` has to stay in the field.

### Granting directly

Direct grants exist for the exception case — one person needs one extra capability, and creating a role for it would be noise. The grant function defines each permission if it is missing and then attaches it to the person.

Direct grants and group permissions are indistinguishable at enforcement time. Both appear in the same `perms` claim, and a policy cannot tell which produced an entry.


## Effective access

A person's access is the union of two sources: their direct grants, and the permissions of every group they belong to.

```python
async def permissions_of(user: AuthUser) -> list[str]:
    direct = await Permission.of(user)
    via_groups: list[str] = []
    for group in await Group.of_user(user):
        via_groups.extend(await group.get_permissions())
    return _strip(user.project, user.env, [*direct, *via_groups])
```

| Property | What it means in practice |
| --- | --- |
| Union, not intersection. | A permission from any group suffices. |
| No inheritance between roles. | Being in `manager` does not imply `employee`. Assign both, or repeat the permissions. |
| No deny rules. | Nothing subtracts a permission. Removing it from every source is the only way. |
| Deduplicated and sorted. | A permission reached two ways appears once. |
| Environment-filtered. | Anything without the prefix is dropped. |

<Warning>
There is no deny mechanism anywhere in this model. If you need "everyone can read posts except contractors", you express it by not granting the permission and then handling the exception separately — not by granting it broadly and subtracting it.
</Warning>

### No inheritance

Roles are flat. A manager who should also be able to do what employees do needs both roles assigned, or the employee's permissions repeated in the manager role.

| Structure | Result |
| --- | --- |
| `manager` holds `reports:export`; person is in both `employee` and `manager`. | Works. |
| `manager` holds `reports:export`; person is in `manager` only. | Works for the export, but nothing employee-level. |
| `manager` holds `reports:export` and every employee permission. | Works, but the two roles must be kept in step by hand. |

The second row is the trap. It looks like it works until someone tests an employee-level action and finds it denied, because the role name implied a hierarchy that does not exist.

### Reading a user's access

The admin view of a user — what Studio and service keys get — includes both `roles` and `permissions`:

```json
{
  "id": "01JQ7Z3M9K4YB2XQ8V0N5T6RJPD",
  "email": "grace@example.com",
  "roles": ["employee", "manager"],
  "permissions": [
    "expenses:approve",
    "expenses:submit",
    "leave:review",
    "leave:submit",
    "reports:export"
  ]
}
```

The `permissions` array is the resolved union, with the environment prefix removed. It is the authoritative answer to "what can this person do", and it is worth using rather than recomputing it from roles in your own tooling.

The ordinary user-facing view includes `roles` but **not** `permissions`. A signed-in person asking who they are sees their roles and their own profile, not the resolved capability list.


## In the access token

Permissions reach downstream services as two claims, and both are read at issue time.

| Claim | Source |
| --- | --- |
| `roles` | The groups the person belongs to, prefixed and stripped. |
| `perms` | The resolved union, prefixed and stripped. |

Also on the token, and relevant to authorization decisions: `aal` for the assurance level, and `org` with `org_role` for the organization's membership role.

<Warning>
Because the claims are a snapshot, a permission change does not take effect until the person's token is refreshed. With the default 15-minute access lifetime, that is up to 15 minutes of the old access remaining valid. Revoking a person's access is therefore not instant — it requires either waiting, or revoking the sessions explicitly.
</Warning>

### The three-way refresh behaviour

Refreshing re-reads roles and permissions, so a grant lands on the next refresh. The `org` field on the refresh request has a three-way behaviour that is easy to get wrong, because it is expressed with a sentinel rather than a null:

| What you send | What happens |
| --- | --- |
| An organization slug | Switches the session to that organization. |
| `null` explicitly | Clears the organization. |
| The field omitted entirely | Keeps the current one. |

The module-level sentinel that expresses the third case is used because "not provided" and "explicitly null" are different in JSON but would otherwise be indistinguishable once parsed.
