Three worked shapes, drawn from products people actually build, with the trade-off named for each.

### Support and operations

```json
{
  "name": "support",
  "description": "Can read anything and act on accounts; cannot delete data",
  "permissions": [
    "accounts:read",
    "accounts:disable",
    "reports:read"
  ]
}
```

The point of not granting `*` here is that the next permission your product adds — a delete, a payout, a bulk export — is not automatically live for the support team on the day you write it.

<Warning>
The temptation to give support `*` because it is faster is the most common long-term mistake in this area. It feels safe because nobody has been hurt yet, and it is exactly the arrangement that turns a small new permission into an incident.
</Warning>

### Two tiers and an override

```json
{ "name": "viewer",  "permissions": ["records:read"] }
{ "name": "editor",  "permissions": ["records:read", "records:write"] }
{ "name": "admin",   "permissions": ["records:read", "records:write", "records:delete"] }
```

Note that `editor` repeats `records:read` rather than inheriting it, because there is no inheritance. That repetition is the price of a flat model, and it is small until you have twenty permissions and five tiers — at which point you should reduce the number of tiers rather than automate the copying.

### Least privilege by cohort

```json
{ "name": "customer",   "permissions": ["orders:read:own", "orders:create"] }
{ "name": "staff",      "permissions": ["orders:read", "orders:update"] }
{ "name": "auditor",    "permissions": ["orders:read"] }
```

Encoding the scope in the permission name — `orders:read:own` rather than `orders:read` plus a condition — pushes the rule into the permission itself. It is more names to manage, but each policy stays a single test and there is nothing to forget to add.

| Approach | Cost |
| --- | --- |
| Scope in the permission name. | More names; each policy is one term. |
| Scope in a policy condition. | Fewer names; every policy must remember the condition. |

<Note>
If you choose the second, write the condition into a reusable form rather than retyping it. A policy that checks the permission but forgets the ownership test is the classic half-implemented authorization bug.
</Note>

### An override that is really a direct grant

One contractor needs `reports:export` for a month. Creating a role for it leaves a role with one member that nobody remembers to remove later.

### An override that is really a direct grant

| | A role for one person | A direct grant |
| --- | --- | --- |
| Visible on the user. | As a role badge. | In its own list, labelled. |
| Easy to find later. | No — check every role's members. | Yes — one list on one user. |
| Reversible. | Remove them from the role. | Click the cross. |
| Scales past one person. | Yes. | You end up with a role anyway. |


## Frequently asked questions, second pass

<AccordionGroup>
  <Accordion title="Does a role need to exist before a user can be assigned to it?">
    No, and that is a trap. Assigning an undefined name creates the role with no permissions and adds the person to it, so the assignment "succeeds" and grants nothing.
  </Accordion>
  <Accordion title="Can two roles hold the same permission?">
    Yes. There is a uniqueness constraint on the pair within a group, not on the permission across groups. Two roles may both hold `reports:read`, and a person in both still sees it once in their resolved list.
  </Accordion>
  <Accordion title="Can a person belong to a role twice?">
    No. Membership is unique on the person and group, so a second assignment is a no-op rather than a duplicate row.
  </Accordion>
  <Accordion title="What does the admin roles listing return besides roles?">
    It returns the environment's full set of defined permissions as well, which is what lets the editing form show you every permission in this environment rather than only the ones currently in use.
  </Accordion>
  <Accordion title="Are permissions ever deleted?">
    Not by editing a role or by deleting one. Deleting a role removes its memberships and the group; the permission rows survive so they can be reused. Pruning unused permission rows is a database-level decision, not an API one.
  </Accordion>
  <Accordion title="Is a role name case-sensitive?">
    It is stored as given and compared exactly, so `Editor` and `editor` would be different groups — except that the name pattern requires a lowercase first letter, so `Editor` is rejected at the route.
  </Accordion>
  <Accordion title="Can I set a role's name from a script after creating it?">
    Not by updating the field: the name is the key of a create-or-replace operation and the field is disabled in Studio. Create the new one, move the members, delete the old one.
  </Accordion>
  <Accordion title="Why does the resolved permissions list look sorted?">
    Because the resolver deduplicates and sorts as its last step. Do not rely on the order for anything; it is stable, not meaningful.
  </Accordion>
  <Accordion title="Does a user's roles list appear in the access token?">
    Yes, as `roles`, with the environment prefix removed. The user-facing profile endpoint returns it too, so a client can render a role-based interface without decoding the token.
  </Accordion>
  <Accordion title="Does the user-facing profile include permissions?">
    No. The profile returns `roles`; the resolved `permissions` array is part of the admin view, used by Studio and by service keys.
  </Accordion>
  <Accordion title="Are the permissions themselves deleted with a role?">
    No. The permission rows survive, so they remain available to other roles and to direct grants. Only the group and its memberships go.
  </Accordion>
  <Accordion title="Can I rename a role?">
    Not by editing the name field — it is disabled for an existing role, and the admin route takes the name as the key of a create-or-replace operation. To rename, create the new role, assign it to the same people, then delete the old one.
  </Accordion>
  <Accordion title="Do I need to define a permission before using it in a policy?">
    No. A policy can name a permission that does not exist; it simply never matches. Definition happens implicitly when a role or a grant mentions it.
  </Accordion>
  <Accordion title="Why does the user view show permissions I never granted?">
    Because it shows the resolved union across every group the person belongs to. Look at the roles to explain it, and at **Direct permissions** to find anything that did not come from a role.
  </Accordion>
  <Accordion title="Can a role name be the same in two environments?">
    Yes, and that is the point of the prefix. They are separate groups with separate memberships and separate permissions, and neither can be seen from the other.
  </Accordion>
  <Accordion title="Is there a way to make a change take effect immediately?">
    Not for an access token that already exists. Revoke the person's sessions, which ends the refresh path; the current access token then has only its remaining lifetime. Otherwise the change lands on the next refresh.
  </Accordion>
</AccordionGroup>


## Permissions in every policy

The permission claims as policies see them, and what each one is for.

| Path | Type | Source |
| --- | --- | --- |
| `$auth.permissions` | A list of strings. | The resolved union at issue time. |
| `$auth.roles` | A list of strings. | Group memberships at issue time. |
| `$auth.authenticated` | A boolean. | Whether a caller was verified at all. |
| `$auth.kind` | A string. | `user`, `operator`, `service`, or `anonymous`. |
| `$auth.aal` | A string. | `aal1`, or `aal2` after a second factor. |
| `$auth.org` | A string or null. | The session's organization slug. |
| `$auth.org_role` | A string or null. | The caller's role in that organization. |
| `$auth.user_id` | A string. | The caller's id. |
| `$auth.email` | A string or null. | The address the token was issued for. |
| `$auth.claims` | The raw claims. | Everything above, plus anything else. |

For an anonymous caller the same paths exist and every one of them is null or empty, which is why a policy written only with permission checks denies anonymous callers without needing an explicit test.

### Choosing between a role check and a permission check

| | `{ "role": "manager" }` | `{ "permission": "reports:export" }` |
| --- | --- | --- |
| Answers | Is this person a manager? | Can this person export reports? |
| Survives a role rename. | No. | Yes, if the permission name is unchanged. |
| Satisfied by `*`. | No. | Yes. |
| Can be granted ad hoc. | Only by creating the role. | Yes, directly. |
| Reads better in the policy. | Sometimes. | Usually. |

The third row is the one that decides it most often. Gating on a role name means a wildcard does not help, so your support account needs that role created and assigned before it can do anything.

<Tip>
Prefer permission checks in policies and use roles as the delivery mechanism. The policy then states what the action requires, and how people come to hold it stays an administrative question.
</Tip>

### Combining with other conditions

A permission check is rarely the whole answer. The usual shapes:

```json
{ "all": [ { "permission": "records:write" }, { "owner": true } ] }
```

```json
{ "any": [ { "permission": "records:delete" }, { "owner": true } ] }
```

The first says only the owner may write. The second says anyone with the permission may, and otherwise the owner may. Both are common, and they are not interchangeable — the second is the one people mean by "editors and owners", and writing the first by mistake locks the editors out.

<Warning>
When a permission is a capability and a condition is a scope, write both. A permission alone grants the action everywhere; a condition alone relies on whatever grants access to anyone at all, which includes every other role and the wildcard.
</Warning>

### Supporting a request

A worked policy, because the pieces are clearer once they are assembled.

Suppose an expense can be approved by anyone holding `expenses:approve`, but only for expenses in the organization their session is scoped to, and only if they are actually signed in with a second factor.

```json
{
  "all": [
    { "authenticated": true },
    { "service": false },
    { "permission": "expenses:approve" },
    { "eq": ["$record.org", "$auth.org"] },
    { "aal": "aal2" }
  ]
}
```

Reading it line by line:

| Term | Why it is there |
| --- | --- |
| `authenticated` | Rejects anonymous callers before anything else is evaluated. |
| `service: false` | Stops a service credential from satisfying the rest, if one should never approve. |
| `permission` | The capability itself. Satisfied by the role or by a direct grant, and by `*`. |
| `eq` on `$record.org` | The scope. Uses the session's organization, which is set at sign-in or at refresh. |
| `aal: aal2` | Requires the second factor, because this action moves money. |

Every term maps to one of the four things a real authorization decision needs: who is calling, what they may do, where they may do it, and how strongly they proved themselves.

<Warning>
The `$auth.org` term is null for any session that was never scoped to an organization. With the `eq` above, a null org will not equal a record's org, so an unscoped session is denied. That is the right default, and it is worth being deliberate about: if your sign-in flow does not always set an organization, some legitimate users will fail here.
</Warning>

### The same decision without a policy

Akountz does not enforce application permissions. It resolves them, stamps them into a token, and stops. Everything above is your policy's job.

| Layer | What it decides |
| --- | --- |
| Akountz | Who the caller is, what they hold, and whether their token is valid for this environment. |
| The gateway | Whether the token verifies at all. |
| Your policy | Whether this particular action is allowed. |

<Note>
This division is why an authorization bug is a policy bug. If Akountz resolved the permissions correctly and stamped them correctly, and the policy still denied the action, the defect is in the policy — which means it is also in a file you can read and test.
</Note>

### Testing a policy directly

A policy that denies everyone in production and everyone in staging looks identical from the outside, which is why testing it against a real user session matters more than reading it.

| Test | What it catches |
| --- | --- |
| A user holding the permission. | A misspelled permission name. |
| A user without it. | A condition that passes too easily. |
| The same user, unscoped organization. | An `eq` on `$auth.org` behaving as null. |
| The same user, `aal1` instead of `aal2`. | An assurance check that is not being evaluated. |
| A service credential. | A missing `service: false`. |
