Policies read the verified claims. No policy ever queries the permission tables, and none can.

### The shorthand

A permission check is a shorthand that expands into a condition:

```json
{ "permission": "reports:export" }
```

which is equivalent to:

```json
{
  "all": [
    {
      "any": [
        { "contains": ["$auth.permissions", "reports:export"] },
        { "contains": ["$auth.permissions", "*"] }
      ]
    }
  ]
}
```

The `any` against the wildcard is worth pausing on. A permission check passes if the caller holds that permission **or** holds `*`, so the wildcard is checked by the permission shorthand itself. The `role` shorthand has no such branch — it is a plain membership test against `$auth.roles`, so a caller holding `*` does **not** satisfy a role check.

<Warning>
That asymmetry matters when you write a policy that mixes the two. `{ "permission": "reports:export" }` passes for a caller holding `*`; `{ "role": "manager" }` does not. If your superuser account holds only `*` and your policy gates on a role name, that account is denied.
</Warning>

<Note>
Inside Pawabase services, the same rule appears in the principal's own permission check, which returns true when the caller holds the named permission or `*`. That path additionally returns true for a service or operator whose roles include `admin` — a separate convenience that does not exist for project users. See [Auth in policies](/auth/auth-in-policies/overview) for how the three caller kinds differ.
</Note>

### Other shorthands worth knowing

| Shorthand | Expands to a test on |
| --- | --- |
| `authenticated` | `$auth.authenticated` equals the given boolean. |
| `role` | `$auth.roles` contains any of the given names. |
| `permission` | `$auth.permissions` contains each named permission, or `*`. |
| `owner` | The record's owner column equals `$auth.user_id`. |
| `service` | `$credential.is_service` equals the given boolean. |
| `kind` | `$auth.kind` equals `user`, `operator` or `service`. |
| `scope` | `$credential.scopes` contains the named scope. |
| `aal` | `$auth.aal` equals `aal1` or `aal2`. |

Full detail in [Policy shorthands](/policies/shorthands) and [Policy conditions](/policies/conditions).


## Roles are not organization roles

Two different things in Pawabase are called a role, and confusing them produces bugs that are hard to see.

| | Application roles | Organization roles |
| --- | --- | --- |
| What they are | A group plus permissions. | A string on a membership row. |
| Where they live | `perm_groups` and `perm_group_permissions`. | `Membership.role`, table `akz_memberships`. |
| Which values | Anything matching the name pattern. | Exactly `owner`, `admin`, `member`, `viewer`. |
| What they control | Access to your data, through policies. | Nothing by themselves. They are a label your application reads. |
| Where they appear | The `roles` claim. | The `org_role` claim. |

Organization roles are **not enforced by the platform**. The four values are validated on the way in, but nothing checks them in a policy. If your application wants only owners to delete an organization, you write that condition yourself against `$auth.org_role`.

<Warning>
There is a fourth thing also called a role: Studio operators, who are people who administer Pawabase itself rather than users of your project. They are an entirely separate concept, live in the reserved `_platform` environment, and have nothing to do with either table above.
</Warning>

### The org claims

`org` and `org_role` are read at issue time and describe the organization the session is scoped to.

| Claim | Value |
| --- | --- |
| `org` | The slug, or `null`. |
| `org_role` | The person's role in that organization, or `null`. |

There are two cases where both come back null even when an organization was named. If the user is not a member, the role is null — and the organization is nulled too, rather than reported as an error. The exception is when the organization was named on the request, where membership is required and a non-member is refused with a 403 before any token is minted.

<Note>
Because the role is read at issue time, promoting someone from `member` to `admin` does not change their existing tokens. It lands on the next refresh, like any other permission change.
</Note>


## Studio's Roles tab

Roles are managed under **Users & auth → Roles**. The card is titled **Roles** and its empty state reads *"No roles yet."*

| Element | Label |
| --- | --- |
| Create button | **New role** |
| Table columns | **Role**, **Description**, **Permissions**, **Members** |
| Modal title when creating | **New role** |
| Modal title when editing | The role's name |
| Modal fields | **Name**, **Description**, **Permissions** |
| Modal actions | **Delete**, **Save** |
| Toast on save | **Saved** |
| Toast on delete | **Deleted** |

The **Name** field's placeholder is `editor`. It is disabled when editing an existing role, because a rename would mean creating a different group and moving every membership across.

The **Permissions** field is a comma-separated text input whose hint reads *"Comma-separated, e.g. posts:write, posts:publish. `*` grants everything."* The hint is accurate: `*` satisfies every permission check, and the wildcard is what makes a single broad role possible.

### The Members column

It shows a count, from the group's member count. Note what it does **not** count: direct permission grants. A person holding `reports:export` directly appears in no role's member count, because they belong to no group.

<Note>
A member count of zero on a role that people clearly have does not mean the role is broken. It means the access is arriving by direct grant, which is invisible in this table. Check the user view's **Direct permissions** list to confirm.
</Note>

### Creating a role

<Steps>
  <Step title="Open the Roles tab">
    Go to **Users & auth → Roles** for the environment you intend to change. Roles are per environment, and the tab shows only the selected one.
  </Step>
  <Step title="Click New role">
    The modal opens with an empty name, no description and no permissions. It is titled **New role**, which is how you tell it apart from editing.
  </Step>
  <Step title="Fill in the name">
    Lowercase first letter, then lowercase letters, digits, underscore, colon or hyphen. The placeholder shows `editor`. A name with a capital or a space is rejected.
  </Step>
  <Step title="Add a description">
    Free text. It is shown in the table and is never evaluated, so it is worth writing for the next person who opens this screen.
  </Step>
  <Step title="List the permissions">
    Comma-separated, names you choose — `expenses:approve, reports:export` works. Typing a name that does not exist yet creates it.
  </Step>
  <Step title="Save">
    The list you typed becomes the role's complete permission set. Omitted permissions are removed from the role and from everyone in it.
  </Step>
</Steps>

### Assigning roles to a person

Roles are assigned from the **Users** tab, not the Roles tab. Open the person, and the **Roles** field carries the hint *"Comma-separated role names from the Roles tab."*

| Fact | Consequence |
| --- | --- |
| The field is the full desired list. | Keep existing role names in it when adding one. |
| Saving computes the difference. | Roles you left out are revoked. |
| A name that does not exist is created, empty. | A typo produces a silent no-op role rather than an error. |
| `null` leaves the field out of the update. | Roles are untouched when you save some other field. |

Below the roles field, the user modal has a **Direct permissions** list. Each entry is a badge with a small cross that revokes it, and beside it a text input with the placeholder `posts:write` and a **Grant** button. Revoking and granting here touch `user_permissions` only; they do not change any role.


## The admin routes

Studio and service keys reach the same operations over HTTP. Every one takes the project and environment in its path and requires a service token, because these are administrative operations on an environment's identities.

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `{base}/roles` | List the environment's roles, plus every permission defined in it. |
| PUT | `{base}/roles` | Create or replace a role. |
| DELETE | `{base}/roles/{name}` | Delete a role and its memberships. |
| POST | `{base}/users/{id}/permissions` | Grant direct permissions. |
| DELETE | `{base}/users/{id}/permissions` | Revoke direct permissions. |

`{base}` is `/projects/{project}/envs/{env}`.

The listing route returns both the roles and the environment's full permission set, which is what lets Studio's modal offer a complete picture rather than only the names currently in use.

### Creating or replacing

```bash
curl -X PUT "https://api.example.com/auth/v1/projects/acme/envs/production/roles" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" \
  -d '{
    "name": "payroll",
    "description": "Payroll staff",
    "permissions": ["expenses:approve", "reports:export"]
  }'
```

The name is validated against the pattern. A name that fails is a `422` from the request model, which is one of the few places where a bad role name produces a clear error rather than silent behaviour.

### Deleting

Deleting a role removes its memberships and then the group itself. The permission rows it held are **not** deleted, so they remain defined and available for other roles or for direct grants.

<Warning>
Deleting a role does not rewrite policies that reference its name. A policy checking `role: "payroll"` will deny everyone once the role is gone, and it will do so silently. Find the policies before deleting.
</Warning>

### Granting and revoking directly

```bash
curl -X POST "https://api.example.com/auth/v1/projects/acme/envs/production/users/01JQ7Z3M9K4YB2XQ8V0N5T6RJPD/permissions" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" \
  -d '{"permissions": ["reports:export"]}'
```

Both take the same body shape, a list of permission names. Granting defines any that do not exist yet. Revoking removes the direct grants only and leaves group permissions untouched — so revoking a permission someone also gets from a role changes nothing, which is the behaviour to expect.


## Roles in backups

An environment's backup includes its roles, their descriptions and their permissions, each user's role assignments, and each user's direct permissions. So the whole authorization model travels with the identities.

| In the backup | Restored as |
| --- | --- |
| Each role's name and description | A role defined with those values. |
| Each role's permission list | Permissions attached to that role. |
| Each user's roles | Group memberships, added if missing. |
| Each user's direct permissions | Direct grants. |
| Password hashes | Preserved, so people keep their passwords. |

Restoring with `replace` first removes every role in the environment, then rebuilds from the document — which makes a restore the moment when role definitions actually change rather than merely being re-applied.

<Note>
Because permissions are created on demand, a restore never fails on a missing permission; it creates it. That makes restores forgiving, and also means a backup taken with a typo in a permission name restores the typo rather than correcting it.
</Note>


## Default roles

`default_roles` is the one authorization setting in the environment's `auth` block. It lists the roles granted to every account at creation.

```json
{ "auth": { "default_roles": ["customer"] } }
```

| Property | Consequence |
| --- | --- |
| Applied at account creation. | Not at verification, and not at first sign-in. |
| Not retroactive. | Existing accounts are unaffected when you change the list. |
| Applies to every creation path. | Sign-up, magic-link creation, and accounts created in Studio. |
| Names are environment-prefixed like all others. | The same list means different roles in different environments. |

<Warning>
If a name in `default_roles` does not exist, it is created empty and the person is added to it. So a typo in this setting gives every new account a role that grants nothing, silently, and the Roles tab will show a role with a plausible name and an empty permission list.
</Warning>
