Magic links are passwordless sign-in by emailed one-time link. The user gives an email address, a message arrives with a link in it, and following that link signs them in — no password is ever created, typed, or stored for them.

The mechanism is small: a token with the `magic` purpose, an email built from a template, and a link whose destination depends on one configuration setting. Almost every surprising behaviour on this page falls out of that last part. An environment with a `site_url` sends people to your application. An environment without one sends them to a page hosted by Akountz itself, and the two paths complete the sign-in differently.

  <Card title="Fifteen minutes" icon="clock">The token lives for 900 seconds — the shortest of the emailed link types, because a magic link is answered immediately rather than found later.</Card>
  <Card title="Where it lands is configurable" icon="arrow-right">With a `site_url`, the link goes to your app. Without one, to an Akountz-hosted page. Same flow, visibly different result.</Card>
</CardGroup>

## Where magic links sit in the layered model

Magic links are entirely an identity-layer feature, with one configuration dependency.

| Layer | What magic links ask of it |
| --- | --- |
| **Akountz** (identity) | Owns the `OneTimeToken` row, sends the message, consumes the token, starts the session. |
| **The API** (project config) | Owns `magic_link_enabled`, `site_url`, and the `magic` email template. |
| **Gateway / `pawabase_core`** | Verifies the resulting token, like any other. Not involved in the flow. |

The tenancy rule applies as everywhere: a token is scoped to one `project` + `env` pair, so a magic link issued in staging cannot be redeemed in production even if the email addresses match.

<Info>
If you have not read [Authentication](/auth/overview) first, do that — this page assumes the layered model and the per-environment tenancy rule.
</Info>

## The two requests

There are only two routes, and the split between them is what makes the flow feel magic: asking for a link is context-scoped and looks like an ordinary API call, while redeeming it depends on where the link points.

| Route | Method | Purpose |
| --- | --- | --- |
| `/auth/v1/magic-link` | POST | Email a sign-in link. Always answers the same way. |
| `/auth/v1/magic-link/verify` | POST | Redeem the token and get a session. |

The hosted page, when there is no `site_url`, uses a third route that is not in the schema:

| Route | Method | Purpose |
| --- | --- | --- |
| `/auth/v1/links/{project}/{env}/magic` | GET | Redeem the token and either redirect or show a page. |

### Asking for a link

```bash
curl -X POST "https://api.example.com/auth/v1/magic-link" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "content-type: application/json" \
  -d '{"email": "ada@example.com"}'
```

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `email` | string | required | The address to send to. Normalised to lowercase. |
| `create_user` | bool | `true` | Whether an unknown address creates an account. |
| `redirect_to` | string | null | Where to land afterwards. Must be allowlisted. |

The response is the same whether or not the address has an account:

```json
{ "sent": true, "message": "If the address has an account, a message is on its way." }
```

<Warning>
That identical response is deliberate and is the point. If the endpoint answered differently for a registered and an unregistered address, it would be a membership oracle — a script could enumerate which addresses have accounts in your environment. Every endpoint that emails a link in Pawabase answers this way.
</Warning>

### What `create_user` actually does

This flag has more reach than its name suggests, and it interacts with two other settings.

The account is only created when **all** of these hold:

| Condition | Setting |
| --- | --- |
| The address has no account. | — |
| `create_user` is true. | the request |
| Sign-up is enabled in this environment. | `signup_enabled` |
| The account is not disabled. | — |

If sign-up is off, an unknown address simply receives nothing, and the response is unchanged. The user sees "check your email" forever, which is the correct behaviour for a membership oracle but a poor experience for someone who genuinely expected an account.

<Warning>
An account created this way gets **no password**. Password sign-in cannot succeed against it until someone sets one through a recovery link. This is the normal state for a magic-link-only user, not a fault. See [Managing users](/auth/managing-users).
## Where the link lands

This is the decision that most often surprises people, and it comes down to one setting: `site_url`.

Every emailed link in Pawabase is built the same way. The handler takes the kind, the token and an optional redirect target, and then chooses a destination:

| Environment state | The link points at |
| --- | --- |
| `site_url` is set | `{site_url}/auth/callback?token=...&type=magic` |
| `site_url` is empty | `{public_url}/auth/v1/links/{project}/{env}/magic?token=...` |

Both carry the same token. What differs is **who completes the flow**.

**With a `site_url`, your application does the work.** The link opens a page on your domain with the token in the query string. That page is yours: you read the token, post it to `/auth/v1/magic-link/verify`, store the session, and decide what the user sees next. You control the page, the styling, and what happens after sign-in.

**Without one, Akountz hosts the page.** The link opens a page served by the identity service itself. It redeems the token server-side and shows a plain confirmation — *"You're all set"* — or, if a `redirect_to` was supplied and is allowlisted, redirects to it with the tokens in the URL fragment.

The second path works perfectly well for an internal tool or a proof of concept. The difference is that you get no page of your own, no control over the post-sign-in experience, and a page whose look is not yours.

<Warning>
The setting is shared with every other emailed link — verification, recovery, email change. Setting `site_url` to get magic links pointing at your app changes where **all** of them point. That is usually what you want, and it is worth knowing before you expect one flow to behave differently from another.
</Warning>

<Info>
If `site_url` is empty and `public_url` is also empty, the hosted link is built from an empty base and will not work. Both being unset is a misconfiguration rather than a supported mode — set at least one.
</Info>

### The allowlist, again

`redirect_to` is checked against the same allowlist used by OAuth: `site_url` plus `redirect_urls`, matched on exact equality or a `/` or `?` boundary.

| Base | `redirect_to` | Allowed |
| --- | --- | --- |
| `https://app.example.com` | `https://app.example.com/welcome` | yes |
| `https://app.example.com` | `https://app.example.com.evil.test/` | no |
| — | `http://localhost:3000/after` | only if listed in `redirect_urls` |

An allowlisted `redirect_to` is added to the link itself, so the hosted page knows where to send the user afterwards.

<Info>
A `redirect_to` that fails the allowlist is rejected at the request stage with `400 redirect_to is not an allowed URL`, rather than being quietly dropped. That is the safer failure, but it does mean a misconfigured client sees a 400 rather than a link that "did nothing".
</Info>
## The token

The link carries a one-time token: a signature over the id of a `magic` row, with the row making it single-use.

| Purpose | Lifetime |
| --- | --- |
| `magic` | **900 seconds** — fifteen minutes |

For context, this is the shortest-lived emailed token in the system:

| Purpose | Lifetime | Why |
| --- | --- | --- |
| `mfa` | 300 seconds | Answered immediately. |
| `link` | 600 seconds | A linking ticket. |
| `magic` | **900 seconds** | Answered immediately, in the same sitting. |
| `recovery` | 3600 seconds | Found in an inbox minutes later. |
| `verify`, `email_change` | 24 hours | Deliberately forgiving. |
| `invite` | 7 days | Arrives with an onboarding flow. |

Fifteen minutes is deliberately short. The person who asked for the link is sitting in front of a page waiting for it, so the window only has to cover their attention span. A magic link that stayed valid for an hour would be a credential sitting in an inbox for an hour.

<Warning>
The copy the user receives says *"It works once, for 15 minutes"*, and that is accurate. If you override the template, keep that promise true — a custom subject promising longer does not make the token longer.
</Warning>

### Single use, and what that means under pressure

The token can be redeemed exactly once. Redemption uses a conditional update — an update that applies only while the row is unused — and if it matched no rows, someone else got there first.

That matters in a specific and common scenario: **the user opens the link twice.**

| What happened | Result |
| --- | --- |
| First click. | Redeemed. A session is created. |
| Second click — same tab, or a refresh. | Fails. The link is spent. |

The first redemption already worked, so the user is signed in and may not notice the second failure. But if the first response was lost — a closed tab, a dropped connection, a navigation away before the request landed — the token is consumed and the user must ask for another.

<Info>
There is no "resume this sign-in" behaviour and no second redemption. Design the callback page to store the session as its first action, not after a round trip to your own backend, so a failure between the two does not strand a user who has already spent their token.
</Info>

### Every failure is the same error

A magic token that is already used, expired, malformed, signed for another environment, or simply wrong produces one identical failure: a `400` whose detail is *"the link is invalid or has expired"*.

| Condition | Same error? |
| --- | --- |
| Already redeemed | yes |
| Expired | yes |
| Signature does not verify | yes |
| Row missing | yes |
| Token from another environment | yes |

<Warning>
Do not try to distinguish these in your error handling. There is no information in the distinction that helps a legitimate user, and several of them are exactly what an attacker probing the endpoint wants to learn.
</Warning>
## Redeeming the token

### With a `site_url` — your page does the work

Your callback page reads the token from the query string and posts it.

```text
// Your /auth/callback page.
const params = new URLSearchParams(window.location.search);
const token = params.get("token");

if (token) {
  const res = await fetch("/auth/v1/magic-link/verify", {
    method: "POST",
    headers: { "content-type": "application/json", "X-Pawabase-Context": CONTEXT },
    body: JSON.stringify({ token }),
  });
  const body = await res.json();

  if (res.ok && body.access_token) {
    storeSession(body);
    history.replaceState(null, "", "/");
  } else if (body.mfa_required) {
    promptForCode(body.mfa_token);
  } else {
    // "the link is invalid or has expired" -- send them back to request another.
  }
}
```

```bash
curl -X POST "https://api.example.com/auth/v1/magic-link/verify" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "content-type: application/json" \
  -d '{"token": "..."}'
```

The response is the standard token response — the same shape as a password sign-in, which is what makes magic links droppable into an existing client:

```json
{
  "access_token": "...",
  "refresh_token": "...",
  "token_type": "bearer",
  "expires_in": 900,
  "expires_at": 1750000000,
  "session_id": "9f2c1ab4e7d84f0c9b3a5e61d2c4807f6a9e3b5c1d0f28496ab7c3e5d1f0a2b4c6",
  "org": null,
  "org_role": null,
  "user": { }
}
```

### Without a `site_url` — the hosted page does the work

The browser lands on the Akountz-hosted link. It redeems the token itself and then does one of two things:

| Situation | What the user sees |
| --- | --- |
| No `redirect_to`, or the result has no tokens | A plain *"You're all set"* page. |
| `redirect_to` present, allowlisted, and a session resulted | A redirect carrying the tokens in the fragment. |

```text
https://app.example.com/welcome#access_token=...&refresh_token=...&expires_in=900&token_type=bearer
```

<Warning>
Tokens arrive in the **fragment** on this path, not in the query string — the same protection as the OAuth callback, for the same reason. A page that reads them must read `location.hash` in the browser, and cannot render them server-side. See [Social login](/auth/social-login) for the fragment-handling pattern.
</Warning>

<Info>
There is one more case worth knowing: if the account has MFA enrolled, redemption returns a challenge rather than a session, and there are no tokens to redirect with. The hosted page will show its confirmation rather than a code prompt — which is a good reason to set a `site_url` and own the callback page if you offer magic links to users who have enrolled MFA.
</Info>

### What redemption does to the account

Beyond starting the session, completing a magic link has two effects that are easy to miss.

| Effect | Condition | Why it matters |
| --- | --- | --- |
| The email is marked verified. | Always, if not already. | Holding the link proves control of the inbox. |
| MFA is challenged. | The account has MFA and the environment allows it. | Returns `mfa_required` instead of a session. |

The first is the important one. **A magic link verifies the email address**, without a separate confirmation step. Opening the link is the proof.

<Info>
This means magic links and email verification do not conflict. A user who signs up with verification required can confirm their address simply by completing a magic-link sign-in. It also means the two messages are genuinely interchangeable evidence of inbox control.
</Info>
## The message

The default magic-link email is short, and the shortness is deliberate — it is a link and an instruction, nothing else.

```text
Subject: Your {project} sign-in link

Sign in to {project} with this link. It works once, for 15 minutes:

{link}
```

| Placeholder | Replaced with |
| --- | --- |
| `{project}` | The project's display name, falling back to the project slug. |
| `{link}` | The URL built for this environment — your app's or Akountz's, depending on `site_url`. |

There is no `{email}` in the default magic template, though the placeholder is available if you write your own. An unknown placeholder is **left in the message literally** rather than raising an error, so a typo shows up in the delivered mail where you will see it, instead of failing silently.

<Warning>
That behaviour cuts both ways. A typo in an override does not stop the email being sent — it produces an email containing `{link}`, which looks delivered and useful and cannot be used. If a magic link arrives and does not work, check the template first.
</Warning>

### Overriding the copy

Templates are overridden per environment, under the `magic` key:

```json
{
  "auth": {
    "emails": {
      "magic": {
        "subject": "Your Acme sign-in link",
        "text": "Sign in to Acme with this link. It works once, for 15 minutes:\n\n{link}\n\nIf you did not request this, ignore this message."
      }
    }
  }
}
```

| Field | Default |
| --- | --- |
| `subject` | `"Your {project} sign-in link"` |
| `text` | The two-line body above. |

Both are optional — supply one and the other keeps its default.

<Warning>
Your `text` is what most recipients read, and it is also what gets converted to the HTML part of the message. The plain text is escaped and newlines become line breaks, with the link value wrapped in an anchor. So an ampersand in your copy renders correctly rather than breaking the HTML, and your link becomes a clickable link rather than a wall of text.
</Warning>

<Info>
Delivery goes through the API's mail service, which means your **environment's own SMTP settings** are used. A staging environment with a sandbox mail service sends to its sandbox; production sends for real. See [Environments and promotion](/studio/environments-and-promotion).
</Info>

### The other four message kinds

`magic` is one of exactly five message kinds. Knowing the others is useful because they share the template machinery and the `{link}` placeholder.

| Kind | Sent by | Purpose |
| --- | --- | --- |
| `verify` | Sign-up and resend | Confirm an email address. |
| `recovery` | Password recovery request | Set a new password. |
| `magic` | Magic-link request | Passwordless sign-in. |
| `invite` | Organization invitation | Accept an invitation. |
| `email_change` | An email change request | Confirm a new address. |

| Kind | Lifetime of its token | Placeholders |
| --- | --- | --- |
| `verify` | 24 hours | `{project}`, `{link}` |
| `recovery` | 1 hour | `{project}`, `{link}`, `{email}` |
| `magic` | 15 minutes | `{project}`, `{link}` |
| `invite` | 7 days | `{project}`, `{link}`, `{organization}`, `{role}` |
| `email_change` | 24 hours | `{project}`, `{link}` |

Note that only `invite` has the organisation placeholders. If you write an invitation template, `{organization}` and `{role}` are available there and nowhere else.

<Info>
Every one of these uses the same destination logic described above, so a `site_url` change moves all five at once. See [Email verification](/auth/email-verification) and [Password recovery](/auth/password-recovery) for the flows that use the other two.
</Info>

## Configuring magic links

Two settings, and they do different jobs.

```json
{
  "auth": {
    "magic_link_enabled": true,
    "site_url": "https://app.example.com"
  }
}
```

| Setting | Default | Controls |
| --- | --- | --- |
| `magic_link_enabled` | `true` | Whether the flow is offered at all. |
| `site_url` | `""` | Where the link lands, and who completes it. |

### Turning magic links off

With `magic_link_enabled` false, `POST /auth/v1/magic-link` returns `403 magic links are disabled`. That is the only effect — **existing magic links keep working** until they expire, because they are already issued tokens and the switch is not consulted at redemption.

<Warning>
Because the default is **on**, an environment that has never been configured offers magic links. Any client building a sign-in screen from `GET /auth/v1/settings` will render one, and any user can request a link and create an account through it. If you do not want that, set it to false explicitly.
</Warning>

| You want | Set |
| --- | --- |
| Magic links available, landing on your app | `magic_link_enabled: true` and a `site_url` |
| Magic links available, hosted by Akountz | `magic_link_enabled: true`, no `site_url` |
| No magic links | `magic_link_enabled: false` |
| Links that create accounts | `signup_enabled: true` |
| Links that only work for existing users | `signup_enabled: false`, or `create_user: false` per request |

<Info>
Remember the ten-second configuration cache. Turning magic links off in Studio does not stop the endpoint immediately, and a request in that window will still send a message.
</Info>
## What Studio shows

Magic links appear in three places on the **Users & auth** page, and none of them is where people expect.

### The environment switch

Under the **Configuration** tab, the **Sign-in methods** section holds **Magic links**, whose hint reads *"Passwordless sign-in by emailed one-time link."* That is `magic_link_enabled`.

It sits directly beside **MFA (TOTP)**, whose hint reads *"Let users add an authenticator app for aal2."* The two switches are the only members of that section, because they are the two sign-in methods the section covers — everything else in authentication is either a consequence of these or a fallback.

<Info>
The hint text is precise: an *emailed one-time link*. It is not a code, not a magic word, and not a password reset. That is the whole feature.
</Info>

### The site URL

Under **Configuration**, the **URLs** section holds **Site URL**, whose placeholder is `https://app.example.com`, and **Additional allowed redirect URLs**, whose placeholder is a staging callback path.

The section is described in the interface as *"Where a browser is allowed to land after an OAuth or magic-link redirect"* — naming magic links explicitly alongside OAuth, because both flows use the same redirect machinery and the same setting.

<Warning>
This is the setting that decides where magic links land, and it is easy to leave blank because it is optional. Leaving it blank is not an error: it means Akountz-hosted pages, which work. But it does mean the user sees a page that is not yours, and that you cannot style or extend.
</Warning>

### The email template

Under **Configuration**, the **Email templates** section holds per-message subject and body overrides, including the magic-link copy. The other templates in that section are the passwords, email-change and organization-invite ones.

| What you set | What changes |
| --- | --- |
| **Magic links** | Whether the flow is offered. |
| **Site URL** | Where links land, and who completes the flow. |
| **Additional allowed redirect URLs** | Which `redirect_to` values are accepted. |
| Magic template subject and body | What the user reads. |

### What is not in Studio

There is no interface for setting `create_user`. It is a per-request field only, and its effective value also depends on `signup_enabled`, which is in the **Sign-up** section described as *"Who can create an account, and whether their email must be confirmed first."*

### The sign-in audit trail

Under the **Sign-in activity** tab, a completed magic-link sign-in appears with its method recorded, so a magic-link session is distinguishable from a password one.

| Event | When |
| --- | --- |
| `user.created` | The request created an account for an unknown address. |
| `user.signed_in` | A session started, with the method. |
| `user.verified` | The email was marked verified by the redemption. |

The **failures only** checkbox filters the table to the failures, which is how you would spot a client posting a `redirect_to` that is failing the allowlist.

<Info>
A repeated `400 redirect_to is not an allowed URL` does not appear in this tab — it fails at the request stage, before a token is issued or an email sent. Check your client's logs for that one.
</Info>
## The security properties

Magic links move the trust boundary from "something you know" to "something you received", and the design choices below are what keeps that from being a downgrade.

### The inbox is the credential

There is no second factor. The proof is possession of a message in one specific inbox, plus the ability to click within fifteen minutes. That is a single factor, and it is why the resulting session is `aal1` — the same as a password sign-in.

| Property | Password sign-in | Magic-link sign-in |
| --- | --- | --- |
| Factors | one | one |
| Secret's lifetime | until changed | 15 minutes |
| Replayable after use | no | no |
| Guessable | no | no — 40 bits of entropy in the signature |
| Session assurance | `aal1` | `aal1` |

<Warning>
Treat a magic-link session as exactly as sensitive as a password session. It is not a lesser login. The only difference is where the credential came from.
</Warning>

### What the design prevents

| Attack | What stops it |
| --- | --- |
| Forging a magic link | The token is signed for this environment and purpose. |
| Replaying a used link | The row is marked used by a conditional update. |
| Using an expired link | Both the signature and the row carry a fifteen-minute expiry. |
| Using a link from another environment | The signature and the row are both bound to project and environment. |
| Enumerating which addresses have accounts | The response is identical either way. |
| Intercepting the link in transit | TLS, and the link is useless once spent. |
| Clicking a link on the wrong device | Fifteen minutes, and it goes to one inbox. |

The enumeration row is the one people forget is a design goal rather than an accident. It is the reason the endpoint answers "sent" for addresses that do not exist, and the reason the response cannot be improved to say "no such account".

<Info>
The same response shape is used by password recovery and email verification for the same reason. Every endpoint that emails a link in Pawabase refuses to confirm whether an address is registered.
</Info>

### Where the weak points are

The security of the flow rests on two assumptions, and it is worth being honest about both.

**The inbox is secure.** Anyone with access to the mailbox can sign in. This is why an account with a magic link should still be considered only as protected as its email provider allows — which is why MFA on top of it is a genuine improvement rather than a checkbox.

**The link is not scanned by a security product.** Mail scanners and URL rewriting tools fetch links in incoming mail to check them. A security appliance that follows the link to scan it will consume the token, and the user who then clicks it finds an expired link.

<Warning>
This is the most common real-world cause of "I clicked the link and it said it had expired". If your organisation rewrites or pre-fetches links in mail, magic-link flows need a short window — which is part of why the fifteen minutes exists — or an exemption for your own domain.
</Warning>

| Weak point | Mitigation |
| --- | --- |
| Mail scanning consumes the token | Keep the window short; ask IT to exempt your domain. |
| Shared or forwarded mailboxes | Not a mitigation problem — do not offer magic links to shared accounts. |
| Forwarding rules | A forwarded link is a live credential for fifteen minutes. |
| Shared devices | The session is bound to the browser that completed it. |

### Link forwarding, honestly

A forwarded magic link is a working credential for its remaining lifetime. If someone forwards the message to another address, that person can complete the sign-in.

This is not a defect — it is inherent to any email-based credential — but it sets a boundary worth stating: **the magic link authenticates the inbox, not the human who requested it.** If your threat model includes a compromised mailbox, magic links inherit exactly that compromise.

<Info>
This is the strongest argument for offering MFA alongside magic links rather than instead of them, and for treating `aal2` as a meaningful upgrade on a passwordless account.
</Info>
## Worked scenarios

### A known user requests a link

The address matches an account, the account is not disabled, and `create_user` is irrelevant because there is nothing to create.

A `magic` token is issued and the message is sent. The response is the standard "sent" body, identical to what an unknown address would have received.

The user clicks. The token is redeemed, the email is marked verified if it was not already, and a session is created with its method recorded as a magic-link sign-in. No MFA challenge unless the account has a factor.

### An unknown address requests a link

Two branches, decided by `create_user` and `signup_enabled`.

| `create_user` | `signup_enabled` | Result |
| --- | --- | --- |
| true | true | An account is created, `user.created` is emitted, and a link is sent. |
| true | false | Nothing is created and no message is sent. |
| false | true | Nothing is created and no message is sent. |
| false | false | Nothing is created and no message is sent. |

In all four cases the **response is identical**. The user cannot tell from the response whether they now have an account, and neither can anyone else.

<Warning>
The rows where nothing is sent are the ones that generate support tickets. A user who requests a link, gets "check your email", and has no account is the expected behaviour of a membership-oracle-safe endpoint in an invite-only environment. Your interface should say "if that address has an account, a message is on its way", not "we sent you a link".
</Warning>

### A disabled account requests a link

The address matches an account, but the account is disabled, so no token is issued and no message is sent. The response is the same one.

If the user already holds an unexpired link from before the account was disabled, redemption refuses with `403 this account is disabled`. The flag is checked at redemption as well as at issue, so disabling an account closes both doors.

### A user with MFA completes a magic link

The token is redeemed successfully. The account has MFA, so **no session is issued**. A challenge comes back instead:

```json
{ "mfa_required": true, "mfa_token": "..." }
```

The client posts that to `/auth/v1/token` with `grant_type=mfa` and a code, and gets the session at `aal2`.

| Where the link landed | What the user sees |
| --- | --- |
| Your app, with a `site_url` | Whatever your callback page renders. Handle the branch. |
| The hosted page | *"You're all set"*, and they are **not** actually signed in. |

<Warning>
The second row is a genuine trap. A user with MFA who uses an Akountz-hosted magic link is told everything is fine and ends up signed out. If you offer magic links to users who enrol MFA — which you should — set a `site_url` so your own page handles the challenge.
</Warning>
### The link is clicked twice

First click redeems it and creates a session. Second click fails with the generic expired-or-invalid error.

If the user was on your callback page and the session was stored on the first load, they are signed in and the second failure is invisible. If the first response never reached the client, the token is gone and they need a new link.

<Info>
There is no way to make a magic link survive a second click. The single-use property is what makes it safe to send through mail infrastructure that might prefetch it.
</Info>

### A local developer follows a magic link

Two distinct failures, both common and both confusing.

| Symptom | Cause |
| --- | --- |
| The link opens a page that is not styled like yours. | No `site_url`, so the hosted page is used. |
| The hosted link 404s. | `public_url` is empty, so the link was built from an empty base. |
| Your callback page says the link is invalid or has expired. | The environment does not match the one that issued the link. |
| `redirect_to is not an allowed URL`. | `http://localhost` is not in the allowlist. |

<Warning>
The third row catches people who copy a magic link between environments, which is easy to do while testing because the token looks environment-agnostic. It is not: the signature and the row are both bound to one project and environment.
</Warning>

### Verifying the setup

Two checks confirm magic links are wired correctly.

```bash
# 1. Request one. The response is identical whether or not the address exists.
curl -sX POST "$BASE/auth/v1/magic-link" \
  -H 'content-type: application/json' \
  -d '{"email":"ada@example.com"}'

# 2. Redeem the token from the message. Expect the standard token response.
curl -sX POST "$BASE/auth/v1/magic-link/verify" \
  -H 'content-type: application/json' -d '{"token":"..."}'

# 3. Try it a second time. Expect the invalid-or-expired error.
```

| What it tells you | Good result |
| --- | --- |
| The endpoint is enabled | A "sent" body, not a 403. |
| The link landed where you expected | Your domain, if `site_url` is set. |
| Redemption works | The standard token response. |
| Single use holds | The second attempt fails. |

<Info>
Testing the double redemption once is worth doing. It is the failure a user will hit first, and knowing the exact error shape means the message you write for it will be right.
</Info>

## Choosing between the sign-in methods

Magic links are one of four ways in, and the choice between them is a product decision with real trade-offs.

| | Magic link | Password | Magic link + password | Social |
| --- | --- | --- | --- | --- |
| Credentials stored | none | one, hashed | one, hashed | none |
| User must type something at sign-in | no | yes | yes | no |
| Reset needed if forgotten | ask for a new link | email a link | email a link | nothing |
| Phishing exposure | a real login link is a real credential | password is a real credential | both | the provider's login |
| Works without an authenticator app | yes | yes | yes | yes |
| Survives the inbox being compromised | no | yes | no | no |
| Best for | convenience, infrequent use | repeat use, high security | repeat use | accounts that would rather not have a password |

<Warning>
The honest summary is that a magic link trades a durable secret for an expiring one. That is a genuine improvement for an occasional user, and a genuine downgrade for a user whose inbox is the weakest link in their security. If you offer both, most people use the password after the first few sign-ins.
</Warning>

### Offering both

The methods are not mutually exclusive, and the settings are independent.

| Setting | Controls |
| --- | --- |
| `magic_link_enabled` | Whether the link is offered. |
| `password_policy`, `password_min_length` | Whether passwords are set, and how strong. |

An account created by a magic link has **no usable password**, so a sign-in screen offering both will show a password field that cannot succeed until the user sets one. That is the normal state, and the resolution is a password recovery link — the same mechanism that creates the first password.

<Info>
There is no separate "set a password" flow for passwordless accounts. Password recovery is it, which is one reason the recovery message says the link works once, for an hour.
</Info>

### Sign-in surfaces

A sign-in screen should be built from `GET /auth/v1/settings` rather than from hardcoded assumptions, because every method on it is per environment.

```json
{
  "signup_enabled": true,
  "email_verification_required": false,
  "magic_link_enabled": true,
  "mfa_enabled": true,
  "providers": ["google"],
  "password_policy": { "kind": "basic", "min_length": 8 }
}
```

| Field | What your UI should do |
| --- | --- |
| `magic_link_enabled` | Show or hide the "email me a link" option. |
| `providers` | Render one button per name. |
| `signup_enabled` | Whether to offer registration. |
| `email_verification_required` | Whether to explain the confirmation step. |
| `password_policy` | Whether to show strength hints on a password field. |

<Warning>
Do not show a magic-link option because you assume the feature exists. It defaults to **on**, so an environment with a stale or inherited configuration may be offering a flow whose mail does not arrive.
</Warning>

## Deployment considerations

### Environments and mail

Delivery goes through the API's mail service using each environment's own SMTP settings. This matters more for magic links than for other email, because the link is the entire credential.

| Environment | What happens |
| --- | --- |
| Sandbox SMTP | Links are caught by the sandbox and never arrive. |
| A catch-all inbox | Links arrive, but to an address nobody reads. |
| No SMTP configured | The request succeeds and no message is sent. |

<Warning>
A request returning "sent" does not mean a message was delivered — only that a token was issued and handed to the mail service. There is no delivery confirmation to read back. When testing magic links, confirm the message actually arrived rather than trusting the response.
</Warning>

### Promotion

Magic links are configuration, so they promote with the environment. Accounts do not promote at all.

| Promoted | Not promoted |
| --- | --- |
| `magic_link_enabled` | Users |
| `site_url` | One-time tokens |
| `emails.magic` | Sessions |
| `signup_enabled` | |

<Info>
Promoting staging to production carries the magic-link settings with it, which is usually what you want. It also means a staging-only `site_url` can land in production, sending production's sign-in links to a staging host. Check it after a promotion.
</Info>

### Rate limits

| Bucket | Limit | Window | Applies to |
| --- | --- | --- | --- |
| `akz:links` | 10 | 60 seconds | The magic-link request. |
| `akz:auth` | 30 | 60 seconds | `/token`, including MFA completion. |

Ten requests a minute per caller is the limit on how fast links can be requested. It is the second brake behind the identical-response design: a script cannot enumerate accounts by watching which requests succeed, because none of them do.

<Info>
A resend button that fires on every click will hit this quickly. Cooldown the button client-side rather than discovering the limit through a 429.
</Info>

### What a magic-link session can do

The session that comes back is an ordinary session, so everything downstream behaves the same as any other sign-in.

| Aspect | Value |
| --- | --- |
| Assurance level | `aal1`, or `aal2` if MFA was challenged. |
| Lifetime | The environment's access and refresh TTLs, 15 minutes and 30 days by default. |
| Refresh | Normal rotation, with the same theft detection. |
| Revocation | Normal — it appears in the session list like any other. |
| Organization scoping | Starts unscoped; refresh with an `org` to switch. |
| Roles | Read at issue time from the account. |

<Warning>
Because the session is ordinary, a lost or abandoned link leaves no residue to clean up. The token is consumed or expires, and nothing else was created.
</Warning>

## Troubleshooting

Magic-link problems are almost always one of a handful of causes, and the error text points at which.

| Symptom | Cause | Fix |
| --- | --- | --- |
| `403 magic links are disabled` | `magic_link_enabled` is false. | Turn **Magic links** on in the Configuration tab. |
| The link says invalid or expired, immediately. | A mail scanner fetched it. | Ask IT to exempt your domain. |
| The same, after fifteen minutes. | The window elapsed. | Request a new one. |
| The same, on the second click. | Already redeemed. | Expected. Check whether the first attempt worked. |
| The same, straight away in development. | Wrong environment. | The token is bound to one project and environment. |
| `400 redirect_to is not an allowed URL` | The target is not in the allowlist. | Add it, or use `site_url`. |
| No email arrives. | Mail service, or no account and no sign-up. | Check SMTP, and whether the address exists. |
| The email arrives with `{link}` in it. | A placeholder typo in an override. | Fix the template. |
| The hosted page returns 404. | `public_url` is empty. | Set `site_url`, or set `public_url`. |
| The hosted page says "You're all set" but I am not signed in. | MFA was challenged and the page cannot prompt. | Set a `site_url` and handle the challenge. |
| No link appears in the sign-in screen. | Hardcoded assumptions, or a stale config cache. | Render from the settings response. |
| `429` on repeated requests. | Ten per minute. | Cooldown the resend button. |

<Warning>
The two that generate the most confusion are the mail scanner and the double click, because both present as "the link is invalid or has expired" with no further detail. That is the error the design intends — see [Every failure is the same error](#every-failure-is-the-same-error) — so diagnosing them means knowing your users' mail setup.
</Warning>

<AccordionGroup>
  <Accordion title="Why did my user get no email?">
    Three possibilities, in the order worth checking: the address has no account and `create_user` is false or sign-up is off; the account is disabled; or the mail service is not delivering. The response is identical in all three, by design. The audit trail will tell you whether an account was created for that request.
  </Accordion>
  <Accordion title="Can I resend the same link?">
    There is no resend that reuses a token. Each request issues a fresh one, and each is independently valid and single-use. Two valid links existing at once is expected, not a bug.
  </Accordion>
  <Accordion title="Does a magic link confirm the email address?">
    Yes. Completing one marks the address verified if it was not already, because holding the message is the proof. This is why magic links can substitute for a separate verification message.
  </Accordion>
  <Accordion title="Why is the session aal1?">
    Because a magic link is one factor. It is exactly as strong as a password session, and exactly as deserving of an `aal2` policy if your users have enrolled MFA.
  </Accordion>
  <Accordion title="Can a user sign in with a magic link and a password?">
    Only once they have a password. An account created by a magic link has none, so password sign-in fails until one is set through password recovery. Offering both methods in a UI is normal; the password field simply does not work yet.
  </Accordion>
</AccordionGroup>
### Two valid links at once

Requesting two links for the same address issues two independent tokens, both valid, both single-use.

| Consequence | Detail |
| --- | --- |
| Either one can sign in. | They are not related to each other. |
| Using one does not invalidate the other. | Redemption marks one row, not the account. |
| Both can produce sessions. | Separate sessions, in separate token families. |
| Each counts separately for the rate limit. | Ten requests a minute regardless. |

<Warning>
Two concurrent valid links means a forwarded link remains usable after the recipient has already signed in with their own. There is no mechanism to revoke a single outstanding magic token, which is another way of seeing that the security here rests on the fifteen-minute window rather than on revocation.
</Warning>

### Diagnosing a token that will not verify

When you need to know why a specific token failed, the row answers it.

```sql
SELECT purpose, expires_at, used_at, user_id
FROM akz_one_time_tokens
WHERE project = 'acme' AND env = 'production'
ORDER BY id DESC LIMIT 5;
```

| What the row shows | Diagnosis |
| --- | --- |
| `used_at` is set | Someone redeemed it — possibly a mail scanner, possibly the user. |
| `used_at` null, `expires_at` in the past | It aged out. |
| No row at all | The signature did not verify, or it was issued for another environment. |
| A row with the right purpose | The failure is on the client side. |

<Warning>
The row is only findable by id, and the id is inside the signed payload. If you have the token, you can decode it to get the id without verifying the signature, then look the row up directly — which tells you whether the problem is the signature or the row.
</Warning>

### What to build, in summary

The interface decisions that matter, gathered.

| Decision | Recommendation |
| --- | --- |
| Render the option from settings | Not hardcoded. The feature defaults to on. |
| The request's copy | "If that address has an account, a message is on its way." |
| The callback page | Store the session as its first action. |
| Token handling | Read it from the query string; clean the URL afterwards. |
| Expired or invalid | Offer another link. Do not diagnose further. |
| `mfa_required` | Handle the branch, or do not offer magic links to enrolled users. |
| The resend button | Cooldown it. |
| Session storage | The same as any other sign-in. |

<Info>
Every one of these is a consequence of something documented above rather than a separate opinion: the identical response is why the copy is cautious, the single use is why the callback must store first, and the MFA branch is why a `site_url` matters more than it first appears.
</Info>

## The whole flow, end to end

The complete sequence in one place, for both destination modes, because the branching is the part worth having in your head.

### With a `site_url` — your application completes the flow

```text
  user enters an email address
        |
        |  POST /auth/v1/magic-link  {email}
        v
  {sent: true, message: "If the address has an account..."}
        |                      (identical in every case)
        |  a `magic` token is issued: signed, 900s, tied to project+env
        v
  the message arrives, carrying
  https://app.example.com/auth/callback?token=...&type=magic
        |
        |  the user clicks
        v
  YOUR /auth/callback page
        |
        |  POST /auth/v1/magic-link/verify  {token}
        v
  the row is consumed by a conditional update
  the email is marked verified
        |
        +-- MFA enrolled? --> {mfa_required, mfa_token} --> POST /token grant_type=mfa
        |
        v
  the standard token response, method "magic_link"
```

### Without a `site_url` — Akountz completes the flow

```text
  user enters an email address
        |
        |  POST /auth/v1/magic-link  {email}
        v
  {sent: true, ...}
        |
        v
  the message arrives, carrying
  https://auth.example.com/auth/v1/links/acme/production/magic?token=...&type=magic
        |
        |  the user clicks; AKOUNTZ redeems the token
        v
  the email is marked verified; MFA is checked
        |
        +-- redirect_to allowlisted AND a session resulted
        |      --> redirect to your page with #access_token=...
        |
        +-- otherwise
               a plain "You're all set" page
```

<Warning>
The two diagrams are identical up to the last hop. Everything a user experiences about *arriving* is the same; what differs is who redeems the token and what page they see afterwards.
</Warning>

### What each layer contributes

A table attributing each step, because when something breaks the layer tells you where to look.

| Step | Layer | If it fails |
| --- | --- | --- |
| Reading the config | API, cached by Akountz | Settings ignored; check the cache. |
| The request itself | Akountz | `403` or `400`. |
| Account lookup and creation | Akountz | Silent — same response. |
| Issuing the token | Akountz | Silent — same response. |
| Sending the message | The API's mail service | Silent — same response. |
| The recipient's inbox | External | Link never arrives, or a scanner ate it. |
| Clicking the link | Browser | Nothing happens. |
| Redeeming | Akountz or your page | The invalid-or-expired error. |
| The session | Akountz | Standard token failures. |

<Info>
The four steps that fail **silently** are the ones worth checking first when a user reports that nothing happened, because the response was a success in every case.
</Info>

### Data you can inspect

The token row is the only place a magic-link question can be answered definitively, and it holds more than the obvious columns.

```sql
SELECT purpose, email, user_id, expires_at, used_at
FROM akz_one_time_tokens
WHERE project = 'acme' AND env = 'production'
  AND purpose = 'magic'
ORDER BY id DESC LIMIT 10;
```

| Column | What it answers |
| --- | --- |
| `purpose` | Whether this is a magic token at all. |
| `project`, `env` | Which environment issued it. |
| `user_id` | Which account it belongs to. Null means the address had no account. |
| `email` | Where it was sent. |
| `expires_at` | When it stopped being usable. |
| `used_at` | Whether it was redeemed, and when. |

<Warning>
A row with a null `user_id` is normal for a flow where the address had no account and none was created — the token still exists because it was issued before the branch that sends mail. A row that was issued and never used is what a scanner leaves behind.
</Warning>

### The signature, in one paragraph

The token in the link is a signed payload, not a random string. The signature is what makes it unforgeable, and the timestamp inside it is what makes it expire; the row is a separate thing that makes it single-use. Verifying the signature only proves the token was issued by this system for this environment and purpose — it says nothing about whether the token has already been used, which is why the row check comes after.

| Property | Provided by |
| --- | --- |
| Cannot be forged | The signature. |
| Expires after 900 seconds. | The signature's age, checked against the purpose's lifetime. |
| Cannot be used twice. | The row, marked by a conditional update. |
| Bound to one environment. | The row, filtered by project and environment. |
| Bound to one purpose. | The serializer is keyed by purpose. |

<Info>
A token signed for one purpose cannot be redeemed as another. A `verify` token is not a `magic` token, which is what stops a verification link being used to sign someone in.
</Info>

### Asking the right question of the audit trail

Because the request endpoint is silent about outcomes, the sign-in history is where you learn what happened.

| Question | Where to look |
| --- | --- |
| Did a link complete a sign-in? | A sign-in event with the magic-link method. |
| Was an account created by a request? | A `user.created` event with the magic-link method. |
| Was the email verified by redemption? | A `user.verified` event. |
| Did someone ask for a link and never use it? | The token row, unused. |
| Why did redemption fail? | The redemption endpoint's error, not the request. |

<Info>
There is no login event for a *request*. A row is issued and a message is sent, and until someone redeems a token there is no sign-in to record. That is why "the user says they never got the email" is answered by the token row rather than the activity tab.
</Info>

### Migrating between the two modes

Moving an environment from Akountz-hosted pages to your own application, which is the usual direction of travel.

| Step | Why |
| --- | --- |
| Set `site_url`. | The switch that moves every emailed link. |
| Deploy your callback page. | It must handle `token`, `mfa_required`, and the invalid case. |
| Add local redirect bases if you develop locally. | `http://localhost` is not in the allowlist otherwise. |
| Verify the token request in your page. | A wrong context header produces a redemption failure. |

Going the other way — removing `site_url` to use hosted pages — needs no code change, and your callback page simply stops being used. Links in flight keep pointing at whatever they were built with.

<Warning>
Links already sent are unaffected by a `site_url` change. Each message carries the URL it was built with, so a user who requested a link before the change lands on the old destination and finds it still working.
</Warning>

### A complete configuration

A magic-link environment configured for real use, with the settings that actually matter.

```json
{
  "name": "production",
  "public_url": "https://auth.example.com",
  "auth": {
    "signup_enabled": true,
    "require_email_verification": true,
    "magic_link_enabled": true,
    "mfa_enabled": true,
    "site_url": "https://app.example.com",
    "redirect_urls": ["http://localhost:3000/auth/callback"],
    "emails": {
      "magic": {
        "subject": "Your Acme sign-in link",
        "text": "Sign in to Acme with this link. It works once, for 15 minutes:\n\n{link}\n\nIf you did not request this, ignore this message."
      }
    }
  }
}
```

| Setting | Why it is there |
| --- | --- |
| `site_url` | Links land on your callback page, not the hosted one. |
| `public_url` | The base for any hosted page, and for the OAuth callback. |
| `redirect_urls` | Local development only. |
| `magic_link_enabled` | Explicit, though it is the default. |
| `require_email_verification` | On, and satisfied by a magic-link redemption. |
| `emails.magic` | A subject with the product name and a body that says the window. |

<Warning>
The override's body keeps the *"works once, for 15 minutes"* sentence from the default, and adds a line for people who did not request it. Both are worth copying into any template you write — the first is a promise you are making, and the second prevents a forwarded link from being opened out of curiosity.
</Warning>

### Comparing the three emailed links

The three link-based flows share their machinery entirely, and confusing them is easy when diagnosing a failure.

| | Magic | Verification | Recovery |
| --- | --- | --- | --- |
| Purpose | `magic` | `verify` | `recovery` |
| Lifetime | 15 minutes | 24 hours | 1 hour |
| Signs someone in | yes | yes | yes, after setting a password |
| Marks email verified | yes | yes | no |
| Creates an account | optionally | no | no |
| Needs the user to supply a new password | no | no | yes |
| Revokes other sessions | no | no | **yes** |

Two of those rows carry real consequences.

**Verification signs the user in.** Completing a verification link returns a session, not just a confirmation. That is a design choice: the person proved control of the inbox, which is exactly the factor a sign-in requires, so there is no reason to make them type a password afterwards.

**Recovery revokes every other session.** Setting a new password ends all existing sessions for that account, because a password reset is the remedy for a suspected compromise and leaving the old sessions alive would defeat the point. See [Password recovery](/auth/password-recovery).

<Info>
Because the three flows share the same token and link machinery, a mixed-up purpose fails with the same invalid-or-expired error as an expired one. If a user reports that a *verification* email did not work, the most likely explanations are expiry at twenty-four hours or a second click.
</Info>

### How the flows share code

The same handler completes all of them, branching on the kind. That is why the behaviours above are consistent rather than individually implemented.

| Kind | Branch behaviour |
| --- | --- |
| `magic` | Marks email verified, challenges MFA, starts a session. |
| `verify` | Marks email verified, starts a session. |
| `recovery` | Peeks first to validate, then sets a password and starts a session. |
| `email_change` | Changes the address, marks it verified, returns no session. |

The recovery branch is the interesting one, because it runs twice: once with `peek` to check the token is good enough to render a form, and once to consume it. The peek does not mark the row used, which is what allows a form to be shown and then submitted.

<Warning>
The consequence is that a recovery token survives being rendered on a page but not being submitted. If a user loads the form and walks away, the link still works — up to an hour from issue. Do not assume loading a link has spent it.
</Warning>

### What the `type` parameter is for

The link carries `type` alongside `token`, and it names which flow the token belongs to.

| Field | Purpose |
| --- | --- |
| `token` | The signed one-time token. |
| `type` | The kind, so a shared callback page can route. |
| `redirect_to` | Present only when one was supplied and allowed. |

Your callback page can therefore dispatch on `type` before deciding which endpoint to call, rather than posting every token to every endpoint and relying on the errors.

```text
const { token, type, redirect_to: redirectTo } = Object.fromEntries(
  new URLSearchParams(window.location.search)
);

const endpoints = {
  magic: "/auth/v1/magic-link/verify",
  verify: "/auth/v1/verify",
  recovery: "/auth/v1/recover/confirm",
  email_change: "/auth/v1/email/confirm",
};
const endpoint = endpoints[type];
```

<Info>
A shared callback page is worth doing if you offer more than one link flow. Each token is only valid for its own purpose, so a mismatched dispatch produces an invalid error rather than a wrong action — safe, but confusing to users.
</Info>

### Account creation through a magic link

The details of the branch that creates an account, because it produces a specific kind of user.

| Aspect | Result |
| --- | --- |
| Password | None. An unusable password is set. |
| Username | Derived from the email local part. |
| Email verification | Not set by creation. Set when the link is redeemed. |
| Roles | The environment's `default_roles`. |
| Organizations | None, unless invited separately. |
| Event | `user.created`, with the magic-link method. |

The verification row is worth pausing on: an account created by a request is **unverified**, and becomes verified only when the link is redeemed. So in an environment requiring verification, the account exists but cannot sign in normally until the link is followed.

<Warning>
If `require_email_verification` is on and the user never follows the link, an account exists in the system that has never verified anything. That is expected, and it is why the **Users** tab in Studio can be filtered for unverified accounts — they are pending, not broken. See [Managing users](/auth/managing-users).
</Warning>

### Setting a password afterwards

A magic-link account has no usable password, and password sign-in fails against it until one exists. The route to a password is password recovery, which works because the flow never required a password in the first place.

```bash
curl -X POST "$BASE/auth/v1/recover" \
  -H 'content-type: application/json' \
  -d '{"email": "ada@example.com"}'
```

The recovery link sets a password, revokes every other session — including the magic-link session the user may currently hold — and signs them in again.

<Warning>
Because recovery revokes all sessions, a user who sets a password while signed in via magic link will be signed out and back in. That is correct behaviour and it surprises people the first time.
</Warning>

### Testing the flow properly

Magic links are unusually hard to test end to end, because the link leaves your server. Three techniques cover it.

**Read the token out of the mail sink.** With a sandbox SMTP service, the message is captured rather than sent, so you can copy the token directly and test redemption without an inbox.

```bash
# Request, then extract the token from the captured message.
curl -sX POST "$BASE/auth/v1/magic-link" \
  -H 'content-type: application/json' -d '{"email":"ada@example.com"}'

# Redeem it. Expect the standard token response.
curl -sX POST "$BASE/auth/v1/magic-link/verify" \
  -H 'content-type: application/json' -d '{"token":"..."}'
```

**Decode the link without verifying it.** The token is a signed payload, and decoding it — without verifying the signature — gives you the id, which is enough to find the row and answer most questions.

**Test the failure paths deliberately.** Expiry, double redemption, and a token from another environment all produce the same error, so you cannot tell them apart by testing one and assuming the others behave.

| Path | How to force it |
| --- | --- |
| Expired | Wait fifteen minutes, or edit the row's expiry. |
| Already used | Redeem twice. |
| Wrong environment | Redeem a staging token against production. |
| Not allowed | Send a `redirect_to` outside the allowlist. |
| Disabled | Disable the account, then request. |

<Info>
Because the failure is deliberately uniform, a test suite that asserts on specific errors for specific causes will fail — and that failure is the design working. Assert on the status and the fact that it is the same message.
</Info>

### Load and abuse resistance

| Protection | Value | What it stops |
| --- | --- | --- |
| Request limit | 10 per 60 seconds | Request floods. |
| Identical response | always | Account enumeration. |
| Short lifetime | 900 seconds | A stale link in an inbox. |
| Single use | once | Replay after redemption. |
| Bound to environment | yes | Cross-environment use. |

<Warning>
The identical response means you cannot build a "this address is not registered, sign up?" prompt on top of this endpoint. If your product needs that reassurance, the answer is a separate flow that also does not leak — an invitation, or an account-recovery page that behaves the same way.
</Warning>

### Comparison with the other one-time tokens

Every one-time token in the system, and what its lifetime is chosen for.

| Purpose | Lifetime | Consumed by | Revocable individually |
| --- | --- | --- | --- |
| `mfa` | 5 minutes | A code entry | no |
| `link` | 10 minutes | A provider callback | no |
| `magic` | 15 minutes | A sign-in | no |
| `recovery` | 1 hour | A password form | no |
| `verify` | 24 hours | A confirmation | no |
| `email_change` | 24 hours | A confirmation | no |
| `invite` | 7 days | An acceptance | no |

The pattern is the lifetime tracks how long a person plausibly takes between receiving and using the message, and nothing longer. An invitation gets a week because it may arrive as part of an onboarding sequence; a magic link gets fifteen minutes because the person asked for it and is waiting.

<Info>
None of them can be revoked individually, which is worth knowing for the long-lived ones. An invitation that should not have been sent cannot be cancelled by revoking the token — you revoke the invitation itself. See [Organizations](/auth/organizations).
</Info>

### A browser implementation, complete

A callback page that handles every branch, since the branches are what get missed.

```text
// /auth/callback?token=...&type=magic
const params = new URLSearchParams(window.location.search);
const token = params.get("token");
const type = params.get("type");

async function redeem(kind, value, extra = {}) {
  const res = await fetch(`/auth/v1/${kind}`, {
    method: "POST",
    headers: {
      "content-type": "application/json",
      "X-Pawabase-Context": CONTEXT,
    },
    body: JSON.stringify({ token: value, ...extra }),
  });
  return { ok: res.ok, body: await res.json() };
}

if (!token) {
  renderError("This link is missing its token.");
} else {
  const { ok, body } =
    type === "recovery"
      ? await redeem("recover/confirm", token, { password: await promptForPassword() })
      : type === "magic"
      ? await redeem("magic-link/verify", token)
      : await redeem(type, token);

  if (!ok) {
    // Every failure is "the link is invalid or has expired" -- so say that,
    // offer another link, and stop. Do not try to work out which it was.
    renderExpired(body.detail);
  } else if (body.mfa_required) {
    // The account has MFA. Nothing was signed in yet.
    promptForCode(body.mfa_token);
  } else if (body.access_token) {
    // Store FIRST, then clean the URL. A failure after this point strands
    // the user with a spent token.
    storeSession(body);
    history.replaceState(null, "", "/");
  } else {
    // email_change returns {email, changed} and signs nobody in.
    renderChanged(body.email);
  }
}
```

| Branch | Shape | Action |
| --- | --- | --- |
| Invalid or expired | `{detail}` | Offer another link. Do not diagnose. |
| MFA required | `{mfa_required, mfa_token}` | Prompt for a code. |
| A session | the token response | Store, then clean the URL. |
| Email change | `{email, changed}` | Confirm. No session. |

<Warning>
The ordering in the success branch is deliberate and is the single most important line on this page. Storing the session before anything else that could fail is what stops a user ending up with a consumed token and no session.
</Warning>

<Info>
The same page handles verification and email change because the flows share the token machinery. Dispatching on `type` is what makes that safe — a token for one purpose cannot be redeemed as another.
</Info>

### Without JavaScript, or without a page

Some deployments have no application to land on, and that is a legitimate configuration rather than a compromise.

| You have | What happens |
| --- | --- |
| No `site_url`, a `public_url` | Akountz-hosted pages complete every link flow. |
| No `site_url`, no `public_url` | The link is built from an empty base and will not work. |
| A `site_url` but no page deployed | The link lands on a 404. |

The middle row is the only genuinely broken state, and it produces a link that looks right in the inbox and fails when clicked.

<Warning>
Setting a `site_url` before deploying the page that handles it is the most common sequencing mistake. In that window every magic link goes to a 404, and the only remedy is requesting a new one after the page is live.
</Warning>

### Frequently asked, with short answers

**Should I offer magic links and passwords together?**
Yes, if you want both kinds of user. They do not conflict; a magic-link account simply has no password until it sets one.

**Does a magic link create an account?**
Only when the address has none, `create_user` is true, and sign-up is enabled. Otherwise nothing is created and no message is sent — with an identical response either way.

**Why does the response not tell me whether the address exists?**
Because that would make the endpoint a membership oracle, letting anyone enumerate which addresses have accounts in your environment. Every endpoint that emails a link answers the same way.

**Can the user land on a specific page afterwards?**
Yes, with `redirect_to`, if it is inside the allowlist. Anything else is rejected when the link is requested.

**How long is the link valid?**
Fifteen minutes, once. The default email says so.

**Does it work if the user clicks twice?**
No. The second click fails, and the error says invalid or expired. The first click already worked.

**Is it safe with a mail scanner?**
Not reliably — a scanner that prefetches links will consume the token. Ask for an exemption for your domain.

**Does it verify the email address?**
Yes. Completing the link is the proof of inbox control.

**Does it work for a user with MFA?**
Yes, but it returns a challenge rather than a session, and you need a `site_url` so your page can prompt for the code.

**Which session level does it produce?**
`aal1` — one factor, exactly like a password sign-in.

**Where do I turn it on?**
**Magic links** in the **Sign-in methods** section of the **Configuration** tab. It is on by default.

Every body involved, so nothing has to be inferred.


| Body | From | Branch on |
| --- | --- | --- |
| The sent acknowledgement | the request | nothing — it is always this |
| The token response | redemption | `access_token` present |
| The challenge | redemption | `mfa_required` |
| The error | any failure | status only |

<Warning>
The request response has no variant. If your client branches on it to decide whether to show a different message, one of those branches will be wrong for users whose address simply does not exist.
</Warning>

### Errors, exhaustively

| Status | Detail | From | Meaning |
| --- | --- | --- | --- |
| 403 | `magic links are disabled` | request | `magic_link_enabled` is false. |
| 400 | `redirect_to is not an allowed URL` | request | The target is not allowlisted. |
| 400 | `the link is invalid or has expired` | redemption | Spent, expired, malformed, or wrong environment. |
| 403 | `this account is disabled` | redemption | The account was disabled after the link was issued. |
| 422 | `a valid email address is required` | request | The address failed normalisation. |
| 429 | rate limited | request | Ten per minute. |

The 422 is worth noting because it is the one failure the endpoint does distinguish. A malformed address is refused outright rather than being silently accepted, because normalising it would be guesswork — and no message is sent, so nothing leaks.

<Info>
A `422` is the only request-time failure that depends on the *input* rather than on whether the address exists. Everything else about an address is answered identically.
</Info>

| Question | Answer |
| --- | --- |
| Does it have a password? | No, unless one was set later. |
| Is the email verified? | Yes, once the link is redeemed. |
| What roles does it have? | The environment's `default_roles`. |
| Is it in an organization? | Not unless invited. |
| What can it sign in with afterwards? | Magic link, and password or social once set up. |

### The configuration keys, complete

Every setting that changes this flow, with what an unset value means.

| Key | Default | Effect when unset |
| --- | --- | --- |
| `magic_link_enabled` | `true` | The flow is offered. |
| `site_url` | `""` | Akountz-hosted pages are used. |
| `redirect_urls` | `[]` | Only `site_url` is allowlisted. |
| `signup_enabled` | `true` | Links can create accounts. |
| `emails.magic` | built-in | The default copy is used. |
| `mfa_enabled` | `true` | Enrolled users are challenged. |
| `public_url` | `""` | Falls back to Akountz's own setting. |

<Warning>
Three of those seven default to a permissive value, which is why an unconfigured environment offers magic links, creates accounts through them, and challenges enrolled users. Nothing here is off unless it is explicitly turned off.
</Warning>

### Operating a magic-link deployment

The recurring tasks, and what each of them needs.

| Task | Where | Notes |
| --- | --- | --- |
| Confirm the flow works | A sandbox mail service | The only reliable end-to-end check. |
| Turn it on | **Magic links** in Configuration | On by default; be explicit. |
| Change the destination | **Site URL** | Moves every emailed link. |
| Change the copy | **Email templates** | Keep the fifteen-minute promise. |
| Find who used it | **Sign-in activity** | Successes show the method. |
| Find who requested and did not use it | The token table | There is no event for it. |
| Reset someone who lost everything | **New password** in the user modal | The only recovery path. |

<Warning>
The gap in that table is worth naming. A user who requested a link and never used it leaves **no trace in the activity tab**, because there was no sign-in. The token row is the only record. If you are chasing "did they get the email", that row is where the answer is.
</Warning>

### The three questions to answer before offering magic links

| Question | Why it matters |
| --- | --- |
| Where does the link land? | Decides whether you own the callback and whether MFA can be prompted. |
| What does the request say to the user? | It cannot confirm an account exists, and the copy has to reflect that. |
| What happens if mail is scanned? | Their link will be dead on arrival. Decide whether to raise this with IT. |

The third is the one that generates the most user reports and the least engineering work, because nothing in your code can fix it.

### A note on naming

The feature is called magic links because the credential is the message rather than something the user knows. The same mechanism is described elsewhere as a passwordless link, an email OTP, or a one-time sign-in link, and all four names refer to the same thing here: a `magic`-purpose token delivered by email and redeemed once.

<Info>
If you are reading documentation from another product that uses one of those names, check which purpose it maps to before assuming the behaviour matches. The distinguishing features here are the fifteen-minute window, the identical request response, and the account creation controlled by `create_user`.
</Info>

### The request, exhaustively

Every field, every constraint, and what each one actually governs.

| Field | Type | Required | Default | Governs |
| --- | --- | --- | --- | --- |
| `email` | string | yes | — | Where the link goes. Normalised to lowercase. |
| `create_user` | bool | no | `true` | Whether an unknown address creates an account. |
| `redirect_to` | string | no | `null` | Where the user lands afterwards. Must be allowlisted. |

| Condition | Result |
| --- | --- |
| `magic_link_enabled` is false. | `403`, before anything else is considered. |
| `redirect_to` fails the allowlist. | `400`, before any token is issued. |
| The address is malformed. | `422`, before any lookup. |
| Otherwise. | A token is issued if there is somewhere to send it. |

<Info>
The order of those checks is what you want: the feature check, the redirect check, the address check, and only then the lookup. It means a misconfigured client is told so, rather than being answered with a cheerful acknowledgement that will fail later.
</Info>

### `create_user`, restated precisely

The flag interacts with two things, and the interaction is not obvious from the name.

| `signup_enabled` | `create_user` | Unknown address |
| --- | --- | --- |
| true | true | Account created, link sent. |
| true | false | No account, no message. |
| false | true | No account, no message. |
| false | false | No account, no message. |

So in an invite-only environment, `create_user` makes no difference at all — sign-up being off already prevents creation. The flag only has an effect where sign-up is on, where it lets you let *some* users self-serve and not others.

<Warning>
Because three of the four rows are identical and share a response with the fourth, a client cannot tell a user that magic links will not create them an account. If your product needs to say that, the setting that decides it is `signup_enabled`, and it should be explained before they type their address.
</Warning>
