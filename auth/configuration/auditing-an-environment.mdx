When you inherit an environment, or review one before a launch, the useful move is to compare the live block against the defaults rather than reading it top to bottom. Every difference is either a decision somebody made or a mistake, and the defaults tell you which features are running unexamined.

| If you find | It means |
| --- | --- |
| `password_policy` absent or `"basic"` | Nobody chose a policy. Eight characters of anything is in force. |
| `require_email_verification` absent | Addresses are unproven, and every emailed link flow inherits that. |
| `site_url` empty | Redirects land on Akountz's own pages. |
| A provider with no `client_id` | A provider that looks configured and is invisible to every client. |
| `default_roles` naming an unknown role | New accounts carry a role granting nothing. |
| `emails` empty | Users receive the built-in copy, which mentions the project name only. |
| `access_ttl` very high | Removed permissions stay live for that long. |
| `refresh_ttl` at 2592000 | The thirty-day default, which is long for anything sensitive. |

Three questions settle most of it:

**Which keys are absent?** Anything absent is running on a default you did not choose. In a block where several keys are absent, the environment has been partially configured rather than deliberately set up.

**Which keys are present but null?** Null means the default, so a key that looks configured is not. This is the failure the config format makes possible and the one a visual review is most likely to miss.

**Do the role names exist?** `default_roles` is not validated against the Roles tab, so this needs checking by hand. It is the only item on this list where the configuration is silently wrong rather than silently default.

<Warning>
An audit that reads the block in Studio can miss a null, because the form renders a null as its default value. Read the block through an API if you are auditing rather than editing — the form tells you what the controls would write, not necessarily what is stored.
</Warning>


## Promotion and drift

Promoting a definition from one environment to another moves the `auth` block. That is convenient until the environments are supposed to differ, at which point the promotion either overwrites a deliberate difference or is blocked by one.

The keys that normally *should* differ, because they name the environment itself:

| Key | Why it differs |
| --- | --- |
| `site_url` | The application's origin differs per environment. |
| `providers.*.client_id` | Each environment registers its own OAuth application. |
| `providers.*.client_secret` | A `secret://` reference that must resolve per environment. |
| `emails` | Often tuned to the environment — a staging notice, a real domain. |

The keys that normally should *not* differ, because a difference is a bug:

| Key | A difference means |
| --- | --- |
| `password_policy`, `password_min_length` | Staging accepts passwords production rejects, so staging tests mislead. |
| `require_email_verification` | Same, for the verification flow. |
| `signup_enabled` | Legitimate to differ, but often accidental. |
| `access_ttl`, `refresh_ttl` | Different session security between environments, usually unintended. |

<Warning>
`site_url` promoted from staging to production is the single most consequential drift in this block: the value is correct in the environment it came from and silently wrong in the one it lands in, and users reach the wrong application without any error.
</Warning>

| What promotion carries | What it does not |
| --- | --- |
| The `auth` block | Users, in any environment |
| Routes, functions, policies | Sessions |
| Data definitions | Secrets referenced by `secret://` |
| — | Anything provisioned per environment |

<Info>
The practical consequence is that a correctly promoted environment can still have no users, no working provider, and no deliverable email, and look entirely correct in a config review. Configuration is promoted; the things that depend on it are provisioned.
</Info>

### Secrets do not travel

A `secret://NAME` reference is a name, not a value. The name travels with the configuration; whether it *resolves* is a property of the environment that reads it.

That produces the same failure mode as a missing `client_id`: the provider stops being reported to clients and 404s on use, with no error anywhere in the configuration. The distinction is that the configuration looks entirely correct.

| Situation | Result |
| --- | --- |
| The secret exists in both environments. | Works after promotion. |
| The secret exists in development only. | The provider is silently absent in production. |
| The reference is misspelled. | Same, in every environment. |

<Warning>
A dangling `secret://` reference and an empty `client_id` produce the identical symptom — a missing provider button — for entirely different reasons. If a provider is invisible, check both, and check them in the environment you are actually serving rather than the one you configured.
</Warning>


## Terms, precisely

| Term | Means |
| --- | --- |
| **`AuthConfig`** | One environment's authentication settings, with defaults applied. |
| **`auth` block** | The settings object inside an environment payload. Thirteen configurable keys. |
| **Akountz** | The identity service. Reads the `auth` block; never writes it. |
| **Environment** | One `project` + `env` pair. The unit of tenancy and of configuration. |
| **Platform environment** | The reserved `_platform` environment holding Studio's operators. Not configurable. |
| **`redirect_allowed`** | Whether a URL may receive tokens: the site URL or an allowlisted prefix. |
| **`enabled_providers()`** | The providers reported to clients — enabled *and* with a client id. |
| **`secret://NAME`** | A reference to a stored secret, used instead of a literal credential. |
| **`config_ttl`** | Seconds an environment's config is cached. Default 10. Installation setting. |
| **`aal`** | Authentication assurance level. `aal1` normally, `aal2` after MFA. |

<Warning>
`signup_enabled`, `magic_link_enabled`, and `mfa_enabled` all default to **on**, and all three treat an explicit `null` as absent. That single behaviour, repeated across the block, is responsible for most of the confusion this page exists to prevent.
</Warning>


## What to take away

Five things.

**An unset key is the default, not "off".** And `null` counts as unset. The permissive defaults mean that clearing a value is not the same as disabling it.

**Only the API writes this block; Akountz only reads it.** That is why there is no validation on unknown keys and no error when a feature you disabled stays on.

**Configuration is cached for ten seconds.** A save followed by an immediate retry can read the old values, and no test should assert on a setting in the same breath as changing it.

**The platform environment is not yours.** `_platform` is hardcoded, holds Studio's operators, and is why signing into Studio does not test your application's sign-in.

**Each environment needs its own everything.** Site URL, OAuth registrations, secret references, and users. Promotion moves configuration and nothing else.

From here, [Authentication](/auth/overview) gives the layered model these settings sit in, [Passwords](/auth/passwords) covers the grant the policy governs, and [Security model](/auth/security-model/overview) covers what to validate before real users arrive.
