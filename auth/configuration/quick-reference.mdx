### Keys, defaults, and where they live

| Key | Default | Studio control | Section |
| --- | --- | --- | --- |
| `signup_enabled` | `true` | **Sign-up enabled** | Sign-up |
| `require_email_verification` | `false` | **Require email verification** | Sign-up |
| `default_roles` | `[]` | **Default roles** | Sign-up |
| `password_policy` | `"basic"` | **Policy** | Passwords |
| `password_min_length` | `8` | **Minimum length** | Passwords |
| `access_ttl` | `900` | **Access token lifetime** | Passwords |
| `refresh_ttl` | `2592000` | **Refresh token lifetime** | Passwords |
| `magic_link_enabled` | `true` | **Magic links** | Sign-in methods |
| `mfa_enabled` | `true` | **MFA (TOTP)** | Sign-in methods |
| `site_url` | `""` | **Site URL** | URLs |
| `redirect_urls` | `[]` | **Additional allowed redirect URLs** | URLs |
| `providers` | `{}` | Provider cards | OAuth providers |
| `emails` | `{}` | **Email templates** | Email templates |

### The values that catch people

| Written | Actual effect |
| --- | --- |
| `"signup_enabled": null` | Enabled — the default. |
| `"signup_enabled": "false"` | Enabled — a truthy string. |
| `"magiclink_enabled": false` | No effect — the key is unknown. |
| `"enabled": null` on a provider | Enabled — only `false` disables. |
| `site_url: "app.example.com"` | Matches nothing — no scheme. |
| A generic provider missing an endpoint | Fails on use, not on listing. |

### The platform environment, hardcoded

`signup_enabled` false, `password_policy` strict, `password_min_length` 10, `access_ttl` 3600, `refresh_ttl` seven days, `magic_link_enabled` false.

<Warning>
If you cannot find a setting on this page, it is in one of three places: the installation settings above, the reserved platform environment, or your own policies. The `auth` block governs what an environment *offers* — never what your policies *allow*.
</Warning>


## Configuring an environment from scratch

A worked shape, for an environment nobody has configured yet. The order is not a procedure — it is roughly the order in which dependencies bite.

**An application URL, so redirects have somewhere to land.** `site_url` set to the application's origin, with the scheme. Nothing else in the configuration works properly without it, and an empty value produces Akountz-hosted pages that look like a bug.

**A password policy worth the name.** `strict`, with a minimum of twelve or more. The `basic` default is a length check and nothing else.

**Verification, if the product holds real data.** `require_email_verification` on, because every link-based flow depends on the address belonging to whoever holds it.

**Sign-up, deliberately.** Either off for an invite-only product, or on with `default_roles` naming roles that actually exist — the second row of that pair is the one that gets skipped, and it is what produces accounts that can sign in and do nothing.

**Lifetimes matched to the risk.** `access_ttl` sized against how long a removed permission may keep working; `refresh_ttl` sized against how long a stolen refresh token is acceptable.

**Providers, only if you need them.** Four shipped names, credentials as `secret://` references, and a separate OAuth registration per environment because the callback URL contains the project and environment.

**Email copy, once the flows work.** Overrides per kind, with placeholders checked. Editing templates before mail delivery works just moves the failure.

**Then read the block back.** Thirteen keys, and comparing what you wrote against the defaults shows every deliberate change and every typo'd key at once.

```json
{
  "signup_enabled": false,
  "require_email_verification": true,
  "password_policy": "strict",
  "password_min_length": 12,
  "access_ttl": 900,
  "refresh_ttl": 604800,
  "magic_link_enabled": true,
  "mfa_enabled": true,
  "site_url": "https://app.example.com",
  "redirect_urls": [],
  "providers": {
    "github": {
      "enabled": true,
      "client_id": "Iv1.abc123",
      "client_secret": "secret://GITHUB_SECRET",
      "scopes": ["read:user"]
    }
  },
  "default_roles": ["customer"],
  "emails": {}
}
```

<Warning>
The one thing this block cannot express is whether `customer` exists. `default_roles` is not validated against the role list, so a typo produces accounts carrying a role that grants nothing, and no error anywhere. Create the roles first, in the **Roles** tab of the same environment.
</Warning>


## The route surface, for reference

Which endpoints read these settings, and which of them consult which key. Useful when you are tracing "which setting controls this behaviour".

| Route | Settings it reads |
| --- | --- |
| `GET /auth/v1/settings` | `signup_enabled`, `require_email_verification`, `magic_link_enabled`, `mfa_enabled`, `enabled_providers()`, `password_policy`, `password_min_length` |
| `POST /auth/v1/signup` | `signup_enabled`, `redirect_allowed`, `require_email_verification`, `default_roles`, the password policy, `access_ttl`, `refresh_ttl` |
| `POST /auth/v1/token` | `require_email_verification`, `mfa_enabled`, `password_*` at change time only, `access_ttl`, `refresh_ttl` |
| `POST /auth/v1/recover` | `emails.recovery`, and `site_url` for the link |
| `POST /auth/v1/recover/confirm` | The password policy |
| `POST /auth/v1/magic-link` | `magic_link_enabled`, `emails.magic`, `site_url` |
| `POST /auth/v1/verify/request` | `emails.verify`, `site_url` |
| `GET /auth/v1/authorize/...` | `providers`, `redirect_allowed`, `public_url` |
| `GET /auth/v1/callback/...` | `providers`, `signup_enabled`, `site_url` |
| `GET /auth/v1/user`, `PATCH` | The password policy, `emails.email_change`, `site_url` |
| `POST /auth/v1/identities/link` | `providers`, `site_url` |

Two patterns in that table are worth naming.

**The settings endpoint is deliberately incomplete.** It reports what a client needs in order to render a sign-in screen, and nothing else. There is no list of roles, no user, and no token — it is a public description of the environment, callable before sign-in.

**`site_url` appears wherever a link is built.** Verification, recovery, magic link, invitations, email change, and identity linking all consult it, because all of them produce a URL that a browser will follow.

<Info>
The admin routes under `/projects/{project}/envs/{env}` do not read most of these keys, because they act on users rather than admitting them. Creating a user applies the password policy; everything else about an account's sign-in behaviour comes from the settings above.
</Info>


## Choosing values deliberately

The defaults are a starting point. These are the decisions worth making consciously rather than inheriting.

| Decision | The tension |
| --- | --- |
| Sign-up on or off | Open growth versus who may hold an account. |
| Verification required | Deliverability risk versus address ownership. |
| `basic` or `strict` | Onboarding friction versus credential strength. |
| Minimum length | Longer is better, up to the point users reuse a shorter one anyway. |
| `access_ttl` | Refresh load versus how long a removed permission survives. |
| `refresh_ttl` | Convenience versus exposure of a stolen credential. |
| Magic links on | Removes credential risk; adds dependence on mail delivery. |
| MFA available | Costs nothing until users opt in; requires offering enrolment. |
| `default_roles` | Convenience versus a wrong name granting nothing. |

Three of these have consequences that are not obvious from the setting itself:

**Verification versus deliverability.** Requiring confirmation means a user cannot use the product until they find the mail. If your mail service is flaky, you have converted a delivery problem into a sign-up problem.

**Length versus composition.** Raising `password_min_length` under `basic` buys length without strength. The same characters under `strict` buy both, because the validator assesses the whole password rather than counting it.

**Refresh lifetime versus convenience.** A long `refresh_ttl` means users are not asked to sign in again for weeks. It also means a stolen refresh token is useful for weeks — until it is used, at which point the whole family dies and both parties are signed out.

<Warning>
Whichever values you choose, they belong in the environment's `auth` block rather than in your client. A client that hardcodes an assumption about the policy, the lifetimes, or which methods exist will break the moment an operator changes any of them — and it will break in the environment you did not test.
</Warning>


## The whole block as one artifact

For reference when writing configuration by hand or reviewing a change. This is the full default block, then a second block showing a tightened environment, so the two can be diffed by eye.

**Defaults**

```json
{
  "signup_enabled": true,
  "require_email_verification": false,
  "password_policy": "basic",
  "password_min_length": 8,
  "access_ttl": 900,
  "refresh_ttl": 2592000,
  "magic_link_enabled": true,
  "mfa_enabled": true,
  "site_url": "",
  "redirect_urls": [],
  "providers": {},
  "default_roles": [],
  "emails": {}
}
```

**A tightened production environment**

```json
{
  "signup_enabled": false,
  "require_email_verification": true,
  "password_policy": "strict",
  "password_min_length": 12,
  "access_ttl": 900,
  "refresh_ttl": 604800,
  "magic_link_enabled": true,
  "mfa_enabled": true,
  "site_url": "https://app.example.com",
  "redirect_urls": ["https://app.example.com/auth/callback"],
  "providers": {},
  "default_roles": ["customer"],
  "emails": {}
}
```

Seven keys differ between them, and each one is a decision rather than a default:

| Key | From | To | The decision |
| --- | --- | --- | --- |
| `signup_enabled` | `true` | `false` | Invite-only. |
| `require_email_verification` | `false` | `true` | Addresses must be proven. |
| `password_policy` | `"basic"` | `"strict"` | Strength, not just length. |
| `password_min_length` | `8` | `12` | A floor worth having. |
| `refresh_ttl` | `2592000` | `604800` | Seven days rather than thirty. |
| `site_url` | `""` | The origin | Redirects land in the product. |
| `default_roles` | `[]` | `["customer"]` | New accounts are not powerless. |

`access_ttl`, `magic_link_enabled`, `mfa_enabled`, `redirect_urls`, `providers`, and `emails` are unchanged, and their defaults are defensible — 900 seconds, both methods available, no providers without configuration, and the built-in email copy.

<Warning>
The diff is the review. Reading a proposed change as a list of changed keys is far more reliable than reading the resulting block, because a key that was *meant* to change and did not is invisible in the output and obvious in the diff.
</Warning>
