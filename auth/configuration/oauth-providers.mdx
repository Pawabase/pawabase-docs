The `providers` object is keyed by provider name, and each entry is that provider's configuration. Studio renders one card per entry under a section described as *"Social sign-in. Reference credentials as secret://NAME rather than pasting them here."*

### The providers that ship

Four providers have built-in knowledge of their endpoints and scopes. Anything else is a generic provider and must supply its own.

| Key | Class | Extra |
| --- | --- | --- |
| `google` | `GoogleOAuthProvider` | — |
| `github` | `GithubOAuthProvider` | — |
| `discord` | `DiscordOAuthProvider` | — |
| `microsoft` | `MicrosoftOAuthProvider` | Accepts a `tenant` setting. |

<Warning>
There is no Apple, Facebook, or LinkedIn provider. If you need one, it is a generic provider and you supply all three endpoints yourself. Readers arriving with a list of providers in mind should treat that list as shorter than they expect.
</Warning>

OIDC is used when `openid` appears among the scopes, which is how you get an identity token rather than plain OAuth. Microsoft's `tenant` narrows which tenant the login is accepted from — `common` accepts any, and a specific tenant id restricts it.

### Generic providers

Any name outside those four becomes a generic OAuth provider, and it must supply three endpoints:

| Required key | Without it |
| --- | --- |
| `authorize_endpoint` | A 500 naming the provider and saying it needs the endpoints |
| `token_endpoint` | The same |
| `userinfo_endpoint` | The same |

```json
{
  "providers": {
    "gitlab": {
      "enabled": true,
      "client_id": "...",
      "client_secret": "secret://GITLAB_SECRET",
      "authorize_endpoint": "https://gitlab.com/oauth/authorize",
      "token_endpoint": "https://gitlab.com/oauth/token",
      "userinfo_endpoint": "https://gitlab.com/api/v4/user",
      "scopes": ["read_user"]
    }
  }
}
```

<Info>
The failure mode is unhelpful in an instructive way: the 500 appears when the provider is *used*, not when it is configured or listed. A generic provider missing an endpoint will therefore look like a broken button rather than a configuration error, because it lists fine and only fails on click.
</Info>

A shipped provider can still be given the three endpoint keys, and doing so overrides the built-in values. That is the escape hatch for a provider whose endpoints have changed.

### Every provider key

| Key | Type | Default | Meaning |
| --- | --- | --- | --- |
| `enabled` | bool | `true` when absent | Whether the provider is available. |
| `client_id` | str | — | The OAuth client id. **Required for the provider to appear at all.** |
| `client_secret` | str | — | A `secret://NAME` reference, not a literal. |
| `scopes` | list[str] | Provider defaults | Requested scopes. `openid` selects OIDC. |
| `tenant` | str | — | Microsoft only. Which tenant to accept. |
| `authorize_endpoint` | str | Shipped value | Generic providers must set it. |
| `token_endpoint` | str | Shipped value | Generic providers must set it. |
| `userinfo_endpoint` | str | Shipped value | Generic providers must set it. |

`enabled` defaults to enabled when the key is absent, which is a second place where an unset key means "on". A provider card with the switch off and no `enabled` key at all behaves differently, and only the first is what the switch shows you.

<Warning>
Because `enabled` is read as "not explicitly false", writing `"enabled": null` leaves the provider **enabled**. If you are generating this block programmatically, emit a real boolean or omit the key deliberately — do not emit null.
</Warning>

### Credentials as references

**Credentials are referenced as `secret://NAME`, never pasted.** The **Client secret** field's placeholder is `secret://GITHUB_SECRET`, which is the intended shape of the value.

| Approach | Consequence |
| --- | --- |
| `"client_secret": "secret://GITHUB_SECRET"` | The value is resolved at use time from the installation's secrets. |
| `"client_secret": "ghp_abc123..."` | The literal sits in the environment definition, in every export, and in every backup. |

The configuration block is readable, promotable, and included in environment definitions — which makes it the wrong place for anything secret, regardless of how the environment is secured.

<Warning>
A `secret://` reference that does not resolve behaves like a missing credential, which means the provider stops being reported to clients — the same invisible state as an empty `client_id`. Check that the secret exists in *this* environment; a reference that resolves in development may dangle in production.
</Warning>

### What makes a provider "enabled"

This is the rule that produces the most confusing provider symptom, so it is worth stating on its own.

A provider counts as enabled if **both** conditions hold:

1. `enabled` is not explicitly `false` — so absent, `true`, or `null` all pass.
2. `client_id` is present and non-empty.

Both the settings endpoint and the provider builder apply this same filter, which means there is **no partially enabled state**. A provider either appears in the client and works, or it does not appear and 404s when used.

<Warning>
A provider card with every field filled in except the client id looks complete. The switch is on. It simply does not exist as far as any client is concerned, and the failure mode is a *missing button* rather than an error — which is why this is so often misdiagnosed as a client bug.
</Warning>

| In the block | Reported to clients? | Usable? |
| --- | --- | --- |
| `enabled: true`, `client_id` set | Yes | Yes |
| `enabled: true`, no `client_id` | **No** | No — 404 on use |
| `enabled: false`, `client_id` set | No | No — 404 on use |
| `enabled` absent, `client_id` set | Yes | Yes |
| `enabled: null`, `client_id` set | Yes | Yes |

The last two rows are the same shape of surprise as the unset-key rule elsewhere, and the same fix applies: emit a real boolean, or omit it deliberately.

<Info>
Because the filter is on both sides, you cannot have a provider that is listed but broken. That is a good property: a client that renders exactly what it is told will never offer a button that cannot work.
</Info>

### The callback URL

The callback is `{public_url}/auth/v1/callback/{project}/{env}/{provider}`. Both the project and the environment are **in the path**, unlike every other route.

That is because these are browser navigations. A browser cannot carry the gateway-signed context header that every other route uses to learn the environment, so the environment has to be in the URL.

The consequence for configuration is that the same provider has a different callback URL in each environment, and each one must be registered with the provider. `public_url` comes from the environment payload or falls back to Akountz's own setting, which is why it is worth checking after moving an installation behind a different hostname.


## Email templates

The `emails` object overrides the subject and body of each auth message, keyed by kind. Exactly five kinds exist, and each has a default subject and body you can see in Studio.

| Kind | Default subject |
| --- | --- |
| `verify` | `Confirm your email for {project}` |
| `recovery` | `Reset your {project} password` |
| `magic` | `Your {project} sign-in link` |
| `invite` | `You are invited to {organization} on {project}` |
| `email_change` | `Confirm your new email for {project}` |

```json
{
  "emails": {
    "verify": {
      "subject": "Confirm your Acme account",
      "text": "Hi,\n\nConfirm your address to finish setting up Acme:\n\n{link}\n\nIf you did not sign up, ignore this message."
    }
  }
}
```

<Warning>
An unknown kind is ignored rather than rejected, exactly like an unknown top-level key. A typo such as `verifcation` produces no error and no effect — the built-in default is used instead, and you will see your old copy in the inbox.
</Warning>

### Placeholders

Each template may use these, and no others:

| Placeholder | Available in |
| --- | --- |
| `{project}` | All five kinds. The project display name. |
| `{link}` | All five kinds. The action link, already formatted. |
| `{email}` | All five kinds. The address involved. |
| `{organization}` | `invite` only. |
| `{role}` | `invite` only. The role the invite would grant. |

<Info>
An unknown placeholder is **left in the message literally** rather than raising an error. A typo therefore shows up as visible stray text in the delivered mail — `{lnik}` appearing in the body, for instance — rather than as a failed send.
</Info>

That behaviour is a deliberate choice about where a bug should be visible. A template that silently dropped an unknown placeholder would produce a mail with a missing link and no explanation; one that leaves it literal produces a visibly broken mail that somebody notices immediately. The cost is that you will not get a validation error at configuration time.

<Warning>
The plain-text template is also HTML-escaped when the HTML part is generated, and newlines become line breaks, with the `{link}` value wrapped in an anchor. Raw HTML in your template will appear escaped — `<b>` shows as `<b>` rather than rendering bold.
</Warning>

### Delivery

Email goes through the API's mail service, which means it uses the **environment's** SMTP settings. This is the most common cause of "auth emails never arrive", and it is not a template problem.

| Step | Requirement | Symptom if missing |
| --- | --- | --- |
| 1 | The environment's mail service works. | The request succeeds and nothing is delivered. |
| 2 | `site_url` is set. | The mail arrives, on Akountz's own domain. |
| 3 | The address has an account, where relevant. | The response is identical either way, by design. |

<Warning>
A successful response from a recovery or magic-link request proves nothing about delivery — those endpoints answer identically whether or not the address exists, which is the anti-enumeration property. Watch the SMTP side to confirm a message was actually sent.
</Warning>

### Where the link points

`site_url` decides this, and it is worth being clear because the difference is visible to users and confusing the first time you see it.

| `site_url` | Destination |
| --- | --- |
| Set | Your application, at `{site_url}/auth/callback?token=...&type=...` |
| Empty | Akountz's own hosted page, at `{public_url}/auth/v1/links/{project}/{env}/{kind}?...` |

The `type` parameter tells your callback which flow the token belongs to, so one route can dispatch verification, recovery, and magic-link completion without guessing.

When there is no `site_url`, Akountz serves its own page and the flow still completes — the token is consumed and the session issued. It is a working configuration, not a broken one. What you lose is your own branding and your own session handling, because the user never reaches your application.

<Warning>
An environment can be fully functional with no `site_url` and still surprise everybody who expected to land in the product. If you are demoing and users report landing on a Pawabase page, this field is empty — and the fix is **Configuration** → **URLs** → **Site URL**.
</Warning>

### One-time token lifetimes

The links your templates point at are backed by single-use, time-limited tokens, and the lifetime is fixed per purpose rather than configurable:

| Purpose | Lifetime |
| --- | --- |
| `magic` | 15 minutes |
| `mfa` | 5 minutes |
| `link` | 10 minutes |
| `recovery` | 1 hour |
| `verify` | 24 hours |
| `email_change` | 24 hours |
| `invite` | 7 days |

They are ordered by how much the user can be trusted to act promptly. A sign-in link is short because it grants access; a verification link is long because the user may not check their inbox for hours and the link only confirms an address.

Already used, expired, and unknown all produce the same error, which means a double-clicked link and a prefetched one are indistinguishable to the user.


## The configuration cache

Each environment's config is fetched once and cached under a key naming the project and environment, for a TTL that defaults to **ten seconds**.

This is the reason a save in Studio followed by an immediate retry can read the old values. It is short enough to be easy to forget and long enough to reliably catch you in a test script or a fast manual retry.

| Property | Value |
| --- | --- |
| Cache key | `authcfg:{project}:{env}` |
| TTL | `config_ttl`, default 10 seconds |
| Scope | Installation-wide setting, not per environment |
| Cleared by editing? | No. It expires. |

<Warning>
Editing auth settings in Studio can take up to ten seconds to take effect. Any test that saves a setting and immediately asserts on the result will fail intermittently — which is worse than a consistent failure, because it looks like a flake rather than a cache.
</Warning>

Because `config_ttl` is an installation setting rather than an environment setting, you cannot give one environment a shorter cache than another. It also applies to every consumer of the config equally.

<Info>
The cache is why the unset-key behaviour is safe to rely on and also why it is worth checking: the config you inspect may not be the config in force, and neither may be what you just saved.
</Info>
