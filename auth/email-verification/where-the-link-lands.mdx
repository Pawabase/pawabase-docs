This is the decision that surprises people most often, and it comes down to one setting: `site_url`.

Every emailed link in Pawabase is built the same way. The builder takes the kind, the token and an optional redirect target, then chooses a destination.

| Environment state | The link points at |
| --- | --- |
| `site_url` is set | `{site_url}/auth/callback?token=...&type=verify` |
| `site_url` is empty | `{public_url}/auth/v1/links/{project}/{env}/verify?token=...` |

Both carry the same token. What differs is **who completes the flow**.

**With a `site_url`, your application does the work.** The link opens a page on your domain with the token in the query string. That page is yours: you read the token, post it to `/auth/v1/verify`, store the session, and decide what the person sees next. You control the page, the styling, and everything after.

**Without one, Akountz hosts the page.** The link opens a page served by the identity service itself. It redeems the token server-side and shows a short confirmation — *"You're all set"* — or, if a `redirect_to` was supplied and is allowlisted, redirects to it with the tokens in the URL fragment.

The second path works perfectly well for an internal tool. The difference is that you get no page of your own and no control over the post-verification experience.

<Warning>
The setting is shared with every other emailed link — recovery, magic, email change. Setting `site_url` so verification links point at your app changes where **all** of them point. That is usually what you want; it is worth knowing before you expect one flow to behave differently from another.
</Warning>

<Info>
If `site_url` is empty and `public_url` is also empty, the hosted link is built from an empty base and will not resolve. Both unset is a misconfiguration, not a supported mode.
</Info>

### The redirect allowlist

`redirect_to` is checked against the same allowlist used by OAuth: `site_url` plus every entry in `redirect_urls`, matched on exact equality or on a `/` or `?` boundary.

| Candidate URL | `site_url` is `https://app.example.com` |
| --- | --- |
| `https://app.example.com` | allowed |
| `https://app.example.com/welcome` | allowed |
| `https://app.example.com/welcome?next=/x` | allowed |
| `https://app.example.com.evil.test/` | refused |
| `https://evil.test/?x=https://app.example.com` | refused |
| `https://app.example.computer/` | refused |

The boundary rule is what makes prefix matching safe. A naive `startswith` would accept `https://app.example.com.evil.test`, because the attacker chose a domain that begins with yours.

An empty `redirect_to` is always allowed, and means "no redirect".

### What the hosted page does with a successful redemption

The hosted page reads `token` and `redirect_to` from the query string. After redeeming, it applies one further check: the redirect only happens if the result actually contains an `access_token`. If it does, four fields are carried in the **URL fragment**:

```text
https://app.example.com/welcome#access_token=eyJ...&refresh_token=eyJ...&expires_in=900&token_type=bearer
```

Fragments, not query parameters, because a fragment is not sent to servers and is not written to access logs on the redirect hop. A bearer token in a query string ends up in your server's logs, in proxy logs, and in browser history.

If there is no usable redirect target, the page shows *"You're all set"* and the person closes the tab. **In that case they are not signed in anywhere** — the session was created and its tokens were discarded with the response. They will need to sign in on your application with their password.

<Warning>
This is the practical reason to set `site_url`. Without it, a person who verifies from the hosted page and then returns to your application still has to sign in, and the "you're all set" message gives them no reason to expect that.
</Warning>

If redemption fails, the hosted page renders the error text with the failing status code: *"This link cannot be used"*, followed by the error's detail.


## What a successful redemption returns

A confirmed address is also a session. This surprises people who expect `{"verified": true}`, and it is worth understanding why.

The handler consumes the token and then, only if the user was not already verified, stamps `email_verified_at` with the current time and emits a `user.verified` event carrying the user id and address, with the user as the actor. It then starts a session with the method recorded as `email_verification`, and returns the standard payload.

| Field | Meaning |
| --- | --- |
| `access_token` | A bearer token for this project and environment. |
| `refresh_token` | The rotating half of the token family. |
| `token_type` | Always `"bearer"`. |
| `expires_in` | The environment's `access_ttl`, 900 seconds by default. |
| `expires_at` | Absolute expiry as a Unix timestamp. |
| `session_id` | The token family hex string. This is what `DELETE /auth/v1/sessions/{session_id}` takes. |
| `org` | The organization slug the tokens were issued for, or `null`. |
| `org_role` | The person's role in that organization, or `null`. |
| `user` | The user object, now with `email_verified: true` and an `email_verified_at` timestamp. |

The reasoning behind returning a session is that the person has just proved control of the address by clicking a link from inside that inbox. Making them type a password immediately afterwards adds friction without adding assurance — the link and the password would both have arrived at the same mailbox.

<Note>
If the account already had `email_verified_at` set — which happens when a magic link already stamped the address — the stamp and the event are skipped, but the session is still issued. Redeeming a `verify` token twice fails at the second attempt, because the first attempt consumed it.
</Note>

### The event

```json
{
  "name": "user.verified",
  "project": "acme",
  "env": "production",
  "payload": {
    "user_id": "01JQ7Z3M9K4YB2XQ8V0N5T6RJPD",
    "email": "ada@example.com"
  },
  "actor": "01JQ7Z3M9K4YB2XQ8V0N5T6RJPD"
}
```

The actor is the user themselves. Subscribe to it if your application needs to run something the moment an address becomes trustworthy — provisioning a default workspace, sending a welcome sequence, unlocking a gated resource. See [Events](/events/overview).

### What the access token carries

The claims a downstream service sees are the same ones every sign-in produces, because verification reuses the standard session path. Only `aal` differs in origin: it is `aal1`, because verification did not involve a second factor.

| Claim | Value here |
| --- | --- |
| `prj`, `env` | The environment that issued the token. A token from staging is refused in production. |
| `aal` | `aal1`, unless the account has MFA and the flow asked for it — it does not. |
| `email` | The address just verified. |
| `roles`, `perms` | Read at issue time from the environment's groups and permissions. |
| `org`, `org_role` | `null` unless the request named an organization. |

That last row is worth a note. Verification never asks for an organization, so a session started this way is always org-less. See [Tokens and sessions](/auth/tokens-and-sessions) for the full claim list and [Organizations](/auth/organizations/overview) for what the org claims are for.


## The message

There are exactly five kinds of message in Akountz, and verification is the `verify` one. Each kind has a default subject and body; an environment overrides either under `emails` in its auth settings.

The defaults for verification are:

| Part | Default |
| --- | --- |
| Subject | `Confirm your email for {project}` |
| Body | `Welcome to {project}.` / `Confirm your email address by opening this link:` / `{link}` / `If you did not sign up, you can ignore this message.` |

`{project}` resolves to `project_name` when the environment sets one, and to the project slug otherwise. That fallback is worth knowing: in an environment with no display name, the subject of every message is the bare slug.

### Placeholders

| Placeholder | Available in | Resolves to |
| --- | --- | --- |
| `{project}` | every kind | The environment's display name, or its slug. |
| `{email}` | every kind | The address the message was sent to. |
| `{link}` | every kind | The URL the message points at. |
| `{organization}` | `invite` only | The organization's display name. |
| `{role}` | `invite` only | The role the invitation grants. |

An unknown placeholder is left **literal** rather than raising. A typo like `{lin}` appears in the delivered message as `{lin}`, and the message still sends. This is deliberate: a template mistake should be visible in the inbox rather than turning into an exception that silently stops delivery.

<Warning>
Because unknown placeholders survive, a template with a typo produces a message that looks almost right and contains literal braces. When testing template changes, actually read the delivered message. A successful send is not evidence that the template is valid.
</Warning>

### Overriding the template

```json
{
  "auth": {
    "emails": {
      "verify": {
        "subject": "Confirm your email for {project}",
        "text": "Welcome aboard.\n\nConfirm {email} by opening this link:\n\n{link}\n\nThis link is good for 24 hours."
      }
    }
  }
}
```

The override is merged key by key over the defaults, so you can replace the subject alone and keep the default body.

### Delivery, escaping and the HTML part

Delivery goes through the API's mail service, which means it uses the **environment's own SMTP settings**. A staging environment with a different mail configuration sends through different infrastructure from production, and the message copy comes from that same environment's `emails` block.

There is also an HTML alternative part. The plain text is HTML-escaped, newlines become `<br>`, and wherever `{link}` was substituted, the URL is wrapped in an anchor. The result is wrapped in a single paragraph. It is a reasonable rendering, not a designed one — if you want a branded message, send it through the mail tooling described in [Mail](/mail/overview) using a `user.verified` subscription, and keep the Akountz message as the transactional fallback.

<Note>
`{link}` is escaped twice in the HTML part: once for the visible text and once, with quoting enabled, for the `href`. That is what keeps an address containing `&` or `"` from breaking out of the attribute.
</Note>

### Sending your own message instead

The verification token is issued whenever someone asks, and the request route answers identically whether or not it sends. So a common pattern is: let Akountz send, and additionally deliver your own branded message from a `user.created` or `user.verified` subscription.

The catch is that your own message would need its own valid token, and there is no public route that hands one out. The `verify/request` route sends the default message every time. In practice this means the Akountz message is the one that works, and your subscription should treat it as a notification rather than a replacement.


## Studio

Everything on this page is reachable from one screen. Open the project, pick the environment, and go to **Users & auth**. The layout title is *"Users & auth"* and its description reads *"End users of this environment, managed by Akountz: accounts, sessions, MFA, roles and organizations."*

The tabs, in order, are **Users**, **Roles**, **Organizations**, **Sign-in activity**, and **Configuration**. Verification touches three of them.

### Turning the requirement on

The switch lives under **Configuration**, in the card titled **Akountz configuration**, in the **Sign-up** section — *"Who can create an account, and whether their email must be confirmed first."*

| Label | Hint shown beneath it |
| --- | --- |
| **Sign-up enabled** | *"Turn off to invite-only new accounts."* |
| **Require email verification** | *"Unverified users can't sign in until they confirm."* |

Turn on **Require email verification**, save, and remember the 10-second configuration cache before testing.

<Tip>
Leave **Sign-up enabled** on while you roll verification out. If you turn sign-up off at the same time, you cannot tell whether an account that failed to arrive was a verification problem or simply nobody being allowed to register.
</Tip>

### Resending by hand

Under **Users**, find the person — the search box's placeholder is *"Search email or name"* — open them, and use **Verify email**.

That action stamps `email_verified_at` directly. It does not consume a token and does not send a message. It is the operational escape hatch for the case where the mail never arrived, the address is a typo, or the person is on the phone.

The same modal shows the state as **Marked verified** once the account has a timestamp, and carries the actions **Disable**, **Enable**, **MFA reset**, **Signed out everywhere**, **Session revoked**, **Password set**, **New role**, and a **Roles** field whose hint reads *"Comma-separated role names from the Roles tab."*

### Reading the attempts

The **Sign-in activity** tab shows what actually happened. It has a failures-only checkbox and columns **When**, **Event**, **Email**, **Result**, **IP**. The Result badge renders `ok` in green and the `reason` string in red.

| Event | Success | Reason when it fails |
| --- | --- | --- |
| `sign_in` | `ok` | `unknown email`, `locked`, `wrong password`, `disabled` |
| `recovery_requested` | `ok` | — |
| `password_reset` | `ok` | — |

A person repeatedly hitting `confirm your email address first` does not appear there, because that refusal happens after the password check and does not write a login event. The signal for "cannot get in because unverified" is the sign-up response, not the activity log.

<Note>
The `Sign-in activity` tab is backed by `akz_login_events`. Successes are hidden by default; untick the failures-only box to see the full history, including the sign-ins that worked. See [Managing users](/auth/managing-users/overview) for the full screen.
</Note>
