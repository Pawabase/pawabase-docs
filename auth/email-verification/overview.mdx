Email verification answers one question: does this person control the inbox behind this address? Once answered, the account carries a timestamp — `email_verified_at` — and every later decision about that account can treat the address as trustworthy.

In Pawabase verification is not a separate service with its own rules. It is one **purpose** of the shared one-time token mechanism, and one environment flag that decides whether the question is asked at all. That is why almost every question about verification — how long the link lasts, where it goes, what happens if it is opened twice, whether it can be previewed — has the same answer as the corresponding question about magic links and password recovery. The mechanism is described once, in [One-time tokens](#the-one-time-token-behind-every-link), and reused.

<CardGroup cols={3}>
  <Card title="Off by default" icon="toggle">`require_email_verification` is `false`. Verification is a switch you opt into per environment, not a stage every account passes through.</Card>
  <Card title="A 24-hour token" icon="clock">The `verify` token carries a 24-hour lifetime, the longest of the emailed link types, because a confirmation mail may sit in an inbox overnight.</Card>
  <Card title="Redeeming signs you in" icon="key">A successful confirmation does not return a bare "verified" flag. It starts a session and returns the full token payload.</Card>
</CardGroup>

## Where this sits in the layered model

Verification touches all three layers, but only one of them owns anything.

| Layer | What it does for verification |
| --- | --- |
| **Akountz** (identity) | Owns the `OneTimeToken` row, sends the message, consumes the token, stamps the user, starts a session. |
| **The API** (project config) | Owns `require_email_verification`, `site_url`, the redirect allowlist, and the `verify` message override. Akountz reads them. |
| **Gateway / `pawabase_core`** | Verifies the resulting access token like any other. It never sees the one-time token. |

The tenancy rule applies without exception. A verification token is scoped to one `project` + `env` pair, so a link issued for `acme/staging` cannot be redeemed against `acme/production` even when the address is identical. The signature and the row lookup both carry the environment, which is what makes that true rather than merely likely.

<Info>
If the layered model and the per-environment tenancy rule are unfamiliar, read [Authentication](/auth/overview) first. Everything on this page is an instance of them.
</Info>


## Verification is optional, and that changes the flow

The flag decides whether an account is *asked* to verify. It does not decide whether the account *can*.

| Setting | Effect |
| --- | --- |
| `require_email_verification: false` | Sign-up returns a session immediately. No message is sent. The account is unverified and stays that way until someone verifies it. |
| `require_email_verification: true` | Sign-up returns `session: null` and `verification_required: true`, and sends the message. Password sign-in is refused with `403 confirm your email address first` until the address is stamped. |

The distinction that matters in practice: **an unverified account is a normal account.** Creating one without verification does not make it provisional. It cannot sign in with a password in an environment that requires verification, but it is fully present — it can hold data, appear in Studio's user list, be granted roles, and be given permissions.

That has a consequence worth stating plainly, because it surprises people who expect the flag to be a gate rather than a rule. An unverified account in a verification-required environment is stuck, not restricted. It exists, it holds its roles, and there is no route by which it signs in until someone redeems a link or an operator stamps it. If your sign-up form creates accounts that people are expected to complete later, that is the state they sit in meanwhile.

<Warning>
Turning `require_email_verification` off does not un-verify anyone. It stops new accounts from being blocked and lets existing unverified accounts sign in again. The `email_verified_at` timestamps stay exactly as they were.
</Warning>

<Note>
Editing the flag in Studio does not take effect instantly. Each environment's configuration is cached for the Akountz `config_ttl` setting, 10 seconds by default. A sign-in attempt in the first few seconds after the change can still be refused.
</Note>


## What sign-up returns under each setting

The response shape differs, and a client that assumes one shape will break on the other. With verification required, sign-up is a `201` whose body contains no tokens at all:

```json
{
  "user": {
    "id": "01JQ7Z3M9K4YB2XQ8V0N5T6RJPD",
    "email": "ada@example.com",
    "username": "ada",
    "name": "Ada Lovelace",
    "avatar_url": null,
    "email_verified": false,
    "email_verified_at": null,
    "user_metadata": {},
    "app_metadata": {},
    "roles": [],
    "mfa_enabled": false,
    "identities": [],
    "created_at": "2026-03-04T09:12:31+00:00",
    "last_sign_in_at": null
  },
  "session": null,
  "verification_required": true
}
```

Without it, sign-up returns the ordinary session payload with `verification_required: false`:

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "bearer",
  "expires_in": 900,
  "expires_at": 1750000900,
  "session_id": "6f1c9a84be2d47f0",
  "org": null,
  "org_role": null,
  "user": { "...": "the same user object" },
  "verification_required": false
}
```

A client should branch on `session` being `null`, or on `verification_required`, and route the person to a "check your email" screen rather than into the application.


## The three routes

Verification is reached through exactly two schema routes, plus the hosted link page when no `site_url` is configured.

| Route | Method | Purpose |
| --- | --- | --- |
| `/auth/v1/verify/request` | POST | Send, or re-send, the confirmation message. |
| `/auth/v1/verify` | POST | Redeem the token: stamp the address and start a session. |
| `/auth/v1/links/{project}/{env}/verify` | GET | The Akountz-hosted page. Only reachable when `site_url` is empty. |

The request route is context-scoped and needs the normal environment context. The redemption route is too — it takes the token from the body rather than the URL, and the environment comes from the request context just as it does for sign-in.

### Asking for the message

```bash
curl -X POST "https://api.example.com/auth/v1/verify/request" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{"email": "Ada@example.com"}'
```

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `email` | string | required | The address. Stripped and lowercased, then validated. |
| `redirect_to` | string | `null` | Where the link should land afterwards. Must be allowlisted, or the request is refused with `400 redirect_to is not an allowed URL`. |

The address is normalised before it is looked up, so case never matters. `Ada@example.com`, ` ada@example.com ` and `ADA@EXAMPLE.COM` are the same account. Normalisation also requires the shape `^[^@\s]+@[^@\s]+\.[^@\s]+$` and a length of at most 255; anything else is `422 a valid email address is required`.

The response is identical whether or not anything was sent:

```json
{ "sent": true, "message": "If the address has an account, a message is on its way." }
```

A message actually goes out only when the address has an account in this environment and that account's `email_verified_at` is still `null`. An already-verified account gets nothing.

<Warning>
That fixed response is the design, not a shortcut. A request route that answered differently for registered and unregistered addresses would let anyone enumerate which addresses hold accounts in your environment. The same response is used by the recovery and magic-link routes.
</Warning>

Both the verification and recovery request routes are limited to **10 requests per 60 seconds** per caller, under the rate-limit key `akz:links`, backed by the Akountz `redis_url`. Sign-up and sign-in have a separate budget of 30 per 60 seconds under `akz:auth`. MFA endpoints carry their own 10 per 60 seconds under `akz:mfa`.

### Redeeming the token

```bash
curl -X POST "https://api.example.com/auth/v1/verify" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{"token": "Im91Yi1ub3QtYS1yZWFsLXRva2VuIg.Xt3m9Q.hJ8k2vB7nQ4sT1xZ"}'
```

| Field | Type | Meaning |
| --- | --- | --- |
| `token` | string | Between 10 and 2048 characters. The value from the link's `token` query parameter. |

That length range is the only shape validation applied to the body. Everything else about the token is decided by the mechanism below.

### Redeeming from a browser page

If you host your own confirmation page, the shape of the work is small: read `token` from the query string, post it, store whatever comes back.

```bash
# On your page, /auth/callback?token=...&type=verify
curl -X POST "https://api.example.com/auth/v1/verify" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d "{\"token\": \"$(python3 -c 'import sys,urllib.parse;print(urllib.parse.parse_qs(sys.argv[1]).get("token",[""])[0])' "$QUERY_STRING")\"}"
```

The TypeScript SDK exposes the verification exchange. Other clients can use the HTTP shape above;
the Python SDK does not manage application-user auth. See [Calling Pawabase](/connect).


## The one-time token behind every link

Verification, recovery, magic links, invitations, MFA challenges, email changes and OAuth identity linking all issue tokens from the same function in `app/links.py`. The token is a signed reference to a row; the row makes it single-use. Understanding it once removes the guesswork from every link-based flow in the system.

### The row

`OneTimeToken` lives in the `akz_one_time_tokens` table.

| Field | Meaning |
| --- | --- |
| `id` | A ULID. The only thing the signed token carries. |
| `project` | The project the token belongs to. Part of every lookup. |
| `env` | The environment name. Part of every lookup. |
| `purpose` | What the token may be used for. A `verify` token cannot be redeemed as a `magic` token. |
| `user` | The account it belongs to, or `null` for a token issued against an address that has no account yet. |
| `email` | The address it was issued for. Defaults to the user's own address when a user is given. |
| `data` | Purpose-specific extras. Verification uses none; magic links and MFA record the sign-in method here. |
| `expires_at` | When the row stops being redeemable. |
| `used_at` | Set the moment the token is redeemed. `null` until then. |

The tenancy columns are what make a token environment-scoped. They are not decoration: the redemption query filters on `id`, `project`, `env` and `purpose` together, so a row from another environment is simply not found.

### The signature

The string in the email is a timed signature over `{"id": "<ulid>"}`, produced with a secret derived for that project and environment and a salt that includes the purpose. Two consequences follow, and both are worth internalising.

The token cannot be forged, because a valid signature requires the environment's signing secret. And the token cannot be moved between purposes, because the salt differs — a signature made for `verify` will not verify against `recovery`, even for the same row.

<Warning>
The signature is derived from Akountz's `internal_secret` combined with the project and environment. Rotating that secret invalidates every outstanding one-time token in every environment at once. Do it during a maintenance window, and expect users mid-flow to see `400 the link is invalid or has expired`.
</Warning>

### Lifetimes are per purpose

| Purpose | Lifetime | Used by |
| --- | --- | --- |
| `verify` | 24 hours | This page. |
| `recovery` | 1 hour | [Password recovery](/auth/password-recovery/overview). |
| `magic` | 15 minutes | [Magic links](/auth/magic-links/overview). |
| `invite` | 7 days | Organization invitations. |
| `mfa` | 5 minutes | The second-factor challenge issued before a session. |
| `email_change` | 24 hours | Confirming a change of address. |
| `link` | 10 minutes | Linking an OAuth provider to a signed-in account. |

Verification and email-change tokens share the 24-hour figure because both answer a question a person may not look at until tomorrow: *is this address yours?* Magic links are the opposite case — the person is waiting at the browser when the mail arrives — and get 15 minutes.

The lifetime is enforced twice: once by the signature's own max age, and once by comparing the row's `expires_at`. The row is what makes a token revocable and auditable; the signature is what makes it unforgeable.

### Consuming a token

Redemption is one operation with four checks, in order:

| Check | On failure |
| --- | --- |
| The signature verifies within the purpose's lifetime. | `400 the link is invalid or has expired` |
| A row exists with this id, in this project, env and purpose. | the same 400 |
| The row's `used_at` is `null` and `expires_at` is in the future. | the same 400 |
| The conditional update matched a row. | the same 400 |

One error for all four, deliberately. A caller cannot distinguish an expired link from an already-used one from one that was never real, so the endpoint leaks nothing about which addresses have outstanding tokens.

The fourth check is the interesting one. Marking a token used is a **conditional update**:

```python
updated = await OneTimeToken.filter(id=row.id, used_at=None).update(
    used_at=datetime.now(UTC)
)
if not updated:
    raise invalid
```

The filter says: update this row only if it is still unused. If two requests arrive with the same token at the same moment, both pass the earlier read, both attempt the update, and exactly one matches a row. The loser gets the same `400` the winner would have got for a used token. Single-use is a property of the write, not of a check that can race.

<Note>
The same conditional-update pattern appears twice more in the codebase, for the same reason: consuming an MFA recovery code, and accepting an organization invitation. Both are "this thing may only happen once" operations where a read-then-write would be wrong.
</Note>

### Peeking

Consumption can be told not to consume. In peek mode the signature and the row are checked, the caller gets the row back, and `used_at` is left alone.

That is what lets a form be rendered before anything is submitted. The hosted recovery page peeks to decide whether to show the password form at all; the submit consumes. MFA works the same way — the challenge is peeked, the code is checked, and the token is only consumed once the code is right, so a mistyped code does not burn the challenge.

Verification never peeks. There is nothing to confirm before the confirmation.
