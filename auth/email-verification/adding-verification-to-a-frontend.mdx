The pieces you need, in the order you need them.

### The "check your inbox" screen

After sign-up returns `session: null`, show something that says three things: we sent a message, it may take a minute, here is a button to send another. Then stop. Do not poll an endpoint hoping verification has happened — there is no such endpoint, and the honest answer is that verification is not observable except by asking `/auth/v1/user` with a session you do not yet have.

### The resend button

```bash
curl -X POST "https://api.example.com/auth/v1/verify/request" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{"email": "grace@example.com"}'
```

Always render the same confirmation whether or not it sent. If you disable the button because the address is already verified, you have turned the uniform response into a membership oracle — one your own frontend now performs on your behalf.

<Warning>
Disable the button on a timer, not on the response. The rate limit is 10 per 60 seconds, and the correct client behaviour is to stop asking long before that rather than to let the server refuse.
</Warning>

### The confirmation page

Your page needs three cases, and they are easy to get wrong in ways that strand people.

| Case | What to show |
| --- | --- |
| `token` missing from the query string | An error saying the link is incomplete, with a link to request a new one. |
| Redemption returned a session | Success, and send them into the application. |
| Redemption returned `400` | The link is invalid or expired. Offer a resend. Do not say which of the two it was. |

The third case is the one that needs thought. Because every failure looks identical, your page cannot tell someone "try again in ten minutes" when the truth might be "this link was already used". Phrase it as *"This link is no longer valid"* and give the resend. That is honest whatever the cause.

### Reading verification state on an existing session

A signed-in person can ask who they are, and the answer carries the boolean:

```bash
curl "$PAWABASE_URL/auth/v1/user" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $ACCESS_TOKEN"
```

```json
{
  "id": "01JQ7Z3M9K4YB2XQ8V0N5T6RJPD",
  "email": "grace@example.com",
  "username": "grace",
  "name": "Grace Hopper",
  "avatar_url": null,
  "email_verified": true,
  "email_verified_at": "2026-03-04T09:31:07+00:00",
  "user_metadata": { "plan": "free" },
  "app_metadata": {},
  "roles": ["customer"],
  "mfa_enabled": false,
  "identities": [],
  "created_at": "2026-03-04T09:30:58+00:00",
  "last_sign_in_at": "2026-03-04T09:31:07+00:00",
  "aal": "aal1",
  "session_id": "6f1c9a84be2d47f0"
}
```

This is the endpoint your frontend should call at startup, because it answers "am I signed in, and am I verified" in one request. The `email_verified` field is a boolean derived from whether `email_verified_at` is null — it is not a separate column that can drift.

Two fields on that object are worth reading alongside it. `aal` tells you whether the session passed a second factor, which decides whether a sensitive screen is available. `session_id` is the token family, and it is what `DELETE /auth/v1/sessions/{session_id}` takes when someone wants to end one device rather than all of them.

<Note>
This is the user-facing view. The admin view, used by Studio and service keys, adds `disabled`, `disabled_at`, `locked_until`, `last_sign_in_ip`, `has_password` and `permissions`. Do not build a client around the admin fields; they exist for operators.
</Note>


## Verification and the rest of the identity surface

### Does verification gate anything by itself?

No. This is the single most common misunderstanding. `require_email_verification` controls exactly two things: whether a message is sent at sign-up, and whether password sign-in refuses an unverified account.

| Behaviour | Gated by the flag? |
| --- | --- |
| A message is sent at sign-up. | Yes. |
| Password sign-in is refused. | Yes. |
| Magic-link sign-in is refused. | No. It verifies the address as part of signing in. |
| Social sign-in is refused. | No. |
| A refresh-token grant is refused. | No. |
| Reading or writing application data. | No. That is a policy. |
| Holding roles and permissions. | No. |

The third row is the one that surprises. If a person who cannot sign in with a password receives a magic link, they are in. The magic link proves the same thing the verification link would have.

### Why that is coherent

The design answer is that a magic link is not weaker than a password. It required control of the mailbox at the moment of use. Refusing it for an unverified account would mean refusing the very proof that would resolve the objection.

<Warning>
If your product requires that every account passes through an explicit confirmation screen — for compliance, or because a separate team approves accounts — you need to enforce that yourself. The system will not do it for you, and the flag's name suggests it might.
</Warning>

### Passwords are unaffected

Verification does not change the password policy, the hashing, or the lockout counters. An account created through verification has a normal password, hashed by Sillo's user model with `passlib` — bcrypt by default, with a `pbkdf2_sha256` fallback. See [Passwords](/auth/passwords).

### Lockout is unaffected, and separate

Ten failures locks an account for fifteen minutes. Those are Akountz *installation* settings, not per-environment configuration, which means one instance's lockout policy applies across all of its environments while the failure counters live per environment.

A person who cannot sign in because they are locked is a different support conversation from one who cannot sign in because they are unverified, and the **Sign-in activity** tab distinguishes them by the `reason` string.

### Organizations are unaffected

Verification state is not consulted when joining an organization, and organization membership is not consulted when verifying. The two features share the mailbox but not the rules. See [Organizations](/auth/organizations/overview).

<Note>
The one interaction worth knowing is indirect: an invitation is mailed, and accepting an invitation requires a signed-in user. If that address has no account, the person must sign up first. Whether that sign-up requires verification depends on the flag.
</Note>


## Why the messages answer identically

This deserves a section of its own, because the design decision is unusual enough that teams routinely "fix" it.

Every route in Akountz that causes a message to be sent returns the same body:

```json
{ "sent": true, "message": "If the address has an account, a message is on its way." }
```

That covers `/auth/v1/verify/request`, `/auth/v1/recover` and `/auth/v1/magic-link`.

### The threat it prevents

Consider the alternative. If an unknown address returned `404 no such user`, then anyone could POST a list of addresses and learn which of your users have accounts. Addresses are not a secret — they appear in commits, in shared documents, in breach notifications — so a membership oracle here is a reconnaissance tool for everything else.

The fixed response removes the oracle. A script can send a million requests and learn nothing, because the response is a constant function of nothing.

### What it costs, honestly

The cost is real and worth stating rather than hiding:

| Cost | Mitigation |
| --- | --- |
| A person who typoed their address sees "check your email" and nothing arrives. | Make them retype the address to confirm before you promise delivery. |
| Support cannot tell whether a message was sent. | Nobody can, by design. Check the mail logs instead. |
| A client that wants to show "you already have an account" cannot. | Do not try to build that on this endpoint. |

<Warning>
The temptation to "improve" this — by returning 404 for unknown addresses, or by adding an `already_registered` field — is among the most damaging changes you can make to this part of the system. It is not an improvement, and the next audit will find it.
</Warning>

### What still varies

The *body* is constant; the *work done* is not. A request for a registered, unverified address creates a token and sends a message. A request for an unregistered address, or for a verified account, does neither. That asymmetry is invisible from outside, which is the point.

### The one thing that is not uniform

The rate limit is applied before the lookup, so a flood of requests for addresses that do not exist is throttled exactly as a flood for addresses that do. That is another reason the timing of the response leaks nothing useful.


## Frequently asked questions

<AccordionGroup>
  <Accordion title="Does verification create the account if it does not exist?">
    No. `verify/request` never creates an account. It only sends a message when one already exists. If you want an address to become an account by receiving a link, that is the magic-link flow with `create_user` set to true, not this one.
  </Accordion>
  <Accordion title="Can I resend to an address whose account is already verified?">
    You can call the route. Nothing is sent, and the response is the same one it always is. This is why the client must not infer delivery from the response.
  </Accordion>
  <Accordion title="How many outstanding verify tokens can one account have?">
    As many as you request. Each call creates a new row. They are independent, so an older link remains valid even after a newer one is sent — both will work, once each.
  </Accordion>
  <Accordion title="Does redeeming an old link after a new one work?">
    Yes, if the old token has not been used and has not passed 24 hours. Sending a new message does not invalidate the previous token. If you want a resend to supersede an earlier message, there is no route for that; issue an email change or ask the person to be careful with which link they open.
  </Accordion>
  <Accordion title="Can an account be un-verified?">
    Not through the API. `email_verified_at` is only ever set, never cleared, by any user-facing route. Studio's **Verify email** sets it. There is no un-verify action, and that is deliberate.
  </Accordion>
  <Accordion title="Is the verification token a JWT?">
    No. It is a signed reference to a row, using a timed serializer rather than the JWT machinery used for access tokens. The distinction matters: one-time tokens are not bearer credentials, they are lookups, and they carry no claims of their own.
  </Accordion>
  <Accordion title="Does the token leak information if someone reads the database?">
    The token string is not stored. Only the row is, and the row's id is not the token — it is the token's payload. Someone with read access to `akz_one_time_tokens` still cannot reconstruct a redeemable token without the signing secret.
  </Accordion>
  <Accordion title="What happens if two people open the same link?">
    One succeeds and gets a session. The other gets `400`. The conditional update is what guarantees this, and it is why the link behaves the way people expect when a mail client pre-fetches it.
  </Accordion>
</AccordionGroup>
