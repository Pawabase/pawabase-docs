Sign-up is the flow that touches the most settings at once, so it is worth following end to end with an environment configured a particular way.

Assume `acme/production` has:

```json
{
  "auth": {
    "signup_enabled": true,
    "require_email_verification": true,
    "password_policy": "strict",
    "password_min_length": 12,
    "access_ttl": 900,
    "refresh_ttl": 2592000,
    "site_url": "https://app.acme.test",
    "default_roles": ["customer"]
  }
}
```

A person submits the sign-up form.

```bash
curl -X POST "https://api.example.com/auth/v1/signup" \
  -H "X-Pawabase-Context: $CONTEXT" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "email": "Grace@Example.com",
    "password": "correct-horse-battery-8",
    "name": "Grace Hopper",
    "data": { "plan": "free" },
    "redirect_to": "https://app.acme.test/welcome"
  }'
```

What happens, in order:

| Step | What the service does |
| --- | --- |
| 1 | Refuses if `redirect_to` is outside the allowlist. `https://app.acme.test/welcome` is under `site_url`, so it passes. |
| 2 | Normalises the address to `grace@example.com` and checks it against this environment's accounts. |
| 3 | Derives a username: the local part `grace`, stripped of anything outside `a-z0-9_.-`, truncated to 40. On collision it appends a random number. |
| 4 | Runs the strict password validator. A failure is a `422` carrying a list of problems. |
| 5 | Creates the account, unverified, with `user_metadata` set from `data`. |
| 6 | Assigns every role in `default_roles` — here, `customer`. |
| 7 | Emits `user.created`. |
| 8 | Because the flag is on, issues a `verify` token, sends the message, and returns `session: null`. |
| 9 | The link in the message is `https://app.acme.test/auth/callback?token=…&type=verify&redirect_to=https%3A%2F%2Fapp.acme.test%2Fwelcome`. |

The account now exists with the `customer` role and no session. It is a real account with real permissions; it simply cannot sign in yet.

### Following the link

The person's browser opens that URL on your domain. Your page reads the query string and posts the token:

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "bearer",
  "expires_in": 900,
  "expires_at": 1750000900,
  "session_id": "6f1c9a84be2d47f0",
  "org": null,
  "org_role": null,
  "user": {
    "id": "01JQ7Z3M9K4YB2XQ8V0N5T6RJPD",
    "email": "grace@example.com",
    "username": "grace",
    "name": "Grace Hopper",
    "email_verified": true,
    "email_verified_at": "2026-03-04T09:31:07+00:00",
    "user_metadata": { "plan": "free" },
    "app_metadata": {},
    "roles": ["customer"],
    "mfa_enabled": false,
    "identities": [],
    "created_at": "2026-03-04T09:30:58+00:00",
    "last_sign_in_at": "2026-03-04T09:31:07+00:00"
  }
}
```

Note four things:

`user_metadata` came from the sign-up `data` and is visible on the returned object. It is also carried in the token's `meta` claim, which policies must not trust, because the user can edit it through `PATCH /auth/v1/user`.

`app_metadata` is empty and was never settable at sign-up. Only an administrator or a service key can write it, which is what makes the `app` claim safe to rely on.

`roles` is `["customer"]`, assigned at creation, and read at issue time.

`last_sign_in_at` moved, because starting a session calls the same success recording that password sign-in does.

<Warning>
The address in the response is `grace@example.com`, not what was typed. If your form shows a confirmation using the submitted string, capitalise or trim it yourself before comparing it to anything the API returns.
</Warning>

### Knowing what the environment offers

`GET /auth/v1/settings` reports what this environment supports, including whether verification is required, whether sign-up is open, and which providers are usable. Read it at startup rather than hardcoding any of it in your frontend, because all of it is per environment and can change without a deploy.

```json
{
  "signup_enabled": true,
  "email_verification_required": true,
  "magic_link_enabled": true,
  "mfa_enabled": true,
  "providers": ["github", "google"],
  "password_policy": { "kind": "strict", "min_length": 12 }
}
```

The `providers` array comes from filtering the environment's provider block down to those that are both enabled and carry a `client_id`. A provider you configured without a `client_id` is simply absent, and asking for it directly returns `404`. Use the list to decide which buttons to render, and treat the redirect flow behind them as a black box until you have read [Social login](/auth/social-login/overview).

`email_verification_required` is the field worth reading at startup, because it tells your sign-up screen whether to expect tokens or a "check your inbox" page. Everything else on that response is a convenience; this one changes what you build.

### The same address, two environments

This is the case that catches people out, and it is the tenancy rule doing exactly what it says.

| | `acme/staging` | `acme/production` |
| --- | --- | --- |
| Account for `grace@example.com` | exists, unverified | exists, verified |
| Password | `staging-pass-1` | `production-pass-9` |
| Roles | `tester` | `customer` |
| Sessions | separate | separate |
| Verification message | staging's SMTP, staging's `emails` block | production's |

A verification link from staging redeemed against production fails, because the token's row carries `env: "staging"` and production's redemption filters on `env: "production"`. The error is the same 400 as for an expired link.

The corollary for testing: verify in the environment whose context header you are sending. If your staging page posts to the production context, the redemption fails and looks like a bug in the link.

<Note>
The same rule governs roles, and it is the one that produces "I gave them the role but nothing changed". A role granted in staging is a different group from the identically named role in production, and the permission in the token is only ever the one belonging to the environment that issued it. See [Roles and permissions](/auth/roles-and-permissions/overview).
</Note>


## Studio, step by step

The Configuration tab is the only place the flag lives, and it is worth walking through because the surrounding fields decide things verification depends on.

Open **Users & auth → Configuration**. The card is titled **Akountz configuration** and describes itself as *"Settings live in the project's auth block — this screen edits them."* Each card has a **Description** button in its corner, which reveals a live view of the JSON behind the form. That view is the fastest way to confirm what was actually saved.

<Steps>
  <Step title="Open the environment">
    Pick the project, then the environment in the environment switcher. The flag is per environment, and the form shows only the selected one.
  </Step>
  <Step title="Find the sign-up card">
    It is the first card, with the hint *"Who can create an account, and whether their email must be confirmed first."*
  </Step>
  <Step title="Turn on Require email verification">
    The hint under it reads *"Unverified users can't sign in until they confirm."* This is the switch. It does nothing to existing accounts.
  </Step>
  <Step title="Set the site URL if you have a frontend">
    In the URLs card, **Site URL** takes your application base. Its placeholder is `https://app.example.com`. Without it, confirmation links go to Akountz's hosted page.
  </Step>
  <Step title="Save and wait">
    The environment's configuration is cached for 10 seconds. A sign-in or a redemption in that window uses the previous values.
  </Step>
  <Step title="Check the view">
    Click **Description** on the card and confirm the JSON now contains `require_email_verification: true`.
  </Step>
</Steps>

### The other cards that matter here

| Card | Fields | Relevance to verification |
| --- | --- | --- |
| **Akountz configuration** | **Sign-up enabled**, **Require email verification**, **Password policy**, **Minimum password length** | The first two decide the flow. |
| **Tokens** | **Access token lifetime**, **Refresh token lifetime** | Decide how long the session returned by redemption lasts. |
| **URLs** | **Site URL**, **Redirect URLs** | Decide where the link goes and where it may send people afterwards. |
| **Default roles** | A tag input, placeholder `customer`, hint *"Granted automatically at sign-up."* | Applied at account creation, before verification. |
| **Email templates** | Subject and body per kind, with a placeholder hint | Controls the message text. |

<Note>
**Default roles** are granted at account creation, which for a verification-required environment is the moment the person submits the form — not the moment they confirm. An unverified account already holds its roles.
</Note>

### The email template editor

The Email templates card has one section per kind. The subject field's hint shows the default in guillemets, and the body field carries a hint listing the available placeholders.

For the verification kind the hint is:

```text
Default: "Confirm your email for {project}". Placeholders: {project} {email} {link}
```

The invitation kind's hint appends `{organization} {role}`, because those two exist only for invitations.

<Warning>
Studio writes the template into the environment's `auth.emails` block. There is no per-kind toggle and no "send me a test" button. To test a change, trigger a real flow against a real address and read the delivered message.
</Warning>
