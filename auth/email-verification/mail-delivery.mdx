Verification depends on mail actually leaving the platform, and mail is the layer most likely to fail quietly. The important thing to know is where it lives.

### The environment owns its SMTP

Delivery goes through the API's mail service, not through Akountz's own transport. That means:

| Property | Source |
| --- | --- |
| SMTP host and credentials | The environment's mail configuration, in the API. |
| From address and reply-to | The same. |
| The message subject and body | The environment's `emails` block, via Akountz. |
| The link inside it | Akountz's `link()` builder. |
| The signing secret for that link | Akountz's `internal_secret`, derived per environment. |

So a message is a joint product: the API's transport, Akountz's template and signing. When one environment's mail works and another's does not, the difference is in the API configuration, not in Akountz.

<Note>
Because the transport is per environment, a staging environment can use a completely different mail provider from production without Akountz knowing. Staging verification links will still work; they just come from a different sender.
</Note>

### Delivery failures are silent to the person

The `sent` response means the request was accepted and, where applicable, handed to the mail service. It does not mean the message was delivered, and there is no delivery callback in Akountz. If your provider offers one, wire it to your own subscription on `user.verified` and `user.created` events rather than expecting it from this path.

For a transactional flow you control end to end, use the mail tooling described in [Mail](/mail/overview) and subscribe to identity events. That gives you delivery reporting; Akountz's own message does not.

### The HTML alternative part

The body is sent twice: as plain `text` and as a simple `html` part. The HTML is built from the same string with newlines converted to breaks, HTML-escaped, and the link substituted as an anchor.

| Concern | How it is handled |
| --- | --- |
| A display name containing `<` | Escaped. |
| A link containing `&` | Escaped in the visible text and in the `href`, with quoting enabled. |
| Line breaks | Converted to `<br>`. |
| Everything else | Wrapped in a single `<p>`. |

<Warning>
The generated HTML is functional, not branded. If your confirmation message is part of how your product is perceived, override the `text` and send a designed message yourself. The Akountz message is best treated as the functional fallback that always exists.
</Warning>

### Templates are per environment, and there are five kinds

| Kind | Subject default | Unique placeholders |
| --- | --- | --- |
| `verify` | `Confirm your email for {project}` | — |
| `recovery` | `Reset your {project} password` | — |
| `magic` | `Your {project} sign-in link` | — |
| `invite` | `You are invited to {organization} on {project}` | `{organization}`, `{role}` |
| `email_change` | `Confirm your new email for {project}` | — |

Two things about that table. There is no template for an MFA challenge, because an MFA challenge is handed to the client directly, never mailed. And `{organization}` and `{role}` exist only for `invite`; using them in a `verify` template leaves them literal in the delivered message, because unknown placeholders survive rather than raising.

### A safe override

```json
{
  "auth": {
    "emails": {
      "verify": {
        "subject": "Confirm your email for {project}",
        "text": "Hi,\n\nPlease confirm this address for your {project} account:\n\n{link}\n\nThe link works once, and is good for 24 hours. If you did not request an account, ignore this message."
      }
    }
  }
}
```

Including the lifetime and the single-use property in the message is worth doing for every kind. It sets an expectation that matches the system, and it means a person who clicks an old link understands what happened instead of assuming something broke.


## Verifying the flow works

A checklist you can actually run, with the thing to look for at each step. Every step uses the publishable key and a real user session, never a service key, because a service key bypasses the flows you are trying to test.

### Before you start

Confirm the environment's settings: **Sign-up enabled** on, **Require email verification** on, **Site URL** set to your application, and a redirect URL that covers where you want to land. Wait 10 seconds for the configuration cache.

### The run

<Steps>
  <Step title="Create an account in the environment you are testing">
    Use a real address you can read. Not an address you have used in another environment — the whole point is that the account must be new *here*.
  </Step>
  <Step title="Confirm the response has no tokens">
    `session` must be `null` and `verification_required` must be `true`. If you got tokens, the flag did not apply — wait out the cache and try again with a new address.
  </Step>
  <Step title="Confirm the message arrived, and read it">
    Check that `{link}` was substituted rather than appearing literally, that the destination is your `site_url`, and that `redirect_to` survived encoding.
  </Step>
  <Step title="Open the link">
    It should land on your own page at `/auth/callback` with `token` and `type=verify` in the query string.
  </Step>
  <Step title="Redeem it">
    `POST /auth/v1/verify` should return a full token payload, and `user.email_verified` should be `true` with a non-null `email_verified_at`.
  </Step>
  <Step title="Try the same link again">
    Expect `400 the link is invalid or has expired`. This is not a failure; it is the property you are testing.
  </Step>
  <Step title="Sign in with the password">
    It should now succeed. Before the redemption it would have returned `403 confirm your email address first`.
  </Step>
  <Step title="Check the event stream">
    `user.verified` should have fired exactly once, with the user as the actor.
  </Step>
</Steps>

### The negative cases

Positive paths prove little on their own. These are the ones that catch real problems:

| Test | How | Expected |
| --- | --- | --- |
| Requesting for an unregistered address | `POST /auth/v1/verify/request` with an address that has no account | The same `sent` body. No message. No error. |
| Requesting for a verified account | Same address, now verified | The same `sent` body. No message. |
| Redeeming in the wrong environment | Post a staging token with the production context | `400`. |
| Redeeming after 24 hours | Wait, or use a token you have kept | `400`. |
| A malformed token | Send `token: "short"` | `422` from schema validation, not `400`. |
| A disallowed `redirect_to` | `POST /auth/v1/signup` with `redirect_to` on another domain | `400 redirect_to is not an allowed URL`. |
| A lookalike domain | `redirect_to: https://app.acme.test.evil.example/` | `400`. Prefix matching must not accept it. |

### Testing the hosted page

If you have no `site_url`, the link goes to Akountz's own page. Test it by clearing the field temporarily.

| Check | Expected |
| --- | --- |
| The page opens from the message. | A plain page titled *"You're all set"*, or a redirect if `redirect_to` was allowlisted. |
| The token is consumed. | A second visit shows *"This link cannot be used"*. |
| With a `redirect_to` inside the allowlist. | A `302` to your URL with four fields in the fragment. |
| With no `redirect_to`. | The confirmation page, and no session on your side. |

<Note>
Check the redirect carries a fragment and not a query string. If you ever see `?access_token=…`, something is wrong — that value has been written into a server log somewhere.
</Note>

### What a service key will not tell you

A service-key request bypasses the parts of the flow you are trying to exercise. Specifically, it does not prove that:

- an unverified account would be refused a password grant,
- a message would actually be sent,
- a one-time token would be rejected after use,
- the redirect allowlist would accept your target.

Run all of the above with a publishable key and a real session. Use a service key only for the admin operations in [Managing users](/auth/managing-users/overview).


## Security properties

What this design actually defends against, and what it does not.

### Forgery

A token is a signature over a row id. Producing one that verifies requires the secret derived for that project and environment from Akountz's `internal_secret`. There is no other way to make a valid token, and no field in a request that lets a caller influence the signature.

### Replay

The row's `used_at`, set by a conditional update, makes each token good for exactly one redemption. This is what protects against the common attacks:

| Attack | Why it fails |
| --- | --- |
| An attacker reads the link from a forwarded message. | It works — once. The legitimate recipient then finds it invalid. |
| A link preview in a mail client fetches the URL. | The GET consumes the token. The recipient then finds it invalid. This is the one real operational hazard. |
| Two people click the same link. | One wins; the other gets `400`. |

<Warning>
Mail clients that fetch links to build previews will consume the token before the person sees it. This affects every link-based flow. If your audience uses such clients, tell people to copy the link rather than click it, or build your confirmation page so that a consumed token can be recovered from by issuing a new one immediately. There is no route that extends a token's life.
</Warning>

### Scope

A token cannot be used for another purpose or another environment. The purpose is in the signing salt, and the environment is in both the derived secret and the row lookup. So a staging verification token presented to production fails, and a verification token presented to the recovery route fails, with the same undifferentiated error.

### Disclosure

The redemption endpoint's error is constant, the request endpoint's response is constant, and neither reveals whether an address is registered. Combined with the fact that tokens are only ever mailed to the address they concern, the flow gives an attacker no oracle to work from.

<Note>
The one thing an attacker with a mailbox can do is verify an address they control, which is exactly the point. Verification proves control, not goodness.
</Note>

### What verification is not

It is not a second factor. It proves the address is reachable; it does not prove the person at the keyboard is the account holder. Use [MFA](/auth/mfa/overview) for that, and gate on `aal` where the distinction matters:

```json
{ "aal": "aal2" }
```

### Sessions started by redemption

A session issued this way is an ordinary session: `aal1`, a token family, a refresh lifetime from the environment's `refresh_ttl`. Nothing about it is marked as having come from a link, apart from the recorded method. Do not treat a link-derived session as more or less trustworthy than a password one — it is exactly as trustworthy as the mailbox.


## Choosing a configuration

Three setups, with the trade-off stated rather than implied.

### Setup A: no verification, no frontend

Leave `require_email_verification` false and `site_url` empty. Sign-up returns a session; magic links work; nothing is mailed.

Best for: an internal tool, a proof of concept, or any environment where people are pre-provisioned by an administrator.

The cost: an unverified account is indistinguishable from a verified one, so anything downstream that needs a trustworthy address has nothing to check. If your product sends password resets by mail, that is the number to weigh.

### Setup B: verification, Akountz hosts the pages

Set `require_email_verification` true and leave `site_url` empty.

Best for: getting the guarantee without building any UI.

People click a link, see *"You're all set"*, and then sign in on your application with a password. Every flow works, the pages are plain, and nothing is yours to maintain.

The cost: the pages are not branded, and the sign-in step after verification is friction the message does not explain. People report this as "the link said it worked but I still couldn't log in", which is a real support burden.

### Setup C: verification, your application completes every flow

Set `require_email_verification` true and `site_url` to your application. Add `redirect_urls` for anything else you need to land on.

Best for: a product with a frontend. This is the recommended setup.

You build one page — `/auth/callback` — that reads `token` and `type` from the query string and dispatches on the type:

| `type` | Route to post to |
| --- | --- |
| `verify` | `/auth/v1/verify` |
| `magic` | `/auth/v1/magic-link/verify` |
| `recovery` | `/auth/v1/recover/confirm` |
| `email_change` | `/auth/v1/email/confirm` |

The cost: you own that page, including its handling of the two failure modes. In exchange, verification ends with the person signed in, on your own screen, with your own design.

<Tip>
One page handling four `type` values is less work than four pages. The dispatch is a single conditional, and you get consistent error handling for free.
</Tip>

### Migrating between them

Moving from setup B to setup C needs no data migration. Set `site_url`, and the next message sent goes to your application. Outstanding links built under the old setting still point at the hosted page and still work, because the token is the token.

<Warning>
The reverse is not true in one direction. Links already sent to your application's `/auth/callback` do not change, because they are absolute. After clearing `site_url`, any link you already sent is still pointing at your page — and that page must still exist, or those people see nothing at all. Leave the page in place for at least the longest token lifetime, 24 hours.
</Warning>
