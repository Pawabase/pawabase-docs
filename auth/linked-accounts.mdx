A Pawabase account can have several **identities**: its password, plus any number of social or company logins (Google, GitHub, Apple, a customer's SAML or OIDC login). Each identity is a provider and the provider's id for the person. Signing in with any of them lands in the **same account**, with the same user id, roles and data.

Identities are attached in two ways: **automatically**, when someone signs in with a provider whose verified email matches their account, and **on request**, when a signed-in person connects a provider from your account page.

## Automatic linking on sign-in

When someone completes a social or company sign-in, Pawabase looks for an account in this order:

1. **An account that already has this identity** (same provider, same provider id): they're signed in to it.
2. **An account with the same email address**, but only if the provider says the address is **verified** (or the company login is set to trust its emails): the identity is attached to that account, and they're signed in to it.
3. **Neither**: a new account is created (when sign-ups are allowed, or through an organization's company login).

The verified-email condition is what makes automatic linking safe. Without it, someone could create a provider account with your address, unverified, and sign in to your Pawabase account with it. When the provider's address **isn't verified** and an account with that address already exists, the sign-in is refused with `#error=email_unverified_conflict` on the return address: the person should sign in another way and link the provider from their account page.

## Linking on request

From a signed-in person's account page, start a link. They go to the provider and come back with the identity attached:

<CodeGroup>
```typescript TypeScript
const url = await pawabase.auth.linkIdentityUrl("github", { redirectTo: "https://app.example.com/settings/sign-in" });
window.location.assign(url);

// Back on /settings/sign-in:
const result = await pawabase.auth.getSessionFromUrl();
if (result.status === "linked") show(`${result.provider} is now connected`);
else if (result.status === "error") show(result.error);   // e.g. identity_already_linked
```

```python Python
url = pb.auth.link_identity_url("github", redirect_to="https://app.example.com/settings/sign-in")
# send the person's browser to `url`
```
</CodeGroup>

- The provider must be switched on in **Users & auth → Sign-in → Social providers** ([Social sign-in](/auth/social-sign-in)), and the return address allowed ([Redirect URLs](/auth/redirect-urls)).
- Linking ignores the email: a GitHub account with a different address can be linked, because the person proved they own both by being signed in here and at GitHub.
- If that provider identity already belongs to **another** account, the link is refused with `#error=identity_already_linked`. One provider identity can belong to only one account.

## List and unlink

<CodeGroup>
```typescript TypeScript
const user = await pawabase.auth.getUser();
for (const identity of user.identities) {
  console.log(identity.id, identity.provider, identity.email);
}

await pawabase.auth.unlinkIdentity(identityId);
```

```python Python
user = pb.auth.get_user()
for identity in user["identities"]:
    print(identity["id"], identity["provider"], identity["email"])

pb.auth.unlink_identity(identity_id)
```
</CodeGroup>

Pass the identity's `id` exactly as you received it.

### You can't remove the last way in

Unlinking is refused with `409` "set a password before removing your only sign-in method" when it would leave the person with **no password and no other identity**. Build your account page to match: disable **Disconnect** on the only identity of a person without a password, and offer **Set a password** first (see [User profile](/auth/user-profile)).

A person whose only identity is removed can still get in with an [email code](/auth/email-codes) or a [sign-in link](/auth/sign-in-links) if those are enabled, because those prove ownership of the email rather than of a provider account.

```tsx
function SignInMethods({ user, hasPassword }: { user: User; hasPassword: boolean }) {
  const onlyWayIn = !hasPassword && user.identities.length === 1;
  return (
    <ul>
      {user.identities.map((identity) => (
        <li key={identity.id}>
          {identity.provider} · {identity.email}
          <button disabled={onlyWayIn} onClick={() => pawabase.auth.unlinkIdentity(identity.id)}>
            Disconnect
          </button>
        </li>
      ))}
    </ul>
  );
}
```

## In Studio

**People → Users** shows each person's ways in, in the **Sign-in** column (`password`, `google`, `github`…), and their page lists them under **Linked accounts**. Studio shows them; the person links and unlinks them from your app.

## Events

`identity.linked` (with `user_id` and `provider`) when an identity is attached, on request or automatically, and `identity.unlinked` when one is removed. Subscribe flows or [auth webhooks](/auth/auth-webhooks) to them, for example to email the person "GitHub was connected to your account", which helps them notice a link they didn't make.

## Duplicate accounts

If someone ended up with two accounts (signed up with a password at one address, and later with a provider using another address), linking can't merge them; each provider identity belongs to one account. To merge:

1. Decide which account to keep.
2. Take a [backup](/backups/overview).
3. Move their records to the kept account's user id (owner fields, organization memberships), from a script with a secret key or in the [SQL editor](/database/sql-editor).
4. Delete the other account in [Users](/auth/users).
5. Have them link the second provider to the kept account from your account page.
