A **guest** is a real account that doesn't have the person's email or password yet. It has a user id, a session and its own data, so someone can try your app, fill a cart or save a draft right away, and you ask them to create an account only when they have a reason to. When they do, the guest **becomes** that account: same user id, so everything they made stays theirs.

## Turn it on

**Users & auth → Sign-in → Sign-in & registration → Ways to sign in → Guest sign-in.** When it's off, starting a guest session answers `403` "guest sign-in is disabled".

## What a guest is, exactly

| | Guest | Full account |
| --- | --- | --- |
| User id, session, tokens | Yes | Yes |
| Email | A reserved placeholder: `guest-…@guest.invalid` (it can never receive mail) | The person's address |
| Password | None | Optional |
| Marked as a guest | `app_metadata.anonymous: true`, and `is_anonymous: true` on the user | No |
| [Default roles](/auth/sign-up-restrictions) | **Not** given | Given at sign-up |
| [Domain restrictions](/auth/sign-up-restrictions) | Not applied (there's no real address to judge) | Applied |
| Counts toward your plan's user limit | Yes | Yes |

Because a guest has a placeholder email, **don't** test `!user.email` to find guests. Use `is_anonymous`.

## Start a guest session

<CodeGroup>
```typescript TypeScript
const session = await pawabase.auth.signInAnonymously();
session.user.id;              // a real user id: use it as the owner of what they create
session.user.is_anonymous;    // true
```

```python Python
session = pb.auth.sign_in_anonymously()
```
</CodeGroup>

The session is stored and refreshed like any other, so reloading the page keeps the same guest. Starting guests is rate-limited per address and can be protected with [bot protection](/auth/bot-protection).

**Create the guest when the person first does something worth keeping**, not on page load. Otherwise every visitor who leaves after a second becomes a user, filling your user list and your plan's user count.

## Upgrade to a full account

When the guest decides to keep their work, give the **same** account an email (and optionally a password):

<CodeGroup>
```typescript TypeScript
const { user, verification_sent } = await pawabase.auth.upgradeAnonymous({
  email: "ada@example.com",
  password: "a long passphrase",          // optional: without it they sign in with links or codes
  name: "Ada",
  redirectTo: `${location.origin}/auth/callback`,
});
```

```python Python
result = pb.auth.upgrade_anonymous(email="ada@example.com", password="a long passphrase", name="Ada")
```
</CodeGroup>

What happens:

1. The account gets the email, name and password; the `anonymous` mark is removed. Its user id doesn't change, so every record the guest owned is now Ada's.
2. The address is set as **unverified**, and a **Confirm your email** message is sent to it (always, `verification_sent: true`), with your `redirectTo` ([Redirect URLs and email links](/auth/redirect-urls)).
3. The `user.upgraded` event fires (with `user_id` and `email`).
4. The current session continues. Their token still says "guest" until it's renewed; call `pawabase.auth.refreshSession()` after upgrading if your screens read `is_anonymous` from the session.

Refusals:

| Status | When |
| --- | --- |
| `409` "this is already a full account" | The person isn't a guest |
| `409` "an account with this email already exists" | The address belongs to someone else: they should sign in to that account instead |
| `403` | The address's domain is refused by your [restrictions](/auth/sign-up-restrictions) |
| `422` | The password breaks the [password policy](/auth/password-policy) |

<Warning>
Don't call `signUp` for a guest. It creates a **different** user, and everything the guest made stays with the old guest id.
</Warning>

### When the email already has an account

A returning customer browses as a guest, adds to a cart, then tries to "create an account" with an address they already use: `409`. Ask them to sign in instead, then move what the guest made to their account from your server (update the owner field on the guest's records to the signed-in user's id with a secret key) before the guest is cleaned up.

## Telling guests apart

**In your app**, to decide what to show:

<CodeGroup>
```typescript TypeScript
const user = await pawabase.auth.getUser();
if (user.is_anonymous) showBanner("Save your progress: create an account");
```

```python Python
user = pb.auth.get_user()
if user.get("is_anonymous"):
    show_banner("Save your progress")
```
</CodeGroup>

**In access rules**, guests are signed-in users: every rule that allows signed-in users allows guests. To keep something for full accounts only (inviting others, exporting, paying), add a condition that the caller isn't a guest:

```json
{ "all": [ { "authenticated": true }, { "not": { "truthy": "$auth.claims.app.anonymous" } } ] }
```

`$auth.claims.app` is the person's private metadata as carried in their token, and only your server or Studio can change it, so a guest can't remove the mark themselves. Save it as a [named rule](/policies/named-rules) such as `full_account` and use it where needed.

## Clean-up

Guests are deleted automatically, with their sessions, **30 days after their last sign-in**. A guest signs in once, when the guest session starts; keeping the session alive by refreshing it doesn't count as a new sign-in. In practice: **a guest is deleted about 30 days after it was started, even if it's still being used**. Upgraded accounts are never touched.

Plan your app around it: prompt guests to create an account well before a month passes (for example when they come back after a few days, or when what they've made becomes valuable), and don't promise guests that their work is kept indefinitely. The 30 days is an installation setting, not something you change per environment.

Records your tables hold for a deleted guest aren't deleted with them: they keep the old user id as their owner, and nobody can reach them through owner rules any more. If guests create a lot, clean those rows up on a [schedule](/automation/schedules), or use a relation that removes them.

## A cart that survives sign-up

1. The visitor adds the first item: call `signInAnonymously()`, then create `cart_items` (with an owner field, so each item belongs to the guest).
2. They keep shopping across reloads: the stored session keeps the same guest.
3. At checkout they enter an email: call `upgradeAnonymous({ email })`.
4. The cart still belongs to the same user id. Nothing to migrate; the confirmation email follows.
