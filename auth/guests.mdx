A **guest** is a real user with no email or password yet. They get an id, a session and their own data. Use guests to let people try the app, fill a cart or save a draft, and ask them to create an account only when they have a reason to.

## In Studio

**Users & auth → Sign-in → Sign-in & registration → Ways to sign in → Guest sign-in.** *Let someone start with no details and become a real account later. A guest nobody has used for 30 days is removed.*

## Start a guest session

<CodeGroup>
```typescript TypeScript
const session = await pawabase.auth.signInAnonymously();
session.user.id;
```

```python Python
session = pb.auth.sign_in_anonymously()
```
</CodeGroup>

Create the guest when the person first does something worth saving, not when the page loads, so visitors who leave immediately don't create thousands of empty users. Guest creation is rate limited per address.

The session is stored like any other: reloading the page keeps the same guest.

## Upgrade to an account

When they sign up, attach the email to the **same** user. Everything the guest created stays theirs.

<CodeGroup>
```typescript TypeScript
const { user, verification_sent } = await pawabase.auth.upgradeAnonymous({
  email: "ada@example.com",
  password: "a long passphrase",
  name: "Ada",
  redirectTo: "https://myapp.com/welcome",
});
```

```python Python
result = pb.auth.upgrade_anonymous(email="ada@example.com", password="a long passphrase", name="Ada")
```
</CodeGroup>

If emails must be verified, a link is sent (`verification_sent`) and the upgrade is complete once they click it. The `user.upgraded` auth webhook event fires.

<Warning>
Do not call `signUp` for a guest. It creates a different user, and the guest's records stay with the old one.
</Warning>

## Know if someone is a guest

A guest has no email. Use that to decide what to show:

```typescript
const user = await pawabase.auth.getUser();
const isGuest = !user.email;
```

Show "Save your progress: create an account" while `isGuest` is true.

## Limit what guests can do

Guests are real users, so they can do everything a signed-in user can unless your [access rules](/policies/overview) say otherwise. For sensitive actions (inviting others, exporting data, paying) require a confirmed email in the rule: *$auth.email is set*.

## Clean-up

A guest unused for 30 days is removed automatically, together with their sessions. Anything you stored against their id should tolerate that, or be tied to the upgraded account first.

## A cart that survives sign-up

1. Visitor adds an item: call `signInAnonymously()` once, then write `cart_items` with `owner_id = user.id`.
2. Visitor checks out: call `upgradeAnonymous({ email, password })`.
3. The cart records still belong to the same id. No migration.
