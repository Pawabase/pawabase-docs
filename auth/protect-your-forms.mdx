Contact forms, newsletter sign-ups, waitlists, comments and checkouts attract scripts as much as sign-in does. The widget puts [bot protection](/auth/bot-protection) on any of them, whether or not the rest of your app runs on Pawabase.

## How it works

1. The page runs the widget. It solves a check in the background (Pawabase's own, or your provider's widget) and receives a **pass**.
2. The form sends the pass with everything else.
3. Your server asks Pawabase whether the pass is good, with a secret key, and refuses the form when it is not.

A pass works **once**, for **five minutes**, for the **form it was earned on**. It is issued only after Pawabase has seen the visitor's real address, so blocking, suspicion and your provider's verification all apply.

Forms are checked whether or not sign-in protection is switched on: a page that shows the widget wants it. The settings that apply are the ones in **Users & auth → Bot protection → Settings**: the provider, your sites, trusted addresses, suspicion and blocking. In *only when it looks like an attack* mode, a visitor who looks ordinary does almost no work (about a millisecond); an address that floods a form gets harder checks, then a block.

## 1. Add the widget to the page

One script tag, and an element where the form should show it:

```html
<script src="https://api.example.com/auth/v1/captcha/widget.js?apikey=pb_pk_…" async defer></script>

<form action="/contact" method="post">
  <input name="email" type="email" required>
  <textarea name="message"></textarea>
  <div class="pawabase-captcha" data-action="contact"></div>
  <button>Send</button>
</form>
```

Use your **publishable** key. The widget needs no build step, no framework and no cookies.

It shows a small "Verified" badge once done, and puts the pass in a hidden field named `pawabase-captcha-response`. If the form is sent before the pass is ready (or after it expired), the widget holds the submission, earns one, then sends the form itself.

`data-action` names the form. Use lowercase letters, digits, `_` and `-`, up to 32 characters: `contact`, `newsletter`, `checkout-2`. Each form's numbers appear separately in Studio, and a pass for one form is refused for another.

### Options

Set these as `data-` attributes on the element:

| Attribute | Values | Default |
| --- | --- | --- |
| `data-action` | Your form's name | `form` |
| `data-execution` | `render` (start at once), `interaction` (when the form is first touched), `submit` (when it is sent) | `render` |
| `data-size` | `normal`, `compact`, `invisible` (nothing shown) | `normal` |
| `data-theme` | `auto` (follows the device), `light`, `dark` | `auto` |
| `data-callback` | A global function called with the pass | |
| `data-expired-callback` | Called when a pass expires before the form was sent | |
| `data-error-callback` | Called with the error when a check cannot be passed | |
| `data-response-field-name` | The hidden field's name | `pawabase-captcha-response` |

On the script tag, `data-project` (or `&project=` in its address) names your project, and `data-environment` (or `&environment=`) picks an environment other than the project's default.

With `render`, the widget earns a fresh pass shortly before the old one expires, a few times, for someone still typing.

### From JavaScript

The script adds `window.pawabaseCaptcha`:

| Call | Does |
| --- | --- |
| `render(element, options)` | Draws a widget where you choose; returns its id. Options are the attributes above, in camelCase |
| `execute(id)` | Earns a pass now; resolves with it |
| `getResponse(id)` | The current pass, or `""` |
| `reset(id)` | Forgets the pass |
| `remove(id)` | Removes the widget |
| `solve(action)` | Earns a pass with no element, for a `fetch()` your page makes |

The element also fires `pawabase-captcha:verified`, `pawabase-captcha:expired` and `pawabase-captcha:error` events.

```html
<script>
  async function send(form) {
    const pass = await pawabaseCaptcha.solve("contact");
    await fetch("/api/contact", { method: "POST", body: JSON.stringify({ ...formData(form), captcha: pass }) });
  }
</script>
```

### With the SDK

In an app that already uses the SDK, earn a pass without the widget. The built-in check is solved for you; for a hosted provider, give `getToken` (see [Bot protection](/auth/bot-protection#with-the-sdk)).

<CodeGroup>
```typescript TypeScript
const { pass } = await pawabase.captcha.protect("contact");
await fetch("/api/contact", {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({ email, message, captcha: pass }),
});
```

```python Python
granted = pb.captcha.protect("contact")
httpx.post("https://example.com/api/contact", json={"email": email, "message": message, "captcha": granted["pass"]})
```
</CodeGroup>

## 2. Check the pass on your server

With a **secret** key. Never in the browser: a publishable key is refused.

<CodeGroup>
```typescript TypeScript
import { createClient } from "@pawabase/client";

const pawabase = createClient({ url: "https://api.example.com", project: "01JC4…", apiKey: process.env.PAWABASE_SECRET_KEY! });

export async function contact(request: Request) {
  const form = await request.formData();
  const result = await pawabase.captcha.verify(String(form.get("pawabase-captcha-response") ?? ""), {
    action: "contact",
    remoteip: request.headers.get("x-forwarded-for")?.split(",")[0],
  });
  if (!result.success) return new Response("Failed the security check", { status: 400 });
  // … handle the form
}
```

```python Python
import os
from pawabase import Pawabase

pb = Pawabase("https://api.example.com", os.environ["PAWABASE_SECRET_KEY"], project="01JC4…")

def contact(form, client_ip):
    result = pb.captcha.verify(form.get("pawabase-captcha-response", ""), action="contact", remoteip=client_ip)
    if not result["success"]:
        raise PermissionError("Failed the security check")
    # … handle the form
```
</CodeGroup>

`action` refuses a pass earned on another form. `remoteip` (the visitor's address) lowers the score of a pass presented from somewhere other than where it was earned.

### The answer

The answer has the same shape as Cloudflare Turnstile's and Google reCAPTCHA's, so code written for them reads it.

| Field | Holds |
| --- | --- |
| `success` | Whether the pass is good. Refuse the form when it is not |
| `error-codes` | Why not: `missing-input-response`, `invalid-input-response` (not a pass from this environment), `timeout-or-duplicate` (expired, or already used), `action-mismatch` |
| `action` | The form it was earned on |
| `hostname` | The site the page was on, when the browser said |
| `challenge_ts` | When it was earned |
| `score` | 0 (certainly automated) to 1 (certainly a person), from the suspicion seen when it was earned |
| `same_address` | Whether it came from `remoteip`; `null` when you gave none |
| `provider` | `pawabase`, `turnstile`, `hcaptcha`, `recaptcha`, or `trusted` for an address you listed as never checked |
| `unverified` | `true` when it was issued during a provider outage with *Let people through* |

For most forms, `success` is enough. For something costly (a free trial, a payment), also look at `score` and send low ones to review, or ask for more.

A pass is spent by the first check that accepts it. A check that refuses it for `action-mismatch` leaves it unspent.

## Use the widget on sign-in forms

The same widget works on your auth forms: name the action (`signup`, `signin`, `magic_link`, `email_code`, `recover`, `verify_resend` or `anonymous`) and send the pass as the `x-captcha-token` header, or as `captchaToken` / `captcha_token` in the SDK. Pawabase checks it directly; there is nothing to verify yourself.

<CodeGroup>
```typescript TypeScript
const pass = pawabaseCaptcha.getResponse(widgetId);
await pawabase.auth.signUp({ email, password, captchaToken: pass });
```

```python Python
pb.auth.sign_up(email=email, password=password, captcha_token=pass_)
```
</CodeGroup>

## Content-Security-Policy

The widget runs its work in Web Workers created from `blob:` addresses, on several cores. A policy without `worker-src blob:` refuses them; the widget then does the work on the page itself, in small slices, which is slower but still works.

To allow the widget, add your API's address to `script-src` and `connect-src`, and `blob:` to `worker-src`. A hosted provider also needs its own addresses (for example `https://challenges.cloudflare.com` for Turnstile in `script-src` and `frame-src`).

## Watching it

**Users & auth → Bot protection → Overview** lists your forms by name, with passes issued, failed checks and blocks. Blocked addresses and refusals are on **Activity**.
