Deployed functions run in the **functions runtime**: a pool of confined worker processes, Deno for TypeScript and Python for Python. The
runtime can be a **service of its own** (the `functions` container in `docker-compose.yml`, the default) or run **inside the server**
(a single-process installation).

```
client ─► gateway ─► server ──────────────────────────────► functions service ─► Deno / Python workers
                     key, firewall, policy, quotas,          pools, limits,           confined: no sockets,
                     metering, the invocation's grant        streaming, fetch()       only their own files
                          ▲                                       │
                          └─── ctx.runtime calls, run reports ◄───┘   (signed with the grant)
```

## Separate or embedded

| | Service (`PAWABASE_FUNCTIONS_RUNTIME_URL=http://functions:8100`) | Embedded (empty URL) |
| --- | --- | --- |
| Where workers run | the `functions` container | the server's container |
| Restart, scale, resource | on their own | with the server |
| What the runtime can reach | the server's internal listener, with a grant | everything the server can |
| When to use it | any real installation | one process, development, tests |

The code is the same in both. Only the transport changes.

## What the runtime is trusted with

The runtime service has **no database or Redis credentials and keeps no secrets**:

- The **server** decides whether an invocation may run (API key, the function's `auth` or policy, scopes, plan quotas, the project's
  concurrency limit). It then signs a **grant**: the environment, the branch, the function, the caller and the request id, valid for the
  function's timeout plus a margin.
- The runtime passes the grant back with each `ctx.runtime` call (`/internal/v1/functions/rpc/*` on the server's internal listener).
  The server acts exactly as the grant says. A runtime cannot act for another environment or caller, or after the invocation is over.
- A function's secrets reach its workers as environment variables. The service fetches them from the server when the workers start,
  and the server tells it on every request which version is current.
- Finished runs are reported to the server under their grant, and the server records them. A report cannot name another function or
  request.

Workers are confined by Landlock and seccomp (`PAWABASE_SANDBOX_CONFINEMENT`, `required` on Linux). They can read only their deployment,
its vendored modules, the kit and the system's libraries, and write only their own temporary folder. They cannot trace, signal or
namespace anything. In `guarded` network mode they cannot create sockets at all. On macOS (development) only the process boundary
applies, and the server says so at start-up.

<Warning>
Deployments must be on a real volume (`PAWABASE_DEPLOYMENTS_PATH`, `/data/deployments` in the images), not a bind mount from macOS.
Landlock cannot grant access to paths on such a mount, so a confined worker would find nothing to load. The runtime now refuses to
start such a worker and says why, instead of answering `FunctionMissing`.
</Warning>

## A request's life

1. The gateway resolves the key and applies the firewall, the key's rules, rate limits and the body-size limit.
2. The server finds the HTTP function (`functions/<name>/index.ts`) of the environment (and branch, `x-pawabase-branch`). It checks the
   method and the origin, authorises the caller, counts the invocation against the plan, takes a project execution slot and signs the
   grant.
3. The runtime picks a worker of that function with room (a request starts one if none has room: a **cold start**), streams the request
   in and waits for the response's head until the function's `timeout`.
4. The response streams back as it is produced. A caller that goes away, or a function that runs out of time, aborts the request
   (`ctx.signal`).
5. When the response is over and `waitUntil` work has settled, the run is recorded: method, path, status, duration, cold start, bytes,
   fetches, background time and logs.

## Workers

- **Per function.** Each HTTP function of each deployment has workers of its own, so one function's memory, crash or slow code does not
  touch another's. `fn()` functions share a deployment's workers, one call at a time each, as before.
- **Concurrent.** An HTTP function worker serves up to `config.concurrency` (else `PAWABASE_FUNCTIONS_WORKER_CONCURRENCY`, 32) requests
  at once. When all are full another starts, up to `PAWABASE_FUNCTIONS_MAX_WORKERS` (8). Beyond that a request waits
  `PAWABASE_FUNCTIONS_QUEUE_SECONDS` (10) for room, then gets `503 function_busy`.
- **Warm.** `config.warm` workers are kept running while idle. Others stop after `PAWABASE_SANDBOX_IDLE_SECONDS` (300).
- **Draining.** A new deployment or new secrets make the old workers drain: they take no new requests, finish what they have (including
  `waitUntil` work) and stop.
- **Crashes.** A worker that exits fails only its own in-flight requests (`502 function_crashed`, with the reason). The next request
  starts a fresh one.

## Resource limits

Every run of every function is held to its **project's** limits, so one project cannot starve another on a shared installation. They
are project limits like the request quotas, set when the project is created and changed by the operator, never from Studio or code:

```bash
pawabase-server project limits set my-project --max-function-memory-mb 256 --max-function-cpu-seconds 10
```

| Project limit | Holds | Enforced by |
| --- | --- | --- |
| `max_function_timeout_seconds` | wall-clock time per run (a function may ask for less) | the server and the runtime |
| `max_function_memory_mb` | memory a worker may hold (Deno also gets it as its heap) | the watchdog, from `/proc` |
| `max_function_cpu_seconds` | CPU per `fn()` run; for HTTP functions, the longest computation without yielding | the watchdog (`fn()`), the worker's heartbeat (HTTP) |
| `max_concurrent_runs_per_function` | runs of one function at once per environment | the server |
| `max_function_body_mb` | request body of an HTTP function | the server, before the function runs |
| `max_function_workers` | workers per HTTP function | the runtime's pool |

A project that sets none of them gets the installation's defaults. No project may go above the installation's maximums
(`PAWABASE_FUNCTION_MAX_MEMORY_MB`, `PAWABASE_FUNCTION_MAX_CPU_SECONDS`, `PAWABASE_FUNCTIONS_MAX_TIMEOUT_SECONDS`,
`PAWABASE_FUNCTIONS_MAX_BODY_MB`, `PAWABASE_FUNCTIONS_MAX_WORKERS`). CPU and memory are read from `/proc`, so they are enforced on Linux
only. Each run records the limits it had, the CPU time and peak memory it used, and the limit that stopped it.

The project-wide `max_function_concurrency` (all functions of a project at once) and `max_function_invocations_per_month` still apply on
top.

## Network

`PAWABASE_FUNCTIONS_NETWORK` decides how a function reaches the network:

`guarded` (default)
: Workers have no sockets. `fetch()` is made by the runtime through the outbound guard: no private or reserved addresses, the address
  checked is the one connected to (no DNS rebinding), redirects re-checked hop by hop, credentials dropped across origins, and a limit
  on requests and bytes per invocation.

`direct`
: Workers may open their own connections (raw TCP database drivers, SMTP libraries). The filesystem, syscall and signal confinement
  still apply, but the outbound guard does not. Use it only for code you trust with your network.

## Imports

TypeScript deployments' `npm:`, `jsr:` and URL imports are fetched when the deployment is activated, into
`<deployments>/.deno/<digest>/`, and workers run `--cached-only`. Fetching needs network from the **server** at deploy time, and
follows `PAWABASE_FUNCTION_INSTALL` unless `PAWABASE_FUNCTION_VENDOR` says otherwise. Point `PAWABASE_FUNCTION_NPM_REGISTRY` at a mirror if
you have one.

## Settings

| Setting | Default | |
| --- | --- | --- |
| `PAWABASE_FUNCTIONS_RUNTIME_URL` | `http://functions:8100` in compose, empty otherwise | where the server sends invocations; empty runs them in the server |
| `PAWABASE_FUNCTIONS_API_URL` | `http://pawabase:8001` in compose | how the service reaches the server's internal listener |
| `PAWABASE_FUNCTIONS_RUNTIME_HOST` / `_PORT` | `0.0.0.0` / `8100` in its container | where the service listens (internal network only) |
| `PAWABASE_FUNCTIONS_NETWORK` | `guarded` | `guarded` or `direct` |
| `PAWABASE_FUNCTIONS_WORKER_CONCURRENCY` | `32` | requests per HTTP function worker |
| `PAWABASE_FUNCTIONS_MAX_WORKERS` | `8` | workers per HTTP function |
| `PAWABASE_FUNCTIONS_QUEUE_SECONDS` | `10` | how long a request waits for room |
| `PAWABASE_FUNCTIONS_MAX_TIMEOUT_SECONDS` | `400` | the most a function's `timeout` may be |
| `PAWABASE_FUNCTIONS_BACKGROUND_SECONDS` | `300` | how long `waitUntil` work may run after the response |
| `PAWABASE_FUNCTION_DEFAULT_MEMORY_MB` / `_MAX_MEMORY_MB` | `512` / `2048` | memory per run when the project sets none / the most any project may set |
| `PAWABASE_FUNCTION_DEFAULT_CPU_SECONDS` / `_MAX_CPU_SECONDS` | `0` (the timeout) / `300` | CPU per run |
| `PAWABASE_FUNCTION_DEFAULT_TIMEOUT_SECONDS` | `30` | timeout of an `fn()` run when the project sets none (HTTP: 150) |
| `PAWABASE_FUNCTIONS_MAX_BODY_MB` | `50` | the largest request body any project may allow |
| `PAWABASE_FUNCTIONS_FETCH_LIMIT` / `_FETCH_MAX_BYTES` | `200` / 64 MB | outbound requests and bytes per invocation |
| `PAWABASE_FUNCTION_VENDOR` | follows `PAWABASE_FUNCTION_INSTALL` | fetch remote imports at deploy |
| `PAWABASE_FUNCTION_NPM_REGISTRY` | npm | a registry mirror for vendoring |
| `PAWABASE_SANDBOX_CONFINEMENT` | `auto` (`required` on Linux) | `required`, `auto` or `off` |
| `PAWABASE_SANDBOX_IDLE_SECONDS` | `300` | how long an idle worker is kept |

Both containers must share `PAWABASE_INTERNAL_SECRET` (service tokens and grants are signed with it) and the deployments volume.

## Watching it

`GET /platform/v1/envs/<env>/functions-runtime` (and Studio's **Performance** tab on an HTTP function) shows where functions run, the
limits, and each worker: what it is serving, its heap, and whether it is draining. For each function it also shows requests, errors,
cold starts and their duration, rejections, timeouts and latency percentiles. `POST …/functions-runtime/restart` drains workers. The
service's own `/health` answers without a token for container health checks.
