Everything in an environment is one of two things:

- **Definitions** describe the backend: a table and its fields, an access rule, a flow, a bucket, a mail template, a schedule. You (or your team, or your CI) write them.
- **Data** is what the backend holds while people use it: records in tables, users and their sessions, uploaded files, flow runs, events, logs. Your users and your system create it.

The split matters because the two are handled differently everywhere: by Studio, by promotion, by blueprints, by backups and by infrastructure as code.

## What counts as a definition

| Definition | In Studio | In the API (`/platform/v1/envs/{env}/…`) |
| --- | --- | --- |
| Tables and their API | **Develop → Data** | `resources` |
| Reusable shapes | **Develop → Data → Tools → Schemas** | `schemas` |
| Named access rules | **Security → Policies** | `policies` |
| Sign-in settings, roles and permissions | **Security → Users & auth** | `auth` and role endpoints |
| Flows | **Build → Flows** | `flows` |
| Custom routes | **Build → Routes** | `routes` |
| Schedules | **Build → Schedules** | `schedules` |
| Event subscriptions | **Build → Events** | `subscriptions` |
| Outgoing webhooks and incoming hooks | **Build → Webhooks** | `webhooks`, `inbound-hooks` |
| Mail templates | **Services → Mail** | `mail-templates` |
| Buckets | **Services → Storage** | `buckets` |
| Realtime channel rules | **Services → Realtime** | `realtime-channels` |
| AI agents, knowledge bases, connected apps | **Services → AI** | `agents`, `knowledge-bases`, `connections` |

Studio is an editor over these definitions. Saving in Studio, deploying with infrastructure as code, installing a blueprint and calling the Management API all write the same thing: a definition built in one way looks identical to one built in another.

## Definitions are checked before they're stored

When a definition is saved, Pawabase validates it **completely** before accepting it: a rule that doesn't parse, a flow that names a block that doesn't exist, a template with a syntax error, a cron expression that can't run, a relation to a missing table. The save is refused with `422` and a message saying what's wrong. A definition that was accepted is one the runtime can execute, so problems show up when you save, not when a user hits them at 3 a.m.

## Saving a table changes the database

Most definitions take effect the moment they're saved. **Tables** also have a database side: the definition says what the table should look like, and the database has to be changed to match. Pawabase never does that silently:

- **Creating a table** creates it in the database straight away.
- **Changing a table** produces a **plan**: the list of statements needed to make the database match. Safe changes (a new optional column, a new index) are selected for you; changes that rewrite values or can lose data (a type change, a removal) are marked and need you to confirm by typing. Nothing runs until you **Apply**.
- A change that can't apply to existing rows (a new **required** column with no default on a table that has rows) is refused until you give it a default or fill the column first.
- Applied changes are recorded and can be **rolled back**; values a change would have lost are kept beside the column until you purge them.

Each table's **History** shows what was applied and what's pending. See [Migrations and history](/database/migrations-and-history).

## How each tool treats definitions and data

| | Definitions | Data |
| --- | --- | --- |
| **Studio** | Edited in place | Browsed and edited in the table editor, file browser, user list |
| **Promote** (environment → environment) | Copied, with a review | Never moved |
| **API versions** (`/rest/v1`, `/rest/v2`) | Frozen per version, so v1 clients keep working while v2 changes | Shared: both versions read the same tables |
| **Blueprints** | The whole set, in one zip | Optional sample rows only; never users, sessions, keys or secret values |
| **Infrastructure as code** | Written in code, planned and deployed | Not touched |
| **Backups** | Included (the *Definitions* part) | Included: table rows, and users with password hashes. **Not** stored files, sessions, logs, API keys or secret values |
| **Management API** | Read and written | Records through the data API; users through admin endpoints |

Three practical consequences:

1. **Promoting never empties or overwrites production data.** A new table arrives empty in production; existing tables keep their rows.
2. **A blueprint is safe to share.** It carries shape and optional sample rows, never your users or credentials. Provider keys and secret values become `${VARIABLES}` the installer fills in.
3. **Files need their own backup plan.** Environment backups hold table rows but not the objects in buckets; keep a copy of your storage separately if you can't recreate files.

## Secrets and credentials

Secrets (provider keys, signing secrets, passwords for outside services) are neither ordinary definitions nor ordinary data:

- They're stored encrypted per environment and **never returned** by the API: Studio shows names, versions and rotation dates, not values.
- Definitions refer to them by name (`secret://STRIPE_KEY`, `{{ secrets.STRIPE_KEY }}` in a flow), so the definition can be promoted while each environment keeps its own value.
- They're left out of blueprints and backups, so moving a definition never moves a credential.

See [Secrets](/secrets/overview).

## Choosing how to manage definitions

| You want | Use |
| --- | --- |
| To explore, prototype, or change one thing quickly | **Studio** |
| A reviewed path from development to production | **Promote** |
| Definitions in Git, reviewed in pull requests, deployed by CI | **[Infrastructure as code](/iac/overview)** |
| A starter or template other people install | **[Blueprints](/developers/blueprints)** |
| Your own tooling (a script, an IDE, an AI builder) to manage a project | **[Management client](/developers/management-client)** or the **[Integrations](/integrations/overview)** Management API |

These mix well. A common set-up: build in Studio in `development`, keep the result in code with infrastructure as code, deploy to `staging` and `production` from CI, and keep secrets in Studio per environment.
