The word **organization** refers to two different product concepts, and only one exists in a normal self-hosted Pawabase installation.

| Concept | Where it exists | What it owns |
| --- | --- | --- |
| Pawabase Cloud organization | Pawabase Cloud dashboard | Cloud projects, billing, and the people who manage them |
| Application organization | Authentication inside a Pawabase environment | Your application's users, memberships, teams, and invitations |
| Self-hosted platform organization | Nowhere | Base Pawabase does not have this layer |

<Warning>
A normal Pawabase installation does not ask you to create an organization or team before opening
Studio. It also does not use organizations to own Pawabase projects. Those dashboard concepts
belong to Pawabase Cloud.
</Warning>

## Base Pawabase opens one backend directly

One self-hosted Pawabase installation is one project. Opening Studio takes you directly to that runtime's default environment. There is no organization switcher, project picker, platform membership list, or **Team** page in base Studio.

\`\`\`text
self-hosted Pawabase installation
└── one backend runtime
    ├── development environment
    ├── optional staging environment
    └── optional production environment
\`\`\`

The optional Studio username and password protect access to this one runtime. They are deployment credentials, not organization memberships or operator roles.

| Base Studio concept | Available |
| --- | --- |
| Environment switcher | Yes |
| **Environments** page | Yes |
| **Audit log** | Yes |
| Organization switcher | No |
| Platform **Team** page | No |
| Multiple project picker | No |
| Per-operator organization roles | No |

If several people administer a self-hosted installation, protect Studio at the deployment boundary and use infrastructure access controls appropriate to your team. Do not expect Cloud's organization membership model to appear inside base Studio.

## Pawabase Cloud organizations own Cloud projects

Pawabase Cloud adds the account and billing layer around Pawabase installations. A Cloud customer signs in to the Cloud dashboard, creates or joins an organization, manages its team, and creates projects. Each Cloud project is a separate Pawabase installation.

\`\`\`text
Pawabase Cloud organization
├── team members and invitations
├── plan and billing
├── Cloud project A → Pawabase installation A
└── Cloud project B → Pawabase installation B
\`\`\`

The Cloud dashboard contains **Organizations**, **Team**, **Projects**, **Billing**, **Activity**, and **Settings**. Those labels belong to the Cloud dashboard, not to the Studio running inside each project.

Cloud organization roles are:

| Role | Cloud workspace meaning |
| --- | --- |
| viewer | Read organization and project information |
| member | Create and use projects |
| admin | Manage the team, billing, and project settings |
| owner | Full organization control, including ownership-sensitive actions |

Cloud owners and admins can use **Open Studio** for a project. Cloud verifies their organization role and opens that project's Studio through a short-lived access link. Studio itself still manages one Pawabase runtime; the surrounding Cloud dashboard supplies the multi-organization and multi-project experience.

<Info>
When this documentation says **Cloud organization**, it means the Pawabase Cloud workspace. When it
says **application organization**, it means a tenant or workspace your own application exposes to
its users.
</Info>

## Application organizations are part of authentication

Base Pawabase does support organizations and teams for applications you build. These are end-user identity features inside one environment. A SaaS product can use them to model customer companies, workspaces, departments, or other tenant groups.

Manage them under **Services → Users & auth → Organizations**. Applications use the public authentication API described in [Application organizations](/auth/organizations/overview).

\`\`\`text
Pawabase environment
└── application authentication
    ├── users
    ├── application organizations
    │   ├── memberships
    │   ├── teams
    │   └── invitations
    └── roles and permissions
\`\`\`

Application organizations do not own Pawabase installations, environments, resources, or Studio configuration. They belong to the application running inside one environment.

| Application concept | Meaning |
| --- | --- |
| Organization | A tenant or workspace in your product |
| Membership | A user's relationship to that organization |
| Team | A subgroup inside an application organization |
| Invitation | A request for an application user to join |
| Organization role | owner, admin, member, or viewer inside the application organization |
| Environment scope | Memberships and teams exist only in the environment where they were created |

## Choose the correct model

| Requirement | Use |
| --- | --- |
| Manage people who pay for and operate several hosted Pawabase projects | Pawabase Cloud organization |
| Create another hosted backend | Pawabase Cloud project |
| Separate development data from production data in one installation | Pawabase environments |
| Give application customers company workspaces | Application organizations |
| Divide one customer workspace into departments | Application teams |
| Let another administrator access self-hosted Studio | Deployment-level Studio protection and infrastructure access controls |

A frequent mistake is reading an application-organization example as instructions for administering Studio. Application memberships affect application sessions and policies. They do not grant access to Studio.

Another mistake is documenting Cloud dashboard behavior as if it were part of the open-source runtime. If a page tells a self-hosted reader to create an organization before they can create a backend, the page is describing Pawabase Cloud and must say so explicitly.

## Environment isolation still applies

Application users, organizations, teams, invitations, roles, and sessions are environment-specific. Creating a customer organization in development does not create it in production, and promoting definitions does not copy application identities.

That separation is intentional:

| Development | Production |
| --- | --- |
| Synthetic companies and test invitations | Real customer organizations |
| Test roles and memberships | Production role assignments |
| Disposable sessions | Real user sessions |
| Test provider credentials | Production provider credentials |

Use identity backup and restore only when you deliberately intend to move identity data. Do not treat definition promotion as an identity migration.
