description: "What vector fields need from the database, how Pawabase turns it on, and what to do when it is not there."

Vector fields use **pgvector**, a PostgreSQL extension. It is not part of stock PostgreSQL, and only a database administrator may create it, so it is set up where your data lives rather than from a table's settings.

## What happens for you

| Where your data is | What to do |
| --- | --- |
| **Pawabase Cloud** | Nothing, on planes whose data plane runs a pgvector image (new data planes do). Otherwise the table change is blocked with a clear message, as below. |
| **A self-hosted API plane with its own data plane** | Run the data plane's Postgres from an image that has pgvector, such as `pgvector/pgvector:pg16` (the deploy guide's data-plane compose file uses it). The plane's agent turns the extension on in each project's database when it creates or re-checks it. |
| **Your own Postgres** | Install pgvector, then run `CREATE EXTENSION vector;` once in the database as a superuser. |

When you save a table with a vector field, Pawabase checks. If the extension is missing, the change is **blocked with a plain message** ("Vector fields need the pgvector extension, and this database does not have it…") and nothing is changed.

## Checking a data plane

`agent check` on the API plane reports `vectors: true` or `false` for the data plane's database, so you find out before a customer does.

## Existing databases

pgvector's image is built on Debian; the stock `postgres:16-alpine` is built on Alpine. **Do not swap one image for the other under an existing data directory**: their text sorting differs, which can corrupt indexes. To move an existing data plane, dump it and restore it into a new one running the pgvector image.

## Search needs PostgreSQL

Vector search is a PostgreSQL feature. A project on another database can keep a vector field's data, but cannot search it, and says so.
