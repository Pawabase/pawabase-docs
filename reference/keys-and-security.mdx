Every client needs two things: your project's **API URL** and an **API key**. There are two kinds of key.

| | Publishable key | Secret key |
| --- | --- | --- |
| Starts with | `pb_pk_` | `pb_sk_` |
| Where it lives | Browsers, mobile apps, anywhere | A server you control |
| What it does | Identifies your project. Requests are limited by your access rules and the signed-in user | Bypasses every access rule and can manage users and settings |
| Safe to publish | Yes | **Never** |

## Rules of thumb

1. Put the **publishable** key in client code. It is meant to be seen.
2. Keep the **secret** key in an environment variable on a server. The browser build of the client refuses to start with one.
3. Never trust the browser for permissions. Your access rules run on the server for every request, whatever the client sends.
4. Do not store anything sensitive in `user_metadata`, since the user can edit it. Store permissions in `roles` or `app_metadata`, set from a server.

## Choosing a key on a server

| You are doing | Use |
| --- | --- |
| Admin work, jobs, imports, scripts | The secret key |
| Handling a request for one signed-in user | The publishable key with that user's access token, so rules apply to them |

See [Node.js](/quickstarts/node) for both patterns.

## Rotating a key

If a secret key may have leaked, create a new one in the dashboard under **API keys**, deploy it, and delete the old one. A publishable key can be rotated the same way if you want to; apps built with the old one will need rebuilding.

## Redirect addresses

Links in emails (confirmation, reset, invite) and social sign-in can only return to addresses you have listed under **Authentication → Redirect URLs**. List exactly your app's addresses, including `http://localhost:…` for development, and no wildcards you do not need.
